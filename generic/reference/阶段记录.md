# 阶段记录

## 适用场景

开工、每个 flow 出口写阶段记录，接续或修订时查上次停在哪，记录写错要改或删，`business_ui_stage` 写失败时读。阶段记录挂在制作工单上，给产品、流程负责人和开发观测看「这个应用做到哪一段、每段做完了什么、为什么进下一段、下一段打算怎么做」。它是记账动作，不是任何 flow 的进入条件，结单门也不检查它。

## 规则

### 什么时候写

| 时机 | 写什么 |
|---|---|
| 开工四步做完、定下第一个 flow 后（`SKILL.md` 第 4 节第 5 步） | 一条 `stage="kickoff"`，`next_stage` 填第一个要做的 flow |
| 每个 flow 出口满足后（含未通过要回退时） | 一条 `stage=<刚结束的 flow>`，**必须**和本地阶段标记在同一步写 |
| G7 交付报告 `insert` 之后、`task_manager(action="complete")` 之前 | 一条 `stage="G7"`、`next_stage="closeout"`；结单后工单只读，写不进 |

- 同一出口的先后：先更新本地阶段标记并写阶段记录，再发阶段评分（G1、G6）；G7 的阶段评分仍在交付报告发出之后，按 [../design/阶段评分.md](../design/阶段评分.md)。
- 每张工单自成一条链：第一条必须是 `kickoff`，之后每条的 `stage` 必须等于上一条的 `next_stage`。可以往回走（G6 未通过 → `next_stage="G4"`）。
- 记下本会话 `create` 返回的记录 `id`：只有这些记录允许按下文删除。

### 只留一种口径

阶段出口叙述（本段完成情况、出口是否满足、为什么进下一段、下一段计划、跳过与合并及理由）只写阶段记录，**禁止**再写成工单 checkpoint。工单 checkpoint 只记业务事实（资产 ID、版本、`run_id`、部署编号、确认原话）和结单门要的路线证据；G1「确认页已确认」与 G6 验收结论两条 checkpoint 照写。方案页 `status` 照常写进展。

### 每个字段怎么写

`completion`、`reason`、`next_plan` 用业务语言写给没看过对话的人，字数上限以工具 Schema 为准，超了会被拒、不会截断。

| 字段 | 写法 |
|---|---|
| `result` | 出口条件全满足 `passed`；没满足、要回退 `failed`；带遗留进下一段 `partial`，遗留写进 `open_issues` |
| `completion` | 做出了什么，出口条件逐项是否满足；kickoff 写开工四步的结果（工单、应用工程、脚手架版本） |
| `reason` | 为什么现在可以进下一段，如「开发者已确认确认页」「开发者说可以上线」；kickoff 写为什么从这个 flow 开始 |
| `next_plan` | 下一段准备做什么、预计产出；`next_stage="closeout"` 时可不写 |
| `open_issues` | 遗留问题、未验证项；没有就不传 |
| `evidence` | 只放 ID 与版本：资产 ID、`run_id`、`project_id`、版本号、`deployment_id`；**禁止**放凭据、链接参数或容器地址 |
| `business_ui_id` | 传应用家族 ID。G5 `setup` 之后的第一条（通常是 G5 出口）**必须**带；修订工单的开工记录直接带。之前没带的记录由平台自动补，不必回头 `update`；一张工单只对应一个应用 |

```text
business_ui_stage(action="create", task_id="wft_xxx", stage="G1", result="passed",
  completion="确认页已确认：一条回访路线、两张表、三个页面；出口两项均满足",
  reason="开发者回复「可以」确认了确认页", next_stage="G4",
  next_plan="新建回访总结能力和回访路线，冒泡一次",
  skipped=[{"stage": "G2", "reason": "不接外部数据和新能力，平台已有工具够用"},
           {"stage": "G3", "reason": "一条路线两张表，确认页已够施工"}])
```

### 跳过与合并

往前跳（`next_stage` 与 `stage` 之间隔了阶段）时，中间每个本工单还没有记录的阶段都**必须**写进 `skipped` 并带理由；合并也用跳过表达，理由写「并入 Gx 一起做」。返工后跳回已做过的阶段（如 G4 返工后再到 G6，G5 已有记录）不用再写理由。

### 接续与修订先 list

- 接续：先 `business_ui_stage(action="list", task_id=…)`，看汇总里的当前阶段和最新一条的计划，用一句业务话告诉开发者「上次做完 Gx，下一步 Gy，计划是…」，再按 [../tasks/接续.md](../tasks/接续.md) 接上。本会话第一条记录的 `stage` 就是最新一条的 `next_stage`。
- 修订或原工单已结单另开新工单：先 `business_ui_stage(action="list", business_ui_id=…)` 看这个应用上次停在哪、有什么遗留问题；新工单从 `kickoff` 起一条新链，开工记录带 `business_ui_id`，`next_stage` 填开始的 flow，前面没做的阶段写进 `skipped`。
- 写入成功但返回带 `chain_warning`：记录已存下，说明这个应用在别的工单上还有没写到结单的链。把 `open_tasks` 记进本段阶段文档，汇报时提一句，**禁止**去改、删那些工单的记录。

### 空链补记（阶段记录上线前已开工的工单）

`list(task_id)` 为空而本地已有 `passed` 的 flow 时，先补写 kickoff：`next_stage` 填当前要做的 flow，已做过的阶段写进 `skipped`，理由写「阶段记录上线前已完成，见工单 checkpoint」（本地有意跳过的 flow 写原来的跳过理由）；之后按正常出口记录。

### 补记漏写的出口

某个出口写失败，链会落后于实际进度。下一个出口写入前先 `list`，最新一条的 `next_stage` 不是你刚结束的 flow 时：那个阶段实际做过，就先补写它的记录（`completion` **必须**以「补记：」开头），等它返回成功后再写本出口（多条记录依次写，**禁止**同时发出）；没做过，就把本条的 `stage` 填成链上要求的阶段，`result` 按实际，`completion` 写清实际做了什么，中间缺的阶段写进 `skipped`。

### 改错与删除

- 文字写错或漏写：`update` 改 `completion`、`reason`、`next_plan`、`open_issues`、`evidence` 或 `skipped` 的理由，带 `edit_reason`。阶段值、结果和跳过了哪些阶段改不了。
- 下一阶段写错：`delete` 本工单最新一条（`reason` 写删除理由，至少 5 个字），再按删除后的最新一条重写。只能删最新一条，删除留痕。
- 删除限制：**禁止**删除不是本会话写入的记录，开发者明确要求删除的除外；`next_stage="closeout"` 的记录只在本会话 `task_manager(action="complete")` 被拒时才能删。

### 结单门被拒

本会话写的 G7 记录（下一阶段 closeout）已写，`complete` 被拒（如要求补路线证据）时：删掉这条 G7 记录（理由如「结单门被拒，回 G4 补跑路线」），再写一条 G7（`result="failed"`，`next_stage` 填要回去的 flow），补完后按出口正常写，最后重写 G7（`next_stage="closeout"`）再 `complete`。

### 写失败怎么办

写失败**禁止**停下制作，**禁止**反复重试；各错误码怎么改见 [报错对照.md](报错对照.md)「阶段记录」。

- 校验类错误（缺字段、超长、取值不对、缺跳过理由、应用不符）：按返回里的字段、`missing_stages` 纠正一次。
- `STAGE_CHAIN_CONFLICT` 与 `STAGE_CHAIN_MISMATCH`：都先 `list` 再决定，按上文补记规则纠正一次。
- 网络错误、超时、5xx：结果不明，先 `list` 一次看是否已写入，已写入就算完成。
- 工具不在当前工具列表里：不虚构，不改用工单 checkpoint 代写。
- 纠正一次仍失败、没写入、或工具不可用：把错误原文（工具返回的 `error` 文本原样复制，连同错误码）记进本段阶段文档（kickoff 记进第一个 flow 的阶段文档），继续下一个 flow。之后补记成功时，在阶段文档原错误下面**追加**补记结果（记录 `id`），**禁止**删改原来的错误原文。
- 一次失败只影响这一个出口。之后**每个**出口照常先 `list` 再写，按上文「补记漏写的出口」把漏的补上；**禁止**沿用上一次的失败结论（如「链已被关闭」「写不进」）跳过本出口的 `list` 与写入，链的状态以本次 `list` 为准。

## 常见错误

- 只写「进入 G4」，`completion`、`reason` 留空。
- 阶段记录写了，工单 checkpoint 又写一遍「G3 完成，进入 G4」或跳过说明。
- 把阶段记录当成进下一个 flow 的前提，写失败就停下等，或反复重试。
- 某个出口写失败后，后面的出口不再 `list`、不再写，到最后才一次补记；或阶段文档只写错误码、不写返回的错误原文。
- 遇到不是本会话写的 closeout 记录挡路，删掉它再写。
- 接续时不先 `list`，凭本地标记直接写，被链校验拒绝。
- `evidence` 里放 token、带签名的链接或容器地址。

## 相关工具与契约主题

`business_ui_stage(action=create / list / get / update / delete)`，字段与取值以工具 Schema 为准；`task_manager(action="get" / "complete")`。
