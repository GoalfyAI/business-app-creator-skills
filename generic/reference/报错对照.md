# 报错对照

## 适用场景

工具返回错误码、运行失败、部署或预览打不开、真跑被拒、结单或上线被拒，需要判断归属和处置时读；遇到平台问题要不要报、怎么报也读这里。先看返回里给的出口和提示，本表只补返回里没说清的部分。一个错误码只在一处写处置：脚手架版本类见 [脚手架与预置件.md](脚手架与预置件.md)，工具接入类见 [依赖与MCP接入.md](依赖与MCP接入.md)，协作者权限、提请属主上线、基线过期类见 [多人协作.md](多人协作.md)「协作相关报错」，其余都在本文件。

## 规则

### 通用原则

- 按返回的结构化错误改同一份对象再试；闸门拒绝时按返回给的出口处理，在原工单、原对象上改，字段只用工具定义里有的。
- 同一错误连续两次（`repeated_error_count>=2`）就换思路，不原样重跑。
- 余额不足、鉴权失败这类 `recoverable=False` 的错误，不重试，如实告诉开发者。
- 两类反馈分开走：制作过程中的平台或工具问题走 `submit_dev_feedback`；使用者对应用业务功能的反馈走 `business_ui_feedback`（见 [用户反馈.md](用户反馈.md)）。

### 平台问题怎么报

先按本文件处理；应用自己的脚本、页面、数据格式、提示词问题自己改，不提交。确实是平台问题时按阻塞程度报：

| 情况 | `blocking` | 什么时候提交 |
|---|---|---|
| 按指引处理后仍走不下去、没有可行绕法 | `blocked` | 立即提交，附报错原文和 `project_id` / `run_id` |
| 已绕过 | `worked_around` | 不即时提交，绕法记进开发记录；⑤ 上线或本次会话结束时和功能诉求汇总成一条 |
| 功能诉求（含开发者在卡点选择题里选了「等平台修」：该功能本次不做） | `request` | 同上，汇总成一条 |

- **`attribution`**（新建时必填）按事实选：平台行为与它自己的 Schema 或说明不符选 `platform_defect`；按设计如此但不够用选 `platform_limit`；Skill 写法与工具实际行为不一致选 `skill_mismatch`；本机或安装问题选 `environment`；查过仍判断不了选 `unknown`。
- **先查再建**：新建前先 `query_dev_feedback` 查本人未关闭的反馈，同一问题用已有记录查询或追加，不重复新建。追加不传新建专用的 `blocking` / `attribution` / `oa_task_ref`。
- **编号选择器**：回执里的 `code` 是平台反馈主编号，交付和报告优先写它；`source_code` 是稳定来源别名，兼容字段 `feedback_id` 等于 `source_code`，来源号另注、不称作主号。查询或追加用 `feedback_code="<code>"`（例如 `query_dev_feedback(feedback_code="FB-801")`、`submit_dev_feedback(feedback_code="FB-801", content="补充证据")`）；回执同时给了 `source_code` 时也可用 `source_code=…`，旧客户端用 `feedback_id=…`。三个选择器一次只传一个，编号按回执原样用。
- **结果要完整**：创建、重放、追加、详情和列表都要有同一条记录的真实 `id` / `code` / `source_code` / `feedback_id`；缺失或矛盾时不报成功。不存在或无权、映射缺字段、解析失败时停止这次追加，不换编号再试、不自动新建。
- **写入结果 `unknown`**（超时或坏回包，可能已收到）：先 `query_dev_feedback` 核对；服务恢复后用同一主体、制作工单、原正文和原参数重放，可以换成已核实的同一记录的主号或来源号，正文、工单和参数保持原样。列表有坏行或分页没取完时写「未取全」，不作全量结论。没有权威详情地址时不写链接。
- **提交成功只代表收到**：不等于问题已确认或已解决，不能据此放行验收。
- **对开发者怎么说**：平台问题挡住进度时，交接消息里写「卡在哪、谁在处理、对你的影响」，报错原文放进交付物的原始原因折叠里；修复由平台方做，不请开发者修，也不请开发者授权你改生产库、平台库或别人的数据（[../SKILL.md](../SKILL.md)「红线」）。

阻塞的平台问题没人修时按这个顺序升级：

1. 提交后先做不受它影响的部分，交接消息开头写「卡住了」。
2. 每次继续工作时用 `query_dev_feedback` 看处理进展；有回复按回复做。
3. 提交满 1 个工作日仍没有处理人回复，或回复了但给不出修复时间：给开发者发一道选择题，只问开发者能拍板的事。选项从这几种里挑能成立的：
   - 等平台修：写清这期间哪些功能做不了、预计影响哪一段；选了它，该功能本次不做，按 `request` 汇总；
   - 换做法绕开：写清和 PRD 比少了什么、多花多少（换做法会改「要什么」的，退回 ①）；
   - 这次先不做受影响的功能；
   - 请开发者把反馈编号转给平台负责人催办：选项里附上反馈编号和一句问题说明，不附报错原文。
4. 开发者选了以后照做，记进阶段文档。

### 工单闸门

**`SCENE_SKILL_UPGRADE_REQUIRED`** — Skill 版本过期，工单**未创建**。立即停止所有写操作，在本次会话内完成升级：从 `metadata.update.update_guides` 取所在宿主的升级文档，拉取后逐步照做；再搜索已安装的 SKILL.md（在宿主的插件安装目录里搜 `skill-version`），从 description 读出 `[skill-version:...]` 标记，原样填入 `skill_version` 重试。

合法版本串只来自升级后已安装的 SKILL.md（拒单响应、changelog、记忆里的都不能用）。搜不到已安装的 SKILL.md、或文件里没有标记，说明未安装或安装已损坏：取 `metadata.update.install_guides` 里所在宿主的安装文档重新安装后再读标记。升级成功并重试通过之后，提示开发者重启客户端让新 Skill 内容生效——重试只解除闸门，你上下文里的 Skill 内容仍是旧版。

**`SCENE_SKILL_VERSION_MISSING`** — 本次 create 没有填 `skill_version`（或填了 `dev`），工单**未创建**。这不代表 Skill 过期，不升级、不重装：按上一条的方法读出标记原样填入重试；重试后返回 `SCENE_SKILL_UPGRADE_REQUIRED` 才按上一条升级；搜不到 SKILL.md 或没有标记时按上一条重新安装。

**`SCENE_SKILL_UPGRADE_RECOMMENDED`** — 有新版本但不阻断，工单已正常创建，`task_id` 可直接使用。继续当前任务，交付时顺带提示开发者升级。

**`WORKFLOW_TASK_MODE_MISMATCH`** — 工单模式与动作不匹配，不是工单不存在或属于他人。按 `metadata` 里的 `actual_mode` 和 `required_mode` 纠正：只读工单要执行写操作时，新建 `mode="write"` 工单并传 `continued_from_task_id`，按 [../SKILL.md](../SKILL.md)「开工」带 `skill_version`。

### 编排与路线

| 现象 | 处理 |
|---|---|
| 工具或 action 不存在 | 回看当前工具定义，按实际 action 和字段改；工具确实不在列表里时如实告诉开发者该能力当前不可用 |
| 预览报字段、工具或路径错误 | 按报错精确修同一份草稿，再重跑预览 |
| `otpe_manage(verify)` 的 `static_contract` 失败 | 看 `errors[].where/msg`，多半是 `_output` 形状或事件契约；改脚本（[编排脚本.md](编排脚本.md)「建、校验和上线 TPE」） |
| `otpe_manage(verify)` 的 `toolsets_online` / `tpe_online` 失败 | `online_toolsets` / `otpe_manage(action="online")` 上线后反读 |
| 冒泡没到终态 | 服务端每次最多等约 45 秒；用同一 `run_id` 续等，不重新发起；修了脚本后重新冒泡取新证据 |
| 冒泡失败 | 看 `steps[].error`；同一错误连续两次（`repeated_error_count>=2`）换策略，不原样重跑；同类事实错误、引用错误或无产物连续两轮时，停止加字段，按 [编排脚本.md](编排脚本.md)「FA 与脚本的职责边界」重判职责 |
| 不确定 FA 用了哪个模型 | 回执顶层 `resolved_model` / `resolved_mode` 是这次验证运行（外层 SA）的模型和模式，不是 FA 的。FA 按资产配置运行：`required` 模式固定用该模型，`agent_selected` 模式用资产兜底模型，未配兜底用平台默认组；用 `get_asset(fast_agent)` 查 `model_selection_mode` 与 `model_name` |
| FA 失败或 `FA_STEP_BUDGET_EXCEEDED`，不知道它每一轮做了什么 | 先看 `manage_goalfymax_project` 的 `wait` / `status` 返回的 `fast_agent_failures` 和下一步提示；再用 `get_project_execution_logs(action="detail", log_type="fast_agents", project_id=…)` 看逐轮的工具、参数和截断标记（`args_truncated_by_repeat_guard`）。冒泡回执里的 `project_id` 在冒泡发起后 2 小时内可读 |
| 冒泡异常长跑或积分持续上涨 | 用 `scene_package_manage(action="cancel", task_id, run_id)`（单条冒泡用 `otpe_manage`）止损，冒泡项目只能这样停；回执 `cancelled` + `not_evaluated` 不算资产失败；按 `cancellation.stopped_nodes` 和 `steps[].error` 排查后重新冒泡 |
| `ORCH_NODE_FAILED` | 兜底错误码，按排查信息里的失败类别归因：`business_gate` 是脚本按规则主动停止，查业务条件与输入；`contract_error` / `script_bug` / `shell_exit` 归制作侧，修同一份脚本或契约；`tool_error` 看上游工具与 `recoverable` / `attempts`；`fa_error` 是 FA 预算或异常退出；`timeout` 先查最慢的一步。信息是「结果为空」且判失败与上一条工具返回只隔几十毫秒，多半是没等分段返回收齐 |
| `Workflow business event requires persisted Runtime identity` | 正式运行时是把带事件的 TPE 直接派发了：建单节点或多节点路线后从路线入口重跑；冒泡时是服务端没分配验证身份，报平台问题。Runtime ID 只用平台生成的 |
| `WORKFLOW_RUNTIME_IDENTITY_INCONSISTENT` | 三元身份部分缺失，是调用链内部错误，不是业务输入问题；核对入口是否完整传递服务端生成的身份 |
| 路线保存被拒 | 按返回的节点、字段、路径错误修同一个对象；节点只能读直接依赖的上游输出 |
| `WORKFLOW_FORM_PENDING` / `ORCH_INTERACTION_PENDING` | 项目里还有表单没答完，又在同一项目提交了入口表单。不是故障：让使用者回该项目答完，新业务新建项目；页面做法见 [前端页面.md](前端页面.md)「表单与文件」 |
| `WORKSPACE_PATH_UNTRUSTED` | 节点返回的文件路径没有可信来源。把要返回的文件实际写入或复制到 `ctx.output_dir` 再返回真实路径；不能只改路径字符串、虚构文件或删掉文件声明，见 [编排脚本.md](编排脚本.md)「文件产物」 |
| `ORCH_DELIVERY_FILE_UNISOLATED` | 声明为文件的交付不在最终节点产物目录；先复制进 `ctx.output_dir` 再返回 |
| `ORCH_DELIVERY_FILE_UNVERIFIED`，或交付出现「内部资料：文件名」、该交付的文件没成为附件 | 未声明为文件的 workspace 路径不会成为附件。有意保留的出处引用属正常；本来要交付的文件，逐项核对真实文件、最终节点目录、文件声明和交付映射（见 [业务路线.md](业务路线.md)「交付与审阅」） |
| 交付审阅提交后回 `rejected`，`field_errors` 为 `ORCH_DELIVERY_ACTION_INVALID` 或 `DELIVERY_REVIEW_REPLY_INVALID` | 审阅应答缺 `action_key`、夹带了业务数据，或动作不在本次声明内；项目会停在 waiting-input 等使用者重选，最长 2 小时。审阅只提交 `{ action_key }`；要改数据用中途表单或带表单的审阅动作；页面展示被拒原因 |
| 工具集关联成功但运行时加载不到 | 有工具集仍是离线；`online_toolsets` 后反读 |
| 需要使用者各自授权的工具调用失败 | 授权卡没配或没绑定 |
| 外部工具报参数格式错、路径不存在 | 回该工具的当前契约看文件参数收 URL、`/workspace` 路径还是内容本体；拿不准就取样一次 |
| `get_project_execution_logs(download)` 报不存在或受保护目录 | 不存在：先 `outputs` 看清单，节点产物在 `/workspace/task_agent/<taskpoint>/output/`；受保护目录（`input/`、`skills/`、`.env` 等）本来就不提供下载 |
| 资产详情字段为空 | 先看 `can_view_params`：`false` 是权限脱敏，不是空资产；告诉开发者后再决定 |

### 工程检查与开发工作集

| 现象 | 处理 |
|---|---|
| `npm run doctor` / `verify` 失败 | 先修第一条 `FAIL`；`GIT_ROOT_MISMATCH` 见 [开发者中心与工作区.md](开发者中心与工作区.md)「应用放在哪」 |
| 前端契约门禁报 packs 不一致 | 核对 `goalfy-app.json` 的 `packs` 与 `frontend/schema/packs/` 目录（[前端页面.md](前端页面.md)「场景包契约」「清起始件」） |
| `create_table` / `extract` 被拒 | 看返回的列与 diff；破坏性变更要带迁移脚本（[数据模板.md](数据模板.md)「改已上线的模板」）；带码的见「应用上线与数据模板」 |
| 开发工作集连接串过期 | `dataset_template_workspace(action="connect")` 重签（[数据模板.md](数据模板.md)「开发工作集」） |

### 版本与结单

| 现象 | 处理 |
|---|---|
| 版本闸门拒绝（如 `PERSONAL_VERSION_FINALIZE_REQUIRED`） | 内容修改撞了上线行：先取可编辑草稿；上线动作撞了未上线草稿：走上线。状态字段只由平台改 |
| `task_manager(insert)` 带 `format_warning`（检查点建议一条路线一条） | 记录已写入，但多条路线合在一条里；补成每条路线一条，各带自己的 `run_id` |
| `WORKFLOW_TASK_ROUTE_BUBBLE_EVIDENCE_REQUIRED` | 有路线没有对得上的运行证据：没跑、跑失败、`run_id` 属于别的路线、或证据早于最后一次路线修改。补一次路线冒泡或 `workspace` 真跑，或问过开发者后写豁免（写法见 [部署与版本.md](部署与版本.md)「三道门」）；在同一张工单上按返回逐条给的出口处理，不反复重试 |
| `has_ui: true` 但 `entry_url` 为空 | 部署后又派生了新草稿行，地址留在旧行；在当前草稿行重新部署并反读 |

### 部署与预览

| 错误码或现象 | 含义 | 处置 |
|---|---|---|
| 部署 `status` 失败 | 构建或启动失败 | 看返回里的构建日志尾部；本地先 `npm run verify:release` 复现，修好后重新部署 |
| 部署被脚手架闸门拒绝 | 脚手架低于必须线等 | 按 [脚手架与预置件.md](脚手架与预置件.md) 的错误码表处理 |
| `BUSINESS_UI_DEPLOYMENT_QUOTA_EXCEEDED` | 部署占用达到上限 | 把返回里的占用明细和每个释放选项的影响用业务话给开发者看，等开发者指明释放哪个、怎么释放；下线或删除由开发者决定，你不自己做，也不原样重试。开发者释放后用同样参数重新部署 |
| `BUSINESS_UI_CONTRACT_OUTDATED` | 挂载场景包的编排型 TPE 契约与部署时不一致 | 先看出现时机：应用草稿（testing）刚 deploy 成功、之后没有换挂也没有改场景包时出现，是平台对草稿的误报，不再重复 deploy，照常往下走（不拦上线；上线后草稿转正式会重新核对）。换挂或改了场景包之后出现，重新 deploy 一次吸收新契约；契约变化波及页面时先按 [../tasks/修订.md](../tasks/修订.md) 评估影响 |
| `BUSINESS_UI_WORKSPACE_BEHIND_TEMPLATE`（`deploy` 时） | 绑定到应用的工作集缺草稿钉定模板版本的表或列；`metadata.missing` 逐表点名，`metadata.data_uid` 是这个工作集 | 按 `metadata.next_action`：对 `data_uid` `connect` 取写连接，用幂等 DDL 在这个工作集上补齐缺的表和列（列注释带 `[editable:…]`），`inspect` 核对后重新 `deploy`。开发数据在这个工作集里，它保持绑定（见 [数据模板.md](数据模板.md)「改已上线的模板」） |
| `BUSINESS_UI_PREVIEW_DATA_UNBOUND`（`deploy` 时） | 开发工作集被解绑了 | 重新 `bind` 回原工作集再部署，应用的上线、下线状态保持不动（不为此上线派生草稿、下线或删除应用）；开发工作集一直绑定在应用上（见 [数据模板.md](数据模板.md)「开发工作集」） |
| `TEMPLATE_WORKSPACE_IN_USE_BY_DEPLOYMENT`（`close` 时） | 还有部署跑在这个工作集上，`metadata.holders` 点名 | 开发工作集本来就不 close；保持绑定，接着做原来的事（[数据模板.md](数据模板.md)「开发工作集」） |
| 报错带 `metadata.asset_state=draft`（文案以「草稿态」开头） | 发生在挂本人场景包草稿的部署、预览或上线联动上；`draft_asset_ids` 是涉及的草稿行 | 按原错误码处理，报平台问题时注明是草稿态 |
| 工作台「在线预览」报 `PREVIEW_NOT_READY`（请先完成应用上传和部署） | 当前草稿没有部署成功的记录，或部署后又派生了新草稿行；在线预览不需要上线 | 在当前草稿行重新 `ship` 到 `success` 再请开发者打开；`ship` 已成功仍报未就绪，才按平台问题报 |
| 开发者说在线预览只显示「Agentic APP 不存在或加载失败」（`code` 3024） | 当前草稿没部署成功，或开发者的账号无权访问这个应用；不表示应用被下线 | 先 `business_ui_manage(action="get")` 核对当前草稿有没有部署成功，没有就在当前草稿行重新 `ship` 到 `success` 再请他重开；`ship` 已成功仍打不开，才按平台问题报。应用的上线、下线状态保持不动 |

### 真跑

| 错误码或现象 | 含义 | 处置 |
|---|---|---|
| `BUSINESS_UI_NOT_ONLINE`（`manage_goalfymax_project(run)` 时） | 带 `business_ui_id` 真跑没传 `business_ui_data_space="workspace"`，按正式实例口径要求应用已上线 | 补传 `workspace` 重跑，读写开发工作集；不需要上线，不是平台问题 |
| `BUSINESS_UI_NOT_DEPLOYED`（`run` 带 `workspace` 时） | 还没有开发者本人部署成功的版本，或 `business_ui_id` 传成了版本行 ID | 先 `ship` 到 `success`，再用家族 ID 重跑 |
| `BUSINESS_UI_NOT_RELEASED`（`resolve`，或不传 `workspace` 的 `run` 时） | 上线了但从未发布；正式入口、使用者打开的和正式实例真跑用的都是已发布版本 | 制作和验收用在线预览和 `workspace` 真跑，不需要它；发不发布由开发者在发布管理页决定 |
| 真跑卡在 `waiting-input` | 中途表单或审阅在等回答 | 用 `reply` 回表单（见 [部署与版本.md](部署与版本.md)「真跑」）；没人答就是正常挂起 |
| 上线前 `resolve` 报「还没有上线版本」 | `resolve` 只认上线版本 | 上线前本来就这样，不是平台问题；草稿验收用 `workspace` 真跑和本机版 |
| 换了场景包或模板版本后真跑结果没变 | 这次跑的不是你要验证的版本，或改的是页面、后端代码（只换挂载会直接生效，改代码要重新部署） | 看返回的 `business_ui.version` 是不是要验证的版本；改了代码就重新部署后再真跑（见 [部署与版本.md](部署与版本.md)「真跑」） |

### 应用上线与数据模板

| 错误码 | 含义 | 处置 |
|---|---|---|
| `BUSINESS_UI_NO_BUNDLE` | 还没有源码包 | 回 ④：部署成功后再上线 |
| `BUSINESS_UI_NOT_DEPLOYED`（finalize 时） | 源码包没有成功构建部署 | 部署到 `success` 再上线 |
| finalize 只传 `business_ui_id` 被拒 | 家族里有多份草稿，平台不替你挑 | 按 [部署与版本.md](部署与版本.md)「上线」显式传 `draft_asset_id` |
| `TEMPLATE_WORKSPACE_EMPTY`（`extract` 时） | 工作集里没有业务表：零张表，或只有平台维护的系统表 `app_write_requests`（系统表不算） | 每个应用都要有数据模板和至少一张业务表。回 PRD「会记下来的东西」和开发者定下要存的表（只展示的应用也要存数据快照、收藏或查看记录等），`create_table` 建好再 `extract`；表都要有业务用途 |
| `TEMPLATE_BASELINE_REQUIRED`（`extract` 时） | 给已有模板出新版本没带 `expected_base_version` | `inspect` 读出模板当前 `template_version`，确认它就是这次改结构的起点后填进 `expected_base_version` 重调；仍在原模板上出新版本 |
| `TEMPLATE_BASELINE_CHANGED`（`extract` 时） | 从你开始改结构到抽取之间，别人已经抽出了更新的模板版本 | 重新 `inspect`，核对对方加的表列和你的改动都在工作集里（缺了先补，对方的结构保留），再用新的 `template_version` 作为 `expected_base_version` 重新 `extract` |
| `BUSINESS_UI_TEMPLATE_REQUIRED` | 带代码包的应用上线时没有挂数据模板 | 回 ③ 建表并 `extract` 出模板版本 → 按 [数据模板.md](数据模板.md)「建应用身份与挂模板」挂模板并绑工作集 → 重新部署（模板进指纹）→ 上线 |
| `BUSINESS_UI_TEMPLATE_SWITCHED` | 换绑到另一个模板家族（等于换库） | 不允许；需要新库就新建应用 |
| `BUSINESS_UI_TEMPLATE_UPGRADE_PATH_BROKEN` | 模板升级链缺迁移脚本 | 回 ③：破坏性变更的 `extract` 随带 `migration_script` |
| `BUSINESS_UI_TEMPLATE_REGRESSION` | 回滚钉回了更老的模板版本 | 没有降级：把旧结构重新抽成一个新版本再挂 |
| `BUSINESS_UI_UPGRADE_REHEARSAL_FAILED` | 迁移脚本在临时库彩排失败 | 按返回的错误修脚本，重新 `extract` |
| `BUSINESS_UI_RELEASED_CANNOT_OFFLINE` | 已发布到目录的应用不能直接下线 | 请开发者先在发布管理页取消发布（见 [部署与版本.md](部署与版本.md)「下线与删除」） |
| `CHANGE_NOTE_REQUIRED` | 建应用草稿没带变更说明 | 写清这次改了什么，带 `change_note` 重调 |

## 常见错误

- 看到 `ORCH_NODE_FAILED` 就判定是工具坏了。
- 被闸门拒绝后另开工单或改名重试。
- 把 `submit_dev_feedback` 提交成功当成问题已解决，放行验收。
- 把应用自己的问题、已绕过的小问题当场提成反馈，或同一问题每次再遇到都新建一条。
- 把在线预览的 3024 当成应用被下线，去上线或下线；没先重新 `ship` 就报平台问题。
- 草稿刚部署成功就出现 `BUSINESS_UI_CONTRACT_OUTDATED`，反复重新部署。
- 部署占用超限时自己下线或删除别的应用。
- 余额不足时反复重试。
