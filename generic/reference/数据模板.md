# 数据模板

## 适用场景

设计要存下来的表、建数据模板、定列的可编辑性、决定谁建行谁写列、编排脚本读写应用库、改已上线模板的结构时读。

## 规则

### 是什么

- 数据模板是开发期定稿的表结构（含逐列可编辑性与审计列）。用户首次打开应用时，平台照模板给这个用户建一份自己的库，应用后端直连它，编排脚本经平台数据集 FA 读写同一份。
- **没有应用就没有应用库**：场景包单独运行时这份库不存在，数据集 FA 只会读到 `found=false`。
- 开发工作集：`dataset_template_workspace(action="open")` 给你一个独立 PG schema 和 2 小时有效的写连接串，用来建表、灌样例、跑查询；它不占配额、不给最终用户用。`extract` 只抽结构（表、列、类型、主键、注释、关系），不带样例数据。
- **预览数据不进正式版**：「在线试用」里产生的数据写在开发工作集里；上线后每个使用者（包括开发者本人）第一次打开时都从空库开始，平台没有迁移数据的机制。**禁止**承诺或暗示预览里录入、收藏、反馈的数据会带到正式版；上线后必须存在的设定不能只存在工作集数据里，按 G5 第 5 步处理。
- 一个应用只挂这一份模板；应用角色没有 DDL 权限，应用代码**禁止** `CREATE / ALTER TABLE`，结构只走模板。

### 数据放哪

| 类别 | 例子 | 放哪 |
|---|---|---|
| 用户自己的数据 | 门店档案、账号绑定、禁用表达、偏好 | 模板表，列 `editable:user` |
| 路线读写的字段 | 每次运行的结果、效果指标、回写的统计 | 模板表，列 `editable:agent` |
| 系统字段 | 主键、关联 id、审计列 | 模板表，列 `editable:system` |
| 界面意图 | 草稿、筛选条件、已读态 | `sdk.storage`，不进库 |
| 文案、开关 | — | 代码 |

**禁止**把该进库的数据写成前端 mock 数组、静态 JSON 或后端常量。文件只存路径、文件名、时间，不存文件体。

### 每张表回答五问

1. **存什么**：看板要算的指标所需字段现在就要有。
2. **逐列可编辑性**：每列 `comment` 以 `[editable:user|agent|system] ` 开头再写中文名，选项列加 `{options:a|b|c}`。每列恰好一个写入方：用户和路线都要写的信息拆成两列（用户填的 + AI 建议的）。漏写注释的列按最保守的 user 处理，路线写不进去。
3. **审计**：有写入的表带审计列，都是 `system`，按下表声明。脚手架 `createCrudService` 建行只填业务列和 `updated_by`，更新只改业务列并自动带 `updated_at`、`row_version + 1`，所以 NOT NULL 的审计列必须在库里有默认值；平台不替你补，`gen:pages` 会在生成前检查并拒绝缺默认值的表。

   | 列 | `type` | `nullable` | `default` |
   |---|---|---|---|
   | `created_at` | `timestamptz` | `false` | `CURRENT_TIMESTAMP` |
   | `updated_at` | `timestamptz` | `false` | `CURRENT_TIMESTAMP` |
   | `updated_by` | `varchar(16)` | `false` | `'system'` |
   | `last_run_id` | `varchar(128)` | `true` | 无 |
   | `row_version` | `integer` | `false` | `1` |
   | `deleted_at` | `timestamptz` | `true` | 无 |
4. **冲突**：用户和路线同时改一行靠 `row_version` 乐观锁，后写方重读重试；没有静默覆盖。
5. **回流**：路线产出直接入库，还是先作草稿等用户确认后入库——按业务风险定，写进确认页。

### 谁建行、谁写列

- **身份列由应用后端建行时填**：主键、父记录外键、项目与业务关联 id、`version_no`、`created_at`。建行时还不知道的值（如发起后才生成的 Runtime id）不设成建行必填，运行关联落在 `last_run_id`。
- **审计列由这次写入的一方随写入更新**：路线写库（数据集 FA，或脚本直接执行固定 SQL）更新 agent 列时同一条 UPDATE 带上 `updated_by='agent'`、`last_run_id`、`updated_at=now()`、`row_version=row_version+1`；建行时带上 `updated_by='agent'`、`last_run_id`，其余审计列取模板默认值。`last_run_id` 取 `ctx.run_id`（本次运行编号，形如 `WFR-…`），经数据集 FA 写时由脚本写进 `context_hint`。过渡规则：平台在写库时自动填写系统列的能力上线后删除本条；届时手写的值会被平台覆盖，不会报错。
- **数据集 FA 只更新已建行的 agent 列**：按入口带入的 id 定位，不写身份列。个数在运行中才确定的新行，脚本按 `output_schema` 返回产出，由应用后端的生产回流接口建行。
- **例外：路线要自给时**（到点或数据变化自动发起、没有后端参与的同步类路线）：路线要的记录都由路线自己按业务键幂等写入（同一业务键重复触发命中同一行），不依赖应用后端回流：前置记录由第一个节点建，运行中产生的失败记录、水位、修订等也由写它的节点建；只写本路线负责的行，身份列与 `last_run_id` 一并填上。能写死的用脚本直接执行 `INSERT … ON CONFLICT` 固定 SQL，需要模型判断的经数据集 FA；生产上优先走固定 SQL，数据集 FA 的「自给建行」规则目前只更新到 QA，PRE 与生产仍是旧版。脚本调 FA 时 `context_hint` 写明「自给建行」，给出目标表、业务键列与值、要填的身份列与值、本次 `run_id` 和允许更新的 agent 列；没写「自给建行」，数据集 FA 只按行 id 更新、不建行。业务键在模板里必须有唯一约束，否则 FA 以 `found=false`「未入库」收口。

### 编排脚本怎么读写应用库

| 时机 | 谁来做 | 走不走 FA |
|---|---|---|
| 发起时铺底（门店信息等） | 应用后端直读库拼进发起报文；入口 `input_schema` 留好这些字段 | 否 |
| 执行中取数 | 脚本调数据集 FA `operation="read"`，每条业务流至多读一次，结果沿节点输出往下传 | 是 |
| 收尾更新已建行 | 脚本调数据集 FA `operation="write"`，`context_hint` 给唯一键、行 id、目标表和只写的 agent 列 | 是 |
| 收尾新增行 | 路线经 `output_schema` 返回产出，应用后端生产回流接口建行；自给路线没有回流，按上面「例外」由路线自己建行 | 否 |
| 读写语句能事先写死（按业务日幂等建行、水位推进、失败记录） | 脚本直接 `tool("GOALFYAI_TOOL_query_business_app_dataset", action="exec", mode="reader"/"writer", sql=…, params=…)` 执行固定 SQL，先 `action="tables"` / `"inspect"` 查实表列；要写入的值一律用 `:name` 占位符放进 `params`，不拼进 SQL 字面量；`INSERT … ON CONFLICT` 的冲突目标必须是模板里已有的唯一约束，`DO UPDATE` 同样带上 `row_version = <表>.row_version + 1`、`updated_at = now()`；审计列按上面「谁建行、谁写列」在同一条 SQL 里写，`last_run_id` 取 `ctx.run_id` | 否 |

- 数据集 FA 在 `business_app_dataset` 工具集里，平台建好，包作者不自制；`tool()` 里写完整调用名（以 `get_asset(asset_type="toolset")` 反读为准），并把这个工具集挂进 TPE 的预加载清单。
- `_output` 只声明本路线真正要用的切面，必含 `found`。表不存在、查不到行、实例还没建都是 `found=false` 的常态，不重试、不报错、不编数，回退表单值或通用策略。
- 上游 FA 返回非成功状态时不调用写。

### 建表与出版本

1. `open` 记下 `data_uid`；连接串填 `backend/.env`，**禁止**进工单、聊天、代码；过期用 `connect` 重签，已知应用时传 `business_ui_id` 防止两个应用串库。
2. `create_table`（推荐）或用连接串建表；每表至少一列 `primary_key=true`（代理主键用 `bigserial`）；类型写 PG 精确类型；列的 `default` 原样写成 PG DEFAULT 并进模板，只接受字面量、`true/false`、`NULL`、数字、`CURRENT_TIMESTAMP`、`now()`、`gen_random_uuid()`。
3. 需要时 `set_relations` 声明关系（整体替换）。
4. `inspect` 反读，逐列核对类型、主键、注释、`default`。
5. 把 `inspect` 结果翻成业务语言，和确认页「会存下来的东西」对一遍；对不上改到一致再 `extract`。首次不传 `template_id` 新建模板；修订时传 `template_id` 出新版本。
6. `business_ui_manage(action="update", dataset_template_id, dataset_template_version)` 挂载，版本钉整数，**禁止**跟随最新；`bind` 把工作集绑到应用。绑定后开发者 deploy 出的预览容器直接连工作集的库（角色 `bui_w_<data_uid>`），所以工作集一直留到 G7 结单前；关之前必须先 `bind business_ui_id=0` 解绑并重新 `deploy` 当前版本行，容器换到独立开发库后再 `close`。平台在 close 时会检查，还有版本行的当前部署跑在工作集上就拒绝并在 `metadata.holders` 点名。

**连接纪律**：写连接经数据集代理，`BEGIN / COMMIT / ROLLBACK`、`SET ROLE`、`SET search_path` 都会被拒；要原子性就压进一条 SQL（CTE、`INSERT ... ON CONFLICT`、`UPDATE ... FROM`）。

### 改已上线的模板

- 模板版本被上线的应用钉住后不可变：改结构 = 工作集里改 → `extract` 新版本 → 应用出草稿改挂载 → 重新部署 → 定版。
- **改结构就在绑定到应用的那个工作集上改**（`connect` 取写连接，`CREATE TABLE IF NOT EXISTS` / `ALTER TABLE … ADD COLUMN IF NOT EXISTS`，幂等），再从它 `extract`。开发者容器直连这个工作集，里面有开发期数据；平台不会替它迁移结构。另开一个工作集抽出新版本再钉到草稿，绑定的工作集还是旧结构，`deploy` 会被 `BUSINESS_UI_WORKSPACE_BEHIND_TEMPLATE` 拒绝并逐表点名缺的表列，回这个工作集补齐后重新 `deploy`；**禁止**为此解绑、换绑空工作集或 `close`。
- 只改默认值（`ALTER COLUMN … SET DEFAULT`）是增量：`extract` 不收脚本，响应 `diff.defaults_changed` 逐列列出旧值 → 新值，存量实例升级时平台自动 `SET DEFAULT`。
- 删列、改类型这类破坏性变更，`extract` 必须带 `migration_script`（幂等、单事务、只动本 schema、不建外键）；定版时平台在临时库彩排。存量用户只往前升、没有降级。新增列、新增表优先；删列改类型先问开发者存量数据怎么迁。
- 换模板家族等于换库，平台拒绝；需要新库就新建应用。

## 常见错误

- 列注释漏了 `[editable:…]` 前缀，路线写不进去。
- 身份列设成 NOT NULL 又没人填，数据集 FA 写不进，甚至自己编造 INSERT。
- `created_at`、`updated_at`、`row_version` 建成 NOT NULL 却没给 `default`：脚手架建行不填它们，使用者第一次保存就失败；`gen:pages` 会拒绝，回工作集 `ALTER COLUMN … SET DEFAULT` 后重新 `extract`。
- 同一列用户和路线都写，靠运行时仲裁。
- 在 G5 就 `close` 工作集，预览部署退化成空库。
- 开发者容器还连着工作集就 `close`：schema 和角色一起被删，容器休眠唤醒后健康检查永远 503，页面卡在 Waking up。先解绑并重新 deploy 再关。
- 应用已绑定工作集，却另开一个空工作集建新结构、抽出新版本钉到草稿，再想把新工作集 bind 过来或让平台"自动迁移"旧工作集：新工作集 bind 被拒（已有绑定），旧工作集不会被迁移；正确做法是回绑定的工作集用写连接补齐表列，再从它 `extract`。
- 为「存用户数据」去挂目录里的「××档案场景包」；那是另一条产品线，不是应用库。
