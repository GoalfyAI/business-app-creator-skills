# 前端页面

## 适用场景

搭或改应用页面、接 SDK、做入口表单、项目页、交付审阅、数据管理、看板时读。页面规则的正本在应用工程里：`frontend/README.md`、`frontend/docs/business-ui-guide.md`、`frontend/src/sdk/docs/`；本文只列最容易出错的约束。

## 规则

### 界面以开发者为准，预置件可用可不用

优先级从高到低：**开发者在确认页「界面」一节和之后反馈里说的样子** > 本文「界面风格」的自定规则 > 脚手架预置件和起始应用的默认样子。

- 开发者说过要什么样，就**必须**做成那样：可以完全自己写前端，也可以大改起始应用和预置件；用不用预置件、用多少、改到什么程度由你按开发者要求判断，**禁止**为了少写代码或套用预置件把开发者要的样子改掉，也**禁止**只换品牌色、圆角就当作满足了开发者的风格要求。
- 预置件是少写代码的工具，不是页面的样子：样子对得上就直接用；对不上就复制到 `pages/`、`components/` 改，或整页自己写；外壳（导航、布局、配色体系）也可以自己写，不受 `config.ts` 几个外观开关的限制。不改 `ui/`、`blocks/` 源码，要改就复制出来改，免得丢掉脚手架升级能力。
- 可以换或加 UI 框架、组件库、图表库与样式方案，只要在脚手架的 React/Vite 运行边界内、能通过 `npm run verify:release`、不污染宿主页面。
- 自写或大改时**必须**保住平台行为，不是外观：照样经下面「SDK 两层与保留件」列的 hook 和组件接平台；消息中心未读角标、历史记录找回、项目状态、表单应答、交付审阅、只读置灰、宿主保留区避让、亮暗跟随宿主的行为与预置件一致。拿不准某个行为怎么做时，读对应预置件的源码照着实现，而不是放弃自写。
- 示例页面（`examples/`）只用来理解协议，不复用它的结构和视觉。
- **开发者给的配色和亮暗跟随一起做**：开发者的原型、截图或参考站通常只有一套配色（多半是亮色）。把它原样用作亮色主题；暗色主题按同一套色相自己配（背景、文字、边框换成暗色，品牌色保持可辨），宿主切换亮暗时跟着切。**禁止**因为原型只有一套配色就放弃跟随宿主，也**禁止**为了跟随宿主把亮色下的原型配色改掉。开发者明确说过「只要一种配色、不跟宿主」时照开发者说的做，并在页面说明里写一句「宿主切暗色时应用仍是亮色」。

### 参考网站

开发者给了喜欢的网站时，按它的样子做：

- 先把参考站的版式、配色、字体、间距、组件形态拆成一份设计说明（颜色值、字号层级、圆角、阴影、栅格、导航形态），写进 G5 阶段文档，再按它实现。
- 可以用网站复刻类工具从公开页面抽设计令牌和页面结构作为起点，例如开源的 Ditto（MIT，可输出 Vite 代码，带 MCP）或 ai-website-cloner 类 Skill；也可以直接读参考页面的公开 HTML/CSS。抽出来的代码**必须**改造进本应用：数据一律经 SDK 与自家后端，**禁止**保留对参考站接口、脚本或 CDN 的引用，**禁止**引入 fetch / XHR。
- **只借样式，不搬内容**：**禁止**照搬参考站的 Logo、品牌名、图片、插画、文案和字体文件（字体用开源或系统字体近似）；第三方代码按其许可证使用。
- 只抓开发者给的公开页面；**禁止**抓需要登录的页面、GoalfyMax 自身页面或在线预览地址，**禁止**为抓取使用开发者的账号或会话。
- 环境里没有这类工具或抓不到时，请开发者给截图，按截图实现，不因此降级成默认样子。

### 界面风格

开发者没说过要什么样时，按这一节自定外观，不照搬脚手架默认。写页面前先定下面几项，写进本段阶段文档，一句话一项：

| 项 | 在哪配 | 怎么定 |
|---|---|---|
| 品牌色 | `src/app/config.ts` 的 `APPEARANCE.accent`（6 位 hex，优先于宿主主色） | 按行业与调性选：内容种草类偏红、金融财务类深蓝或墨绿、餐饮零售暖色、工具效率类冷静色；主色只用在可点的东西与品牌处，状态色（告警、成功、提醒）另有，不拿主色表示状态 |
| Logo | `BRAND.logo` | 用贴合业务的图标（`@ant-design/icons`）或 `frontend/src/` 下的图片；不要用名字首字方块凑数 |
| 导航图标 | `NAV` 每项的 `icon` | 线性图标，同一套风格；不再用单字方块 |
| 布局 | `LAYOUT` | `sidebar` 功能多、层级深；`topbar` 页面少（≤5 个）、内容要铺满；`topbar-sidebar` 功能多又要品牌感（顶栏放品牌与通知、账号） |
| 圆角 | `APPEARANCE.radius` | `sharp` 数据密集的工作台；`default` 通用；`round` 面向消费者、内容类 |
| 首页重点 | `pages/HomePage` | 按用户每天打开要先看什么来组织（经营数据、待办、内容库、最新结果），见下一节「首屏与导航按客户业务任务组织」；`HomeBlock` 可用作骨架，内容区按业务自己拼 |

- 缺省蓝色、名字首字方块、单字导航只是没配置时的兜底，交付时不应还是这个样子。
- 开发者没提外观要求时，外壳外观优先改 `config.ts`；`config.ts` 的开关做不出确认页要的样子时，自写外壳（见上一节）。装饰（插画、背景）写在 `src/components/` 或页面里，颜色跟随宿主亮暗。
- `src/app/config.ts` 没有 `APPEARANCE` / `LAYOUT` 说明脚手架较旧，按 [脚手架与预置件.md](脚手架与预置件.md) 升级后再配。

### 首屏与导航按客户业务任务组织

页面是给目标客户用的，按他要完成的事组织，不按功能模块或平台对象组织：

- **首页是业务工作台**：打开就回答「现在情况怎样、为什么、下一步做什么」——业务目标或关键数字、支撑它的依据、一个最该点的下一步动作；待办与最近结果放在旁边。**禁止**首屏被通用列表、运行状态或空白占位主导。
- **导航顺序 = 客户完成业务的顺序**：例如「建档 → 诊断 → 处理建议 → 复盘」，名称用客户的业务词；脚手架默认导航只是骨架，按 G3 客户验收条目里的操作顺序重排，不照搬。
- **区分第一次使用和日常使用**：第一次要先建档、授权或导入的，空库时首页引导去做这一步；有数据后首页回到日常工作台。
- **示例数据要连到业务**：预览里的示例数据能解释业务目标、展示一份完整成果，并能接着点下一步操作；不放「测试 1」「foo」这类与业务无关的数据，示例数据在界面上标明是示例。
- **不露平台信息**：mock 标记、运行状态细节、日志、阶段、数据集名称不放在客户界面上；需要排查的信息放在开发者看的地方。

### SDK 两层与保留件

- **App 层**（顶层 `sdk`）：`session`（实例上下文与权限，`permission='view'` 时置灰全部发起与写入入口）、`projects`、`getProject` / `createProject`、`inbox`、`api`（自家后端）、`storage`（界面意图）、`ui.reservedAreas`（宿主浮层占用区，交互组件要避开）、`theme`、`file`（应用级文件）。
- **项目句柄层**：`business`（start / onCall / reply / onResult / 查询）、`upload`、`file`、`chat`、`observe`、`info`。
- **保留件必经，不改不删**：`useProject`、`useProjectExecution`、`useProjectDraft`、`useInbox`、`useRuntimeUserFiles`、表单渲染、错误归一化、`FileField`、`MarkdownContent`、局部错误边界。表单预填已下线，残留的相关文件不接入；表单 schema 的唯一来源是契约包 `forms/` 与 `getForms(formId)`。
- **一切平台调用经 SDK**：后端走 `sdk.api.request`（纯路径、GET/DELETE 无 body、载荷 ≤ 256 KiB；`code !== 0` 必须给用户反馈，不静默失败、不自动重试）；**禁止** fetch / XHR / axios（ESLint 硬禁）。

### 必备页面

| 页面 | 要求 |
|---|---|
| 首页 | 根路由是欢迎页或业务展示页（可以就是看板），不是占位或空白；待办入口带 `useInbox().unreadCount` 角标 |
| 历史运行入口 | 用户要能找回以前每次发起的进度与结果。默认用首页 `HomeBlock` 的「最近记录」（分页可翻到全部，`recordsTitle` 按业务对象命名）；业务要按对象管理时用 `useOwnedProjects` 自写业务化视图（如「诊断记录」）；脚手架版本较旧、没有这两个件时，按同样的取数规则自写。**禁止**向客户放通用「项目列表」页，导航与文案不出现「项目」。取数规则不变：打开、翻页、手动刷新时拉 `sdk.projects.list`，**禁止**轮询，`onStatusChange` 按 `projectId` 就地更新；空态引导去发起第一次业务 |
| 消息中心 | 必经 `useInbox()`；条目带归属项目、表单显示名、文案；点击导航到对应项目的应答状态 |

### 业务页面

- **看板**：数据只来自后端统计接口；每个数值能点开看口径；空数据有引导态；跟随 `sdk.theme` 亮暗。
- **数据管理**：只对 `editable:user` 列开放编辑，`agent` 列只读并标来源；批量与删除有确认；错误按后端信封 `code/msg` 呈现。
- **业务发起（入口表单）**：必经 `useProjectDraft(draftKey)`，`restoring` 期间禁提交；按 `getForms(formId)` 渲染，没有预填，稳定信息由后端发起时拼进 `submit_data`；文件字段经 `project.upload`，全部上传完成才允许提交；`accepted` 导航到项目页，`rejected` 原窗重填，`failed` 展示错误不自动重试。复用已有项目的下拉框不列还有表单没答完的项目；新业务一律新建项目。
- **项目页与交付审阅**：阶段进度按业务事件归约，**禁止**轮询；服务端调起表单时导航到可恢复的应答状态；交付审阅按 `display` 的 `headline / facts / notices / sections` 渲染，只在有活动调用时渲染动作按钮、只提交 `action_key`，`agent_gate` 只读；已提交表单以 key-value 展示，不露裸 JSON 和裸路径。
- **让宿主小喇叭能跳进来**：`goalfy-app.json` 的 `routes` 声明项目页、表单应答页与交付审阅页的路径模板（脚手架默认带 `project: /projects/{project_id}`、`form: /projects/{project_id}/forms/{form_id}/calls/{call_msg_id}`、`delivery_review: /projects/{project_id}/runtimes/{workflow_runtime_id}/delivery`，SDK 随握手交给宿主），用户在宿主小喇叭点一条失败、待填表单或交付消息时按它直接落到应用里对应的页面；改了这些页面的路由必须同步改声明，另有单独执行详情页的可加 `runtime`（占位符只有 `{project_id}` `{workflow_runtime_id}` `{business_id}` `{orchestration_id}` `{form_id}` `{call_msg_id}`）。`npm --prefix frontend run check` 校验每条模板都对得上 `App.tsx` 注册的路由，对不上直接失败；**禁止**留下对不上的模板，没有对应页面的应用去掉那条声明即可，宿主会退到项目页或在自己的面板里展开消息详情。
- **交付审阅只提交所选动作**：`reply(callMsgId, { action_key })`，**禁止**把业务数据（如确认后的商家信息）塞进审阅应答——缺 `action_key` 或夹带字段时 SDK 本地判 `rejected`，`npm --prefix frontend run check` 直接失败。要让用户在审阅前后修改数据，在路线里设计中途表单，或声明带表单的审阅动作（`start_orchestration`）。审阅与所有表单的 `rejected` 都要把 `data.field_errors` 的原因展示给用户，不能当成已提交。
- **给使用者看的都是人话**：业务用中文名（`useOrchestrationNames` 按路线契约取 name），时间用本地时间（`formatDisplayTime` / `formatDisplayDateTime`），执行过程按「第 N 步 · 状态」合并（`taskpointSteps`），都在 `@/shared`；**禁止**在界面上显示路线 ID、项目 ID、`businessId` / `workflowRuntimeId` / `taskpointEventId` 等内部 ID、`Runtime` / `编排` / `TaskPoint` 这类术语和原始时间串。脚手架预置的项目页已按这个口径显示，旧应用升级脚手架后重新部署才生效；`npm --prefix frontend run check` 对业务页面直接显示内部 ID 会给警告，要清零。
- **应答到运行的过渡**：项目层 `useProject(projectId)` 与 `useProjectExecution(project)` 只建一次，应答页、进度页、审阅页共享；应答用 `execution.reply`，不绕过它自己调 `project.business.reply`；**禁止**在每个子路由或因 inbox 变化重建句柄。提交后立即显示「正在提交」，`accepted` 显示「已受理」，收到 `running` 立即切到执行中。

### 业务文案

- **简洁同时保留业务含义**：先从已确认需求、真实路线/表单/记录及产物取名称，再写完整短语。整体对象与入口动作分别命名；只有上传就写上传，确实发起筛选才写开始筛选，不用“任务/提交/查看”或删掉“项目”代替业务化。
- **必须接到实际页面**：当前模板 `frontend/README.md`「业务文案」是配置字段、优先级和接线的唯一工程来源；按它填写应用文案、入口动作和各表单覆盖，保留开发者已有显式定制。若实际模板尚不支持，先按 [脚手架与预置件.md](脚手架与预置件.md) 核版本和能力，不自造字段、改版本串或假定下载过就已升级。固定层不读取业务配置，应用外壳须主动传入。
- **上下文一致且不虚构**：同一记录在历史、消息、详情与返回中可识别，真实名称优先，缺名不用内部标识。补充按真实表单命名，结果按实际产物命名；没有产物就不制造报告入口。通用“刷新/返回首页/正在提交/已受理”清楚时保留，不能把状态含义改掉。
- **验证消费结果**：沿 G5 的简短对应逐场景看实际文案与动作；配置写了但未接线、仍用无业务含义的默认词、把上传当筛选或把提交当完成，都要修正后再收口。静态词检查、构建和模板登记只证明各自事项，不证明业务语义正确。

### 表单与文件

- 三类回显各归其位：草稿回显（`sdk.storage`）、驳回回显（`rejected` 返回的参数原窗重填）、已提交回显（`getRuntimeForms`）。
- 校验失败：顶部一条提示，全部无效项高亮，首个无效项滚入并聚焦；提交中禁用写入口。
- 文件值只能由上传产生；展示 URL 经 `getViewUrl` 现取现用；下载只在用户点击时调用。应用级持久文件用 `sdk.file` 与 `shared/ApplicationFileField`，只存 `path`。
- **禁止**把当前路由写进 `sdk.storage`，业务代码不调 `sdk.notifyRoute` / `onHostNavigate`。

### 做完怎么查

- `npm --prefix frontend run check` 通过；用脚手架本地布局回归查桌面与移动宽度下的溢出与裁切，并对照代码检查键盘、焦点、对比度和长文本，至少修一轮。开发者想看时，需求全部完成后在「演示预览」看完成版，制作中在草稿部署成功后的「在线预览」看；他看了不算验收。
- 能点、能填、能切换的地方都要有人操作过：由前端测试覆盖，或 ④ 在开发者同意后由你在在线预览里照验收条目点过（见 [开发者中心与工作区.md](开发者中心与工作区.md)「④ 用浏览器验收」）；测不了的写「未测」和原因，不请开发者代测。
- 设计做不了（SDK 拿不到的数据、路线不发的事件）时回 G3 改清单或回 G4 改契约，**禁止**静默改设计继续做。
- 文案与注释用中文；组件单一职责，超过约 200 行考虑拆分。

## 常见错误

- 开发者给了参考样式，却只改品牌色和圆角，页面仍是起始应用的样子。
- 照搬参考站的 Logo、图片、文案，或保留对参考站接口、CDN 的引用。
- 用 fetch 直连后端，ESLint 拦下或上线后跨域失败。
- 每个子路由各建一个项目句柄，重新订阅触发重放，把用户拉回旧表单。
- 表单在上传未完成时就能提交。
- 下拉框列出挂着未答表单的项目，用户在那里提交新入口表单被当成答复。
- 数据管理页让用户改 `agent` 列。
- 项目页、记录页直接显示路线 ID、`PRJ-…` 任务标题或 `2026-09-29T03:31:50` 这样的原始时间，使用者看不懂。
- 留着起始页占位或示例包，`verify:release` 失败。
