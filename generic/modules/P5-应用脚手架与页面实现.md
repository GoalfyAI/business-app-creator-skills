> 专业模块。只回答「怎么做」，由阶段层 G1–G7 按需调用；不自带阶段流程。

## 1. 进入前提

- 目标场景包**已上线**（未上线转 business-app-creator 先完成）；
- 有 `write` 工单；
- 开发者已说明应用的业务意图：给谁用、解决什么持续经营问题、用户一天/一周会在这里做几次什么事。

**进入后的第一个动作是向开发者要参考资料**（与 business-app-creator S1 向开发者要参考资料、打法同一做法），一次问清、记进工单：

| 问什么 | 为什么 |
|---|---|
| 页面设计参考：喜欢的产品、截图、品牌规范、已有的设计稿 | 决定 §5.5 第 3 步的设计方向；有参考就不必自己调研 |
| 想要的功能：对着 §2.2 的功能选择菜单逐项问“要不要、为什么” | 菜单里的每一项都要开发者定，缺的写“不做 + 理由” |
| 现有数据：Excel / 表格 / 其它系统导出，字段长什么样 | §4 数据设计的起点，模板字段贴用户真实数据而不是想象 |
| 谁来用、多久用一次、一次做什么 | 定页面的主行动与看板指标 |

拿不到参考也要记“无参考”，然后按 §5.5 第 2 步自行调研。

**定义**：业务应用 = 运行在 GoalfyMax 宿主 iframe 里的前端 App + 一个专属后端 + 每个用户各一份的 PG schema（业务应用数据集）。前两者打进**一个镜像、一个 Pod**（脚手架 `frontend/` + `backend/` 双目录），schema 由平台按**业务应用数据集模板**版本给每个用户各建一份；发布单位是独立资产 `business_ui`（自己的家族与版本，挂恰好 1 个场景包 + 至多 1 个模板）。

**它在平台里的地位**（SDK 4.0）：应用是与项目并立的**一级实体**——用户从宿主导航直接进入应用，一个应用实例可以创建并管理 **N 个项目**。所以应用不是“某个项目里的一块面板”，而是用户持续经营某件事的**工作台**：看现状（看板）→ 发起一次生产（创建项目跑场景包）→ 跟进（项目页）→ 产出回流入库 → 用户修正（数据管理）→ 再看现状。这条 SaaS 链路是一切设计的骨架。

**给谁用**：场景包的最终用户（店主、运营、销售……由开发者在访谈里定），不是开发者自己。每个用户看到的是**自己的**数据（schema 隔离 + 实例权限），协作场景由平台的 `permission`（`edit` / `view`）裁决——`view` 态必须置灰全部发起与写入口。

**由什么组成**（设计时逐项回答“有没有、几个”）：

| 组成 | 内容 | 由谁定 |
|---|---|---|
| 挂载的场景包 | 恰好 1 个（一期）；契约区按 `schema/packs/<pack_id>/` 分目录 | P5 第 3 节 反读 |
| 业务应用数据集模板 | 至多 1 个；表结构 + 逐列声明 + 审计字段 | P4 第 4 节 设计 → A2 落地 |
| 三个必备页面 | 首页、项目列表页、消息中心（脚手架硬约束：只约束存在且可达，不约束形态） | 脚手架 |
| 业务页面 | 四类原型按业务取舍：看板 / 数据管理 / 业务发起（入口表单） / 项目页（进行态 + 应答表单 + 交付审阅） | P5 第 4 节 |
| 专属后端接口 | 三类：CRUD（编辑回流）/ 统计聚合（喂看板）/ 生产回流 | P5 第 4 节 页面反推 |
| 前端私有状态 | `sdk.storage`：草稿、筛选、当前 businessId 等**界面意图**（32 key / 512 KiB） | 不存业务数据 |

## 2. 项目模型与功能选择菜单

### 2.1 项目：业务应用之下的一层

业务应用在项目**之上**：一个应用实例里，用户可以创建多个项目。**项目 = 用户的一次计划选择**——用户决定“这一次要干一件什么事”，一次业务路线运行连同它的入口表单、运行中表单、消息、文件、业务事件与交付，都装在这个项目里。项目是过程的容器，**不是**应用的数据面：长期沉淀的业务数据在业务应用数据集里，项目只通过 `system` 列（项目 id / `last_run_id`）与数据行关联。

开发应用时必须拿到**在这个应用实例里创建的全部项目**：`sdk.projects.list` 分页拉（打开 / 翻页 / 手动刷新时拉，禁轮询）+ `sdk.projects.onStatusChange` 按 `projectId` 就地更新（拉推成对）。列表只含本实例名下已受理的项目，两段式建项目的临时项目在首启受理前不入列表——这是设计使然，不是漏数据。

**项目详情也必须消费当前项目的状态推送**，不能只让列表实时、详情等待业务事件或 Runtime 查询。设计中分别画出“正在提交”“已受理，准备继续”“正在执行”：点击立即进入提交反馈；`accepted` 只结束业务确认阶段，当前项目 `running` 才是执行中的依据；若 `running` 先到，先展示执行中但保持尚未完成的提交锁。应答页与进度页共用项目层的句柄和过渡态，切换子路由不能丢掉这段过渡；`rejected` 回到可修正表单，`failed` 或发送失败显示错误。阶段进度仍来自业务事件，不能用项目 `running` 伪造已完成阶段（接入见 P5 第 10.3 节.1）。

用户发起一次生产时只有两种选择，页面上要让他显式选：

| 选择 | 用户做什么 | 应用做什么 | 何时用 |
|---|---|---|---|
| **创建** | 点动作按钮 → 填入口表单 → 提交 | 必经保留件 `useProjectDraft(draftKey)` 拿草稿句柄（一个表单会话一个句柄）；提交时 `project.business.start()` 触发**两段式建项目**：先懒创建服务端临时项目，再发起业务路线；首启 `accepted` 后临时项目转正入列表；发起后跳转项目页 | 新的一件事、新的一个对象（新门店、新一期活动） |
| **复用** | 点动作按钮 → 在项目下拉框里选一个已有项目 → 填表单 → 提交 | 下拉框选项**只来自** `sdk.projects.list`（无本地记录、不猜 id）；选中后经 `sdk.getProject(id)` 的句柄 `business.start()`，消息进入所选项目、不产生新项目；后一条路线能读到前一条在同一项目里的交付文件 | 在同一件事上做下一步（路线 2 接着路线 1 的产出） |

创建态 / 进行态的分界由此而来（总入口约束 3）：**业务发起页是唯一的发起入口**，项目页只看进度、应答表单、审阅交付，不发起新的业务路线运行。项目页里“再来一次”的需求，做法是跳回业务发起页并把该项目预选进下拉框。`permission='view'` 时创建与复用两个入口一起置灰。

下面是当前脚手架（`frontend/README.md` 三、SDK 速览与 `src/sdk/docs/`）真实提供的能力，按“必备 / 建议 / 可选”分级。**A1 要拿着这张表向开发者逐项问**，结果（做 / 不做 + 理由）写进《业务应用计划书》第 ⑤ 章；勾选的每一项都要在 §5 页面设计里落到具体页面，并在 P6 第 11 节 自动化测试门里有对应用例。

| 等级 | 功能 | 靠什么实现（正本） | 说明 |
|---|---|---|---|
| **必备** | 首页 / 项目列表页 / 消息中心 | 脚手架硬约束；`useInbox`、`sdk.projects`（`business-ui-guide.md`） | 只约束存在且可达，形态自定；首页可以就是看板 |
| **必备** | 业务发起（入口表单，创建 / 复用两形态） | `useProjectDraft` + `project.business.start`、契约区 `getForms`（`business.md`） | 挂载的场景包有可主动发起的业务路线就必备（§2.1） |

| **建议** | 执行记录与已提交表单回看 | `getRuntimeForms`、`getRuntimeDelivery`（`business.md`） | 用户回看“我当时填了什么、产出是什么” |
| **建议** | Runtime 用户文件补传 / 删除 | 保留件 `useRuntimeUserFiles`（全量替换语义） | 对某次运行补资料 |

## 3. 场景包给了你什么（契约基线）

应用的**入口与出口全部由场景包定义**，不由应用发明。逐项**反读**（禁止推测），写成契约基线表记入工单：

| 接缝物 | 从哪反读 | 决定应用的什么 |
|---|---|---|
| **入口表单与中途表单** | `get_asset(scenario_package)` 返回的 `business_forms`（每张表单的 `form_id`、入口 / 中途、所属路线与节点、字段名与类型 / 必填、`skip_when`——由业务路线映射与 Schema 推出，权威）+ 场景包 Skill 文件 `forms/<form_id>.json`（标题、字段说明、控件提示、顺序）；据此手写契约区 `schema/packs/<pack_id>/forms/*.json`（`inputSchema` 与 `business_forms` 字段一致） | **入口**：业务发起页要实现哪几张表单、每个字段的类型/必填/文件字段；哪些字段由应用后端在发起时拼进 `submit_data`（用户不用填）、哪些必须用户填。**中途**：项目页要能应答哪几张表单、各在哪个节点后出现、`skip_when` 时不会出现 |
| **业务路线**（`orchestrations/*.json`：`entryFormId`、`formIds`、`delivery`） | 同上 | 有几条可主动发起的路线（= 几个“发起”按钮）；服务端中途会调起哪些表单（= 项目页要能应答的表单）；终态审阅形态（`user_gate+ask` 有动作按钮 / `user_gate+result` 自动交付 / `agent_gate` 只读） |
| **编排型 TPE `output_schema` / `display`** | 场景包编排型 TPE 资产 | **出口**：交付页能渲染哪些业务字段（对比、清单、结论），`display` 五字段兜底；**生产回流**能入库的字段来源 |
| **业务事件契约** | 编排型 TPE 资产 `business_event_contracts` | 项目页的进行态能显示到什么粒度（有 `stage_*` 才有阶段进度；没声明就不做进度模块） |
| **面向系统的公开语义**（business-app-creator S3-7.3） | 场景包工单 | 页面文案：路线的业务名、里程碑、交付、到达标准——**不用编排型 TPE 名、节点 ID、工具名** |
| **数据集读写通道**（business-app-creator S3-2.4） | 场景包编排型 TPE 脚本 | 哪些字段由编排型 TPE 经业务应用数据集 FA **读**（应用要保证这些列有数据）、哪些由它**写回**（应用要展示这些产出列） |

**契约区为空或只剩演示包，说明上游未就绪：停止业务设计并报告**，不照截图猜字段。多包（v4）时每包一个目录、`form_id` / `orchestration_id` 全 App 唯一。

**先读场景包的《制作书》**（场景包工单里的 `build_book`，S2 定稿版）：它的第 ⑧-6 章已经定了业务应用数据集的逐列字段、声明与读写来源，第 ⑧-7 章定了配套应用的页面清单、看板字段与可编辑列——**本节以它们为起点做细化，不推翻**；要改字段或页面范围，属于制作书口径变化，回场景包线沟通后再动。制作书里没有 ⑧-6/⑧-7（老包或未规划配套应用）时，才按本文 §4–§5 从零设计。

## 4. 页面设计

### 4.1 页数从哪来

页数 = 三个必备页面 + 按业务取舍的四类业务页面。不多不少的判据：**每个页面对应用户的一个明确意图**，多个意图挤一页会让高风险交互（提交、删除）和浏览混在一起，一个意图拆多页会造成孤岛。

| 页面 | 必备？ | 用户在这做什么 | 数据从哪读 | 动作往哪发 |
|---|---|---|---|---|
| **首页** | 必备 | 落地、看待办红点、进入各处；可以就是看板 | `useInbox().unreadCount`、后端统计 API | 导航 |
| **项目列表页** | 必备 | 看所有归属项目的状态 | `sdk.projects.list` + `onStatusChange`（拉推成对，禁轮询） | 进项目页 |
| **消息中心** | 必备 | 跨项目待答表单、结果通知 | `useInbox()` | 进对应项目的应答状态 |
| **看板**（展示态） | 按业务 | 看现状、决定干什么 | 后端统计聚合 API（只读 SQL） | 进业务发起 / 数据管理 |
| **数据管理**（编辑态） | 按业务 | 增删改自己的业务数据、上传/替换文件 | 后端 CRUD | 后端 CRUD（幂等写） |
| **业务发起**（创建态） | 有可主动发起的业务路线就必备 | 填入口表单发起一次生产；或选已有项目复用 | 契约区 `getForms`（无预填；稳定信息由后端在发起时拼进 `submit_data`） | `useProjectDraft` 草稿句柄 → `project.business.start()`（两段式建项目） |
| **项目页**（进行态） | 必备 | 看进度、应答服务端调起表单、审阅交付、看执行记录与已提交表单、编辑 Runtime 用户文件 | 业务事件 / `pending` / `getRuntimeForms` / `getRuntimeDelivery` | `reply()`（三次握手）、审阅动作只提交 `action_key` |

**禁止孤岛**：除首页外每个页面在任何状态（含错误、只读、`form-submitting`）都要有可操作的 App 内返回入口与确定性兜底；路由表必须有通配兜底回落首页。

### 4.2 看板怎么选字段

看板的每个数值都要能回答“从哪张表、哪些列、什么口径算出来的”。选字段的规则：

- **只从业务应用数据集算**，不从 `PublicDelivery` 或聊天消息里现算——交付回流入库（4.2 第 5 问）才有看板；
- **指标 = 对 `editable:agent` 列（产出、效果）的聚合，维度 = `editable:user` 列（门店、账号、目标）与时间**；用户列本身不是指标；
- 每个指标标注：来源表 / 聚合方式 / 时间窗 / 编辑实时性（用户改了数据多久反映）；大结果分页、单查询在 10 s 内；
- 空数据是常态（新用户零数据）：每个看板块要有引导态，指向“去发起第一次”或“去补数据”；
- 指标数量宁少勿多——用户每天真的会看的那几个，其余进详情页。

### 4.3 可编辑性怎么在页面上体现

列注释里的 `[editable:*]` 声明要**肉眼可见**地落到页面：

- **数据管理页**：只有 `editable:user` 列开控件；`agent` 列只读展示并标明“由生产写入”（含最近写入时间 / 来源运行）；`system` 列不展示或收进详情；
- **看板 / 详情**：一律只读；
- **文件字段**：全程只读卡片，值只能由上传动作产生——不出现路径文本框，不允许手改路径；编辑态有“替换 / 清除”，查看态无写入口；上传中有状态、失败可删后重传；提交必须等全部上传到终态；
- **`view` 权限 / `form-submitting` 期间**：全部写入口置灰并说明原因，返回入口不受影响；
- **用户列被生产建议覆盖的场景不存在**（4.2 第 2 问拆列），所以页面不需要“接受 AI 建议覆盖我的值”这种危险控件；需要采纳时是“把 AI 建议列复制到用户列”的显式动作。

### 4.4 文件在页面上怎么出现

- **上传先分级，看文件属于谁**——两级都返回 `/workspace` 路径、表单值都只存路径，但归属和生命周期不同，选错的后果是真实的：

  | 文件属于 | 用哪级 | 怎么调 | 典型位置 |
  |---|---|---|---|
  | **这一次生产**（本次表单的附件、这次要处理的素材） | 项目级 | 草稿句柄 `project.upload(file)` → `project.file.getViewUrl / download`；组件 `shared/FileField`（必须传项目句柄） | 业务发起页的入口表单、项目页的运行中表单 |
  | **用户本人，跨项目反复用**（品牌手册、菜单、实拍素材库、历史资料） | 应用级 | `sdk.file.upload(file)` → `sdk.file.list / getViewUrl / download`；组件 `shared/ApplicationFileField`（上传 + 历史分页 + 预览 + 下载 + 多选） | 数据管理页、资料库；入口表单里"从历史资料里选"的字段 |
  | **某次运行的补充材料**（对已跑的运行补传 / 删除） | Runtime 用户文件 | 保留件 `useRuntimeUserFiles`（全量替换语义） | 项目页执行记录 |

  两条硬边界：***数据管理页不能用 `project.upload`***——草稿句柄上的首次上传会懒创建一个临时项目，用户只是想存一份资料却多出一个项目；**应用级文件要进本次生产**时不用重传，把选中的 `path` 写进 `business.start` / `reply` 的 formdata，宿主发帧前会重新解析并登记给目标项目，源文件不动。扩展名黑名单与 300 MB 上限由平台拦，界面要把失败原因显示出来；
- **Excel 等结构化文件要“展示在表单里”**：文件本体走上传（给 Agent 读），**预览与填入由前端解析**（在浏览器里读表头/前几行渲染成表格或填入字段）——两条路并行，不互相替代；解析失败不阻断上传；
- **需要用户调整顺序**（选题排序、素材排序）：入口表单页是 App 自绘的（`inputSchema` 原样保留，通用渲染只消费常用子集，复杂字段手写定制页），数组字段完全可以做成拖拽排序，**提交时按数组顺序**——前提是编排型 TPE 的 `input_schema` 把它声明为数组且顺序有业务含义（这是场景包侧 S1/S2 的设计，A1 反读时确认，缺就回场景包线补）；
- **展示**：图片经 `project.file.getViewUrl` **现取现用**（URL 短时效，禁止存进 storage / formdata）；非图片按可读文件名展示；下载只经 `project.file.download` 且只能由用户显式点击触发；`[[file:/workspace/...]]` 标记经安全渲染；
- **交付物**：`artifacts[].workspace_path` 只传文件 RPC，`output_paths` 只作归属标签，禁止渲染路径文本。

### 4.5 从设计到原型

设计动作按顺序做，先读钉版指南再动手（`references/前端设计指南/`，四份官方 guidance 的离线副本；新页面 / 重设计全读四份，小改只读产品认知一份 + 受影响那份）：

1. **理解产品**（`codex-ui-ux`）：用户是谁、要完成什么、认哪些业务词；入口、首个决策、主行动、成功态、恢复路径；加载 / 空 / 错误 / 权限 / 破坏性 / 长内容 / 移动各状态。***不从装饰或组件画廊起手***。
2. **竞品调研**：先问开发者有无参考（品牌规范、喜欢的产品）；没有再调研 3 个以上同类产品——模块划分、主行动怎么突出、状态怎么表达、空态/等待/失败怎么处理、视觉层级靠什么建立；截图报告留存进工单，只取参考点不照搬。
3. **定一个有辨识度的方向**（`frontend-design`）：贴合业务的设计主张、配色、字体系统、布局逻辑、密度和一个记忆点；对着真实任务校验后再编码。避开 AI 通用默认；用真实界面文案；主行动与信息层级一眼可辨。**脚手架 demo 的页面结构、排版、视觉是第一规则禁止复用的**（这是脚手架的硬约束，不是建议）。
4. **设计完整交互**：从入口到完成的最短连贯旅程；先定义全部重要状态再打磨快乐路径；移动端主行动可达。
5. **原型、计划书与一次确认**：见 §6——原型跑起来后截图进《业务应用计划书》，连同后端功能阐述一起交开发者确认。

## 8. 开发顺序

脚手架规定的顺序，别倒着来：

1. **按 lock 装依赖**：`cd backend && npm ci`；`cd frontend && npm ci --ignore-scripts`。`npm ci` 很慢，shell 工具可能在装完前提前返回或报“超时”——那不是失败，把超时设到 300 s 以上或轮询到真正结束，**不要**当失败反复重跑；
2. **先定数据放哪**（P4 第 4.1 节 四类）；
3. **先做后端 service 层**，用 `buiTable('表名')` 直查本用户 schema；再按 A1 页面反推的接口写 route 层；
4. **接口先有契约，前端在后端之后**：每个公开接口在 `frontend/schema/api/<operationId>.yaml` 落一份只含一个 operation 的完整 OpenAPI 3.1 文档（`method + path` 算一个接口，一个接口一个文件），后端按它实现、前端只按它调用（method、path、参数、响应逐项匹配）、本地 mock 也按同一 YAML 实现；**没有契约或契约不完整时停止开发，不得从 route / service / 测试 / 注释里猜接口**。前端请求与响应类型依据对应 YAML 建立；`scripts/gen-types.ts` 是历史遗留的后端 model 类型同步辅助，**禁止用于 `sdk.api.request` 公开接口**。所有前端源码在 `frontend/src/` 下，不要在仓库根建 `src/`；
5. **每做完一层测完一层**；
6. **发布前真跑一遍**：`./run-dev.sh start` 同时拉起后端（:8000）与前端（:5175），打开页面**确认数据真的从后端加载出来了**（页面能开不算）；
7. 写代码前在项目根 `git init` 并提交模板基线，之后每个独立可验证的改动单独 commit——没有基线就看不出“模板 vs 改动”。

## 9. 后端实现

**正本是 `backend/README.md`，动手前通读；本节是落地顺序与易错点。**

按 models → services → routes 三层实现三类 API：

| API 类 | 内容 | 特有纪律 |
|---|---|---|
| **CRUD**（编辑回流） | 数据管理页的增删改查 | 写入前按**列注释声明**校验写权（`editable:user` 才接受用户写）；写入带来源标记 `user_edited`、更新审计四件套并比对 `row_version`；***写接口必须幂等***（键是宿主注入的 `X-Goalfy-Business-Request-Id`，相同 ID = 同一逻辑操作）；删除走确认语义（软删或二次确认由 A1 设计定） |
| **统计聚合**（喂看板） | 看板页的指标与列表 | 按 P5 第 4.2 节 的指标清单实现，每个指标能说出来源表与聚合口径；单查询在 `statement_timeout`（10 s）内、响应体 ≤ 1 MiB；大结果**必须分页** |
| **生产回流** | 场景包产出入库 | 按 A1 的入库语义实现（直接入库 / 草稿待确认）；来源标记 `generated`、`updated_by='agent'`、写入 `last_run_id`；***`editable:user` 列不得覆盖*** |

**生产侧还有第二条回流通道**：配套场景包的编排型 TPE 经平台级业务应用数据集 FA（cn-qa 现名 `Business_app_fastagent`，business-app-creator S3-2.4）通过它的 HTTP 工具读写**同一份** schema，不进沙箱——应用后端直连与这个 FA 是同一数据的两条路：**应用自己的前后端数据流通全部由你在后端代码里实现**（本节的 CRUD / 统计 / 回流接口 + `buiTable()` 直连），FA 只服务项目内的 agent。应用设计要吃下三件事实：

- **启动铺底不经 FA**：发起业务路线时要带上的上下文由用户在入口表单里填写、或由应用后端拼进发起报文（`submit_data`），**没有表单预填通道**（平台侧与脚手架侧的 prefill 已下线），FA 只管执行中按需取数与收尾回写；
- **FA 的写权与你一致**：只写 `editable:agent` 列、模板结构只增不改；它的 `found=false` 是常态结果——界面与后端把空数据当缺省处理，不当错误；
- **平台元数据展示有滞后**：FA 写入后界面直连立即可读，滞后的只是平台侧数据集的行数/统计展示，不要为此加同步回调。

后端硬约束速查（正本细则在 `backend/README.md`，此处只列最易踩的）：

- 响应一律用 `response.ts` 的 `ok/okEmpty/list/fail` 构造——**字段是 `msg` 不是 `message`**、`data` 非 null 非数组对象（列表包一层 `{ items: [...] }`）、业务失败也 HTTP 200、自定义码 ≥ 1000（1~999 是平台保留段；1000~1099 是脚手架 `BACKEND_CODES` 保留段：1004 `FORBIDDEN_BY_PERMISSION`、1005 `CONFLICT`、1006 `COLUMN_NOT_WRITABLE` 等；**业务自定义码从 1100 起**；`fail()` 对 `code < 1000` 直接抛 `RangeError`）。前端 SDK 信封守卫与 max 转发层**共同**校验，任一处不符就折成 `BAD_GATEWAY`，业务码与提示语全丢；
- 引用表只有一种写法 `buiTable('orders')`，***绝不写死 schema 名或 handle***——每个用户实例的 schema 都不同（`bui_{data_uid}`），写死了第二个用户就炸；
- **只做 DML**：应用角色没有 DDL 权限（数据库层拒）；要改表回 A2 出新模板版本；
- **连接经 dataset-proxy，三条会被直接拒**：`BEGIN`/`COMMIT`/`ROLLBACK`（autocommit 单条语句，要原子性压进一条 SQL：CTE、`INSERT ... ON CONFLICT`、单条 `UPDATE ... FROM`）、`SET ROLE`、`SET search_path`；
- 上游超时 13 s、`statement_timeout` 10 s——**只剩 3 s 余量**，别设计需要长时间计算的同步接口；
- `async` 路由必须 try-catch（Express 4 不转发 rejected promise，漏写 = 请求 hang 到超时）；
- 数据库判空在函数体内（模块顶层判空 = import 即 throw = Pod CrashLoopBackOff）；
- 身份从 `getContext(req)` 取宿主注入的 `X-Goalfy-Context`（没有 `Authorization`、没有 `X-Goalfy-User-*`）；隔离维度 = viewer × 实例；写接口用 `canWrite` / `requireBusinessRequestId`；
- 线上只注入三个 env（`DATASETS_DATABASE_URL` / `DATASETS_DATABASE_TYPE` / `DATASETS_MANIFEST`）+ `PORT`，**没有别的注入通道**——需要第三方密钥先与平台定；
- 生产态不开 CORS（后端在公网域名上，不是内网 Service）。

`cd backend && npm test` 用进程内的 PG 兼容测试库，不需要数据集凭证，永远不碰真实 schema——含信封契约自检，先过它再联调。

## 10. 前端实现

**正本是 `frontend/README.md` 与 `frontend/docs/business-ui-guide.md`；demo 只用于理解协议，第一规则禁止复用其页面结构、排版与视觉。**

### 10.1 SDK 两层与保留件

- **App 层**（顶层 `sdk`）：`session`（实例上下文与权限，`permission='view'` 时置灰全部发起入口）、`projects`（归属项目集合，拉推成对）、`getProject` / `createProject`、`inbox`（跨项目待办）、`api`（自家后端通道）、`storage`（viewer × 实例隔离的界面意图，32 key / 512 KiB）、`ui.reservedAreas`（宿主浮层占用区，交互组件必须避开）、`theme`；
- **项目句柄层**：`business`（start / onCall / reply / onResult / 查询面）、`upload`、`file`、`chat`、`observe`、`info`、输入互斥；
- **保留件必经，不改不删**：`useProject` / `useProjectExecution` / `useProjectDraft` / `useInbox` / `useRuntimeUserFiles`、表单渲染、错误归一化、`FileField`、`MarkdownContent`、局部错误边界。表单预填（`useFormPrefill` / `getFormPrefill`）已下线，脚手架里若仍残留相关文件或文档，**不接入、不依赖**；表单 schema 的唯一真源是契约包 `forms/` 与 `getForms(formId)`；
- **一切平台调用经 SDK**：后端 API 走 `sdk.api.request`（path 纯路径、GET/DELETE 无 body、`query` 仅标量或一维数组、载荷 ≤ 256 KiB；`code !== 0` 必须给用户反馈，无静默失败、无自动重试）；项目文件走 `project.upload` 只传路径，应用级持久文件走 `sdk.file`（正本 `src/sdk/docs/application-file.md`）；**禁 fetch/XHR/axios（ESLint 硬禁）**。

### 10.2 三个必备页面

- **首页**：根路由呈现欢迎页 / 业务展示页（可以就是看板），非脚手架占位、非空白、不直落深层表单；待办入口带 `useInbox().unreadCount` 角标；
- **项目列表页**：`sdk.projects.list` 打开/翻页/手动刷新时拉（禁轮询）+ `onStatusChange` 按 `projectId` 就地更新（禁止收推送就整页重拉）；行内有项目名、状态、更新时间；临时项目不入列表是设计使然；空列表引导去发起首个项目；
- **消息中心**：必经 `useInbox()`（合流、去重在 SDK；禁止页面自行订阅 `sdk.inbox` 手写状态机、禁止把待办写进 storage）；条目带归属项目、表单显示名、下发文案；点击导航到对应项目的应答状态并走对账链路；已读态只影响展示。

### 10.3 四类业务页面

- **看板**：数据只来自后端统计 API；图表选型自由；每个数值可溯源（点开能看口径）；空数据引导态；跟随 `sdk.theme` 亮暗；
- **数据管理**：控件按列类型渲染，**只对 `editable:user` 列开放编辑**，`agent` 列只读并标注来源；提交走后端 CRUD，错误按信封 `code/msg` 呈现；批量与删除有确认；
- **业务发起（入口表单）**：必经 `useProjectDraft(draftKey)`（一个表单会话一个草稿句柄；`restoring` 期间禁提交）；入口表单按 `getForms(formId)` 的静态 schema 渲染，**没有预填**：用户自己的门店 / 账号等稳定信息若要少填，由应用后端在发起时拼进 `submit_data`（S3-2.4 的"时机 1"），不在表单里回填；文件字段经 `project.upload`（草稿句柄上首个 upload/start 懒创建临时项目，对 App 透明）；**提交必须等全部上传终态**（按钮禁用 + onFinish 内拦截）；`start()` → `accepted` 转正入列表、导航到项目页并写提交快照；`rejected` 原窗重填（保留草稿、复用同一提交记录）；`failed` 展示结构化错误不自动重试。复用已有项目 = 用户在下拉框显式选中（选项只来自后端项目列表）后在该项目句柄上 `start()`；
- **项目页**：项目状态与应答过渡按 §4.3.1 接入；阶段进度按业务事件（订阅一次、纯归约、live/backfill/replay 同构消费，禁轮询）；服务端调起表单到达 → 导航到可恢复的应答状态，按 `formId` 从契约区取 `inputSchema` 渲染、`arguments` 只做回显；**交付审阅页**按 `display` 五字段语义渲染（`headline` / `facts` / `notices` / `sections`，`schema_version` 不渲染），业务字段按 A1 出口设计呈现，**只在存在活动 Call 时渲染动作按钮**、只提交 `action_key`，`agent_gate` 只读；执行记录三级下钻（`list` → `get` → 三件套）每级只拉一次；已提交表单以 key-value 展示（label 用 schema title、选项值映射显示名、file 字段只读卡片，禁裸 JSON、禁裸路径）；Runtime 用户文件经 `useRuntimeUserFiles`（全量替换语义）。

#### 10.3.1 应答提交到运行的页面过渡

项目层通过 `useProject(projectId)` 持有一个句柄，并在同一层调用 `useProjectExecution(project)`；应答页、进度页与交付审阅页共享返回的 `projectStatus`、`pendingRun`、`submitting`、`workflowRuntimeId` 和 `reply`。实际应答入口使用 `execution.reply`（与原 SDK `reply` 签名相同），由保留件封装 `sdk.projects.onStatusChange` 的当前 `projectId` 筛选与启动过渡；不要绕过它另调 `project.business.reply` 后手写另一套过渡。**不得在每个子路由重新创建句柄或执行态保留件，也不得因 inbox / pending 列表变化重建它们**；消息中心只负责提醒与导航。`onCall` 监听也不得因子路由、`pathname` 或导航函数引用变化而重建，以免重新订阅触发 replay，把用户拉回旧表单。仅把辅助函数导出、未在实际页面接入，不算完成。

| 依据 | 页面反馈 | 提交与过渡边界 |
|---|---|---|
| 用户通过校验并点击应答提交 | 立即显示“正在提交”或同义反馈，禁重复提交 | 提交握手尚未完成；不能显示为已受理或已执行 |
| `reply()` 返回 `accepted`，当前项目尚未收到 `running` | 显示“已受理，准备继续” | 提交握手完成；启动过渡仍保留，不能恢复为可再次应答的旧表单 |
| 当前项目收到 `running` | 立即切到执行中的展示，不等业务事件、`getWorkflowRuntime` 或 `getRuntimeForms` 刷新 | 启动过渡结束；若业务结果仍未返回，提交锁仍保持，运行推送不代替第三次握手 |
| `rejected` / `failed` / 发送异常 | 分别恢复原窗重填或显示可读错误 | 结束本次启动过渡；不自动重试，不把其他项目或旧运行状态当成本次成功 |
| 权威终止状态或新的待处理 Call 到达 | 展示终止/错误，或进入新的应答状态 | 按权威事实结束启动过渡，不必等一个不会再来的 `running`，也不把它解释为运行成功；未完成的提交锁仍由业务结果或发送失败收束 |

项目执行态只可优先投影到 `execution.workflowRuntimeId` 对应的**本次应答 Runtime**，不能把同项目历史 Runtime 或已有终态改显示为 running；阶段进度、已提交内容和交付仍以各自权威数据为准。`pendingRun` 是短暂的界面过渡，**不能落为服务端业务事实或持久化运行结果**。同一项目切换应答页与进度页时继续消费原句柄的结果和状态，不能丢提交等待者、闪回旧表单或重复发出 `reply()`。真实离开项目或切换项目时按保留件生命周期清理；刷新后的恢复走服务端权威数据，不把内存过渡伪装成已恢复的运行。

### 10.4 表单与文件的通用纪律

- 三类回显各归其位：草稿回显（`sdk.storage`，稳定 `draftId`）/ 驳回回显（`rejected.next.arguments` 原窗重填）/ 已提交回显（`getRuntimeForms` 权威源，提交快照兜底）；`accepted` 后删草稿写快照，`rejected` 保留草稿；
- 校验失败：视口顶部居中一条 toast，全部无效项高亮，首个无效项展开、滚入、聚焦；`form-submitting` 期间禁用全部写入口并持续显示原因；
- 文件字段：值只能由上传产生、全程只读卡片、上传中有状态、失败可删后重传、编辑态有替换/清除、多文件按契约数组提交；展示 URL 经 `getViewUrl` 现取现用；下载只经 `project.file.download` 且只在用户点击处理器内调用，禁自动/批量、禁自动重试；
- **Excel 等结构化上传的表单内预览**：文件本体照常上传得 path；预览/填入在浏览器端解析（表头 + 前几行），解析失败不阻断上传；
- **应用级文件库**（`sdk.file`，P5 第 2.2 节 勾选了才做）：`upload(file)` 不建项目、返回的 `path` 是唯一可写进 formdata / storage 的值；`list` 是不透明游标分页，只在打开、刷新、用户点“加载更多”时调（禁轮询）；`getViewUrl` 短时效、用完即弃；`download` 只在用户点击处理器内调。表单里用脚手架 `shared/ApplicationFileField`（上传 + 历史分页 + 图片/PDF 预览 + 下载 + 多选，值只存 path）；`shared/FileField` 仍是项目级、必须传项目句柄。选中的应用文件 path 直接写进 `business.start` / `reply` 的 formdata，宿主发帧前重新解析并登记给目标项目，解析失败会阻止启动而不会静默漏附件；源文件不因关联项目而移动。`permission='view'` 时上传入口必须禁用。capability（upload / file.read / file.download）由 `npm run check` 自动扫描；
- **可排序表单**：数组字段可做拖拽排序，提交按数组顺序；顺序语义以编排型 TPE `input_schema` 为准（P5 第 4.4 节）；
- 禁止把当前路由写进 `sdk.storage`（宿主已持久化 last_route）；禁止业务代码调 `sdk.notifyRoute` / `onHostNavigate`。

### 10.5 构建与打磨（前端设计工作流后半程）

原型确认后，原型代码直接演进为正式实现，不重写。按顺序：

1. **用精选组件构建**（`components` 指南，MIT 白名单：Magic UI / Cult UI / KokonutUI / shadcn/ui；***不从 Aceternity、ReactBits、Vue Bits、Tremor、21st.dev 或名单外的库取代码***）：一屏至多一个主视觉件；取来的组件适配项目 token、响应式、内容、性能与 `prefers-reduced-motion`，不原样出厂；UI 库与样式方案自由（antd + Less CSS Modules 是默认可替换），限定业务样式作用域、支持宿主亮暗、避开 `reservedAreas`；
2. **打磨交互工艺**（`emil-design-eng` 指南）：每个动效有目的；高频操作即时；缓动时长跟手；按压/悬停/聚焦一致；过渡可被安全打断；凡引起内容变化的交互都有过程动画不闪烁跳变，`prefers-reduced-motion` 时去位移缩放、保留并缩短透明度过渡；
3. **真实渲染、走一遍、再修一轮**：跑起来用浏览器看真实渲染；桌面与移动各过主旅程和非正常态；查键盘导航、可见焦点、对比度、触控目标、长文本、溢出；先修结构再修装饰；***至少完成一轮渲染页修正，不许只看源码就宣布完成***；
4. **对照设计文档逐条核对**模块划分、页面结构、交互流转、视觉层级，不一致改到一致；**测试每一个可交互的地方**——能点、能填、能拖、能切换的都实际操作一遍；
5. **冲突处理**：开发中发现设计做不了（SDK 拿不到的数据、编排型 TPE 不发的事件）→ 回 A1 改设计、带更新后的原型重过确认；***禁止静默改设计继续往下做***；
6. 冲突规则：用户要求与仓库约束 > 一切 guidance；产品清晰与任务完成 > 视觉新奇；无障碍与减少动效 > 动画偏好；本节白名单 > guidance 目录里的更大清单。

文案与注释一律中文；组件单一职责，超 ~200 行考虑拆分。

## 11. 本地测试

正本：`frontend/README.md` §五「完成定义与自测矩阵」（唯一权威）与 `frontend/docs/dev-host-testing.md`。顺序：

1. 后端 `npm test` 全绿（含信封契约自检）；
2. `./run-dev.sh start` 真跑：Direct Mock 下走通 **自测矩阵 A–E 组**（三面 / 入口表单两段式 / 项目详情 / api 通道与路由 / 旗标态 `?mock=view|preview|permission-cycle|storage-off|attention|frames-off`，以 `frontend/README.md` §五自测矩阵为准）——mock 验证的是界面状态机完备性，**mock 跑通 ≠ 功能正确**；**Direct Mock 下 `sdk.api.request` 全部在内存 mock 里应答，根本不会打本地后端**（vite 没有 `/api` 代理），所以"本地界面数据展示正常"**不能**作为前后端联调证据；后端只能靠 `npm test` 与浏览器直连 `:8000`（本地才开 CORS）单独验；真实链路（宿主服务端转发、身份注入、真实 schema）只在上传后的远端调试阶段（A4）验证；需要宿主主动事件或 Bridge 证据的场景用 Dev Host Mock（:5176）；
3. **mock 可测边界是封闭白名单**：业务事件真实语义、真实业务路线行为、真实文件 URL、开发者后端真实行为等**不可 mock**——不为了可测而改 mock/固定层、不自造桩、不降断言，在完成回复中标注“留待远端调试阶段验证”；
4. **Playwright 动态验收门**：按真实页面、`schema/` 与路由动态编写用例，覆盖表**必须包含编辑场景（写权校验、误删确认、编辑后看板刷新）与看板场景（空数据、分页）**，禁止复制 demo 字段或选择器；断言谓词先证明自己能失败；这套用例在 P6 第 11 节 要对着预部署部署物整套重跑，所以从第一条起就不绑 mock 数据的具体值——换成真数据仍成立；用例名带《业务应用计划书》⑤ / ⑦ / ⑨ 的条目编号，A4 才能对账“确认过的功能都测了”；
5. `cd frontend && npm run check` 通过（type-check + lint + capabilities/packs 校验）；交付前 `npm run check:release`（加示例残留检测：示例目录、演示包契约、起始页占位、`packs` 未声明真实场景包，任一残留即失败）。
6. 业务页面不写单元测试；`npm test`/`vitest` 跑的是脚手架自身的测试，与 App 完成定义无关，不需要运行。

前端校验项与后端校验项转入结果检查表（状态 `pending`，A4 用预部署真实数据闭合）。

| 项目 | 业务应用之下的一层：用户的一次计划选择，一次业务路线运行及其表单、消息、文件、交付都装在项目里；由用户在应用里**创建**（表单提交时两段式建项目）或**复用**（下拉框选已有项目）；应用经 `sdk.projects` 拿到本实例名下全部项目（P5 第 2.1 节） |
| 《业务应用计划书》 | A1 的交付物：一份 MD，含功能清单、每页截图展示、后端功能阐述、自动化测试计划；开发者确认后才进 A2/A3，之后按它干、不再问（P5 第 5 节） |
| 应用级文件 / 项目文件 | `sdk.file`：不依赖项目、跨项目复用的持久文件（资料库）；`project.upload` + `project.file`：属于某个项目的文件。两者并存，表单值都只存 workspace 路径 |
| business_ui | 业务应用的发布单位：独立资产（家族 + 版本），挂 1 个场景包 + ≤1 个业务应用数据集模板；create → 上传 deploy 源码包 → finalize 上线（A4/A5） |
| 业务应用数据集 | 应用的后端数据库：用户点开应用时从模板 copy 出的专属 PG schema，存用户记载、交互历史、交付与流转数据；应用后端直连 + 项目内 agent 经业务应用数据集 FA 访问同一份 |
| 业务应用数据集模板 | 开发期定稿的表结构模板资产（含逐列声明与审计字段）；用户首次打开应用时从它 copy 出业务应用数据集 |
| 业务应用数据集 FA | 平台级 FastAgent（cn-qa 现名 `Business_app_fastagent`，随 `business_app_dataset` 工具集上线）：场景包编排型 TPE 经它的 HTTP 工具读写业务应用数据集，不进沙箱（A3 第 3 节三件事实）。**这是给项目内 agent 用的通道**；应用自己的前后端读写走后端直连 `buiTable()`（A3 第 3 节） |
| `buiTable('表名')` | 后端引用自己 schema 里表的唯一写法，从 `DATASETS_MANIFEST` 解析真名（`bui_{data_uid}`）；不写死 schema 名、不用 handle |
| 三个必备页面 | 首页 / 项目列表页 / 消息中心——脚手架硬约束，只约束存在且可达，不约束形态 |
| 可编辑性声明 | PG 列注释里的 `[editable:user\|agent\|system]` 前缀，谁能写这列的唯一正本 |
| 创建态 / 进行态 | 应用页 = 发起一切；项目页 = 只看进度和回表单 |
| 生产回流 / 编辑回流 | 场景包产出写库 / 用户手动改库——两条写入通道，共治规则见约束 9 |
| 信封 | 后端响应固定 `{code, msg, data}`；`msg` 不是 `message`，`data` 非 null 对象 |
