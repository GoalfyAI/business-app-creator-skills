## 1. 用户画像七问

服务 G1 第 2.2 节读材料判缺口。开发者说不清服务对象时，按这张表分轮问；第三列说明每一问的答案会决定后面哪件事，问不到的答案就是要标出来的假设。

| 要问什么 | 例，餐饮场景 | 它决定后面什么 |
|---|---|---|
| 服务谁：职业、角色、经营形态、规模 | 单店或小连锁的餐饮老板，自己管运营 | 业务终点与路线的用词、后续所有文案的语域 |
| 他们眼里的专业词汇与判断标准 | 爆品、客单价、复购、差评 | 正反例的措辞、验收判定的措辞 |
| 他们的决策节奏与使用场景 | 每天营业结束后看十分钟、周一定下周活动 | 路线数量与粒度、哪些环节值得最终用户确认 |
| 现在怎么做、卡在哪 | 手工翻评价、凭感觉定活动 | 替代方案与基线 |
| 有几类人群 | 老板、店长、运营专员各自关心什么 | 是否需要多条路线或多套子画像 |
| 有没有可参考的资料与打法 | 同行怎么做、他自己的活动与复盘、内部 SOP、行业报告、看好的竞品 | 候选路线的起点；先问开发者，再自己调研 |
| 高风险边界与不可触碰 | 涉及资金、发布到公开平台、处理顾客个人信息 | 红线与授权边界 |

## 2. 信息缺口六类

服务 G1 第 2.2 节读材料判缺口。把开发者材料里缺的东西归到六类之一，对照第三列决定是问开发者、自己查、用默认，还是等授权；分错类会把该自己查的事推给开发者，或把该开发者拍板的事用默认值糊过去。

| 缺口类型 | 例子 | 处理 |
|---|---|---|
| 意图缺失 | "帮我做个东西" | **必须**向开发者询问明确目标，**禁止**先设计方案 |
| 关键参数缺失 | 创建任务未描述业务场景；诊断任务未指定目标 | 目标明确但缺执行前提，**必须**向开发者索要 |
| 知识缺失 | "我不知道需要哪些工具" | 属于你的调查范畴，纳入 G2 摸底，**不要**让开发者回答平台问题 |
| 工程偏好缺失 | 命名风格、代码组织、等价展示细节 | 存在可逆且不改变业务语义的默认时采用并记录影响，不当阻塞项 |
| 产品决策缺失 | 路线、审阅责任、产品形态、最终用户介入 | 放入决策卡集中确认；只有一个独立决策时单项询问；**不得**由你用默认值 |
| 授权缺失 | 发布、删除、收费、真机运行 | 在对应动作前明确确认，**不得**用默认值代替授权 |

## 3. 访谈清单

服务 G1 第 2.2 节读材料判缺口。每轮访谈从这里取一到三项，不一次全问；下方"启动前至少明确"是进入收敛一之前的最低信息量。

按需组合，每轮一到三个事项：

- 业务场景：业务是什么、服务谁、现在怎么做、最终要什么结果
- 参考素材：有没有已执行项目、完整日志、文档、SOP、已有能力容器
- 业务边界：哪些系统、数据、权限、成本、时效、合规条件不能改
- 成功标准：什么最终用户可见结果能证明这件事做成了
- 任务模式：新建、优化已有，还是从执行失败的项目反查原因

启动前至少明确：业务目标、最终用户、业务终点、关键输入与产出、操作对象、可读取的证据、高风险边界、初步验收标准。其余平台知识由你自己调查。

## 4. 三层目标与客户类型

服务 G1 第 2.3 节收敛一问题一。第一张表把一句业务目的拆成客户期望、产品承诺、本次任务三层，防止三层互相冒充；第二张表说明同一件工作对三类客户是三种产品，判断客户类型时逐列对照，四列就是你给开发者的对照材料。

| 目标层次 | 需要明确的内容 | 小红书图文示例 |
|---|---|---|
| 客户期望 | 希望改善什么业务状态 | 减少内容制作负担，或增加工作日下午的有效咨询 |
| 产品承诺 | 能够稳定负责哪段工作，以什么证据验收 | 基于已确认事实，完成可审阅和采用的内容 |
| 本次任务 | 在本次条件下具体交付什么 | 制作一条围绕某款在售商品的图文 |

三者有关联，但不能互相替代。同样的工作，对不同客户是不同产品：

| 客户与情境 | 真正购买的改善 | 可以承担的责任 | 主要验证方式 |
|---|---|---|---|
| 已有选题能力、制作积压的内容团队 | 加快符合简报的内容生产 | 在事实、风格和格式约束下交付素材 | 可用交付耗时、返工次数、单位采用成本 |
| 缺少专职运营、难以稳定更新的店主 | 减少从选题到备稿的持续负担 | 基于经营事实，帮助选题、制作和审阅 | 店主介入时间、实际采用、持续使用 |
| 想改善特定时段客流的门店 | 改善某段营销或获客工作 | 根据可控范围选择内容、营销执行或增长服务 | 相应的行动、有效咨询、到店或交易证据 |

## 5. 研究十问与价值假设句式

服务 G1 第 2.3 节收敛一的五问与收敛落点。十问表是五问的完整版，五问答不全时逐行补，第二列是每一问应该收成什么结论；价值假设句式是收敛一的最终产出格式，每个括号必须有来源类型；"可采用"五条是验收标准的操作化模板。

| 需要研究的问题 | 应形成的结论 |
|---|---|
| 谁使用、谁付钱、谁决定采用、谁承担结果 | 使用者、购买者与责任人的区别 |
| 什么事件触发需求，多久发生一次，不处理会怎样 | 使用时机、频率与问题严重度 |
| 客户现在怎么完成，为什么不继续使用现有办法 | 替代方案及时间、成本、质量基线 |
| 主要瓶颈是信息、判断、执行、协调还是质量 | 产品应介入的位置 |
| 要改变哪个可观察状态，交付怎样帮助这一变化 | 从交付到采用再到效果的因果假设 |
| 哪些部分可控，哪些依赖客户和外部平台 | 产品承诺、必要前提与外部依赖 |
| 什么算可用、完成和失败，如何验收 | 交付标准、效果观察标准与失败标准 |
| 需要什么资料、预算、时效与授权，缺失后如何处理 | 最低输入、适用条件、降级与停止条件 |
| 客户差异哪些只需配置，哪些会改变业务方法 | 可复用范围与产品边界 |
| 改善是否支持付费，价格能否覆盖交付成本 | 可验证的价值假设与服务经济性 |

答不出的标未知并配验证办法。

**价值假设句式**：为【具体客户】，在【触发情境】下，以【时间、预算和业务约束】完成【可验收的工作】；相较【现有办法】改善【可观察指标】。产品负责【范围】，客户负责【必要投入和决定】，通过【证据】判断完成；出现【条件】时补充、调整或停止。

**"可采用"的操作化**：必要事实无误、素材与实际经营相符、符合约定内容要求、文件可用、必要修改已处理。

## 6. 关键决策十问、三条独立轴与四个时机

服务 G1 第 2.4 节收敛二。十问表是关键决策清单的列定义，每个决策逐行回答；三条轴是问题四的标注口径；四个时机表用来判断哪些工作属于模板制作期、哪些属于客户初始化、哪些才是每次运行要做的，防止把初始化工作塞进每次运行。

只挑显著改变客户价值、资源投入、对外承诺或后续路径的决定。每个决定回答：

| 需要回答 | 应落下的内容 |
|---|---|
| 为什么此时需要决定，可以怎么选 | 触发条件、推荐方案与实质备选；适用时包括补证据、暂缓或转交 |
| 依据什么，哪些只是推测 | 业务事实、历史记录、外部证据、专业规则与假设分别列明 |
| 哪些条件会改变推荐 | 供给、时段、成本、受众和偏好变化的影响 |
| 信息不足怎么办 | 可以读取、值得补问、可用默认值和应暂缓的界限 |
| 谁适合判断，谁有权决定 | 确定性规则、AI 建议、业务负责人和领域专家的职责 |
| 什么动作得到了授权 | 对象、账号、金额或数量、时效和范围；沿用已有授权的条件 |
| 判断错误会怎样 | 影响大小、可逆性、发现时机和补救代价 |
| 用户看到什么才能有效决定 | 建议、关键证据、主要取舍、未知项及确认后实际发生的动作 |
| 决定怎样执行，失败如何处理 | 具体动作、状态保留、重试、恢复与转交方式 |
| 如何验证，并让下一次工作受益 | 验收证据、复查时机、修改及拒绝理由、实际行动与观察结果 |

每项重要规则都要能给出一个改变选择的反例。

**三条独立轴**互不排斥：证据够不够；判断由谁负责；动作得到什么授权。证据充足不代表已获得行动授权，用户批准不代表专业判断正确。

**四个时机**分开：

| 时机 | 需要完成的工作 | 主要产出 |
|---|---|---|
| 模板设计 | 研究客户工作、价值承诺、专业判断和形态必要性 | 收敛一至四的结论及可验证案例 |
| 客户初始化 | 建立业务事实、偏好、资料来源、默认目标和授权 | 可以持续维护的客户情境与必要配置 |
| 每次使用 | 读取有效信息，识别变化和缺失，完成必要判断与执行 | 可采用结果、当前状态和实际行动记录 |
| 周期复盘与维护 | 检查采用、质量、成本及方法适用性，处理资料和规则变化 | 经验证的调整及受影响对象的处理结果 |

模板承担可复用的业务研究，不让每位客户重新定义方法；系统沿用已确认且有效的事实，不每次从"为什么做营销"开始访谈；曾经有效的资料和判断也不永久生效。

## 7. 正反例的四处复用

服务 G1 第 2.5 节收敛三问题二。写正反例时先看它们后面会被用在哪四处，据此决定颗粒度：能直接当运行输入、能写成示例、能填进表单的正例才算具体。

| 用途 | 怎么用 |
|---|---|
| 判断需求理解是否正确 | 把正例的处理过程讲给开发者听，错了立刻能发现 |
| 编排型 TPE 运行验证 | 正例直接作为代表性输入，见 G4 |
| 场景 Skill 文件 | 写成示例，运行 Agent 照着做，见 P3 知识写作 |
| 真机验证 | 照着正例填入口表单与运行中表单的答案，另构造一条自然业务需求核聊天路由，见 G5 |

正例定义"好"的形态，反例定义"错"的边界；被圈定的关键产出环节，其验收判定从这里长出来。

## 8. 形态比较基线与三种形态

服务 G1 第 2.6 节收敛四。第一张表是公平比较的基线：逐行先看第二列"直接使用能力容器可能已能解决"，剩下的才是第三列应用要证明的价值；第二张表按"适用情境 / 成立条件"选三种形态之一；第三张表是业务环节分工的示例，写必要对象与操作时照它的四列拆。

公平的比较基线：使用同一套专业能力，在模型、工具、资料、授权和人工支持相当的条件下，客户直接使用能力容器，还要承担哪些显著负担。

| 客户承担的工作 | 直接使用能力容器可能已能解决 | 业务应用需要证明的额外价值 |
|---|---|---|
| 获得专业建议并执行任务 | 复用业务路线、工具和判断规则 | 让客户更容易在业务情境中调用、掌握和调整这些能力 |
| 提供门店、商品和品牌资料 | 读取项目资料或已连接的数据源 | 直接维护当前有效资料，清楚知道变化会影响哪些工作 |
| 知道工作进行到哪里 | 查看单个项目记录、运行状态和结果 | 以业务对象汇总多次工作的当前状态，快速找到需要处理的事项 |
| 审阅和修改结果 | 在对话、表单或产出文件中反馈 | 提供适合图文对比、局部修改、筛选和批量处理的操作方式 |
| 找回并复用已有内容 | 检索历史项目和文件 | 按商品、用途、版本和采用状态组织内容，减少查找与核对 |
| 连续处理下一轮工作 | 再次调用已有能力容器和资料 | 保留业务情境、减少重复组织，并在事实变化时提示受影响的对象 |

这些差异都是待证明的收益。数据持久化、人工审阅、多次执行、定时触发本身不是应用独占能力。

| 可选形态 | 适用情境 | 主要成立条件 |
|---|---|---|
| 直接使用能力容器 | 任务边界清楚，输入和结果易表达，跨任务整理负担较小 | 专业能力足够，客户能够方便地获得和采用结果 |
| 能力容器加轻量交互，或接入现有系统 | 缺少少数可视操作，或客户已有资料和业务工作台 | 补足关键操作即可，避免让客户重复维护两套信息 |
| 独立业务应用 | 存在明确、持续的业务对象管理和直接操作需求 | 新增收益足以覆盖初始化、学习、开发和维护成本 |

形态选择的产出：能力容器使用基线、尚未解决的客户负担、必要的对象与操作、替代形态、应用新增成本、验证指标、停止开发或收缩形态的条件。

**业务环节分工示例**，小红书图文：

| 业务环节 | 专业执行应承担的工作 | 适合由应用提供的操作 | 有效的人为决定 |
|---|---|---|---|
| 确定本次需求 | 识别需求与素材条件，必要时建议补充或暂缓 | 展示本期任务与待补事项，从具体商品发起制作 | 确认本期需求、供给和优先事项 |
| 选择方向 | 根据已确认事实提出方向，区分证据与假设 | 对照查看关键事实、建议和可调整条件 | 核实门店事实，选择符合经营意图的方向 |
| 准备素材 | 检查商品、素材与使用范围是否匹配 | 浏览、关联、筛选素材并标明缺失项 | 提供或确认真实素材及使用范围 |
| 制作与审阅 | 生成、校验并处理修改意见 | 对比图文版本、修改局部、查看处理状态 | 接受结果，或指出具体事实和表达问题 |
| 实际采用 | 在能力与授权范围内执行，或交付可用文件 | 区分待审、可用、已采用等业务状态 | 决定采用；实际发布时明确账号、版本与时间 |
| 后续复用 | 读取有效事实、拒绝理由及可获得的反馈 | 按商品和用途检索内容，提示需要复核的关联项 | 确认事实变化，调整下一次约束与优先事项 |

## 9. 最终审阅三形态与终态顺序

服务 G1 第 2.7 节收敛五问题一。开发者选审阅形态时，用这张表的"运行语义 / 适用信号"两列向他说明每种形态意味着什么；下方终态顺序与纪律是写修订续接方式时必须遵守的平台规则，G1 正文只用业务语言，平台名称留在这里。

交付核验回答"这份结果是否真实、完整、可交付"，最终审阅回答"业务上是否接受这份结果、是否需要修订或改走其他路线"。两者**禁止**合并：输出契约、数值、证据和文件校验通过，不代表最终用户或运行 Agent 已完成业务验收；节点级 `sa_handoff` 和质量检查编排型 TPE 也不是最终审阅的替代品。

| 形态 | 运行语义 | 适用信号 |
|---|---|---|
| `user_gate + ask` | Runtime 向应用下发冻结交付和已声明动作；最终用户完成三次握手后，Runtime 直接执行所选的完成、失败或新路线动作，不额外唤起 Agent | 业务完成需要最终用户批准、满意度确认、方案选择、修订、改路线或高风险授权 |
| `user_gate + result` | Runtime 按既有链路自动交付并结束，不要求最终用户或运行 Agent 参与 | 生成且核验通过即达到业务终点，不需要额外业务判断 |
| `agent_gate` | 唯一主动唤起运行 Agent 评价或选路的最终审阅边界；Agent 按开发者确认的可验证标准选择已声明动作 | 接受标准客观、可执行且确实需要 Agent 判断 |

纪律：`user_gate` **不得**再叠加一层"交给 Agent 收尾"；只有路线明确声明 `agent_gate`，或最终用户选择了已声明的"交由 Agent 处理"动作时，才建立 Agent 边界；`apc_skill`、节点 `sa_handoff`、业务应用都**不得**用额外提示词模拟这次接管。

终态顺序固定：解析真实 TaskPoint 输出；核验交付资格；冻结本次 Delivery；执行已声明的最终审阅；根据审阅动作完成业务、结构化失败或开启新路线。审阅明确接受前，**禁止**把结果展示当成已验收，**禁止**把 Business 标记为已完成。修订、重做或改路线必须保留当前 Delivery，按当前契约新建运行实例，不覆盖旧结果。

能力容器只声明对外稳定的资产契约：中间节点用 `sa_handoff`，最终审阅用 `delivery.review`。Max Runtime 如何生成 Agent 边界通知、注入执行上下文或封装内部控制消息，属于平台实现细节，**禁止**复制进路线对象、`apc_skill`、场景 Skill 或应用契约。

## 10. 红线四类

服务 G1 第 2.7 节收敛五问题二。四类红线逐类写，第二列是每类要写成什么样；写不出某一类要说明为什么没有。

| 类 | 写什么 |
|---|---|
| 业务红线 | 资金、公开平台发布、顾客个人信息、替用户做不可逆决定；逐条写"完全不做"还是"必须最终用户逐次授权" |
| 范围红线 | 本次明确不覆盖的人群、路线、产出形态及理由，防止后续为了"完整"又设计回来 |
| 质量红线 | 绝不能出现的产出：错误事实、越权承诺、违反平台合规的内容；直接进结果检查表反例 |
| 变更红线 | 能力削减或替换必须先经开发者确认；高风险动作必须明确授权 |

红线用最终用户听得懂的话写；整个制作周期内**只能加严，不能放松**。

## 12. 验证与经济性口径

服务 G1 第 2.3 节收敛一问题五与第 2.8 节计划书 ② 章。价值假设怎么验证、记录哪些指标、成本怎么算，都从这里取；G7 交付报告的观察指标基线也用同一口径。

验证分三个相互关联的比较：产品与客户现有办法相比是否有价值；专业能力相当时，业务应用与直接使用能力容器相比是否有增量价值；同一模板交付给更多客户时，质量能否保持、交付和维护成本能否控制。通用 AI 对照不能替代第二项，单店成功不能替代第三项。

可选一个具体客群、一项明确承诺，从少量真实客户的多个需求周期开始，例如 5 到 10 家门店、2 到 4 周；这足以发现问题，不足以单独证明增长因果。比较时保持任务难度、资料、模型、工具、授权和人工支持可比。

主要记录：首次可用交付耗时、客户介入分钟数、事实错误和返工、实际采用比例、下一次确有需求时是否再次使用、真实付款。应用对照另记初始化和学习时间、查找与核对负担、跨任务错误、视觉或批量操作收益。

所有人工救火和免费代操作计入交付成本。单位交付成本至少包括模型、图像或视频、外部数据、重试、人工校验、支持和退款；固定研发、维护与获客投入纳入整体经济性判断。节省的分钟数不能机械换算为现金收益；只有客户实际获得容量、减少外包，或愿意为便利付费，价值才可能被产品捕获。按成果收费时先定义成果、拒收、返工和争议处理。经营效果需要更强的证据，生成成功、内容采用、效果相关、增量因果分层验证。
