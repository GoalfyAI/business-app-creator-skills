# G5 后端业务闭环验证

本阶段的目的是**证明部件组合后能完成业务并留下正确事实**。分两个子闭环：G5a 执行闭环，把已验单元装成业务路线并在真实项目里跑通；G5b 应用数据闭环，把数据模板、后端与验证实例接通。两条线可穿插推进，依赖次序由真实契约决定。工具细则见 P4、P5、P6、P7。

## 1. 进入依据

所用单元已通过 G4 适用验收；数据与交互契约与 G3 一致；G2 的试验授权不覆盖本阶段的真跑，真跑另取授权。

进入本阶段先把 `docs/stages/G5-后端业务闭环验证.md` 的 `status` 改成 `in_progress`、`WORKSPACE.md` 的 `current_stage` 改成 G5。

## 2. 本阶段建设

### G5a 执行闭环

**步骤 1：组装业务路线。** 全部节点编排型 TPE 挂载并通过单体验收后才写路线；带业务事件的单条编排型 TPE 写成单节点路线。制作顺序固定：冻结每条路线的职责、入口表单、路线输入定义、到达标准；确认每条编排型 TPE 有根对象输入输出定义与当前版本运行证据；画依赖图，全部可达、无环；逐字段建入口映射、节点映射、交付映射；可预知的最终用户输入全放入口表单；需要时声明节点级 Agent 介入并写可验证标准；按 G3 已确认的交付对象与审阅形态声明唯一的最终交付与审阅动作，动作只写 `action_key` 与 `kind`，跳转动作另加 `orchestration_id` 与可选 `target_input_mapping`，**`label` 与 `description` 不可写**；整体替换保存，长对象经 `orchestration_url` 提交，按服务端返回精确修同一个对象，**禁止**发明兼容字段。

`delivery.mapping` 三条规则：要交付的文件路径字段**必须**进 mapping，否则不登记为 Artifact；缺失字段自动跳过，必填由 `output_schema.required` 裁决；路径必须是 `output_schema` 声明过且位于本节点产物目录内的文件。

保存并反读后做**静态接缝检查**：入口、节点依赖、扇出汇合、mapping、运行中交互、Delivery、Review 引用真实资产并满足契约；mapping 检查含文件覆盖。保存成功只证明静态结构合法。规划配套应用时同步冻结**面向应用的公开语义**：每条路线的业务名称、适用条件、入口表单目的、里程碑、可能的交互、最终交付、到达标准，**不得**用编排型 TPE 名或节点 ID 代替。

**步骤 2：路线级 Bubble。** 对发布范围内每条路线执行：`scene_package_manage(action="bubble", task_id, scene_package_id, orchestration_id, workflow_input, review_action_key)`，`workflow_input` 用代表性入口根对象，只有 `agent_gate` 才传 `review_action_key`；后续只传同一 `task_id` 与服务端返回的 `run_id` 轮询；返回 `waiting_input` 时读 `interaction.form_id/arguments`，用 `formdata` 回复当前表单；只有 `status="success"` 且 `validation.status="passed"` 才算通过，失败按 `repair_target`、`repair_action` 修它指向的原资产再重启，只有 `repair_target="platform_runtime"` 才按平台故障处理。默认 `evidence_level="summary"`，定位不了失败时才对同一 `run_id` 用 `full`。每条路线通过后写一条检查点，**一条路线一条**：`task_manager(insert, entry_type="checkpoint", metadata={"evidence_type":"orchestration_bubble_validated","scene_package_id":...,"orchestration_id":...,"run_id":...})`，结单时机器核对。路线 Bubble 里 FastAgent 为桩、外部副作用被 `ctx.dry_run` 阻断，它证明整图控制与交付接缝，**不能**证明内容质量；含 FastAgent 的路线**必须**在全真里覆盖真实内容。

**步骤 3：草稿态端到端全真。** 在草稿态目标版本上执行，不需要先上线。一次性向开发者说明本轮范围：跑哪几条路线、每条用哪个入口表单与什么测试样例、运行中表单怎么答、会启动的编排型 TPE 与 FastAgent、费用与外部副作用；批准即为本轮滚动验证的预授权，修正环内重复运行不再逐次询问。**主入口是表单直跑**，它走真实路线运行时：

1. 建项目并启动：`manage_goalfymax_project(action="run", task_id, idempotency_key, scenario_package_ids=[<草稿态目标版本的物理行 id>], submit_data={...})`，`task` 省略。`submit_data` 里 `orchestration_id` 填路线 id，`business_id` 由你生成并在同一业务实例内沿用，`form_id` 填入口表单 id，`formdata` 按表单 Schema 用开发者确认的测试样例填；**`workflow_runtime_id` 不要传**，它只由服务端生成。返回的 `project_id` 后续全部复用，**不要**为查状态或小修反复新建项目。
2. 绑定数据：素材先逐个 `file_to_url(purpose="tool_test_fixture")`，在 `run` 的 `workspace_files` 里带 `relative_path` 与 `formdata_pointer`，指向 `formdata` 里的空占位字段。测试素材来自开发者给的正反例，不虚构。
3. 观察运行：`status` 看状态，`wait` 等待推进，`history` 看交互；运行中业务表单和最终交付审阅都用 `reply` 应答，带 `business_id`、`orchestration_id`、`workflow_runtime_id`、`form_id` 与 `formdata`；`confirm` 只是普通聊天确认，**不能**用来应答任何业务表单；失控用 `stop`。日志用 `get_project_execution_logs`：`summary` 看概览，`detail` 按 `log_type` 分页读原始日志，`outputs` 列产物，`download` 或 `bundle` 取回核对。到达终态后用 `get_project_execution_logs(action="workflow_trace")` 读步级轨迹：每个节点的排队、执行、后处理耗时与重试数，每步的 `status`、`elapsed_ms`、`error`、`repeated_error_count`，与 G2 能力地图逐步对比。异常分三类归因：路由错、执行错、产出错。
4. 专项核对并记入工单：节点派发顺序与依赖图一致；`delivery.mapping` 求值结果与产物一致；运行中表单在声明的节点出现；业务事件生命周期齐全；Delivery 冻结、Artifact 登记、最终 Review 按声明生效；失败分支以结构化 `fail_business` 收口。

主入口跑通后用 `task="<自然业务需求>"` 再跑一次聊天入口核路由，**禁止**验收话术，**禁止**指定工具名或调用顺序；带事件的编排型 TPE 在此入口事件降级是平台行为。

**步骤 4：修正环与漂移检查。** 发现问题在同一草稿行修改并直接重跑；每次重跑后用 `workflow_trace` 按步对比前后成功率与耗时，编排应当让成功率上升、费用下降，否则编排没有价值。每次到达终态后对照《制作书》前七章做漂移检查：画像，用词与假设是否落在画像里；旅途，实际走过的里程碑与停点是否与设计一致；预计产出，形态、业务字段、质量是否达到正反例标准。实现偏离回 G4 修同一份资产；口径偏离回 G1 更新基线再改制作书。读本次运行的问题单：`fail` **必须**修复后重跑；`advice` 由你判断，不采纳写理由。平台未提供问题单时按三层复盘人工归纳，**不得**虚构。结果检查表逐条闭合，只处理 `pending`，正例产出一致、反例被正确识别处理才置 `passed`；`waived` 必须带理由。

**步骤 5：定稿上线能力容器。** 前提：前三层候选验收通过、全真到达终态、问题单无未处置 fail、结果检查表全绿；存在 `full_validation_skipped` **不得**上线。授权已在《制作书》第 ⑨ 章明确写出时直接执行，否则单独确认。`finalize_asset_version_online(asset_type="scenario_pack", draft_asset_id=<草稿行>, change_note=...)`，平台校验运行时身份、连接信息、文件物化、依赖闭包；依赖的 `latest` 引用定稿时钉到具体版本。上线后**必须**反读线上状态与版本。能力容器上线**不等于**应用已交付。

### G5b 应用数据闭环

**步骤 6：制作数据模板。** `dataset_template_workspace(open, name, description)` 开独立 schema 并记下 `data_uid`，返回的连接串是凭据，**不进工单、不进聊天、不进代码**。逐列按 G3 的四类归位打标。建表用 `create_table(table_name, target_columns=[...])`：每表至少一列 `primary_key=true`；类型写 PG 精确类型；**每列 `comment` 必填且以 `[editable:user|agent|system] ` 开头**，漏写等于该列按 `user` 处理、生产写不进去；每张有写入的表带审计四件套与 `row_version`。需要灌最小样例跑典型查询时用写连接，样例不进模板；连接经 dataset-proxy，`BEGIN`、`COMMIT`、`ROLLBACK`、`SET ROLE`、`SET search_path` 会被拒。`set_relations` 声明关系。`inspect(data_uid)` 反读逐表逐列核对，不带偏差往下走。把 `inspect` 结果翻成业务语言交开发者确认后再 `extract(data_uid, template_name, template_description)`；修订已有模板传 `template_id` 出新版本，破坏性变更**必须**随带 `migration_script`。记录模板 id 与版本号。**不要**在这里 `close`，工作集要留到交付之后。

**步骤 7：实现后端。** 动手前通读 `backend/README.md`。`cd backend && npm ci`；按 models、services、routes 三层实现三类接口：CRUD，写入前按列注释校验写权，带来源标记 `user_edited`，比对 `row_version`，写接口幂等，键是 `X-Goalfy-Business-Request-Id`；统计聚合，按看板指标清单实现，每个指标能说出来源表与口径，单查询在 10 秒内，大结果分页；生产回流，来源标记 `generated`，`updated_by='agent'`，写 `last_run_id`，**`editable:user` 列不得覆盖**。每个公开接口先在 `frontend/schema/api/<operationId>.yaml` 落 OpenAPI 契约，无契约不开发。硬约束：响应只用 `ok/okEmpty/list/fail` 构造，字段是 `msg`，业务失败也 HTTP 200，自定义码从 1100 起；引用表只写 `buiTable('表名')`；只做 DML；`async` 路由必须 try-catch；身份从 `getContext(req)` 取；写接口用 `canWrite` 与 `requireBusinessRequestId`；生产态不开 CORS；线上只注入三个 env 加 `PORT`。`cd backend && npm test` 全绿再联调。

**步骤 8：建立验证实例。** `business_ui_manage(action="create", name, scenario_pack_id=<家族 id>, dataset_template_id, task_id)`；`dataset_template_version` 钉整数号，**禁止 follow latest**。打包只用 `./scripts/pack.sh`，镜像必须用户无关。上传与部署：`business_ui_bundle` 的 `prepare_upload` 到 `complete_upload` 到 `deploy(source_sha256)` 到 `status` 轮询到终态 `success`；响应里 `database` 为 `null` 说明还没挂模板，先 `business_ui_manage(update, dataset_template_id, dataset_template_version)` 再 deploy。在真实应用实例验证五步：发起时带入、执行中取数、结果回流、编辑、再次读取。应用前端未就绪时用步骤 3 的表单直跑通道打后端。此时**不要求**完整界面，但**不能缺**实例与数据通道证据。

能力容器在无应用数据的项目里跑通，只证明该输入与回退路径，**不得**据此判 G5b 通过。平台不允许提前提供测试实例时，落 `platform_blocked` 并补能力；**禁止**把必需项豁免后上线。

另须实现并验证：异步任务定位；输入、产物、版本关联；幂等与冲突；部分失败恢复；错误归因；引用旧产物的权限与有效性。优先使用当前 Runtime 的重入方式；**禁止**承诺平台未验证的任意节点断点续跑。

## 3. 给开发者看什么

工作台中间区从本阶段起显示本地跑着的业务应用，`render_type` 为 `business_app_iframe`，指向 `./run-dev.sh` 起的 5175；应用没起来页面就是空的，所以本阶段全程保持服务在跑。文档照写，作为记录。

记入 `docs/stages/G5-后端业务闭环验证.md`：按业务节点排列的真实运行时间线；预期与实际路线对照；数据读入与写回的前后对照；停止、恢复、部分失败记录。每个显示"完成"的节点都能指出实际成立的事实。

## 4. 要确认哪些边界

本轮真跑范围与费用；未取到必要数据时补充还是拒绝；部分成果是否可交付；哪些修改重用旧结果、哪些重算；历史结果与运行实例如何保留；后台持续执行与费用上限；能力容器上线授权。

## 5. 门禁 Checklist

- `G5-01` U3 适用项逐条验证；核对真实路线的映射、介入、交付与审阅，**禁止**拼接单元日志。
- `G5-02` 从实例记录能反查一次任务实际消费了哪份资料、哪个对象或周期，产物回到哪个实例、任务、版本。数据库里"有资料"**不算**已用上。对应 U2-06、U6-01。
- `G5-03` 重复请求或回调、后端写权拒绝、并发版本冲突三类用例分别有结论；只验前端禁用**不算**。对应 U4-05、U6-01。
- `G5-04` U4 的离开、补充、结果未知、部分失败、重复请求、取消各有处理记录。
- `G5-05` 交付完整性、文件可取用、业务审阅、外部动作回执分别核验；无可靠回执的动作保持未知。对应 U5-01、U5-06。
- `G5-06` U5 修改与版本保护、U6 事实与偏好复用分别取证。
- `G5-07` 路线证据与应用数据证据分别闭合；实例缺失、数据通道未测明确阻断对应承诺。

## 6. 证据与结论

产出路线真实日志、`project_id` 与情景、漂移结论、问题单处置、结果检查表状态、应用实例测试记录、数据库前后状态、模板版本、部署终态。能力容器部分按场景包验收检查清单裁决；后端与数据面按应用验收检查清单裁决。落工单标签 `orchestration_bubble_validated`、`orchestration_runtime_verified`、`data_loop_verified`。

**阶段出口动作**：门禁全过后，把 `docs/stages/G5-后端业务闭环验证.md` 的 `status` 改 `passed`，写 `stage_exit`，从存在 business_ui 草稿起打包部署一次，再把 `WORKSPACE.md` 的 `current_stage` 改成下一阶段并把下一阶段文档置 `in_progress`；工作台自动切换。顺序见协议四第 6 节。

## 7. 失败回退

单元问题：回 G4。路线或数据语义问题：回 G3。真实能力不可用：回 G2。回跳沿用原记录，不重复落账。
