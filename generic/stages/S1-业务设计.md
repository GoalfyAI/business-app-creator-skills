# S1 业务设计

从业务素材到已确认的《场景包计划书》。本阶段只做业务设计，不选资产、不创建任何正式资产。

## 1. 进入前提、目的与产出物

进入前提：有 `write` 工单（路由器·前置条件）。

**本阶段的目的只有一个：引导开发者产出一份《场景包计划书》**——记录场景包服务的用户画像、用户旅途轨迹和交付结果，**不涉及任何具体资产的选择**（用什么 Workflow、工具、FastAgent 在 S2 决定）。它是 S2 资产设计的基本资料：S2 在计划书之上补上资产与路线的设计，形成完整的《场景包制作书》（本 Skill 各处所说的“方案 Plan”）；后续任何实质变更都要回到计划书更新并重新确认。

本阶段产出：用户画像、用户旅途轨迹（里程碑与候选路线、正反例 = 结果检查表种子、质量评估标准）、面向开发者的业务路线图、交付角色与红线，按 5.1 七章格式写入工单并经开发者确认的《场景包计划书》。修订已上线包的任务还需持有草稿行（见第 6 节）。

### 1.1 三个角色：谁在用这份 Skill、为谁做、给谁用

| 角色 | 是谁 | 在 S1 里的位置 |
|---|---|---|
| **开发 Agent** | 正在执行本 Skill 的你 | 引导者：提问、调查、提案、把计划书写出来；**不替开发者做产品决定，也不替最终用户猜需求** |
| **开发者** | 使用场景包助手 MCP 制作场景包的人 | 决策者与事实来源：最终用户是谁、业务怎么跑、什么算好——这些只有他知道；计划书由他确认 |
| **最终用户** | 场景包上线后真正使用它的人（店主、运营、销售……） | **不在场**。你无法得知他们需要什么，只能通过开发者给出的**用户画像**与**旅途轨迹**代入他们 |

因此 S1 的每一步提问，都是在替不在场的最终用户向开发者要答案；每一个设计决定，都要能回溯到画像与旅途，而不是回溯到“平台有这个能力”。

### 1.2 用户画像：向开发者索要的第一件事

在收集任何素材之前，**必须**先向开发者要到用户画像；画像不清楚，后面所有设计都建立在猜测上，**不得进入第 3 节**。画像至少回答：

| 要问什么 | 例（餐饮场景包） | 它决定后面什么 |
|---|---|---|
| 服务谁：职业 / 角色 / 经营形态 / 规模 | 单店或小连锁的餐饮老板，自己管运营 | 里程碑与路线的用词、`apc_skill` 与界面文案的语域、业务应用数据集的表与列名（门店 / 菜品 / 客单 / 翻台，而不是 entity / item） |
| 他们眼里的专业词汇与判断标准 | “爆品”“客单价”“复购”“差评” | 样例选择（S3-3.2）的领域调研方向、验收判定的措辞、FastAgent 规范文件的术语 |
| 他们的决策节奏与使用场景 | 每天营业结束后 10 分钟看一眼、周一定下周活动 | 路线数量与粒度、哪些环节值得最终用户确认、业务应用的看板要看什么 |
| 现在怎么做、卡在哪 | 手工翻评价、凭感觉定活动 | 理想态与价值预测的基线（S2 第 3 节） |
| 有几类人群 | 老板 / 店长 / 运营专员各自关心什么 | 是否需要多条路线或多套子画像（第 3 节） |
| **有没有可参考的资料与打法** | 同行怎么做、他自己做过的活动与复盘、内部 SOP、行业报告、他看好的竞品 | 旅途与候选路线的**起点**、样例选择的调研方向——**先问开发者，再自己去调研**，不反过来 |
| 高风险边界与不可触碰 | 涉及资金、发布到公开平台、处理顾客个人信息 | 计划书的“红线”（4.4）与授权边界 |

画像关键词要**贯穿全程**：从这一刻起，里程碑名称、路线适用条件、`apc_skill` 里的业务规则、样例选择的调研对象、业务应用数据集的表 / 列命名与业务说明，都用画像里的词——出现平台词（Workflow、节点、TPE、Schema）或泛词（实体、条目、对象）就是画像没有落到设计里。

开发者一时说不清画像时，用 2.3 的访谈方法分轮问；实在给不出，**如实记录“画像不明”作为计划书的首要风险**，并把由此导致的所有假设标出来。

## 2. 素材收集与信息缺口

### 2.1 业务素材收集

开发者主动提供的材料按可信度排序：**已执行项目（最高，含真实策略、绕行、失败和交付）** → 上传文档与 SOP → 指定的已有场景包。

开发者提供的参考项目、SOP、文档**必须完整读取**（约束 3）——在本阶段它们用来核对旅途：最终用户实际怎么走、在哪卡住、拿到了什么。对参考项目的**三层分析**（轮次统计、瓶颈定位、真实调用链、Skill 使用情况）属于资产设计，放在 S2 2.1；本阶段只做通读与业务层面的提炼。已有场景包、官方基础包与平台能力的摸底同样在 S2 第 2 节，**本阶段不看资产、不选工具**。

### 2.2 关键缺口判定

务必区分五类信息缺口，处理方式完全不同：

| 缺口类型 | 例子 | 处理 |
|---|---|---|
| **意图缺失** | "帮我做个东西" | **必须**向开发者询问明确目标，**禁止**先设计方案 |
| **关键参数缺失** | 创建模式未描述业务场景；诊断模式未指定目标场景包 | 目标明确但缺执行前提，**必须**向开发者索要 |
| 知识缺失 | "我不知道需要哪些工具" | 属于调查范畴，把"摸底线上资产与工具能力"纳入后续工作，**不要**让开发者回答平台问题 |
| 工程偏好缺失 | 命名风格、代码组织、等价展示细节 | 存在可逆且不改变业务语义的默认时采用并记录影响，**不要**把工程偏好当成必须先解决的阻塞项 |
| 产品决策缺失 | 路线、Focus/泛化、审阅责任、界面模块、最终用户介入 | 放入 Plan 集中确认；只有一个独立决策时单项询问，**不得**由 Agent 使用默认值 |
| 开发者授权缺失 | 发布、删除、收费、真机运行 | 在对应动作前明确确认，**不得**用默认值代替授权 |

开发者上传文档或文件时，**必须**完整阅读后再继续。**严禁**只浏览或只读一部分；内容被截断或分页时**必须**续读到结束。对开发者材料的不完整理解是错误输出最常见的根源。

### 2.3 访谈方法

访谈按需组合，**不要**一次性全问。每轮聚焦最影响下一步的一到三个事项；相互关联的产品选择优先汇总到 Plan：

- 业务场景：业务是什么、服务谁、现在怎么做、最终要什么结果
- 参考素材：有没有已执行项目、完整日志、文档、SOP、已有场景包
- 业务边界：哪些系统、数据、权限、成本、时效、合规条件不能改
- 成功标准：什么最终用户可见结果能证明场景包有效
- 模式：新建、优化已有，还是从执行失败的项目反查原因

启动前至少明确：业务目标、最终用户、业务终点、关键输入与产出、操作对象、可读取的证据、高风险边界、初步验收标准。其余平台知识由你自己调查。

## 3. 用户旅途轨迹：里程碑、候选路线与正反例

有了画像，第二件事是确定**用户旅途轨迹**——最终用户带着什么进来、经过什么、拿着什么出去。本节的产物合起来要回答六个问题（收口见 3.4）：

1. 用户通过这个场景包**能完成什么事**（业务终点，用画像的词说）；
2. 能设计**几条路线**、每条给什么目标 / 前置状态的人走；
3. 服务**几类人群**（画像里的子群体各走哪条路线、看什么产出）；
4. 用户**输入什么、输出得到什么**（入口要填的、最终拿到的交付，以及中途要确认的）；
5. **质量怎么评估**——什么样的产出算好、什么算错（正反例 → 结果检查表；样例选择 → 验收判定）；
6. **怎么得到高质量结果**——哪些环节必须由 FastAgent 带规范判断、哪些必须最终用户审阅、哪些靠确定性固化。


### 3.1 里程碑与候选路线

基于素材和项目分析回答：场景从什么触发、分几个关键阶段、每阶段的目标与输入与责任方与最终用户可见产出、阶段间怎么依赖、最终怎么证明业务终点成立。

向开发者展示里程碑理解、候选路线和权限边界，作为方案 Plan 的第一组业务决策集中确认；Agent 的提炼结果在确认前只属于候选草案。

先问开发者有没有现成的打法——同行怎么做、他自己以前怎么做、有没有 SOP 或复盘材料——有就以它为候选路线的起点，没有再从素材与访谈提炼。参考项目的路线转成**候选路线**，**不要**直接固化成所有最终用户的唯一 SOP。每条路线注明：适用目标、前置条件、在哪里判断走哪条、哪些步骤是稳定可固化的、最终用户确认点、失败与降级路径，以及**到达标准**（能证明这条路线已走完、业务终点已达成的证据）。

### 3.2 索取正例与反例

确认里程碑的同时，**必须**向开发者索取具体案例——里程碑是抽象的，开发者点头了也不代表双方对"具体一个输入该产出什么"的理解一致。

对每个关键阶段各要一组：

| | 索取内容 |
|---|---|
| **正例** | 一个真实输入，以及开发者期望场景包向最终用户交付的产出。**必须**是具体的，不接受"大概就是分析一下"这类描述 |
| **反例** | 一个容易被做错的情况，以及为什么错、正确做法是什么 |

**反例往往比正例更有价值**——它暴露的是开发者或最终用户觉得“显然不该这样”、但没说出口的隐含规则。Agent 负责从证据中提炼候选规则；规则会改变业务行为时，必须交开发者确认后再固化。

案例写入工单后，在四处复用：

| 用途 | 怎么用 |
|---|---|
| 判断需求理解是否正确 | 把正例的处理过程讲给开发者听，错了立刻能发现 |
| Workflow 运行验证 | 正例直接作为代表性输入（见 `stages/S3-资产制作.md` 4.3） |
| 场景 Skill 文件 | 写成示例，运行时 Agent 照着做（见 `stages/S3-资产制作.md` 8.3） |
| 真机验证 | 照着正例构造自然业务需求（见 `stages/S4-验证与修正.md` 3） |

开发者给不出具体案例时，**必须**如实记录这个情况——它意味着需求尚未清晰，后续所有判断都建立在推测上，要在方案里标明这个风险。

正反例同时是**质量评估标准的雏形**：正例定义“好”的形态，反例定义“错”的边界；被开发者在 S3-3.2 样例选择里圈定的关键产出环节，其验收判定也从这里长出来。“如何得到高质量结果”的答案随之明确——需要领域判断的环节交给带规范文件的 FastAgent、其余确定性步骤固化（资产层面的落法在 S2 第 3–4 节），需要业务拍板的环节交给最终用户审阅（4.2）。

### 3.3 正反例转入结果检查表

收集到的每组正反例，**必须**同时按「输入 + 期望产出」结构化写入结果检查表（作为初始条目，状态 `pending`），并按路由器 5.3 落工单权威快照。结果检查表在 S4 逐条闭合、S5 结单校验；正反例只留在工单散文里而不转入表，视为本节未完成。

### 3.4 旅途轨迹收口

进入第 4 节前，把六问的答案对齐成一张表写入工单（它就是计划书第 ② 章的底稿）：

| 问题 | 答案落点 |
|---|---|
| 能完成什么事 | 业务终点 + 到达标准（3.1） |
| 几条路线、各给谁走 | 候选路线清单：适用目标 / 前置条件 / 选路节点（3.1） |
| 几类人群 | 画像子群体 → 路线 / 产出的映射（1.2 + 3.1） |
| 输入什么、输出什么 | 每条路线的入口信息、中途确认点、最终交付物（3.1） |
| 质量怎么评估 | 每个关键阶段的正反例（3.2）+ 结果检查表种子（3.3） |
| 怎么得到高质量结果 | 哪些环节需要领域判断、哪些最终用户审阅、哪些可固化——业务层面的判断写在这里，落成哪种资产在 S2 第 3–4 节决定 |

任一格为空即旅途未闭合，回访谈补齐，不带着空格进入设计。

## 4. 交付结果

旅途的终点要落成可确认的交付结果：路线怎么走（业务语言）、结果交付给谁、谁来审、审什么、用户的数据怎么被用又怎么回流、哪些事绝对不做。本节四小节合起来就是计划书的第 ③④⑤⑦ 章。

### 4.1 面向开发者的业务路线图

涉及一条或多条业务路线时，完整方案 Plan **必须**先提供一张业务语言表达的路线依赖图。图中至少包含：路线入口、主要业务阶段、固定依赖、扇出与汇合、最终用户介入、Agent 介入、最终交付、审阅责任方，以及接受、拒绝、修订、重做或改走其他路线的出口。图只表达“业务如何到达终点”，不得出现资产数字标识、内部节点标识、工具名、Schema 路径或脚本调用链。

这张图是开发者确认业务结构的依据，不是可直接保存的机器编排对象。开发者确认后，开发 Agent 才能把它转换为真实 Workflow 节点、字段映射和编排契约；转换过程中发现业务依赖、介入点或出口需要实质变化时，必须先回到方案 Plan 更新业务路线图并重新确认。

### 4.2 最终交付的核验与审阅角色

交付核验回答“这份结果是否真实、完整、可交付”，最终审阅回答“业务上是否接受这份结果、是否需要修订或改走其他路线”。两者**禁止**合并：Workflow 输出契约、数值、证据和文件校验通过，不代表最终用户或 Agent 已完成业务验收；节点级 `sa_handoff` 和质量检查 Workflow 也不是最终审阅的替代品。

最终审阅形态是场景包产品契约，**必须由开发者在计划书第 ④ 章中确认**，开发 Agent 只能依据业务事实提出推荐，不能替开发者选定：

| 形态 | 运行语义 | Agent 向开发者说明的适用信号 |
|---|---|---|
| `user_gate + ask` | Runtime 向业务应用下发冻结交付和已声明动作；最终用户完成三次握手后，Runtime 直接执行所选的完成、失败或新路线动作，不额外唤起 Agent | 业务完成需要最终用户批准、满意度确认、方案选择、修订、改路线或高风险授权 |
| `user_gate + result` | Runtime 按既有 result / end-task 链路自动交付并结束，不要求最终用户或运行时 Agent 参与 | 生成且核验通过即达到业务终点，不需要额外业务判断 |
| `agent_gate` | 唯一主动唤起运行时 Agent 评价或选路的最终审阅边界；Agent 按开发者确认的可验证标准选择已声明动作 | 接受标准客观、可执行且确实需要 Agent 判断，而不是简单自动结束 |

完整交付方案必须分别回答四个问题：**结果最终交付给谁使用、谁负责判断业务上是否接受、可以执行哪些审阅动作、修订/重做/改路线后如何继续**。审阅责任方不能由“结果由谁使用”反推：结果可以交付给最终用户使用，但由 Agent 按客观标准审阅；也可以无需任何额外审阅，核验通过后直接交付并结束。

开发 Agent 必须把交付对象、推荐形态、理由、最终用户体验、失败或重入影响和可选动作一并交给开发者确认。开发者选择与已声明的高风险授权边界冲突时，指出冲突并重新询问，不得静默改成另一种 Gate。不能因为场景包能生成报告就默认要求最终用户回答“是否满意”，也不能因为 Agent 已读过结果就默认业务已接受。

`user_gate` 不得再叠加一层“交给 Agent 收尾”：`ask` 的具体动作由 Runtime 在收到有效表单答复后直接执行，`result` 由 Runtime 自动交付并结束。只有编排明确声明 `agent_gate`，或最终用户选择了已声明的“交由 Agent 处理”动作时，才建立 Agent 边界。制作方案、`apc_skill`、节点 `sa_handoff` 和业务应用都不得用额外 Agent 提示词模拟这次接管。

终态顺序**必须**是：解析真实 TaskPoint 输出 → 核验交付资格 → 冻结本次 Delivery → 执行已声明的最终审阅 → 根据审阅动作完成业务、结构化失败或开启新路线。在审阅明确接受前，**禁止**把结果展示当成已验收，**禁止**把 Business 标记为已完成，也**禁止**用旧的“Agent 先发送结果再接管结束”链路绕过 Delivery Review。修订、重做或改路线必须保留当前 Delivery，按当前契约新建运行实例，不覆盖旧结果。

场景包制作只声明对外稳定的资产契约：中间节点用 `sa_handoff`，最终审阅用 `delivery.review`。Max Runtime 如何生成 Agent 边界通知、注入执行上下文或封装内部控制消息，属于平台实现细节，**禁止**复制进 `workflow_orchestration`、`apc_skill`、场景 Skill 或业务应用契约。

### 4.3 业务应用数据集的业务面

场景包规划配套业务应用（约束 8）时，最终用户的长期数据都在**业务应用数据集**里（app-creator 线制作模板，用户点开应用时各得一份）。计划书只回答**业务问题**——用画像的词，不谈字段落地：

| 问题 | 计划书里要写什么 |
|---|---|
| **如何作用** | 用户自己的哪些数据（门店档案、历史效果、禁用表达……）会影响路线怎么走、产出怎么写——逐项说影响的是选路、参数还是文案 |
| **何时用到** | 这些信息是发起时就该带上的（用户一填就有）、还是跑到中途才需要“看情况取”的——只做业务层面的区分，走表单还是走脚本读在 S2 6.5 决定 |
| **如何回流** | 哪些产出与效果数据应该留在用户的资产里供看板展示与下次参考、留成什么粒度、是直接生效还是先作草稿等用户确认（回流入库语义由开发者定） |

数据集里的表与列由 app-creator 线设计，但**列名与业务说明必须与本计划书的画像用词一致**——两条线各说各话，Workflow 写回的字段应用就展示不出来。未规划配套业务应用时本节写“不适用”，并说明数据如何随交付给到用户。

### 4.4 红线

计划书必须有一章**明确不做的事和不可触碰的边界**，它比“做什么”更能防止后续设计跑偏：

- **业务红线**：画像 1.2 里问出来的不可触碰项——涉及资金、对公开平台发布、处理顾客个人信息、替用户做不可逆决定等，逐条写明是“完全不做”还是“必须最终用户逐次授权”；
- **范围红线**：本次明确不覆盖的人群、路线、产出形态，及理由——防止 S2 为了“完整”把它们又设计回来；
- **质量红线**：绝不能出现的产出（反例里最严重的那几类：错误事实、越权承诺、违反平台合规红线的内容），它们直接进结果检查表的反例条目；
- **变更红线**：能力削减或替换必须先经开发者确认（约束 12），高风险动作必须明确授权（约束 6）。

红线用最终用户听得懂的话写，并交开发者逐条确认——这一章在整个制作周期内**只能加严，不能放松**。

## 5. 《场景包计划书》与开发者确认

### 5.1 计划书的固定格式

方案 Plan 的业务部分是一份**固定格式的《场景包计划书》**，管理型语言（路由器 3.2），七章顺序不可增删调换，每章写不出就明写“待确认 / 不适用 + 理由”，不留空：

| 章 | 内容 | 来源 |
|---|---|---|
| ① 预计的用户画像 | 服务谁、专业词汇、决策节奏、使用场景、人群分类、不可触碰边界 | 1.2 |
| ② 预计的用户旅途 | 能完成什么事、几条路线各给谁走、输入与输出、中途确认点、质量评估标准、高质量手段 | 3.4 收口表 |
| ③ 预计的编排路线 | 面向开发者的业务路线图：入口、业务阶段、固定依赖、扇出/汇合、最终用户与 Agent 介入、动作出口；每条路线的到达标准 | 4.1 |
| ④ 预计的交付角色 | 每条路线结果交付给谁、谁负责业务审阅、`user_gate + ask` / `user_gate + result` / `agent_gate` 选哪种、允许哪些动作、修订/重做/改路线怎么续 | 4.2 |
| ⑤ 业务应用数据集 | 是否规划配套业务应用；用户数据如何作用、何时用到、如何回流；不配套时数据如何随交付给到用户 | 4.3 |
| ⑥ 预计的产出与质量 | 每条路线的最终交付物形态、关键产出环节及其正反例、验收判定的雏形 | 3.2 / 3.3 |
| ⑦ 红线 | 业务红线、范围红线、质量红线、变更红线 | 4.4 |

计划书**不写**：用哪些 Workflow / 工具 / FastAgent、资产边界、能力缺口、发布范围——这些是 S2 在计划书之上补出的第 ⑧⑨ 章（S2 7.2），合起来才是完整的《场景包制作书》。

每章包含推荐、依据、影响和待确认选择。对业务应用只记录是否规划及其要承载的业务旅程；页面与模块设计在 app-creator 线的 A1 完成，本场景包工单不为它定稿任何界面内容。

计划书**写入工单**（`task_manager(insert, entry_type="checkpoint")`，`metadata.evidence_type="build_book"`，`metadata.stage="S1"`）；S2 在同一标签下重写为完整制作书。

**格式自检**（提交前逐条）：七章齐全且顺序不变；每章用画像的词而不是平台词（出现 Workflow / 节点 / TPE / Schema 即不合格）；每条路线在 ②③④⑥ 四章里都能找到自己（旅途 → 路线图 → 交付角色 → 产出与质量），缺一处即路线未闭合；⑦ 红线非空。

### 5.2 开发者确认

把《场景包计划书》全文交给开发者**逐章确认**（确认的是计划书，不是口头摘要）。确认的对象：画像是否准确、旅途是否是最终用户真实会走的路、路线图与交付角色是否符合业务、数据集的作用与回流是否是他想要的、产出与质量标准是否够具体、红线是否完整。

Agent 的提炼结果在确认前只属于候选草案；开发者要求改的地方改完重新提交整份，不做口头补丁。

### 5.3 计划书硬门

计划书未经开发者确认，**不进入 S2**。确认后 S2 可以开始只读调查与资产设计；**任何资产的创建仍受 S2 7.4 的制作书硬门约束**——计划书确认不等于资产创建授权，更不等于上线授权（约束 6）。

计划书确认后若在 S2 发现旅途、交付角色或红线需要实质变化，回到本节更新计划书并重新确认，不在 S2 里静默改业务口径。

## 6. 修订类任务的版本入口

修订**已上线**的场景包时，一切内容修改必须发生在草稿行上（详见 [场景包版本体系与发布逻辑](../references/场景包版本体系与发布逻辑.md)）：先取得可编辑草稿：`ensure_editable_asset_draft(asset_type="scenario_pack", asset_id=<家族或任一版本行>, operation_id=...)`——从当前 live 版本派生出 `testing` 状态的新物理行，版本号省略即自动递增 patch；家族同一时刻只允许一个草稿，已存在时返回既有草稿（幂等）。动手前用 `list_asset_versions` 看清家族里哪一行是现役 live、有没有搁浅的旧草稿（要放弃的用 `abandon_asset_version_draft`，放弃前先 `get_asset_usage_impact` 确认无引用）。拿到草稿行标识后再进入 S2。修订类任务的计划书从上一工单的 `build_book` 继承并按本次变化增量修订，不从零写。

修订类任务的结果检查表**必须**从上一工单的最新 `result_checklist_snapshot` 继承全部条目，再叠加本次新增的正反例；条目指纹对新版本重算，受影响条目回退 `pending`——这是修订不坏旧例的回归机制（见 [表结构与累加机制](../references/表结构与累加机制.md)）。**禁止**只建本次新条目而丢弃历史条目。

## 7. 出口条件

以下全部满足后，按路由器 4.1 进入 S2：

- 用户画像（1.2）与旅途轨迹收口表（3.4）已写入工单，无空格；
- 《场景包计划书》按 5.1 七章格式写入工单（`build_book`，`stage="S1"`）并经开发者逐章确认；
- 结果检查表已初始化（正反例已按 3.3 转入）；
- 修订类任务已持有草稿行标识。

以上全部满足后，按路由器 6.1 落一条 `stage_exit` 账，再进入下一阶段。
