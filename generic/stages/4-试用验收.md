# ④ 试用验收（工作区阶段 G6）

交出一份验收报告和验收清单逐条结论。你按验收条目逐条测：页面条目由你在应用的本机版上用无头浏览器照条目操作，同时跑前端检查和本地布局回归；业务结果在开发者同意部署后，用开发工作集真跑并查库；测不了的按 2.4 的表记「未测」。没过的改好再测，每条都有结论后交报告。开发者不逐条试、不打勾：他看报告，「好不好你说了算」的几条看你附上的实际结果，最后说「可以上线」。验证分两层：冒泡管改，真跑、本机版页面验收加验收报告管收。

## 1. 进入条件

- ③ 交棒：应用根 `npm run verify` 全绿，每个功能都做好了或标明没做成；读写应用库的路线在阶段文档 G4 有反读自查表且四项都是「有」（四项定义见 [../reference/编排脚本.md](../reference/编排脚本.md)「读写应用库」），没有就回 ③ 补，不部署。
- 本轮需求已全部实现：进 ④ 前你先生成本地完成版，开发者可以在「演示预览」看，生成办法见 [../reference/开发者中心与工作区.md](../reference/开发者中心与工作区.md)「演示预览为空」；Studio 下不生成完成版。

## 2. 段里怎么做

### 2.1 本机先测

不用部署的先做：页面条目、`npm --prefix frontend run check`、本地布局回归。本机版怎么起、只访问本机地址、无头操作与截图、起不来怎么修，都按 [../reference/开发者中心与工作区.md](../reference/开发者中心与工作区.md)「本机版页面验收」。空库表现也在本机版上验：清空本机 Mock 数据，看引导和首次设置入口。

### 2.2 先问部署，再部署

- 部署要开发者单独授权：之前没有明确同意过，就在原对话里照 [../SKILL.md](../SKILL.md)「红线」的部署授权原句问一次（什么算同意也在那里），同意的原话记 checkpoint；之前明确同意过的直接沿用。
- 同意后先做工具集上线前的第二道检查（[../reference/依赖与MCP接入.md](../reference/依赖与MCP接入.md)「工具集上线的两道检查」），再按 [../reference/部署与版本.md](../reference/部署与版本.md)「部署」部署到 `success`。挂着本人场景包草稿也能部署，场景包不用先上线。部署只到开发者的在线预览，不上线、不发布。
- 还没同意：不部署，本机版的检查照做；依赖已部署版本的条目（`workspace` 真跑、开发工作集里查到的行）按 2.4 的表记「未测」，他之后同意时部署并补测。开发者在没部署的情况下说「可以上线」，按 [5-上线.md](5-上线.md)「2.1 只上线已部署的草稿」处理。

### 2.3 工作集真跑

有模型步骤，或路线要读写应用库、调外部接口时做；只有脚本步骤且 ③ 的 `full_run` 已覆盖时可省，省了写明原因。例子由你挑，挑法同 [3-制作.md](3-制作.md)「2.1 后台能力」，验收条目里点名的样例都要跑到。PRD 已列的费用直接执行；PRD 没列的副作用（对外发送、写正式数据）按 [../SKILL.md](../SKILL.md)「花费」说清范围、开发者明确同意后执行。

1. 调用方式（`workspace`、家族 ID、`business_id`、`wait` / `reply`、`route_runs`）按 [../reference/部署与版本.md](../reference/部署与版本.md)「真跑」。
2. `workflow_trace` 看每步，模型步骤的输出逐条读；写库的结果去应用库里查到那一行。
3. 读写应用库的路线，对每条 TPE 调 `otpe_manage(action="verify", task_id, tpe_id, project_id)` 补运行证据，`passed` 即完成；③ 只差运行证据的 TPE 在这里补齐，冒泡和结单门豁免代替不了它。
4. 记下每个按钮这次实际花了多少（`cost_credits`），和 PRD 的估算比。
5. ③ 标「做好了，等部署后真跑」的功能，真跑通过后按 [3-制作.md](3-制作.md)「2.3 进度与「我先跑了一遍」」的格式补发「我先跑了一遍」。
6. **回写演示示例**：③ 在阶段文档 G5 记了「待 ④ 回写」的演示和示例，从这次真跑通过的结果里选一份写回代码，去掉「示例」占位，按 2.2 重新部署，修改记录写明。回写不算退回 ③，在 2.4 之前做完。

失败在同一草稿改再跑；每次只改一处，不同时改脚本和路线。

### 2.4 逐条判定

逐条对照 ② 定稿的验收条目，照「照着做」做一遍，按「这样算对」判，每条记「怎么测的」和证据。结论只有四种：通过 / 没通过 / 好不好你说了算 / 未测。

| 条目要看的 | 怎么测 | 「通过」要的证据 |
|---|---|---|
| 业务结果：报告、内容、识别出来的东西、写进库的记录、发出的消息 | 2.3 的真跑；条目点名的样例没跑到的，照条目再真跑一次 | 这次 `workspace` 真跑的 `project_id`、`workflow_trace` 里对应步骤的摘要、库里查到的那一行（不写库的写拿到的产出） |
| 页面上的操作和显示：点哪、跳到哪、空态、提示文字、必填校验、打回和重新生成、切语言、只读置灰、消息中心跳转、离开再回来 | 本机版上用无头浏览器照条目操作（2.1） | 操作步骤、截图文件路径或断言原文、打开过的本机路由；前端检查与布局回归的结果 |
| 到点或有新记录时自动开始的 | `business_ui_automation(bubble)` 按自动化的入口跑一次（[../reference/自动化.md](../reference/自动化.md)「验证」） | 冒泡的 `run_id` 与结果；「到点真触发」另列一条，按下面的表记「未测」 |
| ② 标「要人判断」的（内容能不能直接对外、语气像不像、业务判断对不对、前后两批有没有变好） | 照样做一遍，不下结论 | 实际结果原文附进报告，结论「好不好你说了算」 |

怎么判：

- **看实际产出**：页面或日志显示「已完成」「成功」不算通过，要看到真的产出（报告内容、库里的行、发出的消息）。
- **页面条目**：「通过」要有本机版操作步骤，以及截图文件路径或断言原文；只请求过页面地址（`curl`、HEAD 返回 200）不算操作过。页面文案与动作按 ③ 记下的业务含义逐项核对（[../reference/前端页面.md](../reference/前端页面.md)「业务文案」），加载、空态、只读、暂停、失效也核对。只读置灰在本机版 Mock 里设 `permission='view'` 验；Mock 做不到时按下表记「只有线上才能验证：平台登录身份」。
- **冒泡不能证明读写**：冒泡（含 `full_run`）只证明路线能跑。读写应用库的条目只有冒泡证据（读库返回 `not_a_business_app_project`、写库被 `ctx.dry_run` 跳过）时，自查记录写「冒泡无法验证真实读写」，不算通过，回 2.3 用 `workspace` 真跑、在开发工作集查到写入的行才算通过；开发者还没同意部署的按下表记「未测」。机制见 [../reference/编排脚本.md](../reference/编排脚本.md)「冒泡与真跑能证明什么」。
- **证据只认你自己取得的**：部署成功本身、开发者的口头回报、他在在线预览或演示预览（含 Studio 本地演示）里看到的、已发布的版本，都不作证据。宿主提供的受限检查能力的机器结果可以作补充，和你在本机版上的操作分开记，不代替页面条目的本机版操作。
- **没通过**：结果不对、报错、该写的行没写，记「没通过」，按 2.6 改；挡上线，开发者选了接受的除外。
- 按 [../checklists/验收清单.md](../checklists/验收清单.md) 逐条写结论（通过 / 没通过 / 好不好你说了算 / 未测 / 不适用）和一句依据。

**「未测」只用于下面几类**（唯一枚举）。这些条目里本机版能看的部分照常测并写证据；其余部分结论「未测」、证据「无」，原因照下表原文写。本机版能测的条目都要测；测不了的不请开发者代测（[../SKILL.md](../SKILL.md)「红线」）。

| 情况 | 原因原文 | 以后开发者自己怎么看 |
|---|---|---|
| 依赖平台登录身份：按真实账号显示的内容、协作者打开的是自己的草稿、要另一种账号才看到的 | 「只有线上才能验证：平台登录身份」 | 发布后在正式入口看 |
| 依赖真实宿主桥接：从宿主的消息提醒跳进应用、宿主弹出的授权与付款窗口及真实授权和付款、宿主注入的真实身份与路线 | 「只有线上才能验证：真实宿主桥接」 | 同上 |
| 本机版起不来，按「本机版页面验收」修过仍不行 | 「本机版起不来」，加做过哪些处理和错误原文 | 交接消息逐条列出 |
| 开发者还没同意部署，条目依赖已部署版本 | 「你还没同意部署到在线预览」 | 同意部署后补测（⑤「2.1 只上线已部署的草稿」） |
| 到点真触发 | 「到点触发要等真实时间，且要发布后在正式入口开规则」 | 发布后在应用的「自动化」面板开规则，等到点看 |
| 使用者从目录或分享打开 | 「从目录或分享打开要先发布」 | 发布后从目录或分享打开看 |

### 2.5 交验收报告

所有条目都有结论后交；交之前进度照常按「正在做」报。报告的七项、「全部条目」六列表头和「要你做的」照抄文本，见 [../design/验收报告与上线结果.md](../design/验收报告与上线结果.md)「验收报告」。

报告的硬门，三条都满足才交：

1. 每条「通过」都有 2.4 要的证据，「全部条目」里后三列都填了（有「冒泡无法验证真实读写」的行就不满足）；
2. 每条「未测」都写了原因，且属于 2.4「未测」表里的一类，原因与情况对得上；
3. 报告和交接消息只请开发者看报告、回话，不请他去在线预览、演示预览或正式入口里看、点、试条目或查数据。

有一条不满足：G6 记 `failed`，不交报告、不请开发者说「可以上线」，回 2.3、2.4 补齐。

### 2.6 按反馈改

- 开发者说哪条不对、或「好不好你说了算」的结果不满意，或他自己在在线预览里用的时候发现问题：改完按 2.2 重新部署，重测这一条和受影响的条目（页面条目在本机版上重测），报告里只更新变了的条目。他的回报只用来定位问题。
- 改了场景包草稿的重新部署即可，不用上线；已上线的应用挂载钉在旧版本号时，先换挂到场景包草稿再部署（[../reference/部署与版本.md](../reference/部署与版本.md)「场景包上线」）。改了挂载（场景包版本、模板版本）后先重新部署再真跑（同一文件「真跑」）。
- 结果不对、要改做法的回 ③，和预期差得多的按 [3-制作.md](3-制作.md)「2.4 什么时候请开发者拍板」出选择题；开发者发现要的东西本身不对，回 ①。
- 开发者要在还有条目没通过时上线：把没通过的条目逐条做成「接受，先上线 / 等改好再上线」选择题，写清上线后使用者会遇到什么；选了「接受」的结论记「没通过，开发者选了接受」，写进上线结果「还没验证的和风险」。「未测」的条目不出这道题。

## 3. 开发者要看、要做的

- 之前没有明确同意过部署的，答是否部署到开发者在线预览用于试用验收。
- 看验收报告；「好不好你说了算」的几条看实际结果。
- 说「可以上线」，或说哪一条还要改。

## 4. 产出与落盘

- 工单 checkpoint：场景包草稿或上线版本、部署证据（`deployment_id`、`source_sha256`、`deployed_scaffold_version`）、真跑的 `project_id` 与结论、每条 TPE 的 `verify(tpe_id, project_id)` 结论、开发者对部署的原话、开发者（和需求方）说「可以上线」的原话、未测的条目及原因、开发者选了接受的条目。
- 阶段文档 G6：验收报告全文（每条怎么测的、证据、结论）、页面条目的操作步骤、截图路径与本机路由、前端检查与布局回归结果、修改记录、验收清单逐条结论、实际花费。
- 交付物：方案页交报告时 `status` 为 `waiting`，`.pv-you` 写「看验收报告，没问题回『可以上线』」；入口、权限、部署问题推进不了时为 `blocked` 并写 `.pv-owner`；通过的条目移入「已验证」，证据写部署编号与真跑的 `project_id` 或「本机版」；未测的留在「未验证」并写原因（版式见 [../design/方案页.md](../design/方案页.md)）。Studio 下验收报告写成开发文档「验收报告」（[../design/开发文档/验收报告.md](../design/开发文档/验收报告.md)），过了 2.5 的硬门才用 `studio_write_proposal(documentType="acceptance")` 保存；按反馈重测后出新一版。

## 5. 交棒条件

- 开发者同意部署的，最近一次部署 `status=success`；还没同意的，依赖已部署版本的条目都记了「未测」；
- 每条验收条目都有结论：通过（带 2.4 要的证据）/ 好不好你说了算（附了实际结果）/ 未测（属于 2.4 表里的一类、写了原因）/ 没通过且开发者选了接受；已部署时，读写应用库的条目至少有一次 `workspace` 真跑的 `project_id`，这些路线每条 TPE 最近一次 `verify(tpe_id, project_id)` 为 `passed`；
- 验收清单逐条有结论；
- 验收报告过了 2.5 的硬门并已发给开发者；开发者（和需求方）看过报告后明确说了「可以上线」或等价表述，原话已记 checkpoint；有「未测」条目时说「可以上线」照样算；
- 出口阶段记录：在「可以上线」checkpoint 之后用 `business_ui_stage` 写 G6，全部通过 `result=passed`，有「未测」为 `partial` 并在 `completion` 逐条写明未测条目与原因；`workspace.json` 的 G6 标 `passed`。硬门不过时两者都是 `failed`。两套取值的对应见 [../reference/开发者中心与工作区.md](../reference/开发者中心与工作区.md)「三件套与阶段标记」。

## 6. 出问题怎么办

| 现象 | 先看 | 回到 |
|---|---|---|
| 部署失败、被脚手架闸门拒绝、部署占用超限、`BUSINESS_UI_CONTRACT_OUTDATED` | [../reference/报错对照.md](../reference/报错对照.md)「部署与预览」 | 本段 2.2；源码问题回 ③ |
| 开发者说在线预览打不开或未就绪 | 同一文件「部署与预览」 | 本段 2.2 |
| 真跑报错、卡 `waiting-input`、`resolve` 报还没有上线版本 | 同一文件「真跑」 | 本段 2.3 |
| 本机版或无头浏览器起不来 | [../reference/开发者中心与工作区.md](../reference/开发者中心与工作区.md)「本机版页面验收」 | 本段 2.1 |
| 协作者预览提示需用新版脚手架重建，或充值相关操作被拒 | [../reference/多人协作.md](../reference/多人协作.md)「预览、费用与限制」：预期限制，不是平台问题 | 本段 2.4 |
| 真跑内容不对 | 模型步骤提示词、模型档位或输出字段 | ③ |
| 页面行为不对 | 页面块或生成页 | ③ |
| 开发者说要的东西本身不对 | — | ①：改 PRD，只重做受影响的部分 |
| 疑似平台问题 | [../reference/报错对照.md](../reference/报错对照.md)「平台问题怎么报」 | — |
