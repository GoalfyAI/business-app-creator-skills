# ③ 制作（工作区阶段 G4、G5）

按施工单把后台能力、数据和页面做出来。这一段主要是你在做；开发者要知道每个功能做到哪了，后台做好的功能你自己挑例子先跑一遍，把跑了什么、结果怎样给开发者看，开发者不用填、也不用确认；只有和 ② 的预期差得多时才在这一段请开发者拍板。环境出错、外部服务没钱、平台报错这类问题你自己处理，不转给开发者。

## 1. 进入条件

- ② 交棒：判断题都答了「对」，验收条目已确认，施工单在阶段文档 G3 里。
- 从修订进来时，先取可编辑草稿（场景包 `ensure_draft`、应用 `business_ui_manage(action="ensure_draft")`、其他资产 `ensure_editable_asset_draft`），只改受影响的资产。

## 2. 段里怎么做

先做后台能力（2.1），再做数据和页面（2.2）。每做好一个功能，发一次进度（2.3）。每一步的参数以工具当前 Schema 为准，这里只给顺序和必带项。

### 2.1 后台能力（G4）

1. **场景包草稿**：新建 `scene_package_manage(action="create", task_id, name, description, apc_skill)`；已有包用 `ensure_draft`，官方或他人的包先 `clone_asset`。`apc_skill` 用开发者的词写「这个包能做哪几件事、各自什么时候用、发起前要收齐什么」，1–4k 字，不写资产 ID。
2. **接入缺的工具**（① 判定要接入时）：按 [../reference/依赖与MCP接入.md](../reference/依赖与MCP接入.md) 先预览再注册，需要使用者各自授权的配授权卡。
3. **FA**：每个模型步骤一个 `create_fast_agent(name, description, prompt_content, model_name, model_selection_mode="required", …)`，`model_name` 用 PRD 定的档位对应的模型；一个 FA 只承担一个语义责任。只要这个模型步骤要按客户、任务或上一步结果去应用库挑选素材、记录或上下文，**不管施工单怎么写**，建 FA 时就按 [../reference/数据模板.md](../reference/数据模板.md)「FA 挂工具」挂上 `query_business_app_dataset` 工具组并反读确认，不要等到做数据和页面时再补；**禁止**把素材摘要、记录列表整批塞进入口字段来绕过。由脚本查出一批记录再交给 FA 判断的，FA 的 `input_schema` 只收文件路径（`records_path`，或分片清单 `chunks_manifest_path`）和日期范围这类控制字段，**禁止**出现 `records`、`records_json`、`feedback_items`、`items` 这类装整批内容的字段；输出按 `record_id` 逐条给标签和理由，**不**输出总数、分类数（计数由脚本统计）。提示词写清输入字段、输出对象每个字段的含义和非成功状态；输出要给部分成功留出口（见 [../reference/编排脚本.md](../reference/编排脚本.md#fa-与脚本的职责边界)）。建完 `get_asset(asset_type="fast_agent")` 反读 `mr_name` 和模型配置，脚本里用这个名字，**禁止**自己拼前缀或用数字 ID。
4. **工具集**：把核实过的工具组、FA 装进 `create_toolset(name, description, tool_group_ids, fast_agent_ids)`；脚本要读写应用库的，把工具组「query_business_app_dataset」也装进来；一条路线通常一个工具集。含 MCP 工具组的，用 `otpe_tool_test` 对其中的工具做一次安全的真实取样；只含 FA 的，`get_asset` 反读 FA 配置无误即可上线。然后 `online_toolsets`，再 `get_asset` 反读确认全部上线——离线工具集运行时加载不到，编排型 TPE 也建不了。
5. **编排型 TPE**：脚本按 [../reference/编排脚本.md](../reference/编排脚本.md) 三种模板之一改，第一次写之前读 `get_diagnosis_doc(topic="otpe_single")`。从「三种模板」整段复制再改业务词，不从零写：入口函数名、`emit_business_event` 的 `event_type`（`stage_started` / `stage_result` / `stage_failed`）都写字面量，不用变量拼；事件契约照同一节「对应的事件契约」抄，只改 `event_key` 和 stage 名。定 `_output` 时先过同一参考的职责边界门禁：控制面保持最小，内容走稳定载体引用，同类错误连续两轮就停止扩 Schema 并重划职责。路线读写应用库的，preview 前逐项自查，**任一项不满足先改，禁止 preview / create**：
   - 脚本复制了统一的 `db()`，所有应用库读写都经 `db()`，写库语句包在 `if not ctx.dry_run:` 里，没有自写 `query_db`、`sql_literal`，也没有用 f-string、`+`、`.format()` 把业务值拼进 SQL；
   - 工具集装了工具组「query_business_app_dataset」并在 `preload_toolset_ids` 里；要自查应用库的 FA 反读 `tool_group_ids` 不为空；
   - `input_schema` 只放发起者必须给的业务键和少量临时补充（如当次的 `goal_override`、`extra_requirements`，只作补充，不能带客户、素材、记录全文，也不能让脚本因它跳过查库），**不得**出现 `fallback_*`、`materials_summary`、`materials_text`、`snippets`、`records`、`records_json`、`customer_profile`、`customer_summary` 这类整包字段来代替本该从应用库查的数据，也不留「入口传了就用、没传再查库」的兜底；
   - 脚本查到一批记录要交给 FA 判断的，先按 [../reference/编排脚本.md](../reference/编排脚本.md#文件产物) 写进 `ctx.process_dir`，调用 FA 只传路径；
   - 一次处理的条数按 PRD 的用量上限设计（分批、分片、超出时怎么提示），不在脚本里写死一个比用量小的上限。

   `otpe_manage(action="preview", task_id, script, input_schema, output_schema, business_event_contracts, preload_toolset_ids)` 通过后 `create`（同一组参数加 `scene_package_id`、`name`、`description`），再 `online`。事件契约最少两条：`stage_started` + `stage_result`。

   **反读自查**：要用施工单「存数据」里的表（客户、素材、历史记录），或结果要存下来给页面看、给下次用的路线，都算读写应用库，不按「这样写更简单」判断。这类路线 `online` 后用 `get_asset(asset_type="tpe")` 反读脚本、`get_asset(asset_type="fast_agent")` 反读要查库的 FA，在阶段文档 G4 每条路线记四项「有 / 没有」：① 脚本有 `db(`，读写库都经它；② 写库包在 `if not ctx.dry_run:` 里，并照 [../reference/编排脚本.md](../reference/编排脚本.md)「三种模板」二选一：路线自己建的行照模板一写 `INSERT … ON CONFLICT (<业务键>) DO UPDATE`（业务键在表上有唯一约束），后端已建的行照模板三写 `UPDATE … WHERE id = :id` 且改到的行数不是 1 就返回 `blocked`，不带 `ON CONFLICT` 的 `INSERT` 不算；③ 工具集含「query_business_app_dataset」并在 `preload_toolset_ids` 里，要查库的 FA 反读的 `actual_tool_group_ids` 含它（`configured_tool_group_ids` 只是配置值，为空或不含它都算「没有」）；④ `input_schema` 没有上面列的整包字段。任一项「没有」就回本步改，**禁止**部署、进 ④ 或在进度里写「做好了」；只发事件、只做计算、不查库也不写库的脚本是空壳，不算做好。
6. **verify**：`otpe_manage(action="verify", task_id, tpe_id)` 看 `verdict`：`blocked` 按 `failed` 项改后重来；`needs_bubble` 说明静态项都过了，只差运行证据。
7. **单条冒泡只用于多节点路线的单节点调试**：路线只有一个节点时跳过。多节点路线里某个节点要单独调通时，`otpe_manage(action="bubble", task_id, tpe_id, workflow_input=<代表性输入>)` 拿 `run_id`，只传 `run_id` 续等到终态，再 `verify(tpe_id, run_id)`。
8. **路线**：`scene_package_manage(action="assemble", task_id, scene_package_id, tpe_ids=[按顺序], orchestration_id, title, entry_form_id)` 得到草稿；处理 `unresolved` 与 `notes`，再把 `workflow_orchestration` 原样传给 `scene_package_manage(action="update", scene_package_id, workflow_orchestration)` 保存。分支、并行、中途表单、Agent 接管按 [../reference/业务路线.md](../reference/业务路线.md) 手写接缝。
9. **拿真实结果**：
   - **先挑例子**：例子由你挑，不请开发者填、也不请开发者确认。从 ① ② 已有的东西里挑：开发者给过或 ① 真查过的样例、② 判断题和验收条目里写到的边界情况（同名多家、名字像别的东西、做过一次再做、查不到）。每条路线一个正常例子，有明确边界规则的再各加一个；每个例子写一句「为什么挑这个」，说清要看它会不会出哪种错。
   - **不读写应用库的路线**：`scene_package_manage(action="bubble", task_id, scene_package_id, orchestration_id, workflow_input=<挑好的例子>, full_run=true)`，让模型步骤真的跑出内容；续等只传 `run_id`，回填中途表单传 `run_id + formdata`。到终态后对路线里每条 TPE 调 `verify(tpe_id, run_id=<WRV- run_id>)`，`passed` 即完成。用回执里的 `project_id` 调 `get_project_execution_logs(action="workflow_trace", project_id)` 取每一步做了什么、产出什么，按 2.3「我先跑了一遍」交给开发者看；原文记进阶段文档 G4。改了脚本或路线才重新跑。
   - **读写应用库的路线**：部署前跑不了真数据。静态 `verify(tpe_id)` 返回 `needs_bubble` 且 `failed` 为空就算这一步做完，进度「后台」标「做好了，等部署后真跑」，运行证据在 ④ 用 workspace 真跑补。要调试不碰库的步骤时可以冒泡；冒泡里读库返回 `not_a_business_app_project`、写库被 `ctx.dry_run` 跳过都是预期；**不要**为了让冒泡通过把读库包进 `dry_run`、从入口塞数据、加 `fallback_*` 兜底或删掉读写。

**冒泡的边界**：不加 `full_run` 时 FA 是桩（按输出 schema 造值），工具、shell、文件照常真实执行，只有脚本按 `ctx.dry_run` 判断的外部动作被跳过；桩跑通只算「只用模拟数据试过」。桩值导致下游失败时，也对同一路线加 `full_run=true` 重跑一次。PRD 已同意制作中的测试费用，`full_run` 直接跑，跑完在方案页「费用与副作用」补一句实际花费，并在交接消息里报；会对外发送、或累计将超上限时先问。冒泡里某一步异常长跑、步数或 `cost_credits` 一直在涨时，先止损再排查：路线冒泡 `scene_package_manage(action="cancel", task_id, run_id)`，单条冒泡 `otpe_manage(action="cancel", task_id, run_id)`；回执 `status=cancelled` 不算资产失败。冒泡验证项目只读，`manage_goalfymax_project(stop)` 会被拒绝，停冒泡只能用 cancel。

**参数由谁填**：事件契约、`_output`、`_rationale` 在脚本模板里已有位置，只改业务词；入口映射、节点映射、交付映射由 `assemble` 生成，你只审 `unresolved`；`tpe_id`、`scene_package_id` 来自上一步返回值，记进工单，不手抄。

### 2.2 数据和页面（G5）

页面要调用的路线先能跑（每条 TPE verify 通过或只差运行证据）；只改表、页面或后端、不碰路线时不需要重做 2.1。应用工程里要有 `frontend/registry.json`，缺失时按 [../reference/脚手架与预置件.md](../reference/脚手架与预置件.md) 核对当前工程、实际版本与迁移完整性，不从文件存在与否猜版本；满足合同后再使用页面块与生成器。

1. **应用身份**（先于把 `current_stage` 改成 G5）：`business_ui_manage(action="setup", task_id, name, scenario_pack_id=<场景包家族 ID>, operation_id=<稳定键>)` 得到 `business_ui_id`；在应用根执行返回的 `scaffold_bind_command` 回填 `app.json` 与 `WORKSPACE.md`。重复调用按 `operation_id` 复用，不会建出第二个应用。
2. **数据模板**（每个应用都要做，至少一张业务表），细则见 [../reference/数据模板.md](../reference/数据模板.md)：
   1. `dataset_template_workspace(action="open", task_id, name, description)` 记下 `data_uid`；返回的连接串填进 `backend/.env`，**禁止**进工单和聊天。
   2. 每张表 `create_table(task_id, data_uid, table_name, target_columns=[…])`：至少一列 `primary_key=true`；每列 `comment` 以 `[editable:user|agent|system]` 开头再写中文名，选项列在注释里加 `{options:a|b|c}`；有写入的表带审计列 `created_at`、`updated_at`、`updated_by`、`last_run_id`、`row_version`、`deleted_at`（都是 `system`），NOT NULL 的审计列必须带 `default`，列定义与默认值见《数据模板》「审计列」。
   3. `inspect` 反读，确认列与注释都在；与施工单表清单不一致就改到一致。
   4. `extract(task_id, data_uid, template_name, template_description)` 出模板版本，记下模板 ID 与整数版本号。
   5. `business_ui_manage(action="setup", task_id, business_ui_id, dataset_template_id, dataset_template_version, data_uid)` 一次挂模板（版本钉整数）并把开发工作集绑到应用；已挂同版本的步骤会跳过。返回 `success=false` 时看 `steps` 里哪步 `failed`，修正后原参数重调；仍失败再用 `business_ui_manage(action="update")` 与 `dataset_template_workspace(action="bind")` 单步处理。工作集一直保留（见 ⑤）。
3. **数据页一条命令**：把 `inspect` 返回的 `columns` 原样存成 `<表名>.json`（形如 `{"table","label","columns":[…]}`），执行 `npm run gen:pages -- --table <表名> --label <中文名> --spec <表名>.json`。它生成列表 / 详情 / 新建 / 编辑页、OpenAPI、后端 CRUD 与测试，接好路由、导航和挂载；再跑一次不会覆盖。
4. **场景包契约进前端**：场景包契约写进 `frontend/schema/packs/<pack>/`（见 `frontend/schema/README.md`），路线的入口表单、项目层、表单应答、交付审阅由预置件按它自动推导；示例包在第 8 步一起清。
5. **按 PRD「界面」写业务页**：「界面」一节是页面的最高依据。开发者给了参考网站、截图或原型时，页面结构和样子照它做（《前端页面》「界面以开发者为准，预置件可用可不用」「参考网站」）；写「开发者不指定」时，按《前端页面》「界面风格」自定，配进 `src/app/config.ts`，写进阶段文档 G5。PRD「谁来用」有几种人，就按每种人「看到什么」组织首屏和导航；首屏与导航按验收条目里的业务顺序组织，不照搬脚手架默认导航。平台行为（消息中心、历史记录、表单应答、交付审阅、只读置灰、保留区避让）**必须**与预置件一致；不改 `ui/`、`blocks/` 源码，要改就复制出来。正式版每个使用者从空库开始：页面要有空库时的引导；上线后必须存在的设定，所有人一样的写成代码默认值或场景包配置，每人不同的做首次设置入口。
   **演示和示例要放真实成果的**（新人演示、首页示例报告这类）：这一段先放 ① 里真拿到的数据；模型要写的内容还没真跑出来时，放一份标明「示例」的占位，并在阶段文档 G5 记下「待 ④ 回写」和位置。④ 真跑出结果后按 ④ 2.2 第 6 步回写。
   **业务文案必须填写并接入**：按 [../reference/前端页面.md](../reference/前端页面.md)「业务文案」落实；字段、覆盖优先级和接线只读当前模板 `frontend/README.md`「业务文案」。
6. **后端接口**：生成的 CRUD 够用就不写；要统计或生产回流时在 `backend/src/common` 上包一层（`createCrudService` 的 `applyGeneratedResult` 写 agent 列），先写 `frontend/schema/api/<operationId>.yaml` 再实现。
7. **外部平台授权、充值、自动化**（PRD 列了才做）：分别见 [../reference/授权与充值.md](../reference/授权与充值.md)、[../reference/自动化.md](../reference/自动化.md)。
8. **清掉起始件、对齐路由**（以下几项散在《前端页面》和《脚手架与预置件》，这里一次做完）：
   - 去掉示例包 `demo-pack`：删 `frontend/schema/packs/demo-pack/`，`goalfy-app.json` 的 `packs` 只留本应用的包；
   - 删掉起始页占位、demo 路由和对应导航项；
   - `goalfy-app.json` 的 `routes` 逐条对上 `App.tsx` 实际注册的项目页、表单应答页、交付审阅页路径，没有对应页面的那条删掉（《前端页面》「让宿主小喇叭能跳进来」）；
   - 示例数据在界面上标明是示例，不放与业务无关的数据；
   - 跑 `npm --prefix frontend run check`，路由模板、packs、内部 ID 警告都清零。
9. **本地跑**：从应用根执行 `npm --prefix frontend run check` 与 `npm run verify`，检查范围与前端测试入口见 [../reference/脚手架与预置件.md](../reference/脚手架与预置件.md)「命令」。修改前端行为后另跑前端测试；类型检查与构建不能替代测试。要做本地联调或布局回归时用 `npm run dev` / `npm run dev:restart` 后台起服务；这是给测试用的，开发者中心的「演示预览」不显示工作源码，要等需求全部完成后生成完成版（见 [../reference/开发者中心与工作区.md](../reference/开发者中心与工作区.md)「演示预览为空」）。

**不要做的**：不写占位页、不留 demo 路由（`npm run verify:release` 会拦）；不用 antd 重画已有的块，不引新图表库；不手写 OpenAPI 与后端 CRUD（生成器出的可以改）；应用代码**禁止** `CREATE / ALTER TABLE`，表结构只走数据模板。

### 2.3 进度（给开发者）

每做好一个功能发一条交接消息（[../design/交接消息.md](../design/交接消息.md)），开头「【③ 制作 → 正在做】」，附一张进度表，只报做到哪了：

| 功能 | 后台 | 页面 | 存数据 |
|---|---|---|---|
| <功能名> | 见下 | 做好了 / 在做 / 没开始 / 不需要 | 做好了 / 在做 / 没开始 / 不需要 |

「后台」一格写四种之一：

- **做好了，真跑过**：2.1 第 9 步 `full_run` 跑到终态；
- **做好了，只用模拟数据试过**：桩跑通；
- **做好了，等部署后真跑**：读写应用库的路线，静态 `verify` 只差运行证据，④ 部署后真跑；
- **在做 / 没开始**。

- 进度表下面写一句总数（例如「19 项里做好 15 项」），和方案不一样的地方各写一句（换了什么、对使用者有什么不同）。读写应用库的功能「后台」标「做好了」时，同一条消息里写一句「存数据自查：<路线名> 四项都有」，四项是 2.1 第 5 步的反读自查；写不出这句就不能标「做好了」。
- **我先跑了一遍**：后台「做好了，真跑过」的功能，进度里附上 2.1 第 9 步跑的结果，每个功能先写一句总的（「跑了 3 个例子，都和方案说的一样」），再按例子列：

  | 项 | 写什么 |
  |---|---|
  | 例子 | 用业务话说是哪个例子，例如「清水缘和服租 · 京都」 |
  | 为什么挑这个 | 要看它会不会出哪种错，例如「店名和景点很像，看会不会把清水寺当成门店」 |
  | 用了什么 | 入口填了哪些、哪些空着 |
  | 每一步 | 按 ② 的步骤逐步一句结果；停在使用者要确认的那一步时写「停在这一步，等使用者……」，主语是使用者，不是开发者 |
  | 结果 | 最后拿出来的东西，摘要即可；和 ② 的预期一样不一样 |
  | 花了多少、用了多久 | 这一次的实测 |

  开发者看了觉得哪里不对，直接说是哪一条；不说就不用等。这一块不放输入框、不放「运行」按钮，开发者不用填也不用点头。原始输出只放阶段文档 G4，进度里写业务话。
- 跑出来的结果和预期不一样、但只是做法上的偏差（漏字段、格式不对、时间写错），你自己改好再跑，进度里写一句「和预期不一样的 N 处已经改了」。和 ② 的预期差得多、要开发者拍板的，按 2.4 把预期和实际放在一起问。
- 页面做完给一段**页面说明**：每个页面给哪种人用、显示什么、有哪些按钮。可以附本地布局回归的截图（只连本机 Mock，不是线上页面），写明「示意，按本地完成版截」。
- **没做成的**写哪件事没做成、原因、影响哪个功能。

### 2.4 什么时候请开发者拍板

| 情况 | 怎么问 |
|---|---|
| 真实结果和 ② 的预期差得多，不是你能改好的偏差（例如报告要 49 分钟、说好 30 分钟） | 两份放在一起，做成选择题：按预期改做法（写代价）/ 接受现在的结果 |
| 累计花费到上限的 80% | 选择题：继续 / 减少测试份数 / 提高上限 |
| 做的时候发现做不到 | 选择题：换做法（写差别）/ 这次先不做；要的东西因此变了就退回 ① |

另外两种情况也停下来问，它们属于开发者自己手上的事：缺开发者本人才能给的东西（授权、密钥、业务事实），按「要你做的」列出；要做 PRD 没列的外部副作用（花钱、发送、写正式数据），先说清范围再问。

除此之外不停下来等开发者。**禁止**请开发者「重新连接开发能力」、提供凭证路径、批准改数据库、决定回归测试范围；这些按 [../reference/报错对照.md](../reference/报错对照.md) 自己处理，处理不了按 `SKILL.md` 第 7 节报平台问题，交接消息里写「卡住了」和对开发者的影响；没人修时按同一节「阻塞的平台问题没人修时按这个顺序升级」做，满 1 个工作日给开发者出选择题。

## 3. 不给开发者的

提示词改动、模型名、测试过了多少项、verify 报告、原始运行日志和 JSON（「我先跑了一遍」只写业务话）、建表、迁移、部署过程、环境出错和重连。

## 4. 产出与落盘

- 工单 checkpoint：场景包草稿 ID、每个新建资产的 ID 与 `mr_name`、每个 FA 的模型、每条 TPE 的 verify 结论、每条路线的冒泡 `run_id`、是否 `full_run` 与终态、花费；`business_ui_id`、`data_uid`、模板 ID 与版本、`npm run verify` 结果。
- 阶段文档 G4：资产清单的实际结果与 verify 摘要；每次试跑的例子、为什么挑、入口原文、每一步结果、输出原文、`run_id` 与 `project_id`、花费与用时，以及和预期的对照；开发者拍板的题和答案。阶段文档 G5：表结构（`inspect` 结果的业务说明）、页面清单的实际结果、「已确认业务含义—界面文案—实际页面/动作」简短对应（包含整体对象、各入口/补充动作及真实产物），不另建文案计划书。
- 方案页 `status` 写当前进展；`full_run` 或真跑到终态的才进「已验证」并写 `data-evidence`；桩跑通、本地预览的写进「未验证」并写明「只用模拟数据跑过」「本地预览」。
- 阶段标记：G4、G5 `passed`。

## 5. 交棒条件

下面都满足后，先用命令把 [4-试用验收.md](4-试用验收.md) 从头读到尾，再做 ④ 的第一件事。

- 每个功能的后台、页面、存数据都是「做好了」或「不需要」（后台是三种「做好了」之一），或标明没做成及原因，开发者已就没做成的选过；
- 每个后台「做好了，真跑过」的功能，都已经按 2.3 给开发者发过「我先跑了一遍」（例子、为什么挑、每一步、结果）；只写「示例已跑通」这类一句话结论的不算；FA 是桩的冒泡（没加 `full_run`）不能写成「真跑过」；
- 每条读写应用库的路线，2.1 第 5 步的反读自查表四项都是「有」，表已记进阶段文档 G4；
- 每条编排型 TPE：最近一次 `verify` 为 `passed`（带路线冒泡或单条冒泡的 `run_id`）；读写应用库的路线只差运行证据（`needs_bubble`、`failed` 为空），`passed` 由 ④ 真跑补上；
- 每条不碰应用库的路线：当前合同下最近一次冒泡到终态 `success` 的 `run_id` 已记入工单；失败的已修好重跑，或已按 ⑤ 的结单门说明原因；
- `business_ui_id` 已绑定、数据模板版本已挂到应用、工作集已绑定；
- 应用根 `npm run verify` 全绿，业务文案已由实际页面和动作消费；
- 累计花费没超过上限，或超出部分开发者已选过。

## 6. 出问题怎么办

| 现象 | 先看 | 回到 |
|---|---|---|
| verify `static_contract` 失败 | `errors[].where/msg`，多半是 `_output` 形状或事件契约 | 本段 2.1 第 5 步 |
| verify `toolsets_online` / `tpe_online` 失败 | `online_toolsets` / `otpe_manage(action="online")` | 本段 2.1 第 4、5 步 |
| 冒泡失败 | `steps[].error`；`repeated_error_count>=2` 换策略，不原样重跑；同类事实错误、引用错误或无产物连续两轮时，按 [编排脚本职责边界](../reference/编排脚本.md#fa-与脚本的职责边界) 停止加字段并重判职责 | 本段或 ② 施工单 |
| 冒泡没到终态 | 服务端最多等约 45 秒，用同一 `run_id` 续等，不要重新发起 | 本段 |
| 冒泡异常长跑，步数或积分一直涨 | 先 `cancel` 同一 `run_id` 止损，再看 `cancellation.stopped_nodes` 与 `steps[].error` | 本段「冒泡的边界」 |
| 不确定 FA 用了哪个模型 | 回执顶层 `resolved_model` / `resolved_mode` 是这次验证运行（外层 SA）的模型和模式，不是 FA 的；FA 按资产配置运行：`required` 模式固定用该模型，`agent_selected` 模式用资产兜底模型，未配兜底用平台默认组；用 `get_asset(fast_agent)` 查 `model_selection_mode` 与 `model_name` | 本段 2.1 第 3 步 |
| FA 失败或 `FA_STEP_BUDGET_EXCEEDED`，不知道它每一轮做了什么 | 先看 `manage_goalfymax_project` wait/status 返回的 `fast_agent_failures` 和下一步提示；再用 `get_project_execution_logs(action='detail', log_type='fast_agents', project_id=…)` 看逐轮的工具、参数和截断标记（`args_truncated_by_repeat_guard`）。冒泡回执里的 `project_id` 在冒泡发起后 2 小时内可读 | — |
| `npm run doctor` / `verify` 失败 | 先修第一条 `FAIL`；`GIT_ROOT_MISMATCH` 见 [../reference/开发者中心与工作区.md](../reference/开发者中心与工作区.md) | 本段 |
| `create_table` / `extract` 被拒 | 返回的列与 diff；破坏性变更要带迁移脚本 | 本段 2.2 第 2 步 |
| 连接串过期 | `dataset_template_workspace(action="connect")` 重签 | 本段 |
| 前端契约门禁报 packs 不一致 | `goalfy-app.json` 的 `packs` 与 `frontend/schema/packs/` 目录 | 本段 2.2 第 4、8 步 |
| 页面要的数据路线不给 | TPE 的 `output_schema` 缺字段 | 本段 2.1 改 schema，或回 ② 改施工单的页面清单 |
| 真实结果始终达不到预期，要换做法 | — | ②：改业务说明，请开发者重新答那道判断题 |
| 其他报错码 | [../reference/报错对照.md](../reference/报错对照.md) | — |
