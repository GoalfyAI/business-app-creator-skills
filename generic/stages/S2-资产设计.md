# S2 资产设计

拿着已确认的《场景包计划书》做资产设计——复用项目与场景包、摸底能力、选执行形态、设计路线编排与架构、方案挑战——产出**完整的《场景包制作书》**并经开发者确认。本阶段不创建任何正式资产；制作在 S3。

## 1. 进入前提

《场景包计划书》已按 S1 5.1 写入工单并经开发者确认（`build_book`，`stage="S1"`）——本阶段在它之上做资产设计（第 2–7 节），形成完整制作书并过制作书硬门后进入 S3 制作。修订已上线包的任务已持有草稿行（S1 第 6 节）。

**边界**：计划书里的业务口径（画像、旅途、交付角色、红线）在本阶段只做落地不做改写；资产设计发现业务口径要变，回 S1 第 5 节。

## 2. 复用：项目、场景包与资产摸底

拿着已确认的计划书（`build_book`，S1）开始资产设计。先复用、再摸底、最后才谈缺口——三个来源按此顺序看：参考项目（真实执行记录，可信度最高）、已有场景包与官方基础包（能派生就不从零建）、平台能力（工具组 / 工具集 / FastAgent / 数据集）。

### 2.1 参考项目三层深读

开发者提供了参考项目时**必须**完成三层，**禁止**只看摘要下结论（约束 3）。

**第一层 概览**：读项目摘要，统计总轮次、最终用户请求序列、执行阶段、Agent 与工具分布、等待与失败概况。摘要是压缩后的统计信息，**只能**用于建立全局视图和定位需要深挖的轮次，**不能**作为结论。

**第二层 深读**：读取完整原始日志的全部分页，截断时**必须**续读到结束。重点看：最终用户原始意图与约束、规划逻辑与步骤拆分、工具调用密集的阶段（调用链、参数传递、前后依赖）、任务点与 FastAgent 的输入输出质量、失败重试、等待原因、最终交付是否匹配预期。

**第三层 分析**：形成以下可复核结论并写入工单：

- **轮次分类统计**：总轮次、有效推进、重复沟通、失败重试、等待
- **瓶颈定位**：消耗最多轮次的阶段，根因归类为缺知识、缺工具、缺指引、缺前置检查或资产边界错误
- **真实调用链提取**：每个业务阶段实际调了什么、顺序如何、有没有前置依赖但 Agent 不知道
- **Skill 使用情况**：哪些文件被读取、哪些应该被引导读取但没有

多个项目对比时，**必须**逐项目保留独立事实，再提炼共性，**禁止**用平均值掩盖异常。

**完成标准**：三层全部完成并写入工单后才能进入下一步。**禁止**只看摘要就跳过深读——这是本阶段最容易出现的问题。

### 2.2 复用已有场景包与官方基础包

你**必须**主动获取的：

- 用 `get_asset` 查看**官方基础场景包**的完整配置，理解其预加载与动态工具集的组合方式，作为选型基准
- 用 `list_assets` 加 `get_asset` 查找可参考的已有场景包；开发者要"基于某个已上线包做一个变体"时，用 `get_scene_package_lineage` 看它的来源与派生包，再评估是走**派生**（`create_derived_scene_package`，见路由器 §7.1）还是新建
- 用 `get_diagnosis_doc(scene_package)` 读当前场景包契约

复用的判据是**计划书**：候选场景包 / 派生来源覆盖了计划书 ②③ 章里的哪些路线与交付、用词与画像是否一致、缺什么。能派生就不从零建（路由器 §7.1）。

### 2.3 能力摸底与覆盖矩阵

三个只读工具：

| 工具 | 用途 |
|---|---|
| `list_assets` | 按类型搜索可复用资产。关键词只匹配名称和 ID，建议用英文短词；不传关键词会返回全量，注意上下文开销 |
| `get_asset` | 批量反读完整配置、关系、Schema、状态，一次 1–20 个 |
| `dataset_read` | 只读查看长期数据集：描述、使用指南、Skill 文件、表、列、行 |

用 `list_assets` 和 `get_asset` 搜索并完整反读场景包、任务点、工具集、FastAgent、工具组、数据集；摸底的目标来自计划书第 ②③⑥ 章——每个里程碑、每条路线、每类产出各需要什么能力。看 Schema 和真实配置，**不要**只看描述。

搜索结果**不是**完整资产契约，选型前**必须**用 `get_asset` 下钻（约束 4）。重要选择结论用 `task_manager(insert)` 留痕。

一次 `get_asset` 只返回该资产自身的配置，**不会**展开它引用的子资产。诊断时**必须**按层逐级下钻。

场景涉及数据查询或报表时，用 `list_assets` 列出开发者有权访问的长期数据集，`get_asset` 或 `dataset_read` 确认表结构与权限范围。数据集**只能**绑定真实可访问的，**禁止**假设开发者拥有某个数据集。开发者没有对应数据集时明确告知需要先去准备。

按每个里程碑建立覆盖矩阵：**已覆盖 / 可组合覆盖 / 需维护 / 真实缺口 / 受限能力 / 验证方式**。

向开发者输出每个里程碑的覆盖情况，把缺口处理选项、影响和推荐纳入制作书第 ⑨ 章（7.2），由开发者确认；Agent 不得以“工具缺口不可阻塞”为由自行削减业务目标。

### 2.4 工具缺口四层处理

工具缺口**不可**阻塞创建流程，但**不得**静默削减开发者明确要求或参考项目中已有的能力（约束 12）。按以下优先级处理：

**第一层 Skill 弥补**（成本最低，优先尝试）：工具能力已覆盖，问题只是缺调用顺序、前置检查、字段准备或结果审视方法。把指导写进正确层级即可。

**第二层 接入现有能力**：先在平台上找，平台没有再去外部找。

平台内：用 `list_assets` 和 `get_asset` 确认是否已有可复用的工具组——重复注册同一个服务会产生互相冲突的资产。

平台没有时**从外部获取**。你运行在能联网、能读写本地文件、能执行命令的环境里，这是 Max 内部制作助手做不到的，**应当主动利用**：

| 目标 | 去哪找 |
|---|---|
| 现成 MCP 服务 | MCP 官方索引、代码托管平台、包管理平台（npm / PyPI），以及开发者自己的私有仓库 |
| 现成 Skill 包 | 同上；开发者手里可能已有内部沉淀的包 |

找到候选后**先在本地验证，再走平台注册**。顺序反了会浪费大量试错：本地能起来、工具清单和返回结构都确认过，注册基本一次通过；直接注册再排错，每轮都要等平台反馈。

评估候选时**必须**看清四件事：

| 维度 | 为什么要看 |
|---|---|
| 是否仍在维护 | 长期不更新的服务上线后容易失效 |
| 连接方式 | 决定注册时传地址还是启动命令，以及运行环境要装什么 |
| 认证方式 | 全场景包共用一份凭证，还是每个终端用户各自授权——后者**必须**配授权卡 |
| 有无破坏性操作 | 决定哪些工具可以取样、哪些**禁止**取样，以及要不要在使用指南里加约束 |

开发者提供本地包或压缩包时，走 `file_to_url` 换取引用后注册或导入（见 S3 2.3）。完整的注册流程、失败调试循环和上线检查见 [依赖与 MCP 接入](../references/依赖与MCP接入.md)。

**第三层 形成开发需求**（开发者有协作团队时）：为缺失能力生成可直接转交的需求说明，**必须**写明业务动作、目标系统、必需输入与输出、授权方式、最终用户与项目隔离要求、副作用、失败语义、验收样例。格式要便于开发者一键转发给工程师。

**第四层 开发者确认后降级**：用已有能力继续制作，**必须**明确说明未覆盖的阶段、对结果的影响、以后补齐的条件和受影响的验证，并取得开发者确认。

### 2.5 实现思路调研

**不知道某个效果如何实现时**（有目标、无做法）——**先询问开发者是否有参考资料或已知同类产品**；没有再去 GitHub 等开源平台自行调研同类实现。调研的是**实现思路**而非现成资产，产出可以是自建 Workflow / 工具的设计依据，或转交开发需求（第三层）的技术方案参考。结论与来源记入工单。

## 3. 理想态与价值预测

### 3.1 现状、理想态与配置手段

构建"现状 → 理想态 → 配置手段"的映射，它决定后续 Skill 要写到什么颗粒度：

| 现状问题 | 配置手段 |
|---|---|
| 缺知识导致试错 | 补业务规则或场景 Skill 文件 |
| 不知道能力顺序导致绕行 | 补阶段前置检查和工具集搭配指引 |
| 参数结构不清导致失败 | 补必填结构、字段来源、示例 |
| 找不到能力导致浪费 | 在 `apc_skill` 建立能力与文件索引 |
| 重复、稳定、高复用的真实步骤 | 评估做成 Workflow |
| 需要临场判断或中途交互 | 按开发者确认的边界保留给 SystemAgent、任务点或最终用户 |

**有真实项目基线时**可以预测轮次、失败重试或人工确认的改善幅度，但**必须**列出计算依据、假设、不可优化部分和误差范围。**没有基线时只做定性判断**，**禁止**编造数字（约束 2）。

### 3.2 Focus 与泛化

形成使用模式候选：

- **Focus**（"让这个任务更快更省"）→ Skill 写到工具调用级别，固化执行路径
- **泛化**（"沉淀经验用于类似场景"）→ Skill 写到策略级别，保留选路弹性

Agent 根据开发者目标和证据给出推荐，但 **Focus / 泛化必须作为方案 Plan 的显式选择项由开发者确认**；不得因为参考项目更具体就自动选择 Focus，也不得因为素材不足就自动选择泛化。

### 3.3 必须评估是否使用 Workflow

**这一步不能跳过，也不能默认不用。** 逐个里程碑对照第 4 节的信号判断，把结论和理由写入工单。

之所以要强制评估，是因为**做 Workflow 的工作量明显高于普通场景包**——要写脚本、备齐依赖、过上线检查、跑运行验证。省事的做法是全部交给 SystemAgent 临场处理，但那样会把消耗转移到每一次运行上。

两种做法的实际差异：

| | 交给 Agent 临场处理 | 固化成 Workflow |
|---|---|---|
| 每次运行的推理量 | 重新理解任务、重新决定调用顺序、重新组织参数 | 只在 FastAgent 承担的那几个环节里推理，确定性衔接不经大模型 |
| 推理消耗 | 上述推理**每次运行都会重复发生** | 确定步骤不经过大模型 |
| 耗时 | 随推理轮次增加 | 按脚本直接执行 |
| 一致性 | 同样输入可能走出不同路径 | 同输入同路径 |
| 出错定位 | 要读整段对话日志 | 定位到具体步骤 |

判断时先看**结构是否适合固化**：存在至少两个真实步骤，步骤顺序、数据流或扇出汇合关系稳定，不需要大模型在运行中改变下一步，就具备 Workflow 结构条件。再看**固化收益**：会被反复跑、定期产出、或最终用户每次只改几个参数时，固化的稳定性和成本收益更高。重复执行是重要收益信号，**不是唯一准入条件**；一次性任务若仍是确定、稳定的多步管道，也可以采用 Workflow。一次性探索分析若执行走向需要临场判断，则交给 Agent 或普通任务点。

向开发者提交结论时用业务语言讲清取舍：哪些阶段建议固化、这样做在稳定性和使用成本上的区别、哪些阶段建议保留临场判断以及为什么。**是否采用 Workflow 及对应资产边界由开发者在方案 Plan 中确认**；禁止只说"建议用 Workflow"而不说明理由，也禁止为了省制作工作量而不做评估。

向开发者提交价值预测与方案 Plan：预期效果、主要优化点、无法覆盖的部分、使用模式、Workflow 取舍及待确认项。开发者确认前不进入正式资产创建。

## 4. 执行形态选择

### 4.1 资产概念

场景包的组成与 TPE 双类型关系在路由器 `SKILL.md` §7.1；运行时自带的默认能力、四种执行形态各自的构成与能力边界，正本在 [平台对象与运行模型](../references/平台对象与运行模型.md) 第二章。本节只承载选型决策；业务侧的“需要什么”来自计划书第 ②⑥ 章。

### 4.2 四者对照

| | SystemAgent 直接执行 | FastAgent | 普通任务点 | Workflow |
|---|---|---|---|---|
| 是否独立资产 | 否 | 是 | 是（TPE） | 是（TPE） |
| 上下文 | 主对话 | 每次全新隔离 | 独立 | 独立 |
| 能否与最终用户交互 | 能 | **不能** | **能** | 单条**不能** |
| 执行步骤 | 临场决定 | 临场决定 | 临场决定 | **预先固定** |
| 自带文件/命令/邮件 | — | **不自带** | 自带 | 自带 |
| 与编排的关系 | — | 被 Workflow 调用 | **不能**作为编排节点 | 可作为编排节点 |
| 多次运行的一致性 | 每次重新推理，路径可能不同 | 每次重新推理 | 每次重新推理 | 同输入同路径 |

### 4.3 怎么选

按以下顺序完成一次决策，**不要**按复杂度、步骤数量或资产数量来回切换：

1. 先判断执行路径是否需要大模型在运行中决定下一步，或是否需要自然语言往返。需要时使用普通任务点；不需要时继续。
2. 再判断是否存在至少两个实质步骤、稳定数据流、固定扇出/汇合，或同一路径需要参数化复跑。存在时使用 Workflow；需要多个职责边界时拆成多个 Workflow 并写入图编排。
3. 若整个任务是一个环节的完整工作——一次输入，自己带着工具搜、读、判、写直到产出，一次输出——使用 FastAgent，不为它增加单步转发 Workflow。
4. 若只是当前上下文中确定的少量调用，且没有独立复用价值，由 SystemAgent 直接执行。

决策结果可用下表复核：

| 需要 | 形态 |
|---|---|
| 确定的 1–5 次调用、指令量小、仅当前场景用 | SystemAgent 直接执行 |
| 独立上下文、开放式判断、执行中需要自然语言交互 | 普通任务点 |
| 一个环节从输入到产出的完整工作（含其中的多轮工具调用）、无需中途交互、多场景复用 | FastAgent |
| 至少两个稳定真实步骤、固定数据流、会被反复跑 | 单 Workflow |
| 单条 Workflow 需要发布业务事件、接受业务表单握手或进入 Delivery Review | 单节点业务路线编排 |
| 一条路线内多个 Workflow 的固定依赖、扇出、汇合和交付 | 多节点业务路线编排 |

任务"复杂"或"有多个步骤"**不自动**意味着要用普通任务点，也**不意味着要拆成多个 FastAgent**——一个 FastAgent 挂上工具就能完成复杂但无需交互的整个环节。只有执行中确实需要补信息、暂停确认或自然语言交互时才选普通任务点。

**看到这些信号优先按 Workflow 设计**：

- **反复执行的固定流程**：每日简报、日报、周报这类同一条流程反复跑的产出
- **固定流水线**：搜索 → 筛选汇总 → 生成报告（→ 发送）这类定型流水
- **多对象并行加汇总**：多品牌、多平台、多主题并行调研后做横向对比
- **参数化复跑**：最终用户每次只填几个参数，跑同一套步骤、产出同类结果

判别标准：固定流水线、参数化复跑和定期产出通常适合 Workflow；一次性探索分析若执行走向需要临场判断，则使用普通任务点或 Agent。不能只凭“是否重复”覆盖前述结构判断；成本结构的对比与"必须评估"的门见 3.3，不在此重复。

### 4.4 FastAgent 粒度与数量纪律

**一个业务环节一个 FastAgent。** FastAgent 是带工具的完整执行单元（正本见 [平台对象与运行模型](../references/平台对象与运行模型.md) 2.2）：一个环节里“搜索 → 筛选 → 读取 → 判断 → 按规范产出并落文件”这一整串，该由**一个** FastAgent 挂上所需工具组一口气做完；脚本只负责环节之间的确定性衔接。三条判据：

1. **拆不拆看职责，不看步骤**：拆分 FastAgent 的唯一理由是职责边界不同——不同领域知识、不同产出契约、需要在别处独立复用。同一环节内步骤再多也不拆；**禁止**为每个判断点建一个 FastAgent，**禁止**按“角色”把同域职责拆成多个只在措辞上不同的 FastAgent。
2. **工具挂给 FastAgent，还是脚本自己调，看“下一步靠不靠结果决定”**：固定的准备与收口（取表单值、取数据集固定字段、落产物目录、发事件、回写）由脚本 `tool()` 做；凡是要看着结果决定下一步查什么、读什么、改什么的，属于 FastAgent 内部——把工具组挂给它。脚本里出现 `tool → FastAgent → tool → FastAgent` 的长链，多半是把本该属于一个 FastAgent 的环节切碎了。
3. **不挂工具、只做文字变换的 FastAgent 是误用**：读文件、写文件、格式转换、数据搬运这类去掉大模型也能确定性完成的步骤，直接用工具调用，**禁止**为其创建 FastAgent——无论赋予什么角色。

同一条 Workflow 内**同域多类产出**用「一个 FastAgent + 交付物参数分发 + 按交付物划分的规范文件」承载——提示词只写共同原则与分发规则，每类交付物一份规范文件按需读取。

方案中 FastAgent 超过 3 个时，**必须**逐个说明不可合并的理由（职责边界具体是什么；该判据同时列入方案挑战检查清单）。

### 4.5 两个相反的错误

两个相反的错误都要避免：

**不要给单个 FastAgent 套一层 Workflow。** 如果脚本只做一件事——调用一个 FastAgent，然后把结果原样返回，中间没有任何其他处理——这层 Workflow 不提供任何价值，**直接使用那个 FastAgent** 即可。

**也不要因为步骤少就否定 Workflow。** 一条只有两三步的线性流程（搜索 → 清洗 → 汇总）完全正当。判据是**有没有至少两个实质步骤、数据有没有在步骤之间流转**，与步骤多少无关。

## 5. 业务路线编排设计

计划书第 ③ 章的业务路线图在这里落成真实的编排对象设计（节点、映射、运行中交互、Agent 介入、交付与审阅）；组装写入在S3 第 7 节。

### 5.1 业务路线编排对象

业务路线编排是场景包上的**一个整体对象**，用来固化业务入口、运行身份、执行依赖、交付与审阅。路线可以只有一个 Workflow 节点，也可以包含多个 Workflow：

- **单节点路线**：单条 Workflow 声明或调用业务事件、需要业务表单握手、需要 Delivery Review，或需要由业务应用启动时使用。只有一个节点不代表可以绕开 Business Runtime。
- **多节点路线**：一条路线包含多个 Workflow 的固定依赖、扇出、汇合、交互和交付时使用。
- **直接派发**：仅适用于没有业务事件契约、没有 `emit_business_event`、不依赖 Business/Runtime 握手的单条 Workflow。

构成：

```text
编排对象
├── 版本标记
└── 路线 ×N                     每条路线对应一种业务走法
    ├── 唯一标识、名称、描述
    ├── 入口表单标识
    ├── 路线级输入定义
    ├── 节点依赖图                节点引用已挂载的 Workflow，必须无环且全部可达
    ├── 节点输入映射              逐字段声明取值来源：路线输入，或依赖的上游节点输出
    ├── 运行中交互（可选）         上游成功后才能确定、且供尚未派发的下游节点使用的输入
    ├── 节点级 Agent 介入（可选）  节点成功后需要检查或处理异常时声明
    └── 唯一最终交付与审阅动作  交付核验与业务验收是两个独立阶段
```

写入时采用**整体替换**语义，因此写前**必须**反读原值（见 S3 9.1）。字段的具体名称、结构和版本要求以 `get_diagnosis_doc` 的当前契约为准（见 S3 4.1）。

运行期事实：已发布路线在业务应用与聊天两个入口天然并存，走哪个入口由最终用户自选（界面经 Runtime 运行，聊天直调时业务事件自动降级）——这是平台行为，不是设计决策。制作侧**不设计**也**不引导**入口选择。

### 5.2 何时不使用固定编排

以下情况**不要**强行画成固定依赖图：

| 情况 | 应当采用 |
|---|---|
| 整条路径需要临场规划，或 Agent 介入产生的新值要成为后继输入 | 普通任务点 |
| 最终用户改稿、重做或改走另一条路线 | 冻结当前交付、开启新的运行实例。**禁止**在同一张图里画回边模拟循环，**禁止**覆盖旧交付或旧文件 |
| 制作期就能预知的最终用户输入 | 全部放入口表单，不用运行中交互 |
| 只有上游节点成功后才能确定、且要供尚未派发的下游节点使用的输入 | 节点级运行中交互 |
| 节点成功后需要 Agent 检查或处理异常 | 在该节点声明 Agent 介入，并写清指令和可验证的继续或接管标准 |

编排只调度**已经存在且通过单体验收**的 Workflow。场景包没有 Workflow 时**禁止**伪造空节点或空图。

## 6. 架构方案设计

### 6.1 工具集划分

**工具集划分**：

- 预加载：每次运行都必须出现的核心能力
- 动态：按需加载的辅助能力
- 选型规则：克隆官方包继承的核心工具集**不可**移除；优先复用系统级工具集；**按能力域**匹配，**不要**按业务场景创建专用工具集

**执行形态提案**：按第 4 节形成普通任务点、FastAgent、Workflow 或直接执行的候选边界，**不要**用"默认用 FastAgent"或"只有交互才建任务点"这类简化规则。Agent 必须说明推荐理由、运行体验、成本和可变性，把第 3 节的评估结论纳入制作书第 ⑧ 章；开发者确认后才落成具体资产，**禁止**在实现阶段自行推翻已确认结论。

### 6.2 内部资产清单

**内部资产清单**（记入工单，除非开发者要求技术说明，否则不放入业务方案）：

- 每个 FastAgent：名称、职责、输入输出、真实关联的工具组
- 每个工具集：能力域、成员、加载方式、使用指南要点
- 每个任务点：路由描述、交互需求、输入输出、关联工具集
- 每条 Workflow：稳定业务阶段、脚本要用的工具名、完整依赖清单、输入输出定义、辅助文件、副作用；配套业务应用时，**每个输入字段的来源**（入口表单 / 读业务应用数据集 / 上游节点）与数据集缺失时的回退（S3 2.4）
- 每条编排路线：入口、节点、映射、交付审阅、重入方式
- 数据集：为什么绑定、在哪个节点读取

所有 ID **必须**工具查询确认（约束 4）。

**开发者可见的业务路线图**：提案包含 Workflow 或固定业务路线时，在完整方案 Plan 中用业务阶段名称画出每条候选路线的入口、依赖、扇出/汇合、最终用户与 Agent 介入、最终交付、审阅责任和动作出口。它与内部资产清单分开：前者用于确认产品如何运行，后者才用于确认真实资产如何承载；不得把内部节点标识、工具名或字段映射暴露到业务方案中。

### 6.3 执行结构表

方案的**强制产出**。为每条 Workflow 建立执行结构条目：

- 步骤清单：每步做什么、用什么（工具或 FastAgent）
- 步骤间依赖：谁的输出喂给谁
- **并行组**：相互无依赖且可安全并发的步骤归入同一并行组；相邻无依赖步骤**未**归入并行组的，写明原因（副作用顺序、共享路径、会话状态等）
- FastAgent 清单：本条 Workflow 用到的全部 FastAgent，及按 4.4 的不可合并理由

**并行组怎么画**，逐步骤按序检查：

1. **数据依赖**：这一步的输入是否用到另一步的输出？不用，继续；
2. **副作用独立**：是否写同一路径、共享同一会话、或有顺序语义的外发动作？没有，可并行；
3. **典型形态点名**：**对多个对象执行同一操作（循环逐个调用工具或 FastAgent）默认设计为并行组**——串行处理 N 个独立对象是最常见的浪费，除非对象间有真实依赖或共享副作用，并写入 `no_parallel_reason`。

设计时需要正反例的，读 `get_diagnosis_doc(workflow_example_parallel)`——**不要**等到写脚本才第一次接触并行原语。

**展示载体判定**：`by` 为 FastAgent 的步骤和关键工具步骤，建表时逐步判定其结果是否面向最终用户，三档：**不展示**（内部中间产物，默认）／**进业务事件**（值得单独展示的中间里程碑，走 S3 5.4 事件候选流程，由开发者确认）／**进交付**（内容作为业务字段纳入最终 `output`——仅交付文件路径时，界面只能提供预览与下载，渲染不出文件里的内容）。判定记入该步的 `user_facing` 字段。***FastAgent 与工具的原始返回不是展示载体***——要给用户看的结果必须经事件或交付转成业务表达（如"素材盘点完成：4 张中 1 张可直接使用"，而不是工具返回原文）。

按路由器 5.1、5.3 落本地工作副本与工单权威快照。本表建立后，后续任何脚本或结构修改都**必须**同步更新对应条目（见 S3 4.4）。

### 6.4 起草 apc_skill 与场景 Skill 文件

**起草 `apc_skill` 与场景 Skill 文件**：按 S3 8.3 校验颗粒度——逐一对照第 3 节里每个"预期减少的轮次"，确认都有对应的可执行指导，且每个文件都有明确读取时机。

### 6.5 业务应用数据集读写的落地

计划书第 ⑤ 章只回答了业务问题；本节把它落到字段与通道：

| 计划书里的业务判断 | 落地 |
|---|---|
| 发起时就该带上的用户数据 | 进入口 `input_schema`，由业务应用在发起时预填（S2 9.4 时机 1）——不为它起 FastAgent，也不在脚本里读 |
| 中途“看情况取”的数据 | Workflow 脚本调 `dscli_business_dataset` 读（S3 2.4 时机 2），每条业务流至多一次读；表单字段设可选、`found=false` 回退表单值 |
| 要回流的产出与效果数据 | 脚本收尾 `operation="write"`（S3 2.4 时机 3），`context_hint` 给唯一键；写回哪张表哪些列与 app-creator 线对齐，列名用画像的词 |

逐字段写进内部资产清单（6.2）与执行结构表（6.3）的对应步骤；未规划配套业务应用时本节不适用。

## 7. 方案挑战与制作书定稿

### 7.1 方案挑战

创建任何资产前**必须**完整读取 [方案挑战检查清单](../checklists/方案挑战检查清单.md) 并执行。质疑成立就修方案；不成立就说明证据和取舍。**禁止**在证据不足时判定通过。

挑战以执行结构表为对象逐条目进行，**只处理状态为 `pending` 的条目**（路由器 5.3 累加机制）；全部条目通过后，将执行结构表表级布尔位 `challenged` 置 `true`。

### 7.2 完整《场景包制作书》：在计划书上补第 ⑧⑨⑩ 章

S1 的七章计划书（`build_book`，`stage="S1"`）原样沿用，本阶段补三章，合起来是完整的《场景包制作书》——本 Skill 各处所说的“方案 Plan”。**它是制作期唯一的依据**：定稿后 Workflow 编排、接口、前后端全部照它落地，不再向开发者提问；所以它必须具体到“照着能做出来”，并且**每个设计决定都带选择原因**（选了什么 / 没选什么 / 为什么）。

#### 第 ⑧ 章 资产设计（七小节，不可省略）

| 小节 | 内容 | 来源 |
|---|---|---|
| **⑧-1 路线与人群映射** | 是否多套编排：每条路线服务计划书 ① 里的哪类人群 / 商家类型、适用条件与选路节点；多路线共享哪些节点；只做一条路线时说明为什么一条够。**选择原因**：为什么按人群分路线而不是在一条路线里分支，或反之 | 计划书 ①②③ + 5.1 |
| **⑧-2 每条路线的编排流程** | 逐路线一张流程表：节点顺序与依赖（无环、可达）；每个节点 = 哪条 Workflow；节点内步骤清单（每步用什么工具或 FastAgent、输入从哪来、输出给谁）；入口表单字段与 `input_schema`；节点间映射；运行中交互（哪个节点后要用户补什么）；Agent 介入点；业务事件（哪些节点发 `stage_*`、给谁看）；交付映射（哪些文件与业务字段进 `delivery`）；审阅形态与动作（承接计划书 ④）。**选择原因**：为什么固化成 Workflow 而不是交给任务点 / 直接执行；并行组为什么这样画 | 5.1、6.3、12–14 节预告 |
| **⑧-3 FastAgent 设计决策** | 逐 FastAgent 一行：承担计划书 ② 里的哪个环节；挂载哪些工具组、为什么这些；输入定义要点、输出契约；规范文件清单。**核心选择原因**：这个环节为什么是**一个 FastAgent 带多个工具连续执行**（边搜边判、读完再决定、试错取数）而不是拆成多个单输出 FastAgent；或者反过来，为什么这个环节只需要一个单输入单输出的 FastAgent、工具在脚本里调（4.4 粒度纪律的逐例落地）；超过 3 个 FastAgent 时逐个说不可合并的职责边界 | 4.4、6.2、6.3 |
| **⑧-4 工具集与依赖** | 预加载 / 动态工具集划分与理由；每个工具组的来源（平台已有 / 新注册 MCP / 私有包 / Skill 包）；需要授权卡的能力；复用了哪些已有场景包或派生自哪个包 | 2.2–2.4、6.1 |
| **⑧-5 普通任务点、直接执行与知识文件** | 保留给普通任务点或 SystemAgent 直接执行的环节及理由；`apc_skill` 大纲（业务终点、里程碑、选路、权限边界、文件索引）；场景 Skill 文件清单与读取时机；Focus / 泛化选择 | 3.2、4.3、6.4 |
| **⑧-6 业务应用数据集字段表** | 先按下方建模约定分成实体 / 情境 / 历史事件三类表并画出运转链，再逐表逐列：列名（用画像的词）/ 类型 / `[editable:user\|agent\|system]` 声明 / 来源（用户在应用填、Workflow 哪个节点写回、系统）/ 被哪条路线的哪个节点读；审计四件套与 `row_version`；文件路径列。**多商家类型的字段变体**：哪些列对某类商家可选或缺省不同、哪些表只有某类人群才有——写成“公共列 + 按类型的可选列”，不为每类商家另建一套表。**选择原因**：为什么这些字段进数据集而不是每次让用户填；用户列与产出列怎么拆开避免覆盖 | 6.5、计划书 ⑤、app-creator 约束 9 |
| **⑧-7 配套业务应用** | 是否制作；若制作：页面清单（三必备页 + 按业务取舍的看板 / 数据管理 / 业务发起 / 项目页）、看板要看哪些字段（来自 ⑧-6 的产出列）、哪些列在数据管理页可编辑、文件在哪出现、发起入口对应 ⑧-1 的哪条路线；**这一节是交给 app-creator A1 的输入**——A1 在此基础上细化，不推翻。不制作时写明数据如何随交付给到用户 | 计划书 ⑤、app-creator A1 |

**⑧-6 的建模约定：数据的归属与运转**。字段表不是平铺一堆列——先按三类表划分，每类的写入方、更新方式、读取方与保留策略不同：

| 类 | 是什么 | 例 | 谁写 / 怎么更新 | 谁读 | 保留 |
|---|---|---|---|---|---|
| **实体** | 用户经营的对象，长期存在、慢变 | 门店、账号、菜品、素材库 | 用户在应用填改（`editable:user`）；主键与审计列系统写 | 发起时铺底进入口表单；Workflow 读基线信息；看板按实体分组 | 长期；删除走软删 |
| **情境** | 当前目标、偏好、约束、时段——决定“这一次怎么做” | 本月目标、禁用表达、活动档期、风格偏好 | 用户填改为主；生产要给建议时写**独立的建议列**（拆列，不覆盖用户列） | Workflow 执行中按需取（S3 2.4 时机 2）；应用预填 | 覆盖更新，`updated_at` 留痕 |
| **历史事件** | 每次运行 / 发布 / 效果的记录，只增不改 | 一次生成的选题与结果、发布后的效果数据、用户的审阅动作 | Workflow 收尾回写（`editable:agent`，带 `last_run_id`）；应用生产回流 | 看板聚合、下次运行参考、执行记录页 | 追加；不覆盖旧交付 |

- **归属**：情境与历史事件都挂在实体上（`set_relations` 按表名声明关系）——任一条历史事件必须能回答“属于哪个实体、来自哪次运行”；
- **运转逻辑**：用户在应用填实体与情境 → 发起时铺底进入口表单 → Workflow 读情境与历史决定策略 → 产出写回历史事件 → 看板从历史事件按实体聚合 → 用户修正实体 / 情境 → 下次运行更准。制作书里把这条链画一遍，逐箭头标出读写的表与列；
- **多商家变体**落在实体表：一个“类型列”+ 按类型的可选列；情境与历史事件表结构对所有类型共用，只是取值不同。

#### 第 ⑨ 章 能力缺口、发布范围与授权

缺口处理方案（第几层、影响什么）、发布范围（哪些资产与路线属于本次候选版本）、是否“前三层候选验收通过后上线”的执行承诺、端到端全真验证范围。**“发布范围”和“上线授权”必须分开表达**：制作书明确写出“前三层候选验收通过后上线”并由开发者统一确认时，不再在发布前重复询问；没有该执行承诺、只列发布范围时，`stages/S5-发布与交付.md` 必须另行取得上线授权。

#### 第 ⑩ 章 制作纪律：定稿之后

- 制作期**不再向开发者提问或提案**，全部依据本书；工程细节（命名、代码组织、等价实现）自主决定；
- **什么算冲突、必须停下沟通**：本书与真实契约（实时 Schema、`get_diagnosis_doc`）不符；平台能力不支持本书设计的模式；按本书做会触碰第 ⑦ 章红线；发现计划书口径（画像、旅途、交付角色）需要改；本书两处自相矛盾。沟通时列冲突点、双方依据与候选处置，**不静默取舍、不绕过、不自作主张改书**；
- 冲突解决后**整份重写制作书**并重新确认，再继续；
- 制作书之外的“更好的想法”记入工单备忘，不在本次实现。

#### 写作与落账

- 每个设计决定写成“选择 / 未选 / 理由”三段，不写只有结论的条目；
- 术语用画像的词，工具名、Schema、节点标识只出现在 ⑧-2 ~ ⑧-6 的技术表格里，不进 ①–⑦；
- 完整制作书**整份重写进工单**（`build_book`，`stage="S2"`）；设计与计划书冲突时不改制作书糊过去——回 S1 第 5 节更新计划书并重新确认。

**格式自检**：①–⑩ 齐全；⑧-1 的每条路线在 ⑧-2 有流程表、在 ⑧-6 能找到它读写的列、在 ⑧-7 能找到它的发起入口；⑧-3 每个 FastAgent 都对应计划书 ② 的一个环节并写了“为什么是一个 / 为什么这样挂工具”；⑧-6 每列有声明与来源；⑨ 的发布范围与 ⑧-1 的路线一一对应；⑩ 在。

### 7.3 开发者确认

执行结构表 `challenged=true` 后，连同完整《场景包制作书》（含 S1 已确认的七章与本阶段的 ⑧⑨ 章）一并展示给开发者，由开发者确认 ⑧⑨⑩ 三章并复核 ①–⑦ 未被资产设计改变语义。开发者要求改的地方改完**整份**重新提交；这次确认之后进入制作期，按第 ⑩ 章纪律不再逐项请示。本次确认**兼作关键 FastAgent 的圈定时刻**：开发者在 FastAgent 清单上圈出关键产出环节（面向最终用户的输出文案类），被圈定的环节在S3 第 3 节制作时必须执行样例选择流程（S3 3.2）。Focus / 泛化在同一次确认中显式选择。

### 7.4 制作书硬门

**制作书硬门**：只有开发者对完整制作书（含 ⑧⑨⑩ 章）完成统一确认后，才能进入 S3 开始依赖资产、普通任务点、场景包草稿、Workflow、关联关系或业务路线编排的创建与修改。确认前只允许继续只读调查、候选方案起草、方案挑战和不改变外部状态的验证。任一未确认项不得被 Agent 当成默认值写入资产；后续若改变路线依赖、交付对象、审阅责任、动作、重入方式或介入点，属于计划书口径变化，回 S1 第 5 节更新计划书并重新确认，再回本节更新制作书。确认后，同一范围内的可逆离线操作获得授权；上线动作仅在 Plan 同时满足上一段的明确执行承诺时获得授权（约束 6）。
