# ② 方案（工作区阶段 G3）

让开发者确认「你们是按我的想法在做」。你先按轮问清做法上的取舍；再把 PRD 和取舍的答案编成技术方案（施工单），这部分只给自己和后续 Agent 用；然后按功能翻译成业务说明：这个功能帮你完成什么业务，按什么顺序、用什么数据、每一步谁来做，完成后你拿到什么、记在哪里。每个功能一道判断题，开发者逐题答「对」或「不对」，确认你照他选的写对了。

## 1. 进入条件

- ① 交棒：PRD 已确认，核实对照表里每一步都有能力来源。
- 从修订进来时，只编译和说明受影响的功能。

## 2. 段里怎么做

### 2.1 先问取舍（给开发者）

PRD 定了要什么，同一件事往往有几种做法都能做，但使用者的感受不一样（快慢、全不全、要不要人把关）。这些取舍写方案前先问清，不留到判断题里才发现不对。

1. **找出取舍**：按 PRD 每个刚需，在你心里过一遍做法（不写给开发者），从 [../design/按轮问.md](../design/按轮问.md) 里 ② 的起步方向开始，列出做法有两种以上都成立、选哪种使用者感受得到的地方；对话中冒出新的取舍随时加上。只有一种做法成立的、或使用者感受不到的（用哪个工具、表怎么建），你自己定，不问。
2. **先试跑关键步骤**：取舍要看真实效果才能选的（例如报告看 6 篇要多久、看全要多久），用 ① 的真实样例把关键的模型步骤试跑一次，按 [../tasks/能力试用.md](../tasks/能力试用.md) 建极简试用包，记下输出、用时、花费，写进题干。累计花费加上这次试跑不超过 PRD 的花费上限时直接跑，超出时先问。依赖试跑结果的题等结果出来再问，其余照常发。
3. **按轮问**：按 [../design/按轮问.md](../design/按轮问.md) 问，每题带推荐答案，有选项的写清选了会怎样；PRD 和 ① 里已定的事不再问；开发者没回的题不算定，下一轮接着问；问到没有空着的取舍为止。每轮的交接消息开头「【② 方案 → 等你确认】」。
4. **确认理解**：问完先发一条「我理解的是这些」，按功能列出定下的取舍（[../design/按轮问.md](../design/按轮问.md)「先确认理解，再动笔」），开发者回「对」再编施工单。
5. 开发者的回答改变的是「要什么」而不是「怎么做」时，退回 ① 改 PRD。

没有取舍可问时（只有一种做法成立），在交接消息里说一句「做法上没有要你选的」，直接往下做。

### 2.2 编施工单（AI 内部）

逐行把 PRD「每一步谁来做」映射成要造的东西（顺序固定：工具集 → FA → 编排型 TPE → 路线）：

| PRD 里的 | 变成 | 备注 |
|---|---|---|
| 脚本步骤 | 编排脚本里的一步 `await tool(…)` | 脚本按 [../reference/编排脚本.md](../reference/编排脚本.md) 三种模板之一改。路线要读写应用库，或有「从应用里取客户、任务、素材、记录交给模型判断，再把结果存回表」的，现在就读 [../reference/数据模板.md](../reference/数据模板.md)「编排脚本怎么读写应用库」，逐行写清：固定读写由脚本 `db()` 执行；要模型按情况挑选的数据由业务 FA 挂 `query_business_app_dataset` 只读查，**禁止**改成入口传全部素材或规则预填；这条路线有没有应用后端回流（没有就由脚本自己写库） |
| 模型步骤 | 一个 FastAgent（复用或新建） | 输出对象每个字段含义、非成功状态（`needs_input`、`insufficient_evidence` 等）在这里定；按 PRD 的档位定 `model_name`，`model_selection_mode="required"` |
| 人 · 开始 | 路线入口表单 | 入口字段怎么定见 [../reference/数据模板.md](../reference/数据模板.md)「入口字段放哪」；`assemble` 会把上游没提供的字段放进入口 |
| 人 · 在应用页面上操作（选一项、改字段、采纳或不采用、标记状态，不需要模型） | 页面 + 应用后端接口写表，不经路线 | 写哪张表、哪几列（列为 `user` 可编辑），后端接口按 [../reference/前端页面.md](../reference/前端页面.md)「业务页面」与 ③ 2.2 第 6 步；操作后要接着让模型做事的，由页面发起下一条路线，入口只传业务键（如项目 ID），路线自己读库拿刚写进去的内容 |
| 人 · 中途补信息 | 节点级运行中交互 | 只把表单值写进尚未派发的下游字段，见 [../reference/业务路线.md](../reference/业务路线.md) |
| 人 · 审阅结果 | 路线 `delivery.review` | 缺省 `user_gate`；要「修改后重跑」加跳转到另一条路线 |
| 放进去 / 拿出来 | TPE 的 `input_schema` / `output_schema`，以及模板表 | 字段名用英文蛇形，含义写进 `description`；文件用 `format: workspace-file-path` |
| 会停下的情况 · 停下来 | 让异常冒泡 | 平台按失败类别归因并告知使用者 |
| 会停下的情况 · 标记继续 | `try/except` 只包那一次 `tool()`，输出带 `status` 与 `warnings` | 读 `e.recoverable` 决定写法 |
| 会停下的情况 · 重试一次 | 同上，except 里再调一次 | 工具内部已重试的不再叠加 |
| 会记下来的东西 | 数据模板里的表与列 | 每列定 `user / agent / system`，见 [../reference/数据模板.md](../reference/数据模板.md) |
| 页面 | 预置件、`gen:pages` 生成页或定制页 | 按 PRD「界面」，见 [../reference/前端页面.md](../reference/前端页面.md) |
| 用量上限 | 一次最多处理多少条、单次运行时长 | 超过平台单次运行能力的，改成分批或分片；做不到回 ① |

每个业务输入从入口来还是读库，按 [../reference/数据模板.md](../reference/数据模板.md)「入口字段放哪」定，同一个值只走一边。再定：

- 路线数：一条业务路线通常一条编排型 TPE 就够；要中途表单、并行或节点级接管才拆多条；一条路线超过 8 步就拆。只有脚本步骤的应用也建一条最小路线。
- 数据怎么进出：每个业务输入从哪来（入口表单或读应用库，按《数据模板》「入口字段放哪」），每个产出写到哪（更新已建行 / 回流建新行），以及同一业务再做一次时是更新原记录（写明业务键，如「同一门店同一周」）还是每次新增一条（如巡检历史），见 [../reference/数据模板.md](../reference/数据模板.md)「谁建行」。
- 只有脚本步骤时：施工单写一行「一条最小路线 + N 张表 + 数据页」即可，不展开；业务说明、判断题和验收条目照写。最小路线只作为平台要求的挂载依赖，不为纯数据管理应用虚构额外业务流程。

施工单写进阶段文档 G3：

| 清单 | 每项写什么 |
|---|---|
| 资产清单 | 类型、名称、复用还是新建、来源资产 ID、FA 的模型 |
| 路线草图 | 每条路线：`orchestration_id`、节点顺序、入口字段、中途表单、审阅方式 |
| 表清单 | 表名、列、每列可编辑性、唯一键、谁建行 |
| 页面清单 | 预置件 / 生成页 / 定制页，各自给哪种人用、读写哪张表或哪条路线 |

### 2.3 翻成业务说明和判断题（给开发者）

每个刚需写一段：

| 内容 | 写什么 |
|---|---|
| 完成什么业务 | 一句话 |
| 怎么完成 | 按什么顺序、用什么数据、每一步谁来做；数据从哪来、什么时候算、哪一步要人把关 |
| 做不成时 | 使用者看到什么 |
| 完成后 | 拿到什么、记在哪里 |
| 例子 | 用 ① 里开发者给的或真拿到的数据举例；模型要写的内容还没做出来，写成「预期会得到……」并标「预期」 |
| 判断题 | 按 [../design/选择题与判断题.md](../design/选择题与判断题.md) 写，一题 |

另加一张「每一步用什么、花多少」：每一步写脚本还是模型、哪一档、为什么这样选、每次约多少积分，配一道判断题。

页面这一段不给开发者看，页面长什么样已在 PRD「界面」确认过；页面上点了以后发生什么，有取舍的已在 2.1 问过。

### 2.4 验收条目定稿

把 PRD 每个刚需的「怎样算做成」写成能逐条照做的验收条目，④ 按它验收。每条是一次完整的使用者任务，用使用者的话写，不写平台概念：

| 列 | 写什么 | 例 |
|---|---|---|
| 谁 | 哪种人 | 人① 使用者 |
| 从哪进、先看到什么 | 打开应用后首屏应该看到的东西，从哪里开始 | 首页先看到「新建项目」和做过的项目 |
| 用什么、按什么顺序做 | 用什么数据；操作步骤，与业务顺序一致 | 只填「莫定标娘惹糕点」→ 提交 → 选候选 → 等报告 |
| 最后拿到什么 | 成果，以及它能支撑的下一步 | 中英文报告，能直接下载发给商家，接着生成内容 |
| 怎样算过 | 可以判断的标准 | 有槟城 Lebuh Chulia 的候选；30 分钟内出报告 |

- 每个刚需至少一条；有中途补信息、审阅、会停下的情况的，各写一条走到那一步的。
- 第一次使用和日常使用不一样（例如第一次要先建档）时分开写。
- 每条预先标出「AI 能判断」还是「要人判断」（例如报告能不能直接发给商家、语气像不像店家写的），④ 自测时照这个分。

### 2.5 费用与副作用复核

按施工单重算：制作还要花多少（冒泡、`full_run`、真跑的份数 × 每份花费）、上线后每用一次多少。超出 ① 的上限时，做成选择题放进这次交付。

读写应用库的路线要到 ④ 部署后才能真跑，这时拿不到它的实测花费，按这个顺序估：

1. ① 用试用包跑过同类模型步骤的，用那次实测；
2. 没跑过的，每个模型步骤按 [../design/谁来做.md](../design/谁来做.md) 的档位每次花费 × 预计调用次数，付费工具按单价 × 预计次数，相加；
3. 每个数都标「估算」，并写出算法（几次 × 每次多少），不写成实测。

③ 里不碰库的路线 `full_run` 出了实测，就用实测更新同类步骤的估算；④ 真跑后全部换成实测，累计到上限的 80% 时按 [../design/交接消息.md](../design/交接消息.md) 停下问。

再核对会调的收费工具、会写或发出去的东西，与 PRD「费用与副作用」一致；施工单里多出 PRD 没列的写入或发送，回 ① 补确认，不在 ② 里默认带过。

### 2.6 发出

一次发出：每个功能的业务说明和判断题、「每一步用什么、花多少」、验收条目、费用复核、一句施工摘要（要做几件事）。交接消息开头「【② 方案 → 等你确认】」，「要你做的」写「逐题答对或不对；看一遍验收条目」。

开发者答「不对」的题，改完只重问那一题，牵动别的功能的连同受影响的功能一起重问（见 [../design/选择题与判断题.md](../design/选择题与判断题.md)「判断题」）；答「不对」且要改的是要什么、不要什么，退回 ①。

Studio 宿主：这一段写方案一份开发文档，**必须**照 [../design/开发文档/方案.md](../design/开发文档/方案.md) 的模板写，取舍题问完后和判断题一起发。方案和与验收条目一致的 `acceptance.json` 用 `studio_write_proposal(documentType="proposal")` 保存；判断题都答「对」、开发者同意这一版后，用 `studio_confirm_proposal` 登记原话并读回，才进 ③；方案改了就重新确认。做法见 [../reference/开发者中心与工作区.md](../reference/开发者中心与工作区.md)「Studio 宿主」。

## 3. 开发者要看、要做的

- 写方案前，按轮回答做法上的取舍题（同意推荐的回「按推荐」）。
- 读每个功能的业务说明和例子，判断是不是自己想的那样。
- 逐题回答判断题。
- 确认验收条目。

## 4. 不给开发者的

施工单原文：流程怎么拆、表怎么建、提示词、模型名、技术点清单；页面设计。

## 5. 产出与落盘

- 阶段文档 G3：取舍题的「已定的事」（每条写是什么、谁说的或按默认、哪一轮定的）和试跑记录、施工单、给开发者的业务说明、每道判断题和开发者的回答（含「不对」时的原话和改动）、验收条目定稿、费用复核。
- 方案页「开发内容」补「怎么做」（业务说明，用业务话说有几条路线、存几张表、几个页面）与「怎么验收」（验收条目）；与 PRD 不一致的地方用 `pv-changed` 标出并加版本号。
- 工单 checkpoint：`方案已确认`，附资产清单摘要、路线与表名、验收条目数。
- 阶段标记：G3 `passed`。

## 6. 交棒条件

下面都满足后，先用命令把 [3-制作.md](3-制作.md) 从头读到尾，再做 ③ 的第一件事。

- 取舍都定了（开发者答的或按默认），开发者对「我理解的是这些」回了「对」，施工单按定下的取舍写；
- 每个功能的判断题都单独发给了开发者，并且都答了「对」；PRD 确认后直接开始制作、跳过判断题的，不算交棒；Studio 宿主读到了当前这一版方案的确认；
- 验收条目开发者确认了，PRD 每个刚需至少一条；
- PRD 每一行在施工单里都能找到对应项，费用没有超出上限（或超出部分开发者已选过），副作用没有超出 PRD「费用与副作用」；
- 出口阶段记录：用 `business_ui_stage` 写 G3 一条（写法见 [../reference/开发者中心与工作区.md](../reference/开发者中心与工作区.md)「三件套与阶段标记」）。

## 7. 出问题怎么办

| 现象 | 先看 | 回到 |
|---|---|---|
| 某一行编不出来（没有对应能力） | G2 对照表 | ①：改 PRD，告诉开发者做不到和替代 |
| 编完费用超出上限 | PRD「花多少」 | 本段 2.5 做成选择题 |
| 编完多出 PRD 没列的写入或发送 | PRD「费用与副作用」 | ①：补确认 |
| 开发者要的东西变了 | — | ①：改 PRD 再确认 |
| 取舍要看效果才能选，试跑跑不了（读写应用库要部署后才能跑、工具被平台问题挡住） | 本段 2.1 第 2 步 | 用 ① 真调拿到的数据和同类步骤的估算写题干，标「估算」，照常问；只是还没跑完的，等结果 |
| PRD 里写了 Skill 禁止的做法（例如请开发者授权改使用者的安装记录、改生产库） | `SKILL.md` 第 3 节、第 7 节末尾 | 这一项不编进施工单；交接消息里告诉开发者这件事只能由平台方做、你已按第 7 节报平台问题，对哪个功能有影响；退回 ① 把 PRD 那一处改成平台问题和对开发者的影响，开发者确认后再回来 |
| 一条路线超过 8 步 | 本段 2.2 | 拆成两条路线，业务说明里讲清 |
