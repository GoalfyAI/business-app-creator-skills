# S4 验证与修正

三层验收、草稿态端到端全真滚动、问题单消化与结果检查表闭合。

## 1. 验证总览

发布前读取 [场景包验收检查清单](../checklists/场景包验收检查清单.md)，把 `apc_skill`、Skill 文件、任务点、工具集、FastAgent、工具组、数据集、Workflow、编排、交付物作为**一个业务闭环**完成前三层候选验收。逐项确认前期确认的每个里程碑、候选路线、业务路线图、交付对象、审阅责任、审阅动作、介入点、前置检查、授权和到达标准，都能在真实资产里找到对应承载；后续发生的任何实质变更都有开发者重新确认记录。

**完整证据固定分为四层，不得互相替代：**

| 层级 | 必查内容 | 能证明 | 不能证明 |
|---|---|---|---|
| 1. Preview / 静态契约 | 资产反读、脚本、输入输出 Schema、工具引用、按需业务事件声明与静态生命周期、按需编排保存与接缝 | 当前资产和静态契约可保存、引用闭合 | Provider 真实返回、事件持久化、路线运行 |
| 2. 工具取样 / 依赖证据 | 安全低副作用工具的真实输入输出、依赖状态和权限 | 代表性依赖在当前环境可调用，候选 `_output` 有真实样本 | 整条 Workflow 或其他输入正确 |
| 3. 制作期 Bubble | 先逐 Workflow 检查当前路径的步骤、文件、输入输出、按需持久化业务事件和覆盖率，再逐路线检查真实图控制、表单、Delivery/Artifact 与终态 Review 接缝 | 当前版本当前输入的节点数据管路与路线控制接缝成立；带事件时可证明验证事件链成立 | FastAgent 真实内容、被阻断的外部副作用、未触达分支、正式业务运行 |
| 4. 业务路线端到端全真运行 | 在草稿态目标版本上，检查真实图控制、表单、Agent 介入、业务事件真实发布、Delivery、Runtime `artifact_ready`、Review 和最终产物 | 被批准路线的真实业务闭环 | 未运行路线和未来输入都正确 |

**第四层端到端全真是上线（定稿并真正上线）的前置**：全部通过后才进入 S5 的上线门。没有第四层真实日志时，只能记录前三层通过和整图运行盲区；**禁止**用多条单 Workflow 的运行证据拼接成整图运行证据。业务应用对事件与交付的消费在 app_creator 线验收，不属于本包的验证对象。

前三层候选验收的裁决口径不变：critical 全部关闭；warning 已修复或经开发者明确接受；发布范围内资产与前三层证据一致；被跳过或被平台阻断的项都有明确影响说明和后续条件。

开发者选择跳过端到端全真时，**必须**记录跳过决定、FastAgent 内容盲区、未触达分支和副作用盲区（`full_validation_skipped`）；**存在该标签时不得上线、不得结单**（见路由器 8.3），**禁止**声称已有全真证据。

## 2. 三层验收

### 2.1 Preview 与静态契约

第一层证据：资产反读、脚本 Preview、输入输出 Schema、工具引用、业务事件静态生命周期（S2-5.3 的条件硬门）、编排保存反读与静态接缝检查（S2-8.2）。

### 2.2 工具取样与依赖证据

第二层证据：安全低副作用工具的真实调用取样（S2-3.2）、依赖状态与权限确认（S2-2.2 两道检查）。

### 2.3 单条 Workflow Bubble

第三层第一段：逐 Workflow 执行 S2-5.3 闭环的第 6–8 步，取得终态轨迹并做语义验收。

带业务事件的 Workflow，单条 Bubble 必须读取 `run_evidence.business_events`：核对脚本声明的事件、已持久化事件、缺失必需事件、未触达事件、顺序与持久化裁决。只有数据库持久化成功的事件才能计入；实时投递成功本身不算证据。本次路径缺少 `stage_started`、缺少 `stage_result/stage_failed` 终态或顺序错误时，Bubble 必须失败。Runtime 自有的 `artifact_ready` 与 `delivery_ready` 不属于单条脚本生命周期门；它们在路线级 Bubble 中分别以 Artifact 登记和 Delivery 冻结后的真实事件为证。无业务事件的 Workflow 记录脚本事件检查为“不适用”，不得虚构空事件证据。

### 2.4 路线级 Bubble

全部节点完成单 Workflow Bubble、编排保存反读并通过静态接缝检查后，对发布范围内的每条路线执行一次**路线级 Bubble**。它仍属于第三层制作期演练，不需要用户批准，也不替代第四层全真运行。调用顺序固定为：

1. 启动：`scene_package_manage(action="bubble", task_id=..., scene_package_id=..., orchestration_id=..., workflow_input=..., review_action_key=...)`。`workflow_input` 使用该路线的代表性入口根对象；只有 `delivery.review.type="agent_gate"` 时才传一个已声明的具体 `review_action_key`。
2. 轮询：后续只传同一 `task_id` 和服务端返回的 `run_id`，不得重复入口输入，不得创建或补写项目、Business、Runtime、表单或消息标识。
3. 回填：返回 `status="waiting_input"` 时，读取当次 `interaction.form_id/arguments`，再用同一 `task_id/run_id` 和 `formdata` 回复；每次只回答当前表单。
4. 终态：只有 `status="success"` 且 `validation.status="passed"` 才算路线 Bubble 通过；失败时优先读取 `failure_stage`、`repair_target`、`repair_action` 和可选的 `failed_node_id/failed_step_key`，按 `repair_action` 修正它指向的原 Workflow 或编排，再重新启动；只有 `repair_target="platform_runtime"` 时才按平台故障处理。禁止只看笼统错误自行猜修改入口，也不复用已结束的 `run_id`。

路线 Bubble 默认 `evidence_level="summary"`：只读取路线终态、节点与步骤计数、失败步骤错误、输出字段、事件覆盖摘要、Artifact 引用、Delivery 验证和 Review 结果。完整步骤输出、最终输出值和业务事件 Payload 仍保存在 Runtime；只有精简证据不足以定位失败时，才对同一 `run_id` 显式使用 `evidence_level="full"`。不得把完整证据默认塞入工单、记忆或最终交付，也不得因为默认响应精简就重复执行路线。

每条路线通过后，用 `task_manager(insert, entry_type="checkpoint")` 写一条精简证据，并把以下结构放入 `metadata`：`{"evidence_type":"orchestration_bubble_validated","scene_package_id":<真实场景包标识>,"orchestration_id":"<真实路线标识>","run_id":"<本次通过的真实 run_id>"}`。这不是人工自证：`task_manager(complete)` 会读取同一工单已有的工具调用审计，核对当前编排路线、`run_id` 和终态；缺失、失败、属于其他路线或早于最后一次编排修改的证据都会拒绝结单。结单成功响应中的 `completion_evidence.route_bubbles` 才是机器确认结果。

路线 Bubble 复用真实图 Runtime，检查节点依赖、mapping、扇出/汇合、运行中业务表单、持久化业务事件、Delivery 冻结、Artifact 登记和最终 Review。各节点仍使用既有 dry-run Bubble 语义：FastAgent 为桩，显式外部副作用由 `ctx.dry_run` 阻断；声明的 `sa_handoff` 只验证边界可跨越并记录为桩，不声称验证 Agent 判断；最终用户表单和 `user_gate` 使用真实结构化握手。当前路线 Bubble 的 Review 只接受终止本业务的 `complete_business` 或 `fail_business` 动作，不演练 `start_orchestration` 跳转；含跳转的路线保留到第四层全真运行验证。路线 Bubble 因此能证明本次输入下整图控制和交付接缝成立，不能证明 FastAgent 内容质量、被阻断的外部副作用或未触达分支。

### 2.5 证据强度分级

路线 Bubble 的验证证据带强度标记（如 `fa_stubbed`、`uses_shell`），按路线特征分级裁决：

- **纯工具链路**（不含 FastAgent 步骤）：桩跑证据即可放行进入第四层；
- **含 FastAgent 的路线**：桩跑证据只证明管路，**必须**在第四层全真中覆盖 FastAgent 真实内容后才算完整。

### 2.6 冒泡结论的引用纪律

引用冒泡证据时**必须**如实说明边界：Bubble 中 FastAgent 恒为桩，**不能证明任何内容质量**；桩值（空字符串、空数组、空对象）可能触发脚本为真实异常准备的降级分支，使冒泡走过的路径与真跑不同。**禁止**以"冒泡通过"表述"质量可控"或"内容正确"；冒泡证明的只是当前输入下的管路与接缝。

## 3. 草稿态端到端全真滚动

### 3.1 授权与范围

场景包、需要的业务路线编排和上线前三层候选验收全部通过后，即可在**草稿态目标版本**上执行端到端全真运行；不需要先上线。

按需要验收的**业务路线**一次性说明端到端运行范围、可能启动的全部 Workflow、FastAgent 费用和外部副作用，并询问开发者是否真实运行。开发者批准后即为对本轮滚动验证的**预授权**：修正环内的重复运行不再逐次询问。带业务事件的单 Workflow 也按单节点业务路线申请和执行；**禁止**在每条 Workflow 的制作循环中逐条申请全真验证。

草稿态真跑就是真实项目运行：外部副作用照常发生、FastAgent 照常计费，**必须**按约束 6 对待。

### 3.2 真机验证与日志

| 工具 | 用途 |
|---|---|
| `manage_goalfymax_project` | 在真实项目中挂载场景包并运行：`run` / `status` / `wait` / `send` / `reply` / `confirm` / `history` / `stop` |
| `get_project_execution_logs` | 读取真实项目日志与产物：`summary` / `detail` / `outputs` / `download` / `bundle` |

`run` 会启动真实 Agent、FastAgent、工具和外部副作用，**必须**先取得开发者授权（约束 6）。

端到端全真运行挂载**草稿态目标版本**（草稿物理行标识）；反读确认挂载的正是待验收的那一版。

开发者批准后，通过 `manage_goalfymax_project` 的业务表单入口启动真实项目：提交目标 `orchestration_id` 和入口 `formdata`，由服务端生成 Runtime 身份；运行中出现业务表单时，按开发者确认的测试样例，使用同一项目和同一 Runtime 的结构化表单回复继续。一次获批运行覆盖所选路线的完整编排、最终用户介入、Agent 介入、业务事件、Delivery 和 Review，不把它拆成若干单 Workflow 全真运行，也不把带业务事件的单 Workflow 改走直接派发。

`run` 的任务描述**必须**是自然的业务需求，像最终用户真实提需求那样写。**禁止**写成验收话术，**禁止**指定 Workflow、FastAgent、工具名称、内部 ID、调用顺序或分步方法——要让场景包自己完成路由。

要验收固定编排的直派入口时，显式传入模拟业务应用首次提交的数据；省略则表示普通对话启动。

**运行实例标识由服务端生成，任何情况下都不由调用方传入。** 完整规则：

- 首次启动**只**提交已发布的编排标识和入口表单
- 服务端完成校验、创建首批真实任务点之后，才回传运行实例标识
- 入口被拒绝或首批派发失败时，**不会**也**不得**暴露预留的标识
- 对话入口、Agent 介入和路线重入同样由服务端生成新标识
- 同一个运行实例内的任务点、交互、交付和运行查询**必须**沿用同一个标识

轮询、追问和日志读取**必须**复用同一个项目标识，**不要**为了查状态或做小修就反复新建项目。

### 3.3 修正环

发现问题后，在**同一个草稿行**上修改并直接重跑，不需要每圈定稿或上线：

```text
草稿行真跑 → 分析（第 5 节）+ 问题单（第 4 节）→ 修改草稿（回 S2 对应节）
     ▲                                                    │
     └────── 执行结构表条目指纹变化 → 回退 pending ──────────┘
```

- 修改脚本或结构后，执行结构表条目按 S2-5.4 回退 `pending`，仅对回退条目增量重挑战与重验；
- 结果检查表相关条目同步回退 `pending`，重跑后重新闭合；
- 修正环收敛（问题单无未处置 fail、检查表全绿）后，才进入 S5 定稿上线。

## 4. 问题单（findings）消化

每次真跑到达终态后，读取本次运行的问题单：由平台按运行流转记录生成的结构化条目，每条包含类别、位置、证据、建议与严重级：

- **fail**：结构性底线违约（如拒绝产出却未给出理由清单、输出自相矛盾、话术承诺未兑现）。**必须**修复后重跑；不修复不得进入 S5。
- **advice**：优化建议（如相邻无依赖步骤串行执行、按真实耗时估算的并行收益）。由你结合业务判断是否采纳；不采纳时在工单记录理由。

问题单按条目指纹累加：已处置（`finding_resolved` / `finding_waived`）的条目在后续运行中不重复报告；`waived` **必须**带理由（路由器 8.3）。平台尚未提供问题单能力时，按第 5 节人工复盘并把发现按同一结构记入工单，不得虚构平台生成的问题单。

## 5. 运行结果三层复盘

与 `stages/S1-业务设计.md` 第 3 节同样的三层方法：摘要建立概览 → 完整深读日志与产物 → 分析实际路线是否符合设计、工具调用是否合理、FastAgent 结果是否被有效采用、最终用户确认点是否正确、最终交付是否达到到达标准。

发现问题回到对应阶段修复并重验，形成"运行 → 分析 → 优化 → 回归"的闭环；闭环在草稿态内滚动（3.3），轮询和日志读取复用同一项目标识（3.2）。

## 6. 结果检查表闭合

对结果检查表逐条目执行闭合，**只处理状态为 `pending` 的条目**：

- **测试用例条目**（S1-4.3 转入的正反例）：以条目输入执行真跑或复用已有运行记录，对照期望产出判定。正例须产出与期望一致的交付；反例须正确识别并按预期方式处理（拒绝、改写或引导），**不得**产出反例描述的错误结果。含开发者在样例选择（S2-4.2）中确定的验收判定时，一并核对。
- **前端校验项**（S3 转入）：按已冻结界面契约核对对应页面行为与渲染。草稿态端到端全真到达终态后，**必须**用真实运行的交付数据在已部署界面上过一遍完整旅程：返回结果是否完整渲染、有无原始 JSON 或内部字段直出、提交前后状态流转是否正确。仅凭 mock 数据或契约静态比对**不足以**闭合本类条目。
- **编排校验项**：按路线级 Bubble 与全真记录核对交付、审阅与重入行为。

判定通过置 `passed`；确认不适用或开发者接受偏差时置 `waived` 并记录理由。**禁止**为凑全绿而放宽期望产出的判定标准；判定依据与运行证据记入工单。

## 7. 出口条件

以下全部满足后，按路由器 4.1 进入 S5：

- 发布范围内每条路线的路线级 Bubble 证据在案（`orchestration_bubble_validated`）；
- 草稿态端到端全真到达终态，记录在案；含 FastAgent 的路线已按 2.5 在全真中覆盖真实内容；
- 问题单无未处置的 fail；
- 结果检查表全部 `passed` / `waived`。

以上全部满足后，按路由器 6.1 落一条 `stage_exit` 账，再进入下一阶段。
