# 运行模型与渲染语义

一次运行的模型与渲染语义。本文是这两类知识的**正本**：各阶段文件只引用不复述。资产概念（场景包组成、四种执行形态的构成与边界）的正本在路由器 `SKILL.md` 第 7 节。

## 一、运行模型

一次场景包运行中各角色的关系与时序。理解它才能设计出边界正确的资产，也才能判断哪些环节值得呈现给最终用户。

### 1.1 角色关系

```text
最终用户
  │ 聊天输入 / 业务应用表单
  ▼
SystemAgent（主对话，每轮可见 apc_skill）
  │ 按任务点描述路由，派发 TPE
  ├─▶ TaskAgent（普通任务点：独立上下文，临场决定步骤，可中途向用户提问）
  │      └─ 调工具 / 调 FastAgent
  ├─▶ Workflow（确定性脚本：按固定步骤执行）
  │      ├─ tool(...)          确定性工具调用
  │      └─ FastAgent(...)     脚本内的推理步骤（每次全新隔离会话）
  └─（挂了编排时）业务路线 Runtime：按依赖图确定性派发各节点 Workflow，
        处理入口表单、运行中交互、Agent 介入、Delivery 冻结与最终审阅
```

- **SystemAgent** 是全场唯一持续面对最终用户的 Agent；任务点与 Workflow 都在独立上下文运行，结果回流后由它衔接对话。
- **业务路线 Runtime** 是确定性控制器：路线一旦启动，节点派发、字段映射、交付冻结都不经过大模型；只有声明的 Agent 介入点和最终审阅会把控制权交回 Agent 或最终用户。
- **FastAgent 没有记忆**：每次调用都是隔离会话，脚本或调用方必须把全部必要背景随参数传入。

### 1.2 一次带编排的运行时序

```text
入口（用户提交入口表单 / 聊天启动路线）
  → Runtime 派发首批节点 Workflow
  → 节点执行：stage_started → 工具/FastAgent 步骤 → stage_result（或 stage_failed）
  → 产生文件交付物：脚本写入产物目录并按 output_schema 返回路径
  → 全部节点达成 → Delivery mapping 求值（文件路径字段的求值结果即 Artifact 登记来源）
      → 文件登记 → artifact_ready（平台自动，逐份） → 冻结 → delivery_ready（平台自动）
  → 最终审阅（user_gate + ask / user_gate + result / agent_gate，见 S1-7.4）
  → 按审阅动作：完成业务 / 结构化失败 / 开启新路线（新 Runtime，旧交付保留）
```

文件路径字段***必须同时***出现在 `output_schema` 与最终节点 `delivery.mapping` 中——只声明并返回、未进入 mapping 的文件不会被登记为 Artifact；mapping 引用的缺失字段自动跳过，必填由 `output_schema` 的 `required` 裁决（规则详见 `stages/S2-资产制作.md` 8.1）。

事件、表单握手与 Delivery Review 各自的契约细节见 `stages/S2-资产制作.md` 第 6 节；三种审阅形态的语义见 `stages/S1-业务设计.md` 7.4。

### 1.3 入口并存

已发布路线在业务应用与聊天两个入口天然并存，走哪个入口由最终用户自选：业务应用提交经 Runtime 运行（有业务事件、有界面状态）；聊天中直接派发已挂载的 Workflow 时业务事件自动降级不生效（无业务应用）。这是平台运行期行为，不是设计决策——制作侧不设计也不引导入口选择（见 `stages/S2-资产制作.md` 6.2）。

## 二、渲染语义

"渲染"指把运行中的事实投影给最终用户：业务应用的阶段状态、中间结果、提醒，以及交付页的最终呈现。本章回答**什么值得投影、何时投影、投影的意义**——具体的事件声明语法在 `stages/S2-资产制作.md` 第 6 节，界面工程细则在脚手架仓文档。

### 2.1 投影的通道

| 通道 | 载体 | 何时发生 |
|---|---|---|
| 业务阶段状态 | `stage_started` / `stage_result` / `stage_failed` 业务事件 | 脚本在业务节点显式发布（生命周期硬门必发；密度事件按需） |
| 平台交付事实 | `artifact_ready` / `delivery_ready` | Runtime 在文件登记、交付冻结后自动发布，脚本不参与 |
| 提醒 | `attention_required` 事件 | 不要求最终用户回答、但值得引起注意的事实 |
| 运行中交互 | 业务表单握手 | 上游成功后才能确定、且供未派发下游使用的输入 |
| 最终交付呈现 | `output` 业务字段（定制界面直接消费）；`output.display`（兜底出口） | Delivery 冻结后 |

### 2.2 什么值得投影（判断依据）

- **以最终用户的等待体验为出发点**：一次运行中，用户在界面上能否回答"现在到哪了、出了什么、接下来会怎样"。达不到就缺投影；能回答就够了，**不要**为完整而完整。
- **投影业务事实，不投影执行机制**：阶段名用最终用户能理解的业务语言，**禁止**出现 Workflow、节点、工具、Agent 这类平台概念（约束 9 与事件硬门的一贯要求）。
- **中间结果只在"值得单独看"时投影**：一个阶段的产出会影响用户对后续的预期（如"已找到 3 个候选方向"）才值得发中间 `stage_result`；纯技术过渡步骤不投影。**禁止**在每个 `tool()` 后机械发事件，业务应用不做进度条。
- **密度由消费方反推**：事件候选与其页面用途在方案 Plan 中提出并由开发者确认（`stages/S2-资产制作.md` 6.4；业务应用的页面设计在 app_creator 线完成）——没有消费方的事件不声明。

### 2.3 投影的意义

- 对**最终用户**：把不可见的多分钟执行变成可理解的业务进程，等待可容忍、异常可解释、结果可信任。
- 对**开发者与诊断**：持久化的业务事件是运行的公开事实轨迹，验收（事件覆盖核对）与诊断（阶段级定位）都建立在它上面。
- 对**交付质量**：交付页直接消费 `output` 业务字段呈现业务形态（对比、清单、结构化内容），`output.display` 是平台标准的**兜底展示出口**（无定制界面的包、聊天内呈现使用）。由此对 `output_schema` 有两条硬要求：
  - **字段描述必须含面向呈现的语义**（该字段是什么、每项含义），不能只写给下游脚本看；
  - ***要渲染的内容必须以业务字段出现在 `output` 中***：界面对工作区文件只有预览 URL 与下载，**读不到文件正文**——内容只落文件、`output` 只给计数和路径的契约，界面等于写在假数据上。凡要给最终用户看的列表、正文、结论、对比，都进业务字段。

投影设计的产物落点：事件契约（Workflow 资产）、渲染决策（样例选择编译产物之一，`stages/S2-资产制作.md` 4.2）、面向系统的公开语义（编排定稿后冻结，`stages/S2-资产制作.md` 8.3）；业务应用侧的事件归约与页面响应设计在 app_creator 线完成。
