# 选择题与判断题

尚未明确、要开发者拍板的取舍做成选择题；② 生成方案后做整版确认；② 定稿的验收条目照本文「验收条目」写。题目只问 [../SKILL.md](../SKILL.md)「开发者确认什么」里的四类事。什么时候问、一轮问哪些、每个应用都要问哪几题、什么算定了，见 [按轮问.md](按轮问.md)。

## 选择题（①、② 写方案前、③ 用）

```text
❓ Q2 从哪开始：使用者要先填什么才能开始？平台上的地图工具按店名能查到候选门店，海外店要多一步网页核实。
   A 只填店名，城市选填：门店由应用去查，查到几家时让使用者选
   B 店名、城市、官网、小红书主页都填：查得更准，但使用者要先准备好这些
   C 其他，说说你的想法
➡️ 推荐 A，只填店名
```

- 每题一个标题、一段说明、一个推荐答案；题目写成开发者回「是」就是采纳推荐。
- 说明先写为什么要问，再给事实依据（真跑花了多少、实测多久、查到什么；还没查到就不写）。
- 有现成做法时给 2–4 个选项，每个写清选了会怎样（多花多少、少什么功能、慢多少）；最后固定加一个「其他，说说你的想法」，不让选项把开发者的想法堵死；推荐答案单独一行写在最后。
- 题目要花钱（试跑、真调）时，题干写清份数和约多少积分；说不出数时等查到再出题。
- 要别人答的题，题号后写清请谁答：需求方与开发者不是同一人时写「请需求方答」；材料里提需求的人和拍板的人不是同一个时，按材料里的说法写「请业务负责人答」。开发者可以代答，在「要你做的」里说明。① 的选择题和 ② 的取舍题都适用。
- 答案记进 PRD（② 记进方案）对应的题下面，写清谁答的：「开发者答：A」「需求方答：B，补充：……」。

### 事实题

只有开发者知道、平台上查不到的事实（「你们现在把跟进记录记在哪」「给谁用、多久用一次」），照样出题，但不给选项、不给推荐：题干写清要他说什么，可以举一两个说法帮他理解，标明「这题只有你知道，没有推荐答案」。回「是」不算答了；回「不确定」怎么处理见 [按轮问.md](按轮问.md)「什么算定了」。

## 整版确认

② 取舍、验收要求和费用变化在生成方案 HTML 前问清，已答事项直接沿用。生成后只确认一次整版，或请开发者直接指出哪里要改，不另发逐项判断或整版确认表单。

Studio 中点宿主确认卡或对话明确同意任选其一，完成后不再要求另一种确认；登记和读回见 [开发文档/README.md](开发文档/README.md)「确认怎么登记」。其他宿主在对话中确认，记录当前版本和原话。

收到修改意见时，只澄清尚未明确的改动和受影响的取舍，保留其他已答事项；保存新版、说明变化，再确认一次整版。要改的是要什么、不要什么时，退回 ① 改 PRD。

## 验收条目

② 把 PRD 每个刚需的「怎样算做成」写成能逐条照做的验收条目，④ 照它逐条测。每条是一次完整的使用者任务，用使用者的话写，不写平台概念：

| 列 | 写什么 | 例 |
|---|---|---|
| 谁 | 人① 使用者 | 人① 使用者 |
| 从哪进、先看到什么 | 打开应用后首屏应该看到的东西，从哪里开始 | 首页先看到「新建项目」和做过的项目 |
| 用什么、按什么顺序做 | 用什么数据；操作步骤，与业务顺序一致 | 只填「莫定标娘惹糕点」→ 提交 → 选候选 → 等报告 |
| 最后拿到什么 | 成果，以及它能支撑的下一步 | 中英文报告，能直接下载发给商家，接着生成内容 |
| 怎样算过 | 可以判断的标准 | 有槟城 Lebuh Chulia 的候选；30 分钟内出报告 |

- 每个刚需至少一条；有中途补信息、审阅、会停下的情况的，各写一条走到那一步的。
- 第一次使用和日常使用不一样（例如第一次要先建档）时分开写。
- 每条预先标「AI 能判断」还是「要人判断」（例如报告能不能直接发给商家、语气像不像店家写的），④ 照这个分；「要人判断」的条目在验收报告里是「好不好你说了算」。
