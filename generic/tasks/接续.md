# 接续

## 识别信号

- 开发者说「继续」「接着做」「上次那个应用」，或当前目录已有 `app.json`、`WORKSPACE.md`、`workspace.json`。
- 开发者给了此前的 `task_id`、应用名或 `business_ui_id`。
- 开发者打开插件继续一个协作中的应用，或收到了提请属主上线、基线过期的站内信。

## 先读什么

1. 当前应用工程根的三件套：`WORKSPACE.md` 的 `current_stage` 与 `business_ui_id`，`workspace.json` 的阶段标记，`docs/stages/` 下当前阶段的阶段文档，`docs/proposal/index.html` 的 PRD 与 `status`。
2. 原工单：`task_manager(action="get", task_id=…)` 看已记的 checkpoint（资产 ID、版本、run_id）。原工单是只读或已结单时新建 write 工单并传 `continued_from_task_id`，同样按 SKILL.md「开工」第 1 步带 `skill_version`。
3. 协作状态：`business_ui_manage(action="get")` 看 `role`、待上线清单和自己草稿的基线是否过期，处理完再接本轮改动。属主有待上线清单时先问开发者要不要上线；协作者草稿基线过期时，先按 [../reference/多人协作.md](../reference/多人协作.md)「基线过期的合并」依次下载新版源码、本地 git 合并、重新派生草稿、上传部署、再提请；只读协作者用 read 工单，只走诊断路线。
4. 本地缺失或换了机器：`workspace_remote_status` 看云端状态，`workspace_pull` 取回，先比较差异、保留本地新改动再合并，不默认用云端覆盖本地。规则见 [../reference/开发者中心与工作区.md](../reference/开发者中心与工作区.md)。
5. 脚手架版本：按 [../reference/脚手架与预置件.md](../reference/脚手架与预置件.md) 带 `workspace_id` 调一次 `download_template` 核门槛；低于必须线先迁移。
6. 缺失的工作区文件用 `npm run scaffold:repair -- --app-name "<应用名>"` 补，保留已有事实。
7. 本轮涉及文案或页面时，读取已有业务文案、实际接线和已确认路线/表单/产物，按 [../reference/前端页面.md](../reference/前端页面.md)「业务文案」只核受影响场景；已有正确配置和定制保留，不能用默认词覆盖，也不从零重做需求确认。

## 从哪一段进

按方案页 `status`、`current_stage` 和工单 checkpoint 判断做到了哪一段（工作区阶段和五段的对应见 `SKILL.md` 第 6 节），从还没交棒的那一段接上；段内已 `passed` 的阶段不重做。标 `not_started` 的可能是上次有意跳过的（阶段文档里有原因），按原因重新判断要不要做，不因为没标 `passed` 就补做。接上前核对它依赖的东西是否仍成立：PRD 已确认、判断题已答、资产还在、版本没被别人改、冒泡证据仍是当前合同下的；不成立就回到失效的那一段。

旧应用按七个节点做过、没有 PRD 时：已经上线的按修订处理；还没上线的，先把已有确认页补成 PRD 差异版（补上谁来用、每一步谁来做、花费上限和用量），请开发者确认一次，再从对应的段接上。旧应用的阶段名可能是旧名，按 G 键对应，只改状态不改名。

接上后先发一条交接消息，告诉开发者现在在哪一段、下一步、要他做什么。

开发者要看本地页面而「演示预览」是空的，按 [../reference/开发者中心与工作区.md](../reference/开发者中心与工作区.md) 的「演示预览为空」判断是还没生成完成版、需要生成，还是要重新启动。
