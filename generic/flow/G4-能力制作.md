# G4 能力制作

按资产清单（G3 的编译结果，或简单需求在确认页里已列清的部分）造场景包里的能力：工具集 → FA → 编排型 TPE → 路线。每条 TPE 用 verify 出报告，每条路线冒泡到终态。对开发者只说「某功能做好了」。

## 1. 进入条件

- 知道要造或要改哪些资产：G3 编译结果与确认页一致，或确认页已经列清。
- 从修订进来时，先取可编辑草稿（`ensure_draft` 或 `ensure_editable_asset_draft`），只改受影响的资产。

## 2. 做什么

每一步的参数以工具当前 Schema 为准，这里只给顺序和必带项。

1. **场景包草稿**：新建 `scene_package_manage(action="create", task_id, name, description, apc_skill)`；已有包用 `ensure_draft`，官方或他人的包先 `clone_asset`。`apc_skill` 用开发者的词写「这个包能做哪几件事、各自什么时候用、发起前要收齐什么」，1–4k 字，不写资产 ID。
2. **接入缺的工具**（G2 判定要接入时）：按 [../reference/依赖与MCP接入.md](../reference/依赖与MCP接入.md) 先预览再注册，需要最终用户各自授权的配授权卡。
3. **FA**：每条模型行一个 `create_fast_agent(name, description, prompt_content, …)`，且一个 FA 只承担一个语义责任。只要这条模型行要按客户、任务或上一步结果去应用库挑选素材、记录或上下文，**不管施工单怎么写**，建 FA 时就按 [../reference/数据模板.md](../reference/数据模板.md)「FA 挂工具」挂上 `query_business_app_dataset` 工具组并反读确认，不要等到 G5；**禁止**把素材摘要、记录列表整批塞进入口字段来绕过。提示词写清输入字段、输出对象每个字段的含义和非成功状态；输出要给部分成功留出口（见 [../reference/编排脚本.md](../reference/编排脚本.md#fa-与脚本的职责边界)）。建完 `get_asset(asset_type="fast_agent")` 反读 `mr_name`，脚本里用这个名字，**禁止**自己拼前缀或用数字 ID。
4. **工具集**：把 G2 核实过的工具组、FA 装进 `create_toolset(name, description, tool_group_ids, fast_agent_ids)`；脚本要读写应用库的，把工具组「query_business_app_dataset」也装进来；一条路线通常一个工具集。本轮新建或导入的工具集做一次安全的运行时测试后 `online_toolsets`，再 `get_asset` 反读确认全部上线——离线工具集运行时加载不到。
5. **编排型 TPE**：脚本按 [../reference/编排脚本.md](../reference/编排脚本.md) 三种模板之一改，第一次写之前读 `get_diagnosis_doc(topic="otpe_single")`。定 `_output` 时先过同一参考的职责边界门禁：控制面保持最小，内容走稳定载体引用，同类错误连续两轮就停止扩 Schema 并回到 G3/G4 重划职责。路线读写应用库的，preview 前逐项自查，**任一项不满足先改，禁止 preview / create**：脚本复制了统一的 `db()`，所有应用库读写都经 `db()`，写库语句包在 `if not ctx.dry_run:` 里，没有自写 `query_db`、`sql_literal`，也没有用 f-string、`+`、`.format()` 把业务值拼进 SQL；工具集装了工具组「query_business_app_dataset」并在 `preload_toolset_ids` 里；要自查应用库的 FA 反读 `tool_group_ids` 不为空；`input_schema` 只放发起者必须给的业务键和少量临时补充，**不得**出现 `materials_summary`、`materials_text`、`snippets`、`records`、`records_json`、`customer_profile`、`customer_summary` 这类整包素材、记录、客户资料字段来代替本该从应用库查的数据，也不留「入口传了就用、没传再查库」的兜底。`otpe_manage(action="preview", task_id, script, input_schema, output_schema, business_event_contracts, preload_toolset_ids)` 通过后 `create`（同一组参数加 `scene_package_id`、`name`、`description`），再 `online`。事件契约最少两条：`stage_started` + `stage_result`。
6. **verify**：`otpe_manage(action="verify", task_id, tpe_id)` 看 `verdict`：`blocked` 按 `failed` 项改后重来；`needs_bubble` 说明静态项都过了，只差冒泡证据。
7. **单条冒泡只用于多节点路线的单节点调试**：路线只有一个节点时跳过这一步，直接做第 8、9 步。多节点路线里某个节点要单独调通时，`otpe_manage(action="bubble", task_id, tpe_id, workflow_input=<代表性输入>)` 拿 `run_id`，只传 `run_id` 续等到终态，再 `verify(tpe_id, run_id)`。
8. **路线**：`scene_package_manage(action="assemble", task_id, scene_package_id, tpe_ids=[按顺序], orchestration_id, title, entry_form_id)` 得到草稿；处理 `unresolved`（类型不一致、输出为空）与 `notes`，再把 `workflow_orchestration` 原样传给 `scene_package_manage(action="update", scene_package_id, workflow_orchestration)` 保存。分支、并行、中途表单、Agent 接管按 [../reference/业务路线.md](../reference/业务路线.md) 手写接缝。
9. **路线冒泡一次**：`scene_package_manage(action="bubble", task_id, scene_package_id, orchestration_id, workflow_input)`；续等只传 `run_id`，回填中途表单传 `run_id + formdata`。到终态后对路线里每条 TPE 调 `verify(tpe_id, run_id=<路线冒泡的 WRV- run_id>)`，它按 `tpe_id` 取该节点的结果，`passed` 即完成，不必再单独冒泡。每条路线一个正常样例；有明确边界规则时再加一个边界样例；改了脚本或路线才重新冒泡。终态记 `run_id` 进工单，一条路线一条 checkpoint。

**冒泡的边界**：冒泡里 FA 是桩（按输出 schema 造值），工具、shell、文件照常真实执行，只有脚本按 `ctx.dry_run` 判断的外部动作被跳过。桩值导致下游失败、或模型行的真实输出需要验证时，对同一路线加 `full_run=true` 重跑一次；确认页已同意制作中的测试费用，直接跑，跑完在方案页记实际花费。花费明显超出确认页估算、或会对外发送时才先问。

**参数由谁填**：事件契约、`_output`、`_rationale` 在脚本模板里已有位置，只改业务词；入口映射、节点映射、交付映射由 `assemble` 生成，你只审 `unresolved`；`tpe_id`、`scene_package_id` 来自上一步返回值，记进工单，不手抄。

## 3. 产出与落盘

- 工单 checkpoint：场景包草稿 ID、每个新建资产的 ID 与 `mr_name`、每条 TPE 的 verify 结论、每条路线的冒泡 `run_id` 与终态。
- 本段阶段文档记录资产清单的实际结果与 verify 报告摘要。
- 方案页 `status` 写当前进展；冒泡通过只算「未验证」（写明「只用模拟数据跑过」），真跑到终态成功的才进「已验证」并写 `data-evidence`。
- 阶段标记：G4 `passed`。

## 4. 给开发者看什么

每做好一条路线说一句：「投放诊断已经能跑通，用示例数据试过一次」；冒泡里模型结果是占位的，要说明「内容效果留到预览时用真数据看」。

## 5. 出口

- 每条编排型 TPE：最近一次 `verify` 的 `verdict=passed`（带路线冒泡或单条冒泡的 `run_id`）；
- 每条路线：以当前合同下最近一次冒泡到终态，`success` 的 `run_id` 已记入工单；失败的已修好重跑，或已按 [G7-上线交付.md](G7-上线交付.md) 的结单门说明原因。

## 6. 出问题怎么办

| 现象 | 先看 | 回到 |
|---|---|---|
| verify `static_contract` 失败 | `errors[].where/msg`，多半是 `_output` 形状或事件契约 | 本段第 5 步 |
| verify `toolsets_online` / `tpe_online` 失败 | `online_toolsets` / `otpe_manage(action="online")` | 本段第 4、5 步 |
| 冒泡失败 | `steps[].error`；`repeated_error_count>=2` 换策略，不原样重跑；同类事实错误、引用错误或无产物连续两轮时，按 [编排脚本职责边界](../reference/编排脚本.md#fa-与脚本的职责边界) 停止加字段并重判 FA、脚本与工具职责 | G3 或本段 |
| 冒泡没到终态 | 服务端最多等约 45 秒，用同一 `run_id` 续等，不要重新发起 | 本段 |
| 以为 FA 用了回执顶层的模型 | 顶层 `resolved_model` / `resolved_mode` 是这次验证运行（外层 SA）的模型和模式，不是编排里 FA 的模型；FA 按资产配置运行：必选模式固定用该模型，可选模式用资产兜底模型，未配兜底用平台默认组；用 `get_asset(fast_agent)` 查看 `model_selection_mode` 与 `model_name` | — |
| FA 失败或 `FA_STEP_BUDGET_EXCEEDED`，不知道它每一轮做了什么 | 先看 `manage_goalfymax_project` wait/status 返回的 `fast_agent_failures` 和下一步提示；再用 `get_project_execution_logs(action='detail', log_type='fast_agents', project_id=…)` 看逐轮的工具、参数和截断标记（`args_truncated_by_repeat_guard`）。冒泡回执里的 `project_id` 在冒泡发起后 2 小时内可读 | — |
| 路线保存被拒 | 按返回的节点、字段、路径错误改同一个对象 | 本段第 8 步 |
| 编译结果做不出来 | G3 清单与 G2 对照表 | G3 或 G2 |
| 其他报错码 | [../reference/报错对照.md](../reference/报错对照.md) | — |
