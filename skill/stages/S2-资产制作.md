# S2 资产制作

按已确认的方案 Plan，自底向上创建与修改全部资产。

## 1. 进入前提

S1 出口条件全部满足（执行结构表 `challenged=true` 且方案 Plan 已确认）。修订已上线包的任务已持有草稿行——**一切内容修改只发生在草稿行上**；内容写入被版本闸门拦截（结构化错误提示需要先定稿或先建草稿）时，回 S1 第 11 节取得可编辑草稿，**禁止**绕过闸门直接改上线版本（详见 [场景包版本体系与发布逻辑](../references/场景包版本体系与发布逻辑.md)）。

## 2. 创建顺序与依赖准备

### 2.1 依赖资产准备

按约束 5 自底向上创建，**每创建一步都反读**名称、关系、状态、权限。本节只准备场景包草稿之前的底层依赖和普通任务点；Workflow 必须等 10.2 创建真实场景包草稿容器后，再按第 5 节创建并挂载。

### 2.2 工具集上线的两道检查

**工具集上线有两道检查，都不能跳**：

**第一道：Workflow 依赖检查**（任何 Workflow 创建前）：确定完整的预加载工具集清单 → 对本轮新建或导入的工具集做安全的运行时测试 → 全部无失败后调 `online_toolsets` → 反读确认全部已上线 → 才能创建 Workflow。

**第二道：交付前最终检查**：对待上线清单里尚未上线的工具集逐一做安全测试 → 破坏性操作跳过 → 全部无失败后上线 → 反读确认。

任一测试失败、余额不足、授权中断或流程异常，**必须**保留原资产和进度，恢复后从未完成的验证继续，**禁止**跳过验证直接上线。

**开发者已有的离线工具集可以关联，但运行时不会被加载。** 发现这种情况**必须**停止交付并告知开发者，**禁止**擅自上线别人的资产。

新建工具组后按需配授权卡（2.3）。为需要最终用户各自授权的能力配卡是正式依赖，不是可选项。

创建 FastAgent、工具集或普通任务点时，提示词或使用指南较长，可以按 3.3 使用实时 Schema 暴露的 `prompt_content_url`、`tool_usage_guide_url` 或 `prompt_template_url`。服务端解析后仍按对应原字段创建；创建完成后反读正文和资产关系，URL 成功下载不能替代资产反读。

### 2.3 授权卡

工具需要**终端用户各自的第三方账号授权**（区别于写在请求头里的服务级认证）时，授权卡是正式依赖。不配的话终端用户无法完成授权、工具调用会失败。

| 工具 | 用途 |
|---|---|
| `create_auth_card` | 为工具组创建授权卡 |
| `update_auth_card` | 更新已绑定的授权卡配置 |
| `link_auth_card` | 用授权卡标识关联到已有卡片，共用其授权配置 |

**禁止**把任何个人令牌写入 Skill 文本、脚本或工单。详细配置见 [依赖与 MCP 接入](../references/依赖与MCP接入.md)。

完整的注册流程、调试循环、私有包处理、授权卡配置和上线检查见 **[依赖与 MCP 接入](../references/依赖与MCP接入.md)**。

### 3.2 工具真实取样

**什么时候用取样**：写 Workflow 脚本时需要知道某个工具的真实返回结构——光看工具描述推不出嵌套字段的实际形状，猜错会导致下游步骤读不到字段。取样一次拿回真实样本，再据此写脚本里的输出声明。可以同时提交一个候选的输出结构，让本次样本顺带校验它。

工具只依赖已有业务项目上下文时传项目标识，这不会启动新项目。工具需要读取测试文件时，先用 `file_to_url(purpose="tool_test_fixture")` 把 Agent 本地文件换成临时文件引用；把返回的 `data.file_ref` 放进 `workspace_files`，再用 `workspace_bindings` 声明由哪个目标工具顶层参数接收该文件路径或父目录。服务端会复用冒泡验证的隐藏项目，从临时 HTTPS URL 下载真实文件、写入 `/workspace` 后调用工具，并在成功或失败后自动清理。此模式不要同时传 `project_id`。

**取样会真实调用供应商接口。** 破坏性、发布、凭证、金融或任何不可逆的工具**禁止**取样，只对**安全只读**的工具做。

### 3.3 文件与创作型长文本准备

先判断提交内容属于哪一类，二者的生命周期不同，**禁止**混用：

| 类型 | 典型内容 | 提交方式 | 平台保存结果 |
|---|---|---|---|
| 资产文件 | Skill 文件、辅助脚本、模板、样例、私有包、Logo、工具取样文件 | `file_to_url` 换取文件引用，再把引用绑定到资产或验证项目 | 文件作为独立资产或附件保留 |
| 创作型文本 | Workflow 脚本、`apc_skill`、业务路线编排 JSON、FastAgent 提示词、工具集使用指南、普通任务点提示词、待更新字段全文 | 短内容直接传原文本字段；长内容或需要反复维护时，在实时 Schema 暴露对应 `*_url` 后传服务端可访问的 HTTPS 文本地址 | 服务端只读取一次正文，再按原文本字段的校验、确认、保存和上线链路处理；URL 本身不绑定为资产文件，也不作为配置保存 |

创作型文本 URL 只是一种**输入传输方式**，不产生新的资产类型。使用时遵守以下规则：

- 原文本字段与对应 `*_url` **二选一**；Workflow 的局部补丁还要遵守实时 Schema 中与完整脚本来源的互斥关系
- URL 必须是服务端可访问的 HTTPS 文本地址，不得指向内网、客户端本地路径或需要浏览器登录的页面；编码、大小、重定向和地址安全限制以实时 Schema 为准
- 外部 Agent 的本地 `/workspace` 不属于 Max 沙箱，**禁止**作为 `script_file` 传入；内部 Max Agent 只有在实时 Schema 暴露 `script_file` 时才可使用
- 提交成功后**必须**反读最终正文、JSON 对象或脚本摘要，确认平台保存的是解析后的内容而不是 URL；下载、解析或校验失败时停止提交，禁止截断正文后伪装成功
- URL、临时上传地址和带签名的查询参数**禁止**写入工单；工单只记录目标资产、内容用途和反读结论

#### 资产文件：第一步换取文件引用

`file_to_url` 是唯一的文件通道，**必须**声明用途，服务端按用途决定大小、类型和存储规则：

| 用途 | 用于 |
|---|---|
| `skill_file` | Skill 文件、辅助脚本、模板、样例 |
| `skill_package` | 要导入成工具集的标准 Skill 包 |
| `mcp_package` | 要注册成工具组的私有 MCP 包 |
| `scene_package_logo` | 场景包 Logo 图片 |
| `tool_test_fixture` | 真实工具取样时需要落入隐藏 `/workspace` 的本地测试文件 |

四个 action（本地新文件没有直传内容的路径，只能 `prepare` → 客户端 PUT → `complete` 三跳）：

| action | 说明 |
|---|---|
| `prepare` | 申请上传地址，**必须**传真实字节数 |
| `complete` | 确认上传，换回文件引用。传入的凭据**必须**来自同一工单、同一用途的 `prepare` |
| `from_url` | 已有可信 HTTPS 地址时跳过上传直接导入。**仅支持** `skill_file`，且地址**必须**服务端可访问、**不得**指向内网 |
| `export` | 按明确资产 ID 把 Workflow 脚本或 FastAgent 提示词导出成可下载文件（用途 `asset_text`） |

**不接收** base64。临时上传地址**禁止**写入工单。

#### 资产文件：第二步绑定到资产

| 情况 | 做法 |
|---|---|
| 资产还没创建 | 在创建调用里直接带上文件引用 |
| 资产已存在 | 用 `upload_skill_files` 补挂，需要指定资产类型和标识 |
| 场景包的场景 Skill 文件 | 用 `scene_package_manage(update)` 带文件引用 |
| 场景包 Logo | 用 `update_scenario_package_logo` 带文件引用 |

`upload_skill_files` 和场景包更新都支持合并（merge）与整体替换（replace），但**缺省相反**：场景包更新（`scene_package_manage(update)`）缺省 merge，保留既有文件；***`upload_skill_files` 缺省 replace，省略参数会覆盖整个 Skill 目录***——补挂单个文件时显式传 `skill_files_mode="merge"`（支持 scenario_package / toolset / fast_agent），定点删除用 `remove_skill_paths`。

### 3.4 业务应用数据集读写通道（为业务应用制作的场景包）

场景包配套业务应用（约束 8，app_creator 线）时，运行期的用户数据都存在**业务应用数据集**里——用户点开应用时从模板 copy 出的那份 PG schema，它是应用的后端数据库，应用后端直连它，项目内的执行则经平台级 FastAgent **`dscli_business_dataset`** 在沙箱内读写同一份数据。该 FA 是平台资产建一次，**包作者不用自制**，制作时把它所在的 **Business UI Dataset 工具集**挂进相关 TPE 的预加载清单即可；调用语法与红线由工具集使用指南在运行时注入，本节只写设计侧必须知道的：

**三个时机的分工**（设计路线时按此归位，不要错配）：

| 时机 | 谁来做 | 走不走 FA |
|---|---|---|
| 项目启动铺底（门店信息、当前进度等上下文） | 应用后端直读 PG 拼进发起报文 | **否**——此时 agent 尚不存在，制作侧不为它设计取数步骤 |
| 执行中按需取数（需要理解业务语义的"要什么"，如"结合本店近 30 天数据定内容方向"） | 脚本调 FA（`operation="read"`） | 是。**每条业务流至多一次读**，结果沿 node_output 流转给全部下游，不逐节点重复取 |
| 收尾回写（交付结果与效果数据落库，供看板展示与下次运行参考） | 脚本调 FA（`operation="write"`） | 是。`context_hint` **必须**给出唯一键或幂等依据——编排重跑会让同一段写再执行一次 |

**四条设计纪律**：

- 制作期就能写死"取哪张表哪个字段"的，走确定性取数，**不起 FA**——FA 只用于需要业务语义理解的取数；
- **`found=false` 是常态结果不是错误**：表不存在、查不到行都这样收口，下游节点必须把它当缺省处理（"无数据时按通用策略执行"），***绝不因空数据 fail***；
- 写权由列注释声明裁决：FA 只写 `editable:agent` 列、模板结构只增不改（声明正本与写权矩阵见 app_creator 约束 9）；
- 不传 `sandbox_id`——workflow 路径自动继承 TA 沙箱；脚本引用该 FA 后 TA 会自动预建沙箱。

## 4. FastAgent 制作

### 4.1 输入定义与提示词设计

FastAgent 的构成、输入定义硬性要求与最大轮次取值的正本见路由器 `SKILL.md` 7.3。制作时按 S1 已确认的执行结构表落实每个 FastAgent 的职责、输入输出与关联工具组；同域多类产出遵守 S1-6.4 的数量纪律（一个 FastAgent + 交付物参数分发 + 规范文件）。

### 4.2 样例选择流程

凡 S1-10.3 圈定的关键 FastAgent（面向最终用户的输出文案类产出），提示词定稿前**必须**执行样例选择，三步：

1. **领域调研**：**先询问开发者是否有参考资料**（范例、竞品、过往内容）；开发者给不出时才自行上网调研——从产出的目标平台或领域取真实样本入手。**禁止**凭空或随机生成样例。
2. **生成候选样例**：基于调研产出 2–3 种不同取向的**具体**理想输出样例，标注参考来源。
3. **开发者选择**：让开发者在具体样例之间选择，**不要**让开发者在抽象形容词之间选择。选择结果同源编译进三处：该 FastAgent 的提示词、该环节在结果检查表中的验收判定、该环节产出的渲染决策。

过程类环节（中间数据变换、不面向最终用户的产出）不执行本流程，不打扰开发者。

### 5.2 依赖上线检查

见 2.2 第一道检查。**未通过禁止创建 Workflow。**

脚本要用到辅助文件时，先完成上传闭环并提供完整的目标文件集合。

### 5.3 单条 Workflow 的完整闭环

提交脚本前先按运行环境与变更范围选择来源，**不要**为了改一处重新生成并重传整份脚本：

| 场景 | 选择 |
|---|---|
| 脚本较短，或首次提交时正文已在当前上下文中稳定生成 | 直接传内联 `script` |
| 外部 Agent 已在自己的工作区维护完整脚本，或脚本较长、需要多轮修改 | 把完整 UTF-8 脚本放在服务端可访问的 HTTPS 地址，通过 `script_url` 提交 |
| 外部 Agent 只修改服务端现有脚本中的一个精确片段 | 在实时 Schema 支持时使用 `script_patch`，携带当前脚本摘要和唯一匹配的改前、改后文本，避免覆盖并发更新 |
| 内部 Max Agent 在同一项目 `/workspace` 中维护脚本文件 | 仅在内部实时 Schema 暴露时使用 `script_file`；外部 Agent 禁止使用 |

完整脚本来源、局部补丁和路径参数的互斥关系以实时 Schema 为准。只修改输入输出定义、依赖或其他配置时，**不要**顺带重传未变化的脚本；使用 URL 或补丁后仍进入同一套 Preview、保存、上线和反读流程，不得降低验证层级。

1. 从前期确认的方案冻结业务职责、根对象输入输出定义、是否需要业务事件及其契约、正式运行入口、代表性输入、文件与副作用边界
2. 反读工具集成员和上线状态，确认全部可用
3. 有辅助文件时完成上传
4. `preview`——按返回的字段、工具、路径和确定性规则修**同一份草稿**
5. `create` 或 `update`——保存后反读标识、命令标识、输入输出定义、业务事件契约、依赖和版本
6. `bubble` 启动并轮询到终态——**必须**复用同一个运行标识
7. 检查运行结果的步骤、轨迹、覆盖率、未触达工具、最终输出和错误
8. 读取 [Workflow 验收检查清单](../checklists/Workflow验收检查清单.md) 做语义验收；不通过就更新原 Workflow 并重跑

Preview 对业务事件采用**条件硬门**：业务事件契约和 `emit_business_event` 调用必须同时为空，或同时构成完整闭环。未声明且未调用时按无事件 Workflow 验证；一旦声明或调用，至少声明并调用 `stage_started` 和 `stage_result`，首个业务动作前保证已经发布 `stage_started`，每条可达 `return` 前保证发布 `stage_result`，受控业务失败分支可用 `stage_failed`；声明未使用、调用未声明或类型不一致均拒绝保存。Preview 只证明静态生命周期闭合，不证明事件已入库。

**产出文件的交付链**：FastAgent 在隔离会话里运行，生成的文件落在它自己的任务点目录，不会自动出现在本 Workflow 的产物目录。平台信任**真实返回**：FastAgent 或工具返回的 workspace 路径可以直接写进本节点输出、在节点间传递。要**随交付给用户**的文件则须在最终节点收口：把文件收进 `ctx.output_dir`（复制，或由脚本写入内容），以 `workspace-file-path` 在 `output_schema` 声明，并进入 `delivery.mapping`（8.1 规则一）——***交付守卫只登记最终节点产物目录内的文件，留在会话目录里的路径到不了用户手上***。

跨运行引用先前产物**必须持有其绝对 workspace 路径**（经状态文件或输入字段传递）——每次运行的产物目录都不同，用"当前目录 + 命名约定"拼路径读取先前运行的文件，第二次运行起必然找不到。增量修订场景沿用先前运行的产物时，凡要随本次交付的文件，先复制进本次 `ctx.output_dir` 再进 mapping；跨运行的历史路径只应存在于状态文件与输入字段，***出现在交付 `output` 的文件字段里必被 `ORCH_DELIVERY_FILE_UNISOLATED` 拒绝***。

**运行前必须先查对外副作用。** 发信、通知、发布、扣费、创建远端对象、写正式业务状态这类动作，**必须**用运行环境提供的演练标记挡住，并返回满足输出定义的明确未执行状态。**禁止**用演练标记跳过普通工具调用、跳过输入输出管路，或绕过桩值造成的下游失败。

**运行返回"执行完成"不等于业务验证通过。** 它只说明脚本在本次输入下正常返回并满足已声明的契约。**禁止**据此标记通过或向开发者宣称验证完成——未触达的工具和分支**必须**列为盲区。

单条 Workflow 的 Preview、bubble 和语义验收属于自动制作门，不需要向开发者逐条申请全真运行。FastAgent 内容、未触达分支和外部副作用盲区保留到整包端到端全真验证阶段统一处理。

### 5.4 执行结构表同步

修改任何 Workflow 脚本或结构（步骤、依赖、并行组、所用 FastAgent），**必须**同步更新执行结构表的对应条目并回写工单权威快照（路由器 5.3）。条目内容变化后其指纹随之变化、状态自动回退 `pending`——下一次方案挑战与验收**只处理这些回退条目**，未变化条目不重复检查。脚本与表不一致时以修正一致为先，**禁止**带着不一致进入 S4。

## 6. 业务事件设计

### 6.1 何时声明

写事件契约前先读 [Workflow 验收检查清单](../checklists/Workflow验收检查清单.md) 的事件章节，**尤其"必查反模式"小节**——多数事件设计错误（如为界面声明 `stage_progress`）在那里已被点名。

业务事件表达 Business Runtime 和业务应用可以稳定消费的公开事实，不是工具调用日志。只有确实需要业务路线可观察性、业务应用状态、业务表单握手或 Delivery Review 时才声明；未声明事件的 Workflow 不得调用 `emit_business_event`。事件类型、事件声明字段和原语签名**必须**以当前 `workflow_tpe_manage` 实时 Schema 与 `workflow_single` 规范为准；实时契约没有暴露业务事件能力时，相关 Workflow 裁决为 `platform_blocked`，**禁止**用标准输出、普通消息或自造 `print_event` 调用模拟。

### 6.2 正式运行入口

正式运行入口由事件契约决定：

| Workflow 事实 | 正式运行入口 | 身份规则 |
|---|---|---|
| 没有业务事件契约，脚本也没有调用 `emit_business_event` | 可以按实时工具契约直接派发单 Workflow | 不要求 Business Runtime 身份 |
| 单条 Workflow 声明或调用业务事件 | **必须**先写入只有一个节点的业务路线，再从该路线启动 | 服务端持久化并生成 `business_id`、`orchestration_id`、`workflow_runtime_id` |
| 多条 Workflow 构成固定业务路线 | **必须**写入多节点业务路线并从入口启动 | 同一运行实例中的节点共享服务端建立的 Business/Runtime 上下文 |
| 制作期 Bubble | 使用服务端分配的验证身份，不属于正式业务实例 | 验证身份只用于本次 Bubble，禁止复制到正式运行 |

脚本、SystemAgent、外部 Agent、业务应用和 MCP 调用方都**不得**生成、猜测、复用或补写上述正式运行身份。出现 `Workflow business event requires persisted Runtime identity` 时，先检查是否把带事件 Workflow 直接派发；这通常是运行入口错误，不是最终用户输入或 Workflow 业务逻辑错误。若是正式运行，建立或修正单节点/多节点业务路线后从路线入口重跑；若是 Bubble，服务端没有分配验证身份则裁决为 `platform_blocked`，不得在脚本里伪造 ID 绕过。

**运行期补充（三通道，不改变上表的制作侧要求）**：上表约束的是制作侧结构——带事件的 Workflow 必须建单节点路线，业务应用与路线启动经由 Business Runtime 运行。除此之外，平台还允许最终用户在聊天中直接派发**已挂载**的 Workflow：该通道下业务事件自动降级为不生效（无业务应用、不写业务事件），属于平台运行期行为，非设计决策，制作侧不设计也不引导入口选择。Runtime 身份按三态判定：三元身份齐全为路线内节点派发；全部缺失为聊天直调、事件自动降级；**部分缺失**为内部链路错误，服务端以 `WORKFLOW_RUNTIME_IDENTITY_INCONSISTENT` 拒绝——遇到该错误按 SD-诊断与维护 的报错对照排障，身份仍然禁止伪造。

### 6.3 生命周期硬门

声明业务事件的 Workflow，其生命周期覆盖遵守以下硬门：

| 业务节点 | 要求 |
|---|---|
| 脚本开始执行 | 在必要的输入读取后、首个业务动作前，***必须***发布 `stage_started`，名称使用最终用户能理解的业务阶段，不使用 Workflow、节点或工具名称 |
| 正常结束 | 每一个可能正常 `return` 的分支，在结果已经真实成立后，***必须***发布 `stage_result`；事件载荷与最终返回对象分别遵守各自契约，不能用事件替代返回值 |
| 产生文件交付物 | 脚本只把真实文件写入 `ctx.output_dir` 并按 `output_schema` 返回路径；要交付的文件路径字段同时进入最终节点 `delivery.mapping`（规则见 8.1）。Runtime 完成 Artifact 登记后自动发布 `artifact_ready`。脚本不得声明或发布该平台事件 |
| 路线最终结果可交付 | 最终节点按 `output_schema` 正常返回，编排完成 Delivery mapping、文件登记（输入即 mapping 的求值结果）和冻结后，Runtime ***必须***自动发布 `delivery_ready`；脚本不得声明或发布。该事件只表示具备审阅条件，不表示最终用户已经接受 |
| 可控业务失败 | 脚本明确识别并以业务失败结束的分支，***必须***发布 `stage_failed`；无法在脚本内可靠解释的技术异常仍让异常冒泡，禁止捕获后伪装成业务成功 |

### 6.4 事件密度与契约字段

各事件类型的 `payload_schema.required` **必须**包含对应平台字段（preview 保存时校验，缺失直接拒绝写入；业务字段在此之外自由声明）：

| 事件类型 | `required` 必须包含 |
|---|---|
| `stage_started` | `stage_key`、`stage_name` |
| `stage_result` | `stage_key` |
| `stage_failed` | `stage_key`、`error_code`、`message` |
| `attention_required` | `level`、`title`、`message` |
| `stage_progress` | `stage_key`、`progress_percent` |

除上述硬门外，事件密度由业务可见性决定：细分业务阶段的额外 `stage_started`、值得单独展示的中间 `stage_result`，以及不要求最终用户回答的 `attention_required`，均***建议结合配套业务应用的消费需要考虑***。Agent 在方案 Plan 中提出事件候选及其消费用途（已有 app_creator 线的系统设计时与其对齐），由开发者确认；只有确认系统确实需要据此更新阶段、结果模块或提醒时才声明。**禁止**在每个 `tool()` 后机械发事件。不为进度条声明 `stage_progress` 作为系统契约。

什么值得投影给最终用户、何时渲染、渲染的意义是什么，判断依据见 [运行模型与渲染语义](../references/运行模型与渲染语义.md)。

除 Runtime 自有的 `artifact_ready` 与 `delivery_ready` 外，脚本发布的事件都**必须**先在 Workflow 资产中声明稳定的 `event_key`、平台事件类型、版本、成立条件和根对象 Payload Schema，再由脚本调用当前受控业务事件原语。脚本不得动态拼接事件名，不得把内部 ID、原始工具返回、提示词、脚本、敏感信息或未脱敏错误放进载荷。事件声明有不兼容变化时升级事件版本；已有配套业务应用在消费该包时，同时通知 app_creator 线把系统契约视为已变化重新验收。

当前受控原语为 `emit_business_event(event_type=..., event_key=..., payload=...)`。`event_type` 与 `event_key` **必须**使用非空字符串字面量，`payload` **必须**是对象；调用只能引用资产中同名、同类型的已发布事件契约。业务事件契约的每一项包含 `event_key`、`event_type`、`event_version`、`description` 和根对象 `payload_schema`，且 `payload_schema.additionalProperties` 必须为 `false`。具体字段仍以实时 Schema 和 `workflow_single` 为最终事实源。

创建或更新 Workflow 时，直接通过 `workflow_tpe_manage(action="create"|"update", business_event_contracts=[...])` 随执行契约一并写入；写入后使用 `get_asset(asset_type="tpe", id=...)` 反读确认脚本与事件契约一致。不要另建事件配置文件，也不要用脚本常量代替资产契约。

业务事件是单向可观察性，不改变既有交互职责：入口表单、运行中补充表单、Runtime 恢复和最终审阅继续使用编排的 Business/Runtime 握手。`attention_required` **不得**复制一个正在等待最终用户填写的 `business_interaction`，Runtime 发布的 `delivery_ready` **不得**代替 Delivery Review。`runtime.delivery_ready` 的 `PublicDelivery` 结构与固定 `delivery.review` 审阅表单是平台固定契约（消费侧细则以脚手架仓当前文档为准，app_creator 线执行）；不得要求任何消费方从 Workflow 自定义事件或原始消息帧猜交付结构。

## 7. 对外声明来源类 Workflow 的证据要求

研究、资讯、调研这类会对外声明信息来源的 Workflow，**必须**保留可校验的"结论—证据"链：

- 上游把结论与其引用的证据标识、证据的来源地址、域名、日期作为**结构化对象整体传递**，**禁止**只拼接摘要文本后丢掉证据
- 下游每条结论**必须**带非空的证据引用，来源字段**只能**复制被引用证据的真实值，**禁止**改写
- 步骤输出与最终输出定义**必须**在根级声明证据契约

运行时会拒绝不存在的引用和被改写的来源。最终文档里的具体断言仍需逐条内容核对，**禁止**用"文件已生成"代替核对。

## 8. 业务路线编排组装

### 8.1 制作顺序

需要业务事件、业务表单握手、Delivery Review、业务应用入口或多 Workflow 固定依赖时，全部节点 Workflow 都已挂载并通过单体验收后，才能写编排。带业务事件的单条 Workflow 必须写成只有一个节点的业务路线；多条 Workflow 按真实依赖写成多节点路线。制作顺序：

1. 为每条候选路线冻结稳定职责、入口表单、路线输入定义、到达标准
2. 确认每条 Workflow 都有根对象输入输出定义、当前版本的运行证据；声明业务事件的节点还要确认当前事件契约完整
3. 画路线内依赖图：所有节点可达、无环，依赖只表达数据与执行先后
4. 逐字段建立入口映射、节点映射和交付映射，核对路径、必填、基础类型和文件格式
5. 制作期可预知的最终用户输入全部放入口表单；只有上游成功后才知道、且要喂给未派发下游的输入，才用运行中交互
6. 需要 Agent 在节点成功后审查或处理异常时，在该节点声明介入，写清指令和可验证标准
7. 读取 `stages/S1-业务设计.md` 第 10 节已确认的交付对象、最终审阅形态、审阅责任方、最终用户体验和风险；质量检查、内容核验或节点 `sa_handoff` 不能代替最终审阅
8. 按已确认方案声明唯一的最终交付与审阅动作。当前有四种动作：结束业务、以结构化原因拒绝交付并结束业务、跳转到另一条路线（**必须**指向真实存在的路线且入口匹配）、交由 Agent 处理；Agent 不得根据实现便利自行删减、增加或替换动作。两条声明规则：
   - **声明字段**：每个动作只写 `action_key` 与 `kind`，跳转动作另加 `orchestration_id` 与可选 `target_input_mapping`。***`label` 与 `description` 不可写***——保存门拒收未知字段，按钮中文文案由 Runtime 按动作类型生成；
   - **跳转的两种形态，按"这一跳需不需要用户新输入"二选一**：不需要 → 声明 `target_input_mapping`（每项 `source='delivery'` 从冻结交付取值，**必须覆盖目标路线 `input_schema` 全部 required 字段**，保存门校验），用户点跳转直启目标路线、不弹入口表单；需要（如选篇、写修改意见）→ 不声明映射，跳转弹出目标路线入口表单，已知信息的预填由业务应用实现（app_creator 线）
9. 按已确认动作设计最终审阅接受路径；存在最终用户修订、重做或改路线语义时，同时设计一条新建 Runtime 且保留当前 Delivery 的路径。真实资产与已确认业务路线图不一致时，停止写入并回到 `stages/S1-业务设计.md` 第 10 节更新 Plan，**不得**在本阶段重新替开发者做产品决策
10. 整体替换保存；对象较长时可按 3.3 在实时 Schema 支持后通过 `workflow_orchestration_url` 提交完整 JSON。按服务端返回的节点、字段和路径错误精确修**同一个对象**，**禁止**自行发明兼容字段

**交付映射（`delivery.mapping`）的三条规则**：

1. ***要交付的文件，路径字段必须进 mapping***：Artifact 登记的来源是 mapping 的求值结果——只在 `output_schema` 声明并返回、未进 mapping 的文件不会被登记，界面会显示无产出文件。文件路径字段可以嵌套在对象或数组里（如 `$.items[].card_paths[]`），求值结果中的 workspace 路径会被逐个登记，不需要为登记而拍平结构；
2. **缺失字段自动跳过**：mapping 引用的字段在本次返回中缺失时跳过该交付字段，必填与否由 `output_schema` 的 `required` 裁决——仅部分分支返回的字段（如失败分支的 `blocked_stage`）可以放进 mapping；
3. **文件路径须可验证**：mapping 引用的 workspace 路径要求是 `output_schema` 声明过、且位于本节点产物目录内的文件，二者之一不满足则交付被拒（`ORCH_DELIVERY_FILE_UNVERIFIED` / `ORCH_DELIVERY_FILE_UNISOLATED`）。

入口映射（`entry.input_mapping`）同理：表单未填的可选字段被跳过，必填由路线 `input_schema` 的 `required` 裁决；需要默认值的字段用映射的 `default` 变换声明。

保存成功**只证明静态结构合法**，不能替代整条路线的运行证据（见 `stages/S4-验证与修正.md`）。

### 8.2 静态接缝检查

保存并反读编排后，完成静态接缝检查：入口、节点依赖、扇出汇合、mapping、运行中交互、Delivery 和 Review 必须引用真实资产并满足当前契约；单节点路线也必须检查入口映射、唯一 Delivery 和 Review。mapping 检查含***文件覆盖***：要交付的文件路径字段必须都在 mapping 里——漏映射的文件不会登记为 Artifact（8.1 规则一），发现缺失即回改 mapping 再通过。该证据仍属于第一层 Preview/静态契约，不能证明路线已经执行。不得用一条或多条单 Workflow 轨迹拼接成路线证据，也不得自行创建图执行器或伪造 Runtime 身份。`emit_business_event` 在单 Workflow bubble 中仍必须取得服务端分配的验证 Business/Runtime 身份；缺失时该 Workflow 的 bubble 裁决为 `platform_blocked`。正式运行时，带业务事件的单 Workflow 不能直接派发，必须通过单节点路线取得持久化 Business Runtime。FastAgent 真实内容、显式外部副作用、业务事件真实发布和跨路线跳转统一留到第四层端到端全真运行验证；业务应用对事件的消费在 app_creator 线验收，不属于本包证据。

路线级 Bubble 的执行与证据纪律见 S4-验证与修正。

### 8.3 面向界面的公开语义

已规划配套业务应用时，编排完成还要冻结一份**面向系统的公开语义**：每条路线的业务名称、适用条件、入口表单目的、最终用户可理解的里程碑、可能出现的最终用户交互、最终交付和到达标准。它们是 app_creator 线 A1 契约基线的事实输入，**不得**用 Workflow 名称、节点 ID 或工具步骤代替。

## 9. 信息归属与知识写作

### 9.1 信息归属

**同一条信息只写在一个地方。** 这是所有配置决策的根本依据。

| 信息 | 权威位置 |
|---|---|
| 单个工具的用途、参数、正式 Schema | 工具组（MCP 层工具描述） |
| 工具或 FastAgent 的搭配方式、调用顺序 | 工具集使用指南 |
| FastAgent 的自包含推理方法 | FastAgent 提示词 |
| 普通任务点的交互式执行方法 | 任务点提示词 |
| 单阶段稳定步骤与数据流 | Workflow 脚本与输入输出定义 |
| 单节点或多节点业务路线的入口、依赖、映射、中途交互、最终交付 | 业务路线编排 |
| 业务终点、候选路线、里程碑、选路条件、权限、前置检查、知识读取时机 | `apc_skill` |
| 长知识、模板、案例、字段字典、详细 SOP | 场景 Skill 文件 |
| 数据语义与查询规则 | 数据集使用指南 |
| 页面与公开交互契约 | 业务应用源码（app_creator 线制作，不属于场景包资产） |

常见放错层级的情况：

- 工具集使用指南里重复单个工具的描述（那是工具组的事）
- 场景 Skill 文件里写 FastAgent 的内部逻辑（那是 FastAgent 提示词的事）
- FastAgent 执行时要用的写作规范、规则库挂在场景 Skill 文件下（FastAgent 读不到，见 9.2 可见性边界；按执行者归属挂到对应 FastAgent 名下）
- 工具集使用指南里写业务 SOP（那是场景 Skill 文件的事）
- `apc_skill` 或工具集指南里重复已固化在编排里的依赖图（形成两份真相，见约束 9）
- 同一信息出现在两个地方（必有一个放错了）

反过来也**不要**为了消除重复，把运行时 Agent 每轮都必须知道的业务路由、关键前置检查、能力选择和加载时机从 `apc_skill` 里删掉。

### 9.2 文本字段与 Skill 文件的分工

| 资产 | 文本字段（始终注入） | Skill 文件（按需读取） |
|---|---|---|
| 场景包 | `apc_skill` | 场景 Skill 文件 |
| 工具集 | 使用指南 | 工具集 Skill 文件 |
| 普通任务点 | 提示词模板 | 任务点 Skill 文件 |
| FastAgent | 提示词内容 | FastAgent Skill 文件 |

区分标准：**Agent 每轮都需要知道的写文本字段，做某件具体事时才需要查的写 Skill 文件。**

文本字段适合决策规则、约束、路由逻辑。Skill 文件适合大段领域知识、脚本模板、案例、示例输出、详细 SOP。

每个上传的 Skill 文件**必须**被对应文本字段在明确阶段按名称索引，否则 Agent 只看到文件名、不知道何时该读。

**可见性边界（知识不随挂载关系流动）**：每类 Skill 文件只对它挂在名下的执行者可见——场景 Skill 文件由项目里的 SystemAgent 读取；FastAgent 运行在隔离会话中，能读到的只有**自己名下**的 FastAgent Skill 文件和所挂工具集的 Skill 文件；Workflow 脚本只读自己任务点目录（`ctx.skill_dir`）。***场景包挂再多行业知识，FastAgent 一篇也读不到；FastAgent 执行要用的知识必须挂到它自己名下***，并按上面的索引规则在其提示词中写明何时读哪篇。

### 9.3 Skill 颗粒度标准

**从理想态反推颗粒度。** 凡是希望减少的失败、绕行或沟通轮次，都**必须**有对应的可执行指导。

| 目标消除的瓶颈 | 至少要写到什么程度 | 主要归属 |
|---|---|---|
| 不知道先做什么 | 阶段目标、前置检查、能力选择、交付条件 | `apc_skill` |
| 不知道工具怎么搭配 | 先取得什么结果，再由什么能力消费 | 工具集使用指南 |
| 不知道参数怎么准备 | 必填结构、来源、约束、失败处理 | 工具集 / 场景 Skill / Workflow 定义 |
| 找不到能力 | 条件 → 加载哪个能力域或读哪个文件 | `apc_skill` |
| 缺领域知识 | 可执行规则、数据字典、案例 | 场景 Skill 文件 |
| 交付结果不稳定 | 输出模块、质量标准、验收证据 | `apc_skill` 加对应执行资产 |

**不达标的写法**（缺前置步骤、缺判断条件、缺产出定义）：

- "创建创意，配置品牌组件、标题组件"——没说前置步骤和参数结构
- "使用素材处理工具进行裁剪"——没说用哪个工具、什么条件下用
- "输出结构化投放方案"——没定义方案必须包含哪些模块

**达标的写法**：

- "创建创意前：先取得模板列表，再查组件依赖，最后按模板要求准备素材"
- "素材处理判断：尺寸不对走缩放；格式不对走转换；需要生成图走生图再入库"
- "投放方案必须包含：推广目标、日预算、定向策略（地域加年龄加兴趣）、创意方向、投放时段"

**禁止**"完善流程""调用相关工具""输出高质量报告"这类不可执行的空话。**必须**补齐触发条件、输入来源、关键判断、期望产出和失败处置。

### 9.4 apc_skill 必须包含什么

`apc_skill` 是场景包最高优先级的知识注入，写好它是本项工作的核心产出。至少覆盖：

1. **场景问题与业务终点**：解决什么问题、适用条件是什么
2. **里程碑**：分几个阶段、每阶段目标和最终用户可见产出
3. **候选路线与选路节点**：不同目标或前置状态对应哪条路径、在哪里判断走哪条
4. **必需输入、预期交付、验收标准**
5. **权限边界**：哪些 Agent 可以自主判断、哪些必须最终用户决定、哪些属于高风险授权；这些边界由开发者在制作 Plan 中确认
6. **未被其他资产固化的关键业务规则、前置检查、能力选择**
7. **Skill 文件索引**：在哪个阶段按名称读取哪个文件

不应包含：具体实现细节（选择器、路径、接口参数格式、代码片段），以及约束 9 列出的禁写内容。

### 9.5 工具集使用指南必须包含什么

只写**工具之间的关系**：适用条件、输入怎么衔接、结果怎么审视、失败怎么处理。单个工具的说明留在工具组。

已经由 Workflow 脚本固化的调用顺序**不要**在这里再写一份。这里只说明"该 Workflow 是这条稳定流程的首选入口"，以及底层工具或 FastAgent 各自可独立处理的情况。

多个工具或 FastAgent 需要配合时**必须**写搭配模式。工具彼此独立、且不含 FastAgent 时可以为空，不算缺陷。

## 10. 场景包草稿组装与联动校验

### 10.1 场景包与 Workflow 工具

| 工具 | 用途 |
|---|---|
| `scene_package_manage` | 场景包 `create` / `get` / `update` / `online`，以及业务路线级 `bubble`。`create` 默认克隆官方基础场景包并返回未上线草稿；`get` 不需要 `task_id`；`bubble` 对已保存路线执行制作期整图演练，默认返回精简证据，仅在失败排障时用 `evidence_level="full"` 读取完整轨迹；它不代替单 Workflow Bubble 或端到端全真运行。长 `apc_skill` 或完整编排 JSON 可在实时 Schema 支持时分别通过 `apc_skill_url`、`workflow_orchestration_url` 提交 |
| `workflow_tpe_manage` | Workflow 的 `preview` / `create` / `update` / `attach` / `online` / `bubble`。外部 Agent 可按变更范围选择内联 `script`、完整 `script_url` 或更新时的 `script_patch`；内部 Max Agent 还可在实时 Schema 支持时使用 `script_file` |
| `update_scenario_package_logo` | 设置场景包 Logo。**必须**先用 `file_to_url` 声明 Logo 用途上传图片，拿到文件引用后再调用本工具 |
| `scene_package_ui_bundle` | 存量附属界面的维护（下载官方模板、上传定制源码、部署、查状态）；新业务应用一律走 app_creator 线，不使用本工具 |

前置依赖：`workflow_tpe_manage(create)` 要求**场景包草稿已存在、且依赖工具集已通过上线检查**。

场景包只能直接挂载工具集、任务点（含 Workflow）、长期数据集和固定版本数据集模板。工具组和 FastAgent **必须**先组进工具集，再把工具集关联到场景包。

单节点或多节点业务路线都通过场景包的编排字段**整体写入**，采用整体替换语义；**禁止**把它复制进 `apc_skill`（约束 9）。

### 10.2 场景包草稿组装

调 `scene_package_manage(create)` 建离线草稿。当前 `create` 默认克隆官方基础场景包，**必须**立即反读继承到的能力、关系和告警，只改真正需要改的部分。

写入较长的 `apc_skill` 时，可以按 3.3 在实时 Schema 支持后使用 `apc_skill_url`；平台解析后保存的仍是 `apc_skill` 正文。反读时按 9.4 检查正文完整性、颗粒度和禁写内容，不以调用成功或 URL 可访问作为验收。

保存场景包标识，后续修复**更新同一草稿**，**禁止**新建平行资产来绕过错误。

该草稿此时是后续 Workflow 的真实归属容器，不代表 Workflow、最终关联或业务路线已完成。提案包含 Workflow 时，创建并反读草稿后进入第 5 节，在同一草稿上创建、挂载和验收 Workflow，再写入最终关联与业务路线编排。

场景 Skill 文件按 3.3 的两步链路处理：先用 `file_to_url` 声明 Skill 文件用途取得引用，再用 `scene_package_manage(update)` 绑定。**默认合并**会保留既有文件（例如官方包继承来的调度策略文件），整体替换会**覆盖整个目录**——除非确认要清空，否则用合并。

依赖资产的 Skill 文件同理：创建时可以直接带文件引用，已经创建完的用 `upload_skill_files` 补挂——注意它的缺省是整体替换，补挂时显式传 `skill_files_mode="merge"`（见 3.3）。

开发者提供了 Logo 图片时，先用 `file_to_url` 声明 Logo 用途上传，再用返回的文件引用调 `update_scenario_package_logo`。**禁止**用修改文本字段的方式直接写入图标地址，**禁止**把临时上传地址当作 Logo 保存。开发者没提供图片时不调用，保持默认图标。

### 10.3 创建后联动校验

每步完成后检查联动关系：任务点关联变动后检查工具集是否同步；资产被替换后检查 `apc_skill` 里的引用是否失效；工具集成员变化后检查使用指南是否还准确。

此时**不要**向开发者宣称场景包可以直接使用——还没验收。

## 11. 出口条件

以下全部满足后，按路由器 4.1 进入 S4：

- 全部资产 Preview 通过；含 Workflow 时，每条完成单条 bubble 与语义验收（5.3 第 8 步）；
- 执行结构表无 `pending` 条目（5.4 同步与增量重挑战已完成）；
- 关键 FastAgent 的样例选择流程已完成（4.2）；
- 需要编排的路线已保存、反读并通过静态接缝检查（8.2）。

以上全部满足后，按路由器 6.1 落一条 `stage_exit` 账，再进入下一阶段。
