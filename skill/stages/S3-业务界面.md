# S3 业务界面

从预设计到部署验收。本阶段只在开发者已在总体方案 Plan 中选择制作业务界面时执行（约束 8）。

## 1. 进入前提与选择门

业务界面的选择规则、交付门与 `platform_blocked` 纪律见路由器约束 8，进入本阶段前重读一遍。

预设计（第 2 节）在 S1 方案确认后、Workflow 脚本动笔前完成。

### 1.1 实现阶段入口

本节只在开发者已明确选择制作业务界面时执行。业务界面预设计和官方脚手架首次阅读已在第 2 节完成，本节只处理最终契约冻结与工程实现，不重新从页面创意开始。进入本节前必须同时满足：场景包包含 Workflow；受影响 Workflow 已完成 Preview、必要的工具取样、单条 bubble 和语义验收；顶层编排已保存反读并完成静态接缝检查；发布范围内每条业务路线的路线级 Bubble 已通过；`ui_predesign_brief` 已按真实事件、Schema 和编排更新；预设计阶段的脚手架已安全解压、必读文件已完整阅读且 `template_identity` 已记录。

任一条件不成立时回到对应阶段处理。不得用单条轨迹拼接成整图证据；业务事件、宿主运行契约、官方模板、部署或绑定能力不足以完成开发者已选择的业务界面时，先按约束 8 读取并复用已有能力修复同一份产物；确认仍不可完成后才记录 `platform_blocked`。该状态未解除且总体 Plan 未移除业务界面时，不得通过提前编码绕过，也不得上线场景包或结单。

## 2. 业务界面预设计

总体方案 Plan 提案包含一条或多条 Workflow 时，已应按约束 8 向开发者说明业务界面可承载专属输入、业务阶段状态、运行中交互、结果与交付物，并在同一份 Plan 中确认本次是否制作。进入本节时直接读取已确认选择，**不得再次询问**。

开发者选择制作时，**必须**在编写脚本和创建 Workflow 资产前完成以下准备：

1. 完整读取 [业务界面设计方法论](../references/业务界面设计方法论.md)；
2. 调用 `scene_package_ui_bundle(action="download_template", task_id=<task_id>)` 下载当前官方脚手架，核验响应、字节数、归档格式、安全路径和唯一模板根目录，并记录不含临时下载地址的 `template_identity`；
3. 完整阅读模板根目录的 `AGENTS.md`、`README.md`、`schema/README.md` 和 `src/sdk/docs/README.md`；涉及业务事件或最终交付时，继续读取模板当前要求的 Business、Delivery、类型定义与参考页面文件；
4. 基于真实脚手架能力，把最终用户旅程、页面地图、模块 include/exclude、状态—行动、事件响应、视觉方向和边界样例整理成 `ui_predesign_brief` 与预设计 Plan，由开发者确认页面范围和关键体验。

本阶段只建立模板能力认知与界面预设计，**不修改模板业务代码、不开始编码、不冻结尚未稳定的运行标识**。开发者选择不制作时，记录决定并直接进入后续资产制作，不下载脚手架、不生成占位设计、不把缺少界面列为验收问题。

预设计至少包含：

- 最终用户从选择路线、填写入口信息、等待执行、补充中途表单到审阅交付的完整旅程；
- 页面地图、模块决策账本，以及每个模块采用、合并、延后或不采用的理由；
- 状态—行动矩阵，明确每种业务状态下的可见信息、允许动作和恢复方式；
- 业务节点—事件—界面响应表，写清稳定事件名与版本、Payload 字段、归约后视图状态、回放/补拉反馈和快照权威边界，用于反向约束 Workflow 必须事件和建议事件；
- 关键交互、边界样例、视觉方向和中文文案承诺。

JSON Schema 与 SDK 能力只是设计事实，不能直接推导页面模块；Agent 的模块推荐也不能代替开发者确认。预设计可以随 Workflow 和编排事实修订，但不得提前写死内部 ID、Workspace 路径、工具步骤或未发布 Schema。仅当开发者已选择制作业务界面时，`ui_predesign_brief` 未完成或关键模块仍未确认才阻止开始 Workflow 脚本制作。

## 3. 交付页的呈现原则

交付页应**直接消费 `output` 业务字段**做贴合业务的呈现——脚本按 `output_schema` 返回的全部业务字段都会随交付到达界面，界面按已冻结契约渲染对比、列表、结构化内容等业务形态；`output.display` 是平台标准的**兜底展示出口**（未制作定制界面的包、聊天内呈现使用）。为支撑界面消费，`output_schema` 的字段描述**必须**含面向呈现的语义（该字段是什么、每项含义），不能只写给下游脚本看。什么值得投影、何时渲染的判断依据见 [运行模型与渲染语义](../references/运行模型与渲染语义.md)；页面结构、守卫与渲染的工程细则以脚手架仓当前文档为准。

## 4. 最终契约冻结

全部受影响 Workflow 已完成前三层验证，顶层编排已保存反读并完成静态接缝检查，且发布范围内每条业务路线的路线级 Bubble 已通过后，才进入业务界面实现阶段。此时把 `ui_predesign_brief` 与真实资产合并为最终 `ui_design_brief`，补齐场景—界面映射、视觉取舍、边界样例和最终页面状态，并冻结场景包、Workflow、业务事件、顶层编排、表单和宿主运行契约。路线级 Bubble 未通过或当前环境无法提供该证据时，业务界面记录为 `platform_blocked`，不得进入编码。

在首次编码前和每次上传/部署前，均执行契约变更检查：

1. 反读当前 TPE 的输入/输出 Schema、业务事件契约、Workflow 脚本版本和场景包顶层编排契约；
2. 与业务界面的 `schema/orchestrations/`、`schema/forms/`、事件归约表、控件与结果渲染逻辑、`ui_contract_snapshot` 逐项比对；
3. 根据差异判定路线、入口、运行中交互、里程碑、结果和交付所受影响；
4. 对受影响的界面契约和实现完成更新，并重新执行相关验收。

**契约门**：无法证明新旧契约兼容时，停止业务界面发布。编排脚本仅作为制作期变更检查的事实依据，不得写入前端源码、由浏览器执行或向最终用户展示。

## 5. 官方模板复核与工程实现

### 5.1 官方模板复核与工程初始化

工程实现使用第 2 节已下载并阅读的官方模板，但在首次修改业务代码前必须复核模板是否仍为当前版本：

1. 重新取得当前官方模板信息，与预设计阶段的 `template_identity` 比较；
2. 官方返回的版本或校验值可比且确认未变时，继续使用已验证的唯一模板根目录；
3. 模板已变更，或响应没有足以证明未变的版本/校验信息时，重新下载当前模板，重做字节数、归档、安全解压和唯一根目录检查，重读变更文档与固定 SDK 源码，更新 `template_identity`、`ui_predesign_brief` 和 `ui_design_brief`；
4. 只有模板复核、最终契约冻结和开发者已确认的设计范围同时成立后，才在模板声明的业务代码范围内开始编码。保持 SDK、启动入口、桥接协议、错误边界和模板保留件不变。

不得从空目录、通用脚手架、仓库克隆或历史源码副本初始化；预设计阶段不得修改脚手架业务代码。业务界面仅消费宿主公开的运行契约；任务点标识、工具清单、提示词、脚本、依赖图和 Agent 控制动作均不属于前端契约。

### 5.2 实现、检查与打包

按已冻结的设计与运行契约，完成业务控件、文件上传、提交与受理、等待、权限、错误恢复、结果展示和回落路径。提交报文按用户实际填写组织：未填写的可选字段直接省略即可——入口映射会跳过缺失字段，必填由路线 `input_schema` 的 `required` 裁决（见 S2-8.1）。***同时消费入口提交的拒绝报文***：`status="rejected"` 时呈现 `field_errors` 并允许修正——被拒却仍显示提交成功，是最难排查的一类假象。业务阶段状态在共享协调层只建立一次 `onBusinessEvent` 订阅，三类批次使用同一纯归约器；订阅后对当前 Runtime 读取一次快照，由 SDK 负责排序、去重、缺口补拉和回放。禁止使用定时器、事件回调查询或 `getBusinessEvents` 轮询状态；Runtime 终态、表单握手和 Delivery Review 仍是各自领域的权威事实。

最终交付必须按 [业务界面设计方法论](../references/业务界面设计方法论.md) 的固定契约处理：`runtime.delivery_ready` 由 Runtime 自动发布，`delivery.review` 通过既有 Business Call 三次握手完成；业务代码使用当前模板导出的 `isRuntimeDeliveryReadyEvent`、`isDeliveryReviewCall` 及对应常量识别两条通道，不手写协议判断或修改固定 SDK。事件和 Call 未通过守卫时分别降级为普通业务提示和普通 Call，不得当作交付渲染。`PublicDelivery.output.display` 按 `schema_version/headline/facts/notices/sections` 的标准结构渲染主标题、事实、提醒和正文；文件只把 `workspace_path` 交给 `sdk.file.*`，`output_paths` 仅作结果字段归属标签。`delivery.*` 是平台保留表单命名空间，不另造协议或静态表单 Schema；`call.formId` 与 `call.arguments` 同级，不存在额外 `interaction` 包装层。当前模板缺少这些 Delivery 守卫、Business `onCall/pending/reply` 或文件能力时，记录具体缺口并裁决为 `platform_blocked`，不得在业务代码中补造兼容层。

（呈现补充，不改变上段的守卫与文件纪律：上段对 `output.display` 的四区块渲染要求适用于**兜底出口**；定制界面按第 3 节直接消费 `output` 业务字段做贴业务呈现，display 的渲染规范以脚手架仓当前文档为准。）

正式打包前：

1. 移除演示页面、演示路由、演示契约和占位文案；
2. 开发过程执行模板当前要求的 `npm run check`，交付前执行 `npm run check:release`；除非当前模板明确改变流程，不在本地执行独立 build 或发布；
3. 验证主路径、权限变化、空态、错误、刷新恢复和契约漂移等关键边界；
4. 打包源码，校验归档清单、字节数和摘要。

macOS 环境中，解压后必须清理 `._*`、`.DS_Store` 和 `__MACOSX`；打包时使用 `COPYFILE_DISABLE=1` 并重新核对归档清单。AppleDouble 旁车文件含二进制内容，测试框架可能将其误识别为源码或测试文件并触发 `[PARSE_ERROR]`。出现此类解析错误时，先检查归档元数据残留，不得因此修改模板固定层或跳过测试。

## 6. 部署与验收

**部署顺序**：业务界面部署是草稿行上的**最后一步内容动作**。正确顺序：先完成编排修改（`publish_mode=staged`）→ 在**同一草稿行**上部署业务界面 → 最后上线该草稿。部署完成后再修改编排会派生新草稿行，源码包随行继承（`has_ui: true`），但**部署激活地址不继承**（`entry_url` 为空字符串），界面地址丢失，必须在新草稿上重新部署。上线前反读确认 `entry_url` 非空。

完成打包后，依次执行源码包上传、部署、终态查询和绑定结果反读。部署达到成功终态后，按 [业务界面验收检查清单](../checklists/业务界面验收检查清单.md) 执行验收。

**交付门**：

- 运行契约发生变化时，重新执行契约冻结、受影响回归和部署验收；
- 宿主能力不支持目标 Workflow 运行契约时，先按约束 8 复核并重试已有能力；确认仍不支持后记录业务界面平台阻断，并停止业务界面发布、场景包上线和工单结单。只有开发者明确修改总体 Plan、移除业务界面交付后，才按新范围继续；
- 未取得部署成功终态和绑定反读证据时，不得宣称业务界面已交付。

## 7. 出口条件

以下全部满足后，按路由器 4.1 进入 S4：

- 部署达到成功终态，绑定结果反读证据在案；
- `npm run check:release` 通过；
- 前端校验项已转入结果检查表（状态 `pending`，S4 闭合）。

以上全部满足后，按路由器 6.1 落一条 `stage_exit` 账，再进入下一阶段。
