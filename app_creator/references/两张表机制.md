# 两张表机制

制作过程的质量记账：把每一条设计承诺和验证义务落成**可挑战、可闭合、可继承**的条目，用内容指纹绑定状态。它解决两个真实问题——

- **不漏**：页面、接口、模板表、测试用例逐条列出，没有"整体感觉没问题"这种裁决；
- **不重**：`passed`/`waived` 的条目不再碰，只处理 `pending`——修改一处只回退受影响条目，成本随改动范围走，不随应用规模走。

| 表 | 回答的问题 | 建立 | 推进 | 闭合 |
|---|---|---|---|---|
| **应用结构表** | 设计承诺站不站得住 | A1 初始化（按设计文档逐组落条目） | A3 实现中随改动回退/重挑战 | 全组 `challenged=true` 才能交开发者确认 |
| **结果检查表** | 实现有没有被真实验证 | A1 转入正反例种子 | A3 补入前端/后端校验项（`pending`） | A4 用预部署环境的真实数据逐条闭合 |

## 1. 双副本

| 副本 | 位置 | 职责 |
|---|---|---|
| 本地工作副本 | `app-{应用标识}/应用结构表.md`、`app-{应用标识}/结果检查表.md` | 每轮直接读它定位进度；修改先落这里 |
| 工单权威副本 | `task_manager(insert)` 结构化条目，`metadata.evidence_type` 分别为 `app_structure_snapshot` / `result_checklist_snapshot` | 跨轮次续作的唯一事实源；本地变更后**必须**回写快照 |

续作时从工单**最新快照**重建本地文件；***禁止沿用残留的本地文件不对账***——本地文件可能停在任何一轮的中间状态。

## 2. 应用结构表

按三类对象分组，**每个页面、每个后端接口、每张模板表各一组**。一个条目 = 一条可以被单独挑战的设计承诺：

```json
{
  "group": "page:数据管理",
  "items": [
    {
      "id": "page-mgmt-editable",
      "content": {
        "what": "会员表编辑页只对 editable:user 列开放编辑，agent/system 列只读展示且有视觉区分",
        "checks": ["逐列声明来自 describe 反读，不是前端硬编码", "只读列在界面上能被用户识别"]
      },
      "hash": "<内容指纹>",
      "status": "pending",
      "evidence": null,
      "waive_reason": null
    }
  ],
  "challenged": false
}
```

`group` 命名：`page:看板`、`api:POST /members`、`table:members`。

**挑战判据**——对每组条目逐条自问，答不上来就是设计没做完，回 A1 补：

- **页面组**：职责单一且归入四类原型（看板 / 数据管理 / 业务发起 / 项目页）之一；每块数据说得出从哪个接口读；每个动作说得出发往哪里；可编辑性区分在设计中有体现；
- **接口组**：信封结构、幂等性、写权校验、分页与超时预算逐项可答；写接口说得出来源标记落在哪列；
- **模板表组**：数据设计五问（存什么 / 逐列可编辑性 / 审计 / 冲突规则 / 回流语义）全部有答案；逐列 COMMENT 声明齐备。

**`challenged`（组级布尔）**：全组条目 `passed` 或 `waived` 后置 `true`；任一条目回退 `pending` 时同步回退 `false`。全部组 `challenged=true` 才算"结构表已立住"，才能把设计交开发者确认。

## 3. 结果检查表

平铺条目（不分组），三类 `kind`，各有明确来源：

```json
{
  "id": "tc-edit-not-overwritten",
  "kind": "test_case",
  "content": {
    "input": "用户手改会员备注列后，重跑一次生产回流",
    "expected": "备注列保持用户版本，未被 generated 数据覆盖",
    "polarity": "negative"
  },
  "hash": "<内容指纹>",
  "status": "pending",
  "evidence": null,
  "waive_reason": null
}
```

| kind | 来源 | 验证什么 |
|---|---|---|
| `test_case` | A1 的典型用户操作正例与数据边界反例（含"用户编辑不被生产覆盖"这类共治用例） | 业务行为符合设计 |
| `frontend_check` | A3 的 Playwright 验收门 | 页面在真实浏览器里按契约工作 |
| `backend_check` | A3 的接口测试（含信封契约自检） | 接口按硬约束工作 |

**闭合纪律**：置 `passed` 必须以**预部署环境的真实数据**为据（A4）；mock 通过只能作为过程证据追加在条目上，状态保持 `pending`。`evidence` 记录判定依据（测试运行标识、核对记录的工单条目位置），空口的 `passed` 视为未验证。

## 4. 状态机

```text
              （新建 / 关联内容变化 → hash 变化）
                        │
                        ▼
      ┌────────────  pending  ────────────┐
      │ 挑战或校验通过                      │ 确认不适用 / 开发者接受偏差
      ▼                                   ▼
    passed                             waived（必须带 waive_reason）
      │                                   │
      └──── 关联内容再次变化 → 回退 pending ──┘
```

## 5. 指纹规则

- 指纹对条目 `content` 与其**关联源**（代码片段、schema 定义、设计文档段落）的规范化文本取摘要；时间戳、空白等无关变动不计入；
- 修改关联内容后必须重算指纹：变化即回退 `pending`（含组级 `challenged` 同步回退）；***禁止带着过期的 `passed` 推进***；
- 只处理 `pending` 的前提是指纹诚实——跳过重算等于把回归漏洞记成通过。

## 6. 跨工单继承

修订类任务（改一个已发布的应用）从上一工单的**最新快照**继承全部条目：指纹对新版本重算，受影响条目自动回退 `pending`，未受影响的 `passed`/`waived` 原样保留。这是"修订不坏旧例"的回归机制——旧承诺不因新工单而重新全量验证，也不因没人想起而静默失守。
