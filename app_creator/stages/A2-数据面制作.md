# A2 数据面制作

把 A1 确认的模板草案落成真实的**业务应用数据集模板**，并挂到发布单位。工具是 `dataset_template_workspace`（模板制作工作集），除 `inspect` 外的动作都要求 `write` 工单。

## 1. 进入前提

- A1 数据设计五问逐表回答完毕，模板草案（表 / 列 / 类型 / 逐列可编辑性声明 / 审计字段）经开发者确认；
- 有 `write` 工单；
- 发布单位 `business_ui` 可以尚未创建——模板先抽出，A4 创建 business_ui 时再挂载。

## 2. 工作集是什么

开发者自己造模板的沙盒：`open` 给你一个**独立 PostgreSQL schema** 和 **2 小时有效的写连接串**，可以用 ORM/psql 建表、灌样例、跑查询；也可以不碰连接串，用 `create_table` 声明表。它**不是通用数据集**：不占配额、不出现在数据集列表、不给最终用户用。`extract` 从工作集的真实结构抽成**固定版本的模板**——只抽结构（表、列、类型、主键、注释、关系），不带样例数据、视图、索引；用户点开应用时系统照模板给每个用户建一套自己的库。

## 3. 制作步骤

1. **开工作集**：`open(name=<模板名>, description)`，记下 `data_uid`。返回的连接串是凭据——***不进工单、不进聊天、不进代码***；过期用 `connect(data_uid)` 重签，已知目标应用时传 `business_ui_id` 让平台校验绑定，防止两个应用的库串用。
2. **建表**（两种方式可混用）：
   - **声明式（推荐）**：`create_table(table_name, target_columns=[...])`。每表**至少一列 `primary_key=true`**（生成型代理主键用 `bigserial`）；类型写 PG 精确类型（`character varying(120)` / `numeric(10,2)` / `timestamptz` / `jsonb`）；***每列 `comment` 必填，且以 `[editable:user|agent|system] ` 开头再接业务说明***（约束 9）——它会写成 PG COMMENT 并随模板 copy，是应用后端与 `dscli_business_dataset` FA 读到写权声明的**唯一渠道**，漏写 = 该列被按最保守的 user 处理、生产写不进去；
   - **连接式**：用写连接 ORM/psql 建表、灌**最小真实样例**、跑 A1 设计的典型查询（看板聚合、编辑读写，`statement_timeout` 10s 内）——样例只用于验证，不进模板。
   - **每张有写入的表带审计四件套 + 行版本**：`created_at` / `updated_at` / `updated_by`（`user|agent|system`，声明 `system`）/ `last_run_id`，加 `row_version` 做行级乐观锁——用户在编辑页改用户列、生产同时重写产出列时，靠它让后写方重读重试，而不是字段级仲裁。
3. **声明关系**：`set_relations(relations=[{source_table, source_column, target_table, target_column, relation_type}])`，整体替换、按表名。
4. **反读**：`inspect(data_uid)` 读回真实结构，逐表逐列核对类型、主键、**每列 comment 的声明可见**；与 A1 草案不一致时改到一致（`drop_table` 重建或经连接 ALTER），不带着偏差往下走。
5. **抽模板**：`extract(data_uid, template_name, template_description)`。首次不传 `template_id` 即新建模板；修订已有模板时传 `template_id` 给它**出新版本**（整数版本号递增；缺省沿用本工作集上次抽出的模板）。记录返回的模板 id 与版本号——A4 挂载、A5 交付报告都要用。
6. **挂载**（A4 创建 business_ui 后）：`business_ui_manage(update, business_ui_id, dataset_template_id, dataset_template_version)`，版本钉整数号、***禁止 follow latest***。
7. **收工**：`close(data_uid)` 删除工作集——模板已抽出，工作集没有保留价值。

## 4. 定稿门与变更纪律

- **定稿确认**：把 `inspect` 结果翻成业务语言交开发者确认——每张表存什么、哪些列用户能改、哪些列生产写、审计怎么查。确认后才 `extract`；
- **模板版本一旦被上线的 business_ui 钉住就不可变**：改结构 = 工作集里改 → `extract` 出新版本 → business_ui 出草稿改挂载版本 → 重新 deploy / finalize（A5 修订节）。只增不改的原则同样约束模板演进：新增列 / 新增表优先，改类型或删列要评估已 copy 出去的用户库怎么迁——这是产品决策，进拍板；
- 应用代码禁 `CREATE / ALTER TABLE`（约束 4），结构变更只走本阶段。

## 5. 一期红线（仍然成立）

- **一个业务应用只绑这一个数据集**：写权限是项目级放开的，多绑一个长期数据集就多放开一个写面；
- 模板表 owner 是否已收成服务账号（数据库级硬护栏）以平台当前实现为准；在此之前"模板结构只增不改"靠 FA 提示词与本阶段纪律共同守住。

## 6. 出口条件

- 模板已 `extract`，模板 id 与版本记入工单；`inspect` 反读显示全部列声明与审计列齐备；
- A1 设计的典型查询在工作集内验证通过；
- 开发者确认定稿；工作集已 `close`；
- 应用结构表"模板表"分组条目重挑战通过。

以上全部满足后，落一条 `stage_exit` 账，进入 A3。
