# 业务文案

给页面、入口、按钮、表单、记录起名字和写提示时读；修订或接续时只核受影响的场景。

## 先定名

从 PRD 已确认的需求、真实的路线、表单、记录和产物里取名字，写成完整短语。

- 一次记录代表的整体业务对象，和每个入口实际做的动作分别命名：只有上传就写上传，确实发起筛选才写开始筛选；包含上传、清洗、筛选的整体事项按整体对象命名，不笼统叫「筛选」。
- 不用「任务 / 提交 / 查看」这类空词，也不靠删掉「项目」二字来冒充业务化。

## 接到实际页面

- 当前模板 `frontend/README.md`「业务文案」是配置字段、覆盖优先级和接线的唯一工程来源；按它填写应用文案、入口动作和各表单覆盖，保留开发者已有的显式定制。
- 模板还不支持时，按 `agenticapp-tool-workspace`「核脚手架版本」核版本和能力，不自造字段、不改版本串、不假定下载过就已升级。
- 固定层不读取业务配置，应用外壳要主动传入。

## 上下文一致、不虚构

- 同一记录在历史、消息、详情与返回中都认得出；真实名称优先，缺名时不用内部标识代替。
- 补充按真实表单命名，结果按实际产物命名；没有产物就不放报告入口。
- 通用的「刷新 / 返回首页 / 正在提交 / 已受理」意思清楚时保留，不改它们的状态含义。

## 逐场景核对

沿阶段文档 G5 的「已确认业务含义—界面文案—实际页面/动作」对应，逐个场景看实际文案和动作：

- 上传、发起、补充分别核；受理和完成分别核；有无产物分别核。
- 上传不写成已发起，提交或受理不写成完成，没定义的产物不出现。
- 因为和已有记录冲突或重复被拒（例如预约撞期）时，提示写出冲突的是哪一条（名称、时间段），并给能直接去改的入口；保存失败的提示用业务话，不出现数据库列名或请求编号。
- 配置写了没接线、仍是无业务含义的默认词，都改好再收口。模板兜底能跑不等于业务文案通过；静态词检查、构建和模板登记只证明各自那件事，不证明业务含义对。
- 修订或接续时只核受影响的场景，已有的正确配置和定制保留，不用默认词覆盖，也不从零重做需求确认。
