# 业务页面

写看板、入口表单、项目页、交付审阅、表单与文件时读。这里写旧应用（项目句柄）的接法；新 SDK 应用以执行为单位，差别见 SKILL「新 SDK 应用」，写法以模板 `frontend/src/sdk/docs/README.md` 为准。

## 每页都要的

- **几种状态都做出来**：第一次没有数据、资料不全（还缺什么、去哪补）、处理中、失败（原因和下一步）、完成。写页面前先列这一页有哪些状态和各自显示什么，不等开发者逐个提醒。
- **同一个判断只算一处**：「要不要关注」「是什么状态」这类判断由后端或路线算好存下来，各页面读同一个结果，不在不同页面各算一遍。已经存过的资料直接带出，不让使用者重填。

## 历史运行入口

使用者要能找回以前每次发起的进度与结果。默认用首页 `HomeBlock` 的「最近记录」（分页可翻到全部，`recordsTitle` 按业务对象命名）；要按对象管理时用 `useOwnedProjects` 自写业务化视图（如「诊断记录」）。不放通用「项目列表」页，导航与文案不出现「项目」。打开、翻页、手动刷新时拉 `sdk.projects.list`，不轮询，`onStatusChange` 按 `projectId` 就地更新；空态引导去发起第一次业务。

## 看板

数据只来自后端统计接口；每个数值能点开看口径；空数据有引导态；跟随 `sdk.theme` 亮暗。

## 业务发起（入口表单）

- 必经 `useProjectDraft(draftKey)`，`restoring` 期间禁提交；按 `getForms(formId)` 渲染，没有预填。
- 入口只带业务键和使用者这次填的值。业务键由页面提交时带入，不让使用者填；库里已有的信息由路线按业务键读库（见 `agenticapp-tool-data-template`「设计表」的入口字段），不由后端拼进 `submit_data`。
- 文件字段经 `project.upload`，全部上传完成才允许提交。
- `accepted` 导航到项目页，`rejected` 原窗重填，`failed` 展示错误、不自动重试。
- 复用已有项目的下拉框不列还有表单没答完的项目；新业务一律新建项目。否则使用者在那里提交的新入口表单会被当成答复（平台报 `WORKFLOW_FORM_PENDING` / `ORCH_INTERACTION_PENDING`，不是故障：让使用者回该项目答完）。

## 项目页与交付审阅

- 阶段进度按业务事件归约，不轮询；服务端调起表单时导航到可恢复的应答状态。
- 交付审阅按 `display` 的 `headline / facts / notices / sections` 渲染；只在有活动调用时渲染动作按钮、只提交 `action_key`；`agent_gate` 只读。已提交表单以 key-value 展示，不露裸 JSON 和裸路径。
- **审阅只提交所选动作**：`reply(callMsgId, { action_key })`，业务数据（如确认后的商家信息）不放进审阅应答。缺 `action_key` 或夹带字段时 SDK 本地判 `rejected`，`npm --prefix frontend run check` 直接失败。要让使用者在审阅前后改数据，在路线里设计中途表单，或声明带表单的审阅动作（`start_orchestration`）。
- 审阅与所有表单的 `rejected` 都要把 `data.field_errors` 的原因展示给使用者，不能当成已提交。服务端回的 `ORCH_DELIVERY_ACTION_INVALID` / `DELIVERY_REVIEW_REPLY_INVALID` 也是这个原因，项目会停在 waiting-input 等使用者重选，最长 2 小时。
- **应答到运行的过渡**：项目层 `useProject(projectId)` 与 `useProjectExecution(project)` 只建一次，应答页、进度页、审阅页共享；应答用 `execution.reply`，不绕过它自己调 `project.business.reply`；不在每个子路由或因 inbox 变化重建句柄（重新订阅会触发重放，把使用者拉回旧表单）。提交后立即显示「正在提交」，`accepted` 显示「已受理」，收到 `running` 立即切到执行中。

## 让宿主小喇叭能跳进来

- `goalfy-app.json` 的 `routes` 声明项目页、表单应答页与交付审阅页的路径模板。脚手架默认带：
  - `project: /projects/{project_id}`
  - `form: /projects/{project_id}/forms/{form_id}/calls/{call_msg_id}`
  - `delivery_review: /projects/{project_id}/runtimes/{workflow_runtime_id}/delivery`
- SDK 随握手交给宿主；使用者在宿主小喇叭点一条失败、待填表单或交付消息时，按它直接落到应用里对应的页面。
- 改了这些页面的路由要同步改声明；另有单独执行详情页的可加 `runtime`。占位符只有 `{project_id}` `{workflow_runtime_id}` `{business_id}` `{orchestration_id}` `{form_id}` `{call_msg_id}`。
- `npm --prefix frontend run check` 校验每条模板都对得上 `App.tsx` 注册的路由，对不上直接失败。没有对应页面的应用去掉那条声明，宿主会退到项目页或在自己的面板里展开消息详情。

## 给使用者看的都是人话

- 业务用中文名（`useOrchestrationNames` 按路线契约取 name），时间用本地时间（`formatDisplayTime` / `formatDisplayDateTime`），执行过程按「第 N 步 · 状态」合并（`taskpointSteps`），都在 `@/shared`。
- 界面上不显示路线 ID、项目 ID、`businessId` / `workflowRuntimeId` / `taskpointEventId` 等内部 ID，`Runtime` / `编排` / `TaskPoint` 这类术语，`PRJ-…` 任务标题和 `2026-09-29T03:31:50` 这样的原始时间串。`npm --prefix frontend run check` 对业务页面直接显示内部 ID 会给警告，要清零。

## 表单与文件

- 三类回显各归其位：草稿回显（`sdk.storage`）、驳回回显（`rejected` 返回的参数原窗重填）、已提交回显（`getRuntimeForms`）。
- 校验失败：顶部一条提示，全部无效项高亮，首个无效项滚入并聚焦；提交中禁用写入口。
- 文件值只能由上传产生；展示 URL 经 `getViewUrl` 现取现用；下载只在使用者点击时调用。应用级持久文件用 `sdk.file` 与 `shared/ApplicationFileField`，只存 `path`。
- 当前路由不写进 `sdk.storage`，业务代码不调 `sdk.notifyRoute` / `onHostNavigate`。

## 常见错误

| 错误 | 正确做法 |
|---|---|
| 上传没完成就能提交；下拉框列出挂着未答表单的项目，使用者在那里提交的新入口表单会被当成答复，平台报 `WORKFLOW_FORM_PENDING` / `ORCH_INTERACTION_PENDING` | 全部上传完才可提交；不列未答完的项目 |
| 页面直接显示路线 ID、`PRJ-…` 任务标题或原始时间串；直接显示内部 ID 时 `npm --prefix frontend run check` 报警告 | 用 `@/shared` 的中文名、本地时间和步骤合并 |
