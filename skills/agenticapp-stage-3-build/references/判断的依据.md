# 判断的依据

③ 偏离方案、遇到做不到或报错、要决定复用还是新建、核对功能是否做全时读。SKILL.md「这一段要做对的判断」只列判断什么，依据和判错的表现在这张表里。

| 判断什么 | 依据 | 判错的表现 |
|---|---|---|
| 结果和 ② 的预期差多少：自己能改的偏差，还是推进不下去 | 漏字段、格式不对、时间写错这类做法上的偏差自己改好再跑；差得多、不是你能改好的（报告要 49 分钟、说好 30 分钟）算推进不下去，这是方案取舍，回 ②，两份放在一起出选择题：按预期改做法（写代价）/ 接受现在的结果 | 悄悄改了方案不说；小问题也去问；悄悄改的到 ④ 对不上验收条目记「没通过」 |
| 要换用收费工具、换到更贵的一档，或资料要新发往外部服务 | 方案没写的花钱或对外动作都要先问：出选择题，写清多花多少、资料发给谁；他选了再做 | 换了工具或数据去向不说，到 ④、发布后他才发现 |
| 做的时候发现做不到 | 算推进不下去，回 ②，出选择题：换做法（写差别）/ 这次先不做；要的东西因此变了回 ① | 静默改设计继续做；到 ④ 同样记「没通过」 |
| 报错是应用自己的问题还是平台问题 | 先查当前工具 Skill 的「常见错误」；应用自己的脚本、页面、数据问题自己改，平台问题按入口「报错和平台问题」报 | 平台问题反复重试；自己的问题提成平台反馈 |
| 复用还是新建 | ① 的判定结论；自己的草稿续用，官方或他人的先 clone | 有现成的另建一份；重复注册同一个 MCP 会产生互相冲突的重复资产 |
| 方案里的功能是不是都做了 | ② 的施工单与验收条目，逐个功能对照 | 编辑入口没做、首页数字点不开，进度却写做好了；④ 验收没通过，又要改一轮 |
| 检查不过时守住检查 | `verify`、`doctor`、版本闸门不过就改源码或按 `agenticapp-tool-workspace` 升级脚手架 | 手工补版本清单、换打包方式绕过闸门；平台部署时还按上传包再校验版本清单 |
| 起始件清干净 | `agenticapp-tool-frontend` 的清起始件清单 | 无关待办、红点留到交付版；留下的占位让 `verify:release` 失败 |
