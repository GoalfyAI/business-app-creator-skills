# 读写应用库与反读自查

路线要读写智能应用自己的库（应用库，不是长期数据集）时读。用到施工单「存数据」里的表（客户、素材、历史记录），或结果要存下来给页面看、给下次用的路线，都是读写应用库的路线，脚本要真的读写应用库；只发事件、只做计算、不碰库的脚本不算做好。

谁建行、谁写哪一列，同一业务再做一次是更新还是新增，入口放哪些字段，按 `agenticapp-tool-data-template`「谁建行、谁写列」「入口字段放哪」先定好。

## 读写应用库的路线必须全部有

下面只列条目，做法和理由各在括号里那一处写。

1. 复制统一的 `db()`，所有应用库读写都经它（「统一的 `db()`」）。
2. 业务值经 `params`，SQL 是固定字符串（「SQL 怎么写」）。
3. 写库包在 `if not ctx.dry_run:` 里（「统一的 `db()`」）。
4. 写失败或行数不对返回 `blocked`「未入库」，只结束本节点，要停整条路线就抛错（「统一的 `db()`」）。
5. 上游 FA 非成功状态时脚本内不再往下做（[脚本骨架与失败出口.md](脚本骨架与失败出口.md)「失败出口怎么写」）。
6. 更新原记录用 `INSERT … ON CONFLICT (<业务键>) DO UPDATE`，业务键在模板里有唯一约束（`agenticapp-tool-data-template`「同一业务再做一次：更新还是新增」「建表时的列规则」）。
7. 审计列随写入更新（`agenticapp-tool-data-template`「谁建行、谁写列」）。
8. 路线只写 agent 列，FA 只读（「什么时候由谁读写」）。
9. 连接纪律（「SQL 怎么写」）。
10. `preload_toolset_ids` 含装了「query_business_app_dataset」的工具集（「统一的 `db()`」）。
11. 入口没有整包字段（「反读自查四项」第 4 项）。
12. 读不到按「没有数据」收口，读库不包 `dry_run`（「统一的 `db()`」）。

## 什么时候由谁读写

读写都走平台工具 `GOALFYAI_TOOL_query_business_app_dataset`：能写死的语句由脚本直接执行；要看情况决定查什么的，交给挂了这个工具的 FA 自己查。

| 时机 | 谁来做 |
|---|---|
| 发起时要用的上下文（当前这条记录、它的客户档案、门店信息） | 入口只放业务键和使用者这次才给的值；库里已有的由脚本按业务键用 `db()` 读，不由应用后端拼进发起报文 |
| 执行中取数，查什么事先能定 | 脚本用 `db()` 执行固定 SELECT，每条业务流至多读一次，读出来交给 FA 总结、判断是允许的（如按日期和班组取当天记录交给模型写日报），结果沿节点输出往下传 |
| 执行中取数，要看上一步结果再决定查什么 | 业务 FA 挂上这个工具自己查，只用 `mode="reader"`（见下面「要按情况查库的 FA」） |
| 收尾写库 | FA 产出要写的值，脚本用 `db(..., mode="writer")` 执行固定 SQL，只写 agent 列 |

## SQL 怎么写

- 要写入或用来筛选的业务值一律用 `:name` 占位符放进 `params`，SQL 本身是固定字符串：不用 f-string、`+`、`.format()` 把业务值放进 SQL，不自写 `sql_literal()`、`query_db()` 之类的转义或查询函数。JSON 用 `:x::jsonb`，一批行用 `jsonb_to_recordset(:rows::jsonb)`。
- 写之前先用这个工具的 `action="tables"` / `"inspect"` 查实表列。
- `INSERT … ON CONFLICT` 的冲突目标要求见 `agenticapp-tool-data-template`「建表时的列规则」；审计列写法（含 `DO UPDATE`）见 `agenticapp-tool-data-template`「谁建行、谁写列」。
- 连接纪律：写连接经数据集代理，`BEGIN / COMMIT / ROLLBACK`、`SET ROLE`、`SET search_path` 都会被拒；要原子性就压进一条 SQL（CTE、`INSERT ... ON CONFLICT`、`UPDATE ... FROM`）。
- FA 只用 `mode="reader"` 查；写库一律由脚本按 FA 的输出执行固定 SQL。

## 统一的 `db()`

脚本里的读写统一用下面这个 `db()`，**复制进脚本**再用：

```python
async def db(sql, mode="reader", params=None, why="读写应用库"):
    """执行一条固定 SQL。返回 (ok, 行列表, 影响行数, 错误说明)；行是 {列名: 值}。不抛异常，调用方按读写分别收口。"""
    # json 是脚本环境内置的，直接用；不要写 import json，preview 禁止任何 import。
    try:
        raw = await tool("GOALFYAI_TOOL_query_business_app_dataset", action="exec", mode=mode, sql=sql,
                         params=params or {}, _rationale=why, _text=True)
        body = json.loads(raw)
        if body.get("output") is not None or body.get("success") is False:  # 外层信封；不写 "output" in body，preview 会把它当 shell 回显判定
            if body.get("success") is not True:
                return False, [], 0, str(body.get("error") or "应用库读写失败")
            body = json.loads(body["output"])
        results = body.get("results") or []
        if not results:
            return False, [], 0, "应用库没有返回结果"
        result = results[-1]
        rows = [dict(zip(result.get("columns") or [], row)) for row in result.get("rows") or []]
        return True, rows, result.get("row_count", 0), ""
    except Exception as exc:  # 工具报错（如冒泡里的 not_a_business_app_project）、返回解析失败都在这里收口
        return False, [], 0, str(exc)
```

- `db()` 里的 `try` 只包这一次工具调用和返回解析，是「`try` 只包可选的那一次调用」之外的唯一写法；照抄，不删。
- 参数直接写在 `tool(...)` 里，不改成 `**kwargs` 展开：静态校验看不到展开里的 `_rationale`，会报告警。`json` 已内置，不补 `import json`。
- **读**：`ok=False`（不是智能应用项目、实例还没建）或查不到行，都按「没有数据」收口，回退表单值或通用策略，不重试、不编数。读库不用包 `dry_run`：冒泡里读到空（工具报 `not_a_business_app_project`）是预期，读到数据之后的分支到 ④ 工作集实际跑里核对。
- **写**：`ok=False` 或该改的行数对不上，本节点返回 `status="blocked"`，`note` 写「未入库：原因」。这只结束本节点，多节点路线里下游照常派发；要停整条路线就抛错。
- **写库包在 `if not ctx.dry_run:` 里**：只有冒泡（单条、路线、`full_run` 都算）里 `ctx.dry_run` 为真，而冒泡的验证项目也没有应用库；实际跑、在线预览、自动化、使用者运行里 `ctx.dry_run` 为假，应用库在运行开始前就已建好。所以写库语句一律包在 `if not ctx.dry_run:` 里：冒泡时跳过、不报「未入库」，其余场景照常写。这是跳过不是删除：写库保留在脚本里，不为冒泡改成入口传素材或交给页面、后端代写。
- 为了让冒泡通过，把读库包进 `dry_run`、从入口塞数据、加 `fallback_*` 兜底或删掉读写，都是错的。
- 这个工具不是 TA 默认工具：TPE 的 `preload_toolset_ids` 里要有一个装了工具组「query_business_app_dataset」的工具集，否则 preview 报「无法解析到 preload_toolsets」。

## 要按情况查库的 FA

FA 要按客户、任务或上一步结果去应用库挑素材、记录或上下文时，建 FA 时就挂应用库只读工具；以这一步实际要不要按情况查库为准，施工单漏写的也挂，并回 ② 把施工单补上：

1. `list_assets(asset_type="tool_group", keyword="query_business_app_dataset")` 找到平台工具组，把它的 ID 填进 `create_fast_agent` 的 `tool_group_ids`。
2. 提示词写明只用 `mode="reader"`、先 `tables` / `inspect` 再查、只取本步需要的切面，写库交给脚本。
3. `get_asset(asset_type="fast_agent")` 反读：返回的 `actual_tool_group_ids`（平台实际展开的工具组）含 `query_business_app_dataset` 所在工具组；`configured_tool_group_ids` 只是配置值，不作证据。挂不上时按 [编排报错对照.md](编排报错对照.md) 排查，取数方式保持由 FA 自己查。

只读文件做判断的 FA（如模板二的判读 FA）不挂这个工具。

## 反读自查四项

每条读写应用库的路线 preview 前逐项自查一遍，任一项不满足先改再 preview；`online` 后用 `get_asset(asset_type="tpe")` 反读脚本、`get_asset(asset_type="fast_agent")` 反读要查库的 FA，四项各记「有 / 没有」：

1. **脚本有 `db(`**：复制了上面统一的 `db()`，所有应用库读写都经它，业务值都经 `params`。
2. **写库包在 `if not ctx.dry_run:` 里**，写法照 ② 定的「同一业务再做一次」是更新原记录还是新增一条；写失败返回 `blocked`「未入库」（只结束本节点，要停整条路线就抛错）。
3. **工具集含「query_business_app_dataset」并在 `preload_toolset_ids` 里**；要查库的 FA 按上面「要按情况查库的 FA」第 3 步反读。
4. **入口没有整包字段**：`input_schema` 符合「入口字段放哪」——应用库里已有的只传业务键、由脚本按键读，整批记录、素材、档案、摘要都不从入口进，也没有「入口传了就用、没传再查库」的兜底；当次的少量补充（如 `goal_override`、`extra_requirements`）只作补充，不带客户、素材、记录全文，也不让脚本因它跳过查库。出现 `fallback_*`、`materials_summary`、`materials_text`、`snippets`、`records`、`records_json`、`customer_profile`、`customer_summary` 这类字段即记「没有」。

四项都「有」，这条路线才算做好；四项结果记进阶段文档 G4，是 ③ 的交棒门。FA 返回 `needs_input` 时脚本不写库（[脚本骨架与失败出口.md](脚本骨架与失败出口.md)「失败出口怎么写」）。
