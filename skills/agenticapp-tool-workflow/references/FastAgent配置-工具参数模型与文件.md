# FastAgent 配置详解（三）：工具、输入参数、模型、调用方式、轮次与 Skill 文件

给 FA 选工具、写输入参数结构、选模型、设调用方式和最大轮次、开 memory.md 或上传 Skill 文件时读。

本文分 3 份：[FastAgent配置-定位名称描述.md](FastAgent配置-定位名称描述.md)、[FastAgent配置-系统提示词.md](FastAgent配置-系统提示词.md)、[FastAgent配置-工具参数模型与文件.md](FastAgent配置-工具参数模型与文件.md)。

## 工具选择

选择该 FA 可调用的工具。对 SA 不可见。

### 配置范式

只选该 FA 任务所需的工具，不要多选无关工具。工具越少，FA 执行越精准。

> FA 的工具可以来自任何 MCP，不受其所属工具集的限制。所属工具集只决定 SA 何时能"看到"这个 FA，不限制 FA 内部能用什么工具。

### 诊断要点

- 所选工具是否都在系统提示词的执行流程或工具使用策略中被提及
- 是否有多余的工具（系统提示词未提及但被选中）
- 是否有遗漏的工具（系统提示词提到但未被选中）

## 输入参数结构

定义调用方调用该 FA 时需要传入的参数格式（JSON Schema）。调用方根据此结构构造调用参数。顶层必须是 `type=object`，每个字段都有 `type` 和足够详细的 `description`。

字段按谁调用这个 FA 来定：

| 调用方 | 字段 | 说明 |
| --- | --- | --- |
| SA 或 TA | 标准字段 `query`、`expected_result`、`context_hint`，按需加业务字段 | SA/TA 用任务描述的方式调用，`query` 必填 |
| 编排型 TPE 脚本 | 脚本要传的业务字段，如 `topic`、`search_results_path` | 脚本用 `tool()` 按字段名传值，字段名就是脚本和 FA 之间的约定 |

### 配置范式

- 重点检查每个参数的 description 是否说明了在该 FA 场景下应该传什么
- 如果 description 仍是模板默认文案（如 "Goal-oriented task statement"），建议补充该 FA 的业务上下文说明
- 必填参数和可选参数区分明确

### 诊断要点

- SA/TA 调用的 FA 不建议改标准字段的名字；脚本调用的 FA 用业务字段不算问题，字段名要和脚本传的一致
- 检查 description 是否补充了业务上下文（而非仅保留模板默认文案）
- 必填和可选参数是否通过 required 明确区分

## 模型配置

FA 使用的模型。对 SA 不可见。

### 配置范式

- 简单任务（格式转换、信息提取、分类打标、数据搬运）→ 轻量模型，降低成本
- 复杂任务（多步推理、内容生成、代码编写）→ 强模型，保证质量
- 档位和具体模型见 [执行形态与模型档位.md](执行形态与模型档位.md)

### 诊断要点

- 任务复杂度是否与模型能力匹配
- 简单的数据搬运任务是否误用了强模型（浪费成本）
- 需要推理判断的任务是否使用了过弱的模型

---

## 调用方式

调用方（SA 或 TA）调用该 FA 时的执行模式。

### 配置范式

| 模式 | 行为 | 适用场景 |
| --- | --- | --- |
| **同步** | 调用方等待 FA 执行完成，拿到结果后再继续 | 后续任务依赖 FA 的返回结果 |
| **异步** | 调用方发起调用后不等待，继续执行其他任务 | FA 执行耗时较长，且后续任务不依赖其结果 |

### 诊断要点

- 如果后续步骤依赖 FA 结果，是否设为了同步
- 如果 FA 执行耗时长且后续步骤不依赖结果，是否设为了异步以提升效率

---

## 最大轮次

FA 执行的最大轮次上限。一轮 = 一次推理 + 工具调用。

### 配置范式

平台下限、估算方法和建议范围见 [执行形态与模型档位.md](执行形态与模型档位.md)「`max_turns`」。批量任务把对象数算进预估步数。

> 设置过低会导致任务未完成就中断，设置过高会浪费资源。

### 诊断要点

- 最大轮次是否与任务复杂度匹配
- 批量任务是否考虑了数据量对轮次的影响
- 是否存在设置过低导致频繁中断，或过高导致资源浪费

---

## 是否使用 memory.md

开启后 FA 自动加载 memory.md 文件到上下文。

### 配置范式

适合开启的场景：FA 需要了解项目的历史记录、之前的执行结果或持久化的笔记内容。

大多数场景下不需要开启。

## Skill 文件

上传知识文件，FA 在执行过程中可按需读取。对 SA 不可见。

### 配置范式

适合放的内容：

| 内容类型 | 示例 | 为什么放 Skill 文件而非系统提示词 |
| --- | --- | --- |
| 详细检查清单 | 合同条款审核规则完整清单 + 各类条款的判定标准 | 内容长，放系统提示词太占 token |
| 决策树/判断规则 | "违约责任条款：赔偿上限 > 合同金额 → 高风险；无争议解决条款 → 中风险" | 规则多，且可能随业务更新 |
| 案例示例 | 风险评估报告的输入输出样例 | 帮助 FA 理解预期格式 |
| FA 专属的领域知识 | 该子任务相关的详细业务知识 | 内容多且只有这个 FA 需要 |

**与系统提示词的分工**：
- 系统提示词 = 执行流程和行为规则（短、精），每次执行自动加载
- Skill 文件 = 详细参考资料（长、全），FA 需要时主动读取

**FA Skill 文件 vs 场景包知识 Skill 文件**：

| | FA Skill 文件 | 场景包知识 Skill 文件 |
| --- | --- | --- |
| 读者 | FA（对 SA 不可见） | SA |
| 内容粒度 | FA 执行子任务的专属知识 | 多场景共享的通用知识 |
| 示例 | "合同条款审核时各类条款的风险判定规则" | "公司合同管理制度总则" |

> **关键**：如果上传了 Skill 文件，必须在系统提示词中加上「Skill 文件指南」。FA 只能读自己的 Skill 文件，不能读场景包或工具集的 Skill 文件。如果 FA 需要某份共用知识，需要在 FA 的 Skill 文件中提供 FA 视角的版本。

### 诊断要点

- 系统提示词是否过长（应拆分详细规则到 Skill 文件）
- 如果有 Skill 文件，系统提示词是否有 Skill 文件指南
- Skill 文件内容是否与工具集技能或场景 Skill 文件重复
- FA Skill 文件的内容是否是 FA 执行所需的专属知识（而非通用领域知识）
