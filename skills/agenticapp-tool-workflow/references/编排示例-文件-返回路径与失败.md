# 文件路径与产物正反例（二）：返回路径与失败编码

最终输出要返回文件路径、或想用空路径表示失败时读；最后有判断清单。来源信任的三类规则在 [编排示例-文件-三个目录.md](编排示例-文件-三个目录.md) 开头。

本文分 2 份：[编排示例-文件-三个目录.md](编排示例-文件-三个目录.md)、[编排示例-文件-返回路径与失败.md](编排示例-文件-返回路径与失败.md)。

## 4. 最终输出返回 Workspace 路径，不返回 URL 或 `/tmp`

错误 `output_schema`：

```json
{
  "type": "object",
  "required": ["report_url"],
  "properties": {
    "report_url": {"type": "string", "format": "uri"}
  }
}
```

实际 preview 诊断：

```text
$.properties.report_url 禁止 URL 产出；内部编排型 TPE 只能传值或 workspace 绝对路径
```

`default` 或 `examples` 中写入预签名 URL、`file://...` 或 `/tmp/...`，也会命中“禁止 URL 或 /tmp 路径”的 Schema 诊断。

最小修复：

```diff
-  "required": ["report_url"],
+  "required": ["report_path"],
   "properties": {
-    "report_url": {"type": "string", "format": "uri"}
+    "report_path": {
+      "type": "string",
+      "format": "workspace-file-path"
+    }
   }
```

脚本直接返回 `{"report_path": report_path}`。下载 URL 只由交付边界临时生成，不进入 `TaskPoint.output.data`，也不作为跨编排型 TPE 状态。

修复后证据：Scene Schema gate 通过；Core 的 `workspace-file-path` FormatChecker 会继续拒绝 URL、非 `/workspace/` 路径、NUL 和 `..` 路径穿越。

所属契约：编排型 TPE 保存稳定 Workspace 文件事实，外部下载链接由文件服务按需生成。

## 5. 返回路径前必须真的生成文件

错误脚本：

```python
async def run(input, ctx):
    report_path = f"{ctx.output_dir}report.md"
    return {"report_path": report_path}
```

它返回了正确目录下的正确字符串，但没有任何步骤生成文件。

实际 Runtime 诊断：

```text
WORKSPACE_FILE_NOT_FOUND: workspace output file(s) do not exist for this user/project
```

如果返回一个既不来自本编排型 TPE input、也不是本次工具结果的其他 TaskPoint `/workspace/task_agent/.../output/...` 文件，即使文件存在，也会先命中：

```text
WORKSPACE_PATH_UNTRUSTED: workspace output path(s) are not produced by this run or its inputs/tools
```

最小修复：

```diff
     report_path = f"{ctx.output_dir}report.md"
+    await tool(
+        "file",
+        action="file_write_text",
+        abs_path=report_path,
+        text=input.get("report", ""),
+        _rationale="保存本轮 Markdown 交付物"
+    )
     return {"report_path": report_path}
```

文本类产物优先用 `file_write_text`，它会自动创建父目录。只有业务明确要求“非空”时才额外用 `test -s`；不要为了 Core 已有的存在性检查给每个文件都新增 shell 沙盒。使用 shell 生成其他文件时必须自行 `mkdir -p`，并让非零退出码作为步骤失败冒泡，不要解析终端回显猜成功。

修复后证据：生成步骤成功后才返回；编排型 TPE 收尾继续通过 JSON Schema、来源信任和 File Service 存在性三层校验，只有全部通过才提交 `finished(success)`。

所属契约：文件路径不是成功证据；文件必须属于当前用户/项目、来源可信并真实存在。

## 6. 不要用空路径编码失败

错误脚本：

```python
async def run(input, ctx):
    try:
        report_path = await build_report(input, ctx)
        return {"status": "success", "report_path": report_path}
    except Exception as error:
        return {"status": "failed", "report_path": "", "error": str(error)}
```

若 `report_path` 声明了 `format:"workspace-file-path"`，空字符串必然违反格式；若为了通过而删除其格式，或只删除文件字段的 `required`，则会让不存在的产物被提交为成功事实。技术失败应让异常冒泡，由 Runtime 写入结构化 `otpe_error`：

```diff
     except Exception as error:
-        return {"status": "failed", "report_path": "", "error": str(error)}
+        raise
```

只有“没有符合条件的数据，因此不生成报告”本身是业务允许的终态时，才能返回合法无产物结果：

```python
async def run(input, ctx):
    items = await collect_items(input)
    if not items:
        return {"status": "no_output", "reason": "no_matching_items"}
    report_path = await build_report(items, ctx)
    return {"status": "success", "report_path": report_path}
```

对应 `output_schema` 在根级声明 `report_path` 的 `workspace-file-path` 格式，用条件约束要求 `status=success` 时该字段必填；`no_output` 分支省略该字段，不能传 `""`。这样既不会把技术失败包装成成功，也不会削弱成功产物契约。

下游工具或 FastAgent 以结构化返回值（返回值本身是路径，或 JSON / 对象字段的值是路径）给出的文件路径可以作为候选产物继续传递，Runtime 仍会核对来源和存在性；只在说明文字里出现的路径（如 `file` 工具的写入回执）不算，这类文件要返回就写进 `ctx.output_dir`。若下游只给出目标目录或未来写入位置，应先生成明确文件、文件列表或归档包，再作为编排型 TPE 产出返回。

所属契约：成功产物、技术失败和合法无产物是三种不同语义，不能共用空路径占位。

## 判断清单

1. 用户文件来自声明了 `format: "file"/"image"` 的 input 字段；
2. 模板和辅助脚本通过 `skill_file_urls` 交付，并以 `ctx.skill_dir` 引用；
3. 中间文件写 `ctx.process_dir`，最终候选交付物写 `ctx.output_dir`；`process_dir` 里的文件不作为输出返回——输出的文件路径只认 `ctx.output_dir`、input 文件字段和工具/FastAgent 的结构化返回，`file` 写入回执不算；
4. `output_schema` 的文件字段使用 `format: "workspace-file-path"`；
5. 最终返回 Workspace 路径，不返回 URL、`/tmp`、本地开发机路径或 base64；
6. 返回前确认生成步骤成功；最终仍以 Core File Service 校验为准。
7. 技术失败让异常冒泡；合法无产物用明确状态并省略文件字段，禁止空字符串或占位路径。
