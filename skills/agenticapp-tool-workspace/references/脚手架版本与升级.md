# 脚手架版本与升级

判断版本够不够、判断修 bug 要不要重新拉脚手架、判定新建与存量、判断要不要升级（执行步骤在 [升级任务.md](升级任务.md)）、读工单里的版本记录、处理 `SCAFFOLD_*` 错误时读。

## 版本依据

工作台随 Goalfy App 安装和更新，应用脚手架以本应用的版本清单和在线门槛为依据，两者分别更新。

| 依据 | 从哪来 | 说明 |
|---|---|---|
| 工作区里的实际版本 | 应用根 `scaffold-release.json` 的 `version`，格式 `vYYYYMMDD-六位随机hex` | 没有文件就是未声明，不从 package.json 或日期猜。同一文件里的 `sdk_version`、`skill_version`、`upgraded_at` 由升级脚本写回，调工具时有才传、缺了不补；只有 `version` 的旧文件也合法 |
| Skill 最低要求 | 入口 `SKILL.md` 里的 `scaffold-min-required-version` 机器标记 | 发布清单自动镜像为 `scaffold_min_required_version` 并登记到平台 |
| 必须线 | MCP 在线返回的 `min_required_version` | 已合并平台抬杆与本版 Skill 最低要求；先后由服务端按登记 ID 判断，你不按字符串排序 |
| 建议线 | MCP 在线返回的 `min_recommended_version` | 服务端按登记 ID 判断。低于它可以继续开发和部署：在工作区开发时提示「建议升级脚手架版本」，线上运行或唤醒时提示升级。建议线由平台策略维护，你不改 |
| 最新可下载版本 | 平台已登记的最新模板 | 要校验下载包 `sha256`，解包后版本与响应 `version` 相同 |

Goalfy App 的版本、模板压缩包名、智能应用名和目录名都不是脚手架版本依据。不同应用各用自己的工作区标识，上报版本时不复用另一个应用的记录。应用处理过哪些升级指南记在 `docs/upgrade/history.json`（[升级手册模板.md](升级手册模板.md)「history.json」）。

## 核脚手架版本的细则

对应 SKILL.md「核脚手架版本」的四步：

- 第 1 步（读工作区里的版本）：模板暂存目录、其他应用、Goalfy 安装目录里的清单都不算。
- 第 2 步（`download_template`）：只传这几个；Skill 的最低版本发布时已登记，服务端按工单绑定的 Skill 版本取，版本号一律以返回为准。用缓存模板也要先在线核。
- 第 3 步（核返回字段）：最低版本按契约可以为空，不自行补。缺版本治理字段或返回 `SCAFFOLD_POLICY_UNAVAILABLE`：记下缺口等平台就绪，不自填版本绕过。
- 第 4 步（新建时解压）：确认 `frontend/`、`backend/`、`scripts/`、`Dockerfile`、`scaffold-release.json` 都在第一层、版本与响应 `version` 相同；缺了是解压错了，重解，不当成模板缺件报平台。

## 修 bug 不迁移与重新拉脚手架

- **所在路以 MCP 返回为准**：已有应用调下载入口、`upgrade_plan` 或部署被拒（`metadata.scaffold_version`）时，返回里的 `scaffold_route` 是应用所在的路（`legacy` 旧路、`new` 新路），`route_source` 是判路依据，照原样记进开发记录，**禁止**自己按版本串、`executor` 或日期另判；必须线、建议线以返回为准。`upgrade_plan` 的 `fixed_layer.base_source=current_is_latest`（`latest.version` 等于本地 `version`、不带下载地址）表示模板已是最新，**禁止**另找模板下载，按已是最新结束、不读指南；`base_source=sdk_major_skipped` 时不给固定层差异和下载地址：同时 `scaffold_route=legacy`（旧路应用，最新模板是 SDK 5）时**不是**已是最新，只说明一键升级不跨主版本，要重新拉脚手架时按下一条迁移；`scaffold_route` 不是 `legacy`（新路主版本不同或确认不了）时按已是最新结束。
- **修 bug、加功能不重新拉脚手架**：开发者要修页面、接口、数据或路线的问题，或加功能（修订、诊断、用户反馈）时，在现有工程上直接改、验证、部署，不重新下载模板、不迁移。下载入口返回 `upgrade_recommended=true` 时只在开发记录写「建议升级脚手架版本」，改完照常部署；**禁止**把升级 SDK、换模板或迁到新路当成修 bug 的前提，也不向开发者这样建议。
- **一旦重新拉脚手架就按指南做完**：`upgrade_required=true`、部署报 `SCAFFOLD_UPGRADE_REQUIRED`、开发者要升级，或改动确实要换新模板时，才按 [升级任务.md](升级任务.md) 重新拉脚手架。拿到的是平台最新模板，旧路应用拿到的就是 SDK 5 模板：按《升级任务》运行插件自带的 `business-app-creator/scripts/upgrade_guides.py candidates` 取升级指南（含旧应用迁到新路的指南），按指南完成迁移（平台细节见 `agenticapp-task-revise` 的 [新SDK应用的修订.md](../../agenticapp-task-revise/references/新SDK应用的修订.md)「旧应用迁到新 SDK」），**禁止**问开发者要不要迁（指南要求告知的影响照常告知，发布时间由开发者定），**禁止**只换固定层不迁，**禁止**为了不迁另找旧版模板。

## 新建与存量

`scaffold-release.json` 的 `guide_baseline: "pending"` 只由平台打包新模板时写入，表示这可能是刚建的新应用。看到它时在 SKILL.md「核脚手架版本」时判定（新建应用在「初始化或接续工作区」的 `scaffold:init` 之后、`npm run setup` 之前），判定完**必须**删掉这个字段。同时满足四条才算新建：

1. `scaffold-release.json` 有 `guide_baseline: "pending"`；
2. 应用根就是 Git 仓库根（`git rev-parse --show-toplevel` 等于应用根），全部提交只有一个（`git rev-list --count HEAD` 为 1），它就是 `scaffold:init` 的模板基线提交：提交说明「chore(scaffold): 模板基线」、作者 `goalfy-agent <agent@goalfy.local>`（`git log -1 --format='%s|%an <%ae>'`）；
3. `git status --porcelain` 为空（未跟踪文件也算改动，`.gitignore` 忽略的不算）；
4. `docs/upgrade/history.json` 不存在。

- 新建：运行 `python3 <skills目录>/business-app-creator/scripts/upgrade_guides.py baseline`（`<skills目录>` 是本 Skill 目录的上一级，升级指南与读取脚本随插件放在其中的 `business-app-creator/` 下），基线 = 当前插件自带的全部有效指南：把输出 `applied_guides` 里的每条 `{did, sha, how: "baseline"}` 原样写进 `docs/upgrade/history.json` 的 `applied_guides`。然后删掉 `guide_baseline`，只 `git add scaffold-release.json docs/upgrade/history.json` 提交「chore(upgrade): 记录指南基线」。
- 有标记但第 2–4 条任一不满足（已有业务提交、有未提交改动、用 `--no-git` 建后自己提交、基线提交失败或说明与作者对不上），或上一条脚本报错（退出码不是 0）：只删标记、不写 `history.json`，按存量处理；应用根是 Git 根时只提交 `scaffold-release.json`。
- 没有标记、也没有 `history.json` 的是存量应用：升级时看插件自带的全部有效指南，多出来的由逐条判断记为已满足或不适用。
- **禁止**手工给应用加、或保留这个字段；升级脚本不会把它带进已有应用。

## 升级步骤

`upgrade_required=true` 时**必须**先升级再继续制作或预部署；`upgrade_recommended=true` 时开发可以继续，先在开发记录中写「建议升级脚手架版本」，并在下一次预部署前完成升级；修 bug、加功能的会话不因建议线升级，按上面「修 bug 不迁移与重新拉脚手架」改完照常部署。两种情况都按 [升级任务.md](升级任务.md) 执行：取升级计划、替换固定层、按升级指南改业务代码并逐条测试、跑验证链、预览部署、用相同 `workspace_id` 再调下载入口上报（这是工单的 `local_report`）。新下载模板的版本不提前当成本地应用版本上报；验证失败或冲突没处理完不上报、不预部署。建议线由平台策略维护，Agent 不修改。

目标模板没有 `scripts/upgrade-scaffold.mjs`，`upgrade_plan` 报 `SCAFFOLD_VERSION_MISSING` 给不出计划，或返回 `fixed_layer.base_source=sdk_major_skipped` 且 `scaffold_route=legacy`（旧路迁到 SDK 5，下载用 `download_template` 取最新模板，业务代码按插件自带的迁移指南改）时，才按下面手工迁移：

1. 将最新模板下载到独立目录并核 SHA256。在应用根先提交一次 Git 作为回滚点。
2. 对照旧模板、新模板和当前应用，迁移前后端平台固定层、应用预览适配、校验脚本及受影响依赖；保留业务页面、后端业务逻辑、身份、阶段文档、方案页和数据。不在业务目录直接 `git pull` 或整包覆盖来代替迁移，也不从已下载的新模板清单直接认定旧应用已升级。
3. 固定层迁移完成后带入目标模板的版本清单；运行 `setup`、`doctor`、`verify` 和适用的 `verify:release`。迁移冲突或验证失败时，记录未完成状态，不上报升级完成、不预部署。缺少真实工作集时，先完成所需绑定与配置，再跑 release 验证。
4. 通过后用相同 `workspace_id` 再调用下载入口上报已采用版本。之后再有升级计划时照 [升级任务.md](升级任务.md) 处理升级指南。

**固定层迁移边界**：固定层由模板包里的 `scaffold-fixed-layer.json` 定义：`mode=replace` 的文件整文件以目标版本为准，`mode=merge` 的文件（如 `backend/src/app.ts`、`frontend/src/main.tsx`、`frontend/goalfy-app.json` 与三份 `package.json`）只合并差异；升级脚本按清单处理，动不了的写成 `<path>.upgrade-new` 和 `docs/upgrade/conflicts.md`。依赖、路由接线与测试清单读目标模板的 `AGENTS.md` 和 `README.md`。业务代码按升级指南改，固定层升级带来的 doctor/verify 问题没有指南覆盖时也按 [升级任务.md](升级任务.md) 第 7 步修；只换版本清单、或只迁前端（漏了后端平台模块与 `backend/src/app.ts` 的挂载）都不能证明升级完整。迁移结果与无需修改的依据分别记录。

## 部署时的版本证据

- 版本清单要在 `npm run verify:release` 打出的实际源码包里一起上传，不只放在被排除的 `app.json`、`workspace.json` 或 `docs` 里。
- 平台在建库、起容器前读上传包，校验实际字节的 `source_sha256`、根版本清单、平台抬杆和工单对应 Skill 的已登记最低版本。工单自动追加 `scaffold_version` 记录，`evidence=bundle_verified`，并记 `gate_passed`。只有 `gate_passed=true` 才表示这次版本检查通过，不代表部署或业务验收成功。
- 部署返回带 `data.scaffold_upgrade_notice`：服务端按上传包判定过了必须线、低于建议线，部署有效。把提示里的 `current_version` 与 `recommended_version` 原样写进开发记录和上线结果的「脚手架建议线」一项，并把升级列入下一轮计划。
- 三种记录分别保留：`local_report` 是工作区申报，`bundle_verified` 是源码包校验，`deployed_scaffold_version` 是某次部署的来源版本。`task_manager(action="get")` 的 `scaffold_versions` 分别列出各工作区的 `local_report` 和各应用的 `bundle_verified`，完整历史在 `entries`。历史部署的空值记「未知」。
- `latest_version`、`min_required_version`、`min_recommended_version` 用于升级判断，实际版本以部署记录为准。查某个正在运行或唤醒的使用者实例时，以该实例自己的部署绑定及版本为依据：低于必须线提示需要升级，低于建议线提示建议升级。应用最新提交的版本只证明该提交，旧实例是否升级要看实例侧证据。

## 版本错误

| 错误 | 处置 |
|---|---|
| `SCAFFOLD_UPGRADE_REQUIRED` | 低于必须线；按「升级步骤」升级（旧路应用拿到的是 SDK 5 模板，按插件自带的迁移指南迁完）、验证、重新打包上传，再部署 |
| `SCAFFOLD_VERSION_MISSING` | 包里缺版本清单，`upgrade_plan` 给不出计划；按「升级步骤」里的手工迁移完成升级，不凭空补版本 |
| `SCAFFOLD_VERSION_UNKNOWN` | 工作区里的应用用了平台未登记的版本；**禁止**改版本串，改用平台已登记的模板，或按平台问题报、由维护者先发布登记 |
| `SCAFFOLD_FIXED_LAYER_UNAVAILABLE` | `upgrade_plan` 时最新模板没有固定层清单，是平台侧未就绪；本次不升级、不手工迁移，按平台问题报；修 bug 照常继续 |
| `SCAFFOLD_MANIFEST_INVALID` | 源码包损坏、根清单格式错误或重复；修打包与清单，不只改请求里的版本 |
| `SCAFFOLD_BUNDLE_HASH_MISMATCH` | 部署时：SHA256 与实际上传包不符，对这次真实字节重新打包、算摘要、上传。`upgrade_plan` 时（含 `SCAFFOLD_BUNDLE_CORRUPT`）：平台存的模板包损坏，本次不升级，按平台问题报 |
| `SCAFFOLD_POLICY_UNAVAILABLE` | 平台缺最低版本登记或策略读不到；记下缺口，由维护者修复，不跳过检查、不自填版本 |
| `SCAFFOLD_BUSINESS_UI_ID_INVALID`（`scaffold:bind` / `scaffold:init` 时） | 平台返回了 8 位短码而工作区里的脚手架只认数字，或应用 ID 被手改。用 `download_template` 查必须线并升级脚手架，再原样重新绑定；不改写 ID，不重新 `setup` 出另一个应用 |

版本拦截不会自动覆盖工作区里的业务文件，也不会因为另建工单而消失。紧急放行只由服务端策略管理，你不改这个策略。

## 常见错误

| 错误 | 正确做法 |
|---|---|
| 只迁前端 SDK 和版本清单就算升级，漏了后端平台模块与 `backend/src/app.ts` 的挂载；旧工程缺件时自写兼容代码。这样证明不了升级完整 | 按三方差异迁移完整固定层；缺件先升级 |
| 有升级计划却手工对照模板改固定层，或运行应用里的旧版 `npm run scaffold:upgrade` | 按 [升级任务.md](升级任务.md) 第 4 步运行已校验模板里的 `scripts/upgrade-scaffold.mjs`；手工迁移只在「升级步骤」写的两种情况下用 |
| 有业务提交的应用带着 `guide_baseline` 被当成新建，把全部指南记成已执行 | 按「新建与存量」四条都满足才算新建，否则只删标记、按存量处理 |
| 修 bug、加功能时重新拉脚手架，或要求先升级 SDK、迁到新路 | 按「修 bug 不迁移与重新拉脚手架」在现有工程上改完照常部署 |
| 重新拉到 SDK 5 模板后只换固定层、不按插件自带的迁移指南迁，或停下问开发者要不要迁 | 按 [升级任务.md](升级任务.md) 取迁移指南迁完，不问要不要迁 |
| 旧路应用要重新拉脚手架时，把 `upgrade_plan` 的 `sdk_major_skipped` 当成已是最新结束，或等旧路的新模板 | `scaffold_route=legacy` 时按「修 bug 不迁移与重新拉脚手架」第一条迁到 SDK 5 |
