# 工具描述最佳实践（一）：核心哲学、模板与关键字段

要深度优化工具描述（自己开发的 MCP 工具）时读。

本文分 2 份：[工具描述最佳实践-模板与字段.md](工具描述最佳实践-模板与字段.md)、[工具描述最佳实践-参数与实例.md](工具描述最佳实践-参数与实例.md)。

这是一份关于\*\*“为 Agent 编写工具说明（Tool Definitions）”的完整最佳实践指南\*\*。

这份指南基于 Anthropic Claude Code 的生产级 Prompt 进行了深度解构。核心原则是：**工具说明不是写给人类开发者看的 API 文档，而是写给 LLM 看的“行为编程指令”**。

---

### 一、 核心哲学：工具说明即 Prompt

在编写工具说明时，必须建立三个认知：

1.  **意图优先（Intent-First）**：模型首先要决定“是否调用这个工具”。你的描述必须包含**路由逻辑**。

2.  **防御性编程（Defensive Prompting）**：假设模型会偷懒、会幻觉、会参数填错，在说明中预先封堵。

3.  **思维链引导（CoT Induction）**：不要只描述功能，要描述**操作流程**（例如：“在写之前必须先读”）。

---

### 二、 通用结构模板

根据工具性质，分为\*\*“决策型”**和**“动作型”\*\*两种模板。

#### 模板 A：决策型工具 (Decision Tools)

**适用场景**：`EnterPlanMode`, `Task`, `TodoWrite` (涉及流程分支、状态切换、高成本操作) **重点**：教模型 **“什么时候该用，什么时候不该用”**。

```markdown
## [工具名称]

**[简述]**
一段话概括核心价值。

**[When to Use - 触发条件]**
主动使用此工具，当满足以下任一条件时：
1. [条件 A：定量标准，如“涉及 3 个以上文件”]
2. [条件 B：定性标准，如“用户需求模糊”]
3. [条件 C：特定场景，如“架构设计阶段”]

**[When NOT to Use - 反向过滤]**
在以下情况跳过此工具：
1. [反例 A：任务太简单]
2. [反例 B：有更专用的工具]

**[Usage Notes - 最佳实践]**
- [参数技巧：如何填写参数能获得最佳结果]
- [性能提示：如“建议并行调用”]
- [副作用警告：如“此操作会覆盖原文件”]

**[Examples - 少样本学习]**
<example>
User: [模糊指令]
Assistant: [展示正确的工具调用]
<reasoning>
[解释为什么要用这个工具]
</reasoning>
</example>
```

#### 模板 B：动作型工具 (Atomic Tools)

**适用场景**：`Edit`, `Bash`, `ReadFile` (单一功能、明确执行、易出错) **重点**：教模型 **“如何正确地用”** 和 **“参数约束”**。

```markdown
## [工具名称]

**[简述]**
执行具体的[X]操作。

**[CRITICAL REQUIREMENTS - 强制约束]**
- [安全红线：如“禁止删除数据”]
- [格式红线：如“必须使用绝对路径”]
- [依赖红线：如“调用此工具前必须先调用 Read”]

**[Usage Notes - 最佳实践]**
- [参数技巧：如何填写参数能获得最佳结果]
- [性能提示：如“建议并行调用”]
- [副作用警告：如“此操作会覆盖原文件”]

**[JSON Schema]**
(参数定义的 Description 字段同样重要，见下文)
```

### 三、 关键字段编写指南

#### 1. Description (工具描述)

*   **不要写**：`"Executes bash commands."` (太干瘪)

*   **要写**：`"Executes terminal operations like git, npm, docker. Do NOT use for file editing."` (包含场景和负面约束)

#### 2. When to Use / When NOT to Use (核心路由)

*   **量化标准**：LLM 对模糊概念处理不好。

*   _Bad_: "Use for complex tasks."

*   _Good_: "Use when a task requires **3 or more** distinct steps."

*   **排他性**：明确指出替代方案。

*   _Example_: "If searching for a specific class, use `Glob` instead of `Task`."

#### 3. MUST / NEVER (注意力控制)

使用大写关键词作为“停止信号”，防止模型惯性操作。

*   **MUST / NEVER**：约束句只用这两个词，规则见 [工具描述迭代规范.md](工具描述迭代规范.md)「约束关键词」。

*   _Example_: "You **MUST** read the file before editing. **NEVER** guess the line number."

*   输出格式的要求也这样写。

*   _Example_: "Including a 'Sources' section is required: you **MUST** add it."

#### 4. Examples (少样本增强)

这是最强大的手段。

*   **格式**：使用 XML 标签 `<example>` 包裹，模拟 User 和 Assistant 的对话。

*   **包含推理**：如果可能，加入 `<reasoning>` 标签，显式展示"为什么要选这个工具"。

*   **正反例**：不仅要给 Good Example，对于决策型工具，要给 Bad Example（即"本该用这个工具但没用"或"不该用却用了"）。

**示例 - TodoWrite 工具的正反例：**

```xml
<!-- Good Example：多步骤任务应使用 TodoWrite -->
<example>
User: 帮我实现一个用户登录功能，包括前端表单、后端 API 和数据库验证。
Assistant: 我来帮你实现用户登录功能。这是一个多步骤任务，让我先创建任务列表来跟踪进度。

*创建 TodoWrite:*

1. 设计数据库用户表结构
2. 实现后端登录 API 端点
3. 添加密码哈希和验证逻辑
4. 创建前端登录表单组件
5. 集成前后端并测试

*开始第一个任务*

<reasoning>
使用 TodoWrite 因为：
1. 任务涉及 5 个以上独立步骤
2. 跨越前端、后端、数据库多个层面
3. 需要按顺序完成，后续步骤依赖前置步骤
4. 用户需要清晰了解整体进度
</reasoning>
</example>

<!-- Bad Example：简单任务不应使用 TodoWrite -->
<example>
User: 把 README 里的拼写错误 "recieve" 改成 "receive"。
Assistant: 让我直接修复这个拼写错误。

*使用 Edit 工具修改文件*

<reasoning>
不使用 TodoWrite 因为：
1. 这是单一、明确的修改任务
2. 只涉及一个文件的一处改动
3. 不需要规划或跟踪进度
4. 创建任务列表反而增加不必要的复杂性
</reasoning>
</example>
```
