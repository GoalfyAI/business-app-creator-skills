# 工具描述迭代规范

根据 Bad Case 优化工具描述（Description）和输入参数结构（Input Schema）时读。

基于 Bad Case 优化工具 Description 和 Input Schema 的标准化流程。

## 核心原则

工具说明不是 API 文档，而是**写给 LLM 的行为编程指令**。

| 原则 | 说明 |
| --- | --- |
| 意图优先 | 描述必须包含路由逻辑（何时用/何时不用） |
| 防御性编程 | 预设模型会误用，在说明中预先封堵 |
| 思维链引导 | 不只描述功能，要描述操作流程 |

## Bad Case → 工具修改映射

| Bad Case 类型 | 修改位置 | 修改策略 |
| --- | --- | --- |
| **工具误用** | Description `### When NOT to Use` | 添加排他性说明 + 替代方案 |
| **参数错误** | Input Schema `description` | 添加格式约束 + 示例 |
| **执行上下文混淆** | Description `### CRITICAL REQUIREMENTS` | 明确执行环境边界 |
| **操作未验证** | Input Schema 或 Description | 添加验证参数或流程要求 |
| **交互闭环缺失** | Input Schema `description` | 说明参数组合的完整性 |

## 迭代流程

```plaintext
1. 分析 Bad Case    → 确定问题类型（误用/参数/上下文/闭环）
2. 定位修改位置    → Description vs Input Schema
3. 选择修改策略    → 见下方模式库
4. 改写描述        → 按模板写进 MCP 服务代码
5. 发布并刷新      → 部署 MCP 服务后调 register_and_refresh_tool_group
6. 复测            → 工具行为用 otpe_tool_test 确认（先按工具取样排除不能取样的工具）；Bad Case 重跑原来出错的路线或 FA，花钱按入口规则
```

描述是技术细节，不用请开发者逐条确认。MCP 服务不归你改时，把改写好的描述交给开发者。

## 修改模式库

### 模式 1：执行上下文混淆

**症状**：Agent 在工具 A 中使用了工具 B 特有的 API/对象

**修改位置**：Description → `### CRITICAL REQUIREMENTS`

**模板**：

```markdown
### CRITICAL REQUIREMENTS
- This tool runs in **[环境名]** context, NOT [另一环境名]
- **NEVER** use [禁用的 API/对象] — it does not exist in this context
- If you need [禁用的能力], use `[替代工具名]` instead
```

**示例**（browser\_evaluate）：

```markdown
### CRITICAL REQUIREMENTS
- This tool runs in **browser console** context, NOT Playwright host
- **NEVER** use `page.waitForSelector()` or any Playwright API — use standard DOM APIs (`document.querySelector`)
- If you need Playwright features (waitForSelector, evaluate with page object), use `browser_run_code` instead
```
---

### 模式 2：操作后未验证

**症状**：Agent 执行操作后未确认结果就继续/放弃

**修改位置**：Input Schema → 添加验证相关参数说明，或 Description → 流程要求

**模板 A**（参数级）：

```markdown
"submit": {
  "type": "boolean",
  "description": "Whether to submit after input. **MUST** set to true for search/form operations unless you plan to click a separate submit button in the next step."
}
```

**模板 B**（流程级）：

```markdown
### Usage Notes
- After operations that trigger async updates (search, submit, filter):
  1. **MUST** verify page state changed as expected (DOM diff, URL change, new elements)
  2. If no change detected, check interaction details (missing submit button click?)
  3. **NEVER** assume success without verification
```
---

### 模式 3：交互闭环缺失

**症状**：输入与提交分离，导致操作无效

**修改位置**：Input Schema → 参数 `description` 说明原子性

**模板**：

```markdown
"text": {
  "type": "string",
  "description": "Text to fill. For search operations, combine with `submit: true` to complete the interaction in one step. Filling without submit has no effect until explicitly submitted."
}
```

或添加参数组合约束：

```markdown
### Parameter Combinations
| Scenario | Required Params | Notes |
|----------|----------------|-------|
| Search | text + submit:true | Single atomic operation |
| Multi-step form | text + submit:false, then click | Explicit two-step |
```
---

### 模式 4：工具选择错误

**症状**：Agent 使用了功能相近但不适合当前场景的工具

**修改位置**：Description → `### When to Use` / `### When NOT to Use`

**模板**：

```markdown
### When to Use
- [具体场景 1]
- [具体场景 2]

### When NOT to Use
- **[场景 A]** → Use `[工具 X]` instead
- **[场景 B]** → Use `[工具 Y]` instead
```
---

### 模式 5：参数格式错误

**症状**：Agent 填入了格式不符的参数值

**修改位置**：Input Schema → `description` + `enum`/`pattern`

**模板**：

```markdown
"filename": {
  "type": "string",
  "description": "Output filename. **MUST** be filename only — no path characters (`/`, `\`, `:`). Example: `screenshot.png`",
  "pattern": "^[^/\\:]+$"
}
```

## 约束关键词

| 级别 | 关键词 | 用于 |
| --- | --- | --- |
| 绝对禁止 | **NEVER** | 会导致运行时错误或安全问题 |
| 强制要求 | **MUST** | 核心行为约束 |
| 条件要求 | **If...MUST** | 特定场景下的约束 |

约束句不用 CRITICAL、IMPORTANT、ALWAYS、MANDATORY，统一用 MUST/NEVER。`CRITICAL REQUIREMENTS` 只作小节标题，小节里的每一条仍用 MUST/NEVER 写。

## 常见反模式

| 反模式 | 正确做法 |
| --- | --- |
| 只说"不要用 X" | 说明替代方案："use Y instead" |
| 参数描述只写类型 | 加入格式要求 + 示例 |
| 流程约束放在 FA 提示词 | 通用约束放工具说明，FA 只写特定策略 |
| 为单个 bad case 加特例 | 提取通用模式 |
| 随意新增章节 | 如非必要，避免新增章节，遵循现有格式 |
