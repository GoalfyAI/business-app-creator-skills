# 验收条目

把 PRD 每个环节的「怎样算做成」写成能逐条照做的验收条目，④ 照它逐条测。缺失或有歧义的验收要求先在问取舍时问清；已明确的直接整理成条目，不逐条再要确认。

## 五列

每条是一次完整的使用者任务，用使用者的话写，不写平台概念：

| 列 | 写什么 | 例 |
|---|---|---|
| 谁 | 人① 使用者 | 人① 使用者 |
| 从哪进、先看到什么 | 打开应用后首屏应该看到的东西，从哪里开始 | 首页先看到「新建项目」和做过的项目 |
| 用什么、按什么顺序做 | 用什么数据；操作步骤，与业务顺序一致 | 只填「莫定标娘惹糕点」→ 提交 → 选候选 → 等报告 |
| 最后拿到什么 | 成果，以及它能支撑的下一步 | 中英文报告，能直接下载发给商家，接着生成内容 |
| 怎样算过 | 可以判断的标准 | 有槟城 Lebuh Chulia 的候选；30 分钟内出报告 |

每条预先标「AI 能判断」还是「要人判断」（报告能不能直接发给商家、语气像不像店家写的）。④ 照这个分，「要人判断」的在验收报告里是「好不好你说了算」。

条目是写给 ④ 的你自己照着做的：「用什么、按什么顺序做」只能是你做得到的事——在演示版上操作、用测试数据跑一遍路线、查库里的记录。要在在线预览里点页面、要发布后才有、要真实账号才看得到的，你做不到，写成条目到 ④ 只会变成「未测」；写方案时就知道的，不写成条目，④ 直接列进报告的未测（原因按 `agenticapp-stage-4-acceptance`「证据与未测」）。

## 哪些必须各写一条

- 每个刚需至少一条。
- 有中途补信息、审阅的：各写一条走到那一步的。
- 能改记录的（改期、改状态、编辑）：各写一条改完回到列表或日历找到这条的。
- 有翻页、切换视图的（上月下月、周和月）：各写一条翻过去再翻回来的。
- PRD 节点里每个「做不成时」各写一条失败条目：「用什么、按什么顺序做」写怎么在测试里造出这次失败（入口少传字段、测试库里删掉依赖的行、演示版 Mock 返回失败等）；「怎样算过」写使用者看到什么提示、能不能重试、已有数据有没有被改坏。
- 记录之间会冲突的（预约撞期、库存超卖、重名）：写一条造出冲突的，按 PRD 定的拦下或提醒判，提示写出和哪一条冲突；时间类的按时段有没有重叠算，不只比开始时间是否相同。要拦下的再写一条被拦后在同一张表单改正、再提交成功的。
- 第一次使用和日常使用不一样时（第一次要先建档）分开写。
- 需求里有几条业务线（几个账号、几家店、几类业务、几个计划）的：各写一条新增第二条线、两条同时进行、改其中一条的预算或内容不影响另一条、其中一条重新生成不盖掉另一条的。
- Studio 宿主下另写一条「在 Studio 里打开看各页面」，④ 记「未测」（Studio 窗口），这是 Studio 要的唯一例外；其他宿主不写这一条。

## 写全

- **条目名里有几个动作，就写几个动作**：例如「编辑并停用商品」，「用什么、按什么顺序做」和「怎样算过」要把编辑和停用都写到；写不全就拆成几条。
- **结果要存下来或之后还要用的刚需，写完整条链**：操作 → 取到资料 → 模型或下一步用上 → 结果显示出来 → 保存 → 刷新或重新打开后找回 → 下次使用时被读到（例如使用者存的材料，下一次生成时确实用上了）。不停在「显示完成」「运行成功」。
- **「怎样算过」要能判断**：写看得到的东西（出现哪条候选、多久内出报告、库里有这一行），不写「效果好」「准确」。写不出能判断的标准时，回问取舍那一步问清。

Studio 宿主下另交一份与条目一致的 `acceptance.json`，按 `agenticapp-host-studio`。
