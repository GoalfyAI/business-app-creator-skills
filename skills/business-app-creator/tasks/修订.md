# 修订

## 识别信号

- 开发者要改已上线应用的页面、接口、表结构、路线、提示词或能力。
- 开发者按使用者反馈报告要求改应用（先按 [用户反馈.md](用户反馈.md) 校验决定）。
- 开发者是这个应用的编辑协作者（`role=editor`）要改应用：按本文「编辑协作者怎么改」。
- 协作者自己的草稿基线过期（`baseline_stale=true`、提请或上线返回 `PERSONAL_VERSION_STALE_SOURCE`、站内信通知基线过期）：按本文「基线过期的合并」。

## 先读什么

1. 建 write 工单，`skill_version` 按 [../SKILL.md](../SKILL.md)「开工」建工单；定位应用工程并按 [接续.md](接续.md) 核对本地与云端。
2. 看版本与角色：先 `business_ui_manage(action="get")` 看 `role`。`viewer` 不能修订，转 [诊断.md](诊断.md)；`editor` 按本文「编辑协作者怎么改」；属主用 `list_asset_versions` 看场景包、应用、模板各自的现役版本和有没有搁浅草稿。
3. 取可编辑草稿：场景包 `scene_package_manage(action="ensure_draft")`，应用 `business_ui_manage(action="ensure_draft", change_note=…)`（必须带 `change_note` 写这次改了什么），其他资产 `ensure_editable_asset_draft`。对上线行直接 update 会自动派生草稿，之后一律用返回的 `draft_asset_id`。规则见 [../reference/部署与版本.md](../reference/部署与版本.md)「修订、回滚、作废」。
4. 评估影响：共享资产用 `get_asset_usage_impact` 看谁在用；改表结构先看 [../reference/数据模板.md](../reference/数据模板.md)「改已上线的模板」（应用有协作者时按本文「编辑协作者怎么改」）；改 TPE 的输入输出会波及路线映射和页面。改到的路线还经平台数据集 FA 转手读写应用库的，顺带改成现在的写法（见 [../reference/数据模板.md](../reference/数据模板.md)「常见错误」）。
5. 涉及文案、入口或产物时，按 [../reference/前端页面.md](../reference/前端页面.md)「业务文案」只核受影响的部分，保留已有正确的配置和定制。
6. 修订前后用 `compare_asset_versions` 取配置差异，留给 ⑤ 写进上线结果。

## 从哪一段进

修订也走五段，每段只做和这次改动有关的部分。按改了什么决定从哪一段开始、要不要出 PRD 差异版：

| 改什么 | 从哪一段开始 | PRD |
|---|---|---|
| 要的东西变了：业务规则、功能范围、谁来用、每一步谁来做 | ① 需求确认 | 出差异版，请开发者确认 |
| 换工具或模型、接新能力 | ① 需求确认（只核实受影响的步骤） | 出差异版，写清对能不能做和花费的影响，请开发者确认 |
| 做法变了，要开发者重新判断 | ② 方案（只重答受影响的判断题） | 不变 |
| 只改做法：脚本、提示词、路线、表结构、页面、后端接口 | ③ 制作 | 不变 |
| 只改文案或样式 | ③ 制作（本地 verify 后直接 ④） | 不出，在对话里说清改什么、请开发者确认一句 |

- PRD 差异版只列：这次改什么、影响哪些功能、谁来用和每一步谁来做有没有变、费用与用量有没有变、正在用的人会看到什么变化；改动处按 [../reference/开发者中心与工作区.md](../reference/开发者中心与工作区.md)「方案页」标出。
- 要上线的修订 ④ 和 ⑤ 每次都做：④ 只验受影响的条目加一条完整主流程；⑤ 的上线结果写配置差异（给后续 Agent 的部分）和「正在用的人会看到什么变化，已有数据怎么处理」（见 [../stages/5-上线.md](../stages/5-上线.md)）。
- Studio 宿主：先用 `studio_read_creation` 分别按 `documentType="prd"`、`"proposal"` 读当前确认状态，以宿主返回为准；改动在已确认范围内的不自行增加确认步骤；要改 PRD 或方案的，按 ① 或 ② 保存新的一版并请开发者重新确认（[../reference/开发者中心与工作区.md](../reference/开发者中心与工作区.md)「Studio 宿主」）。

### 编辑协作者怎么改

权限、工具行为和报错见 [../reference/多人协作.md](../reference/多人协作.md)。按这个顺序做，起点仍按上表：

1. 看版本：应用的版本和草稿看 `business_ui_manage(action="get")` 的返回；场景包、工具集、FA 等属主名下资产看 `get_asset` 和 `ensure_editable_asset_draft` 的返回，不调 `list_asset_versions`。
2. 应用草稿和各层资产按 [../reference/多人协作.md](../reference/多人协作.md)「编辑协作者的草稿与各层资产」：只改自己的草稿，自下而上逐层派生、验证、上线这一层、往上改引用，最后在自己的应用草稿上换挂。
3. 新建或克隆资产时带 `collaboration_business_ui_id=<应用家族 ID>`，新建前告诉开发者资产会落在属主名下（[../reference/多人协作.md](../reference/多人协作.md)「协作中新建或克隆的资产」）。
4. 改开发库结构：先告诉开发者要加改哪些表和列，请他先和属主及其他编辑协作者说一声，避免两人同时改；然后按 [../reference/多人协作.md](../reference/多人协作.md)「共享开发工作集」带基线改结构、抽新版本，再在自己的应用草稿上 `update` 挂新模板版本、重新部署。
5. ④ 和属主一样由你按 [../stages/4-试用验收.md](../stages/4-试用验收.md) 逐条测：部署授权按 [../SKILL.md](../SKILL.md)「红线」；`workspace` 真跑前先把自己的草稿 `ship` 到 `success`；只有协作者身份才看得到的表现记「未测」。
6. ⑤ 不上线应用，改为提请属主上线（[../reference/多人协作.md](../reference/多人协作.md)「提请属主上线」）。

### 基线过期的合并

协作者的草稿基线过期，说明属主已经上线了更新的版本，这份草稿是从旧版派生的。按顺序做：

1. 用业务话告诉开发者原因和下面要做的事，他确认后开始。
2. 先把本地当前改动提交到 git（应用目录还没有 git 仓库就先初始化再提交）。
3. `business_ui_bundle(action="download")` 下载最新上线版的源码包，放到另一个分支，用 git 合并到自己的改动上；不直接用新版覆盖本地，也不用本地覆盖新版。冲突在技术上怎么合由你定；合并结果会影响使用者已有数据或页面行为的，用业务话出选择题给开发者。
4. 从最新上线版重新派生自己的应用草稿（`ensure_draft` 带 `change_note`）。返回的仍是那份过期草稿时，告诉开发者后先用 `abandon_asset_version_draft` 作废它，再重新派生。
5. 合并后的代码跑 `npm run verify:release`，`ship` 到新草稿，按 ④ 重新验收受影响的条目。
6. 再次提请属主上线。

场景包、工具集等资产层的草稿过期时同理：从新上线版重新派生，把改动重做到新草稿上。
