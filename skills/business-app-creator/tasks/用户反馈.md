# 用户反馈

## 识别信号

- 开发者要查应用的使用者反馈、整理反馈报告。
- 开发者要按报告里的决定改应用。
- 开发者要把处理结果同步给提交反馈的使用者（不予处理、已完成）。

## 先读什么

工具参数、文件格式和脚本用法都在 [../reference/用户反馈.md](../reference/用户反馈.md)，下面只写顺序。

1. **工单**：用现有开放的 read 或 write 工单；没有就建 read 工单。要改应用或同步状态时用 write 工单（`skill_version` 按 [../SKILL.md](../SKILL.md)「开工」建工单）。
2. **定对象**：按名称找应用时用 `business_ui_manage(action="list")` 解析家族 ID，同名有歧义先和开发者确认，不用 `project_id` 或场景包 ID 代替。只读查询不要求应用绑定场景包最新版本，也不要求已发布。协作者也能查所协作应用的反馈；只读协作者只查询、只出报告，不改应用、不同步状态。
3. **取证**：`list` 逐页取完，原始结果存成 `feedback-raw.json`，记 `snapshot_at`；没取全就写「未取全」，不下全量结论。每张图调 `attachment_url`，用脚本 `download` 下到 `images/`。没有反馈也生成空报告，写明查询范围。
4. **整理与出报告**：按问题整理 `feedback-issues.json`，用脚本 `render` 生成 `feedback-report.md`，交给开发者；刷新已有报告时先合并已保存的文件，保留已有决定。
5. **等开发者决定**：开发者在报告的决定块里填 `accepted` / `rejected` 和原因；`pending` 的不处理。只查反馈或整理报告时到这里为止，不改状态。
6. **按决定执行**（开发者明确要求按报告执行后）：先用脚本 `validate`，只处理返回的 `accepted` 问题，`review_ready` 的不重复改；记下 `report_sha256`，每次开始写对应代码前带 `--expected-sha256` 再校验一次。核对应用家族、当前源码、真实调用链和 `developer_notes` 后，按 [修订.md](修订.md) 改；`accepted` 不等于授权提交或部署，红线和部署授权照常适用。改动期间按实际更新决定块的 `implementation_status`（`in_progress` / `review_ready` / `blocked`），改动文件、验证结果、未解决的问题写进 `feedback-issues.json` 的 `implementation_result`，然后重新取摘要、刷新报告。改完交开发者看，不自动上线、不提交代码、不部署。被拒的问题保留原因，不执行。
7. **同步使用者可见状态**（开发者明确要求后）：
   - 不予处理：`update_status(status="rejected")` 带理由，理由会展示给提交者。
   - 已完成：修复要经过 ④ 验证并上线，再由开发者自己在发布管理页发布；开发者告诉你已发布后，核对发布成功，再 `update_status(status="completed")` 带 `completed_release_id` 和说明。开发者还没发布或发布失败时保持 `pending`；你不发布、不请求发布，也不为关闭反馈催促发布。
   - 一条反馈拆成多个问题时，不因其中一个完成就整条完成：还有待决定或未解决的问题就保持 `pending`；全部不予处理才写 `rejected`；部分采纳、部分拒绝的，先请开发者明确整条反馈的最终结果和给使用者的说明，再同步。
   - 多条同步时逐条记录结果，有失败的分别写明，不说全部已同步。

## 从哪一段进

- 查反馈、出报告、同步状态都不进五段。
- 按报告改应用是一次修订：按 [修订.md](修订.md) 的起点表从受影响的那一段进，④ 和 ⑤ 照常做。
- 没有旧报告时说明无法得知以前的决定；换设备要带上整个报告目录。服务端只保存每条反馈的使用者可见状态，每个问题的决定和实施记录在报告里。
