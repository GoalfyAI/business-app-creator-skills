# 确认页：一页说清，一次确认

Studio 的方案版本、内容摘要和确认由宿主绑定精确原生回执；方案先于工程，确认后内容变化使旧确认失效。已有当前应用自动交付授权在原范围内沿用，不为每一版新增人工上线门槛。详见 [Studio自动交付](../reference/Studio自动交付.md)。

G1 发给开发者的只有这一页。普通宿主写进 `docs/proposal/index.html`，Studio 写入宿主分配的 artifact；确认前不为写方案初始化业务工程。「它帮你做什么」写进 `.pv-goal`，分工表写成业务过程的 `.pv-steps`，其余各节写进「开发内容」。普通宿主 `status` 为 `waiting`、`.pv-you` 写「确认这份方案，或告诉我要改哪里」；Studio 由宿主生成原生确认卡，页面不自造确认状态。共用正文末尾必须接下面对应宿主的「上线范围」正文，只选一种，不把编辑说明留在页面。版式见 [../reference/开发者中心与工作区.md](../reference/开发者中心与工作区.md)「方案页」。用开发者的词，不出现 FA、TPE、工具集、Runtime。

```
## <应用名>

**它帮你做什么**：一句话。

**功能清单**
1. <功能一>：用户在哪里点什么，得到什么
2. <功能二>
3. 数据管理：可以看和改哪些表

**界面**（必填；来自 G1 第 2 步主动问的回答）
- 参考：<网站链接 / 截图 / 同类产品，没有写「无」>
- 第一眼看到：<开发者原话>
- 整体感觉：<密集工作台 / 简洁大方……；品牌色、Logo>
- <页面名>：放什么、怎么排、参考哪张图；按开发者原话写
- 开发者说「你看着办」或没答时，只写一行「开发者不指定，按《前端页面》界面风格自定」

**分工表**（有需要模型判断或人工介入的步骤时才有）

**做不成的时候**
<有分工表时把第四列汇总成三句话；没有时写拉不到数、写不进库时用户会看到什么>

**需要你准备的**（有才写）
- <账号授权 / 密钥 / 示例数据 / 群或机器人>：用在哪一步，缺了影响什么

**费用与副作用**

- 制作中的测试：冒泡与真跑约 <N> 积分（查不到单价写「费用未知，跑完告诉你实际花了多少」）
```

### Studio 上线范围正文

```text
**上线范围**
- 请通过当前方案的确认卡确认内容；确认后按本页及已有授权自动制作、检查、定版和发布，完成后可在在线预览使用
- 方案内容变化时会展示新版并重新请你确认，确认前不继续制作；检查未通过或结果未知会说明原因
- 只执行本页及已有授权范围内的动作；未列出或超出估算的费用、对外发送或正式数据写入会先向你确认
- 用的人：<谁>
```

### 普通宿主上线范围正文

```text
**上线范围**
- 先在开发者中心的「在线试用」里验收，你说「可以上线」再定版应用；发布到目录由你在发布管理页操作
- 用的人：<谁>
```

### Studio 确认规则

- 通过 `studio_read_creation({})` 读取 `proposal.status=confirmed`，且当前 `version`、`digest` 与 `confirmationCommandId` 的精确原生 accepted receipt 匹配后，才能进入工程。draft、卡已提交、自然语言「可以」、HTTP200 或模型总结均不是准入证据。
- 修改正文、费用/副作用或 acceptance.json 任一内容都使旧确认失效；用 `studio_write_proposal` 提交新 version，宿主计算新 digest，展示新版并等待新的原生确认。新确认前不 scaffold:init、不建业务资产、不改业务源文件，不能凭旧回执直接继续。
- 当前精确确认只批准本页列明的范围；费用与副作用必须展示，既有自动交付授权在原范围内沿用，未列出或明显超出估算的动作另行确认。确认后的交付入口仅为 `studio_deliver`，后续只由 `studio_read_creation` 查询原操作，不增加人工发布步骤。

### 普通宿主确认规则

- 开发者回复「可以」或等价表述即视为确认，进 G2；回复里有改动就改页，改完不用再问一遍，直接做。
- 开发者对这一页说「可以」，即同意其中列出的费用与副作用，包括制作中的冒泡、真跑和自动化试跑；之后一路做到开发者能在「在线试用」里验收，不再逐项确认。预览通过后的应用定版仍要开发者再说一次「可以上线」。确认页没列的上线、花钱、对外发送动作不得执行。

### 共用内容规则

- 「会存下来的东西」必填，至少一张表：每个应用都必须有数据模板和至少一张业务表，没有业务表时抽取模板会被平台拒绝。列出每张表的表名、字段、选项列的全部取值与默认值，照抄开发者原话。只展示、看起来不用存东西的应用也要想清楚存什么，例如拉取到的数据快照（看过的比赛、报表结果）、用户的收藏或常用筛选、查看记录，和开发者确认后写进这一节。定下的每张表都要有实际写入它的页面、后端接口或路线，不能只为通过检查建一张没人写的表。
- 只有规则步骤的应用去掉「分工表」一节，其余各节照写。
- 「费用与副作用」这一段不能省。费用一律写积分，不写 token；算法见 [../reference/平台对象速查.md](../reference/平台对象速查.md)「积分怎么算」，查不到单价就写「费用未知，真跑后告诉你实际花了多少积分」，不编数字。
- 「需要你准备的」只列开发者本人才能提供的东西，写进方案页的 `needs` 一节。
- 「界面」一节确认后就是页面的**最高依据**，高于脚手架预置件和默认外观，G5 按它做、G6 按它验；开发者给的截图、参考链接放进方案页，路径写在这一节。
