# PRD：① 交给开发者的一份文档

PRD 是开发者确认过的「要什么、不要什么、能不能做」。② 照它出方案，③ 照它做，④ 照它验收，后面所有段都以它为准。开发者懂业务、不懂代码，所以每一节都从业务讲起，用开发者的词，不出现 FA、TPE、工具集、Runtime、资产编号。

PRD 写进方案页 `docs/proposal/index.html`（统一版式见 [../reference/开发者中心与工作区.md](../reference/开发者中心与工作区.md)「方案页」），同时在聊天里发交接消息。

## 有哪些节

| 节 | 写什么 | 写进方案页的哪里 |
|---|---|---|
| 你要的是什么 | 要解决的业务问题、做成后有什么不一样；这一轮做到哪一步 | `.pv-goal` 与「开发内容」开头 |
| 谁来用 | 给谁用、多久用一次、在应用里做什么、看到什么（写法见 [谁来做.md](谁来做.md)） | 「开发内容」 |
| 每一步谁来做 | 每条路线的脚本、模型、人三色步骤，模型写档位和每次花费（写法见 [谁来做.md](谁来做.md)） | `#business-process` 的 `.pv-steps` |
| 做不成的时候 | 把各路线「做不成怎么办」一列汇总成三句话；只有脚本步骤时写拉不到数、写不进库时使用者会看到什么 | `.pv-fallback` |
| 要做的功能 | 刚需和非刚需；每个刚需按下面「放进去 → 拿出来」写；非刚需一句话，写这次做不做 | 「开发内容」 |
| 能不能做 | 每个要做的事：用平台现成的 / 要新做 / 做不到，附依据（真调拿回来的东西、实测用时） | 「开发内容」 |
| 做不到的和替代 | 为什么做不到、替代后有什么不一样；要开发者选的做成选择题 | 「开发内容」 |
| 界面 | 参考、第一眼看到什么、整体感觉、各页面放什么（见下面「界面」） | 「开发内容」 |
| 会记下来的东西 | 记哪些东西、存在哪张表、有哪些内容、谁写进去、谁能改 | 「开发内容」 |
| 自动发生的事 | 什么时候自动做什么；没有就写「没有，全部是使用者点了才做」 | 「开发内容」 |
| 要从外面拿的数据 | 从哪个平台拿什么、每次多少钱、要开发者或使用者做什么（授权、分享） | 「开发内容」 |
| 这次不做的 | 明确排除的东西，以及放到哪一期 | 「开发内容」 |
| 花多少 | 做这个应用：已花的、预计还要花的、上限；上线后：每用一次约多少、按用量每周约多少 | 「开发内容」 |
| 按默认补上的 | 开发者回「是」「按推荐」「你看着办」、按推荐定下的，在原处标「按默认」；开发者没回的不算，不写进 PRD 当已定 | 原处 |
| 选择题 | 编号，附推荐答案和选了会怎样（写法见 [选择题与判断题.md](选择题与判断题.md)） | 「开发内容」末尾，答过的写答案 |
| 要你提供的 | 材料、账号、授权、数据分享，每样写清用在哪一步、缺了影响什么 | `#needs` |
| 费用与副作用（不能省） | 会调用：<外部工具名>，每次约 N 积分；制作中的测试：冒泡与真跑约 N 积分；会写入 / 发送：有就写，没有写「不会向外发送任何东西」 | 「开发内容」 |
| 上线范围 | 先由 AI 按验收条目逐条测（页面在本机版上测，业务结果在开发者同意部署后真跑验）、交验收报告，开发者看完说「可以上线」才上线，这一版成为开发者自己的正式版；发布后已安装的使用者会更新到这一版，发不发、发给谁由开发者在发布管理页定 | 「开发内容」 |

费用一律写积分，不写 token；算法见 [../reference/平台对象速查.md](../reference/平台对象速查.md)「积分怎么算」。查不到单价就写「费用未知，真跑后告诉你实际花了多少积分」，不编数字。

## 放进去 → 拿出来：每个刚需怎么写

开发者最能判断的是两头：要用到的东西自己有没有，拿到的结果是不是自己要的。每个刚需写成一组：

```text
刚需 2. 生成一份能直接发给商家的分析报告　[已试过，能做]
放进去：确认好的门店和官方账号；小红书上这家店的笔记和作者粉丝数；周边同类店、城市热门内容、关键词数据
拿出来：中文、英文对外报告各一份，开头列数据缺口；内部版一份；可以下载（附真实样例节选）
中间：先把公开信息一次查齐，再只根据查到的写报告；页面显示各部分进度，做完点「查看分析报告」。
会停下的情况：某类数据查不到不停，写进数据缺口继续。
这样算对：每个数字说得出来源；缺的数据写在缺口里，不靠猜补。
这样不行：对外报告出现工具名、接口名、价格；把互动量说成到店人数。
怎样算做成：5 个测试商家都能出报告；对外报告里搜不到上面那些词；需求方读完觉得能直接发给商家。
```

- **放进去**：这个功能要用到的东西，都用业务话写：使用者填的、上传的，前面功能的结果，从外部平台拿的，读的哪些记录。
- **拿出来**：使用者最后拿到的东西，带一个样例。① 里已经真拿到的写真实数据；要模型写的内容还没做出来，标「预期」。
- **中间**：一两句话说清怎么开始、做了什么、结束时使用者能选什么。
- **会停下的情况**：什么时候不给结果、使用者会看到什么。没有就不写；情况多时列成「遇到的情况 / 应用怎么做」小表。
- **这样算对 / 这样不行 / 怎样算做成**：三行都必填。「这样不行」写反向案例：哪些情况不算、哪些做法不能接受。「怎样算做成」写照着做、应该看到什么，② 据此定验收条目。
- 标题后面标核实结论：「已试过，能做」「能做」「要新做，没试过」「做不到，见替代」。

### 线上应用会出现的情况和写法

| 分组 | 情况 | 写在哪、怎么写 |
|---|---|---|
| 怎么开始 | 使用者点按钮、在聊天里发起 | 「中间」第一句：你点什么、填什么 |
| 怎么开始 | 到点自动、有新记录时自动 | 「中间」第一句写「每天 9 点自动开始」「有新笔记时自动开始」；标限制：中途不能停下等人、不能上传文件、最短 60 分钟一次。「怎样算做成」分两条写：同一条路线发起一次能出对的结果（④ 验）；到点或有新记录时真的自动开始（上线后开发者在 ⑤ 打开规则验） |
| 中间 | 模型判断或写内容 | 「拿出来」放模型写出的内容样例；「中间」写依据什么写。模型不能和使用者来回对话 |
| 中间 | 从外部平台拿东西 | 「放进去」写从哪个平台拿什么；要使用者自己授权、要付钱的单独标出 |
| 中间 | 中途停下等使用者补信息 | 「会停下的情况」写「停下来请你补填……」 |
| 中间 | 按情况走不同的路 | 「中间」写「如果……就……」；超过两种情况就列小表 |
| 中间 | 几件事同时做、一批东西逐个处理 | 「中间」写「一个一个……」「同时……」；写清一次最多处理多少条 |
| 中间 | 交给 Agent 接手 | 「中间」写「你可以手动交给 Agent 继续」；只能使用者手动交 |
| 中间 | 上传文件、结果里带附件 | 「放进去」或「拿出来」写清是什么文件 |
| 怎么结束 | 直接给结果 | 「中间」最后一句写「结果直接给你」 |
| 怎么结束 | 等使用者确认 | 「中间」最后一句写可选的几种：接受 / 不要 / 交给 Agent / 重新生成；重新生成就是再用一次这个功能 |
| 记录 | 读哪些记录、存到哪 | 「放进去」写读了哪些记录；存到哪统一写在「会记下来的东西」 |
| 做不成时 | 停下，或记下来接着做 | 「会停下的情况」写停下时看到什么；记下来接着做的写在「中间」；要重试的写「重试一次」（平台不会自动重试） |
| 跨次、跨天 | 记住上次做到哪 | 「中间」写「接着上次做，不重复」 |
| 跨次、跨天 | 跨好几天、中间要使用者到外部平台手动做 | 拆成几个刚需，后一个的「放进去」写前一个的结果，中间写一句「你照方案在聚光后台投放，2 天后回来」 |
| 记录页 | 只是增删改记录、不走流程 | 不写放进去 → 拿出来，单独一句；流程写进去的内容在页面上只能看、不能改 |

## 界面

开发者给过截图、原型、参考应用、草图，或在对话里说过页面长什么样（有哪些页、每页放什么、怎么排），一并记下，照它写。开发者没说过页面长什么样时，写 PRD 前**必须**主动问一次，三个问题一起发、不逐个追问：

- 有没有喜欢的参考：网站链接、截图、同类产品，或「像 X 那样」；
- 使用者打开应用第一眼要看到什么（数字、待办、最新结果、内容库……）；
- 整体感觉：信息密集的工作台还是简洁大方，偏专业、活泼还是高端；有没有品牌色、Logo。

开发者答了什么就照抄进这一节。开发者给的截图、参考文件放进 `docs/proposal/` 下，路径写在这一节。

```text
界面
- 参考：<网站链接 / 截图 / 原型文件，没有写「无」>
- 第一眼看到：<开发者原话>
- 整体感觉：<……；品牌色、Logo>
- <页面名>：放什么、怎么排、参考哪张图
```

开发者说「你看着办」，只写一行「开发者不指定，按《前端页面》界面风格自定」。这一节确认后就是页面的**最高依据**，高于脚手架预置件和默认外观。

## 会记下来的东西

```text
| 记什么 | 存在哪张表 | 有哪些内容 | 谁写进去 | 谁能改 |
|---|---|---|---|---|
| 项目 | projects | 项目名称、商家名称、确认的门店、报告文件、内容 | 应用自动写 | 只能看 |
| 内容采纳 | content_adoptions | 哪篇被复制、采纳或不采用，不采用的原因 | 人① 使用者 | 使用者写 |
```

- 必填，至少一张表：每个应用都必须有数据模板和至少一张业务表，没有业务表时抽取模板会被平台拒绝。只展示、看起来不用存东西的应用也要想清楚存什么（拉到的数据快照、收藏、常用筛选、查看记录）。
- 选项列写全部取值和默认值，照抄开发者原话。
- 每张表都要有实际写入它的页面、后端接口或路线，不为通过检查建没人写的表。
- 写一句「在线预览里记下的东西，正式上线后不会带过去」。

## 版本、批注和确认

- 开发者用聊天回复批注：指出是哪一节、哪一条、哪里不对。需求方的意见由开发者转来，或开发者让你直接按需求方的文档改。
- 每出新一版：先按方案页规则把当前页存成 `history/v<N>.html`，再改 `index.html`、`data-version` 加一；改过的词句用 `<mark class="pv-changed">` 包住；交接消息的「刚做完」写这一版改了哪几处。
- 开发者回「确认这一版」或等价表述（「可以」「没问题，开始吧」）即确认。回复里同时有改动时，改完再发一版，请开发者对改动处确认一次。
- 确认 PRD 即同意其中列出的费用与副作用和花费上限；之后制作中的冒泡、真跑、自动化试跑不再逐次确认。累计花费到上限的 80% 时按 [交接消息.md](交接消息.md) 停下问。

## 写完自查

- 每个刚需都有放进去、拿出来、这样算对、这样不行、怎样算做成，和核实结论；
- 「谁来用」写了给谁用、看到什么，提到的别人参与已写成使用者自己的一步或写进「这次不做的」，「每一步谁来做」每一步都标了脚本、模型或人，模型步骤写了档位和花费；
- 花费上限、上线后的用量都有答案（开发者答的或按默认）；「费用与副作用」一节在，查不到单价的写了「费用未知」；
- 做不到的都在「能不能做」里写明，并有替代选择题；
- 「要你提供的」和选择题里没有 `SKILL.md` 第 3 节禁止请开发者确认的事：批准改生产库或平台库、改别人（包括使用者）的安装记录或数据、提供凭证路径、重连开发能力、决定测试范围、修环境；有就删掉，改由你按 `SKILL.md` 第 7 节处理；
- 没有开发者看不懂的词：搜一遍 FA、TPE、工具集、Runtime、schema、编排、冒泡、资产 ID，有就改成业务话。
