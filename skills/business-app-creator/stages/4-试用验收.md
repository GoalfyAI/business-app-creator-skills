# ④ 试用验收（工作区阶段 G6）

开发者以使用者的身份，用真实数据把应用真正用一遍，逐条告诉你对不对，最后说「可以上线」。这是开发者最能拿捏的一步。你先部署、先用真实数据跑、先按验收条目自己试一遍，没过的先修；你自己没试通过的，不交给开发者试。验证只有两层：冒泡管改，真跑和开发者验收管收。

## 1. 进入条件

- ③ 交棒：应用根 `npm run verify` 全绿，每个功能都做好了或标明没做成。
- 本轮需求已全部实现：在桌面开发者中心里执行 `prepare_business_app_skill` 返回的完成版命令，开发者就能在「演示预览」看本地完成版（见 [../reference/开发者中心与工作区.md](../reference/开发者中心与工作区.md)「演示预览为空」）。

## 2. 段里怎么做

### 2.1 部署

场景包不必先上线：挂着你本人的场景包草稿也能部署。

1. 先调 `business_ui_bundle(action="download_template")` 核脚手架门槛，需要升级时完成迁移与验证。
2. 在应用根目录运行 `npm run verify:release`，全部检查通过后生成 `.pack/business-ui-bundle.tar.gz`，按这个包算 `source_sha256` 与 `size_bytes`。**禁止**用 `npm run pack`、直接运行打包脚本或手写 tar 代替 `verify:release`，那样会跳过发布检查。
3. `business_ui_bundle(action="ship", task_id, business_ui_id, source_sha256, file_name="business-ui-bundle.tar.gz", size_bytes)`（`file_name` 只写文件名，带目录会被拒）：
   - 返回 `status=upload_required`：按 `upload_url` 与 `headers` PUT 源码包原字节，原参数加 `bundle_key` 再调；
   - 返回未终态：原参数加 `deployment_id` 再调，服务端每次最多等约 45 秒；**禁止**去掉 `deployment_id` 重调，那会重新起容器；
   - 到 `success` 为止。`steps` 标明每步 done / skipped / resumed。明确失败且原因不在源码包时，再用 `prepare_upload` / `complete_upload` / `deploy` / `status` 单步排查。
4. `business_ui_manage(action="get")` 核对部署已写进当前草稿；记下 `deployment_id`、`source_sha256`、`deployed_scaffold_version`。`entry_url` 是开发者容器地址，只用来核对绑定，不打开、不发给任何人。`deploy` 返回带 `scaffold_upgrade_notice` 时原样记进开发记录，交付报告要写。

### 2.2 用真实数据跑

有模型步骤，或路线要读写应用库、调外部接口时做；只有脚本步骤且 ③ 的 `full_run` 已覆盖时可省，省了写明原因。用 ① 里开发者给的真实样例。PRD 已列的费用直接执行；没列的、会对外发送或写正式数据的先说明再执行。

1. `manage_goalfymax_project(action="run", task_id, idempotency_key, scenario_package_ids=[<场景包当前草稿或上线版本的物理行 ID>], submit_data={…}, business_ui_id=<应用家族 ID，路线读写应用库时传>, business_ui_data_space="workspace")`。返回 `BUSINESS_UI_NOT_ONLINE` 或要求先上线时，补 `business_ui_data_space="workspace"` 重跑，不要为真跑去 finalize。`workspace` 跑你刚部署的版本，读写开发工作集，和「在线试用」是同一份库，应用不用先上线；路线不碰应用库就不传 `business_ui_id`。
2. `manage_goalfymax_project(action="wait", project_id)` 等到终态，中途表单或审阅用 `reply`；以 `route_runs` 里各路线的状态为准（路线完成后项目可能仍显示 running），`succeeded` 表示这条路线真跑通过，结单门会把它记为这条路线的证据。
3. 对路线里每条 TPE 调 `otpe_manage(action="verify", task_id, tpe_id, project_id)`，`passed` 即完成；③ 只差运行证据的 TPE 必须在这里补齐，读写应用库的路线不能用在线试用人工验收、冒泡或结单门豁免代替这一步。
4. `get_project_execution_logs(action="workflow_trace", project_id)` 看每步，模型步骤的输出人眼核一遍；写库的结果去应用数据管理页或库里查一条。
5. 记下每个按钮这次实际花了多少（`cost_credits`），和 PRD 的估算比。
6. **回写演示示例**：③ 在阶段文档 G5 记了「待 ④ 回写」的演示和示例，从这次真跑通过的结果里选一份写回代码，去掉「示例」占位，按 2.1 重新 `verify:release` 并部署，修改记录写明。回写不算退回 ③，在 2.3 自测之前做完。

失败在同一草稿改再跑；每次只改一处，不同时改脚本和路线。

### 2.3 按验收条目自己试一遍

逐条对照 ② 定稿的验收条目，用真跑的项目、日志和应用库数据核对每条「应该看到什么」，记「通过 / 偏差」和证据；偏差先改再部署，改到你能判断的都通过。

- 按 ③ 的业务含义对应核首页、历史、详情、消息、发起、补充、提交查看、审阅及返回：名称对应同一实际事项，上传不冒充已发起，提交或受理不冒充完成，未定义产物不出现报告；加载、空态、只读、暂停、失效也核对。
- 页面上的样子和操作你看不到线上页面，只核你能拿到证据的部分；需要截图时用本地布局回归（只连本机 Mock），写明不是线上截图。
- ② 里标「要人判断」的条目（内容能不能直接对外、语气像不像、业务判断对不对），你不下结论，标「AI 判断不了，请你判断」。
- 按 [../checklists/验收清单.md](../checklists/验收清单.md) 逐条写「通过 / 不适用 + 一句依据」，做不到的列为没法验证。

### 2.4 交给开发者试

发交接消息，开头「【④ 试用验收 → 等你试用】」，附试用清单：

| # | 试一下（从哪进、用什么数据、按什么顺序做） | 这样算对 | 开发者 | 需求方 |
|---|---|---|---|---|
| 1 | 新建项目，只填「莫定标娘惹糕点」，提交 | 出现槟城的候选 | 对 / 不对：____ | 对 / 不对：____ |

同时说明：

- **在哪试**：开发者中心右侧「在线试用」，从首页进入，以 <使用者角色> 的身份逐条照做；多种人的应用，说明怎样切换或分别用哪个身份试。「在线试用」用绑定的 `business_ui_id` 换一次性凭据，带真实身份和真实路线，不需要先上线。
- **能操作什么**：哪些功能能点、哪些还不能用及原因。
- **试用里的数据**：写在开发用的一份数据里，正式版不会带过去；哪些是示例数据；试用里真实的付款和授权是真的。
- **你自己试的结果**：每条通过还是改过什么；标「AI 判断不了」的几条。
- **用真实数据跑出的结果**：本段真跑的完整结果，加上 ③ 里 `full_run` 跑出的内容，请开发者对照 ② 的预期看对不对。
- **没法验证的**：哪几项试用里验证不了（例如使用者手上的应用不随发布自动更新），为什么、上线后可能怎样，做成选择题「接受，先上线 / 等解决再上线」。到点或有新记录时自动开始的，分两步验：这里用 `business_ui_automation(bubble)` 按自动化的入口跑一次，把结果给开发者对照；`run_once` 要求应用已上线，真跑和到点触发都写进 ⑤「你要做的」，上线后验（见 [../reference/自动化.md](../reference/自动化.md)「验证」）。
- **实际花费**：每个按钮实际花了多少，和估算比；每份报告要等多久、能不能同时开几个。
- 需求方和开发者不是同一人时，请开发者把同一份清单转给需求方，两人各自标。

清单之外开发者也可以随便用，有问题直接说。你不开任何浏览器去打开「在线试用」、正式入口或登录页替开发者点。

**开发者要求先试**：你还有条目没试通过，开发者明确说要先自己试、或先给需求方试时，照开发者的要求交，但只交在「在线试用」里试，不上线、不发布：

- 交接消息开头仍写「【④ 试用验收 → 正在做】」，「刚做完」先写「按你的要求先交给你试，还有 N 条我没试通过」；
- 试用清单照常给全，没试通过的条目在「这样算对」后面标「我还没试通过：<哪里不对>，预计 <什么时候> 改好」，请开发者先跳过或只看不标；
- 开发者在这些条目上标的「对」不算验收，改好后你重试通过，再请开发者重测这几条；
- 交棒条件不变：每条都要你试通过、开发者重测过，开发者说「可以上线」才进 ⑤。开发者要在没试通过的情况下直接上线，把没通过的条目逐条做成「接受，先上线 / 等改好再上线」选择题，写清上线后使用者会遇到什么；选了「接受」的条目结论记「没试通过，开发者选了接受」，交付报告「还没验证的和风险」里写明。

### 2.5 按反馈改，只重测受影响的

- 开发者标「不对」的，改完重新 `verify:release` 并部署；修改记录写「问题 / 改了什么 / 要重测哪几条」，只请开发者重测受影响的条目，不让他把清单从头再试一遍。
- 改了场景包草稿的重新部署即可，不用上线。应用已上线过、挂载钉在旧版本号时，先 `business_ui_manage(action="update", business_ui_id, scenario_pack_id, scenario_pack_version=<场景包草稿版本号>)` 换挂到草稿再部署，否则试用仍跑旧的上线版本。
- 结果不对、要改做法的回 ③；开发者发现要的东西本身不对，回 ①。

### 2.6 阶段评分（仅 Codex）

开发者说「可以上线」之后，按 [../design/阶段评分.md](../design/阶段评分.md) 单独发一条「G6 demo 试用」评分，发完直接进 ⑤，**禁止**等评分回复。

## 3. 开发者要看、要做的

- 照试用清单逐条做，标对或不对，写一句哪里不对。
- 看真实数据跑出的结果对不对；判断标「AI 判断不了」的几条。
- 对没法验证的几项，选接不接受先上线。
- 说「可以上线」。

## 4. 不给开发者的

部署过程、`verify` 与在线检查结果、版本号、容器地址。你自己没试通过的条目不交给开发者试。

## 5. 产出与落盘

- 工单 checkpoint：场景包草稿或上线版本、`deployment_id`、`source_sha256`、`deployed_scaffold_version`、真跑的 `project_id` 与结论、每条 TPE 的 `verify(tpe_id, project_id)` 结论、开发者和需求方说「可以上线」的原话、没法验证的项和开发者的选择。
- 阶段文档 G6：试用清单逐条结论（你自测 / 开发者 / 需求方）、修改记录、验收清单逐条结论、实际花费；「阶段评分」一节按 [../design/阶段评分.md](../design/阶段评分.md) 记录。
- 方案页：「在线试用」可打开时 `status` 为 `waiting`，`.pv-you` 写「在『在线试用』里照清单试这 N 条」；入口、权限、部署问题推进不了时为 `blocked` 并写 `.pv-owner`；开发者照做通过的条目移入「已验证」，证据写部署编号与原话时间；没走到的留在「未验证」并写原因。
- 阶段标记：G6 `passed`。

## 6. 交棒条件

- 最近一次部署 `status=success`，「在线试用」可用；
- 每条验收条目都有结论（对 / 不对已改并重测为对 / 没法验证或没试通过且开发者选了接受），开发者以使用者身份照做过；
- 验收清单逐条有结论，没法验证的项已记录；
- 读写应用库的路线，每条 TPE 最近一次 `verify(tpe_id, project_id)` 为 `passed`；
- 开发者（和需求方）明确说了「可以上线」或等价表述。

## 7. 出问题怎么办

| 现象 | 先看 | 回到 |
|---|---|---|
| 部署 `status` 失败 | 返回里的构建日志尾部；本地先 `npm run verify:release` | ③ |
| 部署被脚手架闸门拒绝 | [../reference/脚手架与预置件.md](../reference/脚手架与预置件.md) 错误码表 | 升级后重来 |
| 「在线试用」打不开或提示未就绪 | `PREVIEW_NOT_READY`：当前草稿没有部署成功的记录，在当前草稿行重新 `ship` 到 `success`；再核对 `business_ui_id` 与环境；`ship` 已成功仍未就绪才报平台问题 | 本段 2.1 |
| 定版前 `resolve` 报「还没有上线版本」 | `resolve` 只认上线版本，定版前本来就这样；草稿验收走「在线试用」，不记 platform_blocked，也不为拿入口去 finalize | 本段 2.4 |
| 真跑卡 `waiting-input` | 用 `reply` 回表单；没人答就是正常挂起 | 本段 |
| 真跑返回 `BUSINESS_UI_NOT_ONLINE` | 传了 `business_ui_id` 没传 `business_ui_data_space="workspace"`；补上再跑，不需要 finalize，不记 platform_blocked | 本段 2.2 |
| 真跑返回 `BUSINESS_UI_NOT_DEPLOYED` | 还没有你本人部署成功的版本，或 `business_ui_id` 传成了版本行 ID；先 `ship` 到 `success`，用家族 ID 重跑 | 本段 2.1 |
| 真跑内容不对 | 模型步骤提示词、模型档位或输出字段 | ③ |
| 页面行为不对 | 页面块或生成页 | ③ |
| 开发者说要的东西本身不对 | — | ①：改 PRD，只重做受影响的部分 |
| 疑似平台问题 | 走不下去才立即 `submit_dev_feedback(blocking="blocked")`；能绕过就继续，记进开发记录，⑤ 交付时汇总；提交后没人修按 `SKILL.md` 第 7 节的升级顺序做 | — |
