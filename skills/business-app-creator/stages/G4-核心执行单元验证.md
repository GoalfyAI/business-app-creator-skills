# G4 核心执行单元验证

本阶段的目的是**证明每个关键部件单独能用**。按《制作书》自底向上创建依赖资产、能力容器草稿和编排型 TPE，每个单元取得当前版本的真实运行轨迹。制作期只按书做，**只在冲突时停下沟通**。契约表格与脚本细则见 P3。

## 1. 进入依据

《制作书》已确认并落 `build_book`；执行结构表 `challenged=true`；正式制作授权明确。可按独立业务切片推进，**不要求**所有未来功能一次设计完。

修订已上线版本的任务先持有草稿行：内容写入被版本闸门拦截时，用 `ensure_editable_asset_draft` 取得可编辑草稿，**禁止**绕过闸门改上线版本。一切内容修改只发生在草稿行上。

进入本阶段先把 `docs/stages/G4-核心执行单元验证.md` 的 `status` 改成 `in_progress`、`WORKSPACE.md` 的 `current_stage` 改成 G4。

## 2. 本阶段建设

### 2.1 制作期纪律

不重新提问、不重新提案；命名、代码组织、等价实现自主决定。**必须停下沟通的五种冲突**：制作书与实时 Schema 或 `get_diagnosis_doc` 不符；平台不支持制作书的模式；按书做会触碰红线；发现画像、旅途、交付角色要变；制作书自相矛盾。沟通时列冲突点、双方依据、候选处置，**不静默取舍、不绕过、不自作主张改书**。冲突解决后整份重写制作书并重新确认。更好的想法记工单备忘。

同范围的修代码、改字段映射**不重复确认**。只在四种情况回来问：原设计无法成立；质量或成本取舍改变；必须增加最终用户介入；更换已指定能力。

### 2.2 读契约

`get_diagnosis_doc` 按主题读服务端当前契约，需要 `task_id`，主题表见 P3 第 9.1 节。读取纪律：确认要做编排型 TPE 后读一次 `otpe_authoring`；动笔写任何脚本前**必读** `otpe_single`；需要带业务事件的单节点路线或多节点依赖图时读 `otpe_multi`；写第一条脚本前、拆 FastAgent 前、设计数据面前各读一遍 `counter_examples`；命中并行、文件、失败降级、Agent 介入时先读示例索引再读匹配的那一个。同一主题在同一任务里**只通读一次**。契约与实时 Schema 或服务端报错冲突时，**以实时 Schema 和报错为准**，记录差异并停止提交冲突字段。

### 2.3 按依赖顺序准备资产

顺序固定，**不得**跳跃：工具组与授权卡；FastAgent；工具集；普通任务点；能力容器草稿；编排型 TPE 创建与挂载；其他关联与业务路线。每创建一步都反读名称、关系、状态、权限。

1. **工具组与授权卡。** G2 已注册的直接复用。新接入按 G2 第 2.4 节的链路做：`preview_tool_group` 后 `register_and_refresh_tool_group`。需要最终用户各自授权的工具用 `create_auth_card` 配卡，参数用工具组注册返回的授权绑定标识，**不是**工具组标识；这是正式依赖，不是可选项。
2. **FastAgent。** 按执行结构表落实职责、输入输出、关联工具组，用 `create_fast_agent` 创建；长提示词经 `prompt_content_url` 提交。创建或克隆完成后**立即反读返回值里的 `mr_name`** 记入执行结构表，它是脚本里 `tool()` 的调用名，含创建后才有的物理 ID，**禁止**推算或拼接。被圈定的关键 FastAgent 提示词定稿前**必须**执行样例选择三步：先问开发者有无参考资料，没有再自行调研真实样本；生成两到三种取向的具体样例并标来源；让开发者在具体样例之间选，**不要**在抽象形容词之间选。选择结果同源编译进提示词、结果检查表的验收判定、渲染决策。FastAgent 执行要用的规范文件挂到它自己名下并在提示词里写明何时读。
3. **工具集。** `create_toolset` 装入工具组或 FastAgent；使用指南只写工具之间的关系：适用条件、输入衔接、结果审视、失败处理。已固化在脚本里的调用顺序**不要**再写一份。
4. **工具集上线第一道检查。** 任何编排型 TPE 创建前：确定完整的预加载工具集清单；对本轮新建或导入的工具集做安全的运行时测试；全部无失败后调 `online_toolsets`；反读确认全部已上线。任一测试失败、余额不足、授权中断，保留原资产和进度，恢复后从未完成的验证继续，**禁止**跳过验证直接上线。开发者已有的离线工具集可以关联但运行时不会加载，发现时**必须**停止并告知，**禁止**擅自上线别人的资产。
5. **普通任务点。** `create_tpe`，前提是工具集已上线。
6. **共享资产先克隆。** 被其他容器引用的工具集、FastAgent、普通任务点先 `clone_asset` 复制，在副本上改，再更新当前容器的引用；副本调用名一律从返回值反读。

### 2.4 创建能力容器草稿

`scene_package_manage(create)` 建离线草稿，默认克隆官方基础包，**必须**立即反读继承到的能力、关系和告警，只改真正需要改的部分。写 `apc_skill`，长内容经 `apc_skill_url`，反读时按 G3 第 2.6 节的大纲检查正文完整性、颗粒度与禁写内容。场景 Skill 文件先 `file_to_url(purpose="skill_file")` 换取引用，再 `scene_package_manage(update)` 绑定，**默认合并**，整体替换会覆盖整个目录。给依赖资产补挂用 `upload_skill_files`，它的缺省是整体替换，补挂时显式传 `skill_files_mode="merge"`。开发者给了 Logo 时先 `file_to_url(purpose="scene_package_logo")` 再 `update_scenario_package_logo`。

保存容器标识，后续修复**更新同一草稿**，**禁止**新建平行资产绕过错误。空容器建好**不算**完成。

### 2.5 创建编排型 TPE

前提：草稿容器存在，依赖工具集已通过第一道检查。

**脚本来源按变更范围选**：短脚本或首次提交传内联 `script`；长脚本或多轮修改放服务端可访问的 HTTPS 地址经 `script_url` 提交；只改一个片段用 `script_patch`；外部 Agent **禁止**使用 `script_file`。只改输入输出定义或依赖时**不要**顺带重传脚本。

**按执行结构表的执行者写脚本**：规则步写成代码；模型自主步用 `tool()` 调 FastAgent 并带重试与判定；模型加确认步产出候选进中途表单；最终用户步用中途表单收结果；回退链写成分支；已声明并行组的步骤按 `otpe_example_parallel` 落实。脚本承担确定性衔接；FastAgent 承担需要看结果再决定的完整环节。脚本里出现 `tool → FastAgent → tool → FastAgent` 的长链，多半是把一个环节切碎了。

**业务事件按条件硬门写**：契约和 `emit_business_event` 调用要么同时为空，要么同时构成完整闭环。一旦声明，首个业务动作前发 `stage_started`，每条可达 `return` 前发 `stage_result`，受控业务失败分支发 `stage_failed`；`artifact_ready` 与 `delivery_ready` 由 Runtime 自动发布，脚本**不得**声明。每类事件的 `payload_schema.required` 必含平台字段，表见 P3 第 10.4 节。契约经 `otpe_manage(create|update, business_event_contracts=[...])` 随执行契约写入，`event_key` 用字面量，`payload` 是对象，`additionalProperties` 为 `false`。**禁止**在每个 `tool()` 后机械发事件；**禁止**为进度条声明 `stage_progress`。

**文件交付链**：FastAgent 生成的文件落在它自己的会话目录，不会自动出现在本节点产物目录。要随交付给用户的文件**必须**在最终节点收进 `ctx.output_dir`，以 `workspace-file-path` 在 `output_schema` 声明，并进入 `delivery.mapping`。交付守卫只登记本节点产物目录内的文件，入口表单上传的、上游传来的、会话目录里的文件原样放进交付字段一律被拒；修法不是补声明或找可信来源，而是复制进 `ctx.output_dir`。跨运行引用先前产物**必须持有绝对 workspace 路径**，用"当前目录加命名约定"拼路径第二次运行必然找不到。

**数据集读写写在脚本里**：需要执行中取数时 `tool("GOALFYAI_FASTAGENT_Business_app_fastagent", operation="read", query=..., _output={...})`，mr_name 以 `get_asset(toolset)` 反读为准，`_output` 必含 `found` 并只声明本路线消费的切面，每条业务流至多一次读，`found=false` 回退表单值**绝不因空数据 fail**；收尾 `operation="write"` 带 `context_hint` 唯一键；`business_app_dataset` 工具集进预加载清单。形状见 P4 第 3 节。

**来源类编排型 TPE**必须保留"结论、证据"链：上游把结论与证据标识、来源地址、域名、日期作为结构化对象整体传递；下游每条结论带非空证据引用，来源字段只能复制真实值；根级声明证据契约。

**运行前先查对外副作用**：发信、通知、发布、扣费、创建远端对象、写正式业务状态**必须**用演练标记挡住并返回满足输出定义的未执行状态。**禁止**用演练标记跳过普通工具调用或输入输出管路。

**每张表单落一份 Skill 文件** `forms/<form_id>.json`：`form_id`、`title`、字段的 `label`、`description`、控件提示、顺序，与 `business_forms` 字段一一对应，随容器上传。

**Preview 与保存**：`otpe_manage(preview)`，按返回的字段、工具、路径和确定性规则修**同一份草稿**；`create` 或 `update` 保存后反读标识、命令标识、输入输出定义、事件契约、依赖和版本。

**执行结构表同步**：修改任何脚本或结构后**必须**同步更新对应条目并回写工单快照；条目指纹变化自动回 `pending`，下一次挑战与验收只处理回退条目。脚本与表不一致时先修一致，**禁止**带着不一致进入验证。

### 2.6 单元验证

每条编排型 TPE 取得当前版本的终态轨迹：

1. `otpe_manage(bubble)` 启动并轮询到终态，**必须**复用同一个运行标识。单条冒泡每次都是独立项目与沙箱：脚本要读上游产物时，先 `file_to_url(purpose="tool_test_fixture")` 上传一份，在首次启动的 `workspace_files` 里挂进去，`workflow_input` 的文件字段留空占位；冒泡报"文件找不到"多半是这一层，不是脚本错。
2. 检查终态报告：`steps[]` 逐步看 `status`、`error`、`elapsed_ms`、`repeated_error_count`、`arguments`，`repeated_error_count>=2` 是重复撞同一错误，先换策略再重跑；再看 `coverage`、`unreached_tools`、`final_output`、`error`。`run_trace` 只是摘要，不作判据。带业务事件的读 `run_evidence.business_events`：核对声明事件、已持久化事件、缺失必需事件、顺序；只有数据库持久化成功的事件计入，本次路径缺 `stage_started` 或缺终态事件时冒泡**必须**失败。
3. 读编排型 TPE 验收检查清单做语义验收；不通过就更新原编排型 TPE 并重跑。
4. 按已确认样例核查真实内容；局部修改的三项各有依据：旧产物可读取、指定内容保留、目标内容改变。FastAgent 桩或 `success` **不能**代替。
5. 桩值可能触发脚本为真实异常准备的降级分支，成功路径反而没验到。处置是换成与桩值对得上的输入重跑，不是改脚本迁就桩，更不是拿拦截分支通过当成功。

**运行返回"执行完成"不等于业务验证通过。** 未触达的工具和分支**必须**列为盲区；缺终态轨迹的单元落 `needs_bubble`。单条编排型 TPE 的 Preview、bubble 和语义验收属于自动制作门，**不需要**向开发者逐条申请。FastAgent 真实内容、未触达分支、外部副作用盲区留到 G5 全真统一处理。

### 2.7 联动校验

每步完成后检查联动：任务点关联变动后检查工具集是否同步；资产被替换后检查 `apc_skill` 里的引用是否失效；工具集成员变化后检查使用指南是否还准确。G2 的证据有条件复用：模型、提示、工具或上下文变化后**必须**重查，集成形态变了**不得**照搬旧通过。此时**不要**向开发者宣称容器可以直接使用。

## 3. 给开发者看什么

开发者中心中栏从本阶段起显示本地跑着的业务应用，`render_type` 为 `business_app_iframe`，指向 `./run-dev.sh` 起的 5175；应用没起来页面就是空的，所以本阶段全程保持服务在跑。文档照写，作为记录。

记入 `docs/stages/G4-核心执行单元验证.md` 的单元验证一节：当前单元的业务职责、预期与实际产物对照、成功与失败路径、耗时与费用观测。脚本以标注步骤说明每一段为什么存在。内部日志按需展开并脱敏。

## 4. 要确认哪些边界

见 2.1 的四种情况。其余按书执行。

## 5. 门禁 Checklist

- `G4-01` 资产身份、版本、挂载、依赖上线状态、授权均经反读；未修改其他应用依赖的共享原件。
- `G4-02` 脚本、结构表、行为契约一致；普通输入与原产物、版本、修改约束都到达实际消费节点；输出字段覆盖成功与失败出口。对应 U2-06、U5-02。
- `G4-03` 单元有当前版本的终态轨迹；关键路径可用；未覆盖路径明确列出。空循环**不算**覆盖。
- `G4-04` 按已确认样例核查真实内容；局部修改的三项各有依据。FastAgent 桩或 success **不能**代替。对应 U5-02、U5-03。
- `G4-05` 文件真实存在且来源正确；事件与结果各司其职；受控业务失败、技术异常、合法无产物未混为成功。
- `G4-06` 副作用演练边界与实际调用一致；影响后续的变更已重查关联项。

## 6. 证据与结论

产出 Preview 记录、保存反读、Bubble `run_id`、事件持久化证据、真实产物对照、盲区清单。落工单检查点 `needs_bubble` 与执行结构表快照。本阶段的出口是"制作完成"，不是"验证通过"。

**阶段出口动作**：门禁全过后，把 `docs/stages/G4-核心执行单元验证.md` 的 `status` 改 `passed`，写 `stage_exit`，从存在 business_ui 草稿起打包部署一次，再把 `WORKSPACE.md` 的 `current_stage` 改成下一阶段并把下一阶段文档置 `in_progress`，最后 `workspace_push` 整个 Workspace；开发者中心自动切换。顺序见协议四第 6 节。

## 7. 失败回退

单元设计不成立：回 G3。依赖能力不可用：回 G2。修同一份资产，**禁止**反复建新资产规避问题。
