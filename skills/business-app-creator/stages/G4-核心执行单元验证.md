# G4 核心执行单元验证：确定"每个部件实际成立"

> 阶段层文件。旧 S3 制作与 S4 单体验证合并为"一个单元的完成闭环"。方法在 [P3](../modules/P3-执行形态与路线制作.md)（依赖准备、FastAgent、编排型 TPE、事件、知识）、[P2](../modules/P2-能力发现与模型试验.md)（MCP 接入与取样）、[P6](../modules/P6-验证与证据裁决.md)（Preview / Bubble / 证据裁决）。

## 1. 进入依据

当前切片的运行设计、边界与验收标准已确认；正式制作授权明确。可按独立业务切片推进，不要求所有未来功能一次设计完。

## 2. 本阶段建设

1. **按依赖准备**：工具组与授权卡 → FastAgent → 工具集 → 按需普通任务点（P3 的 S3 §1；上线两道检查；共享资产先克隆再改，协议约束 11）。
2. **创建或复用能力容器草稿**（场景包草稿）：反读继承关系；不是空容器建好就算完成（P3 的 S3 §9）。
3. **编排型 TPE**：草稿容器与已就绪依赖存在后创建；脚本承担确定性衔接，FastAgent 承担需要看结果再决定的完整环节；按 G3 执行结构表的 executor 写：规则步是代码、自主步 `tool()`/FA 带重试与判定、确认步产候选进中途表单、人工步用中途表单收结果；回退链写成分支；长规范放到执行者可读取的位置并验证加载（P3 的 S3 §4、§8）。
4. **单元验证**：每个单元做 Preview、保存反读、单体验证（P6 的 S4 §2.1–2.3）；检查真实输入输出、文件、事件、已覆盖与未覆盖分支。Bubble 只是证据之一。
5. **复用 G2 证据的条件**：模型、提示、工具或上下文变化后须重查；集成形态变了不能照搬旧通过。
6. **维护对应关系**：设计步骤 — 脚本步骤 — 实际轨迹；修原草稿并更新结构表（条目回 pending → 增量重挑战），不靠反复建新资产规避问题。

## 3. 给开发者看什么

当前单元的业务职责、预期 / 实际产物对照、成功 / 失败路径、耗时与费用观测；脚本以标注步骤说明"这一段为什么存在"。内部日志按需展开并脱敏。

## 4. 要确认哪些边界

只在原设计无法成立、质量 / 成本取舍改变、必须增加人工、或更换已指定能力时回来问；同范围的修代码、改字段映射不反复确认。

## 5. 门禁 Checklist（G4）

- `G4-01` 资产身份、版本、挂载、依赖上线状态、授权均经反读；未修改其他应用依赖的共享原件。
- `G4-02` 脚本、结构表、行为契约一致；普通输入与原产物 / 版本 / 修改约束都到达实际消费节点；输出字段覆盖成功与失败出口（U2-06/U5-02）。
- `G4-03` 单元有当前版本的终态轨迹；关键路径可用，未覆盖路径明确列出；不能用空循环冒充覆盖。
- `G4-04` 按已确认样例核查真实内容；局部修改的"旧产物可读取、指定内容保留、目标内容改变"分别有依据，不能用 FA 桩或 success 代替（U5-02/U5-03）。
- `G4-05` 文件真实存在且来源正确；事件与结果各司其职；受控业务失败、技术异常、合法无产物没有混为成功。
- `G4-06` 副作用演练边界与实际调用范围一致；影响后续的变更均重查关联项。

## 6. 证据与结论

产出：资产清单、结构表、单元轨迹、实际产物与检查结论；按 [编排型 TPE 验收检查清单](../checklists/编排型TPE验收检查清单.md) 逐条裁决；工单 `needs_bubble` / 单元 checkpoint。**G4 通过不宣称整包可用**：整条路线与应用回流尚待 G5。

## 7. 失败回退

修复同一资产，不换新资产；原设计不成立回 G3；能力不可用回 G2。

## 继承与调整

S3 制作 + S4 单体验证合并；保留底层契约规范（P3、references）。主责 P2 / P3 / P6。
