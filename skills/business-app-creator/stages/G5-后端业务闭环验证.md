# G5 后端业务闭环验证

本阶段的目的是**证明部件组合后能完成业务并留下正确事实**。分两个子闭环：G5a 执行闭环，把已验单元装成业务路线并在真实项目里跑通；G5b 应用数据闭环，把数据模板、后端与验证实例接通。两条线可穿插推进，依赖次序由真实契约决定。工具细则见 G3 第 8 节、G3 第 8 节、本文第 8 节、G7 第 8 节。

## 1. 进入依据

所用单元已通过 G4 适用验收；数据与交互契约与 G3 一致；G2 的试验授权不覆盖本阶段的真跑，真跑另取授权。

## 2. 本阶段建设

### G5a 执行闭环

**步骤 1：组装业务路线。** 全部节点编排型 TPE 挂载并通过单体验收后才写路线；带业务事件的单条编排型 TPE 写成单节点路线。制作顺序固定：冻结每条路线的职责、入口表单、路线输入定义、到达标准；确认每条编排型 TPE 有根对象输入输出定义与当前版本运行证据；画依赖图，全部可达、无环；逐字段建入口映射、节点映射、交付映射；可预知的最终用户输入全放入口表单；需要时声明节点级 Agent 介入并写可验证标准；按 G3 已确认的交付对象与审阅形态声明唯一的最终交付与审阅动作，动作只写 `action_key` 与 `kind`，跳转动作另加 `orchestration_id` 与可选 `target_input_mapping`，**`label` 与 `description` 不可写**；整体替换保存，长对象经 `orchestration_url` 提交，按服务端返回精确修同一个对象，**禁止**发明兼容字段。

`delivery.mapping` 三条规则：要交付的文件路径字段**必须**进 mapping，否则不登记为 Artifact；缺失字段自动跳过，必填由 `output_schema.required` 裁决；路径必须是 `output_schema` 声明过且位于本节点产物目录内的文件。

保存并反读后做**静态接缝检查**：入口、节点依赖、扇出汇合、mapping、运行中交互、Delivery、Review 引用真实资产并满足契约；mapping 检查含文件覆盖。保存成功只证明静态结构合法。规划配套应用时同步冻结**面向应用的公开语义**：每条路线的业务名称、适用条件、入口表单目的、里程碑、可能的交互、最终交付、到达标准，**不得**用编排型 TPE 名或节点 ID 代替。

**步骤 2：路线级 Bubble。** 对发布范围内每条路线执行：`scene_package_manage(action="bubble", task_id, scene_package_id, orchestration_id, workflow_input, review_action_key)`，`workflow_input` 用代表性入口根对象，只有 `agent_gate` 才传 `review_action_key`；后续只传同一 `task_id` 与服务端返回的 `run_id` 轮询；返回 `waiting_input` 时读 `interaction.form_id/arguments`，用 `formdata` 回复当前表单；只有 `status="success"` 且 `validation.status="passed"` 才算通过，失败按 `repair_target`、`repair_action` 修它指向的原资产再重启，只有 `repair_target="platform_runtime"` 才按平台故障处理。默认 `evidence_level="summary"`，定位不了失败时才对同一 `run_id` 用 `full`。每条路线通过后写一条检查点，**一条路线一条**：`task_manager(insert, entry_type="checkpoint", metadata={"evidence_type":"orchestration_bubble_validated","scene_package_id":...,"orchestration_id":...,"run_id":...})`，结单时机器核对。路线 Bubble 里 FastAgent 为桩、外部副作用被 `ctx.dry_run` 阻断，它证明整图控制与交付接缝，**不能**证明内容质量；含 FastAgent 的路线**必须**在全真里覆盖真实内容。

**步骤 3：草稿态端到端全真。** 在草稿态目标版本上执行，不需要先上线。一次性向开发者说明本轮范围：跑哪几条路线、每条用哪个入口表单与什么测试样例、运行中表单怎么答、会启动的编排型 TPE 与 FastAgent、费用与外部副作用；批准即为本轮滚动验证的预授权，修正环内重复运行不再逐次询问。**主入口是表单直跑**，它走真实路线运行时：

1. 建项目并启动：`manage_goalfymax_project(action="run", task_id, idempotency_key, scenario_package_ids=[<草稿态目标版本的物理行 id>], submit_data={...})`，`task` 省略。`submit_data` 里 `orchestration_id` 填路线 id，`business_id` 由你生成并在同一业务实例内沿用，`form_id` 填入口表单 id，`formdata` 按表单 Schema 用开发者确认的测试样例填；**`workflow_runtime_id` 不要传**，它只由服务端生成。返回的 `project_id` 后续全部复用，**不要**为查状态或小修反复新建项目。
2. 绑定数据：素材先逐个 `file_to_url(purpose="tool_test_fixture")`，在 `run` 的 `workspace_files` 里带 `relative_path` 与 `formdata_pointer`，指向 `formdata` 里的空占位字段。测试素材来自开发者给的正反例，不虚构。
3. 观察运行：`status` 看状态，`wait` 等待推进，`history` 看交互；运行中业务表单和最终交付审阅都用 `reply` 应答，带 `business_id`、`orchestration_id`、`workflow_runtime_id`、`form_id` 与 `formdata`；`confirm` 只是普通聊天确认，**不能**用来应答任何业务表单；失控用 `stop`。日志用 `get_project_execution_logs`：`summary` 看概览，`detail` 按 `log_type` 分页读原始日志，`outputs` 列产物，`download` 或 `bundle` 取回核对。异常分三类归因：路由错、执行错、产出错。
4. 专项核对并记入工单：节点派发顺序与依赖图一致；`delivery.mapping` 求值结果与产物一致；运行中表单在声明的节点出现；业务事件生命周期齐全；Delivery 冻结、Artifact 登记、最终 Review 按声明生效；失败分支以结构化 `fail_business` 收口。

主入口跑通后用 `task="<自然业务需求>"` 再跑一次聊天入口核路由，**禁止**验收话术，**禁止**指定工具名或调用顺序；带事件的编排型 TPE 在此入口事件降级是平台行为。

**步骤 4：修正环与漂移检查。** 发现问题在同一草稿行修改并直接重跑。每次到达终态后对照《制作书》前七章做漂移检查：画像，用词与假设是否落在画像里；旅途，实际走过的里程碑与停点是否与设计一致；预计产出，形态、业务字段、质量是否达到正反例标准。实现偏离回 G4 修同一份资产；口径偏离回 G1 更新基线再改制作书。读本次运行的问题单：`fail` **必须**修复后重跑；`advice` 由你判断，不采纳写理由。平台未提供问题单时按三层复盘人工归纳，**不得**虚构。结果检查表逐条闭合，只处理 `pending`，正例产出一致、反例被正确识别处理才置 `passed`；`waived` 必须带理由。

**步骤 5：定稿上线能力容器。** 前提：前三层候选验收通过、全真到达终态、问题单无未处置 fail、结果检查表全绿；存在 `full_validation_skipped` **不得**上线。授权已在《制作书》第 ⑨ 章明确写出时直接执行，否则单独确认。`finalize_asset_version_online(asset_type="scenario_pack", draft_asset_id=<草稿行>, change_note=...)`，平台校验运行时身份、连接信息、文件物化、依赖闭包；依赖的 `latest` 引用定稿时钉到具体版本。上线后**必须**反读线上状态与版本。能力容器上线**不等于**应用已交付。

### G5b 应用数据闭环

**步骤 6：制作数据模板。** `dataset_template_workspace(open, name, description)` 开独立 schema 并记下 `data_uid`，返回的连接串是凭据，**不进工单、不进聊天、不进代码**。逐列按 G3 的四类归位打标。建表用 `create_table(table_name, target_columns=[...])`：每表至少一列 `primary_key=true`；类型写 PG 精确类型；**每列 `comment` 必填且以 `[editable:user|agent|system] ` 开头**，漏写等于该列按 `user` 处理、生产写不进去；每张有写入的表带审计四件套与 `row_version`。需要灌最小样例跑典型查询时用写连接，样例不进模板；连接经 dataset-proxy，`BEGIN`、`COMMIT`、`ROLLBACK`、`SET ROLE`、`SET search_path` 会被拒。`set_relations` 声明关系。`inspect(data_uid)` 反读逐表逐列核对，不带偏差往下走。把 `inspect` 结果翻成业务语言交开发者确认后再 `extract(data_uid, template_name, template_description)`；修订已有模板传 `template_id` 出新版本，破坏性变更**必须**随带 `migration_script`。记录模板 id 与版本号。**不要**在这里 `close`，工作集要留到交付之后。

**步骤 7：实现后端。** 动手前通读 `backend/README.md`。`cd backend && npm ci`；按 models、services、routes 三层实现三类接口：CRUD，写入前按列注释校验写权，带来源标记 `user_edited`，比对 `row_version`，写接口幂等，键是 `X-Goalfy-Business-Request-Id`；统计聚合，按看板指标清单实现，每个指标能说出来源表与口径，单查询在 10 秒内，大结果分页；生产回流，来源标记 `generated`，`updated_by='agent'`，写 `last_run_id`，**`editable:user` 列不得覆盖**。每个公开接口先在 `frontend/schema/api/<operationId>.yaml` 落 OpenAPI 契约，无契约不开发。硬约束：响应只用 `ok/okEmpty/list/fail` 构造，字段是 `msg`，业务失败也 HTTP 200，自定义码从 1100 起；引用表只写 `buiTable('表名')`；只做 DML；`async` 路由必须 try-catch；身份从 `getContext(req)` 取；写接口用 `canWrite` 与 `requireBusinessRequestId`；生产态不开 CORS；线上只注入三个 env 加 `PORT`。`cd backend && npm test` 全绿再联调。

**步骤 8：建立验证实例。** `business_ui_manage(action="create", name, scenario_pack_id=<家族 id>, dataset_template_id, task_id)`；`dataset_template_version` 钉整数号，**禁止 follow latest**。打包只用 `./scripts/pack.sh`，镜像必须用户无关。上传与部署：`business_ui_bundle` 的 `prepare_upload` 到 `complete_upload` 到 `deploy(source_sha256)` 到 `status` 轮询到终态 `success`；响应里 `database` 为 `null` 说明还没挂模板，先 `business_ui_manage(update, dataset_template_id, dataset_template_version)` 再 deploy。在真实应用实例验证五步：发起时带入、执行中取数、结果回流、编辑、再次读取。应用前端未就绪时用步骤 3 的表单直跑通道打后端。此时**不要求**完整界面，但**不能缺**实例与数据通道证据。

能力容器在无应用数据的项目里跑通，只证明该输入与回退路径，**不得**据此判 G5b 通过。平台不允许提前提供测试实例时，落 `platform_blocked` 并补能力；**禁止**把必需项豁免后上线。

另须实现并验证：异步任务定位；输入、产物、版本关联；幂等与冲突；部分失败恢复；错误归因；引用旧产物的权限与有效性。优先使用当前 Runtime 的重入方式；**禁止**承诺平台未验证的任意节点断点续跑。

## 8. 细则

本节是第 2 节各步骤点名的表格、契约、纪律清单与示例。它不是流程：进入与出口以第 1 节和第 5 节为准，**禁止**从本节推断阶段顺序。

### 8.1 业务路线组装


#### 8.1.1 制作顺序

需要业务事件、业务表单握手、Delivery Review、业务应用入口或多条编排型 TPE 固定依赖时，全部节点编排型 TPE 都已挂载并通过单体验收后，才能写业务路线。带业务事件的单条编排型 TPE 必须写成只有一个节点的业务路线；多条编排型 TPE 按真实依赖写成多节点路线。制作顺序：

1. 为每条候选路线冻结稳定职责、入口表单、路线输入定义、到达标准
2. 确认每条编排型 TPE 都有根对象输入输出定义、当前版本的运行证据；声明业务事件的节点还要确认当前事件契约完整
3. 画路线内依赖图：所有节点可达、无环，依赖只表达数据与执行先后
4. 逐字段建立入口映射、节点映射和交付映射，核对路径、必填、基础类型和文件格式
5. 制作期可预知的最终用户输入全部放入口表单；只有上游成功后才知道、且要喂给未派发下游的输入，才用运行中交互
6. 需要 Agent 在节点成功后审查或处理异常时，在该节点声明介入，写清指令和可验证标准
7. 读取 P1已确认的交付对象、最终审阅形态、审阅责任方、最终用户体验和风险；质量检查、内容核验或节点 `sa_handoff` 不能代替最终审阅
8. 按已确认方案声明唯一的最终交付与审阅动作。当前有四种动作：结束业务、以结构化原因拒绝交付并结束业务、跳转到另一条路线（**必须**指向真实存在的路线且入口匹配）、交由 Agent 处理；Agent 不得根据实现便利自行删减、增加或替换动作。两条声明规则：
   - **声明字段**：每个动作只写 `action_key` 与 `kind`，跳转动作另加 `orchestration_id` 与可选 `target_input_mapping`。***`label` 与 `description` 不可写***——保存门拒收未知字段，按钮中文文案由 Runtime 按动作类型生成；
   - **跳转的两种形态，按"这一跳需不需要用户新输入"二选一**：不需要 → 声明 `target_input_mapping`（每项 `source='delivery'` 从冻结交付取值，**必须覆盖目标路线 `input_schema` 全部 required 字段**，保存门校验），用户点跳转直启目标路线、不弹入口表单；需要（如选篇、写修改意见）→ 不声明映射，跳转弹出目标路线入口表单，已知信息的预填由业务应用实现（app-creator 线）
9. 按已确认动作设计最终审阅接受路径；存在最终用户修订、重做或改路线语义时，同时设计一条新建 Runtime 且保留当前 Delivery 的路径。真实资产与已确认业务路线图不一致时，停止写入并回到 P1更新 Plan，**不得**在本节重新替开发者做产品决策
10. 整体替换保存；对象较长时可按 2.3 在实时 Schema 支持后通过 `orchestration_url` 提交完整 JSON。按服务端返回的节点、字段和路径错误精确修**同一个对象**，**禁止**自行发明兼容字段

**交付映射（`delivery.mapping`）的三条规则**：

1. ***要交付的文件，路径字段必须进 mapping***：Artifact 登记的来源是 mapping 的求值结果——只在 `output_schema` 声明并返回、未进 mapping 的文件不会被登记，界面会显示无产出文件。文件路径字段可以嵌套在对象或数组里（如 `$.items[].card_paths[]`），求值结果中的 workspace 路径会被逐个登记，不需要为登记而拍平结构；
2. **缺失字段自动跳过**：mapping 引用的字段在本次返回中缺失时跳过该交付字段，必填与否由 `output_schema` 的 `required` 裁决——仅部分分支返回的字段（如失败分支的 `blocked_stage`）可以放进 mapping；
3. **文件路径须可验证**：mapping 引用的 workspace 路径要求是 `output_schema` 声明过、且位于本节点产物目录（`/workspace/task_agent/<taskpoint>/output/`）内的文件，二者之一不满足则交付被拒（`ORCH_DELIVERY_FILE_UNVERIFIED` / `ORCH_DELIVERY_FILE_UNISOLATED`）。来自入口表单、上游节点或 FastAgent 会话目录的文件不因"来源可信"而豁免——要交付先复制进本节点 `ctx.output_dir`（4.3 产出文件的交付链）。

入口映射（`entry.input_mapping`）同理：表单未填的可选字段被跳过，必填由路线 `input_schema` 的 `required` 裁决；需要默认值的字段用映射的 `default` 变换声明。

**业务表单的定义落在哪**：Hub 不登记表单 Schema——业务路线里只有 `form_id` 和映射（入口表单是 `entry.input_mapping`，中途表单是源节点 `after_success.target_input_mapping`）。字段清单由此可推，`get_asset(scenario_package)` 会算好放在 `business_forms` 里（每张表单：`form_id`、入口还是中途、属于哪条路线哪个节点、字段名与目标字段的类型 / 必填、`skip_when`），这是权威来源，业务应用线直接读，不必再逐个映射反推。但标题、字段说明、控件提示、排序这些展示信息 Hub 没有——写业务路线时同步为每个 `form_id` 落一份场景 Skill 文件 `forms/<form_id>.json`（`form_id`、`title`、字段的 `label` / `description` / 控件提示 / 顺序，与 `business_forms` 的字段一一对应），随场景包上传（2.3）；制作书 ⑧-2 的"运行中交互"一栏也按表单列出字段。

保存成功**只证明静态结构合法**，不能替代整条路线的运行证据（见 本文第 8 节）。

#### 8.1.2 静态接缝检查

保存并反读业务路线后，完成静态接缝检查：入口、节点依赖、扇出汇合、mapping、运行中交互、Delivery 和 Review 必须引用真实资产并满足当前契约；单节点路线也必须检查入口映射、唯一 Delivery 和 Review。mapping 检查含***文件覆盖***：要交付的文件路径字段必须都在 mapping 里——漏映射的文件不会登记为 Artifact（7.1 规则一），发现缺失即回改 mapping 再通过。该证据仍属于第一层 Preview/静态契约，不能证明路线已经执行。不得用一条或多条单条编排型 TPE 轨迹拼接成路线证据，也不得自行创建图执行器或伪造 Runtime 身份。`emit_business_event` 在单条编排型 TPE bubble 中仍必须取得服务端分配的验证 Business/Runtime 身份；缺失时该编排型 TPE 的 bubble 裁决为 `platform_blocked`。正式运行时，带业务事件的单条编排型 TPE 不能直接派发，必须通过单节点路线取得持久化 Business Runtime。FastAgent 真实内容、显式外部副作用、业务事件真实发布和跨路线跳转统一留到第四层端到端全真运行验证；业务应用对事件的消费在 app-creator 线验收，不属于本包证据。

路线级 Bubble 的执行与证据纪律见 S4-验证与修正。

#### 8.1.3 面向界面的公开语义

已规划配套业务应用时，业务路线完成还要冻结一份**面向系统的公开语义**：每条路线的业务名称、适用条件、入口表单目的、最终用户可理解的里程碑、可能出现的最终用户交互、最终交付和到达标准。它们是 app-creator 线 A1 契约基线的事实输入，**不得**用编排型 TPE 名称、节点 ID 或工具步骤代替。

### 8.2 验证总览


三层验收、草稿态端到端全真滚动、问题单消化与结果检查表闭合。

发布前读取 [场景包验收检查清单](../checklists/场景包验收检查清单.md)，把 `apc_skill`、Skill 文件、任务点、工具集、FastAgent、工具组、数据集、编排型 TPE、业务路线、交付物作为**一个业务闭环**完成前三层候选验收。逐项确认前期确认的每个里程碑、候选路线、业务路线图、交付对象、审阅责任、审阅动作、介入点、前置检查、授权和到达标准，都能在真实资产里找到对应承载；后续发生的任何实质变更都有开发者重新确认记录。

**S3 与本节是反复回路**：S3 交来的是“制作完成”的资产（Preview 过、业务路线保存过），本节从单条编排型 TPE Bubble 开始逐层验证；任一层失败，回 S3 对应节修同一份资产（改脚本回 G4 第 8.4 节、改业务路线回 本文第 8.1 节、改依赖回 S3 第 1–2 节），再回本节重验，直至第四层收敛。回跳沿用原 `stage_exit` 记录，不重复落账。

**完整证据固定分为四层，不得互相替代：**

| 层级 | 必查内容 | 能证明 | 不能证明 |
|---|---|---|---|
| 1. Preview / 静态契约 | 资产反读、脚本、输入输出 Schema、工具引用、按需业务事件声明与静态生命周期、按需业务路线保存与接缝 | 当前资产和静态契约可保存、引用闭合 | Provider 真实返回、事件持久化、路线运行 |
| 2. 工具取样 / 依赖证据 | 安全低副作用工具的真实输入输出、依赖状态和权限 | 代表性依赖在当前环境可调用，候选 `_output` 有真实样本 | 整条编排型 TPE 或其他输入正确 |
| 3. 制作期 Bubble | 先逐编排型 TPE 检查当前路径的步骤、文件、输入输出、按需持久化业务事件和覆盖率，再逐路线检查真实图控制、表单、Delivery/Artifact 与终态 Review 接缝 | 当前版本当前输入的节点数据管路与路线控制接缝成立；带事件时可证明验证事件链成立 | FastAgent 真实内容、被阻断的外部副作用、未触达分支、正式业务运行 |
| 4. 场景包端到端真跑 | 在草稿态目标版本上、真实项目里**经入口表单直跑（`submit_data`）启动业务路线**：路线运行时真实派发、运行中业务表单、Agent 介入、FastAgent 真实内容、工具真实调用、业务事件、Delivery 冻结与最终审阅；再以聊天入口跑一次核路由；对照结果检查表（第 6 节）与计划书（3.4） | 场景包在真实路线运行时里按计划书跑通并交付 | 未运行情景和未来输入都正确；应用前端与 SDK 三次握手、回流入库（app-creator A4） |

**第四层端到端全真是上线（定稿并真正上线）的前置**：全部通过后才进入 S5 的上线门。没有第四层真实日志时，只能记录前三层通过和整图运行盲区；**禁止**用多条单条编排型 TPE 的运行证据拼接成整图运行证据。第四层经表单直跑走的是真实路线运行时：运行中表单、业务事件、Delivery 冻结、Review 这些 Runtime 接缝在这里真实验证；app-creator A4 只再验应用前端与 SDK 三次握手、回流入库，不重复验路线运行时。

前三层候选验收的裁决口径不变：critical 全部关闭；warning 已修复或经开发者明确接受；发布范围内资产与前三层证据一致；被跳过或被平台阻断的项都有明确影响说明和后续条件。

开发者选择跳过端到端全真时，**必须**记录跳过决定、FastAgent 内容盲区、未触达分支和副作用盲区（`full_validation_skipped`）；**存在该标签时不得上线、不得结单**（见总入口 8.3），**禁止**声称已有全真证据。

### 8.3 路线级 Bubble 与证据强度

#### 8.3.1 路线级 Bubble

全部节点完成单条编排型 TPE Bubble、业务路线保存反读并通过静态接缝检查后，对发布范围内的每条路线执行一次**路线级 Bubble**。它仍属于第三层制作期演练，不需要用户批准，也不替代第四层全真运行。调用顺序固定为：

1. 启动：`scene_package_manage(action="bubble", task_id=..., scene_package_id=..., orchestration_id=..., workflow_input=..., review_action_key=...)`。`workflow_input` 使用该路线的代表性入口根对象；只有 `delivery.review.type="agent_gate"` 时才传一个已声明的具体 `review_action_key`。
2. 轮询：后续只传同一 `task_id` 和服务端返回的 `run_id`，不得重复入口输入，不得创建或补写项目、Business、Runtime、表单或消息标识。
3. 回填：返回 `status="waiting_input"` 时，读取当次 `interaction.form_id/arguments`，再用同一 `task_id/run_id` 和 `formdata` 回复；每次只回答当前表单。
4. 终态：只有 `status="success"` 且 `validation.status="passed"` 才算路线 Bubble 通过；失败时优先读取 `failure_stage`、`repair_target`、`repair_action` 和可选的 `failed_node_id/failed_step_key`，按 `repair_action` 修正它指向的原编排型 TPE 或业务路线，再重新启动；只有 `repair_target="platform_runtime"` 时才按平台故障处理。禁止只看笼统错误自行猜修改入口，也不复用已结束的 `run_id`。

路线 Bubble 默认 `evidence_level="summary"`：只读取路线终态、节点与步骤计数、失败步骤错误、输出字段、事件覆盖摘要、Artifact 引用、Delivery 验证和 Review 结果。完整步骤输出、最终输出值和业务事件 Payload 仍保存在 Runtime；只有精简证据不足以定位失败时，才对同一 `run_id` 显式使用 `evidence_level="full"`。不得把完整证据默认塞入工单、记忆或最终交付，也不得因为默认响应精简就重复执行路线。

每条路线通过后，用 `task_manager(insert, entry_type="checkpoint")` 写一条精简证据——**建议一条路线一条检查点**：`orchestration_id` 与 `run_id` 各是单个标识，五条路线就写五条，各带自己的 `run_id`。把多条路线的标识用逗号合在一条里也能存，但工具会在响应里带 `format_warning` 提醒，而且 `complete` 按路线逐条核对时对不上——省下的那几次 insert 会在结单时还回来。把以下结构放入 `metadata`：`{"evidence_type":"orchestration_bubble_validated","scene_package_id":<真实场景包标识>,"orchestration_id":"<真实路线标识>","run_id":"<本次通过的真实 run_id>"}`。这不是人工自证：`task_manager(complete)` 会读取同一工单已有的工具调用审计，核对当前业务路线、`run_id` 和终态；缺失、失败、属于其他路线或早于最后一次业务路线修改的证据都会拒绝结单。结单成功响应中的 `completion_evidence.route_bubbles` 才是机器确认结果。

路线 Bubble 复用真实图 Runtime，检查节点依赖、mapping、扇出/汇合、运行中业务表单、持久化业务事件、Delivery 冻结、Artifact 登记和最终 Review。各节点仍使用既有 dry-run Bubble 语义：FastAgent 为桩，显式外部副作用由 `ctx.dry_run` 阻断；声明的 `sa_handoff` 只验证边界可跨越并记录为桩，不声称验证 Agent 判断；最终用户表单和 `user_gate` 使用真实结构化握手。当前路线 Bubble 的 Review 只接受终止本业务的 `complete_business` 或 `fail_business` 动作，不演练 `start_orchestration` 跳转；含跳转的路线保留到第四层全真运行验证。路线 Bubble 因此能证明本次输入下整图控制和交付接缝成立，不能证明 FastAgent 内容质量、被阻断的外部副作用或未触达分支。

#### 8.3.2 证据强度分级

路线 Bubble 的验证证据带强度标记（如 `fa_stubbed`、`uses_shell`），按路线特征分级裁决：

- **纯工具链路**（不含 FastAgent 步骤）：桩跑证据即可放行进入第四层；
- **含 FastAgent 的路线**：桩跑证据只证明管路，**必须**在第四层全真中覆盖 FastAgent 真实内容后才算完整。

#### 8.3.3 冒泡结论的引用纪律

引用冒泡证据时**必须**如实说明边界：Bubble 中 FastAgent 恒为桩，**不能证明任何内容质量**；桩值（空字符串、空数组、空对象、示例路径）可能触发脚本为真实异常准备的降级分支，使冒泡走过的路径与真跑不同——例如桩返回的示例底图路径与你传的素材对不上，脚本正确地走了“引用不存在、要求补拍”的拦截分支，成功路径反而没验到。处置是**换成与桩值对得上的输入重跑**把成功路径也覆盖到，不是改脚本去迁就桩，更不是拿拦截分支通过当成功。**禁止**以"冒泡通过"表述"质量可控"或"内容正确"；冒泡证明的只是当前输入下的管路与接缝。

### 8.4 草稿态端到端全真滚动


#### 8.4.1 授权与范围

场景包、需要的业务路线和上线前三层候选验收全部通过后，即可在**草稿态目标版本**上执行端到端真跑；不需要先上线。

第四层要验的是**路线运行时在真实项目里的运行**：只有经业务应用入口表单启动的路线才经过业务路线 Runtime——节点派发、字段映射、扇出汇合、运行中业务表单、Agent 介入、业务事件、Delivery 冻结、Artifact 登记、最终 Review 全在它手里；聊天入口直派编排型 TPE 时 Runtime 不参与、业务事件降级，验不到路线运行时。所以***第四层的主入口是表单直跑（`submit_data`）***，模拟的正是业务应用的首次提交，**不需要应用前端就绪**；聊天入口另跑一次只核路由。应用前端、SDK 三次握手与回流入库由 app-creator A4 验，不在本节重复。

一次性向开发者说明本轮真跑范围：要跑哪几条路线、每条用哪个入口表单与什么测试样例（来自计划书 ②③ 与 G1 第 8.3.2 节 的正例）、运行中表单打算怎么答、可能启动的全部编排型 TPE 与 FastAgent、费用与外部副作用，并询问是否真实运行。批准即为本轮滚动验证的**预授权**：修正环内的重复运行不再逐次询问；带业务事件的单条编排型 TPE 也按单节点路线申请和执行；**禁止**在每条编排型 TPE 的制作循环中逐条申请真跑。一次获批运行覆盖所选路线的完整业务路线、最终用户介入、Agent 介入、业务事件、Delivery 和 Review，**不把它拆成若干单条编排型 TPE 真跑，也不把带业务事件的编排型 TPE 改走聊天直派**。

草稿态真跑就是真实项目运行：外部副作用照常发生、FastAgent 照常计费，**必须**按约束 6 对待。

#### 8.4.2 真跑四步：建项目、绑数据、看运行、拿结果

| 工具 | 用途 |
|---|---|
| `manage_goalfymax_project` | 在真实项目中挂载场景包并运行：`run` / `status` / `wait` / `send` / `reply` / `confirm` / `history` / `stop`。后续动作各有用途：`reply` 应答**一切业务表单**（运行中表单和最终交付审阅 `delivery.review` 都是），带四个身份 `business_id` / `orchestration_id` / `workflow_runtime_id` / `form_id` + `formdata`；`confirm` 只是一句普通聊天确认（默认"用户已同意执行"），不带业务身份，**不能用来应答任何业务表单**；`send` 回答 SA 的自然语言追问 |
| `get_project_execution_logs` | 读取真实项目日志与产物：`summary` / `detail` / `outputs` / `download` / `bundle`。`outputs` 帮你找产物：列 `/workspace/output`、每个编排型 TPE 节点的产物目录 `/workspace/task_agent/<taskpoint>/output/` 以及交付记录里登记的 artifacts；`download` 能拿项目 `/workspace` 下任何真实存在的文件（输入、挂载、缓存、密钥等受保护目录除外），路径不在 `outputs` 里也行，只要它存在 |
| `file_to_url(purpose="tool_test_fixture")` | 把本地测试素材换成文件引用，供 `run` 绑进项目 |

**① 创建项目并经入口表单启动路线（主入口）**（`submit_data` 里三个身份的来源：`orchestration_id` 填计划要跑的那条路线在 `orchestrations[]` 里的 id；`business_id` 由你生成，建议 `biz-<场景包简称>-<日期>-<两位序号>`，同一次业务实例的后续 `reply` 沿用同一个值；`form_id` 填该路线入口表单的 id；**`workflow_runtime_id` 不要传**，它由 Max Backend 生成，传了直接报错；`form_submit_id` 可不传，服务端按 `idempotency_key + form_id` 派生）：`manage_goalfymax_project(action="run", task_id, idempotency_key, scenario_package_ids=[<草稿态目标版本的物理行 id>], submit_data={...})`，**`task` 省略**——一次 `run` 创建一个真实项目、挂载草稿态目标版本，把 `submit_data` 当作业务应用的首次提交交给路线运行时直接启动路线，不经 SA。`scenario_package_ids` 必须且只能一个；反读确认挂的正是待验收那一行。`submit_data` 的字段按实时 Schema 填：入口表单所属的业务路线标识与表单标识、按该表单 `inputSchema` 填好的 `formdata`（用开发者确认的测试样例，不用验收话术）。***运行实例标识由服务端生成，任何情况下不由调用方传入***：首次启动只提交业务路线标识与入口表单；服务端校验并创建首批真实任务点后才回传运行实例标识；入口被拒或首批派发失败时不会也不得暴露预留标识；对话入口、Agent 介入和路线重入同样由服务端生成新标识；同一运行实例内的任务点、交互、交付和查询**必须**沿用同一标识。返回加密 `project_id`，后续 `status/wait/reply/confirm/history/stop` 与日志工具**全部复用它**，不要为了查状态或做小修反复新建项目。`idempotency_key` 必填，同一次运行的重试用同一个键；`mode` 与 `model` 建项目后固定。

**第二入口——聊天入口核路由**：主入口跑通后，再用 `task="<自然业务需求>"`（不传 `submit_data`）跑一次：`task` **必须**是自然、真实、可变化的业务情景，像最终用户直接提需求那样写——**禁止**验收话术，**禁止**指定编排型 TPE、FastAgent、工具名、内部 ID、调用顺序或分步方法，要让 SA 按 `apc_skill` 自己完成路由。这一跑只证明"聊天里能进到这条路线"（入口并存，reference 3.3）；带业务事件的编排型 TPE 在此入口事件降级是平台行为，不是缺陷，路线运行时的证据以主入口为准。

**② 用上传文件绑定数据**：情景需要素材（菜单、Excel、图片、历史文档）时，先逐个 `file_to_url(purpose="tool_test_fixture")` 取得 `file_ref`，在 `run` 里放进 `workspace_files`（每项 `purpose` / `file_key` / `file_name` / `relative_path`；`relative_path` 是目标项目数据目录下的**相对后缀**，***不要拼成 /workspace/...***）。表单直跑时每个文件**还必须**带 `formdata_pointer`：指向 `submit_data.formdata` 里现有 `null` 或空字符串占位字段的 JSON Pointer（如 `/menu_file`、`/attachments/0`），服务端上传完成后把真实 `/workspace/...` 路径写进该位置再启动；聊天入口那次不传 `formdata_pointer`，`task` 里按**文件名**引用附件。文件在 Agent 或编排型 TPE 启动前登记完成。测试素材来自开发者给的正反例（G1 第 8.3.2 节），不用虚构数据。

**③ 观察运行、异常与结果**：`status` 看当前状态，`wait`（单次 ≤45 s）等待推进，`history` 看对话与交互记录；运行中出现**业务表单**（路线声明的中途表单）时，用 `reply` 在同一项目、同一运行实例上提交按测试样例填好的结构化表单——到服务端业务确认才算答完；最终交付审阅（`delivery.review`）同样是业务表单，也用 `reply` 应答，沿用同一 `business_id` / `workflow_runtime_id`；`confirm` 只用于普通聊天确认，不能用于任何业务表单——用它应答表单会被当成普通聊天输入放行，表单仍挂着，失败到很里面才暴露；聊天入口那次 SA 追问用 `send` 回答；失控时 `stop`。日志与产物用 `get_project_execution_logs`：先 `summary` 看概览（阶段、Agent / 工具分布、等待与失败），再 `detail` 按 `log_type`（`system_agent` / `task_agents` / `fast_agents`）分页读原始日志定位问题，`outputs` 列产物、`download` / `bundle` 取回核对。异常分三类归因：**路由错**（SA 没走到该走的资产 → 看 `apc_skill` 与任务点描述）、**执行错**（FastAgent / 工具报错 → 看对应日志与依赖状态）、**产出错**（跑完了但结果不对 → 进第 5 节复盘与第 6 节对比）。

路线运行时专项核对（表单直跑到达终态后，逐项判定并记入工单）：节点派发顺序与依赖图一致；`delivery.mapping` 求值结果与产物一致；运行中表单在声明的节点出现、未声明处没有停顿；业务事件生命周期齐全（`stage_started` / `stage_result` 或 `stage_failed`，`artifact_ready` / `delivery_ready` 由 Runtime 自动发布）；Delivery 冻结、Artifact 登记与最终 Review 动作按声明生效；失败分支以结构化 `fail_business` 收口。

**④ 拿结果对比**：产物与终态对照结果检查表逐条判定（第 6 节）；再按 3.4 对照计划书做漂移检查。每次真跑的 `project_id`、情景、结论写入工单。

#### 8.4.3 修正环

发现问题后，在**同一个草稿行**上修改并直接重跑，不需要每圈定稿或上线：

```text
草稿行真跑 → 分析（第 5 节）+ 漂移检查（3.4）+ 问题单（第 4 节）→ 修改草稿（回 S3 对应节 / 口径漂移回 S1）
     ▲                                                    │
     └────── 执行结构表条目指纹变化 → 回退 pending ──────────┘
```

- 修改脚本或结构后，执行结构表条目按 S3-4.4 回退 `pending`，仅对回退条目增量重挑战与重验；
- 结果检查表相关条目同步回退 `pending`，重跑后重新闭合；
- 修正环收敛（问题单无未处置 fail、检查表全绿）后，才进入 S5 定稿上线。

#### 8.4.4 与计划书对比：漂移检查

每次真跑到达终态后，拿运行记录对照 S1 计划书（`build_book`，`stage="S1"`）的三章：

| 对照 | 看什么 | 漂移信号 | 处置 |
|---|---|---|---|
| ① 用户画像 | 运行中 SA / FastAgent 的用词、对象、假设是否落在画像里 | 用平台词对用户说话；把商家类型搞错；追问画像里已知的信息；产出不像给这类用户看的 | 用词与假设的问题回 S3（`apc_skill` / 提示词 / 规范文件）；画像本身写错回 G1 第 8.5 节 |
| ② 用户旅途 | 实际走过的里程碑、路线内的节点与停下来问用户的地方（表单直跑），以及聊天入口那次 SA 选中的路线，对照计划书 ②③ | 多走或少走了阶段；选路与人群不匹配；在计划书没安排的地方问用户，或该确认的地方没停 | 路线 / 任务点描述 / 业务路线回 S3；旅途设计本身错回 S1 |
| ⑥ 预计产出 | 交付物形态、业务字段、质量，对照计划书 ⑥ 与结果检查表 | 形态不同；缺业务字段、只给文件不给内容；质量低于正反例标准；红线被碰 | 资产回 S3；预期本身不合理或红线要调回 S1 |

漂移分两类处置：**实现偏离**——回 S3 修同一份资产再重跑；**口径偏离**——计划书要改，回 G1 第 8.5 节更新并重新确认，再改制作书（G3 第 8.5.2 节）与资产。三项都无漂移，本轮真跑才算“符合计划书”；漂移结论逐次写入工单，作为交付报告“效果结论”的依据。

### 8.5 问题单（findings）消化


每次真跑到达终态后，读取本次运行的问题单：由平台按运行流转记录生成的结构化条目，每条包含类别、位置、证据、建议与严重级：

- **fail**：结构性底线违约（如拒绝产出却未给出理由清单、输出自相矛盾、话术承诺未兑现）。**必须**修复后重跑；不修复不得进入 S5。
- **advice**：优化建议（如相邻无依赖步骤串行执行、按真实耗时估算的并行收益）。由你结合业务判断是否采纳；不采纳时在工单记录理由。

问题单按条目指纹累加：已处置（`finding_resolved` / `finding_waived`）的条目在后续运行中不重复报告；`waived` **必须**带理由（总入口 8.3）。平台尚未提供问题单能力时，按第 5 节人工复盘并把发现按同一结构记入工单，不得虚构平台生成的问题单。

### 8.6 运行结果三层复盘


与 G2 第 8.1.1 节同样的三层方法：摘要建立概览 → 完整深读日志与产物 → 分析实际路线是否符合设计、工具调用是否合理、FastAgent 结果是否被有效采用、最终用户确认点是否正确、最终交付是否达到到达标准。

发现问题回到对应阶段修复并重验，形成"运行 → 分析 → 优化 → 回归"的闭环；闭环在草稿态内滚动（3.3），轮询和日志读取复用同一项目标识（3.2）。

### 8.7 结果检查表闭合


对结果检查表逐条目执行闭合，**只处理状态为 `pending` 的条目**：

- **测试用例条目**（S1-3.3 转入的正反例）：以条目输入执行真跑或复用已有运行记录，对照期望产出判定。正例须产出与期望一致的交付；反例须正确识别并按预期方式处理（拒绝、改写或引导），**不得**产出反例描述的错误结果。含开发者在样例选择（S3-3.2）中确定的验收判定时，一并核对。
- **前端校验项不属于本表**：业务应用页面的验证在 app-creator A4 的应用结果检查表里；场景包的结果检查表只有 `test_case` 与 `orchestration_check` 两类。
- **业务路线校验项**：按路线级 Bubble 与全真记录核对交付、审阅与重入行为。

判定通过置 `passed`；确认不适用或开发者接受偏差时置 `waived` 并记录理由。**禁止**为凑全绿而放宽期望产出的判定标准；判定依据与运行证据记入工单。

### 8.8 建立发布单位（business_ui）


业务应用的发布单位是独立资产 **business_ui**：自己的家族 ID 与版本，独立于场景包与项目。一个 business_ui 挂载**恰好 1 个场景包**（发起业务路线时用它的 apc_id 建项目）和**至多 1 个业务应用数据集模板**。

- `business_ui_manage(action="create", name=..., scenario_pack_id=<场景包家族 id>, dataset_template_id=..., task_id=...)`；create 幂等（`operation_id` 缺省由工单与名称派生，重复调用不会建出第二个）；
- `scenario_pack_version` 缺省 latest，**定版上线时钉到当时的具体版本**；`dataset_template_version` 缺省钉模板最新版，***禁止 follow latest***；
- `business_ui_id` 传家族 ID 或任一版本行 ID 均可：传了旧行或家族根时工具自动重定向到家族最新 live，并在 metadata 标注 `redirected_from_asset_id`——看到该标注说明手里的 ID 已过期，后续一律改用解析后的 ID。

### 8.9 源码包上传与构建发布（business_ui_bundle）


打包**只用** `./scripts/pack.sh`（打包 + 归档自检 + 算 sha256 三步原子，产物 `.pack/business-ui-bundle.tar.gz`；它会拒掉缺 `Dockerfile`、含凭证 `.env`、AppleDouble、`node_modules/`、超 50 MiB 等情况）——tar 带时间戳，手工分步打包会让 `deploy` 的 `source_sha256` 对不上。判据只有一条：根目录有 `Dockerfile` 才走镜像通道（有后端）；**镜像必须用户无关**，用户差异只在注入的 env，编译期写死 schema 名或用户 ID 的产物无法给第二个用户复用。然后：

```
prepare_upload(file_name, size_bytes) → complete_upload(bundle_key)
→ deploy(source_sha256) → status(deployment_id) 轮询到终态
```

- `deploy` **必带** `source_sha256`；构建发布必须达到终态 `success`，中间态不算完成；
- `deploy` 由 Hub 走与**用户点开应用同一条链**（2026-09-02 起）：给开发者自己的工作集库注入连接串、按根 `Dockerfile` 起容器，MCP 只轮询 Hub 记录到终态。响应里 `database` 为 `null` 表示 business_ui 还没挂业务应用数据集模板、容器没注库——先 `business_ui_manage(update, dataset_template_id, dataset_template_version)` 再 deploy；
- 前提：business_ui 已挂载一个**带编排型 TPE** 的场景包，否则 Hub 拒绝上传、读取、部署和状态查询；
- 构建失败按返回的结构化报错修同一份源码重新上传部署，不得跳过；
- 上传/部署动作作用在**草稿行**上；已上线版本先出草稿（见 A5 修订节）。有 live 行之后 `business_ui_id` 传家族根会解析到 live 行，写动作（`update` / `ensure_draft` / `deploy`）的返回里带草稿编号，`get` 的返回也会附一句提示点名草稿编号与下一步——后续对草稿行的操作用那个编号，不用去翻 `list_asset_versions`。

### 8.10 工作集是什么


开发者自己造模板的沙盒：`open` 给你一个**独立 PostgreSQL schema** 和 **2 小时有效的写连接串**，可以用 ORM/psql 建表、灌样例、跑查询；也可以不碰连接串，用 `create_table` 声明表。它**不是通用数据集**：不占配额、不出现在数据集列表、不给最终用户用。`extract` 从工作集的真实结构抽成**固定版本的模板**——只抽结构（表、列、类型、主键、注释、关系），不带样例数据、视图、索引；用户点开应用时系统照模板给每个用户建一套自己的库（`bui_{data_uid}`）。

### 8.11 制作步骤


1. **开工作集**：`open(name=<模板名>, description)`，记下 `data_uid`。返回的连接串是凭据——***不进工单、不进聊天、不进代码***；过期用 `connect(data_uid)` 重签，已知目标应用时传 `business_ui_id` 让平台校验绑定，防止两个应用的库串用。
2. **逐列打标**：每列先按 G3 第 8.9.1 节 的四类归位——用户自己的数据 → `editable:user`；场景包运行期所需 / 产出 → `editable:agent`（这些正是 business-app-creator S3-2.4 里编排型 TPE 读写的列，列名要和场景包侧对齐）；主键 / 审计 / 关联 id → `editable:system`。界面意图（草稿、筛选）**不进模板**，那是 `sdk.storage` 的事。文件只存路径列（`text`）+ 文件名 + 时间，不存文件体。
3. **建表**（两种方式可混用）：
   - **声明式（推荐）**：`create_table(table_name, target_columns=[...])`。每表**至少一列 `primary_key=true`**（生成型代理主键用 `bigserial`）；类型写 PG 精确类型（`character varying(120)` / `numeric(10,2)` / `timestamptz` / `jsonb`）；***每列 `comment` 必填，且以 `[editable:user|agent|system] ` 开头再接业务说明***（约束 9）——它会写成 PG COMMENT 并随模板 copy，是应用后端与业务应用数据集 FA 读到写权声明的**唯一渠道**，漏写 = 该列被按最保守的 user 处理、生产写不进去；
   - **连接式**：用写连接 ORM/psql 建表、灌**最小真实样例**、跑 A1 设计的典型查询（看板聚合、编辑读写，`statement_timeout` 10 s 内）——样例只用于验证，不进模板。
   - **每张有写入的表带审计四件套 + 行版本**：`created_at` / `updated_at` / `updated_by`（`user|agent|system`，声明 `system`）/ `last_run_id`，加 `row_version` 做行级乐观锁——用户在编辑页改用户列、生产同时重写产出列时，靠它让后写方重读重试，而不是字段级仲裁。
4. **声明关系**：`set_relations(relations=[{source_table, source_column, target_table, target_column, relation_type}])`，整体替换、按表名。
5. **反读**：`inspect(data_uid)` 读回真实结构，逐表逐列核对类型、主键、**每列 comment 的声明可见**；与 A1 草案不一致时改到一致（`drop_table` 重建或经连接 ALTER），不带着偏差往下走。
6. **抽模板**：`extract(data_uid, template_name, template_description)`。首次不传 `template_id` 即新建模板；修订已有模板时传 `template_id` 给它**出新版本**（整数版本号递增；缺省沿用本工作集上次抽出的模板）。记录返回的模板 id 与版本号——A4 挂载、A5 交付报告都要用。
7. **挂载**（A4 创建 business_ui 后）：`business_ui_manage(update, business_ui_id, dataset_template_id, dataset_template_version)`，版本钉整数号、***禁止 follow latest***。
8. **不要在这里 close**：工作集要一直留到 A5 交付之后——A3 后端本地开发用的连接串就是它，A4 `deploy` 给开发者容器注入的也是它（`database.purpose=template_workspace`）；这里 close 掉，A3 没库、A4 退化成按模板新建空实例、A2 灌的验证样例全丢。收工动作在 G7 第 8.11 节 结单前。

**本地验证时的连接纪律**：写连接经 dataset-proxy，`BEGIN` / `COMMIT` / `ROLLBACK`、`SET ROLE`、`SET search_path` 都会被直接拒——autocommit 单条语句，要原子性就压进一条 SQL（CTE、`INSERT ... ON CONFLICT`、单条 `UPDATE ... FROM`）。A3 后端本地开发用的连接串就是这里 `open` 出来的，填进 `backend/.env`（模板 `backend/.env.example`），***不进工单、不进代码、不进聊天***。

### 8.12 定稿门与变更纪律


- **定稿确认**：把 `inspect` 结果翻成业务语言交开发者确认——每张表存什么、哪些列用户能改、哪些列生产写、审计怎么查。确认后才 `extract`；
- **模板版本一旦被上线的 business_ui 钉住就不可变**：改结构 = 工作集里改 → `extract` 出新版本 → business_ui 出草稿改挂载版本 → 重新 deploy / finalize（A5 修订节）；
- **破坏性变更必须带迁移脚本**：与上一版 diff 为破坏性（删列 / 改类型）时，`extract` 必须随带 `migration_script`（`v{上一版}_to_v{新版}.sql`：幂等、单事务、只动本 schema、**不得建外键**），否则被拒并返回 diff。脚本挂在模板版本链上，business_ui 定版时校验升级链完整并在临时库**真跑一遍彩排**（失败即 `BUSINESS_UI_UPGRADE_REHEARSAL_FAILED`）；存量用户实例沿版本链**只往前升、没有降级**——回滚钉回更老的模板版本会被 `BUSINESS_UI_TEMPLATE_REGRESSION` 拒绝，要回退就把旧结构重新抽成一个新版本。所以：新增列 / 新增表优先，删列改类型先问“存量用户的数据怎么迁”，这是产品决策，进拍板；
- **换模板家族 = 换库**：把 business_ui 从一个模板家族换绑到另一个会被 `BUSINESS_UI_TEMPLATE_SWITCHED` 拒绝——那种情况请新建业务应用；
- 应用代码禁 `CREATE / ALTER TABLE`（约束 4），结构变更只走本节。

### 8.13 一期红线（仍然成立）


- **一个业务应用只绑这一个数据集**：写权限是项目级放开的，多绑一个长期数据集就多放开一个写面；
- 应用角色**没有 DDL 权限**（数据库层拒，不靠自觉），表结构的唯一出口就是本节的模板；编排型 TPE 侧 FA 的“只增不改”仍靠提示词与本节纪律共同守住。

### 8.14 开发顺序


脚手架规定的顺序，别倒着来：

1. **按 lock 装依赖**：`cd backend && npm ci`；`cd frontend && npm ci --ignore-scripts`。`npm ci` 很慢，shell 工具可能在装完前提前返回或报“超时”——那不是失败，把超时设到 300 s 以上或轮询到真正结束，**不要**当失败反复重跑；
2. **先定数据放哪**（G3 第 8.9.1 节 四类）；
3. **先做后端 service 层**，用 `buiTable('表名')` 直查本用户 schema；再按 A1 页面反推的接口写 route 层；
4. **接口先有契约，前端在后端之后**：每个公开接口在 `frontend/schema/api/<operationId>.yaml` 落一份只含一个 operation 的完整 OpenAPI 3.1 文档（`method + path` 算一个接口，一个接口一个文件），后端按它实现、前端只按它调用（method、path、参数、响应逐项匹配）、本地 mock 也按同一 YAML 实现；**没有契约或契约不完整时停止开发，不得从 route / service / 测试 / 注释里猜接口**。前端请求与响应类型依据对应 YAML 建立；`scripts/gen-types.ts` 是历史遗留的后端 model 类型同步辅助，**禁止用于 `sdk.api.request` 公开接口**。所有前端源码在 `frontend/src/` 下，不要在仓库根建 `src/`；
5. **每做完一层测完一层**；
6. **发布前真跑一遍**：`./run-dev.sh start` 同时拉起后端（:8000）与前端（:5175），打开页面**确认数据真的从后端加载出来了**（页面能开不算）；
7. 写代码前在项目根 `git init` 并提交模板基线，之后每个独立可验证的改动单独 commit——没有基线就看不出“模板 vs 改动”。

### 8.15 后端实现


**正本是 `backend/README.md`，动手前通读；本节是落地顺序与易错点。**

按 models → services → routes 三层实现三类 API：

| API 类 | 内容 | 特有纪律 |
|---|---|---|
| **CRUD**（编辑回流） | 数据管理页的增删改查 | 写入前按**列注释声明**校验写权（`editable:user` 才接受用户写）；写入带来源标记 `user_edited`、更新审计四件套并比对 `row_version`；***写接口必须幂等***（键是宿主注入的 `X-Goalfy-Business-Request-Id`，相同 ID = 同一逻辑操作）；删除走确认语义（软删或二次确认由 A1 设计定） |
| **统计聚合**（喂看板） | 看板页的指标与列表 | 按 G3 第 8.12.2 节 的指标清单实现，每个指标能说出来源表与聚合口径；单查询在 `statement_timeout`（10 s）内、响应体 ≤ 1 MiB；大结果**必须分页** |
| **生产回流** | 场景包产出入库 | 按 A1 的入库语义实现（直接入库 / 草稿待确认）；来源标记 `generated`、`updated_by='agent'`、写入 `last_run_id`；***`editable:user` 列不得覆盖*** |

**生产侧还有第二条回流通道**：配套场景包的编排型 TPE 经平台级业务应用数据集 FA（cn-qa 现名 `Business_app_fastagent`，business-app-creator S3-2.4）通过它的 HTTP 工具读写**同一份** schema，不进沙箱——应用后端直连与这个 FA 是同一数据的两条路：**应用自己的前后端数据流通全部由你在后端代码里实现**（本节的 CRUD / 统计 / 回流接口 + `buiTable()` 直连），FA 只服务项目内的 agent。应用设计要吃下三件事实：

- **启动铺底不经 FA**：发起业务路线时要带上的上下文由用户在入口表单里填写、或由应用后端拼进发起报文（`submit_data`），**没有表单预填通道**（平台侧与脚手架侧的 prefill 已下线），FA 只管执行中按需取数与收尾回写；
- **FA 的写权与你一致**：只写 `editable:agent` 列、模板结构只增不改；它的 `found=false` 是常态结果——界面与后端把空数据当缺省处理，不当错误；
- **平台元数据展示有滞后**：FA 写入后界面直连立即可读，滞后的只是平台侧数据集的行数/统计展示，不要为此加同步回调。

后端硬约束速查（正本细则在 `backend/README.md`，此处只列最易踩的）：

- 响应一律用 `response.ts` 的 `ok/okEmpty/list/fail` 构造——**字段是 `msg` 不是 `message`**、`data` 非 null 非数组对象（列表包一层 `{ items: [...] }`）、业务失败也 HTTP 200、自定义码 ≥ 1000（1~999 是平台保留段；1000~1099 是脚手架 `BACKEND_CODES` 保留段：1004 `FORBIDDEN_BY_PERMISSION`、1005 `CONFLICT`、1006 `COLUMN_NOT_WRITABLE` 等；**业务自定义码从 1100 起**；`fail()` 对 `code < 1000` 直接抛 `RangeError`）。前端 SDK 信封守卫与 max 转发层**共同**校验，任一处不符就折成 `BAD_GATEWAY`，业务码与提示语全丢；
- 引用表只有一种写法 `buiTable('orders')`，***绝不写死 schema 名或 handle***——每个用户实例的 schema 都不同（`bui_{data_uid}`），写死了第二个用户就炸；
- **只做 DML**：应用角色没有 DDL 权限（数据库层拒）；要改表回 A2 出新模板版本；
- **连接经 dataset-proxy，三条会被直接拒**：`BEGIN`/`COMMIT`/`ROLLBACK`（autocommit 单条语句，要原子性压进一条 SQL：CTE、`INSERT ... ON CONFLICT`、单条 `UPDATE ... FROM`）、`SET ROLE`、`SET search_path`；
- 上游超时 13 s、`statement_timeout` 10 s——**只剩 3 s 余量**，别设计需要长时间计算的同步接口；
- `async` 路由必须 try-catch（Express 4 不转发 rejected promise，漏写 = 请求 hang 到超时）；
- 数据库判空在函数体内（模块顶层判空 = import 即 throw = Pod CrashLoopBackOff）；
- 身份从 `getContext(req)` 取宿主注入的 `X-Goalfy-Context`（没有 `Authorization`、没有 `X-Goalfy-User-*`）；隔离维度 = viewer × 实例；写接口用 `canWrite` / `requireBusinessRequestId`；
- 线上只注入三个 env（`DATASETS_DATABASE_URL` / `DATASETS_DATABASE_TYPE` / `DATASETS_MANIFEST`）+ `PORT`，**没有别的注入通道**——需要第三方密钥先与平台定；
- 生产态不开 CORS（后端在公网域名上，不是内网 Service）。

`cd backend && npm test` 用进程内的 PG 兼容测试库，不需要数据集凭证，永远不碰真实 schema——含信封契约自检，先过它再联调。

### 8.16 上线门


上线门、定稿上线、交付报告与结单。

进入前提（总入口 4.1）：S4 出口条件全部满足——前三层候选验收通过、草稿态端到端全真到达终态、问题单无未处置 fail、结果检查表全绿。存在 `full_validation_skipped` 时**不得**进入本节。

发布是外部状态变更。开发者当前请求已明确要求上线，或已确认的总体 Plan 明确写出“前三层候选验收通过后上线”或同等清晰的执行动作时，发布授权已经成立，达到上线门后直接执行上线动作，**不得**重复询问。总体 Plan 只列发布范围、候选资产或路线而没有明确上线动作时，发布授权尚未成立，调用前**必须**单独确认（约束 6）。

### 8.17 定稿与上线


上线动作把草稿态版本**定稿并真正上线**：草稿物理行由 `testing` 晋级为 `live` 并对最终用户可运行；同一家族的旧上线版本保持不变，已在使用旧版本的项目不受影响（详见 [场景包版本体系与发布逻辑](../references/场景包版本体系与发布逻辑.md)）。

定稿上线由平台执行以下闸门与动作，被拦时按结构化错误处理、**禁止**绕过：

- **运行时身份**：FastAgent、工具集、TPE 的物理行必须有运行时注册身份，否则上线后不可调用；
- **工具组连接信息**：URL、沙箱或启动命令三者其一，否则上线出的是不可运行的死配置；
- **文件物化就绪**：Skill 文件等对象存储内容必须已就绪，未就绪的草稿不允许定稿；
- **依赖闭包**：定稿时把依赖的 `latest` 引用钉到当刻解析的具体版本；开发者显式选择跟随最新的依赖保留 `latest` 语义——这意味着主动放弃"旧版本跑旧逻辑"，**必须**让开发者知情。

上线动作：`finalize_asset_version_online(asset_type="scenario_pack", draft_asset_id=<草稿行>, change_note=...)`——闭包校验通过后把草稿晋级 live，旧版本继续可用。被版本闸门拒绝（提示需要先定稿或先建草稿）时按 SD-诊断与维护 的报错对照处理。

### 8.18 上线后反读


上线后**必须**反读线上状态和目标版本；**禁止**因为离线验收通过就宣称已发布（约束 10）。反读确认的线上版本是交付报告的事实基线，也是后续维护与诊断的起点。
