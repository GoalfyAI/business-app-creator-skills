# ⑤ 上线（工作区阶段 G7）

开发者看完 ④ 的验收报告说「可以上线」后，你定版报告里验过的那一版，交一份「上线结果」：定了哪一版、④ 验过什么、实际花了多少、开发者可以做的事。这一段不再请开发者确认什么，也不请开发者发布：发布后已安装的使用者会更新到这一版，发不发、发给谁由开发者自己在发布管理页决定。你不调用发布、不等发布，也不在发布的版本或正式实例上做验证，验证已在 ④ 的在线预览和开发工作集里做完。

## 1. 进入条件

- ④ 交棒：每条验收条目都有结论，开发者（和需求方）看过验收报告，说了「可以上线」；报告里有「未测」条目时同样进 ⑤，你不追问、不请开发者代测。
- 上线是外部状态变更：只有开发者这次明确说了「可以上线」或等价表述才执行，`finalize` 的时间必须晚于「可以上线」的 checkpoint。
- 已用 `business_ui_manage(action="get")` 确认当前 `role`：`owner` 照第 2 节做；`editor` 走第 2 节末尾「协作者分支」；`viewer` 不进 ⑤。

## 2. 段里怎么做

1. **改过的先重新部署**：④ 之后改过场景包或应用的，按 ④ 2.1 重新部署，让定版的是验过的最新草稿；改动影响到的条目按 ④ 2.5 重测。场景包不用单独上线，下一步定版应用时会先校验、再把挂着的本人场景包草稿一起定版上线。
2. **定版前自查预览数据**：在线预览里确认过、上线后还要用的设定是否只存在开发工作集里；是的话先按 ③ 2.2 第 5 步搬到代码默认值、场景包配置或首次设置入口，重新部署后再定版。
3. **定版应用**：`business_ui_manage(action="finalize", draft_asset_id=…, task_id)`；有协作者时家族里可能同时有多份草稿，这时**必须**显式传要定版的那份 `draft_asset_id`（先用 `business_ui_manage(action="get")` 看草稿、创建人和变更说明，和开发者确认是哪一份），只传 `business_ui_id` 会被拒，平台不替你挑。场景包草稿随它一起上线，定版后反读两者的版本号记进工单。被拒按 [../reference/部署与版本.md](../reference/部署与版本.md) 的定版错误码处理。
4. **反读**：`business_ui_manage(action="resolve")` 核对上线版本与挂载的场景包版本，`entry_url` 非空说明入口已写进版本；resolve 报没有上线版本说明定版没生效，**禁止**宣称已上线。`entry_url` 是开发者容器地址，**禁止**写进上线结果或发给任何人当入口。
5. **结单门**：每条路线要以当前合同下最近一次到终态的运行通过，路线冒泡和 ④ 的 `workspace` 真跑都算（真跑以 `route_runs` 里该路线 `succeeded` 为通过）。最近一次失败或没法验证时，先问开发者是否接受，再写（真跑失败时 `run_id` 填那次的 `project_id`）：

   ```text
   task_manager(action="insert", entry_type="checkpoint", metadata={"evidence_type": "route_verification_waived", "scene_package_id": …, "orchestration_id": …, "reason": "<至少 5 个字>", "run_id": <失败那次；没跑过就不带>})
   ```

   一条路线一条。`complete` 被拒（如 `WORKFLOW_TASK_ROUTE_BUBBLE_EVIDENCE_REQUIRED`）时按返回里逐条给的出口做，**禁止**删标签、改文字或另开工单绕过，也不要反复重试。
6. **算总花费**：对工单里记下的每个冒泡、真跑项目重新读一次 `cost_credits`（沙盒按周期记账，刚结束时可能没算全），汇总开发期累计，和 ① 的上限、② 的预计比。
7. **写上线结果**：按下面第 3 节写，写进工单 `task_manager(action="insert", entry_type="result")` 和方案页。
8. **写阶段记录 G7**：用 `business_ui_stage` 写 G7，`next_stage` 填 `closeout`，必须在下一步 `complete` 之前（写法见 [../reference/开发者中心与工作区.md](../reference/开发者中心与工作区.md)「三件套与阶段标记」）。
9. **结单并发出**：`task_manager(action="complete")`；结单响应里的 `delivery_note` 原样补进上线结果，再发给开发者。本轮记下的已绕过平台问题和功能诉求，此时汇总成一条 `submit_dev_feedback`（`blocking` 按主要情况选 `worked_around` 或 `request`），没有就不提；已有同一反馈优先按 `feedback_code` 追加，报告优先写回执 `code`，`source_code` 另注为来源别名。缺完整身份或写入 `unknown` 按 [../reference/报错对照.md](../reference/报错对照.md) 核对，不写成已提交成功。工单正常结单，不因为还没发布而停住。
10. **开发工作集保留**：上线后开发工作集继续绑定在应用上，**不要**解绑、不要为它重新 `deploy`、不要 `close`。在线预览只能连工作集，下次修订改表结构也在这个工作集上改（见 [../reference/数据模板.md](../reference/数据模板.md)「改已上线的模板」）；它只给开发者和协作者用，改它不影响使用者各自的实例库。解绑后 `deploy` 会报 `BUSINESS_UI_PREVIEW_DATA_UNBOUND`，`close` 会被 `TEMPLATE_WORKSPACE_IN_USE_BY_DEPLOYMENT` 拒绝，遇到说明走错了，重新 `bind` 回原工作集即可；**禁止**为此 finalize 派生出来的草稿、下线或删除应用。工作区用 `workspace_push` 保存到云端。

**协作者分支**（`role=editor`）：第 1、2 步照做；第 3、4 步换成 `business_ui_manage(action="request_finalize")` 提请属主定版，做法与报错见 [../reference/多人协作.md](../reference/多人协作.md)「提请定版」；**禁止**调 `finalize`、`resolve` 冒充上线。第 5–9 步照做，上线结果「定版的版本」一行写「已提请，等属主定版」和草稿版本、变更说明，不写上线版本；第 10 步不涉及。交接消息只说：「已提请，等属主定版。属主定版后才会上线，发布也由属主决定；属主先定版了别人的草稿时，你会收到基线过期的通知，需要先合并再提请。」属主处理协作者的提请时，`draft_asset_id` 用那份协作者草稿，其余照第 1–10 步。

**Studio 宿主**同样照第 1–10 步：你定版、报告结果与实际花费、说明发布会让已安装的使用者更新到这一版；**不**调用目录发布、不请求发布、不在发布的版本上真跑，发布由开发者在发布管理页决定。定版没生效时不宣称已上线；写入结果未知时只查询原操作，不重新发起写入（[../reference/开发者中心与工作区.md](../reference/开发者中心与工作区.md)「Studio 宿主」）。

## 3. 上线结果

给开发者的部分只放这个应用自己的东西，用业务话写，结论先行，每一句都能指到证据：

| 项 | 写什么 |
|---|---|
| 定版的版本 | 已定版的是第几版、和上一版比改了什么 |
| ④ 验过什么 | 通过几条、「好不好你说了算」几条及开发者的意见、开发者选了接受的没通过条目；用真实数据跑出的结果一句话 |
| 未测的 | ④ 有「未测」条目时单列：逐条写条目和原因，说明这些行为没有验证；因为要先发布才看得到而未测的（到点真触发、从目录或分享打开），告诉开发者发布后可以自己看、怎么看；没有就写「没有」 |
| 实际花了多少 | 本段 N；累计 N；上限 N。以后每用一次约多少，按 PRD 的用量每周约多少 |
| 发布会怎样 | 照抄：「发布后已安装的使用者会更新到这一版；正式入口和到点自动化在发布后才能用；发不发、发给谁由你定」 |
| 你可以做的事 | 编号列出，都由开发者自己决定做不做：① 在发布管理页发布，选发给谁；② 发布后从 GoalfyMax → 我的资产 → 智能应用 → 打开正式入口，看「未测的」里要先发布才看得到的几条（写清怎么看）；③ 有定时任务的，发布后在正式入口的「自动化」面板打开规则，外部数据有固定更新时间的按北京时间写清规则时间要在它之后；④ 把应用分享给使用者，可以附上下面的使用说明 |

交接消息里在上线结果后面附几句，不单独成节、不放进方案页的上线结果：

- 怎么打开：发布后开发者和使用者从 GoalfyMax → 我的资产 → 智能应用 → <应用名> → 打开，或从目录、分享打开；发布前开发者想自己看，用工作台「在线预览」。不写容器地址。
- 使用说明：每种人第一次打开看到什么、先做什么（每人一份自己的数据，打开是空的；在线预览里的数据不会带过去），平时怎么用，按业务顺序一句话。
- 平台通用的提醒照实写一句，例如刚发布一两分钟内可能启动失败、一段时间没人用会休眠；改已上线的应用时，发布后正在用的人会看到什么变化、已有数据怎么处理。
- 还没验证的和风险：④ 里开发者选了接受的没通过条目、能力缺口。

给后续 Agent 的部分写进工单和阶段文档 G7，不发给开发者：应用名、上线版本、是否已发布（结单时写「未发布，由开发者决定」）；部署状态（`success`）与 `deployment_id`、`source_sha256`、`deployed_scaffold_version`（低于建议线时写「当前 vX 低于建议线 vY，建议下一轮升级」；有 `scaffold_upgrade_notice` 原样写）；场景包定版版本、已验证路线与 `run_id`、豁免的路线与理由；数据模板 ID 与版本；④ 真跑的 `project_id` 与结论，或省略真跑的原因；验收清单通过项数、不适用项、未测的条目与原因；修订时 `compare_asset_versions` 取的前后配置差异。

## 4. 开发者要看、要做的

- 看上线结果。
- 自己决定发不发布、发给谁、什么时候发；发布后按「你可以做的事」看正式入口、开定时任务、分享。

交接消息开头「【⑤ 上线 → 已完成】」，「要你做的」写「看上线结果；发不发布、发给谁由你定，不用回复我」。**禁止**写「请你发布」或等开发者回「发布了」。开发者之后说正式入口里哪条不对、到点触发的结果不对，按 [../tasks/修订.md](../tasks/修订.md) 或 [../tasks/诊断.md](../tasks/诊断.md) 开新工单处理。

## 5. 不给开发者的

定版过程、版本行 ID、结单门、容器地址。

## 6. 产出与落盘

- 工单：上线结果（`entry_type="result"`），`complete` 成功。
- 阶段文档 G7：上线结果全文、给后续 Agent 的部分。
- 方案页 `status` 改为 `done`，`.pv-summary` 写上线结论，`.pv-you` 写「你可以做的事」，`.pv-meta` 写开发期累计花费；「已验证 / 未验证」与上线结果一致，「未测」的留在「未验证」。
- Studio 宿主：不写方案页，上线结果写进「验收报告」最后一节，照 [../design/开发文档/验收报告.md](../design/开发文档/验收报告.md) 骨架里的「上线结果」写，再用 `studio_write_proposal(documentType="acceptance")` 保存新的一版。
- 阶段标记：G7 `passed`。

## 7. 结束条件

- 开发者说「可以上线」之后才定版；上线的是 ④ 验收过的那一版：`resolve` 能取到上线版本，且 `entry_url` 非空（协作者分支改为 `request_finalize` 成功）；
- 上线结果写了定版的版本、④ 的结论、三个花费数、发布会怎样和你可以做的事；有「未测」条目时单列了；
- G7 阶段记录在 `complete` 之前写了；
- `task_manager(action="complete")` 成功，上线结果已写入工单与方案页。

## 8. 出问题怎么办

| 现象 | 先看 | 回到 |
|---|---|---|
| 定版被拒 | [../reference/部署与版本.md](../reference/部署与版本.md) 定版错误码 | ④ 或 ③ |
| `BUSINESS_UI_FINALIZE_OWNER_ONLY`、`PERSONAL_VERSION_STALE_SOURCE` 或提请被拒 | [../reference/多人协作.md](../reference/多人协作.md)「协作相关报错」 | 协作者分支或基线过期的合并 |
| 结单被拒 | 返回里的路线状态；补一次路线冒泡或 `workspace` 真跑，或问开发者后写豁免 | ③ 或 ④ |
| 开发者说「先发布再结单」或要你在正式版里跑一次 | 告诉他发布由他决定，验证已在 ④ 的在线预览和开发工作集里做完；照常结单 | 本段第 9 步 |
| 开发者上线后要改 | [../tasks/修订.md](../tasks/修订.md)，新需求从 ① 走 | — |
| 要下线、回滚、删除 | [../reference/部署与版本.md](../reference/部署与版本.md)，每一步都要开发者确认 | — |
