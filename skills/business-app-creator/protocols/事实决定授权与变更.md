# 协议一：事实、决定、授权与变更

> 共享协议层，各阶段使用同一套规则。本文合并了旧 scene-creator 十二条约束与 app-creator 九条约束，去重后按"事实 / 决定 / 授权 / 变更"四组排列。违反任一条，任务视为失败；其他文件引用编号，不再展开。

## A. 事实

**F1 零捏造与参数溯源**。严禁虚构工具、action、资产 ID、Schema、返回字段、资产状态、业务数据或运行证据。每个工具参数必须能追溯到：开发者输入、上游真实输出、已反读的资产配置、服务端契约、或已明确记录的假设。真实数据不可得时如实说明；估算不得写成运行结果；统计值与结论标明来源、假设、盲区。

**F2 材料完整读取**。开发者指定的文档、项目、日志必须完整读取，截断或分页续读到结束；参考项目完成三层分析（P2 的 S2 §2.1）。

**F3 标识与结果必须反读**。传入任何 ID 前先 `get_asset` / `list_assets` 读回确认真实名称（家族根 id 自动解析到最新 live，核旧版本传物理行 id）；每次创建、更新、关联、上线之后读回确认实际结果，返回成功不等于内容正确。

**F4 受限资产不等于空资产**。`can_view_params=false` 时配置为空是脱敏结果，运行时仍可调用；必须先向开发者说明并等确认；确认后重试带 `allow_restricted=true`。

**F5 工具定义是唯一事实**。本 Skill 写的工具名、action、字段可能滞后；冲突时以当前工具定义为准，差异记工单；列表里找不到的工具不得假设存在或虚构平行工具。探测凭证只做只读查询，不创建工单、资产或项目。

**F6 取证纪律**。判定"平台限制"前先全文检索 Skill 与清单、复核实时工具定义与结构化报错，归因平台必须给证据；判定"文档没写"前先检索，命中不为 0 按原文执行；修复前先确认直接触发条件。结论方向恰好是"不是我的问题"时把标准再抬一档。

**F7 如实汇报**。证据分层记录，不用上层文字检查冒充下层运行验证；核心目标达成而次要受限时可停止重试，但交付必须说明没做到什么、原因、改进条件；禁止时间预测或承诺；只有发布状态与实际证据都成立才说"可直接使用"。

## B. 决定

**D1 三个角色**。开发者（用本 Skill 制作、维护、发布业务应用的人，拥有产品形态与业务契约决定权）；最终用户（未来使用应用的人，只在开发者确认的入口、表单、审阅、授权节点参与）；开发 Agent（执行调查、提案、制作、验证，准备完整的事实、候选、推荐、影响、风险，不代替开发者决定）。写"向开发者确认"指当前使用者；不把两者合称"用户"后自行补全意图。

**D2 确认只放在改变产品结果、契约、风险或责任的节点**：业务理解与目标、候选路线、聚焦还是泛化、执行形态、路线依赖图、交付对象、最终审阅责任与动作、最终用户或 Agent 介入点、能力削减或替换、影响其他应用的改动、外部副作用、删除、发布、收费、真机运行、数据留存范围与隐私、逐列可编辑性与覆盖规则、回流入库语义、页面范围、设计与原型、上线授权。只读调查、候选草案、同一确认范围内的机械实现、离线修复、可逆验证自主推进。

**D3 决策卡**。每次给开发者的决策卡只含：当前问题、证据、推荐、替代、选择后改变什么、验收怎么看、需要决定什么。目标 / 责任 / 范围变化 → 确认业务决定；费用 / 权限 / 发布 / 外部副作用 → 确认动作授权；同一范围的实现与修复 → Agent 自主；测试不通过 → 展示失败证据与修复路径，人同意继续不改变测试结果；非阻塞改善想法 → 记为后续建议，不扩张本次功能。

**D4 两种对齐方式**。多个相互影响的决策先形成 Plan（已确认事实、候选、推荐与理由、影响、待选事项、验收标准；涉及路线时附依赖图与交付方案），统一确认前不写正式契约、不创建资产；只有一个决策或缺开发者才有的事实时单项询问。业务路线、聚焦 / 泛化、执行形态、最终审阅、最终用户介入、能力削减、外部副作用**没有安全默认**。

**D5 面向开发者的表达**。业务方案里只说能解决什么问题、分几个阶段、各产出什么、候选与推荐、需要决定什么、最终用户在哪参与；禁止资产数字 ID、技术字段名、代码片段、内部调用链。平台术语由 Agent 转译；内部记录带 ID 消歧，方案用名称。工作语言跟随开发者。

**D6 用户确认不替代专业判断**。业务方能核实事实，不能承担专业判断；系统拿证据并说明不确定性，必要时引入专家；不靠一个确认按钮转移责任。

## C. 授权

**A1 工单先行**。新任务第一项业务调用必须是 `task_manager`；`read` 与 `write` 不混用；`write` 必须传完整 `skill_version`；建立后每次调用带 `task_id`（它是审计范围，不是资产标识）。

**A2 高风险操作需明确授权**：修改影响其他应用的共享资产；替换开发者指定或权限受限的能力；删除、替换凭证、扩大权限；能力容器上线、应用定稿上线、目录发布；收费、发信、通知、正式业务写入等外部副作用；在真实项目中运行。Plan 只有明确写出上线动作时才同时构成上线授权；范围、路线、能力削减或风险实质变化必须重新确认。试验授权与正式制作授权分开。

**A3 修改共享资产前先克隆**。被其他应用引用的工具集、FastAgent、普通任务点先 `clone_asset` 在副本改；副本调用名一律从返回值反读，不推算不拼接；脚本里的 `tool("<mr_name>")` 与预加载声明换成副本调用名。

**A4 能力削减或替换必须先确认**。对开发者引用或明确预期的能力，不得静默削减、替换、降级；单独说明原能力、不能沿用的原因、替代边界，暂停等确认；不混在长篇汇报里。

**A5 后端边界与身份**。专属后端由 p2s 部署在公网域名上，不是内网 Service；链路为 `App(iframe) → sdk.api.request → 宿主 → Max 后端 api-proxy（服务器到服务器）→ 本后端`；Max 只发三个头（`Content-Type` / `X-Goalfy-Business-Request-Id` / `X-Goalfy-Context`），其余请求头与 cookie 属平台内部、不得依赖；`X-Goalfy-Context` 是 base64 claims，是否签名以 `backend/README.md` 为准（截至 2026-09-07 未签名），未签名期间基于 claims 的判权只拦误操作、不是安全边界，资金、批量删除、对外发布不得只凭 claims 放行。三条纪律：写权限后端自判（`canWrite`，宿主不区分读写不兜底）；生产态不开 CORS；没有第三方密钥注入通道。响应一律 `{code, msg, data}` 信封、业务失败也 HTTP 200、自定义码 ≥1000（1000~1099 脚手架保留，业务码从 1100 起）。

**A6 调用契约零改动**。应用与平台只有两种交互：发起一次业务路线运行（`chat.start + metadata.submit_data`）与应答运行中表单（三次握手，到业务确认才算完成；最终交付审阅 `delivery.review` 也是业务表单，用 `reply`，`confirm` 只用于普通聊天确认）。不发明字段、不改语义、不绕开 SDK。创建态 / 进行态分界：应用是唯一发起入口，项目页不发起新运行。

**A7 桥层与数据面硬限制**。`GET/DELETE` 无 body、嵌套查询走 POST、请求 ≤256KiB、响应 ≤1MiB、上游超时 13s（`statement_timeout` 10s）、写接口幂等（键 `X-Goalfy-Business-Request-Id`）、文件只传路径；连接经 dataset-proxy，禁 `BEGIN/COMMIT/ROLLBACK`、`SET ROLE`、`SET search_path`；应用代码禁 `CREATE/ALTER TABLE`，加表改表回模板；一个应用只绑一个数据模板；schema 真名禁止硬编码，引用表只用 `buiTable('表名')`；镜像必须用户无关。

**A8 编辑与生产共治**。逐字段可编辑性唯一正本是 PG 列注释 `[editable:user|agent|system]`；`user` 列 FA 与生产回流不得覆盖；读不到声明的列按 user 处理；所有写入带来源标记（`user_edited` / `generated`）；回流入库语义由开发者在 G3 声明。

**A9 apc_skill 禁写**。不写资产数字 ID（用名称）、不复制业务路线依赖图、不写单个工具完整 Schema、不写制作过程、不写最终用户私有数据。

**A10 设计纪律**。脚手架 demo 只用于理解协议与 SDK，禁复用其页面结构与视觉；生产级原型经开发者确认后才编码；与 demo 高度相似且说不出业务理由 = 设计未做。

## D. 变更

**C1 自底向上的创建顺序**：工具组与授权卡 → FastAgent → 工具集 → 普通任务点 → 能力容器草稿 → 编排型 TPE 创建与挂载 → 其他关联与业务路线。草稿容器与最终关联是两个阶段；单元未通过验收前不写最终路线；单条编排型 TPE 只要声明业务事件，正式运行也必须有单节点业务路线。

**C2 变更影响必须展示**。任何改动先按需求追踪矩阵列出受影响的页面 / 数据 / 执行 / 测试与未影响项及理由，改后回报实际修改与验证结果；沿真实依赖使相关通过记录失效，不能只改路线 JSON 却保留原页面验收结论（协议二）。

**C3 从受影响阶段重新进入**，不全量重做；同一确认范围内修同一资产，不靠反复建新资产规避问题。

**C4 部署与下线纪律**。先预部署验证再交付；下线走 `business_ui_manage(offline)`（拆容器、保留库与源码，可重新上线）；已发布到目录的先取消发布才能下线；删除才是不可逆的；回滚应用不等于数据库可降级。

**C5 先包后应用只是工程前置**。能力容器（场景包）上线是应用制作的契约基线，不是产品探索的顺序；G1–G3 已把业务与应用一并设计。能力容器工单结单不等于应用已交付。
