# 智能应用开发指南

<!-- scaffold-min-required-version:v20260916-8941ec -->

本 Skill 要求的脚手架最低版本由上述机器标记记录。它与 MCP 返回的环境抬杆共同生效，按服务端发布登记 ID 比较；开工、接续及预部署时执行[脚手架版本与升级](references/脚手架版本与升级.md)。

> 版本 v3.0，2026-09-08。本 Skill 是**一个主导入口、七个阶段、一套共享协议、八份细则正本**。阶段文件 G1 至 G7 是唯一主线，读完即可执行；细则正本只放阶段文件写不下的表格、契约、纪律清单与示例，在阶段文件点名时查阅。总入口负责识别任务、盘点材料、路由阶段、控制范围与授权、验收整套智能应用。

## 0. 智能应用是什么

本 Skill 的产出物只有一种：**智能应用**——交付给一类明确客户、由最终用户持续使用的应用。它结合客户持续变化的业务事实，在约定目标、权限与验收标准内，稳定完成一类反复发生的工作，并在下一次工作中复用已经确认的信息和经验。

智能应用由五个部分组成，每个部分承担用户使用链路上固定的环节。缺任何一环，做出来的就只是一个能出结果的聊天入口，不是智能应用：

| 组成部分 | 是什么 | 承担的使用环节 | 最终用户做什么 | 应用做什么 |
|---|---|---|---|---|
| **前端应用** | 在脚手架上实现的页面：首页、项目列表、消息中心是平台必备；看板、数据管理、业务发起、项目页与交付审阅是业务页面。只经 SDK 与平台交互，自己不发 HTTP | 看到现状 | 打开应用看看板：指标、列表、待办 | 展示本用户的统计、历史结果与进行中的任务 |
| | | 发起一件事 | 选任务入口，只填自己才知道的信息，或选一个已有项目复用 | 读取已有资料带入发起报文，创建项目，按业务路线开始执行 |
| | | 拿到结果与修改 | 预览、核对事实、下载；对指定版本提修改意见，比较、确认；承诺发布时授权发布 | 呈现完整产物与依据；只改目标部分、联动受影响内容、保留旧版本、失败不覆盖；执行已授权的外部动作并取回执 |
| | | 离开再回来 | 关掉页面、换设备、隔天再打开 | 任务与结果可找回，从正确位置继续，不重复执行不重复扣费 |
| | | 反馈 | 说这次结果哪里不对、有没有用 | 关联到具体任务与版本，进入优化 |
| **专属后端** | Express 加 PG，直连本用户的 app schema；部署在 p2s 公网域名，经 Max 后端服务端转发到达 | 编辑数据 | 在数据管理页增删改自己的业务数据 | 按逐列可编辑性放行，带来源与审计；统计聚合喂看板；产出回流入库 |
| **智能应用数据模板** | 表、字段、逐列可编辑性 user、agent、system，来源标记，回流语义；用户首次打开时从模板复制出专属一份，一用户一 schema，被后端直连和执行中的你两条通道读写 | 下次更省事 | 不再重复解释门店、账号、偏好 | 复用已确认的事实与长期偏好；单次要求只影响本次；可查看可纠正；生产回流不覆盖用户改过的字段 |
| **能力容器** | 平台里叫场景包，定义执行中的你在这个业务里能做什么、怎么做、用什么做：业务路线、任务点、工具集与 FastAgent、工具组与授权卡、apc_skill 与场景 Skill 文件、长期数据集引用 | 执行中参与 | 在必要节点补充事实、做业务选择、给动作授权 | 连续执行已确定的步骤，只在缺信息、需取舍、授权不足时暂停并说明原因；冻结交付、发起审阅 |
| **发布单位 business_ui** | 智能应用在平台里的资产身份：自己的家族与版本，挂载一个或多个能力容器、至多 1 份数据模板 | 版本与交付 | 用到的始终是验过的那个版本 | 绑定明确的容器版本与模板版本；契约变化触发受影响测试 |

能力容器内部的四类对象各管一段：**业务路线**对应用户的每个入口，定义入口表单、节点依赖与并行、中途表单、交付冻结与审阅、重入；**任务点**分两型，编排型 TPE 是确定性脚本，编排工具与 FastAgent，普通任务点派给 TaskAgent 临场执行、可与用户交互；**工具集**装工具与 FastAgent 并附使用指南，预加载或动态加载；**apc_skill 与场景 Skill 文件**是运行时你看得到的业务规则与知识。

运行关系：用户在页面发起 → 业务路线在一个项目里跑 → 任务点调用工具与 FastAgent → 产出回流到本用户的 schema → 页面展示、用户编辑 → 下次运行读取已确认的事实与偏好。

交付物 = 能力容器版本 + 应用版本 + 数据模板版本 + 验收记录，验收记录里每条业务承诺都对应规则、实现与分阶段证据。能力容器工单结单不等于智能应用已交付。

## 1. 总入口负责什么

1. **识别任务。** 六类：新建、接续、修订、诊断、能力试用、仅讨论。围绕当前工作台中的具体应用形成方案，属于新建或接续的业务方案工作；“先讨论方案、暂不开发”限制本次推进范围，不免除本地方案展示。纯概念咨询或未指向具体应用的开放讨论不初始化工程。开发者明确要求只在聊天里回答、不写文件时，遵从其要求。
2. **盘点已有材料、资产与证据。** 从最早未满足的必要条件进入，**禁止**机械从 G1 重做。
3. **每阶段给出四样。** 推荐下一步、理由、待决策事项、验收依据。平台术语由你转译成业务语言。
4. **控制范围、权限、试验费用与副作用。** 到必要决定点暂停；其余已授权工作连续推进。
5. **验证失败时返回问题归属与证据。** **禁止**把失败转述为"请开发者自行处理"。
6. **最终验收整套智能应用。** 按 G1 编号的承诺清单逐条对账，能力容器工单结单**不等于**应用已交付。

### 1.1 角色与称谓

本 Skill 里只有四个角色，所有"人"都必须落到前两个之一：

| 角色 | 是谁 | 在本 Skill 里做什么 |
|---|---|---|
| **开发者** | 使用本 Skill 制作、维护、发布智能应用的人。代表客户方回答业务事实 | 拥有产品形态、业务契约、授权的决定权。所有"向开发者确认""开发者拍板""开发者授权"都指他。文中"客户方"指开发者所服务的客户，其事实由开发者转达 |
| **最终用户** | 智能应用上线后使用它的人 | 只在开发者确认过的入口、表单、审阅、授权节点参与运行。运行期分工里的"最终用户"就是这一步由他来做 |
| **你** | 此刻执行本 Skill 的你 | 调查、提案、制作、验证；准备事实、候选、推荐、影响、风险；**不代替**开发者决定。本 Skill 全文用「你」称呼 |
| **运行 Agent** | 智能应用运行时在能力容器里执行任务的你，包括 SystemAgent、TaskAgent、FastAgent | 只按已确认的设计执行；**禁止**把技术选型问题转嫁给最终用户 |

称谓规则：开发期的确认、授权、审核，主语一律写**开发者**；运行期每一步谁来做，主语一律写**最终用户**或**运行 Agent**；需要专业判断而最终用户无法承担的，写**专家**，由开发者引入。单独出现的"用户"一律指最终用户；本 Skill 用「你」称呼你；单独出现的「你」指运行 Agent。**禁止**用"人""业务方"这类不落到角色的称呼。

### 1.2 任务识别

| 开发者要做什么 | 任务类型 | 工单 | 从哪进 |
|---|---|---|---|
| 为当前工作台中的具体应用形成业务方案，或把业务目的、SOP、经验、参考项目做成智能应用 | 新建 | `write` | G1；只讨论方案时限定于本轮方案范围 |
| 继续此前未完成的制作 | 接续 | `get` 原工单 | 先读当前应用本地文件；换机或本地缺失才按协议四第 6 节恢复，核对阶段与证据后进入未完成处，不默认用云端覆盖本地 |
| 改已上线应用的页面、接口、表、路线、能力 | 修订 | `write`，先取可编辑草稿 | 受影响的最早阶段，规则见协议一约束 24 |
| 效果差、报错、数据不对、页面异常 | 诊断 | `read`；转修复时新建 `write` | P8 定位后路由到所属阶段 |
| 验证一个外部能力值不值得做进来 | 能力试用 | `write` | G2，流程见 P2 能力试用一节 |
| 纯概念咨询、未指向具体应用的开放讨论，或明确只在聊天里回答、不写文件 | 仅讨论 | 不建工单 | 对话答复，不初始化应用，不创建平台资产 |

新建、接续等制作任务先过工单 Gate，规则见协议四第 1 节；再按 1.3 确认桌面工作区、核脚手架版本并初始化或接续应用，准备方案入口。具体应用的方案工作也适用；仅讨论分支不执行初始化。只讨论方案不自动授权实现业务能力、部署或发布；接续沿用原应用身份和实际阶段，不因讨论方案重建或重置。意图或关键参数缺失时先问。缺口分六类：意图、关键参数、知识、工程偏好、产品决策、授权，判定方法见 P1 第 2 节。

**工程偏好有正本，开工前读一次。** `dev_preferences(action="pull")` 取当前开发者的个性化文档，返回 `version` 与下载地址，按需阅读其中的开发偏好与项目约定。文档里写过的照做，其余采用可逆默认；当前指令优先。开发者明确表达且适用于后续工作的偏好，用 `dev_preferences(action="push", base_version=<pull 返回的 version>, content=<修改后的完整 Markdown>)` 保存。首次 `exists=false` 时 `base_version` 传 `null`；版本冲突先重新 pull、合并再保存；`RESULT_UNKNOWN` 或 `result="unknown"` 时先 pull 核对实际内容与版本，再决定下一步。保存范围限长期偏好与项目约定，平台问题与功能诉求走 `submit_dev_feedback`。本工具按自身 Schema 调用，身份由已验证上下文提供。

### 1.3 开发者中心：在 Goalfy 桌面工作台中制作应用

**工作台由 App 管理。** Goalfy App 负责工作台的安装、更新与运行。你在当前应用对应的工作目录中制作，维护应用身份、阶段记录和方案文件。

**开场先准备方案工作区。** 识别为当前工作台中的具体应用任务后，在展开长篇分析、样品研究或多轮访谈前，先按 1.2 通过工单 Gate，再完成本节规定的归属确认、脚手架检查、初始化或接续。首次实质性方案答复结束前，必须将已知业务目标、初步范围、当前结论和待明确事项写入 `docs/proposal/index.html`，形成可阅读的最小草案，并核实工作台是否识别和展示。内容不足标为未知，不等待完整计划书或最终应用名称；临时名称明确可修改。

分别核实外层工作目录存在、本应用身份文件齐全、方案入口可读取、宿主方案页已展示，每项结论各自需要对应证据。没有宿主观察能力时只报告文件与契约检查结果，将右侧页面展示标为未观察。初始化或展示失败时报告具体阻塞和已完成部分，让开发者明确知道当前进度。

**方案是有统一入口的 HTML 组包。** `docs/proposal/index.html` 展示业务过程、开发内容与进度，可按内容使用 Tab、折叠和目录导航，样式、脚本与配套资源留在 `docs/proposal/` 内。组织和审美以方便查阅为准：结论直观、层次清楚、视觉克制；具体规则见协议三第 7 节。`docs/stages/` 下七份 md 给你和后续 Agent 保存完整事实与技术证据。

`workspace.json` 是阶段状态正本，阶段开工、完成或验证失败时及时更新；开发者要看的进度同步到方案 HTML 的当前阶段、承诺清单与开发内容。新建或切换会话时，先核当前应用目录与身份，接续已有工程。写入前重读受影响文件，保留其他会话的新改动；有冲突时先核对差异，确认取舍后再写入。

**获取应用脚手架与保存资料。** 智能应用脚手架经 `business_ui_bundle` 的 `download_template` 获取并核版本；应用资料的云端状态、读取与保存分别使用 `workspace_remote_status`、`workspace_pull`、`workspace_push`，接续与差异处理按协议四第 6 节执行。

**定位应用工程。** `goalfy-app-scaffold` 是智能应用的工程模板。“应用工程根”指本次应用自己的目录：先根据当前会话的实际 cwd 和已有文件确认归属，在 Goalfy 分配工作目录的 `apps/` 下定位本次应用；已有应用沿用其目录与身份，新应用在确认位置后初始化。

**一应用一目录，顶层名称要能区分业务。** 新建时在工作台指定的位置使用与本次业务对应的稳定目录名，例如 `restaurant-koc`、`order-audit`。同名目录已存在时先读身份：同一应用接续，另一个应用使用有意义的区分名称并保留原目录。目录树的顶层写实际应用目录名。以一个新应用为例：

```text
restaurant-koc/             本次应用工程根，位于工作台分配的 apps/ 下
├── app.json                本应用名称与业务界面身份
├── WORKSPACE.md            本应用工作区身份与阶段索引
├── workspace.json          七阶段状态
├── scaffold-release.json   本应用实际采用的脚手架版本
├── docs/                   本应用方案、阶段记录与历史
├── frontend/
└── backend/
```

每个应用分别初始化名称与工作区身份，使用自己的 `workspace_id`、`business_ui_id` 和阶段记录。保留工作台分配的外层目录名；目录名便于人识别，平台归属以身份文件为准。接续时沿用已有实际目录与身份。

制作任务建工单后、初始化或继续开发之前，按下面顺序：

1. **先确认归属，再核脚手架版本。** 新建先确认应用目录；接续先定位原应用并读本地文件，换机或本地缺失时按协议四第 6 节恢复，已有内容先比较、保留差异再处理。读取该应用根 `scaffold-release.json`（缺失传空），调用 `business_ui_bundle(action="download_template", task_id=..., current_scaffold_version=..., workspace_id=<已有工作区标识>)`。新建尚无工作区时省略 `workspace_id`。最低版本由服务端按工单绑定的 Skill 版本取已登记值，调用时只传这些参数。新建用当前环境已登记的最新模板，校验下载包 `sha256` 和解包后的 `version`；已有应用低于必须线时完成实际代码迁移与验证，通过后继续；低于建议线时在开发记录中提示“建议升级脚手架版本”，安排升级后再进入预部署。每次检查以本应用清单和 MCP 在线结果为依据，完整规则见[脚手架版本与升级](references/脚手架版本与升级.md)。
2. **在本应用目录生成工作区。** 模板解包到已确认的新应用目录；若压缩包带通用外层目录，整理到本应用工程根，使身份与方案入口位于约定路径。工作区文件统一由脚手架命令生成：

   - **新建**：`npm run scaffold:init -- --environment <环境> --app-name "<智能应用名称>"`，已经有业务界面草稿时再加 `--business-ui-id <真实 ID>`。它生成本应用的 `app.json`、`WORKSPACE.md`、`workspace.json`、方案页和七份阶段文档；`workspace_id` 自动生成并落盘。示例应用独立保存在 `examples/`。
   - **接续时补齐工作区文件**：已有工作区使用 `npm run scaffold:repair -- --app-name "<智能应用名称>"`，保留已有事实，只补缺失文件。
   - **装依赖并自检**：`npm run setup`，然后 `npm run doctor`。先修第一条 `FAIL`；`WARN` 按当前阶段处理。
   - **三条硬约束**（prod 观测里两个应用因此没上线）：① `app.json`、`WORKSPACE.md`、`workspace.json`、方案页与阶段文档一律由 `scaffold:init` / `scaffold:repair` 生成，手写的文件会被契约逐条打回；② 应用工程根必须是 Git 根——`scaffold:init` 默认在应用根 `git init` 并提交模板基线，旧版本或传了 `--no-git` 时自己在应用根做，应用嵌在开发者中心 `apps/<app>/` 子目录时同样在应用根单独初始化，否则 doctor 报 `GIT_ROOT_MISMATCH`；③ 模板自带示例包 `frontend/schema/packs/demo-pack/` 且已在 `goalfy-app.json.packs` 声明，用 `scaffold:init -- --without-demo-pack` 去掉它（或删目录并同步移出 packs），二者一致 verify 才会通过。

   应用工程根必须有合法 `app.json`，且 `schema_version` 形如 `goalfy.app/vN`；`WORKSPACE.md` 未就绪会显示“初始化中”。`workspace.json` 是阶段状态正本，七项按 G1 到 G7 排，`name` 用阶段中文名，G1 为 `in_progress`、其余 `not_started`，与阶段 md 的状态同步。`docs/proposal/index.html` 必须在首次实质性方案答复结束前按已知业务重写并删除模板标记；缺口写未知，不保留通用占位文案。即使最终只用能力容器，仍保留本应用的方案与阶段工作目录。
3. **应用调试按需准备。** App 管理工作台内部服务，G1 到 G3 的方案与设计由 Goalfy 展示。需要真实应用预览时，按已校验脚手架的命令准备本应用的前后端调试；先查当前运行状态，已就绪就复用。预览连接、端口与运行时声明由工作台和脚手架管理，保留桌面注入的 `GOALFY_DEV_FRAME_ANCESTORS` 及来源限制。预览失败先核应用版本、运行状态与连接提示，定位原因后处理。应用调试与预部署验证的区别见 P5 第 8 节。
4. **Max 真实交互使用在线预览。** 应用完成上传并部署后，凡需要 Max 真实身份、真实业务路线、运行中表单、交付审阅、数据管理或用户旅程操作的验证与展示，都在工作台右侧「在线预览」页完成。在线预览使用工作台启动时绑定的 `business_ui_id` 与环境，向同环境 Max 换取一次性预览凭据；凭据不写入应用、方案页或工单。开始操作前核对上传、部署、环境、应用版本和测试账号，操作后记录请求标识、部署信息、页面状态与结果。`PREVIEW_NOT_READY`、身份或配置缺失等情况按具体返回记录为阻塞并处理；这类 Max 交互使用工作台在线预览，不另起浏览器窗口或标签页。未上传的本地页面继续使用「预览」页调试，Max 真实交互证据写在在线预览结果中。
5. **身份两处同改，用命令改。** `app.json` 的 `id` 与 `WORKSPACE.md` 的 `business_ui_id` 是同一个应用身份。G1 到 G4 的新应用两处写真实的 `null`，`WORKSPACE_BUSINESS_UI_PENDING` 允许继续本地开发。G4 门禁通过后、推进 G5 前，先创建仅含应用身份的 `business_ui` 草稿，再运行 `npm run scaffold:bind -- --business-ui-id <真实 ID>` 原子回填，绑定成功才允许进入 G5；G5 在同一草稿上补齐数据模板与后端。`goalfy-app.json` 用于交付清单，开发期身份由上述两份文件维护。
6. **命令定位到本应用。** 桌面会话 cwd 可能是外层专属工作目录；工程命令的工作目录必须明确指向 `apps/<本应用目录名>` 的实际绝对路径。后续命令持续使用已确认的应用工程根。

之后按协议三第 7 节更新方案、按协议四第 6 节记录阶段与保存云端。对话同步、资料保存、源码上传和部署结果分别核验，以各自的成功证据为准。`.workbench/` 交由工具维护并排除在版本控制之外，持久化进度写入应用工程的身份、方案与阶段文件。

### 1.4 前置：工具可用性

business-app-creator 的 MCP 工具在会话开始时已在工具列表里。用某个工具前先确认它存在。**当前看到的工具定义是唯一事实**，规则见协议一约束 26。找不到的工具不假设存在，按约束 26 处理。确认凭证只做只读查询。

**撞到平台问题就报上去。** 开发或验证中遇到疑似平台缺陷、或需要平台侧处理的明确诉求，用 `submit_dev_feedback` 提一条，**不需要**先查清根因，你已经临时绕过去的也照提。同一个问题要补证据或补排查过程时，带上这次返回的 `feedback_id` 追加，**不要**新建；换一次开发里再次发生才新建。提交成功只表示内容已收到，**不表示**缺陷已确认或已解决，**禁止**据此放行验收。要看处理进度用 `query_dev_feedback`，查到 `null` 表示还没进展，**禁止**据此编造结论；这是可选动作，**不要**为了等它停下工作。上报**不替代** `platform_blocked`：范围受影响时该停的交付照停。开发偏好与项目约定不走这个工具，走 `dev_preferences`。

**承诺清单是七个阶段的主线，阶段只是时间轴。** G1 把《业务计划书》里的每条承诺抽成编号 `C1`、`C2`…，此后 G2 每条对应一次能力实测或标"无需实测"，G3 每条映射到节点、页面或表，G4 到 G6 每条逐条拿证据，G7 逐条对账；每个阶段出口整份重写 `commitment_list`，并把每条承诺与状态显示在开发者中心页面顶部。规则见协议二第 1 节。

**阶段文件读取纪律。** 进入任何阶段的第一个动作是完整读取该阶段文件；一次只读一份；出口条件满足后落 `stage_exit` 再进下一阶段；修正环内的回跳沿用原记录。每个阶段固定七项：进入依据、本阶段建设、给开发者看什么、要确认哪些边界、门禁 Checklist、证据与结论、失败回退。给开发者看的方案是应用工程根下的 `docs/proposal/index.html`，按阶段持续展示业务路线、能力与费用选择、页面设计、开发进度及交付摘要；不把设计示意当成真实应用。`docs/stages/` 下七份 md 给 Agent 保留事实与完整证据，工单标签存同一份全文。载体、固定内容与更新规则见协议三第 7 节。

**平台对象什么时候创建。** **禁止**提前建空容器；**禁止**用页面替代单元证据。

## 5. 两层 Checklist

- **G 门禁**，文件 `checklists/G门禁检查清单.md`。回答"是否具备进入下一阶段的条件"，共 48 条。每条只有三列：查什么、证据是什么、不过怎么办。门禁引用 U 项的分阶段结论，**不替代**业务行为。
- **U 业务行为验收明细**，文件 `checklists/U业务行为验收明细.md`。八组：U1 开始、续用与历史；U2 信息准备与真正使用；U3 Agent 连续推进；U4 离开与异常恢复；U5 结果检查与反复修改；U6 留存、偏好与效果回传；U7 跨应用 Agent，条件适用；U8 临时编排，条件适用。G3 实例化为本项目用例，G4、G5、G6 分层取证，G7 复验。
- **专业验收清单**：`checklists/方案挑战检查清单.md` 用于 G3；`checklists/编排型TPE验收检查清单.md` 用于 G4；`checklists/场景包验收检查清单.md` 用于 G5a 能力容器上线门；`checklists/应用验收检查清单.md` 用于 G5b、G6、G7。

## 6. 贯穿七阶段的四项横向设计

1. **使用问题是开发要求。** U1 至 U6 按阶段落实：G1 定价值，G2 验前提，G3 定行为，G4 与 G5 做能力，G6 验使用，G7 验最终版本。U7 与 U8 不是自动加入的必备功能；纳入承诺时 G2 必须验前提。
2. **优化能力与"优化已经有效"分开。** 规则见协议四第 3 节。
3. **两类知识、两类问题分开存放。** 规则见协议四第 2 节。
4. **展示、确认、执行、验收连成一条。** 不是每步都让开发者点确认，见协议一约束 22；可视化是同一事实的不同视图，见协议三第 2 节；路线变更必须展示影响，见协议二第 5 节。
