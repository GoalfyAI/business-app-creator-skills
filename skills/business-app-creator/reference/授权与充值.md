# 授权与充值

## 适用场景

应用要让最终用户授权外部平台账号（如广告平台）、要在应用里充值，或处理授权选择冲突、充值未开通时读。

## 规则

### 当前环境能力与版本依据

Skill 不固定某个 SDK 或脚手架版本号，也不把历史示例版本作为当前最低版本。开始接入前读取目标环境工具返回的脚手架版本与兼容要求、脚手架 SDK 文档、实际导出与类型定义，以及目标宿主的 Bridge/RPC 契约；记录环境、来源、实际版本和所需接口。`scaffold-min-required-version` 是发布系统维护的最低兼容下限，不是唯一指定版本，也不是授权/支付 API 存在性的证据。平台当前明确的最低兼容版本要求仍须满足，应用依赖与锁文件固定到已验证版本，不自动升级最新版。

分别核查授权 `context/authorize/revoke` 与支付 `open` 的存在性、签名和宿主支持情况。下文接口名描述本功能需要的能力；调用参数以当前环境契约为准，契约发生实质变化时说明差异，不猜兼容。仅版本号不同不能判定能力缺失，版本号相同也不能证明接口可用。

若文档、实际 SDK 导出或宿主能力不一致，先排查工作区旧模板/缓存、依赖来源及部署版本，给出具体文件路径、缺失接口和运行错误。区分“代码已实现”“目标环境已部署配置”“真实验收通过”；不能通过手写桥接、伪造接口或成功结果来绕过缺口。此检查不改变预览验收与定版的真实验收要求。

充值能力还需核对应用后端的安全代理、实际路由接线、原始请求体采集、依赖和固定层测试，不能只检查前端 `authorization` / `payment` 导出。沿用已有应用时，按 [脚手架与预置件.md](脚手架与预置件.md) 迁移前后端平台固定层；平台服务已部署不代表旧应用源码已具备代理。

### 能力发现与应用授权选择

确认页功能清单里写了「外部平台授权」才做。先确定应用草稿及固定场景包；尚无应用时记录候选与充值能力待核查，按 G5 第 1 步取得 `business_ui_id` 后再查询，不为探测能力提前创建空资产。仅使用目标环境 `business_ui_manage` 实时 schema 提供的 action；缺少时先刷新连接、核对部署，记录待核查项。

| 调用 | 用途与关键输入 |
| --- | --- |
| `business_ui_manage(action="ensure_draft", task_id=..., business_ui_id=...)` | 取得明确的 `draft_asset_id`；后续读取候选、保存、部署与 finalize 使用同一草稿。 |
| `business_ui_manage(action="list_authorization_candidates", task_id=..., business_ui_id=...)` | 读取草稿候选，将 `platforms` 的名称、图标与 `candidates` 四元组对应。选择默认空；用户已明确指定平台时据此筛选，不重复确认，存在实质歧义时再澄清。MCP ID 不等于工具组 ID。 |
| `business_ui_manage(action="save_authorization_selection", task_id=..., draft_asset_id=..., ...)` | 传候选原样四元组数组、`authorization_candidates_revision` 和草稿当前 `expected_authorization_policy_digest`。摘要初始为空串，非空为平台返回的 64 位小写十六进制值；空数组表示明确不选，并发字段不可省略。 |
| `business_ui_manage(action="get_recharge_config", task_id=..., business_ui_id=...)` | 只读平台开通状态。`enabled=false` 与查询失败分别记录，不承诺充值可用、不要求开发者填写收款账号或自行构造支付链接。 |

确认页与方案页记录选中平台、用途、对应页面及“在哪个应用授权，只有这个应用及其项目可用”；账号数量以实际 OAuth 结果为准。保存冲突时停止部署，使用原草稿重读候选与策略，将差异交给开发者确认后再保存，不自动重试旧选择或静默增加许可。草稿与定版语义见 [部署与版本.md](部署与版本.md)。

平台收银台与第三方 MCP 写操作分别核查：缺少建投/调投工具不代表支付不可用。原范围涉及自动操作而实际仅支持人工处理时，说明差异并由用户决定，不静默降级。能力与证据等级统一按本文第一节记录。

### 接入与交互

调用参数以当前环境 SDK 与宿主契约为准。以下规则分别约束授权、预览与支付：

| 场景 | 接入规则 |
| --- | --- |
| 授权状态与交互 | 每次进入页面或重新获得焦点读取 `sdk.authorization.context()`。直接调用 `sdk.authorization.authorize({auth_card_id})` 或 `sdk.authorization.revoke({authorization_id})`，按返回 `status`（success/cancelled）及刷新后的 `context` 更新页面；ID 原样取自 context，请求失败保留重试入口。 |
| 授权检测与业务恢复 | `authorization_required` 是检测结果，不是弹卡指令。“授权账户”不先启动检测项目或跳转对话找卡。失败/取消不标业务成功、不进入最终交付审核；成功后重新查状态，由用户继续业务，不自动重放充值或投放。 |
| 身份与凭据 | 宿主处理 OAuth/custom 表单。业务应用不读取、存储或转发 token、密钥、custom fields，不自行传 user_id、business_ui_id、版本、预览标识或回调 URL；只读/他人实例不允许真实授权。 |
| 预览隔离 | 开发者中心「在线使用」支持真实授权和充值，只读取本用户、本应用、当前作用域的授权，不回退全局。同一开发者和稳定应用更新草稿、重新部署预览后复用预览授权与订单；发布不复制到正式实例。即使广告账户相同，授权和订单也不能跨作用域共用。预览付款是真实付款。 |
| 充值账户与建单 | 配置实际返回 `enabled=true` 后，让用户从 `context.recharge_accounts` 明确选择实时核验的账户引用；普通授权记录 ID 不能替代该引用。由专属后端创建订单及 checkout，再调用 `sdk.payment.open({order_id, checkout_id})`。同一充值意图重试复用幂等键。 |
| 支付与到账 | `completed` 仅表示收银台流程结束，`cancelled` 表示关闭/取消；返回后均重新查单。服务端 `payment_status=paid` 才表示已付款，`fulfillment_status=completed` 才表示已到账。 |
| 独立 mock 与未开通 | 独立 mock 返回空平台列表及明确未开通结果，不能作真实 OAuth 证据；充值返回 `unavailable/CAPABILITY_UNAVAILABLE`。不模拟支付成功，不用外链替换平台收银台。 |
| 接口故障定位 | 核对当前 `sdk/authorization.ts`、宿主 RPC、预览会话及容器配置注入，按本文第一节区分制品、部署与验收证据，不能从一次错误推断平台缺少 OAuth 能力。 |

测试取消、授权失败后重试、解除后列表刷新、跨应用/跨预览作用域拒绝及应用切换时弹窗取消；不得用生产真实授权或真实支付做自动化测试。

### 交付检查

- 核对最终提交快照的授权选择与开发者确认记录一致；交付说明逐项列出用户需要授权的平台，并说明只对本应用及其项目生效。修改选择必须回到新草稿，不能直接修改已冻结版本。
- 告知用户可在应用内或平台“我的授权”解除同一份授权；“我的授权”卡片显示应用名称及 logo。解除不影响其他应用各自的授权。
- 交付前重新查询 `business_ui_manage(action="get_recharge_config", task_id=..., business_ui_id=...)`。记录环境、应用 ID、查询时间及实际返回；未开通则明确写“充值暂不可用”，不展示收款主体、不宣称收款/到账闭环完成。只有平台真实返回启用且后续充值闭环通过验收，才能展示平台返回的收款主体信息。
- 发布前按当前环境契约确认目标宿主支持应用实际使用的 SDK、Bridge 协议及授权和支付 RPC；部署、插件发布及真实支付各按其单独授权与验收流程执行。

## 常见错误

- 把 `authorization_required` 当成弹卡指令，先起检测项目或跳对话找卡。
- 业务应用自己读取、存储或转发 token、密钥、custom fields。
- 用普通授权记录 ID 代替充值账户引用。
- 把 `completed`（收银台关闭）当成已付款；以服务端 `payment_status=paid` 与 `fulfillment_status=completed` 为准。
- 保存授权选择冲突后自动用旧选择重试。
- 在独立 mock 里模拟支付成功，当成真实证据。
