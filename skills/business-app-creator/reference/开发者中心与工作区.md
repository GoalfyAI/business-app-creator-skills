# 开发者中心与工作区

## 适用场景

在 Goalfy 桌面开发者中心（工作台）里新建或接续应用、维护工作区文件、更新阶段标记、写阶段记录、处理「演示预览」为空、在本机版上用无头浏览器验收页面条目、在 Studio 宿主里保存文档、换机或跨会话接续时读。方案页给开发者看的内容怎么写见 [../design/方案页.md](../design/方案页.md)。

## 规则

### 应用放在哪

- 工作台由 Goalfy App 安装和更新；你在工作台分配的工作目录下工作，每个应用一个目录：`apps/<应用目录名>/`。目录名用能区分业务的稳定英文名（如 `restaurant-koc`）；同名目录已存在时先读身份，同一应用就接续，另一个应用换名，不覆盖原目录。
- 桌面会话的 cwd 可能是外层工作目录；所有工程命令都在 `apps/<应用目录名>` 的实际绝对路径下执行。

### 命令行宿主

没有开发者中心的宿主（如 Codex、Claude Code 命令行）里，五段和所有规则照旧，只有这几处不同：

- 应用放在当前工作目录下的 `apps/<应用目录名>/`，命名规则同上一节。
- 开发者看不到右栏，方案页照常写；交接消息里给方案页的绝对路径，PRD 和方案的正文按节贴进聊天，开发者对贴出的这一版 PRD 或整版方案明确确认。
- 没有「演示预览」，不生成本地完成版；④ 的本机版页面验收照常做（本节下面「本机版页面验收」）。
- 没有工作台「在线预览」入口；上线结果「怎么打开」写从 GoalfyMax 打开这个应用（发布后使用者从目录或分享打开），不写工作台入口。
- **应用工程根是 Git 根**：`scaffold:init` 默认在应用根 `git init` 并提交模板基线；传了 `--no-git` 时自己在应用根初始化，否则 `doctor` 报 `GIT_ROOT_MISMATCH`。

```text
<应用目录>/
├── app.json                应用名称与身份（id = business_ui_id）
├── WORKSPACE.md            工作区身份、current_stage、阶段文档索引
├── workspace.json          阶段标记正本（doctor 校验格式，开发观测读取）
├── scaffold-release.json   本应用实际采用的脚手架版本
├── docs/proposal/index.html  方案页（右栏「方案」；Studio 下没有）
├── docs/proposal/proposal.css  方案页固定样式（脚手架维护，不改）
├── docs/stages/            七份阶段文档
├── docs/history/           历史记录
├── frontend/
└── backend/
```

### 三件套与阶段标记

| 文件 | 规则 |
|---|---|
| `app.json`、`WORKSPACE.md`、`workspace.json`、方案页、阶段文档 | 一律由 `scaffold:init` / `scaffold:repair` 生成，之后只改状态和内容字段；手写的契约会逐条打回 |
| 身份 | `app.json` 的 `id` 与 `WORKSPACE.md` 的 `business_ui_id` 是同一个值；G1–G4 可以是 `null`，进 G5 前用 `npm run scaffold:bind -- --business-ui-id <ID>` 原子回填（`business_ui_manage(action="setup")` 返回的 `scaffold_bind_command` 就是它，见 [数据模板.md](数据模板.md)「建应用身份与挂模板」） |
| 阶段文档 | 只用 `docs/stages/` 里已生成的七份，一个工作区阶段一份，不另建文件：② 的施工单、业务说明、取舍及验收要求的答案、整版确认依据、验收条目、费用复核都写进 G3 那一份。PRD 的正本在方案页（Studio 下是开发文档 PRD）；确认版全文只在 G1 阶段文档存一次，之后各段写「依据 PRD 第 N 版」，只记和 PRD 不一样的地方，不再复制全文 |
| `workspace.json` | 只有 `targets` 数组，按 G1–G7 顺序七项，每项只有 `name` 与 `status` |
| 阶段文档 front matter | `stage`、`stage_name`、`status`、`render_type` 等字段固定，只用约定字段 |
| 状态 | 进入一段时把它包含的第一项标 `in_progress`；段内每完成一项标 `passed`，失败标 `failed`；交棒时这一段包含的各项都应是 `passed`，没做的保持 `not_started` 并在阶段文档写一句原因。退回到前一段时，把那一段和之后各段已标 `passed` 的项改回 `in_progress` 或 `not_started`，阶段文档写明退回原因；旧的 `passed` 不算这一轮的结论。五段与七项的对应见 [../SKILL.md](../SKILL.md)「五段」 |
| 状态更新 | `workspace.json` 的 `status`、阶段文档 front matter 的 `status`、`WORKSPACE.md` 的 `current_stage` 在同一动作里改，`current_stage` 指向正在做的那一项；契约不要求按顺序通过。路线验证的豁免（`route_verification_waived`）只记下这条路线没验证及原因，不算 `passed` |
| 阶段名 | 以工作区里已有的为准，按 G 键对应，只改状态不改名 |

写入前重读受影响的文件，保留其他会话的新改动；有冲突先核对差异再写。`.workbench/` 由工具维护，不入库。

**两套取值**：阶段标记（`workspace.json` 与 front matter 的 `status`）取 `not_started` / `in_progress` / `passed` / `failed`；阶段记录（`business_ui_stage` 的 `result`）取 `passed` / `partial` / `failed`。对应关系：

| 这一项的情况 | 阶段标记 | 阶段记录 `result` |
|---|---|---|
| 做完，交棒条件都满足 | `passed` | `passed` |
| G6 交棒条件都满足，但有「未测」条目 | `passed` | `partial`（`completion` 逐条写未测条目与原因） |
| 没做成，或 G6 报告硬门不过 | `failed` | `failed` |

### 阶段记录

阶段标记给本地工作区看，阶段记录写进平台给开发观测看。每段出口对段内实际做过的每一项各调一次只写的 `business_ui_stage`（哪一段写哪几项、写在什么之前，见各段「交棒条件」；没通过、退回前面的段也写；③ 建好应用后带上 `business_ui_id`），把三件事写清楚：

1. **现在到哪**：`stage` 填刚结束的那一项（G1–G7），`result` 按上表填。
2. **这一项完成得怎样**：`completion` 写做出了什么、交棒条件逐项是否满足；遗留问题写 `open_issues`，证据指针（部署编号、checkpoint、版本号等）放 `evidence`。
3. **为什么往下走**：`next_stage` 填下一项（G1–G7，结单填 `closeout`），`reason` 写为什么现在进它，`next_plan` 写下一项打算做什么（结单时传空串）；跳过的项写进 `skipped`，每个都给理由。

```text
business_ui_stage(task_id="wft_xxx", stage="G1", result="passed",
  completion="PRD 第 2 版已确认：1 张借用记录表、首页+登记页，开发者回复「确认这一版」",
  next_stage="G2", reason="PRD 要接外部借阅系统，需要核实现有工具",
  next_plan="查借阅系统工具组并真调一次取样")
```

- **一项调一次**：写失败不挡交付，把错误原文记进本段阶段文档，接着往下做，不重试。
- **只写不读**：接续、修订照旧按本地阶段文档和工单 checkpoint 定位。

### 方案页

非 Studio 宿主才有方案页。

- `docs/proposal/index.html` 是开发者在右栏看到的方案，改动后工作台自动刷新。资源留在 `docs/proposal/` 内。内容和版式按 [../design/方案页.md](../design/方案页.md) 写，`doctor` 按那套版式校验；工作区缺 `docs/proposal/proposal.css` 时先 `npm run scaffold:repair` 补齐，样式只用它。
- `docs/stages/` 的七份文档给你和后续 Agent 存完整事实与证据，跳过的项对应文档只写一句跳过的原因；方案页给开发者看结论。
- **改动标记**：相对上一版改过的词句用 `<mark class="pv-changed">` 包住，旧高亮在下一版去掉。
- **历史版本**：升版前先把当前页复制成 `docs/proposal/history/v<当前版本>.html`，副本里的 `href="proposal.css"` 改成 `href="../proposal.css"`，再改 `index.html` 并把 `data-version` 加一；`.pv-meta` 链到上一版。旧版只存不改。

### 演示预览与在线预览

| 用途 | 在哪里 | 能证明什么 |
|---|---|---|
| 本地完成版演示 | 需求全部完成、完整验证通过后生成的本机固定副本，开发者中心右栏「演示预览」（不需要部署） | 完成版的页面渲染、交互、本地后端与 Mock 联调 |
| 真实身份、真实路线、运行中表单、交付审阅、数据管理 | 草稿部署成功后，工作台右侧「在线预览」（不需要上线） | 真实链路；开发者自己想看时用，你不打开 |
| 发布后的正式应用、到点自动运行 | 开发者从 GoalfyMax 打开这个应用（开发者本人也要先发布；「自动化」面板只在这里可用） | 不用于 ④ 验收 |

- 「在线预览」用工作台绑定的 `business_ui_id` 换一次性凭据；凭据不写入应用、交付物或工单。它只要求当前草稿部署成功；数据写在开发工作集里，和 `workspace` 真跑是同一份库，测试写入的数据不进使用者实例。打不开或未就绪的处置见 [报错对照.md](报错对照.md)「部署与预览」。
- 保留桌面注入的 `GOALFY_DEV_FRAME_ANCESTORS` 与来源限制；预览端口和连接声明沿用工作台与脚手架生成的值。
- 你自己看页面效果用 `npm --prefix frontend run check` 和脚手架自带的本地布局回归 `test:e2e:layout`（无头、只连本机内置 Mock，查 390/768/1440px 溢出与裁切；命令、端口和首次安装 Chromium 见应用里的 `frontend/docs/dev-host-testing.md`）；④ 的页面条目另按「本机版页面验收」逐条操作。

#### 演示预览为空

「演示预览」只展示本机上一次生成的**完成版固定副本**，不需要部署或上线：工作台把应用复制一份，跑标准完整验证（`scripts/verify.mjs`）和脚手架示例残留检查，通过后固定这份副本，在本机用本地后端与 Mock 起服务展示。制作中的工作源码不会直接显示；之后的修改要等下一次生成完成版才会出现，期间保留上一次的完成版。Studio 下不生成完成版，本节不适用（见「Studio 宿主」）。

开发者说演示预览是空的，按右栏显示的标题处理：

1. **「应用尚未完成」**：还没生成过完成版。本轮需求没全部做完时，告诉开发者演示预览要等需求全部实现并通过完整验证后才有；制作中你用 `npm --prefix frontend run check` 与本地布局回归拿证据。需求全部完成后才生成完成版：应用根 `npm run verify` 全绿后，执行开发者中心的 `prepare_business_app_skill` 返回的 `completedPreview.argv`（只把 `<appPath>` 换成应用根的绝对路径），失败按输出修好再执行。这条命令只生成并固定副本，不启动服务：成功后右栏变为「预览未启动」，按第 2 条请开发者启动。
2. **「预览未启动」**：完成版已生成，请开发者点「重新启动」。没有完成版标记的应用第一次点时，工作台会先跑一遍完整验证再建立副本，通过才启动。启动失败时按右栏给出的原因处理（例如端口被占用时如实说明，不结束不属于本应用目录的进程）。
3. **「暂时无法确认应用完成状态」**：工作台没读到完成状态，请开发者点「重新检查」；仍不行就如实告诉开发者工作台读不到完成状态，并说明右栏给出的原因。

开发者正在看上一版演示时生成了新的完成版，右栏会提示「新的完成版已就绪」：请开发者保存好正在填写的内容后点「内容已保存，切换到完成版」，不会自动切换。

演示预览只认工作台生成的完成版：`.workbench/completed-preview.json` 由工作台写，完整验证不能跳过，工作台也不显示 `npm run dev` 起的工作源码。你自己做本地联调或布局回归时可以 `npm run dev` / `npm run dev:restart`（后台启动，不用前台命令、`&` 或 `nohup` 自己拼），那是给测试用的。

### 本机版页面验收

④ 里要在页面上操作或看显示的验收条目（页面条目），由你在应用的本机版上用无头浏览器照条目逐条操作。怎么判结论、哪些记「未测」，见 [../stages/4-试用验收.md](../stages/4-试用验收.md)「2.4 逐条判定」；浏览器边界的红线在 [../SKILL.md](../SKILL.md)「红线」，这一节写具体做法。

#### 只访问本机地址

- 浏览器（Playwright 无头 Chromium）只打开本机版输出里的本机地址（`127.0.0.1` 或 `localhost`）。GoalfyMax 正式入口、登录页、在线预览或演示预览的地址、容器地址要走平台登录和身份注入，不在你要访问的范围里；开发者已登录的会话也不借用。
- 访问被工具审批拒绝时到此为止：不重试、不绕过，也不请开发者放开授权；它是工具限制，不当作平台或应用故障上报。

#### 做法

1. **起本机版**：在应用根 `npm run dev:restart` 后台起本机版（本地后端加 Dev Host，SDK 的平台能力由内置 Mock 提供），从输出读 Dev Host 地址（默认 `http://127.0.0.1:5176/`），`npm run dev:status` 看是否在跑；命令、端口和首次安装 Chromium 见应用里的 `frontend/docs/dev-host-testing.md`。Studio 下桌面入口已在跑当前工程的开发服务时直接用它，不另起、不停掉。
2. **无头操作**：用 Playwright 无头 Chromium 打开 Dev Host 地址，等页面顶部出现 `Bridge ready`、应用内容出现后再操作和截图，内容区空白的截图不作证据。只做验收条目里的点击和输入；条目里有付款或授权的，做到付款或授权窗口出现为止，本机版里的结果是 Mock。
3. **记证据**：每条记操作步骤、截图文件路径（写进阶段文档 G6；不截图的写断言原文）和打开过的本机路由。
4. **跑本地检查**：同一份代码跑 `npm --prefix frontend run check` 与本地布局回归 `test:e2e:layout`，结果写进验收报告。
5. **收尾**：关闭浏览器；本机版是你起的，用 `npm run dev:stop` 停掉。

本机版里平台能力是 Mock：依赖平台登录身份、真实宿主桥接的部分本机版上看到的不作证据，按 ④「2.4 逐条判定」的「未测」表记。

#### 本机版起不来时

`npm run dev:restart` 失败、缺 Chromium 或系统库时你自己修：按输出补依赖，按 `frontend/docs/dev-host-testing.md` 装 Playwright Chromium（例如 `npx playwright install chromium`）；工程本身的问题回 ③ 修。修好后再测这几条；仍起不来的按 ④「2.4 逐条判定」记「未测」。

### Studio 宿主

当前宿主实际提供 Studio 制作工具（工具列表里有 `studio_write_proposal`、`studio_read_creation`、`studio_confirm_proposal`）时按本节做，没有这些工具时不用本节。Studio 只管文档怎么保存、显示和确认；五段的顺序、每段确认什么、④ 怎么验收、⑤ 做到哪一步，都按 `SKILL.md` 和 `stages/` 执行，和其他宿主相同。表单与记忆卡见 [Studio表单与卡片.md](Studio表单与卡片.md)。

- **四份开发文档代替方案页**：Studio 第三栏「开发文档」有 PRD、方案、制作进度、验收报告四份，按 [../design/开发文档/README.md](../design/开发文档/README.md) 的模板写成 HTML，用 `studio_write_proposal` 按 `documentType`（`prd`、`proposal`、`progress`、`acceptance`）分别保存，互不覆盖；用 `studio_read_creation` 按 `documentType` 读。哪一段写哪一份见该 README「哪一段写哪一份」。
- **确认**：① 的 PRD、② 的方案在 Studio 里不用表单确认，交文档后开发者在确认卡上确认，或在聊天里明确同意后由你登记（表单与卡片见 [Studio表单与卡片.md](Studio表单与卡片.md)「按轮问怎么写成表单」）；什么算确认见 [../design/PRD.md](../design/PRD.md)「版本、批注和确认」，`studio_confirm_proposal` 怎么登记和读回见 [../design/开发文档/README.md](../design/开发文档/README.md)「确认怎么登记」。
- **文档模式**：Studio 会话的命令环境自带 `GOALFY_SCAFFOLD_DOCUMENT_MODE=studio`，开工时 `scaffold:init` 照常运行，不另传 `--document-mode`；脚手架把 `document_mode: studio` 写进 `WORKSPACE.md`，不生成 `docs/proposal/`，之后 `doctor`、`scaffold:repair` 和发布验证都沿用这个模式，不补回方案页。
- **验收范围文件**：工程里的 `studio.acceptance.json` 与方案的 `acceptance.json` 验收范围一致，格式按宿主和脚手架合同，不自行增减条目。
- **演示**：桌面入口管理当前工程的开发服务，你只准备工程与依赖，不另起后台服务、不生成完成版。
- **写入结果未知**：Studio 工具或平台写入返回结果未知时，只查询原操作的结果，不重新发起写入。

### 云端保存与换机

- `workspace_remote_status` 看云端状态，`workspace_pull` 取回，`workspace_push` 保存。
- 接续时先读本地；本地缺失或换机才 pull。已有内容先比较、保留差异再合并，不默认用云端覆盖本地。
- 同步了对话记录、恢复了阶段文档，都不代表恢复了脚手架代码；代码以应用目录的 Git 与 `scaffold-release.json` 为准。

## 常见错误

- 手写 `workspace.json` 或阶段文档，字段或顺序不对被契约打回。
- 把 `current_stage` 改成 G5 而 `business_ui_id` 仍是 `null`，契约拒绝；先 `scaffold:bind`。
- 在外层工作目录跑 `npm` 命令，改到别的应用或模板暂存目录。
- 把工作区里已有的阶段改成新名，和已有阶段文档路径对不上。
- 本地演示预览能看到就宣称真实链路已通。
- 需求没做完就生成完成版，或用 `npm run dev` 起工作源码，想让演示预览提前显示。
- 用浏览器打开在线预览、正式入口、登录页或容器地址，或借用开发者的登录会话。
- 把本机版里 Mock 出来的身份、授权、付款当成线上验证通过。
