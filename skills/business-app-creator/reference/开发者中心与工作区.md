# 开发者中心与工作区

## 适用场景

在 Goalfy 桌面开发者中心（工作台）里新建或接续应用、写方案页、更新阶段标记、写阶段记录、「演示预览」为空、④ 在在线预览里用浏览器验收页面条目、换机或跨会话接续时读。

## 规则

### 应用放在哪

- 工作台由 Goalfy App 安装和更新；你在工作台分配的工作目录下工作，每个应用一个目录：`apps/<应用目录名>/`。目录名用能区分业务的稳定英文名（如 `restaurant-koc`）；同名目录已存在时先读身份，同一应用就接续，另一个应用换名，不覆盖原目录。
- 桌面会话的 cwd 可能是外层工作目录；所有工程命令都在 `apps/<应用目录名>` 的实际绝对路径下执行。
- **应用工程根必须是 Git 根**：`scaffold:init` 默认在应用根 `git init` 并提交模板基线；旧版本或传了 `--no-git` 时自己在应用根初始化，否则 `doctor` 报 `GIT_ROOT_MISMATCH`。

```text
<应用目录>/
├── app.json                应用名称与身份（id = business_ui_id）
├── WORKSPACE.md            工作区身份、current_stage、阶段文档索引
├── workspace.json          阶段标记正本（doctor 校验格式，开发观测读取）
├── scaffold-release.json   本应用实际采用的脚手架版本
├── docs/proposal/index.html  方案页（右栏「方案」）
├── docs/proposal/proposal.css  方案页固定样式（脚手架维护，不要改）
├── docs/stages/            七份阶段文档
├── docs/history/           历史记录
├── frontend/
└── backend/
```

### 三件套与阶段标记

| 文件 | 规则 |
|---|---|
| `app.json`、`WORKSPACE.md`、`workspace.json`、方案页、阶段文档 | 一律由 `scaffold:init` / `scaffold:repair` 生成；**禁止**手写，契约会逐条打回 |
| 身份 | `app.json` 的 `id` 与 `WORKSPACE.md` 的 `business_ui_id` 是同一个值；G1–G4 可以是 `null`，进 G5 前用 `npm run scaffold:bind -- --business-ui-id <ID>` 原子回填 |
| `workspace.json` | 只有 `targets` 数组，按 G1–G7 顺序七项，每项只有 `name` 与 `status` |
| 阶段文档 front matter | `stage`、`stage_name`、`status`、`render_type` 等字段固定；**禁止**加未约定字段 |
| 五段与七项 | ① = G1、G2，② = G3，③ = G4、G5，④ = G6，⑤ = G7。进入一段时把它包含的第一项标 `in_progress`；段内每完成一项标 `passed`，失败标 `failed`；交棒时这一段包含的各项都应是 `passed`，没做的保持 `not_started` 并在阶段文档写一句原因 |
| 状态更新 | `workspace.json` 的 `status`、阶段文档 front matter 的 `status`、`WORKSPACE.md` 的 `current_stage` 在同一动作里改，`current_stage` 指向正在做的那一项；契约不要求按顺序通过。路线验证的豁免（`route_verification_waived`）只记下这条路线没验证及原因，不算 `passed` |
| 阶段名 | 以工作区里已有的为准；旧应用的七项可能是旧名（业务目标与范围、关键能力可行性……），按 G 键对应，只改状态不改名 |
| 示例包 | 模板自带 `frontend/schema/packs/demo-pack/` 并声明在 `goalfy-app.json` 的 `packs`；用 `scaffold:init -- --without-demo-pack` 去掉，或删目录并同步移出 `packs` |

写入前重读受影响的文件，保留其他会话的新改动；有冲突先核对差异再写。`.workbench/` 由工具维护，不入库。

**阶段记录**：阶段标记给本地工作区看，阶段记录写进平台给开发观测看。每段出口对段内实际做过的每一项各调一次只写的 `business_ui_stage`，把三件事写清楚：

1. **现在到哪**：`stage` 填刚结束的那一项（G1–G7），`result` 填 `passed` / `failed` / `partial`。
2. **这一项完成得怎样**：`completion` 写做出了什么、交棒条件逐项是否满足；遗留问题写 `open_issues`，证据指针（部署编号、checkpoint、版本号等）放 `evidence`。
3. **为什么往下走**：`next_stage` 填下一项（G1–G7，结单填 `closeout`），`reason` 写为什么现在进它，`next_plan` 写下一项打算做什么（结单时传空串）；跳过的项写进 `skipped`，每个都给理由。

```text
business_ui_stage(task_id="wft_xxx", stage="G1", result="passed",
  completion="PRD 第 2 版已确认：1 张借用记录表、首页+登记页，开发者回复「确认这一版」",
  next_stage="G2", reason="PRD 要接外部借阅系统，需要核实现有工具",
  next_plan="查借阅系统工具组并真调一次取样")
```

- **什么时候写**：和阶段标记同一步写。① 出口写 G1、G2；② 出口写 G3；③ 出口写 G4、G5；④ 出口写 G6，写在开发者「可以上线」的 checkpoint 之后，有「未测」条目时 `result` 填 `partial`，`completion` 逐条写明未测条目和原因；⑤ 出口写 G7，`next_stage` 填 `closeout`，写在 `task_manager(action="complete")` 之前（结单后写不进）。没通过、退回前面的段也写。③ 建好应用后带上 `business_ui_id`。
- **只调一次**：失败就把错误原文记进本段阶段文档，接着往下做，**禁止**重试、改参数再调或因此停下。
- **只写不读**：接续、修订照旧按本地阶段文档和工单 checkpoint 定位。

### 方案页

- `docs/proposal/index.html` 是开发者在右栏看到的方案，改动后工作台自动刷新。资源留在 `docs/proposal/` 内。
- 第一次实质答复结束前写入最小草案：已知目标、范围、待明确事项，未知的标「未知」；删掉模板占位文案。
- `docs/stages/` 的七份文档给你和后续 Agent 存完整事实与证据，跳过的项对应文档只写一句跳过的原因；方案页给开发者看结论。
- 工作区有 `docs/proposal/proposal.css` 时按下面的**固定版式**写（`doctor` 按固定版式校验）；没有这个文件的旧工作区先 `npm run scaffold:repair` 补齐，脚手架版本太旧补不出来时按原写法，不自造样式文件。

#### 固定版式

只写内容和类名，**不写** `<style>`、`style=` 属性，样式全部来自 `proposal.css`。页面按顺序只有这几块：

```html
<main data-proposal="2" data-version="3">            <!-- 方案每次改动后 data-version 加一 -->
  <header>
    <div class="pv-eyebrow">智能应用方案 · 第 3 版</div>
    <h1>应用名</h1>
    <p class="pv-goal">一句话：它帮开发者做什么。</p>
  </header>
  <section id="status" data-state="blocked" data-stage="G6">
    <div class="pv-state">G6 预览验收</div>
    <p class="pv-summary">一句话现状。</p>
    <p class="pv-you">开发者要做什么；不用做也写「现在不用做」。</p>
    <p class="pv-owner">谁在处理（卡住时必填）。</p>
    <details class="pv-raw"><summary>查看原始原因</summary><pre>报错原文、编号</pre></details>
  </section>
  <section id="needs">                               <!-- 没有要开发者准备的东西时整节省略 -->
    <h2>需要你准备的</h2>
    <ul class="pv-needs">
      <li data-ready="no">聚光广告账号授权<small>用在第 2 步拉取投放数据；没有它第 2 步起都跑不了</small></li>
      <li data-ready="yes">一份持仓示例表<small>用在导入功能的验收</small></li>
    </ul>
  </section>
  <section id="business-process">
    <h2>业务过程</h2>
    <ol class="pv-steps">
      <li data-kind="rule">固定规则做的一步</li>
      <li data-kind="model">要模型判断的一步（会花钱）</li>
      <li data-kind="human">要开发者或用户决定的一步</li>
    </ol>
    <p class="pv-fallback">做不成时用户会看到什么。</p>
  </section>
  <section id="development-content"><h2>开发内容</h2>功能、会存下来的表、费用与副作用、上线范围</section>
  <section id="verification">
    <h2>验证情况</h2>
    <ul class="pv-verified"><li data-evidence="部署 p2s-3316">已经真实验证过的事</li></ul>
    <ul class="pv-unverified"><li>还没验证的事，写明原因</li></ul>
  </section>
  <p class="pv-meta">本版改动：… · 历史版本：<a href="history/v2.html">第 2 版</a></p>
</main>
```

| 块 | 规则 |
|---|---|
| `status` 的 `data-state` | `working` 在做、`waiting` 等开发者、`blocked` 卡住、`done` 已完成；颜色由它决定。平台问题、权限、部署失败等你推进不了的一律 `blocked`，不写成进行中 |
| `status` 内容 | `waiting`、`blocked` 必须有 `.pv-you`；`blocked` 必须有 `.pv-owner`；报错原文与编号只放进 `.pv-raw` 折叠 |
| `pv-steps` | 每一步都标 `data-kind`：脚本 `rule`、模型 `model`、人 `human`；来自 PRD「每一步谁来做」，写法见 [../design/谁来做.md](../design/谁来做.md) |
| `verification` | 「已验证」每条用 `data-evidence` 写证据（部署、运行、项目编号或本地命令）；桩运行、只在本地看过、没真跑过的一律放「未验证」 |
| `needs` | 开发者要提供、别人替不了的东西：第三方账号授权、密钥、示例数据、机器人或群、要开通的平台能力。每项写用在哪一步、缺了影响什么，`data-ready` 标 `yes` / `no`。G1 列出，G2 核实资产时补全，之后备好一项改一项；有 `no` 且挡住当前进度时，`status` 的 `.pv-you` 写「准备下面 N 项」 |
| 改动 | 相对上一版改过的词句用 `<mark class="pv-changed">` 包住，旧高亮在下一版去掉 |
| 历史版本 | 升版前先把当前页复制成 `docs/proposal/history/v<当前版本>.html`，副本里的 `href="proposal.css"` 改成 `href="../proposal.css"`，再改 `index.html` 并加一；`.pv-meta` 链到上一版。旧版只存不改 |
| 用词 | 正文不出现 FA、TPE、FastAgent、Runtime；编号放在 `data-evidence` 或 `.pv-raw` 里 |

各阶段只更新对应的块，见 `stages/` 各段文件「产出与落盘」。

### 演示预览与在线预览

| 用途 | 在哪里 | 能证明什么 |
|---|---|---|
| 本地完成版演示 | 需求全部完成、完整验证通过后生成的本机固定副本，开发者中心右栏「演示预览」（不需要部署） | 完成版的页面渲染、交互、本地后端与 Mock 联调 |
| Max 真实身份、真实路线、运行中表单、交付审阅、数据管理 | 草稿上传并部署成功后，工作台右侧「在线预览」，或 GoalfyMax 的 `/business-ui/<应用 ID>/preview`（不需要上线） | 真实链路；④ 的页面条目在这里验 |
| 上线并发布后的正式应用、原生定时任务 | GoalfyMax → 我的资产 → 智能应用 → 打开（正式入口 `/business-ui/<应用 ID>`，开发者本人也要先发布；「自动化」面板只在这里可用） | 不用于 ④ 验收 |

- 「在线预览」用工作台绑定的 `business_ui_id` 与环境向同环境 Max 换一次性凭据；凭据不写入应用、方案页或工单。它只要求当前草稿部署成功，不需要上线；数据写在开发工作集里，和 `workspace` 真跑是同一份库，测试写入的数据不进使用者实例。
- 验收由你做（见 [../stages/4-试用验收.md](../stages/4-试用验收.md)）：业务结果用 `workspace` 真跑验；页面条目在开发者同意后，由你按下面「④ 用浏览器验收」在在线预览里操作。开发者自己想看随时可以在工作台「在线预览」里用，他的口头回报不作「通过」的证据。
- 工作台「在线预览」报 `PREVIEW_NOT_READY`（请先完成应用上传和部署）：当前草稿没有部署成功的记录，或部署后又派生了新草稿行。在当前草稿行重新 `ship` 到 `success` 再开；`ship` 已成功仍报未就绪，才按平台问题 `submit_dev_feedback`。这个提示只出现在开发者从工作台打开的预览里。
- 保留桌面注入的 `GOALFY_DEV_FRAME_ANCESTORS` 与来源限制；预览端口和连接声明沿用工作台与脚手架生成的值。
- 你自己看页面效果用 `npm --prefix frontend run check` 和脚手架自带的本地布局回归 `test:e2e:layout`（只连本机内置 Mock，命令、端口和首次安装 Chromium 见应用里的 `frontend/docs/dev-host-testing.md`）；它们是脚手架的本地测试命令，不打开 GoalfyMax，不受「④ 用浏览器验收」的同意要求限制，也不能代替 ④ 的页面验收。

#### 演示预览为空

「演示预览」只展示本机上一次生成的**完成版固定副本**，不需要部署或上线：工作台把应用复制一份，跑标准完整验证（`scripts/verify.mjs`）和脚手架示例残留检查，通过后固定这份副本，在本机用本地后端与 Mock 起服务展示。制作中的工作源码不会直接显示；之后的修改要等下一次生成完成版才会出现在演示预览里，期间保留上一次的完成版。

开发者说演示预览是空的，按右栏显示的标题处理：

1. **「应用尚未完成」**：还没生成过完成版。本轮需求没全部做完时，告诉开发者演示预览要等需求全部实现并通过完整验证后才有，不需要等部署；制作中想看页面效果，你用 `npm --prefix frontend run check` 与本地布局回归拿证据，草稿 `ship` 成功后开发者也可以先在「在线预览」看真实链路。**不要**为了提前打开演示预览去生成完成版。需求已全部完成时，应用根 `npm run verify` 全绿后执行 `prepare_business_app_skill` 返回的 `completedPreview.argv`（只把 `<appPath>` 换成应用根的绝对路径），失败按输出修好再执行。这条命令只生成并固定副本，不启动服务：成功后右栏变为「预览未启动」，按第 2 条请开发者启动。
2. **「预览未启动」**：完成版已生成（或 10-09 以前做的旧应用已有构建产物），请开发者点「重新启动」。旧应用第一次点时，工作台会先跑一遍完整验证再建立副本，通过才启动。启动失败时按右栏给出的原因处理（例如端口被占用时如实说明，不结束不属于本应用目录的进程）。
3. **「暂时无法确认应用完成状态」**：工作台没读到完成状态，请开发者点「重新检查」；仍不行就如实告诉开发者工作台读不到完成状态，并说明右栏给出的原因。

开发者正在看上一版演示时生成了新的完成版，右栏会提示「新的完成版已就绪」：请开发者保存好正在填写的内容后点「内容已保存，切换到完成版」，不会自动切换。

**禁止**手写 `.workbench/completed-preview.json`、跳过验证，或用 `npm run dev` 起工作源码来充当演示预览：工作台不会显示工作源码的服务。你自己做本地联调或布局回归时仍可以 `npm run dev` / `npm run dev:restart`（后台启动，不用前台命令、`&` 或 `nohup` 自己拼），那是给测试用的，不是演示预览。

### ④ 用浏览器验收

④ 里要在页面上操作或看显示的验收条目（下称页面条目），由你在这个应用的在线预览里操作；业务结果照常用 `workspace` 真跑和查库（见 [../stages/4-试用验收.md](../stages/4-试用验收.md)）。`SKILL.md` 第 0 节的四条浏览器红线在这里展开，浏览器的启动参数、地址和做法只写在这一节。

#### 五步

1. **询问**：有页面条目时，先发一道选择题，问开发者是否同意你打开一个浏览器窗口、由他登录 GoalfyMax 后你在这个应用的在线预览里操作。这是开发者「自己手上的事」的授权。题里写明只做哪几条、不打开发布管理页和其他页面、不做付款和授权、做完关闭窗口，例如：「验收里有 4 条要在页面上操作，是否同意我打开一个浏览器窗口，你在里面登录 GoalfyMax 后，我在这个应用的在线预览里操作？只做这 4 条，不打开发布管理页和其他页面，不做付款和授权，做完关闭窗口」。开发者的原话用 `task_manager(action="insert", entry_type="checkpoint")` 记下。同意的范围只限这个应用、这次 ④ 和它的重验，开发者可以随时收回。开发者没回或不同意时不启动浏览器，按下面「测不了时」处理。
2. **启动**：用 Playwright 启动有界面的 Chromium，浏览器资料只在内存：脚本用 `launch(headless=False)` 加 `new_context`，或 Playwright MCP 带 `--isolated`、不带 `--headless`。**禁止**用 `launch_persistent_context`、`--user-data-dir`、`--storage-state`、`--save-session`，**禁止**保存 `storage_state`；**禁止**用开发者日常浏览器及其资料、连接开发者已打开的浏览器或用 Codex 内置浏览器。一次操作期间保持同一个浏览器上下文，跨多次工具调用不断开。
3. **登录**：打开当前环境的 GoalfyMax 地址，请开发者在窗口里自己登录，登录好回「登录好了」。你不在登录页输入任何内容，登录后落到的页面不做任何操作。

   | 环境 | GoalfyMax 地址 |
   |---|---|
   | 生产 | `https://goalfymax.goalfyai.cn` |
   | PRE | `https://goalfymax.pre.goalfyai.cn` |
   | QA | `https://goalfymax.qa.goalfyai.cn` |

4. **操作**：直接打开 `<GoalfyMax 地址>/business-ui/<应用 ID>/preview`。应用 ID 原样取工作区 `app.json` 的 `id`（与 `WORKSPACE.md` 的 `business_ui_id` 同值），它是应用家族 ID，与 `business_ui_manage(action="get")` 返回 `data` 里的 `resource_group_id` 相同；**禁止**用 `get` 返回的 `data.id`、`next_action` 给的 `draft_asset_id` 或其他版本行 ID，它们是给 MCP 工具用的，填进地址会查不到预览、页面加载失败；地址上不加 `asset_version_id`。应用 ID 是 8 位短码时同样原样填入。
   不带版本时，GoalfyMax 打开登录者本人最新部署成功的草稿；本人没有这样的草稿时，属主看到家族里最新可预览的版本，协作者看到最新正式版，都不报错。所以**必须**先在当前草稿 `ship` 到 `success` 再打开。编辑协作者用自己的账号登录，同一地址打开的是他自己最新部署成功的草稿。
   等应用页面内容出现后再操作和截图，内容区空白的截图不作证据。只做验收条目里的点击和输入，不点 GoalfyMax 的导航，不在页面里执行脚本读数据或调接口；条目里有真实付款或授权的，做到付款或授权窗口出现为止，不确认。某个操作让页面离开预览页时，立即回到预览页并在报告里写明。每条记操作步骤、截图和主窗口打开过的地址（去掉 `?` 与 `#` 之后的部分）。
5. **关闭**：页面条目做完、开发者收回同意或出错停止时关闭浏览器，登录状态随之消失。重验时重新启动，由开发者重新登录。

#### 预览打不开时

GoalfyMax 预览页任何失败都只显示「Agentic APP 不存在或加载失败」和「重试」按钮，不显示原因；这时 HTTP 状态仍是 200，原因只在响应体的 `code` 里。看到这句话后，从浏览器网络记录读 `POST /business-uis/<应用 ID>/preview-session` 这一条响应体的 `code`、`message`（Playwright MCP 用 `browser_network_requests` 找到这一条，再用 `browser_network_request` 只取 response-body；脚本用 `response` 事件）。只读失败的这一条，不读请求头；**禁止**读取或保存成功的 `preview-session` 响应，它含会话令牌和带令牌的入口地址。按 `code` 处理：

| `code` | 处理 |
|---|---|
| 3027「预览部署尚未就绪」、3024「智能应用已下线，预览容器不在线」、3028「暂无可预览的提交版本」，或 404 且 `get` 显示当前草稿没有部署成功 | 这是当前草稿的部署问题，3024 不表示应用被下线。**禁止**定版、下线或先提反馈：在当前草稿行重新 `ship` 到 `success`，重新打开同一预览地址，重做同一条目，报告写明 `code` 并附重试后的截图。`ship` 成功后重开仍是这几种结果，才 `submit_dev_feedback`（附 `code`、`message` 与时间），这几条按「测不了时」标「未测」。预览打开了却看不到 ③ 最后一次 `ship` 改的内容时同样处理 |
| 3023「预览会话不存在或已过期」 | 点「重试」或重新打开预览地址一次；仍是 3023 按「登录后无权访问或会话失效」处理 |
| 403；或 404 而 `get` 显示当前草稿已部署成功；或预览里应用自己的请求返回 3040 | 按「登录后无权访问或会话失效」处理 |
| 预览里应用自己的请求返回 3041（协作者预览须属主用新模板重建） | 告诉开发者须由属主用新脚手架模板重建，这几条标「未测」，原因写 `code` 3041；属主重建后开发者告诉你时，重新启动浏览器再测 |

#### 登录后无权访问或会话失效

开发者说登录不了，或登录后预览页报无权访问、会话失效（上表第 2、3 行）时：你不换账号、不打开其他页面，先关闭浏览器，把看到的情况和 `code` 告诉开发者（例如编辑协作者还没接受邀请），请他确认这个账号有权访问这个应用。开发者确认后，你重新启动浏览器，由开发者在新窗口里重新登录，再做同一条目。再次不成立，或开发者说登录不了，这几条标「未测」，原因写「身份方式不可用」及 `code`，**禁止**请开发者代测。当前环境的 GoalfyMax 地址打不开时也按这一类处理。

#### 测不了时

页面条目一律由你在浏览器里测；**禁止**请开发者在在线预览或其他地方代测，开发者的口头回报不作「通过」的证据。测不了只有三种情况，先按下表自己处理，处理完仍测不了的条目才标「未测」：

| 情况 | 先怎么处理 |
|---|---|
| 开发者不同意启动浏览器 | 不启动、不追问；交接消息说明哪几条因此没测、改主意说同意时再测。开发者在 ⑤ 之前说同意时按五步测这几条，报告只更新这几条 |
| 浏览器起不来（缺 Chromium、系统库等） | 把原因和修复命令（例如 `npx playwright install chromium`）告诉开发者，问是否同意由你运行；同意后运行并重新启动浏览器，开发者在窗口里登录，你测这几条。**禁止**改用其他浏览器或已登录的会话。开发者不同意运行、修复命令失败或修复后仍起不来时标「未测」，原因写「浏览器起不来」及错误原文；开发者之后自己修好环境告诉你时，重新启动浏览器测这几条 |
| 身份方式不可用或预览打不开 | 预览打不开先按「预览打不开时」重新 `ship`、重开预览；身份方式不可用按「登录后无权访问或会话失效」处理 |

仍测不了的条目，验收报告结论写「未测」、证据写「无」，原因写属于哪种情况、做过哪些处理、看到的错误或 `code`；交接消息逐条列出。开发者照常可以说「可以上线」进入 ⑤，你不追问、不因此拒绝定版。开发者自己发现并说出的页面问题按没通过回 ③ 修改，改完由你重测。

### 云端保存与换机

- `workspace_remote_status` 看云端状态，`workspace_pull` 取回，`workspace_push` 保存。
- 接续时先读本地；本地缺失或换机才 pull。已有内容先比较、保留差异再合并，不默认用云端覆盖本地。
- 同步了 Codex 对话、恢复了阶段文档，都不代表恢复了脚手架代码；代码以应用目录的 Git 与 `scaffold-release.json` 为准。

## 常见错误

- 手写 `workspace.json` 或阶段文档，字段或顺序不对被契约打回。
- 把 `current_stage` 改成 G5 而 `business_ui_id` 仍是 `null`，契约拒绝；先 `scaffold:bind`。
- 在外层工作目录跑 `npm` 命令，改到别的应用或模板暂存目录。
- 给旧应用的阶段改成新名，和已有阶段文档路径对不上。
- 本地演示预览能看到就宣称真实链路已通。
- 需求没做完就生成完成版，或用 `npm run dev` 起工作源码，想让演示预览提前显示。
- 没问开发者就启动浏览器，或用 `get` 返回的版本行 ID 拼预览地址，预览加载失败。
- 把预览页 `code` 3024 当成应用被下线去定版或下线；`ship` 前就提反馈。
- 读取或保存成功的 `preview-session` 响应、把登录状态存进文件。
- 浏览器起不来、预览打不开时，没有按恢复办法处理就标「未测」，或请开发者自己去在线预览试。
