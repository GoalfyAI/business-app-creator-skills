# 部署与版本

## 适用场景

部署应用、在开发工作集里真跑、上线应用或场景包、修订已上线版本、回滚、下线、删除、过结单门时读。部署、上线、发布三个词的含义见 [../SKILL.md](../SKILL.md)「角色与用词」；什么时候问开发者、什么时候做，见各段文件。报错码怎么处置见 [报错对照.md](报错对照.md)。

## 规则

### 三道门

| 门 | 什么时候判 | 依据 | 不过怎么办 |
|---|---|---|---|
| Skill 版本 | `task_manager(action="create")` 建工单时 | 已安装 Skill 的 `[skill-version]` 标记 | 按 [报错对照.md](报错对照.md)「工单闸门」升级 Skill |
| 脚手架版本 | `download_template` 核版本、`deploy` 读上传包 | 包内 `scaffold-release.json` 与平台必须线 / 建议线 | 按 [脚手架与预置件.md](脚手架与预置件.md) 迁移后重新打包 |
| 结单 | `task_manager(action="complete")` | 每条路线在当前合同下最近一次到终态的运行通过（路线冒泡，或 `workspace` 真跑里 `route_runs` 该路线 `succeeded`），或有这条路线的 `route_verification_waived` 检查点 | 补跑，或问过开发者后写豁免 |

结单门的豁免：最近一次失败或没法验证时，先问开发者是否接受，接受后每条路线写一条：

```text
task_manager(action="insert", entry_type="checkpoint", metadata={"evidence_type": "route_verification_waived", "scene_package_id": …, "orchestration_id": …, "reason": "<至少 5 个字>", "run_id": <失败那次；真跑失败填那次的 project_id；没跑过就不带>})
```

豁免只记下这条路线没验证及原因，不算通过。`complete` 被拒时按返回里逐条给的出口补证据或写豁免（码义见 [报错对照.md](报错对照.md)「版本与结单」），在同一张工单上处理。`complete` 成功后返回的 `delivery_note` 原样补进上线结果。

### 应用生命周期

```text
setup（建身份、挂模板、绑工作集） → update（授权选择、自动化）
  → ship（部署）→ success（在线预览可打开；workspace 真跑跑这一版）
  → finalize（上线） → resolve 反读上线版本
  → 开发者在发布管理页决定是否发布（发布后开发者本人和已安装的使用者用上这一版）
```

`setup` 的两步（建身份、挂模板并绑工作集）见 [数据模板.md](数据模板.md)「建应用身份与挂模板」。

- 上线的平台前提：本地 `npm run verify:release` 全绿，同一源码的部署 `success`。没部署成功过的草稿上不了线。
- 上线时场景包引用钉到当时的具体版本，把版本号记进工单和上线结果。
- 上线、发布、下线、删除只有属主能做；编辑协作者用 `request_finalize` 提请，见 [多人协作.md](多人协作.md)「提请属主上线」。

### 部署

部署 = 把当前草稿 `ship` 到开发者的在线预览。打包与脚手架闸门见 [脚手架与预置件.md](脚手架与预置件.md)「预部署与证据」。

1. `business_ui_bundle(action="download_template")` 核脚手架门槛，需要升级时先完成迁移与验证。
2. 在应用根运行 `npm run verify:release`，全部检查通过后得到 `.pack/business-ui-bundle.tar.gz`，按这个包算 `source_sha256` 与 `size_bytes`。部署包只由 `verify:release` 产出，它包含部署前的检查。
3. `business_ui_bundle(action="ship", task_id, business_ui_id, source_sha256, file_name="business-ui-bundle.tar.gz", size_bytes)`：`file_name` 只写文件名；`business_ui_id` 是上线行、要自动派生草稿时同时带 `change_note`，写这次改了什么。
   - 返回 `status=upload_required`：按 `upload_url` 与 `headers` PUT 源码包原字节，原参数加 `bundle_key` 再调；
   - 返回未终态：原参数加原 `deployment_id` 续调（服务端每次最多等约 45 秒再返回），直到终态；带着 `deployment_id` 续调才不会重新起容器；
   - 到 `success` 为止。`steps` 标明每步 done / skipped / resumed。明确失败且原因不在源码包时，再用 `prepare_upload` / `complete_upload` / `deploy` / `status` 单步排查。
4. `business_ui_manage(action="get")` 核对部署已写进当前草稿。

- **部署证据**：`deployment_id`、`source_sha256`、`deployed_scaffold_version` 一起记；失败或进行中的部署只记本次尝试，当前线上版本沿用它已成功绑定的部署事实。上线后反读目标应用版本当前绑定的部署，确认是验过的同一份，写入上线结果和 `docs/history/`；回滚时重新核对恢复的绑定与脚手架版本。返回带 `scaffold_upgrade_notice` 时按 [脚手架与预置件.md](脚手架与预置件.md)「预部署与证据」记。
- **派生草稿要重新部署**：派生出的新草稿行不继承部署地址，在新行重新部署并反读。
- **`entry_url`**：`get`、`resolve` 返回的 `entry_url` 是开发者容器地址，只用于核对平台绑定与诊断，不打开、不写进任何给人看的东西、不发给任何人。生产构建直开返回 `HOST_REQUIRED`，本地开发构建直开只进 Mock，都不能证明真实身份、数据集或路线。

### 真跑

制作和验收的真跑都在开发工作集里跑，只要求应用已部署成功，不要求上线。

```text
manage_goalfymax_project(action="run", task_id, idempotency_key,
  scenario_package_ids=[<场景包当前草稿或上线版本的物理行 ID>],
  submit_data={"business_id": …, "orchestration_id": …, <入口表单字段>},
  business_ui_id=<应用家族 ID>, business_ui_data_space="workspace")
```

- **`business_ui_data_space="workspace"`**：路线读写应用库时带 `business_ui_id`（应用家族 ID，不是版本行 ID）并同时带 `workspace`，读写的是开发工作集，和在线预览是同一份库，测试数据不进使用者实例。路线不碰应用库就不传 `business_ui_id`。
- **跑的是哪一版**：开发工作集真跑用这个应用版本号最高、且有可用容器的版本（草稿一创建就会被选中）。只改了挂载（换场景包版本、换模板版本）、没重新部署的版本也会被选中：场景包和 TPE 按它的挂载解析，容器沿用它继承的源版本，所以源版本必须部署过。返回的 `business_ui.version` 是这次用的应用版本、`host_version` 是实际承载的容器版本，跑完先核对 `version` 是不是你要验证的那一版；改了页面或后端代码的，要重新部署才会生效。
- **`submit_data`**：必须有 `business_id`（你生成，例如 `biz-<场景包简称>-<日期>-<序号>`，同一业务实例里不变，后面 `reply` 沿用）和 `orchestration_id`（场景包编排里要启动的那条路线的 id），其余是入口表单字段。
- **等结果**：`manage_goalfymax_project(action="wait", project_id)` 等到终态（`wait` 不接受 `wait_seconds`）。中途表单或审阅用 `reply`：回业务表单时 `content` 传空字符串，答案放在表单数据里；卡在 `waiting-input` 而没人答，是正常挂起。
- **看结果**：以 `route_runs` 里各路线的状态为准（路线完成后项目可能仍显示 running）；`succeeded` 表示这条路线真跑通过，结单门会把它记为这条路线的证据。`get_project_execution_logs(action="workflow_trace", project_id)` 看每步。
- **补 TPE 运行证据**：`otpe_manage(action="verify", task_id, tpe_id, project_id)`，见 [编排脚本.md](编排脚本.md)「冒泡与真跑能证明什么」。

**写到哪份库**：在线预览和带 `workspace` 的真跑写开发工作集（同一份，在线预览里看得到）；带 `business_ui_id` 不传 `workspace` 的真跑写开发者本人的正式实例，要应用已上线并发布，制作和验收不用它；自动化和使用者的运行写各自的实例。

### 草稿、上线、发布各能做什么

| 要做的事 | 草稿部署成功即可 | 要先上线 | 还要发布 |
|---|---|---|---|
| 开发者在工作台「在线预览」里看（真实身份、开发工作集、路线） | ✓ | | |
| 路线冒泡、不带 `business_ui_id` 的真跑、带 `business_ui_id` 和 `workspace` 的真跑 | ✓ | | |
| 保存自动化声明、`business_ui_automation` 的 `validate` / `bubble`（挂本人场景包草稿也按草稿校验） | ✓ | | |
| `business_ui_automation(run_once)`、`resolve` 反读、发布管理页预览 | | ✓ | |
| 带 `business_ui_id` 不传 `workspace` 的真跑（读写正式实例） | | ✓ | ✓ |
| 开发者本人从正式入口打开、在「自动化」面板开真实到点规则 | | ✓ | ✓ |
| 使用者从目录或分享打开 | | ✓ | ✓ |

- **在线预览**只要求两件事：是开发者本人的应用或他协作的应用；当前草稿部署成功（部署记录与草稿行的地址、源码摘要一致）。协作者预览的限制见 [多人协作.md](多人协作.md)「预览、费用与限制」。
- **部署状态和入口分两句写**：部署成功只说明容器起来了。部署后、上线前，入口是工作台「在线预览」；上线后、发布前，正式入口仍打不开（开发者本人也一样），想看仍用「在线预览」；发布后，开发者本人和使用者从 GoalfyMax 打开这个应用，或从目录、分享打开。
- 表里要发布的几项不属于制作和验收；上线结果把它们写进开发者「你可以做的事」，写法见 [../design/验收报告与上线结果.md](../design/验收报告与上线结果.md)「上线结果」。

### 上线

1. `business_ui_manage(action="finalize", draft_asset_id=…, task_id)`。家族里可能同时有多份草稿（有协作者时），所以显式传要上线的那份 `draft_asset_id`：先用 `business_ui_manage(action="get")` 看草稿、创建人和变更说明，和开发者确认是哪一份；平台不替你挑。
2. 挂在应用上的本人场景包草稿随应用一起上线：finalize 时平台先校验、再把它一起上线。
3. `business_ui_manage(action="resolve")` 反读上线版本与挂载的场景包版本，两者版本号记进工单；`entry_url` 非空说明入口已写进版本。resolve 报没有上线版本说明上线没生效，照实说没上线。`resolve` 只认上线版本，上线前报「还没有上线版本（只有草稿）」是正常结果。

### 场景包上线

- `finalize_asset_version_online(asset_type="scenario_pack", draft_asset_id=<草稿行>, change_note=…)` 把草稿晋级为上线版本；旧上线版本不变，已在用旧版的项目不受影响。
- 平台闸门：FA、工具集、TPE 有运行时身份；工具组有连接信息；Skill 文件已就绪；依赖里的 `latest` 引用钉到当刻版本（开发者显式选择跟随最新的除外，要让他知情）。
- 挂在应用上的本人场景包草稿不单独上线：部署预览直接跑草稿，上线应用时一起上线（见「上线」）。单独上线只用于不经应用、直接给别人用的场景包。协作者改属主名下的场景包按 [多人协作.md](多人协作.md)「协作中新建或克隆的资产」。
- 挂载引用钉了版本号时，只有该版本还没上线才会用本人草稿。已上线应用改场景包：`business_ui_manage(action="update", business_ui_id, scenario_pack_id, scenario_pack_version=<场景包草稿版本号>)` 把应用草稿换挂到场景包草稿，再重新部署；上线应用时这份草稿一起上线。
- 上线后反读版本；草稿验证通过不等于已上线。

### 修订、回滚、作废

| 动作 | 工具 | 规则 |
|---|---|---|
| 看家族 | `list_asset_versions` | 任何版本操作前先看清现役上线版本和有没有搁浅草稿。智能应用以外的资产只有资产属主能查；协作者看属主名下资产用 `get_asset` 和 `ensure_editable_asset_draft` 的返回，见 [多人协作.md](多人协作.md) |
| 取草稿 | `ensure_editable_asset_draft`，场景包 `scene_package_manage(action="ensure_draft")`，应用 `business_ui_manage(action="ensure_draft")` | 对上线行直接 update 会自动派生草稿，之后一律用返回的 `draft_asset_id`；`reused: true` 表示沿用已有草稿。应用建草稿（含 update、对已有应用的 `setup`、`ship` 自动派生）带 `change_note` 写这次改了什么，首次 `setup` 建应用身份不用带；协作者只用自己创建的草稿，见 [多人协作.md](多人协作.md) |
| 比较 | `compare_asset_versions(base_version_id, target_version_id)` | 比配置，不比效果；结论写进上线结果 |
| 作废草稿 | `abandon_asset_version_draft` | 只能作废未上线且未被引用的草稿；先 `get_asset_usage_impact` 看影响面并告诉开发者 |
| 回滚 | `rollback_asset_version(version_id)` | 用历史版本内容克隆出新草稿，不改历史行；反读挂载与源码包，部署后走 ④ 验收再上线；每一步开发者确认 |

- **引用不自动跟随**：TPE 上线新版本后，路线 `workflow_ref` 与挂载关系仍指旧行。`otpe_manage(update)` 带着场景包草稿时会自动采用新版本，响应 `message` 开头有【自动采用】提示，看到就反读该草稿；定稿后 `output.mounted_by_stale` 列出仍钉旧版的场景包，逐个 `attach` 或记下不跟进的理由。
- 改挂载（场景包或模板版本）属于契约变更，先按 [../tasks/修订.md](../tasks/修订.md) 评估影响。

### 下线与删除

每一步都要开发者确认（[../SKILL.md](../SKILL.md)「红线」）。

- **下线** `business_ui_manage(action="offline", business_ui_id)`：拆掉全部容器，使用者的库、源码包、版本记录保留，可逆。确认时说清使用者会失去入口但数据不丢。已发布到目录的先由开发者在发布管理页取消发布（否则 `BUSINESS_UI_RELEASED_CANNOT_OFFLINE`）。重新上线 = 对当前版本重新部署后再上线。
- **删除** `business_ui_manage(action="delete", confirm_permanent_delete=true)`：永久删除整个家族的全部版本、实例、库和源码包，不可恢复，传任一版本行也是删整个家族。要开发者明确授权；有在线或已发布版本的，逐字复述应用名让开发者确认。进度只用 `deletion_status` 查；`cleanup_failed` 且 `retrying=true` 是删除中，不报失败；终态 `failed` 要开发者确认下游修好后带 `retry_failed=true` 重发。
- 停用在用的应用用下线，不用删除。

## 常见错误

- 按传进去的上线行 ID 反读，以为修改没生效；应按 `draft_asset_id` 反读。
- 版本工具面传 `asset_type="scenario_package"`，被拒；这里要 `scenario_pack`。
- 上线后不 `resolve`，没发现上线未生效。
- 把 `entry_url` 当应用地址交付，开发者打开后只看到 Mock 假数据。
- 换了场景包或模板版本没重新部署就真跑，跑的还是旧版本。
- 为了真跑或打开在线预览去 finalize；它们只要部署成功。
- 用 `delete` 轮询删除进度。
- 被版本闸门拒绝后绕过去直接改状态字段。
