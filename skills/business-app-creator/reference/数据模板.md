# 数据模板

## 适用场景

设计要存下来的表、建应用身份并挂模板、建数据模板、定列的可编辑性、决定谁建行谁写列、编排脚本读写应用库、管开发工作集、改已上线模板的结构时读。

## 规则

### 是什么

- 数据模板是开发期定稿的表结构（含逐列可编辑性与审计列）。使用者首次打开应用时，平台照模板给这个使用者建一份自己的库，应用后端直连它，编排脚本和场景包里的 FA 经平台工具 `GOALFYAI_TOOL_query_business_app_dataset` 读写同一份。
- **没有应用就没有应用库**：场景包单独运行时这份库不存在，读写会报错；读的地方按「没有数据」收口，不报错、不编数。
- 每个应用必须挂且只挂一份模板，模板里至少一张业务表（系统表不算，只有系统表时 `extract` 会报 `TEMPLATE_WORKSPACE_EMPTY`）。应用角色没有 DDL 权限，表结构只走模板，应用代码里不写 `CREATE / ALTER TABLE`。
- `extract` 只抽结构（表、列、类型、主键、注释、关系），不带样例数据。

### 预览数据不进正式版

- 在线预览里产生的数据（包括 ④ 验收时写入的）写在开发工作集里；上线后每个使用者（包括开发者本人）第一次打开时都从空库开始，平台没有迁移数据的机制。不承诺、不暗示预览里录入、收藏、反馈的数据会带到正式版。
- 上线后必须存在的设定不能只存在工作集数据里：所有人一样的写成代码默认值或场景包配置；每人不同的做首次设置入口，空库时页面引导去填（页面怎么引导见 [前端页面.md](前端页面.md)「首屏与导航按客户业务任务组织」）。

### 数据放哪

| 类别 | 例子 | 放哪 |
|---|---|---|
| 使用者自己的数据 | 门店档案、账号绑定、禁用表达、偏好 | 模板表，列 `editable:user` |
| 路线读写的字段 | 每次运行的结果、效果指标、回写的统计 | 模板表，列 `editable:agent` |
| 系统字段 | 主键、关联 id、审计列 | 模板表，列 `editable:system` |
| 界面意图 | 草稿、筛选条件、已读态 | `sdk.storage`，不进库 |
| 文案、开关 | — | 代码 |

该进库的数据都进模板表，不写成前端 mock 数组、静态 JSON 或后端常量。文件只存路径、文件名、时间，不存文件体。

### 入口字段放哪

② 编施工单时，路线的每个业务输入按下面判断，同一个值只走一边：

| 这个值 | 放哪 |
|---|---|
| 使用者这次发起时才给的（新店名、这次的要求、上传的文件） | 入口表单字段 |
| 应用库里已经有的（前一条路线存下的、使用者在页面上确认或改过的、首次设置里填的） | 入口只放业务键，脚本用 `db()` 按键读库 |
| 所有人一样、不随每次变的设定 | 写进代码默认值或场景包配置，不进入口 |

同一个值不既放入口又读库（不写「入口传了就用、没传再查库」）。③ 的反读自查第四项按这张表核（[编排脚本.md](编排脚本.md)「反读自查四项」）。

### 每张表回答五问

1. **存什么**：看板要算的指标所需字段现在就要有。
2. **逐列可编辑性**：每列 `comment` 以 `[editable:user|agent|system] ` 开头再写中文名，选项列加 `{options:a|b|c}`。每列恰好一个写入方：使用者和路线都要写的信息拆成两列（使用者填的 + AI 建议的）。漏写注释的列按最保守的 user 处理，路线写不进去。
3. **审计**：有写入的表带审计列，都是 `system`，按下表声明。脚手架 `createCrudService` 建行只填业务列和 `updated_by`，更新只改业务列并自动带 `updated_at`、`row_version + 1`，所以 NOT NULL 的审计列必须在库里有默认值；平台不替你补，`gen:pages` 会在生成前检查并拒绝缺默认值的表。

   | 列 | `type` | `nullable` | `default` |
   |---|---|---|---|
   | `created_at` | `timestamptz` | `false` | `CURRENT_TIMESTAMP` |
   | `updated_at` | `timestamptz` | `false` | `CURRENT_TIMESTAMP` |
   | `updated_by` | `varchar(16)` | `false` | `'system'` |
   | `last_run_id` | `varchar(128)` | `true` | 无 |
   | `row_version` | `integer` | `false` | `1` |
   | `deleted_at` | `timestamptz` | `true` | 无 |
4. **冲突**：使用者和路线同时改一行靠 `row_version` 乐观锁，后写方重读重试；没有静默覆盖。
5. **回流**：路线产出直接入库，还是先作草稿等使用者确认后入库——按业务风险定，写进 PRD。

### 谁建行、谁写列

- **身份列由建行的一方填**：主键、父记录外键、项目与业务关联 id、`version_no`、`created_at`。建行时还不知道的值（如发起后才生成的 Runtime id）不设成建行必填，运行关联落在 `last_run_id`。
- **审计列由这次写入的一方随写入更新**：路线写库更新 agent 列时，同一条 SQL 带上 `updated_by='agent'`、`last_run_id`、`updated_at=now()`、`row_version=row_version+1`；建行时带上 `updated_by='agent'`、`last_run_id`，其余审计列取模板默认值。`last_run_id` 取 `ctx.run_id`（本次运行编号，形如 `WFR-…`），用 `params` 传进 SQL。
- **两种情形，按路线有没有应用后端参与选一种**：

  | 情形 | 谁建行 | 路线怎么写 |
  |---|---|---|
  | 有应用后端参与（使用者在页面上发起，后端先建好记录） | 应用后端建行并填身份列；个数在运行中才确定的新行，脚本按 `output_schema` 返回产出，由后端的生产回流接口建行 | 只更新已建行的 agent 列：按入口带入的 id 执行 `UPDATE … WHERE id = :id`，改到的行数不是 1 就返回 `blocked`「未入库」；不写身份列 |
  | 路线自给（到点或数据变化自动发起、没有后端参与的同步类路线） | 路线自己建：前置记录由第一个节点建，运行中产生的失败记录、水位、修订等也由写它的节点建 | 只写本路线负责的行，身份列与 `last_run_id` 一并填上；不依赖后端回流 |

- **同一业务再做一次是更新还是新增**（② 施工单里定）决定写法：
  - 更新原记录：路线自己建的行用 `INSERT … ON CONFLICT (<业务键>) DO UPDATE`，业务键在模板里有唯一约束，同一业务键重复触发命中同一行；后端已建的行用上表的 `UPDATE … WHERE id`；后端建行时同样按业务键先查后建（`INSERT … ON CONFLICT (<业务键>) DO UPDATE … RETURNING id`），同一业务拿到的总是同一行 id，再把这个 id 作为业务键带进入口。
  - 每次都留一条（巡检历史、操作日志）：直接 `INSERT` 并写 `last_run_id`，不建这条唯一约束。
- 写失败一律返回 `blocked`「未入库」，不吞掉；写库语句包在 `if not ctx.dry_run:` 里（[编排脚本.md](编排脚本.md)「读写应用库」）。

### 编排脚本怎么读写应用库

读写都走平台工具 `GOALFYAI_TOOL_query_business_app_dataset`：能写死的语句由脚本直接执行；要看情况决定查什么的，交给挂了这个工具的 FA 自己查。

| 时机 | 谁来做 |
|---|---|
| 发起时要用的上下文（当前这条记录、它的客户档案、门店信息） | 入口只放业务键和使用者这次才给的值；库里已有的由脚本按业务键用 `db()` 读，不由应用后端拼进发起报文 |
| 执行中取数，查什么事先能定 | 脚本用 `db()` 执行固定 SELECT，每条业务流至多读一次，读出来交给 FA 总结、判断是允许的（如按日期和班组取当天记录交给模型写日报），结果沿节点输出往下传 |
| 执行中取数，要看上一步结果再决定查什么 | 业务 FA 挂上这个工具自己查，只用 `mode="reader"`；怎么挂、怎么反读见 [编排脚本.md](编排脚本.md)「建 FA」 |
| 收尾写库 | FA 产出要写的值，脚本用 `db(..., mode="writer")` 执行固定 SQL，只写 agent 列；建行还是更新按上面「谁建行、谁写列」 |

- 脚本读写统一用 [编排脚本.md](编排脚本.md)「读写应用库」的 `db()`；TPE 要预加载装了工具组「query_business_app_dataset」的工具集。
- 要写入或用来筛选的业务值一律用 `:name` 占位符放进 `params`，SQL 本身是固定字符串：不自写 `sql_literal()`、`query_db()` 之类的转义或查询函数，不用 f-string、`+`、`.format()` 把业务值放进 SQL；JSON 用 `:x::jsonb`，一批行用 `jsonb_to_recordset(:rows::jsonb)`。写之前先 `action="tables"` / `"inspect"` 查实表列。
- `INSERT … ON CONFLICT` 的冲突目标必须是模板里已有的唯一约束，否则直接报错；`DO UPDATE` 同样带上 `row_version = <表>.row_version + 1`、`updated_at = now()`。
- FA 只用 `mode="reader"` 查；写库一律由脚本按 FA 的输出执行固定 SQL。
- 连接纪律：写连接经数据集代理，`BEGIN / COMMIT / ROLLBACK`、`SET ROLE`、`SET search_path` 都会被拒；要原子性就压进一条 SQL（CTE、`INSERT ... ON CONFLICT`、`UPDATE ... FROM`）。

### 建应用身份与挂模板

1. **应用身份**（在把 `current_stage` 改成 G5 之前）：`business_ui_manage(action="setup", task_id, name, scenario_pack_id=<场景包家族 ID>, operation_id=<稳定键>)` 得到 `business_ui_id`；在应用根执行返回的 `scaffold_bind_command`，回填 `app.json` 与 `WORKSPACE.md`。重复调用按 `operation_id` 复用，不会建出第二个应用。
2. **挂模板并绑工作集**（模板版本抽出后）：`business_ui_manage(action="setup", task_id, business_ui_id, dataset_template_id, dataset_template_version, data_uid)` 一次完成：挂模板（版本钉整数，不跟随最新）并把开发工作集绑到应用；已挂同版本的步骤会跳过。返回 `success=false` 时看 `steps` 里哪一步 `failed`，修正后用原参数重调；仍失败再单步处理：`business_ui_manage(action="update", dataset_template_id, dataset_template_version)` 挂载、`dataset_template_workspace(action="bind")` 绑定。
3. `update` 与 `bind` 单独用于之后换挂模板版本或换绑工作集；改已上线模板的换挂见下面「改已上线的模板」。

### 建表与出版本

1. `dataset_template_workspace(action="open", task_id, name, description)`，记下 `data_uid`；连接串的保管见下面「开发工作集」。
2. 每张表 `create_table(task_id, data_uid, table_name, target_columns=[…])`（推荐），或用连接串建表：每表至少一列 `primary_key=true`（代理主键用 `bigserial`）；类型写 PG 精确类型；每列注释按上面「每张表回答五问」写可编辑性，有写入的表带审计列；列的 `default` 原样写成 PG DEFAULT 并进模板，只接受字面量、`true/false`、`NULL`、数字、`CURRENT_TIMESTAMP`、`now()`、`gen_random_uuid()`。
3. 需要时 `set_relations` 声明关系（整体替换）。
4. `inspect` 反读，逐列核对类型、主键、注释、`default`。
5. 把 `inspect` 结果翻成业务语言，和 PRD「会记下来的东西」、施工单的表清单对一遍；对不上改到一致再 `extract(task_id, data_uid, template_name, template_description)`，记下模板 ID 与整数版本号。首次不传 `template_id`，新建模板；给已有模板出新版本时传 `template_id`，并带 `expected_base_version`：开始改结构前先从 `inspect`（或 `open`、`connect` 的返回）读出模板当前版本 `template_version`，原样填入。缺了返回 `TEMPLATE_BASELINE_REQUIRED`，基线已被别人抽走返回 `TEMPLATE_BASELINE_CHANGED`，处置见 [报错对照.md](报错对照.md)。
6. 按上面「建应用身份与挂模板」第 2 步挂到应用并绑工作集。

### 开发工作集

- `open` 给你一个独立 PG schema 和 2 小时有效的写连接串，用来建表、灌样例、跑查询；它不占配额、不给使用者用。连接串只填进 `backend/.env`，不进工单、聊天、代码；过期用 `dataset_template_workspace(action="connect")` 重签，已知应用时传 `business_ui_id`，防止两个应用串库。
- 开发工作集只给开发者和协作者用；在里面改数据或结构不影响使用者实例里的库。
- 绑定到应用后，部署出的在线预览容器直接连工作集的库（角色 `bui_w_<data_uid>`）。在线预览和带 `business_ui_data_space="workspace"` 的真跑读写的都是这一份；使用者运行和自动化读写各自的实例（真跑怎么调见 [部署与版本.md](部署与版本.md)「真跑」）。
- **一直绑定在应用上**：制作、验收、上线之后都保留绑定，不解绑、不 `close`、不为它重新 deploy。`close` 会把 schema 和角色一起删掉，连着它的预览容器唤醒后健康检查一直 503，页面卡在 Waking up；平台在 close 时会检查，还有部署跑在工作集上就拒绝并在 `metadata.holders` 点名。
- 要看空库时页面怎么显示，在本机版上清空本机 Mock 数据看，不为此解绑或换绑工作集。
- 应用有协作者时，这个工作集由属主和全部协作者共用：编辑协作者改结构前先核对模板基线并和其他人协调，只读协作者只能用只读连接查询，见 [多人协作.md](多人协作.md)。

### 改已上线的模板

- 上线之后开发工作集继续绑定在应用上（不解绑、不 `close`、不为它重新 deploy），下一次改结构还在它上面改，见上面「开发工作集」；误操作时的错误码处置见 [报错对照.md](报错对照.md)。
- 模板版本被上线的应用钉住后不可变：改结构 = 工作集里改 → `extract` 新版本 → 应用出草稿改挂载 → 重新部署 → 上线。
- 已有模板缺列：在工作集里加列，再 `extract` 新版本，不另建一张同义表。
- **改结构就在绑定到应用的那个工作集上改**（`connect` 取写连接，`CREATE TABLE IF NOT EXISTS` / `ALTER TABLE … ADD COLUMN IF NOT EXISTS`，幂等），再从它 `extract`。开发者的预览容器直连这个工作集，里面有开发期数据；平台不会替它迁移结构。从另一个工作集抽出的新版本钉到草稿时，绑定的工作集还是旧结构，`deploy` 会被拒（`BUSINESS_UI_WORKSPACE_BEHIND_TEMPLATE`，处置见 [报错对照.md](报错对照.md)）：回绑定的工作集补齐表列后重新 `deploy`，工作集保持绑定。
- 只改默认值（`ALTER COLUMN … SET DEFAULT`）是增量：`extract` 不收脚本，响应 `diff.defaults_changed` 逐列列出旧值 → 新值，存量实例升级时平台自动 `SET DEFAULT`。
- 删列、改类型这类破坏性变更，`extract` 必须带 `migration_script`（幂等、单事务、只动本 schema、不建外键）；上线时平台在临时库彩排。存量实例只往前升、没有降级。新增列、新增表优先。迁移脚本怎么写由你定；会改变使用者已有数据或页面行为的（例如删掉一列使用者填过的内容、改了类型后旧值显示不同），用业务话出选择题请开发者定。
- 换模板家族等于换库，平台拒绝；需要新库就新建应用。
- 应用有协作者时改结构的流程见 [../tasks/修订.md](../tasks/修订.md)。

## 常见错误

- 列注释漏了 `[editable:…]` 前缀，路线写不进去。
- 身份列设成 NOT NULL 又没人填，路线写不进，或者 FA 自己编造 INSERT。
- 路线经平台数据集 FA（`GOALFYAI_FASTAGENT_Business_app_fastagent`）转一手去读写应用库；新路线不用它，修订时遇到改成脚本固定 SQL，要判断的给业务 FA 挂工具。
- 让 FA 用 `mode="writer"` 直接写库。
- 路线说好「脚本按唯一键写库」，实际只把结果返回、让应用后端去写；没有后端回流的自动化路线这样写永远进不了库。
- 要模型决定查什么的取数，没给 FA 挂工具，改成把素材全从入口传进来。
- `created_at`、`updated_at`、`row_version` 建成 NOT NULL 却没给 `default`：脚手架建行不填它们，使用者第一次保存就失败；`gen:pages` 会拒绝，回工作集 `ALTER COLUMN … SET DEFAULT` 后重新 `extract`。
- 同一列使用者和路线都写，靠运行时仲裁。
- `close` 了开发工作集，或为关它去解绑、重新 deploy。
- 应用已绑定工作集，却另开一个空工作集建新结构、抽出新版本钉到草稿，再想把新工作集 bind 过来或让平台「自动迁移」旧工作集：新工作集 bind 被拒（已有绑定），旧工作集不会被迁移；正确做法是回绑定的工作集用写连接补齐表列，再从它 `extract`。
- 为「存使用者数据」去挂目录里的「××档案场景包」；那是另一条产品线，不是应用库。
