# 脚手架与预置件

## 适用场景

新建、接续应用前核脚手架版本，判定新建与存量；判断要不要升级（执行步骤在 [../tasks/升级.md](../tasks/升级.md)）；本地跑检查、生成数据页、写后端接口；预部署前复查门槛与打包；处理脚手架版本拒绝；搭页面前确认预置件与生成器怎么用时读。脚手架版本属于应用工程，与 Skill 版本、插件版本、`business_ui` 业务版本分别记录。

## 规则

### 预置件

搭页面先读当前应用的 `frontend/registry.json` 选件；组件、页面块、生成器和后端通用层的用法读脚手架 README。`registry.json` 缺失时按下面「版本依据」核对当前工程、实际版本与迁移完整性，不从文件存在与否猜版本；满足版本要求后再用页面块与生成器。

### 命令

- 工程命令、测试范围与打包规则读应用根 README 和 package.json；前后端细则读各自 README。stages 只安排什么时候跑，不另维护命令表。
- 本地跑：从应用根执行 `npm --prefix frontend run check` 与 `npm run verify`。修改前端行为后另跑前端测试；类型检查与构建不能替代测试。
- 本地联调或布局回归时用 `npm run dev` / `npm run dev:restart` 在后台起服务；这是给测试用的，不是演示预览（演示预览、在线预览各证明什么见 [开发者中心与工作区.md](开发者中心与工作区.md)「演示预览与在线预览」）。
- 部署用的源码包只由 `npm run verify:release` 产出：它跑完整校验并打出要上传的包；不用 `npm run pack`、直接运行打包脚本或手写 tar 代替。

### 生成数据页

- 把 `inspect` 返回的 `columns` 原样存成 `<表名>.json`（形如 `{"table","label","columns":[…]}`），执行 `npm run gen:pages -- --table <表名> --label <中文名> --spec <表名>.json`。
- 它生成列表 / 详情 / 新建 / 编辑页、OpenAPI、后端 CRUD 与测试，接好路由、导航和挂载；再跑一次不会覆盖。生成前会检查表的 NOT NULL 审计列有没有默认值（[数据模板.md](数据模板.md)「每张表回答五问」）。
- 数据页、OpenAPI 与后端 CRUD 都由生成器出，生成后可以改，不手写。

### 后端接口

- 生成的 CRUD 够用就不写。
- 要统计或生产回流时在 `backend/src/common` 上包一层（`createCrudService` 的 `applyGeneratedResult` 写 agent 列），先写 `frontend/schema/api/<operationId>.yaml` 再实现。

### 版本闸门与升级

**工作台与应用脚手架分别更新。** 工作台随 Goalfy App 安装和更新；应用脚手架以本应用的版本清单和在线门槛为依据。

**低于必须线先升级**：本地脚手架低于必须线（下载入口返回 `upgrade_required=true`，或部署报 `SCAFFOLD_UPGRADE_REQUIRED`）时，先按下面「升级步骤」完成升级和验证，再继续制作或部署。其他文件只写当前脚手架的做法，遇到缺件、缺配置项、缺命令的旧工程，一律按这里升级，不另写兼容做法。

#### 版本依据

- 本地实际版本：应用根 `scaffold-release.json` 的 `version`，格式为 `vYYYYMMDD-六位随机hex`。没有文件就是未声明，不能从 package.json 或日期猜。同一文件里的 `sdk_version`、`skill_version`、`upgraded_at` 由升级脚本写回，调工具时有才传、缺了不补；只有 `version` 的旧文件也合法。应用处理过哪些升级指南记在 `docs/upgrade/history.json`（[升级手册模板.md](升级手册模板.md)「history.json」）。
- Skill 最低要求：`SKILL.md` 里的 `scaffold-min-required-version` 机器标记，发布清单自动镜像为 `scaffold_min_required_version` 并登记到平台。
- 平台最低要求（必须线）：MCP 在线返回的 `min_required_version`，已合并平台抬杆与本版 Skill 最低要求，服务端按登记 ID 判断先后，不自己按字符串排序。
- 平台建议要求（建议线）：MCP 在线返回的 `min_recommended_version`，服务端按登记 ID 判断先后。低于建议线时允许继续开发和部署，本地开发提示「建议升级脚手架版本」，线上运行或唤醒时提示升级脚手架版本。
- 最新可下载版本：平台已登记的最新模板；要校验下载包 `sha256`，解包后版本要与响应 `version` 相同。Goalfy App 的版本、模板压缩包名、智能应用名和目录名都不是脚手架版本依据。

#### 新建与接续

建工单后、初始化或继续开发之前，调用 `business_ui_bundle(action="download_template", task_id=..., current_scaffold_version=<本地清单，缺失为空>, workspace_id=<已有应用的真实标识>)`。Skill 的最低脚手架版本在发布时已登记，服务端按工单绑定的 Skill 版本取值，调用时只传上述参数，任何版本号都以 MCP 返回为准。

新建尚无工作区时省略 `workspace_id`，下载并校验最新模板，再 `scaffold:init`。模板包是 `.tar.gz`，`frontend/`、`backend/`、`scripts/`、`Dockerfile`、`scaffold-release.json` 直接在包的第一层：解压用 `tar -xzf <包> -C <应用目录>`，不加 `--strip-components`；解压后先确认这五项都在应用目录第一层，缺了就是解压错了，重新解压，不当成模板缺件去报平台问题。使用缓存模板也要先在线核版本，下载过不等于不用查。下载响应的 `version`、`sha256`、`min_required_version`、`min_recommended_version`、`upgrade_required`、`upgrade_recommended` 要齐全，最低版本可以按契约为空，不自行补值。已有应用先恢复真实目录与阶段资料，再查版本（云端恢复与代码的关系见 [开发者中心与工作区.md](开发者中心与工作区.md)「云端保存与换机」）。响应缺少版本治理字段或返回 `SCAFFOLD_POLICY_UNAVAILABLE` 时，记录缺口并等平台就绪，不自行填写版本绕过。

**核版本要核当前应用。** 在已确认的应用工程根读清单（见 [开发者中心与工作区.md](开发者中心与工作区.md)「应用放在哪」）；模板暂存目录、其他应用、Goalfy 安装目录都不能替代。新模板先校验再放进本应用的独立目录，已有应用则走下面的升级步骤。不同应用分别使用自己的工作区标识，上报版本时不复用另一个应用的记录。

版本达到必须线就可以继续，不必每次升级到最新。

#### 新建与存量

`scaffold-release.json` 的 `guide_baseline: "pending"` 只由平台打包新模板时写入，表示这可能是刚建的新应用。看到它时在「开工」第 2 步判定（新建应用在第 3 步 `scaffold:init` 之后、`npm run setup` 之前），判定完**必须**删掉这个字段。同时满足四条才算新建：

1. `scaffold-release.json` 有 `guide_baseline: "pending"`；
2. 应用根就是 Git 仓库根（`git rev-parse --show-toplevel` 等于应用根），全部提交只有一个（`git rev-list --count HEAD` 为 1），它就是 `scaffold:init` 的模板基线提交：提交说明「chore(scaffold): 模板基线」、作者 `goalfy-agent <agent@goalfy.local>`（`git log -1 --format='%s|%an <%ae>'`）；
3. `git status --porcelain` 为空（未跟踪文件也算改动，`.gitignore` 忽略的不算）；
4. `docs/upgrade/history.json` 不存在。

- 新建：调 `business_ui_bundle(action="upgrade_plan", task_id, current_scaffold_version, skill_version, workspace_id, applied_guides=[], detail="summary")`（`truncated=true` 时把已取到的 `did` 与 `sha` 加进 `applied_guides` 接着取完），把其中 `released=true` 的每份指南写进 `docs/upgrade/history.json` 的 `applied_guides`，每条 `{did, sha, how: "baseline"}`；QA/PRE 的未上线指南不记。然后删掉 `guide_baseline`，只 `git add scaffold-release.json docs/upgrade/history.json` 提交「chore(upgrade): 记录指南基线」。
- 有标记但第 2–4 条任一不满足（已有业务提交、有未提交改动、用 `--no-git` 建后自己提交、基线提交失败或说明与作者对不上），或上一条取计划报错：只删标记、不写 `history.json`，按存量处理；应用根是 Git 根时只提交 `scaffold-release.json`。
- 没有标记、也没有 `history.json` 的是存量应用：升级时看全部有效已发布指南，多出来的由逐条判断记为已满足或不适用。
- **禁止**手工给应用加、或保留这个字段；升级脚本不会把它带进已有应用。

#### 升级步骤

`upgrade_required=true` 时**必须**先升级再继续制作或预部署；`upgrade_recommended=true` 时开发可以继续，先在开发记录中写「建议升级脚手架版本」，并在下一次预部署前完成升级。两种情况都按 [../tasks/升级.md](../tasks/升级.md) 执行：取升级计划、替换固定层、按升级指南改业务代码并逐条测试、跑验证链、预览部署、用相同 `workspace_id` 再调下载入口上报（这是工单的 `local_report`）。新下载模板的版本不提前当成本地应用版本上报；验证失败或冲突没处理完不上报、不预部署。建议线由平台策略维护，Agent 不修改。

目标模板没有 `scripts/upgrade-scaffold.mjs`，或 `upgrade_plan` 报 `SCAFFOLD_VERSION_MISSING` 给不出计划时，才按下面手工迁移：

1. 将最新模板下载到独立目录并核 SHA256。在应用根先提交一次 Git 作为回滚点。
2. 对照旧模板、新模板和当前应用，迁移前后端平台固定层、应用预览适配、校验脚本及受影响依赖；保留业务页面、后端业务逻辑、身份、阶段文档、方案页和数据。不在业务目录直接 git pull 或整包覆盖来代替迁移，也不从已下载的新模板清单直接认定旧应用已升级。
3. 固定层迁移完成后带入目标模板的版本清单；运行 setup、doctor、verify 和适用的 verify:release。迁移冲突或验证失败时，记录未完成状态，不上报升级完成、不预部署。缺少真实工作集时，先完成所需绑定与配置，再跑 release 验证。
4. 通过后用相同 `workspace_id` 再调用下载入口上报已采用版本。之后再有升级计划时照 [../tasks/升级.md](../tasks/升级.md) 处理升级指南。

#### 前后端固定层迁移边界

固定层由模板包里的 `scaffold-fixed-layer.json` 定义：`mode=replace` 的文件整文件以目标版本为准，`mode=merge` 的文件（如 `backend/src/app.ts`、`frontend/src/main.tsx`、`frontend/goalfy-app.json` 与三份 `package.json`）只合并差异；升级脚本按清单处理，动不了的写成 `<path>.upgrade-new` 和 `docs/upgrade/conflicts.md`。依赖、路由接线与测试清单读目标模板的 AGENTS.md 和 README。业务代码按升级指南改，固定层升级带来的 doctor/verify 问题没有指南覆盖时也按 [../tasks/升级.md](../tasks/升级.md) 第 7 步修；只换版本清单或只迁前端不能证明升级完整。迁移结果与无需修改的依据分别记录。

#### 预部署与证据

- 预部署前再次调用下载入口查门槛，以覆盖开发期间的抬杆。
- 脚手架版本清单要在 `npm run verify:release` 打出的实际源码包里一起上传，不只放在被排除的 app.json、workspace.json 或 docs 中。
- 平台在建库、起容器前读取上传包，校验实际字节的 `source_sha256`、根版本清单、平台抬杆和工单对应 Skill 的已登记最低版本。工单自动追加 `scaffold_version` 记录，`evidence=bundle_verified`，并记录 `gate_passed`；只有 `gate_passed=true` 才表示这次版本检查通过，不代表部署或业务验收已成功。查询工单的 `scaffold_versions` 可分别看各工作区 `local_report` 和各 business_ui 的 `bundle_verified`，完整历史在 `entries` 中。
- 部署成功后要记的部署证据见 [部署与版本.md](部署与版本.md)「部署」。`deploy` 返回里带 `data.scaffold_upgrade_notice` 时，说明服务端按上传包判定它过了必须线但低于建议线，部署有效：把提示里的 `current_version` 与 `recommended_version` 原样写进开发记录和上线结果的「脚手架建议线」一项，并把升级列入下一轮计划。
- 工单 `local_report` 表示本地申报，`bundle_verified` 表示源码包校验，`deployed_scaffold_version` 表示指定部署的来源版本，三者分别保留。历史部署空值记为「未知」；`latest_version`、`min_required_version` 和 `min_recommended_version` 用于升级判断，实际版本以部署记录为准。查询某个正在运行或唤醒的使用者实例时，以该实例自己的部署绑定及版本为依据：低于必须线提示需要升级，低于建议线提示建议升级脚手架版本；应用最新提交的版本只证明该提交，旧实例是否升级还需实例侧证据。

#### 版本错误

| 错误 | 处置 |
|---|---|
| `SCAFFOLD_UPGRADE_REQUIRED` | 低于必须线；按「升级步骤」升级、验证、重新打包上传，再 deploy |
| `SCAFFOLD_VERSION_MISSING` | 包里缺版本清单，`upgrade_plan` 给不出计划；按「升级步骤」里的手工迁移完成升级，不凭空补版本 |
| `SCAFFOLD_VERSION_UNKNOWN` | 本地用了平台未登记的版本；**禁止**改版本串，改用平台已登记的模板，或按平台问题报、由维护者先发布登记 |
| `SCAFFOLD_FIXED_LAYER_UNAVAILABLE` | `upgrade_plan` 时最新模板没有固定层清单，是平台侧未就绪；本次不升级、不手工迁移，按平台问题报 |
| `SCAFFOLD_MANIFEST_INVALID` | 源码包损坏、根清单格式错误或重复；修复打包与清单，不只改请求中的版本 |
| `SCAFFOLD_BUNDLE_HASH_MISMATCH` | 部署时：SHA256 与实际上传包不符，对本次真实字节重新打包、算摘要、上传。`upgrade_plan` 时（含 `SCAFFOLD_BUNDLE_CORRUPT`）：平台存的模板包损坏，本次不升级，按平台问题报 |
| `SCAFFOLD_POLICY_UNAVAILABLE` | 平台缺少最低版本登记或策略不可读取；由维护者修复，不跳过检查 |

版本拦截不会自动覆盖本地业务文件，也不会通过另建工单消失。紧急放行只由服务端策略管理，制作 Agent 不修改该策略。

## 常见错误

- 从 `package.json`、模板压缩包名或日期猜脚手架版本；只认 `scaffold-release.json` 与 MCP 返回。
- 在业务目录直接 `git pull` 新模板或整包覆盖来「升级」，冲掉业务代码。
- 只迁移前端 SDK 和版本清单，漏了后端平台模块与 `backend/src/app.ts` 的挂载。
- 版本清单没进 `npm run verify:release` 打出的源码包，只放在被排除的文件里。
- 用 `npm run pack` 或手写 tar 打部署包。
- 把新下载模板的版本提前当成本地应用版本上报。
- 旧工程缺件时照着旧做法自写兼容代码，而没有先升级脚手架。
- 有升级计划却手工对照模板改固定层，或运行应用里的旧版 `npm run scaffold:upgrade`。
- 有业务提交的应用带着 `guide_baseline` 被当成新建，把全部指南记成已执行。
