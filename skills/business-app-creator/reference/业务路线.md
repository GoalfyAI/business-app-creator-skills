# 业务路线

## 适用场景

组装或修改路线、用 `assemble`、加中途表单、设计交付与审阅、处理「改稿 / 重做 / 换路线」、路线保存或冒泡报错时读。多节点、并行、扇出、中途表单、Agent 接管的字段写法读 `get_diagnosis_doc(topic="otpe_multi")`。

## 规则

### 路线对象

- 场景包上的 `workflow_orchestration` 是整体业务路线（一包一份），里面 `orchestrations[]` 每一项是一条路线，`orchestration_id` 是它的标识；路线冒泡、结单核对、Runtime 绑定都以它为单位。
- 一条路线包含：入口表单标识、路线级输入定义、节点依赖图（节点引用已挂载的编排型 TPE，无环且全部可达）、节点输入映射、可选的运行中交互与节点级 Agent 介入、唯一的最终交付与审阅。
- 写入是**整体替换**：写前反读原值，改完整份传回。保存成功只证明静态结构合法，不能代替冒泡。
- 路线只调度已存在且 verify 通过的编排型 TPE；场景包没有编排型 TPE 时**禁止**伪造空节点或空图。
- 平台要求应用挂的场景包至少有一条路线；只有规则步骤的应用也建一条最小的单节点路线。

### 什么时候用路线、用哪种

| 情况 | 做法 |
|---|---|
| 单条 TPE 声明或调用了业务事件、需要表单握手或交付审阅、要从应用发起 | 单节点路线 |
| 多条 TPE 有固定依赖、扇出、汇合 | 多节点路线 |
| 单条 TPE 无事件、不需要握手 | 可以直接派发，不需要路线 |
| 整条路径要临场规划，或 Agent 介入产生的新值要成为后续输入 | 普通任务点，不画固定图 |
| 用户改稿、重做、改走另一条路线 | 冻结当前交付，开启新的运行实例；**禁止**画回边模拟循环，**禁止**覆盖旧交付 |
| 制作期就能预知的用户输入 | 全部放入口表单 |
| 只有上游成功后才知道、且要喂给未派发下游的输入 | 节点级运行中交互（中途表单） |
| 节点成功后需要 Agent 检查或处理异常 | 该节点声明 Agent 介入，写清指令与可验证的继续或接管标准 |

### assemble 怎么用

1. 各节点 TPE 已建好并挂进场景包后，按执行顺序调 `scene_package_manage(action="assemble", task_id, scene_package_id, tpe_ids=[…], orchestration_id, title, entry_form_id)`。
2. 它读各 TPE 的输入输出 Schema：同名字段接上游输出，并把被读的节点列为直接依赖；其余字段进入口表单；交付覆盖末节点输出；审阅缺省 `user_gate`。返回合并进现有编排的 `workflow_orchestration` 草稿，不写库。
3. 先处理 `unresolved`（类型不一致、输出为空）与 `notes`（需改名的字段），再整份传给 `scene_package_manage(action="update", scene_package_id, workflow_orchestration)` 保存。
4. 局限：只做线性和「读谁就依赖谁」的接线；分支、并行、扇出、中途表单、Agent 接管、跳转到另一条路线仍按 `otpe_multi` 手写。节点只能从直接依赖的上游读 `node_output`。

### 交付与审阅

- **交付映射**：要交付的文件，路径字段必须进 `delivery.mapping`，否则不会登记为附件；映射引用的字段本次缺失时跳过，必填由 `output_schema` 的 `required` 决定。文件必须真实存在、声明为 `workspace-file-path`、在最终节点的 `ctx.output_dir` 里。
- 未声明为文件的 workspace 路径不会成为附件：旧环境会拒收（`ORCH_DELIVERY_FILE_UNVERIFIED`），新环境替换成「内部资料：文件名」。本来要交付的文件没成为附件时补齐复制、声明和映射，不以引用文字代替。
- **审阅动作**：结束业务、以结构化原因拒绝并结束、跳转到另一条路线、交由 Agent 处理。每个动作只写 `action_key` 与 `kind`，跳转另加 `orchestration_id` 与可选 `target_input_mapping`；**禁止**写 `label`、`description`，按钮文案由 Runtime 生成。
- **跳转两种形态**：不需要用户新输入时声明 `target_input_mapping`（每项 `source='delivery'`，覆盖目标路线全部必填字段），用户点了直接启动；需要新输入（如写修改意见）时不声明映射，跳转后展示目标路线的入口表单。
- 审阅形态：`user_gate` 停在审阅等用户确认（缺省）；`agent_gate` 由 Agent 按路线声明的标准收尾，用户不逐次审阅。

### 表单定义放哪

Hub 不登记表单 Schema，路线里只有 `form_id` 和映射；`get_asset(asset_type="scenario_package")` 返回的 `business_forms` 是字段清单的权威来源。标题、字段说明、控件提示、顺序这些展示信息，写路线时同步为每个 `form_id` 落一份场景 Skill 文件 `forms/<form_id>.json`。

- **入口映射**：`entry.input_mapping` 的规则只声明 `source/node_id/path/transform`，来源只能是 `formdata`；**禁止**在映射规则里直接写 `default` 字段。完整写法以 `get_diagnosis_doc(topic="otpe_multi")` 为准。
- **入口默认值**：Schema 的 `default` 只是声明，不会自动填充实际输入。表单或调用方**必须**在提交前把默认值写入实际表单数据，再通过 `source="formdata"` 与 `path` 映射；首次路线冒泡用 `workflow_input` 传入已填值的入口数据。不要把 `transform` 当作入口运行时自动补默认值的保证。

### 冒泡

- `scene_package_manage(action="bubble", task_id, scene_package_id, orchestration_id, workflow_input)` 发起；续等只传 `run_id`；回填中途表单传 `run_id + formdata`。三种组合只选一种，多传的 `evidence_level` 会被忽略。
- 每条路线以当前合同下最近一次到终态的运行为准，路线冒泡与真跑都算；路线或节点改过之后旧证据作废，要重跑。
- 路线冒泡的 `WRV-` run_id 可以直接交给 `otpe_manage(action="verify", tpe_id, run_id)`，单节点路线不必再单独冒泡。
- 一条路线一条工单 checkpoint，各带自己的 `run_id`。

## 常见错误

- 改路线时只传改动的那条，覆盖掉其他路线（整体替换语义）。
- 节点读了非直接依赖的上游输出，保存被拒。
- 要交付的文件只在 `output_schema` 里声明，没进交付映射，界面显示无产出文件。
- 审阅动作写了 `label`，保存门拒收未知字段。
- 用多条单条 TPE 的冒泡拼成路线证据。
- 为改稿在同一张图里画回边。
