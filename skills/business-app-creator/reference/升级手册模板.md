# 升级手册模板

## 适用场景

执行 [../tasks/升级.md](../tasks/升级.md) 收尾或整次失败时写 `docs/upgrade/` 下的手册、`latest.json`、`history.json`，以及开工判定新建应用写指南基线（[脚手架与预置件.md](脚手架与预置件.md)「新建与存量」）时读。开发者和 Studio 总览看这三个文件知道升级换了什么、每条指南怎么判断、改了哪些业务文件、测得怎样、还有什么待确认。

## 规则

### 取值来源

- 手册与 `latest.json` 里的每个版本号、指南、文件路径都来自本次 `upgrade_plan` 的返回、`scripts/upgrade_guides.py candidates` 的输出（临时记录里的原文）和本次实际执行结果；**禁止**凭记忆补写计划里没有的改动，也**禁止**删掉计划里有的指南。
- 指南按 `impact` 分三表（必须 `required`、建议 `recommended`、仅告知 `none`），表里没有指南写「无」；`reconsider` 里复核后仍不适用的单列「曾判不适用」。没有任何指南时只写固定层。
- 固定层差异取 `fixed_layer.changed / added / removed`，每个路径注 `replace` 或 `merge`（取自 `fixed_layer.target_manifest.files[].mode`，`removed` 取 `base_manifest`）；`fixed_layer.base_source` 照写：`manifest` 是登记时的清单，`backfilled` 是平台按旧包回填的基线，`missing` 是没有基线、所有 replace 文件都要人工核对，`current_is_latest` 是模板已是最新，`sdk_major_skipped` 是跨 SDK 主版本、没有固定层差异（`scaffold_route=legacy` 时旧路迁到 SDK 5，固定层按迁移指南迁；其他按已是最新）。
- 「实际改了的业务文件」取 `guide_commits.files`，与 `git show --name-only` 一致；「要改的业务文件」是判断时按 `actions` 定下的文件。
- 手册写给开发者看，用业务语言说明影响；路径、命令和提交号原样保留。

### 手册骨架

文件名 `docs/upgrade/<YYYY-MM-DD>-升级手册.md`，照下面写，小节不增不减：

```markdown
# 升级手册 <YYYY-MM-DD>

## 结果
- 状态：完成 / 失败（步骤 <step>，原因 <一句话>）
- 版本：<本地 version> → <latest.version>；sdk_version <现值> → <target.sdk_version>
- 必须线 / 建议线：<min_required_version> / <min_recommended_version>（upgrade_required=<…>，upgrade_recommended=<…>）
- 指南来源：制作 Skill <skill_version> 自带的升级指南
- 回滚点：upgrade: before <from>→<to>（<提交号>）

## 固定层
- 基线来源：<base_source>
- changed / added / removed：<path>（replace|merge）…
- 冲突与处置：<path> — <处置一句话>（详见 docs/upgrade/conflicts.md）

## 指南
### 必须（required）
| 指南 | 判断与依据 | 决定与理由 | 要改的业务文件 | 实际改了的业务文件 | 测试与结果 | 提交 |
|---|---|---|---|---|---|---|
| <did> <title> | <不适用/已满足/适用>：<看了哪些文件、哪些代码> | <做/暂缓/待确认/失败>：<理由> | <path…> | <path…> | <test_id> <passed/failed/skipped> | <提交号> |
### 建议（recommended）
（同上表头；无指南写「无」）
### 仅告知（none）
（同上表头；无指南写「无」）
### 曾判不适用
- <did> <title>：复核结论与依据

## 待确认问题
- <did>：<问题>（问于 <时间>，未答）

## 验证
- setup / doctor / verify / verify:release：<通过|失败|跳过>（doctor 写第 8 步重跑的最终结果）
- doctor/verify 报的问题与适配：<检查码>：<怎么修的，提交号；或「不是升级带来的，未改」「未修好」>（没有写「无」）
- 预览部署：<deployment_id，或跳过原因>
- 上报：<local_report，或未上报原因>

## 失败与可疑指南
- <失败步骤、did、test_id 与输出摘要；suspect_guides 按交集文件数由多到少>（完成时写「无」）
```

### latest.json

放在应用根 `docs/upgrade/latest.json`，本任务写、Studio 读；哪些字段每次重写、哪些沿用上次，见示例后的说明：

```json
{"status":"checked|awaiting_consent|done|failed",
 "step":"precheck|plan|upgrade|setup|judge|adapt|verify|guide|verify:release|deploy|report|",
 "from":"v20260924-653df8","to":"v20261104-57ee8b",
 "skill_version":"v20261110-abcdef",
 "counts":{"required":1,"recommended":4,"none":0,"changed_since_applied":0},
 "manual":"docs/upgrade/2026-11-05-升级手册.md","before_commit":"…",
 "awaiting":{"reason":"deploy_consent","asked_at":"RFC3339","guides":["D-4001"],"consent":"","consented_at":""},
 "conflicts":["frontend/src/sdk/authorization.ts"],
 "notices":["已执行记录缺失，将重新核对全部已发布指南"],
 "guide_decisions":[{"did":"D-4013","impact":"recommended","decision":"apply|not_applicable|already_done|deferred|asked","basis":"看了哪些文件、哪些代码","reason":""}],
 "guide_tests":[{"did":"D-4013","test_id":"t1","status":"passed|failed|skipped","evidence":"输出摘要或跳过原因","finished_at":"RFC3339"}],
 "guide_commits":[{"did":"D-4013","commit":"…","files":["backend/src/routes/orders.routes.ts"]}],
 "doctor_findings":[{"source":"doctor|verify","code":"检查码","level":"FAIL|WARN","message":"输出原文摘要","fix":"adapt|guide:D-4013|none","commit":"…|null","status":"fixed|open"}],
 "questions":[{"did":"D-4100","question":"订单页提交后是否保留草稿","asked_at":"RFC3339"}],
 "suspect_guides":[{"did":"D-4013","files":["backend/src/routes/orders.routes.ts"]}],
 "failure":{"step":"guide","did":"D-4100","test_id":"t1","error":"","consecutive":1},
 "feedback":[{"did":"D-4100","code":"FB-…"}],
 "rollback_stash":{"message":"upgrade-rollback v20260924-653df8→v20261104-57ee8b 2026-11-05T15:00:00+08:00","commit":"…","files":["frontend/src/pages/Orders.tsx"],"created_at":"RFC3339"},
 "rollback_backup":{"branch":"upgrade-backup/v20260924-653df8-to-v20261104-57ee8b-20261105150000","head":"…","developer_commits":[{"commit":"…","subject":"改订单页文案"}]},
 "rollback_setup":{"status":"passed|failed","error":""},
 "rollback_platform":[{"tool":"business_ui_manage","action":"update","what":"","before":"","after":"","status":"restored|failed","error":""}],
 "pre_upgrade_wip":{"commit":"…","files":["frontend/src/pages/Orders.tsx"]},
 "steps":[{"name":"plan","status":"ok|failed|skipped","at":"RFC3339","note":""}],
 "error":"","updated_at":"RFC3339"}
```

- `checked`：只取了计划、没改应用文件，`to` 与 `counts` 已填。`awaiting_consent`：第 6 步停下等部署授权，`step=judge`，`from`、`to`、`before_commit`、`awaiting`（`guides` 列要部署后测试的必须做的指南 did）已填，并已单独提交；这是没做完的升级，下次进来按 [../tasks/升级.md](../tasks/升级.md)「先读什么」第 5 条处理，收尾或回滚时整份改写、去掉 `awaiting`。`done`：收尾完成并上报。`failed`：`step` 填失败的那一步，`error` 一句原因；第 3 步提交回滚点以后的失败已回滚到 `before_commit`，只有 `step=report` 保留已完成的修改。
- 写 `awaiting_consent` 时只改 `status`、`step`、`from`、`to`、`before_commit`、`awaiting`、`updated_at`，其余字段保留上次的值（`failure` 要留给连续失败计数）。开发者同意部署后只在 `awaiting` 补 `consent`（原话）与 `consented_at`，`status` 不变，单独提交 `upgrade: consent given`；`consented_at` 已填表示升级在同意后继续做、还没收尾，中断时按 [../tasks/升级.md](../tasks/升级.md)「先读什么」第 5 条的中断处理，不再问部署。
- 沿用与重写：`status=checked`，或第 3 步提交回滚点之前的 `failed`（`step` 为 `precheck` / `plan`、没改应用文件）时，只改 `status`、`step`、`to`、`skill_version`、`counts`、`notices`、`steps`、`error`、`updated_at`，其余字段（含 `failure`、`feedback`、`questions`、`suspect_guides`、上次的 `guide_*`）保留上次的值，**禁止**整份重写；其他情况整份重写，但 `feedback` 与没答的 `questions` 照样沿用。
- `guide_commits`：指南动作没有改动任何文件时不提交，记 `{"did":"…","commit":null,"files":[]}`，手册「实际改了的业务文件」写「无改动」。
- `skill_version`、`counts` 原样取脚本输出，不自己数；没读指南（已是最新）时不写。
- `guide_decisions` 收尾时不再有 `asked`：没答的已转 `deferred`。`questions` 只留还没答的问题，供下次升级判断「同一问题不重复问」。
- `failure` 记最近一次整次失败（第 13 步），只检查和第 3 步之前的失败不动它，`done` 时清掉；`consecutive` 是同一 `required` 指南连续导致整次失败的次数（`failure.did` 为空——固定层或 doctor/verify 报的问题不归某条指南——时记 0）：上次 `latest.json` 的 `failure.did` 相同时加 1，否则为 1；第 6 步得不到部署授权的整次失败（`failure.step=judge`）与中断回滚（`error`「升级中断没有做完，已回滚」）不计入：本次是这种失败时记 0，上次是这种失败时本次按上次没有同一指南的失败算（记 1）。`feedback` 沿用上次的记录，本次新提交或追加的编号加在后面。
- `rollback_stash`：整次回滚前工作区不干净、整体暂存时写（第 13 步第 3 条），`message` 是 stash 说明（按它在 `git stash list` 里找，编号会变）、`commit` 是 stash 提交号，暂存里可能同时有开发者的改动和升级做到一半的内容；没建 stash 时不写。`rollback_backup`：回滚点之后有不以 `upgrade: ` 开头的提交、在 `HEAD` 打了备份分支时写（第 13 步第 2 条）。`rollback_setup`：回滚后重新 `npm run setup` 的结果。`rollback_platform`：第 7、9 步改过平台上的应用配置、整次回滚时逐项恢复的结果（第 13 步第 3 条），`what` 用白话写改的是什么，`before` / `after` 写原值与升级中的值，没改过平台配置时不写。`pre_upgrade_wip`：第 3 步把开发者没提交的改动单独提交时写（收尾与整次失败都写）。手册「失败与可疑指南」各写一行（暂存说明、备份分支名、setup 结果）。
- `steps` 与 `notices` 只写本次。`steps[].at` 是该步实际结束的时间：每步结束时就把时间记进临时记录，收尾或回滚时照抄，**禁止**统一填写入 `latest.json` 时的当前时间。`doctor` 不是失败步骤：第 5 步 doctor 的 `FAIL` 记进 `doctor_findings`（`steps` 里该项 `status=failed` 照写），交给适配，放行看第 8 步 `verify`；`doctor_findings` 每次整份重写。

### history.json

放在应用根 `docs/upgrade/history.json`。`applied_guides` 记本应用处理过哪些指南，只由本任务收尾与开工判定写；`upgrades` 是升级记录，由升级脚本在 [../tasks/升级.md](../tasks/升级.md) 第 4 步追加，本任务不改。写 `applied_guides` 时先读当前文件、只替换这一个字段，`upgrades` 与其他字段原样保留：

```json
{"upgrades":[{"from":"v20260924-653df8","to":"v20261104-57ee8b","upgraded_at":"RFC3339","…":"由升级脚本写"}],
 "applied_guides":[
  {"did":"D-4013","sha":"0123456789abcdef","how":"tested","fail_count":0,"updated_at":"RFC3339"},
  {"did":"D-4009","sha":"…","how":"deferred","reason":"待开发者确认：订单页提交后是否保留草稿","fail_count":0,"updated_at":"RFC3339"},
  {"did":"D-4001","sha":"…","how":"failed","reason":"t1 失败：…","fail_count":1,"updated_at":"RFC3339"}
]}
```

- `sha` 直接取脚本输出里该指南的 `sha`（文件内容 sha256 的前 16 位），**禁止**自己算或改；`how` 只取 `tested`、`already_done`、`not_applicable`、`deferred`、`failed`、`baseline`，`deferred` 与 `failed` 必须带 `reason`。
- 同一 did 只留一条：再处理时更新 `sha`、`how`、`reason`、`updated_at`；`fail_count` 是该 did 记成 `failed` 的累计次数，本次 `failed` 加 1，其他结果保留原值。
- 脚本输出 `retired` 里的 did 删掉。
- 读取时的异常：
  - 文件不存在：按存量处理（`applied_guides` 为空，脚本会返回本 Skill 自带的全部有效指南），`latest.json` 的 `notices` 写「已执行记录缺失，将重新核对全部已发布指南」。
  - JSON 损坏或含合并冲突标记（`<<<<<<<`、`=======`、`>>>>>>>`）：按存量处理并同样提示；第 3 步提交回滚点前把原文件改名为 `history.json.broken-<YYYYMMDDTHHMMSSZ>` 保留，**禁止**在原文件上覆盖；收尾时新建 `history.json`。
  - 合法 JSON 但没有 `applied_guides`：按空列表处理；是数组（旧版升级脚本的升级记录）时，收尾写回成 `{"upgrades": <原数组>, "applied_guides": […]}`，原记录不丢。

## 常见错误

- 手册写在执行前或边做边改，单条回退后手册与实际提交对不上；手册、`latest.json`、`history.json` 只在收尾或整次失败时写。
- 不写判断依据直接记 `not_applicable` / `already_done`，或把 `required` 指南记成 `deferred`。
- 整次失败后仍改 `history.json`，下次检查漏掉本该重做的指南。
- 手工改 `history.json` 的 `how` 或 `sha` 让指南不再返回；或把 `not_applicable` 记成已执行，应用后来用上该功能时没人复核。
- 自己数待处理条数，和脚本 `counts`、Studio 总览对不上。
- 损坏的 `history.json` 直接覆盖，原记录丢失。
