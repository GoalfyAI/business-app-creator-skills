# 新路应用（新 SDK）

## 适用场景

应用工程的 `frontend/goalfy-app.json` 写了 `"executor": "launch_agent"`，或要把旧应用迁到新路时读。本文件只写新路和旧路不同的地方；没提到的照各段文件（`stages/`）与 reference 原文做。

## 规则

### 先认是哪条路

- 以应用工程 `frontend/goalfy-app.json` 的 `executor` 为准：`"launch_agent"` 是新路；没有这个字段是旧路，照原文挂场景包。新建应用用哪条路由当前脚手架模板决定，**禁止**手工给旧模板加 `executor` 或删掉它。
- 新路的一次运行叫「执行」，标识是 `business_id`（`BIZ-…`，**服务端生成**，调用方不自填）。执行里没有运行 Agent（助手），没有对话；每个使用者实例一个隐藏项目，多次执行在里面并行。
- 同一应用的旧版本仍走旧路；发布新 SDK 版本后，新发起的执行走新路。

### 和旧路不同的做法

| 环节 | 旧路 | 新路 |
|---|---|---|
| 路线和 TPE 挂在哪 | 场景包 | 应用版本：`workflow_orchestration`（格式与场景包里的完全相同）+ `tpe_ids` |
| 建应用 | ③ 建应用身份 `business_ui_manage(action="setup", scenario_pack_id=…)`（[数据模板.md](数据模板.md)「建应用身份与挂模板」） | ① 开发者确认 PRD 后就 `business_ui_manage(action="create", task_id, name)` 建应用占位，拿到 `business_ui_id`；不建场景包。③ 的 `setup` 传这个 `business_ui_id`、不传 `scenario_pack_id` |
| 保存路线 | `scene_package_manage(action="update", workflow_orchestration)` | `business_ui_manage(action="update", business_ui_id, workflow_orchestration, tpe_ids)`；两者都是**整体替换**，编排里引用的每个 TPE 都要在 `tpe_ids` 里；`tpe_ids` 写 TPE 资源组 ID 加具体版本号，不要写某个版本行的 ID（写错时部署会一直停在构建中） |
| 节点能用的工具 | 节点只用它的 TPE 自己挂的工具集（加上 FastAgent 自己的工具）；场景包工具箱是给主控 Agent 用的 | 相同：节点脚本调用的工具要挂在该节点 TPE 上（`update_asset_relations(asset_type="tpe", asset_id, add_toolset_ids)`）；新路没有主控 Agent，场景包工具箱不再需要 |
| 组装路线 | `assemble` 传 `scene_package_id` | `scene_package_manage(action="assemble", business_ui_id, tpe_ids, orchestration_id, …)`：并入应用版本原有路线与 TPE，返回的 `workflow_orchestration` 与 `tpe_ids` 原样交给上一行保存 |
| 路线冒泡 | `scene_package_manage(action="bubble", scene_package_id, …)` | 传应用家族 `business_ui_id` 代替 `scene_package_id`，对你最新的草稿发起一次预览执行；`run_id` 就是 `business_id`（`BIZ-` 开头）；交付审阅用 `run_id + formdata={"action_key": …}` 回填；入口要读文件时带 `workspace_files`（先 `file_to_url(purpose="tool_test_fixture")` 上传，`formdata_pointer` 指向 `workflow_input` 里的空文件字段），文件传进你自己的预览隐藏项目，每次冒泡放在单独的 `bubble-<随机串>/` 目录，表单字段会被填成真实路径；带文件发起失败或超时（回执 `next_action="ask_developer"`）时不要直接重发：每次发起都会新建一次执行，先请开发者在预览页的执行记录里确认这次冒泡是否已在运行；不接受 `review_action_key`；止损用 `action="cancel", run_id` |
| 真跑 | `manage_goalfymax_project(action="run", scenario_package_ids=[…], business_ui_id, …)`（[部署与版本.md](部署与版本.md)「真跑」） | 传 `business_ui_id`、`business_ui_data_space`（制作阶段 `workspace` 跑已部署的草稿、读写开发工作集；上线后 `instance` 跑上线版本）与 `submit_data={orchestration_id, form_id, formdata}`，不传 `scenario_package_ids`；回执的 `business_id` 用于 `status / wait / reply / stop`；没有 `send`（新路没有对话）；回复由 MCP 补 `orchestration_id`，按回执 `next_action.template` 填 |
| 查轨迹 | `get_project_execution_logs(action="workflow_trace", project_id)` | 再带上 `business_id`，只看这一次执行（一个隐藏项目里有多次执行） |
| 结单门豁免 | checkpoint 写 `scene_package_id` | 写 `business_ui_id`、`business_ui_version_id`（冒泡或真跑回执里的提交号）与 `orchestration_id`，其余字段同 [部署与版本.md](部署与版本.md)「三道门」 |
| 表单展示定义 | 场景 Skill 文件 `forms/<form_id>.json` | 前端工程 `frontend/schema/packs/<pack>/forms/` 与 `orchestrations/`，构建时收集；`goalfy-app.json` 的 `packs` 列出用到的目录 |
| 前端 SDK | 项目句柄、聊天 | 以执行为单位：`sdk.business.start` 发起（回执前禁用提交按钮）、`useExecution(businessId)` 取执行句柄、消息中心聚合待答；没有项目句柄和聊天。写法以模板 `frontend/src/sdk/docs/README.md` 为准 |

### 编排不能用需要运行 Agent 的写法

新路没有运行 Agent（助手）接手，Hub 保存时拒收（400，`workflow orchestration invalid` 带具体位置），改编排即可：

- **禁止**交付审阅 `review.type = "agent_gate"`，**禁止**审阅动作 `kind = "agent_gate"`（交由 Agent 处理），**禁止**节点 `sa_handoff`。
- 审阅只用 `user_gate`：停下来等使用者（`message_type: "ask"`），或直接交付（`message_type: "result"`）。动作只在 `complete_business`、`fail_business`、`start_orchestration` 里选。
- 结果好不好由使用者审阅，平台不替你判断。能用规则判断的写进 TPE：输出校验、`business_gate`。脚本抛错（`business_gate`）是新流程唯一的业务停止写法：返回阻断状态只结束本节点，下游照常派发。
- 自动化路线同样只能 `user_gate`，见 [自动化.md](自动化.md)「收尾方式」。

### 修正上次交付

使用者审阅不满意、要在上一趟基础上改时：

1. 审阅加一个 `start_orchestration` 动作，指向修正路线。要使用者写修改意见时，不声明 `target_input_mapping`，跳转后展示修正路线的入口表单，表单里放反馈字段；也可以在审阅页面上直接带反馈字段：回复审阅时 `formdata` 里 `action_key` 以外的字段都算反馈。
2. 修正路线的脚本从 `ctx.previous_delivery` 读上一趟：`previous_runtime_id`、`file_paths`（上一趟交付文件路径）、`action_key`、`feedback`、`summary`（交付内容摘要，最多 2000 字，`summary_truncated` 标是否截断）。要全文就读 `file_paths` 里的文件，在它基础上改，**禁止**从头重做。第一趟时它是 `None`。
3. 交付文件在同一使用者的隐藏项目里，按普通 workspace 路径读；要随本次交付的文件照常复制进本节点 `ctx.output_dir`。

### 编排脚本的额外约定

- 中间文件写在 `ctx.process_dir` 下：同一隐藏项目里多次执行并行，写到固定路径会互相覆盖。
- 平台不自动重跑失败节点；派发超时、派发中断也判失败，等使用者点重试。重试会重跑失败节点的全部步骤：含外部发送（发信、发消息、下单）的步骤在 TPE 描述里写明会不会重复发送，用幂等键或先查后发防重复。幂等键由三段拼成：`ctx.business_id`（本次执行编号，重试时不变）、本步标识（脚本里写死的步骤名或消息类型，同一应用内不重复）、本步要发送的对象。缺了本步标识，同一次执行里两步给同一个人发不同消息（先「请审批」后「已通过」）时，第二条会被当成重复跳过。同一步里给同一对象发多条（例如逐条提醒同一负责人处理 3 张逾期单）时，再拼上这条消息对应的业务记录编号（如订单号），否则后几条会被当成重复跳过。修正路线与上一趟同属一次执行，再拼上 `ctx.previous_delivery` 的 `previous_runtime_id`。单条冒泡里 `ctx.business_id` 是 `None`，幂等键写在 `if not ctx.dry_run:` 里拼；旧路也是 `None`，不能用它作幂等键。
- 多个执行可能同时改同一条业务数据，平台只保证同一执行内部串行。会冲突的写库用数据集唯一约束或幂等键兜住；不同执行的 `ctx.business_id` 不同，跨执行的冲突不能只靠它。
- 数据只来自应用自身的实例数据（数据模板）和官方、公开数据集；**禁止**依赖开发者个人的普通数据集，使用者运行时没有权限。
- 执行路径优先读写数据集，少调应用后端：应用后端无人访问时会休眠，冷启动会拖慢执行。

### 上线与发布

- 占位草稿（还没挂编排）**不能**上传源码包和部署（`BUSINESS_UI_NO_SCENARIO_PACK`），也就上线不了；先在 ③ 把编排与 `tpe_ids` 挂上（[../stages/3-制作.md](../stages/3-制作.md)「2.1 后台能力」的「路线」），再部署、上线、发布。发布时还要求挂了编排（`BUSINESS_UI_INVALID_SCENARIO_PACK_REFS`）。
- 改过编排后重新部署一次再发布：部署记录对着的是旧契约时发布会被拒（`BUSINESS_UI_CONTRACT_OUTDATED`，码义见 [报错对照.md](报错对照.md)「部署与预览」）。
- 新路没有场景包：⑤ 里场景包随应用上线、`resolve` 反读场景包版本这些核对，改为核对应用版本上挂的编排与 `tpe_ids`。
- 发布新 SDK 版本受灰度名单控制。被拒时把原文告诉开发者，**禁止**为了能发布改回旧路。
- 有运行中的执行时发布会失败并返回数量（发布保护），等执行结束或由开发者决定取消。

### 旧应用迁到新路

1. 编排格式不变：从场景包取出 `workflow_orchestration` 与 TPE 清单，去掉需要运行 Agent 的写法。
2. 核对节点工具：节点在旧路就只用 TPE 自己挂的工具集，迁移不改变节点能用的工具；场景包工具箱里的工具是给主控 Agent 用的，不用搬。只需确认每个节点脚本调用的工具都挂在该节点 TPE 上（旧应用里偶有脚本调了 TPE 没挂的工具，借迁移补上）。
3. 用 `business_ui_manage(action="update", business_ui_id, workflow_orchestration, tpe_ids)` 挂到应用草稿；场景包挂载与编排挂载互斥，同一份草稿只留一种。
4. 换新 SDK 脚手架，页面改成以执行为单位（模板 README），重新部署、试用验收后再上线；发布由开发者决定。
5. 发布后，旧路上停在等待使用者的执行会被平台取消并通知使用者，上线前告诉开发者。

### 报错对照

| 错误码 | 意思 | 怎么做 |
|---|---|---|
| `APP_VERSION_NOT_LAUNCH_AGENT` | 按新路发起，但该版本不是新路部署 | 核对 `goalfy-app.json` 的 `executor` 与部署记录；旧路应用按原文传场景包 |
| `APP_VERSION_OUTDATED` | 页面版本落后，或执行属于旧版本（看 `details.reason`） | 页面让使用者刷新；旧版本的执行不能再回复，重新发起 |
| `EXECUTION_LIMIT_REACHED` | 运行中的执行已达上限 | 等已有执行结束，或取消不需要的再发起 |
| `EXECUTION_START_DISABLED` | 平台暂停了新路发起 | 不重试，告诉开发者；已有执行不受影响 |
| `EXECUTION_NOT_RETRYABLE` | 重试了不可重试的执行 | 看执行失败原因，修好后重新发起 |
| `EXECUTION_ALREADY_STARTED` | 同一提交号带了不同输入 | 换新的 `idempotency_key` / 提交号 |
| `EXECUTION_STATE_LIMIT` | 执行的状态记录超出上限 | 减少同一执行里的重试、修正次数，改成新开执行 |
| `BUSINESS_UI_NO_SCENARIO_PACK` | 应用版本既没挂场景包也没挂编排，上传或部署被拒 | 新路应用先用 `business_ui_manage(action="update")` 挂编排与 `tpe_ids` 再部署 |
| `WORKFLOW_INTERACTION_REJECTED` | 回复的表单已被处理、不可回答或执行已结束 | 重新 `status` 取当前待答表单 |

## 常见错误

- 给新路应用建了场景包，或在 `setup` 里传 `scenario_pack_id`。
- 只传改动的那条路线或漏了 `tpe_ids` 里的 TPE，覆盖或保存被拒（`references unmounted tpe_id`）。
- 新路编排沿用旧路的「交由 Agent 处理」审阅动作，保存被拒。
- 工具集挂在场景包或别处而不在节点 TPE 上，运行时报工具名无效（`invalid tool call name`）。
- 冒泡或真跑自己编 `business_id`，或用 `send` 跟执行对话。
- 修正路线不读 `ctx.previous_delivery`，从头重做。
- 中间文件写在固定路径，并行执行互相覆盖。

## 相关工具与契约主题

`business_ui_manage(action=create / update / setup / get / finalize)`、`scene_package_manage(action=assemble / bubble / cancel)`（传 `business_ui_id`）、`manage_goalfymax_project(action=run / status / wait / reply / stop)`（按 `business_id`）、`get_project_execution_logs(action="workflow_trace", business_id)`；契约主题 `otpe_multi`、`otpe_example_failure`。
