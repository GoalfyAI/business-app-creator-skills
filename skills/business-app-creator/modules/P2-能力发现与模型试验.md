## 1. 参考项目三层深读要点

服务 G2 第 2.1 节第一来源。三层各看什么、能证明什么，逐层对照，缺一层就不算完成。

| 层 | 用什么 | 看什么 | 能证明 | 不能证明 |
|---|---|---|---|---|
| 概览 | `get_project_execution_logs(summary)` | 总轮次、最终用户请求序列、执行阶段、Agent 与工具分布、等待与失败概况 | 全局视图、需要深挖的轮次 | 任何结论 |
| 深读 | `get_project_execution_logs(detail)`，按 `log_type` 分页读完 | 最终用户原始意图与约束、规划逻辑与步骤拆分、工具调用密集阶段的调用链与参数传递、任务点与 FastAgent 输入输出质量、失败重试、等待原因、最终交付是否匹配 | 实际发生了什么 | 为什么发生 |
| 分析 | 写入工单 | 轮次分类统计：有效推进、重复沟通、失败重试、等待；瓶颈定位与根因：缺知识、缺工具、缺指引、缺前置检查、资产边界错误；真实调用链；Skill 使用情况 | 可复核的结论 | 其他项目也如此 |

## 2. 复用与摸底工具、覆盖矩阵六态

服务 G2 第 2.1 节第二、第三来源。三个只读工具各有用途与限制；矩阵每行必须落六态之一。

| 工具 | 用途 | 限制 |
|---|---|---|
| `list_assets` | 按类型搜索可复用资产 | 关键词只匹配名称和 ID，建议用英文短词；不传关键词返回全量，注意上下文开销；结果不是完整契约 |
| `get_asset` | 批量反读完整配置、关系、Schema、状态，一次 1 至 20 个 | 只返回该资产自身，不展开子资产，诊断时逐级下钻；`can_view_params=false` 时配置为空是脱敏，不是空资产 |
| `dataset_read` | 只读查看长期数据集的描述、使用指南、Skill 文件、表、列、行 | 读不到业务应用数据集 |
| `get_scene_package_lineage` | 看一个能力容器的来源与派生 | 用于判断走派生还是新建 |
| `get_diagnosis_doc(scene_package)` | 读当前能力容器契约 | 需要 `task_id` |

| 六态 | 含义 |
|---|---|
| 已覆盖 | 现有资产直接满足，反读过 Schema 与真实配置 |
| 可组合覆盖 | 多个现有资产组合能满足，组合方式已写明 |
| 需维护 | 现有资产能用但要改提示词、指南或配置 |
| 真实缺口 | 平台内外都没有，进第 3 节四层处理 |
| 受限能力 | 有资产但权限受限或脱敏，需要开发者确认后 `allow_restricted=true` |
| 待验证 | 有候选但没有真实证据，进试验问题清单 |

两类不要误认的资产：目录里名为"××档案场景包""业务档案助手"的官方包属于业务档案产品线，不是业务应用数据集的来源，不拿来"留存用户数据"；`business_app_dataset` 工具集只在规划配套业务应用时才挂，计划书第 ⑥ 章形态为"直接使用能力容器"的不挂它。

## 3. 能力来源五层、执行者判据、外部候选四维度、开发需求说明格式

服务 G2 第 2.2 节。先按执行者判据决定这一步要不要模型，再按五层顺序找来源；外部候选逐维度打勾，任一维度否决即出结论；转开发需求照格式写。

**执行者判据。** 把模型拿掉，用规则、代码或工具能不能把这一步做对。

| 情形 | 执行者 |
|---|---|
| 数据获取、接口调用、文件读写、格式转换、计算、校验、按字段选路、查表 | 工具或脚本代码，不用模型 |
| 裸跑里模型每次结果完全一致且全部通过 | 伪装成判断的规则，写成代码 |
| 语义理解、内容生成、没有确定规则可写的判断 | 模型；一个业务环节一个 FastAgent，挂上所需工具 |
| 需要看结果再决定下一步查什么、读什么、改什么 | FastAgent 内部，工具挂给它 |
| 需要与最终用户自然语言往返 | 普通任务点 |

| 层 | 适用条件 | 做法 |
|---|---|---|
| 1 已有资产 | 官方内置底座工具组、已上线工具集、FastAgent、能力容器能覆盖 | `list_assets` 找，`get_asset` 逐级反读，`get_scene_package_lineage` 看派生；能派生不从零建 |
| 2 外部探索 | 已有资产没有，外部有现成 MCP 服务、Skill 包或可封装的库 | GitHub、npm、PyPI、MCP 官方索引、开发者私有仓库；四维度评估；先本地验证再注册；注册前 `list_assets` 查重 |
| 3 自建工具 | 外部没有现成的，但能力是确定性的 | 把 API 或库封成 MCP 工具组，或写进编排型 TPE 脚本的代码步；不用模型 |
| 4 形成开发需求 | 需要平台或团队开发 | 写可直接转交的需求说明 |
| 5 确认后降级 | 前四层都不成立 | 写明未覆盖阶段、对结果的影响、补齐条件、受影响验证，取得确认 |

| 维度 | 为什么要看 |
|---|---|
| 是否仍在维护 | 长期不更新的服务上线后容易失效 |
| 连接方式 | 决定注册时传地址还是启动命令，以及运行环境要装什么 |
| 认证方式 | 全容器共用一份凭证，还是每个最终用户各自授权；后者**必须**配授权卡 |
| 有无破坏性操作 | 决定哪些工具可以取样、哪些**禁止**取样，以及使用指南里要不要加约束 |

**开发需求说明格式**：业务动作；目标系统；必需输入与输出；授权方式；最终用户与项目隔离要求；副作用；失败语义；验收样例。写成开发者能一键转发给工程师的格式。

## 4. 能力形态判定、接入工具与前置依赖、授权卡

服务 G2 第 2.3 节第 1 至 3 步。先按形态表分三类决定试用路径；接入时每个工具都有前置条件，漏了就失败；需要最终用户各自授权的能力必须配卡。

| 形态 | 试用路径 |
|---|---|
| 现成 MCP 服务 | 本地验证、平台接入、取样、试跑 |
| 标准 Skill 包 | 同上，接入用 `import_skill_package` |
| CLI 工具、代码库、普通应用 | 需要先包装成可注册的包。默认只评估包装成本并出结论；开发者明确要求时才包装 |

| 工具 | 用途 | 前置 |
|---|---|---|
| `preview_tool_group` | 预览一个新的 MCP 连接，验证可用性并发现工具 | 注册前**必须**先做 |
| `register_and_refresh_tool_group` | 注册新工具组，或刷新已有工具组的工具列表 | 先 `preview_tool_group`；预览时用过的前置安装步骤，注册时**必须**一并带上；先 `list_assets` 确认无重复注册 |
| `upload_and_register_tool_group` | 上传开发者的私有包并注册 | 先 `file_to_url(purpose="mcp_package")` 取得文件引用 |
| `import_skill_package` | 导入标准 Skill 包，自动创建离线工具集 | 先 `file_to_url(purpose="skill_package")` |
| `create_toolset` | 创建工具集 | 成员工具组或 FastAgent 已存在 |
| `online_toolsets` | 工具集上线 | 安全的运行时测试全部无失败 |
| `otpe_tool_test` | 对已有 MCP 工具做一次真实调用取样 | 已知目标工具组与工具标识；需要文件时先 `file_to_url(purpose="tool_test_fixture")`，再同时提供 `workspace_files` 与 `workspace_bindings`，不传 `project_id` |
| `scene_package_manage(create)` | 建试用包草稿，默认克隆官方基础包 | 立即反读继承 |
| `manage_goalfymax_project(run)` | 草稿态试跑 | 试验授权已取得；`task` 用自然业务需求 |
| `delete_asset` | 作废试用包草稿 | 开发者确认并告知名称 |
| `get_project_execution_logs(action="workflow_trace")` | 真跑项目的步级轨迹：业务、Runtime、节点、运行、步骤五层，每步 `step_key`、`kind`、`status`、`tokens`、`elapsed_ms`、`error`、`repeated_error_count`、`arguments`，节点有 `queue_ms`、`execution_ms`、`postprocess_ms` 与 `retry_count` | 项目已有编排型 TPE 运行；需要 `task_id` |

| 授权卡工具 | 用途 |
|---|---|
| `create_auth_card` | 为工具组创建授权卡，参数用工具组注册返回的授权绑定标识，**不是**工具组标识 |
| `update_auth_card` | 更新已绑定的授权卡配置 |
| `link_auth_card` | 用授权卡标识关联到已有卡片，共用其授权配置 |

**禁止**把任何个人令牌写入 Skill 文本、脚本或工单。完整的注册流程、调试循环、私有包处理、上线检查见 `references/依赖与MCP接入.md`。

## 5. 复用工具契约看什么

服务 G2 第 2.3 节第 4 步。脚本要直接调用的已有工具，写第一行调用前先读它的实时契约，逐行核下表；拿不准的再取样。读契约与取样都记为该工具的输入约定，G3 写进执行结构表。

| 看什么 | 例子 |
|---|---|
| 文件或路径类参数收什么 | `file_to_url` 换出的 HTTPS URL、`/workspace` 绝对路径、还是文件内容本体；能不能收目录 |
| 必填与互斥 | 哪些必填；哪几个参数二选一 |
| 值域与格式 | 枚举、日期格式、语言码、编码、最大条数或字节数 |
| 返回结构是否声明 | 声明了就据此写 `_output`；没声明或含嵌套数组的，取样定 |
| 副作用与授权 | 是否只读；要不要授权卡 |

取样的两个目的：输入按约定给能不能被接受；真实返回的嵌套形状。可以同时提交一个候选的输出结构让样本顺带校验。工具组刷新或换版本后输入约定可能变，对应条目回 `pending`，按上面两步再过一次。冒泡报"参数格式不对""路径不存在"多半是这一步省掉了。

真实教训：某个外部 MCP 工具的文件参数只接受 `file_to_url` 换出来的 URL，不接受 workspace 路径；没读描述就照别的工具的写法写了脚本，冒泡才发现，改脚本、改上游文件准备、重跑一轮。

## 6. 试验报告八项

服务 G2 第 2.7 节。报告结论先行，八项固定，每项标能证明什么、不能证明什么。

| 项 | 写什么 |
|---|---|
| 结论 | 可行、不可行、需要包装后再评估 |
| 能力形态与接入方式 | 形态判定；注册结果，或包装成本预估与路径 |
| 验证证据 | 本地验证结果；工具清单与真实返回结构要点；逐任务试跑记录 |
| 质量印象 | 结果能不能用、稳定性、与预期的差距 |
| 成本 | 接入耗时、试跑积分、适用时的包装预估 |
| 风险 | 维护状态、认证模式、破坏性边界、许可证 |
| 正式化范围 | 值得时：哪些能力值得进正式资产、适合什么业务场景 |
| 盲区 | 没试到什么；哪些结论是从有限任务外推的；**禁止**夸大覆盖面 |

试用产出在正式流程里的复用：已注册的工具组与工具集在 G4 依赖准备直接引用；工具真实返回结构是 G4 取样要拿的东西；试跑记录是 G1、G3 的参考素材；正式化范围建议是 G3 路线设计的输入。

## 7. 文件与创作型长文本准备

服务 G2 第 2.3 节的取样文件，以及 G4 第 2.4、2.5 节的 Skill 文件、Logo、长脚本、长提示词。先判断提交内容属于哪一类，两类生命周期不同，**禁止**混用。

| 类型 | 典型内容 | 提交方式 | 平台保存结果 |
|---|---|---|---|
| 资产文件 | Skill 文件、辅助脚本、模板、样例、私有包、Logo、工具取样文件 | `file_to_url` 换取文件引用，再把引用绑定到资产或验证项目 | 文件作为独立资产或附件保留 |
| 创作型文本 | 编排型 TPE 脚本、`apc_skill`、业务路线 JSON、FastAgent 提示词、工具集使用指南、普通任务点提示词 | 短内容直接传原文本字段；长内容在实时 Schema 暴露对应 `*_url` 后传服务端可访问的 HTTPS 文本地址 | 服务端只读取一次正文，再按原文本字段的校验、确认、保存链路处理；URL 本身不保存 |

创作型文本 URL 的规则：原文本字段与对应 `*_url` **二选一**；URL 必须是服务端可访问的 HTTPS 地址，不得指向内网、客户端本地路径或需要登录的页面；外部 Agent 的本地 `/workspace` **禁止**作为 `script_file` 传入；提交成功后**必须**反读最终正文确认保存的是解析后的内容；URL、临时上传地址、带签名的查询参数**禁止**写入工单。

**`file_to_url` 的五种用途**：

| 用途 | 用于 |
|---|---|
| `skill_file` | Skill 文件、辅助脚本、模板、样例 |
| `skill_package` | 要导入成工具集的标准 Skill 包 |
| `mcp_package` | 要注册成工具组的私有 MCP 包 |
| `scene_package_logo` | 能力容器 Logo 图片 |
| `tool_test_fixture` | 真实工具取样或冒泡时需要落入隐藏 `/workspace` 的本地测试文件 |

**四个 action**，本地新文件只能三跳：

| action | 说明 |
|---|---|
| `prepare` | 申请上传地址，**必须**传真实字节数 |
| `complete` | 确认上传，换回文件引用；凭据**必须**来自同一工单、同一用途的 `prepare` |
| `from_url` | 已有可信 HTTPS 地址时直接导入；**仅支持** `skill_file`，地址不得指向内网 |
| `export` | 按资产 ID 把编排型 TPE 脚本或 FastAgent 提示词导出成可下载文件 |

**不接收文件内容本体**：没有任何参数能把文件正文或 base64 正文直接传给工具，本地新文件只能 `prepare` 拿地址、客户端 PUT、`complete` 换引用。`prepare` 里唯一的 base64 是 `content_md5`，它是对原始字节算的 16 字节 MD5 的标准 Base64 编码，不是文件。

**绑定到资产**：资产还没创建，在创建调用里直接带文件引用；资产已存在，用 `upload_skill_files` 补挂；能力容器的场景 Skill 文件用 `scene_package_manage(update)` 带引用；Logo 用 `update_scenario_package_logo`。缺省相反要记住：`scene_package_manage(update)` 缺省 merge，保留既有文件；`upload_skill_files` 缺省 replace，省略参数会覆盖整个 Skill 目录，补挂单个文件时显式传 `skill_files_mode="merge"`，定点删除用 `remove_skill_paths`。

**同名不同物**：制作期的 External MCP 工具 `file_to_url` 与编排型 TPE 脚本运行期的沙箱工具 `file_to_url` 只是名字相同。

| | 制作期 External MCP `file_to_url` | 运行期沙箱 `file_to_url` |
|---|---|---|
| 在哪调 | 你在 MCP 里调 | 脚本里 `tool("file_to_url", ...)` |
| 入参 | `action`、`purpose`、上传凭据 | `file_paths`：`/workspace` 绝对路径列表；可选 `url_ttl`，8h、1d、3d、7d，默认 1d |
| 返回 | `data.file_ref` | `results[]`，每项 `{"workspace_path", "url", "error"?}`，另有 `url_validity` |

脚本侧三条：返回里的键是 `workspace_path` 不是 `file_path`；逐项检查 `url` 为 `null` 的失败项，不拿别的文件的 URL 顶上；URL 有时效，用完即弃，不落库不进交付。

## 8. 结果检查表条目字段与四来源

服务 G2 第 2.4 节。结果检查表在 G2 建，起点是计划书第 ⑤ 章的正反例；每一行是一个测试条目，本表定义每行要记什么、从哪来。

| 来源 | 内容 | 占比建议 |
|---|---|---|
| 黄金路径 | G1 的正例，业务最常见的输入 | 30% |
| 真实历史 | 参考项目的真实输入与当时的人工产出，人工产出直接当参考答案 | 30% |
| 扰动变体 | 对黄金路径做系统扰动：缺一个字段、多一个无关文件、输入含歧义、素材质量差、量翻十倍；由你生成，开发者只勾选 | 30% |
| 长尾与反例 | G1 的反例、路线之外用户会说的话、越界请求 | 10% |

| 字段 | 取值 |
|---|---|
| 编号、所属路线 | 定位 |
| 来源 | 黄金路径、真实历史、扰动变体、长尾与反例 |
| 输入 | 表单字段、文件、需要的数据集内容，要能重放 |
| 覆盖步骤 | 这条案例走到哪些业务步骤 |
| 判定方式 | 规则判、开发者判 |
| 参考 | 期望产出、判定标准或历史人工产出 |
| 风险等级 | 低、中、高，来自红线与交付角色 |
| 留给 G5 | 是否制作期不跑，只在 G5 回归时跑 |

原则：一个步骤的案例太少，就不能把它分给模型自主；分配时看最差的几次，不看平均。

## 9. 步级记录表

服务 G2 第 2.5 节问题四。每步一行记进工单。裸跑阶段从执行日志、工具取样返回和项目运行记录里抄；有了编排型 TPE 之后，冒泡终态的 `steps[]` 与真跑的 `workflow_trace` 直接给出每步字段，照抄即可。

| 字段 | 从哪拿 |
|---|---|
| 案例、步骤、第几次 | 你自己编号 |
| 执行者 | 工具、FastAgent 或直接模型；FastAgent 记所用模型 |
| 工具调用 | 每次调用的工具、是否成功、错误类型：裸跑从 `get_project_execution_logs(detail)` 或 `otpe_tool_test` 返回读；有脚本后从 `steps[]` 的 `status`、`error`、`repeated_error_count` 读 |
| 输出是否过 Schema | 对照声明检查 |
| 判定结果 | 规则判或开发者判的结论与理由 |
| 耗时 | 裸跑从执行日志读；有脚本后读 `steps[].elapsed_ms` 与节点三段耗时 |
| 费用 | 项目运行记录里的积分消耗，加外部工具供应商价格折算，标估算；`steps[].tokens` 目前多数为 0，不作依据 |
| 模型说缺什么、自述的假设 | 从日志读；提示词要求它列出 |
| 归因 | 第 11 节的结论 |

| 指标 | 怎么算 | 说明 |
|---|---|---|
| 成功率 | 技术成功：工具无错且输出过 Schema；业务成功：判定通过 | 两个都记 |
| 质量 | 判定结果；与真实历史人工产出对照的胜率 | 见第 10 节 |
| 耗时 | 看最慢的几次，拆模型时间与工具时间 | 不用平均 |
| 费用 | 每次成功交付的费用，失败重试计入 | 比每次运行的费用更有用 |
| 稳定性 | 同一案例同一步多次结果是否一致 | 不一致是"能做但没把握"的信号 |

三种工具调用失败分开记：没调，改工具描述；调错，改契约或加转换；调了但没用上，改提示词。

## 10. 判定方式与三个对照

服务 G2 第 2.5 节问题三。分工决策只认两种判定：规则判与开发者判。

| 判定 | 适用 | 做法 |
|---|---|---|
| 规则判 | 有确定答案的：Schema、文件是否存在、数量、字段范围、红线词、格式 | 写成检查项逐条对，G4 可以写进脚本 |
| 开发者判 | 文案、方案、选题这类没有唯一答案但有好坏的 | 对照 G1 正反例与历史人工产出成对比较，问"哪份更接近能采用的"；你先给判断和理由，开发者只改不一致的 |

三个对照同时看：和普通聊天直接做相比有没有更好，没有说明这一步做成能力没有价值；和真实历史人工产出相比能不能替代人；任何一次触红线一票否决，不进平均。

## 11. 差分归因

服务 G2 第 2.5 节问题五。同一步、同样输入，只改一个变量再跑一次；顺序固定权限、工具、信息、模型。工具步用 `otpe_tool_test` 重调，FastAgent 步改提示词或换模型后在试用包里重跑。

| 怀疑 | 改什么 | 结果翻了说明 | 前置判据，不用重跑就能定 |
|---|---|---|---|
| 权限 | 补授权卡、放开工具权限 | 权限问题 | 工具返回 401、403 或授权卡缺失 |
| 工具 | 换等价工具，或把工具返回换成人工构造的正确返回 | 工具问题 | 工具报错、超时、返回不符合声明的形状 |
| 信息 | 把模型说缺的信息补进输入 | 信息问题 | 模型明确说缺什么，或编造了输入里没有的事实 |
| 模型 | 换更强的模型跑同一步 | 模型能力问题 | 以上三条都排除后剩下的 |

失败原因分布决定修什么：权限占大头修前置检查与授权引导；工具占大头修契约、加转换、换工具；信息占大头把缺的信息变成入口表单字段或数据集列；模型占大头换更强的模型，还不行退回人。

## 12. 能力地图格式

服务 G2 第 2.5 节落点与第 2.6 节输入。每条路线一张表，一行一个业务步骤。

| 列 | 内容 |
|---|---|
| 步骤 | 业务步骤，用画像的词 |
| 案例数与运行次数 | 太少标出 |
| 成功率 | 技术成功、业务成功各一列 |
| 稳定性 | 多次结果是否一致 |
| 最慢耗时 | 拆模型时间与工具时间 |
| 每次成功费用 | 含失败重试 |
| 判定方式 | 规则判、开发者判 |
| 失败原因分布 | 权限、工具、信息、模型各占比 |
| 风险等级 | 低、中、高，来自计划书 ③⑦ 章 |

绿黄红：绿是通过率高且稳定，黄是通过率中等、不稳定或案例太少，红是通过率低。开发者只需要决定黄的。

## 13. 分工矩阵与规则判据

服务 G2 第 2.6 节问题一。先用规则判据排除不该用模型的步骤，剩下的按两轴分档。

**规则判据**：输出能从输入用确定逻辑算出来，校验、格式化、按字段选路、阈值判断、查表；或者裸跑里模型在这一步每次结果完全一致且全部通过。后一种是伪装成判断的规则，写成代码。

| | 低风险，可逆、内部中间产物 | 中风险，面向用户、可改 | 高风险，对外发布、资金、删数据、触红线域 |
|---|---|---|---|
| 通过率高且稳定 | 模型自主 | 模型自主，抽样复核 | 模型加确认 |
| 通过率中等，或不稳定 | 模型自主加自动重试 | 模型加确认，只在没把握时 | 模型加确认，每次 |
| 通过率低 | 模型备料加人做 | 人做 | 人做 |
| 案例太少 | 模型加确认 | 模型加确认 | 人做 |

"高、中等、低"的界线按业务定，开发者确认；高风险一列不随通过率上升而放松。

| 执行者 | 脚本里是什么，G4 落实 |
|---|---|
| 规则 | 普通代码 |
| 模型自主 | `tool()` 或 FastAgent 调用，带自动重试与规则检查 |
| 模型加确认 | FastAgent 产出候选，中途表单让用户过目、选或改，继续 |
| 人 | 中途表单：表单说明写清要做什么、模型做到哪、为什么没把握、建议选项；表单字段收人做完的结果 |

## 14. 确认形式与没把握的旁证

服务 G2 第 2.6 节问题二。只在这一次没把握时才确认。

| 旁证 | 怎么取 | 成本 |
|---|---|---|
| 规则旁证 | 输出触发软规则：长度异常、引用了输入里没有的事实、数值超出历史范围；脚本里写成检查 | 零 |
| 模型自报 | 提示词要求列出假设与不确定项，非空即没把握 | 零；模型自报偏乐观，配合规则旁证用 |

| 确认形式 | 做法 | 用法 |
|---|---|---|
| 过目 | 中途表单展示结果，用户不改就继续 | 默认 |
| 选择 | 模型给 2 到 3 个候选，用户点一个 | 默认 |
| 修改 | 用户改字段 | 少用，成本最高 |

人的确认时间要折算进费用，否则"全退回人工"永远最便宜。

## 15. 回退链触发表

服务 G2 第 2.6 节问题四。每步一条回退链，G4 写成脚本分支；每步定重试次数上限。

| 触发 | 动作 | 说明 |
|---|---|---|
| 工具报错，错误类属于权限 | 直接转人，授权引导 | 重试无意义 |
| 工具报错，错误类属于工具 | 重试一次，换等价工具，转人 | 记录工具失败率 |
| 输出未过 Schema 或规则判定 | 同模型重试一次，换更强的模型 | 多数形状错误强模型能修 |
| 结果不稳定或未过业务判定 | 换更强的模型，转模型加确认 | 不确定不等于错，先升级再问人 |
| 模型提出缺信息 | 不升级模型，直接问用户或查数据集 | 信息问题升级模型没用 |
| 重试次数到上限 | 转模型加确认或人 | 防止无限重试 |
| 触红线 | 停，转人 | 一票否决 |

升级模型只是换 FastAgent 或编排型 TPE 的 `model_selection_mode` 与允许模型清单里的配置值，不用改资产。退回人要带齐材料：这步要做什么、模型已做到哪、为什么没把握、建议的选项。

## 16. 分工建议表格式与泳道图

服务 G2 第 2.6 节落点与第 3 节展示。三样东西的关系：**能力地图是事实**，收敛一测出来的每步数字；**分工建议表是决定**，收敛二按分工矩阵从能力地图推出来的每步执行者；**泳道图是分工建议表的图形版**，给开发者看的。三者行数相同，一行一个业务步骤。

**分工建议表**，每步一行：

| 列 | 内容 | 来自 |
|---|---|---|
| 步骤 | 业务步骤，用画像的词，与能力地图同名 | 计划书 ④ |
| 建议执行者 | 规则、模型自主、模型加确认、人，四选一 | 第 13 节分工矩阵 |
| 依据 | 能力地图该行的成功率、稳定性、案例数，一句话 | 第 12 节 |
| 风险等级 | 低、中、高 | 计划书 ③⑦ |
| 错了怎样 | 影响、可逆性、发现时机，一句话 | G1 收敛二问题三 |
| 确认形式与触发 | 模型加确认才填：过目、选择、修改之一；触发是每次，还是规则旁证或模型自报 | 第 14 节 |
| 回退链 | 按触发写的动作序列，最后一档必须是人 | 第 15 节 |
| 重试上限 | 次数 | 第 15 节 |
| 判定方式 | 规则判、开发者判 | 第 10 节 |
| 颜色 | 绿、黄、红，与能力地图同 | 第 12 节 |
| 开发者决定 | 待定、已确认、改为某执行者；黄的必须有值 | 第 3 节展示后填 |

**泳道图**：横向是业务步骤，按运行顺序从左到右；纵向四条泳道，从上到下是规则、模型自主、模型加确认、人。每个步骤是一张卡片，放在建议执行者所在的泳道；卡片上只写四样：步骤名、颜色、成功率、错了怎样。黄卡加"待定"标记，开发者只看黄卡。**禁止**在卡片上写工具名、节点标识、字段名。

输出形式：给开发者看用 Mermaid 流程图，四个 `subgraph` 当泳道，卡片按步骤顺序连线；写进工单 `capability_map` 时用上面的表，不存图。示例：

```mermaid
flowchart LR
  subgraph 规则
    s1[读取门店档案<br/>绿 100%<br/>错了：数据为空，重跑]
  end
  subgraph 模型自主
    s2[提炼本周热点<br/>绿 96%<br/>错了：选题偏，可改]
  end
  subgraph 模型加确认
    s3[生成图文<br/>黄 82% 待定<br/>错了：事实有误，返工]
  end
  subgraph 人
    s4[发布到账号<br/>高风险<br/>错了：不可撤回]
  end
  s1 --> s2 --> s3 --> s4
```
