# P2 能力发现、工具接入与模型试验

> 细则正本。阶段文件 G1–G7 是唯一主线；本文只放 G 文件写不下的表格、契约、纪律清单与示例，在 G 文件点名时查阅。本文不含流程，不含进入与出口条件。

服务 G2 关键能力可行性、G4 依赖准备。内容：参考项目三层深读、复用已有能力容器与官方基础包、能力摸底与覆盖矩阵、工具缺口四层处理、实现思路调研；能力试用的完整流程；MCP 接入与依赖制作、复用工具先读契约再真实取样、文件与创作型长文本准备。G2 把试用与取样前移到正式制作之前，试验授权与制作授权分开。

## 1. 复用：项目、场景包与资产摸底

拿着已确认的计划书（`build_book`，S1）开始资产设计。先复用、再摸底、最后才谈缺口——三个来源按此顺序看：参考项目（真实执行记录，可信度最高）、已有场景包与官方基础包（能派生就不从零建）、平台能力（工具组 / 工具集 / FastAgent / 数据集）。

### 1.1 参考项目三层深读

开发者提供了参考项目时**必须**完成三层，**禁止**只看摘要下结论（约束 3）。

**第一层 概览**：读项目摘要，统计总轮次、最终用户请求序列、执行阶段、Agent 与工具分布、等待与失败概况。摘要是压缩后的统计信息，**只能**用于建立全局视图和定位需要深挖的轮次，**不能**作为结论。

**第二层 深读**：读取完整原始日志的全部分页，截断时**必须**续读到结束。重点看：最终用户原始意图与约束、规划逻辑与步骤拆分、工具调用密集的阶段（调用链、参数传递、前后依赖）、任务点与 FastAgent 的输入输出质量、失败重试、等待原因、最终交付是否匹配预期。

**第三层 分析**：形成以下可复核结论并写入工单：

- **轮次分类统计**：总轮次、有效推进、重复沟通、失败重试、等待
- **瓶颈定位**：消耗最多轮次的阶段，根因归类为缺知识、缺工具、缺指引、缺前置检查或资产边界错误
- **真实调用链提取**：每个业务阶段实际调了什么、顺序如何、有没有前置依赖但 Agent 不知道
- **Skill 使用情况**：哪些文件被读取、哪些应该被引导读取但没有

多个项目对比时，**必须**逐项目保留独立事实，再提炼共性，**禁止**用平均值掩盖异常。

**完成标准**：三层全部完成并写入工单后才能进入下一步。**禁止**只看摘要就跳过深读——这是本节最容易出现的问题。

### 1.2 复用已有场景包与官方基础包

你**必须**主动获取的：

- 用 `get_asset` 查看**官方基础场景包**的完整配置，理解其预加载与动态工具集的组合方式，作为选型基准
- 用 `list_assets` 加 `get_asset` 查找可参考的已有场景包；开发者要"基于某个已上线包做一个变体"时，用 `get_scene_package_lineage` 看它的来源与派生包，再评估是走**派生**（`create_derived_scene_package`，见总入口 §7.1）还是新建
- 用 `get_diagnosis_doc(scene_package)` 读当前场景包契约

复用的判据是**计划书**：候选场景包 / 派生来源覆盖了计划书 ②③ 章里的哪些路线与交付、用词与画像是否一致、缺什么。能派生就不从零建（组合 / 继承 / 派生的边界见 [平台对象与运行模型](../references/平台对象与运行模型.md) 第五章）。

### 1.3 能力摸底与覆盖矩阵

三个只读工具：

| 工具 | 用途 |
|---|---|
| `list_assets` | 按类型搜索可复用资产。关键词只匹配名称和 ID，建议用英文短词；不传关键词会返回全量，注意上下文开销 |
| `get_asset` | 批量反读完整配置、关系、Schema、状态，一次 1–20 个 |
| `dataset_read` | 只读查看长期数据集：描述、使用指南、Skill 文件、表、列、行 |

用 `list_assets` 和 `get_asset` 搜索并完整反读场景包、任务点、工具集、FastAgent、工具组、数据集；摸底的目标来自计划书第 ②③⑥ 章——每个里程碑、每条路线、每类产出各需要什么能力。看 Schema 和真实配置，**不要**只看描述。

搜索结果**不是**完整资产契约，选型前**必须**用 `get_asset` 下钻（约束 4）。重要选择结论用 `task_manager(insert)` 留痕。

一次 `get_asset` 只返回该资产自身的配置，**不会**展开它引用的子资产。诊断时**必须**按层逐级下钻。

场景涉及数据查询或报表时，用 `list_assets` 列出开发者有权访问的长期数据集，`get_asset` 或 `dataset_read` 确认表结构与权限范围。数据集**只能**绑定真实可访问的，**禁止**假设开发者拥有某个数据集。开发者没有对应数据集时明确告知需要先去准备。

两类不要误认的资产：目录里名为"××档案场景包""业务档案助手"的官方包是业务档案产品线（另一套数据面），不是业务应用数据集的来源，也不要为了"留存用户数据"去复用它们；`business_app_dataset` 工具集（业务应用数据集 FA 所在）只在场景包配套业务应用时才挂——计划书 ⑤ 写"不适用"的包不挂它。

按每个里程碑建立覆盖矩阵：**已覆盖 / 可组合覆盖 / 需维护 / 真实缺口 / 受限能力 / 验证方式**。

向开发者输出每个里程碑的覆盖情况，把缺口处理选项、影响和推荐纳入制作书第 ⑨ 章（7.2），由开发者确认；Agent 不得以“工具缺口不可阻塞”为由自行削减业务目标。

### 1.4 工具缺口四层处理

工具缺口**不可**阻塞创建流程，但**不得**静默削减开发者明确要求或参考项目中已有的能力（约束 12）。按以下优先级处理：

**第一层 Skill 弥补**（成本最低，优先尝试）：工具能力已覆盖，问题只是缺调用顺序、前置检查、字段准备或结果审视方法。把指导写进正确层级即可。

**第二层 接入现有能力**：先在平台上找，平台没有再去外部找。

平台内：用 `list_assets` 和 `get_asset` 确认是否已有可复用的工具组——重复注册同一个服务会产生互相冲突的资产。

平台没有时**从外部获取**。你运行在能联网、能读写本地文件、能执行命令的环境里，这是 Max 内部制作助手做不到的，**应当主动利用**：

| 目标 | 去哪找 |
|---|---|
| 现成 MCP 服务 | MCP 官方索引、代码托管平台、包管理平台（npm / PyPI），以及开发者自己的私有仓库 |
| 现成 Skill 包 | 同上；开发者手里可能已有内部沉淀的包 |

找到候选后**先在本地验证，再走平台注册**。顺序反了会浪费大量试错：本地能起来、工具清单和返回结构都确认过，注册基本一次通过；直接注册再排错，每轮都要等平台反馈。

评估候选时**必须**看清四件事：

| 维度 | 为什么要看 |
|---|---|
| 是否仍在维护 | 长期不更新的服务上线后容易失效 |
| 连接方式 | 决定注册时传地址还是启动命令，以及运行环境要装什么 |
| 认证方式 | 全场景包共用一份凭证，还是每个终端用户各自授权——后者**必须**配授权卡 |
| 有无破坏性操作 | 决定哪些工具可以取样、哪些**禁止**取样，以及要不要在使用指南里加约束 |

开发者提供本地包或压缩包时，走 `file_to_url` 换取引用后注册或导入（见 P2 第 10.3 节）。完整的注册流程、失败调试循环和上线检查见 [依赖与 MCP 接入](../references/依赖与MCP接入.md)。

**第三层 形成开发需求**（开发者有协作团队时）：为缺失能力生成可直接转交的需求说明，**必须**写明业务动作、目标系统、必需输入与输出、授权方式、最终用户与项目隔离要求、副作用、失败语义、验收样例。格式要便于开发者一键转发给工程师。

**第四层 开发者确认后降级**：用已有能力继续制作，**必须**明确说明未覆盖的阶段、对结果的影响、以后补齐的条件和受影响的验证，并取得开发者确认。

### 1.5 实现思路调研

**不知道某个效果如何实现时**（有目标、无做法）——**先询问开发者是否有参考资料或已知同类产品**；没有再去 GitHub 等开源平台自行调研同类实现。调研的是**实现思路**而非现成资产，产出可以是自建编排型 TPE / 工具的设计依据，或转交开发需求（第三层）的技术方案参考。结论与来源记入工单。

## 2. 进入前提与定位

快速验证一个外部能力（GitHub 仓库、MCP 服务、Skill 包）**值不值得做成正式场景包**。本节从总入口 4.1 独立进入，不属于创建主干；产出是**一份带证据的试用结论**，不是可交付的场景包。

进入前提：有 `write` 工单（试用会创建工具组、工具集与试用包草稿）；开发者已给出能力来源（仓库地址 / MCP 服务地址 / 包文件），以及（可选）想验证的具体问题。

**定位边界，先讲清楚再开始**：

- 试用包**永不上线**：不定稿、不交付给最终用户、不结正式交付单。它的生命周期终点是本节的试用结论。
- 试用结论为"值得"时，正式化**必须**新开工单走 S1 完整流程（见第 8 节的材料复用）；**禁止**把试用包就地转成正式包绕过质量门。
- 试用跳过的是业务设计与验收流程，**不跳过**：工单 Gate（约束 1）、本地验证先行、真跑授权（约束 6）、如实汇报（约束 10）。

## 3. 摸底定形态

完整读取能力来源的文档（README、使用说明；约束 3 同样适用），回答两件事：

**能力形态**：

| 形态 | 试用路径 |
|---|---|
| 现成 MCP 服务 | 直接走第 3–6 节 |
| 标准 Skill 包 | 直接走第 3–6 节（接入用 `import_skill_package`） |
| CLI 工具 / 代码库 / 普通应用 | **需要先包装成可注册的包才能进平台。** 默认只评估包装成本并直接进入第 7 节出结论（"需要包装，预估成本与路径"本身就是结论的一部分）；**仅当开发者明确要求时**才动手包装并继续试用 |

**评估四维度**（与 S2-2.4 同一套判据）：

| 维度 | 为什么要看 |
|---|---|
| 是否仍在维护 | 长期不更新的服务上线后容易失效 |
| 连接方式 | 决定注册时传地址还是启动命令，以及运行环境要装什么 |
| 认证方式 | 全场景包共用一份凭证，还是每个终端用户各自授权——后者**必须**配授权卡 |
| 有无破坏性操作 | 决定哪些工具可以取样、哪些**禁止**取样，以及试跑任务的安全边界 |

四维度中任一项已足以否决（如项目已停止维护、认证模式平台无法承载）时，**可以**直接进入第 7 节出"不值得"结论，不必走完后续步骤——试用通道的价值就是尽早给出答案。

## 4. 本地验证

**先在本地验证，再走平台注册**：起服务、装依赖，确认工具清单与真实返回结构。顺序反了会浪费大量试错：本地能起来、工具清单和返回结构都确认过，注册基本一次通过；直接注册再排错，每轮都要等平台反馈。

本地验证失败且排查后仍不可用时，直接进入第 7 节出结论，附失败证据。

## 5. 平台接入

按 P2 第 10.1 节的接入工具链执行：`preview_tool_group` → `register_and_refresh_tool_group`（或 `import_skill_package` / `upload_and_register_tool_group`）；预览时用过的前置安装步骤，注册时必须一并带上。需要终端用户各自授权的能力，试用期即须配授权卡（S3-1.3），否则试跑走不通。

注册前**必须**用 `list_assets` 确认平台上没有同一服务的既有工具组——重复注册同一个服务会产生互相冲突的资产（S2-2.4）。已有注册时直接复用，并在结论里注明。

## 6. 极简试用包

组一个**最小可跑**的试用包：

1. `scene_package_manage(create)` 建草稿（默认克隆官方基础包，立即反读继承）；
2. 新建工具集装入本次接入的工具组（或导入 Skill 包产生的工具集），关联到试用包；工具集须过安全测试并上线（S3-1.2 第一道检查同样适用——离线工具集运行时不加载）；
3. `apc_skill` 只写最小内容：这个能力是什么、什么时候用、调用时的关键注意点（认证、破坏性边界）。**不写**里程碑、候选路线、正反例；**不建**执行结构表与结果检查表；**不做**方案挑战。

试用包名称**必须**带明显的试用标识（如「试用」前缀），防止被误认为正式包。

## 7. 草稿态试跑

用开发者关心的 **1–3 个真实任务**在草稿态试跑（`manage_goalfymax_project`，真跑纪律与运行实例规则同 P6 第 3.2 节）：

- 试跑是真实运行：FastAgent 照常计费、外部副作用照常发生，**必须**先按约束 6 取得开发者授权；含破坏性工具的任务**禁止**作为试跑任务；
- 任务描述用自然业务需求，**禁止**指定工具名或调用顺序——试的就是"平台上的 Agent 能不能用好它"；
- 逐任务记录：任务、实际调用、结果质量、耗时与积分消耗、失败与原因。

## 8. 试用结论

出一份**结论先行**的试用报告，写入工单：

- **结论**：值得做成正式包 / 不值得 / 需要包装后再评估
- **能力形态与接入方式**：形态判定、注册结果（或包装成本预估与路径）
- **验证证据**：本地验证结果、工具清单与真实返回结构要点、逐任务试跑记录
- **质量印象**：结果能不能用、稳定性、与预期的差距
- **成本**：接入耗时、试跑积分消耗、（若适用）包装预估成本
- **风险**：维护状态、认证模式、破坏性边界、许可证
- **值得时**：建议的正式化范围（哪些能力值得进正式包、适合什么业务场景）
- **盲区**：没试到什么、哪些结论是从有限任务外推的（约束 10——**禁止**夸大试用覆盖面）

## 9. 收尾与正式化衔接

**收尾（出结论后立即执行）**：

- **试用包草稿作废**（`delete_asset`，删除前按约束 6 确认并告知名称）——防止试用包被当正式包使用；
- **工具组与工具集保留**：注册是重资产（重复注册冲突），转正式时直接复用；结论为"不值得"且开发者同意清理时才删除；
- 工单以试用结论作为最终记录，`task_manager(complete)` 收尾。

**正式化衔接（结论为"值得"、开发者决定做正式包时）**：新开 `write` 工单进入 S1，以下试用产出直接复用：

| 试用产出 | 在正式流程中的用途 |
|---|---|
| 已注册的工具组/工具集 | S2 依赖准备直接引用，免重复注册 |
| 工具真实返回结构 | S3-2.2 取样要拿的东西，试用已拿到 |
| 试跑记录 | S1-2.1 的参考素材（真实执行记录，可信度最高级） |
| 试用报告的正式化范围建议 | S1 里程碑与候选路线的输入 |

## 10. 工具通道与文件准备

按已确认的《制作书》（P3 第 5.2 节，`build_book`，`stage="S2"`）自底向上创建、挂载、验证全部资产。**制作期基本不再与开发者交流**：业务路线怎么画、FastAgent 挂什么工具、字段叫什么，都照书做；只有冲突才停下沟通。

### 10.1 MCP 接入与依赖制作

| 工具 | 用途 |
|---|---|
| `preview_tool_group` | 预览一个新的 MCP 连接，验证可用性并发现工具。注册前**必须**先做 |
| `register_and_refresh_tool_group` | 注册新工具组，或刷新已有工具组的工具列表 |
| `upload_and_register_tool_group` | 上传自有包并注册（开发者提供的私有包） |
| `import_skill_package` | 导入标准 Skill 包，自动创建离线工具集 |
| `create_fast_agent` | 创建 FastAgent；长提示词可在实时 Schema 支持时通过 `prompt_content_url` 提交 |
| `create_toolset` | 创建工具集；长使用指南可在实时 Schema 支持时通过 `tool_usage_guide_url` 提交 |
| `online_toolsets` | 工具集上线 |
| `create_tpe` | 创建普通任务点，**必须**先有工具集；长提示词模板可在实时 Schema 支持时通过 `prompt_template_url` 提交 |
| `otpe_tool_test` | 对已有 MCP 工具做一次**真实调用取样**，拿回真实返回结构；依赖 `/workspace` 时可把 `file_to_url` 上传的真实文件落入临时隐藏验证项目，调用结束后清理。不会修改场景包资产 |

前置依赖顺序（工具定义里看不到，但漏了就会失败）：

| 工具 | 前置 |
|---|---|
| `register_and_refresh_tool_group` | 先 `preview_tool_group`；**预览时用过的前置安装步骤，注册时必须一并带上** |
| `upload_and_register_tool_group`、`import_skill_package` | 先用 `file_to_url` 取得文件引用 |
| `create_toolset` | 成员工具组或 FastAgent 已存在 |
| `create_tpe` | 工具集已备好**并已上线** |
| `otpe_tool_test` | 已知目标工具组与工具标识；目标工具需要文件时，先用 `file_to_url(purpose="tool_test_fixture")` 上传，再同时提供 `workspace_files` 与 `workspace_bindings`，不要再传 `project_id` |
| 授权卡三件套 | 都要工具组注册返回的授权绑定标识（**不是**工具组标识） |

完整的注册流程、调试循环、私有包处理、授权卡配置和上线检查见 **[依赖与 MCP 接入](../references/依赖与MCP接入.md)**。

### 10.2 复用工具的接入建议：先读契约，再真实取样

脚本里要直接 `tool()` 调用的**已有工具**（平台工具组、别人注册的外部 MCP、复用包里带来的工具），建议在写第一行调用之前过两步。不是硬门，是省一轮返工的做法——真实教训：某个外部 MCP 工具的文件参数只接受 `file_to_url` 换出来的 URL，不接受 workspace 路径；没读它的描述就照别的工具的写法写了脚本，冒泡才发现，改脚本、改上游文件准备、重跑一轮。

**第一步 读实时契约**：`get_asset` 下钻到该工具所在的工具组，读它的描述与输入定义——不要只靠工具名、别的场景包里的用法或"一般都这样"去推。值得看清并记下的：

| 看什么 | 例子 |
|---|---|
| 文件 / 路径类参数收什么 | `file_to_url` 换出的 HTTPS URL、`/workspace` 绝对路径、还是文件内容本体；能不能收目录 |
| 必填与互斥 | 哪些必填；哪几个参数二选一 |
| 值域与格式 | 枚举、日期格式、语言码、编码、最大条数 / 字节数 |
| 返回结构是否声明 | 声明了就据此写 `_output`；没声明或含嵌套数组的，第二步取样定 |
| 副作用与授权 | 是否只读；要不要授权卡（1.3） |

这些记为该工具的**输入约定**，顺手写进执行结构表对应条目（4.4）——脚本里的准备步骤（先 `file_to_url` 还是先落 `/workspace`）按它来写，比按习惯写少踩坑。

**第二步 真实取样**：对拿不准的**安全只读**复用工具做一次 `otpe_tool_test`（返回结构没声明、文件参数形态不明、第一次用的外部 MCP，都算拿不准），输入用代表性的真实值（文件走 `tool_test_fixture`），一次验两件事——输入按约定给能不能被接受（格式对不对），以及真实返回的嵌套形状（光看描述推不出，猜错下游读不到字段）。可以同时提交一个候选的输出结构让样本顺带校验。取样过了再写脚本里的 `tool()` 与 `_output` 更稳；样本要点（不含 URL、凭证）记入工单与执行结构表。破坏性、发布、凭证、金融或不可逆的工具**不取样**——只读契约，并用演练标记挡住（4.3）。

**什么时候值得重做**：工具组刷新（`register_and_refresh_tool_group`）或换了工具版本后，输入约定可能变，对应条目指纹回退 `pending`，建议按上面两步再过一次。跳过这两步不违规，但冒泡报"参数格式不对""路径不存在"时，先回这里补。

工具只依赖已有业务项目上下文时传项目标识，这不会启动新项目。工具需要读取测试文件时，先用 `file_to_url(purpose="tool_test_fixture")` 把 Agent 本地文件换成临时文件引用；把返回的 `data.file_ref` 放进 `workspace_files`，再用 `workspace_bindings` 声明由哪个目标工具顶层参数接收该文件路径或父目录。服务端会复用冒泡验证的隐藏项目，从临时 HTTPS URL 下载真实文件、写入 `/workspace` 后调用工具，并在成功或失败后自动清理。此模式不要同时传 `project_id`。

**取样会真实调用供应商接口。** 破坏性、发布、凭证、金融或任何不可逆的工具**禁止**取样，只对**安全只读**的工具做。

### 10.3 文件与创作型长文本准备

先判断提交内容属于哪一类，二者的生命周期不同，**禁止**混用：

| 类型 | 典型内容 | 提交方式 | 平台保存结果 |
|---|---|---|---|
| 资产文件 | Skill 文件、辅助脚本、模板、样例、私有包、Logo、工具取样文件 | `file_to_url` 换取文件引用，再把引用绑定到资产或验证项目 | 文件作为独立资产或附件保留 |
| 创作型文本 | 编排型 TPE 脚本、`apc_skill`、业务路线 JSON、FastAgent 提示词、工具集使用指南、普通任务点提示词、待更新字段全文 | 短内容直接传原文本字段；长内容或需要反复维护时，在实时 Schema 暴露对应 `*_url` 后传服务端可访问的 HTTPS 文本地址 | 服务端只读取一次正文，再按原文本字段的校验、确认、保存和上线链路处理；URL 本身不绑定为资产文件，也不作为配置保存 |

创作型文本 URL 只是一种**输入传输方式**，不产生新的资产类型。使用时遵守以下规则：

- 原文本字段与对应 `*_url` **二选一**；编排型 TPE 的局部补丁还要遵守实时 Schema 中与完整脚本来源的互斥关系
- URL 必须是服务端可访问的 HTTPS 文本地址，不得指向内网、客户端本地路径或需要浏览器登录的页面；编码、大小、重定向和地址安全限制以实时 Schema 为准
- 外部 Agent 的本地 `/workspace` 不属于 Max 沙箱，**禁止**作为 `script_file` 传入；内部 Max Agent 只有在实时 Schema 暴露 `script_file` 时才可使用
- 提交成功后**必须**反读最终正文、JSON 对象或脚本摘要，确认平台保存的是解析后的内容而不是 URL；下载、解析或校验失败时停止提交，禁止截断正文后伪装成功
- URL、临时上传地址和带签名的查询参数**禁止**写入工单；工单只记录目标资产、内容用途和反读结论

#### 资产文件：第一步换取文件引用

`file_to_url` 是唯一的文件通道，**必须**声明用途，服务端按用途决定大小、类型和存储规则：

| 用途 | 用于 |
|---|---|
| `skill_file` | Skill 文件、辅助脚本、模板、样例 |
| `skill_package` | 要导入成工具集的标准 Skill 包 |
| `mcp_package` | 要注册成工具组的私有 MCP 包 |
| `scene_package_logo` | 场景包 Logo 图片 |
| `tool_test_fixture` | 真实工具取样时需要落入隐藏 `/workspace` 的本地测试文件 |

四个 action（本地新文件没有直传内容的路径，只能 `prepare` → 客户端 PUT → `complete` 三跳）：

| action | 说明 |
|---|---|
| `prepare` | 申请上传地址，**必须**传真实字节数 |
| `complete` | 确认上传，换回文件引用。传入的凭据**必须**来自同一工单、同一用途的 `prepare` |
| `from_url` | 已有可信 HTTPS 地址时跳过上传直接导入。**仅支持** `skill_file`，且地址**必须**服务端可访问、**不得**指向内网 |
| `export` | 按明确资产 ID 把编排型 TPE 脚本或 FastAgent 提示词导出成可下载文件（用途 `asset_text`） |

**不接收** base64。临时上传地址**禁止**写入工单。

#### 资产文件：第二步绑定到资产

| 情况 | 做法 |
|---|---|
| 资产还没创建 | 在创建调用里直接带上文件引用 |
| 资产已存在 | 用 `upload_skill_files` 补挂，需要指定资产类型和标识 |
| 场景包的场景 Skill 文件 | 用 `scene_package_manage(update)` 带文件引用 |
| 场景包 Logo | 用 `update_scenario_package_logo` 带文件引用 |

`upload_skill_files` 和场景包更新都支持合并（merge）与整体替换（replace），但**缺省相反**：场景包更新（`scene_package_manage(update)`）缺省 merge，保留既有文件；***`upload_skill_files` 缺省 replace，省略参数会覆盖整个 Skill 目录***——补挂单个文件时显式传 `skill_files_mode="merge"`（支持 scenario_package / toolset / fast_agent），定点删除用 `remove_skill_paths`。

#### 同名不同物：脚本里的 `file_to_url` 是另一个工具

上面说的 `file_to_url` 是**制作期的 External MCP 工具**（`prepare → PUT → complete`，换回 `data.file_ref`，用来把文件交给平台绑到资产或验证项目）。**编排型 TPE 脚本运行期**还有一个同名的**沙箱工具** `file_to_url`（运行时默认能力，reference 2.1），用途完全不同：把 `/workspace` 里的文件换成限时 HTTPS URL，交给只收 URL 的外部工具（生图、识图、第三方 MCP）。两者只是名字相同，入参与返回都不一样：

| | 制作期 External MCP `file_to_url` | 运行期沙箱 `file_to_url` |
|---|---|---|
| 在哪调 | 你（制作 Agent）在 MCP 里调 | 编排型 TPE 脚本里 `tool("file_to_url", ...)` |
| 入参 | `action` / `purpose` / 上传凭据 | `file_paths`：`/workspace` 绝对路径**列表**；可选 `url_ttl`（8h / 1d / 3d / 7d，默认 1d） |
| 返回 | `data.file_ref`（`file_key` 等） | `results[]`，每项 `{"workspace_path": <你传的路径>, "url": <限时 URL 或 null>, "error"?}`；另有 `url_validity` |

写脚本时的三条：**返回里的键是 `workspace_path`，不是 `file_path`**——按它建"路径 → URL"映射，写成 `file_path` 取到的全是空；逐项检查 `url` 为 `null` 的失败项，不要拿上一轮或别的文件的 URL 顶上；URL 有时效，用完即弃，不落库不进交付。这个坑靠读描述发现不了——按 2.2 取样一次，`_output` 照真实返回写。
