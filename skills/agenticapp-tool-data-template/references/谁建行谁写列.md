# 谁建行、谁写列

② 定施工单里每条路线怎么写库、③ 写路线和后端的写库部分前读。SQL 怎么经 `db()` 执行、占位符和连接纪律见 `agenticapp-tool-workflow`「读写应用库」，这里只定谁写哪一行、哪一列。

## 身份列与审计列

- **身份列由建行的一方填**：主键、父记录外键、项目与业务关联 id、`version_no`、`created_at`。建行时还不知道的值（如发起后才生成的 Runtime id）不设成建行必填，运行关联落在 `last_run_id`。
- **审计列由这次写入的一方随写入更新**：
  - 路线更新 agent 列：同一条 SQL 带上 `updated_by='agent'`、`last_run_id`、`updated_at=now()`、`row_version=row_version+1`；
  - 路线建行：带上 `updated_by='agent'`、`last_run_id`，其余审计列取模板默认值；
  - `last_run_id` 取 `ctx.run_id`（本次运行编号，形如 `WFR-…`），用 `params` 传进 SQL；
  - `INSERT … ON CONFLICT … DO UPDATE` 同样带上 `row_version = <表>.row_version + 1`、`updated_at = now()`。
- 路线只写 agent 列，不写 user 列。

## 谁建行：两种情形选一种

按路线有没有应用后端参与：

| 情形 | 谁建行 | 路线怎么写 |
|---|---|---|
| 有应用后端参与（使用者在页面上发起，后端先建好记录） | 应用后端建行并填身份列；个数在运行中才确定的新行，脚本按 `output_schema` 返回产出，由后端的生产回流接口建行 | 只更新已建行的 agent 列：按入口带入的 id 执行 `UPDATE … WHERE id = :id`，改到的行数不是 1 就返回 `blocked`「未入库」；不写身份列 |
| 路线自给（到点或数据变化自动发起、没有后端参与的同步类路线） | 路线自己建：前置记录由第一个节点建，运行中产生的失败记录、水位、修订等也由写它的节点建 | 只写本路线负责的行，身份列与 `last_run_id` 一并填上；不依赖后端回流 |

没有后端回流的路线（例如自动化路线）只把结果返回、指望应用后端去写，永远进不了库：说好「脚本按唯一键写库」就要脚本自己写。

## 同一业务再做一次：更新还是新增

在 ② 施工单里定，决定写法：

- **更新原记录**：
  - 路线自己建的行：`INSERT … ON CONFLICT (<业务键>) DO UPDATE`，业务键在模板里有唯一约束，同一业务键重复触发命中同一行；
  - 后端已建的行：上表的 `UPDATE … WHERE id`；
  - 后端建行时同样按业务键先查后建（`INSERT … ON CONFLICT (<业务键>) DO UPDATE … RETURNING id`），同一业务拿到的总是同一行 id，再把这个 id 作为业务键带进入口。
- **每次都留一条**（巡检历史、操作日志）：直接 `INSERT` 并写 `last_run_id`，不建这条唯一约束。

## 写失败

写失败一律返回 `blocked`「未入库」，不吞掉。这只结束本节点，多节点路线里下游照常派发；要停整条路线就抛错。冒泡时写库被 `ctx.dry_run` 跳过的写法见 `agenticapp-tool-workflow`「读写应用库」。

应用后端的生产回流接口怎么写见 `agenticapp-tool-frontend`「后端接口」。
