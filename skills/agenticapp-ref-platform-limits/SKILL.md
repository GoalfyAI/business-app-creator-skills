# 平台能做到多大

开发者要的是一个能用的应用，不是一句「做不到」。这份 Skill 帮你把需求拆到每一步，逐步对照平台边界，给出**能做到的最大版本**，并让开发者知道边界在哪。

判错有两个方向，都常见：**过度承诺**（没问量级就说能做，到 ④ 或上线后才暴露）和**过度保守**（一有风险就砍需求，能分批做的说做不到）。判断力是在限制内找到最大的「能」。

边界分两类：

- **定性边界**（能不能）：没有团队、模型不能和使用者来回对话、平台不自动重试、自动化要发布后才有……见 [references/定性边界.md](references/定性边界.md)。
- **数字**（能多大）：冒泡 30 分钟、单次工具返回约 10000 token、长期数据集默认 1000 行……都待平台核实，见 [references/已知数字.md](references/已知数字.md)。很多项还没有数字，见 [references/还没有数字的项.md](references/还没有数字的项.md)。

## 什么时候用

- ① 核实 PRD 每一步能不能做、写「能不能做」「用量」时（`agenticapp-stage-1-requirements`）。
- ② 编施工单、定每一步串行还是并行、要不要分批时（`agenticapp-stage-2-plan`）。
- ③ 真实结果的用时、读取量和预期差得多，要判断是做法问题还是撞上了边界时。

## 按这个顺序判断

1. **拆到每一步**。按 PRD「每一步谁来做」，每一步写清：谁做（脚本 / 模型 / 人）、一次处理多少条、单条多大、多久一次、同时有多少份在跑、数据从哪来、结果交给谁。
2. **问量级**。开发者没说的量级按 ① 的用量题问（一周大概用多少次、一次最多处理多少条），同时会有多少份在跑也要弄清，不自己假设一个小数。量级是只有他知道的业务事实，出题时不给推荐答案。
3. **逐步对照**。每一步先对 [定性边界](references/定性边界.md)，再对 [已知数字](references/已知数字.md)；量级碰到 [还没有数字的项](references/还没有数字的项.md) 的，按下面「还没有数字时」处理。
4. **算一遍**。按「总量 ÷ 单次能处理的量 × 单次用时」算出要几次、多久，和开发者要的时间、PRD 的用量上限比；算出来的数标「估算」并写出算法。
5. **给结论**，每一步只有三种：
   - **能做**：在边界以内，写依据（查过什么、真调过什么）。
   - **变形后能做**：分批、降量、换做法、加人工节点，写清比原需求少了什么或慢了多少，变形影响使用者感受的做成选择题请开发者选。
   - **做不到**：写原因、影响哪个功能，当轮给替代选择题（换做法 / 改范围 / 等平台）；要平台补的能力按入口 [平台问题怎么报.md](../agenticapp-creator/references/平台问题怎么报.md) 汇总成 `request`。
6. **写下来**。结论写进 PRD「能不能做」「用量」和功能卡的「这样不行」「会停下的情况」；分批、并行、降量落进 ② 的施工单；④ 用接近用量上限的一批测一次（`agenticapp-stage-4-acceptance`）。

## 常用的变形

| 撞上的边界 | 变形 | 比原需求少了什么，要不要问 |
|---|---|---|
| 需求里有审核、复核、领导看汇总这类多人分工 | 写成使用者自己的一步；另一人的动作是刚需时出选择题 | 少了另一个人的那一步，要问 |
| 一批数据交给模型读不全（单次返回约 10000 token） | 一条一行写成文件、按分片读；计数、求和交给脚本 | 使用者感受不到，不问 |
| 长期数据集一次只回 1000 行且不报错 | SQL 里筛选、带 `LIMIT`；要全量导出成文件处理 | 不问 |
| 一次处理量太大，一次运行跑不完或会被上限挡住 | 分批：每批一次运行，逐条记状态，可续跑；或降量：每次只处理最近 / 最重要的 N 条 | 分批会慢、降量会少，要问 |
| 模型不能和使用者来回对话 | 能预知的放入口表单，上游结果出来后才知道的用中途表单，结果用审阅确认 | 不问 |
| 平台不自动重试 | 每个外部调用写失败出口（停下 / 标记继续 / 重试一次） | 写进「会停下的情况」 |
| 结果模型偶尔会判错、编造 | 加使用者审阅节点，或脚本复算 | 多一步操作，写进 PRD |
| 批量导入后想逐条自动处理（事件触发有每小时和排队上限） | 改成定时触发、一次处理一批 | 不再「改完立刻处理」，要问 |
| 自动化路线里有中途表单或要人判断 | 中途判断改成规则或 FA 判断；做不到就只能人工发起 | 少了「自动」，要问 |
| 发信、发布这类工具不能取样 | 按参数说明判断，④ 只发给开发者自己一次 | 写「能做，没真发过」 |

## 还没有数字时

需求的量级落在 [还没有数字的项](references/还没有数字的项.md) 上时，不编数字，从下面挑成立的做：

1. **真调一次**。① 里能用能力试用包测的就测（`agenticapp-stage-1-requirements`）；要整条路线才能测的，在 ② 的施工单里写成待测项，③ 冒泡或 ④ 实际跑时用接近用量上限的一批测。记下这次的条数、用时、是否被拒、报错原文，写成「实测：日期、条件、结果」。花钱的先按入口「花费」问；只对安全的操作测。
2. **问开发者分批**。量级明显偏大、又测不了时，出选择题：分批（每批多少、慢多少）/ 降量（少了什么）/ 先按原量做，④ 测出问题再改。推荐答案写依据。
3. **报 `platform_limit`**。需要平台给出上限或放宽上限的，按入口 [平台问题怎么报.md](../agenticapp-creator/references/平台问题怎么报.md) 提交：挡住进度的 `blocked`，不挡的汇总成 `request`。提交成功不等于有了数字，PRD 里照实写「平台上限未知，按……设计」。

## 你可能会这么想 → 实际

| 想法 | 实际 |
|---|---|
| 工具名字对上了，这一步能做 | 要真调一次看返回，不能取样的按参数说明判断并写明「没真发过」 |
| 开发者没说量级，就按小量设计 | 先问；没问的量级到 ④ 或上线后才暴露 |
| 1 万条也能一次并行跑完 | 并发和单次时长都没有数字，按「还没有数字时」测或分批 |
| 有风险就先砍掉这个功能 | 先找变形：分批、降量、换做法、加人工节点 |
| 替代方案能跑就行 | 替代方案要写清比原需求少了什么，少太多就继续找 |
| 已知数字是精确阈值，卡着用 | 都待平台核实，留余量；实测不一致以实测为准 |
| 我估一个上限写进 PRD 先用着 | 不编数字：写「估算」和算法，或写「平台上限未知」 |

## 判错的表现

| 方向 | 表现 |
|---|---|
| 过度承诺 | 什么都说「能做」；没问量级；大批量并行照单全收；多人审核流程照搬；做不到的不说，到 ④ 或上线后才暴露 |
| 过度保守 | 一有风险就砍需求；能分批做的说做不到；替代方案比需求小太多 |
