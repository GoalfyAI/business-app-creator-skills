# 场景包版本体系与发布逻辑

场景包与各类资产的统一版本机制：家族与物理行、草稿态、定稿上线。修订已上线包、执行上线动作、处理版本类报错前按需重读本文。版本相关的具体 action 与参数**以你实际看到的工具定义为准**。

## 1. 家族与物理行（最重要的心智模型）

**一个"场景包"对外是一个家族（family），家族内每个版本是一个独立物理行（独立 ID）。**

```text
家族（稳定家族标识）
 ├─ 物理行 A  v26.8.0  已上线      ← 旧版本仍在线，已使用它的项目继续用
 ├─ 物理行 B  v26.8.2  已上线      ← 家族当前对外版本
 └─ 物理行 C  v26.8.3  草稿态      ← 制作中（下一版），独立 ID
```

- 版本引用（如挂载关系里的 `{"id":..., "version":"26.8.1"}`）指向**具体物理行**；
- 列表与挂载视图按家族折叠取最新可运行版；**草稿绝不顶替已上线版本**对外生效；
- **修订不影响现役版本**：草稿是另一个物理行，改它、跑它，线上零影响。
- **挂载参数三形态**：整数（定版时钉住当时版本，缺省）／`{id, version}`（钉死指定版本）／`{id, follow: true}`（保留 latest，运行时跟随家族最新 live——开发者显式选择才用）。`follow` 只适用于场景包的挂载关系；Workflow 对工具集、工具集与 FastAgent 对工具组**永远固定版本**。
- **引用不自动跟随**：钉死引用（具体物理行 ID 或 `{id, version}`）永远指向那一行。被引用资产上线新版本后，引用方（编排 `workflow_ref`、挂载关系）需要更换并反读确认——***不更换引用，新版本永不被运行***。工具在两个环节帮你：
  - **update 自动采用**：`workflow_tpe_manage(update)` 未显式传 `target_scene_package_draft_id`、且调用带的 `scene_package_id` 是 testing/offline **草稿**时，自动把该草稿采用到新版本（换挂载引用并重写编排引用）；live 包不会被顺手改，仍走显式 `attach`；
  - **定稿后的钉旧提示**：Workflow 定稿上线后，工具在 `output.mounted_by_stale` 里**列出仍钉着旧版的场景包**，并在 message 给出下一步（对每个包草稿 `attach`；live 包先 `ensure_editable_asset_draft` 出草稿再 attach）。收到该清单必须逐个处置，或在工单记录明确不跟进的理由——"静默跑旧脚本"已从无提示变为有清单，无视清单即为明知故犯。

  显式 `follow` 语义的引用则跟随家族最新。

- **读侧家族解析（get_asset）**：传**家族根 id** 时自动解析到家族**最新 live 行**返回，条目带 `family_resolution`（requested / resolved 的 id 与版本）——读到的内容代表家族现役最新，不再是根物理行的初版。要核对某个旧版本，必须传那一行的**具体物理 id**。

对制作的直接含义：**引用资产 ID 时必须先反读确认（约束 4）**——同一个"场景包"在不同语境下可能指家族或某个具体版本行，混用会改错对象。

## 2. 版本状态与草稿态

个人自助链路的版本状态：**草稿态（testing）→ 定稿上线（live 且对最终用户可运行）**。

- **对 live 行直接 update 时的响应怎么读**：`update_asset_field` / `update_asset_relations` 打在已上线行上不会报错，工具会先自动派生草稿再把修改落到草稿上，响应 `metadata` 里并列两个 ID——`source_asset_id` 是你传进来的那个（live 行或家族），`draft_asset_id` 是新产生的草稿物理行。***之后的一切操作用 `draft_asset_id`***；同一响应里还会带 Hub 原始返回的字段，别把别的 `id` 当草稿行。按传进去的编号反读会"像没生效"，按 `draft_asset_id` 反读才是真相；`reused: true` 表示家族已有草稿、这次没有新建。
- **草稿态**：制作与验证态。内容编辑**只允许**发生在草稿行上；三层验收、端到端全真、修正环全部在草稿行完成（`stages/S4-验证与修正.md`）。
- 家族同一时刻只允许**一个**草稿；已存在时复用，不新建。
- 草稿的文件内容（Skill 文件等）有独立的物化就绪状态，**未就绪的草稿不允许定稿**。

## 3. 主链路

```text
① 取得可编辑草稿（修订已上线包时）
     从当前上线版本派生草稿行：新物理行、版本号递增、Skill 目录自父版本复制
        ▼
② 草稿行上制作与修改（S2）
     内容写入被版本闸门拦截 = 撞了已上线行 → 回到①取得草稿，禁止绕过
     派生草稿继承 Skill 目录与界面源码包，但不继承部署激活地址（entry_url）：
     带存量附属界面的包，派生出新草稿行后部署地址不继承（`entry_url` 为空），上线前须在新行重新部署并反读确认非空（属存量维护，见 SD 3.4）
        ▼
③ 草稿态验证（S4：三层验收 + 端到端全真 + 修正环，全在草稿行滚动，不需要每圈定稿）
        ▼
④ 定稿上线（S5）
     一步完成定稿+真正上线；平台闸门：运行时身份 / 工具组连接信息 / 文件物化就绪；
     依赖闭包：latest 引用钉到当刻版本（显式跟随除外，须开发者知情）；
     旧上线版本保持不变
```

配套出口（S5 第 6 节）：作废草稿（先看影响面）、回滚到历史版本（须开发者确认）、按版本查看与对比。

## 4. 术语纪律

| 概念 | 含义 |
|---|---|
| 家族 | 同一个"场景包"对外的稳定身份 |
| 物理行 | 一个具体版本对应的资产行（独立 ID） |
| 草稿态 | testing 状态的物理行；制作、修改与全部验证在此进行 |
| **上线** | 定稿并真正上线：草稿行晋级 live、对最终用户可运行；**端到端全真通过是其前置** |

**禁止**用"发布"指代上线动作；面向外部市场的发布链路不属于制作工具面，不在本 Skill 表述范围。

两处容易踩的命名差异：

- **家族标识有两个字段名**：版本工具面用 `resource_group_id`，资产列表/详情用 `apc_display_id`——二者同指一个家族。
- **`asset_type` 拼法两套、无别名**：版本工具面用 `scenario_pack`，业务工具面（list / get / clone / update）用 `scenario_package`；在版本面传 `scenario_package` 会被直接拒绝。

## 5. 版本类报错

撞版本闸门（内容修改被拒 / 上线动作被拒）的处理见 `stages/SD-诊断与维护.md` 4.6 报错对照。统一原则：**按结构化错误指引走正规链路（建草稿 / 定稿上线），禁止绕过闸门直接改写状态。**

统一版本体系之前创建的存量资产可能整族没有版本事实，平台会在需要时就地补基线——这是正常兜底，不是错误（`stages/SD-诊断与维护.md` 1.5）。
