# S2 资产设计与制作

拿着已确认的《场景包计划书》，先做资产设计——复用项目与场景包、摸底能力、选执行形态、设计路线编排与架构、方案挑战、补齐制作书并经开发者确认——再按制作书自底向上创建与验收全部资产。

## 1. 进入前提

《场景包计划书》已按 S1 5.1 写入工单并经开发者确认（`build_book`，`stage="S1"`）——本阶段先在它之上做资产设计（第 2–7 节，形成完整制作书并过制作书硬门），再进入资产制作（第 8 节起）。修订已上线包的任务已持有草稿行——**一切内容修改只发生在草稿行上**；内容写入被版本闸门拦截（结构化错误提示需要先定稿或先建草稿）时，回 S1 第 6 节取得可编辑草稿，**禁止**绕过闸门直接改上线版本（详见 [场景包版本体系与发布逻辑](../references/场景包版本体系与发布逻辑.md)）。

**边界**：计划书里的业务口径（画像、旅途、交付角色、红线）在本阶段只做落地不做改写；资产设计发现业务口径要变，回 S1 第 5 节。

## 2. 复用：项目、场景包与资产摸底

拿着已确认的计划书（`build_book`，S1）开始资产设计。先复用、再摸底、最后才谈缺口——三个来源按此顺序看：参考项目（真实执行记录，可信度最高）、已有场景包与官方基础包（能派生就不从零建）、平台能力（工具组 / 工具集 / FastAgent / 数据集）。

### 2.1 参考项目三层深读

开发者提供了参考项目时**必须**完成三层，**禁止**只看摘要下结论（约束 3）。

**第一层 概览**：读项目摘要，统计总轮次、最终用户请求序列、执行阶段、Agent 与工具分布、等待与失败概况。摘要是压缩后的统计信息，**只能**用于建立全局视图和定位需要深挖的轮次，**不能**作为结论。

**第二层 深读**：读取完整原始日志的全部分页，截断时**必须**续读到结束。重点看：最终用户原始意图与约束、规划逻辑与步骤拆分、工具调用密集的阶段（调用链、参数传递、前后依赖）、任务点与 FastAgent 的输入输出质量、失败重试、等待原因、最终交付是否匹配预期。

**第三层 分析**：形成以下可复核结论并写入工单：

- **轮次分类统计**：总轮次、有效推进、重复沟通、失败重试、等待
- **瓶颈定位**：消耗最多轮次的阶段，根因归类为缺知识、缺工具、缺指引、缺前置检查或资产边界错误
- **真实调用链提取**：每个业务阶段实际调了什么、顺序如何、有没有前置依赖但 Agent 不知道
- **Skill 使用情况**：哪些文件被读取、哪些应该被引导读取但没有

多个项目对比时，**必须**逐项目保留独立事实，再提炼共性，**禁止**用平均值掩盖异常。

**完成标准**：三层全部完成并写入工单后才能进入下一步。**禁止**只看摘要就跳过深读——这是本阶段最容易出现的问题。

### 2.2 复用已有场景包与官方基础包

你**必须**主动获取的：

- 用 `get_asset` 查看**官方基础场景包**的完整配置，理解其预加载与动态工具集的组合方式，作为选型基准
- 用 `list_assets` 加 `get_asset` 查找可参考的已有场景包；开发者要"基于某个已上线包做一个变体"时，用 `get_scene_package_lineage` 看它的来源与派生包，再评估是走**派生**（`create_derived_scene_package`，见路由器 §7.1）还是新建
- 用 `get_diagnosis_doc(scene_package)` 读当前场景包契约

复用的判据是**计划书**：候选场景包 / 派生来源覆盖了计划书 ②③ 章里的哪些路线与交付、用词与画像是否一致、缺什么。能派生就不从零建（路由器 §7.1）。

### 2.3 能力摸底与覆盖矩阵

三个只读工具：

| 工具 | 用途 |
|---|---|
| `list_assets` | 按类型搜索可复用资产。关键词只匹配名称和 ID，建议用英文短词；不传关键词会返回全量，注意上下文开销 |
| `get_asset` | 批量反读完整配置、关系、Schema、状态，一次 1–20 个 |
| `dataset_read` | 只读查看长期数据集：描述、使用指南、Skill 文件、表、列、行 |

用 `list_assets` 和 `get_asset` 搜索并完整反读场景包、任务点、工具集、FastAgent、工具组、数据集；摸底的目标来自计划书第 ②③⑥ 章——每个里程碑、每条路线、每类产出各需要什么能力。看 Schema 和真实配置，**不要**只看描述。

搜索结果**不是**完整资产契约，选型前**必须**用 `get_asset` 下钻（约束 4）。重要选择结论用 `task_manager(insert)` 留痕。

一次 `get_asset` 只返回该资产自身的配置，**不会**展开它引用的子资产。诊断时**必须**按层逐级下钻。

场景涉及数据查询或报表时，用 `list_assets` 列出开发者有权访问的长期数据集，`get_asset` 或 `dataset_read` 确认表结构与权限范围。数据集**只能**绑定真实可访问的，**禁止**假设开发者拥有某个数据集。开发者没有对应数据集时明确告知需要先去准备。

按每个里程碑建立覆盖矩阵：**已覆盖 / 可组合覆盖 / 需维护 / 真实缺口 / 受限能力 / 验证方式**。

向开发者输出每个里程碑的覆盖情况，把缺口处理选项、影响和推荐纳入制作书第 ⑨ 章（7.2），由开发者确认；Agent 不得以“工具缺口不可阻塞”为由自行削减业务目标。

### 2.4 工具缺口四层处理

工具缺口**不可**阻塞创建流程，但**不得**静默削减开发者明确要求或参考项目中已有的能力（约束 12）。按以下优先级处理：

**第一层 Skill 弥补**（成本最低，优先尝试）：工具能力已覆盖，问题只是缺调用顺序、前置检查、字段准备或结果审视方法。把指导写进正确层级即可。

**第二层 接入现有能力**：先在平台上找，平台没有再去外部找。

平台内：用 `list_assets` 和 `get_asset` 确认是否已有可复用的工具组——重复注册同一个服务会产生互相冲突的资产。

平台没有时**从外部获取**。你运行在能联网、能读写本地文件、能执行命令的环境里，这是 Max 内部制作助手做不到的，**应当主动利用**：

| 目标 | 去哪找 |
|---|---|
| 现成 MCP 服务 | MCP 官方索引、代码托管平台、包管理平台（npm / PyPI），以及开发者自己的私有仓库 |
| 现成 Skill 包 | 同上；开发者手里可能已有内部沉淀的包 |

找到候选后**先在本地验证，再走平台注册**。顺序反了会浪费大量试错：本地能起来、工具清单和返回结构都确认过，注册基本一次通过；直接注册再排错，每轮都要等平台反馈。

评估候选时**必须**看清四件事：

| 维度 | 为什么要看 |
|---|---|
| 是否仍在维护 | 长期不更新的服务上线后容易失效 |
| 连接方式 | 决定注册时传地址还是启动命令，以及运行环境要装什么 |
| 认证方式 | 全场景包共用一份凭证，还是每个终端用户各自授权——后者**必须**配授权卡 |
| 有无破坏性操作 | 决定哪些工具可以取样、哪些**禁止**取样，以及要不要在使用指南里加约束 |

开发者提供本地包或压缩包时，走 `file_to_url` 换取引用后注册或导入（见 9.3）。完整的注册流程、失败调试循环和上线检查见 [依赖与 MCP 接入](../references/依赖与MCP接入.md)。

**第三层 形成开发需求**（开发者有协作团队时）：为缺失能力生成可直接转交的需求说明，**必须**写明业务动作、目标系统、必需输入与输出、授权方式、最终用户与项目隔离要求、副作用、失败语义、验收样例。格式要便于开发者一键转发给工程师。

**第四层 开发者确认后降级**：用已有能力继续制作，**必须**明确说明未覆盖的阶段、对结果的影响、以后补齐的条件和受影响的验证，并取得开发者确认。

### 2.5 实现思路调研

**不知道某个效果如何实现时**（有目标、无做法）——**先询问开发者是否有参考资料或已知同类产品**；没有再去 GitHub 等开源平台自行调研同类实现。调研的是**实现思路**而非现成资产，产出可以是自建 Workflow / 工具的设计依据，或转交开发需求（第三层）的技术方案参考。结论与来源记入工单。

## 3. 理想态与价值预测

### 3.1 现状、理想态与配置手段

构建"现状 → 理想态 → 配置手段"的映射，它决定后续 Skill 要写到什么颗粒度：

| 现状问题 | 配置手段 |
|---|---|
| 缺知识导致试错 | 补业务规则或场景 Skill 文件 |
| 不知道能力顺序导致绕行 | 补阶段前置检查和工具集搭配指引 |
| 参数结构不清导致失败 | 补必填结构、字段来源、示例 |
| 找不到能力导致浪费 | 在 `apc_skill` 建立能力与文件索引 |
| 重复、稳定、高复用的真实步骤 | 评估做成 Workflow |
| 需要临场判断或中途交互 | 按开发者确认的边界保留给 SystemAgent、任务点或最终用户 |

**有真实项目基线时**可以预测轮次、失败重试或人工确认的改善幅度，但**必须**列出计算依据、假设、不可优化部分和误差范围。**没有基线时只做定性判断**，**禁止**编造数字（约束 2）。

### 3.2 Focus 与泛化

形成使用模式候选：

- **Focus**（"让这个任务更快更省"）→ Skill 写到工具调用级别，固化执行路径
- **泛化**（"沉淀经验用于类似场景"）→ Skill 写到策略级别，保留选路弹性

Agent 根据开发者目标和证据给出推荐，但 **Focus / 泛化必须作为方案 Plan 的显式选择项由开发者确认**；不得因为参考项目更具体就自动选择 Focus，也不得因为素材不足就自动选择泛化。

### 3.3 必须评估是否使用 Workflow

**这一步不能跳过，也不能默认不用。** 逐个里程碑对照第 4 节的信号判断，把结论和理由写入工单。

之所以要强制评估，是因为**做 Workflow 的工作量明显高于普通场景包**——要写脚本、备齐依赖、过上线检查、跑运行验证。省事的做法是全部交给 SystemAgent 临场处理，但那样会把消耗转移到每一次运行上。

两种做法的实际差异：

| | 交给 Agent 临场处理 | 固化成 Workflow |
|---|---|---|
| 每次运行的推理量 | 重新理解任务、重新决定调用顺序、重新组织参数 | 只在 FastAgent 承担的那几个环节里推理，确定性衔接不经大模型 |
| 推理消耗 | 上述推理**每次运行都会重复发生** | 确定步骤不经过大模型 |
| 耗时 | 随推理轮次增加 | 按脚本直接执行 |
| 一致性 | 同样输入可能走出不同路径 | 同输入同路径 |
| 出错定位 | 要读整段对话日志 | 定位到具体步骤 |

判断时先看**结构是否适合固化**：存在至少两个真实步骤，步骤顺序、数据流或扇出汇合关系稳定，不需要大模型在运行中改变下一步，就具备 Workflow 结构条件。再看**固化收益**：会被反复跑、定期产出、或最终用户每次只改几个参数时，固化的稳定性和成本收益更高。重复执行是重要收益信号，**不是唯一准入条件**；一次性任务若仍是确定、稳定的多步管道，也可以采用 Workflow。一次性探索分析若执行走向需要临场判断，则交给 Agent 或普通任务点。

向开发者提交结论时用业务语言讲清取舍：哪些阶段建议固化、这样做在稳定性和使用成本上的区别、哪些阶段建议保留临场判断以及为什么。**是否采用 Workflow 及对应资产边界由开发者在方案 Plan 中确认**；禁止只说"建议用 Workflow"而不说明理由，也禁止为了省制作工作量而不做评估。

向开发者提交价值预测与方案 Plan：预期效果、主要优化点、无法覆盖的部分、使用模式、Workflow 取舍及待确认项。开发者确认前不进入正式资产创建。

## 4. 执行形态选择

### 4.1 资产概念

场景包的组成与 TPE 双类型关系在路由器 `SKILL.md` §7.1；运行时自带的默认能力、四种执行形态各自的构成与能力边界，正本在 [平台对象与运行模型](../references/平台对象与运行模型.md) 第二章。本节只承载选型决策；业务侧的“需要什么”来自计划书第 ②⑥ 章。

### 4.2 四者对照

| | SystemAgent 直接执行 | FastAgent | 普通任务点 | Workflow |
|---|---|---|---|---|
| 是否独立资产 | 否 | 是 | 是（TPE） | 是（TPE） |
| 上下文 | 主对话 | 每次全新隔离 | 独立 | 独立 |
| 能否与最终用户交互 | 能 | **不能** | **能** | 单条**不能** |
| 执行步骤 | 临场决定 | 临场决定 | 临场决定 | **预先固定** |
| 自带文件/命令/邮件 | — | **不自带** | 自带 | 自带 |
| 与编排的关系 | — | 被 Workflow 调用 | **不能**作为编排节点 | 可作为编排节点 |
| 多次运行的一致性 | 每次重新推理，路径可能不同 | 每次重新推理 | 每次重新推理 | 同输入同路径 |

### 4.3 怎么选

按以下顺序完成一次决策，**不要**按复杂度、步骤数量或资产数量来回切换：

1. 先判断执行路径是否需要大模型在运行中决定下一步，或是否需要自然语言往返。需要时使用普通任务点；不需要时继续。
2. 再判断是否存在至少两个实质步骤、稳定数据流、固定扇出/汇合，或同一路径需要参数化复跑。存在时使用 Workflow；需要多个职责边界时拆成多个 Workflow 并写入图编排。
3. 若整个任务是一个环节的完整工作——一次输入，自己带着工具搜、读、判、写直到产出，一次输出——使用 FastAgent，不为它增加单步转发 Workflow。
4. 若只是当前上下文中确定的少量调用，且没有独立复用价值，由 SystemAgent 直接执行。

决策结果可用下表复核：

| 需要 | 形态 |
|---|---|
| 确定的 1–5 次调用、指令量小、仅当前场景用 | SystemAgent 直接执行 |
| 独立上下文、开放式判断、执行中需要自然语言交互 | 普通任务点 |
| 一个环节从输入到产出的完整工作（含其中的多轮工具调用）、无需中途交互、多场景复用 | FastAgent |
| 至少两个稳定真实步骤、固定数据流、会被反复跑 | 单 Workflow |
| 单条 Workflow 需要发布业务事件、接受业务表单握手或进入 Delivery Review | 单节点业务路线编排 |
| 一条路线内多个 Workflow 的固定依赖、扇出、汇合和交付 | 多节点业务路线编排 |

任务"复杂"或"有多个步骤"**不自动**意味着要用普通任务点，也**不意味着要拆成多个 FastAgent**——一个 FastAgent 挂上工具就能完成复杂但无需交互的整个环节。只有执行中确实需要补信息、暂停确认或自然语言交互时才选普通任务点。

**看到这些信号优先按 Workflow 设计**：

- **反复执行的固定流程**：每日简报、日报、周报这类同一条流程反复跑的产出
- **固定流水线**：搜索 → 筛选汇总 → 生成报告（→ 发送）这类定型流水
- **多对象并行加汇总**：多品牌、多平台、多主题并行调研后做横向对比
- **参数化复跑**：最终用户每次只填几个参数，跑同一套步骤、产出同类结果

判别标准：固定流水线、参数化复跑和定期产出通常适合 Workflow；一次性探索分析若执行走向需要临场判断，则使用普通任务点或 Agent。不能只凭“是否重复”覆盖前述结构判断；成本结构的对比与"必须评估"的门见 3.3，不在此重复。

### 4.4 FastAgent 粒度与数量纪律

**一个业务环节一个 FastAgent。** FastAgent 是带工具的完整执行单元（正本见 [平台对象与运行模型](../references/平台对象与运行模型.md) 2.2）：一个环节里“搜索 → 筛选 → 读取 → 判断 → 按规范产出并落文件”这一整串，该由**一个** FastAgent 挂上所需工具组一口气做完；脚本只负责环节之间的确定性衔接。三条判据：

1. **拆不拆看职责，不看步骤**：拆分 FastAgent 的唯一理由是职责边界不同——不同领域知识、不同产出契约、需要在别处独立复用。同一环节内步骤再多也不拆；**禁止**为每个判断点建一个 FastAgent，**禁止**按“角色”把同域职责拆成多个只在措辞上不同的 FastAgent。
2. **工具挂给 FastAgent，还是脚本自己调，看“下一步靠不靠结果决定”**：固定的准备与收口（取表单值、取数据集固定字段、落产物目录、发事件、回写）由脚本 `tool()` 做；凡是要看着结果决定下一步查什么、读什么、改什么的，属于 FastAgent 内部——把工具组挂给它。脚本里出现 `tool → FastAgent → tool → FastAgent` 的长链，多半是把本该属于一个 FastAgent 的环节切碎了。
3. **不挂工具、只做文字变换的 FastAgent 是误用**：读文件、写文件、格式转换、数据搬运这类去掉大模型也能确定性完成的步骤，直接用工具调用，**禁止**为其创建 FastAgent——无论赋予什么角色。

同一条 Workflow 内**同域多类产出**用「一个 FastAgent + 交付物参数分发 + 按交付物划分的规范文件」承载——提示词只写共同原则与分发规则，每类交付物一份规范文件按需读取。

方案中 FastAgent 超过 3 个时，**必须**逐个说明不可合并的理由（职责边界具体是什么；该判据同时列入方案挑战检查清单）。

### 4.5 两个相反的错误

两个相反的错误都要避免：

**不要给单个 FastAgent 套一层 Workflow。** 如果脚本只做一件事——调用一个 FastAgent，然后把结果原样返回，中间没有任何其他处理——这层 Workflow 不提供任何价值，**直接使用那个 FastAgent** 即可。

**也不要因为步骤少就否定 Workflow。** 一条只有两三步的线性流程（搜索 → 清洗 → 汇总）完全正当。判据是**有没有至少两个实质步骤、数据有没有在步骤之间流转**，与步骤多少无关。

## 5. 业务路线编排设计

计划书第 ③ 章的业务路线图在这里落成真实的编排对象设计（节点、映射、运行中交互、Agent 介入、交付与审阅）；组装写入在第 14 节。

### 5.1 业务路线编排对象

业务路线编排是场景包上的**一个整体对象**，用来固化业务入口、运行身份、执行依赖、交付与审阅。路线可以只有一个 Workflow 节点，也可以包含多个 Workflow：

- **单节点路线**：单条 Workflow 声明或调用业务事件、需要业务表单握手、需要 Delivery Review，或需要由业务应用启动时使用。只有一个节点不代表可以绕开 Business Runtime。
- **多节点路线**：一条路线包含多个 Workflow 的固定依赖、扇出、汇合、交互和交付时使用。
- **直接派发**：仅适用于没有业务事件契约、没有 `emit_business_event`、不依赖 Business/Runtime 握手的单条 Workflow。

构成：

```text
编排对象
├── 版本标记
└── 路线 ×N                     每条路线对应一种业务走法
    ├── 唯一标识、名称、描述
    ├── 入口表单标识
    ├── 路线级输入定义
    ├── 节点依赖图                节点引用已挂载的 Workflow，必须无环且全部可达
    ├── 节点输入映射              逐字段声明取值来源：路线输入，或依赖的上游节点输出
    ├── 运行中交互（可选）         上游成功后才能确定、且供尚未派发的下游节点使用的输入
    ├── 节点级 Agent 介入（可选）  节点成功后需要检查或处理异常时声明
    └── 唯一最终交付与审阅动作  交付核验与业务验收是两个独立阶段
```

写入时采用**整体替换**语义，因此写前**必须**反读原值（见 16.1）。字段的具体名称、结构和版本要求以 `get_diagnosis_doc` 的当前契约为准（见 11.1）。

运行期事实：已发布路线在业务应用与聊天两个入口天然并存，走哪个入口由最终用户自选（界面经 Runtime 运行，聊天直调时业务事件自动降级）——这是平台行为，不是设计决策。制作侧**不设计**也**不引导**入口选择。

### 5.2 何时不使用固定编排

以下情况**不要**强行画成固定依赖图：

| 情况 | 应当采用 |
|---|---|
| 整条路径需要临场规划，或 Agent 介入产生的新值要成为后继输入 | 普通任务点 |
| 最终用户改稿、重做或改走另一条路线 | 冻结当前交付、开启新的运行实例。**禁止**在同一张图里画回边模拟循环，**禁止**覆盖旧交付或旧文件 |
| 制作期就能预知的最终用户输入 | 全部放入口表单，不用运行中交互 |
| 只有上游节点成功后才能确定、且要供尚未派发的下游节点使用的输入 | 节点级运行中交互 |
| 节点成功后需要 Agent 检查或处理异常 | 在该节点声明 Agent 介入，并写清指令和可验证的继续或接管标准 |

编排只调度**已经存在且通过单体验收**的 Workflow。场景包没有 Workflow 时**禁止**伪造空节点或空图。

## 6. 架构方案设计

### 6.1 工具集划分

**工具集划分**：

- 预加载：每次运行都必须出现的核心能力
- 动态：按需加载的辅助能力
- 选型规则：克隆官方包继承的核心工具集**不可**移除；优先复用系统级工具集；**按能力域**匹配，**不要**按业务场景创建专用工具集

**执行形态提案**：按第 4 节形成普通任务点、FastAgent、Workflow 或直接执行的候选边界，**不要**用"默认用 FastAgent"或"只有交互才建任务点"这类简化规则。Agent 必须说明推荐理由、运行体验、成本和可变性，把第 3 节的评估结论纳入制作书第 ⑧ 章；开发者确认后才落成具体资产，**禁止**在实现阶段自行推翻已确认结论。

### 6.2 内部资产清单

**内部资产清单**（记入工单，除非开发者要求技术说明，否则不放入业务方案）：

- 每个 FastAgent：名称、职责、输入输出、真实关联的工具组
- 每个工具集：能力域、成员、加载方式、使用指南要点
- 每个任务点：路由描述、交互需求、输入输出、关联工具集
- 每条 Workflow：稳定业务阶段、脚本要用的工具名、完整依赖清单、输入输出定义、辅助文件、副作用；配套业务应用时，**每个输入字段的来源**（入口表单 / 读业务应用数据集 / 上游节点）与数据集缺失时的回退（9.4）
- 每条编排路线：入口、节点、映射、交付审阅、重入方式
- 数据集：为什么绑定、在哪个节点读取

所有 ID **必须**工具查询确认（约束 4）。

**开发者可见的业务路线图**：提案包含 Workflow 或固定业务路线时，在完整方案 Plan 中用业务阶段名称画出每条候选路线的入口、依赖、扇出/汇合、最终用户与 Agent 介入、最终交付、审阅责任和动作出口。它与内部资产清单分开：前者用于确认产品如何运行，后者才用于确认真实资产如何承载；不得把内部节点标识、工具名或字段映射暴露到业务方案中。

### 6.3 执行结构表

方案的**强制产出**。为每条 Workflow 建立执行结构条目：

- 步骤清单：每步做什么、用什么（工具或 FastAgent）
- 步骤间依赖：谁的输出喂给谁
- **并行组**：相互无依赖且可安全并发的步骤归入同一并行组；相邻无依赖步骤**未**归入并行组的，写明原因（副作用顺序、共享路径、会话状态等）
- FastAgent 清单：本条 Workflow 用到的全部 FastAgent，及按 4.4 的不可合并理由

**并行组怎么画**，逐步骤按序检查：

1. **数据依赖**：这一步的输入是否用到另一步的输出？不用，继续；
2. **副作用独立**：是否写同一路径、共享同一会话、或有顺序语义的外发动作？没有，可并行；
3. **典型形态点名**：**对多个对象执行同一操作（循环逐个调用工具或 FastAgent）默认设计为并行组**——串行处理 N 个独立对象是最常见的浪费，除非对象间有真实依赖或共享副作用，并写入 `no_parallel_reason`。

设计时需要正反例的，读 `get_diagnosis_doc(workflow_example_parallel)`——**不要**等到写脚本才第一次接触并行原语。

**展示载体判定**：`by` 为 FastAgent 的步骤和关键工具步骤，建表时逐步判定其结果是否面向最终用户，三档：**不展示**（内部中间产物，默认）／**进业务事件**（值得单独展示的中间里程碑，走 12.4 事件候选流程，由开发者确认）／**进交付**（内容作为业务字段纳入最终 `output`——仅交付文件路径时，界面只能提供预览与下载，渲染不出文件里的内容）。判定记入该步的 `user_facing` 字段。***FastAgent 与工具的原始返回不是展示载体***——要给用户看的结果必须经事件或交付转成业务表达（如"素材盘点完成：4 张中 1 张可直接使用"，而不是工具返回原文）。

按路由器 5.1、5.3 落本地工作副本与工单权威快照。本表建立后，后续任何脚本或结构修改都**必须**同步更新对应条目（见 11.4）。

### 6.4 起草 apc_skill 与场景 Skill 文件

**起草 `apc_skill` 与场景 Skill 文件**：按 15.3 校验颗粒度——逐一对照第 3 节里每个"预期减少的轮次"，确认都有对应的可执行指导，且每个文件都有明确读取时机。

### 6.5 业务应用数据集读写的落地

计划书第 ⑤ 章只回答了业务问题；本节把它落到字段与通道：

| 计划书里的业务判断 | 落地 |
|---|---|
| 发起时就该带上的用户数据 | 进入口 `input_schema`，由业务应用在发起时预填（S2 9.4 时机 1）——不为它起 FastAgent，也不在脚本里读 |
| 中途“看情况取”的数据 | Workflow 脚本调 `dscli_business_dataset` 读（9.4 时机 2），每条业务流至多一次读；表单字段设可选、`found=false` 回退表单值 |
| 要回流的产出与效果数据 | 脚本收尾 `operation="write"`（9.4 时机 3），`context_hint` 给唯一键；写回哪张表哪些列与 app-creator 线对齐，列名用画像的词 |

逐字段写进内部资产清单（6.2）与执行结构表（6.3）的对应步骤；未规划配套业务应用时本节不适用。

## 7. 方案挑战与制作书定稿

### 7.1 方案挑战

创建任何资产前**必须**完整读取 [方案挑战检查清单](../checklists/方案挑战检查清单.md) 并执行。质疑成立就修方案；不成立就说明证据和取舍。**禁止**在证据不足时判定通过。

挑战以执行结构表为对象逐条目进行，**只处理状态为 `pending` 的条目**（路由器 5.3 累加机制）；全部条目通过后，将执行结构表表级布尔位 `challenged` 置 `true`。

### 7.2 完整《场景包制作书》：在计划书上补第 ⑧⑨ 章

S1 的七章计划书（`build_book`，`stage="S1"`）原样沿用，本阶段补两章，合起来是完整的《场景包制作书》——本 Skill 各处所说的“方案 Plan”：

| 章 | 内容 | 来源 |
|---|---|---|
| ⑧ 执行形态与资产边界 | 各阶段用直接执行 / 普通任务点 / FastAgent / Workflow 的结论与理由、Focus / 泛化选择、复用了哪些已有场景包 / 资产、执行结构表摘要、内部资产清单要点 | 第 2–6 节 |
| ⑨ 能力缺口、发布范围与授权 | 缺口处理方案、发布范围、是否“前三层候选验收通过后上线”的执行承诺、端到端全真验证范围 | 2.4 / 约束 6 |

⑧⑨ 两章至少显式列出（历次评审沉淀，全部保留）：

- 各阶段采用直接执行、普通任务点、FastAgent 或 Workflow 的执行形态与资产边界，以及 Focus / 泛化选择；
- 面向开发者的业务路线依赖图与真实编排对象的对应关系（计划书 ③ 章的每条路线 → 哪些 Workflow 节点、入口表单、映射）；
- 完整交付方案在资产上的落点：审阅形态与动作如何声明进编排；
- 业务应用数据集读写的字段与通道落地（6.5）；
- 能力缺口处理、发布范围、是否在前三层候选验收通过后执行上线，以及端到端全真验证范围。

“发布范围”和“上线授权”必须分开表达：发布范围只回答哪些资产与路线属于本次候选版本；上线授权回答候选验收通过后是否实际调用上线动作。制作书明确写出“前三层候选验收通过后上线”并由开发者统一确认时，不再在发布前重复询问；没有该执行承诺、只列发布范围时，`stages/S5-发布与交付.md` 必须另行取得上线授权。

完整制作书**整份重写进工单**（`build_book`，`stage="S2"`）；设计与计划书冲突时不改制作书糊过去——回 S1 第 5 节更新计划书并重新确认。

**格式自检**：①–⑨ 齐全；⑧ 里每个 FastAgent 都能说出对应哪个业务环节（4.4 粒度纪律）；⑨ 的发布范围与 ③ 的路线一一对应。

### 7.3 开发者确认

执行结构表 `challenged=true` 后，连同完整《场景包制作书》（含 S1 已确认的七章与本阶段的 ⑧⑨ 章）一并展示给开发者，由开发者确认 ⑧⑨ 两章并复核 ①–⑦ 未被资产设计改变语义。本次确认**兼作关键 FastAgent 的圈定时刻**：开发者在 FastAgent 清单上圈出关键产出环节（面向最终用户的输出文案类），被圈定的环节在第 10 节制作时必须执行样例选择流程（10.2）。Focus / 泛化在同一次确认中显式选择。

### 7.4 制作书硬门

**制作书硬门**：只有开发者对完整制作书（含 ⑧⑨ 章）完成统一确认后，才能开始依赖资产、普通任务点、场景包草稿、Workflow、关联关系或业务路线编排的创建与修改。确认前只允许继续只读调查、候选方案起草、方案挑战和不改变外部状态的验证。任一未确认项不得被 Agent 当成默认值写入资产；后续若改变路线依赖、交付对象、审阅责任、动作、重入方式或介入点，属于计划书口径变化，回 S1 第 5 节更新计划书并重新确认，再回本节更新制作书。确认后，同一范围内的可逆离线操作获得授权；上线动作仅在 Plan 同时满足上一段的明确执行承诺时获得授权（约束 6）。

## 8. 创建顺序与依赖准备

### 14.1 依赖资产准备

按约束 5 自底向上创建，**每创建一步都反读**名称、关系、状态、权限。本节只准备场景包草稿之前的底层依赖和普通任务点；Workflow 必须等 16.2 创建真实场景包草稿容器后，再按第 11 节创建并挂载。

### 14.2 工具集上线的两道检查

**工具集上线有两道检查，都不能跳**：

**第一道：Workflow 依赖检查**（任何 Workflow 创建前）：确定完整的预加载工具集清单 → 对本轮新建或导入的工具集做安全的运行时测试 → 全部无失败后调 `online_toolsets` → 反读确认全部已上线 → 才能创建 Workflow。

**第二道：交付前最终检查**：对待上线清单里尚未上线的工具集逐一做安全测试 → 破坏性操作跳过 → 全部无失败后上线 → 反读确认。

任一测试失败、余额不足、授权中断或流程异常，**必须**保留原资产和进度，恢复后从未完成的验证继续，**禁止**跳过验证直接上线。

**开发者已有的离线工具集可以关联，但运行时不会被加载。** 发现这种情况**必须**停止交付并告知开发者，**禁止**擅自上线别人的资产。

新建工具组后按需配授权卡（8.3）。为需要最终用户各自授权的能力配卡是正式依赖，不是可选项。

创建 FastAgent、工具集或普通任务点时，提示词或使用指南较长，可以按 9.3 使用实时 Schema 暴露的 `prompt_content_url`、`tool_usage_guide_url` 或 `prompt_template_url`。服务端解析后仍按对应原字段创建；创建完成后反读正文和资产关系，URL 成功下载不能替代资产反读。

### 14.3 授权卡

工具需要**终端用户各自的第三方账号授权**（区别于写在请求头里的服务级认证）时，授权卡是正式依赖。不配的话终端用户无法完成授权、工具调用会失败。

| 工具 | 用途 |
|---|---|
| `create_auth_card` | 为工具组创建授权卡 |
| `update_auth_card` | 更新已绑定的授权卡配置 |
| `link_auth_card` | 用授权卡标识关联到已有卡片，共用其授权配置 |

**禁止**把任何个人令牌写入 Skill 文本、脚本或工单。详细配置见 [依赖与 MCP 接入](../references/依赖与MCP接入.md)。

| `create_toolset` | 创建工具集；长使用指南可在实时 Schema 支持时通过 `tool_usage_guide_url` 提交 |
| `online_toolsets` | 工具集上线 |
| `create_tpe` | 创建普通任务点，**必须**先有工具集；长提示词模板可在实时 Schema 支持时通过 `prompt_template_url` 提交 |
| `workflow_tool_test` | 对已有 MCP 工具做一次**真实调用取样**，拿回真实返回结构；依赖 `/workspace` 时可把 `file_to_url` 上传的真实文件落入临时隐藏验证项目，调用结束后清理。不会修改场景包资产 |

前置依赖顺序（工具定义里看不到，但漏了就会失败）：

| 工具 | 前置 |
|---|---|
| `register_and_refresh_tool_group` | 先 `preview_tool_group`；**预览时用过的前置安装步骤，注册时必须一并带上** |

| 授权卡三件套 | 都要工具组注册返回的授权绑定标识（**不是**工具组标识） |

完整的注册流程、调试循环、私有包处理、授权卡配置和上线检查见 **[依赖与 MCP 接入](../references/依赖与MCP接入.md)**。

### 15.2 工具真实取样

**什么时候用取样**：写 Workflow 脚本时需要知道某个工具的真实返回结构——光看工具描述推不出嵌套字段的实际形状，猜错会导致下游步骤读不到字段。取样一次拿回真实样本，再据此写脚本里的输出声明。可以同时提交一个候选的输出结构，让本次样本顺带校验它。

工具只依赖已有业务项目上下文时传项目标识，这不会启动新项目。工具需要读取测试文件时，先用 `file_to_url(purpose="tool_test_fixture")` 把 Agent 本地文件换成临时文件引用；把返回的 `data.file_ref` 放进 `workspace_files`，再用 `workspace_bindings` 声明由哪个目标工具顶层参数接收该文件路径或父目录。服务端会复用冒泡验证的隐藏项目，从临时 HTTPS URL 下载真实文件、写入 `/workspace` 后调用工具，并在成功或失败后自动清理。此模式不要同时传 `project_id`。

**取样会真实调用供应商接口。** 破坏性、发布、凭证、金融或任何不可逆的工具**禁止**取样，只对**安全只读**的工具做。

### 15.3 文件与创作型长文本准备

先判断提交内容属于哪一类，二者的生命周期不同，**禁止**混用：

| 类型 | 典型内容 | 提交方式 | 平台保存结果 |
|---|---|---|---|
| 资产文件 | Skill 文件、辅助脚本、模板、样例、私有包、Logo、工具取样文件 | `file_to_url` 换取文件引用，再把引用绑定到资产或验证项目 | 文件作为独立资产或附件保留 |
| 创作型文本 | Workflow 脚本、`apc_skill`、业务路线编排 JSON、FastAgent 提示词、工具集使用指南、普通任务点提示词、待更新字段全文 | 短内容直接传原文本字段；长内容或需要反复维护时，在实时 Schema 暴露对应 `*_url` 后传服务端可访问的 HTTPS 文本地址 | 服务端只读取一次正文，再按原文本字段的校验、确认、保存和上线链路处理；URL 本身不绑定为资产文件，也不作为配置保存 |

创作型文本 URL 只是一种**输入传输方式**，不产生新的资产类型。使用时遵守以下规则：

- 原文本字段与对应 `*_url` **二选一**；Workflow 的局部补丁还要遵守实时 Schema 中与完整脚本来源的互斥关系
- URL 必须是服务端可访问的 HTTPS 文本地址，不得指向内网、客户端本地路径或需要浏览器登录的页面；编码、大小、重定向和地址安全限制以实时 Schema 为准
- 外部 Agent 的本地 `/workspace` 不属于 Max 沙箱，**禁止**作为 `script_file` 传入；内部 Max Agent 只有在实时 Schema 暴露 `script_file` 时才可使用
- 提交成功后**必须**反读最终正文、JSON 对象或脚本摘要，确认平台保存的是解析后的内容而不是 URL；下载、解析或校验失败时停止提交，禁止截断正文后伪装成功
- URL、临时上传地址和带签名的查询参数**禁止**写入工单；工单只记录目标资产、内容用途和反读结论

#### 资产文件：第一步换取文件引用

`file_to_url` 是唯一的文件通道，**必须**声明用途，服务端按用途决定大小、类型和存储规则：

| 用途 | 用于 |
|---|---|
| `skill_file` | Skill 文件、辅助脚本、模板、样例 |
| `skill_package` | 要导入成工具集的标准 Skill 包 |
| `mcp_package` | 要注册成工具组的私有 MCP 包 |
| `scene_package_logo` | 场景包 Logo 图片 |
| `tool_test_fixture` | 真实工具取样时需要落入隐藏 `/workspace` 的本地测试文件 |

四个 action（本地新文件没有直传内容的路径，只能 `prepare` → 客户端 PUT → `complete` 三跳）：

| action | 说明 |
|---|---|
| `prepare` | 申请上传地址，**必须**传真实字节数 |
| `complete` | 确认上传，换回文件引用。传入的凭据**必须**来自同一工单、同一用途的 `prepare` |
| `from_url` | 已有可信 HTTPS 地址时跳过上传直接导入。**仅支持** `skill_file`，且地址**必须**服务端可访问、**不得**指向内网 |
| `export` | 按明确资产 ID 把 Workflow 脚本或 FastAgent 提示词导出成可下载文件（用途 `asset_text`） |

**不接收** base64。临时上传地址**禁止**写入工单。

#### 资产文件：第二步绑定到资产

| 情况 | 做法 |
|---|---|
| 资产还没创建 | 在创建调用里直接带上文件引用 |
| 资产已存在 | 用 `upload_skill_files` 补挂，需要指定资产类型和标识 |
| 场景包的场景 Skill 文件 | 用 `scene_package_manage(update)` 带文件引用 |
| 场景包 Logo | 用 `update_scenario_package_logo` 带文件引用 |

`upload_skill_files` 和场景包更新都支持合并（merge）与整体替换（replace），但**缺省相反**：场景包更新（`scene_package_manage(update)`）缺省 merge，保留既有文件；***`upload_skill_files` 缺省 replace，省略参数会覆盖整个 Skill 目录***——补挂单个文件时显式传 `skill_files_mode="merge"`（支持 scenario_package / toolset / fast_agent），定点删除用 `remove_skill_paths`。

### 15.4 业务应用数据集读写通道（为业务应用制作的场景包）

场景包配套业务应用（约束 8，app-creator 线）时，运行期的用户数据都存在**业务应用数据集**里——用户点开应用时从模板 copy 出的那份 PG schema，应用后端直连它，Workflow 则经平台级 FastAgent **`dscli_business_dataset`** 在沙箱内读写同一份数据。该 FA 是平台资产建一次，**包作者不用自制**。

**这是一个 Workflow 输入来源的设计决策，FA 调用要写在脚本里**——用法与脚本里调用任何其他 FastAgent 完全相同（`tool(...)` 显式调用 + 所在工具集进预加载清单），不是一套挂上就自动生效的特殊机制；唯一的特殊之处是沙箱自动继承（见下文）。 每条 Workflow 需要的每个业务输入，都由开发者在 S1 方案里决定从哪来、在 S2 落进 `input_schema` 与脚本：

| 输入来源 | 适用 | 怎么落 |
|---|---|---|
| **入口表单**（最终用户填） | 每次运行都会变、只有用户知道、数据集里没有的信息 | 进路线 / Workflow 的 `input_schema`，由表单渲染 |
| **读业务应用数据集**（脚本调 FA） | 用户已经在应用里记载过、或能从历史数据推出的信息——本店信息、近 30 天效果、禁用表达、历史选题 | 脚本开头 `tool("dscli_business_dataset", operation="read", query="...", _output={...})`，结果沿 node_output 流转给全部下游 |
| **两者组合兜底** | 数据集可能没有、可能不足 | 表单字段设为可选；脚本先读数据集，`found=false` 或所需字段缺失时**回退用表单值**；两边都没有时按通用策略执行或以 `stage_failed` 业务失败收口——回退顺序与缺失时的行为由开发者在 Plan 里定，不由脚本临场猜 |

脚本里的写法（正本是工具集使用指南与 FA 的 Skill 文件，运行时自动注入；这里只给形状）：

```python
ctx_data = tool("dscli_business_dataset",
    _output={"type": "object", "required": ["found"],
             "properties": {"found": {"type": "boolean"},
                            "banned_words": {"type": "array", "items": {"type": "string"}}}},
    operation="read", query="读本店禁用表达清单")
banned = ctx_data["banned_words"] if ctx_data["found"] else input.get("banned_words", [])
```

- `_output` 按**本路线真正消费的切面**声明，必含 `found`；禁止"把表都读给我"式的大而全 schema；
- **每条业务流至多一次读**：结果沿 node_output 流转给全部下游，不逐节点重复取；
- 收尾**回写**同样写在脚本里：`operation="write"`，`context_hint` **必须**给出唯一键或幂等依据——编排重跑会让同一段写再执行一次；
- 不传 `sandbox_id`——workflow 路径自动继承 TA 沙箱；脚本引用该 FA 后 TA 会自动预建沙箱。

**依赖声明**（是前置，不是使用方式）：脚本里用到的每个 FastAgent 必须在预加载工具集清单里声明（Workflow 依赖规则）——把 **Business UI Dataset 工具集**挂进该 TPE 的预加载清单，并过 8.2 的上线检查。

**三个时机的分工**（设计路线时按此归位，不要错配）：

| 时机 | 谁来做 | 走不走 FA |
|---|---|---|
| 项目启动铺底（门店信息、当前进度等上下文） | 应用后端直读 PG 拼进发起报文 | **否**——此时 agent 尚不存在；制作侧只需把这些字段放进 `input_schema` 供应用预填 |
| 执行中取数（需要理解业务语义的"要什么"） | 脚本调 FA（`operation="read"`） | 是——见上表第二行 |
| 收尾回写（交付结果与效果数据落库，供看板展示与下次运行参考） | 脚本调 FA（`operation="write"`） | 是 |

**两条纪律**：

- **`found=false` 是常态结果不是错误**：表不存在、查不到行都这样收口，下游必须把它当缺省处理（回退表单值或通用策略），***绝不因空数据 fail***；
- 写权由列注释声明裁决：FA 只写 `editable:agent` 列、模板结构只增不改（声明正本与写权矩阵见 app-creator 约束 9）。

## 10. FastAgent 制作

### 16.1 输入定义与提示词设计

FastAgent 的构成、输入定义硬性要求与最大轮次取值的正本见 [平台对象与运行模型](../references/平台对象与运行模型.md) 2.2。制作时按第 6 节确认的执行结构表落实每个 FastAgent 的职责、输入输出与关联工具组；同域多类产出遵守 4.4 的粒度纪律（一个 FastAgent + 交付物参数分发 + 规范文件）。

### 16.2 样例选择流程

凡 7.3 圈定的关键 FastAgent（面向最终用户的输出文案类产出），提示词定稿前**必须**执行样例选择，三步：

1. **领域调研**：**先询问开发者是否有参考资料**（范例、竞品、过往内容）；开发者给不出时才自行上网调研——从产出的目标平台或领域取真实样本入手。**禁止**凭空或随机生成样例。
2. **生成候选样例**：基于调研产出 2–3 种不同取向的**具体**理想输出样例，标注参考来源。
3. **开发者选择**：让开发者在具体样例之间选择，**不要**让开发者在抽象形容词之间选择。选择结果同源编译进三处：该 FastAgent 的提示词、该环节在结果检查表中的验收判定、该环节产出的渲染决策。

过程类环节（中间数据变换、不面向最终用户的产出）不执行本流程，不打扰开发者。

### 17.3 单条 Workflow 的完整闭环

提交脚本前先按运行环境与变更范围选择来源，**不要**为了改一处重新生成并重传整份脚本：

| 场景 | 选择 |
|---|---|
| 脚本较短，或首次提交时正文已在当前上下文中稳定生成 | 直接传内联 `script` |
| 外部 Agent 已在自己的工作区维护完整脚本，或脚本较长、需要多轮修改 | 把完整 UTF-8 脚本放在服务端可访问的 HTTPS 地址，通过 `script_url` 提交 |
| 外部 Agent 只修改服务端现有脚本中的一个精确片段 | 在实时 Schema 支持时使用 `script_patch`，携带当前脚本摘要和唯一匹配的改前、改后文本，避免覆盖并发更新 |
| 内部 Max Agent 在同一项目 `/workspace` 中维护脚本文件 | 仅在内部实时 Schema 暴露时使用 `script_file`；外部 Agent 禁止使用 |

完整脚本来源、局部补丁和路径参数的互斥关系以实时 Schema 为准。只修改输入输出定义、依赖或其他配置时，**不要**顺带重传未变化的脚本；使用 URL 或补丁后仍进入同一套 Preview、保存、上线和反读流程，不得降低验证层级。

1. 从前期确认的方案冻结业务职责、根对象输入输出定义、是否需要业务事件及其契约、正式运行入口、代表性输入、文件与副作用边界
2. 反读工具集成员和上线状态，确认全部可用
3. 有辅助文件时完成上传
4. `preview`——按返回的字段、工具、路径和确定性规则修**同一份草稿**
5. `create` 或 `update`——保存后反读标识、命令标识、输入输出定义、业务事件契约、依赖和版本
6. `bubble` 启动并轮询到终态——**必须**复用同一个运行标识
7. 检查运行结果的步骤、轨迹、覆盖率、未触达工具、最终输出和错误
8. 读取 [Workflow 验收检查清单](../checklists/Workflow验收检查清单.md) 做语义验收；不通过就更新原 Workflow 并重跑

Preview 对业务事件采用**条件硬门**：业务事件契约和 `emit_business_event` 调用必须同时为空，或同时构成完整闭环。未声明且未调用时按无事件 Workflow 验证；一旦声明或调用，至少声明并调用 `stage_started` 和 `stage_result`，首个业务动作前保证已经发布 `stage_started`，每条可达 `return` 前保证发布 `stage_result`，受控业务失败分支可用 `stage_failed`；声明未使用、调用未声明或类型不一致均拒绝保存。Preview 只证明静态生命周期闭合，不证明事件已入库。

**产出文件的交付链**：FastAgent 在隔离会话里运行，生成的文件落在它自己的任务点目录，不会自动出现在本 Workflow 的产物目录。平台信任**真实返回**：FastAgent 或工具返回的 workspace 路径可以直接写进本节点输出、在节点间传递。要**随交付给用户**的文件则须在最终节点收口：把文件收进 `ctx.output_dir`（复制，或由脚本写入内容），以 `workspace-file-path` 在 `output_schema` 声明，并进入 `delivery.mapping`（14.1 规则一）——***交付守卫只登记最终节点产物目录内的文件，留在会话目录里的路径到不了用户手上***。

跨运行引用先前产物**必须持有其绝对 workspace 路径**（经状态文件或输入字段传递）——每次运行的产物目录都不同，用"当前目录 + 命名约定"拼路径读取先前运行的文件，第二次运行起必然找不到。增量修订场景沿用先前运行的产物时，凡要随本次交付的文件，先复制进本次 `ctx.output_dir` 再进 mapping；跨运行的历史路径只应存在于状态文件与输入字段，***出现在交付 `output` 的文件字段里必被 `ORCH_DELIVERY_FILE_UNISOLATED` 拒绝***。

**运行前必须先查对外副作用。** 发信、通知、发布、扣费、创建远端对象、写正式业务状态这类动作，**必须**用运行环境提供的演练标记挡住，并返回满足输出定义的明确未执行状态。**禁止**用演练标记跳过普通工具调用、跳过输入输出管路，或绕过桩值造成的下游失败。

**运行返回"执行完成"不等于业务验证通过。** 它只说明脚本在本次输入下正常返回并满足已声明的契约。**禁止**据此标记通过或向开发者宣称验证完成——未触达的工具和分支**必须**列为盲区。

单条 Workflow 的 Preview、bubble 和语义验收属于自动制作门，不需要向开发者逐条申请全真运行。FastAgent 内容、未触达分支和外部副作用盲区保留到整包端到端全真验证阶段统一处理。

### 17.4 执行结构表同步

修改任何 Workflow 脚本或结构（步骤、依赖、并行组、所用 FastAgent），**必须**同步更新执行结构表的对应条目并回写工单权威快照（路由器 5.3）。条目内容变化后其指纹随之变化、状态自动回退 `pending`——下一次方案挑战与验收**只处理这些回退条目**，未变化条目不重复检查。脚本与表不一致时以修正一致为先，**禁止**带着不一致进入 S4。

## 12. 业务事件设计

### 12.1 何时声明

写事件契约前先读 [Workflow 验收检查清单](../checklists/Workflow验收检查清单.md) 的事件章节，**尤其"必查反模式"小节**——多数事件设计错误（如为界面声明 `stage_progress`）在那里已被点名。

业务事件表达 Business Runtime 和业务应用可以稳定消费的公开事实，不是工具调用日志。只有确实需要业务路线可观察性、业务应用状态、业务表单握手或 Delivery Review 时才声明；未声明事件的 Workflow 不得调用 `emit_business_event`。事件类型、事件声明字段和原语签名**必须**以当前 `workflow_tpe_manage` 实时 Schema 与 `workflow_single` 规范为准；实时契约没有暴露业务事件能力时，相关 Workflow 裁决为 `platform_blocked`，**禁止**用标准输出、普通消息或自造 `print_event` 调用模拟。

### 12.2 正式运行入口

正式运行入口由事件契约决定：

| Workflow 事实 | 正式运行入口 | 身份规则 |
|---|---|---|
| 没有业务事件契约，脚本也没有调用 `emit_business_event` | 可以按实时工具契约直接派发单 Workflow | 不要求 Business Runtime 身份 |
| 单条 Workflow 声明或调用业务事件 | **必须**先写入只有一个节点的业务路线，再从该路线启动 | 服务端持久化并生成 `business_id`、`orchestration_id`、`workflow_runtime_id` |
| 多条 Workflow 构成固定业务路线 | **必须**写入多节点业务路线并从入口启动 | 同一运行实例中的节点共享服务端建立的 Business/Runtime 上下文 |
| 制作期 Bubble | 使用服务端分配的验证身份，不属于正式业务实例 | 验证身份只用于本次 Bubble，禁止复制到正式运行 |

脚本、SystemAgent、外部 Agent、业务应用和 MCP 调用方都**不得**生成、猜测、复用或补写上述正式运行身份。出现 `Workflow business event requires persisted Runtime identity` 时，先检查是否把带事件 Workflow 直接派发；这通常是运行入口错误，不是最终用户输入或 Workflow 业务逻辑错误。若是正式运行，建立或修正单节点/多节点业务路线后从路线入口重跑；若是 Bubble，服务端没有分配验证身份则裁决为 `platform_blocked`，不得在脚本里伪造 ID 绕过。

**运行期补充（三通道，不改变上表的制作侧要求）**：上表约束的是制作侧结构——带事件的 Workflow 必须建单节点路线，业务应用与路线启动经由 Business Runtime 运行。除此之外，平台还允许最终用户在聊天中直接派发**已挂载**的 Workflow：该通道下业务事件自动降级为不生效（无业务应用、不写业务事件），属于平台运行期行为，非设计决策，制作侧不设计也不引导入口选择。Runtime 身份按三态判定：三元身份齐全为路线内节点派发；全部缺失为聊天直调、事件自动降级；**部分缺失**为内部链路错误，服务端以 `WORKFLOW_RUNTIME_IDENTITY_INCONSISTENT` 拒绝——遇到该错误按 SD-诊断与维护 的报错对照排障，身份仍然禁止伪造。

### 12.3 生命周期硬门

声明业务事件的 Workflow，其生命周期覆盖遵守以下硬门：

| 业务节点 | 要求 |
|---|---|
| 脚本开始执行 | 在必要的输入读取后、首个业务动作前，***必须***发布 `stage_started`，名称使用最终用户能理解的业务阶段，不使用 Workflow、节点或工具名称 |
| 正常结束 | 每一个可能正常 `return` 的分支，在结果已经真实成立后，***必须***发布 `stage_result`；事件载荷与最终返回对象分别遵守各自契约，不能用事件替代返回值 |
| 产生文件交付物 | 脚本只把真实文件写入 `ctx.output_dir` 并按 `output_schema` 返回路径；要交付的文件路径字段同时进入最终节点 `delivery.mapping`（规则见 14.1）。Runtime 完成 Artifact 登记后自动发布 `artifact_ready`。脚本不得声明或发布该平台事件 |
| 路线最终结果可交付 | 最终节点按 `output_schema` 正常返回，编排完成 Delivery mapping、文件登记（输入即 mapping 的求值结果）和冻结后，Runtime ***必须***自动发布 `delivery_ready`；脚本不得声明或发布。该事件只表示具备审阅条件，不表示最终用户已经接受 |
| 可控业务失败 | 脚本明确识别并以业务失败结束的分支，***必须***发布 `stage_failed`；无法在脚本内可靠解释的技术异常仍让异常冒泡，禁止捕获后伪装成业务成功 |

### 12.4 事件密度与契约字段

各事件类型的 `payload_schema.required` **必须**包含对应平台字段（preview 保存时校验，缺失直接拒绝写入；业务字段在此之外自由声明）：

| 事件类型 | `required` 必须包含 |
|---|---|
| `stage_started` | `stage_key`、`stage_name` |
| `stage_result` | `stage_key` |
| `stage_failed` | `stage_key`、`error_code`、`message` |
| `attention_required` | `level`、`title`、`message` |
| `stage_progress` | `stage_key`、`progress_percent` |

除上述硬门外，事件密度由业务可见性决定：细分业务阶段的额外 `stage_started`、值得单独展示的中间 `stage_result`，以及不要求最终用户回答的 `attention_required`，均***建议结合配套业务应用的消费需要考虑***。Agent 在方案 Plan 中提出事件候选及其消费用途（已有 app-creator 线的系统设计时与其对齐），由开发者确认；只有确认系统确实需要据此更新阶段、结果模块或提醒时才声明。**禁止**在每个 `tool()` 后机械发事件。不为进度条声明 `stage_progress` 作为系统契约。

什么值得投影给最终用户、何时渲染、渲染的意义是什么，判断依据见 [平台对象与运行模型](../references/平台对象与运行模型.md)。

除 Runtime 自有的 `artifact_ready` 与 `delivery_ready` 外，脚本发布的事件都**必须**先在 Workflow 资产中声明稳定的 `event_key`、平台事件类型、版本、成立条件和根对象 Payload Schema，再由脚本调用当前受控业务事件原语。脚本不得动态拼接事件名，不得把内部 ID、原始工具返回、提示词、脚本、敏感信息或未脱敏错误放进载荷。事件声明有不兼容变化时升级事件版本；已有配套业务应用在消费该包时，同时通知 app-creator 线把系统契约视为已变化重新验收。

当前受控原语为 `emit_business_event(event_type=..., event_key=..., payload=...)`。`event_type` 与 `event_key` **必须**使用非空字符串字面量，`payload` **必须**是对象；调用只能引用资产中同名、同类型的已发布事件契约。业务事件契约的每一项包含 `event_key`、`event_type`、`event_version`、`description` 和根对象 `payload_schema`，且 `payload_schema.additionalProperties` 必须为 `false`。具体字段仍以实时 Schema 和 `workflow_single` 为最终事实源。

创建或更新 Workflow 时，直接通过 `workflow_tpe_manage(action="create"|"update", business_event_contracts=[...])` 随执行契约一并写入；写入后使用 `get_asset(asset_type="tpe", id=...)` 反读确认脚本与事件契约一致。不要另建事件配置文件，也不要用脚本常量代替资产契约。

业务事件是单向可观察性，不改变既有交互职责：入口表单、运行中补充表单、Runtime 恢复和最终审阅继续使用编排的 Business/Runtime 握手。`attention_required` **不得**复制一个正在等待最终用户填写的 `business_interaction`，Runtime 发布的 `delivery_ready` **不得**代替 Delivery Review。`runtime.delivery_ready` 的 `PublicDelivery` 结构与固定 `delivery.review` 审阅表单是平台固定契约（消费侧细则以脚手架仓当前文档为准，app-creator 线执行）；不得要求任何消费方从 Workflow 自定义事件或原始消息帧猜交付结构。

## 13. 对外声明来源类 Workflow 的证据要求

研究、资讯、调研这类会对外声明信息来源的 Workflow，**必须**保留可校验的"结论—证据"链：

- 上游把结论与其引用的证据标识、证据的来源地址、域名、日期作为**结构化对象整体传递**，**禁止**只拼接摘要文本后丢掉证据
- 下游每条结论**必须**带非空的证据引用，来源字段**只能**复制被引用证据的真实值，**禁止**改写
- 步骤输出与最终输出定义**必须**在根级声明证据契约

运行时会拒绝不存在的引用和被改写的来源。最终文档里的具体断言仍需逐条内容核对，**禁止**用"文件已生成"代替核对。

## 14. 业务路线编排组装

### 14.1 制作顺序

需要业务事件、业务表单握手、Delivery Review、业务应用入口或多 Workflow 固定依赖时，全部节点 Workflow 都已挂载并通过单体验收后，才能写编排。带业务事件的单条 Workflow 必须写成只有一个节点的业务路线；多条 Workflow 按真实依赖写成多节点路线。制作顺序：

1. 为每条候选路线冻结稳定职责、入口表单、路线输入定义、到达标准
2. 确认每条 Workflow 都有根对象输入输出定义、当前版本的运行证据；声明业务事件的节点还要确认当前事件契约完整
3. 画路线内依赖图：所有节点可达、无环，依赖只表达数据与执行先后
4. 逐字段建立入口映射、节点映射和交付映射，核对路径、必填、基础类型和文件格式
5. 制作期可预知的最终用户输入全部放入口表单；只有上游成功后才知道、且要喂给未派发下游的输入，才用运行中交互
6. 需要 Agent 在节点成功后审查或处理异常时，在该节点声明介入，写清指令和可验证标准
7. 读取 `stages/S1-业务设计.md` 第 16 节已确认的交付对象、最终审阅形态、审阅责任方、最终用户体验和风险；质量检查、内容核验或节点 `sa_handoff` 不能代替最终审阅
8. 按已确认方案声明唯一的最终交付与审阅动作。当前有四种动作：结束业务、以结构化原因拒绝交付并结束业务、跳转到另一条路线（**必须**指向真实存在的路线且入口匹配）、交由 Agent 处理；Agent 不得根据实现便利自行删减、增加或替换动作。两条声明规则：
   - **声明字段**：每个动作只写 `action_key` 与 `kind`，跳转动作另加 `orchestration_id` 与可选 `target_input_mapping`。***`label` 与 `description` 不可写***——保存门拒收未知字段，按钮中文文案由 Runtime 按动作类型生成；
   - **跳转的两种形态，按"这一跳需不需要用户新输入"二选一**：不需要 → 声明 `target_input_mapping`（每项 `source='delivery'` 从冻结交付取值，**必须覆盖目标路线 `input_schema` 全部 required 字段**，保存门校验），用户点跳转直启目标路线、不弹入口表单；需要（如选篇、写修改意见）→ 不声明映射，跳转弹出目标路线入口表单，已知信息的预填由业务应用实现（app-creator 线）
9. 按已确认动作设计最终审阅接受路径；存在最终用户修订、重做或改路线语义时，同时设计一条新建 Runtime 且保留当前 Delivery 的路径。真实资产与已确认业务路线图不一致时，停止写入并回到 `stages/S1-业务设计.md` 第 16 节更新 Plan，**不得**在本阶段重新替开发者做产品决策
10. 整体替换保存；对象较长时可按 9.3 在实时 Schema 支持后通过 `workflow_orchestration_url` 提交完整 JSON。按服务端返回的节点、字段和路径错误精确修**同一个对象**，**禁止**自行发明兼容字段

**交付映射（`delivery.mapping`）的三条规则**：

1. ***要交付的文件，路径字段必须进 mapping***：Artifact 登记的来源是 mapping 的求值结果——只在 `output_schema` 声明并返回、未进 mapping 的文件不会被登记，界面会显示无产出文件。文件路径字段可以嵌套在对象或数组里（如 `$.items[].card_paths[]`），求值结果中的 workspace 路径会被逐个登记，不需要为登记而拍平结构；
2. **缺失字段自动跳过**：mapping 引用的字段在本次返回中缺失时跳过该交付字段，必填与否由 `output_schema` 的 `required` 裁决——仅部分分支返回的字段（如失败分支的 `blocked_stage`）可以放进 mapping；
3. **文件路径须可验证**：mapping 引用的 workspace 路径要求是 `output_schema` 声明过、且位于本节点产物目录内的文件，二者之一不满足则交付被拒（`ORCH_DELIVERY_FILE_UNVERIFIED` / `ORCH_DELIVERY_FILE_UNISOLATED`）。

入口映射（`entry.input_mapping`）同理：表单未填的可选字段被跳过，必填由路线 `input_schema` 的 `required` 裁决；需要默认值的字段用映射的 `default` 变换声明。

保存成功**只证明静态结构合法**，不能替代整条路线的运行证据（见 `stages/S4-验证与修正.md`）。

### 14.2 静态接缝检查

保存并反读编排后，完成静态接缝检查：入口、节点依赖、扇出汇合、mapping、运行中交互、Delivery 和 Review 必须引用真实资产并满足当前契约；单节点路线也必须检查入口映射、唯一 Delivery 和 Review。mapping 检查含***文件覆盖***：要交付的文件路径字段必须都在 mapping 里——漏映射的文件不会登记为 Artifact（14.1 规则一），发现缺失即回改 mapping 再通过。该证据仍属于第一层 Preview/静态契约，不能证明路线已经执行。不得用一条或多条单 Workflow 轨迹拼接成路线证据，也不得自行创建图执行器或伪造 Runtime 身份。`emit_business_event` 在单 Workflow bubble 中仍必须取得服务端分配的验证 Business/Runtime 身份；缺失时该 Workflow 的 bubble 裁决为 `platform_blocked`。正式运行时，带业务事件的单 Workflow 不能直接派发，必须通过单节点路线取得持久化 Business Runtime。FastAgent 真实内容、显式外部副作用、业务事件真实发布和跨路线跳转统一留到第四层端到端全真运行验证；业务应用对事件的消费在 app-creator 线验收，不属于本包证据。

路线级 Bubble 的执行与证据纪律见 S4-验证与修正。

### 14.3 面向界面的公开语义

已规划配套业务应用时，编排完成还要冻结一份**面向系统的公开语义**：每条路线的业务名称、适用条件、入口表单目的、最终用户可理解的里程碑、可能出现的最终用户交互、最终交付和到达标准。它们是 app-creator 线 A1 契约基线的事实输入，**不得**用 Workflow 名称、节点 ID 或工具步骤代替。

## 15. 信息归属与知识写作

### 15.1 信息归属

**同一条信息只写在一个地方。** 这是所有配置决策的根本依据。

| 信息 | 权威位置 |
|---|---|
| 单个工具的用途、参数、正式 Schema | 工具组（MCP 层工具描述） |
| 工具或 FastAgent 的搭配方式、调用顺序 | 工具集使用指南 |
| FastAgent 的自包含推理方法 | FastAgent 提示词 |
| 普通任务点的交互式执行方法 | 任务点提示词 |
| 单阶段稳定步骤与数据流 | Workflow 脚本与输入输出定义 |
| 单节点或多节点业务路线的入口、依赖、映射、中途交互、最终交付 | 业务路线编排 |
| 业务终点、候选路线、里程碑、选路条件、权限、前置检查、知识读取时机 | `apc_skill` |
| 长知识、模板、案例、字段字典、详细 SOP | 场景 Skill 文件 |
| 数据语义与查询规则 | 数据集使用指南 |
| 页面与公开交互契约 | 业务应用源码（app-creator 线制作，不属于场景包资产） |

常见放错层级的情况：

- 工具集使用指南里重复单个工具的描述（那是工具组的事）
- 场景 Skill 文件里写 FastAgent 的内部逻辑（那是 FastAgent 提示词的事）
- FastAgent 执行时要用的写作规范、规则库挂在场景 Skill 文件下（FastAgent 读不到，见 15.2 可见性边界；按执行者归属挂到对应 FastAgent 名下）
- 工具集使用指南里写业务 SOP（那是场景 Skill 文件的事）
- `apc_skill` 或工具集指南里重复已固化在编排里的依赖图（形成两份真相，见约束 9）
- 同一信息出现在两个地方（必有一个放错了）

反过来也**不要**为了消除重复，把运行时 Agent 每轮都必须知道的业务路由、关键前置检查、能力选择和加载时机从 `apc_skill` 里删掉。

### 15.2 文本字段与 Skill 文件的分工

| 资产 | 文本字段（始终注入） | Skill 文件（按需读取） |
|---|---|---|
| 场景包 | `apc_skill` | 场景 Skill 文件 |
| 工具集 | 使用指南 | 工具集 Skill 文件 |
| 普通任务点 | 提示词模板 | 任务点 Skill 文件 |
| FastAgent | 提示词内容 | FastAgent Skill 文件 |

区分标准：**Agent 每轮都需要知道的写文本字段，做某件具体事时才需要查的写 Skill 文件。**

文本字段适合决策规则、约束、路由逻辑。Skill 文件适合大段领域知识、脚本模板、案例、示例输出、详细 SOP。

每个上传的 Skill 文件**必须**被对应文本字段在明确阶段按名称索引，否则 Agent 只看到文件名、不知道何时该读。

**可见性边界（知识不随挂载关系流动）**：每类 Skill 文件只对它挂在名下的执行者可见——场景 Skill 文件由项目里的 SystemAgent 读取；FastAgent 运行在隔离会话中，能读到的只有**自己名下**的 FastAgent Skill 文件和所挂工具集的 Skill 文件；Workflow 脚本只读自己任务点目录（`ctx.skill_dir`）。***场景包挂再多行业知识，FastAgent 一篇也读不到；FastAgent 执行要用的知识必须挂到它自己名下***，并按上面的索引规则在其提示词中写明何时读哪篇。

### 15.3 Skill 颗粒度标准

**从理想态反推颗粒度。** 凡是希望减少的失败、绕行或沟通轮次，都**必须**有对应的可执行指导。

| 目标消除的瓶颈 | 至少要写到什么程度 | 主要归属 |
|---|---|---|
| 不知道先做什么 | 阶段目标、前置检查、能力选择、交付条件 | `apc_skill` |
| 不知道工具怎么搭配 | 先取得什么结果，再由什么能力消费 | 工具集使用指南 |
| 不知道参数怎么准备 | 必填结构、来源、约束、失败处理 | 工具集 / 场景 Skill / Workflow 定义 |
| 找不到能力 | 条件 → 加载哪个能力域或读哪个文件 | `apc_skill` |
| 缺领域知识 | 可执行规则、数据字典、案例 | 场景 Skill 文件 |
| 交付结果不稳定 | 输出模块、质量标准、验收证据 | `apc_skill` 加对应执行资产 |

**不达标的写法**（缺前置步骤、缺判断条件、缺产出定义）：

- "创建创意，配置品牌组件、标题组件"——没说前置步骤和参数结构
- "使用素材处理工具进行裁剪"——没说用哪个工具、什么条件下用
- "输出结构化投放方案"——没定义方案必须包含哪些模块

**达标的写法**：

- "创建创意前：先取得模板列表，再查组件依赖，最后按模板要求准备素材"
- "素材处理判断：尺寸不对走缩放；格式不对走转换；需要生成图走生图再入库"
- "投放方案必须包含：推广目标、日预算、定向策略（地域加年龄加兴趣）、创意方向、投放时段"

**禁止**"完善流程""调用相关工具""输出高质量报告"这类不可执行的空话。**必须**补齐触发条件、输入来源、关键判断、期望产出和失败处置。

### 15.4 apc_skill 必须包含什么

`apc_skill` 是场景包最高优先级的知识注入，写好它是本项工作的核心产出。至少覆盖：

1. **场景问题与业务终点**：解决什么问题、适用条件是什么
2. **里程碑**：分几个阶段、每阶段目标和最终用户可见产出
3. **候选路线与选路节点**：不同目标或前置状态对应哪条路径、在哪里判断走哪条
4. **必需输入、预期交付、验收标准**
5. **权限边界**：哪些 Agent 可以自主判断、哪些必须最终用户决定、哪些属于高风险授权；这些边界由开发者在制作 Plan 中确认
6. **未被其他资产固化的关键业务规则、前置检查、能力选择**
7. **Skill 文件索引**：在哪个阶段按名称读取哪个文件

不应包含：具体实现细节（选择器、路径、接口参数格式、代码片段），以及约束 9 列出的禁写内容。

### 15.5 工具集使用指南必须包含什么

只写**工具之间的关系**：适用条件、输入怎么衔接、结果怎么审视、失败怎么处理。单个工具的说明留在工具组。

已经由 Workflow 脚本固化的调用顺序**不要**在这里再写一份。这里只说明"该 Workflow 是这条稳定流程的首选入口"，以及底层工具或 FastAgent 各自可独立处理的情况。

多个工具或 FastAgent 需要配合时**必须**写搭配模式。工具彼此独立、且不含 FastAgent 时可以为空，不算缺陷。

## 16. 场景包草稿组装与联动校验

### 16.1 场景包与 Workflow 工具

| 工具 | 用途 |
|---|---|
| `scene_package_manage` | 场景包 `create` / `get` / `update` / `online`，以及业务路线级 `bubble`。`create` 默认克隆官方基础场景包并返回未上线草稿；`get` 不需要 `task_id`；`bubble` 对已保存路线执行制作期整图演练，默认返回精简证据，仅在失败排障时用 `evidence_level="full"` 读取完整轨迹；它不代替单 Workflow Bubble 或端到端全真运行。长 `apc_skill` 或完整编排 JSON 可在实时 Schema 支持时分别通过 `apc_skill_url`、`workflow_orchestration_url` 提交 |
| `workflow_tpe_manage` | Workflow 的 `preview` / `create` / `update` / `attach` / `online` / `bubble`。外部 Agent 可按变更范围选择内联 `script`、完整 `script_url` 或更新时的 `script_patch`；内部 Max Agent 还可在实时 Schema 支持时使用 `script_file` |
| `update_scenario_package_logo` | 设置场景包 Logo。**必须**先用 `file_to_url` 声明 Logo 用途上传图片，拿到文件引用后再调用本工具 |
| `scene_package_ui_bundle` | 存量附属界面的维护（下载官方模板、上传定制源码、部署、查状态）；新业务应用一律走 app-creator 线，不使用本工具 |

前置依赖：`workflow_tpe_manage(create)` 要求**场景包草稿已存在、且依赖工具集已通过上线检查**。

场景包只能直接挂载工具集、任务点（含 Workflow）、长期数据集和固定版本数据集模板。工具组和 FastAgent **必须**先组进工具集，再把工具集关联到场景包。

单节点或多节点业务路线都通过场景包的编排字段**整体写入**，采用整体替换语义；**禁止**把它复制进 `apc_skill`（约束 9）。

### 16.2 场景包草稿组装

调 `scene_package_manage(create)` 建离线草稿。当前 `create` 默认克隆官方基础场景包，**必须**立即反读继承到的能力、关系和告警，只改真正需要改的部分。

写入较长的 `apc_skill` 时，可以按 9.3 在实时 Schema 支持后使用 `apc_skill_url`；平台解析后保存的仍是 `apc_skill` 正文。反读时按 15.4 检查正文完整性、颗粒度和禁写内容，不以调用成功或 URL 可访问作为验收。

保存场景包标识，后续修复**更新同一草稿**，**禁止**新建平行资产来绕过错误。

该草稿此时是后续 Workflow 的真实归属容器，不代表 Workflow、最终关联或业务路线已完成。提案包含 Workflow 时，创建并反读草稿后进入第 11 节，在同一草稿上创建、挂载和验收 Workflow，再写入最终关联与业务路线编排。

场景 Skill 文件按 9.3 的两步链路处理：先用 `file_to_url` 声明 Skill 文件用途取得引用，再用 `scene_package_manage(update)` 绑定。**默认合并**会保留既有文件（例如官方包继承来的调度策略文件），整体替换会**覆盖整个目录**——除非确认要清空，否则用合并。

依赖资产的 Skill 文件同理：创建时可以直接带文件引用，已经创建完的用 `upload_skill_files` 补挂——注意它的缺省是整体替换，补挂时显式传 `skill_files_mode="merge"`（见 9.3）。

开发者提供了 Logo 图片时，先用 `file_to_url` 声明 Logo 用途上传，再用返回的文件引用调 `update_scenario_package_logo`。**禁止**用修改文本字段的方式直接写入图标地址，**禁止**把临时上传地址当作 Logo 保存。开发者没提供图片时不调用，保持默认图标。

### 16.3 创建后联动校验

每步完成后检查联动关系：任务点关联变动后检查工具集是否同步；资产被替换后检查 `apc_skill` 里的引用是否失效；工具集成员变化后检查使用指南是否还准确。

此时**不要**向开发者宣称场景包可以直接使用——还没验收。

## 17. 出口条件

以下全部满足后，按路由器 4.1 进入 S4：

- 全部资产 Preview 通过；含 Workflow 时，每条完成单条 bubble 与语义验收（11.3 第 8 步）；
- 执行结构表无 `pending` 条目（11.4 同步与增量重挑战已完成）；
- 关键 FastAgent 的样例选择流程已完成（10.2）；
- 需要编排的路线已保存、反读并通过静态接缝检查（14.2）。

以上全部满足后，按路由器 6.1 落一条 `stage_exit` 账，再进入下一阶段。
