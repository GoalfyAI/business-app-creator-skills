# 验收报告：数据说明与完整样例

写 `docs/studio/acceptance/data.json` 时照这里写，生成用 `build_studio_doc.py acceptance`。**写什么**按 `agenticapp-stage-4-acceptance` 的[验收报告模板](../../agenticapp-stage-4-acceptance/assets/验收报告.md)、[证据与未测](../../agenticapp-stage-4-acceptance/references/证据与未测.md)，上线结果按 `agenticapp-stage-5-launch` 的[上线结果模板](../../agenticapp-stage-5-launch/assets/上线结果.md)。

页面长这样：四个结论数（由脚本按条目算）→ 业务路径检查（每条路径的每一步通过没有、依据是哪几条条目，可回放）→ 好不好你说了算 → 未测的 → 实际跑出的结果 → 自动发生的 → 实际花费 → 全部条目（折叠）→ 修改记录 → 上线结果（⑤ 才有）。

结论数、未测条数都由脚本从 `items` 和 `extra_untested` 算，不手写；条目之外没验证的事写进 `extra_untested`，一样算进未测。

## 字段

| 字段 | 必填 | 写什么 |
|---|---|---|
| `app`、`version`、`updated`、`changes` | 是 | 同需求说明 |
| `impact` | 是 | 还有没通过、未测的，一句话说清影响；都通过写「全部通过」 |
| `items[]` | 是 | 方案里的全部验收条目：`id`（和方案一致）、`title`、`result`（`通过` / `没通过` / `好不好你说了算` / `未测`）；没通过且开发者选了接受的加 `"accepted": true`；不是未测的写 `how`（页面条目写操作步骤，业务条目写用了哪个例子）、`seen`、`evidence`（这次你自己取得的：截图、断言原文、库里查到的那一行）；页面条目的截图写进 `shots`；要他判断的另写 `actual`（实际结果原文）；未测的写 `untested` |
| `items[].untested` | 未测时 | `kind` 只能是下表之一；标「要补充」的写 `detail`。原因和「这意味着」由脚本按 `kind` 填 |
| `extra_untested[]` | 有就写 | 条目之外没验证的事（例如在线预览里的页面没打开过）：`title`、`kind`、`detail` |
| `paths[]` | 是 | 业务路径：`name`、`detail`、`nodes[]`（`title`、`state`：`pass` / `fail` / `blocked` / `unknown`，`items`：依据的条目编号，`note`：受阻、未验证时写为什么）、`links[]`（相邻两步之间怎么衔接，比节点少一条） |
| `results[]` | 是 | 实际跑出的结果：`title`、`text`、`test_data` |
| `automation` | 是 | 自动发生的那件事试的结果；没有自动化写「没有」 |
| `costs[]` | 是 | `action` `actual` `estimate` `wait` |
| `fix_log[]` | 重测后 | `problem` `change` `retested[]` |
| `launch.items[]` | ⑤ 上线后 | 按顺序七项，`title` 依次是：上线的版本、④ 验过什么、未测的、实际花了多少、发布会怎样、发布要准备的、你可以做的事；`text` 按上线结果模板写 |

未测只能是这几类（`证据与未测.md` 的原文，脚本按 `kind` 填原因）：

| `kind` | 原因 | 要补充 |
|---|---|---|
| `login` | 要用真实账号登录才看得到：平台登录身份 | |
| `bridge` | 要在 GoalfyMax 里打开才看得到：提醒、授权和付款窗口 | |
| `studio` | 要在 Studio 窗口里打开才看得到 | |
| `cannot_run` | 演示版跑不起来 | 做过的处理和错误原文 |
| `not_placed` | 你说先不放到在线预览 | |
| `sample` | 缺你手上的样本 | 哪一份 |
| `online_page` | 在线预览里的页面我打不开 | |
| `schedule` | 到点触发要等真实时间 | |
| `catalog` | 从目录或分享打开要先发布 | |
| `cannot_fail` | 测试中造不出这种失败 | 试过哪些做法 |

路径节点的结论要和条目对得上：标 `pass` 的，依据的条目都要是「通过」；标 `fail` 的，依据里要有一条「没通过」。脚本会核对。

## 容易写错的

- 只写通过的路径：没通过、受阻、没验证的路径也要画出来，开发者要看到哪里没走通。
- 页面只在演示版上试过，在线预览里没打开过，却不写：写进 `extra_untested`（`online_page`）。
- 用回放、截图代替验证：路径节点的结论只能来自条目的证据。
