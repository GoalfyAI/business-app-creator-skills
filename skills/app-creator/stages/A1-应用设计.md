# A1 应用设计

从一个已上线的场景包出发，设计出一个完整的业务应用：它是什么、给谁用、场景包给了它什么入口和出口、存什么数据、有几页、每页读什么写什么、字段的可编辑性怎么在页面上体现、文件在哪里出现。做法与场景包线一样：先向开发者要参考资料，再拿一份《业务应用计划书》（每页截图展示 + 后端功能阐述）给开发者确认，确认后才进入 A2 / A3 制作。

## 1. 进入前提

- 目标场景包**已上线**（未上线转 scene-creator 先完成）；
- 有 `write` 工单；
- 开发者已说明应用的业务意图：给谁用、解决什么持续经营问题、用户一天/一周会在这里做几次什么事。

**进入后的第一个动作是向开发者要参考资料**（与 scene-creator S1 向开发者要参考资料、打法同一做法），一次问清、记进工单：

| 问什么 | 为什么 |
|---|---|
| 页面设计参考：喜欢的产品、截图、品牌规范、已有的设计稿 | 决定 §5.5 第 3 步的设计方向；有参考就不必自己调研 |
| 想要的功能：对着 §2.2 的功能选择菜单逐项问“要不要、为什么” | 菜单里的每一项都要开发者定，缺的写“不做 + 理由” |
| 现有数据：Excel / 表格 / 其它系统导出，字段长什么样 | §4 数据设计的起点，模板字段贴用户真实数据而不是想象 |
| 谁来用、多久用一次、一次做什么 | 定页面的主行动与看板指标 |

拿不到参考也要记“无参考”，然后按 §5.5 第 2 步自行调研。

**定义**：业务应用 = 运行在 GoalfyMax 宿主 iframe 里的前端 App + 一个专属后端 + 每个用户各一份的 PG schema（业务应用数据集）。前两者打进**一个镜像、一个 Pod**（脚手架 `frontend/` + `backend/` 双目录），schema 由平台按**业务应用数据集模板**版本给每个用户各建一份；发布单位是独立资产 `business_ui`（自己的家族与版本，挂恰好 1 个场景包 + 至多 1 个模板）。

**它在平台里的地位**（SDK 4.0）：应用是与项目并立的**一级实体**——用户从宿主导航直接进入应用，一个应用实例可以创建并管理 **N 个项目**。所以应用不是“某个项目里的一块面板”，而是用户持续经营某件事的**工作台**：看现状（看板）→ 发起一次生产（创建项目跑场景包）→ 跟进（项目页）→ 产出回流入库 → 用户修正（数据管理）→ 再看现状。这条 SaaS 链路是一切设计的骨架。

**给谁用**：场景包的最终用户（店主、运营、销售……由开发者在访谈里定），不是开发者自己。每个用户看到的是**自己的**数据（schema 隔离 + 实例权限），协作场景由平台的 `permission`（`edit` / `view`）裁决——`view` 态必须置灰全部发起与写入口。

**由什么组成**（设计时逐项回答“有没有、几个”）：

| 组成 | 内容 | 由谁定 |
|---|---|---|
| 挂载的场景包 | 恰好 1 个（一期）；契约区按 `schema/packs/<pack_id>/` 分目录 | A1 §3 反读 |
| 业务应用数据集模板 | 至多 1 个；表结构 + 逐列声明 + 审计字段 | A1 §4 设计 → A2 落地 |
| 三个必备页面 | 首页、项目列表页、消息中心（脚手架硬约束：只约束存在且可达，不约束形态） | 脚手架 |
| 业务页面 | 四类原型按业务取舍：看板 / 数据管理 / 业务发起（入口表单） / 项目页（进行态 + 应答表单 + 交付审阅） | A1 §5 |
| 专属后端接口 | 三类：CRUD（编辑回流）/ 统计聚合（喂看板）/ 生产回流 | A1 §5 页面反推 |
| 前端私有状态 | `sdk.storage`：草稿、筛选、当前 businessId 等**界面意图**（32 key / 512 KiB） | 不存业务数据 |

### 2.1 项目：业务应用之下的一层

业务应用在项目**之上**：一个应用实例里，用户可以创建多个项目。**项目 = 用户的一次计划选择**——用户决定“这一次要干一件什么事”，一次编排运行连同它的入口表单、运行中表单、消息、文件、业务事件与交付，都装在这个项目里。项目是过程的容器，**不是**应用的数据面：长期沉淀的业务数据在业务应用数据集里，项目只通过 `system` 列（项目 id / `last_run_id`）与数据行关联。

开发应用时必须拿到**在这个应用实例里创建的全部项目**：`sdk.projects.list` 分页拉（打开 / 翻页 / 手动刷新时拉，禁轮询）+ `sdk.projects.onStatusChange` 按 `projectId` 就地更新（拉推成对）。列表只含本实例名下已受理的项目，两段式建项目的临时项目在首启受理前不入列表——这是设计使然，不是漏数据。

用户发起一次生产时只有两种选择，页面上要让他显式选：

| 选择 | 用户做什么 | 应用做什么 | 何时用 |
|---|---|---|---|
| **创建** | 点动作按钮 → 填入口表单 → 提交 | 必经保留件 `useProjectDraft(draftKey)` 拿草稿句柄（一个表单会话一个句柄）；提交时 `project.business.start()` 触发**两段式建项目**：先懒创建服务端临时项目，再发起编排；首启 `accepted` 后临时项目转正入列表；发起后跳转项目页 | 新的一件事、新的一个对象（新门店、新一期活动） |
| **复用** | 点动作按钮 → 在项目下拉框里选一个已有项目 → 填表单 → 提交 | 下拉框选项**只来自** `sdk.projects.list`（无本地记录、不猜 id）；选中后经 `sdk.getProject(id)` 的句柄 `business.start()`，消息进入所选项目、不产生新项目；后一条路线能读到前一条在同一项目里的交付文件 | 在同一件事上做下一步（编排 2 接着编排 1 的产出） |

创建态 / 进行态的分界由此而来（路由器约束 3）：**业务发起页是唯一的发起入口**，项目页只看进度、应答表单、审阅交付，不发起新编排。项目页里“再来一次”的需求，做法是跳回业务发起页并把该项目预选进下拉框。`permission='view'` 时创建与复用两个入口一起置灰。

### 2.2 功能选择菜单（拿给开发者逐项定）

下面是当前脚手架（`frontend/README.md` 三、SDK 速览与 `src/sdk/docs/`）真实提供的能力，按“必备 / 建议 / 可选”分级。**A1 要拿着这张表向开发者逐项问**，结果（做 / 不做 + 理由）写进《业务应用计划书》第 ⑤ 章；勾选的每一项都要在 §5 页面设计里落到具体页面，并在 A4 §4 自动化测试门里有对应用例。

| 等级 | 功能 | 靠什么实现（正本） | 说明 |
|---|---|---|---|
| **必备** | 首页 / 项目列表页 / 消息中心 | 脚手架硬约束；`useInbox`、`sdk.projects`（`business-ui-guide.md`） | 只约束存在且可达，形态自定；首页可以就是看板 |
| **必备** | 业务发起（入口表单，创建 / 复用两形态） | `useProjectDraft` + `project.business.start`、契约区 `getForms`（`business.md`） | 挂载的场景包有可主动发起的编排就必备（§2.1） |
| **必备** | 项目页（进行态：进度 / 应答表单 / 交付审阅） | 业务事件、`pending` / `reply()` 三次握手、`getRuntimeDelivery`、`display` 五字段（`business.md`） | 有业务发起就有它 |
| **必备** | `view` 权限只读态 | `sdk.session.permission`（`session.md`） | 全部发起与写入口置灰并说明原因 |
| **建议** | 看板（展示态） | 后端统计聚合 API（`backend/README.md`）、`sdk.theme` | 每个数值可溯源到表与口径；空数据引导态（§5.2） |
| **建议** | 数据管理（编辑态） | 后端 CRUD（幂等键 `X-Goalfy-Business-Request-Id`）、逐列可编辑性（§5.3） | 用户自主增删改自己的业务数据 |
| **建议** | 生产回流入库 | 后端回流 API + Workflow 经 `dscli_business_dataset` 写回（S3-2.4） | 没有回流就没有看板；入库语义（直接 / 草稿确认）在 §4.2 第 5 问定 |
| **建议** | 应用级文件库（资料库） | `sdk.file` upload / list / getViewUrl / download + `shared/ApplicationFileField`（`application-file.md`） | 不依赖项目的持久文件：打开应用就能上传资料、刷新后复用历史文件、把选中文件带进新项目的表单。用户有“反复用同一批资料”的诉求时选它 |
| **建议** | 项目文件（上传 / 预览 / 下载） | `project.upload`、`project.file.getViewUrl / download`、`shared/FileField` | 属于某个项目的文件：表单附件、过程交付物；上限 300 MB、扩展名黑名单由平台拦 |
| **建议** | 执行记录与已提交表单回看 | `getRuntimeForms`、`getRuntimeDelivery`（`business.md`） | 用户回看“我当时填了什么、产出是什么” |
| **建议** | Runtime 用户文件补传 / 删除 | 保留件 `useRuntimeUserFiles`（全量替换语义） | 对某次运行补资料 |
| **可选** | 表单预填 | `useFormPrefill` + 应用后端把用户数据铺底（S3-2.4 时机 1） | 用户不必重复填自己的门店 / 账号信息 |
| **可选** | Excel 等结构化文件在表单内预览 / 预填 | 文件照常上传得 path + 浏览器端解析表头与前几行（§5.4） | 两条路并行，解析失败不阻断上传 |
| **可选** | 可拖拽排序的数组字段 | 自绘表单页；顺序语义以 Workflow `input_schema` 为准（§5.4） | 选题排序、素材排序 |
| **可选** | 亮暗主题 / 多语言 | `sdk.theme`、`sdk.lang`（`ui-theme.md`、`session.md`） | 跟随宿主 |
| **可选** | 界面偏好与草稿持久化 | `sdk.storage`（viewer × 实例隔离，32 key / 512 KiB；`storage.md`） | 筛选条件、看板布局、未提交草稿；不存业务数据 |
| **可选** | 与项目内 agent 对话 | `project.chat` 发消息 / 拉历史 / 订阅实时；`sdk.ui` 切到宿主聊天面板（`chat.md`、`message-guide.md`） | 用户要在应用里直接和执行中的 agent 说话时选 |
| **可选** | 协作者与项目权限展示 | `project.info`（`project.md`） | 多人协作的应用 |
| **可选** | 打开外部链接 | `sdk.ui.openExternal`（宿主确认框后 noopener 打开） | 跳到第三方后台 |
| **可选** | 图表 / 移动端适配 | 图表选型自由；主行动在移动端可达（§5.5 第 4 步） | 按用户使用设备定 |

不在表里的能力（例如应用自定义 env、第三方密钥注入、后端主动推送）当前脚手架没有，**不许诺**；开发者要时记为开放项，找平台确认。

## 3. 场景包给了你什么（契约基线）

应用的**入口与出口全部由场景包定义**，不由应用发明。逐项**反读**（禁止推测），写成契约基线表记入工单：

| 接缝物 | 从哪反读 | 决定应用的什么 |
|---|---|---|
| **入口表单**（`schema/packs/<pack_id>/forms/*.json`，`inputSchema` 原样） | 场景包 `get_asset` + 脚手架契约区 | **入口**：业务发起页要实现哪几张表单、每个字段的类型/必填/文件字段；哪些字段可由应用预填（`useFormPrefill`）、哪些必须用户填 |
| **业务路线编排**（`orchestrations/*.json`：`entryFormId`、`formIds`、`delivery`） | 同上 | 有几条可主动发起的路线（= 几个“发起”按钮）；服务端中途会调起哪些表单（= 项目页要能应答的表单）；终态审阅形态（`user_gate+ask` 有动作按钮 / `user_gate+result` 自动交付 / `agent_gate` 只读） |
| **Workflow `output_schema` / `display`** | 场景包 Workflow 资产 | **出口**：交付页能渲染哪些业务字段（对比、清单、结论），`display` 五字段兜底；**生产回流**能入库的字段来源 |
| **业务事件契约** | Workflow 资产 `business_event_contracts` | 项目页的进行态能显示到什么粒度（有 `stage_*` 才有阶段进度；没声明就不做进度模块） |
| **面向系统的公开语义**（scene-creator S3-7.3） | 场景包工单 | 页面文案：路线的业务名、里程碑、交付、到达标准——**不用 Workflow 名、节点 ID、工具名** |
| **数据集读写通道**（scene-creator S3-2.4） | 场景包 Workflow 脚本 | 哪些字段由 Workflow 经 `dscli_business_dataset` **读**（应用要保证这些列有数据）、哪些由它**写回**（应用要展示这些产出列） |

**契约区为空或只剩演示包，说明上游未就绪：停止业务设计并报告**，不照截图猜字段。多包（v4）时每包一个目录、`form_id` / `orchestration_id` 全 App 唯一。

**先读场景包的《场景包制作书》**（场景包工单里的 `build_book`，S2 定稿版）：它的第 ⑧-6 章已经定了业务应用数据集的逐列字段、声明与读写来源，第 ⑧-7 章定了配套应用的页面清单、看板字段与可编辑列——**本阶段以它们为起点做细化，不推翻**；要改字段或页面范围，属于制作书口径变化，回场景包线沟通后再动。制作书里没有 ⑧-6/⑧-7（老包或未规划配套应用）时，才按本文 §4–§5 从零设计。

## 4. 数据设计（本阶段的重心）

应用表是**用户的业务资产**。先分类，再逐表回答五问。

### 4.1 先把数据分四类，放对地方

| 类别 | 例子 | 放哪 |
|---|---|---|
| **用户自己的数据**（用户在应用里记载、编辑的） | 门店档案、账号绑定、素材索引、禁用表达、目标与偏好 | 业务应用数据集，列声明 `editable:user` |
| **场景包运行期所需 / 产出的字段** | 每次运行的选题、生成结果、效果指标、回写的统计 | 业务应用数据集，列声明 `editable:agent`；这些列是 S3-2.4 里 Workflow 读/写的对象 |
| **系统字段** | 主键、`created_at` / `updated_at` / `updated_by` / `last_run_id` / `row_version`、项目与 Runtime 关联 id | 业务应用数据集，列声明 `editable:system` |
| **界面意图与实体引用** | 草稿、筛选条件、当前 businessId、已读态 | `sdk.storage`（viewer × 实例隔离），**不进库** |
| 文案、路由名、开关 | — | 代码 |

***不要把该进库的数据写成前端 mock 数组、静态 JSON、后端常量或占位符***——这是脚手架的第一条数据纪律。

进库的表再按**实体 / 情境 / 历史事件**三类组织（长期慢变的经营对象 / 决定“这一次怎么做”的目标与约束 / 只增不改的运行与效果记录），情境与历史事件挂在实体上——这套约定的正本在场景包制作书 ⑧-6（scene-creator S2 7.2），本阶段沿用它画出的运转链，不另起一套。

### 4.2 逐表五问

1. **存什么**：按 4.1 分类列出每列；看板要算的指标所需字段此刻就要有；“读历史数据优化后续选择”的预留字段也在这里定；
2. **逐列可编辑性**（约束 9）：`user` / `agent` / `system` 三态，**每列恰好一个写入方**——用户和生产都要写的信息，在模板阶段就拆成两列（用户填的 + AI 建议的），不靠运行期仲裁；
3. **审计**：每张有写入的表带四件套 + `row_version`；来源标记（`user_edited` / `generated`）落在哪列；
4. **冲突规则**：行级并发（用户在编辑页改用户列、生产同时重写产出列）靠 `row_version` 乐观锁——后写方重读重试；***没有“静默覆盖”这个选项***；
5. **回流入库语义**：生产产出**直接入库**还是**先作草稿、用户在编辑页确认后入库**——按业务风险定（对外表达类建议草稿确认，内部统计类可直接入库）。

### 4.3 文件怎么进数据面

数据集**只存路径与元数据，不存文件体**。三类文件各有来源与归属：

| 文件 | 从哪来 | 存什么 | 谁能改 |
|---|---|---|---|
| 用户现场上传（Excel、图片、素材） | 入口表单 / 数据管理页经 `project.upload` → 返回 `/workspace/...` 路径 | 表单值就是路径；要作为用户资产长期引用时，在数据集里存路径 + 文件名 + 上传时间（`editable:user`） | 用户（替换 / 清除） |
| 应用级持久文件（品牌手册、素材库、历史资料） | 应用内任意位置经 `sdk.file.upload` → 返回 `path`（不依赖项目、跨项目复用；`list` 能翻历史） | 表单值 / 数据集只存 `path` + `name` + `size` + 上传时间（`editable:user`）；作为 Workflow 输入时把 `path` 写进 formdata，宿主登记给目标项目 | 用户；源文件不因关联项目而移动或删除 |
| 过程交付物 | Workflow 写进 `ctx.output_dir`，经 `delivery.mapping` 登记为 `PublicDelivery.artifacts[].workspace_path` | 回流时存路径 + 所属 Runtime / delivery_id（`editable:agent`） | 生产（每次运行新增，不覆盖旧交付） |
| Runtime 用户文件 | 用户在执行记录页对某次运行补传/删除（`userFilePaths`，全量替换语义） | 不单独建表，读 Runtime 权威值 | 用户，经保留件 `useRuntimeUserFiles` |

产出：业务应用数据集模板草案（表 / 列 / 类型 / 逐列声明 / 审计字段 / 文件路径列），交 A2 落成真实模板。

## 5. 页面设计

### 5.1 页数从哪来

页数 = 三个必备页面 + 按业务取舍的四类业务页面。不多不少的判据：**每个页面对应用户的一个明确意图**，多个意图挤一页会让高风险交互（提交、删除）和浏览混在一起，一个意图拆多页会造成孤岛。

| 页面 | 必备？ | 用户在这做什么 | 数据从哪读 | 动作往哪发 |
|---|---|---|---|---|
| **首页** | 必备 | 落地、看待办红点、进入各处；可以就是看板 | `useInbox().unreadCount`、后端统计 API | 导航 |
| **项目列表页** | 必备 | 看所有归属项目的状态 | `sdk.projects.list` + `onStatusChange`（拉推成对，禁轮询） | 进项目页 |
| **消息中心** | 必备 | 跨项目待答表单、结果通知 | `useInbox()` | 进对应项目的应答状态 |
| **看板**（展示态） | 按业务 | 看现状、决定干什么 | 后端统计聚合 API（只读 SQL） | 进业务发起 / 数据管理 |
| **数据管理**（编辑态） | 按业务 | 增删改自己的业务数据、上传/替换文件 | 后端 CRUD | 后端 CRUD（幂等写） |
| **业务发起**（创建态） | 有可主动发起的编排就必备 | 填入口表单发起一次生产；或选已有项目复用 | 契约区 `getForms` + `useFormPrefill`（应用后端预填的用户数据） | `useProjectDraft` 草稿句柄 → `project.business.start()`（两段式建项目） |
| **项目页**（进行态） | 必备 | 看进度、应答服务端调起表单、审阅交付、看执行记录与已提交表单、编辑 Runtime 用户文件 | 业务事件 / `pending` / `getRuntimeForms` / `getRuntimeDelivery` | `reply()`（三次握手）、审阅动作只提交 `action_key` |

**禁止孤岛**：除首页外每个页面在任何状态（含错误、只读、`form-submitting`）都要有可操作的 App 内返回入口与确定性兜底；路由表必须有通配兜底回落首页。

### 5.2 看板怎么选字段

看板的每个数值都要能回答“从哪张表、哪些列、什么口径算出来的”。选字段的规则：

- **只从业务应用数据集算**，不从 `PublicDelivery` 或聊天消息里现算——交付回流入库（4.2 第 5 问）才有看板；
- **指标 = 对 `editable:agent` 列（产出、效果）的聚合，维度 = `editable:user` 列（门店、账号、目标）与时间**；用户列本身不是指标；
- 每个指标标注：来源表 / 聚合方式 / 时间窗 / 编辑实时性（用户改了数据多久反映）；大结果分页、单查询在 10 s 内；
- 空数据是常态（新用户零数据）：每个看板块要有引导态，指向“去发起第一次”或“去补数据”；
- 指标数量宁少勿多——用户每天真的会看的那几个，其余进详情页。

### 5.3 可编辑性怎么在页面上体现

列注释里的 `[editable:*]` 声明要**肉眼可见**地落到页面：

- **数据管理页**：只有 `editable:user` 列开控件；`agent` 列只读展示并标明“由生产写入”（含最近写入时间 / 来源运行）；`system` 列不展示或收进详情；
- **看板 / 详情**：一律只读；
- **文件字段**：全程只读卡片，值只能由上传动作产生——不出现路径文本框，不允许手改路径；编辑态有“替换 / 清除”，查看态无写入口；上传中有状态、失败可删后重传；提交必须等全部上传到终态；
- **`view` 权限 / `form-submitting` 期间**：全部写入口置灰并说明原因，返回入口不受影响；
- **用户列被生产建议覆盖的场景不存在**（4.2 第 2 问拆列），所以页面不需要“接受 AI 建议覆盖我的值”这种危险控件；需要采纳时是“把 AI 建议列复制到用户列”的显式动作。

### 5.4 文件在页面上怎么出现

- **上传**：入口表单与数据管理页的文件字段 → `project.upload(file)` → 得 `/workspace` 路径写回字段；勾选了应用级文件库（§2.2）的字段改用 `shared/ApplicationFileField`（上传 + 历史分页 + 预览 + 下载 + 多选，值只存 `path`）；扩展名黑名单与 300 MB 上限由平台拦，界面要把失败原因显示出来；
- **Excel 等结构化文件要“展示在表单里”**：文件本体走上传（给 Agent 读），**预览与预填由前端解析**（在浏览器里读表头/前几行渲染成表格或预填字段）——两条路并行，不互相替代；解析失败不阻断上传；
- **需要用户调整顺序**（选题排序、素材排序）：入口表单页是 App 自绘的（`inputSchema` 原样保留，通用渲染只消费常用子集，复杂字段手写定制页），数组字段完全可以做成拖拽排序，**提交时按数组顺序**——前提是 Workflow 的 `input_schema` 把它声明为数组且顺序有业务含义（这是场景包侧 S1/S2 的设计，A1 反读时确认，缺就回场景包线补）；
- **展示**：图片经 `project.file.getViewUrl` **现取现用**（URL 短时效，禁止存进 storage / formdata）；非图片按可读文件名展示；下载只经 `project.file.download` 且只能由用户显式点击触发；`[[file:/workspace/...]]` 标记经安全渲染；
- **交付物**：`artifacts[].workspace_path` 只传文件 RPC，`output_paths` 只作归属标签，禁止渲染路径文本。

### 5.5 从设计到原型

设计动作按顺序做，先读钉版指南再动手（`references/前端设计指南/`，四份官方 guidance 的离线副本；新页面 / 重设计全读四份，小改只读产品认知一份 + 受影响那份）：

1. **理解产品**（`codex-ui-ux`）：用户是谁、要完成什么、认哪些业务词；入口、首个决策、主行动、成功态、恢复路径；加载 / 空 / 错误 / 权限 / 破坏性 / 长内容 / 移动各状态。***不从装饰或组件画廊起手***。
2. **竞品调研**：先问开发者有无参考（品牌规范、喜欢的产品）；没有再调研 3 个以上同类产品——模块划分、主行动怎么突出、状态怎么表达、空态/等待/失败怎么处理、视觉层级靠什么建立；截图报告留存进工单，只取参考点不照搬。
3. **定一个有辨识度的方向**（`frontend-design`）：贴合业务的设计主张、配色、字体系统、布局逻辑、密度和一个记忆点；对着真实任务校验后再编码。避开 AI 通用默认；用真实界面文案；主行动与信息层级一眼可辨。**脚手架 demo 的页面结构、排版、视觉是第一规则禁止复用的**（这是脚手架的硬约束，不是建议）。
4. **设计完整交互**：从入口到完成的最短连贯旅程；先定义全部重要状态再打磨快乐路径；移动端主行动可达。
5. **原型、计划书与一次确认**：见 §6——原型跑起来后截图进《业务应用计划书》，连同后端功能阐述一起交开发者确认。

## 6. 《业务应用计划书》与一次确认

A1 的交付物是**一份 MD**：《业务应用计划书》。它对应场景包线的《场景包制作书》——开发者确认它，之后 A2 / A3 / A4 就照它干；写给不懂前端的人，读完能提得出意见。

### 6.1 十章结构

| 章 | 内容 | 来自 |
|---|---|---|
| ① 应用定位 | 给谁用、持续经营什么事、SaaS 链路一句话（展示 → 生产 → 回流 → 编辑）、用户一天 / 一周在这里做几次什么 | §1 访谈 |
| ② 参考资料与打法 | 开发者给的参考（截图 / 产品 / 品牌规范）+ 自行调研的参考点；只取参考点，不照搬 | §1、§5.5 第 2 步 |
| ③ 契约基线 | §3 六项反读结果：几条路线、几张入口表单、中途表单、审阅形态、`output_schema` 字段、业务事件粒度、数据集读写列 | §3 |
| ④ 项目模型 | 创建 / 复用两形态各在哪一页、下拉框列什么、发起后去哪、项目页看什么 | §2.1 |
| ⑤ 功能清单 | §2.2 菜单逐项：做 / 不做 + 理由；做的落在哪一页 | §2.2 |
| ⑥ 数据面 | 模板草案（表 / 列 / 类型 / 逐列声明 / 审计 / 文件路径列）、实体 / 情境 / 历史事件归属、可编辑性矩阵、冲突规则、回流入库语义 | §4 |
| ⑦ 页面与截图展示 | 每个页面一节：用户在这做什么、**原型截图**（含空态 / 只读 / 出错至少各一张）、读哪张表哪些列、主行动往哪发、可编辑性怎么可见、文件在哪出现 | §5、6.2 |
| ⑧ 后端功能阐述 | 每个接口一行 + 两条链路（生产回流、表单预填）各一段 | 6.3 |
| ⑨ 验收与自动化测试计划 | A4 §4 三类的用例来源：⑤ 每个勾选功能 → 用例编号；每条路线的编排运作用例；每张表的增删改查与写权 / 幂等 / 冲突用例 | ⑤⑥⑦⑧ |
| ⑩ 制作纪律与开放项 | 确认后不再向开发者提问，A2 / A3 / A4 照本书干；执行中发现与本书冲突，**停下来找开发者**，不自行改口径；脚手架没有的能力列为开放项 | — |

原 5.5 第 5 步“产品设计文档”的全部内容都在这十章里：模块决策账本在 ⑤，看板指标清单在 ⑦ 看板页一节，可编辑性矩阵在 ⑥，文件出现位置在 ⑦，文案与术语检查（契约字段 `description` 不上界面；能靠交互说清的不写解释文字）与一句话风格主张放 ①。

### 6.2 截图展示怎么做

1. 先做**本地可交互原型**：生产级（真实组件、间距、字号、交互态，不是灰块线框）、所有路由可开（含空态、失败态、只读态）、每页有贴合业务的演示数据（仅 `import.meta.env.DEV` 判据注入）、主动线可点通；只跑本地**绝不部署**。交给开发者前先按《前端设计指南》第 6 步过一轮渲染页修正；
2. 用 Playwright 对每个页面、每个关键状态截图（Dev Host Mock 模式下写一条 e2e 逐页 `page.screenshot`，或 `npx playwright screenshot <url>`），存进仓库 `docs/plan/screens/`，MD 里用相对路径引用；
3. 每张图配三句：用户在这干什么、数据从哪来、主行动是什么。**图不是装饰：没有截图的页面视为未设计**；
4. 开发者看图提意见 → 改原型 → 重截 → 更新 MD。

### 6.3 后端功能阐述怎么写

每个接口一行，不写实现细节，写“它为哪一页的哪个动作服务”：

| 接口 | 服务哪一页 / 哪个动作 | 读 / 写哪张表哪些列 | 幂等键 | 限制 | 对应 ⑨ 用例 |
|---|---|---|---|---|---|
| `POST /api/stores` | 数据管理页 · 新建门店 | 写 `stores`（`editable:user` 列）+ 审计四件套 | `X-Goalfy-Business-Request-Id` | ≤256 KiB | C-01 |

再各写一段：**生产回流链路**（Workflow 经 `dscli_business_dataset` 写哪些 `agent` 列，还是应用后端收产出后入库；直接入库还是草稿待确认）和**预填链路**（`useFormPrefill` 从哪张表铺底哪些字段）。约束 5 / 6 的信封、码段、桥层限制不用抄，写“遵守 `backend/README.md`”一句即可。

### 6.4 一次确认

- MD + 原型本地地址一起交开发者：MD 确认信息架构、功能取舍与后端范围，原型确认视觉与手感，两者互为对照；
- 开发者提意见 → 改 MD / 原型 → 再确认，直到开发者说“可以”；
- 确认版落工单 checkpoint `app_plan`（MD 正文 + 截图目录指针）；
- ***确认后才进入 A2 / A3；未确认不得编码。*** 确认后要改口径（加功能、改字段、改页面范围）= 计划书修订，回本节重走确认，不在 A3 里悄悄改。

## 7. 出口条件

- 契约基线表（§3 六项）已反读并记入工单；契约区非空非演示包；
- 数据四类已归位，逐表五问回答完毕，业务应用数据集模板草案（含逐列声明、审计字段、文件路径列）经开发者确认；
- 页面清单（§5.1）、看板指标清单（§5.2）、可编辑性矩阵（§5.3）、文件出现位置（§5.4）写进设计文档；
- 回流入库语义、可编辑性与冲突规则经开发者确认；
- 参考资料已问过并记入工单（§1）；项目模型（创建 / 复用两形态落在哪页）与功能清单（§2.2 逐项 做 / 不做 + 理由）经开发者确认；
- 《业务应用计划书》（§6 十章，含每页截图展示与后端功能阐述）经开发者一次确认并落 `app_plan`；
- 应用结构表已初始化（按 页面 / 接口 / 模板表 分组），结果检查表已转入正反例种子（含“用户编辑不被生产覆盖”“空数据看板可用”这类共治用例）。

以上全部满足后，落一条 `stage_exit` 账，进入 A2。
