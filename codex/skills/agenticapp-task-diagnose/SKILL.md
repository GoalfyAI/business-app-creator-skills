# 诊断

诊断交出的是一份诊断报告：出了什么事、证据、归谁、建议怎么修、影响多大。开发者同意修了，再转修订；诊断本身不分段、不走 ④。

这件事最常见的错是**边查边改**：查到一半顺手改了脚本、建了草稿、重跑了一次，结果原来的现场没了，改动也没经过开发者同意和验收。所以诊断只读。其次是按最新版本猜：使用者跑的可能是旧版本，要按那次运行实际挂载的版本查。

## 只读的边界

诊断期间只调读取类工具。不派生草稿、不改资产和代码、不写库、不部署、不冒泡、不实际跑、不改使用者反馈的状态。`otpe_manage(verify)` 要 write 工单，read 工单调用会被拒（`WORKFLOW_TASK_MODE_MISMATCH`）；诊断不调它，读工单里已有的 verify 记录和运行日志。要修时转 `agenticapp-task-revise`（开新的 write 工单）。

只读协作者（`role=viewer`）不管要做什么都走这里，而且只用 `agenticapp-role-collab` 的「只读协作者能读什么」列出的读取。

## 开始前确认

- 开发者给了什么：应用名、`project_id`、`run_id`、截图、错误码。
- 建 read 工单（只读协作者也是 read 工单），`skill_version` 照入口「开工」第 1 步取。

## 按这个顺序做

1. **确定对象**。
   - 应用名用 `business_ui_manage(action="list")` 解析出应用 ID（`business_ui_id`）；项目用 `project_id`。
   - 按项目实际挂载的版本诊断，不按最新版本猜。
   - 只读协作者查属主的预览项目，用 `get` 返回的 `data.owner_preview_projects`。
2. **先广后深看运行**：
   1. `get_project_execution_logs(action="summary", project_id)` 看总体：卡在哪一步、是失败还是在等待；
   2. `get_project_execution_logs(action="workflow_trace", project_id)` 看每一步的输入输出与失败类别（新 SDK 应用再带上 `business_id`，只看这一次执行）；
   3. 需要时按 `log_type` 分页读 `detail`，或用 `outputs` 看产物清单、`download` 取文件；
   4. 资产配置用 `get_asset` 逐级下钻，版本差异用 `compare_asset_versions`；配置质量从哪层查、查哪些维度见 [references/配置诊断检查清单.md](references/配置诊断检查清单.md)。
3. **按错误码归因**。先看返回里给的出口和提示，再按 [references/归因对照.md](references/归因对照.md) 判归属。`ORCH_NODE_FAILED` 是兜底码，要按失败类别归因。
4. **应用侧问题**（页面、接口、库）读应用工程源码和部署记录；常见对应见 [references/归因对照.md](references/归因对照.md)。
5. **写诊断报告**交给开发者，写法见下一节。

## 诊断报告

| 项 | 写什么 |
|---|---|
| 现象 | 开发者或使用者看到了什么，用业务话 |
| 证据 | `project_id`、哪一步、错误原文 |
| 归属 | 制作侧：脚本 / 提示词 / 路线 / 页面 / 数据；或平台侧 |
| 原因 | 每条原因后面写「依据：<这次查到的记录或跑出的结果>」；写不出依据的写「还不知道，要查 <什么> 才能确定」，不写成结论 |
| 建议修法 | 改哪里、改完会怎样。发布、打开自动化规则这些是他自己的事：写「发布并在「自动化」面板打开规则后才会自动跑，发不发由你定」，不写成要他做的步骤，也不等他点完回话 |
| 影响范围 | 哪些功能、哪些使用者、已有数据有没有受影响；每一项同样写依据，没查过的写「还没查」 |

「原因」和「影响范围」里的每一句都要能指到这次的查询或运行。测试里出过的没依据的话：「当时没讲清楚，让你误会了」（交付记录里讲过不止一次）、「库存数据没丢」（没查过表）、「能跑，不花积分」（查询刚返回无权限）。

对开发者只说业务话（入口「交接」）。`project_id`、步骤名、错误原文这类证据放在报告末尾的原始原因折叠里，正文不出现。

## 之后怎么走

- **制作侧问题**：开发者同意修复后，新建 write 工单并传 `continued_from_task_id`，加载 `agenticapp-task-revise`，从归属所在的那一段接上。不提平台反馈。
- **平台侧问题**：按入口「报错和平台问题」报；报告里引用反馈编号时写回执里的 `code` 原样（如 `FB-801`）。
- **只读协作者**：报告照常交给开发者，告诉他自己能查看哪些内容；不转修订，也不自己改。他要改应用时告诉他：改动要请属主或编辑协作者做，可以请属主把他升为编辑协作者后再按修订改，或者把报告交给属主或编辑协作者去改。

## 你可能会这么想 → 实际

| 想法 | 实际 |
|---|---|
| 看到 `ORCH_NODE_FAILED` 就是工具坏了 | 它是兜底码，按失败类别归因；只有 `tool_error` 才去看上游工具 |
| 先改一下再跑一次，看能不能好 | 诊断不改不跑；开发者同意修复后转修订 |
| 他说「立刻跑一次」，给他两种跑法，「你回 A，我马上跑」 | 不给跑法选项：告诉他诊断里不跑，也不在正式版上跑；要改就转修订，验证在修订的 ④ 里做；跑不跑都不影响已查到的结论 |
| 到点没跑，推测明早就会自动跑 | 先读 `agenticapp-tool-automation`：自动化要发布并打开规则后才会跑，有依据再说 |
| 用最新版本的配置对照 | 按那次运行实际挂载的版本对照 |
| 资产详情字段是空的，资产坏了 | 先看 `can_view_params`，`false` 是权限脱敏，不是空资产，告诉开发者（见 `agenticapp-tool-integration`「分享来的工具组」） |
| 只读协作者查数据要写连接 | 只读连接就够，`connect` 怎么带参数按 `agenticapp-role-collab`「只读协作者能读什么」 |

## 记下来

工单 checkpoint：诊断对象（应用 ID、`project_id`、实际挂载的版本）、归属结论与证据、提交过的平台反馈编号。

## 交棒

报告交出后停下等开发者。要不要修只在报告里问一次：他同意修，加载 `agenticapp-task-revise`；他下一句没接这件事，按只想了解原因处理，到此结束，之后的回复不再问。
