# 3.2 编译规则：分工表 → 场景包资产

分工表每一行按下面的规则变成资产，顺序固定：工具集 → FA → 编排型 TPE → 路线。用户不需要知道这些对象；对用户只说「某功能做好了」。

## 逐行映射

| 分工表 | 变成 | 怎么做 |
|---|---|---|
| 规则行 | 编排脚本里的一步 `await tool(…)`；写库用 `Business_app_fastagent` 或后端接口 | 脚本按 [`脚本模板.md`](./脚本模板.md) 三种之一改 |
| 模型行 | 一个 FastAgent | `create_fast_agent(name, description, prompt_content, model_name?, toolset_ids?)`；提示词里写清输入字段、输出对象每个字段的含义、非成功状态（如 `needs_input`、`insufficient_evidence`）；脚本调用时用 `_output` 声明同一份输出对象 |
| 人行 · 触发 | 路线入口表单 | 路线 `input_schema` 的字段 = 用户要填的东西；`assemble` 会把上游没提供的字段自动放进入口 |
| 人行 · 中途补信息 | 节点 `business_interaction` | 读 `get_diagnosis_doc(topic="otpe_multi")` 的 WF-MULTI-06 后加，只把表单值写进尚未派发的下游字段 |
| 人行 · 审阅结果 | `delivery.review`（缺省 `user_gate`，动作 accept / ask_agent） | `assemble` 缺省已给；需要「修改后重跑」加 `start_orchestration` 指向另一条路线 |
| 进什么出什么 | TPE 的 `input_schema` / `output_schema`，以及模板表 | 字段名用英文蛇形，含义写进 `description`；文件用 `format: workspace-file-path` |
| 做不成怎么办 · 停下来 | 让异常冒泡（不 try/except） | 平台按 failure_class 归因并告知用户 |
| 做不成怎么办 · 标记继续 | `try/except` 只包那一次 `tool()`，输出带 `status` 与 `warnings` | 读 `e.recoverable` 决定 `optional_source_retry_later` 还是 `optional_source_unavailable` |
| 做不成怎么办 · 重试一次 | 同上，except 里再调一次 | 工具内部已重试的不再叠加 |

## 制作顺序与调用

每一步的参数以工具当前 schema 为准，这里只给顺序和必带项。

1. **场景包草稿**：新建 `scene_package_manage(action="create", task_id, name, description, apc_skill)`；`apc_skill` 用用户的词写「这个包能做哪几件事、各自什么时候用、发起前要收齐什么」，1–4k 字，不写资产 ID。已有包用 `ensure_draft`。
2. **工具集**：把 3.1 核实过的工具组、FA 装进 `create_toolset(name, description, tool_group_ids, fast_agent_ids)`；一条路线通常一个工具集。`online_toolsets` 上线。
3. **FA**：每条模型行一个 `create_fast_agent`；建完 `get_asset(asset_type="fast_agent")` 反读 `mr_name`，脚本里用这个名字，不自己拼前缀。
4. **编排型 TPE**：每条路线一条（线性路线一条 TPE 就够；要中途表单或并行才拆多条）。`otpe_manage(action="preview", task_id, script, input_schema, output_schema, business_event_contracts, preload_toolset_ids)` 通过后 `create`（同一组参数加 `scene_package_id`、`name`、`description`），再 `online`。事件契约最少两条：`stage_started` + `stage_result`；`create` 缺契约时返回值里有可直接用的最小模板。
5. **verify**：`otpe_manage(action="verify", task_id, tpe_id)` 看 `verdict`：`blocked` 按 `failed` 项改后重来；`needs_bubble` 进下一步。
6. **冒泡一次**：`otpe_manage(action="bubble", task_id, tpe_id, workflow_input=<代表性输入>)` 拿 `run_id`，只传 `run_id` 轮询到终态，再 `verify(tpe_id, run_id)` 直到 `passed`。FA 在冒泡里是桩，只证明管路；内容留到真跑核对。
7. **路线**：`scene_package_manage(action="assemble", task_id, scene_package_id, tpe_ids=[按顺序], orchestration_id, title, entry_form_id)` 得到草稿；看 `unresolved`（类型不一致、输出为空）与 `notes`，改好后把 `workflow_orchestration` 原样传给 `scene_package_manage(action="update", scene_package_id, workflow_orchestration)` 保存，Hub 会做静态校验。
8. **路线冒泡一次**：`scene_package_manage(action="bubble", task_id, scene_package_id, orchestration_id, workflow_input)`，轮询只传 `run_id`，回填表单传 `run_id + formdata`。终态 `success` 记 `run_id` 进工单。

## 参数由谁填

- 事件契约、`_output`、`_rationale`：脚本模板里已经写好位置，只改业务词。
- 入口映射、节点映射、Delivery mapping：`assemble` 生成，你只审 `unresolved`。
- `tpe_id`、`scene_package_id`、`business_ui_id`：来自上一步返回值，记进工单检查点，不手抄。
- 冒泡：TPE 级只传 `tpe_id + workflow_input` 或 `run_id`；路线级只传三种组合之一。多传的 `evidence_level` 会被忽略，不用反复试。
