# 我先跑了一遍怎么写

后台做好、要拿真实结果给开发者看时读。

## 先挑例子

例子由你挑，不请开发者填、也不请他确认。从 ① ② 已有的东西里挑：

- 开发者给过的、或 ① 真查过的样例。没有公开来源的内部数据，按 ① 的做法编测试数据，并标明是编的。
- ② 验收条目里写到的边界情况：同名多家、名字像别的东西、做过一次再做、查不到。

每条路线一个正常例子，有明确边界规则的再各加一个。每个例子写一句「为什么挑这个」，说清要看它会不会出哪种错。挑得太顺的例子看不出问题。

## 怎么跑

| 路线 | 怎么跑 | 后台标什么 |
|---|---|---|
| 不读写应用库 | 用挑好的例子做路线冒泡到终态（有模型步骤要带 `full_run`），再对路线里每条 TPE 用这次的 `run_id` verify 到 `passed`，取每一步做了什么、产出什么（冒泡怎么调、能证明什么见 `agenticapp-tool-workflow`）。改了脚本或路线才重新跑 | 「做好了，实际跑过」，并发「我先跑了一遍」 |
| 读写应用库 | ③ 跑不了真数据，verify 做到 SKILL.md「交棒」的要求就算这一步做完。要调试不碰库的步骤可以冒泡，冒泡里读空、写被跳过是预期 | 「做好了，等在线预览时实际跑」，冒泡跑通不算；④ 工作集实际跑后按同样格式补发 |
| 有模型步骤但只跑了桩（冒泡没加 `full_run`） | — | 「做好了，只用模拟数据试过」，不发 |

## 每个例子写六项

先写一句总的（「跑了 3 个例子，都和方案说的一样」），再按例子列：

| 项 | 写什么 |
|---|---|
| 例子 | 用业务话说是哪个例子，写在开头，例如「清水缘和服租 · 京都」 |
| 为什么挑这个 | 要看它会不会出哪种错，例如「店名和景点很像，看会不会把清水寺当成门店」 |
| 用了什么 | 入口填了哪些、哪些空着；数据是编的写明「测试数据」 |
| 每一步 | 按 ② 的步骤逐步一句结果；停在使用者要确认的那一步时写「停在这一步，等使用者……」，主语是使用者，不是开发者 |
| 结果 | 最后拿出来的东西，摘要即可；和 ② 的预期一样不一样 |
| 花了多少、用了多久 | 这一次的实测 |

- 六项写不全的，这个功能的「后台」不标「做好了，实际跑过」；只写「示例已跑通」这类一句话结论不算发过。
- 跑出来和预期不一样、但只是做法上的偏差：自己改好再跑，写一句「和预期不一样的 N 处已经改了」；差得多的按 SKILL.md「这一段要做对的判断」出选择题。
- 开发者觉得哪里不对直接说是哪一条，不说就不用等；这一块不放输入框、不放「运行」按钮。
- 原始输出只放阶段文档 G4，这里写业务话。
