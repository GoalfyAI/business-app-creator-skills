# 工具取样

要确认某个已有 MCP 工具的真实返回结构、输入约定，或核实一个分享来的工具组能不能用时读。

## 怎么取样

`otpe_tool_test(task_id, tool_group_id, tool_id, input=<最小合法参数>)` 做一次真实调用，看返回的 `structured_content` 是不是 PRD 要的那个对象。可以同时提交一个候选的输出结构，一起校验本次样本。

脚本要直接调用的复用工具里拿不准的那些建议取样一次，既验输入约定（文件参数收 URL 还是 workspace 路径）也验真实返回结构。外部工具报参数格式错、路径不存在时，回该工具的当前契约看文件参数收 URL、`/workspace` 路径还是内容本体；拿不准就取样一次。

## 哪些不取样

**取样会真实调用供应商接口。** 只对安全只读的工具取样；下面这些只看参数说明，不取样：

- 破坏性操作（删除、清空、重置）
- 发布或对外通知（发信、推送、发单）
- 涉及凭证变更
- 涉及资金
- 任何不可逆的动作

不能取样的工具怎么写进 PRD「能不能做」，见 `agenticapp-stage-1-requirements`。取样要花钱时按入口「花费」先问。

## 依赖项目上下文的工具

只依赖已有业务项目上下文的工具还要传项目标识：服务端会把它和可信身份一起作为运行请求头传给目标 MCP，不会因此启动新项目。

## 要读 `/workspace` 测试文件的工具

不借用使用者的项目：

1. 对 Agent 本地文件调用 `file_to_url(purpose="tool_test_fixture")`，完成 `prepare → 客户端 PUT → complete`，取得 `data.file_ref`。
2. 给 `otpe_tool_test` 两组相互独立的信息：`workspace_files` 只接收这些文件引用；`workspace_bindings` 负责把某个文件的真实路径或父目录注入目标工具顶层参数。这种模式下不传 `project_id`。
3. 服务端复用编排型 TPE 冒泡使用的隐藏验证项目，从临时 HTTPS URL 下载文件、写入真实工作区、完成一次 `tools/call`，随后无论成功或失败都释放隐藏项目。

示例：测试目录扫描工具时，分别上传 `docs/a.md` 与 `docs/b.md`，在 `workspace_files` 中提供两个文件引用，只在 `workspace_bindings` 中把其中一个文件的 `parent_dir` 绑定到 `path`，并在普通 `input` 中保留 `pattern: "*.md"`；测试单文件读取工具时，把对应文件的 `file_path` 绑定到文件参数。文件准备数量与参数绑定数量彼此独立，不为第二个文件虚构 `path2` 或 `urls`。

## 取样能证明什么

样本只能证明这一次真实调用和返回结构，不能代替整条编排型 TPE 冒泡验证（`agenticapp-tool-workflow`「路线冒泡」）。
