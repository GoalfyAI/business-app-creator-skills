# 修订

## 识别信号

- 开发者要改已上线应用的页面、接口、表结构、路线、提示词或能力。
- 开发者按用户反馈报告要求改应用（先按 [../reference/用户反馈.md](../reference/用户反馈.md) 校验决定）。

## 先读什么

1. 建 write 工单；定位应用工程并按 [接续.md](接续.md) 核对本地与云端。
2. 看版本：`list_asset_versions` 看场景包、应用、模板各自的现役版本和有没有搁浅草稿。
3. 取可编辑草稿：场景包 `scene_package_manage(action="ensure_draft")`，应用 `business_ui_manage(action="ensure_draft")`，其他资产 `ensure_editable_asset_draft`。对上线行直接 update 会自动派生草稿，之后一律用返回的 `draft_asset_id`。规则见 [../reference/部署与版本.md](../reference/部署与版本.md)。
4. 评估影响：共享资产用 `get_asset_usage_impact` 看谁在用；改表结构先看 [../reference/数据模板.md](../reference/数据模板.md) 的迁移规则；改 TPE 的输入输出会波及路线映射和页面。
5. 把改动写成确认页的差异版（只列这次改什么、影响哪些功能、费用与副作用有没有变），发开发者确认一次；只改文案、样式时在对话里说清改什么、确认一句即可。

## 从哪一段进

从受影响的最早一个 flow 开始，之后只做受影响的部分，用不到的 flow 跳过：

| 改什么 | 从哪个 flow 开始 |
|---|---|
| 业务规则、功能范围、分工 | G1 |
| 换工具或 FA、接新能力 | G2 |
| 脚本、提示词、路线 | G4 |
| 表结构、页面、后端接口 | G5 |
| 只改文案或样式 | G5（本地 verify 后直接 G6） |

每次修订都走完 G6 预览验收再 G7 定版，不存在「小改免验」。修订前后用 `compare_asset_versions` 取配置差异写进交付报告。
