# 诊断

## 识别信号

- 开发者说效果差、报错、数据不对、页面异常、运行卡住，或给了 `project_id`、`run_id`、截图、错误码。
- 这一步只定位不改；要修时转 [修订.md](修订.md)。

## 先读什么

1. 建 read 工单；转修复时新建 write 工单并传 `continued_from_task_id`。
2. 确定对象：应用名用 `business_ui_manage(action="list")` 解析家族 ID；项目用 `project_id`；按项目实际挂载的版本诊断，不按最新版本猜。
3. 先广后深：
   1. `get_project_execution_logs(action="summary", project_id)` 看总体：卡在哪步、失败还是等待；
   2. `get_project_execution_logs(action="workflow_trace", project_id)` 看每步输入输出与失败类别；
   3. 需要时按 `log_type` 分页读 detail，或 `outputs` 看产物清单、`download` 取文件；
   4. 资产配置用 `get_asset` 逐级下钻，版本差异用 `compare_asset_versions`。
4. 报错码对照 [../reference/报错对照.md](../reference/报错对照.md)；`ORCH_NODE_FAILED` 是兜底码，按失败类别归因，不按码本身归因。
5. 应用侧问题（页面、接口、库）读应用工程源码和部署记录，前端收到 `BAD_GATEWAY` 多为后端响应信封违约，`TIMEOUT` 多为异步路由漏了错误处理或查询过慢。

## 从哪一段进

诊断本身不用 flow。报告写清：现象、证据（`project_id`、步骤、错误原文）、归属（制作侧脚本 / 提示词 / 路线 / 页面 / 数据，或平台侧）、建议修法、影响范围。开发者同意修复后按 [修订.md](修订.md) 从归属所在的 flow 接上。平台侧问题用 `submit_dev_feedback` 报上去。
