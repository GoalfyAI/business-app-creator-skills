# 诊断

## 识别信号

- 开发者说效果差、报错、数据不对、页面异常、运行卡住，或给了 `project_id`、`run_id`、截图、错误码。
- 这一步只定位不改；要修时转 [修订.md](修订.md)。
- 开发者是这个应用的只读协作者（`role=viewer`）：不管他要做什么都走本任务，只用 [../reference/多人协作.md](../reference/多人协作.md)「只读协作者能读什么」列的读取。

## 先读什么

1. 建 read 工单（只读协作者也是 read 工单）；转修复时新建 write 工单并传 `continued_from_task_id`，`skill_version` 按 [../SKILL.md](../SKILL.md)「开工」建工单。
2. 确定对象：应用名用 `business_ui_manage(action="list")` 解析应用 ID（`business_ui_id`）；项目用 `project_id`；按项目实际挂载的版本诊断，不按最新版本猜。只读协作者查属主的预览项目，用 `get` 返回的 `data.owner_preview_projects`。
3. 先广后深：
   1. `get_project_execution_logs(action="summary", project_id)` 看总体：卡在哪步、失败还是等待；
   2. `get_project_execution_logs(action="workflow_trace", project_id)` 看每步输入输出与失败类别；
   3. 需要时按 `log_type` 分页读 detail，或 `outputs` 看产物清单、`download` 取文件；
   4. 资产配置用 `get_asset` 逐级下钻，版本差异用 `compare_asset_versions`。
4. 报错码按 [../reference/报错对照.md](../reference/报错对照.md) 归因（`ORCH_NODE_FAILED` 是兜底码，按 [../reference/报错对照.md](../reference/报错对照.md)「编排与路线」写的失败类别归因）。
5. 应用侧问题（页面、接口、库）读应用工程源码和部署记录：前端收到 `BAD_GATEWAY` 多为后端响应信封违约，`TIMEOUT` 多为异步路由漏了错误处理或查询过慢。

## 从哪一段进

诊断本身不分段。报告写清：现象、证据（`project_id`、步骤、错误原文）、归属（制作侧脚本 / 提示词 / 路线 / 页面 / 数据，或平台侧）、建议修法、影响范围。

- 制作侧问题：开发者同意修复后按 [修订.md](修订.md) 从归属所在的那一段接上，不提平台反馈。
- 平台侧问题：按 [../SKILL.md](../SKILL.md)「平台问题」报；报告里引用反馈编号的写法见 [../reference/报错对照.md](../reference/报错对照.md)「平台问题怎么报」。
- 只读协作者：报告照常交给开发者，告诉他自己能查看哪些内容；不转修订，也不自己改。他要改应用时告诉他改动要请属主或编辑协作者做：请属主把他升为编辑协作者后按修订改，或把报告交给属主或编辑协作者去改。诊断不走 ④。
