# P1 业务基线细则

> 细则正本。G1 是主线；本文只放 G1 步骤点名的表格、框架与格式，不含流程，不含进入与出口条件。

## 1. 用户画像七问

| 要问什么 | 例，餐饮场景 | 它决定后面什么 |
|---|---|---|
| 服务谁：职业、角色、经营形态、规模 | 单店或小连锁的餐饮老板，自己管运营 | 里程碑与路线的用词、`apc_skill` 与界面文案的语域、数据集的表与列名 |
| 他们眼里的专业词汇与判断标准 | 爆品、客单价、复购、差评 | 样例选择的领域调研方向、验收判定的措辞、FastAgent 规范文件的术语 |
| 他们的决策节奏与使用场景 | 每天营业结束后看十分钟、周一定下周活动 | 路线数量与粒度、哪些环节值得最终用户确认、看板要看什么 |
| 现在怎么做、卡在哪 | 手工翻评价、凭感觉定活动 | 理想态与价值预测的基线 |
| 有几类人群 | 老板、店长、运营专员各自关心什么 | 是否需要多条路线或多套子画像 |
| 有没有可参考的资料与打法 | 同行怎么做、他自己的活动与复盘、内部 SOP、行业报告、看好的竞品 | 旅途与候选路线的起点、样例选择的调研方向；先问开发者，再自己调研 |
| 高风险边界与不可触碰 | 涉及资金、发布到公开平台、处理顾客个人信息 | 红线与授权边界 |

## 2. 信息缺口六类

| 缺口类型 | 例子 | 处理 |
|---|---|---|
| 意图缺失 | "帮我做个东西" | **必须**向开发者询问明确目标，**禁止**先设计方案 |
| 关键参数缺失 | 创建任务未描述业务场景；诊断任务未指定目标 | 目标明确但缺执行前提，**必须**向开发者索要 |
| 知识缺失 | "我不知道需要哪些工具" | 属于你的调查范畴，纳入 G2 摸底，**不要**让开发者回答平台问题 |
| 工程偏好缺失 | 命名风格、代码组织、等价展示细节 | 存在可逆且不改变业务语义的默认时采用并记录影响，不当阻塞项 |
| 产品决策缺失 | 路线、Focus 与泛化、审阅责任、界面模块、最终用户介入 | 放入决策卡集中确认；只有一个独立决策时单项询问；**不得**由你用默认值 |
| 授权缺失 | 发布、删除、收费、真机运行 | 在对应动作前明确确认，**不得**用默认值代替授权 |

## 3. 访谈清单

按需组合，每轮一到三个事项：

- 业务场景：业务是什么、服务谁、现在怎么做、最终要什么结果
- 参考素材：有没有已执行项目、完整日志、文档、SOP、已有能力容器
- 业务边界：哪些系统、数据、权限、成本、时效、合规条件不能改
- 成功标准：什么最终用户可见结果能证明应用有效
- 任务模式：新建、优化已有，还是从执行失败的项目反查原因

启动前至少明确：业务目标、最终用户、业务终点、关键输入与产出、操作对象、可读取的证据、高风险边界、初步验收标准。其余平台知识由你自己调查。

## 4. 正反例的四处复用

| 用途 | 怎么用 |
|---|---|
| 判断需求理解是否正确 | 把正例的处理过程讲给开发者听，错了立刻能发现 |
| 编排型 TPE 运行验证 | 正例直接作为代表性输入，见 G4 |
| 场景 Skill 文件 | 写成示例，运行 Agent 照着做，见 P3 知识写作 |
| 真机验证 | 照着正例填入口表单 `formdata` 与运行中表单的答案，另构造一条自然业务需求核聊天路由，见 G5 |

正例定义"好"的形态，反例定义"错"的边界；被圈定的关键产出环节，其验收判定从这里长出来。

## 5. 最终审阅三形态与终态顺序

交付核验回答"这份结果是否真实、完整、可交付"，最终审阅回答"业务上是否接受这份结果、是否需要修订或改走其他路线"。两者**禁止**合并：输出契约、数值、证据和文件校验通过，不代表最终用户或运行 Agent 已完成业务验收；节点级 `sa_handoff` 和质量检查编排型 TPE 也不是最终审阅的替代品。

| 形态 | 运行语义 | 适用信号 |
|---|---|---|
| `user_gate + ask` | Runtime 向应用下发冻结交付和已声明动作；最终用户完成三次握手后，Runtime 直接执行所选的完成、失败或新路线动作，不额外唤起 Agent | 业务完成需要最终用户批准、满意度确认、方案选择、修订、改路线或高风险授权 |
| `user_gate + result` | Runtime 按既有链路自动交付并结束，不要求最终用户或运行 Agent 参与 | 生成且核验通过即达到业务终点，不需要额外业务判断 |
| `agent_gate` | 唯一主动唤起运行 Agent 评价或选路的最终审阅边界；Agent 按开发者确认的可验证标准选择已声明动作 | 接受标准客观、可执行且确实需要 Agent 判断 |

纪律：`user_gate` **不得**再叠加一层"交给 Agent 收尾"；只有路线明确声明 `agent_gate`，或最终用户选择了已声明的"交由 Agent 处理"动作时，才建立 Agent 边界；`apc_skill`、节点 `sa_handoff`、业务应用都**不得**用额外提示词模拟这次接管。

终态顺序固定：解析真实 TaskPoint 输出；核验交付资格；冻结本次 Delivery；执行已声明的最终审阅；根据审阅动作完成业务、结构化失败或开启新路线。审阅明确接受前，**禁止**把结果展示当成已验收，**禁止**把 Business 标记为已完成。修订、重做或改路线必须保留当前 Delivery，按当前契约新建运行实例，不覆盖旧结果。

能力容器只声明对外稳定的资产契约：中间节点用 `sa_handoff`，最终审阅用 `delivery.review`。Max Runtime 如何生成 Agent 边界通知、注入执行上下文或封装内部控制消息，属于平台实现细节，**禁止**复制进路线对象、`apc_skill`、场景 Skill 或应用契约。

## 6. 红线四类

| 类 | 写什么 |
|---|---|
| 业务红线 | 资金、公开平台发布、顾客个人信息、替用户做不可逆决定；逐条写"完全不做"还是"必须最终用户逐次授权" |
| 范围红线 | 本次明确不覆盖的人群、路线、产出形态及理由，防止后续为了"完整"又设计回来 |
| 质量红线 | 绝不能出现的产出：错误事实、越权承诺、违反平台合规的内容；直接进结果检查表反例 |
| 变更红线 | 能力削减或替换必须先经开发者确认；高风险动作必须明确授权 |

红线用最终用户听得懂的话写；整个制作周期内**只能加严，不能放松**。

## 7. 《业务计划书》七章

| 章 | 内容 |
|---|---|
| ① 用户画像 | 服务谁、专业词汇、决策节奏、使用场景、人群分类、不可触碰边界 |
| ② 用户旅途 | 能完成什么事、几条路线各给谁走、输入与输出、中途确认点、质量评估标准、高质量手段 |
| ③ 业务路线图 | 入口、业务阶段、固定依赖、扇出与汇合、最终用户与 Agent 介入、动作出口；每条路线的到达标准 |
| ④ 交付角色 | 每条路线结果交付给谁、谁负责业务审阅、三形态选哪种、允许哪些动作、修订与重做与改路线怎么续 |
| ⑤ 业务应用数据集 | 是否规划配套业务应用；用户数据如何作用、何时用到、如何回流；不配套时数据如何随交付给到用户 |
| ⑥ 产出与质量 | 每条路线的最终交付物形态、关键产出环节及其正反例、验收判定的雏形 |
| ⑦ 红线 | 业务红线、范围红线、质量红线、变更红线 |

每章包含推荐、依据、影响和待确认选择。对配套应用只记录是否规划及其承载的业务旅程，页面设计在 G3 完成。计划书是管理型语言，写给不懂平台的人看，不出现资产数字 ID、技术字段名、代码片段、内部调用链。

## 8. 思考框架

**研究十问。** 谁实际使用、谁付钱、谁能决定采用、谁承担结果；什么事件触发需求、多久一次、不处理会怎样；客户现在怎么完成、为什么不继续；真正卡在信息不足、不会判断、来不及执行、协作断裂还是交付质量不稳定；要改变哪个可观察状态；产品能控制哪些、需要客户和外部平台做哪些；什么算可用、完成、失败；需要什么数据、成本、时效与授权，缺失后还能提供什么；不同客户哪些差异只需配置、哪些必须改变业务方法；客户获得的改善能否支持付费。答不出的标未知并配验证办法。

**价值假设句式。** 为【具体客户】，在【触发情境】下，以【时间、预算和业务约束】完成【可验收的工作】；相较【现有办法】改善【可观察指标】。应用负责【范围】，客户负责【必要投入和决定】，通过【证据】判断完成；出现【条件】时补充、调整或停止。

**关键决策表十二问。** 只挑显著改变用户价值、资源投入、对外承诺或后续路径的决定。每个决定回答：为什么此时要决定；可以怎么选，含推荐、备选、不执行、补证据、交专家；依据什么，分列门店事实、历史记录、外部证据、专业规则、待验证假设；哪些条件会改变推荐；信息不足怎么办，分可直接读取、值得补问、可用默认值、应暂缓；谁适合判断，分确定性规则、AI 建议、业务负责人、领域专家；谁能授权什么，含动作对象、账号、金额或数量、时效和范围；判断错误会怎样，含影响、可逆性、发现时机、补救代价；最终用户看到什么才能有效决定；选定后怎样执行；如何知道判断和执行是否合格；什么应进入下一次。每项至少一个会改变选择的真实反例。

**三条独立轴与四个时机。** 三条轴不互斥：证据够不够；判断由谁负责；动作得到什么授权。四个时机分开：模板制作期研究客户问题、价值假设、专业方法、决策与授权规则；客户初始化建立事实、偏好、账号权限、默认目标、素材；每次运行读取已有信息、识别变化与过期项、提出必要建议、处理异常；周期复盘检查采用与结果、方法适用性、质量与成本。先找最容易让结果不可用的三项判断和最常见的两种异常，其余按暴露的问题扩展。
