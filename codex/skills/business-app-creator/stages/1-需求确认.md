# ① 需求确认（工作区阶段 G1、G2）

交给开发者一份确认过的 PRD：要什么、不要什么、谁来用、每一步谁来做、能不能做、做不到的怎么替代、花多少、用多少。「能不能做」必须建立在平台上真查过、真调过的基础上，所以和开发者沟通的同时就去核实，PRD 交出去时已经带着核实结论。

这一段要让开发者看明白两件事：这个应用能不能满足自己的业务需求；每件事会怎么走。看明白了，开发者才能指出哪里不对。

## 1. 进入条件

- 开工四步已完成（`SKILL.md` 第 5 节）：有 write 工单、应用工程已初始化或接续、方案页已有最小草案。开发者只给一句话、方向还不清楚时，方向那一轮在开工前发，方向定了再开工（同一节最后一段）。
- 开发者给了任一材料：一句话目的、需求文档或 PRD、SOP、会议纪要、原型、截图、草图、参考项目、已有应用的问题。
- 从修订进来时，只确认这次要改的部分（见 [../tasks/修订.md](../tasks/修订.md)）。
- 只改文案、样式这类小改动：在对话里说清改什么、确认一句，直接进 ③，不出 PRD。

## 2. 段里怎么做

### 2.1 看开发者给了什么，记下已定的事

开发者可能只给一句话，也可能给一堆材料，按 [../design/按轮问.md](../design/按轮问.md)「从开发者给的东西开始」处理：方向不清楚时先和开发者探讨方向。给了材料的，读全部材料，列出：谁来用、使用者做什么、提到的别人参与（审核、复核等，按 [../design/谁来做.md](../design/谁来做.md)「谁来用」处理）、判断点、交付物、要存下来的东西、开发者提到的数量（一天几次、一次多少条）。不加推测；这些记成「已定的事」，缺的留给 2.2 去问。写清一次记录代表的整体业务对象、每个入口实际做什么、何时只算提交或受理、实际会产生什么结果；没有产物也记明。不要把包含上传、清洗、筛选的整体事项都叫筛选。这些和其他业务事实一起在 PRD 里确认，不另加文案确认轮次。开发者给过截图、原型、参考应用、草图，或在对话里说过页面长什么样（有哪些页、每页放什么、怎么排），一并记下，写进 PRD「界面」。开发者主动要求深入梳理业务时，按 [../design/咨询模式.md](../design/咨询模式.md) 处理。

需求方和开发者不是同一人时，记下需求方是谁；需求方的原话、文档、会议结论和开发者的话同等对待，冲突的做成选择题。

### 2.2 按轮问，问到「要什么」都定了

按 [../design/按轮问.md](../design/按轮问.md) 一轮一轮问：从 ① 的起步方向开始排树，树随开发者的回答长出新的节点。第一轮在看完开发者给的东西后马上发，不等核实做完；之后每轮按上一轮的答案和 2.3 查到的结果，问新变成「现在就能问」的题。

- 题目按 [../design/选择题与判断题.md](../design/选择题与判断题.md) 写；「每个应用都要问的」那几题和界面三问（参考、第一眼看到什么、整体感觉），开发者没说过的都要问到，放在它们依赖的事定下之后的那一轮。
- 已定的事不再问；开发者没回的题不算定，下一轮接着问；问到树上没有空着的节点为止，不限轮数。
- 问完先发一条「我理解的是这些」，发之前核对界面三问都有答案（开发者答的，或开发者说了「按常见做法」）；还没问的先补一轮再发（[../design/按轮问.md](../design/按轮问.md)「先确认理解，再动笔」），开发者回「对」再写 PRD。
- 每轮都是一条交接消息，开头「【① 需求确认 → 等你确认】」，「下一步」写这轮答完后接着问什么或开始写 PRD。

### 2.3 同时核实：平台上有没有、真调一次

和开发者沟通的同时，对每一步做这几件事。这部分是 AI 内部工作，结论用业务话写进 PRD，资产 ID 和试调细节只写进阶段文档。这一段只查不建：不创建场景包、FA、工具集、数据模板、应用（第 3 步的能力试用包除外）。开发者回「确认这一版」之前，工作区阶段标记最多标到 G2，不写编排脚本、不建表、不部署，也不进 ② 以后的任何一段；开工四步建的工单和工作区不算「建」。

1. **逐项查**：

   | 要做的步骤 | 去查 | 怎么查 |
   |---|---|---|
   | 脚本步骤要调的外部能力（拉数、发送、查询） | 工具组 / 工具集 | `list_assets(asset_type="tool_group", keyword=<平台或动作词>)`，命中后 `get_asset` 看工具名、参数、是否要授权卡 |
   | 模型步骤 | FastAgent | `list_assets(asset_type="fast_agent", keyword=<判读 / 生成 / 诊断 + 领域词>)`，命中后 `get_asset` 看输入字段、输出形状、模型配置 |
   | 整条路线像已有应用 | 场景包 | `list_assets(asset_type="scenario_package", keyword=…)`，命中后 `get_asset` 看路线与 TPE |
   | 要存的表 | 数据模板 | `list_assets(asset_type="dataset", keyword=…)`；已有模板看列注释里的 `[editable:user|agent|system]` |
   | 页面 | 脚手架预置件 | 读应用工程的 `frontend/registry.json`：首页（含最近记录）、消息中心、入口表单、项目层、表单应答、交付审阅、列表 / 详情 / 表单数据块 |

   `list_assets` 的关键词只匹配名称和 ID，用英文短词试几次；`get_asset` 配置为空且 `can_view_params=false` 是脱敏，不是空资产。

2. **真调一次**：名字对上不算。用 `otpe_tool_test(task_id, tool_group_id, tool_id, input=<最小合法参数>)` 取样，看 `structured_content` 是不是 PRD 要的那个对象，同时核对文件参数收 URL 还是 `/workspace` 路径。要外部数据的，用开发者的账号或开发者给的样例真拿一次；拿回来的真实数据放进 PRD 当样例，其中客户姓名、电话、证件号这类个人信息打码后再放。**禁止**对删除、发信、发布、涉及资金或凭证、不可逆的工具取样；这类工具只看参数说明，判定见第 4 步。

   **别人分享来的工具组**常见两种情况，按这样处理：
   - **用名称搜不到**：`list_assets` 只匹配名称和 ID，分享来的工具组名字常和开发者说的不一样。先用开发者给的工具名、平台名的英文短词再试；还搜不到，在下一轮问题的「要你做的」里请开发者给工具组 ID（开发者中心资产页或分享消息里能看到），或请分享人再分享一次。拿到 ID 后 `get_asset` 看权限。
   - **看不到参数**（`can_view_params=false`、工具列表为空）：这是脱敏，不是空资产。先用 `otpe_tool_test` 按工具描述或开发者给的样例里能看出的参数取样一次；调用被拒或返回参数错误时，按报错提示补参数再试一次。仍拿不到真实返回的，核实结论写「能用，没取到样」，PRD「能不能做」那一行写「已有现成工具，还没真试过，制作时第一次真跑核实；分享人收回或改动后这一步会停」；不能克隆的，不改它，按原样用。
3. **模型步骤拿不准效果时试一次**：关键的模型步骤（报告、方案、诊断这类要直接交给使用者的内容）效果拿不准、或用时拿不准时，按 [../tasks/能力试用.md](../tasks/能力试用.md) 建一个极简试用包，用开发者的一两条真实样例跑，记下输出、用时和花费。这会产生费用：先在选择题或交接消息里说清份数和约多少积分，开发者同意后再跑；还没查到单价、说不出约多少积分时，等查到后在下一轮问，不发不带数字的同意题。
4. **判定能不能做**：

   | 情况 | 写进 PRD「能不能做」 |
   |---|---|
   | 工具返回覆盖需要 | 能做，用平台现成的；要授权的确认已有授权卡，没有的写进「要你提供的」 |
   | 发信、发布这类不能取样的工具，参数说明覆盖需要（发给谁、发什么） | 能做，用平台现成的，没真发过；④ 只发给开发者自己试一次。发到应用自己的消息中心不算向外发送 |
   | 已有 FA 输出能覆盖「拿出来」 | 能做，用平台现成的（内部记下：直接复用；差一两个字段时 `clone_asset` 后改提示词，不改共享资产） |
   | 官方或他人的场景包像这条路线 | 能做，用平台现成的（内部记下：`clone_asset` 后改；自己的草稿 `ensure_draft` 继续） |
   | 已有模板缺列 | 能做（内部记下：工作集里加列再 `extract` 新版本，不另建同义表） |
   | 平台上没有，外部有现成 MCP 或 Skill 包 | 能做，要接入（内部按 [../reference/依赖与MCP接入.md](../reference/依赖与MCP接入.md)） |
   | 确定性的计算、存取 | 能做，要新做（脚本） |
   | 要模型、平台上没有 | 能做，要新做（模型）；试过的写「已试过」 |
   | 都不行、授权接不上、时间或费用达不到 | **做不到**：写原因、影响哪个功能，给替代选择题（换做法 / 改范围 / 等平台）；要平台补能力的，内部写一条开发需求记进阶段文档，开发者选「等平台」时按 `SKILL.md` 第 7 节提 `submit_dev_feedback(blocking="request")` |

5. **算花费**：付费工具按单价算；模型步骤按 [../design/谁来做.md](../design/谁来做.md)「模型选哪一档」定档，有试跑的用实测花费，没有的写估算。算出两个数：做这个应用（开发和测试）预计多少，上线后每用一次约多少；再按用量题的答案算每周约多少。

### 2.4 写 PRD

按 [../design/PRD.md](../design/PRD.md) 写，「谁来用」和「每一步谁来做」按 [../design/谁来做.md](../design/谁来做.md) 写。开发者说过的名字、字段、选项一字照用，不自行改名或增删取值。平台要求每个应用至少一条路线：只有脚本步骤的应用也挂一个场景包和一条最小路线，应用界面可以不发起它，在 PRD 里如实说明。

### 2.5 发出、批注、出新版

PRD 写进方案页，发交接消息（[../design/交接消息.md](../design/交接消息.md)），开头「【① 需求确认 → 等你确认】」，「要你做的」列：读 PRD 哪里不对就说、答选择题、提供材料和授权、都没问题回「确认这一版」。需求方和开发者不是同一人时，加一项「把 PRD 转给需求方看，或让需求方直接答第 N 题」。

开发者批注后出新一版，标出改了哪里，直到开发者回「确认这一版」。批注里引出的新问题照 2.2 的问法问，已定的事不再问；按默认定下的在 PRD 原处标「按默认」。

Studio 宿主：这一段只写 PRD 一份开发文档，**必须**照 [../design/开发文档/PRD.md](../design/开发文档/PRD.md) 的模板写，按轮问问完、开发者回「对」之后才写第 1 版，不写方案、进度、验收报告。用 `studio_write_proposal(documentType="prd")` 保存；开发者在聊天里明确同意这一版或在确认卡上确认后，用 `studio_confirm_proposal` 登记原话并读回，才算「确认这一版」；PRD 改了就重新确认。读到确认之前不建业务资产、不写业务代码。做法见 [../reference/开发者中心与工作区.md](../reference/开发者中心与工作区.md)「Studio 宿主」。

不写计划书、制作书、承诺清单，不做价值论证、样品挑选。

## 3. 开发者要看、要做的

- 读 PRD，看每个刚需放进去的是不是自己有的、拿出来的是不是自己要的，哪里不对就指出来。
- 确认谁来用、看到什么；确认刚需和非刚需的划分、反向案例、怎样算做成。
- 看真实拿回来的数据，确认是自己的、是要的。
- 对做不到的事选替代做法；定花费上限和上线后的用量；答选择题。
- 提供材料、账号、授权、数据分享（有操作步骤就带着做）。
- 回「确认这一版」。

## 4. 不给开发者的

用哪个工具、哪个 FA、模型名、平台资产编号；难度、成功率；试调的技术细节和报错原文。这些写进阶段文档。

## 5. 产出与落盘

- 方案页：PRD 全文按 [../design/PRD.md](../design/PRD.md) 的对应关系写入；等确认时 `status` 为 `waiting`，`data-stage="G1"`；开发者确认后 `status` 改为 `working`、`data-stage` 改为 `G3`，方案版本加一。
- 阶段文档 G1：「已定的事」（每条写是什么、谁说的或按默认、哪一轮定的）、开发者和需求方原话里的关键事实、确认版 PRD 全文、每一版 PRD 的改动、选择题及谁答的、确认时间与原话。
- 阶段文档 G2：核实对照表：

  | PRD 里的步骤 | 复用什么（资产 ID） | 取样结论（真调返回摘要、花费） | 缺什么 / 怎么处置 |
  |---|---|---|---|

  「缺什么」那一列就是 ② 编译、③ 要造的清单。
- 工单 checkpoint：`PRD 已确认`，附应用名、刚需列表、路线名、表名、花费上限、用量；核实对照表摘要。
- 阶段标记：G1、G2 `passed`（写法见 [../reference/开发者中心与工作区.md](../reference/开发者中心与工作区.md)「三件套与阶段标记」）。

## 6. 交棒条件

下面都满足后，先用命令把 [2-方案.md](2-方案.md) 从头读到尾，再做 ② 的第一件事。

- 写 PRD 前开发者对「我理解的是这些」回了「对」；PRD 写出后开发者回了「确认这一版」或等价表述；Studio 宿主读到了当前这一版 PRD 的确认；
- 每个刚需都有放进去 → 拿出来、这样算对、这样不行、怎样算做成；
- 每一步都标了脚本、模型或人，并有核实结论；做不到的都有开发者选过的替代；
- 选择题都有答案（开发者答的、需求方答的或标「按默认」），用量有；花费上限是一个具体的积分数，写在 PRD 和工单 checkpoint 里，「待定」「看情况」不算；
- 方案页里没有开发者看不懂的词，没有模板占位文案；
- 出口阶段记录：用 `business_ui_stage` 写 G1、G2 各一条（写法见 [../reference/开发者中心与工作区.md](../reference/开发者中心与工作区.md)「三件套与阶段标记」）。

## 7. 出问题怎么办

| 现象 | 先看 | 怎么做 |
|---|---|---|
| 开发者说不清要什么 | 按 [../design/按轮问.md](../design/按轮问.md) 先探讨方向：给两三个具体做法让他选；开发者明确说「帮我先理一理业务」「不确定该做什么」时才进咨询模式 | 本段 2.1 |
| 需求里有红线内容 | `SKILL.md` 第 0 节 | 停止 |
| 取样报参数错、路径不存在 | 工具当前 Schema 的文件参数说明；换 `file_to_url` 或 `/workspace` 路径 | 本段 2.3 |
| 工具要使用者各自授权 | [../reference/依赖与MCP接入.md](../reference/依赖与MCP接入.md) 授权卡一节 | 写进 PRD「要从外面拿的数据」 |
| 资产受限或脱敏 | 按本段 2.3 第 2 步「别人分享来的工具组」处理；结论写进 PRD，开发者确认 PRD 时一并确认 | 本段 |
| 核实发现关键功能做不到 | — | 在这一段就写进 PRD，给替代选择题；**禁止**先做别的、到后面再说 |
| 开发者只想讨论、暂不开发 | [../tasks/仅讨论.md](../tasks/仅讨论.md) 的边界；讨论具体应用时仍写方案页 | 本段 |
