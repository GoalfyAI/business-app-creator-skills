# ③ 制作（工作区阶段 G4、G5）

按施工单把后台能力、数据和页面做出来。交给开发者的是：每个功能做到哪了（后台、页面、存数据三格），后台真跑过的功能各一份「我先跑了一遍」，页面说明，没做成的说明。这一段主要是你在做，开发者不用填、也不用确认；只有和 ② 的预期差得多时才请开发者拍板。环境出错、外部服务没钱、平台报错这类问题你自己处理，不转给开发者。

## 1. 进入条件

- ② 交棒：当前整版方案（含验收条目）已确认，施工单在阶段文档 G3 里。
- 从修订进来：先按 [../reference/部署与版本.md](../reference/部署与版本.md)「修订、回滚、作废」取可编辑草稿，只改受影响的资产；从哪一步开始改见 [../tasks/修订.md](../tasks/修订.md)。

## 2. 段里怎么做

先做后台能力（2.1），再做数据和页面（2.2）；每做好一个功能发一次进度（2.3）。下面每步只写做什么，工具参数、顺序、必带项和报错在引用的 reference 里，参数以工具当前 Schema 为准。

### 2.1 后台能力

G4。按施工单的顺序：

1. **场景包草稿**：新建、续用自己的草稿，官方或他人的包先 clone，并写好 `apc_skill`，见 [../reference/业务路线.md](../reference/业务路线.md)「场景包草稿」。
2. **接入缺的工具**（① 判定要接入时）：先预览再注册，需要使用者各自授权的配授权卡，见 [../reference/依赖与MCP接入.md](../reference/依赖与MCP接入.md)「接入现有 MCP 服务」「授权卡」。
3. **FA**：每个模型步骤一个，模型用 PRD 定的档位；要按情况查应用库的，建时就挂应用库只读工具并反读确认，见 [../reference/编排脚本.md](../reference/编排脚本.md)「建 FA」。
4. **工具集**：把核实过的工具组、FA（脚本要读写应用库时再加「query_business_app_dataset」）装进来，测过后上线并反读，见 [../reference/依赖与MCP接入.md](../reference/依赖与MCP接入.md)「工具集上线的两道检查」。
5. **编排型 TPE**：写第一条前先读诊断主题，从三种模板之一复制改业务词，preview 前逐项自查，再 preview → create → online，见 [../reference/编排脚本.md](../reference/编排脚本.md)「写脚本前先读」「三种模板」「建、校验和上线 TPE」；读写应用库的按同一文件「读写应用库」写。
6. **反读自查**：每条读写应用库的路线 online 后反读，四项各记「有 / 没有」进阶段文档 G4，四项定义见 [../reference/编排脚本.md](../reference/编排脚本.md)「反读自查四项」。任一项「没有」回第 5 步改；四项都有，这条路线才能标「做好了」、才能进 ④。
7. **verify**：看 `verdict` 改到 `passed`，读写应用库的路线到 `needs_bubble` 且 `failed` 为空为止；单条冒泡只用于多节点路线里单个节点的调试。见 [../reference/编排脚本.md](../reference/编排脚本.md)「建、校验和上线 TPE」。
8. **路线**：`assemble` 出草稿，处理 `unresolved` 与 `notes` 后整份保存；分支、并行、中途表单、Agent 接管手写接缝。见 [../reference/业务路线.md](../reference/业务路线.md)「assemble 怎么用」。
9. **拿真实结果**：
   - **先挑例子**：例子由你挑，不请开发者填、也不请开发者确认。从 ① ② 已有的东西里挑：开发者给过或 ① 真查过的样例、② 业务说明和验收条目里写到的边界情况（同名多家、名字像别的东西、做过一次再做、查不到）。每条路线一个正常例子，有明确边界规则的再各加一个；每个例子写一句「为什么挑这个」，说清要看它会不会出哪种错。
   - **不读写应用库的路线**：用挑好的例子做 `full_run` 路线冒泡到终态，再对路线里每条 TPE 用这次的 `run_id` verify 到 `passed`，并取每一步做了什么、产出什么（调用见 [../reference/业务路线.md](../reference/业务路线.md)「冒泡」，能证明什么见 [../reference/编排脚本.md](../reference/编排脚本.md)「冒泡与真跑能证明什么」）；结果按 2.3 发「我先跑了一遍」，原文记进阶段文档 G4。改了脚本或路线才重新跑。
   - **读写应用库的路线**：③ 跑不了真数据。静态 verify 返回 `needs_bubble` 且 `failed` 为空就算这一步做完，进度「后台」标「做好了，等部署后真跑」，运行证据在 ④「2.3 工作集真跑」补。要调试不碰库的步骤时可以冒泡，冒泡里读空、写被跳过是预期（[../reference/编排脚本.md](../reference/编排脚本.md)「读写应用库」）。

`full_run` 和冒泡的费用按 `SKILL.md`「花费」：PRD 已列的直接跑，跑完补进交付物的实际花费。

### 2.2 数据和页面

G5。页面要调用的路线先能跑（每条 TPE verify 通过或只差运行证据）；只改表、页面或后端、不碰路线时不需要重做 2.1。

1. **应用身份**：在把 `current_stage` 改成 G5 之前建好应用身份并回填工作区，见 [../reference/数据模板.md](../reference/数据模板.md)「建应用身份与挂模板」。
2. **数据模板**（每个应用都要做，至少一张业务表）：开工作集、建表、反读核对施工单的表清单、抽出模板版本、挂到应用并绑工作集，见 [../reference/数据模板.md](../reference/数据模板.md)「建表与出版本」「建应用身份与挂模板」。
3. **数据页**：用生成器一条命令生成，见 [../reference/脚手架与预置件.md](../reference/脚手架与预置件.md)「生成数据页」。
4. **场景包契约进前端**：见 [../reference/前端页面.md](../reference/前端页面.md)「场景包契约」。
5. **业务页**：PRD「界面」一节是页面的最高依据，平台行为与预置件一致，空库有引导，见 [../reference/前端页面.md](../reference/前端页面.md)「界面以开发者为准，预置件可用可不用」「界面风格」「首屏与导航按客户业务任务组织」；上线后必须存在的设定放哪见 [../reference/数据模板.md](../reference/数据模板.md)「预览数据不进正式版」。
   - **演示和示例要放真实成果的**（新人演示、首页示例报告这类）：先放 ① 里真拿到的数据；模型要写的内容还没真跑出来时，放一份标明「示例」的占位，在阶段文档 G5 记下「待 ④ 回写」和位置，④ 在「2.3 工作集真跑」后回写。
6. **业务文案**：填写并接到实际页面和动作，见 [../reference/前端页面.md](../reference/前端页面.md)「业务文案」。
7. **后端接口**：见 [../reference/脚手架与预置件.md](../reference/脚手架与预置件.md)「后端接口」。
8. **外部平台授权、充值、自动化**（PRD 列了才做）：分别见 [../reference/授权与充值.md](../reference/授权与充值.md)、[../reference/自动化.md](../reference/自动化.md)。
9. **清起始件、对齐路由**：按 [../reference/前端页面.md](../reference/前端页面.md)「清起始件」逐项做完。
10. **本地跑**：`check`、`verify` 和前端测试全绿，见 [../reference/脚手架与预置件.md](../reference/脚手架与预置件.md)「命令」。③ 不部署，在线预览到 ④ 部署后才有；开发者想看完成版见 [../reference/开发者中心与工作区.md](../reference/开发者中心与工作区.md)「演示预览为空」，Studio 宿主的演示见同一文件「Studio 宿主」。

### 2.3 进度与「我先跑了一遍」

③ 开始时发第一条进度（列出方案里的全部功能，格子按实际状态写）；之后每做好一个功能、跑完一次「我先跑了一遍」、出现或解决一个问题时发一条交接消息，不必每调一次工具就发。开头「【③ 制作 → 正在做】」，写法和样子见 [../design/交接消息.md](../design/交接消息.md)。每条进度消息里有：

- **进度表**：每个功能一行，三格「后台 / 页面 / 存数据」。页面、存数据写「做好了 / 在做 / 没开始 / 不需要」；「后台」只写下面四种之一，这个功能没有后台的写「不需要」：
  - **做好了，真跑过**：2.1「拿真实结果」用 `full_run` 冒泡或真跑跑到了终态；
  - **做好了，只用模拟数据试过**：只有桩跑通（冒泡没加 `full_run`）；
  - **做好了，等部署后真跑**：读写应用库的路线，静态 verify 只差运行证据，④ 部署后真跑；
  - **在做 / 没开始**。
- 表下一句总数（例如「19 项里做好 15 项」），和方案不一样的地方各写一句（换了什么、对使用者有什么不同）。
- 读写应用库的功能「后台」标「做好了」时，写一句「存数据自查：<路线名> 四项都有」；写得出这句才能标「做好了」。
- **我先跑了一遍**：发给每个后台「做好了，真跑过」的功能。读写应用库的路线在 ③ 只标「做好了，等部署后真跑」，冒泡跑通不算；④ 工作集真跑后按同样格式补发。每个功能先写一句总的（「跑了 3 个例子，都和方案说的一样」），再按例子列：

  | 项 | 写什么 |
  |---|---|
  | 例子 | 用业务话说是哪个例子，例如「清水缘和服租 · 京都」 |
  | 为什么挑这个 | 要看它会不会出哪种错，例如「店名和景点很像，看会不会把清水寺当成门店」 |
  | 用了什么 | 入口填了哪些、哪些空着 |
  | 每一步 | 按 ② 的步骤逐步一句结果；停在使用者要确认的那一步时写「停在这一步，等使用者……」，主语是使用者，不是开发者 |
  | 结果 | 最后拿出来的东西，摘要即可；和 ② 的预期一样不一样 |
  | 花了多少、用了多久 | 这一次的实测 |

  六项写不全的，这个功能的「后台」不标「做好了，真跑过」；只写「示例已跑通」这类一句话结论不算发过。开发者觉得哪里不对直接说是哪一条，不说就不用等；这一块不放输入框、不放「运行」按钮。原始输出只放阶段文档 G4，进度里写业务话。
- 跑出来和预期不一样、但只是做法上的偏差（漏字段、格式不对、时间写错）：自己改好再跑，写一句「和预期不一样的 N 处已经改了」；差得多、要开发者拍板的按 2.4 问。
- **页面说明**：页面做完写每个页面做什么用、显示什么、有哪些按钮；可以附本地布局回归的截图（只连本机 Mock，不是线上页面），写明「示意，按本地完成版截」。
- **没做成的**：哪件事没做成、原因、影响哪个功能。

### 2.4 什么时候请开发者拍板

| 情况 | 怎么问 |
|---|---|
| 真实结果和 ② 的预期差得多，不是你能改好的偏差（例如报告要 49 分钟、说好 30 分钟） | 两份放在一起，做成选择题：按预期改做法（写代价）/ 接受现在的结果 |
| 累计花费到上限的 80% | 按 `SKILL.md`「花费」出选择题：继续 / 减少测试份数 / 提高上限 |
| 做的时候发现做不到 | 选择题：换做法（写差别）/ 这次先不做；要的东西因此变了就退回 ① |

缺开发者本人才能给的东西（授权、密钥、业务事实），或要做 PRD 没列的外部副作用时，也停下来问（`SKILL.md`「开发者确认什么」「红线」）。除此之外不停下来等开发者：技术问题按 [../reference/报错对照.md](../reference/报错对照.md) 自己处理，处理不了按 `SKILL.md`「平台问题」报，交接消息写「卡住了」和对开发者的影响。

## 3. 开发者要看、要做的

- 看每条进度消息和「我先跑了一遍」；觉得哪个例子、哪一步不对，直接说是哪一条。不说也行，你不等他。
- 只在 2.4 的三种情况回答选择题。
- 「要你做的」里列了他本人才能给的东西（授权、密钥、业务事实）时提供。

## 4. 产出与落盘

- 工单 checkpoint：场景包草稿 ID、每个新建资产的 ID 与 `mr_name`、每个 FA 的模型、每条 TPE 的 verify 结论、每条路线的冒泡 `run_id`、是否 `full_run` 与终态、花费；`business_ui_id`、`data_uid`、模板 ID 与版本、`npm run verify` 结果。
- 阶段文档 G4：资产清单的实际结果与 verify 摘要；每条读写应用库路线的反读自查四项；每次试跑的例子、为什么挑、入口原文、每一步结果、输出原文、`run_id` 与 `project_id`、花费与用时，以及和预期的对照；开发者拍板的题和答案。
- 阶段文档 G5：表结构（`inspect` 结果的业务说明）、页面清单的实际结果、界面风格的决定、「已确认业务含义—界面文案—实际页面/动作」简短对应（包含整体对象、各入口和补充动作、真实产物），不另建文案计划书；待 ④ 回写的示例位置。
- 交付物（方案页；机制见 [../reference/开发者中心与工作区.md](../reference/开发者中心与工作区.md)「方案页」）：状态写当前进展；`full_run` 或真跑到终态的才进「已验证」并带证据，桩跑通、本地预览的进「未验证」并写明「只用模拟数据跑过」「本地预览」；`full_run` 的实际花费补进「费用与副作用」。Studio 下本段交付物写成「制作进度」开发文档（[../design/开发文档/制作进度.md](../design/开发文档/制作进度.md)），什么时候写、什么时候更新与 2.3 的进度消息相同，格子状态与 2.3 进度表一致。
- 阶段标记：G4、G5 `passed`。

## 5. 交棒条件

- 每个功能的后台、页面、存数据都是「做好了」或「不需要」（后台是三种「做好了」之一），或标明没做成及原因，开发者已就没做成的选过；
- 每个后台「做好了，真跑过」的功能，都已经按 2.3 发过「我先跑了一遍」；FA 是桩的冒泡（没加 `full_run`）不算真跑过；
- 每条读写应用库的路线，反读自查四项都是「有」，已记进阶段文档 G4；
- 每条编排型 TPE：最近一次 `verify` 为 `passed`（带路线冒泡或单条冒泡的 `run_id`）；读写应用库的路线只差运行证据（`needs_bubble`、`failed` 为空），`passed` 由 ④ 真跑补上；
- 每条不碰应用库的路线：当前合同下最近一次冒泡到终态 `success` 的 `run_id` 已记入工单；失败的已修好重跑，或已按 [../reference/部署与版本.md](../reference/部署与版本.md)「三道门」的结单豁免说明原因；
- `business_ui_id` 已建、数据模板版本已挂到应用、开发工作集已绑定；
- 应用根 `npm run verify` 全绿，业务文案已由实际页面和动作使用；
- 累计花费没超过上限，或超出部分开发者已选过。

**出口标记**：G4、G5 标 `passed`；用 `business_ui_stage` 写 G4、G5 各一条，G5 带上 `business_ui_id`（写法见 [../reference/开发者中心与工作区.md](../reference/开发者中心与工作区.md)「三件套与阶段标记」）。

## 6. 出问题怎么办

| 现象 | 怎么办 |
|---|---|
| 工具报错、verify 或冒泡失败、FA 失败、`doctor` / `verify` 不过、建表或抽版本被拒、连接串过期、契约门禁报 packs 不一致 | 按 [../reference/报错对照.md](../reference/报错对照.md) 处理，改完回本段对应的一步 |
| 冒泡异常长跑，步数或积分一直涨 | 先止损再排查，见 [../reference/编排脚本.md](../reference/编排脚本.md)「冒泡与真跑能证明什么」 |
| 同类事实错误、引用错误或无产物连续两轮 | 停止加字段、不原样重跑，按 [../reference/编排脚本.md](../reference/编排脚本.md)「FA 与脚本的职责边界」重划职责；要改施工单的回 ② |
| 页面要的数据路线不给 | TPE 的 `output_schema` 缺字段：本段 2.1 改 schema，或回 ② 改施工单的页面清单 |
| 设计做不了（SDK 拿不到的数据、路线不发的事件） | 回 ② 改页面清单，或本段 2.1 改路线契约；不静默改设计继续做 |
| 真实结果始终达不到预期，要换做法 | 回 ②：问清变化的取舍，改方案并请开发者确认新版整版 |
| 做的时候发现做不到，要的东西因此变了 | 按 2.4 出选择题；要的东西变了回 ① |
