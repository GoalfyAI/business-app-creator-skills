# G2 关键能力可行性

本阶段的目的是**在写任何正式资产之前，证明关键能力真的可行**。把试错前移：先试最可能失败的部分，用真实取样和真实产物说话。产出能力矩阵与试验报告，它们是 G3 决定谁来做、怎么做的直接输入。细则表格见 P2。

## 1. 进入依据

G1 的业务基线、关键决策清单与业务路线草图已确认；关键未知项已列成试验问题。试验授权与正式制作授权**分开取得**：试验授权包括试验数据、隔离环境、费用与调用范围、停止条件。

进入前已有 `write` 工单。试验会创建工具组、工具集和试用包草稿，`read` 工单**不得**执行。

## 2. 本阶段建设

### 2.1 建立承诺、能力、证据、缺口矩阵

把 G1 的每条业务承诺和每个关键决策展开成一行：需要什么能力、已有什么证据、缺什么。证据来源按可信度排三个顺序，**先复用、再摸底、最后才谈缺口**。

**第一来源：参考项目。** 开发者给了参考项目，你**必须**完成三层，**禁止**只看摘要下结论：

1. 概览。读项目摘要，统计总轮次、最终用户请求序列、执行阶段、Agent 与工具分布、等待与失败概况。摘要只用来建立全局视图和定位要深挖的轮次。
2. 深读。读完整原始日志的全部分页，截断时续读到结束。重点看最终用户的原始意图与约束、规划逻辑、工具调用密集的阶段、任务点与 FastAgent 的输入输出质量、失败重试、等待原因、最终交付是否匹配预期。
3. 分析。写入工单四项结论：轮次分类统计；瓶颈定位与根因归类，缺知识、缺工具、缺指引、缺前置检查或资产边界错误；真实调用链；Skill 使用情况。多个项目逐项目保留独立事实再提炼共性，**禁止**用平均值掩盖异常。

**第二来源：已有能力容器与官方基础包。** 用 `get_asset` 读官方基础包的完整配置，理解预加载与动态工具集的组合方式，作为选型基准。用 `list_assets` 加 `get_asset` 找可参考的已有能力容器；开发者要基于某个已上线包做变体时，用 `get_scene_package_lineage` 看来源与派生，评估走派生还是新建。用 `get_diagnosis_doc(scene_package)` 读当前契约。复用的判据是 G1 基线：候选覆盖了哪些路线与交付，用词与画像是否一致，缺什么。

**第三来源：平台能力摸底。** 用 `list_assets` 搜索，用 `get_asset` 完整反读能力容器、任务点、工具集、FastAgent、工具组、数据集。看 Schema 和真实配置，**不要**只看描述。搜索结果不是完整契约，选型前**必须**用 `get_asset` 下钻；一次 `get_asset` 不展开子资产，**必须**逐级下钻。涉及数据查询时用 `list_assets` 列出开发者有权访问的长期数据集，用 `dataset_read` 确认表结构与权限；**禁止**假设开发者拥有某个数据集。名为"××档案场景包"的官方包属于业务档案产品线，不是业务应用数据集的来源。

矩阵的每行落六态之一：已覆盖、可组合覆盖、需维护、真实缺口、受限能力、待验证。选择结论用 `task_manager(insert)` 留痕。

### 2.2 先试最可能失败的部分

按风险排序，顺序固定：取不到数据；模型不能可靠判断；外部工具效果差；成本或时间不可接受。每一项对应一个试验问题，试验问题只有两种答案：有真实证据的可行，或者明确的不可行与原因。

### 2.3 能力缺口的四层处理

缺口**不阻塞**流程，但**不得**静默削减开发者明确要求或参考项目里已有的能力。按优先级处理：

1. **Skill 弥补。** 工具能力已覆盖，缺的只是调用顺序、前置检查、字段准备或结果审视方法。把指导写进正确层级即可。
2. **接入现有能力。** 平台内先用 `list_assets` 与 `get_asset` 确认没有可复用的工具组，重复注册同一服务会产生冲突资产。平台没有再去外部找：MCP 官方索引、代码托管平台、包管理平台、开发者自己的私有仓库。评估四维度：是否仍在维护；连接方式；认证方式，全容器共用凭证还是每个最终用户各自授权；有无破坏性操作。任一维度足以否决时直接出结论。
3. **形成开发需求。** 开发者有协作团队时，写一份可直接转交的需求说明：业务动作、目标系统、必需输入与输出、授权方式、隔离要求、副作用、失败语义、验收样例。
4. **开发者确认后降级。** 用已有能力继续，**必须**写明未覆盖的阶段、对结果的影响、以后补齐的条件与受影响的验证，并取得确认。

不知道某个效果怎么实现时，先问开发者有没有参考资料或同类产品；没有再自行调研实现思路。结论与来源记入工单。

### 2.4 能力试用与真实取样

外部能力要不要用、能不能用，靠试用回答，**禁止**先建全套正式资产。顺序固定：

1. **摸底定形态。** 完整读能力来源的文档。现成 MCP 服务和标准 Skill 包直接进下一步；CLI 工具、代码库、普通应用需要先包装，默认只评估包装成本并出结论，开发者明确要求时才动手包装。
2. **本地验证先行。** 起服务、装依赖，确认工具清单与真实返回结构。本地能起来再注册，注册基本一次通过；反过来每轮都要等平台反馈。本地不可用直接出结论并附证据。
3. **平台接入。** `preview_tool_group` 预览并发现工具，再 `register_and_refresh_tool_group` 注册；预览时用过的前置安装步骤，注册时**必须**一并带上。标准 Skill 包用 `import_skill_package`；开发者的私有包先 `file_to_url` 换取引用再 `upload_and_register_tool_group`。需要最终用户各自授权的能力，试用期就要用 `create_auth_card` 配授权卡，否则试跑走不通。**禁止**把任何个人令牌写进 Skill 文本、脚本或工单。
4. **复用工具先读契约，再真实取样。** 脚本要直接调用的已有工具，先用 `get_asset` 下钻到工具组，读描述与输入定义：文件参数收 URL 还是 workspace 路径；必填与互斥；值域与格式；返回结构是否声明；副作用与授权。拿不准的安全只读工具做一次 `otpe_tool_test` 取样，输入用代表性真实值，文件先 `file_to_url(purpose="tool_test_fixture")` 上传并同时提供 `workspace_files` 与 `workspace_bindings`。取样验两件事：输入按约定能不能被接受；真实返回的嵌套形状。破坏性、发布、凭证、金融、不可逆的工具**禁止**取样。样本要点记入工单，不含 URL 与凭证。
5. **需要看模型判断时组极简试用包。** `scene_package_manage(create)` 建草稿并反读继承；新建工具集装入本次工具组并上线；`apc_skill` 只写这个能力是什么、什么时候用、关键注意点。名称**必须**带试用标识。用 `manage_goalfymax_project(run)` 跑开发者关心的 1 至 3 个真实任务，任务描述用自然业务需求，**禁止**指定工具名或调用顺序。试跑是真实运行，FastAgent 计费、外部副作用照常发生，**必须**先取得授权；含破坏性工具的任务**禁止**作为试跑任务。逐任务记录任务、实际调用、结果质量、耗时与积分、失败与原因。
6. **收尾。** 试用包草稿**永不上线**，出结论后经开发者确认用 `delete_asset` 作废；工具组与工具集保留，转正式时直接复用。

### 2.5 用同一代表性输入比较候选

每个模型或工具候选跑同一输入，记录质量、耗时、费用、失败形态。改稿类承诺**必须**试"旧产物加修改约束"；续作类承诺**必须**试恢复所需的状态与产物读取。只证明从零生成**不算**通过。样本量不足时**禁止**声称稳定成功率。

### 2.6 验证 U 项前提

U2：数据粒度、权限、文件读取、上下文传递，用实际对象核实。U3：模型判断与连续执行的关键样例，覆盖应继续、应补充、应停止三种情境，桩跑不算判断能力。纳入范围时另验 U7 的发现与授权、U8 平台可表达的动态行为。

### 2.7 写试验报告与能力矩阵

报告结论先行，写入工单：结论，可行、不可行、需要包装后再评估；能力形态与接入方式；验证证据，本地验证、工具清单与返回结构要点、逐任务记录；质量印象；成本，接入耗时、试跑积分、包装预估；风险，维护状态、认证模式、破坏性边界、许可证；盲区，没试到什么、哪些结论是外推的。能力矩阵更新每行的状态与证据。

## 3. 给开发者看什么

默认展示两样：**实际产物对比、关键路径能力卡**。每张能力卡回答四个问题：要证明什么、试了什么、结果怎样、现在能承诺到哪。费用与耗时分事实与估算两栏。候选路线只在有显著取舍时并列，**禁止**为凑数量造方案。缺口处理方案带影响与推荐，由开发者选，你**不得**以缺口不可阻塞为由自行削减目标。

## 4. 要确认哪些边界

试验数据；隔离环境；允许的读写；费用与调用范围；停止条件；最终用户兜底是否可接受。使用更大模型**不得**自动扩大费用和数据外发范围。

## 5. 门禁 Checklist

- `G2-01` 试验覆盖本次实际使用方式，包括改稿与续作，不只从零生成。对应 U4、U5。
- `G2-02` 已用实际对象核实数据粒度、权限、文件读取、上下文传递；受限详情未被误判为空资产。对应 U2、U5-02。
- `G2-03` 模型判断与连续执行有真实证据，覆盖应继续、应补充、应停止；桩跑不算判断能力。对应 U3。
- `G2-04` 质量、耗时、费用的事实与估算分开；超限方案未被默认采用。
- `G2-05` 关键路径缺口已解决，或开发者明确改范围。"以后补"不能让原承诺通过。
- `G2-06` 试验环境与资产有标识及清理或保留计划；未擅自上线；无未授权副作用。

## 6. 证据与结论

产出试验报告、真实输出、能力矩阵、选择依据、剩余盲区。落工单检查点 `capability_matrix` 与 `trial_report`。已注册的工具组与工具集、工具真实返回结构、试跑记录直接进入 G3 与 G4 复用。

## 7. 失败回退

能力失败：先换试验策略，包括换工具、补信息、升级模型。目标不成立：回 G1 修改承诺范围。
