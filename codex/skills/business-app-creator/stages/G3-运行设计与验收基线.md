# G3 运行设计与验收基线

本阶段的目的是**确定它到底会怎样工作**。路线、执行者分工、数据、页面状态**联合设计**，一次形成运行设计与验收基线，定稿成《制作书》。定稿之后 G4 到 G6 照书制作，**不再向开发者提问**。表格与契约细则见 本文第 8 节、本文第 8 节、本文第 8 节。

## 1. 进入依据

G2 能力矩阵与试验报告在手；关键能力已验证到足以选择路线；剩余假设已列明。G1 的关键决策清单与业务路线草图是本阶段的输入。

## 2. 本阶段建设

### 2.1 为每个节点决定执行者与形态

拿 G1 的业务路线草图和关键决策清单，逐节点决定四种执行者之一：规则、模型自主、模型加确认、最终用户。依据是 G2 证据里的通过率与稳定性，加上 G1 定的风险等级。高风险节点**永远至少由最终用户确认一次**。

执行形态按固定顺序决策，**禁止**按复杂度或步骤数来回切换：

1. 执行路径是否需要模型在运行中决定下一步，或需要自然语言往返。需要，用普通任务点。
2. 是否存在至少两个实质步骤、稳定数据流、固定扇出汇合，或同一路径需要参数化复跑。存在，用编排型 TPE；多个职责边界拆成多条编排型 TPE 写入路线。
3. 整个任务是一个环节的完整工作，一次输入、自己带工具搜读判写、一次输出。用 FastAgent，不为它套单步转发的编排型 TPE。
4. 只是当前上下文里确定的少量调用，没有复用价值。由 SystemAgent 直接执行。

四种形态的对照表见 本文第 8.2.2 节。**是否使用编排型 TPE 必须逐里程碑评估并写入工单**，不能默认不用：反复执行的固定流程、固定流水线、多对象并行加汇总、参数化复跑都是编排型 TPE 的信号。两个相反的错误都要避免：给单个 FastAgent 套一层编排型 TPE；因为步骤少就否定编排型 TPE。

FastAgent 的粒度纪律：**一个业务环节一个 FastAgent**。拆不拆看职责边界，不看步骤数；工具挂给 FastAgent 还是脚本自己调，看下一步靠不靠结果决定；不挂工具只做文字变换的 FastAgent 是误用。同域多类产出仍是一个 FastAgent 一次调用出全套。方案里 FastAgent 超过三个时，**必须**逐个说明不可合并的理由。

Focus 与泛化**必须**作为显式选择项交开发者确认：Focus 把 Skill 写到工具调用级别，固化路径；泛化写到策略级别，保留选路弹性。**不得**因为参考项目具体就自动选 Focus，**不得**因为素材不足就自动选泛化。

价值预测有真实基线时可以给改善幅度，**必须**列计算依据、假设、不可优化部分和误差范围；没有基线只做定性判断，**禁止**编造数字。

### 2.2 设计业务路线对象

业务路线是能力容器上的一个整体对象。三种走法：单节点路线，单条编排型 TPE 声明业务事件、需要表单握手、需要交付审阅或由应用启动；多节点路线，多条编排型 TPE 的固定依赖、扇出、汇合、交互和交付；直接派发，仅限没有业务事件契约、不依赖握手的单条编排型 TPE。路线对象的构成见 本文第 8.3.1 节。

三类关系**分开画**，不得混成一条 DAG：实现候选的取舍；运行中的条件分支；最终用户的不同业务入口。

以下情况**不要**强行画成固定依赖图：整条路径需要临场规划，用普通任务点；最终用户改稿、重做或改走另一条路线，冻结当前交付并开启新的运行实例，**禁止**画回边模拟循环，**禁止**覆盖旧交付；制作期就能预知的最终用户输入，全部放入口表单；只有上游成功后才知道、且要喂给未派发下游的输入，才用运行中交互；节点成功后需要检查或处理异常，在该节点声明 Agent 介入并写清可验证的继续或接管标准。

每个节点写八项：做什么、为什么、谁做、依据、输入来源、输出去向、失败出口、最终用户介入与交付核验。并行节点先看数据依赖、副作用、共享资源、限流。

### 2.3 架构方案与执行结构表

**工具集划分。** 预加载放每次运行都必须出现的核心能力，动态放按需加载的辅助能力。克隆官方包继承的核心工具集**不可**移除；优先复用系统级工具集；按能力域匹配，**不要**按业务场景建专用工具集。

**内部资产清单**记入工单，不进业务方案：每个 FastAgent 的名称、职责、输入输出、真实关联的工具组；每个工具集的能力域、成员、加载方式、使用指南要点；每个任务点的路由描述、交互需求、输入输出；每条编排型 TPE 的稳定业务阶段、脚本要用的工具名、完整依赖、输入输出定义、辅助文件、副作用，以及每个输入字段的来源；每条路线的入口、节点、映射、交付审阅、重入方式；数据集为什么绑定、在哪个节点读。所有 ID **必须**经工具查询确认。

**开发者可见的业务路线图**与内部资产清单分开：前者用业务阶段名称画入口、依赖、扇出汇合、最终用户与 Agent 介入、最终交付、审阅责任与动作出口；后者才是真实资产怎么承载。**禁止**把节点标识、工具名、字段映射暴露到业务方案。

**执行结构表**是强制产出，每条编排型 TPE 一个条目：步骤清单，每步做什么、用什么；步骤间依赖；并行组，按数据依赖、副作用独立、典型形态三问逐步判断，对多个对象执行同一操作默认设计为并行组，未入并行组的写明 `no_parallel_reason`；FastAgent 清单与不可合并理由；每步的执行者、证据、风险等级、确认形式、回退链、预算；每步结果的展示载体三档，不展示、进业务事件、进交付，记入 `user_facing`。FastAgent 与工具的原始返回**不是**展示载体。需要并行正反例时读 `get_diagnosis_doc(otpe_example_parallel)`。

**应用结构表**在规划配套应用时同步建立：每个页面、每个后端接口、每张模板表一个条目。

**需求追踪矩阵**记每条承诺到节点、数据、页面、资产、验收例的映射。三张表按协议二的双副本、指纹、pending 机制维护。

### 2.4 数据面设计

先回答一个开关问题：**是否规划配套业务应用**。不规划，G1 里"记下来、下次接着用、看历史"这类目标从基线移除或改成随交付给到用户的文件，路线里**不出现**读写数据集的步骤，**不挂** `business_app_dataset` 工具集。规划了，按下面设计。

**数据分四类归位**：用户自己的数据，列声明 `editable:user`；运行期所需与产出的字段，`editable:agent`；系统字段，主键、审计四件套、`last_run_id`、`row_version`，`editable:system`；界面意图与实体引用进 `sdk.storage`，**不进库**。**不要**把该进库的数据写成前端 mock、静态 JSON 或后端常量。

**表分三类组织**：实体，用户经营的长期慢变对象；情境，当前目标、偏好、约束、时段；历史事件，每次运行、发布、效果的记录，只增不改。情境与历史事件挂在实体上，任一条历史事件必须能回答属于哪个实体、来自哪次运行。多商家变体落在实体表的类型列加按类型的可选列。运转链画一遍，逐箭头标读写的表与列：用户填实体与情境，发起时铺底进入口表单，编排型 TPE 读情境与历史决定策略，产出写回历史事件，看板按实体聚合，用户修正实体与情境，下次更准。

**逐表五问**：存什么；逐列可编辑性，每列恰好一个写入方，用户与生产都要写的信息拆成两列；审计四件套加 `row_version`，来源标记落哪列；冲突规则靠 `row_version` 乐观锁，**没有静默覆盖**；回流入库语义，直接入库还是草稿确认，按业务风险定。

**三个时机分工**：项目启动铺底由应用后端直读拼进发起报文，字段放进 `input_schema`，**不走** FA；执行中取数由脚本调业务应用数据集 FA `operation="read"`，每条业务流至多一次读，`found=false` 是常态结果回退表单值，回退顺序由你在本阶段定，**不由脚本临场猜**；收尾回写由脚本调 FA `operation="write"`，`context_hint` 给唯一键。

**文件只存路径与元数据**：用户现场上传经 `project.upload`；应用级持久文件经 `sdk.file.upload`；过程交付物经 `delivery.mapping` 登记；Runtime 用户文件读权威值。

### 2.5 页面与状态设计

规划配套应用时执行本节。

**契约基线先反读，禁止推测**：`get_asset(scenario_package)` 返回的 `business_forms` 决定入口表单与中途表单；`orchestrations` 决定有几个发起按钮、哪些中途表单、终态审阅形态；编排型 TPE 的 `output_schema` 与 `display` 决定交付页能渲染什么；`business_event_contracts` 决定进行态粒度；公开语义决定页面文案；数据集读写通道决定哪些列要有数据、哪些列要展示。契约区为空或只剩演示包时**停止业务设计并报告**。

**项目模型**：业务应用在项目之上，项目是用户的一次计划选择。发起只有创建与复用两种，页面上让用户显式选；业务发起页是唯一的发起入口，项目页只看进度、应答表单、审阅交付。

**功能选择菜单**逐项与开发者定做或不做，表见 本文第 8.10.2 节；不在表里的能力**不许诺**。

**页数等于三个必备页面加按业务取舍的四类业务页面**，每页对应用户一个明确意图。看板每个数值能回答从哪张表、哪些列、什么口径算出来；指标是 `agent` 列的聚合，维度是 `user` 列与时间；空数据是常态，每块有引导态。可编辑性**肉眼可见**：数据管理页只有 `user` 列开控件，`agent` 列只读并标来源。文件按属于谁分级：这一次生产用项目级，跨项目反复用用应用级，某次运行补材料用 Runtime 用户文件；数据管理页**不能**用 `project.upload`。

**状态固定六种**：提交中、已受理、运行中、待补充或审阅、失败、完成。每种状态画出来，每种中断的恢复位置、保留范围、重复执行边界写清。

**设计动作按顺序**：读 `references/前端设计指南/` 的四份指南；先问开发者有无参考，再调研三个以上同类产品并留存截图报告；定一个有辨识度的方向，脚手架 demo 的页面结构与视觉**禁止**复用；设计从入口到完成的完整交互，先定义全部状态再打磨主路径；做本地可交互原型，用 Playwright 逐页逐状态截图存进 `docs/plan/screens/`。**没有截图的页面视为未设计**。

产出《业务应用计划书》十章，章节结构见 本文第 8.13.1 节，后端功能阐述每个接口一行。它与《制作书》一起确认。

### 2.6 绑定知识与实例化 U 行为

领域知识绑到实际执行者与决策点。**同一条信息只写在一个地方**，权威位置表见 本文第 8.6.1 节；每轮都要知道的写文本字段，做某件具体事才查的写 Skill 文件；FastAgent 只读自己名下的 Skill 文件，能力容器挂再多知识它一篇也读不到。颗粒度从理想态反推：凡是希望减少的失败、绕行、沟通轮次，都有对应的可执行指导；**禁止**"完善流程""输出高质量报告"这类空话。`apc_skill` 大纲至少覆盖业务终点、里程碑、候选路线与选路节点、必需输入与验收标准、权限边界、未固化的关键规则、Skill 文件索引。

好坏样例转成验收用例进结果检查表。设计"下次使用哪里读到此次反馈"，**禁止**只建反馈表。

对适用的 U1 至 U8 逐项写成本项目的验收设计，字段固定：编号、适用条件与承诺、前置状态、输入或操作、预期、失败判据、开发者要看的信息、责任、证据类型与版本。明细见 U 业务行为验收明细。本阶段只能记"设计已确认"。

### 2.7 方案挑战

创建任何资产前**必须**完整读取方案挑战检查清单并执行。以执行结构表为对象逐条目挑战，**只处理 `pending` 条目**。质疑成立就修方案；不成立就写证据和取舍。**禁止**证据不足时判定通过。全部通过后置 `challenged=true`。

### 2.8 定稿《制作书》

《制作书》是制作期唯一依据。前七章是 G1 业务基线的定稿：服务对象与画像、用户旅途与里程碑、业务路线图、交付角色与审阅、数据留存开关、预计产出、红线。本阶段补三章，内容表见 本文第 8.5.2 节：

- **第 ⑧ 章 资产设计**七小节：路线与人群映射；每条路线的流程表；FastAgent 设计决策；工具集与依赖；普通任务点、直接执行与知识文件；业务应用数据集字段表；配套业务应用。
- **第 ⑨ 章 能力缺口、发布范围与授权**。"发布范围"与"上线授权"**必须**分开表达；写明"前三层候选验收通过后上线"并经确认，发布前不再重复询问。
- **第 ⑩ 章 制作纪律**：定稿后不再提问；什么算冲突必须停下沟通，制作书与真实契约不符、平台不支持该模式、触碰红线、计划书口径要变、制作书自相矛盾；冲突解决后整份重写再确认；更好的想法记工单备忘。

每个设计决定写成选择、未选、理由三段。术语用画像的词，工具名与字段只出现在第 ⑧ 章的技术表格里。整份写进工单 `build_book`。

**开发者确认一次**：执行结构表 `challenged=true` 后，连同《制作书》与《业务应用计划书》一并展示；确认第 ⑧⑨⑩ 章并复核前七章未被改变语义。本次确认**兼作三件事**：圈定关键 FastAgent，被圈定的环节 G4 制作时必须执行样例选择；Focus 与泛化显式选择；配套应用的功能取舍。要改的地方改完整份重新提交。

**制作书硬门**：确认前只允许只读调查、候选草案、方案挑战和不改变外部状态的验证，**禁止**创建依赖资产、任务点、草稿容器、编排型 TPE、关联或路线。确认后，同一范围内的可逆离线操作获得授权；上线动作仅在第 ⑨ 章明确写出时获得授权。后续若改变路线依赖、交付对象、审阅责任、动作、重入方式或介入点，属于口径变化，回 G1 更新基线再回本阶段。

## 3. 给开发者看什么

**先演示一个完整业务样例，再展示必要的图。** 默认展示业务路线图与结果或页面原型截图；职责有争议时加泳道图；状态容易混淆时加状态图。每个节点给出做什么、为什么、谁做、依据、输入输出、异常、修改影响；技术映射可展开查看。用真实案例在决策图上走一遍：该自动继续、该停下来、该拒绝、该改路线时分别发生什么。

## 4. 要确认哪些边界

信息缺失、冲突、过期；无权限；部分成功；取消与恢复；模型与工具兜底；文件生命周期；局部修改；重复提交；隐私与跨对象隔离；临时需求是否在支持范围。最终用户审阅与运行 Agent 审阅的分工。业务决定与动作授权**分开记录**。**禁止**只确认画面好不好看。

## 5. 门禁 Checklist

- `G3-01` 每条承诺都能追到节点、数据、页面或动作、验收例；没有写在计划里却无承载的功能。
- `G3-02` 节点职责与执行形态有依据；分支可解释；没有为步骤数机械增建任务点或 FastAgent。
- `G3-03` 每个入口字段写明来源、必需或可选或可推断、冲突处理、接收节点；修改入口另声明目标产物、版本与保留约束。对应 U2、U5。
- `G3-04` U3 暂停与授权规则、U4 恢复状态表、U5 修改影响表按适用项确认；响应未知、部分成功、用户取消分别定义出口。
- `G3-05` 资料冲突、用户编辑与生产写入、单次与对象级与长期偏好、效果回传均有规则；每个留存字段能指出下次谁读、何时读。对应 U2-04、U6。
- `G3-06` 开发者已看过覆盖关键分歧的正反情境；业务决定与动作授权分开记录。对应 U3、U7、U8。
- `G3-07` 《制作书》与《业务应用计划书》已确认并冻结到当前版本；实现中发现新事实可提变更，**不得**以"已定稿"拒绝沟通。

## 6. 证据与结论

产出《制作书》、《业务应用计划书》、执行结构表、应用结构表、需求追踪矩阵、节点说明、边界案例、验收索引。落工单检查点 `build_book`、`app_plan`、`execution_structure_snapshot`、`app_structure_snapshot`、`behavior_design`。

## 7. 失败回退

路线的业务含义没对齐：回 G1。依赖能力没证据：回 G2。设计变更沿真实依赖使相关通过记录失效，规则见协议二。

### 8.1 理想态与价值预测


#### 8.1.1 现状、理想态与配置手段

构建"现状 → 理想态 → 配置手段"的映射，它决定后续 Skill 要写到什么颗粒度：

| 现状问题 | 配置手段 |
|---|---|
| 缺知识导致试错 | 补业务规则或场景 Skill 文件 |
| 不知道能力顺序导致绕行 | 补阶段前置检查和工具集搭配指引 |
| 参数结构不清导致失败 | 补必填结构、字段来源、示例 |
| 找不到能力导致浪费 | 在 `apc_skill` 建立能力与文件索引 |
| 重复、稳定、高复用的真实步骤 | 评估做成编排型 TPE |
| 需要临场判断或中途交互 | 按开发者确认的边界保留给 SystemAgent、任务点或最终用户 |

**有真实项目基线时**可以预测轮次、失败重试或人工确认的改善幅度，但**必须**列出计算依据、假设、不可优化部分和误差范围。**没有基线时只做定性判断**，**禁止**编造数字（约束 2）。

#### 8.1.2 Focus 与泛化

形成使用模式候选：

- **Focus**（"让这个任务更快更省"）→ Skill 写到工具调用级别，固化执行路径
- **泛化**（"沉淀经验用于类似场景"）→ Skill 写到策略级别，保留选路弹性

Agent 根据开发者目标和证据给出推荐，但 **Focus / 泛化必须作为方案 Plan 的显式选择项由开发者确认**；不得因为参考项目更具体就自动选择 Focus，也不得因为素材不足就自动选择泛化。

#### 8.1.3 必须评估是否使用编排型 TPE

**这一步不能跳过，也不能默认不用。** 逐个里程碑对照第 4 节的信号判断，把结论和理由写入工单。

之所以要强制评估，是因为**做编排型 TPE 的工作量明显高于普通场景包**——要写脚本、备齐依赖、过上线检查、跑运行验证。省事的做法是全部交给 SystemAgent 临场处理，但那样会把消耗转移到每一次运行上。

两种做法的实际差异：

| | 交给 Agent 临场处理 | 固化成编排型 TPE |
|---|---|---|
| 每次运行的推理量 | 重新理解任务、重新决定调用顺序、重新组织参数 | 只在 FastAgent 承担的那几个环节里推理，确定性衔接不经大模型 |
| 推理消耗 | 上述推理**每次运行都会重复发生** | 确定步骤不经过大模型 |
| 耗时 | 随推理轮次增加 | 按脚本直接执行 |
| 一致性 | 同样输入可能走出不同路径 | 同输入同路径 |
| 出错定位 | 要读整段对话日志 | 定位到具体步骤 |

判断时先看**结构是否适合固化**：存在至少两个真实步骤，步骤顺序、数据流或扇出汇合关系稳定，不需要大模型在运行中改变下一步，就具备编排型 TPE 结构条件。再看**固化收益**：会被反复跑、定期产出、或最终用户每次只改几个参数时，固化的稳定性和成本收益更高。重复执行是重要收益信号，**不是唯一准入条件**；一次性任务若仍是确定、稳定的多步管道，也可以采用编排型 TPE。一次性探索分析若执行走向需要临场判断，则交给 Agent 或普通任务点。

向开发者提交结论时用业务语言讲清取舍：哪些阶段建议固化、这样做在稳定性和使用成本上的区别、哪些阶段建议保留临场判断以及为什么。**是否采用编排型 TPE 及对应资产边界由开发者在方案 Plan 中确认**；禁止只说"建议用编排型 TPE"而不说明理由，也禁止为了省制作工作量而不做评估。

向开发者提交价值预测与方案 Plan：预期效果、主要优化点、无法覆盖的部分、使用模式、编排型 TPE 取舍及待确认项。开发者确认前不进入正式资产创建。

### 8.2 执行形态选择


#### 8.2.1 资产概念

场景包的组成与 TPE 双类型关系在 [平台对象与运行模型](../references/平台对象与运行模型.md) 第五章；运行时自带的默认能力、四种执行形态各自的构成与能力边界，正本在 [平台对象与运行模型](../references/平台对象与运行模型.md) 第二章。本节只承载选型决策；业务侧的“需要什么”来自计划书第 ②⑥ 章。

#### 8.2.2 四者对照

| | SystemAgent 直接执行 | FastAgent | 普通任务点 | 编排型 TPE |
|---|---|---|---|---|
| 是否独立资产 | 否 | 是 | 是（TPE） | 是（TPE） |
| 上下文 | 主对话 | 每次全新隔离 | 独立 | 独立 |
| 能否与最终用户交互 | 能 | **不能** | **能** | 单条**不能** |
| 执行步骤 | 临场决定 | 临场决定 | 临场决定 | **预先固定** |
| 自带文件/命令/邮件 | — | **不自带** | 自带 | 自带 |
| 与业务路线的关系 | — | 被编排型 TPE 调用 | **不能**作为路线节点 | 可作为路线节点 |
| 多次运行的一致性 | 每次重新推理，路径可能不同 | 每次重新推理 | 每次重新推理 | 同输入同路径 |

#### 8.2.3 怎么选

按以下顺序完成一次决策，**不要**按复杂度、步骤数量或资产数量来回切换：

1. 先判断执行路径是否需要大模型在运行中决定下一步，或是否需要自然语言往返。需要时使用普通任务点；不需要时继续。
2. 再判断是否存在至少两个实质步骤、稳定数据流、固定扇出/汇合，或同一路径需要参数化复跑。存在时使用编排型 TPE；需要多个职责边界时拆成多个编排型 TPE 并写入图业务路线。
3. 若整个任务是一个环节的完整工作——一次输入，自己带着工具搜、读、判、写直到产出，一次输出——使用 FastAgent，不为它增加单步转发编排型 TPE。
4. 若只是当前上下文中确定的少量调用，且没有独立复用价值，由 SystemAgent 直接执行。

决策结果可用下表复核：

| 需要 | 形态 |
|---|---|
| 确定的 1–5 次调用、指令量小、仅当前场景用 | SystemAgent 直接执行 |
| 独立上下文、开放式判断、执行中需要自然语言交互 | 普通任务点 |
| 一个环节从输入到产出的完整工作（含其中的多轮工具调用）、无需中途交互、多场景复用 | FastAgent |
| 至少两个稳定真实步骤、固定数据流、会被反复跑 | 单条编排型 TPE |
| 单条编排型 TPE 需要发布业务事件、接受业务表单握手或进入 Delivery Review | 单节点业务路线 |
| 一条路线内多个编排型 TPE 的固定依赖、扇出、汇合和交付 | 多节点业务路线 |

任务"复杂"或"有多个步骤"**不自动**意味着要用普通任务点，也**不意味着要拆成多个 FastAgent**——一个 FastAgent 挂上工具就能完成复杂但无需交互的整个环节。只有执行中确实需要补信息、暂停确认或自然语言交互时才选普通任务点。

**看到这些信号优先按编排型 TPE 设计**：

- **反复执行的固定流程**：每日简报、日报、周报这类同一条流程反复跑的产出
- **固定流水线**：搜索 → 筛选汇总 → 生成报告（→ 发送）这类定型流水
- **多对象并行加汇总**：多品牌、多平台、多主题并行调研后做横向对比
- **参数化复跑**：最终用户每次只填几个参数，跑同一套步骤、产出同类结果

判别标准：固定流水线、参数化复跑和定期产出通常适合编排型 TPE；一次性探索分析若执行走向需要临场判断，则使用普通任务点或 Agent。不能只凭“是否重复”覆盖前述结构判断；成本结构的对比与"必须评估"的门见 3.3，不在此重复。

#### 8.2.4 FastAgent 粒度与数量纪律

**一个业务环节一个 FastAgent。** FastAgent 是带工具的完整执行单元（正本见 [平台对象与运行模型](../references/平台对象与运行模型.md) 2.2）：一个环节里“搜索 → 筛选 → 读取 → 判断 → 按规范产出并落文件”这一整串，该由**一个** FastAgent 挂上所需工具组一口气做完；脚本只负责环节之间的确定性衔接。三条判据：

1. **拆不拆看职责，不看步骤**：拆分 FastAgent 的唯一理由是职责边界不同——不同领域知识、不同产出契约、需要在别处独立复用。同一环节内步骤再多也不拆；**禁止**为每个判断点建一个 FastAgent，**禁止**按“角色”把同域职责拆成多个只在措辞上不同的 FastAgent。
2. **工具挂给 FastAgent，还是脚本自己调，看“下一步靠不靠结果决定”**：固定的准备与收口（取表单值、取数据集固定字段、落产物目录、发事件、回写）由脚本 `tool()` 做；凡是要看着结果决定下一步查什么、读什么、改什么的，属于 FastAgent 内部——把工具组挂给它。脚本里出现 `tool → FastAgent → tool → FastAgent` 的长链，多半是把本该属于一个 FastAgent 的环节切碎了。
3. **不挂工具、只做文字变换的 FastAgent 是误用**：读文件、写文件、格式转换、数据搬运这类去掉大模型也能确定性完成的步骤，直接用工具调用，**禁止**为其创建 FastAgent——无论赋予什么角色。

同一条编排型 TPE 内**同域多类产出**（简报、文案、卡片方案……）仍是**一个 FastAgent、一次调用做完**：提示词写共同原则与各交付物的先后，每类交付物一份规范文件在执行中按需读取，一次返回全套。只有当不同交付物要在**不同节点、不同时间**产出（中间隔着用户确认）时，才用交付物参数分次调用。把同一节点内的几种产出拆成同一 FastAgent 的三次连调（`FA(brief) → FA(copy) → FA(layout)`），和拆成三个 FastAgent 是同一个错误。

两个从真实制作里抓出来的切碎样子，照着对：

- **录入环节切成三段**：用户给的 Excel 或截图要还原成结构化记录，是一个环节——挂文件与识图工具的**一个** FastAgent 自己读、自己还原、自己校验；"脚本先 `shell` 抽表 → FastAgent 只做文字还原 → 脚本落文件"就是把它切成了三段，FastAgent 退化成不挂工具的文字变换器（判据 3）。
- **复用旧 FastAgent 带进来的切碎**：从旧包复用的 FastAgent 若是按交付物分发、每次只出一种产出的形态，不因为"已有"就沿用——改提示词让它一次出全套，或克隆后改；粒度按本节重审，复用不豁免。

方案中 FastAgent 超过 3 个时，**必须**逐个说明不可合并的理由（职责边界具体是什么；该判据同时列入方案挑战检查清单）。

#### 8.2.5 两个相反的错误

两个相反的错误都要避免：

**不要给单个 FastAgent 套一层编排型 TPE。** 如果脚本只做一件事——调用一个 FastAgent，然后把结果原样返回，中间没有任何其他处理——这层编排型 TPE 不提供任何价值，**直接使用那个 FastAgent** 即可。

**也不要因为步骤少就否定编排型 TPE。** 一条只有两三步的线性流程（搜索 → 清洗 → 汇总）完全正当。判据是**有没有至少两个实质步骤、数据有没有在步骤之间流转**，与步骤多少无关。

### 8.3 业务路线设计


计划书第 ③ 章的业务路线图在这里落成真实的业务路线对象设计（节点、映射、运行中交互、Agent 介入、交付与审阅）；组装写入在S3 第 7 节。

#### 8.3.1 业务路线对象

业务路线是场景包上的**一个整体对象**，用来固化业务入口、运行身份、执行依赖、交付与审阅。路线可以只有一个编排型 TPE 节点，也可以包含多个编排型 TPE：

- **单节点路线**：单条编排型 TPE 声明或调用业务事件、需要业务表单握手、需要 Delivery Review，或需要由业务应用启动时使用。只有一个节点不代表可以绕开 Business Runtime。
- **多节点路线**：一条路线包含多个编排型 TPE 的固定依赖、扇出、汇合、交互和交付时使用。
- **直接派发**：仅适用于没有业务事件契约、没有 `emit_business_event`、不依赖 Business/Runtime 握手的单条编排型 TPE。

构成：

```text
业务路线对象
├── 版本标记
└── 路线 ×N                     每条路线对应一种业务走法
    ├── 唯一标识、名称、描述
    ├── 入口表单标识
    ├── 路线级输入定义
    ├── 节点依赖图                节点引用已挂载的编排型 TPE，必须无环且全部可达
    ├── 节点输入映射              逐字段声明取值来源：路线输入，或依赖的上游节点输出
    ├── 运行中交互（可选）         上游成功后才能确定、且供尚未派发的下游节点使用的输入
    ├── 节点级 Agent 介入（可选）  节点成功后需要检查或处理异常时声明
    └── 唯一最终交付与审阅动作  交付核验与业务验收是两个独立阶段
```

**JSON 里的 orchestration 就是这里的路线。** 场景包对象上的字段叫 `workflow_orchestration`（整体业务路线，一包一份），它里面的 `orchestrations[]` 每一项才是一条路线，`orchestration_id` 是路线的标识——路线 Bubble、结单核对、Runtime 绑定都以它为单位。中文说"业务路线"指整体对象，说"路线"指 `orchestrations[]` 的一项，别把英文字段名当成中文的"业务路线"。

写入时采用**整体替换**语义，因此写前**必须**反读原值（见 G4 第 8.7.1 节）。字段的具体名称、结构和版本要求以 `get_diagnosis_doc` 的当前契约为准（见 G4 第 8.4.1 节）。

运行期事实：已发布路线在业务应用与聊天两个入口天然并存，走哪个入口由最终用户自选（界面经 Runtime 运行，聊天直调时业务事件自动降级）——这是平台行为，不是设计决策。制作侧**不设计**也**不引导**入口选择。

#### 8.3.2 何时不使用固定业务路线

以下情况**不要**强行画成固定依赖图：

| 情况 | 应当采用 |
|---|---|
| 整条路径需要临场规划，或 Agent 介入产生的新值要成为后继输入 | 普通任务点 |
| 最终用户改稿、重做或改走另一条路线 | 冻结当前交付、开启新的运行实例。**禁止**在同一张图里画回边模拟循环，**禁止**覆盖旧交付或旧文件 |
| 制作期就能预知的最终用户输入 | 全部放入口表单，不用运行中交互 |
| 只有上游节点成功后才能确定、且要供尚未派发的下游节点使用的输入 | 节点级运行中交互 |
| 节点成功后需要 Agent 检查或处理异常 | 在该节点声明 Agent 介入，并写清指令和可验证的继续或接管标准 |

业务路线只调度**已经存在且通过单体验收**的编排型 TPE。场景包没有编排型 TPE 时**禁止**伪造空节点或空图。

### 8.4 架构方案设计


#### 8.4.1 工具集划分

**工具集划分**：

- 预加载：每次运行都必须出现的核心能力
- 动态：按需加载的辅助能力
- 选型规则：克隆官方包继承的核心工具集**不可**移除；优先复用系统级工具集；**按能力域**匹配，**不要**按业务场景创建专用工具集

**执行形态提案**：按第 4 节形成普通任务点、FastAgent、编排型 TPE 或直接执行的候选边界，**不要**用"默认用 FastAgent"或"只有交互才建任务点"这类简化规则。Agent 必须说明推荐理由、运行体验、成本和可变性，把第 3 节的评估结论纳入制作书第 ⑧ 章；开发者确认后才落成具体资产，**禁止**在实现阶段自行推翻已确认结论。

#### 8.4.2 内部资产清单

**内部资产清单**（记入工单，除非开发者要求技术说明，否则不放入业务方案）：

- 每个 FastAgent：名称、职责、输入输出、真实关联的工具组
- 每个工具集：能力域、成员、加载方式、使用指南要点
- 每个任务点：路由描述、交互需求、输入输出、关联工具集
- 每条编排型 TPE：稳定业务阶段、脚本要用的工具名、完整依赖清单、输入输出定义、辅助文件、副作用；配套业务应用时，**每个输入字段的来源**（入口表单 / 读业务应用数据集 / 上游节点）与数据集缺失时的回退（G4 第 8.9 节）
- 每条业务路线：入口、节点、映射、交付审阅、重入方式
- 数据集：为什么绑定、在哪个节点读取

所有 ID **必须**工具查询确认（约束 4）。

**开发者可见的业务路线图**：提案包含编排型 TPE 或固定业务路线时，在完整方案 Plan 中用业务阶段名称画出每条候选路线的入口、依赖、扇出/汇合、最终用户与 Agent 介入、最终交付、审阅责任和动作出口。它与内部资产清单分开：前者用于确认产品如何运行，后者才用于确认真实资产如何承载；不得把内部节点标识、工具名或字段映射暴露到业务方案中。

#### 8.4.3 执行结构表

方案的**强制产出**。为每条编排型 TPE 建立执行结构条目：

- 步骤清单：每步做什么、用什么（工具或 FastAgent）
- 步骤间依赖：谁的输出喂给谁
- **并行组**：相互无依赖且可安全并发的步骤归入同一并行组；相邻无依赖步骤**未**归入并行组的，写明原因（副作用顺序、共享路径、会话状态等）
- FastAgent 清单：本条编排型 TPE 用到的全部 FastAgent，及按 4.4 的不可合并理由

**并行组怎么画**，逐步骤按序检查：

1. **数据依赖**：这一步的输入是否用到另一步的输出？不用，继续；
2. **副作用独立**：是否写同一路径、共享同一会话、或有顺序语义的外发动作？没有，可并行；
3. **典型形态点名**：**对多个对象执行同一操作（循环逐个调用工具或 FastAgent）默认设计为并行组**——串行处理 N 个独立对象是最常见的浪费，除非对象间有真实依赖或共享副作用，并写入 `no_parallel_reason`。

设计时需要正反例的，读 `get_diagnosis_doc(otpe_example_parallel)`——**不要**等到写脚本才第一次接触并行原语。

**展示载体判定**：`by` 为 FastAgent 的步骤和关键工具步骤，建表时逐步判定其结果是否面向最终用户，三档：**不展示**（内部中间产物，默认）／**进业务事件**（值得单独展示的中间里程碑，走 G4 第 8.5.4 节 事件候选流程，由开发者确认）／**进交付**（内容作为业务字段纳入最终 `output`——仅交付文件路径时，界面只能提供预览与下载，渲染不出文件里的内容）。判定记入该步的 `user_facing` 字段。***FastAgent 与工具的原始返回不是展示载体***——要给用户看的结果必须经事件或交付转成业务表达（如"素材盘点完成：4 张中 1 张可直接使用"，而不是工具返回原文）。

按总入口 5.1、5.3 落本地工作副本与工单权威快照。本表建立后，后续任何脚本或结构修改都**必须**同步更新对应条目（见 G4 第 8.4.4 节）。

#### 8.4.4 起草 apc_skill 与场景 Skill 文件

**起草 `apc_skill` 与场景 Skill 文件**：按 本文第 8.6.3 节 校验颗粒度——逐一对照第 3 节里每个"预期减少的轮次"，确认都有对应的可执行指导，且每个文件都有明确读取时机。

### 8.5 方案挑战与制作书定稿


#### 8.5.1 方案挑战

创建任何资产前**必须**完整读取 [方案挑战检查清单](../checklists/方案挑战检查清单.md) 并执行。质疑成立就修方案；不成立就说明证据和取舍。**禁止**在证据不足时判定通过。

挑战以执行结构表为对象逐条目进行，**只处理状态为 `pending` 的条目**（总入口 5.3 累加机制）；全部条目通过后，将执行结构表表级布尔位 `challenged` 置 `true`。

#### 8.5.2 完整《场景包制作书》：在计划书上补第 ⑧⑨⑩ 章

S1 的七章计划书（`build_book`，`stage="S1"`）原样沿用，本节补三章，合起来是完整的《制作书》——本 Skill 各处所说的“方案 Plan”。**它是制作期唯一的依据**：定稿后编排型 TPE、接口、前后端全部照它落地，不再向开发者提问；所以它必须具体到“照着能做出来”，并且**每个设计决定都带选择原因**（选了什么 / 没选什么 / 为什么）。

##### 第 ⑧ 章 资产设计（七小节，不可省略）

| 小节 | 内容 | 来源 |
|---|---|---|
| **⑧-1 路线与人群映射** | 是否多套业务路线：每条路线服务计划书 ① 里的哪类人群 / 商家类型、适用条件与选路节点；多路线共享哪些节点；只做一条路线时说明为什么一条够。**选择原因**：为什么按人群分路线而不是在一条路线里分支，或反之 | 计划书 ①②③ + 5.1 |
| **⑧-2 每条路线的业务路线流程** | 逐路线一张流程表：节点顺序与依赖（无环、可达）；每个节点 = 哪条编排型 TPE；节点内步骤清单（每步用什么工具或 FastAgent、输入从哪来、输出给谁）；入口表单字段与 `input_schema`；节点间映射；运行中交互（哪个节点后弹哪张表单 `form_id`、每个字段的名称 / 类型 / 必填 / 说明——这是 S3 落 `forms/<form_id>.json` 与业务应用做页面的依据）；Agent 介入点；业务事件（哪些节点发 `stage_*`、给谁看）；交付映射（哪些文件与业务字段进 `delivery`）；审阅形态与动作（承接计划书 ④）。**选择原因**：为什么固化成编排型 TPE 而不是交给任务点 / 直接执行；并行组为什么这样画 | 5.1、6.3、12–14 节预告 |
| **⑧-3 FastAgent 设计决策** | 逐 FastAgent 一行：承担计划书 ② 里的哪个环节；挂载哪些工具组、为什么这些；输入定义要点、输出契约；规范文件清单。**核心选择原因**：这个环节为什么是**一个 FastAgent 带多个工具连续执行**（边搜边判、读完再决定、试错取数）而不是拆成多个单输出 FastAgent；或者反过来，为什么这个环节只需要一个单输入单输出的 FastAgent、工具在脚本里调（4.4 粒度纪律的逐例落地）；超过 3 个 FastAgent 时逐个说不可合并的职责边界 | 4.4、6.2、6.3 |
| **⑧-4 工具集与依赖** | 预加载 / 动态工具集划分与理由；每个工具组的来源（平台已有 / 新注册 MCP / 私有包 / Skill 包）；需要授权卡的能力；复用了哪些已有场景包或派生自哪个包；**脚本要直接调用的复用工具建议各一行**：输入约定（文件参数收 URL 还是 workspace 路径、必填、值域）、返回结构是否已声明、是否安全只读可取样——这是 G4 第 8.8.2 节 接入建议的清单，读不到契约的工具标注"契约未读，制作时补" | 2.2–2.4、6.1 |
| **⑧-5 普通任务点、直接执行与知识文件** | 保留给普通任务点或 SystemAgent 直接执行的环节及理由；`apc_skill` 大纲（业务终点、里程碑、选路、权限边界、文件索引）；场景 Skill 文件清单与读取时机；Focus / 泛化选择 | 3.2、4.3、6.4 |
| **⑧-6 业务应用数据集字段表** | **未规划配套业务应用时本节只写"不适用"**，不凭空设计表，路线里也不能出现读写数据集的步骤（计划书 ⑤ 的开关）。规划了配套应用时：先按下方建模约定分成实体 / 情境 / 历史事件三类表并画出运转链，再逐表逐列：列名（用画像的词）/ 类型 / `[editable:user\|agent\|system]` 声明 / 来源（用户在应用填、编排型 TPE 哪个节点写回、系统）/ 被哪条路线的哪个节点读；审计四件套与 `row_version`；文件路径列。**多商家类型的字段变体**：哪些列对某类商家可选或缺省不同、哪些表只有某类人群才有——写成“公共列 + 按类型的可选列”，不为每类商家另建一套表。**选择原因**：为什么这些字段进数据集而不是每次让用户填；用户列与产出列怎么拆开避免覆盖 | 6.5、计划书 ⑤、app-creator 约束 9 |
| **⑧-7 配套业务应用** | 是否制作；若制作：页面清单（三必备页 + 按业务取舍的看板 / 数据管理 / 业务发起 / 项目页）、看板要看哪些字段（来自 ⑧-6 的产出列）、哪些列在数据管理页可编辑、文件在哪出现、发起入口对应 ⑧-1 的哪条路线；**这一节是交给 app-creator A1 的输入**——A1 在此基础上细化，不推翻。不制作时写明数据如何随交付给到用户 | 计划书 ⑤、app-creator A1 |

**⑧-6 的建模约定：数据的归属与运转**。字段表不是平铺一堆列——先按三类表划分，每类的写入方、更新方式、读取方与保留策略不同：

| 类 | 是什么 | 例 | 谁写 / 怎么更新 | 谁读 | 保留 |
|---|---|---|---|---|---|
| **实体** | 用户经营的对象，长期存在、慢变 | 门店、账号、菜品、素材库 | 用户在应用填改（`editable:user`）；主键与审计列系统写 | 发起时铺底进入口表单；编排型 TPE 读基线信息；看板按实体分组 | 长期；删除走软删 |
| **情境** | 当前目标、偏好、约束、时段——决定“这一次怎么做” | 本月目标、禁用表达、活动档期、风格偏好 | 用户填改为主；生产要给建议时写**独立的建议列**（拆列，不覆盖用户列） | 编排型 TPE 执行中按需取（G4 第 8.9 节 时机 2）；应用发起时带入 | 覆盖更新，`updated_at` 留痕 |
| **历史事件** | 每次运行 / 发布 / 效果的记录，只增不改 | 一次生成的选题与结果、发布后的效果数据、用户的审阅动作 | 编排型 TPE 收尾回写（`editable:agent`，带 `last_run_id`）；应用生产回流 | 看板聚合、下次运行参考、执行记录页 | 追加；不覆盖旧交付 |

- **归属**：情境与历史事件都挂在实体上（`set_relations` 按表名声明关系）——任一条历史事件必须能回答“属于哪个实体、来自哪次运行”；
- **运转逻辑**：用户在应用填实体与情境 → 发起时铺底进入口表单 → 编排型 TPE 读情境与历史决定策略 → 产出写回历史事件 → 看板从历史事件按实体聚合 → 用户修正实体 / 情境 → 下次运行更准。制作书里把这条链画一遍，逐箭头标出读写的表与列；
- **多商家变体**落在实体表：一个“类型列”+ 按类型的可选列；情境与历史事件表结构对所有类型共用，只是取值不同。

##### 第 ⑨ 章 能力缺口、发布范围与授权

缺口处理方案（第几层、影响什么）、发布范围（哪些资产与路线属于本次候选版本）、是否“前三层候选验收通过后上线”的执行承诺、端到端全真验证范围。**“发布范围”和“上线授权”必须分开表达**：制作书明确写出“前三层候选验收通过后上线”并由开发者统一确认时，不再在发布前重复询问；没有该执行承诺、只列发布范围时，P7必须另行取得上线授权。

##### 第 ⑩ 章 制作纪律：定稿之后

- 制作期**不再向开发者提问或提案**，全部依据本书；工程细节（命名、代码组织、等价实现）自主决定；
- **什么算冲突、必须停下沟通**：本书与真实契约（实时 Schema、`get_diagnosis_doc`）不符；平台能力不支持本书设计的模式；按本书做会触碰第 ⑦ 章红线；发现计划书口径（画像、旅途、交付角色）需要改；本书两处自相矛盾。沟通时列冲突点、双方依据与候选处置，**不静默取舍、不绕过、不自作主张改书**；
- 冲突解决后**整份重写制作书**并重新确认，再继续；
- 制作书之外的“更好的想法”记入工单备忘，不在本次实现。

##### 写作与落账

- 每个设计决定写成“选择 / 未选 / 理由”三段，不写只有结论的条目；
- 术语用画像的词，工具名、Schema、节点标识只出现在 ⑧-2 ~ ⑧-6 的技术表格里，不进 ①–⑦；
- 完整制作书**整份重写进工单**（`build_book`，`stage="S2"`）；设计与计划书冲突时不改制作书糊过去——回 G1 第 8.5 节更新计划书并重新确认。

**格式自检**：①–⑩ 齐全；⑧-1 的每条路线在 ⑧-2 有流程表、在 ⑧-7 能找到它的发起入口，规划了配套应用时还要在 ⑧-6 能找到它读写的列（未规划则 ⑧-6 为"不适用"且 ⑧-2 无任何数据集步骤）；⑧-3 每个 FastAgent 都对应计划书 ② 的一个环节并写了“为什么是一个 / 为什么这样挂工具”；⑧-6 每列有声明与来源；⑨ 的发布范围与 ⑧-1 的路线一一对应；⑩ 在。

#### 8.5.3 开发者确认

执行结构表 `challenged=true` 后，连同完整《制作书》（含 S1 已确认的七章与本节的 ⑧⑨ 章）一并展示给开发者，由开发者确认 ⑧⑨⑩ 三章并复核 ①–⑦ 未被资产设计改变语义。开发者要求改的地方改完**整份**重新提交；这次确认之后进入制作期，按第 ⑩ 章纪律不再逐项请示。本次确认**兼作关键 FastAgent 的圈定时刻**：开发者在 FastAgent 清单上圈出关键产出环节（面向最终用户的输出文案类），被圈定的环节在S3 第 3 节制作时必须执行样例选择流程（G4 第 8.3.2 节）。Focus / 泛化在同一次确认中显式选择。

#### 8.5.4 制作书硬门

**制作书硬门**：只有开发者对完整制作书（含 ⑧⑨⑩ 章）完成统一确认后，才能进入 S3 开始依赖资产、普通任务点、场景包草稿、编排型 TPE、关联关系或业务路线的创建与修改。确认前只允许继续只读调查、候选方案起草、方案挑战和不改变外部状态的验证。任一未确认项不得被 Agent 当成默认值写入资产；后续若改变路线依赖、交付对象、审阅责任、动作、重入方式或介入点，属于计划书口径变化，回 G1 第 8.5 节更新计划书并重新确认，再回本节更新制作书。确认后，同一范围内的可逆离线操作获得授权；上线动作仅在 Plan 同时满足上一段的明确执行承诺时获得授权（约束 6）。

### 8.6 信息归属与知识写作


#### 8.6.1 信息归属

**同一条信息只写在一个地方。** 这是所有配置决策的根本依据。

| 信息 | 权威位置 |
|---|---|
| 单个工具的用途、参数、正式 Schema | 工具组（MCP 层工具描述） |
| 工具或 FastAgent 的搭配方式、调用顺序 | 工具集使用指南 |
| FastAgent 的自包含推理方法 | FastAgent 提示词 |
| 普通任务点的交互式执行方法 | 任务点提示词 |
| 单阶段稳定步骤与数据流 | 编排型 TPE 脚本与输入输出定义 |
| 单节点或多节点业务路线的入口、依赖、映射、中途交互、最终交付 | 业务路线 |
| 业务终点、候选路线、里程碑、选路条件、权限、前置检查、知识读取时机 | `apc_skill` |
| 长知识、模板、案例、字段字典、详细 SOP | 场景 Skill 文件 |
| 数据语义与查询规则 | 数据集使用指南 |
| 页面与公开交互契约 | 业务应用源码（app-creator 线制作，不属于场景包资产） |

常见放错层级的情况：

- 工具集使用指南里重复单个工具的描述（那是工具组的事）
- 场景 Skill 文件里写 FastAgent 的内部逻辑（那是 FastAgent 提示词的事）
- FastAgent 执行时要用的写作规范、规则库挂在场景 Skill 文件下（FastAgent 读不到，见 8.2 可见性边界；按执行者归属挂到对应 FastAgent 名下）
- 工具集使用指南里写业务 SOP（那是场景 Skill 文件的事）
- `apc_skill` 或工具集指南里重复已固化在业务路线里的依赖图（形成两份真相，见约束 9）
- 同一信息出现在两个地方（必有一个放错了）

反过来也**不要**为了消除重复，把运行时 Agent 每轮都必须知道的业务路由、关键前置检查、能力选择和加载时机从 `apc_skill` 里删掉。

#### 8.6.2 文本字段与 Skill 文件的分工

| 资产 | 文本字段（始终注入） | Skill 文件（按需读取） |
|---|---|---|
| 场景包 | `apc_skill` | 场景 Skill 文件 |
| 工具集 | 使用指南 | 工具集 Skill 文件 |
| 普通任务点 | 提示词模板 | 任务点 Skill 文件 |
| FastAgent | 提示词内容 | FastAgent Skill 文件 |

区分标准：**Agent 每轮都需要知道的写文本字段，做某件具体事时才需要查的写 Skill 文件。**

文本字段适合决策规则、约束、路由逻辑。Skill 文件适合大段领域知识、脚本模板、案例、示例输出、详细 SOP。

每个上传的 Skill 文件**必须**被对应文本字段在明确阶段按名称索引，否则 Agent 只看到文件名、不知道何时该读。

**可见性边界（知识不随挂载关系流动）**：每类 Skill 文件只对它挂在名下的执行者可见——场景 Skill 文件由项目里的 SystemAgent 读取；FastAgent 运行在隔离会话中，能读到的只有**自己名下**的 FastAgent Skill 文件和所挂工具集的 Skill 文件；编排型 TPE 脚本只读自己任务点目录（`ctx.skill_dir`）。***场景包挂再多行业知识，FastAgent 一篇也读不到；FastAgent 执行要用的知识必须挂到它自己名下***，并按上面的索引规则在其提示词中写明何时读哪篇。

#### 8.6.3 Skill 颗粒度标准

**从理想态反推颗粒度。** 凡是希望减少的失败、绕行或沟通轮次，都**必须**有对应的可执行指导。

| 目标消除的瓶颈 | 至少要写到什么程度 | 主要归属 |
|---|---|---|
| 不知道先做什么 | 阶段目标、前置检查、能力选择、交付条件 | `apc_skill` |
| 不知道工具怎么搭配 | 先取得什么结果，再由什么能力消费 | 工具集使用指南 |
| 不知道参数怎么准备 | 必填结构、来源、约束、失败处理 | 工具集 / 场景 Skill /编排型 TPE 定义 |
| 找不到能力 | 条件 → 加载哪个能力域或读哪个文件 | `apc_skill` |
| 缺领域知识 | 可执行规则、数据字典、案例 | 场景 Skill 文件 |
| 交付结果不稳定 | 输出模块、质量标准、验收证据 | `apc_skill` 加对应执行资产 |

**不达标的写法**（缺前置步骤、缺判断条件、缺产出定义）：

- "创建创意，配置品牌组件、标题组件"——没说前置步骤和参数结构
- "使用素材处理工具进行裁剪"——没说用哪个工具、什么条件下用
- "输出结构化投放方案"——没定义方案必须包含哪些模块

**达标的写法**：

- "创建创意前：先取得模板列表，再查组件依赖，最后按模板要求准备素材"
- "素材处理判断：尺寸不对走缩放；格式不对走转换；需要生成图走生图再入库"
- "投放方案必须包含：推广目标、日预算、定向策略（地域加年龄加兴趣）、创意方向、投放时段"

**禁止**"完善流程""调用相关工具""输出高质量报告"这类不可执行的空话。**必须**补齐触发条件、输入来源、关键判断、期望产出和失败处置。

#### 8.6.4 apc_skill 必须包含什么

`apc_skill` 是场景包最高优先级的知识注入，写好它是本项工作的核心产出。至少覆盖：

1. **场景问题与业务终点**：解决什么问题、适用条件是什么
2. **里程碑**：分几个阶段、每阶段目标和最终用户可见产出
3. **候选路线与选路节点**：不同目标或前置状态对应哪条路径、在哪里判断走哪条
4. **必需输入、预期交付、验收标准**
5. **权限边界**：哪些 Agent 可以自主判断、哪些必须最终用户决定、哪些属于高风险授权；这些边界由开发者在制作 Plan 中确认
6. **未被其他资产固化的关键业务规则、前置检查、能力选择**
7. **Skill 文件索引**：在哪个阶段按名称读取哪个文件

不应包含：具体实现细节（选择器、路径、接口参数格式、代码片段），以及约束 9 列出的禁写内容。

#### 8.6.5 工具集使用指南必须包含什么

只写**工具之间的关系**：适用条件、输入怎么衔接、结果怎么审视、失败怎么处理。单个工具的说明留在工具组。

已经由编排型 TPE 脚本固化的调用顺序**不要**在这里再写一份。这里只说明"该编排型 TPE 是这条稳定流程的首选入口"，以及底层工具或 FastAgent 各自可独立处理的情况。

多个工具或 FastAgent 需要配合时**必须**写搭配模式。工具彼此独立、且不含 FastAgent 时可以为空，不算缺陷。

### 8.7 业务应用数据集的业务面


***没有配套业务应用，就没有业务应用数据集。*** 它是用户点开应用时才 copy 出来的那份库；场景包单独运行时这份库根本不存在，业务应用数据集 FA 读到的只会是 `found=false`。所以计划书 ① 的业务终点里凡是"记下来 / 存起来 / 下次接着用 / 看历史成绩"这类目标，都以配套业务应用为前提——本章第一问"是否规划配套业务应用"就是这类目标的开关：规划 → 这些目标成立，数据面交 app-creator 线；不规划 → 这些目标从计划书移除，或改成"随交付给到用户的文件"，场景包里**不设计**读写数据集的路线与步骤、**不挂** `business_app_dataset` 工具集、脚本**不调**业务应用数据集 FA。资产目录里名为"××档案场景包""业务档案助手"的官方包属于业务档案产品线（另一套数据面），不是业务应用数据集，也不拿来替代它。

场景包规划配套业务应用（约束 8）时，最终用户的长期数据都在**业务应用数据集**里（app-creator 线制作模板，用户点开应用时各得一份）。计划书只回答**业务问题**——用画像的词，不谈字段落地：

| 问题 | 计划书里要写什么 |
|---|---|
| **如何作用** | 用户自己的哪些数据（门店档案、历史效果、禁用表达……）会影响路线怎么走、产出怎么写——逐项说影响的是选路、参数还是文案 |
| **何时用到** | 这些信息是发起时就该带上的（用户一填就有）、还是跑到中途才需要“看情况取”的——只做业务层面的区分，走表单还是走脚本读在 本文第 8.8 节 决定 |
| **如何回流** | 哪些产出与效果数据应该留在用户的资产里供看板展示与下次参考、留成什么粒度、是直接生效还是先作草稿等用户确认（回流入库语义由开发者定） |

数据集里的表与列由 app-creator 线设计，但**列名与业务说明必须与本计划书的画像用词一致**——两条线各说各话，编排型 TPE 写回的字段应用就展示不出来。未规划配套业务应用时本节写“不适用”，并说明数据如何随交付给到用户。

### 8.8 业务应用数据集读写的落地


计划书第 ⑤ 章只回答了业务问题；本节把它落到字段与通道：

| 计划书里的业务判断 | 落地 |
|---|---|
| 发起时就该带上的用户数据 | 进入口 `input_schema`，由业务应用在发起时带入，时机 1 见 G4 第 8.9 节——不为它起 FastAgent，也不在脚本里读 |
| 中途“看情况取”的数据 | 编排型 TPE 脚本调业务应用数据集 FA 读（G4 第 8.9 节 时机 2），每条业务流至多一次读；表单字段设可选、`found=false` 回退表单值 |
| 要回流的产出与效果数据 | 脚本收尾 `operation="write"`（G4 第 8.9 节 时机 3），`context_hint` 给唯一键；写回哪张表哪些列与 app-creator 线对齐，列名用画像的词 |

逐字段写进内部资产清单（6.2）与执行结构表（6.3）的对应步骤；未规划配套业务应用时本节不适用。

### 8.9 数据设计（本阶段的重心）


从一个已上线的场景包出发，设计出一个完整的业务应用：它是什么、给谁用、场景包给了它什么入口和出口、存什么数据、有几页、每页读什么写什么、字段的可编辑性怎么在页面上体现、文件在哪里出现。做法与场景包线一样：先向开发者要参考资料，再拿一份《业务应用计划书》（每页截图展示 + 后端功能阐述）给开发者确认，确认后才进入 A2 / A3 制作。

应用表是**用户的业务资产**。先分类，再逐表回答五问。

#### 8.9.1 先把数据分四类，放对地方

| 类别 | 例子 | 放哪 |
|---|---|---|
| **用户自己的数据**（用户在应用里记载、编辑的） | 门店档案、账号绑定、素材索引、禁用表达、目标与偏好 | 业务应用数据集，列声明 `editable:user` |
| **场景包运行期所需 / 产出的字段** | 每次运行的选题、生成结果、效果指标、回写的统计 | 业务应用数据集，列声明 `editable:agent`；这些列是 S3-2.4 里编排型 TPE 读/写的对象 |
| **系统字段** | 主键、`created_at` / `updated_at` / `updated_by` / `last_run_id` / `row_version`、项目与 Runtime 关联 id | 业务应用数据集，列声明 `editable:system` |
| **界面意图与实体引用** | 草稿、筛选条件、当前 businessId、已读态 | `sdk.storage`（viewer × 实例隔离），**不进库** |
| 文案、路由名、开关 | — | 代码 |

***不要把该进库的数据写成前端 mock 数组、静态 JSON、后端常量或占位符***——这是脚手架的第一条数据纪律。

进库的表再按**实体 / 情境 / 历史事件**三类组织（长期慢变的经营对象 / 决定“这一次怎么做”的目标与约束 / 只增不改的运行与效果记录），情境与历史事件挂在实体上——这套约定的正本在场景包制作书 ⑧-6（business-app-creator 本文第 8.5.2 节），本节沿用它画出的运转链，不另起一套。

#### 8.9.2 逐表五问

1. **存什么**：按 4.1 分类列出每列；看板要算的指标所需字段此刻就要有；“读历史数据优化后续选择”的预留字段也在这里定；
2. **逐列可编辑性**（约束 9）：`user` / `agent` / `system` 三态，**每列恰好一个写入方**——用户和生产都要写的信息，在模板阶段就拆成两列（用户填的 + AI 建议的），不靠运行期仲裁；
3. **审计**：每张有写入的表带四件套 + `row_version`；来源标记（`user_edited` / `generated`）落在哪列；
4. **冲突规则**：行级并发（用户在编辑页改用户列、生产同时重写产出列）靠 `row_version` 乐观锁——后写方重读重试；***没有“静默覆盖”这个选项***；
5. **回流入库语义**：生产产出**直接入库**还是**先作草稿、用户在编辑页确认后入库**——按业务风险定（对外表达类建议草稿确认，内部统计类可直接入库）。

#### 8.9.3 文件怎么进数据面

数据集**只存路径与元数据，不存文件体**。三类文件各有来源与归属：

| 文件 | 从哪来 | 存什么 | 谁能改 |
|---|---|---|---|
| 用户现场上传（Excel、图片、素材） | 入口表单经草稿句柄 `project.upload` → 返回 `/workspace/...` 路径（项目级，属于这一次生产） | 表单值就是路径；要作为用户资产长期引用时，在数据集里存路径 + 文件名 + 上传时间（`editable:user`） | 用户（替换 / 清除） |
| 应用级持久文件（品牌手册、素材库、历史资料） | 应用内任意位置经 `sdk.file.upload` → 返回 `path`（不依赖项目、跨项目复用；`list` 能翻历史） | 表单值 / 数据集只存 `path` + `name` + `size` + 上传时间（`editable:user`）；作为编排型 TPE 输入时把 `path` 写进 formdata，宿主登记给目标项目 | 用户；源文件不因关联项目而移动或删除 |
| 过程交付物 | 编排型 TPE 写进 `ctx.output_dir`，经 `delivery.mapping` 登记为 `PublicDelivery.artifacts[].workspace_path` | 回流时存路径 + 所属 Runtime / delivery_id（`editable:agent`） | 生产（每次运行新增，不覆盖旧交付） |
| Runtime 用户文件 | 用户在执行记录页对某次运行补传/删除（`userFilePaths`，全量替换语义） | 不单独建表，读 Runtime 权威值 | 用户，经保留件 `useRuntimeUserFiles` |

产出：业务应用数据集模板草案（表 / 列 / 类型 / 逐列声明 / 审计字段 / 文件路径列），交 A2 落成真实模板。

### 8.10 项目模型与功能选择菜单


#### 8.10.1 项目：业务应用之下的一层

业务应用在项目**之上**：一个应用实例里，用户可以创建多个项目。**项目 = 用户的一次计划选择**——用户决定“这一次要干一件什么事”，一次业务路线运行连同它的入口表单、运行中表单、消息、文件、业务事件与交付，都装在这个项目里。项目是过程的容器，**不是**应用的数据面：长期沉淀的业务数据在业务应用数据集里，项目只通过 `system` 列（项目 id / `last_run_id`）与数据行关联。

开发应用时必须拿到**在这个应用实例里创建的全部项目**：`sdk.projects.list` 分页拉（打开 / 翻页 / 手动刷新时拉，禁轮询）+ `sdk.projects.onStatusChange` 按 `projectId` 就地更新（拉推成对）。列表只含本实例名下已受理的项目，两段式建项目的临时项目在首启受理前不入列表——这是设计使然，不是漏数据。

**项目详情也必须消费当前项目的状态推送**，不能只让列表实时、详情等待业务事件或 Runtime 查询。设计中分别画出“正在提交”“已受理，准备继续”“正在执行”：点击立即进入提交反馈；`accepted` 只结束业务确认阶段，当前项目 `running` 才是执行中的依据；若 `running` 先到，先展示执行中但保持尚未完成的提交锁。应答页与进度页共用项目层的句柄和过渡态，切换子路由不能丢掉这段过渡；`rejected` 回到可修正表单，`failed` 或发送失败显示错误。阶段进度仍来自业务事件，不能用项目 `running` 伪造已完成阶段（接入见 G6 第 8.1.3 节.1）。

用户发起一次生产时只有两种选择，页面上要让他显式选：

| 选择 | 用户做什么 | 应用做什么 | 何时用 |
|---|---|---|---|
| **创建** | 点动作按钮 → 填入口表单 → 提交 | 必经保留件 `useProjectDraft(draftKey)` 拿草稿句柄（一个表单会话一个句柄）；提交时 `project.business.start()` 触发**两段式建项目**：先懒创建服务端临时项目，再发起业务路线；首启 `accepted` 后临时项目转正入列表；发起后跳转项目页 | 新的一件事、新的一个对象（新门店、新一期活动） |
| **复用** | 点动作按钮 → 在项目下拉框里选一个已有项目 → 填表单 → 提交 | 下拉框选项**只来自** `sdk.projects.list`（无本地记录、不猜 id）；选中后经 `sdk.getProject(id)` 的句柄 `business.start()`，消息进入所选项目、不产生新项目；后一条路线能读到前一条在同一项目里的交付文件 | 在同一件事上做下一步（路线 2 接着路线 1 的产出） |

创建态 / 进行态的分界由此而来（总入口约束 3）：**业务发起页是唯一的发起入口**，项目页只看进度、应答表单、审阅交付，不发起新的业务路线运行。项目页里“再来一次”的需求，做法是跳回业务发起页并把该项目预选进下拉框。`permission='view'` 时创建与复用两个入口一起置灰。

#### 8.10.2 功能选择菜单（拿给开发者逐项定）

下面是当前脚手架（`frontend/README.md` 三、SDK 速览与 `src/sdk/docs/`）真实提供的能力，按“必备 / 建议 / 可选”分级。**A1 要拿着这张表向开发者逐项问**，结果（做 / 不做 + 理由）写进《业务应用计划书》第 ⑤ 章；勾选的每一项都要在 §5 页面设计里落到具体页面，并在 G7 第 8.1 节 自动化测试门里有对应用例。

| **可选** | 打开外部链接 | `sdk.ui.openExternal`（宿主确认框后 noopener 打开） | 跳到第三方后台 |
| **可选** | 图表 / 移动端适配 | 图表选型自由；主行动在移动端可达（§5.5 第 4 步） | 按用户使用设备定 |

不在表里的能力（例如应用自定义 env、第三方密钥注入、后端主动推送）当前脚手架没有，**不许诺**；开发者要时记为开放项，找平台确认。

### 8.11 场景包给了你什么（契约基线）


应用的**入口与出口全部由场景包定义**，不由应用发明。逐项**反读**（禁止推测），写成契约基线表记入工单：

| 接缝物 | 从哪反读 | 决定应用的什么 |
|---|---|---|
| **入口表单与中途表单** | `get_asset(scenario_package)` 返回的 `business_forms`（每张表单的 `form_id`、入口 / 中途、所属路线与节点、字段名与类型 / 必填、`skip_when`——由业务路线映射与 Schema 推出，权威）+ 场景包 Skill 文件 `forms/<form_id>.json`（标题、字段说明、控件提示、顺序）；据此手写契约区 `schema/packs/<pack_id>/forms/*.json`（`inputSchema` 与 `business_forms` 字段一致） | **入口**：业务发起页要实现哪几张表单、每个字段的类型/必填/文件字段；哪些字段由应用后端在发起时拼进 `submit_data`（用户不用填）、哪些必须用户填。**中途**：项目页要能应答哪几张表单、各在哪个节点后出现、`skip_when` 时不会出现 |
| **业务路线**（`orchestrations/*.json`：`entryFormId`、`formIds`、`delivery`） | 同上 | 有几条可主动发起的路线（= 几个“发起”按钮）；服务端中途会调起哪些表单（= 项目页要能应答的表单）；终态审阅形态（`user_gate+ask` 有动作按钮 / `user_gate+result` 自动交付 / `agent_gate` 只读） |
| **编排型 TPE `output_schema` / `display`** | 场景包编排型 TPE 资产 | **出口**：交付页能渲染哪些业务字段（对比、清单、结论），`display` 五字段兜底；**生产回流**能入库的字段来源 |
| **业务事件契约** | 编排型 TPE 资产 `business_event_contracts` | 项目页的进行态能显示到什么粒度（有 `stage_*` 才有阶段进度；没声明就不做进度模块） |
| **面向系统的公开语义**（business-app-creator S3-7.3） | 场景包工单 | 页面文案：路线的业务名、里程碑、交付、到达标准——**不用编排型 TPE 名、节点 ID、工具名** |
| **数据集读写通道**（business-app-creator S3-2.4） | 场景包编排型 TPE 脚本 | 哪些字段由编排型 TPE 经业务应用数据集 FA **读**（应用要保证这些列有数据）、哪些由它**写回**（应用要展示这些产出列） |

**契约区为空或只剩演示包，说明上游未就绪：停止业务设计并报告**，不照截图猜字段。多包（v4）时每包一个目录、`form_id` / `orchestration_id` 全 App 唯一。

**先读场景包的《制作书》**（场景包工单里的 `build_book`，S2 定稿版）：它的第 ⑧-6 章已经定了业务应用数据集的逐列字段、声明与读写来源，第 ⑧-7 章定了配套应用的页面清单、看板字段与可编辑列——**本节以它们为起点做细化，不推翻**；要改字段或页面范围，属于制作书口径变化，回场景包线沟通后再动。制作书里没有 ⑧-6/⑧-7（老包或未规划配套应用）时，才按本文 §4–§5 从零设计。

### 8.12 页面设计


#### 8.12.1 页数从哪来

页数 = 三个必备页面 + 按业务取舍的四类业务页面。不多不少的判据：**每个页面对应用户的一个明确意图**，多个意图挤一页会让高风险交互（提交、删除）和浏览混在一起，一个意图拆多页会造成孤岛。

| 页面 | 必备？ | 用户在这做什么 | 数据从哪读 | 动作往哪发 |
|---|---|---|---|---|
| **首页** | 必备 | 落地、看待办红点、进入各处；可以就是看板 | `useInbox().unreadCount`、后端统计 API | 导航 |
| **项目列表页** | 必备 | 看所有归属项目的状态 | `sdk.projects.list` + `onStatusChange`（拉推成对，禁轮询） | 进项目页 |
| **消息中心** | 必备 | 跨项目待答表单、结果通知 | `useInbox()` | 进对应项目的应答状态 |
| **看板**（展示态） | 按业务 | 看现状、决定干什么 | 后端统计聚合 API（只读 SQL） | 进业务发起 / 数据管理 |
| **数据管理**（编辑态） | 按业务 | 增删改自己的业务数据、上传/替换文件 | 后端 CRUD | 后端 CRUD（幂等写） |
| **业务发起**（创建态） | 有可主动发起的业务路线就必备 | 填入口表单发起一次生产；或选已有项目复用 | 契约区 `getForms`（无预填；稳定信息由后端在发起时拼进 `submit_data`） | `useProjectDraft` 草稿句柄 → `project.business.start()`（两段式建项目） |
| **项目页**（进行态） | 必备 | 看进度、应答服务端调起表单、审阅交付、看执行记录与已提交表单、编辑 Runtime 用户文件 | 业务事件 / `pending` / `getRuntimeForms` / `getRuntimeDelivery` | `reply()`（三次握手）、审阅动作只提交 `action_key` |

**禁止孤岛**：除首页外每个页面在任何状态（含错误、只读、`form-submitting`）都要有可操作的 App 内返回入口与确定性兜底；路由表必须有通配兜底回落首页。

#### 8.12.2 看板怎么选字段

看板的每个数值都要能回答“从哪张表、哪些列、什么口径算出来的”。选字段的规则：

- **只从业务应用数据集算**，不从 `PublicDelivery` 或聊天消息里现算——交付回流入库（4.2 第 5 问）才有看板；
- **指标 = 对 `editable:agent` 列（产出、效果）的聚合，维度 = `editable:user` 列（门店、账号、目标）与时间**；用户列本身不是指标；
- 每个指标标注：来源表 / 聚合方式 / 时间窗 / 编辑实时性（用户改了数据多久反映）；大结果分页、单查询在 10 s 内；
- 空数据是常态（新用户零数据）：每个看板块要有引导态，指向“去发起第一次”或“去补数据”；
- 指标数量宁少勿多——用户每天真的会看的那几个，其余进详情页。

#### 8.12.3 可编辑性怎么在页面上体现

列注释里的 `[editable:*]` 声明要**肉眼可见**地落到页面：

- **数据管理页**：只有 `editable:user` 列开控件；`agent` 列只读展示并标明“由生产写入”（含最近写入时间 / 来源运行）；`system` 列不展示或收进详情；
- **看板 / 详情**：一律只读；
- **文件字段**：全程只读卡片，值只能由上传动作产生——不出现路径文本框，不允许手改路径；编辑态有“替换 / 清除”，查看态无写入口；上传中有状态、失败可删后重传；提交必须等全部上传到终态；
- **`view` 权限 / `form-submitting` 期间**：全部写入口置灰并说明原因，返回入口不受影响；
- **用户列被生产建议覆盖的场景不存在**（4.2 第 2 问拆列），所以页面不需要“接受 AI 建议覆盖我的值”这种危险控件；需要采纳时是“把 AI 建议列复制到用户列”的显式动作。

#### 8.12.4 文件在页面上怎么出现

- **上传先分级，看文件属于谁**——两级都返回 `/workspace` 路径、表单值都只存路径，但归属和生命周期不同，选错的后果是真实的：

  | 文件属于 | 用哪级 | 怎么调 | 典型位置 |
  |---|---|---|---|
  | **这一次生产**（本次表单的附件、这次要处理的素材） | 项目级 | 草稿句柄 `project.upload(file)` → `project.file.getViewUrl / download`；组件 `shared/FileField`（必须传项目句柄） | 业务发起页的入口表单、项目页的运行中表单 |
  | **用户本人，跨项目反复用**（品牌手册、菜单、实拍素材库、历史资料） | 应用级 | `sdk.file.upload(file)` → `sdk.file.list / getViewUrl / download`；组件 `shared/ApplicationFileField`（上传 + 历史分页 + 预览 + 下载 + 多选） | 数据管理页、资料库；入口表单里"从历史资料里选"的字段 |
  | **某次运行的补充材料**（对已跑的运行补传 / 删除） | Runtime 用户文件 | 保留件 `useRuntimeUserFiles`（全量替换语义） | 项目页执行记录 |

  两条硬边界：***数据管理页不能用 `project.upload`***——草稿句柄上的首次上传会懒创建一个临时项目，用户只是想存一份资料却多出一个项目；**应用级文件要进本次生产**时不用重传，把选中的 `path` 写进 `business.start` / `reply` 的 formdata，宿主发帧前会重新解析并登记给目标项目，源文件不动。扩展名黑名单与 300 MB 上限由平台拦，界面要把失败原因显示出来；
- **Excel 等结构化文件要“展示在表单里”**：文件本体走上传（给 Agent 读），**预览与填入由前端解析**（在浏览器里读表头/前几行渲染成表格或填入字段）——两条路并行，不互相替代；解析失败不阻断上传；
- **需要用户调整顺序**（选题排序、素材排序）：入口表单页是 App 自绘的（`inputSchema` 原样保留，通用渲染只消费常用子集，复杂字段手写定制页），数组字段完全可以做成拖拽排序，**提交时按数组顺序**——前提是编排型 TPE 的 `input_schema` 把它声明为数组且顺序有业务含义（这是场景包侧 S1/S2 的设计，A1 反读时确认，缺就回场景包线补）；
- **展示**：图片经 `project.file.getViewUrl` **现取现用**（URL 短时效，禁止存进 storage / formdata）；非图片按可读文件名展示；下载只经 `project.file.download` 且只能由用户显式点击触发；`[[file:/workspace/...]]` 标记经安全渲染；
- **交付物**：`artifacts[].workspace_path` 只传文件 RPC，`output_paths` 只作归属标签，禁止渲染路径文本。

#### 8.12.5 从设计到原型

设计动作按顺序做，先读钉版指南再动手（`references/前端设计指南/`，四份官方 guidance 的离线副本；新页面 / 重设计全读四份，小改只读产品认知一份 + 受影响那份）：

1. **理解产品**（`codex-ui-ux`）：用户是谁、要完成什么、认哪些业务词；入口、首个决策、主行动、成功态、恢复路径；加载 / 空 / 错误 / 权限 / 破坏性 / 长内容 / 移动各状态。***不从装饰或组件画廊起手***。
2. **竞品调研**：先问开发者有无参考（品牌规范、喜欢的产品）；没有再调研 3 个以上同类产品——模块划分、主行动怎么突出、状态怎么表达、空态/等待/失败怎么处理、视觉层级靠什么建立；截图报告留存进工单，只取参考点不照搬。
3. **定一个有辨识度的方向**（`frontend-design`）：贴合业务的设计主张、配色、字体系统、布局逻辑、密度和一个记忆点；对着真实任务校验后再编码。避开 AI 通用默认；用真实界面文案；主行动与信息层级一眼可辨。**脚手架 demo 的页面结构、排版、视觉是第一规则禁止复用的**（这是脚手架的硬约束，不是建议）。
4. **设计完整交互**：从入口到完成的最短连贯旅程；先定义全部重要状态再打磨快乐路径；移动端主行动可达。
5. **原型、计划书与一次确认**：见 §6——原型跑起来后截图进《业务应用计划书》，连同后端功能阐述一起交开发者确认。

### 8.13 《业务应用计划书》与一次确认


A1 的交付物是**一份 MD**：《业务应用计划书》。它对应场景包线的《制作书》——开发者确认它，之后 A2 / A3 / A4 就照它干；写给不懂前端的人，读完能提得出意见。

#### 8.13.1 十章结构

| 章 | 内容 | 来自 |
|---|---|---|
| ① 应用定位 | 给谁用、持续经营什么事、SaaS 链路一句话（展示 → 生产 → 回流 → 编辑）、用户一天 / 一周在这里做几次什么 | §1 访谈 |
| ② 参考资料与打法 | 开发者给的参考（截图 / 产品 / 品牌规范）+ 自行调研的参考点；只取参考点，不照搬 | §1、§5.5 第 2 步 |
| ③ 契约基线 | §3 六项反读结果：几条路线、几张入口表单、中途表单、审阅形态、`output_schema` 字段、业务事件粒度、数据集读写列 | §3 |
| ④ 项目模型 | 创建 / 复用两形态各在哪一页、下拉框列什么、发起后去哪、项目页看什么 | §2.1 |
| ⑤ 功能清单 | §2.2 菜单逐项：做 / 不做 + 理由；做的落在哪一页 | §2.2 |
| ⑥ 数据面 | 模板草案（表 / 列 / 类型 / 逐列声明 / 审计 / 文件路径列）、实体 / 情境 / 历史事件归属、可编辑性矩阵、冲突规则、回流入库语义 | §4 |
| ⑦ 页面与截图展示 | 每个页面一节：用户在这做什么、**原型截图**（含空态 / 只读 / 出错至少各一张）、读哪张表哪些列、主行动往哪发、可编辑性怎么可见、文件在哪出现 | §5、6.2 |
| ⑧ 后端功能阐述 | 每个接口一行 + 生产回流链路一段 | 6.3 |
| ⑨ 验收与自动化测试计划 | G7 第 8.1 节 三类的用例来源：⑤ 每个勾选功能 → 用例编号；每条路线的业务路线运作用例；每张表的增删改查与写权 / 幂等 / 冲突用例 | ⑤⑥⑦⑧ |
| ⑩ 制作纪律与开放项 | 确认后不再向开发者提问，A2 / A3 / A4 照本书干；执行中发现与本书冲突，**停下来找开发者**，不自行改口径；脚手架没有的能力列为开放项 | — |

原 5.5 第 5 步“产品设计文档”的全部内容都在这十章里：模块决策账本在 ⑤，看板指标清单在 ⑦ 看板页一节，可编辑性矩阵在 ⑥，文件出现位置在 ⑦，文案与术语检查（契约字段 `description` 不上界面；能靠交互说清的不写解释文字）与一句话风格主张放 ①。

#### 8.13.2 截图展示怎么做

1. 先做**本地可交互原型**：生产级（真实组件、间距、字号、交互态，不是灰块线框）、所有路由可开（含空态、失败态、只读态）、每页有贴合业务的演示数据（仅 `import.meta.env.DEV` 判据注入）、主动线可点通；只跑本地**绝不部署**。交给开发者前先按《前端设计指南》第 6 步过一轮渲染页修正；
2. 用 Playwright 对每个页面、每个关键状态截图（Dev Host Mock 模式下写一条 e2e 逐页 `page.screenshot`，或 `npx playwright screenshot <url>`），存进仓库 `docs/plan/screens/`，MD 里用相对路径引用；
3. 每张图配三句：用户在这干什么、数据从哪来、主行动是什么。**图不是装饰：没有截图的页面视为未设计**；
4. 开发者看图提意见 → 改原型 → 重截 → 更新 MD。

#### 8.13.3 后端功能阐述怎么写

每个接口一行，不写实现细节，写“它为哪一页的哪个动作服务”：

| 接口 | 服务哪一页 / 哪个动作 | 读 / 写哪张表哪些列 | 幂等键 | 限制 | 对应 ⑨ 用例 |
|---|---|---|---|---|---|
| `POST /api/stores` | 数据管理页 · 新建门店 | 写 `stores`（`editable:user` 列）+ 审计四件套 | `X-Goalfy-Business-Request-Id` | ≤256 KiB | C-01 |

再写一段**生产回流链路**（编排型 TPE 经业务应用数据集 FA 写哪些 `agent` 列，还是应用后端收产出后入库；直接入库还是草稿待确认）；发起时由后端拼进 `submit_data` 的字段（若有）在对应接口行里说明来源表。约束 5 / 6 的信封、码段、桥层限制不用抄，写“遵守 `backend/README.md`”一句即可。

#### 8.13.4 一次确认

- MD + 原型本地地址一起交开发者：MD 确认信息架构、功能取舍与后端范围，原型确认视觉与手感，两者互为对照；
- 开发者提意见 → 改 MD / 原型 → 再确认，直到开发者说“可以”；
- 确认版落工单 checkpoint `app_plan`（MD 正文 + 截图目录指针）；
- ***确认后才进入 A2 / A3；未确认不得编码。*** 确认后要改口径（加功能、改字段、改页面范围）= 计划书修订，回本节重走确认，不在 A3 里悄悄改。
