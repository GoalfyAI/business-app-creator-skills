# ④ 试用验收（工作区阶段 G6）

你按验收条目逐条测：页面条目由你在应用的本机版上用无头浏览器照条目操作，同时跑前端检查和本地布局回归；业务结果在开发者同意部署后，用开发工作集真跑并查库；只有线上才能验证的条目标「未测」。没过的改好再测，每条都有结论后交一份验收报告。开发者不逐条试、不打勾：他看报告，「好不好你说了算」的几条看你附上的实际结果，最后说「可以上线」。验证只有两层：冒泡管改，真跑、本机版页面验收加验收报告管收。

在线预览和 `workspace` 真跑读写的是同一份开发工作集，测试写入的数据留在那里，不进使用者实例。验收不用发布的版本，也不请开发者发布。

## 1. 进入条件

- ③ 交棒：应用根 `npm run verify` 全绿，每个功能都做好了或标明没做成；读写应用库的路线在阶段文档 G4 有反读自查表且四项都是「有」，没有就回 ③ 补，不部署。
- 本轮需求已全部实现：在桌面开发者中心里执行 `prepare_business_app_skill` 返回的完成版命令，开发者就能在「演示预览」看本地完成版（见 [../reference/开发者中心与工作区.md](../reference/开发者中心与工作区.md)「演示预览为空」）。Studio 宿主不生成完成版，演示走桌面入口（同一文件「Studio 宿主」）。

## 2. 段里怎么做

### 2.1 先问部署，再部署

本机版能做的检查（2.3 的页面条目、前端检查、本地布局回归）不用部署，先做。部署到开发者在线预览不能从 PRD 的同意推定，「先试用再决定上线」也不算：之前开发者没有明确同意过这个部署动作和范围时，在原对话问一次，照抄「是否将当前应用部署到开发者在线预览，用于试用验收？这不包含目录正式发布。」文字或语音的明确同意都算，原话记 checkpoint，不加必点按钮或表单；之前已明确同意过的直接沿用，不重复问。部署只 `ship` 到开发者预览，不自动上线、不发布。开发者暂不同意时不部署，本机版的检查照做，依赖已部署版本的条目（`workspace` 真跑、开发工作集里查到的行）结论写「未测」，原因写「你暂不同意部署到在线预览」，不能记成通过；他之后同意时部署并补测这几条。⑤ 只上线已部署成功的草稿，没部署过就上不了线：开发者说「可以上线」时按 [5-上线.md](5-上线.md) 第 2 节第 1 步再问一次。所有宿主都这样做。

场景包不必先上线：挂着你本人的场景包草稿也能部署。

1. 先调 `business_ui_bundle(action="download_template")` 核脚手架门槛，需要升级时完成迁移与验证。
2. 在应用根目录运行 `npm run verify:release`，全部检查通过后生成 `.pack/business-ui-bundle.tar.gz`，按这个包算 `source_sha256` 与 `size_bytes`。**禁止**用 `npm run pack`、直接运行打包脚本或手写 tar 代替 `verify:release`，那样会跳过部署前的检查。
3. `business_ui_bundle(action="ship", task_id, business_ui_id, source_sha256, file_name="business-ui-bundle.tar.gz", size_bytes)`（`file_name` 只写文件名，带目录会被拒；`business_ui_id` 是上线行、要自动派生草稿时同时带 `change_note`，写这次改了什么）：
   - 返回 `status=upload_required`：按 `upload_url` 与 `headers` PUT 源码包原字节，原参数加 `bundle_key` 再调；
   - 返回未终态：原参数加 `deployment_id` 再调，服务端每次最多等约 45 秒；**禁止**去掉 `deployment_id` 重调，那会重新起容器；
   - 到 `success` 为止。`steps` 标明每步 done / skipped / resumed。明确失败且原因不在源码包时，再用 `prepare_upload` / `complete_upload` / `deploy` / `status` 单步排查。
4. `business_ui_manage(action="get")` 核对部署已写进当前草稿；记下 `deployment_id`、`source_sha256`、`deployed_scaffold_version`。`entry_url` 是开发者容器地址，只用来核对绑定，不打开、不发给任何人。`deploy` 返回带 `scaffold_upgrade_notice` 时原样记进开发记录，上线结果要写。

### 2.2 用真实数据跑

有模型步骤，或路线要读写应用库、调外部接口时做；只有脚本步骤且 ③ 的 `full_run` 已覆盖时可省，省了写明原因。例子由你挑，挑法同 ③ 2.1 第 9 步，验收条目里点名的样例都要跑到。PRD 已列的费用直接执行；没列的、会对外发送或写正式数据的先说明再执行。

1. `manage_goalfymax_project(action="run", task_id, idempotency_key, scenario_package_ids=[<场景包当前草稿或上线版本的物理行 ID>], submit_data={…}, business_ui_id=<应用家族 ID，路线读写应用库时传>, business_ui_data_space="workspace")`。返回 `BUSINESS_UI_NOT_ONLINE` 或要求先上线时，补 `business_ui_data_space="workspace"` 重跑，不要为真跑去 finalize。`workspace` 跑你刚部署的版本，读写开发工作集，和在线预览是同一份库，应用不用先上线；路线不碰应用库就不传 `business_ui_id`。
   `submit_data` 里必须有 `business_id`（你生成，例如 `biz-<场景包简称>-<日期>-<序号>`，同一业务实例里不变，后面 `reply` 沿用）和 `orchestration_id`（场景包编排里要启动的那条路线的 id），其余是入口表单字段。
2. `manage_goalfymax_project(action="wait", project_id)` 等到终态（`wait` 不接受 `wait_seconds`），中途表单或审阅用 `reply`，回业务表单时 `content` 传空字符串、答案放在表单数据里；以 `route_runs` 里各路线的状态为准（路线完成后项目可能仍显示 running），`succeeded` 表示这条路线真跑通过，结单门会把它记为这条路线的证据。
3. 对路线里每条 TPE 调 `otpe_manage(action="verify", task_id, tpe_id, project_id)`，`passed` 即完成；③ 只差运行证据的 TPE 必须在这里补齐，读写应用库的路线不能用冒泡或结单门豁免代替这一步。
4. `get_project_execution_logs(action="workflow_trace", project_id)` 看每步，模型步骤的输出你逐条读一遍；写库的结果去应用库里查到那一行。
5. 记下每个按钮这次实际花了多少（`cost_credits`），和 PRD 的估算比。
6. **回写演示示例**：③ 在阶段文档 G5 记了「待 ④ 回写」的演示和示例，从这次真跑通过的结果里选一份写回代码，去掉「示例」占位，按 2.1 重新 `verify:release` 并部署，修改记录写明。回写不算退回 ③，在 2.3 逐条测之前做完。

失败在同一草稿改再跑；每次只改一处，不同时改脚本和路线。

### 2.3 按验收条目逐条测

逐条对照 ② 定稿的验收条目，照「照着做」做一遍，按「这样算对」判通过或没通过，每条记「怎么测的」和证据：

| 条目要看的 | 怎么测 | 证据 |
|---|---|---|
| 业务结果：报告、内容、识别出来的东西、写进库的记录、发出的消息 | 2.2 的真跑；条目点名的样例没跑到的，照条目再真跑一次 | `project_id`、`workflow_trace` 摘录、库里查到的行 |
| 页面上的操作和显示：点哪、跳到哪、空态、提示文字、必填校验、打回和重新生成、切语言、只读置灰、消息中心跳转、离开再回来 | 在本机版上用无头浏览器照条目操作，做法按 [../reference/开发者中心与工作区.md](../reference/开发者中心与工作区.md)「④ 本机版页面验收」；同时跑 `npm --prefix frontend run check` 与本地布局回归 | 操作步骤、截图、打开过的本机路由；前端检查与布局回归的结果 |
| 只有线上才能验证的：依赖平台登录身份、真实宿主桥接（同一节「只有线上才能验证的」） | 本机版能看的部分照常测；依赖线上的部分不测，记「未测」，原因写「只有线上才能验证：<依赖哪一项>」 | 能看的部分同上；其余无 |
| 到点或有新记录时自动开始的 | `business_ui_automation(bubble)` 按自动化的入口跑一次，看结果（见 [../reference/自动化.md](../reference/自动化.md)「验证」） | 冒泡的 `run_id` 与结果；冒泡只验处理逻辑，「到点真触发」另列一条记「未测」，原因写「到点触发要等真实时间，且要发布后在正式入口开规则」 |
| 使用者从目录或分享打开 | 不测，记「未测」，原因写「从目录或分享打开要先发布」 | 无 |

- **看实际产出，不只看状态**：页面或日志显示「已完成」「成功」不算通过，要看到真的产出（报告内容、库里的行、发出的消息）。
- **每条「通过」都要附你取得的证据**：业务条目附这次 `workspace` 真跑的 `project_id`、`workflow_trace` 里对应步骤的摘要、库里查到的那一行；页面条目附本机版上的操作步骤、截图和打开过的本机路由。只请求过页面地址（`curl`、HEAD 返回 200）不算操作过；开发者的口头回报不算证据。冒泡（含 `full_run`）只证明路线能跑，不证明应用库的真实读写，不能拿来给读写应用库的条目标「通过」。部署成功、请开发者打开「演示预览」或「在线预览」都不算验收。
- **Studio 宿主同样在本机版和开发工作集里验收**：开发者看过的 Studio 本地演示、已发布的版本都不作验收证据。宿主提供的受限检查能力可以作为补充，它的机器结果和你在本机版上的操作分开记录，不能代替页面条目的本机版操作（[../reference/开发者中心与工作区.md](../reference/开发者中心与工作区.md)「Studio 宿主」）。
- **测不了的先修再标「未测」**：本机版起不来时按「④ 本机版页面验收」的「本机版起不来时」先自己修；修不好的、只有线上才能验证的、开发者暂不同意部署而依赖已部署版本的，结论写「未测」、证据写「无」、写明原因。**禁止**请开发者在在线预览、演示预览或其他页面代测。要另一种人的账号才能看到的，按「只有线上才能验证：平台登录身份」标「未测」。
- 按 ③ 的业务含义对应核首页、历史、详情、消息、发起、补充、提交查看、审阅及返回：名称对应同一实际事项，上传不冒充已发起，提交或受理不冒充完成，未定义产物不出现报告；加载、空态、只读、暂停、失效也核对。
- ② 里标「要人判断」的条目（内容能不能直接对外、语气像不像、业务判断对不对、前后两批有没有变好），你照样做一遍，但不下结论：把实际结果原文附进报告，标「好不好你说了算」。
- **没通过的**：改好、按 2.1 重新部署，再测这一条和受它影响的条目；改不好、要换做法的回 ③，和预期差得多的按 ③ 2.4 出选择题。报告要等所有条目都有结论再交，交之前进度照常按「正在做」报。
- 按 [../checklists/验收清单.md](../checklists/验收清单.md) 逐条写「通过 / 不适用 + 一句依据」。

### 2.4 交验收报告

发交接消息，开头「【④ 试用验收 → 等你确认】」，附验收报告：

| 项 | 写什么 |
|---|---|
| 结论 | 一共几条：通过几条、未测几条；有开发者选了接受的没通过条目，单独写几条 |
| 好不好你说了算 | 每条附实际结果：报告全文或链接、内容原文、前后对比；开发者觉得不行直接说是哪一条 |
| 未测的 | 每条写原因：只有线上才能验证的写依赖哪一项（平台登录身份、真实宿主桥接）；本机版起不来的写做过哪些处理和错误原文；开发者暂不同意部署的写「你暂不同意部署到在线预览」；到点真触发写「到点触发要等真实时间，且要发布后在正式入口开规则」，从目录或分享打开写「从目录或分享打开要先发布」，并写清上线后开发者自己怎么看。说明这些行为没有验证 |
| 全部条目 | 默认折叠，固定六列，每格都要填：#、验收条目、结论（通过 / 没通过 / 好不好你说了算 / 未测）、`project_id`（页面条目写「本机版」）、`workflow_trace` 摘要或页面操作步骤、查到的行或截图与本机路由（不写库的写拿到的产出；未测写「无」） |
| 用真实数据跑出的结果 | 本段真跑的结果摘要，加上 ③ 里 `full_run` 跑出的内容，和 ② 的预期对照 |
| 自动发生的 | 2.3 冒泡的结果；`run_once` 要求应用已上线、跑的是正式实例，不在 ④ 用 |
| 实际花费 | 每个按钮实际花了多少，和估算比；每份要等多久、能不能同时开几个 |

「全部条目」照这个表头抄，一条验收条目一行：

```text
| # | 验收条目 | 结论 | project_id | workflow_trace 摘要 / 页面操作步骤 | 查到的行 / 截图与地址 / 拿到的产出 |
|---|---|---|---|---|---|
```

读写应用库的条目只有冒泡证据（冒泡里读库报 `not_a_business_app_project`、写库被 `ctx.dry_run` 跳过），没有 `workspace` 真跑查到的行时，自查记录里写「未验证：只冒泡过，没在开发工作集里真跑」，不写「通过」，先回 2.2 真跑补上，补完再交报告；开发者暂不同意部署的，按 2.1 记「未测」。

**报告的硬门**：出现下面任一种，G6 标 `failed`，报告不交，**禁止**请开发者回「可以上线」，先回 2.2、2.3 补：结论是「通过」的行，后三列缺任一格；有「未验证」的行；「未测」的行没写原因；本机版能测的页面条目没测就标了「未测」，或本机版起不来没先修就标了「未测」；到点真触发、从目录或分享打开以外的条目以「要先发布」为由标了「未测」；报告、交接消息里请开发者去「在线预览」「演示预览」或正式入口里看、点、试条目或查数据。

「要你做的」只有这几项，照抄：① 看验收报告；② 看「好不好你说了算」的几条，实际结果已经附在报告里；③ 都没问题回「可以上线」，有问题回「还要改：第几条」。有「未测」条目时加一句：「这几条没有测，原因见报告；你仍然可以回『可以上线』，上线结果会单列它们，只有线上才能看的写了你上线后怎么自己看」；因为开发者暂不同意部署而未测的，再加「你同意部署时我再部署补测；还没部署到在线预览的应用上不了线，你回『可以上线』时我会再问一次是否部署」。报告里有「没通过」的条目时，先按 2.5 最后一条做成选择题放进「要你做的」，开发者选完再请他回「可以上线」。需求方和开发者不是同一人时，请开发者把「好不好你说了算」的几条转给需求方看。

开发者自己在工作台「在线预览」里用的时候发现问题告诉你，按 2.5 处理；他的回报只用来定位问题，不作「通过」的证据。

### 2.5 按反馈改，只重测受影响的

- 开发者说哪条不对、或「好不好你说了算」的结果不满意：改完重新 `verify:release` 并部署，重测这一条和受影响的条目（页面条目在本机版上重测），报告里只更新变了的条目，修改记录写「问题 / 改了什么 / 重测了哪几条」。
- 改了场景包草稿的重新部署即可，不用上线。应用已上线过、挂载钉在旧版本号时，先 `business_ui_manage(action="update", business_ui_id, scenario_pack_id, scenario_pack_version=<场景包草稿版本号>)` 换挂到草稿再部署，否则预览仍跑旧的上线版本。
- 结果不对、要改做法的回 ③；开发者发现要的东西本身不对，回 ①。
- 开发者要在还有条目没通过时直接上线：把没通过的条目逐条做成「接受，先上线 / 等改好再上线」选择题，写清上线后使用者会遇到什么；选了「接受」的条目结论记「没通过，开发者选了接受」，上线结果「还没验证的和风险」里写明。「未测」的条目不用出这道题，开发者说「可以上线」就进 ⑤。

## 3. 开发者要看、要做的

- 之前没有明确同意过部署的，答是否将应用部署到开发者在线预览用于试用验收。
- 看验收报告；「好不好你说了算」的几条看实际结果。
- 说「可以上线」，或说哪一条还要改。

## 4. 不给开发者的

部署过程、`verify` 与在线检查结果、版本号、容器地址、本机版地址、原始日志和 JSON。没有结论的条目不交报告。

## 5. 产出与落盘

- 工单 checkpoint：场景包草稿或上线版本、`deployment_id`、`source_sha256`、`deployed_scaffold_version`、真跑的 `project_id` 与结论、每条 TPE 的 `verify(tpe_id, project_id)` 结论、开发者对是否部署到在线预览的原话、开发者（和需求方）说「可以上线」的原话、未测的条目及原因、开发者选了接受的条目。
- 阶段文档 G6：验收报告全文（每条怎么测的、证据、结论）、页面条目的操作步骤、截图路径与本机路由、前端检查与布局回归结果、修改记录、验收清单逐条结论、实际花费。
- 方案页：交报告时 `status` 为 `waiting`，`.pv-you` 写「看验收报告，没问题回『可以上线』」；入口、权限、部署问题推进不了时为 `blocked` 并写 `.pv-owner`；通过的条目移入「已验证」，证据写部署编号与真跑的 `project_id` 或「本机版」；未测的留在「未验证」并写原因。
- Studio 宿主：不写方案页，验收报告**必须**照 [../design/开发文档/验收报告.md](../design/开发文档/验收报告.md) 的模板写成一份开发文档，过了 2.4 的硬门才用 `studio_write_proposal(documentType="acceptance")` 保存；按反馈重测后出新一版。
- 阶段标记：G6 `passed`。

## 6. 交棒条件

下面都满足后，先用命令把 [5-上线.md](5-上线.md) 从头读到尾，再做 ⑤ 的第一件事。

- 开发者同意部署的，最近一次部署 `status=success`；暂不同意的，依赖已部署版本的条目都记了「未测」；
- 每条验收条目都有结论：通过（带 2.3 规定的证据）/ 未测（写了原因）/ 没通过且开发者选了接受；已部署时，读写应用库的条目至少有一次 `workspace` 真跑的 `project_id`；
- 验收报告已经发给开发者，过了 2.4「报告的硬门」，开发者说「可以上线」是在看过报告之后；有「未测」条目时开发者说「可以上线」照样算；
- 验收清单逐条有结论；已部署时，读写应用库的路线每条 TPE 最近一次 `verify(tpe_id, project_id)` 为 `passed`；
- 开发者（和需求方）看过报告，明确说了「可以上线」或等价表述，原话已记 checkpoint；
- 出口阶段记录：在「可以上线」checkpoint 之后用 `business_ui_stage` 写 G6，全部条目通过为 `passed`，有「未测」条目为 `partial` 并逐条写明未测条目与原因（写法见 [../reference/开发者中心与工作区.md](../reference/开发者中心与工作区.md)「三件套与阶段标记」）。

## 7. 出问题怎么办

| 现象 | 先看 | 回到 |
|---|---|---|
| 部署 `status` 失败 | 返回里的构建日志尾部；本地先 `npm run verify:release` | ③ |
| 部署被脚手架闸门拒绝 | [../reference/脚手架与预置件.md](../reference/脚手架与预置件.md) 错误码表 | 升级后重来 |
| 本机版或无头浏览器起不来 | [../reference/开发者中心与工作区.md](../reference/开发者中心与工作区.md)「本机版起不来时」 | 本段 2.3 |
| 开发者说在线预览只显示「Agentic APP 不存在或加载失败」 | 同一文件「演示预览与在线预览」：先核对当前草稿部署成功，没有就重新 `ship` | 本段 2.1 |
| 开发者说工作台「在线预览」提示未就绪 | `PREVIEW_NOT_READY`：当前草稿没有部署成功的记录，在当前草稿行重新 `ship` 到 `success`；`ship` 已成功仍未就绪才报平台问题 | 本段 2.1 |
| 上线前 `resolve` 报「还没有上线版本」 | `resolve` 只认上线版本，上线前本来就这样；不记 platform_blocked，也不为拿入口去 finalize | 本段 2.3 |
| 真跑卡 `waiting-input` | 用 `reply` 回表单；没人答就是正常挂起 | 本段 |
| 真跑返回 `BUSINESS_UI_NOT_ONLINE` | 传了 `business_ui_id` 没传 `business_ui_data_space="workspace"`；补上再跑，不需要 finalize，不记 platform_blocked | 本段 2.2 |
| 真跑返回 `BUSINESS_UI_NOT_DEPLOYED` | 还没有你本人部署成功的版本，或 `business_ui_id` 传成了版本行 ID；先 `ship` 到 `success`，用家族 ID 重跑 | 本段 2.1 |
| 协作者预览提示需用新版脚手架重建，或充值相关操作被拒 | [../reference/多人协作.md](../reference/多人协作.md)「预览、费用与限制」，这是预期限制，不报平台问题 | 本段 2.3 |
| 真跑内容不对 | 模型步骤提示词、模型档位或输出字段 | ③ |
| 页面行为不对 | 页面块或生成页 | ③ |
| 开发者说要的东西本身不对 | — | ①：改 PRD，只重做受影响的部分 |
| 疑似平台问题 | 走不下去才立即 `submit_dev_feedback(blocking="blocked")`；能绕过就继续，记进开发记录，⑤ 交付时汇总；保留回执 `code` 与 `source_code`，编号使用及未知结果按 [../reference/报错对照.md](../reference/报错对照.md)；提交后没人修按 `SKILL.md` 第 7 节的升级顺序做 | — |
