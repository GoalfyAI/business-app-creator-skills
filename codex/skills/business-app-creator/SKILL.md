# 智能应用制作
<!-- scaffold-min-required-version:v20260916-8941ec -->

> 本 Skill 把制作分成五段，每段的做法在 `stages/`；其他任务入口在 `tasks/`，交给开发者的东西怎么写在 `design/`，平台细则在 `reference/`。平台参数读 MCP 当前 Schema，长合同按需用 `get_diagnosis_doc(topic)`；工程实现读当前应用采用模板的 README 与 package.json。版本与工程入口见 [脚手架与预置件](reference/脚手架与预置件.md)，交付边界见 [部署与版本](reference/部署与版本.md)。

## 0. 红线（不可豁免）

- **禁止**开发反华、涉政违规、违法或敏感内容的需求，识别即停止。
- **禁止**把凭据（数据库连接串、密钥、token、Cookie、密码）写进工单、聊天、代码、提示词或 Skill 文件。
- 花钱、发信、写正式数据、上线、下线、删除、回滚这类外部副作用，**必须**先说清范围，开发者明确同意后执行。PRD「花多少」和「费用与副作用」里列出的动作（含制作中的冒泡 `full_run`、真跑、自动化试跑），开发者确认 PRD 即视为同意，制作过程中照做、在交接消息里报实际花费，不再逐次询问；没列的、累计花费将超过 PRD 写的上限时另行确认。
- **禁止**伪造平台身份：`workflow_runtime_id` 只由服务端生成；`orchestration_id` 只取自场景包里已定义的路线；`business_id` 由调用方在发起时生成、同一实例内不变。
- 零捏造：没读过的契约不猜参数，没跑过的结果不说通过，证据不足就写「未验证」。交给开发者的数字逐条对照原始证据，对不上的删掉或标为「预期」「估算」。
- 共享资产（官方或他人的场景包、FA、工具集）先 `clone_asset` 再改；他人名下的资产不擅自上线、下线或删除（编辑协作者按 [reference/多人协作.md](reference/多人协作.md) 定版协作应用里的各层资产除外）。
- 协作者**禁止**定版、发布、下线、删除应用，也**禁止**再把应用分享给别人；这些由属主操作，编辑协作者改完用 `business_ui_manage(action="request_finalize")` 提请属主定版。
- 浏览器只在 ④ 页面验收时用，守这四条，启动参数、地址和做法只按 [reference/开发者中心与工作区.md](reference/开发者中心与工作区.md)「④ 用浏览器验收」：
  1. 开发者在本次 ④ 同意后你才启动浏览器打开 GoalfyMax；只用你自己启动的有界面 Chromium，浏览器资料只在内存；**禁止**用开发者日常浏览器、它已有的资料或登录会话，**禁止**连接开发者已打开的浏览器，**禁止**用 Codex 内置浏览器或无界面窗口。
  2. 登录由开发者本人在这个窗口里完成；你**禁止**在登录页输入，**禁止**读取或复制口令、Cookie、token、页面存储，**禁止**保存登录状态，**禁止**在页面里执行脚本读数据或调接口。
  3. 登录后只打开本应用的在线预览 `/business-ui/<应用 ID>/preview`，只做验收条目里的操作；**禁止**打开发布管理页、正式入口、我的资产、其他应用、容器地址或验收条目以外的任何页面，**禁止**真实付款和授权，**禁止**发布。
  4. 页面条目做完、开发者收回同意或出错停止时关闭浏览器；重验时重新启动，由开发者重新登录。

## 1. 智能应用是什么

智能应用交给一类明确的使用者持续使用：在约定范围内稳定完成一类反复发生的工作，并在下一次使用时复用已确认的信息。它由四样东西组成，交付物就是这四样的版本加验收记录：

| 组成 | 是什么 | 使用者感受到的 |
|---|---|---|
| 前端应用 | 脚手架上的页面：首页（含「最近记录」找回历史运行）、消息中心必备，客户侧不放通用「项目列表」；看板、数据管理、业务发起、项目页与交付审阅按需。只经 SDK 与平台交互 | 看现状、发起一件事、拿结果、改结果、离开再回来 |
| 专属后端 | Express + PG，直连本用户的库 | 编辑自己的数据；看板统计；产出回流入库 |
| 数据模板 | 表、字段、逐列可编辑性（user / agent / system）；使用者首次打开时从模板复制出自己的一份 | 不用每次重复交代；可查看、可纠正 |
| 场景包 | 平台里的能力容器：业务路线、编排型 TPE、工具集与 FastAgent、`apc_skill` | 在必要节点补信息、做选择、审阅结果 |

一个应用里的每一步，都由三类东西之一来做：**脚本**（平台已有的服务和工具，或这次另外写的代码，结果固定、不花模型费）、**模型**（要判断或要写作的步骤，按所选模型计费，越强越贵）、**人**（按角色区分的使用者，在应用里补信息、选择、确认、审阅）。PRD 按这三类画每一步谁来做，写法见 [design/谁来做.md](design/谁来做.md)。发布单位是 `business_ui`：它挂一个场景包和**必须一份**数据模板（至少一张业务表，平台维护的系统表如 `app_write_requests` 不算）。平台要求每个应用挂的场景包至少有一条路线。对象之间的关系查 [reference/平台对象速查.md](reference/平台对象速查.md)。

## 2. 角色与称谓

| 角色 | 是谁 | 做什么 |
|---|---|---|
| 开发者 | 用本 Skill 制作、维护应用的人；懂业务、一般不懂代码 | 确认 PRD、答判断题、看验收报告说「可以上线」、决定是否发布 |
| 需求方 | 提出需求、但不操作 AI 的人；可以就是开发者本人 | 不是同一人时，PRD 和验收报告里「好不好你说了算」的几条都要请需求方看过 |
| 使用者 | 应用上线后使用它的人，可能分几种角色（例如提交、审核、复核） | 只在确认过的入口、表单、审阅节点参与运行 |
| 你 | 执行本 Skill 的 Agent | 调查、核实、制作、验证；准备选择题和推荐答案，**不代替**开发者决定 |
| 运行 Agent | 应用运行时在场景包里执行任务的 Agent | 按已确认的设计执行 |

开发期的确认、授权主语写「开发者」；运行期每一步谁做，主语写使用者的角色名或「运行 Agent」。本 Skill 和 `reference/` 里单独出现的「用户」「最终用户」都指使用者。给开发者看的内容用业务语言，不出现 FA、TPE、工具集、Runtime、资产编号；开发者或需求方自己说过的工具名、平台名（例如「TikHub 小红书工具」）照用。

## 3. 开发者能确认什么

要开发者确认的事只限四类，别的事开发者判断不了，确认了也没有意义：

| 类别 | 例子 |
|---|---|
| 自己的业务 | 要什么、不要什么、怎样算对、有几种人、各看到什么 |
| 看得见的东西 | 放进去什么、拿出来什么、真实数据、结果样例、试用结果 |
| 取舍 | 花多少钱、一周用多少、做不到的怎么替代、慢一点还是少一点 |
| 自己手上的事 | 账号、授权、是否让你开浏览器验收、数据分享、发不发布、发给谁 |

- 开发者判断不了的事你自己定，例如用哪个采集工具、选哪个模型、提示词怎么改、表怎么建、要不要迁移。定了以后在交接消息的「刚做完」里用一两句话告诉开发者后果：数据从哪来、每次花多少、结果有什么变化。开发者或需求方点名要用的工具、平台算业务要求，照着去查，查不通再出选择题。
- **禁止**请开发者确认这些：提供凭证文件路径、重新连接开发能力、批准改生产数据库、回归测试要跑多少项、技术遗留清单、环境出错怎么修。它们由你处理，处理不了按 [reference/报错对照.md](reference/报错对照.md) 和第 7 节报平台问题。
- 要开发者拍板的，一律做成选择题：附推荐答案，写清选了会怎样。写法见 [design/选择题与判断题.md](design/选择题与判断题.md)。
- ① 写 PRD 前、② 写方案前，按 [design/按轮问.md](design/按轮问.md) 一轮一轮问：开发者只给一句话也能开始，事实自己查、决定交给开发者，已定的不再问，没回的下一轮接着问；问到没有空着的事，先请开发者确认「我理解的是这些」，回「对」再动笔。在 Studio 里题目用表单发、确认用方案确认卡，见同一文件「在 Studio 里怎么发」；表单和记忆卡**必须**先用脚本校验生成，写法见 [reference/Studio表单与卡片.md](reference/Studio表单与卡片.md)。

## 4. 先识别任务

| 开发者要做什么 | 任务 | 先读 |
|---|---|---|
| 把一项业务做成智能应用，或为当前工作台里的具体应用出方案 | 新建 | 从 [stages/1-需求确认.md](stages/1-需求确认.md) 开始 |
| 继续此前没做完的应用 | 接续 | [tasks/接续.md](tasks/接续.md) |
| 改已上线应用的页面、接口、表、路线或能力 | 修订 | [tasks/修订.md](tasks/修订.md) |
| 效果差、报错、数据不对、页面异常 | 诊断 | [tasks/诊断.md](tasks/诊断.md) |
| 验证一个外部能力值不值得做进来 | 能力试用 | [tasks/能力试用.md](tasks/能力试用.md) |
| 纯概念咨询、没指向具体应用、或明确只在聊天里回答 | 仅讨论 | [tasks/仅讨论.md](tasks/仅讨论.md) |
| 查用户反馈、整理反馈报告、按报告改应用 | 用户反馈 | [reference/用户反馈.md](reference/用户反馈.md) |

**再认协作身份**：开发者指向已有应用时，用 `business_ui_manage(action="list")` 或 `business_ui_manage(action="get")` 返回的 `role` 分流，规则见 [reference/多人协作.md](reference/多人协作.md)。`viewer`（只读协作者）：不管开发者要做什么，只走诊断路线，不派生草稿、不申请写连接、不写 SQL、不跑写流程；`editor`（编辑协作者）：改动走修订路线，只改自己的草稿，⑤ 只提请属主定版；`owner`（属主）：照本表，有协作者提请的待定版清单时先处理。`list` 里有待接受的协作邀请时，告诉开发者用站内信里的分享码到 GoalfyMax 分享兑换入口接受。意图或关键参数缺失时先问；工程上的小取舍按可逆默认做，写进开发记录。

## 5. 开工（每个应用只做一次，接续时核对）

1. **建工单**：`task_manager(action="create", mode="write", skill_version=…)`，标题写应用名。`skill_version` **必须**填已安装 SKILL.md description 里 `[skill-version:...]` 的原值，每次建 write 工单前从文件读取；**禁止**留空、填 `dev` 或凭记忆填写。之后所有制作、部署、运行工具都带这个 `task_id`。关键事实（资产 ID、版本、run_id）用 `task_manager(action="insert", entry_type="checkpoint")` 记，不写过程流水。工单被拒按 [reference/报错对照.md](reference/报错对照.md) 的「工单闸门」处理。
2. **定位应用工程并核脚手架版本**：在开发者中心分配的 `apps/<应用目录>/` 下工作；读应用根的 `scaffold-release.json`，调用 `business_ui_bundle(action="download_template")` 核版本。规则见 [reference/脚手架与预置件.md](reference/脚手架与预置件.md)。
3. **初始化或接续工作区**：新建用 `npm run scaffold:init -- --environment <环境> --app-name "<应用名>"`，接续时补齐缺失文件用 `npm run scaffold:repair -- --app-name "<应用名>"`；然后 `npm run setup`、`npm run doctor`。三件套、方案页、阶段标记的规则见 [reference/开发者中心与工作区.md](reference/开发者中心与工作区.md)。
4. **读一次开发者偏好**：`dev_preferences(action="pull")`，按需阅读；写过的照做，其余用可逆默认，当前指令优先。
5. **读协作状态**（已有应用）：`business_ui_manage(action="get")` 看 `role`、待定版清单和自己草稿的基线是否过期；属主先处理待定版，协作者草稿基线过期先合并，做法见 [reference/多人协作.md](reference/多人协作.md)「开工和接续先读协作状态」。

开工后在第一次实质答复结束前，把已知的业务目标、范围和待明确事项写进 `docs/proposal/index.html`，未知的标「未知」。开发者只给了一句话、方向还不清楚（[design/按轮问.md](design/按轮问.md)「从开发者给的东西开始」第三行）时，先不开工：直接发方向那一轮，这一轮不调制作工具、不算实质答复。方向定了，用选定方向起一个暂定应用名（例如「小红书商家诊断报告」），做开工四步，再发下一轮；应用名以后可以改，在 PRD 里定稿。

## 6. 五段

| 段 | 交给开发者 | 开发者要做的 | 包含的工作区阶段 | 读 |
|---|---|---|---|---|
| ① 需求确认 | PRD：要什么、不要什么、谁来用、每一步谁来做、能不能做（已真查真调）、做不到的怎么替代、花多少和用多少 | 写 PRD 前按轮答问题（一句话起步也行）；看懂 PRD、批注、补账号授权，回「确认这一版」 | G1、G2 | [stages/1-需求确认.md](stages/1-需求确认.md) |
| ② 方案 | 每个功能完成什么业务、怎么完成，每个功能一道判断题，验收条目定稿 | 先按轮答做法上的取舍题；再逐题答「对 / 不对」，确认验收条目 | G3 | [stages/2-方案.md](stages/2-方案.md) |
| ③ 制作 | 每个功能做到哪了（后台、页面、存数据）；每个后台做好的功能必须发一次「我先跑了一遍」：你挑的例子、为什么挑、每一步、结果（只写「示例已跑通」不算）；页面说明。读写应用库的路线进 ④ 前必须反读自查：脚本有 `db(`、写库包在 `if not ctx.dry_run:` 里、挂了 `query_business_app_dataset`、入口没有整包字段，缺一项不许部署 | 看；只在三种情况下拍板 | G4、G5 | [stages/3-制作.md](stages/3-制作.md) |
| ④ 试用验收 | 验收报告：你部署后在在线预览里按验收条目逐条测。业务结果用开发工作集真跑（`business_ui_data_space="workspace"`）并查库；页面条目先问开发者是否同意你启动浏览器，同意后在在线预览里操作。每条「通过」附你取得的证据；「好不好你说了算」的几条附实际结果。你测不了的先按恢复办法处理，仍测不了的标「未测」并写原因，**禁止**请开发者代测；报告过不了 ④ 的「报告的硬门」，G6 判 `failed`，不许请开发者说「可以上线」 | 答是否同意你开浏览器（同意就在弹出的窗口里登录）；看报告，说「可以上线」或哪一条还要改 | G6 | [stages/4-试用验收.md](stages/4-试用验收.md) |
| ⑤ 上线 | 上线结果：你定版，写定了哪一版、④ 验过什么（「未测」条目单列）、实际花费（本段、累计、上限）、开发者可以做的事；写明发布后已安装的使用者会更新到这一版，正式入口和到点自动化发布后才能用，发不发、发给谁由开发者定。**禁止**请开发者发布、等发布或在发布的版本上做验证 | 看上线结果；自己决定是否发布、发给谁、分享 | G7 | [stages/5-上线.md](stages/5-上线.md) |

- **按段推进，交棒有条件**：进入每一段的第一件事，是用命令把这一段的 `stages/` 文件从头读到尾（只读过 `SKILL.md` 或上一段的文件不算），读完再调这一段的工具；每段的交棒条件写在段文件末尾，满足了才进下一段（① 开发者回「确认这一版」，② 判断题都答「对」，③ 能部署，④ 报告过了硬门、开发者看后说「可以上线」）；退回时回到写明的那一段，只改受影响的部分：② 要的东西变了、③ 发现做不到、④ 要的东西本身不对回 ①，③ 结果始终达不到预期回 ②，④ 结果不对回 ③。新建和改已上线的应用都走五段；改已上线的应用时每段只做和改动有关的部分，④ 和 ⑤ 每次都做（见 [tasks/修订.md](tasks/修订.md)）。
- **顺序按依赖走**：后一步要用前一步的产出（路线 ID、`business_ui_id`、数据模板）时，先把前一步做完；平台对象用到时再建，**禁止**提前建空容器；① ② 只查不建（能力试用包除外）。
- **只靠交付物接力**：每段的交付物写进方案页和阶段文档，内容要完整到另一个 Agent 只读这些交付物就能接着做下一段，不依赖聊天记录。阶段文档只用 `docs/stages/` 里已生成的七份，一个工作区阶段一份，不另建文件：② 的施工单、业务说明、判断题和回答、验收条目、费用复核都写进 G3 那一份。PRD 的正本在方案页；确认版全文只在 G1 阶段文档存一次，之后各段写「依据 PRD 第 N 版」并只记和 PRD 不一样的地方，不再复制全文。
- **做不到的尽早说**：在 ① 就能查出来的做不到（授权接不上、平台没有这个工具、时间达不到），必须在 ① 的 PRD 里写明并给替代选择题，**禁止**拖到后面的段才说。
- **每次交接说四件事**：刚做完、下一步、要你做的、花了多少；花费固定写「本段 N；累计 N；上限 N」，三个数缺一不发，上限在 ① 定成具体积分数。每段结束和 ③ 的每次进度更新都发一条，写法见 [design/交接消息.md](design/交接消息.md)。
- **中间不设多余的等待**：② 的判断题答完后，一路做到 ④ 交出验收报告，进度写进方案页和交接消息，开发者想看随时看。只在这些时候停下来问开发者：③ 写明的三种拍板情况；缺开发者本人才能给的东西（授权、密钥、业务事实）；要做 PRD 没列的外部副作用；你自己确实推进不下去。
- **上线要开发者开口**：上线前必须有 ④ 的验收报告，每条验收条目都有结论，开发者看过报告明确说「可以上线」，改动再小也一样。验收由你做，页面条目也由你在在线预览里测，开发者不逐条试；报告里有「未测」条目时开发者照样可以说「可以上线」，你不追问、不因此拒绝定版。到点或有新记录时自动开始的那一步，④ 用冒泡在开发工作集里验处理逻辑；到点真触发、使用者从目录或分享打开要先发布才看得到，④ 记「未测」并写原因，⑤ 单列并告诉开发者发布后自己怎么看（见 [stages/4-试用验收.md](stages/4-试用验收.md)）。
- **阶段标记与阶段记录**：工作区仍是 G1–G7 七项，五段对应见上表；每段出口按段文件「交棒条件」写的几项各调一次 `business_ui_stage`。标记和记录的写法只在 [reference/开发者中心与工作区.md](reference/开发者中心与工作区.md)「三件套与阶段标记」。
- **Studio 宿主只管保存与显示**：当前宿主实际提供 Studio 制作工具时，五段和上面各条照旧，Studio 只决定文档怎么保存、显示和确认：① 的确认对象是 PRD，② 的确认对象是方案，都要读到 Studio 的原生确认才往下走；④ 不用 Studio 的本地演示或已发布版本作验收证据；⑤ 你只定版，不做目录发布。做法见 [reference/开发者中心与工作区.md](reference/开发者中心与工作区.md)「Studio 宿主」。

用某个工具前先确认它在你当前的工具列表里；找不到就如实说该能力当前不可用，**禁止**虚构平行工具。调用被拒时按返回的提示改，不猜、不自造兼容字段。

**平台问题按阻塞程度报**：先按 [reference/报错对照.md](reference/报错对照.md) 处理；应用自己的脚本、页面、数据格式、提示词问题自己改，不提交。`submit_dev_feedback` 新建时必填 `blocking` 与 `attribution`：
- **阻塞**（`blocking="blocked"`）：按指引处理后仍走不下去、没有可行绕法，立即提交，附报错原文和 `project_id` / `run_id`；
- **不阻塞**（`worked_around` 已绕过、`request` 功能诉求）：不即时提交，记进开发记录，⑤ 上线或本次会话结束时汇总成一条提交；
- 新建前先 `query_dev_feedback` 查本人未关闭的反馈，同一问题优先用返回的 OA 主号 `code` 作为 `feedback_code` 查询或追加，不重复新建。`source_code` 是稳定来源别名，旧 `feedback_id` 仍等于它；三个选择器至多传一个，禁止猜编号互换。交付优先写 `code`，来源另注。身份缺失、回包矛盾或写入结果 `unknown` 时，按报错对照先核对，禁止补建。
提交成功不等于问题已确认或已解决，不能据此放行验收。平台问题挡住进度时，交接消息里告诉开发者「卡在哪、谁在处理、对你的影响」，不请开发者去修。阻塞的平台问题没人修时按这个顺序升级：
1. 提交后先做不受它影响的部分，交接消息开头写「卡住了」。
2. 每次继续工作时用 `query_dev_feedback` 看处理进展；有回复按回复做。
3. 提交满 1 个工作日仍没有处理人回复，或回复了但给不出修复时间：给开发者发一道选择题，只问开发者能拍板的事。选项从这几种里挑能成立的：
   - 等平台修：写清这期间哪些功能做不了、预计影响哪一段；
   - 换做法绕开：写清和 PRD 比少了什么、多花多少（换做法会改「要什么」的，退回 ①）；
   - 这次先不做受影响的功能；
   - 请开发者把反馈编号转给平台负责人催办：这是开发者自己手上的事，选项里附上反馈编号和一句问题说明，不附报错原文。
4. 开发者选了以后照做，记进阶段文档。

**禁止**为了解开卡点请开发者授权你改生产库、平台库，或改别人（包括使用者）的安装记录和数据；这类修复只能由平台方做。
