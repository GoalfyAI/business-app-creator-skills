# 业务应用开发指南

> 版本 v3.0，2026-09-08。本 Skill 是**一个主导入口、七个阶段、一套共享协议、八份细则正本**。阶段文件 G1 至 G7 是唯一主线，读完即可执行；细则正本只放阶段文件写不下的表格、契约、纪律清单与示例，在阶段文件点名时查阅。总入口负责识别任务、盘点材料、路由阶段、控制范围与授权、验收整套业务应用。

## 0. 业务应用是什么

本 Skill 的产出物只有一种：**业务应用**——交付给一类明确客户、由最终用户持续使用的应用。它结合客户持续变化的业务事实，在约定目标、权限与验收标准内，稳定完成一类反复发生的工作，并在下一次工作中复用已经确认的信息和经验。

业务应用由五个部分组成，每个部分承担用户使用链路上固定的环节。缺任何一环，做出来的就只是一个能出结果的聊天入口，不是业务应用：

| 组成部分 | 是什么 | 承担的使用环节 | 最终用户做什么 | 应用做什么 |
|---|---|---|---|---|
| **前端应用** | 在脚手架上实现的页面：首页、项目列表、消息中心是平台必备；看板、数据管理、业务发起、项目页与交付审阅是业务页面。只经 SDK 与平台交互，自己不发 HTTP | 看到现状 | 打开应用看看板：指标、列表、待办 | 展示本用户的统计、历史结果与进行中的任务 |
| | | 发起一件事 | 选任务入口，只填自己才知道的信息，或选一个已有项目复用 | 读取已有资料带入发起报文，创建项目，按业务路线开始执行 |
| | | 拿到结果与修改 | 预览、核对事实、下载；对指定版本提修改意见，比较、确认；承诺发布时授权发布 | 呈现完整产物与依据；只改目标部分、联动受影响内容、保留旧版本、失败不覆盖；执行已授权的外部动作并取回执 |
| | | 离开再回来 | 关掉页面、换设备、隔天再打开 | 任务与结果可找回，从正确位置继续，不重复执行不重复扣费 |
| | | 反馈 | 说这次结果哪里不对、有没有用 | 关联到具体任务与版本，进入优化 |
| **专属后端** | Express 加 PG，直连本用户的 app schema；部署在 p2s 公网域名，经 Max 后端服务端转发到达 | 编辑数据 | 在数据管理页增删改自己的业务数据 | 按逐列可编辑性放行，带来源与审计；统计聚合喂看板；产出回流入库 |
| **业务应用数据模板** | 表、字段、逐列可编辑性 user、agent、system，来源标记，回流语义；用户首次打开时从模板复制出专属一份，一用户一 schema，被后端直连和执行中的你两条通道读写 | 下次更省事 | 不再重复解释门店、账号、偏好 | 复用已确认的事实与长期偏好；单次要求只影响本次；可查看可纠正；生产回流不覆盖用户改过的字段 |
| **能力容器** | 平台里叫场景包，定义执行中的你在这个业务里能做什么、怎么做、用什么做：业务路线、任务点、工具集与 FastAgent、工具组与授权卡、apc_skill 与场景 Skill 文件、长期数据集引用 | 执行中参与 | 在必要节点补充事实、做业务选择、给动作授权 | 连续执行已确定的步骤，只在缺信息、需取舍、授权不足时暂停并说明原因；冻结交付、发起审阅 |
| **发布单位 business_ui** | 业务应用在平台里的资产身份：自己的家族与版本，恰好挂 1 个能力容器、至多 1 份数据模板 | 版本与交付 | 用到的始终是验过的那个版本 | 绑定明确的容器版本与模板版本；契约变化触发受影响测试 |

能力容器内部的四类对象各管一段：**业务路线**对应用户的每个入口，定义入口表单、节点依赖与并行、中途表单、交付冻结与审阅、重入；**任务点**分两型，编排型 TPE 是确定性脚本，编排工具与 FastAgent，普通任务点派给 TaskAgent 临场执行、可与用户交互；**工具集**装工具与 FastAgent 并附使用指南，预加载或动态加载；**apc_skill 与场景 Skill 文件**是运行时你看得到的业务规则与知识。

运行关系：用户在页面发起 → 业务路线在一个项目里跑 → 任务点调用工具与 FastAgent → 产出回流到本用户的 schema → 页面展示、用户编辑 → 下次运行读取已确认的事实与偏好。

交付物 = 能力容器版本 + 应用版本 + 数据模板版本 + 验收记录，验收记录里每条业务承诺都对应规则、实现与分阶段证据。能力容器工单结单不等于业务应用已交付。

## 1. 总入口负责什么

1. **识别任务。** 六类：新建、接续、修订、诊断、能力试用、仅讨论。仅讨论**不触发**资产创建。
2. **盘点已有材料、资产与证据。** 从最早未满足的必要条件进入，**禁止**机械从 G1 重做。
3. **每阶段给出四样。** 推荐下一步、理由、待决策事项、验收依据。平台术语由你转译成业务语言。
4. **控制范围、权限、试验费用与副作用。** 到必要决定点暂停；其余已授权工作连续推进。
5. **验证失败时返回问题归属与证据。** **禁止**把失败转述为"请开发者自行处理"。
6. **最终验收整套业务应用。** 按 G1 编号的承诺清单逐条对账，能力容器工单结单**不等于**应用已交付。

### 1.1 角色与称谓

本 Skill 里只有四个角色，所有"人"都必须落到前两个之一：

| 角色 | 是谁 | 在本 Skill 里做什么 |
|---|---|---|
| **开发者** | 使用本 Skill 制作、维护、发布业务应用的人。代表客户方回答业务事实 | 拥有产品形态、业务契约、授权的决定权。所有"向开发者确认""开发者拍板""开发者授权"都指他。文中"客户方"指开发者所服务的客户，其事实由开发者转达 |
| **最终用户** | 业务应用上线后使用它的人 | 只在开发者确认过的入口、表单、审阅、授权节点参与运行。运行期分工里的"最终用户"就是这一步由他来做 |
| **你** | 此刻执行本 Skill 的你 | 调查、提案、制作、验证；准备事实、候选、推荐、影响、风险；**不代替**开发者决定。本 Skill 全文用「你」称呼 |
| **运行 Agent** | 业务应用运行时在能力容器里执行任务的你，包括 SystemAgent、TaskAgent、FastAgent | 只按已确认的设计执行；**禁止**把技术选型问题转嫁给最终用户 |

称谓规则：开发期的确认、授权、审核，主语一律写**开发者**；运行期每一步谁来做，主语一律写**最终用户**或**运行 Agent**；需要专业判断而最终用户无法承担的，写**专家**，由开发者引入。单独出现的"用户"一律指最终用户；本 Skill 用「你」称呼你；单独出现的「你」指运行 Agent。**禁止**用"人""业务方"这类不落到角色的称呼。

### 1.2 任务识别

| 开发者要做什么 | 任务类型 | 工单 | 从哪进 |
|---|---|---|---|
| 把业务目的、SOP、经验、参考项目做成业务应用 | 新建 | `write` | G1 |
| 继续此前未完成的制作 | 接续 | `get` 原工单 | 先 `workspace_remote_status`、`workspace_pull` 恢复 goalfy-app-workbench 目录，再进 `WORKSPACE.md` 的 `current_stage` |
| 改已上线应用的页面、接口、表、路线、能力 | 修订 | `write`，先取可编辑草稿 | 受影响的最早阶段，规则见协议一约束 24 |
| 效果差、报错、数据不对、页面异常 | 诊断 | `read`；转修复时新建 `write` | P8 定位后路由到所属阶段 |
| 验证一个外部能力值不值得做进来 | 能力试用 | `write` | G2，流程见 P2 能力试用一节 |
| 只想讨论方案、问概念 | 仅讨论 | 不建工单 | 不进阶段，不创建资产 |

先过工单 Gate，规则见协议四第 1 节；再按 1.3 拉脚手架、起服务。意图或关键参数缺失时先问。缺口分六类：意图、关键参数、知识、工程偏好、产品决策、授权，判定方法见 P1 第 2 节。

### 1.3 开发者中心：第一步永远是拉脚手架、起服务

**开发者中心是什么。** 一个跑在开发者本机的三栏网页，仓库 `goalfy-app-workbench`，地址 `http://127.0.0.1:5180/`。左栏是 G1 到 G7 的开发流程与状态；中栏渲染你维护的一份方案页，固定路径 `docs/proposal/index.html`，脚手架按这个地址渲染，只讲两件事：业务过程，替谁、按什么过程把事做成；开发内容，正在把它做成什么，含分工泳道图、运行路线、业务数据表、页面；右栏是开发协作区，你和开发者的对话交互在这里展示，当前版本正在接入。它只读本地文件：你改 `docs/proposal/index.html`，页面实时更新，不需要开发者刷新。`docs/stages/` 下的七份 md 是给你和后续 Agent 用的工作记录，不展示。

**两个仓、两套服务。** 业务应用脚手架 `goalfy-app-scaffold` 生成应用工程，仓根就是 goalfy-app-workbench 目录；开发者中心 `goalfy-app-workbench` 是独立仓。工作台一次可以管多个应用：它按配置链找应用目录，优先级是命令行、环境变量、`workbench.config.local.json`、`workbench.config.json`、内置默认；`appsDir` 把一个目录下的每个一级子目录当成一个应用，`apps` 是显式清单，两者取并集。单应用调试用环境变量 `GOALFY_WORKBENCH_WORKSPACE` 直接指到应用目录。

**你的目录能不能被工作台看见，取决于两个文件。** 仓根必须有 `app.json` 且 `schema_version` 形如 `goalfy.app/vN`，否则这个目录**整体被忽略**，压根不进应用列表；有了 `app.json` 但 `WORKSPACE.md` 还没就绪，列表里显示"初始化中"且选不中。所以顺序固定：先 `app.json`，再 `WORKSPACE.md`，再七份阶段文档。

任何制作任务的第一个动作，在建工单之后、进入 G1 之前：

1. **拿到 goalfy-app-workbench 目录。** 新建：用业务应用脚手架生成应用工程，仓根有 `app.json`、`WORKSPACE.md`、`docs/history/`、`run-dev.sh`。**脚手架自带的是一份示例应用，不是空模板**：`app.json`、`WORKSPACE.md`、`docs/stages/` 七份 md、`docs/proposal/index.html` 里装的都是别人的业务，**必须**整份换成本应用的内容，**禁止**留着示例的应用名、编号、阶段、版本或正文往下做。七份阶段文档按协议四第 6 节的头重写，未开始的阶段 `status` 写 `not_started`；`docs/proposal/index.html` 由你从零写，规则见协议三第 7 节。接续：先调 `workspace_remote_status(workspaceId)` 看云端有没有保存，有就 `workspace_pull` 拉回，按协议四第 6 节恢复；没有就定位本地已有仓。G1 收敛四结论是"直接用能力容器"时 goalfy-app-workbench 目录 照样存在，代码目录空着。
2. **起两套服务。** 在应用工程根执行 `./run-dev.sh start`：后端 8000、前端 5175、Dev Host 预览壳 5176。在开发者中心仓执行 `./run-dev.sh start`：服务 5179、页面 5180。把 `http://127.0.0.1:5180/` 给开发者。中栏 G4 到 G7 的预览地址**不用手配**：Dev Host 启动时会往应用目录的 `.workbench/dev-host.json` 写调试地址声明，退出自动删，工作台按进程号加探活双重校验自动侦测；只有 QA 远端联调才用环境变量 `GOALFY_WORKBENCH_APP_URL` 显式覆盖。看不到预览就先确认应用工程那边的服务起没起，**不要**去手改那个文件。改了启动相关配置用 `restart`，其余时候**不重启**。
3. **登记身份，两处同改。** `app.json` 写 `schema_version: goalfy.app/v1` 与本应用的 `id`、`name`、`version`；`WORKSPACE.md` 的 `workspace_id` 用一个换电脑也不变的稳定标识，它同时是云端保存的 `workspaceId`，`environment`、`business_ui_id` 填对。**`app.json` 的 `id` 与 `WORKSPACE.md` 的 `business_ui_id` 是同一个应用身份，必须同改**，不一致时工作台的应用列表会报警示。没有 `business_ui` 时两处都留空，G5 建草稿后一起回填。`app.json` 是开发期身份，交付清单 `goalfy-app.json` 是另一回事，**不要**混。
4. **工作目录不动。** 会话的工作目录只能是应用工程根，Skill 执行中**禁止**切到别处。

之后每个阶段按协议三第 7 节填页面、按协议四第 6 节写 md 与改状态，页面自动刷新；每个阶段出口按协议四第 6 节把整个 goalfy-app-workbench 目录 保存到云端。`.workbench/` 是工作台和 Dev Host 自己管的运行时目录，看到里面的文件出现又消失是正常的，**禁止**手改、提交，也**禁止**依赖它存在。

### 1.4 前置：工具可用性

business-app-creator 的 MCP 工具在会话开始时已在工具列表里。用某个工具前先确认它存在。**当前看到的工具定义是唯一事实**，规则见协议一约束 26。找不到的工具不假设存在，按约束 26 处理。确认凭证只做只读查询。

## 2. 七个阶段

```text
开发者提供业务目的、材料或已有应用
  ▼
G1 业务目标与范围        明确用户、结果、边界与好坏样例          验收：做什么、不做什么、合格结果对齐？    否→补事实或改范围
G2 关键能力可行性        真实工具和模型试验；必要时建隔离试用包    验收：关键路径有证据、缺口有处置？        否→换能力或回 G1
G3 运行设计与验收基线    路线、人机分工、数据、页面状态联合设计    验收：行为可理解、边界、实现映射、测试标准齐？ 否→改设计或回 G2
G4 核心执行单元验证      准备依赖与能力容器草稿；创建并验证任务点  验收：单元契约与实际输出成立？            否→修同一资产
G5 后端业务闭环验证      组装路线真跑；数据模板、后端、验证实例    验收：执行、交付、入库、恢复在真实环境闭合？ 否→定位单元、路线、数据
G6 用户操作闭环验证      实现完整界面；接通 SDK、状态、修改与历史  验收：用户能完成、能修改、能继续？        否→修界面或回 G5
G7 预发布与交付          最终部署物完整验收、版本核对、授权上线    验收：承诺、证据、版本、授权与交付一致？   否→回问题所属阶段
  ▼
交付可持续使用的业务应用 ── 真实问题与效果证据，确定影响范围后重入 G1
```

| 阶段 | 文件 | 进入依据 | 会点名的细则 |
|---|---|---|---|
| G1 | `stages/G1-业务目标与范围.md` | 一句目的、PRD、SOP、参考项目、已有应用问题，任一即可 | P1 |
| G2 | `stages/G2-关键能力可行性.md` | G1 基线成立，未知项已列成试验问题 | P2、P6 |
| G3 | `stages/G3-运行设计与验收基线.md` | 关键能力足以选路线 | P1、P3、P4、P5、P6 |
| G4 | `stages/G4-核心执行单元验证.md` | 当前切片设计与验收标准已确认，制作授权明确 | P2、P3、P6 |
| G5 | `stages/G5-后端业务闭环验证.md` | 单元通过适用验收，契约与 G3 一致 | P3、P4、P5、P6、P7 |
| G6 | `stages/G6-用户操作闭环验证.md` | 后端闭环成立，页面设计与真实契约一致 | P5、P6 |
| G7 | `stages/G7-预发布与交付.md` | 使用闭环通过，发布范围与版本关系确定 | P6、P7、P8 |

**承诺清单是七个阶段的主线，阶段只是时间轴。** G1 把《业务计划书》里的每条承诺抽成编号 `C1`、`C2`…，此后 G2 每条对应一次能力实测或标"无需实测"，G3 每条映射到节点、页面或表，G4 到 G6 每条逐条拿证据，G7 逐条对账；每个阶段出口整份重写 `commitment_list`，并把每条承诺与状态显示在开发者中心页面顶部。规则见协议二第 1 节。

**阶段文件读取纪律。** 进入任何阶段的第一个动作是完整读取该阶段文件；一次只读一份；出口条件满足后落 `stage_exit` 再进下一阶段；修正环内的回跳沿用原记录。每个阶段固定七项：进入依据、本阶段建设、给开发者看什么、要确认哪些边界、门禁 Checklist、证据与结论、失败回退。每个阶段给开发者看的展示物都是 goalfy-app-workbench 目录 `docs/stages/` 下该阶段的那一份 md，图用 Mermaid 写在文件里，开发者工作台经 SSE 实时渲染，工单标签存同一份全文，规范见协议三第 7 节。

**平台对象什么时候创建。** **禁止**提前建空容器；**禁止**用页面替代单元证据。

| 对象 | G1 至 G3 | G4 | G5 | G6 至 G7 |
|---|---|---|---|---|

## 5. 两层 Checklist

- **G 门禁**，文件 `checklists/G门禁检查清单.md`。回答"是否具备进入下一阶段的条件"，共 48 条。每条只有三列：查什么、证据是什么、不过怎么办。门禁引用 U 项的分阶段结论，**不替代**业务行为。
- **U 业务行为验收明细**，文件 `checklists/U业务行为验收明细.md`。八组：U1 开始、续用与历史；U2 信息准备与真正使用；U3 Agent 连续推进；U4 离开与异常恢复；U5 结果检查与反复修改；U6 留存、偏好与效果回传；U7 跨应用 Agent，条件适用；U8 临时编排，条件适用。G3 实例化为本项目用例，G4、G5、G6 分层取证，G7 复验。
- **专业验收清单**：`checklists/方案挑战检查清单.md` 用于 G3；`checklists/编排型TPE验收检查清单.md` 用于 G4；`checklists/场景包验收检查清单.md` 用于 G5a 能力容器上线门；`checklists/应用验收检查清单.md` 用于 G5b、G6、G7。

## 6. 贯穿七阶段的四项横向设计

1. **使用问题是开发要求。** U1 至 U6 按阶段落实：G1 定价值，G2 验前提，G3 定行为，G4 与 G5 做能力，G6 验使用，G7 验最终版本。U7 与 U8 不是自动加入的必备功能；纳入承诺时 G2 必须验前提。
2. **优化能力与"优化已经有效"分开。** 规则见协议四第 3 节。
3. **两类知识、两类问题分开存放。** 规则见协议四第 2 节。
4. **展示、确认、执行、验收连成一条。** 不是每步都让开发者点确认，见协议一约束 22；可视化是同一事实的不同视图，见协议三第 2 节；路线变更必须展示影响，见协议二第 5 节。
