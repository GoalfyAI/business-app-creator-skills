# 平台对象速查

## 适用场景

分不清场景包里有什么、四种执行形态怎么选、一次运行里谁在做什么、某个 `*_id` 指向什么、家族 / 物理行 / 草稿 / 上线怎么用、MCP 文字里的词对应本 Skill 的哪个词、模型选哪一档、积分怎么算、某件事用哪个工具时读。版本操作的具体做法在 [部署与版本.md](部署与版本.md)；部署、上线、发布三个词的定义在 [../SKILL.md](../SKILL.md)「角色与用词」。

## 规则

### 场景包由什么组成

场景包（能力容器）定义运行 Agent 在这个业务里能做什么、怎么做、用什么做：

| 组成 | 说明 |
|---|---|
| `apc_skill` | 始终注入，运行 Agent 每轮都能看到；写「能做哪几件事、各自什么时候用、发起前要收齐什么」，不写资产 ID |
| 场景 Skill 文件 | 按需读取的大段知识，启动时只看到文件名 |
| 任务点（TPE） | 同一类资产的两种类型：普通任务点、编排型 TPE；都用 `tpe_id`，查询时看类型标记区分 |
| 业务路线 | 场景包字段 `workflow_orchestration`，里面 `orchestrations[]` 每一项是一条路线，`orchestration_id` 是路线标识 |
| 工具集 | 装工具与 FastAgent，附使用指南；预加载或动态加载 |
| 长期数据集 | 已有数据集的引用，不拥有数据 |

智能应用的前端、后端、数据模板不在场景包里，它们消费场景包的公开契约。最小场景包 = 一份草稿（通常克隆官方基础包）+ 至少一个已上线的工具集 + `apc_skill`。平台没有「包引用包」，跨包复用走共享资产（先克隆再改）；继承用 `create_derived_scene_package` 从已上线版本派生新家族（`clone` 或 `personalization`），血缘用 `get_scene_package_lineage` 看。

### 四种执行形态

| 形态 | 是什么 | 能和使用者交互 | 自带文件 / 命令 / 邮件 | 适合 |
|---|---|---|---|---|
| SystemAgent 直接执行 | 运行时对话的 Agent 自己调工具，不产生资产 | 能 | — | 次数确定、指令量小的动作；只在 `apc_skill` 写规则 |
| FastAgent | 可当工具调用的完整执行单元：挂上工具后在一次调用里多轮做完一个业务环节 | 不能 | 不自带，要用就单独配 | 需要模型判断、判断与工具调用交织的环节 |
| 普通任务点 | 派给 TaskAgent 的任务模板，步骤临场决定，独立上下文 | 能，可中途提问 | 自带 | 整条路径要临场规划，或必须和使用者自然语言往返 |
| 编排型 TPE | 确定性脚本，自己不推理；需要模型的环节调 FastAgent | 不能（中途要人用路线的节点级机制） | 自带 | 稳定、可复跑的执行管道 |

- **FastAgent 没有记忆**：每次调用是全新隔离会话，必要背景都要随参数传入。拆 FA 的唯一理由是职责边界不同（领域知识、产出契约、需要独立复用），不是步骤不同。
- FA 与编排脚本各管什么、怎么建 FA，见 [编排脚本.md](编排脚本.md)「FA 与脚本的职责边界」。

### 模型档位

给开发者只说「快而便宜的一档」「强的一档」「写代码的一档」（说法见 [../design/谁来做.md](../design/谁来做.md)「模型选哪一档」）；具体模型名只写进 FA 配置和阶段文档。

| 档 | 当前可选的模型（以 `create_fast_agent` 的 `model_name` 当前可选值为准） | 适合 |
|---|---|---|
| 快而便宜 | `deepseek-v4.1-flash-thinking-ha` | 核实、抽取、分类、打标签、摘要、校验格式；也能看截图 |
| 强 | `deepseek-v4-pro-thinking-ha`（不看图）、`kimi-k2.6-thinking-ha`（要看截图或图片） | 写能直接对外的报告和文案、多步推理、复杂诊断 |
| 写代码 | `kimi-k2.7-code-ha` | 运行时要写或改代码的步骤 |

- 选定的档写进 FA：`model_name` 填所选模型，`model_selection_mode="required"`；不填时运行时按平台默认组解析，花费和效果都不受控制。
- **`max_turns`**：平台硬下限 5（小于 5 会被拒）。建议值按预估步数算：读输入 1 步 + 每次必需的工具调用各 1 步 + 每个落盘产出 1 步 + 提交 1 步，乘 1.5 向上取整，至少 8、至多 50；预估超过 30 步说明环节太大，先拆。
- 每次约多少积分以实测为准：FA 第一次真跑后从 `get_project_execution_logs` 和 `cost_credits` 取这一步的花费；没测过的写「估算」。

### 一次运行里谁在做什么

- **项目**是一次运行的容器：对话、任务点、Runtime、交付物、日志都在里面。项目钉住场景包的具体物理行，包上线新版本后已运行的项目继续跑旧版。诊断以项目为单位，轮询、追问、读日志复用同一个 `project_id`。
- **业务路线 Runtime** 是确定性控制器：节点派发、字段映射、交付冻结都不经过模型；只有声明的中途表单、Agent 介入点和最终审阅会停下来。
- **时序**：入口表单提交 → 派发首批节点 → 节点 `stage_started` → 工具 / FA → `stage_result`（或 `stage_failed`）→ 全部节点完成 → 交付映射求值、文件登记（`artifact_ready`，平台自动）→ 冻结（`delivery_ready`，平台自动）→ 最终审阅。
- **失败是终态**：Runtime 不替脚本重试；重做、改稿、改路线都是开启新的运行实例并保留旧交付。写入步骤怎么写才经得起再执行一次见 [编排脚本.md](编排脚本.md)「脚本骨架」。
- **入口并存**：已发布路线在智能应用和聊天两个入口都能发起，聊天直调时业务事件自动不生效。制作侧不设计入口选择。
- **投影什么**：以使用者能回答「现在到哪了、出了什么、接下来会怎样」为准；阶段名用业务语言；要给使用者看的内容必须以业务字段出现在 `output` 里，界面读不到工作区文件正文。

### 标识指向什么

| 标识 | 指向 |
|---|---|
| `task_id` | 工单审计范围，**不是**资产 |
| `scene_package_id` | 场景包（家族或某个物理行，看上下文，先反读） |
| `tpe_id` | 任务点，普通任务点和编排型 TPE 共用编号 |
| `toolset_id` / `tool_group_id` / `tool_id` | 依赖资产 |
| `mcp_id` | 授权卡绑定用，**不是** `tool_group_id` |
| `run_id` | 冒泡验证实例，续等时复用 |
| `project_id` | 真实项目，查询、追问、读日志时复用 |
| `business_ui_id` | 智能应用的对外 ID（字符串）：旧应用是数字串（如 `"84"`），新应用是 8 位小写字母数字短码（如 `"k3m9x2ab"`）；指向整个应用家族，不是版本行 |
| `business_ui_version_id` | 智能应用的某个版本行（数字），出现在部署、状态与版本工具的返回里 |
| `deployment_id` | 一次应用部署 |
| `data_uid` | 数据模板开发工作集 |
| 脚本里的工具名 | 用真实的调用名（FA 的 `mr_name`），不用数字 ID |

### 版本四个词

| 词 | 含义 |
|---|---|
| 家族 | 对外的稳定身份；版本工具面叫 `resource_group_id`，资产列表叫 `apc_display_id`，同指一个家族。智能应用例外：对外只用 `business_ui_id`（可能是短码），版本工具对智能应用不返回 `resource_group_id`，版本行在 `business_ui_version_id`；**禁止**用数字推算或代入应用 ID |
| 物理行 | 一个具体版本对应的资产行，独立 ID；版本引用指向具体物理行 |
| 草稿 | `testing` 状态的物理行；制作、修改、验证都在草稿上做；一个家族同一时刻只有一个草稿 |
| 上线 | `testing → live`，旧上线版本保持不变。场景包上线后可被运行；智能应用上线后还要开发者发布，正式入口才能打开。哪些操作要先上线见 [部署与版本.md](部署与版本.md)「草稿、上线、发布各能做什么」 |

### 积分怎么算

GoalfyMax 只按**积分**计费。跟开发者说费用、写估算、汇报花费时一律用积分，不报 token 数，也不自己拿 token 数换算积分。

| 项 | 说明 |
|---|---|
| 换算 | 1 积分 = 0.01 美元的计价额度；充值价以充值页为准 |
| 一个项目花多少 | 四部分相加：模型调用（按所用模型的单价和用量折算）、付费工具（按次或按量）、云端沙盒（存活期间持续计费）、平台资产计费 |
| 开发时哪些花积分 | 冒泡（FA 是桩，但工具、沙盒照常真实执行，付费工具照样扣）、`full_run` 冒泡、真跑、在线预览里的操作与自动化运行，都在 GoalfyMax 上起项目、扣开发者的积分 |
| 哪些不花 GoalfyMax 积分 | 你和开发者之间的对话本身 |

估算按 PRD「会调用：X，每次约 N 积分」写。实际花费看结果里的 `cost_credits`：`manage_goalfymax_project` 的 status / wait 与冒泡终态都带这个字段（该项目截至此刻已花的积分）。

| 字段取值 | 怎么说 |
|---|---|
| `cost_partial=false` | 「这次花了约 N 积分」 |
| `cost_partial=true` | 「至少 N 积分，有一部分还没取到」 |
| `cost_credits=null` | 「这次没取到花费」，不填 0 |

沙盒按周期记账，运行刚结束读到的可能还没算上沙盒部分；汇总累计花费时对记下的每个项目重新读一次。

拿不到实测花费时（例如读写应用库的路线要到 ④ 部署后才能真跑）按这个顺序估：

1. ① 用试用包跑过同类模型步骤的，用那次实测；
2. 没跑过的，每个模型步骤按档位每次花费 × 预计调用次数，付费工具按单价 × 预计次数，相加；
3. 每个数都标「估算」并写出算法（几次 × 每次多少）。

③ 不碰库的路线 `full_run` 出了实测就更新同类估算；④ 真跑后全部换成实测。

## 常见错误

- 把普通任务点和编排型 TPE 当两套资产分别管理；它们都是 TPE。
- 按「步骤」拆 FA，一个环节拆成好几个 FA 串起来。
- 把事实错误当成 Schema 不够严，持续扩充 `_output`，而没有按 [编排脚本.md](编排脚本.md)「FA 与脚本的职责边界」重划 FA、脚本和工具职责。
- FA 调用时只传 ID 不传背景，FA 读不到调用方的历史。
- 拿家族 ID 当物理行用：`get_asset` 传家族根 ID 会解析到最新 live 行；要看某个旧版本必须传那一行的物理 ID。智能应用的应用 ID 可能是短码，物理行 ID 一直是数字；需要物理行时只用 `draft_asset_id`、`business_ui_version_id` 或版本列表返回的行 ID。
- 按形态判断智能应用 ID：`business_ui_id` 是应用的对外 ID，只能原样取自平台返回（`business_ui_manage` 的 `setup` / `list`、`scaffold_bind_command`、工作区 `app.json` / `WORKSPACE.md`）。旧应用是数字串（如 `84`），新应用是 8 位小写字母数字短码（如 `k3m9x2ab`），两种都合法；`84` 与 `"84"` 是同一个应用。**禁止**因形态不同判定为不同应用或出错、新建应用或重新 `setup`；**禁止**把短码换算成数字、把数字补成短码、改大小写、补零或去引号。需要版本行时只用 `draft_asset_id` 或版本列表返回的物理行 ID，不用应用 ID 代替，也不用版本行 ID 代替应用 ID。
- `asset_type` 两套拼法无别名：版本工具面用 `scenario_pack`，业务工具面（list / get / clone / update）用 `scenario_package`。
- 把文件读写、命令执行、邮件发送当成工具缺口去建工具集；普通任务点和编排型 TPE 自带它们。
- 给开发者转述时照搬 MCP 里的「定版」等旧词；按本文「术语表」改说。
