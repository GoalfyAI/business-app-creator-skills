# 平台对象速查

## 适用场景

分不清智能应用由什么组成、执行形态怎么选、一次执行里谁在做什么、某个 `*_id` 指向什么、家族 / 物理行 / 草稿 / 上线怎么用、MCP 文字里的词对应本 Skill 的哪个词、模型选哪一档、积分怎么算、某件事用哪个工具时读。版本操作的具体做法在 [部署与版本.md](部署与版本.md)；部署、上线、发布三个词的定义在 [../SKILL.md](../SKILL.md)「角色与用词」。

## 规则

### 应用由什么组成

智能应用（`business_ui`，对外标识 `business_ui_id`）是发布单位，一个应用版本包括：

| 组成 | 说明 |
|---|---|
| 前端应用 | 脚手架上的页面，只经 SDK 与平台交互，以执行为单位（见 [前端页面.md](前端页面.md)「以执行为单位」）；表单展示定义放 `frontend/schema/packs/<pack>/forms/` 与 `orchestrations/`，`goalfy-app.json` 的 `packs` 列出用到的目录（pack 只是目录名） |
| 专属后端 | Express + PG，直连这个使用者自己的库 |
| 数据模板 | 必须一份，至少一张业务表，见 [数据模板.md](数据模板.md) |
| 业务路线 | 应用版本字段 `workflow_orchestration`，`orchestrations[]` 每一项是一条路线，`orchestration_id` 是路线标识。一条路线 = 入口表单标识、路线级输入、节点依赖图（节点引用编排型 TPE，无环、全部可达）、节点输入映射、可选的节点级中途表单、唯一的最终交付与审阅 |
| 编排型 TPE | 应用版本字段 `tpe_ids`，每项是 TPE 资源组 ID 加版本（具体版本号或 `latest`，上线时钉死；不写版本行 ID）；编排里引用的每个 TPE 都要在里面 |
| 工具集与 FastAgent | 节点脚本调的工具挂在**该节点 TPE** 上（`otpe_manage` 的 `preload_toolset_ids`）；FastAgent 自己的工具照常 |
| 长期数据集 | 官方、公开数据集的引用，不拥有数据；**禁止**依赖开发者个人的普通数据集（使用者运行时无权限） |

- 路线与 `tpe_ids` 用 `business_ui_manage(action="update", business_ui_id, workflow_orchestration, tpe_ids)` 保存，**整体替换**：只传改动的那条路线会覆盖掉其他路线。保存、组装、冒泡见 [业务路线.md](业务路线.md)「路线挂在应用版本上」「assemble 怎么用」「冒泡」。
- 应用工程 `frontend/goalfy-app.json` 写有 `"executor": "launch_agent"`，当前脚手架新建的都是；**禁止**手工增删。没有这个字段的旧应用先按 [旧应用迁移.md](旧应用迁移.md) 升级。
- 复用官方或他人的 TPE、FA、工具集走共享资产：先 `clone_asset` 再改。

### 执行形态

一次运行叫「执行」。执行里没有对话，只有下面三种形态在做事：

| 形态 | 是什么 | 能和使用者交互 | 自带文件 / 命令 / 邮件 | 适合 |
|---|---|---|---|---|
| 编排型 TPE | 路线节点的确定性脚本，自己不推理；需要模型的环节调 FastAgent | 不能（中途要人用路线的节点级中途表单） | 自带 | 稳定、可复跑的执行管道 |
| FastAgent | 可当工具调用的完整执行单元，在 TPE 脚本里调用：挂上工具后在一次调用里多轮做完一个业务环节 | 不能 | 不自带，要用就单独配 | 需要模型判断、判断与工具调用交织的环节 |
| 人（使用者） | 路线的入口表单、节点级中途表单、最终审阅（`user_gate`） | 就是交互本身 | — | 补信息、做选择、审阅结果 |

- **FastAgent 没有记忆**：每次调用是全新隔离会话，必要背景都要随参数传入。拆 FA 的唯一理由是职责边界不同（领域知识、产出契约、需要独立复用），不是步骤不同。
- FA 与编排脚本各管什么、怎么建 FA，见 [编排脚本.md](编排脚本.md)「FA 与脚本的职责边界」。
- 结果好不好由使用者审阅，平台不替你判断；能用规则判断的写进 TPE（输出校验、`business_gate`）。

### 模型档位

给开发者只说「快而便宜的一档」「强的一档」「写代码的一档」（说法见 [../design/谁来做.md](../design/谁来做.md)「模型选哪一档」）；具体模型名只写进 FA 配置和阶段文档。

| 档 | 当前可选的模型（以 `create_fast_agent` 的 `model_name` 当前可选值为准） | 适合 |
|---|---|---|
| 快而便宜 | `deepseek-v4.1-flash-thinking-ha` | 核实、抽取、分类、打标签、摘要、校验格式；也能看截图 |
| 强 | `deepseek-v4-pro-thinking-ha`（不看图）、`kimi-k2.6-thinking-ha`（要看截图或图片） | 写能直接对外的报告和文案、多步推理、复杂诊断 |
| 写代码 | `kimi-k2.7-code-ha` | 运行时要写或改代码的步骤 |

- 选定的档写进 FA：`model_name` 填所选模型，`model_selection_mode="required"`；不填时运行时按平台默认组解析，花费和效果都不受控制。
- **`max_turns`**：平台硬下限 5（小于 5 会被拒）。建议值按预估步数算：读输入 1 步 + 每次必需的工具调用各 1 步 + 每个落盘产出 1 步 + 提交 1 步，乘 1.5 向上取整，至少 8、至多 50；预估超过 30 步说明环节太大，先拆。
- 每次约多少积分：单条 TPE 冒泡（`otpe_manage(action="bubble")`）的 `cost_credits` 是实测；执行回执目前不带花费，其余按「积分怎么算」估算并标「估算」。

### 一次执行里谁在做什么

- **执行**是一次运行的单位，标识 `business_id`（`BIZ-` 开头），**服务端生成**，调用方（你、页面、脚本）从不自己生成或填写。**项目**是每个使用者实例一个的隐藏容器，多次执行在里面并行；交付物、日志在项目里。诊断以执行为单位，查状态、回复都复用同一个 `business_id`；真跑读轨迹另带 `run` 回执里的 `project_id`，冒泡回执不带 `project_id`，冒泡看回执的 `steps` 与节点证据（见 [业务路线.md](业务路线.md)「冒泡」）。
- 执行跟着发起时的应用版本；页面版本落后或执行属于旧版本时回复会被拒（`APP_VERSION_OUTDATED`，见 [报错对照.md](报错对照.md)「执行」）。
- **业务路线 Runtime** 是确定性控制器：节点派发、字段映射、交付冻结都不经过模型；只有声明的中途表单和最终审阅会停下来。
- **时序**：入口表单提交 → 派发首批节点 → 节点 `stage_started` → 工具 / FA → `stage_result`（或 `stage_failed`）→ 全部节点完成 → 交付映射求值、文件登记（`artifact_ready`，平台自动）→ 冻结（`delivery_ready`，平台自动）→ 最终审阅（`message_type:"ask"` 停下等使用者，`"result"` 直接交付）。
- **失败不自动重跑**：平台不替脚本重跑失败节点，派发超时、中断也判失败，等使用者点重试；重试会重跑失败节点的全部步骤。外发步骤防重复、并行写库防冲突见 [编排脚本.md](编排脚本.md)「并行执行的约定」；改上一趟的结果走修正路线，见 [业务路线.md](业务路线.md)「修正上次交付」。
- **投影什么**：以使用者能回答「现在到哪了、出了什么、接下来会怎样」为准；阶段名用业务语言；要给使用者看的内容必须以业务字段出现在 `output` 里，界面读不到工作区文件正文。
- **入口**：路线只能从智能应用发起（页面、自动化、MCP 真跑与冒泡），没有聊天入口。

### 标识指向什么

| 标识 | 指向 |
|---|---|
| `task_id` | 工单审计范围，**不是**资产 |
| `business_ui_id` | 智能应用的对外 ID（字符串）：旧应用是数字串（如 `"84"`），新应用是 8 位小写字母数字短码（如 `"k3m9x2ab"`）；指向整个应用家族，不是版本行 |
| `business_ui_version_id` | 智能应用的某个版本行（数字），出现在部署、状态与版本工具的返回里；冒泡回执、真跑 `status` / `wait` 回执里的版本行也是它，结单豁免填它 |
| `business_id` | 一次执行，`BIZ-` 开头，服务端生成；路线冒泡返回的 `run_id` 就是它；真跑后的 `status / wait / reply / stop` 都按它 |
| `orchestration_id` | 应用版本上的一条路线，只取已定义的 |
| `workflow_runtime_id` | 路线运行实例，服务端生成，不自填 |
| `run_id` | 冒泡返回的标识，续等、回填、止损时复用：路线冒泡是执行号（`BIZ-`，即 `business_id`）；单条 TPE 冒泡是 `WFR-` 开头的单次运行号，不是执行号。脚本里的 `ctx.run_id` 是本节点这一次运行的标识（`WFR-`），重试会换新，不作幂等键 |
| `project_id` | 使用者实例的隐藏项目；真跑 `run` 回执里有，查轨迹时与 `business_id` 一起传；冒泡回执不带 |
| `tpe_id` | 编排型 TPE；`otpe_manage(create)` 回执的 `tpe_id` 就是资源组 ID，`tpe_ids` 里写它加版本 |
| `toolset_id` / `tool_group_id` / `tool_id` | 依赖资产 |
| `mcp_id` | 授权卡绑定用，**不是** `tool_group_id` |
| `deployment_id` | 一次应用部署 |
| `data_uid` | 数据模板开发工作集 |
| 脚本里的工具名 | 用真实的调用名（FA 的 `mr_name`），不用数字 ID |

### 版本四个词

| 词 | 含义 |
|---|---|
| 家族 | 对外的稳定身份；版本工具面叫 `resource_group_id`，资产列表叫 `apc_display_id`，同指一个家族。智能应用例外：对外只用 `business_ui_id`（可能是短码），版本工具对智能应用不返回 `resource_group_id`，版本行在 `business_ui_version_id`；**禁止**用数字推算或代入应用 ID |
| 物理行 | 一个具体版本对应的资产行，独立 ID；版本引用指向具体物理行 |
| 草稿 | `testing` 状态的物理行；制作、修改、验证都在草稿上做；一个家族同一时刻只有一个草稿 |
| 上线 | `testing → live`，旧上线版本保持不变。智能应用上线后还要开发者发布，正式入口才能打开。哪些操作要先上线见 [部署与版本.md](部署与版本.md)「草稿、上线、发布各能做什么」 |

### 积分怎么算

GoalfyMax 只按**积分**计费。跟开发者说费用、写估算、汇报花费时一律用积分，不报 token 数，也不自己拿 token 数换算积分。

| 项 | 说明 |
|---|---|
| 换算 | 1 元 = 100 积分（1 积分 = 0.01 元）；需要让使用者知道约合多少钱时按这个写元 |
| 一次执行花多少 | 四部分相加：模型调用（按所用模型的单价和用量折算）、付费工具（按次或按量）、云端沙盒（存活期间持续计费）、平台资产计费 |
| 开发时哪些花积分 | 冒泡（FA 是桩，但工具、沙盒照常真实执行，付费工具照样扣）、`full_run` 冒泡、真跑、在线预览里的操作与自动化运行，都在 GoalfyMax 上发起执行、扣开发者的积分 |
| 哪些不花 GoalfyMax 积分 | 你和开发者之间的对话本身 |

估算按 PRD「会调用：X，每次约 N 积分」写。只有单条 TPE 冒泡（`otpe_manage(action="bubble")`）的终态带 `cost_credits`（这一次冒泡的花费），按下表说。执行（路线冒泡、`full_run` 冒泡、真跑的回执与 status / wait）目前不带花费：按 PRD 估算报并标「估算」，实际值记「未知」，在交接消息和报告里写明「执行回执不带花费」，不编数字。

| 字段取值 | 怎么说 |
|---|---|
| `cost_partial=false` | 「这次花了约 N 积分」 |
| `cost_partial=true` | 「至少 N 积分，有一部分还没取到」 |
| `cost_credits=null` | 「这次没取到花费」，不填 0 |

沙盒按周期记账，单条冒泡刚结束读到的可能还没算上沙盒部分，汇总前再读一次。

执行和没跑过的步骤按这个顺序估：

1. 同类模型步骤用单条 TPE 冒泡跑过、有 `cost_credits` 的，用那次实测（路线冒泡、真跑都没有实测花费）；
2. 没跑过的，每个模型步骤按档位每次花费 × 预计调用次数，付费工具按单价 × 预计次数，相加；
3. 每个数都标「估算」并写出算法（几次 × 每次多少）。

单条 TPE 冒泡出了实测就更新同类估算。

## 常见错误

- 按「步骤」拆 FA，一个环节拆成好几个 FA 串起来。
- 把事实错误当成 Schema 不够严，持续扩充 `_output`，而没有按 [编排脚本.md](编排脚本.md)「FA 与脚本的职责边界」重划 FA、脚本和工具职责。
- FA 调用时只传 ID 不传背景，FA 读不到调用方的历史。
- 拿家族 ID 当物理行用：`get_asset` 传家族根 ID 会解析到最新 live 行；要看某个旧版本必须传那一行的物理 ID。智能应用的应用 ID 可能是短码，物理行 ID 一直是数字；需要物理行时只用 `draft_asset_id`、`business_ui_version_id` 或版本列表返回的行 ID。
- 按形态判断智能应用 ID：`business_ui_id` 是应用的对外 ID，只能原样取自平台返回（`business_ui_manage` 的 `setup` / `list`、`scaffold_bind_command`、工作区 `app.json` / `WORKSPACE.md`）。旧应用是数字串（如 `84`），新应用是 8 位小写字母数字短码（如 `k3m9x2ab`），两种都合法；`84` 与 `"84"` 是同一个应用。**禁止**因形态不同判定为不同应用或出错、新建应用或重新 `setup`；**禁止**把短码换算成数字、把数字补成短码、改大小写、补零或去引号。需要版本行时只用 `draft_asset_id` 或版本列表返回的物理行 ID，不用应用 ID 代替，也不用版本行 ID 代替应用 ID。
- 把文件读写、命令执行、邮件发送当成工具缺口去建工具集；编排型 TPE 自带它们。
- 自己编 `business_id`，或在脚本里找 `ctx.business_id`（没有这个字段；要跨节点、跨重试不变的键用业务键，见 [编排脚本.md](编排脚本.md)「ctx 有哪些字段」）。
- 保存路线只传改动的那条，或 `tpe_ids` 漏了编排引用的 TPE、写成版本行 ID：其他路线被覆盖或保存被拒。
- 节点脚本调的工具挂在别处而不在该节点 TPE 上，运行时报工具名无效（`invalid tool call name`）。
- 给开发者转述时照搬 MCP 里的「定版」等旧词；按本文「术语表」改说。
