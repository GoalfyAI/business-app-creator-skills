# 部署与版本

## 适用场景

部署应用、上线场景包、定版应用、修订已上线版本、回滚、下线、删除、处理定版或版本闸门报错、过结单门时读。

## 规则

### 三道门

| 门 | 什么时候判 | 依据 | 不过怎么办 |
|---|---|---|---|
| Skill 版本 | `task_manager(action="create")` 建工单时 | 已安装 Skill 的 `[skill-version]` 标记 | 按 [报错对照.md](报错对照.md)「工单闸门」升级 Skill |
| 脚手架版本 | `download_template` 核版本、`deploy` 读上传包 | 包内 `scaffold-release.json` 与环境必须线 / 建议线 | 按 [脚手架与预置件.md](脚手架与预置件.md) 迁移后重新打包 |
| 结单 | `task_manager(action="complete")` | 每条路线在当前合同下最近一次到终态的运行（路线冒泡或真跑）通过，或有 `route_verification_waived` 检查点 | 补跑或问过开发者后写豁免 |

### 应用生命周期

```text
setup（建身份、挂模板、绑工作集） → update（授权选择、自动化）
  → ship（缺包时给上传地址 → PUT → 带 bundle_key 再 ship → 带 deployment_id 续等）→ success（在线预览可用）
  → finalize（定版） → resolve 核对上线版本 → 开发者在发布管理页发布到目录
```

- 部署证据：`deployment_id`、`source_sha256`、`deployed_scaffold_version` 一起记；失败或进行中的部署只记本次尝试。
- 定版前提：本地 `npm run verify:release` 全绿、最近一次部署 `success`、开发者说了「可以上线」。
- 定版时场景包引用钉到当时的具体版本，把版本号记进工单和交付报告。
- 上线只影响开发者自测；使用者看到的是发布管理页发布过的版本。
- 带 `business_ui_id` 的真跑只认已上线版本：首版先 finalize 再真跑；已上线应用出了新草稿，真跑仍按上线版本解析场景包，验不到草稿的挂载变化。

### 部署状态与入口

部署成功只说明容器起来了，不等于有了可交给人的入口。给开发者汇报、写方案页和交付报告时，部署状态和入口分两句写：

| 阶段 | 部署状态怎么写 | 真实入口 |
|---|---|---|
| 部署后、定版前 | `ship` 到 `success`，附 `deployment_id` | 开发者中心右侧「在线预览」（带真实身份、数据集和路线） |
| 定版后 | 已上线版本号 | 开发者自测：GoalfyMax → 我的资产 → 智能应用 → 打开（正式入口 `/business-ui/<家族 ID>`，不需要发布） |
| 发布到目录后 | 已发布 | 使用者从目录打开 |

- `get`、`resolve` 返回的 `entry_url` 是开发者容器地址：直接打开只会进入 mock 模式，没有宿主注入的身份、数据集和接口代理，看到的是假数据。它只用来核对入口有没有写进版本。
- **禁止**把 `entry_url` 或其他容器地址当成应用地址发给开发者或使用者，也不要自己打开它来判断验收结果。
- `resolve` 只认上线版本：定版前它报「还没有上线版本（只有草稿）」是正常结果，不说明缺入口。草稿验收走开发者中心的在线预览，不要记成平台阻塞。

### 哪些用草稿就行，哪些要先上线

三个词各管一层：**草稿**是正在改的版本；**上线**（`finalize`，定版）只把这一版变成开发者自己的正式自测版，使用者看不到；**发布**是开发者在发布管理页把某个上线版本放进目录，使用者才能打开。

| 要做的事 | 草稿部署成功即可 | 要先上线 | 还要发布 |
|---|---|---|---|
| 开发者中心「在线预览」验收（真实身份、数据集、路线） | ✓ | | |
| 路线冒泡、不带 `business_ui_id` 的真跑 | ✓ | | |
| 带 `business_ui_id` 的真跑（`BUSINESS_UI_NOT_ONLINE`） | | ✓ | |
| `resolve` 反读、正式入口打开自测（含原生定时任务）、发布管理页预览 | | ✓ | |
| 使用者从目录打开（`BUSINESS_UI_NOT_RELEASED`） | | ✓ | ✓ |

- 在线预览只看两件事：是你本人的应用，当前草稿部署成功（部署记录与草稿行的地址、源码摘要一致）。不需要上线，也不为打开它去 finalize。
- 需要上线的事（如带 `business_ui_id` 真跑）可以先定版自测版再做：上线不是发布，使用者看不到；按 G6 第 3 步说清后执行。

### 场景包上线

- `finalize_asset_version_online(asset_type="scenario_pack", draft_asset_id=<草稿行>, change_note=…)` 把草稿晋级 live；旧上线版本不变，已在用旧版的项目不受影响。
- 平台闸门：FA、工具集、TPE 有运行时身份；工具组有连接信息；Skill 文件已就绪；依赖里的 `latest` 引用钉到当刻版本（开发者显式选择跟随最新的除外，要让他知情）。
- 智能应用挂着的本人场景包草稿不用单独上线：部署预览直接跑草稿，`business_ui_manage(action="finalize")` 定版应用时先校验、再把它一起定版上线。单独上线只用于不经应用、直接给别人用的场景包。
- 挂载引用钉了版本号时，只有该版本还没上线才会用本人草稿；已上线应用改场景包，要把应用草稿的 `scenario_pack_version` 换成场景包草稿的版本号再部署，定版时这份草稿一起上线。
- 上线后反读版本；**禁止**因为草稿验证通过就说已上线。

### 修订、回滚、作废

| 动作 | 工具 | 规则 |
|---|---|---|
| 看家族 | `list_asset_versions` | 任何版本操作前先看清现役 live 和有没有搁浅草稿 |
| 取草稿 | `ensure_editable_asset_draft`，场景包 `scene_package_manage(action="ensure_draft")`，应用 `business_ui_manage(action="ensure_draft")` | 对 live 行直接 update 会自动派生草稿，之后一律用返回的 `draft_asset_id`；`reused: true` 表示沿用已有草稿 |
| 比较 | `compare_asset_versions(base_version_id, target_version_id)` | 比配置，不比效果；结论写进交付报告 |
| 作废草稿 | `abandon_asset_version_draft` | 只能作废未上线且未被引用的草稿；先 `get_asset_usage_impact` 看影响面并告诉开发者 |
| 回滚 | `rollback_asset_version(version_id)` | 用历史版本内容克隆出新草稿，不改历史行；反读挂载与源码包，走 G6 验收再定版；**必须**开发者确认 |

- **引用不自动跟随**：TPE 上线新版本后，路线 `workflow_ref` 与挂载关系仍指旧行。`otpe_manage(update)` 带着场景包草稿时会自动采用新版本，响应 `message` 开头有【自动采用】提示，看到就反读该草稿；定稿后 `output.mounted_by_stale` 列出仍钉旧版的场景包，逐个 `attach` 或记下不跟进的理由。
- 派生出的新草稿行不继承部署地址，上线前在新行重新部署并反读。
- 改挂载（场景包或模板版本）属于契约变更，先按 [../tasks/修订.md](../tasks/修订.md) 评估影响；每次修订都走完 G6 再定版。

### 下线与删除

- **下线** `business_ui_manage(action="offline", business_ui_id)`：拆掉全部容器，用户库、源码包、版本记录保留，可逆。**必须**开发者确认，确认时说清用户会失去入口但数据不丢。已发布到目录的先在发布管理页取消发布（否则 `BUSINESS_UI_RELEASED_CANNOT_OFFLINE`）。重新上线 = 对当前版本重新部署后定版。
- **删除** `business_ui_manage(action="delete", confirm_permanent_delete=true)`：永久删除整个家族的全部版本、实例、库和源码包，不可恢复，传任一版本行也是删整个家族。**必须**开发者明确授权；有在线或已发布版本的，逐字复述应用名让开发者确认。进度只用 `deletion_status` 查；`cleanup_failed` 且 `retrying=true` 是删除中，不报失败；终态 `failed` 要开发者确认下游修好后带 `retry_failed=true` 重发。
- 停用在用的应用用下线，不用删除。

## 常见错误

- 按传进去的 live 行 ID 反读，以为修改没生效；应按 `draft_asset_id` 反读。
- 版本工具面传 `asset_type="scenario_package"`，被拒；这里要 `scenario_pack`。
- 定版后不 `resolve`，没发现定版未生效。
- 把部署返回或 `resolve` 里的 `entry_url` 当应用地址交付，开发者打开后只看到 mock 假数据。
- 上线了但没发布，使用者打不开（`BUSINESS_UI_NOT_RELEASED`）。
- 用 `delete` 轮询删除进度。
- 被版本闸门拒绝后绕过去直接改状态字段。
