# 部署与版本

## 适用场景

部署应用、在开发工作集里真跑、上线与发布应用、修订已上线版本、回滚、下线、删除、过结单门时读。部署、上线、发布三个词的含义见 [../SKILL.md](../SKILL.md)「角色与用词」；什么时候问开发者、什么时候做，见各段文件。报错码怎么处置见 [报错对照.md](报错对照.md)。路线与 TPE 怎么挂到应用版本上见 [业务路线.md](业务路线.md)「路线挂在应用版本上」。

## 规则

### 三道门

| 门 | 什么时候判 | 依据 | 不过怎么办 |
|---|---|---|---|
| Skill 版本 | `task_manager(action="create")` 建工单时 | 已安装 Skill 的 `[skill-version]` 标记 | 按 [报错对照.md](报错对照.md)「工单闸门」升级 Skill |
| 脚手架版本 | `download_template` 核版本、`deploy` 读上传包 | 包内 `scaffold-release.json` 与平台必须线 / 建议线 | 按 [脚手架与预置件.md](脚手架与预置件.md) 迁移后重新打包 |
| 结单 | `task_manager(action="complete")` | 每条路线在当前合同下最近一次到终态的执行通过（路线冒泡，或 `workspace` 真跑里该路线的执行 `succeeded`），或有这条路线的 `route_verification_waived` 检查点 | 补跑，或问过开发者后写豁免 |

结单门的取证：冒泡从冒泡回执取；真跑从按 `business_id` 调的 `status` / `wait` 回执里的 `route_runs` 取（每条路线按 `business_ui_id` + `business_ui_version_id` + `orchestration_id` 核对，执行号记作这条路线的 `run_id`）。`run` 的回执本身不算证据，真跑到终态后要用 `wait` 或 `status` 读到一次终态。

结单门的豁免：最近一次失败或没法验证时，先问开发者是否接受，接受后每条路线写一条：

```text
task_manager(action="insert", entry_type="checkpoint", metadata={"evidence_type": "route_verification_waived", "business_ui_id": …, "business_ui_version_id": <冒泡回执，或真跑 status / wait 回执里的版本行>, "orchestration_id": …, "reason": "<至少 5 个字>", "run_id": <失败那次的执行号 BIZ-…；没跑过就不带>})
```

豁免只记下这条路线没验证及原因，不算通过。`complete` 被拒时按返回里逐条给的出口补证据或写豁免（码义见 [报错对照.md](报错对照.md)「版本与结单」），在同一张工单上处理。`complete` 成功后返回的 `delivery_note` 原样补进上线结果。

### 应用生命周期

```text
create（① 确认 PRD 后建应用占位，拿 business_ui_id）
  → setup（挂模板、绑工作集）→ update（挂路线与 tpe_ids、授权选择、自动化）
  → ship（部署）→ success（在线预览可打开；workspace 真跑跑这一版）
  → finalize（上线） → resolve 反读上线版本
  → 开发者在发布管理页决定是否发布（发布后开发者本人和已安装的使用者用上这一版）
```

`create` 与 `setup` 见 [数据模板.md](数据模板.md)「建应用身份与挂模板」；挂路线与 `tpe_ids` 见 [业务路线.md](业务路线.md)「路线挂在应用版本上」。

- 上线的平台前提：应用版本已挂编排与 `tpe_ids`；本地 `npm run verify:release` 全绿；同一源码的部署 `success`。没部署成功过的草稿上不了线。
- 上线时把应用版本上挂的编排（各路线 `orchestration_id`）与 `tpe_ids`（TPE 资源组 ID 加版本，上线后读到的是钉死的版本号）记进工单和上线结果。
- 上线、发布、下线、删除只有属主能做；编辑协作者用 `request_finalize` 提请，见 [多人协作.md](多人协作.md)「提请属主上线」。

### 部署

部署 = 把当前草稿 `ship` 到开发者的在线预览。打包与脚手架闸门见 [脚手架与预置件.md](脚手架与预置件.md)「预部署与证据」。

0. 先确认应用草稿已挂编排与 `tpe_ids`。只建了占位、还没挂编排的草稿不能上传源码包和部署（上传、部署返回 400 文本 `business UI must mount a runnable scenario package…`，其他路径返回码 `BUSINESS_UI_NO_SCENARIO_PACK`；文字是历史原因，意思是「没挂编排」），先在 ③ 用 `business_ui_manage(action="update", business_ui_id, workflow_orchestration, tpe_ids)` 挂上。
1. `business_ui_bundle(action="download_template")` 核脚手架门槛，需要升级时先完成迁移与验证。
2. 在应用根运行 `npm run verify:release`，全部检查通过后得到 `.pack/business-ui-bundle.tar.gz`，按这个包算 `source_sha256` 与 `size_bytes`。部署包只由 `verify:release` 产出，它包含部署前的检查。
3. `business_ui_bundle(action="ship", task_id, business_ui_id, source_sha256, file_name="business-ui-bundle.tar.gz", size_bytes)`：`file_name` 只写文件名；`business_ui_id` 是上线行、要自动派生草稿时同时带 `change_note`，写这次改了什么。
   - 返回 `status=upload_required`：按 `upload_url` 与 `headers` PUT 源码包原字节，原参数加 `bundle_key` 再调；
   - 返回未终态：原参数加原 `deployment_id` 续调（服务端每次最多等约 45 秒再返回），直到终态；带着 `deployment_id` 续调才不会重新起容器；
   - 到 `success` 为止。`steps` 标明每步 done / skipped / resumed。明确失败且原因不在源码包时，再用 `prepare_upload` / `complete_upload` / `deploy` / `status` 单步排查。
4. `business_ui_manage(action="get")` 核对部署已写进当前草稿。

- **部署证据**：`deployment_id`、`source_sha256`、`deployed_scaffold_version` 一起记；失败或进行中的部署只记本次尝试，当前线上版本沿用它已成功绑定的部署事实。上线后反读目标应用版本当前绑定的部署，确认是验过的同一份，写入上线结果和 `docs/history/`；回滚时重新核对恢复的绑定与脚手架版本。返回带 `scaffold_upgrade_notice` 时按 [脚手架与预置件.md](脚手架与预置件.md)「预部署与证据」记。
- **派生草稿要重新部署**：派生出的新草稿行不继承部署地址，在新行重新部署并反读。
- **改过编排要重新部署**：改了路线或 `tpe_ids` 后重新部署一次再发布，否则发布被拒（`BUSINESS_UI_CONTRACT_OUTDATED`）。
- **`entry_url`**：`get`、`resolve` 返回的 `entry_url` 是开发者容器地址，只用于核对平台绑定与诊断，不打开、不写进任何给人看的东西、不发给任何人。生产构建直开返回 `HOST_REQUIRED`，本地开发构建直开只进 Mock，都不能证明真实身份、数据集或路线。

### 真跑

制作和验收的真跑都在开发工作集里跑，只要求应用已部署成功，不要求上线。

```text
manage_goalfymax_project(action="run", task_id, idempotency_key,
  business_ui_id=<应用 ID，即 WORKSPACE.md 的 business_ui_id 原值>, business_ui_data_space="workspace",
  submit_data={"orchestration_id": …, "form_id": <入口表单标识>, "formdata": {<入口表单字段>}})
```

- **`business_ui_id`**：应用 ID 原值（8 位短码或存量纯数字），不是版本行 ID。
- **`business_ui_data_space`**：制作和验收传 `workspace`：跑已部署的草稿，读写开发工作集，和在线预览是同一份库，测试数据不进使用者实例。`instance` 跑已发布版本、读写开发者本人的正式实例，要应用已上线**且已发布**，制作和验收不用它。
- **不传** `scenario_package_ids`；**不自己生成** `business_id`。
- **`submit_data`**：只写 `orchestration_id`（应用版本上要启动的那条路线）、`form_id`（这条路线的入口表单标识）与 `formdata`（入口表单字段）。
- **回执**：给 `business_id`（服务端生成的执行号，`BIZ-` 开头）。之后 `status`、`wait`、`reply`、`stop` 都按这个 `business_id`；没有 `send`，执行里没有对话。
- **跑的是哪一版**：开发工作集真跑（和冒泡）优先用你自己建的、版本号最高且部署成功的草稿；你没有这样的草稿时，属主用这个应用版本号最高的已部署版本。只改挂载（编排、`tpe_ids`、模板版本）没重新部署的草稿也会被选中：它沿用上一版的容器，执行按这个草稿上的编排跑；上一版容器已不在线或源码包重传过没部署时报 `BUSINESS_UI_PREVIEW_HOST_UNAVAILABLE`，重新部署这一版。`status` / `wait` 回执的 `business_ui_version_id` 是这次执行用的版本行，跑完先核对它是不是你要验证的那一版；改了页面或后端代码的，要重新部署才会生效；改过挂载的，上线、发布前仍要重新部署（见 [报错对照.md](报错对照.md) `BUSINESS_UI_CONTRACT_OUTDATED`）。
- **等结果**：`manage_goalfymax_project(action="wait", business_id)` 等到终态；每次最多等 `timeout` 秒（0–45，缺省 45），没到终态就再调（`wait` 不接受 `wait_seconds`）。中途表单或审阅用 `reply`：按回执里 `next_action.template` 填，审阅动作放 `formdata.action_key`，`orchestration_id` 由 MCP 补；卡在等待使用者而没人答，是正常挂起。不需要再跑的执行用 `stop` 止损。
- **看结果**：以这次执行的终态为准；`succeeded` 表示这条路线真跑通过，结单门会把它记为这条路线的证据。`get_project_execution_logs(action="workflow_trace", project_id, business_id)`（`project_id` 取 `run` 回执里的）看每步，带上 `business_id` 只看这一次执行（一个隐藏项目里有多次执行）。
- **补 TPE 运行证据**：`otpe_manage(action="verify", task_id, tpe_id, project_id=<run 回执里的 project_id>)`。真跑的执行号不能作 `run_id`（`run_id` 只认冒泡发起的执行，真跑的会报找不到）；`project_id` 取的是隐藏项目里这条 TPE 最近一次运行，所以真跑到终态后马上 verify，中间不再发起别的冒泡或真跑，并核对返回里的 `run_id`。见 [编排脚本.md](编排脚本.md)「冒泡与真跑能证明什么」。

**写到哪份库**：在线预览和 `workspace` 真跑写开发工作集（同一份，在线预览里看得到）；`instance` 真跑写开发者本人的正式实例，要应用已上线并发布，制作和验收不用它；自动化和使用者的执行写各自的实例。

### 草稿、上线、发布各能做什么

| 要做的事 | 草稿部署成功即可 | 要先上线 | 还要发布 |
|---|---|---|---|
| 开发者在工作台「在线预览」里看（真实身份、开发工作集、路线） | ✓ | | |
| 路线冒泡、`workspace` 真跑 | ✓ | | |
| 保存自动化声明、`business_ui_automation` 的 `validate` / `bubble` | ✓ | | |
| `business_ui_automation(run_once)`、`resolve` 反读、发布管理页预览 | | ✓ | |
| `instance` 真跑（读写正式实例） | | ✓ | ✓ |
| 开发者本人从正式入口打开、在「自动化」面板开真实到点规则 | | ✓ | ✓ |
| 使用者从目录或分享打开 | | ✓ | ✓ |

- **在线预览**只要求两件事：是开发者本人的应用或他协作的应用；当前草稿部署成功（部署记录与草稿行的地址、源码摘要一致）。协作者预览的限制见 [多人协作.md](多人协作.md)「预览、费用与限制」。
- **部署状态和入口分两句写**：部署成功只说明容器起来了。部署后、上线前，入口是工作台「在线预览」；上线后、发布前，正式入口仍打不开（开发者本人也一样），想看仍用「在线预览」；发布后，开发者本人和使用者从 GoalfyMax 打开这个应用，或从目录、分享打开。
- 表里要发布的几项不属于制作和验收；上线结果把它们写进开发者「你可以做的事」，写法见 [../design/验收报告与上线结果.md](../design/验收报告与上线结果.md)「上线结果」。

### 上线与发布

1. **前提**：应用草稿已挂编排与 `tpe_ids`（没挂编排上传、部署被拒 `BUSINESS_UI_NO_SCENARIO_PACK`）；改过编排后已重新部署；部署 `success`。
2. **上线**：`business_ui_manage(action="finalize", draft_asset_id=…, task_id)`。家族里可能同时有多份草稿（有协作者时），所以显式传要上线的那份 `draft_asset_id`：只有一份可上线草稿时，直接用 ④ 验过的那份；有多份（协作者也建了草稿）时，用 `business_ui_manage(action="get")` 看草稿、创建人和变更说明，再问开发者上哪一份；平台不替你挑。
3. **反读**：`business_ui_manage(action="resolve")` 反读上线版本，核对它挂的编排（每条路线的 `orchestration_id`）与 `tpe_ids` 是验过的那一份，应用版本号与 `tpe_ids` 记进工单；`entry_url` 非空说明入口已写进版本。resolve 报没有上线版本说明上线没生效，照实说没上线。`resolve` 只认上线版本，上线前报「还没有上线版本（只有草稿）」是正常结果。
4. **发布**由开发者在发布管理页决定，平台规则：
   - 发布要求应用版本挂了编排，否则被拒（`BUSINESS_UI_INVALID_SCENARIO_PACK_REFS`）。
   - 改过编排后没重新部署，部署记录对着旧契约，发布被拒（`BUSINESS_UI_CONTRACT_OUTDATED`）：重新部署再发布。
   - 有运行中的执行时发布失败并返回数量（发布保护，`BUSINESS_UI_EXECUTIONS_RUNNING`）：等执行结束，或由开发者决定取消。
   - 部署的源码包与挂载对不上（`BUSINESS_UI_MOUNT_EXECUTOR_MISMATCH`）：挂好编排后重新部署再上线。
   - 被拒时把原文告诉开发者，**禁止**为了能发布改动 `goalfy-app.json` 的 `executor` 或改成别的写法。

码义与处置见 [报错对照.md](报错对照.md)「部署与预览」「执行」。

### 修订、回滚、作废

| 动作 | 工具 | 规则 |
|---|---|---|
| 看家族 | `list_asset_versions` | 任何版本操作前先看清现役上线版本和有没有搁浅草稿。智能应用以外的资产只有资产属主能查；协作者看属主名下资产用 `get_asset` 和 `ensure_editable_asset_draft` 的返回，见 [多人协作.md](多人协作.md) |
| 取草稿 | `ensure_editable_asset_draft`，应用 `business_ui_manage(action="ensure_draft")` | 对上线行直接 update 会自动派生草稿，之后一律用返回的 `draft_asset_id`；`reused: true` 表示沿用已有草稿。应用建草稿（含 update、对已有应用的 `setup`、`ship` 自动派生）带 `change_note` 写这次改了什么，① 建应用占位不用带；协作者只用自己创建的草稿，见 [多人协作.md](多人协作.md) |
| 比较 | `compare_asset_versions(base_version_id, target_version_id)` | 比配置，不比效果；结论写进上线结果 |
| 作废草稿 | `abandon_asset_version_draft` | 只能作废未上线且未被引用的草稿；先 `get_asset_usage_impact` 看影响面并告诉开发者 |
| 回滚 | `rollback_asset_version(version_id)` | 用历史版本内容克隆出新草稿，不改历史行；反读挂载（编排、`tpe_ids`、模板）与源码包，部署后走 ④ 验收再上线；每一步开发者确认 |

- **引用不自动跟随**：`tpe_ids` 钉了具体版本号的（上线时 `latest` 也会钉死），TPE 上线新版本后应用版本仍指旧版本。要用新版本时，把 `tpe_ids` 换成新的版本号，带全部路线和全部 TPE 重新 `business_ui_manage(action="update")`（整体替换），再重新部署。
- 制作中建、改 TPE 不用传 `publish_mode`：缺省 `staged`，新版本先暂存，`otpe_manage(action="online")` 只启用这条 TPE，按 [编排脚本.md](编排脚本.md)「建、校验和上线 TPE」照常做；挂到应用版本靠 `business_ui_manage(action="update", tpe_ids)`，TPE 上线不会改应用版本。
- 改挂载（路线、TPE 版本或模板版本）属于契约变更，先按 [../tasks/修订.md](../tasks/修订.md) 评估影响。

### 下线与删除

每一步都要开发者确认（[../SKILL.md](../SKILL.md)「红线」）。

- **下线** `business_ui_manage(action="offline", business_ui_id)`：拆掉全部容器，使用者的库、源码包、版本记录保留，可逆。确认时说清使用者会失去入口但数据不丢。已发布到目录的先由开发者在发布管理页取消发布（否则 `BUSINESS_UI_RELEASED_CANNOT_OFFLINE`）。重新上线 = 对当前版本重新部署后再上线。
- **删除** `business_ui_manage(action="delete", confirm_permanent_delete=true)`：把整个家族（全部版本、实例、库和源码包）移入回收站，传任一版本行也是删整个家族；在回收站里可恢复，彻底删除由开发者自己在 GoalfyHub 回收站操作。要开发者明确授权；有在线或已发布版本的，逐字复述应用名让开发者确认。进度只用 `deletion_status` 查；`cleanup_failed` 且 `retrying=true` 是删除中，不报失败；终态 `failed` 要开发者确认下游修好后带 `retry_failed=true` 重发。
- 停用在用的应用用下线，不用删除。

## 常见错误

- 按传进去的上线行 ID 反读，以为修改没生效；应按 `draft_asset_id` 反读。
- 上线后不 `resolve`，没发现上线未生效。
- 把 `entry_url` 当应用地址交付，开发者打开后只看到 Mock 假数据。
- 只建了应用占位、没挂编排就打包部署，被 `BUSINESS_UI_NO_SCENARIO_PACK` 拒。
- `tpe_ids` 写成版本行 ID。
- 改了编排没重新部署就发布，被 `BUSINESS_UI_CONTRACT_OUTDATED` 拒。
- 真跑自己编 `business_id`，或用 `send` 跟执行对话。
- 为了真跑或打开在线预览去 finalize；它们只要部署成功。
- 用 `delete` 轮询删除进度。
- 被版本闸门拒绝后绕过去直接改状态字段。
