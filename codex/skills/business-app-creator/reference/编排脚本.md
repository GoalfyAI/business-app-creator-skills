# 编排脚本

## 适用场景

建 FA、写或改编排型 TPE 脚本、定 `_output` 与失败出口、写事件契约、建与校验 TPE、做读写应用库的反读自查、判断冒泡结果能证明什么时读。原语签名和字段以诊断主题和 `otpe_manage` 的当前 Schema 为准。

## 规则

### 写脚本前先读

- 写第一条编排脚本前读 `get_diagnosis_doc(topic="otpe_authoring")`，再读 `otpe_single`；路线要并行、扇出、中途表单或节点级接管时再读 `otpe_multi`。
- 从下面「三种模板」挑一种整段复制，只改业务词，不从零写：入口函数名、`emit_business_event` 的 `event_type`（`stage_started` / `stage_result` / `stage_failed`）和 `event_key` 都保持字符串字面量；事件契约照「对应的事件契约」抄，只改 `event_key` 和 stage 名。
- 路线要读写应用库的，先按 [数据模板.md](数据模板.md)「编排脚本怎么读写应用库」定好谁读、谁写、谁建行。

### 脚本骨架

- 入口 `async def run(input, ctx)`；返回值按 `output_schema` 逐字段组装，不把工具或 FA 的返回整包转交。
- 每个 `tool()` 带 `_rationale`（为什么调）与 `_output`（按工具真实返回结构声明，只声明脚本要读的字段）。
- 工具返回的是一整段文本（网页、文件原文、长列表文本，如 `open_url`）时，`_output` 只声明一个必填 string 字段：`{"type": "object", "required": ["text"], "properties": {"text": {"type": "string"}}}`，平台直接把原文包进去，不经模型。声明成多个字段会让模型从原文里抽取，原文一长就超时（`_output extraction` 45 秒）；要结构化字段就把原文交给后续 FA 或在脚本里解析。
- 脚本里用到的每个工具和 FA 都要在预加载工具集清单里声明，且工具集已上线。FA 用反读到的 `mr_name`。
- 参数由谁填：事件契约、`_output`、`_rationale` 在模板里已有位置，只改业务词；`tpe_id`、`scene_package_id`、`mr_name` 取上一步工具的返回值并记进工单，不手抄。路线的入口、节点、交付映射由 `assemble` 生成（见 [业务路线.md](业务路线.md)「assemble 怎么用」）。
- 一次处理的条数按 PRD 的用量上限设计（分批、分片、超出时怎么提示），不在脚本里写死一个比用量小的上限。
- 技术失败让异常冒泡；业务没做成按下面「失败出口怎么写」返回真实状态，返回值里的字段和路径都是真实的。
- 有外部副作用的动作（发信、写外部系统、付款）按 `ctx.dry_run` 判断，冒泡时跳过。
- 写库按「会被再执行一次」设计，写法按 [数据模板.md](数据模板.md)「谁建行、谁写列」选。
- 脚本来源：短脚本传 `script`；长脚本或多轮修改用 `script_url`；只改一个片段且 Schema 支持时用 `script_patch`。只改输入输出或依赖时不重传脚本。

### FA 与脚本的职责边界

| 责任方 | 只负责 | 不负责 |
|---|---|---|
| FastAgent | 一个可独立复用的语义责任；在内部按结果自适应判断和调用工具 | 流程分发、跨环节汇合、固定收口 |
| 编排脚本 | 确定性准备、分发、汇合、幂等写入和固定收口 | 判断内容真假、用新增字段替代语义判断 |

`_output` 是脚本与 FA 之间的**控制面最小合同**，不是内容质量检查器。按以下顺序收口：

1. 默认软门禁是顶层字段不超过 8 个、对象嵌套不超过 2 层；超过时拆开语义责任，或把内容改成稳定载体引用，不继续扩 Schema。
2. 内容型大结果（长报告、完整证据集、批量明细）写入数据集或 `ctx.process_dir` 文件等稳定载体；`_output` 只返回 `status`、`note`、引用和脚本真正需要的计数。一篇草稿、几条诊断这类短内容照常以字段返回；节点最终返回里给使用者看的列表、正文、结论仍以业务字段出现，要交付的文件才写 `ctx.output_dir` 并声明交付（见「文件产物」）。
3. Schema 只校验形状，不能证明内容真实。输出分成事实区与推断区：事实保留来源和原文，推断明确标记且不得回填为事实；首版只承诺来源、原文和失败原因可追溯。
4. 同类事实错误、引用错误或无产物连续两轮出现时，停止加字段和原样重试，重判 FA、脚本与工具的职责（要改施工单的回 ②）；仍保留 `completed`、`partial`、`blocked` 等合法出口。

### 建 FA

- 每个模型步骤一个 `create_fast_agent(name, description, prompt_content, model_name, model_selection_mode="required", …)`，一个 FA 只承担一个语义责任。`model_name` 用 PRD 定的档位对应的模型，`max_turns` 按预估步数给；档位对应的模型名单、轮次的取值方法和平台下限见 [平台对象速查.md](平台对象速查.md)「模型档位」，这里不另写数字。
- `input_schema` 顶层是对象，每个字段有类型和足够详细的描述，不留空对象或一两个字的描述；大段素材传路径不传正文，避免超出上下文。FA 没有记忆，必要背景都随参数传入。
- 提示词写清输入字段、输出对象每个字段的含义和非成功状态；输出按「失败出口怎么写」给部分成功留出口。
- 由脚本查出一批记录交给 FA 判断的：FA 的 `input_schema` 只收文件路径（`records_path`，或分片清单 `chunks_manifest_path`）和日期范围这类控制字段；输出按 `record_id` 逐条给标签和理由，总数、分类数由脚本统计。文件怎么写见「文件产物」。
- **要按情况查应用库的 FA**（按客户、任务或上一步结果去应用库挑素材、记录或上下文），建 FA 时就挂应用库只读工具，以这一步实际要不要按情况查库为准——施工单漏写的也挂，并回 ② 把施工单补上：先 `list_assets(asset_type="tool_group", keyword="query_business_app_dataset")` 找到平台工具组，把它的 ID 填进 `tool_group_ids`；提示词写明只用 `mode="reader"`、先 `tables` / `inspect` 再查、只取本步需要的切面，写库交给脚本。挂不上时按 [报错对照.md](报错对照.md) 排查，取数方式保持由 FA 自己查。
- 建完用 `get_asset(asset_type="fast_agent")` 反读：`mr_name`（形如 `PRIVATE_FASTAGENT_<name>_<物理 ID>`，只能从 `create_fast_agent` / `clone_asset` / `get_asset` 的返回值读到，克隆副本的调用名一定和源不同；脚本里调用一律用它）、`model_selection_mode` 与 `model_name`；挂了应用库工具的，看返回的 `actual_tool_group_ids`（平台实际展开的工具组）含 `query_business_app_dataset` 所在工具组，`configured_tool_group_ids` 只是配置值，不作证据。

### 失败出口怎么写

| PRD「做不成怎么办」 | 脚本写法 |
|---|---|
| 停下来告诉使用者 | 不捕获，让异常冒泡；平台按失败类别归因 |
| 标记状态继续 | `try/except` 只包那一次 `tool()`；读异常的 `recoverable` 决定写 `optional_source_retry_later` 还是 `optional_source_unavailable`；输出带 `status` 与 `warnings` |
| 重试一次 | 同上，except 里再调一次；工具内部已重试的（异常带 `attempts`）不再叠加 |
| 业务条件不满足（证据不足、缺前置数据） | 发 `stage_failed` 或以明确的 `status` 正常返回，不抛异常 |

**异常上带的事实**：`exc.failure_class`（`tool_error` / `fa_error` / `shell_exit` / `contract_error`）、`exc.recoverable`（`True` 是限流、超时、冷启动，可换时机重发；`False` 是鉴权、参数、余额，别再试；`None` 判不出）、`exc.attempts`（工具层已试次数）。`try` 只包可选的那一次调用：整段逻辑包进 `try` 会把脚本自己的 `KeyError` / `TypeError` 当成可选步骤失败吞掉。

**FA 的输出要给部分成功留出口**：每次 `tool(FA, _output=…)` 都声明 `status`，枚举至少含 `completed`（全部做完、数据真实）、`partial`（做了一部分，未做的不补不编）、`blocked`（一条没做成，数据字段留空），再配一个 `note` 写做到哪、还差什么、为什么停；缺的是使用者补得上的输入时加 `needs_input` 作为 `blocked` 的细分。读应用库这类只读查询以 `found` 布尔作出口即可。只允许成功态时模型会编造数据去满足 schema，收得越紧越倾向编造。**门禁先裁业务状态**：上游 FA 返回非成功状态（如 `needs_input`、`blocked`）时，脚本不进写库、不进下游，也不原样重试。

**上下文预算**：FA 报 `FA_CONTEXT_BUDGET_EXCEEDED` 时调高轮次没用，要减少单次传入：大段素材传路径、一次处理一个对象。报 `FA_STEP_BUDGET_EXCEEDED` 先看 `partial` 出口有没有写好，再按预估步数调轮次。

### 事件契约

- 只有需要业务路线可观察性、应用状态、表单握手或交付审阅时才声明；声明了就进 Business Runtime 语义，正式运行必须经路线（单条 TPE 也建单节点路线）。
- 硬门：首个业务动作前发 `stage_started`；每个正常 `return` 前发 `stage_result`；可解释的业务失败发 `stage_failed`。契约至少两条：`stage_started` + `stage_result`。`artifact_ready`、`delivery_ready` 由平台自动发，脚本不声明也不调用。
- `payload_schema.required` 必须含平台字段：`stage_started` 要 `stage_key`、`stage_name`；`stage_result` 要 `stage_key`；`stage_failed` 要 `stage_key`、`error_code`、`message`；`attention_required` 要 `level`、`title`、`message`。`additionalProperties` 必须为 `false`。
- 载荷不放内部 ID、原始工具返回、提示词或未脱敏错误。
- `stage_name` 就是使用者在应用顶部执行状态条上看到的那句话：写成「正在<动作><对象>」，如「正在核验商户资料」「正在生成跟进话术」，让人看得出在做什么。
- 一条 TPE 里有两个以上使用者能分辨的业务步骤（如先核验资料、再生成话术）时，每个步骤开始前各发一次 `stage_started`，各用自己的 `event_key`、`stage_key` 并各自声明契约；同一步骤内部的工具调用不再发，也不为进度条声明 `stage_progress`。
- 契约随 `otpe_manage(action="create"|"update", business_event_contracts=[…])` 一起写，写后 `get_asset(asset_type="tpe")` 反读。

### 文件产物

- 要交付的文件写进 `ctx.output_dir`，在 `output_schema` 声明为 `format: workspace-file-path` 并返回真实路径，路线的交付映射也要引用它；入口素材、上游产物要作为本次附件时先复制进 `ctx.output_dir`。
- `ctx.input_dir` 用于输入素材，`ctx.process_dir` 用于过程文件；本次新生成且要返回的文件（包括诊断附件）写进 `ctx.output_dir`。过程文件写入成功、路径存在，都不等于它已成为可信输出。
- 节点输出的来源校验接受 `ctx.output_dir` 下的路径、输入文件字段带入的路径，以及工具以裸路径或完整 JSON 返回的路径。`file` 工具的文字回执 `File written successfully: <path>` 不会被解析为可信来源；把 `ctx.process_dir` 文件仅凭该回执返回，会报 `WORKSPACE_PATH_UNTRUSTED`。将实际文件写入或复制到 `ctx.output_dir` 后再返回，不能只改路径字符串。节点来源校验通过后，最终交付仍须满足上一条的目录与映射要求。
- 要给使用者看的列表、正文、结论以业务字段出现在返回值里，不只落文件。
- 要交给 FA 或工具读取的过程文件按行或按文件分块：一条记录一行，或「简短清单 + 分片文件」。单次工具返回上限约 10000 token（中文约 28KB、英文约 50KB），超出部分只给预览；`file` 只能按整行续读，不能从一行中间接着读，所以几十 KB 的超长单行后半截 FA 读不到，会反复读取直到 `FA_STEP_BUDGET_EXCEEDED`。截断提示出现「本次预览没有完整正文行」就是这种情况，改文件写法，不调高轮次。
- 单个分片控制在单次读取上限以内并留余量：中文约 18KB、英文约 35KB 以内；能一次读完就不要再切小，切得过碎只会增加读取轮次。总条数、最后一条、求和、分类计数这类确定性结果由脚本计算，不让 FA 通读全部数据，也不把 FA 返回的计数当真值。要按语义分类计数时，脚本把记录写成 JSONL 或分片文件、只把路径传给 FA；FA 读文件后按 `record_id` 逐条返回标签（如分类、情绪、是否紧急），脚本再按标签统计。逐条打标签也走文件，不把整批记录作为 FA 的参数数组或 JSON 字符串传入。FA 只读需要语义判断的部分（如只读标题挑选），需要它通读多个分片时在提示词里要求同一轮并行读取。

### shell 步骤的成败

- `shell` 步骤的成败只看命令的退出码：非零即该步失败（`failure_class=shell_exit`），脚本用 `try/except` 接。不用 `echo` 哨兵词再对结果做 `in` 判断，preview 会拦。
- 退出码只看**最后一条命令**：`a | b` 只取 `b` 的，`a; b` 只取 `b` 的。前段失败也要算失败时，用 `&&` 连接，或在一个子 shell 里开 `pipefail`：`( set -o pipefail; pip install -r requirements.txt 2>&1 | tail -20 )`。裸写 `pip install … | tail` 时安装失败会被 `tail` 的成功掩盖，下游照常执行。
- 允许失败的检查（例如 `grep` 没匹配到返回 1）不套 `pipefail`；确实要忽略失败时写明 `|| true`，让意图清楚。
- 同一次运行的 `shell` 步骤共用一个会话，顶层写的 `set -e`、`set -o pipefail`、`cd`、`export` 都会带到后面的步骤；`set -e` / `pipefail` 只写在子 shell 的括号里。

### 读长期数据集（不是智能应用的应用库）

本节只管**长期数据集**（`list_assets(asset_type="dataset")` 列出的 FAQ、知识库、历史数据）；智能应用自己的应用库按下面「读写应用库」，两者规则不同，不混用。

- 路线要参考长期数据集里的记录时，由脚本先用 `shell` 在沙箱里执行 `ds-cli exec` 读出数据，再把结果作为参数交给 FA。`shell` 是编排型 TPE 默认可调用的工具，不用放进工具集；脚本调用了它，平台会建沙箱并注入当前使用者的数据集身份，`ds-cli` 经 dataset-proxy 用这个身份读库。
- 长期数据集由脚本读：编排里的 FA 拿不到沙箱，也看不到数据集的使用说明，只能看到数据集名字。（应用库不同：FA 可以挂工具只读查，见「建 FA」。）
- 只写只读 `SELECT`。表名写成全限定名 `<pg_schema>.表名`：`pg_schema` 取 `list_assets(asset_type="dataset")` 的返回，表名和列名用 `dataset_read(action="tables")`、`dataset_read(action="columns")` 查实。筛选条件、关键字匹配、排序都写进 SQL，带 `LIMIT`，只取 FA 用得上的列。不加 `--max-rows` 时最多返回 1000 行，超出部分会被截断，而且命令不报错；要全量数据时用 `--output <ctx.process_dir 下的路径>` 导出成 CSV，再按文件处理，不把大结果直接交给 FA。
- 命令加 `--format json`，输出是以列名为键的对象数组；`_output` 声明成对象数组，由平台解析终端回显。小数列在输出里是字符串，`_output` 声明成 number 时平台会转成数字。
- `ds-cli` 命令没有参数占位，输入值要拼进 SQL：先在脚本里校验成枚举或数字；自由文本里的单引号写成两个单引号，双引号不放进命令；自由文本用于 `LIKE` 时，先把 `\`、`%`、`_` 前面各加一个反斜杠。（这条只适用于长期数据集；应用库的值一律经 `db()` 的 `params`。）
- 权限按运行应用的使用者算：数据集所有者本人和被分享了该数据集的人能读，其他人会报 `permission denied`，`shell` 以非零退出码失败。应用给别人用时，PRD 要写明所有者需要先把数据集分享给使用者。
- 冒泡时 `shell` 真实执行，读数这一步用冒泡验证。

```python
    if input["category"] not in ("video", "image"):
        return {"status": "needs_input", "note": "category 只能是 video 或 image", "faq": []}
    faq = await tool(
        "shell",
        action="shell_exec",
        command=(
            'ds-cli exec "SELECT question, answer FROM <pg_schema>.faq '
            f"WHERE category = '{input['category']}' ORDER BY updated_at DESC LIMIT 20\" --format json"
        ),
        _rationale="生成前取该品类最近的 FAQ 作为素材",
        _output={"type": "array", "items": {"type": "object",
            "properties": {"question": {"type": "string"}, "answer": {"type": "string"}}}},
    )
```

### 建、校验和上线 TPE

1. `otpe_manage(action="preview", task_id, script, input_schema, output_schema, business_event_contracts, preload_toolset_ids)`。读写应用库的路线 preview 前按「反读自查四项」逐项过一遍，任一项不满足先改再 preview。
2. 通过后 `create`（同一组参数加 `scene_package_id`、`name`、`description`），再 `online`。预加载的工具集要已上线（[依赖与MCP接入.md](依赖与MCP接入.md)「工具集上线的两道检查」）。
3. `otpe_manage(action="verify", task_id, tpe_id)` 看 `verdict`：`blocked` 按 `failed` 项改后重来；`needs_bubble` 说明静态项都过了，只差运行证据；带上运行证据（见「冒泡与真跑能证明什么」）后到 `passed`。
4. 单条冒泡只用于多节点路线里某个节点要单独调通时：`otpe_manage(action="bubble", task_id, tpe_id, workflow_input=<代表性输入>)` 拿 `run_id`，只传 `run_id` 续等到终态，再 `verify(tpe_id, run_id)`。路线只有一个节点时直接用路线冒泡作证据，单条 TPE 的冒泡不拼成路线证据。

### 冒泡与真跑能证明什么

| 验证 | FA | 工具、shell、文件 | 带 `ctx.dry_run` 判断的外部动作 | 能证明 |
|---|---|---|---|---|
| preview | 不执行 | 不执行 | 不执行 | 脚本与契约静态合法 |
| 冒泡 bubble | 桩（按 `_output` 造值） | 真实执行 | 跳过 | 管路通、形状对 |
| 冒泡 `full_run=true` | 真实调用 | 真实执行 | 跳过 | 模型行真实输出；有费用，按 `SKILL.md`「花费」 |
| 真跑 `manage_goalfymax_project(run)` | 真实调用 | 真实执行 | 执行 | 端到端结果 |

- 桩跑通只算「只用模拟数据试过」；桩值导致下游失败时，对同一路线加 `full_run=true` 重跑一次。
- `verify(tpe_id, run_id)` 既接受单条冒泡的 `WFR-` run_id，也接受路线冒泡的 `WRV-` run_id（按 `tpe_id` 取对应节点）。`verify(tpe_id, project_id)` 接受真跑项目作证据，FA 与应用库都是真实执行；读写应用库的路线用它，在 [../stages/4-试用验收.md](../stages/4-试用验收.md)「2.3 工作集真跑」里补（怎么真跑见 [部署与版本.md](部署与版本.md)「真跑」）。
- **止损**：冒泡里某一步异常长跑、步数或 `cost_credits` 一直在涨时，先停再排查：路线冒泡 `scene_package_manage(action="cancel", task_id, run_id)`，单条冒泡 `otpe_manage(action="cancel", task_id, run_id)`；回执 `status=cancelled` 不算资产失败。冒泡的验证项目只读，停冒泡用 cancel（`manage_goalfymax_project(stop)` 对它不可用）。
- 时限：冒泡在隐藏验证项目里跑，按创建时间算——建好没启动 30 分钟后回收；单次运行上限是启动后 30 分钟，读取时报 `timeout`；创建后 1 小时仍未结束就强停回收；已结束的保留到创建后 2 小时，期间同一 `run_id` 可复读。过了时限再读会报找不到，按提示不带 `run_id` 重新发起。

### 读写应用库（智能应用自己的库，不是长期数据集）

用到施工单「存数据」里的表（客户、素材、历史记录），或结果要存下来给页面看、给下次用的路线，都是读写应用库的路线，脚本要真的读写应用库；只发事件、只做计算、不碰库的脚本不算做好。谁读、谁写、谁建行按 [数据模板.md](数据模板.md)「编排脚本怎么读写应用库」「谁建行、谁写列」。脚本里的读写统一用下面这个 `db()`，**复制进脚本**再用：

```python
async def db(sql, mode="reader", params=None, why="读写应用库"):
    """执行一条固定 SQL。返回 (ok, 行列表, 影响行数, 错误说明)；行是 {列名: 值}。不抛异常，调用方按读写分别收口。"""
    # json 是脚本环境内置的，直接用；不要写 import json，preview 禁止任何 import。
    try:
        raw = await tool("GOALFYAI_TOOL_query_business_app_dataset", action="exec", mode=mode, sql=sql,
                         params=params or {}, _rationale=why, _text=True)
        body = json.loads(raw)
        if body.get("output") is not None or body.get("success") is False:  # 外层信封；不写 "output" in body，preview 会把它当 shell 回显判定
            if body.get("success") is not True:
                return False, [], 0, str(body.get("error") or "应用库读写失败")
            body = json.loads(body["output"])
        results = body.get("results") or []
        if not results:
            return False, [], 0, "应用库没有返回结果"
        result = results[-1]
        rows = [dict(zip(result.get("columns") or [], row)) for row in result.get("rows") or []]
        return True, rows, result.get("row_count", 0), ""
    except Exception as exc:  # 工具报错（如冒泡里的 not_a_business_app_project）、返回解析失败都在这里收口
        return False, [], 0, str(exc)
```

- `db()` 里的 `try` 只包这一次工具调用和返回解析，是「`try` 只包可选的那一次调用」之外的唯一写法；照抄，不删。
- 参数直接写在 `tool(...)` 里，不改成 `**kwargs` 展开：静态校验看不到展开里的 `_rationale`，会报告警。`json` 已内置，不补 `import json`。
- 业务值一律用 `:name` 占位符放进 `params`，SQL 本身是固定字符串；不自写 `sql_literal()`、`query_db()` 之类的转义或查询函数（写法细则见 [数据模板.md](数据模板.md)「编排脚本怎么读写应用库」）。
- **读**：`ok=False`（不是智能应用项目、实例还没建）或查不到行，都按「没有数据」收口，回退表单值或通用策略，不重试、不编数。读库不用包 `dry_run`：冒泡里读到空（工具报 `not_a_business_app_project`）是预期，读到数据之后的分支到 ④ 工作集真跑里核对。
- **写**：`ok=False` 或该改的行数对不上，本节点返回 `status="blocked"`，`note` 写「未入库：原因」，不进下游。
- **写库包在 `if not ctx.dry_run:` 里**：只有冒泡（单条、路线、`full_run` 都算）里 `ctx.dry_run` 为真，而冒泡的验证项目也没有应用库；真跑、在线预览、自动化、使用者运行里 `ctx.dry_run` 为假，应用库在运行开始前就已建好。所以写库语句一律包在 `if not ctx.dry_run:` 里：冒泡时跳过、不报「未入库」，其余场景照常写。这是跳过不是删除：写库保留在脚本里，不为冒泡改成入口传素材或交给页面、后端代写。
- 这个工具不是 TA 默认工具：TPE 的 `preload_toolset_ids` 里要有一个装了工具组「query_business_app_dataset」的工具集，否则 preview 报「无法解析到 preload_toolsets」。

### 反读自查四项

每条读写应用库的路线 preview 前逐项自查一遍；`online` 后用 `get_asset(asset_type="tpe")` 反读脚本、`get_asset(asset_type="fast_agent")` 反读要查库的 FA，四项各记「有 / 没有」：

1. **脚本有 `db(`**：复制了上面统一的 `db()`，所有应用库读写都经它，业务值都经 `params`。
2. **写库包在 `if not ctx.dry_run:` 里**，写法照 ② 定的「同一业务再做一次」是更新原记录还是新增一条，按 [数据模板.md](数据模板.md)「谁建行、谁写列」；写失败返回 `blocked`「未入库」。
3. **工具集含「query_business_app_dataset」并在 `preload_toolset_ids` 里**；要查库的 FA 反读的 `actual_tool_group_ids` 含它（只认这个字段，`configured_tool_group_ids` 是配置值，不作证据）。
4. **入口没有整包字段**：`input_schema` 符合 [数据模板.md](数据模板.md)「入口字段放哪」——应用库里已有的只传业务键、由脚本按键读，整批记录、素材、档案、摘要都不从入口进，也没有「入口传了就用、没传再查库」的兜底；当次的少量补充（如 `goal_override`、`extra_requirements`）只作补充，不带客户、素材、记录全文，也不让脚本因它跳过查库。出现 `fallback_*`、`materials_summary`、`materials_text`、`snippets`、`records`、`records_json`、`customer_profile`、`customer_summary` 这类字段即记「没有」。

四项都「有」，这条路线才算做好；四项是 ③ 的交棒门（[../stages/3-制作.md](../stages/3-制作.md)「2.1 后台能力」）。

### 三种模板

常见三种形状：拉数落库、查库判读写回、生成写库。挑一种改业务词，不从零写。三种都读写应用库，先把上面的 `db()` 复制进脚本再用；要模型决定查什么的才交给挂了工具的业务 FA。哪种情形由路线自己建行、哪种只更新后端已建的行，见 [数据模板.md](数据模板.md)「谁建行、谁写列」：模板一、二是路线自给的写法，模板三是更新后端已建行的写法。

#### 一、拉数落库

```python
async def run(input, ctx):
    await emit_business_event(event_type="stage_started", event_key="sync_started",
                              payload={"stage_key": "sync", "stage_name": "正在同步数据"})

    listed = await tool(
        "<工具的 mr_name>",
        account_id=input["account_id"],
        _rationale="取回名下全部记录，后面的步骤都以它为准",
        _output={
            "type": "object",
            "required": ["items"],
            "properties": {"items": {"type": "array", "items": {"type": "object",
                "required": ["id", "name"],
                "properties": {"id": {"type": "string"}, "name": {"type": "string"}}}}},
        },
    )
    rows = [{"external_id": it["id"], "name": it["name"]} for it in listed["items"]]

    written = 0
    if not ctx.dry_run:  # 冒泡跳过写库，真跑照常写
        ok, _, written, err = await db(
            "INSERT INTO accounts (external_id, name, updated_by, last_run_id) "
            "SELECT r.external_id, r.name, 'agent', :run_id FROM jsonb_to_recordset(:rows::jsonb) AS r(external_id text, name text) "
            "ON CONFLICT (external_id) DO UPDATE SET name = EXCLUDED.name, updated_by = 'agent', last_run_id = EXCLUDED.last_run_id, "
            "updated_at = now(), row_version = accounts.row_version + 1",
            mode="writer", params={"rows": rows, "run_id": ctx.run_id}, why="把同步结果按 external_id 幂等落到台账，供应用展示",
        )
        if not ok:
            await emit_business_event(event_type="stage_result", event_key="sync_completed",
                                      payload={"stage_key": "sync", "summary": f"拉到 {len(rows)} 条，未入库"})
            return {"status": "blocked", "note": f"未入库：{err}", "count": len(rows), "written": 0}

    await emit_business_event(event_type="stage_result", event_key="sync_completed",
                              payload={"stage_key": "sync", "summary": f"同步 {len(rows)} 条"})
    return {"status": "completed", "count": len(rows), "written": written}
```

#### 二、查库判读写回

数据已经在应用库里（使用者录入的、上一条路线同步进来的），要模型逐条判断再把结论存回去给页面看。读和写都经 `db()`，记录写成过程文件、只把路径交给 FA，结论按业务键写回；数据从库里读，不改成由入口传路径或整批字段，也不由脚本写死摘要。

```python
async def run(input, ctx):
    await emit_business_event(event_type="stage_started", event_key="inspection_started",
                              payload={"stage_key": "inspection", "stage_name": "正在巡检广告计划"})

    ok, plans, _, err = await db(
        "SELECT id, plan_name, spend_7d, conversions_7d, ctr_7d FROM ad_plans "
        "WHERE account_id = :account_id AND deleted_at IS NULL ORDER BY id LIMIT 500",
        params={"account_id": input["account_id"]}, why="取这个账户下要巡检的计划和近 7 天指标",
    )
    if not plans:  # 读失败或没数据都按「没有数据」收口；冒泡里会走到这里，是预期
        await emit_business_event(event_type="stage_result", event_key="inspection_completed",
                                  payload={"stage_key": "inspection", "summary": "这个账户还没有可巡检的计划"})
        return {"status": "insufficient_evidence", "checked": 0, "flagged": 0, "summary": "还没有可巡检的计划"}

    records_path = f"{ctx.process_dir}/plans.jsonl"
    await tool(
        "file", action="file_write_text", abs_path=records_path,
        text="\n".join(json.dumps(dict(p, record_id=p["id"]), ensure_ascii=False) for p in plans),
        _rationale="把要判断的计划一行一条写成过程文件，FA 只拿路径", _text=True,
    )
    result = await tool(
        "<判读 FA 的 mr_name>",
        query="逐条判断每个计划是否需要关注，给出风险等级和原因",
        records_path=records_path,
        _rationale="由模型逐条判断风险",
        _output={
            "type": "object",
            "required": ["status", "note", "items"],
            "properties": {
                "status": {"type": "string", "enum": ["completed", "partial", "blocked"]},
                "note": {"type": "string"},
                "items": {"type": "array", "items": {"type": "object",
                    "required": ["record_id", "risk_level", "reason"],
                    "properties": {"record_id": {"type": "integer"}, "risk_level": {"type": "string", "enum": ["高", "中", "低", "无"]},
                                   "reason": {"type": "string"}}}},
            },
        },
    )
    if result["status"] == "blocked":
        await emit_business_event(event_type="stage_failed", event_key="inspection_failed",
                                  payload={"stage_key": "inspection", "error_code": "inspection_blocked", "message": result["note"]})
        return {"status": "blocked", "checked": 0, "flagged": 0, "summary": result["note"]}

    known = {p["id"] for p in plans}
    rows = [it for it in result["items"] if it["record_id"] in known]  # FA 返回的 id 只认库里查到的
    if not ctx.dry_run:  # 冒泡跳过写库，真跑照常写
        ok, _, written, err = await db(
            "INSERT INTO plan_inspections (plan_id, inspect_date, risk_level, reason, updated_by, last_run_id) "
            "SELECT r.record_id, current_date, r.risk_level, r.reason, 'agent', :run_id "
            "FROM jsonb_to_recordset(:rows::jsonb) AS r(record_id bigint, risk_level text, reason text) "
            "ON CONFLICT (plan_id, inspect_date) DO UPDATE SET risk_level = EXCLUDED.risk_level, reason = EXCLUDED.reason, "
            "updated_by = 'agent', last_run_id = EXCLUDED.last_run_id, updated_at = now(), "
            "row_version = plan_inspections.row_version + 1",
            mode="writer", params={"rows": rows, "run_id": ctx.run_id}, why="按计划和日期幂等写回巡检结论，供页面展示",
        )
        if not ok or written != len(rows):
            return {"status": "blocked", "checked": len(plans), "flagged": 0, "summary": f"未入库：{err or '写入行数不对'}"}

    flagged = sum(1 for it in rows if it["risk_level"] in ("高", "中"))  # 计数由脚本算，不用 FA 给的数
    await emit_business_event(event_type="stage_result", event_key="inspection_completed",
                              payload={"stage_key": "inspection", "summary": f"巡检 {len(plans)} 个计划，{flagged} 个需要关注"})
    return {"status": result["status"], "note": result["note"], "checked": len(plans), "flagged": flagged, "summary": f"{flagged} 个计划需要关注"}
```

照抄时只换表名、列名、业务键和 FA 的 `mr_name`；这个例子是「同一计划同一天只留一条」，`(plan_id, inspect_date)` 要在数据模板里建唯一约束。② 定的是每次巡检都留一条历史的，去掉 `ON CONFLICT` 子句、不建这个唯一约束，其余照抄。这里的 FA 只读文件，不挂 `query_business_app_dataset`；要 FA 自己按情况查库的，按「建 FA」挂工具并反读。

```python
async def run(input, ctx):

    if not profiles:

    draft = await tool(
        "<生成 FA 的 mr_name>",

            await emit_business_event(event_type="stage_failed", event_key="draft_failed",

            return {"status": "blocked", "note": f"未入库：{reason}", "draft_title": "", "draft_body": ""}

    await emit_business_event(event_type="stage_result", event_key="draft_completed",

```

#### 对应的事件契约（三种共用形状，只改 event_key 与 stage 名）

```json
[
  {"event_type": "stage_started", "event_key": "<stage>_started", "event_version": "1.0", "description": "开始<stage>",
   "payload_schema": {"type": "object", "additionalProperties": false, "required": ["stage_key", "stage_name"],
                      "properties": {"stage_key": {"type": "string"}, "stage_name": {"type": "string"}}}},
  {"event_type": "stage_result", "event_key": "<stage>_completed", "event_version": "1.0", "description": "<stage>完成",
   "payload_schema": {"type": "object", "additionalProperties": false, "required": ["stage_key", "summary"],
                      "properties": {"stage_key": {"type": "string"}, "summary": {"type": "string"}}}},
  {"event_type": "stage_failed", "event_key": "<stage>_failed", "event_version": "1.0", "description": "<stage>失败",
   "payload_schema": {"type": "object", "additionalProperties": false, "required": ["stage_key", "error_code", "message"],
                      "properties": {"stage_key": {"type": "string"}, "error_code": {"type": "string"}, "message": {"type": "string"}}}}

```

模板二、三用到了 `stage_failed`，用模板一时删掉第三条契约。一条 TPE 有多个业务步骤时，每个步骤复制一条 `stage_started` 契约，换成该步骤的 `event_key`。

## 常见错误

- `_output` 抄了工具的全部字段，或和真实返回对不上，verify 报 `static_contract`。
- 用增加角色、关系、否定条件或嵌套 ID 来修正事实错误；Schema 只能约束形状，应按职责边界拆分或返回稳定载体引用。
- 同类错误已连续两轮，仍继续加字段或原样重试，没有重判职责。
- 脚本写成 tool → FA → tool → FA 长链，把「看结果再决定查什么」放在脚本里。
- `stage_name` 写成「正在处理本次任务」「正在执行」这类泛词，或几个业务步骤共用一次 `stage_started`，使用者在状态条上看不出在做什么。
- 每个 `tool()` 后机械发一次事件。
- 捕获全部异常后返回 `status="completed"`，或用空字符串、虚构路径凑成功对象。
- FA 返回 `needs_input` 仍继续写库。
- 分段返回的工具只拿首段就下结论（判失败与上一条返回只隔几十毫秒）；工具自述的不确定态（如 `state="undetermined"`）不是失败。
- 为消除报错给无用途的路径补文件声明。
- 把要给 FA 读的数据 `json.dumps` 成一整行写进文件（几十 KB 单行），FA 只能读到截断预览，续读为空，耗尽轮次。
- 把整批记录作为 FA 的入参字段（如 `records`、`records_json`、`feedback_items`、`items`），或让 FA 输出总数、分类数。
- 自己给 FA 的调用名拼前缀或用数字 ID，没用反读到的 `mr_name`。
- 为了让冒泡通过，把读库包进 `dry_run`、从入口塞数据、加 `fallback_*` 兜底或删掉读写。
- 把长期数据集只交给 FA 的提示词或参数（只传 `dataset_id`），指望它自己去读；FA 只能看到数据集名字，拿到的数据是空的。
