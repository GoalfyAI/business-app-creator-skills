# 编排脚本

## 适用场景

写或改编排型 TPE 脚本、定 `_output` 与失败出口、写事件契约、判断冒泡结果能证明什么时读。第一次写脚本前还要读 `get_diagnosis_doc(topic="otpe_single")`；原语签名和字段以它和 `otpe_manage` 的当前 Schema 为准。

## 规则

### 脚本骨架

- 入口 `async def run(input, ctx)`；返回值按 `output_schema` 逐字段组装，不把工具或 FA 的返回整包转交。
- 每个 `tool()` 带 `_rationale`（为什么调）与 `_output`（按工具真实返回结构声明，只声明脚本要读的字段）。
- 工具返回的是一整段文本（网页、文件原文、长列表文本，如 `open_url`）时，`_output` 只声明一个必填 string 字段：`{"type": "object", "required": ["text"], "properties": {"text": {"type": "string"}}}`，平台直接把原文包进去，不经模型。声明成多个字段会让模型从原文里抽取，原文一长就超时（`_output extraction` 45 秒）；要结构化字段就把原文交给后续 FA 或在脚本里解析。
- 脚本里用到的每个工具和 FA 都要在预加载工具集清单里声明，且工具集已上线。FA 用反读到的 `mr_name`。
- 技术失败让异常冒泡，**禁止**捕获后伪装成业务成功，**禁止**用空字符串或虚构路径凑成功对象。
- 有外部副作用的动作（发信、写外部系统、付款）按 `ctx.dry_run` 判断，冒泡时跳过。
- 写库的步骤按「会被再执行一次」写：带唯一键或先查后写。
- 脚本来源：短脚本传 `script`；长脚本或多轮修改用 `script_url`；只改一个片段且 Schema 支持时用 `script_patch`。只改输入输出或依赖时不重传脚本。

### FA 与脚本的职责边界

| 责任方 | 只负责 | 不负责 |
|---|---|---|
| FastAgent | 一个可独立复用的语义责任；在内部按结果自适应判断和调用工具 | 流程分发、跨环节汇合、固定收口 |
| 编排脚本 | 确定性准备、分发、汇合、幂等写入和固定收口 | 判断内容真假、用新增字段替代语义判断 |

`_output` 是脚本与 FA 之间的**控制面最小合同**，不是内容质量检查器。按以下顺序收口：

1. 默认软门禁是顶层字段不超过 8 个、对象嵌套不超过 2 层；超过时拆开语义责任，或把内容改成稳定载体引用，不继续扩 Schema。该门禁用于新建和修订，不让存量脚本自动失效。
2. 内容型大结果（长报告、完整证据集、批量明细）写入数据集或 `ctx.process_dir` 文件等稳定载体；`_output` 只返回 `status`、`note`、引用和脚本真正需要的计数。不要把长正文、完整证据集或逐项推理塞进控制面。一篇草稿、几条诊断这类短内容照常以字段返回；节点最终返回里给用户看的列表、正文、结论仍以业务字段出现，要交付的文件才写 `ctx.output_dir` 并声明交付（见「文件产物」）。
3. Schema 只校验形状，不能证明内容真实。输出分成事实区与推断区：事实保留来源和原文，推断明确标记且不得回填为事实；首版只承诺来源、原文和失败原因可追溯。
4. 同类事实错误、引用错误或无产物连续两轮出现时，停止加字段和原样重试，回到 G3/G4 重判 FA、脚本与工具职责；仍保留 `completed`、`partial`、`blocked` 等合法出口。

### 失败出口怎么写

| 确认页「做不成怎么办」 | 脚本写法 |
|---|---|
| 停下来告诉用户 | 不捕获，让异常冒泡；平台按失败类别归因 |
| 标记状态继续 | `try/except` 只包那一次 `tool()`；读异常的 `recoverable` 决定写 `optional_source_retry_later` 还是 `optional_source_unavailable`；输出带 `status` 与 `warnings` |
| 重试一次 | 同上，except 里再调一次；工具内部已重试的（异常带 `attempts`）不再叠加 |
| 业务条件不满足（证据不足、缺前置数据） | 发 `stage_failed` 或以明确的 `status` 正常返回，不抛异常 |

**异常上带的事实**（平台较新版本起）：`exc.failure_class`（`tool_error` / `fa_error` / `shell_exit` / `contract_error`）、`exc.recoverable`（`True` 是限流、超时、冷启动，可换时机重发；`False` 是鉴权、参数、余额，别再试；`None` 判不出）、`exc.attempts`（工具层已试次数）。目标环境没有这些属性时只按 `str(exc)` 分支。**禁止**把整段逻辑包进 `try`：脚本自己的 `KeyError` / `TypeError` 会被当成可选步骤失败吞掉。

**FA 的输出要给部分成功留出口**：每次 `tool(FA, _output=…)` 都声明 `status`，枚举至少含 `completed`（全部做完、数据真实）、`partial`（做了一部分，未做的不补不编）、`blocked`（一条没做成，数据字段留空），再配一个 `note` 写做到哪、还差什么、为什么停；缺的是最终用户补得上的输入时加 `needs_input` 作为 `blocked` 的细分。读应用库这类只读查询以 `found` 布尔作出口即可。只允许成功态时模型会编造数据去满足 schema，收得越紧越倾向编造。**门禁先裁业务状态**：上游 FA 返回非成功状态（如 `needs_input`、`blocked`）时，脚本不进写库、不进下游，也不原样重试。

**上下文预算**：FA 报 `FA_CONTEXT_BUDGET_EXCEEDED` 时调高轮次没用，要减少单次传入：大段素材传路径、一次处理一个对象。报 `FA_STEP_BUDGET_EXCEEDED` 先看 `partial` 出口有没有写好，再按预估步数调轮次。

### 事件契约

- 只有需要业务路线可观察性、应用状态、表单握手或交付审阅时才声明；声明了就进 Business Runtime 语义，正式运行必须经路线（单条 TPE 也建单节点路线）。
- 硬门：首个业务动作前发 `stage_started`；每个正常 `return` 前发 `stage_result`；可解释的业务失败发 `stage_failed`。`artifact_ready`、`delivery_ready` 由平台自动发，脚本**禁止**声明或调用。
- `payload_schema.required` 必须含平台字段：`stage_started` 要 `stage_key`、`stage_name`；`stage_result` 要 `stage_key`；`stage_failed` 要 `stage_key`、`error_code`、`message`；`attention_required` 要 `level`、`title`、`message`。`additionalProperties` 必须为 `false`。
- `event_type`、`event_key` 用字符串字面量，不动态拼；载荷不放内部 ID、原始工具返回、提示词或未脱敏错误。阶段名用最终用户能懂的业务语言。
- `stage_name` 就是使用者在应用顶部执行状态条上看到的那句话：写成「正在<动作><对象>」，如「正在核验商户资料」「正在生成跟进话术」；**禁止**「正在处理本次任务」「正在执行」这类看不出在做什么的泛词。
- 一条 TPE 里有两个以上使用者能分辨的业务步骤（如先核验资料、再生成话术）时，每个步骤开始前各发一次 `stage_started`，各用自己的 `event_key`、`stage_key` 并各自声明契约；同一步骤内部的工具调用不再发。
- **禁止**在每个 `tool()` 后机械发事件；不为进度条声明 `stage_progress`。
- 契约随 `otpe_manage(action="create"|"update", business_event_contracts=[…])` 一起写，写后 `get_asset(asset_type="tpe")` 反读。

### 文件产物

- 要交付的文件写进 `ctx.output_dir`，在 `output_schema` 声明为 `format: workspace-file-path` 并返回真实路径，路线的交付映射也要引用它；入口素材、上游产物要作为本次附件时先复制进 `ctx.output_dir`。
- `ctx.input_dir` 用于输入素材，`ctx.process_dir` 用于过程文件；本次新生成且要返回的文件（包括诊断附件）写进 `ctx.output_dir`。过程文件写入成功、路径存在，都不等于它已成为可信输出。
- 节点输出的来源校验接受 `ctx.output_dir` 下的路径、输入文件字段带入的路径，以及工具以裸路径或完整 JSON 返回的路径。`file` 工具的文字回执 `File written successfully: <path>` 不会被解析为可信来源；把 `ctx.process_dir` 文件仅凭该回执返回，会报 `WORKSPACE_PATH_UNTRUSTED`。将实际文件写入或复制到 `ctx.output_dir` 后再返回，不能只改路径字符串。节点来源校验通过后，最终交付仍须满足上一条的目录与映射要求。
- 要给用户看的列表、正文、结论以业务字段出现在返回值里，不只落文件。

### 读长期数据集（不是智能应用的应用库）

本节只管**长期数据集**（`list_assets(asset_type="dataset")` 列出的 FAQ、知识库、历史数据）；智能应用自己的应用库按下面「读写应用库」，两者规则相反，不要混用。

- 路线要参考长期数据集里的记录（FAQ、知识库、历史数据）时，由脚本先用 `shell` 在沙箱里执行 `ds-cli exec` 读出数据，再把结果作为参数交给 FA。`shell` 是编排型 TPE 默认可调用的工具，不用放进工具集；脚本调用了它，平台会建沙箱并注入当前用户的数据集身份，`ds-cli` 经 dataset-proxy 用这个身份读库。
- **禁止**让 FA 自己去读长期数据集：编排里的 FA 拿不到沙箱，也看不到数据集的使用说明，只能看到数据集名字。（应用库不同：FA 可以挂工具只读查，见下节。）
- 只写只读 `SELECT`。表名写成全限定名 `<pg_schema>.表名`：`pg_schema` 取 `list_assets(asset_type="dataset")` 的返回，表名和列名用 `dataset_read(action="tables")`、`dataset_read(action="columns")` 查实，**禁止**猜。筛选条件、关键字匹配、排序都写进 SQL，带 `LIMIT`，只取 FA 用得上的列。不加 `--max-rows` 时最多返回 1000 行，超出部分会被截断，而且命令不报错；要全量数据时用 `--output <ctx.process_dir 下的路径>` 导出成 CSV，再按文件处理，不把大结果直接交给 FA。
- 命令加 `--format json`，输出是以列名为键的对象数组；`_output` 声明成对象数组，由平台解析终端回显。小数列在输出里是字符串，`_output` 声明成 number 时平台会转成数字。
- 拼进 SQL 的输入值先在脚本里校验成枚举或数字；自由文本里的单引号写成两个单引号，双引号不放进命令；自由文本用于 `LIKE` 时，先把 `\`、`%`、`_` 前面各加一个反斜杠。
- 权限按运行应用的用户算：数据集所有者本人和被分享了该数据集的用户能读，其他使用者会报 `permission denied`，`shell` 以非零退出码失败。应用给别人用时，确认页要写明所有者需要先把数据集分享给使用者。
- 冒泡时 `shell` 真实执行，读数这一步用冒泡验证。

```python
    if input["category"] not in ("video", "image"):
        return {"status": "needs_input", "note": "category 只能是 video 或 image", "faq": []}
    faq = await tool(
        "shell",
        action="shell_exec",
        command=(
            'ds-cli exec "SELECT question, answer FROM <pg_schema>.faq '
            f"WHERE category = '{input['category']}' ORDER BY updated_at DESC LIMIT 20\" --format json"

```

### 冒泡与真跑能证明什么

| 验证 | FA | 工具、shell、文件 | 带 `ctx.dry_run` 判断的外部动作 | 能证明 |
|---|---|---|---|---|
| preview | 不执行 | 不执行 | 不执行 | 脚本与契约静态合法 |
| 冒泡 bubble | 桩（按 `_output` 造值） | 真实执行 | 跳过 | 管路通、形状对 |
| 冒泡 `full_run=true` | 真实调用 | 真实执行 | 跳过 | 模型行真实输出；有费用，按确认页已同意的范围跑 |
| 真跑 `manage_goalfymax_project(run)` | 真实调用 | 真实执行 | 执行 | 端到端结果 |

`verify(tpe_id, run_id)` 既接受单条冒泡的 `WFR-` run_id，也接受路线冒泡的 `WRV-` run_id（按 `tpe_id` 取对应节点）；单节点路线直接用路线冒泡作证据。

冒泡在隐藏验证项目里跑，时长按创建时间统一计算：

| 情况 | 时长 |
|---|---|
| 建好但没启动 | 30 分钟后回收 |
| 单次运行上限 | 启动后 30 分钟，读取时报 `timeout` |
| 创建后仍未结束 | 1 小时后强停并回收 |
| 已结束 | 保留到创建后 2 小时，期间同一 `run_id` 可复读 |

过了时限再读会报找不到，按提示不带 `run_id` 重新发起。

### 读写应用库（智能应用自己的库，不是长期数据集）

路线要读写应用库（智能应用自己的库），写脚本之前先读 [数据模板.md](数据模板.md)「编排脚本怎么读写应用库」定好分工。脚本里的读写统一用下面这个 `db()`，**复制进脚本**再用，不要每处自己解析返回：

```python
async def db(sql, mode="reader", params=None, why="读写应用库"):
    """执行一条固定 SQL。返回 (ok, 行列表, 影响行数, 错误说明)；行是 {列名: 值}。不抛异常，调用方按读写分别收口。"""
    # json 是脚本环境内置的，直接用；不要写 import json，preview 禁止任何 import。
    try:
        raw = await tool("GOALFYAI_TOOL_query_business_app_dataset", action="exec", mode=mode, sql=sql,
                         params=params or {}, _rationale=why, _text=True)
        body = json.loads(raw)
        if "output" in body:
            if body.get("success") is not True:
                return False, [], 0, str(body.get("error") or "应用库读写失败")
            body = json.loads(body["output"])
        results = body.get("results") or []
        if not results:
            return False, [], 0, "应用库没有返回结果"
        result = results[-1]
        rows = [dict(zip(result.get("columns") or [], row)) for row in result.get("rows") or []]
        return True, rows, result.get("row_count", 0), ""
    except Exception as exc:  # 工具报错（如冒泡里的 not_a_business_app_project）、返回解析失败都在这里收口
        return False, [], 0, str(exc)
```

- `db()` 里的 `try` 只包这一次工具调用和返回解析，是「不把整段逻辑包进 `try`」的唯一例外；照抄即可，不要删。
- 参数写在 `tool(...)` 里，**禁止**改成 `**kwargs` 展开：静态校验看不到展开里的 `_rationale`，会报告警。`json` 已内置，**禁止**补 `import json`。
- **读**：`ok=False`（不是智能应用项目、实例还没建）或查不到行，都按「没有数据」收口，回退表单值或通用策略，不重试、不编数。
- **写**：`ok=False` 或该改的行数对不上，本节点返回 `status="blocked"`，`note` 写「未入库：原因」，不进下游。
- **冒泡碰不到应用库**：冒泡在隐藏验证项目里跑，没有应用绑定，读一律为空、写一律「未入库」（工具报 `not_a_business_app_project`），这是预期，冒泡照样算通过。`verify(run_id=…)` 唯一的失败项若是这个工具在隐藏项目里的失败步骤，记为「冒泡无法验证真实读写」，照常往下走；真实读写在「在线试用」或真跑里核对。**禁止**为了让冒泡顺利而删掉路线里的应用库读写、改成入口传素材或交给页面/后端代写。
- 这个工具不是 TA 默认工具：TPE 的 `preload_toolset_ids` 里要有一个装了工具组「query_business_app_dataset」的工具集（G4 第 4 步建工具集时把这个工具组一起装进去），否则 preview 报「无法解析到 preload_toolsets」。

### 三种模板

线上路线主要是三种形状：拉数落库、拉数判读、生成写库。挑一种改业务词，不从零写。模板要读写应用库时，先把上面「读写应用库」的 `db()` 复制进脚本再用；要模型决定查什么的才交给挂了工具的业务 FA。读写遵守 [数据模板.md](数据模板.md)「谁建行」：模板一是没有后端参与的同步类路线，按业务键幂等写入；有应用后端参与的路线，新行由后端生产回流接口建，路线只更新已建行。

#### 一、拉数落库

```python
async def run(input, ctx):
    await emit_business_event(
        event_type="stage_started",
        event_key="sync_started",
        payload={"stage_key": "sync", "stage_name": "正在同步数据"},
    )

    listed = await tool(
        "<工具的 mr_name>",
        account_id=input["account_id"],
        _rationale="取回名下全部记录，后面的步骤都以它为准",
        _output={
            "type": "object",
            "required": ["items"],
            "properties": {"items": {"type": "array", "items": {"type": "object",
                "required": ["id", "name"],
                "properties": {"id": {"type": "string"}, "name": {"type": "string"}}}}},
        },
    )
    rows = [{"external_id": it["id"], "name": it["name"]} for it in listed["items"]]

    ok, _, written, err = await db(
        "INSERT INTO accounts (external_id, name, updated_by, last_run_id) "
        "SELECT r.external_id, r.name, 'agent', :run_id FROM jsonb_to_recordset(:rows::jsonb) AS r(external_id text, name text) "
        "ON CONFLICT (external_id) DO UPDATE SET name = EXCLUDED.name, updated_by = 'agent', last_run_id = EXCLUDED.last_run_id, "
        "updated_at = now(), row_version = accounts.row_version + 1",
        mode="writer", params={"rows": rows, "run_id": ctx.run_id}, why="把同步结果按 external_id 幂等落到台账，供应用展示",
    )
    if not ok:
        await emit_business_event(
            event_type="stage_result",
            event_key="sync_completed",
            payload={"stage_key": "sync", "summary": f"拉到 {len(rows)} 条，未入库"},
        )
        return {"status": "blocked", "note": f"未入库：{err}", "count": len(rows), "written": 0}

    await emit_business_event(
        event_type="stage_result",
        event_key="sync_completed",
        payload={"stage_key": "sync", "summary": f"同步 {len(rows)} 条"},
    )
    return {"status": "completed", "count": len(rows), "written": written}
```

#### 二、拉数判读

```python
async def run(input, ctx):
    await emit_business_event(
        event_type="stage_started",
        event_key="diagnosis_started",
        payload={"stage_key": "diagnosis", "stage_name": "正在拉取数据并诊断"},
    )

    notes = await tool(
        "<拉数工具的 mr_name>",
        user_id=input["account_id"],
        limit=30,
        _rationale="取最近 30 条笔记作为诊断依据",
        _output={"type": "object", "required": ["items"], "properties": {"items": {"type": "array", "items": {"type": "object",
            "properties": {"title": {"type": "string"}, "likes": {"type": "integer"}, "published_at": {"type": "string"}}}}}},
    )
    if len(notes["items"]) < 5:
        await emit_business_event(
            event_type="stage_result",
            event_key="diagnosis_completed",
            payload={"stage_key": "diagnosis", "summary": "笔记不足 5 条，证据不足"},
        )
        return {"status": "insufficient_evidence", "note_count": len(notes["items"]), "findings": [], "summary": "笔记不足 5 条，暂不下结论"}

    result = await tool(
        "<判读 FA 的 mr_name>",
        query="按定位、内容问题、风险、建议四类给出诊断",
        notes_json=json.dumps(notes["items"], ensure_ascii=False),
        _rationale="由模型对笔记做判读",
        _output={
            "type": "object",
            "required": ["status", "note", "summary", "findings"],
            "properties": {
                "status": {"type": "string", "enum": ["completed", "partial", "blocked"]},
                "note": {"type": "string"},
                "summary": {"type": "string"},
                "findings": {"type": "array", "items": {"type": "object",
                    "required": ["kind", "title", "reason"],
                    "properties": {"kind": {"type": "string"}, "title": {"type": "string"}, "reason": {"type": "string"}}}},
            },
        },
    )
    if result["status"] == "blocked":
        await emit_business_event(event_type="stage_failed", event_key="diagnosis_failed",
                                  payload={"stage_key": "diagnosis", "error_code": "diagnosis_blocked", "message": result["note"]})
        return {"status": "blocked", "note_count": len(notes["items"]), "findings": [], "summary": result["note"]}

    await emit_business_event(
        event_type="stage_result",
        event_key="diagnosis_completed",
        payload={"stage_key": "diagnosis", "summary": result["summary"]},
    )
    return {"status": result["status"], "note": result["note"], "note_count": len(notes["items"]), "findings": result["findings"], "summary": result["summary"]}
```

   "payload_schema": {"type": "object", "additionalProperties": false, "required": ["stage_key", "stage_name"],

模板二、三用到了 `stage_failed`，用模板一时删掉第三条契约。一条 TPE 有多个业务步骤时，每个步骤复制一条 `stage_started` 契约，换成该步骤的 `event_key`。

## 常见错误

- `_output` 抄了工具的全部字段，或和真实返回对不上，verify 报 `static_contract`。
- 用增加角色、关系、否定条件或嵌套 ID 来修正事实错误；Schema 只能约束形状，应按职责边界拆分或返回稳定载体引用。
- 同类错误已连续两轮，仍继续加字段或原样重试，没有回到 G3/G4 重判职责。
- 脚本写成 tool → FA → tool → FA 长链，把「看结果再决定查什么」放在脚本里。
- `stage_name` 写成「正在处理本次任务」这类泛词，或几个业务步骤共用一次 `stage_started`，使用者在状态条上看不出在做什么。
- 捕获全部异常后返回 `status="completed"`。
- FA 返回 `needs_input` 仍继续写库。
- 分段返回的工具只拿首段就下结论（判失败与上一条返回只隔几十毫秒）；工具自述的不确定态（如 `state="undetermined"`）不是失败。
- 为消除报错给无用途的路径补文件声明。
- 把长期数据集只交给 FA 的提示词或参数（只传 `dataset_id`），指望它自己去读；FA 只能看到数据集名字，拿到的数据是空的。
