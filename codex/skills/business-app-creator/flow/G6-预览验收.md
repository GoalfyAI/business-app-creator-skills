# G6 预览验收

把应用部署好，必要时用真实样例真跑一次，由开发者在开发者中心的「在线试用」里自己走一遍并确认。验证只有两层：冒泡管改，真跑和开发者验收管收。

## 1. 进入条件

- 应用根本地 `npm run verify` 全绿。

## 2. 做什么

1. **打包部署**（场景包不必先上线：挂着你本人的场景包草稿也能部署，预览和真跑跑的就是草稿内容）：应用根 `npm run verify:release` 全绿后 `npm run pack`；`business_ui_bundle(action="download_template")` 再核一次脚手架门槛；再调 `business_ui_bundle(action="ship", task_id, business_ui_id, source_sha256, file_name, size_bytes)`：
   - 返回 `status=upload_required`：按 `upload_url` 与 `headers` PUT 源码包原字节，原参数加 `bundle_key` 再调；
   - 返回未终态：原参数加 `deployment_id` 再调，服务端每次最多等约 45 秒；**禁止**去掉 `deployment_id` 重调，那会重新起容器；
   - 到 `success` 为止。`steps` 标明每步 done / skipped / resumed。`ship` 返回明确失败且原因不在源码包时，再用 `prepare_upload` / `complete_upload` / `deploy` / `status` 单步排查。
2. **反读部署**：`business_ui_manage(action="get")` 核对部署已写进当前草稿；记下 `deployment_id`、`source_sha256`、`deployed_scaffold_version`。返回里的 `entry_url` 是开发者容器地址，只用来核对绑定，不打开、不发给任何人（口径见 [../reference/部署与版本.md](../reference/部署与版本.md)「部署状态与入口」）。`deploy` 返回带 `scaffold_upgrade_notice` 时原样记进开发记录，交付报告要写。
3. **真跑一次**（有模型行，或路线要写库、调外部接口时做；只有规则步骤且冒泡已覆盖时可省，省了写明原因）：确认页已列的费用与副作用直接执行，跑完告诉开发者实际花费；确认页没列、会对外发送或写正式数据的先说明再执行：
   1. `manage_goalfymax_project(action="run", task_id, idempotency_key, scenario_package_ids=[<场景包当前草稿或上线版本的物理行 ID>], submit_data={…}, business_ui_id=<有应用数据要写时才传>)`。带 `business_ui_id` 的真跑只认已上线的应用版本：首版应用还没定版时，先 `business_ui_manage(action="finalize")` 上线再跑——上线只换开发者自己的自测入口，使用者只能看到发布管理页发布过的版本，不是正式发布；路线不写应用数据就不传 `business_ui_id`，不需要先上线；
   2. `manage_goalfymax_project(action="wait", project_id)` 等到终态，中途表单或审阅用 `reply`；返回的 `route_runs` 给出各路线运行时状态（路线完成后项目可能仍显示 running，以 `route_runs` 为准），`succeeded` 表示这条路线真跑通过，结单门会把它记为这条路线的证据；
   3. `get_project_execution_logs(action="workflow_trace", project_id)` 看每步，模型行的输出人眼核一遍；
   4. 写库的结果去应用数据管理页或库里查一条。
   失败在同一草稿改再跑；每次只改一处，不同时改脚本和路线。
4. **先按客户验收条目自查**：逐条对照 G3 的客户验收条目，用真跑的项目、日志和应用库数据核对每条「最后拿到什么」「怎样算过」，记「通过 / 偏差 / 待开发者验收」和证据；偏差先改再部署。只核对你能拿到证据的部分，页面上的样子和操作留给开发者验收。
5. **交给开发者验收**：把客户验收条目原样发给开发者，请他**以目标客户的身份**在开发者中心右侧「在线试用」里从首页进入，逐条照做、对照设计，回复每条通过还是哪里不一样；只说「页面能打开、表单能跑」不算验收。「在线试用」——它用绑定的 `business_ui_id` 换一次性凭据，带真实身份和真实路线；草稿部署成功就能打开，不需要先上线。说明能操作什么、数据写在开发工作集里、哪些是示例数据、预览里的真实付款和授权是真的。你不开 Codex 内置浏览器或任何浏览器去打开「在线试用」、正式入口或登录页替开发者点；你的证据来自部署状态、真跑与日志（见 [../reference/开发者中心与工作区.md](../reference/开发者中心与工作区.md)「看页面只用开发者中心」）。
6. **按反馈改**：开发者提的改动改完重新 `verify:release` 并部署；改了场景包草稿的重新部署即可，不用上线。应用已上线过、挂载钉在旧版本号时，先 `business_ui_manage(action="update", business_ui_id, scenario_pack_id, scenario_pack_version=<场景包草稿版本号>)` 换挂到草稿再部署，否则预览仍跑旧的上线版本。
7. **人判项**：按 [../checklists/验收清单.md](../checklists/验收清单.md) 逐条写「通过 / 不适用 + 一句依据」，做不到的列为未验证项。

## 3. 产出与落盘

- 工单 checkpoint：场景包草稿或上线版本、`deployment_id`、`source_sha256`、`deployed_scaffold_version`、真跑的 `project_id` 与结论、开发者确认预览的原话、未验证项。
- 本段阶段文档写客户验收条目与验收清单的逐条结论：通过 / 偏差（偏差写差在哪、怎么改的）/ 未验证。
- 方案页：「在线试用」可打开时 `status` 为 `waiting`，`.pv-you` 写「在『在线试用』里验收这几项」；入口、权限、部署问题推进不了时为 `blocked` 并写 `.pv-owner`；客户验收条目逐条进「验证情况」：开发者照做通过的移入「已验证」，证据写部署编号与验收原话时间；有偏差或没走到的留在「未验证」并写原因。
- 阶段标记：G6 `passed`。

## 4. 给开发者看什么

「在线试用已部署：请以 <目标客户角色> 的身份，在开发者中心右侧『在线试用』里从首页进入，按下面 N 条逐条照做，告诉我每条通过还是哪里和设计不一样。要改哪里直接说；都通过就回复『可以上线』。」附客户验收条目与未验证项清单。

## 5. 出口

- 最近一次部署 `status=success`，预览入口可用；
- 客户验收条目逐条有结论，开发者以目标客户身份照做过；
- 开发者明确确认预览（说「可以上线」或等价表述）；
- 验收清单逐条有结论，未验证项已记录。

## 6. 出问题怎么办

| 现象 | 先看 | 回到 |
|---|---|---|
| 部署 `status` 失败 | 返回里的构建日志尾部；本地先 `npm run verify:release` | G5 |
| 部署被脚手架闸门拒绝 | [../reference/脚手架与预置件.md](../reference/脚手架与预置件.md) 错误码表 | 升级后重来 |
| 「在线试用」打不开或提示未就绪 | `PREVIEW_NOT_READY` 表示当前草稿没有部署成功的记录：在当前草稿行重新 `ship` 到 `success`；再核对 `business_ui_id` 与环境是否一致。`ship` 已成功仍未就绪才报平台问题 | 本段第 1 步 |
| 定版前 `resolve` 报「还没有上线版本（只有草稿）」 | `resolve` 只认上线版本，定版前本来就这样报；草稿验收走开发者中心「在线试用」，不记 platform_blocked，也不为拿入口去 finalize | 本段第 5 步 |
| 真跑卡 `waiting-input` | 用 `reply` 回表单；没人答就是正常挂起 | 本段 |
| 真跑内容不对 | 模型行提示词或输出字段 | G4 |
| 页面行为不对 | 页面块或生成页 | G5 |
| 真跑返回 `BUSINESS_UI_NOT_ONLINE` | 传了 `business_ui_id` 但应用从未定版；先 `business_ui_manage(action="finalize")` 上线再跑，不记 platform_blocked | 本段第 3 步 |
| 疑似平台问题 | `submit_dev_feedback` 报上去，绕过后继续 | — |
