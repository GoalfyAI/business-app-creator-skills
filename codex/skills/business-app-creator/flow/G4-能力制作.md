# G4 能力制作

按 G3 的资产清单造场景包里的能力：工具集 → FA → 编排型 TPE → 路线。每条 TPE 用 verify 出报告，每条路线冒泡到终态。对开发者只说「某功能做好了」。

## 1. 进入条件

- G3 出口：编译结果与确认页一致。
- 从修订进来时，先取可编辑草稿（`ensure_draft` 或 `ensure_editable_asset_draft`），只改受影响的资产。

## 2. 做什么

每一步的参数以工具当前 Schema 为准，这里只给顺序和必带项。

1. **场景包草稿**：新建 `scene_package_manage(action="create", task_id, name, description, apc_skill)`；已有包用 `ensure_draft`，官方或他人的包先 `clone_asset`。`apc_skill` 用开发者的词写「这个包能做哪几件事、各自什么时候用、发起前要收齐什么」，1–4k 字，不写资产 ID。
2. **接入缺的工具**（G2 判定要接入时）：按 [../reference/依赖与MCP接入.md](../reference/依赖与MCP接入.md) 先预览再注册，需要最终用户各自授权的配授权卡。
3. **FA**：每条模型行一个 `create_fast_agent(name, description, prompt_content, …)`。提示词写清输入字段、输出对象每个字段的含义和非成功状态；输出要给部分成功留出口（见 [../reference/编排脚本.md](../reference/编排脚本.md)）。建完 `get_asset(asset_type="fast_agent")` 反读 `mr_name`，脚本里用这个名字，**禁止**自己拼前缀或用数字 ID。
4. **工具集**：把 G2 核实过的工具组、FA 装进 `create_toolset(name, description, tool_group_ids, fast_agent_ids)`；一条路线通常一个工具集。本轮新建或导入的工具集做一次安全的运行时测试后 `online_toolsets`，再 `get_asset` 反读确认全部上线——离线工具集运行时加载不到。
5. **编排型 TPE**：脚本按 [../reference/编排脚本.md](../reference/编排脚本.md) 三种模板之一改，第一次写之前读 `get_diagnosis_doc(topic="otpe_single")`。`otpe_manage(action="preview", task_id, script, input_schema, output_schema, business_event_contracts, preload_toolset_ids)` 通过后 `create`（同一组参数加 `scene_package_id`、`name`、`description`），再 `online`。事件契约最少两条：`stage_started` + `stage_result`。
6. **verify**：`otpe_manage(action="verify", task_id, tpe_id)` 看 `verdict`：`blocked` 按 `failed` 项改后重来；`needs_bubble` 说明静态项都过了，只差冒泡证据。
7. **单条冒泡只用于多节点路线的单节点调试**：路线只有一个节点时跳过这一步，直接做第 8、9 步。多节点路线里某个节点要单独调通时，`otpe_manage(action="bubble", task_id, tpe_id, workflow_input=<代表性输入>)` 拿 `run_id`，只传 `run_id` 续等到终态，再 `verify(tpe_id, run_id)`。
8. **路线**：`scene_package_manage(action="assemble", task_id, scene_package_id, tpe_ids=[按顺序], orchestration_id, title, entry_form_id)` 得到草稿；处理 `unresolved`（类型不一致、输出为空）与 `notes`，再把 `workflow_orchestration` 原样传给 `scene_package_manage(action="update", scene_package_id, workflow_orchestration)` 保存。分支、并行、中途表单、Agent 接管按 [../reference/业务路线.md](../reference/业务路线.md) 手写接缝。
9. **路线冒泡一次**：`scene_package_manage(action="bubble", task_id, scene_package_id, orchestration_id, workflow_input)`；续等只传 `run_id`，回填中途表单传 `run_id + formdata`。到终态后对路线里每条 TPE 调 `verify(tpe_id, run_id=<路线冒泡的 WRV- run_id>)`，它按 `tpe_id` 取该节点的结果，`passed` 即完成，不必再单独冒泡。每条路线一个正常样例；有明确边界规则时再加一个边界样例；改了脚本或路线才重新冒泡。终态记 `run_id` 进工单，一条路线一条 checkpoint。

**冒泡的边界**：冒泡里 FA 是桩（按输出 schema 造值），工具、shell、文件照常真实执行，只有脚本按 `ctx.dry_run` 判断的外部动作被跳过。桩值导致下游失败、或模型行的真实输出需要验证时，先向开发者说明费用并取得同意，再对同一路线加 `full_run=true` 重跑一次。

**参数由谁填**：事件契约、`_output`、`_rationale` 在脚本模板里已有位置，只改业务词；入口映射、节点映射、交付映射由 `assemble` 生成，你只审 `unresolved`；`tpe_id`、`scene_package_id` 来自上一步返回值，记进工单，不手抄。

## 3. 产出与落盘

- 工单 checkpoint：场景包草稿 ID、每个新建资产的 ID 与 `mr_name`、每条 TPE 的 verify 结论、每条路线的冒泡 `run_id` 与终态。
- 本段阶段文档记录资产清单的实际结果与 verify 报告摘要。
- 方案页「进度」一节：哪些功能的能力已经做好。
- 阶段状态：G4 `passed`，G5 `in_progress`。

## 4. 给开发者看什么

每做好一条路线说一句：「投放诊断已经能跑通，用示例数据试过一次」；冒泡里模型结果是占位的，要说明「内容效果留到预览时用真数据看」。

## 5. 出口

- 每条编排型 TPE：最近一次 `verify` 的 `verdict=passed`（带路线冒泡或单条冒泡的 `run_id`）；
- 每条路线：以当前合同下最近一次冒泡到终态，`success` 的 `run_id` 已记入工单；失败的已修好重跑，或已按 [G7-上线交付.md](G7-上线交付.md) 的结单门说明原因。

## 6. 出问题怎么办

| 现象 | 先看 | 回到 |
|---|---|---|
| verify `static_contract` 失败 | `errors[].where/msg`，多半是 `_output` 形状或事件契约 | 本段第 5 步 |
| verify `toolsets_online` / `tpe_online` 失败 | `online_toolsets` / `otpe_manage(action="online")` | 本段第 4、5 步 |
| 冒泡失败 | `steps[].error`；`repeated_error_count>=2` 换策略，不原样重跑 | 本段 |
| 冒泡没到终态 | 服务端最多等约 45 秒，用同一 `run_id` 续等，不要重新发起 | 本段 |
| 以为 FA 用了回执顶层的模型 | 顶层 `resolved_model` / `resolved_mode` 是这次验证运行（外层 SA）的模型和模式，不是编排里 FA 的模型；编排中的 FA 按其资产配置的 `model_name` 运行，用 `get_asset(fast_agent)` 查看 | — |
| 路线保存被拒 | 按返回的节点、字段、路径错误改同一个对象 | 本段第 8 步 |
| 编译结果做不出来 | G3 清单与 G2 对照表 | G3 或 G2 |
| 其他报错码 | [../reference/报错对照.md](../reference/报错对照.md) | — |
