# G7 上线交付

> **Studio**：上线授权按 [SKILL.md](../SKILL.md) 的 Studio 约定执行，复用下文的版本、预览数据、定版和结单检查。目录发布使用当前实际提供的 MCP 能力；缺少动作时说明缺口，不编造接口。
> 分别报告定版、目录发布和正式运行的实际结果；Studio 在线预览只展示已发布版本。本次要求的发布或验证未完成时，不宣称该项交付完成。
> 写入结果未知时只查询原操作，不重新发起写入。

开发者说「可以上线」后定版应用、过结单门、写交付报告。目录发布由开发者自己在发布管理页操作。定版只有属主能做；协作者按第 2 节「协作者分支」提请属主定版。

## 1. 进入条件

- G6 出口：开发者已确认预览，未验证项已记录。
- 上线是外部状态变更：只有开发者这次明确说了「可以上线」或等价表述才执行。
- 已用 `business_ui_manage(action="get")` 确认当前 `role`：`owner` 走第 2 节第 1–8 步；`editor` 走「协作者分支」；`viewer` 不进 G7。

## 2. 做什么

1. **场景包版本核对**：G6 之后改过场景包的，重新部署应用，让预览跑的是最新草稿。场景包不用单独上线，下一步定版应用时会先校验、再把挂着的本人场景包草稿一起定版上线。
2. **定版前自查预览数据**：预览里确认过、上线后还要用的设定是否只存在工作集数据里；是的话先按 G5 第 5 步搬到代码默认值、场景包配置或首次设置入口，重新部署后再定版。
3. **定版应用**：`business_ui_manage(action="finalize", draft_asset_id=…, task_id)`；有协作者时家族里可能同时有多份草稿，这时**必须**显式传要定版的那份 `draft_asset_id`（先用 `business_ui_manage(action="get")` 看草稿、创建人和变更说明，和开发者确认是哪一份），只传 `business_ui_id` 会被拒，平台不替你挑。场景包草稿随它一起上线，定版后反读两者的版本号记进工单。被拒按 [../reference/部署与版本.md](../reference/部署与版本.md) 的定版错误码处理。
4. **反读**：`business_ui_manage(action="resolve")` 核对上线版本与挂载的场景包版本，`entry_url` 非空说明入口已写进版本；resolve 报没有上线版本说明定版没生效，**禁止**宣称已上线。`entry_url` 是开发者容器地址，**禁止**写进交付报告或发给开发者、使用者当入口。
5. **目录发布提示**：告诉开发者在发布管理页发布；上线只影响开发者自测，没发布时使用者打不开（`BUSINESS_UI_NOT_RELEASED`）。上线后开发者本人已能从「我的资产」进正式入口正式使用；有自动化的应用，真实到点规则在这里开（见 [../reference/自动化.md](../reference/自动化.md)「验证」）。
6. **结单门**：每条路线要以当前合同下最近一次到终态的运行通过，路线冒泡和真跑都算（真跑以 `route_runs` 里该路线 `succeeded` 为通过）。最近一次失败或没法验证时，先问开发者是否接受，再写（真跑失败时 `run_id` 填那次的 `project_id`）：

   ```text
   task_manager(action="insert", entry_type="checkpoint", metadata={"evidence_type": "route_verification_waived", "scene_package_id": …, "orchestration_id": …, "reason": "<至少 5 个字>", "run_id": <失败那次；没跑过就不带>})
   ```

   新路应用把 `scene_package_id` 换成 `business_ui_id` 与 `business_ui_version_id`（冒泡或真跑回执里的提交号）。新路应用没有场景包，第 1、3、4 步里的场景包核对改为核对应用版本上挂的编排与 `tpe_ids`；定版发布的其他差别见 [../reference/新路应用.md](../reference/新路应用.md)「定版与发布」。

   一条路线一条。`complete` 被拒（如 `WORKFLOW_TASK_ROUTE_BUBBLE_EVIDENCE_REQUIRED`）时按返回里逐条给的出口做，**禁止**删标签、改文字或另开工单绕过，也不要反复重试。
7. **交付报告**：写进工单 `task_manager(action="insert", entry_type="result")`、方案页和发给开发者；写一条 G7 阶段记录 `business_ui_stage`（`next_stage="closeout"`，`SKILL.md` 第 5 节），然后 `task_manager(action="complete")`；结单响应里的 `delivery_note` 原样补进报告。本轮记下的已绕过平台问题和功能诉求，此时汇总成一条 `submit_dev_feedback`（`blocking` 按主要情况选 `worked_around` 或 `request`），没有就不提；已有同一反馈优先按 `feedback_code` 追加，报告优先写回执 `code`，`source_code` 另注为来源别名。缺完整身份或写入 `unknown` 按 [../reference/报错对照.md](../reference/报错对照.md) 核对，不写成已提交成功。
8. **开发工作集保留**：上线后开发工作集继续绑定在应用上，**不要**解绑、不要为它重新 `deploy`、不要 `close`。开发版（在线试用）只能连工作集，下次修订改表结构也在这个工作集上改（见 [../reference/数据模板.md](../reference/数据模板.md)「改已上线的模板」）；它只给开发者用，改它不影响使用者各自的实例库。解绑后 `deploy` 会报 `BUSINESS_UI_PREVIEW_DATA_UNBOUND`，`close` 会被 `TEMPLATE_WORKSPACE_IN_USE_BY_DEPLOYMENT` 拒绝，遇到说明走错了，重新 `bind` 回原工作集即可；**禁止**为此 finalize 派生出来的草稿、下线或删除应用。工作区用 `workspace_push` 保存到云端。

**协作者分支**（`role=editor`）：第 1、2 步照做；第 3–5 步换成 `business_ui_manage(action="request_finalize")` 提请属主定版，做法与报错见 [../reference/多人协作.md](../reference/多人协作.md)「提请定版」；**禁止**调 `finalize`、`resolve` 冒充上线，也不做目录发布。第 6、7 步照做，交付报告「应用」一行写「已提请，等属主定版」和草稿版本、变更说明，不写上线版本；第 8 步不涉及。属主处理协作者的提请时，`draft_asset_id` 用那份协作者草稿，其余照第 1–8 步。

## 3. 产出与落盘

交付报告结论先行，每一句「已验证」都能指到证据，至少包含：

| 项 | 内容 |
|---|---|
| 应用 | 名称、上线版本、是否已在目录发布 |
| 部署状态与入口 | 部署状态（`success` 与 `deployment_id`）和怎么打开分开写：开发者自测在 GoalfyMax → 我的资产 → 智能应用 → 打开（正式入口 `/business-ui/<家族 ID>`，不需要发布）；使用者要等发布管理页发布后从目录打开。不写容器地址 |
| 场景包 | 定版时钉住的版本；已验证的路线与冒泡 `run_id`；豁免的路线与理由 |
| 数据模板 | 模板 ID 与版本 |
| 部署 | `deployment_id`、`source_sha256`、`deployed_scaffold_version`；低于建议线时写「当前 vX 低于建议线 vY，建议下一轮升级」 |
| 真跑 | `project_id` 与结论，或省略的原因 |
| 验收清单 | 通过项数、不适用项、未验证项 |
| 运行说明 | 用户首次打开时按模板建自己的库；无流量实例会缩容，首次访问稍慢 |
| 已知限制 | 未验证项、能力缺口、下一步建议 |

阶段标记：G7 `passed`。方案页 `status` 改为 `done`，`.pv-summary` 写上线结论；「已验证 / 未验证」与交付报告一致。

## 4. 给开发者看什么

交付报告本身；再加一句「已上线，你可以在 GoalfyMax → 我的资产 → 智能应用里打开它自测（正式入口，用你自己的应用库，定时任务也在这里开）；去发布管理页发布后，使用者就能在目录里看到」。不附任何容器地址，也不要把「预览」按钮当成上线后的自测入口。

协作者分支只说：「已提请，等属主定版。属主定版后才会上线，发布到目录也由属主操作；属主先定版了别人的草稿时，你会收到基线过期的通知，需要先合并再提请。」

## 5. 出口

- `resolve` 能取到上线版本，且 `entry_url` 非空（协作者分支改为 `request_finalize` 成功）；
- `task_manager(action="complete")` 成功；
- 交付报告已写入工单与方案页。

## 6. 出问题怎么办

| 现象 | 先看 | 回到 |
|---|---|---|
| 定版被拒 | [../reference/部署与版本.md](../reference/部署与版本.md) 定版错误码 | G6 或 G5 |
| `BUSINESS_UI_FINALIZE_OWNER_ONLY`、`PERSONAL_VERSION_STALE_SOURCE` 或提请被拒 | [../reference/多人协作.md](../reference/多人协作.md)「协作相关报错」 | 协作者分支或基线过期的合并 |
| 结单被拒 | 返回里的路线状态；补一次路线冒泡或真跑，或写豁免 | G4 或 G6 |
| 开发者上线后要改 | [../tasks/修订.md](../tasks/修订.md) | — |
| 要下线、回滚、删除 | [../reference/部署与版本.md](../reference/部署与版本.md)，每一步都要开发者确认 | — |
