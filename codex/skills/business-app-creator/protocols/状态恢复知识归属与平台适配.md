# 协议四：状态恢复、知识归属、模板选用与平台适配

> 共享协议层。工单是唯一能跨轮次续作的载体；知识分两类、问题分两类；不内置业务模板；平台对象与执行形态的正本在 references。

## 1. 工单记账与续作

`task_manager`：`create` / `get` / `list` / `insert` / `complete`。

**Gate**：新的制作或优化任务 `create(mode="write")` 并传 SKILL.md frontmatter 里 `[skill-version:...]` 的完整值；只读诊断 `create(mode="read")`；已知 `task_id` 续作 `get`；不知道先 `list`，唯一匹配则 `get`，无匹配才 `create`，多个候选交开发者；只读转修复新建 `write` 并传 `continued_from_task_id`。`read` 工单不得写。Gate 失败按 `reason`：`SCENE_SKILL_UPGRADE_REQUIRED`（本会话升级后用已安装 SKILL.md 的版本串重试）、`SCENE_SKILL_UPGRADE_RECOMMENDED`（不阻断）、`WORKFLOW_TASK_MODE_MISMATCH`（按 `actual_mode` / `required_mode` 纠正）；不新建平行工单或改名绕过（细则 P8 的 SD §4.7）。

**失忆测试**：写入前问"下一轮只剩这份工单还能不能接着干"——不能就必须写，能就禁止写。必须记：影响后续判断的材料与核心结论、事实边界、业务假设与理由、关键决策、资产标识与名称、里程碑、理想态、验证证据摘要、U 行为分阶段结论。禁止记：密钥、Cookie、临时上传地址、原始敏感日志、供应商完整输出、本机路径、整篇正文。数量精确，缺口如实写。

**阶段出口落账 `stage_exit`**：出口条件逐项状态与证据指针（只写指针）。续作先找最新 `stage_exit` 定位流程位置，再拉表快照定位内容进度，再按 SKILL.md 路由进入阶段并完整读取阶段文件；恢复后先反读工单里记录的资产当前状态，不沿用旧记录当现状；从最早未满足的必要条件进入，不机械从 G1 重做。

## 2. 两类知识、两类问题，分开存放

| 类 | 内容 | 绑定到 | 不进入 |
|---|---|---|---|
| 领域知识 | 业务规则、案例、来源、适用范围、生效时间 | 运行时真正需要它的执行者（apc_skill / 场景 Skill 文件 / FastAgent 提示词 / 工具集使用指南；能力容器里的文件不天然对 FA 可见，见 P3 的 S3 §8） | 平台文档 |
| 开发知识 | 工具接入、契约坑、SDK / 部署故障与可复用修复 | 平台与版本（同行业经验库、开发知识库） | 终端用户业务资料 |
| 业务应用问题 | 表现、输入、产物、版本、根因、改进目标 | 路由到 G1–G7 相应阶段（P8） | — |
| 平台 / Skill 问题 | 可复现证据、受影响版本、临时处置、修复状态 | 统一问题台账（收集 → 分类 → 跟进 → 验证 → 回流；状态 待整理 → 已确认 → 处理中 → 待验证 → 已解决；临时绕过不算解决） | 每个应用的私有补丁 |

同行业经验库三类条目：业态知识、关键问题、参考经验；每条带适用条件与时间；个别用户的选择不当作业态通用规则；展示按当前场景筛选；过期标"待复核"。G1 提问前、G3 识别决策前先查。

## 3. 优化能力与"优化已经有效"分开

开发期必须设计并验证：反馈来自哪里、关联哪份输入 / 产物 / 版本、修改是纠错还是偏好、适用范围与撤销、下一次哪个节点使用、如何做可比对照。公共策略或模型 / 工具 / 编排变化属于开发变更，进入相应阶段并回归；用户明确的长期偏好属于应用数据行为，在授权范围内生效；单次修改不自动升级为长期偏好。长期收益要上线后的实际样本证明。

## 4. 模板选用

不在脚手架里内置多套业务模板：粗浅业务 AI 自己能写，复杂专业业务我们不具备业务能力。业务应用是把业务方专业知识与 AI 结合的框架；脚手架 demo 只用于理解协议（协议一 A10）。产品经理式改进走 P8 的提案制：Agent 提出改进提案 → 业务方审核 → 修改 → 再审核发布，不绕过业务方改线上。

## 5. 平台适配

- **命名口径**：产品叫**业务应用助手**；插件 / 市场 / 仓 `business-app-creator`，MCP `business-app-creator-mcp`，本 Skill `business-app-creator`。交付给用户的是**业务应用**；**场景包**只是它在平台里的能力容器（挂载工具集、任务点、业务路线与知识），只在工具调用和资产关系里出现；"场景包助手"是旧称。任务点（TPE，Task-Point-Event）两型：普通 TPE（派给 TaskAgent 临场执行）与编排型 TPE（O-TPE，确定性脚本编排工具与 FastAgent）；"Workflow"是编排型 TPE 的旧称；MCP 工具 `otpe_manage` / `otpe_tool_test`，诊断文档 topic `otpe_*`。平台契约字段（`tpe_type=workflow`、`workflow_orchestration`、`workflow_runtime_id` 等）不改名。
- **三个不能混的概念**：有业务路线的能力容器才能有业务应用（每个入口是一条路线）；一个 `business_ui` 恰好挂一个能力容器加至多一个数据模板，契约全部来自它；业务应用 ≠ 能力容器。
- **平台对象与执行形态**：正本 [平台对象与运行模型](../references/平台对象与运行模型.md)；标识与版本术语 [工具标识与版本术语速查](../references/工具标识与版本术语速查.md)；版本体系 [场景包版本体系与发布逻辑](../references/场景包版本体系与发布逻辑.md)；依赖接入 [依赖与MCP接入](../references/依赖与MCP接入.md)。平台运行契约只通过实时 Schema 与 `get_diagnosis_doc` 获取。
- **脚手架正本**：根 `README.md`、`frontend/README.md` 与 `frontend/CLAUDE.md`、`frontend/docs/business-ui-guide.md`、`frontend/schema/README.md`（契约区 v4）、`frontend/schema/api/`（公开接口 OpenAPI，一接口一文件）、`frontend/src/sdk/docs/`、`backend/README.md`、`frontend/docs/dev-host-testing.md`、`frontend/docs/message-guide.md`；官方前端 guidance 副本在 `references/前端设计指南/`。
- **手工版与平台版**：案例库、步级记分、判定器校准、裸跑探针、差分归因、人工任务、回退链、确认即标注、再分配建议、问题台账、可视化工作台——首发一律按手工版执行（结果检查表加列、人工填表、FA 评分加人工校准、脚本分支、中途表单收人工结果、工单评论 + OA），平台机制建成后替换；Skill 不承诺平台没有的能力。
