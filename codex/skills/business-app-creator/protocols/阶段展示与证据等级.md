# 协议三：阶段展示与证据等级

本协议回答两件事：每个阶段给开发者看什么；什么证据能证明什么。

## 1. 展示不是追加一份长报告

默认只展示三样：**本阶段结论、关键证据、当前待决定项及其影响**。开发者需要时再展开实现细节。每个阶段文件的"给开发者看什么"一节规定默认视图；技术实现映射可展开查看。

按阶段递进的默认视图：G1 业务概述、产物样例、业务路线草图；G2 工具候选与推荐、能力实测结果摘要；G3 完整业务样例、正式路线、费用说明与可点原型；G4 业务模块开发进度与部件效果；G5 整条路线打通情况与真实结果；G6 可操作的真实应用、一次旅程演示与可选美化；G7 交付摘要。共用必备内容见第 7 节，按阶段逐步补齐，不要求在早期编造后续结果。

每条展示的内容标来源类型，只有四种：**事实**，材料或反读里有；**推断**，你按常识得出；**未知**，需要验证；**质疑**，你的反向意见。

面向开发者的方案只说能解决什么问题、分几个阶段、每个阶段产出什么、有哪些候选、推荐理由、哪些事项需要开发者决定、未来哪些节点由最终用户参与。**禁止**在业务方案里出现资产数字 ID、技术字段名、代码片段、内部调用链；技术细节只进入工单记录，或开发者明确要求的技术说明。涉及多个同类资产时，内部记录每次提及必须带 ID 消歧，业务方案改用名称。

| | 写法 |
|---|---|
| 达标 | "在数据采集阶段，系统会自动拉取最近 7 天的数据" |
| 达标 | "完成分析后会暂停，让你确认报告准确性，再进入下一步" |
| 不达标 | "调用 get_douyin_video_list 工具，参数 date_range=7d" |
| 不达标 | "创建 FastAgent: novel_plot_analyzer，关联 tool_group_ids=[7,8]" |

涉及多个同类资产时，内部记录里每次提及**必须**带 ID 以消除歧义；面向开发者的业务方案里改用名称。

## 2. 同一事实的不同视图

业务规则与公开契约保持唯一权威来源。各视图引用同一节点或承诺编号，**禁止**维护多份"审核逻辑"。以节点"审核经营结论"为例：G1 看哪条结论缺依据、怎样算合格；G3 看自动核数与负责人判断各负责什么、退回走哪里；G4 看核验输入、规则、实际判断与反例；G5 看此次审核在哪个运行实例发生、结果如何冻结入库；G6 看待审内容、可操作项、修改影响、旧版本；G7 看对应承诺是否通过、证据属于哪个版本。

## 3. 开发者怎么说"不对"

四种方式：直接改文字或样式；选中批注；在路线图节点上写流程反馈；操作记录。每条自动带页面、步骤、版本上下文。你收到后先判断改的是文字、样式、数据、流程还是承诺。只有影响流程、数据、权限或承诺的才回问范围。改完回报实际修改与验证结果，可撤销。

方案不对时，开发者也可以直接在开发者中心旁边的开发对话中说明；由你关联当前方案步骤与版本，同步修改方案并回报变化。只使用当前宿主已支持的反馈入口；不要把应用运行界面内嵌项目对话、自动关联对话等后续产品能力说成已支持。

## 4. 证据强度

按证据能证明什么判断，**不按**材料数量判断。

| 证据 | 可以证明 | 不能证明 |
|---|---|---|
| 已确认样例、规则、行为演示 | 双方对预期的理解一致 | 平台已具备能力 |
| 真实资产反读、Preview、静态契约检查 | 保存内容、引用和结构成立 | 真实模型内容合格；业务运行成功 |
| 安全工具取样、代表性能力实测 | 该环境、输入、版本下该能力的表现 | 所有输入和整条路线正确 |
| 单条或路线 Bubble | 具体覆盖路径的管路与控制接缝 | FastAgent 桩对应的内容质量；被屏蔽的副作用 |
| 应用本地链路真跑 | 当前界面经 SDK 实际命中本地后端，且请求限制、测试身份、超时、响应上限与信封符合当前脚手架契约 | 平台寻址、真实身份、真实 schema、部署网络成立；仅打开 Goalfy 或看到预览不算此证据 |
| 真实路线执行 | 实际派发、模型与工具输出、表单、交付与审阅 | 应用页面正确；用户实例的数据回流正确 |
| 真实应用实例与浏览器操作 | 当前应用版本的使用与数据闭环 | 长期业务收益已改善 |
| 可比条件下的效果对照 | 特定范围内的改进证据 | 不同人群、未覆盖任务普遍改善 |

后端接口测试、本地链路真跑、预部署验证、上线反读是四种不同证据，**禁止**互相替代，也**禁止**用其中一种的通过去顶另一种的缺席。

状态词只有五个：**待验证、通过、失败、阻断、不适用**。不适用必须说明理由。已知偏差必须写范围、影响、接受人。越权、数据串用、未完成却报成功三种底线**不得**豁免。

## 5. 失败怎么展示

验证失败时返回明确的问题归属与证据，归属只有五类：单元、路线、数据、页面、平台。**禁止**把失败转述为"请开发者自行处理"。测试不通过时展示失败证据与修复路径；开发者同意继续**不改变**测试结果。

## 6. 质量、耗时、费用的口径

成功率分两种：技术成功，即无报错；业务成功，即判定通过。耗时用 p95，并拆分模型时间与工具时间。费用按每次成功交付计，含失败重试与最终用户的确认时间折算。稳定性看同一输入多次结果的一致率。事实与估算分栏；估算必须标假设。

## 7. 展示物的载体：一份 HTML 给开发者，md 给 Agent

开发者中心右栏「方案」只渲染**一份 HTML**：应用工程根下 `docs/proposal/index.html`，一个应用一份，由你从零写并持续维护。这个路径是脚手架写死的渲染入口，**禁止**改名、改位置，也**禁止**把它拆成多份等着工作台去找。这一页所有自带的东西都放在 `docs/proposal/` 下：截图进 `docs/proposal/screens/`，原型页要拆成单独文件的进 `docs/proposal/`，一律用相对路径引用，**禁止**指到这个目录外面。它的读者是**不懂平台资产的开发者**，只回答两件事：**业务过程**，这个应用替谁、按什么过程把事做成；**开发内容**，我们正在把它做成什么、现在做到哪里。原始测试记录、技术证据、工单与部署日志留在 `docs/stages/` 的七份阶段 md 里给你和后续 Agent 用；业务进度、关键效果、阻断与交付摘要要在 HTML 上可见。两者同时维护：md 记事实与证据，HTML 从同一事实提炼结论与取舍，不另造一套状态。

**顶部必有承诺清单块。** 应用名、当前阶段、版本之下，一条承诺一行，业务语言一句话加状态，状态用第 4 节的五个词。它就是协议二第 1 节那张清单的展示版，编号、证据指针、工单标签这些开发者用不上的列不上页面，只显示承诺本身和它现在到哪一步了。承诺状态一变就改，开发者据此一眼看出这个应用答应了什么、兑现了几条。

**这一页是一个结构体，不必是一条长滚动。** 内容多了就分栏：顶部留一排入口，业务过程、开发内容、页面原型各占一个，点哪个看哪个。分几栏、叫什么名字由你定，只有一条要求：**入口必须在顶层可见**，开发者一眼看到有哪几部分，不用滚到底才发现还有东西。承诺清单块常驻顶部，**不进**任何一栏，切到哪都看得见。切换用内联脚本或纯 CSS 实现；所有内容都写在这一份文件里，脚本失效时退化成一页长文仍然能读完，**禁止**把内容藏在要现取的地方。

**固定必要内容，不固定视觉模板。** 除顶部承诺清单外，下列内容按阶段形成并持续保留；布局、栏目名称及额外说明可按业务设计，不要每次自由发挥到漏掉必备项：

- **业务概述与路线图（G1 起）。** 给谁做、为什么值得做、什么算合格、什么不做；用业务语言画出每一步，说明需要用户提供什么、系统做什么、产出什么、谁决定，以及为什么这样安排。G1 是草图，G3 收敛为正式路线。
- **能力选择与费用（G2 起，G3 汇总）。** 将工具或服务候选挂到对应业务步骤，比较实际能做什么、限制、收费及接入条件，给出推荐与理由、待选择项。只列有依据的候选，不凑数量。标清哪些步骤调用 Agent，哪些由规则或工具直接完成，哪些需要人确认；分别说明平台积分和第三方费用的触发条件、承担方与已知计费口径。未知写待核实，估算写假设；不把“不调用 Agent”写成“一定免费”，不编造固定价格。
- **业务草图与实际效果（G3 起）。** 用完整业务样例串起流程、所选能力和可点页面原型，展示业务数据及主行动。明确标注假数据原型；G6 给真实应用入口和操作演示，标明环境、版本与已验证范围，不把原型冒充已实现应用。
- **开发进度与交付（G4 起）。** 按已确认的业务模块说明正在做什么、哪些并行、哪些完成、哪里阻断、下一步是什么；用实际结果摘要说明完成情况。开发活动与第 4 节的验证状态分开，写完代码不等于验证通过；不虚构进度百分比。G7 留下交付入口、版本、已实现能力、使用限制、费用提醒及遗留事项。

**开发者决定业务取舍，不承担接入排障。** 安装、连接、配置等在已有授权范围内由你处理；确需本人登录、授权或付费时，说明原因、权限或费用影响、最短操作入口及是否阻断。工具方案被选中不等于获得授权，更不等于已接通；不得绕过本人授权或代为同意收费。

**把思考深度展现出来。** 页面不是结论清单。每个关键结论旁边写清你是怎么判断的、当时有哪几条路、为什么否掉别的、这个判断错了会怎样、什么信号出现就要回头改。开发者据此才能判断你有没有想到位，也才知道该在哪里插手；只给答案不给取舍，他既无从确认也无从反驳。展开的是判断过程与依据，不是把 md 里的数据、日志、证据搬上来。

**这一页有机器校验，写坏了 doctor 直接判 FAIL。** 硬要求六条：以 `<!doctype html>` 开头；`html` 元素声明 `lang="zh-CN"`；有移动端 viewport 声明；有 `<main>` 和一级标题；正文里**必须同时出现「业务过程」和「开发内容」这两个词**；**禁止**用 `<base>` 改写相对路径基准。资源引用另有一条硬边界：`src`、`poster`、`link href` 和 CSS 的 `url()` 只能指向 `docs/proposal/` 里的相对路径，**禁止**绝对路径、协议头、`//` 开头和 `..`，页内锚点和 `data:` 不受限；截图放 `docs/proposal/screens/`。脚手架生成的骨架带一行模板标记，G1 结束前**必须**按本应用重写并删掉它，开发期留着只是警告，发布期直接判失败。

**写法纪律。** 只用业务语言，允许展示开发者选择、识别或付费所需的工具／服务产品名称；**禁止**资产数字 ID、内部节点标识、API 调用名、技术字段名、代码。待开发者拍板的事项在页面上标出，决定后改成结论。图用内联 SVG，不依赖外部脚本；不引外部样式与脚本，这既是纪律也是上面那条资源边界的硬要求；图片用 `docs/proposal/screens/` 相对路径。真实应用入口使用已反读确认的宿主预览入口或普通导航链接，不作为外部脚本、样式、图片或嵌入资源加载。

**页面原型直接做成能看的东西，不要用文字描述界面。** 从 G3 起，业务应用的每个页面在这一页里给开发者看真的界面：首选把原型页本身写成 HTML 放进"页面原型"那一栏，布局、字段、按钮、状态、空态都摆出来，开发者点得动、看得见，比读一段"这个页面有一个列表和一个筛选器"有用得多。原型只是给人看的壳，用假数据，**禁止**接任何真实接口。做不成可点原型的就放截图，截图是退路不是首选。原型的样式包在自己的容器里，类名加前缀，别污染整页。每个页面配三句话：用户在这干什么、数据从哪来、主行动是什么。每次只改受影响的部分，整份文件原子写入；工作台监听文件自动刷新，**禁止**让开发者手动刷新。

**什么时候更新。** G1 到 G3 每完成一步就更新对应内容，不攒到最后；页面顶部始终写当前阶段与当前实际版本，不提前标成上线版本。G4 到 G7 在模块开工、完成、出现阻断或关键结果时同步更新进度与效果摘要，不只改阶段号；详细运行记录仍留在 md。运行结果让路线、数据、费用或页面设计改了，同步改方案，已确认的业务过程与选型理由继续保留，方便开发者回看。
