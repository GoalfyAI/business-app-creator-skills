# 协议三：阶段展示与证据等级

本协议回答两件事：每个阶段给开发者看什么；什么证据能证明什么。

## 1. 展示不是追加一份长报告

默认只展示三样：**本阶段结论、关键证据、当前待决定项及其影响**。开发者需要时再展开实现细节。每个阶段文件的"给开发者看什么"一节规定默认视图；技术实现映射可展开查看。

按阶段递进的默认视图：G1 一页简报、产物样例、短流程；G2 实际产物对比、能力卡；G3 一个完整业务样例、业务路线图、结果或页面预览，职责有争议时加泳道图，状态容易混淆时加状态图；G4 单元的预期与实际对照、带步骤标注的脚本；G5 真实运行时间线、数据前后对照；G6 可操作的应用、一次旅程演示；G7 交付核对单。

每条展示的内容标来源类型，只有四种：**事实**，材料或反读里有；**推断**，你按常识得出；**未知**，需要验证；**质疑**，你的反向意见。

面向开发者的方案只说能解决什么问题、分几个阶段、每个阶段产出什么、有哪些候选、推荐理由、哪些事项需要开发者决定、未来哪些节点由最终用户参与。**禁止**在业务方案里出现资产数字 ID、技术字段名、代码片段、内部调用链；技术细节只进入工单记录，或开发者明确要求的技术说明。涉及多个同类资产时，内部记录每次提及必须带 ID 消歧，业务方案改用名称。

| | 写法 |
|---|---|
| 达标 | "在数据采集阶段，系统会自动拉取最近 7 天的数据" |
| 达标 | "完成分析后会暂停，让你确认报告准确性，再进入下一步" |
| 不达标 | "调用 get_douyin_video_list 工具，参数 date_range=7d" |
| 不达标 | "创建 FastAgent: novel_plot_analyzer，关联 tool_group_ids=[7,8]" |

涉及多个同类资产时，内部记录里每次提及**必须**带 ID 以消除歧义；面向开发者的业务方案里改用名称。

## 2. 同一事实的不同视图

业务规则与公开契约保持唯一权威来源。各视图引用同一节点或承诺编号，**禁止**维护多份"审核逻辑"。以节点"审核经营结论"为例：G1 看哪条结论缺依据、怎样算合格；G3 看自动核数与负责人判断各负责什么、退回走哪里；G4 看核验输入、规则、实际判断与反例；G5 看此次审核在哪个运行实例发生、结果如何冻结入库；G6 看待审内容、可操作项、修改影响、旧版本；G7 看对应承诺是否通过、证据属于哪个版本。

## 3. 开发者怎么说"不对"

四种方式：直接改文字或样式；选中批注；在路线图节点上写流程反馈；操作记录。每条自动带页面、步骤、版本上下文。你收到后先判断改的是文字、样式、数据、流程还是承诺。只有影响流程、数据、权限或承诺的才回问范围。改完回报实际修改与验证结果，可撤销。

## 4. 证据强度

按证据能证明什么判断，**不按**材料数量判断。

| 证据 | 可以证明 | 不能证明 |
|---|---|---|
| 已确认样例、规则、行为演示 | 双方对预期的理解一致 | 平台已具备能力 |
| 真实资产反读、Preview、静态契约检查 | 保存内容、引用和结构成立 | 真实模型内容合格；业务运行成功 |
| 安全工具取样、代表性能力实测 | 该环境、输入、版本下该能力的表现 | 所有输入和整条路线正确 |
| 单条或路线 Bubble | 具体覆盖路径的管路与控制接缝 | FastAgent 桩对应的内容质量；被屏蔽的副作用 |
| 真实路线执行 | 实际派发、模型与工具输出、表单、交付与审阅 | 应用页面正确；用户实例的数据回流正确 |
| 真实应用实例与浏览器操作 | 当前应用版本的使用与数据闭环 | 长期业务收益已改善 |
| 可比条件下的效果对照 | 特定范围内的改进证据 | 不同人群、未覆盖任务普遍改善 |

状态词只有五个：**待验证、通过、失败、阻断、不适用**。不适用必须说明理由。已知偏差必须写范围、影响、接受人。越权、数据串用、未完成却报成功三种底线**不得**豁免。

## 5. 失败怎么展示

验证失败时返回明确的问题归属与证据，归属只有五类：单元、路线、数据、页面、平台。**禁止**把失败转述为"请开发者自行处理"。测试不通过时展示失败证据与修复路径；开发者同意继续**不改变**测试结果。

## 6. 质量、耗时、费用的口径

成功率分两种：技术成功，即无报错；业务成功，即判定通过。耗时用 p95，并拆分模型时间与工具时间。费用按每次成功交付计，含失败重试与最终用户的确认时间折算。稳定性看同一输入多次结果的一致率。事实与估算分栏；估算必须标假设。

## 7. 展示物的载体：一份 HTML 给开发者，md 给 Agent

开发者中心中栏只渲染**一份 HTML**：goalfy-app-workbench 目录下 `docs/workbench.html`，一个应用一份。它只回答两件事：**业务过程**，这个应用替谁、按什么过程把事做成；**开发内容**，我们正在把它做成什么。验证、证据、工单、交付细节**不上页面**，留在 `docs/stages/` 的七份阶段 md 里给你和后续 Agent 用。两者同时维护：md 记事实与证据，HTML 只放开发者要看的结论与取舍。

**结构体固定。** 模板在 `references/开发者中心页面结构.html`，新建应用时原样复制到 `docs/workbench.html`，之后只填内容，**禁止**增删块、改块的 `id` 或 `data-block`、改顺序。顶部只有应用名、当前阶段、版本、更新时间。两部分十个块：

| 块 | 谁填 | 放什么 |
|---|---|---|
| `biz-who` | G1 | 给谁做、客户是哪一类、四个角色、触发情境、现在怎么完成、替代方案 |
| `biz-promise` | G1 | 价值假设一句、三层目标、可采用标准、失败标准 |
| `biz-journey` | G1 画草图，G3 换成正式路线 | 用户带什么进来、经过什么、拿什么出去；候选路线与到达标准；路线图内联 SVG |
| `biz-decisions` | G1 写判断，G2 补谁来定 | 关键判断表：判断、依据、错了怎样、谁来定、风险；G2 把"谁来定"按实测填成规则、模型、确认、人 |
| `biz-redline` | G1 | 交付给谁、谁说算数、红线四类 |
| `build-shape` | G1 定形态，G2 补能力来源 | 做成能力容器还是应用；由哪些部分组成；关键能力从哪来：已有资产、外部接入、自建 |
| `build-lanes` | G2 | 分工建议表与泳道图：每步谁执行、依据、错了怎样、怎么确认、退到哪；待定项用黄标 |
| `build-route` | G3 | 运行路线图与每个节点：做什么、为什么、谁做、异常时怎样；最终用户与运行 Agent 的介入点、交付、审阅、出口 |
| `build-data` | G3 | 业务数据表，按实体、情境、历史事件三类分组，每张表的列、谁能改、哪次运行读写 |
| `build-pages` | G3 | 页面清单与原型截图，每页三句：用户在这干什么、数据从哪来、主行动是什么 |

**写法规则。** 只用业务语言，**禁止**资产数字 ID、节点标识、工具名、字段名、代码。待开发者拍板的事项写在对应块里，用 `<span class="tag yellow">待定</span>` 标出，决定后改成结论。图用内联 SVG，不依赖外部脚本，Mermaid 源码可作注释附在 SVG 后。不引外部样式与脚本，图片用 `docs/screens/` 相对路径。每次只改受影响的块，同时更新该块的 `data-updated-stage` 与 `data-updated-at`，整份文件原子写入；工作台监听文件自动刷新，**禁止**让开发者手动刷新。块没有内容时保留 `<p class="empty">尚未产出</p>`。

**什么时候更新。** G1 到 G3 每完成一步就填对应块，不攒到最后；G4 到 G7 只更新顶部的阶段与版本，页面内容不变，那几个阶段给开发者看的是应用本身。
