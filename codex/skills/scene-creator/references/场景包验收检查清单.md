# 场景包验收检查清单

> 本文是 `SKILL.md` 的整包验收指南。全部受影响 Workflow 已完成单体验收，且必需业务界面已有当前部署证据后读取。

---

本清单承接 Max `csp_verify_checker` 的职责。外部 Agent 在全部 Workflow 完成 bubble 和单体验收后直接执行，不调用 FastAgent。

## 证据顺序

1. 用 `get_asset(asset_type="scenario_package")` 读取场景包 Skill、Skill 文件、Toolset、TPE/Workflow、数据集和 `workflow_orchestration` 全貌。
2. 读取全部 Toolset 和 TPE/Workflow，核对依赖存在、在线且属于场景包闭包。
3. 只对实际引用或发现异常的 FA、Tool Group、Auth Card、数据集和业务档案继续下钻。
4. 汇总每条 Workflow 当前版本的 Preview、bubble 和 Workflow 验收证据。
5. 读取工单中的业务界面决策；如为 `required`，汇总当前契约对应的源码 SHA256、部署终态和业务界面验收裁决。

## 完整性与一致性

- 名称、描述、`apc_skill` 和场景 Skill 文件与业务目标一致；每个文件有明确读取时机。
- `apc_skill` 包含共同业务终点、运行时里程碑、候选路线、业务输入、权限和 Agent/用户判断，不含数字资产 ID、制作说明、具体私有档案事实或第二份 DAG。
- 同一终点存在多种合理路径时，`apc_skill` 没有把某一路线写成所有用户必须执行的唯一 SOP；每条候选路线说明适用需求、前置条件和选路节点。
- `apc_skill` 明确运行前怎样识别相关实体档案和情境档案、分别读取哪些最小充分信息，以及档案如何实质改变路线、参数、优先级或解释。
- 用户当前明确表达和有效约束优先于历史观察；Agent 推断保持为假设，档案缺失、过期、冲突或不相关时有明确处理，不虚构用户偏好。
- 档案驱动的路线选择保留在 Agent/`sa_handoff` 边界；稳定路段才进入 Workflow，不用动态业务分支 Workflow 或固定 DAG 代替个性化选路。
- 用户选择、调整、拒绝、理由和结果只按现有投稿与审稿机制形成候选事实；场景包不直接修改档案。
- Workflow、普通 TPE、Toolset、FA、Tool Group、数据集和业务档案关系能从真实资产反查。
- Toolset 至少包含 FA 或 Tool Group 之一，Skill 与实际工具一致；需要授权的 Tool Group 已绑定 Auth Card。
- Workflow 使用的普通工具和 FA 位于 preload 闭包；Runtime 默认工具除外。
- 数据源名称与绑定数据集/业务档案一致，不存在引用缺失或无用途绑定。
- 失败、数据缺失、格式变化和外部系统错误有明确处置；高风险动作有用户确认和 dry-run 边界。
- 业务界面决策已明确记录；`required` 时绑定同一场景包、契约未漂移且部署成功，`not_required` 时明确回落现有对话界面。
- 当前 `required` 业务界面的场景包至少挂载一个真实 Workflow；纯 SA 或只有普通任务点时没有绕过平台门槛，并已回落对话界面。
- 业务界面只消费宿主 SDK 和公开运行契约，没有获得 MCP 工具清单、内部脚本、提示词、DAG 或控制动作。

## 编排版本与多 Workflow

- 编排类型与实时 `scene_package_manage` Schema、服务端契约版本一致；设计稿、集成分支和旧示例不作为线上能力证据。
- 当前工具只支持固定 DAG 时，不存在多入口、用户 Gate、重入、受控循环或多交付等未来图字段。
- 未来图只有在实时 Schema、版本化契约和目标场景包兼容性同时成立时验收，不与固定 DAG 对象混写。

- 所有节点引用当前场景包已挂载的 Workflow。
- 节点映射同时满足字段类型和业务含义，最终只有一个 delivery。
- `delivery.node_id` 对应节点声明 `sa_handoff`，要求 Agent 读取已校验结果、调用 `message_user(type="result")` 交付，再执行 `take_over`。
- 运行时 action 只有 `continue_as_planned`、`revise_and_continue`、`take_over`；不存在名为 `resume` 或 `stop` 的 action。若 Hub Schema 仍使用 `decision_criteria.resume/stop`，它们只是制作期判断条件字段。
- Hub 保存结果是 DAG、映射、JSON Path、required、类型和 delivery 形状的唯一静态结论，不复制第二套校验器。

## 验证证据和全真边界

- 每条 Workflow 有当前版本的 bubble `run_id`、终态轨迹和 `passed` 验收裁决。
- 明确记录未触达分支和 FA 桩边界，不把 bubble 声称为内容或副作用的全真验证。
- Hub 保存通过只记录 `orchestration_static_validated`；只有真实项目日志证明目标编排被命中并完成顺序、Gate/handoff 和交付验证时，才记录 `orchestration_runtime_verified`。
- 缺少整图运行入口或日志时必须保留运行盲区，不能用单 Workflow bubble 拼接成整图运行证据。
- 整包验收通过后，逐条询问用户是否全真验证。只有批准覆盖所选路径可能执行的全部 Workflow，才能启动一个真实 Max 项目。
- 用户跳过时仍可交付，但必须记录 `full_validation_skipped`、用户决定和剩余盲区；不得虚构项目、日志或产物证据。

## 输出

输出并写入工单简洁检查点：

- `验证摘要`：场景包名称/ID、检查项数量和 `ready/blocked` 裁决。
- `未通过项`：问题、涉及资产、后果和应使用现有哪个工具修复什么字段。
- `通过项`：已核证范围，不给笼统“通过”。
- `运行证据与盲区`：Workflow/run_id/覆盖率、编排静态或运行证据层级、FA 桩和未触达分支。
- `业务界面`：`required/not_required`、契约摘要、部署裁决与回落策略。
