# 场景包验收检查清单

> 本文是 `SKILL.md` 的整包验收指南。全部受影响 Workflow 已完成单体验收，且必需业务界面已有当前部署证据后读取。

---

本清单承接 Max `csp_verify_checker` 的职责。该名称只说明内部职责来源，不是 scene-creator 外部 MCP 可调用的工具；外部 Agent 在全部 Workflow 完成 bubble 和单体验收后直接执行本清单，不调用 FastAgent。

## 证据顺序

1. 读取工单中的访谈事实、材料目录、项目三层分析、里程碑、候选路线、理想态、能力覆盖矩阵、方案挑战和用户确认范围。
2. 用 `get_asset(asset_type="scenario_package")` 读取场景包 Skill、Skill 文件、Toolset、TPE/Workflow、数据集和 `workflow_orchestration` 全貌。
3. 读取全部 Toolset 和 TPE/Workflow，核对依赖存在、在线且属于场景包闭包。
4. 只对实际引用或发现异常的 FastAgent、Tool Group、Auth Card、数据集和业务档案继续下钻。
5. 汇总每条 Workflow 当前版本的 Preview、bubble 和 Workflow 验收证据。
6. 读取工单中的业务界面状态；场景包包含任意 Workflow 时必须为 `required`，并汇总当前契约对应的源码 SHA256、部署终态和业务界面验收裁决；只有没有 Workflow 时才能为 `not_required`。

## 完整性与一致性

- 名称、描述、`apc_skill` 和场景 Skill 文件与业务目标一致；每个文件有明确读取时机。
- 用户指定材料已完整阅读，参考项目有概览、深读、分析三层证据；价值判断没有把摘要、估算或假设冒充真实基线。
- 每个已确认里程碑、候选路线、异常路径和到达标准都能在场景包或对应资产中找到真实承载。
- 对照理想态中每个预期减少的失败、绕行或沟通轮次，存在达到所需颗粒度的指导或确定执行资产；不可执行空话不算覆盖。
- `apc_skill` 包含共同业务终点、运行时里程碑、候选路线、业务输入、权限和 Agent/用户判断，不含数字资产 ID、制作说明、具体私有档案事实或第二份 DAG。
- 同一终点存在多种合理路径时，`apc_skill` 没有把某一路线写成所有用户必须执行的唯一 SOP；每条候选路线说明适用需求、前置条件和选路节点。
- `apc_skill` 明确运行前怎样识别相关实体档案和情境档案、分别读取哪些最小充分信息，以及档案如何实质改变路线、参数、优先级或解释。
- 用户当前明确表达和有效约束优先于历史观察；Agent 推断保持为假设，档案缺失、过期、冲突或不相关时有明确处理，不虚构用户偏好。
- 档案驱动的路线选择保留在 Agent、用户或 2.0 最终 Review 边界；稳定路段才进入 Workflow，不用动态脚本分支或同一 Runtime 回边代替个性化选路。
- 用户选择、调整、拒绝、理由和结果只按现有投稿与审稿机制形成候选事实；场景包不直接修改档案。
- Workflow、普通 TPE、Toolset、FastAgent、Tool Group、数据集和业务档案关系能从真实资产反查。
- Toolset 至少包含 FastAgent 或 Tool Group 之一，Skill 与实际工具一致；需要授权的 Tool Group 已绑定 Auth Card。
- Workflow 使用的普通工具和 FastAgent 位于 preload 闭包；Runtime 默认工具除外。
- 数据源名称与绑定数据集/业务档案一致，不存在引用缺失或无用途绑定。
- 失败、数据缺失、格式变化和外部系统错误有明确处置；高风险动作有用户确认和 dry-run 边界。
- 业务界面状态由 Workflow 事实确定：存在任意 Workflow 时必须为 `required`，绑定同一场景包、契约未漂移且部署成功；只有纯 SA 或普通任务点、完全没有 Workflow 时才能为 `not_required` 并回落现有对话界面。
- 包含 Workflow 但业务界面缺失、部署失败或宿主能力不兼容时裁决为 `blocked/platform_blocked`，不得通过改记 `not_required`、移除必要 Workflow 或借用无关 Workflow 绕过。
- 业务界面只消费宿主 SDK 和公开运行契约，没有获得 MCP 工具清单、内部脚本、提示词、DAG 或控制动作。

## 编排版本与多 Workflow

- 编排与实时 `scene_package_manage` Schema、服务端契约版本一致；当前对象严格使用 `schema_version:"2.0"` 和非空 `orchestrations[]`，不混入旧 1.0 或设计稿字段。
- 每条路线有唯一业务 ID、清晰名称与描述、入口表单、根对象 input Schema、至少一个入口节点和一个最终 Delivery Review。
- 所有节点引用当前场景包已挂载并完成单体验收的 Workflow；节点 ID 唯一、入口节点无依赖、图无环且全部可达。
- 入口映射覆盖路线 required；节点映射只从路线输入、依赖祖先真实 output 或 scene_config 取值，路径、基础类型、证据对象和 Workspace 文件 format 一致。
- 中途 `business_interaction` 只把表单值写入尚未派发的下游真实字段，不与普通 mapping 重复，不承担路线切换。
- 节点 `sa_handoff` 只用于成功后的 Agent 检查，位置在节点层，指令和 `decision_criteria.resume/stop` 都可验证；它们不是前端业务 action。
- 每条路线只有一个 Delivery；`delivery.review` 类型和 actions 合法。`start_orchestration` 指向同一对象内真实路线，且 `form_id` 与目标入口匹配。
- 业务界面入口没有生成或提交 `workflow_runtime_id`；服务端只在创建首批真实 TaskPoint 后通过 `business_interaction_result(status=accepted)` 回传，入口拒绝或首批派发失败不暴露预留 ID。`fail_business` 不携带目标路线或表单，必须通过 Delivery 内容/统计核验门，并把 Business 置为结构化失败终态。
- 最终交付不再要求 Delivery 节点额外声明 `sa_handoff`；旧“Agent 先发送结果再接管结束”的链路不与 2.0 Review 叠加。
- 重做或改路线创建新 Runtime，旧 Delivery、TaskPoint、attempt 和文件没有被覆盖。
- Hub 保存结果是路线、DAG、映射、交互、Review、JSON Path、required、类型和文件格式的唯一静态结论，不复制第二套校验器。

## 验证证据和全真边界

- 每条 Workflow 有当前版本的 bubble `run_id`、终态轨迹和 `passed` 验收裁决。
- 明确记录未触达分支和 FastAgent 桩边界，不把 bubble 声称为内容或副作用的全真验证。
- Hub 保存通过只记录 `orchestration_static_validated`；只有真实项目日志证明目标编排被命中并完成顺序、Gate/handoff 和交付验证时，才记录 `orchestration_runtime_verified`。
- 缺少整图运行入口或日志时必须保留运行盲区，不能用单 Workflow bubble 拼接成整图运行证据。
- 整包验收通过后，逐条询问用户是否全真验证。只有批准覆盖所选路径可能执行的全部 Workflow，才能启动一个真实 Max 项目。
- 用户跳过时仍可交付，但必须记录 `full_validation_skipped`、用户决定和剩余盲区；不得虚构项目、日志或产物证据。

## 输出

输出并写入工单简洁检查点：

- `验证摘要`：场景包名称/ID、检查项数量和 `ready/blocked` 裁决。
- `未通过项`：问题、涉及资产、后果和应使用现有哪个工具修复什么字段。
- `通过项`：已核证范围，不给笼统“通过”。
- `运行证据与盲区`：Workflow/run_id/覆盖率、编排静态或运行证据层级、FastAgent 桩和未触达分支。
- `业务界面`：由 Workflow 关系推导出的 `required/not_required`、契约摘要、部署裁决与回落策略。
