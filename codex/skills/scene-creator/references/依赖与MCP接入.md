# 依赖与 MCP 接入

> 需要接入新的 MCP 服务、上传私有包、导入 Skill 包、配置授权卡，或处理工具集上线时读取。**你实际看到的工具定义与服务端报错始终优先于本文。**

---

## 什么时候需要接入新能力

先按 `stages/S3-资产制作.md` 1.4的四层顺序判断。**只有确认现有工具无法通过更好的指引组合完成时**，才进入本文的接入流程。

接入前**必须**已经用 `list_assets` 和 `get_asset` 确认平台上确实没有可复用的工具组——重复注册同一个 MCP 会产生互相冲突的重复资产。

## 接入现有 MCP 服务

### 标准流程

**必须**先预览、再注册。预览是为了确认连接可用并发现真实工具清单，跳过预览直接注册会把不可用的连接写成正式资产。

```text
1. preview_tool_group        传连接类型，以及地址或启动命令
2. 成功 → register_and_refresh_tool_group   传相同的连接参数，并选择要纳入的工具
3. 失败 → 进入下方调试循环
4. 注册成功后按需配授权卡
```

注册返回里会带一个用于授权卡绑定的标识，它**不是**工具组标识，配卡时**必须**用前者（见下文）。

### 预览失败的调试循环

以启动命令方式接入时，最常见的失败原因是**运行环境缺少依赖导致服务起不来**。处理方式：

```text
1. 读预览返回的错误信息，判断缺什么
2. 在自己的环境里实际调试安装命令，直到能起得来
3. 把验证过的安装命令收集成前置安装步骤
4. 带上这些安装步骤重新预览
5. 仍失败则继续调试，直到成功
6. 预览成功后，注册时必须带上同一组安装步骤
```

**注册时漏传安装步骤**是这里最容易犯的错：预览时装过的依赖不会自动带到运行时，运行时会再次因为缺依赖而失败，而这个失败要等到真正调用工具时才暴露。

调试过程中的失败尝试**不必**写进工单，但**必须**记录最终有效的安装步骤——下次刷新或排查时需要它。

### 私有包

开发者提供的本地包**必须**走上传路径，**不能**走预览路径。

```text
1. file_to_url            把本地包交给平台，声明对应用途
2. upload_and_register_tool_group   用返回的文件引用注册，同样支持前置安装步骤
```

原因是预览工具运行在独立服务里，**访问不到你本地的文件系统**——给它传本地路径它找不到文件。

### 标准 Skill 包导入

开发者提供的标准 Skill 包（含 Skill 入口文件的压缩包）可以一键导入成工具集：

```text
1. file_to_url            上传压缩包
2. import_skill_package   用文件引用导入
```

导入会自动解析入口文件并创建**离线**工具集，之后仍要通过下方的上线检查。

## 授权卡

### 什么时候必须配

工具需要**终端用户各自的第三方账号授权**时必须配。判断标准是：授权凭证是每个使用者一份，还是全场景包共用一份。

| 情况 | 处理 |
|---|---|
| 每个终端用户用自己的账号授权 | **必须**配授权卡，否则终端用户无法完成授权、工具调用会失败 |
| 服务级认证，全场景包共用一份凭证 | 写在连接配置的请求头里即可，**不需要**授权卡 |

漏配授权卡的后果是：制作期你自己测试可能正常（用的是你的凭证），交付给终端用户后全部调用失败。

### 三种操作

| 需求 | 工具 | 要点 |
|---|---|---|
| 新建一张卡 | `create_auth_card` | 需要授权类型和授权配置 |
| 改已绑卡片的配置 | `update_auth_card` | 只传要改的字段 |
| 复用别人已有的卡 | `link_auth_card` | 需要卡片标识；替换已绑卡片要显式确认，且**必须**先问开发者 |

授权配置的必填内容随授权类型不同：标准授权流程需要三个服务端端点；自定义方式需要字段清单，每个字段要有键名、展示名、类型和是否必填。**具体必填项以实时 Schema 为准。**

创建成功后返回的卡片标识**要提醒开发者妥善保存**——把它分享给其他开发者，对方的 MCP 就能共用这张卡的最终用户授权。

### 安全边界

**禁止**把任何个人令牌、Cookie 或密码写进 Skill 文本、脚本、提示词或工单。授权卡的存在意义就是让凭证留在平台侧、不进入配置内容。

## 工具集上线的两道检查

新建或导入的工具集处于**离线**状态。离线工具集可以被关联配置，但**运行时不会被加载**——这是"配置看起来齐全但运行时找不到能力"最常见的原因。

这两道检查**都不能跳**。

### 第一道：Workflow 依赖检查

**任何 Workflow 创建前必做**：

```text
1. 根据脚本确定完整的预加载工具集清单
2. 对其中本轮新建或导入的工具集做安全的运行时测试
3. 全部无失败后 → online_toolsets（只传本轮新建的标识）
4. get_asset 反读，确认清单里每一个都已上线
5. 通过后才能创建 Workflow
```

在此之前可以做预览，但**禁止**直接创建。

### 第二道：交付前最终检查

**交付前**对待上线清单里尚未上线的工具集：

```text
1. 逐一做安全的运行时测试，破坏性操作跳过
2. 全部无失败后 → online_toolsets
3. get_asset 反读确认全部已上线
4. 已在第一道检查里上线过的，这里只反读、不重复上线
```

### 失败与中断的处理

任一测试失败、余额不足、授权中断或流程异常时：**保留原资产和进度**，恢复后从未完成的验证继续。**禁止**跳过验证直接上线。

### 开发者已有的离线工具集

开发者自己名下处于离线的工具集**可以**关联到场景包，但运行时加载不到。发现这种情况**必须**在交付前停止并告知开发者，**禁止**擅自把别人的资产上线——那是对他人资产状态的越权变更。

## 工具取样

需要确认某个已有 MCP 工具的真实返回结构时，用 `workflow_tool_test` 做一次真实调用取样。

**这会真实调用供应商接口。** 以下工具**禁止**取样：

- 破坏性操作（删除、清空、重置）
- 发布或对外通知（发信、推送、发单）
- 涉及凭证变更
- 涉及资金
- 任何不可逆的动作

只对**安全只读**的工具取样，且**只在**确实缺少可信返回结构定义时才做。可以同时提交一个候选的输出结构一起校验本次样本。

只依赖已有业务项目上下文的工具还要传项目标识——服务端会把它和可信身份一起作为运行请求头传给目标 MCP，不会因此启动新项目。

目标工具需要读取 `/workspace` 测试文件时，不要借用最终用户项目。先对 Agent 本地文件调用 `file_to_url(purpose="tool_test_fixture")`，完成 `prepare → 客户端 PUT → complete`，取得 `data.file_ref`。再给 `workflow_tool_test` 提供两组相互独立的信息：`workspace_files` 只接收这些文件引用；`workspace_bindings` 负责把某个文件的真实路径或父目录注入目标工具顶层参数。服务端会复用 Workflow 冒泡使用的隐藏验证项目，从临时 HTTPS URL 下载文件、写入真实工作区、完成一次 `tools/call`，随后无论成功或失败都释放隐藏项目。这种模式下不要再传 `project_id`。

示例用途：测试目录扫描工具时，分别上传 `docs/a.md` 与 `docs/b.md`，在 `workspace_files` 中提供两个文件引用，只需在 `workspace_bindings` 中把其中一个文件的 `parent_dir` 绑定到 `path`，并在普通 `input` 中保留 `pattern: "*.md"`；测试单文件读取工具时，把对应文件的 `file_path` 绑定到文件参数。文件准备数量与参数绑定数量彼此独立，不要为了第二个文件虚构 `path2` 或 `urls`。该样本只能证明这一次真实调用和返回结构，不能代替整条 Workflow 冒泡验证。

## 依赖变更后的连带处理

工具组刷新、工具删除或参数变化后的完整处理见 `stages/SD-诊断与维护.md` 第 3 节。这里只强调一条：

**参数变化和工具删除都要回头核对所有引用它的地方**——工具集使用指南、FastAgent 提示词、Workflow 脚本、`apc_skill`、场景 Skill 文件。留着失效知识会让运行时 Agent 反复尝试不存在的能力，而且这类问题在静态检查里看不出来。

变更完成后**必须**重跑所有受影响的预览、运行验证和整包验收。
