# 方案挑战检查清单

> 业务方案形成后、创建任何资产之前读取，**由你自己逐项执行**，没有可以代劳的审查工具。没有真实资产证据时**禁止**在证据不足时判定通过。

---

## 证据

先用 `list_assets`、`get_asset` 和按需的 `dataset_read` 核对真实资产，再挑战方案。输入至少包括访谈事实、完整材料阅读结果、项目三层分析、开发者目标、最终用户角色、业务里程碑、候选路线、理想态、能力覆盖矩阵、验收标准，以及拟复用或新建的场景包、Workflow、FastAgent、Toolset、Tool Group 和数据集。**禁止**凭名称、历史对话或记忆推断资产能力。

挑战以执行结构表为对象逐条目执行，**只处理状态为 `pending` 的条目**（累加机制见路由器 5.3 与 references/表结构与累加机制）；全部条目通过后，将执行结构表表级布尔位 `challenged` 置 `true`。

## 必查项

### 业务完整性

- 意图、关键参数和成功标准明确；平台知识缺口由 Agent 调查，没有被错误地抛给开发者。
- 开发者指定的文档、项目和日志已经完整读取；参考项目已完成概览、深读、分析三层工作，没有只看摘要。
- 解决的是稳定、可复用的业务问题，而不是固化一次性项目。
- 主流程、异常路径和最终交付完整；每个阶段有明确输入、输出和责任方。
- 里程碑、候选路线、选路条件、Focus/泛化取舍和理想态都有证据或明确假设；参考项目没有被写成所有最终用户的唯一 SOP。
- 业务路线、Focus/泛化、执行形态、完整交付方案、最终用户/Agent 介入、提案包含 Workflow 时是否规划配套业务应用（仅记意向，制作走 app-creator 线）、能力缺口处理均已作为总体 Plan 选项交由开发者确认；Agent 推荐没有被冒充为开发者决定。
- 提案包含 Workflow 或固定业务路线时，Plan 已用业务语言画出路线入口、主要阶段、固定依赖、扇出/汇合、最终用户与 Agent 介入、最终交付、审阅责任方和动作出口；图中没有资产数字标识、内部节点标识、工具名、Schema 路径或脚本调用链。
- 完整交付方案已分别明确结果交付对象、最终审阅责任方、`user_gate + ask` / `user_gate + result` / `agent_gate` 选择、允许动作，以及修订/重做/改路线的重入方式；“交付给谁”和“谁负责审阅”没有被混为一件事。
- 开发者统一确认完整 Plan 前，没有创建依赖资产、普通任务点、场景包草稿、Workflow、关联关系或业务路线编排；后续路线依赖、交付对象、审阅责任、动作、重入方式或介入点发生实质变化时，会回到 Plan 重新确认。
- 授权、外部写入、通知、邮件、发布和收费等高风险动作有开发者确认、运行时最终用户授权边界与 `ctx.dry_run` 护栏。发布范围和上线授权已经分开表达：只有总体 Plan 明确写出“前三层候选验收通过后上线”并被统一确认，才可把 Plan 确认视为上线授权；只列发布范围时仍需在上线前单独确认。

### 工具、数据和资产依赖完整性

- 每个里程碑都有真实工具或 FastAgent 支撑，参数和能力匹配。
- 所需 Toolset、Tool Group、FastAgent、Workflow 和数据集会实际挂载；不能假设开发者可能拥有。
- 每个里程碑在能力覆盖矩阵中有“已覆盖/可组合/需维护/缺口/验证方式”结论；开发者明确要求的能力没有被静默削减或替换。
- 数据源名称与绑定资产一致，不存在引用缺失或无用途的冗余绑定。
- 不依赖创建者本地路径、外部 Agent 沙箱或其他 Max 项目的临时文件。

### Workflow、普通 TPE 和 FastAgent 选型

- 存在至少两个真实步骤，且顺序、数据流或扇出汇合关系稳定、无需临场改变下一步的流程优先 Workflow；是否重复执行只用于判断固化收益，不作为唯一准入条件。
- FastAgent 按**环节**划分（一个环节一个），拆分理由是职责边界而不是步骤；环节内“看结果决定下一步”的搜索、读取、试错都在 FastAgent 内部完成、工具组挂给它；脚本 `tool()` 只做环节前后的确定性准备、汇合与收口。不挂工具、只做格式转换或搬运的 FastAgent 是误用；同一节点内同一 FastAgent 按交付物连调多次、或"脚本抽数据 → FastAgent 还原 → 脚本落盘"的三段式录入，都视同切碎（S2 4.4 的两个样子）。
- 未规划配套业务应用的方案里没有任何读写业务应用数据集的路线或步骤，不挂 `business_app_dataset` 工具集；"记账 / 留存 / 看历史"类目标要么进配套应用、要么从计划书移除（S1 4.3）。
- 只调用一个 FastAgent 后原样返回的 Workflow 不提供任何价值，应直接使用该 FastAgent。
- Workflow 输入能由最终用户、业务应用数据集或上游 Workflow 提供，输出是最终用户或下游真正需要的稳定对象。
- 只有路线内部依赖固定时才配置多 Workflow 无环 DAG；路线需要临场规划时交给 Agent。
- 多候选路线、最终用户 Gate、改稿和重做使用当前 2.0 多路线契约与新 Runtime；中途最终用户补参和 Agent 介入分别使用已声明的 `business_interaction` 与节点 `sa_handoff`，不在同一 DAG 画回边。
- 交付资格核验与最终业务验收已分开：前者检查输出契约、统计、证据和文件，后者决定接受、修订、改路线或结构化失败；质量检查 Workflow 和节点 `sa_handoff` 不承担最终验收。
- 已向开发者展示每条路线的交付对象、`user_gate + ask`、`user_gate + result`、`agent_gate` 候选及推荐依据、最终用户体验、动作和风险，并记录开发者确认的最终审阅形态；Agent 没有按业务猜测直接选定。涉及不可绕过的最终用户授权时，开发者选择与风险边界一致。
- 最终审阅接受前不会把结果展示当成已验收、不会完成 Business，也不会用旧的 Agent 发送结果与接管结束链路绕过 Delivery Review。
- 场景资产只保存节点 `sa_handoff` 和 `delivery.review` 等公开制作契约；没有把 Max Runtime 的 Agent 边界通知、上下文注入或内部控制消息复制进编排、Skill 或业务应用。
- 工具定义、编排保存门与目标 Max Runtime 对 2.0 的支持**必须**一致；只有静态保存能力时记录 `platform_blocked`，不声称运行可用。
- 包含 Workflow 时已在总体 Plan 中说明可配套业务应用并记录是否规划（制作与交付走 app-creator 线，先包后应用），后续没有重复询问；规划与否都不影响本场景包的方案通过与验收；纯 SA 或只有普通任务点时不伪造依赖绕过平台门槛。

- 执行结构表中 FastAgent 超过 3 个时，是否已逐个说明不可合并的理由（同域多类产出应采用「一个 FastAgent + 交付物参数分发 + 规范文件」，见 S2-4.4）？
- 执行结构表中相邻且无数据依赖的步骤未归入并行组时，是否已写明原因？`no_parallel_reason` **必须**属于可验证的类别（数据依赖、副作用顺序、共享路径、会话状态）；"顺序执行较稳妥""保持简单"这类不构成理由，视为挑战不通过。
- 执行结构表中 FastAgent 与关键工具步骤，是否已逐步判定展示载体（`user_facing`）？把原始返回当作展示、或对用户关心的结果未作判定的，挑战不通过（见 S2-6.3）。
- 执行结构表中 `by=FastAgent` 的每一步，是否代表一个**完整环节**（`what` 写出它内部从输入到产出的全过程与所用工具）？只做读取、搬运、格式转换等确定性操作的 FastAgent，或把一个环节切成多个 FastAgent 串在脚本里的，视为挑战不通过（见 S2-4.4）。

### 鲁棒性和运行时 Skill

- 数据缺失、格式变化、工具失败和外部系统变化有明确失败或降级规则。
- `apc_skill` 包含业务里程碑、权限边界、操作策略和必要系统认知，不含数字资产 ID、制作说明或第二份 DAG。
- 对照理想态中每个预期减少的失败、绕行或沟通轮次，`apc_skill`、Toolset、场景 Skill 或 Workflow 中存在对应的可执行指导；不存在“调用相关工具”“输出高质量结果”等空话。
- 每个场景 Skill 文件都由 `apc_skill` 在明确阶段按名称索引，且信息没有跨层重复。
- Toolset Skill、FastAgent Prompt 与真实工具一致，不使用会让 Agent 自由发挥的泛化描述。

## 输出

输出并写入工单简洁检查点：

- `关键问题`：位置、后果、精确修改办法；未解决前**不得**创建。
- `改进建议`：不阻断但会影响稳定性或质量的问题。
- `确认项`：证据不足或属于业务取舍的问题，由开发者通过 Plan 或单项回答决定。
- `证据`：审查视角和实际读取的资产 ID。

**不得**把方案审查写成运行验证，也**不得**在证据不足时判定通过。
