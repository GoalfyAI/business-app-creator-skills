# 场景包验收检查清单

> 全部受影响 Workflow 已完成运行验证和单体验收后读取。**由你自己逐项执行**，没有可以代劳的验收工具。业务应用不属于本清单对象（约束 8，app_creator 线验收）。

---

## 证据顺序

1. 读取工单中的访谈事实、材料目录、项目三层分析、里程碑、候选路线、理想态、能力覆盖矩阵、方案挑战、方案 Plan 和开发者确认范围。
2. 用 `get_asset(asset_type="scenario_package")` 读取场景包 Skill、Skill 文件、Toolset、TPE/Workflow、数据集和 `workflow_orchestration` 全貌。
3. 读取全部 Toolset 和 TPE/Workflow，核对依赖存在、在线，且都属于本场景包的依赖范围。
4. 只对实际引用或发现异常的 FastAgent、Tool Group、Auth Card 和数据集继续下钻。
5. 上线前只汇总前三层候选验收证据：Preview/静态契约、必要的工具取样、每条 Workflow 当前版本及每条发布路线的 Bubble。第四层不参与发布门；目标版本上线并反读确认后，仅在开发者授权端到端全真运行时补充第四层证据。

## 完整性与一致性

- 名称、描述、`apc_skill` 和场景 Skill 文件与业务目标一致；每个文件有明确读取时机。
- 开发者指定材料已完整阅读，参考项目有概览、深读、分析三层证据；价值判断没有把摘要、估算或假设冒充真实基线。
- 每个已确认里程碑、候选路线、异常路径和到达标准都能在场景包或对应资产中找到真实承载；最终业务路线与开发者确认的业务路线图一致。
- 结果交付对象、最终审阅责任方、审阅形态、允许动作、修订/重做/改路线的重入方式和最终用户/Agent 介入点均与开发者确认的完整交付方案一致；后续实质变更有重新确认记录。
- 对照理想态中每个预期减少的失败、绕行或沟通轮次，存在达到所需颗粒度的指导或确定执行资产；不可执行空话不算覆盖。
- `apc_skill` 包含共同业务终点、运行时里程碑、开发者确认的候选路线、业务输入、权限和 Agent/最终用户判断，不含数字资产 ID、制作说明、具体最终用户的私有业务数据或第二份 DAG。
- 同一终点存在多种合理路径时，`apc_skill` 没有把某一路线写成所有最终用户**必须**执行的唯一 SOP；每条候选路线说明适用需求、前置条件和选路节点。
- 最终用户当前明确表达和有效约束优先于历史观察；Agent 推断保持为假设，数据缺失、过期、冲突或不相关时有明确处理，不虚构最终用户偏好。
- Workflow、普通 TPE、Toolset、FastAgent、Tool Group 和数据集关系能从真实资产反查。
- Toolset 至少包含 FastAgent 或 Tool Group 之一，Skill 与实际工具一致；需要授权的 Tool Group 已绑定 Auth Card。
- Workflow 使用的普通工具和 FastAgent 都在预加载工具集清单内；运行时自带的默认能力除外。
- 每条 Workflow 都已完成业务事件适用性判断：无事件契约且脚本未调用 `emit_business_event` 的单 Workflow 可以直接派发；一旦声明或调用脚本事件，就已实现运行开始与全部终态分支，开始执行有 `stage_started`，正常结束有 `stage_result`，可控业务失败有 `stage_failed`。产生文件与最终交付时分别由 Runtime 在 Artifact 登记和 Delivery 冻结后自动发布 `artifact_ready`、`delivery_ready`，脚本不声明也不自行发布。细分阶段、中间结果和非表单提醒是否增加事件，已结合配套业务应用的消费需要（如有规划）记录理由；`stage_progress` 不作为系统契约。
- Workflow 脚本事件只包含稳定公开业务语义，不含内部 ID、原始工具返回、提示词、脚本、Workspace 路径、临时 URL 或敏感信息；Runtime 自有的 `delivery_ready` 仅按固定 `PublicDelivery` 契约携带文件定位值（路径只作定位，不是面向用户的文本）。事件没有代替运行中表单、Runtime 恢复或最终审阅。
- 数据源名称与绑定数据集一致，不存在引用缺失或无用途绑定。
- 失败、数据缺失、格式变化和外部系统错误有明确处置；高风险动作有开发者确认、运行时最终用户授权边界和 dry-run 边界。

## 业务路线编排

- 带业务事件、业务表单握手、Delivery Review、业务应用入口或多 Workflow 固定依赖时，已建立业务路线编排；单条带事件 Workflow 使用单节点业务路线，不因节点数为一而直接派发。无业务事件且不依赖 Business/Runtime 握手的单 Workflow 可以不建路线。
- 编排与实时 `scene_package_manage` Schema、服务端契约版本一致；当前对象严格使用 `schema_version:"2.0"` 和非空 `orchestrations[]`，不混入旧 1.0 或设计稿字段。
- 每条路线有唯一业务 ID、清晰名称与描述、入口表单、根对象 input Schema、至少一个入口节点和一个最终 Delivery Review。
- 所有节点引用当前场景包已挂载并完成单体验收的 Workflow；节点 ID 唯一、入口节点无依赖、图无环且全部可达。
- 入口映射覆盖路线 required；节点映射只从路线输入、依赖祖先真实 output 或 scene_config 取值，路径、基础类型、证据对象和 Workspace 文件 format 一致。
- 中途 `business_interaction` 只把表单值写入尚未派发的下游真实字段，不与普通 mapping 重复，不承担路线切换。
- 节点 `sa_handoff` 只用于成功后的 Agent 检查，位置在节点层，指令和 `decision_criteria.resume/stop` 都可验证；它们不是前端业务 action。
- 每条路线只有一个 Delivery；`delivery.review` 类型和 actions 合法。`start_orchestration` 指向同一对象内真实路线，且 `form_id` 与目标入口匹配。
- 每条路线的交付对象、最终审阅形态、审阅责任方、动作、重入方式和最终用户/Agent 介入由开发者在方案 Plan 中确认，并与业务到达标准及风险边界一致；工单保留候选、推荐理由、影响和开发者选择，不能只有 Agent 自行判断的结论。
- `user_gate + ask` 的有效选择由 Runtime 直接执行，`user_gate + result` 由 Runtime 自动交付并结束；两者没有额外的 Agent 收尾或普通聊天 `ask`。只有已声明的 `agent_gate` 边界或“交由 Agent 处理”动作会唤起 Agent。
- 交付核验和最终审阅为两个独立阶段；输出 Schema、数值、证据、文件和内容核验通过，不等于业务已接受。质量检查 Workflow 与节点 `sa_handoff` 不可替代最终 Review。
- 业务应用入口没有生成或提交 `workflow_runtime_id`；服务端只在创建首批真实 TaskPoint 后通过 `business_interaction_result(status=accepted)` 回传，入口拒绝或首批派发失败不暴露预留 ID。`fail_business` 不携带目标路线或表单，必须通过 Delivery 内容/统计核验门，并把 Business 置为结构化失败终态。
- 脚本、Agent、业务应用和 MCP 调用方均未生成、猜测、复用或补写 `business_id`、`orchestration_id`、`workflow_runtime_id`；这些身份只由服务端在正式路线运行中持久化生成。Bubble 使用的验证身份未被当作正式业务身份。
- 最终交付不再要求 Delivery 节点额外声明 `sa_handoff`；旧“Agent 先发送结果再接管结束”的链路不与 2.0 Review 叠加。
- 重做或改路线创建新的运行实例，旧的交付、任务点、执行记录和文件没有被覆盖。
- 编排保存结果是路线、DAG、映射、交互、Review、JSON Path、required、类型和文件格式的唯一静态结论，**不要**另做一套等价校验。

## 验证证据和全真边界

- 第一层 Preview 已覆盖资产反读、脚本、输入输出 Schema、工具引用、业务事件适用性与静态生命周期、按需编排保存与接缝。
- 第二层仅对安全低副作用依赖做真实工具取样；一次样本不外推其他输入，也不冒充整条 Workflow。
- 第三层每条 Workflow 有当前版本的 bubble `run_id`、终态轨迹、工具覆盖和 `passed` 验收裁决；带业务事件时还必须有通过持久化裁决的 `run_evidence.business_events`，无事件时明确记录为不适用。
- 第三层每条发布路线另有独立的路线 Bubble `run_id`；启动只提交场景包、路线和入口业务输入，之后只复用该 `run_id` 轮询或回复当前表单。证据覆盖真实图控制、mapping、依赖/扇出汇合、业务表单、持久化事件、Delivery/Artifact 和终态 Review；没有由调用方伪造项目、Business、Runtime、表单或消息身份。
- 每条通过路线已经用结构化工单 metadata 记录 `orchestration_bubble_validated`、场景包标识、路线标识和真实 `run_id`；最终结单返回的 `completion_evidence.route_bubbles` 与发布范围逐条一致。文字声明、旧编排版本的运行或其他路线的 `run_id` 均不计入。
- 路线 Bubble 中 FastAgent、显式外部副作用和 `sa_handoff` Agent 判断仍为桩；当前只用已声明的 `complete_business` 或 `fail_business` 完成 Review，不把 `start_orchestration` 跳转标记为已演练。
- 明确记录未触达分支和 FastAgent 桩边界，不把 bubble 声称为内容或副作用的全真验证。
- 发布门只检查前三层候选验收；不得因缺少第四层而阻止上线，也不得把第四层伪装成发布前证据。
- 已核对上线授权来源：总体 Plan 明确写出“前三层候选验收通过后上线”且开发者已统一确认时，达到发布门后直接上线，不重复询问；Plan 只列发布范围、候选资产或路线时，上线前已有单独授权记录。
- 编排保存通过只记录 `orchestration_static_validated`；第四层只有获批全真项目日志证明真实图控制、表单、Agent 介入、业务事件真实发布、Delivery、Runtime `artifact_ready` 和 Review 均被命中时，才记录 `orchestration_runtime_verified`。
- 缺少第四层真实日志时**必须**记录整图运行盲区，不能用单 Workflow Bubble 拼接成整图运行证据。
- 第四层启动前已反读目标场景包的线上状态和待验证版本；全真项目日志对应的正是该已上线版本。未上线草稿只到第三层，没有通过真实项目入口运行，也没有用旧版本的上线证据代替当前版本。
- 最终审阅覆盖已声明的全部动作：接受后 Business 才进入完成终态；若声明了修订、重做或改路线，还要验证其创建新 Runtime，且旧 Delivery、TaskPoint、执行记录和文件仍可追溯。只证明结果已展示，不算 Review 验收。
- 真实日志证明：核验通过但最终审阅未接受时，Business 仍未完成，且旧的 Agent 结果展示/接管结束链路没有绕过 Review。
- 整包验收通过后，先取得发布授权、上线目标版本并反读确认，再按待验收业务路线一次性询问开发者是否端到端全真验证；带业务事件的单 Workflow 也按单节点路线申请和执行，不在单 Workflow 制作循环中逐条询问。只有目标版本线上反读证据成立，且开发者授权覆盖所选路线可能执行的全部 Workflow、FastAgent、最终用户/Agent 介入和外部副作用时，才能通过业务表单入口启动真实 Max 项目。
- 开发者跳过时仍可交付，但**必须**记录 `full_validation_skipped`、开发者决定和剩余盲区；**不得**虚构项目、日志或产物证据。

## 输出

输出并写入工单简洁检查点：

- `验证摘要`：场景包名称/ID、检查项数量和 `ready/blocked` 裁决。
- `未通过项`：问题、涉及资产、后果和应使用现有哪个工具修复什么字段。
- `通过项`：已核证范围，不给笼统“通过”。
- `运行证据与盲区`：Workflow/run_id/覆盖率、编排静态或运行证据层级、FastAgent 桩和未触达分支。
