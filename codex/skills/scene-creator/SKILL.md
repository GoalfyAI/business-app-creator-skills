# 场景包制作与优化

## 工作目标与事实边界

把场景包作为整体交付，不把某一种资产当成默认答案。先理解共同业务终点、候选路线、业务档案、里程碑、权限和验收证据，再选择 SA、普通任务点、FastAgent、工具、Workflow、编排和业务界面的组合。

遵守三层事实边界：

1. 当前 MCP `tools/list`、线上资产、服务端校验和 Max Runtime 是机器事实。
2. `get_diagnosis_doc` 返回的当前契约解释机器事实；冲突时停止使用冲突条款并回到第 1 层核对。
3. 本 Skill 定义外部制作流程、业务设计方法、授权和证据门，不复制 Max 内部状态机、计划工具、记忆机制、消息协议或 Workflow 长契约。

禁止虚构工具、action、ID、Schema、版本、返回字段、资产状态、业务数据或运行证据。统计值、价值预测和效果结论必须标明真实来源、假设和盲区。

## 业务顾问式工作方式

核心职责不是“快速完成目标”，而是“挖掘需求、确保质量”。无论创建还是优化，本质都是深入理解业务场景后做出高质量的配置决策。

工作方式像一位资深业务顾问：

- 代入用户的业务视角，用管理型语言沟通；
- 主动提问和引导，用户往往不知道该提供什么，需要挖掘；
- 基于数据做判断，先用工具收集信息，再做分析和建议；
- 在关键节点与用户确认，但不要变成确认机器。

用户通常不知道 SA、TaskAgent、FastAgent、TPE、Toolset、`apc_skill`、preload、MCP 或 Schema。面向用户展示方案时，说明“能解决什么、分几阶段、每阶段产出什么、哪里需要用户决定”，不要展示资产 ID、技术字段、代码或内部调用链；技术细节只进入执行记录或用户明确要求的技术说明。

交互遵守：

- 已知信息直接复用，每轮问题聚焦最影响下一步的一至三个事项；
- 平台知识、资产现状、工具能力和 Schema 由 Agent 调查；业务目标、偏好、权限和高风险选择由用户决定；
- 存在安全默认时说明默认方案、适用条件和影响；没有安全默认时等待用户提供事实或决定；
- 问题、能力缺口和验证盲区在发现时透明说明，同时给出可行处理路径；
- 修改前展示改前、改后和影响范围；执行后必须反读，不默认操作成功。

## 意图识别、访谈与任务启动

### 识别模式

| 用户意图 | 模式 | 启动所需最小信息 | 默认工单模式 |
|---|---|---|---|
| 创建场景包、沉淀业务流程、基于经验或项目搭建能力 | 创建 | 业务场景、业务终点，或可完整读取的参考材料 | `write` |
| 检查效果、分析绕行、分析项目执行日志 | 诊断 | 场景包、项目或明确问题对象 | `read` |
| 修改已知问题、落实诊断结论 | 优化 | 目标资产、修改目标和范围 | `write` |
| 继续已有制作、验证或发布任务 | 续作 | `task_id` 或足以定位原工单的信息 | 读取原工单 |
| 验证、上线或检查既有结果 | 验证发布 | 目标资产和期望状态 | 按是否写入选择 |

创建完成后的试运行可以进入诊断；诊断发现缺失资产可以进入优化或补建；优化完成后必须进入回归验证。只执行一次普通业务任务、只咨询概念或开发无关应用时不要进入本 Skill。

### 关键缺口判定

务必区分以下信息缺口：

- **意图缺失**（例如：“帮我做个东西”——没有明确目标）：必须向用户询问明确目标，不能开始方案设计。
- **关键参数缺失**（例如：创建模式下未提供业务场景描述；诊断模式下未指定目标场景包）：任务目标明确但缺少执行必须的前提参数，无法启动。必须向用户索要缺失参数。
- **知识缺失**（例如：“我不知道具体需要哪些工具”）：属于规划和调查范畴，把“调研线上资产与工具能力”纳入后续工作，不要求用户回答平台问题。
- **可选偏好缺失**：存在安全默认时采用并记录影响，不把偏好伪装为硬阻塞。
- **用户授权缺失**：在对应发布、删除、付费、权限扩大或真实副作用动作前明确确认，不能用默认值代替授权。

当用户上传文档或文件时，必须对其进行完整阅读和理解后再继续。严禁只浏览或仅阅读部分内容；内容被截断或分页时续读到结束。访谈按需组合、不要一次性全问：

- 业务场景描述：用户的业务是什么、服务谁、当前怎样做、最终目标是什么？
- 参考素材：是否有已执行项目、完整日志、上传文档、SOP、经验或已有场景包？
- 业务边界：哪些系统、数据、权限、成本、时效和合规条件不能改变？
- 成功标准：什么用户可见结果能够证明场景包有效？
- 创建与诊断：用户是新建、优化已有包，还是从失败项目倒查？

启动前至少明确：业务目标、目标用户、业务终点、关键输入与产出、操作对象、可读取证据、高风险边界和初步验收标准。其余平台知识和能力缺口由 Agent 调查。

### 连接检查与工单 Gate

开始具体任务时读取 [外部 MCP 工具路由](references/external-mcp-tools.md)，再核对实时工具 Schema。安装或连接验证只执行只读 `tools/list` 和一次只读资产查询，不创建工单、资产或项目。

意图和启动参数满足后：

1. 新任务的第一项业务 MCP 调用使用 `task_manager(action="create", mode=...)`。`write` 模式同时传入本文件 description 中的完整 `skill_version`。
2. 已知 `task_id` 的续作先单独 `task_manager(action="get")`。
3. 明确是续作但不知道 ID 时先单独 `task_manager(action="list")`；唯一匹配再 `get`，没有匹配才 `create`，多个候选请用户选择。
4. 等待 Gate 成功后再读取服务端制作契约、搜索资产、规划或写入；`list_assets/get_asset` 不接收 `task_id`，重要选择结论用 `task_manager(insert)` 记录。
5. `read` 诊断转入修复时新建 `write` 工单并传 `continued_from_task_id`，不在只读工单中执行写 action。

工单只记录业务事实、资产标识、决策、假设、阶段产物和验证摘要。不要写入密钥、Cookie、预签名 URL、原始敏感日志、供应商完整输出或内部挂载路径。

### 每阶段共同循环

每个阶段都执行同一闭环：

1. **执行**：完成当前最小原子操作；
2. **检查**：反读工具结果、状态、引用和交付物，严禁默认成功；
3. **记录**：用工单检查点保存可续作的事实、来源、选择、假设、资产和证据摘要；
4. **更新**：根据新证据修正蓝图、风险、阶段状态和下一步；
5. **推进**：满足阶段门后进入下一阶段，否则补证据、修复、重新规划或请求用户决定。

## 场景包模型与设计质量

场景包是一张通往共同业务终点的路线地图：

- **候选路线**：不同目标、准备状态、档案事实或限制对应的可行路径；
- **稳定路段**：输入输出和依赖在制作期可确定，适合工具、FastAgent 或 Workflow；
- **选路节点**：需要理解自然语言、业务档案、风险或当前结果，保留给 Agent、用户或平台已支持的 Gate；
- **到达标准**：证明业务终点和用户可见交付已经成立的证据。

参考项目只提供候选路线和证据，不能自动成为所有用户的唯一 SOP。业务档案只读取足以改变本次路线、参数、优先级或解释的最小充分信息；当前用户表达优先于历史记录，Agent 推断保持为假设，档案缺失、过期或冲突时补充事实或使用明确的安全默认。

### 选择执行形态

按职责而不是复杂度或资产数量选择：

| 需要 | 形态 |
|---|---|
| 少量、低风险、一次性的确定调用 | SA 直接执行 |
| 独立上下文、开放式判断或执行中自然语言交互 | 普通任务点 / TaskAgent |
| 一次输入、自包含推理、一次输出 | FastAgent |
| 至少两个稳定真实步骤、固定数据流或高频复跑 | 单 Workflow |
| 多个 Workflow 的固定扇出、汇合、映射和单次交付 | 当前服务端支持的固定 DAG 编排 |
| 多入口、用户动作、重入、受控循环或多交付 | 仅当实时 Schema 和版本化服务端契约明确支持图编排时使用 |
| 场景专属可视化 Workflow 交互入口 | 当前业务界面能力 |

任务“复杂”或“有多个步骤”不自动意味着普通任务点；FastAgent 可以完成复杂但一次输入后无需交互的子任务。只有执行中确实需要补信息、暂停确认或与用户自然语言交互时，才选择普通任务点。Workflow 只固化无需临场业务判断的稳定真实步骤。

当前实时 `scene_package_manage` 只公开固定 DAG 时，只制作固定 DAG。设计稿、集成分支、旧资产和示例不能证明新图能力已上线；禁止从这些资料复制 `capability`、Gate、边或 Runtime 字段。实时工具和服务端契约出现新版本后，再按该版本提供的形状制作，不能把固定 DAG 与新图对象混写。

业务界面是交互层，不执行或解释内部 DAG。当前 `scene_package_ui_bundle` 要求场景包至少挂载一个 Workflow 时，没有 Workflow 的场景包不能通过该工具制作定制界面；记录当前平台限制并回落对话界面。以后只有实时 Schema 明确解除该门槛时才改变此结论。

### 信息归属

| 信息 | 权威位置 |
|---|---|
| 单工具用途、参数和正式 Schema | Tool Group / 实时工具契约 |
| 工具或 FastAgent 的搭配、加载方式和具体调用链 | Toolset 使用指南 |
| FastAgent 自包含推理方法 | FastAgent Prompt |
| 普通任务点的交互式执行方法 | 任务点 Prompt |
| 单阶段稳定步骤和数据流 | Workflow 脚本与 IO Schema |
| 多 Workflow 依赖、映射和交付 | 当前版本的 `workflow_orchestration` |
| 共同终点、候选路线、里程碑、选路、权限、前置检查和知识读取时机 | `apc_skill` |
| 长知识、模板、案例、字段字典和详细 SOP | 场景 Skill 文件 |
| 数据语义和查询规则 | Dataset Skill |
| 页面与公开交互契约 | 业务界面源码和宿主 SDK |

同一规则只保留一个权威位置。不要在 `apc_skill` 复制 DAG、工具完整 Schema 或制作说明，也不要因为避免重复而删掉 SA 必须始终知道的业务路由、关键前置检查、能力选择和加载时机。

### Skill 颗粒度和 `apc_skill`

从理想态反推 Skill 颗粒度。凡是希望减少的失败、绕行或沟通轮次，都必须有对应的可执行指导：

| 目标瓶颈 | 至少写到什么程度 | 主要归属 |
|---|---|---|
| 不知道先做什么 | 阶段目标、前置检查、能力选择和交付条件 | `apc_skill` |
| 不知道工具如何搭配 | 先取得什么结果，再由什么能力消费 | Toolset 使用指南；`apc_skill` 只写加载时机 |
| 不知道参数或字段怎样准备 | 必填结构、来源、约束和失败处理 | Toolset / 场景 Skill / Workflow Schema |
| 找不到能力 | 条件 → 加载哪个能力域或读取哪个 Skill 文件 | `apc_skill` |
| 缺领域知识 | 可执行规则、数据字典、案例和详细 SOP | 场景 Skill 文件 |
| 交付结果不稳定 | 明确输出模块、质量门和验收证据 | `apc_skill` + 对应执行资产 |

`apc_skill` 至少说明：场景问题、共同终点和适用条件；里程碑、每阶段目标与用户可见产出；候选路线及选路节点；必需输入、预期交付和验收标准；Agent 可判断、用户必须决定与高风险授权的边界；业务档案的最小读取规则、证据优先级和缺失处理；未被其他资产固化的关键业务规则、前置检查和能力选择；在哪个阶段按名称读取哪个场景 Skill 文件；如何通过现有投稿和审稿机制整理候选事实。

每个上传的 Skill 文件都必须被 `apc_skill` 在明确阶段索引。禁止“完善流程”“调用相关工具”“输出高质量报告”这类不可执行空话；必须补齐触发条件、输入来源、关键判断、期望产出和失败处置，但不复制单工具完整参数或 Workflow 脚本。

## 九阶段制作流程

### 1. 识别意图、渐进访谈并建立任务

先按“关键缺口判定”识别模式与硬缺口。只问用户才能回答的问题；从用户已有表达、附件、项目和场景包中能获得的内容直接读取，不重复询问。创建模式先明确业务场景、目标用户和共同终点；诊断模式先明确目标场景包或项目、症状和全量/聚焦范围；续作先恢复原工单。

目标明确后建立工单 Gate，记录原始诉求、已知事实、待验证假设、高风险边界和初步成功标准。计划以业务结果命名，第一项成果是“业务素材与场景理解”，不是“询问用户”。执行路径可预测时使用基础计划；涉及多源整合、多方案权衡、架构重构或高代价决定时使用深度计划。

**阶段产物**：任务模式、目标与对象、访谈事实表、关键缺口表、证据入口、初步验收标准、工单 ID。

**进入下一阶段的门**：意图明确，执行必须的关键参数齐备；剩余缺口属于可调查知识、可安全默认偏好或已识别的未来授权点。

### 2. 收集业务素材并完整深读证据

收集用户主动提供的已执行项目、文档、SOP、规范、经验、数据和已有场景包；再主动读取官方基础场景包、相关经验、可复用场景包与当前服务端 `scene_package` 契约。用户提供的真实项目优先级最高，因为它包含实际策略、绕行、失败和交付。

参考项目必须三层递进分析，不能只看摘要：

1. **概览层**：读取项目 summary，统计用户请求、执行阶段、Agent/FA/工具分布、等待、失败与交付概况；摘要只用于定位，不能作为完整结论。
2. **深读层**：读取 detail 和必要原始日志的全部分页，重点检查用户原始意图、计划逻辑、工具密集阶段、参数传递、TaskAgent/FA 输入输出、失败重试、等待原因和最终交付。
3. **分析层**：统计有效推进、重复沟通、失败重试和等待；定位主要瓶颈并归类为缺知识、缺工具、缺指引、缺前置检查或错误资产边界；提取真实调用链和未被使用的 Skill。

文档必须完整阅读；资产必须反读完整配置、权限、版本、关系和 Schema。受限资产的脱敏空字段不等于资产为空或运行不可用。任何能力削减、替换或降级都先向用户说明原能力、原因、替代边界并等待确认。

**阶段产物**：证据目录、项目三层分析、现状流程、真实调用链、瓶颈与根因、可复用知识、事实与假设分离表。

**进入下一阶段的门**：所有用户指定材料已完整读取；参考项目已完成三层分析；关键结论均能指向用户材料、线上资产、服务端契约或运行日志。

### 3. 提炼里程碑、候选路线并形成场景包蓝图

基于证据回答：场景从什么触发，分几个关键阶段，每阶段目标、输入、责任方和用户可见产出是什么，阶段之间怎样依赖，最终怎样证明业务终点成立。向用户展示里程碑理解并确认遗漏与权限边界。

把参考项目路线转成候选路线，不直接固化为唯一 SOP。为每条路线注明适用目标、准备状态、业务档案事实、前置条件、选路节点、稳定路段、用户确认点、失败/降级路径和到达标准。

构建“现状 → 理想态 → 配置手段”映射：

- 缺知识导致试错：补充业务规则或场景 Skill；
- 不知道能力顺序导致绕行：补充阶段前置检查和 Toolset 搭配指引；
- 参数结构不清导致失败：补充 Schema、字段来源和示例；
- 找不到能力导致浪费：在 `apc_skill` 建立能力与 Skill 文件索引；
- 重复、稳定且高复用的真实步骤：评估 Workflow；
- 需要临场判断或中途交互的阶段：保留给 SA、TaskAgent 或用户。

有真实项目基线时，可以预测轮次、失败重试或人工确认的改善，但必须列出计算依据、假设、不可优化部分和误差；没有真实基线时只做定性价值判断。根据用户诉求明确 Focus（针对已知任务优化到可执行细节）或泛化（沉淀可迁移策略、保留选路弹性）模式。

**阶段产物**：经确认的里程碑、候选路线地图、业务档案影响、理想态与瓶颈映射、Focus/泛化决定、输入输出与验收蓝图。

**进入下一阶段的门**：用户认可业务理解和预期效果；每个里程碑、路线与价值主张都有证据或明确假设；蓝图不遗漏异常路径、授权和最终交付。

### 4. 能力摸底、架构设计、方案挑战并确认

用 `list_assets/get_asset` 搜索并完整反读场景包、任务点、Toolset、FA、Tool Group、Dataset 和相关经验；读取将要创建或诊断的资产规范。按每个里程碑建立能力覆盖表：已覆盖、可组合覆盖、需维护、真实缺口、受限能力和验证方式。长期 Dataset 只能绑定真实可访问资产，不能假设用户拥有；业务档案只使用最小充分事实。

工具缺口按优先级处理：先判断现有能力能否通过更好的 Skill 指引组合完成；再搜索或注册现有 MCP；仍缺失时形成可转交的开发需求；用户接受后也可先跳过并记录能力边界。工具缺口不可阻塞创建流程，但不得静默削减用户明确要求或参考项目中已有的能力。

按“选择执行形态”形成内部资产蓝图：每个资产的职责、复用理由、输入输出、依赖、加载方式、权限、副作用和验证证据；区分预加载核心能力与动态辅助能力。先反读关键 ID 的真实名称，禁止凭记忆填 ID。共享资产可能影响其他场景包时，克隆后再修改。

创建任何资产前完整读取 [方案挑战检查清单](references/方案挑战检查清单.md)。挑战至少检查业务闭环、资产是否多余、Agent/Workflow 边界、依赖闭包、异常路径、外部副作用、交付证据和能力缺口。质疑成立就修正；不成立则说明证据和取舍，不礼貌性通过。

方案是给用户看的，用管理型语言描述“能帮我做什么、分几步、每步产出什么”。说明每阶段哪里暂停确认、缺口怎样处理，不展示“调用某工具、传某字段、创建某 ID”。用户确认整体方案后，授权覆盖同一范围内可逆的离线草稿创建和修复；范围、路线、能力削减或风险发生实质变化时重新确认。

**阶段产物**：能力覆盖矩阵、资产蓝图、差异与缺口方案、方案挑战结论、用户可读方案、确认范围。

**进入下一阶段的门**：关键能力真实可用或缺口处理已确认；方案挑战无未解决阻断项；用户已确认业务方案、交付、授权边界和已知局限。

### 5. 准备依赖并创建或更新场景包草稿

优先复用现有资产。需要新建时按真实依赖自底向上准备：Tool Group/授权卡 → FastAgent → Toolset → 普通任务点；每创建一步都反读关系和状态。只有缺少可信 output Schema 的安全只读 MCP 工具才使用两组代表性输入取样并复验最小候选 Schema；破坏性、发布、凭证、金融或不可逆调用未经授权不得取样。

起草达到“Skill 颗粒度”要求的 `apc_skill` 和必要场景 Skill 文件。逐一对照第 3 阶段的瓶颈、里程碑和候选路线，确认每个预期减少的绕行都有对应指导，每个 Skill 文件都有明确读取时机，数字资产 ID、制作说明、DAG、工具完整 Schema 和具体私有档案事实没有混入。

调用实时 `scene_package_manage` 创建离线草稿；当前 create 默认克隆官方基础场景包时，立即反读继承的基础能力、关系和 warning，只修改真实需要的部分。保存 `scene_package_id`，后续修复更新同一草稿，不创建平行资产绕过错误。上传场景 Skill 文件使用 `workflow_file_upload`，再以 `skill_files_mode="merge"` 绑定。

诊断优化模式先反读目标包全貌；结构类与关系类问题优先修复，再处理文本、Prompt 和知识，最后才重建资产。修改共享资产、替换受限能力、删除或扩大范围需要相应确认。

**阶段产物**：依赖资产及状态、最终 `apc_skill` 草案、场景 Skill 文件与索引、同一场景包离线草稿、继承与差异清单。

**进入下一阶段的门**：草稿可反读；引用真实存在；信息处于正确层级；依赖闭包和权限明确；`apc_skill` 覆盖蓝图且达到可执行颗粒度。

### 6. 按需制作普通任务点、Workflow 和编排

普通任务点用于执行中需要自然语言交互、补信息或开放式判断的完整任务；FastAgent 用于一次输入后自包含完成的子任务。为两者读取匹配服务端规范，确保 Prompt 包含角色、执行策略、工具选择、输入输出和失败处理，并核对依赖资产真实存在。

确认需要 Workflow 后读取 `workflow_authoring`；写脚本前读取 `workflow_single`；确认需要多 Workflow 后读取实时 `workflow_multi`。特殊原语、文件、handoff 或失败模式按需读取匹配示例，同一工单不重复通读同一 topic。

每条 Workflow 执行完整闭环：

1. 从蓝图冻结业务职责、根对象 input/output Schema、代表性输入、文件与副作用边界；
2. 反读 Toolset 成员和在线状态，安全取样后上线本任务新建依赖，再确认 `is_online=true`；
3. 有 `ctx.skill_dir` 文件时完成上传闭环并提供完整目标集合；
4. Preview，按字段、工具、路径和确定性规则修复同一草稿；
5. Create/Update 同一 Workflow，保存并反读 ID、slug、Schema、依赖和版本；
6. bubble start/poll 到终态，检查 steps、run trace、coverage、未触达工具、final output 和 error；
7. 读取 [Workflow 验收检查清单](references/Workflow验收检查清单.md) 做语义验收，失败则更新原 Workflow 并重跑。

多 Workflow 编排前再次读取实时场景包 Schema 和服务端版本契约。当前固定 DAG 使用完整 `workflow_orchestration` 对象整体替换，检查节点引用、依赖、映射、delivery 和 `sa_handoff`；新图只在实时能力明确支持时制作。所有节点先满足单 Workflow 契约，编排保存通过不能替代整条路线运行证据。

**阶段产物**：普通任务点/FA 配置、每条 Workflow 的版本与 bubble 证据、当前版本编排对象、静态校验和未覆盖分支。

**进入下一阶段的门**：实际需要的执行资产已挂载；每条 Workflow Preview、bubble 和语义验收通过；固定 DAG 保存门通过或平台阻断已明确记录。

### 7. 按需制作业务界面

先核对实时 `scene_package_ui_bundle` 的 Workflow 门槛和宿主 SDK 能力。当前场景包已挂载 Workflow 且用户需要定制入口时，完整读取 [业务界面制作契约](references/业务界面制作契约.md)，冻结场景包、Workflow/编排版本、公开输入、状态、文件和最终交付契约。

必须从 `download_template` 返回的当前官方模板开始，校验下载字段、字节数、归档安全和唯一 `goalfy-app.json` 根目录，完整读取模板必读说明。业务界面只消费宿主公开契约，不接收 TPE ID、工具清单、提示词、脚本、DAG 或 Agent 控制动作；固定 DAG 或未来图只有宿主公开匹配版本的顶层运行能力时才提供整包入口。

按模板完成真实业务控件、上传、提交、等待、错误、权限、结果和回落聊天路径；删除 Demo 后执行类型检查、lint、测试、build 和 mock 主路径。打包源码，校验大小与 SHA256，完成 prepare upload → PUT → complete → deploy/status → get。运行契约变化后重新冻结契约并回归部署。

**阶段产物**：UI 契约快照、模板身份、源码包 SHA256、构建测试证据、deployment ID、激活地址和回落策略。

**进入下一阶段的门**：不需要 UI 时已记录原因；需要 UI 时通过 [业务界面验收检查清单](references/业务界面验收检查清单.md)，绑定、SDK、安全、交互、构建和部署全部取得当前证据。

### 8. 整包诊断、分层验收并闭环修复

发布前读取 [场景包验收检查清单](references/场景包验收检查清单.md)，把 `apc_skill`、Skill 文件、任务点、Toolset、FA、Tool Group、Dataset、Workflow、编排、业务界面和交付物作为一个业务闭环验收。逐项确认蓝图中的每个里程碑、候选路线、前置检查、授权和到达标准都有真实承载。

证据分层记录，不用上层文字检查冒充下层运行：

- `asset_contract_validated`：资产存在、关系、权限和 Schema 已反读；
- `workflow_bubble_passed`：目标 Workflow 当前版本有终态轨迹和语义验收；
- `orchestration_static_validated`：Hub 保存门通过节点、映射、交付和版本结构；
- `orchestration_runtime_verified`：真实运行命中目标编排并验证顺序、Gate/handoff 和交付；
- `ui_deployment_verified`：当前契约对应的源码、构建、部署和反读通过；
- `full_validation_skipped`：用户跳过全真运行，并记录 FA 内容、未触达分支和副作用盲区。

诊断遵守“先广后深”：场景包与任务点/Workflow 全部检查；Toolset 全部扫描述、使用指南和关系；只有上层线索、用户反馈或真实引用指向时才深挖 FA、Tool Group、Dataset 和 UI。全量诊断是每层都覆盖，不是每个底层资产都无差别深挖。

逐层检查维度至少包括：

- **场景包**：名称与描述是否表达业务边界；`apc_skill` 是否覆盖蓝图并达到瓶颈所需颗粒度；Skill 文件索引、预加载/动态能力、业务档案和信息归属是否正确；
- **普通任务点 / Workflow**：SA 能否仅凭名称和描述正确路由；输入输出、Prompt/脚本、模型、文件、依赖与交付是否闭合；该职责是否真的需要该执行形态；
- **Toolset**：描述能否支持动态加载；使用指南是否说明真实工具/FA 的搭配；成员是否处于同一能力域并覆盖上层需求；
- **FastAgent**：调用时机、Prompt、工具、模型、轮次、输入 Schema 和输出要求是否匹配自包含子任务；是否应由 SA 直接执行；
- **Tool Group / Dataset / UI**：工具路由与参数 Schema 是否防御性充分；数据绑定和查询规则是否真实有用；UI 是否只消费当前公开契约并完成真实交互闭环。

发现按 critical、warning、suggestion 分级，逐项给出位置、当前事实、规范证据、根因、业务影响、建议和改前/改后。修复顺序为结构与关系 → IO 契约 → 运行知识和 Prompt → UI；每次修复重跑所有受影响验证。缺少整图运行工具或真实日志时只能记录静态通过和运行盲区，不能声称编排已全真验证。

**阶段产物**：整包验收裁决、分层证据矩阵、诊断报告、修复 diff、回归结果、未覆盖分支和剩余盲区。

**进入下一阶段的门**：critical 全部关闭；warning 已修复或经用户接受；发布范围内资产和交付证据一致；任何 `skipped`、`blocked` 或 `platform_blocked` 都有明确影响和后续条件。

### 9. 发布、全真运行、复盘交付并关闭工单

发布前反读最终场景包和所有引用，确认 `apc_skill`、Skill 文件索引、资产状态、专项验证、用户授权和盲区一致。发布是外部状态变更；只有用户当前请求或已确认方案明确包含发布时调用 `scene_package_manage(online)`，随后反读线上状态。不能因离线验收通过就声称已发布。

真实 Max 项目会启动真实 Agent、FA、工具和外部副作用。只有用户批准覆盖所选路线可能执行的全部 Workflow 后才运行；跳过时继续交付并记录 `full_validation_skipped`。运行后复用同一 `project_id` 执行 wait/status/reply 和日志读取，不为轮询或小修复反复新建项目。

全真运行同样三层复盘：summary 建立概览；detail 和产物完整深读；再分析实际路线是否符合蓝图、工具调用是否合理、FA 结果是否被采用、用户确认是否正确、最终交付是否达到到达标准。发现问题回到对应阶段修复并重验，形成“运行 → 分析 → 优化 → 回归”的闭环。

最终交付结论先行，包含：场景包名称/ID和状态、解决的业务问题、里程碑与候选路线、核心资产与能力、验证证据层级、真实项目结果或跳过决定、能力缺口、剩余盲区和后续条件。只有发布状态和实际证据都成立时才能说“可直接使用”。

用 `task_manager(insert)` 记录最终资产、验证层级、全真决定和盲区，再 `task_manager(complete)`。不得用完整日志、凭证或临时 URL 充当工单交付。

**阶段产物**：线上场景包反读、可选真实项目与交付物复盘、最终交付报告、完整工单检查点。

**完成门**：用户授权范围内的发布和验证已经真实完成；交付声明与证据层级一致；工单关闭且没有被隐藏的阻断项。

### 诊断与优化如何进入九阶段

诊断不是九阶段之外的简化流程：阶段 1 明确对象和范围；阶段 2 完整读取资产与日志；阶段 3 建立现状、理想态和验收基线；阶段 4 做分层能力诊断并确认修复方案；阶段 5 修复结构、关系和 Skill；阶段 6/7 重做受影响执行资产和 UI；阶段 8 完成回归验收；阶段 9 按授权发布、试运行和交付。聚焦诊断可以缩小每阶段范围，但不能跳过证据、用户确认或受影响验证。

## 授权与恢复边界

用户确认的整体方案可以授权同一范围内的离线草稿创建、可逆更新、上传和验证。以下动作必须有明确授权，除非用户当前请求已经清楚包含它们：修改会影响其他场景包的共享资产；替换受限或用户指定能力；删除资产、替换凭证或扩大权限；发布场景包或业务界面；收费、邮件、通知、正式业务写入和其他外部副作用；真实 Max 全真运行。

发现受限资产时区分“配置不可见”和“运行不可用”，说明影响后再决定保留、克隆或替换，不把脱敏空字段误判为空资产。工具缺口可以采用已确认的降级方案继续，但不能静默削减能力。

- 工具或 action 不存在：重读实时 Schema，更新调用，不虚构平行工具。
- 工单模式或 Skill 版本不匹配：按结构化错误切换工单或执行受控升级，不绕过 Gate。
- Preview、bubble、Hub 或部署失败：修复同一资产或源码包，再重跑受影响验证。
- 路线需要临场规划：停止强行固化 Workflow，交还 Agent 或普通任务点。
- 当前平台不支持计划中的图或 UI 模式：保留业务蓝图，采用当前可表达的安全路径或记录平台阻断，不用前端或脚本伪装能力。
- 参数错误、偶发超时等可恢复问题：改变参数或条件后重试；禁止原样无限重试。
- 原策略失效或方案挑战发现严重结构问题：返回阶段 3/4 重构蓝图，不在错误架构上堆补丁。
