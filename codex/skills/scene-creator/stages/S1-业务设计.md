# S1 业务设计

从业务素材到已确认的方案 Plan。本阶段不创建任何正式资产。

## 1. 进入前提与产出物

进入前提：有 `write` 工单（路由器·前置条件）。

本阶段产出：里程碑与候选路线、正反例（结果检查表种子）、执行形态结论、面向开发者的业务路线图、执行结构表（`challenged=true`）、已确认的方案 Plan。修订已上线包的任务还需持有草稿行（见第 11 节）。

## 2. 素材收集与信息缺口

### 2.1 业务素材收集

开发者主动提供的材料按可信度排序：**已执行项目（最高，含真实策略、绕行、失败和交付）** → 上传文档与 SOP → 指定的已有场景包。

你**必须**主动获取的：

- 用 `get_asset` 查看**官方基础场景包**的完整配置，理解其预加载与动态工具集的组合方式，作为选型基准
- 用 `list_assets` 加 `get_asset` 查找可参考的已有场景包
- 用 `get_diagnosis_doc(scene_package)` 读当前场景包契约

### 2.2 关键缺口判定

务必区分五类信息缺口，处理方式完全不同：

| 缺口类型 | 例子 | 处理 |
|---|---|---|
| **意图缺失** | "帮我做个东西" | **必须**向开发者询问明确目标，**禁止**先设计方案 |
| **关键参数缺失** | 创建模式未描述业务场景；诊断模式未指定目标场景包 | 目标明确但缺执行前提，**必须**向开发者索要 |
| 知识缺失 | "我不知道需要哪些工具" | 属于调查范畴，把"摸底线上资产与工具能力"纳入后续工作，**不要**让开发者回答平台问题 |
| 工程偏好缺失 | 命名风格、代码组织、等价展示细节 | 存在可逆且不改变业务语义的默认时采用并记录影响，**不要**把工程偏好当成必须先解决的阻塞项 |
| 产品决策缺失 | 路线、Focus/泛化、审阅责任、界面模块、最终用户介入 | 放入 Plan 集中确认；只有一个独立决策时单项询问，**不得**由 Agent 使用默认值 |
| 开发者授权缺失 | 发布、删除、收费、真机运行 | 在对应动作前明确确认，**不得**用默认值代替授权 |

开发者上传文档或文件时，**必须**完整阅读后再继续。**严禁**只浏览或只读一部分；内容被截断或分页时**必须**续读到结束。对开发者材料的不完整理解是错误输出最常见的根源。

### 2.3 访谈方法

访谈按需组合，**不要**一次性全问。每轮聚焦最影响下一步的一到三个事项；相互关联的产品选择优先汇总到 Plan：

- 业务场景：业务是什么、服务谁、现在怎么做、最终要什么结果
- 参考素材：有没有已执行项目、完整日志、文档、SOP、已有场景包
- 业务边界：哪些系统、数据、权限、成本、时效、合规条件不能改
- 成功标准：什么最终用户可见结果能证明场景包有效
- 模式：新建、优化已有，还是从执行失败的项目反查原因

启动前至少明确：业务目标、最终用户、业务终点、关键输入与产出、操作对象、可读取的证据、高风险边界、初步验收标准。其余平台知识由你自己调查。

## 3. 参考项目三层深读

开发者提供了参考项目时**必须**完成三层，**禁止**只看摘要下结论（约束 3）。

**第一层 概览**：读项目摘要，统计总轮次、最终用户请求序列、执行阶段、Agent 与工具分布、等待与失败概况。摘要是压缩后的统计信息，**只能**用于建立全局视图和定位需要深挖的轮次，**不能**作为结论。

**第二层 深读**：读取完整原始日志的全部分页，截断时**必须**续读到结束。重点看：最终用户原始意图与约束、规划逻辑与步骤拆分、工具调用密集的阶段（调用链、参数传递、前后依赖）、任务点与 FastAgent 的输入输出质量、失败重试、等待原因、最终交付是否匹配预期。

**第三层 分析**：形成以下可复核结论并写入工单：

- **轮次分类统计**：总轮次、有效推进、重复沟通、失败重试、等待
- **瓶颈定位**：消耗最多轮次的阶段，根因归类为缺知识、缺工具、缺指引、缺前置检查或资产边界错误
- **真实调用链提取**：每个业务阶段实际调了什么、顺序如何、有没有前置依赖但 Agent 不知道
- **Skill 使用情况**：哪些文件被读取、哪些应该被引导读取但没有

多个项目对比时，**必须**逐项目保留独立事实，再提炼共性，**禁止**用平均值掩盖异常。

**完成标准**：三层全部完成并写入工单后才能进入下一步。**禁止**只看摘要就跳过深读——这是本阶段最容易出现的问题。

## 4. 里程碑、候选路线与正反例

### 4.1 里程碑与候选路线

基于素材和项目分析回答：场景从什么触发、分几个关键阶段、每阶段的目标与输入与责任方与最终用户可见产出、阶段间怎么依赖、最终怎么证明业务终点成立。

向开发者展示里程碑理解、候选路线和权限边界，作为方案 Plan 的第一组业务决策集中确认；Agent 的提炼结果在确认前只属于候选草案。

参考项目的路线转成**候选路线**，**不要**直接固化成所有最终用户的唯一 SOP。每条路线注明：适用目标、前置条件、在哪里判断走哪条、哪些步骤是稳定可固化的、最终用户确认点、失败与降级路径，以及**到达标准**（能证明这条路线已走完、业务终点已达成的证据）。

### 4.2 索取正例与反例

确认里程碑的同时，**必须**向开发者索取具体案例——里程碑是抽象的，开发者点头了也不代表双方对"具体一个输入该产出什么"的理解一致。

对每个关键阶段各要一组：

| | 索取内容 |
|---|---|
| **正例** | 一个真实输入，以及开发者期望场景包向最终用户交付的产出。**必须**是具体的，不接受"大概就是分析一下"这类描述 |
| **反例** | 一个容易被做错的情况，以及为什么错、正确做法是什么 |

**反例往往比正例更有价值**——它暴露的是开发者或最终用户觉得“显然不该这样”、但没说出口的隐含规则。Agent 负责从证据中提炼候选规则；规则会改变业务行为时，必须交开发者确认后再固化。

案例写入工单后，在四处复用：

| 用途 | 怎么用 |
|---|---|
| 判断需求理解是否正确 | 把正例的处理过程讲给开发者听，错了立刻能发现 |
| Workflow 运行验证 | 正例直接作为代表性输入（见 `stages/S2-资产制作.md` 5.3） |
| 场景 Skill 文件 | 写成示例，运行时 Agent 照着做（见 `stages/S2-资产制作.md` 9.3） |
| 真机验证 | 照着正例构造自然业务需求（见 `stages/S4-验证与修正.md` 3） |

开发者给不出具体案例时，**必须**如实记录这个情况——它意味着需求尚未清晰，后续所有判断都建立在推测上，要在方案里标明这个风险。

### 4.3 正反例转入结果检查表

收集到的每组正反例，**必须**同时按「输入 + 期望产出」结构化写入结果检查表（作为初始条目，状态 `pending`），并按路由器 5.3 落工单权威快照。结果检查表在 S4 逐条闭合、S5 结单校验；正反例只留在工单散文里而不转入表，视为本节未完成。

## 5. 理想态与价值预测

### 5.1 现状、理想态与配置手段

构建"现状 → 理想态 → 配置手段"的映射，它决定后续 Skill 要写到什么颗粒度：

| 现状问题 | 配置手段 |
|---|---|
| 缺知识导致试错 | 补业务规则或场景 Skill 文件 |
| 不知道能力顺序导致绕行 | 补阶段前置检查和工具集搭配指引 |
| 参数结构不清导致失败 | 补必填结构、字段来源、示例 |
| 找不到能力导致浪费 | 在 `apc_skill` 建立能力与文件索引 |
| 重复、稳定、高复用的真实步骤 | 评估做成 Workflow |
| 需要临场判断或中途交互 | 按开发者确认的边界保留给 SystemAgent、任务点或最终用户 |

**有真实项目基线时**可以预测轮次、失败重试或人工确认的改善幅度，但**必须**列出计算依据、假设、不可优化部分和误差范围。**没有基线时只做定性判断**，**禁止**编造数字（约束 2）。

### 5.2 Focus 与泛化

形成使用模式候选：

- **Focus**（"让这个任务更快更省"）→ Skill 写到工具调用级别，固化执行路径
- **泛化**（"沉淀经验用于类似场景"）→ Skill 写到策略级别，保留选路弹性

Agent 根据开发者目标和证据给出推荐，但 **Focus / 泛化必须作为方案 Plan 的显式选择项由开发者确认**；不得因为参考项目更具体就自动选择 Focus，也不得因为素材不足就自动选择泛化。

### 5.3 必须评估是否使用 Workflow

**这一步不能跳过，也不能默认不用。** 逐个里程碑对照第 6 节的信号判断，把结论和理由写入工单。

之所以要强制评估，是因为**做 Workflow 的工作量明显高于普通场景包**——要写脚本、备齐依赖、过上线检查、跑运行验证。省事的做法是全部交给 SystemAgent 临场处理，但那样会把消耗转移到每一次运行上。

两种做法的实际差异：

| | 交给 Agent 临场处理 | 固化成 Workflow |
|---|---|---|
| 每次运行的推理量 | 重新理解任务、重新决定调用顺序、重新组织参数 | 只在脚本里调 FastAgent 的那几步推理 |
| 推理消耗 | 上述推理**每次运行都会重复发生** | 确定步骤不经过大模型 |
| 耗时 | 随推理轮次增加 | 按脚本直接执行 |
| 一致性 | 同样输入可能走出不同路径 | 同输入同路径 |
| 出错定位 | 要读整段对话日志 | 定位到具体步骤 |

判断时先看**结构是否适合固化**：存在至少两个真实步骤，步骤顺序、数据流或扇出汇合关系稳定，不需要大模型在运行中改变下一步，就具备 Workflow 结构条件。再看**固化收益**：会被反复跑、定期产出、或最终用户每次只改几个参数时，固化的稳定性和成本收益更高。重复执行是重要收益信号，**不是唯一准入条件**；一次性任务若仍是确定、稳定的多步管道，也可以采用 Workflow。一次性探索分析若执行走向需要临场判断，则交给 Agent 或普通任务点。

向开发者提交结论时用业务语言讲清取舍：哪些阶段建议固化、这样做在稳定性和使用成本上的区别、哪些阶段建议保留临场判断以及为什么。**是否采用 Workflow 及对应资产边界由开发者在方案 Plan 中确认**；禁止只说"建议用 Workflow"而不说明理由，也禁止为了省制作工作量而不做评估。

向开发者提交价值预测与方案 Plan：预期效果、主要优化点、无法覆盖的部分、使用模式、Workflow 取舍及待确认项。开发者确认前不进入正式资产创建。

## 6. 执行形态选择

### 6.1 资产概念

场景包的组成、普通任务点与 Workflow 的 TPE 双类型关系、运行时自带的默认能力、四种执行形态各自的构成与能力边界，正本在路由器 `SKILL.md` 第 7 节（常驻）。本节只承载选型决策。

### 6.2 四者对照

| | SystemAgent 直接执行 | FastAgent | 普通任务点 | Workflow |
|---|---|---|---|---|
| 是否独立资产 | 否 | 是 | 是（TPE） | 是（TPE） |
| 上下文 | 主对话 | 每次全新隔离 | 独立 | 独立 |
| 能否与最终用户交互 | 能 | **不能** | **能** | 单条**不能** |
| 执行步骤 | 临场决定 | 临场决定 | 临场决定 | **预先固定** |
| 自带文件/命令/邮件 | — | **不自带** | 自带 | 自带 |
| 与编排的关系 | — | 被 Workflow 调用 | **不能**作为编排节点 | 可作为编排节点 |
| 多次运行的一致性 | 每次重新推理，路径可能不同 | 每次重新推理 | 每次重新推理 | 同输入同路径 |

### 6.3 怎么选

按以下顺序完成一次决策，**不要**按复杂度、步骤数量或资产数量来回切换：

1. 先判断执行路径是否需要大模型在运行中决定下一步，或是否需要自然语言往返。需要时使用普通任务点；不需要时继续。
2. 再判断是否存在至少两个实质步骤、稳定数据流、固定扇出/汇合，或同一路径需要参数化复跑。存在时使用 Workflow；需要多个职责边界时拆成多个 Workflow 并写入图编排。
3. 若整个任务只是一次输入、自包含推理、一次输出，使用 FastAgent，不为它增加单步转发 Workflow。
4. 若只是当前上下文中确定的少量调用，且没有独立复用价值，由 SystemAgent 直接执行。

重复执行是 Workflow 的重要收益信号，不是唯一结构判据；两三个稳定步骤组成的一次性固定管道也可以是 Workflow。

决策结果可用下表复核：

| 需要 | 形态 |
|---|---|
| 确定的 1–5 次调用、指令量小、仅当前场景用 | SystemAgent 直接执行 |
| 独立上下文、开放式判断、执行中需要自然语言交互 | 普通任务点 |
| 一次输入、自包含推理、一次输出、多场景复用 | FastAgent |
| 至少两个稳定真实步骤、固定数据流、会被反复跑 | 单 Workflow |
| 单条 Workflow 需要发布业务事件、接受业务表单握手或进入 Delivery Review | 单节点业务路线编排 |
| 一条路线内多个 Workflow 的固定依赖、扇出、汇合和交付 | 多节点业务路线编排 |

任务"复杂"或"有多个步骤"**不自动**意味着要用普通任务点——FastAgent 可以完成复杂但无需交互的子任务。只有执行中确实需要补信息、暂停确认或自然语言交互时才选普通任务点。

**看到这些信号优先按 Workflow 设计**：

- **反复执行的固定流程**：每日简报、日报、周报这类同一条流程反复跑的产出
- **固定流水线**：搜索 → 筛选汇总 → 生成报告（→ 发送）这类定型流水
- **多对象并行加汇总**：多品牌、多平台、多主题并行调研后做横向对比
- **参数化复跑**：最终用户每次只填几个参数，跑同一套步骤、产出同类结果

判别标准：固定流水线、参数化复跑和定期产出通常适合 Workflow；一次性探索分析若执行走向需要临场判断，则使用普通任务点或 Agent。不能只凭“是否重复”覆盖前述结构判断。

原因是成本结构不同：交给 Agent 临场处理，等于每次运行都重新推理一遍同样的步骤，这部分消耗**每次运行都会重复发生**；固化成 Workflow 后，确定步骤不再经过大模型，只有真正需要判断的步骤（脚本里调 FastAgent 的地方）才产生推理。运行次数越多，差距越大。是否使用 Workflow 是**必须**评估的事项，见第 5 节。

### 6.4 FastAgent 数量纪律

**FastAgent 是推理单元。** 读文件、写文件、格式转换、数据搬运这类**确定性操作直接用工具调用**，**禁止**为其创建 FastAgent——无论赋予什么角色。判断一个步骤该不该用 FastAgent，先问：去掉大模型这一步还能不能确定性完成？能，就不用。

同一条 Workflow 内的 FastAgent **不拆开**：同域的多类产出用**「一个 FastAgent + 交付物参数分发 + 按交付物划分的规范文件」**承载——提示词只写共同原则与分发规则，每类交付物一份规范文件按需读取。**禁止**按"角色"把同域职责拆成多个只在措辞上不同的 FastAgent。

方案中 FastAgent 超过 3 个时，**必须**逐个说明不可合并的理由（该判据同时列入方案挑战检查清单）。

### 6.5 两个相反的错误

两个相反的错误都要避免：

**不要给单个 FastAgent 套一层 Workflow。** 如果脚本只做一件事——调用一个 FastAgent，然后把结果原样返回，中间没有任何其他处理——这层 Workflow 不提供任何价值，**直接使用那个 FastAgent** 即可。

**也不要因为步骤少就否定 Workflow。** 一条只有两三步的线性流程（搜索 → 清洗 → 汇总）完全正当。判据是**有没有至少两个实质步骤、数据有没有在步骤之间流转**，与步骤多少无关。

## 7. 业务路线设计

### 7.1 业务路线编排

业务路线编排是场景包上的**一个整体对象**，用来固化业务入口、运行身份、执行依赖、交付与审阅。路线可以只有一个 Workflow 节点，也可以包含多个 Workflow：

- **单节点路线**：单条 Workflow 声明或调用业务事件、需要业务表单握手、需要 Delivery Review，或需要由业务界面启动时使用。只有一个节点不代表可以绕开 Business Runtime。
- **多节点路线**：一条路线包含多个 Workflow 的固定依赖、扇出、汇合、交互和交付时使用。
- **直接派发**：仅适用于没有业务事件契约、没有 `emit_business_event`、不依赖 Business/Runtime 握手的单条 Workflow。

构成：

```text
编排对象
├── 版本标记
└── 路线 ×N                     每条路线对应一种业务走法
    ├── 唯一标识、名称、描述
    ├── 入口表单标识
    ├── 路线级输入定义
    ├── 节点依赖图                节点引用已挂载的 Workflow，必须无环且全部可达
    ├── 节点输入映射              逐字段声明取值来源：路线输入，或依赖的上游节点输出
    ├── 运行中交互（可选）         上游成功后才能确定、且供尚未派发的下游节点使用的输入
    ├── 节点级 Agent 介入（可选）  节点成功后需要检查或处理异常时声明
    └── 唯一最终交付与审阅动作  交付核验与业务验收是两个独立阶段
```

写入时采用**整体替换**语义，因此写前**必须**反读原值（见 `stages/S2-资产制作.md` 10.1）。字段的具体名称、结构和版本要求以 `get_diagnosis_doc` 的当前契约为准（见 `stages/S2-资产制作.md` 5.1）。

运行期事实：已发布路线在业务界面与聊天两个入口天然并存，走哪个入口由最终用户自选（界面经 Runtime 运行，聊天直调时业务事件自动降级）——这是平台行为，不是设计决策。制作侧**不设计**也**不引导**入口选择。

### 7.2 何时不使用固定编排

以下情况**不要**强行画成固定依赖图：

| 情况 | 应当采用 |
|---|---|
| 整条路径需要临场规划，或 Agent 介入产生的新值要成为后继输入 | 普通任务点 |
| 最终用户改稿、重做或改走另一条路线 | 冻结当前交付、开启新的运行实例。**禁止**在同一张图里画回边模拟循环，**禁止**覆盖旧交付或旧文件 |
| 制作期就能预知的最终用户输入 | 全部放入口表单，不用运行中交互 |
| 只有上游节点成功后才能确定、且要供尚未派发的下游节点使用的输入 | 节点级运行中交互 |
| 节点成功后需要 Agent 检查或处理异常 | 在该节点声明 Agent 介入，并写清指令和可验证的继续或接管标准 |

编排只调度**已经存在且通过单体验收**的 Workflow。场景包没有 Workflow 时**禁止**伪造空节点或空图。

### 7.3 面向开发者的业务路线图

涉及一条或多条业务路线时，完整方案 Plan **必须**先提供一张业务语言表达的路线依赖图。图中至少包含：路线入口、主要业务阶段、固定依赖、扇出与汇合、最终用户介入、Agent 介入、最终交付、审阅责任方，以及接受、拒绝、修订、重做或改走其他路线的出口。图只表达“业务如何到达终点”，不得出现资产数字标识、内部节点标识、工具名、Schema 路径或脚本调用链。

这张图是开发者确认业务结构的依据，不是可直接保存的机器编排对象。开发者确认后，开发 Agent 才能把它转换为真实 Workflow 节点、字段映射和编排契约；转换过程中发现业务依赖、介入点或出口需要实质变化时，必须先回到方案 Plan 更新业务路线图并重新确认。

### 7.4 最终交付的核验与验收

交付核验回答“这份结果是否真实、完整、可交付”，最终审阅回答“业务上是否接受这份结果、是否需要修订或改走其他路线”。两者**禁止**合并：Workflow 输出契约、数值、证据和文件校验通过，不代表最终用户或 Agent 已完成业务验收；节点级 `sa_handoff` 和质量检查 Workflow 也不是最终审阅的替代品。

最终审阅形态是场景包产品契约，**必须由开发者在方案 Plan 中确认**，开发 Agent 只能依据业务事实提出推荐，不能替开发者选定：

| 形态 | 运行语义 | Agent 向开发者说明的适用信号 |
|---|---|---|
| `user_gate + ask` | Runtime 向业务界面下发冻结交付和已声明动作；最终用户完成三次握手后，Runtime 直接执行所选的完成、失败或新路线动作，不额外唤起 Agent | 业务完成需要最终用户批准、满意度确认、方案选择、修订、改路线或高风险授权 |
| `user_gate + result` | Runtime 按既有 result / end-task 链路自动交付并结束，不要求最终用户或运行时 Agent 参与 | 生成且核验通过即达到业务终点，不需要额外业务判断 |
| `agent_gate` | 唯一主动唤起运行时 Agent 评价或选路的最终审阅边界；Agent 按开发者确认的可验证标准选择已声明动作 | 接受标准客观、可执行且确实需要 Agent 判断，而不是简单自动结束 |

完整交付方案必须分别回答四个问题：**结果最终交付给谁使用、谁负责判断业务上是否接受、可以执行哪些审阅动作、修订/重做/改路线后如何继续**。审阅责任方不能由“结果由谁使用”反推：结果可以交付给最终用户使用，但由 Agent 按客观标准审阅；也可以无需任何额外审阅，核验通过后直接交付并结束。

开发 Agent 必须把交付对象、推荐形态、理由、最终用户体验、失败或重入影响和可选动作一并交给开发者确认。开发者选择与已声明的高风险授权边界冲突时，指出冲突并重新询问，不得静默改成另一种 Gate。不能因为场景包能生成报告就默认要求最终用户回答“是否满意”，也不能因为 Agent 已读过结果就默认业务已接受。

`user_gate` 不得再叠加一层“交给 Agent 收尾”：`ask` 的具体动作由 Runtime 在收到有效表单答复后直接执行，`result` 由 Runtime 自动交付并结束。只有编排明确声明 `agent_gate`，或最终用户选择了已声明的“交由 Agent 处理”动作时，才建立 Agent 边界。制作方案、`apc_skill`、节点 `sa_handoff` 和业务界面都不得用额外 Agent 提示词模拟这次接管。

终态顺序**必须**是：解析真实 TaskPoint 输出 → 核验交付资格 → 冻结本次 Delivery → 执行已声明的最终审阅 → 根据审阅动作完成业务、结构化失败或开启新路线。在审阅明确接受前，**禁止**把结果展示当成已验收，**禁止**把 Business 标记为已完成，也**禁止**用旧的“Agent 先发送结果再接管结束”链路绕过 Delivery Review。修订、重做或改路线必须保留当前 Delivery，按当前契约新建运行实例，不覆盖旧结果。

场景包制作只声明对外稳定的资产契约：中间节点用 `sa_handoff`，最终审阅用 `delivery.review`。Max Runtime 如何生成 Agent 边界通知、注入执行上下文或封装内部控制消息，属于平台实现细节，**禁止**复制进 `workflow_orchestration`、`apc_skill`、场景 Skill 或业务界面契约。

## 8. 能力摸底与缺口处理

### 8.1 能力摸底与覆盖矩阵

三个只读工具：

| 工具 | 用途 |
|---|---|
| `list_assets` | 按类型搜索可复用资产。关键词只匹配名称和 ID，建议用英文短词；不传关键词会返回全量，注意上下文开销 |
| `get_asset` | 批量反读完整配置、关系、Schema、状态，一次 1–20 个 |
| `dataset_read` | 只读查看长期数据集或业务档案：描述、使用指南、Skill 文件、表、列、行 |

用 `list_assets` 和 `get_asset` 搜索并完整反读场景包、任务点、工具集、FastAgent、工具组、数据集。看 Schema 和真实配置，**不要**只看描述。

搜索结果**不是**完整资产契约，选型前**必须**用 `get_asset` 下钻（约束 4）。重要选择结论用 `task_manager(insert)` 留痕。

一次 `get_asset` 只返回该资产自身的配置，**不会**展开它引用的子资产。诊断时**必须**按层逐级下钻。

场景涉及数据查询或报表时，用 `list_assets` 列出开发者有权访问的长期数据集，`get_asset` 或 `dataset_read` 确认表结构与权限范围。数据集**只能**绑定真实可访问的，**禁止**假设开发者拥有某个数据集。开发者没有对应数据集时明确告知需要先去准备。

按每个里程碑建立覆盖矩阵：**已覆盖 / 可组合覆盖 / 需维护 / 真实缺口 / 受限能力 / 验证方式**。

向开发者输出每个里程碑的覆盖情况，把缺口处理选项、影响和推荐纳入方案 Plan，由开发者确认；Agent 不得以“工具缺口不可阻塞”为由自行削减业务目标。

### 8.2 工具缺口四层处理

工具缺口**不可**阻塞创建流程，但**不得**静默削减开发者明确要求或参考项目中已有的能力（约束 12）。按以下优先级处理：

**第一层 Skill 弥补**（成本最低，优先尝试）：工具能力已覆盖，问题只是缺调用顺序、前置检查、字段准备或结果审视方法。把指导写进正确层级即可。

**第二层 接入现有能力**：先在平台上找，平台没有再去外部找。

平台内：用 `list_assets` 和 `get_asset` 确认是否已有可复用的工具组——重复注册同一个服务会产生互相冲突的资产。

平台没有时**从外部获取**。你运行在能联网、能读写本地文件、能执行命令的环境里，这是 Max 内部制作助手做不到的，**应当主动利用**：

| 目标 | 去哪找 |
|---|---|
| 现成 MCP 服务 | MCP 官方索引、代码托管平台、包管理平台（npm / PyPI），以及开发者自己的私有仓库 |
| 现成 Skill 包 | 同上；开发者手里可能已有内部沉淀的包 |

找到候选后**先在本地验证，再走平台注册**。顺序反了会浪费大量试错：本地能起来、工具清单和返回结构都确认过，注册基本一次通过；直接注册再排错，每轮都要等平台反馈。

评估候选时**必须**看清四件事：

| 维度 | 为什么要看 |
|---|---|
| 是否仍在维护 | 长期不更新的服务上线后容易失效 |
| 连接方式 | 决定注册时传地址还是启动命令，以及运行环境要装什么 |
| 认证方式 | 全场景包共用一份凭证，还是每个终端用户各自授权——后者**必须**配授权卡 |
| 有无破坏性操作 | 决定哪些工具可以取样、哪些**禁止**取样，以及要不要在使用指南里加约束 |

开发者提供本地包或压缩包时，走 `file_to_url` 换取引用后注册或导入（见 `stages/S2-资产制作.md` 3.3）。完整的注册流程、失败调试循环和上线检查见 [依赖与 MCP 接入](../references/依赖与MCP接入.md)。

**第三层 形成开发需求**（开发者有协作团队时）：为缺失能力生成可直接转交的需求说明，**必须**写明业务动作、目标系统、必需输入与输出、授权方式、最终用户与项目隔离要求、副作用、失败语义、验收样例。格式要便于开发者一键转发给工程师。

**第四层 开发者确认后降级**：用已有能力继续制作，**必须**明确说明未覆盖的阶段、对结果的影响、以后补齐的条件和受影响的验证，并取得开发者确认。

### 8.3 实现思路调研

**不知道某个效果如何实现时**（有目标、无做法）——**先询问开发者是否有参考资料或已知同类产品**；没有再去 GitHub 等开源平台自行调研同类实现。调研的是**实现思路**而非现成资产，产出可以是自建 Workflow / 工具的设计依据，或转交开发需求（第三层）的技术方案参考。结论与来源记入工单。

## 9. 架构方案设计

### 9.1 工具集划分

**工具集划分**：

- 预加载：每次运行都必须出现的核心能力
- 动态：按需加载的辅助能力
- 选型规则：克隆官方包继承的核心工具集**不可**移除；优先复用系统级工具集；**按能力域**匹配，**不要**按业务场景创建专用工具集

**执行形态提案**：按第 6 节形成普通任务点、FastAgent、Workflow 或直接执行的候选边界，**不要**用"默认用 FastAgent"或"只有交互才建任务点"这类简化规则。Agent 必须说明推荐理由、运行体验、成本和可变性，把第 5 节的评估结论纳入方案 Plan；开发者确认后才落成具体资产，**禁止**在实现阶段自行推翻已确认结论。

### 9.2 内部资产清单

**内部资产清单**（记入工单，除非开发者要求技术说明，否则不放入业务方案）：

- 每个 FastAgent：名称、职责、输入输出、真实关联的工具组
- 每个工具集：能力域、成员、加载方式、使用指南要点
- 每个任务点：路由描述、交互需求、输入输出、关联工具集
- 每条 Workflow：稳定业务阶段、脚本要用的工具名、完整依赖清单、输入输出定义、辅助文件、副作用
- 每条编排路线：入口、节点、映射、交付审阅、重入方式
- 数据集：为什么绑定、在哪个节点读取

所有 ID **必须**工具查询确认（约束 4）。

**开发者可见的业务路线图**：提案包含 Workflow 或固定业务路线时，在完整方案 Plan 中用业务阶段名称画出每条候选路线的入口、依赖、扇出/汇合、最终用户与 Agent 介入、最终交付、审阅责任和动作出口。它与内部资产清单分开：前者用于确认产品如何运行，后者才用于确认真实资产如何承载；不得把内部节点标识、工具名或字段映射暴露到业务方案中。

### 9.3 执行结构表

方案的**强制产出**。为每条 Workflow 建立执行结构条目：

- 步骤清单：每步做什么、用什么（工具或 FastAgent）
- 步骤间依赖：谁的输出喂给谁
- **并行组**：相互无依赖且可安全并发的步骤归入同一并行组；相邻无依赖步骤**未**归入并行组的，写明原因（副作用顺序、共享路径、会话状态等）
- FastAgent 清单：本条 Workflow 用到的全部 FastAgent，及按 6.4 的不可合并理由

**并行组怎么画**，逐步骤按序检查：

1. **数据依赖**：这一步的输入是否用到另一步的输出？不用，继续；
2. **副作用独立**：是否写同一路径、共享同一会话、或有顺序语义的外发动作？没有，可并行；
3. **典型形态点名**：**对多个对象执行同一操作（循环逐个调用工具或 FastAgent）默认设计为并行组**——串行处理 N 个独立对象是最常见的浪费，除非对象间有真实依赖或共享副作用，并写入 `no_parallel_reason`。

设计时需要正反例的，读 `get_diagnosis_doc(workflow_example_parallel)`——**不要**等到写脚本才第一次接触并行原语。

**展示载体判定**：`by` 为 FastAgent 的步骤和关键工具步骤，建表时逐步判定其结果是否面向最终用户，三档：**不展示**（内部中间产物，默认）／**进业务事件**（值得单独展示的中间里程碑，走 S2-6.4 事件候选流程，由开发者确认）／**进交付**（纳入最终 `output` 业务字段或交付叙述）。判定记入该步的 `user_facing` 字段。***FastAgent 与工具的原始返回不是展示载体***——要给用户看的结果必须经事件或交付转成业务表达（如"素材盘点完成：4 张中 1 张可直接使用"，而不是工具返回原文）。

按路由器 5.1、5.3 落本地工作副本与工单权威快照。本表建立后，后续任何脚本或结构修改都**必须**同步更新对应条目（见 S2-资产制作）。

### 9.4 起草 apc_skill 与场景 Skill 文件

**起草 `apc_skill` 与场景 Skill 文件**：按 `stages/S2-资产制作.md` 9.3 校验颗粒度——逐一对照第 5 节里每个"预期减少的轮次"，确认都有对应的可执行指导，且每个文件都有明确读取时机。

## 10. 方案挑战与开发者确认

### 10.1 方案挑战

创建任何资产前**必须**完整读取 [方案挑战检查清单](../checklists/方案挑战检查清单.md) 并执行。质疑成立就修方案；不成立就说明证据和取舍。**禁止**在证据不足时判定通过。

挑战以执行结构表为对象逐条目进行，**只处理状态为 `pending` 的条目**（路由器 5.3 累加机制）；全部条目通过后，将执行结构表表级布尔位 `challenged` 置 `true`。

### 10.2 方案 Plan 内容

然后向开发者提交完整方案 Plan（管理型语言，按路由器 3.2），至少显式列出：

- 里程碑与候选路线，以及 Focus / 泛化选择；
- 各阶段采用直接执行、普通任务点、FastAgent 或 Workflow 的执行形态与资产边界；
- 面向开发者的业务路线依赖图：入口、业务节点、固定依赖、扇出/汇合、最终用户与 Agent 介入点、最终交付和各动作出口；
- 完整交付方案：结果交付给谁、由最终用户还是 Agent 审阅或无需额外审阅、采用 `user_gate + ask` / `user_gate + result` / `agent_gate` 中哪一种、允许哪些动作，以及修订/重做/改路线时如何开启新运行并保留旧交付；
- 提案包含 Workflow 时是否制作业务界面及其高层体验范围；
- 能力缺口处理、发布范围、是否在前三层候选验收通过后执行上线，以及端到端全真验证范围。

每项包含推荐、依据、影响和待确认选择。总体 Plan 只确认是否制作界面、它要承载的业务旅程与高层体验目标；具体页面范围和模块 include/exclude 在 `stages/S3-业务界面.md` 的业务界面预设计 Plan 中确认，不得在读取设计契约前凭空定稿。

“发布范围”和“上线授权”必须分开表达：发布范围只回答哪些资产与路线属于本次候选版本；上线授权回答候选验收通过后是否实际调用上线动作。总体 Plan 明确写出“前三层候选验收通过后上线”并由开发者统一确认时，不再在发布前重复询问；Plan 没有该执行承诺、只列发布范围时，`stages/S5-发布与交付.md` 必须另行取得上线授权。

### 10.3 开发者确认

执行结构表 `challenged=true` 后，连同方案 Plan 一并展示给开发者，由开发者选择方案是否可行。本次确认**兼作关键 FastAgent 的圈定时刻**：开发者在 FastAgent 清单上圈出关键产出环节（面向最终用户的输出文案类），被圈定的环节在 S2 制作时必须执行样例选择流程。Focus / 泛化在同一次确认中显式选择。

### 10.4 Plan 硬门

**Plan 硬门**：只有开发者对上述交付方案和业务路线图完成统一确认后，才能开始依赖资产、普通任务点、场景包草稿、Workflow、关联关系、业务路线编排或业务界面代码的创建与修改。确认前只允许继续只读调查、候选方案起草、方案挑战和不改变外部状态的验证。任一未确认项不得被 Agent 当成默认值写入资产；后续若改变路线依赖、交付对象、审阅责任、动作、重入方式或介入点，必须回到本节更新 Plan 并重新确认。确认后，同一范围内的可逆离线操作获得授权；上线动作仅在 Plan 同时满足上一段的明确执行承诺时获得授权（约束 6）。

## 11. 修订类任务的版本入口

修订**已上线**的场景包时，一切内容修改必须发生在草稿行上（详见 [场景包版本体系与发布逻辑](../references/场景包版本体系与发布逻辑.md)）：先取得可编辑草稿（从当前上线版本派生出 `testing` 状态的新物理行；家族同一时刻只允许一个草稿，已存在时复用），拿到草稿行标识后再进入 S2。取得草稿的具体调用以你实际看到的工具定义为准。

修订类任务的结果检查表**必须**从上一工单的最新 `result_checklist_snapshot` 继承全部条目，再叠加本次新增的正反例；条目指纹对新版本重算，受影响条目回退 `pending`——这是修订不坏旧例的回归机制（见 [表结构与累加机制](../references/表结构与累加机制.md)）。**禁止**只建本次新条目而丢弃历史条目。

## 12. 出口条件

以下全部满足后，按路由器 4.1 进入 S2：

- 执行结构表 `challenged=true`，且已随方案 Plan 经开发者确认（含关键 FastAgent 圈定、Focus/泛化选择）；
- 结果检查表已初始化（正反例已按 4.3 转入）；
- 修订类任务已持有草稿行标识。

以上全部满足后，按路由器 6.1 落一条 `stage_exit` 账，再进入下一阶段。
