## 1. 先划清案例边界

这是一个虚构门店的**方案制作**案例，目标是生成可审核的朋友圈广告获客方案包，不包含真实广告发布、扣费、创建广告账户或修改线上投放状态。

| 类型 | 本案例采用的示意事实 | 真正制作时如何处理 |
|---|---|---|
| 业务对象 | 虚构门店“河畔小馆” | 从用户材料读取（配套了智能应用时才另有智能应用数据集），不得沿用 |
| 业务终点 | 用户取得并确认一份可执行的广告方案包 | 与用户确认真实终点和到达证据 |
| 执行路线 | 首次生成、根据意见修订 | 根据用户目标提炼候选路线，不得默认只有这两条 |
| 能力 | 读取门店资料、生成策略、生成交付文件 | 用 `list_assets/get_asset` 和安全取样确认真实能力 |
| 智能应用 | 入口表单、运行状态、交付审阅 | 从当前官方模板和宿主公开 SDK 契约重新实现 |
| 验证 | Preview、bubble、路线静态保存、界面验收、可选全真 | 只记录真实取得的证据，未覆盖项列为盲区 |

可复用的是**推导方法和证据边界**；不可复用的是**案例结论和配置值**。

## 2. 业务访谈形成的最小事实集

### 2.1 业务终点

运营人员提交门店资料、投放目标、预算、受众偏好、品牌素材和禁用表达后，得到一份可审核的朋友圈广告方案包。方案包至少包含：

- 目标人群和触达理由；
- 三个创意方向；
- 预算与排期建议；
- 素材清单；
- 风险提示和仍需补充的信息；
- 一个可下载的 Workspace 文件。

用户在最终审阅时可以：接受并结束业务、询问 Agent，或填写修改意见开启新的修订路线。旧交付必须保留，修订不能覆盖原文件。

### 2.2 明确不做的事

- 不自动发布广告；
- 不根据案例预算替用户做真实扣费决定；
- 不把“方案已生成”说成“广告已投放”或“已经获客”；
- 不在浏览器界面暴露工具、FastAgent、脚本、节点 ID 或 DAG；
- 不把用户上传文件转换成构建机路径、URL 或 base64 后跨节点传递。

### 2.3 正例

虚构输入：

- 门店：河畔小馆，杭州滨江，家庭聚餐和周末生日宴；
- 目标：两周内收集到店预约线索；
- 预算：3000 元；
- 重点人群：门店 5 公里内、25～45 岁、家庭客群；
- 品牌素材：菜单、门头、包厢图片；
- 禁用表达：“全城第一”“保证到店”“零风险”。

期望结果：方案解释受众、创意、预算和排期之间的关系；所有风险表达有明确标记；交付文件存在且可以审阅；不得触发真实发布。

### 2.4 反例

| 反例 | 为什么错 | 正确处理 |
|---|---|---|
| 未提供预算仍自动填 3000 元 | 把案例值冒充用户事实 | 入口 Schema 拦截必填缺失，或明确要求补充 |
| 输出“全城第一”“保证到店” | 违反用户禁用表达 | 生成阶段返回风险项，交付阶段不得静默删除风险 |
| 把上传文件名或下载 URL 传给下游 | 文件不属于当前 Workspace 契约 | 入口使用 `format:file/image`，节点间保持 `workspace-file-path` |
| 用户点“修改”后覆盖原报告 | 破坏 Delivery 不可覆盖边界 | 启动修订路线的新 Runtime，生成新文件 |
| 页面直接选择某个编排型 TPE 或 TPE ID | 把内部业务路线泄露给智能应用 | 页面只提交公开 `orchestration_id/form_id` 和表单数据 |
| bubble 返回成功就声称广告方案有效 | bubble 可能使用 FastAgent 桩，也未覆盖真实业务内容 | 只证明已触达管路；真实内容需要经授权的全真验证和人工审阅 |

这些反例不是附录。它们必须分别进入入口校验、脚本输出、业务路线 Review、智能应用状态和验收用例。

## 3. 从业务事实推导候选路线

### 3.1 路线 A：首次生成方案

1. 标准化门店资料与投放约束；
2. 生成结构化获客策略；
3. 组装方案包并生成交付文件；
4. 用户审阅交付。

到达标准：结构化结果满足输出契约，交付文件属于当前 Runtime 的 Workspace，风险项未丢失，Delivery 已冻结并等待用户最终动作。

### 3.2 路线 B：根据意见修订

1. 接收已冻结的原方案文件和本轮修改意见；
2. 生成新的修订方案包；
3. 用户审阅新交付。

到达标准：新文件存在，修改意见有对应落实说明，原 Delivery 和原文件仍可追溯。

### 3.3 为什么不把修订画成回边

修订会改变输入并重新生成交付，属于新的业务路线和新 Runtime。若在路线 A 里从 Delivery 画回生成节点，会产生有环图、覆盖旧状态，并让“哪一次输出是正式交付”变得不确定。

## 4. 能力摸底和资产决策

真正制作时先建立覆盖矩阵。本案例只展示判断列，不提供可复制的资产名：

| 业务阶段 | 需要的真实能力 | 要取得的证据 | 选型 |
|---|---|---|---|
| 门店资料标准化 | 读取用户文件（场景包配套了智能应用时才另有智能应用数据集可读）、检查必填和禁用表达 | 资产详情、Input/Output Schema、安全样本 | 确定步骤直接进编排型 TPE；需要语义归纳时调用已验证 FastAgent |
| 策略生成 | 根据结构化资料生成受众、创意、预算和风险 | FastAgent 输入定义、提示词、真实输出结构 | 自包含推理步骤使用 FastAgent，由编排型 TPE 调用 |
| 交付包生成 | 将结构化策略写成 Workspace 文件 | 默认文件能力和真实文件路径 | 编排型 TPE 内确定性生成 |
| 修订 | 读取原文件和修改意见，生成新文件 | 文件契约、修订输出 Schema | 独立编排型 TPE，供修订路线使用 |

如果某项工具真实返回结构不明确，先对安全只读能力取样，再写 `_output`；如果候选能力有发布、扣费或外部写入副作用，不取样、不静默使用，单独取得授权。
