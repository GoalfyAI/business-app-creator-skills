# TPE 配置详解（一）：定位、名称、描述与输入输出要求

判断要不要建普通任务点（TPE）、写或诊断 TPE 的名称、描述、输入要求、输出要求时读。编排型 TPE 的脚本和 Schema 按 [编排型TPE总契约.md](编排型TPE总契约.md) 起的契约写。

本文分 2 份：[TPE配置-定位与输入输出.md](TPE配置-定位与输入输出.md)、[TPE配置-提示词工具集与文件.md](TPE配置-提示词工具集与文件.md)。

TPE（Task Point Engine）是任务执行模板，定义了一种任务类型的完整执行规范。SA 根据 TPE 的名称和描述判断当前用户请求匹配哪种任务类型，通过 skill 工具查询该 TPE 的输入要求后，将任务派发给 TA。TA 启动时加载 TPE 的系统提示词、输出要求和工具集，按模板定义执行任务并返回结果。

### 为什么需要 TPE

理解 TPE 存在的原因，需要从 SA 的运行模式出发：

- SA 只有**一套系统提示词 + Skill 文本**（始终在上下文），所有任务类型的业务路线逻辑都要塞进同一个上下文
- SA 承载**用户对话的完整上下文**，既要做意图路由，又要做任务执行

当业务场景的任务类型越来越多、每种任务的执行方法论差异越来越大时，SA 的上下文会被各种不相关的指令淹没——角色冲突，上下文噪音大，执行质量下降。

**TPE 解决的就是这个问题：**

- TPE 给 TA 注入**独立的系统提示词**——专注于一种任务类型的执行方法论
- TPE 给 TA 配**专属的工具集**——只挂载该任务类型需要的工具
- TA 有**独立的上下文窗口**——不被用户对话历史和其他任务类型的指令污染
- SA 只需要知道每个 TPE 的名称、描述和输入要求，保持轻量的路由角色

### 什么时候需要创建 TPE

在设计场景包之前，先梳理该业务场景需要支撑哪些任务类型。对每种任务类型，判断核心问题：**这个任务类型的执行方法论，是否复杂到已经超出了 SA 在共享上下文中能有效处理的范围？**

| 判断维度 | 不需要 TPE → SA 直接执行 | 需要 TPE → 派发给 TA |
| --- | --- | --- |
| 执行方法论 | 场景 Skill 文件写几十行 SOP，SA 照做就行 | 需要独立的角色定义和专属执行流程 |
| 工具使用策略 | SA 现有工具集的通用策略就够 | 需要不同的工具组合和使用策略 |
| 上下文影响 | 执行指令量小，不影响 SA 处理其他任务 | 塞进 SA 只会让上下文更乱更低效 |

### TPE 与 FA 的区别

TPE 和 FA 都提供上下文隔离和专属执行逻辑，但层级不同：

| | TPE | FA |
| --- | --- | --- |
| 定位 | 任务类型模板，SA 通过它派发任务给 TA | 子任务执行单元，SA/TA 将它当工具调用 |
| 执行者 | TA（独立的 Task Agent） | FA 自身（作为工具被调用） |
| 调用方式 | SA 派发任务，TA 独立执行 | SA/TA 像调用工具一样传参调用 |
| 工具集 | TA 拥有自己的工具集（统一挂载） | FA 直接配置工具，不经过工具集 |
| 典型场景 | 深度研究、代码实现、图片编辑等完整任务 | 合同条款审核、数据报表生成等子任务 |

## 名称

TPE 的名称。SA 在系统提示词中看到所有 TPE 的名称列表，用于识别任务类型。

### 配置范式

> 体现任务类型，让 SA 一看就知道这个 TPE 处理什么类型的任务。如 `deep_research`、`code_implementation_execution`、`image_editing`。

**合格示例**：
```
deep_research
code_implementation_execution
image_editing
tool_error_analysis
```

**不合格示例**：
```
任务1              ← 没有业务含义
my_tpe             ← 看不出任务类型
处理器              ← 太泛化
```

### 诊断要点

- SA 能否仅凭名称判断这个 TPE 处理什么任务类型
- 名称是否与其他 TPE 有明显区分

---

## 描述

TPE 的功能说明。SA 结合描述判断当前用户请求是否匹配该任务类型。

### 配置范式

> 说清楚这个任务类型做什么。如"接收搜索需求，执行深度研究任务，返回结构化研究报告"。

描述应该让 SA 能准确判断用户请求是否属于该任务类型，避免与其他 TPE 的职责范围重叠。

**合格示例**：
```
接收搜索需求，执行多轮深度研究任务，交叉验证信息源后返回结构化研究报告
```

```
接收代码实现需求，在沙箱环境中编写、调试和执行代码，返回可运行的代码和执行结果
```

**不合格示例**：
```
处理各种任务         ← SA 无法判断何时匹配
帮忙做事情          ← 没有信息量
```

### 诊断要点

- 描述是否说清了任务类型的输入和输出
- SA 能否仅凭描述判断某个用户请求是否属于该任务类型
- 描述与其他 TPE 的职责是否有明显的边界区分

## 输入要求

定义 SA 派发任务时需要提供什么信息。SA 通过 skill 工具按需查询该字段。

### 配置范式

输入要求是一个模板，告诉 SA 在派发任务时应该构造什么样的输入。可以包含：
- 必填字段和可选字段
- 字段的格式说明
- 占位符（如 `{date}`、`{query}`）

**示例**（深度研究 TPE）：

```
# Search Plan Template

## Task Instruction (Required)
Please conduct in-depth investigation on: {topic}

## Constraints (Optional)
- Time range: {time_range}
- Source preference: {sources}
```

**示例**（工具错误分析 TPE）：

```
# 请分析以下Agent工具错误消息，生成详细的错误分析报告：日期 {date}
```

输入要求越清晰，SA 构造的输入质量越高，TA 执行的效果越好。

**不合格示例**：

```
请输入任务信息
```

问题：太模糊，SA 不知道需要收集什么信息，只能猜测性地构造输入。

### 诊断要点

- 输入要求是否清晰定义了 SA 需要收集的字段
- 必填和可选字段是否区分明确
- SA 能否根据输入要求模板判断还需要向用户收集哪些信息

## 输出要求

定义 TA 执行完任务后应该返回什么格式的结果。SA 通过 skill 工具按需查询；TA 执行时可见，决定输出格式。

### 配置范式

输出要求可以是：
- **JSON Schema**：结构化输出，适合需要被程序解析或传递给下游的场景
- **Markdown**：自由格式输出，适合报告类、分析类任务
- **自然语言描述**：简单说明输出应包含的内容

**示例**（JSON Schema 格式）：

```json
{
  "title": "DRS Execution Result",
  "type": "object",
  "properties": {
    "summary": { "type": "string", "description": "研究结论摘要" },
    "findings": { "type": "array", "description": "详细发现列表" },
    "sources": { "type": "array", "description": "引用来源" }
  }
}
```

**示例**（简单格式）：

```
markdown
```

### 诊断要点

- 输出要求的格式是否与下游使用场景匹配（需要程序解析用 JSON，展示给用户用 Markdown）
- SA 能否根据输出要求预期 TA 返回的结果结构
- TA 能否根据输出要求明确自己的返回格式
