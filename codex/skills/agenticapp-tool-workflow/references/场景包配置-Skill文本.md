# 场景包配置详解（二）：Skill 文本

写或诊断场景包 Skill 文本（`apc_skill`）时读。

本文分 4 份：[场景包配置-名称描述工具集.md](场景包配置-名称描述工具集.md)、[场景包配置-Skill文本.md](场景包配置-Skill文本.md)、[场景包配置-场景文件.md](场景包配置-场景文件.md)、[场景包配置-知识文件与分工.md](场景包配置-知识文件与分工.md)。

## Skill 文本

文本输入框，内容在项目启动时注入 SA 上下文，作为 SA 的全局知识。

### 配置范式

**核心原则**：Skill 文本始终在 SA 上下文中，必须短而精。只放 SA 必须立即知道的信息，长内容放 Skill 文件。

**按需组合以下板块**：

| 板块 | 何时需要 | 说明 |
| --- | --- | --- |
| **全局约束** | 有跨场景通用的硬性规则时 | 3-8 条，所有场景都适用的规则 |
| **业务路线说明** | 场景包有业务路线时 | 列出路线标识（`orchestration_id`）+ 一句话说明 + 触发条件 + 发起前要收齐的信息 |
| **业务里程碑** | 场景包有业务路线时 | 列出业务阶段和各阶段目标，以及哪些判断留给 Agent 或使用者；不复制路线的节点图 |
| **TPE 路由表** | 有不在路线里、由 SA 派发的 TPE 时 | 列出 TPE 名称 + 一句话说明 + 触发条件 |
| **场景索引表** | 上传了 SA 直接处理的场景 Skill 文件时 | 列出文件名 + 一句话说明 + 触发条件 |
| **文件指南** | 上传了知识 Skill 文件时 | 列出文件名 + 内容 + 阅读时机 |

**简单场景包**：如果场景少、流程简单，不需要拆出单独的场景 Skill 文件——直接在 Skill 文本中写场景的执行流程即可，此时不需要场景索引表板块。

**有业务路线的场景包**：SA 选一条路线、收齐入口信息后发起路线，路线再调度里面的 TPE。路线里的 TPE 不写进 TPE 路由表，也不写「派发任务点」，SA 只用路线启动工具发起。单独派发时运行不报错，但路线 Runtime 不参与，业务事件被抑制，页面收不到进度，中途表单、交付和审阅都不生效。节点图已在 `workflow_orchestration` 里，这里不复制。

**有普通任务点的场景包**：TPE 处理的任务类型不需要场景 Skill 文件（SOP 在 TPE 系统提示词中）。SA 通过 TPE 路由表判断是否匹配某个 TPE，匹配则查询输入要求、收集信息、派发给 TA。

```markdown
## 全局约束
- {约束规则}
- ...

## 业务路线（如有路线）
以下事情走业务路线，收齐信息后发起对应路线，不单独派发路线里的任务：
- {orchestration_id}：{一句话说明}，触发条件：{什么请求匹配}，发起前收齐：{入口信息}
- ...（新增路线追加一行）

## TPE 路由表（如有不在路线里的 TPE）
以下任务类型由 TA 专项执行，匹配后通过 skill 工具查询输入要求，收集信息后派发：
- {TPE名称}：{一句话说明}，触发条件：{什么请求匹配}
- ...（新增 TPE 追加一行）

## 场景索引表（如有 SA 直接处理的场景文件）
以下 Skill 文件包含常见业务场景的标准操作流程：
- 场景_{名}.md：{一句话说明}
- ...（新增场景追加一行）

注意：如果用户意图不匹配任何 TPE 或已有场景，根据已加载工具集的能力自行组合。

## 文件指南
- 知识_{主题}.md：{内容}，{阅读时机}
- ...
```

### 合格示例

**示例 1：IT 运维监控场景包**（有场景 Skill 文件，无 TPE）

```markdown
## 全局约束
- 涉及生产环境的变更操作需先确认审批状态
- 告警处理优先级：P0（立即）> P1（30分钟内）> P2（4小时内）
- 执行重启、扩容等操作前需记录变更日志
- 敏感配置（密码、密钥）展示时脱敏

## 场景索引表
以下 Skill 文件包含常见业务场景的标准操作流程：
- 场景_故障排查.md：从告警到根因定位到修复的完整排查流程
- 场景_服务扩容.md：评估负载 → 确认资源 → 执行扩容的标准流程
- 场景_版本发布.md：从预检到发布到验证的完整发布流程
注意：如果用户意图不匹配任何已有场景，根据已加载工具集的能力自行组合。

## 文件指南
- 知识_告警等级定义.md：各等级告警的判定标准和响应时限，处理告警时参考
- 知识_架构拓扑.md：核心服务的依赖关系和部署架构，故障排查时查阅
```

**示例 2：数据分析场景包**（普通任务点 + 场景 Skill 文件混合模式，没有业务路线）

```markdown
## 全局约束
- 查询生产数据库时仅使用只读账号
- 单次查询结果超过 10000 行时必须分页处理
- 涉及用户隐私数据的报表需标注"内部使用，禁止外传"
- 金额字段统一为元（非分），保留两位小数

## TPE 路由表
以下任务类型由 TA 专项执行，匹配后通过 skill 工具查询输入要求，收集信息后派发：
- deep_research：深度数据研究，触发条件：用户需要多维度深入分析某个业务问题
- code_execution：数据处理代码执行，触发条件：用户需要编写和运行数据处理脚本

## 场景索引表
以下 Skill 文件包含常见业务场景的标准操作流程：
- 场景_月度经营报表.md：从数据提取到报表生成的完整流程
- 场景_异常数据排查.md：数据异常的定位和根因分析流程
注意：如果用户意图不匹配任何 TPE 或已有场景，根据已加载工具集的能力自行组合。

## 文件指南
- 知识_指标定义.md：公司核心指标的计算公式和口径说明，计算指标时参考
- 知识_数据源说明.md：各数据源的表结构和字段含义，编写查询时参考
```

**示例 3：简单场景包**（无场景 Skill 文件，SOP 直接写在 Skill 文本）

```markdown
## 全局约束
- 金额字段统一为元，保留两位小数
- 涉及付款操作需先向用户确认

## 操作流程

### 查询订单状态
1. 调用 `query_order` 获取订单信息
2. 如有物流单号，调用 `track_shipment` 获取物流状态
3. 汇总后向用户展示

### 处理退款
1. 调用 `query_order` 确认订单状态为已签收
2. 调用 `create_refund`，金额不超过订单实付金额
3. 调用 `notify_customer` 通知客户退款进度
```

**示例 4：主题简报场景包**（有业务路线）

```markdown
## 全局约束
- 每条要点都带来源，没有来源的内容不写进简报

## 业务路线
以下事情走业务路线，收齐信息后发起对应路线，不单独派发路线里的任务：
- topic_keypoints_brief：整理一个主题的要点简报，触发条件：使用者想了解某个主题或要一份带出处的要点，发起前收齐：主题（太宽时先请使用者收窄）
```

### 不合格示例与问题

| 问题 | 示例 | 诊断信号 |
| --- | --- | --- |
| 约束过多 | 列了 20 条约束 | 应拆分：通用约束留此处，场景特定约束放场景文件 |
| 有路线却写派发 | 写「匹配后派发给任务点 xxx」，或把路线里的 TPE 列进 TPE 路由表 | 改成发起路线；照写时 SA 可能单独派发 TPE，运行不报错，但页面收不到进度，交付和审阅都不生效 |
| 索引表与文件不对应 | 索引表列了 5 个文件但实际只上传了 3 个 | SA 读取不存在的文件会失败 |
| 写了单工具说明 | "`query_db` 用于查询数据库" | 这是 MCP 层的信息，不应出现在 Skill 文本 |

### 诊断要点

- 全局约束是否只包含所有场景都适用的规则
- 业务路线说明是否覆盖所有路线，且写的是发起路线（如有路线）
- TPE 路由表是否覆盖所有不在路线里的 TPE，且没有列路线里的 TPE
- 场景索引表是否覆盖所有已上传的场景 Skill 文件（如有文件）
- 文件指南是否覆盖所有已上传的知识 Skill 文件（如有文件）。注意：SA 系统提示词（通过 sa_prompt_gid 配置的提示词模板）中可能已包含 Skill 文件的读取时机指引，此时 Skill 文本无需重复，否则违反信息分层原则（同一信息出现在两个地方）
- 是否包含了不属于此层级的信息（如单个工具的描述）
- 有 TPE 时，是否为 TPE 处理的任务类型写了多余的场景文件（不应有）
