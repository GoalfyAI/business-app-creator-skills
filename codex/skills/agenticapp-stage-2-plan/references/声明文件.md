# 声明文件

写声明文件、跑检查、出确认单和走查项时读。声明文件把这个应用「谁能做什么、数据怎么分、每件事做到什么算完成」写成一份结构化的文件：开发者照它生成的确认单确认，③ 照它做，④ 照它生成的走查项逐项走。

## 是什么、放在哪

- 文件名 `declaration.json`，放在应用工程根目录，与 `workspace.json` 同级。
- 键用英文，值里的名称与说明用中文业务话：开发者看的确认单直接取这些值。
- 全部槽位必填。不适用的由你写明取值和原因，脚本不给默认值，空着就是没写。
- 「TaskFlow」指使用者或自动任务发起的一件业务事。它在现有体系上落成一条路线还是一个应用后端接口，写在施工单里，不进声明文件。
- 声明文件只写业务上的事实。资产 ID、模型名、路线编号、表结构细节、接口地址不进声明文件。

## 每个槽位怎么填

**应用**（`app`）：背景五项加名称，每项一两句，来自 PRD，不另起说法。

| 键 | 写什么 |
|---|---|
| `name` | 应用的中文名称 |
| `problem` | 要解决的问题：现在哪里不顺、谁吃亏 |
| `users` | 使用对象：谁会打开这个应用 |
| `doneWell` | 做好的标准：使用者看得到的变化 |
| `scope` | 这次做哪些、不做哪些 |
| `tradeoffs` | 关键取舍：② 问过的取舍和开发者选的 |

**角色**（`roles`，至少一个）：`key`、`name`（中文名称）、`permissions`（权限点，写成「资源.动作」，如 `lead.read`）。平台上每个使用者用自己的一份时，也至少写一个角色，代表这个使用者。

**资源控制点**（`resourceControls`）：数据按什么分开管，如区域、门店、账号。每项 `key`、`name`、`description`（取值举例，谁只能碰哪一份）。这个应用不分的，整项写 `{"none": "为什么不分"}`。

**数据表**（`tables`）：`key`、`name`、`description`、`partition`。按资源控制点划分的写 `{"by": "<资源控制点 key>", "column": "<列>"}`；不划分的写 `{"none": "为什么不划分"}`。

**TaskFlow**（`taskflows`）：

| 键 | 写什么 |
|---|---|
| `key`、`name`、`summary` | 标识、中文名称、功能说明（一句话，使用者的话） |
| `input`、`output` | 一句话，或字段清单（数组） |
| `effect` | `read`（只读数据）或 `write`（会改数据、或对外发送、下单、写入） |
| `permission` | 一个权限点，必须出现在至少一个角色里 |
| `scope` | `{"<资源控制点 key>": "<输入里的字段>"}`：按哪个资源控制点限制、取值从输入的哪个字段来；不限制的写 `{"none": "为什么不限制"}` |
| `doneWhen` | 一句能判断的完成标准：做完后看得到什么、库里多了或改了什么；或固定取值「返回数据即完成」 |
| `uses` | 四个数组都要出现：`tools`（外部工具的中文名称）、`agents`（交给模型判断的步骤的中文名称）、`reads`、`writes`（表 key）。没有就写空数组 `[]`，空数组就是你写明了「没有」 |

**自动任务**（`automations`）：`key`、`name`、`schedule`（触发周期，业务话，如「每个工作日早上 8:30」）、`call`（指向的 TaskFlow key）、`notifyOnIncomplete`（没做完时通知谁）。没有的整项写 `{"none": "为什么没有"}`。

**页面**（`pages`）：`key`、`name`、`summary`、`calls`（这一页发起的 TaskFlow key，至少一个）。

## 固定取值「返回数据即完成」

只给只读、不用工具、不用模型、不写表的 TaskFlow 用：`effect` 为 `read`，`uses.tools`、`uses.agents`、`uses.writes` 都是空数组。其余的都写一句能判断的完成标准。自动任务指向用固定取值的 TaskFlow 时，检查会提醒：自动跑完没人看，想清楚只取数据够不够。

## 一个完整的小例子

线索管理：两个角色、按「区域」分、两张表、四个 TaskFlow、一个自动任务、两个页面（节选掉的两个 TaskFlow 写法相同）。

```json
{
  "version": 1,
  "app": {
    "name": "线索跟进助手",
    "problem": "销售线索散在表格和聊天里，主管不知道哪些线索没人跟、跟到哪一步",
    "users": "销售团队：一线销售和区域销售主管",
    "doneWell": "每条线索都有负责人；销售每天打开就知道先跟哪几条；主管每天早上收到本区域的跟进情况",
    "scope": "做线索查看、分配、记录跟进和每日早报；这次不做线索导入和成交后的合同管理",
    "tradeoffs": "跟进要点由模型从销售的口述里整理，销售可以改；早报只发给主管"
  },
  "roles": [
    { "key": "sales", "name": "销售", "permissions": ["lead.read", "followup.write"] },
    { "key": "manager", "name": "销售主管", "permissions": ["lead.read", "lead.assign", "followup.write", "report.read"] }
  ],
  "resourceControls": [
    { "key": "region", "name": "区域", "description": "线索所属的销售区域，例如华东、华南；每人只能处理自己被授权的区域" }
  ],
  "tables": [
    { "key": "leads", "name": "线索", "description": "每条线索一行：客户、联系人、负责人、阶段", "partition": { "by": "region", "column": "region" } },
    { "key": "followups", "name": "跟进记录", "description": "每次跟进一行：哪条线索、谁跟的、聊了什么、下一步", "partition": { "by": "region", "column": "region" } }
  ],
  "taskflows": [
    { "key": "listLeads", "name": "查看线索", "summary": "按区域和阶段列出线索，逾期没跟的排在前面",
      "input": ["region", "stage"], "output": "线索列表", "effect": "read", "permission": "lead.read",
      "scope": { "region": "region" }, "doneWhen": "返回数据即完成",
      "uses": { "tools": [], "agents": [], "reads": ["leads"], "writes": [] } },
    { "key": "dailyDigest", "name": "发每日跟进早报", "summary": "汇总一个区域昨天的跟进和逾期线索，发给这个区域的主管",
      "input": ["region"], "output": "一份早报", "effect": "write", "permission": "report.read",
      "scope": { "region": "region" }, "doneWhen": "主管在钉钉收到早报，列出昨天跟进了几条、哪些线索逾期没跟",
      "uses": { "tools": ["钉钉工作通知"], "agents": [], "reads": ["leads", "followups"], "writes": [] } }
  ],
  "automations": [
    { "key": "morningDigest", "name": "每日早报", "schedule": "每个工作日早上 8:30", "call": "dailyDigest", "notifyOnIncomplete": "该区域的销售主管" }
  ],
  "pages": [
    { "key": "leadPage", "name": "线索列表", "summary": "看本区域的线索，主管在这里分配", "calls": ["listLeads", "assignLead"] },
    { "key": "followupPage", "name": "跟进", "summary": "选一条线索，记下这次跟进", "calls": ["listLeads", "logFollowup"] }
  ]
}
```

另两个：「分配线索」（`assignLead`，write，`lead.assign`，写 `leads`，完成标准「线索的负责人改成选定的销售，并出现在这个销售的待跟进列表里」）；「记录跟进」（`logFollowup`，write，`followup.write`，`agents` 为「跟进要点整理」，写 `followups` 和 `leads`）。

## 脚本四个命令

脚本在本 Skill 的 `scripts/` 下，只读声明文件，不看应用代码，不连平台：

```bash
node <本 Skill 目录>/scripts/declaration.mjs init <应用根>/declaration.json
node <本 Skill 目录>/scripts/declaration.mjs check <应用根>/declaration.json [--json]
node <本 Skill 目录>/scripts/declaration.mjs confirm <应用根>/declaration.json > <应用根>/确认单.md
node <本 Skill 目录>/scripts/declaration.mjs walkthrough <应用根>/declaration.json [--json]
```

| 命令 | 做什么 | 做成 |
|---|---|---|
| `init` | 生成空模板，每类实体一条空示例项；文件已存在就拒绝，不覆盖 | 模板生成后逐项改成真实内容，空示例项不用的删掉或改成 `none` |
| `check` | 一次列全「必须改」与「请留意」，每条写清哪类、哪一个、哪里不对、怎么改 | 退出码 0，没有「必须改」 |
| `confirm` | 输出给开发者看的确认单；有「必须改」时拒绝生成 | 原样随整版方案发出，不手改 |
| `walkthrough` | 输出走查项清单：功能、工具、权限、自动任务四类，每项有编号、做法、预期，末尾是各类项数 | 每一项进验收条目，不删不并 |

「必须改」是缺项或为空、取值不对、标识重复、引用对不上、固定取值用错。「请留意」不拦，但会写进确认单给开发者看：没有入口的 TaskFlow、没人读写的表、没有表用的资源控制点、没人用的权限点、读写了按资源控制点划分的表自己却不按它限制、自动任务指向用固定取值的 TaskFlow。「请留意」的项能改就改掉；确实就是这样的，留着让开发者在确认单上看到。

## 常见的错

| 错法 | 为什么错 | 改成 |
|---|---|---|
| 填套话：完成标准写「功能正常」「处理成功」「用户满意」 | 走查时没法判断，等于没写 | 写做完后看得到的东西：多了哪一行、改了哪一列、谁收到了什么 |
| 为过检查多声明：补一个没人用的权限点、一张没人读写的表、一个不分数据的资源控制点 | 确认单上多出开发者没要的东西，走查项跟着多出走不了的 | 只写 PRD 里有的；检查报「没有定义」时，先想是不是引用写错了 |
| 「请留意」为了清零就删掉要的东西 | 「请留意」不拦，删掉的才真的丢了 | 确实就是这样的，留着让开发者确认 |
| 把实现细节写进声明：路线编号、资产 ID、模型名、接口路径、表结构 | 声明是给开发者确认的业务事实，实现会变，写进来就要反复改 | 写进施工单 |
| 工具和 Agent 写成英文标识 | 确认单原样取这些名字，开发者看不懂 | 写中文名称，对应哪个平台工具写进施工单 |
| `uses` 里不确定就写空数组 | 空数组表示你写明了「没有」，走查会少列工具项 | 先问清；问不清的并入按轮问 |
