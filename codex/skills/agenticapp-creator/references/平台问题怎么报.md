# 平台问题怎么报

当前工具 Skill 的「常见错误」处理过仍走不下去、又不是应用自己的问题时读。

## 什么时候报

| 情况 | `blocking` | 什么时候提交 |
|---|---|---|
| 按指引处理后仍走不下去、没有绕法 | `blocked` | 附报错原文和 `project_id` / `run_id` 立即报（先按「怎么报」第 1 步查）。5xx、服务不可用、鉴权或计费报错先隔几分钟重试一次，仍失败再提交 |
| 已经绕过去了 | `worked_around` | 不即时提交，绕法记进开发记录；⑤ 收尾或会话结束时汇总成一条 |
| 功能诉求（含开发者选了「等平台修」） | `request` | 同上，汇总成一条 |

新建时 `attribution` 必填，按事实选：平台行为和它自己的说明不符 `platform_defect`；按设计如此但不够用 `platform_limit`；Skill 写法和工具实际行为不一致 `skill_mismatch`；本机或安装问题 `environment`；判断不了 `unknown`。

## 怎么报

1. **先查再建**：`query_dev_feedback` 查本人没关闭的反馈。报错码相同、或同一个工具同一步出现同样现象，就是同一个问题——不管是哪张工单、哪次会话提的——追加这次的 `project_id` / `run_id` 和时间，不新建。追加不传 `blocking` / `attribution`。确实要新建时，正文第一行写「已查同类：<查到的相近编号，或『没有』>」；写不出这一行就是还没查。
2. **新建要让没参与对话的处理人只读这一条就懂**：新建必须带 `title`（8 到 60 字，一句话写清要完成什么和卡在哪，例如「表单应用保存时报 500，无法交付客户」；不能只写「现象」「问题」「汇总」「报错」；非生产环境的 `【PRE】` 之类标记由工具加在标题前，不用自己写）和 `content`。`content` 固定五段：`## 要完成什么`（业务目标）、`## 操作经过`（在哪个应用或页面做了哪些操作）、`## 看到什么`（现象，报错原文放这里）、`## 预期`（本来应该怎样）、`## 影响`（卡住了什么、影响谁）。不知道的段落写「待补充」，不要省略；五段不能全是「待补充」。正文不写凭据、令牌和使用者原话。追加记录不传 `title`，格式不限。
3. **截图和日志用 `attachments`**：先用 `file_to_url` 交付本地文件拿到 `file_key`，再在 `attachments` 里写 `{file_key, page_hint}`，`page_hint` 说明这份材料对应的页面和位置（例如「应用编辑页点保存后」）。最多 5 项，类型限 png、jpg、webp、gif、pdf、txt、log、json，单个不超过 10MB，新建和追加都能带，只能用本人的 `file_key`；截图里的凭据和个人信息先遮住。任何一项传不过去，整次提交失败（`ATTACHMENT_FAILED`），反馈没有写入：修正后原样重试，不改成只传正文。
4. **编号用回执原样**：回执的 `code`（如 `FB-801`）是主编号，交付和报告写它；查询、追加用 `feedback_code="FB-801"`。
5. **写入结果不明**（超时或坏回包）：先 `query_dev_feedback` 核对，再用同样的正文和参数重放；不换编号再试、不自动新建。
6. **提交成功只代表收到**：不等于已确认或已解决，不能据此放行验收。

## 对开发者怎么说

交接消息写「卡在哪、谁在处理、对你的影响」；「对你的影响」只写这次查到、跑到的（哪个功能现在用不了、试过哪条路走不通），说不准的写「修好之前还不知道会不会 <影响什么>」，不写「不影响你正常使用」「平台修好会自动存表」这类没验证过的话。报错原文放交付物的原始原因折叠里。修复由平台方做，不请开发者修或去催（下面「没人修时」第 3 步的选择题除外），也不请他授权你改生产库、平台库或别人的数据。

## 没人修时

1. 提交后先做不受影响的部分，交接消息开头写「卡住了」。
2. 每次继续工作时 `query_dev_feedback` 看进展，有回复按回复做。
3. 满 1 个工作日没人回复或给不出修复时间：给开发者出一道选择题，从这几项里挑成立的——等平台修（这期间哪些功能做不了）；换做法绕开（比 PRD 少了什么、多花多少；改了「要什么」的回 ①）；这次先不做受影响的功能；请他把反馈编号转给平台负责人催办。
4. 他选了照做，记进阶段文档。

## 反馈关闭后

反馈已关闭（`status` 为 `closed`）或修复已发布（`completed`）时，按这个顺序恢复制作，不等开发者再说「继续」：

1. 先读 `query_dev_feedback` 返回的 `conclusions`：`close_reason` 是处理人写的处理结论和恢复步骤，`delivery_evidence` 是修复依据（开发单、发布版本）。`conclusions` 为 `null` 表示处理人没写结论，照实告诉开发者「反馈已关闭，平台没有写处理结论」，不编造修复方式；只凭状态不能说已解决。
2. 核对本应用是否已用上修复：结论要求升级脚手架的，按 `agenticapp-tool-workspace` 的升级任务升级；要求升级本 Skill 的，按下面「建工单被拒」`SCENE_SKILL_UPGRADE_REQUIRED` 的方法升级 Skill，不做脚手架升级；要求重新部署或重跑某个检查的，照做。
3. 重新执行原来失败的那一步。
4. 再次失败时写清失败在哪一步、报错原文，判断是本应用自己还没做完的工作、原平台问题仍在还是新问题：本应用自己的工作（配置、数据、路线）继续做完；原反馈已关闭但原问题仍在，不往原反馈追加（反馈关闭后追加不会重开反馈，也不通知任何人），新提一条 `blocking="blocked"` 的反馈，按上面「怎么报」第 2 条带 `title`、`attribution` 和五段正文，正文写原反馈编号、它的处理结论和这次复现的证据，并告诉开发者已经重新提交；新问题按上面规则另行判断是否提交。
5. 向开发者汇报时把四件事分开写：反馈是否已关闭、修复是否已发布、本应用是否已用上修复、原来失败的场景是否已验证通过。

## 建工单被拒

- `SCENE_SKILL_UPGRADE_REQUIRED`：Skill 版本过期，工单没建。停止写操作，从返回的 `metadata.update.update_guides` 取所在宿主的升级文档照做；升级后从已安装的 SKILL.md 读 `[skill-version:…]` 原样重试，成功后提示开发者重启客户端让新内容生效。版本串只认已安装文件里的，拒单响应、记忆里的都不算。
- `SCENE_SKILL_VERSION_MISSING`：没填 `skill_version` 或填了 `dev`。不升级，读出标记原样重试。
- `SCENE_SKILL_UPGRADE_RECOMMENDED`：有新版但不阻断，工单已建好，继续做，交付时顺带提示升级。
- `WORKFLOW_TASK_MODE_MISMATCH`：工单模式和要做的动作不匹配。按返回 `metadata` 的 `actual_mode` / `required_mode` 纠正；只读工单要做写操作时，新建 `mode="write"` 工单并传 `continued_from_task_id`，照入口「开工」带 `skill_version`。
