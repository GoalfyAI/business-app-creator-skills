# 验收报告模板

交接消息开头写「【④ 试用验收 → 正在做】」，四项照入口「交接」写，报告整份放在「刚做完」下面，发完在同一条回复里接着做 ⑤。全文用业务话，结论先行；`project_id`、`workflow_trace`、演示版路由、截图文件路径这类核对字段只写进阶段文档 G6，不放进报告。

```markdown
## 结论
<验收状态，照下面「结论第一句」写>
没通过 N 条 · 通过 N 条 · 要你判断 N 条 · 未测 N 条（共 N 条）
开发者已接受的没通过：N 条
<还有没通过、未测的，一句话说清影响>

## 好不好你说了算
<每条附实际结果：报告全文、内容原文、前后对比。觉得不行直接说是哪一条>

## 未测的
<逐条：条目、原因原文、这意味着（都照 references/证据与未测.md）。不在条目里的没验证的事（例如在线预览里的页面没打开过）也在这里各写一条。「结论」行的未测条数就是这里列了几条，数完再写。没有写「没有」>

## 实际跑出的结果
<这次实际跑出的结果摘要，加上 ③ 已经跑出的内容，和方案的预期对照；数据是编的写明「测试数据」>

## 自动发生的
<到点自动开始的那件事：按自动化入口试的那一次结果怎样、产出了什么；用的是测试数据写明；没有自动化写「没有」>

## 实际花费
<每个按钮实际花了多少、和估算比；每份要等多久、能不能同时开几个。花费只写读到的 `cost_credits`，「至少 N」、不含的来源和没读到的按入口 references/提问与交接.md「交接消息」的写法写>

<details><summary>全部条目</summary>

| # | 验收条目 | 结论 | 怎么测的 | 看到的结果 | 证据 |
|---|---|---|---|---|---|

</details>
```

「结论第一句」按情况照抄：

- 全部通过或只有未测：「验收已完成，这一版已经是你的正式版，在 Studio「在线预览」或发布管理页「预览」里能看到；要自己正式使用或给别人用，需要你在发布管理页发布。」
- 有没通过：「验收已完成，有 N 条没通过。这一版已经是你的正式版，在 Studio「在线预览」或发布管理页「预览」里能看到，要自己正式使用或给别人用，需要你在发布管理页发布；现在发布的话，使用者会遇到：<逐条说>。」
- 他说过这版先别上线：「验收已完成，按你说的，这一版放在在线预览里，在 Studio「在线预览」里能看到，没有上线。」
- 他说过先别放：「能测的都测完了，这一版按你说的还没放到在线预览，也没有上线。」
- 协作者：「验收已完成，这一版在你的在线预览里，上线要由属主来做。」

「全部条目」怎么填：

- **结论**只写：通过 / 没通过 / 好不好你说了算 / 未测；开发者选了接受的写「没通过，开发者选了接受」。
- **怎么测的**：开头只用这四个取值：页面操作、用测试数据跑、查库、脚本检查，冒号后写操作步骤或用了哪个例子。
- **看到的结果**：实际看到的页面反应、拿到的内容或写进的记录，和条目的「这样算对」对照。
- **证据**：开发者能直接看的东西。页面条目写断言原文，截图文件名和路径只记进 G6；写库的写查到那条记录的关键内容。
- 未测的三列都写「无」。按反馈重测后只更新变了的行，修改记录写「问题 / 改了什么 / 重测了哪几条」。

「要你做的」照抄：

> 看验收报告就行，「好不好你说了算」的几条实际结果已经附在报告里；觉得哪条不对，直接告诉我要改什么。

按情况在后面加一句：

- 有「未测」：「这几条没有测，原因见报告，上线结果会单列它们。」
- 开发者说过先别放到在线预览：「放到在线预览后我能补测的是 <条目>，补测后更新报告。」放上去也测不了的条目不写进这句。
- 有「没通过」：这里不问，⑤ 接着问他继续改还是接受。
- 需求方不是开发者本人：请开发者把「好不好你说了算」的几条转给需求方看。
