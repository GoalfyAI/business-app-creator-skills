# T-3407 内部接入与能力核查说明

本文件仅供内部开发与发布评审，不属于插件分发目录。推广账户业务模板的分发范围保持原约定；通用授权与支付接入契约见 skills/business-app-creator/modules/P5 第 11 节及 P7。

## 已实现的范围

T-3407 已实现应用隔离授权、冻结发布许可、广告账户实时核验、Ads 订单及幂等、宿主收银台、Pay 微信/支付宝收款、支付事实核对和运营到账确认。不得继续使用早期“只支持授权配置与充值能力查询”“充值明确未开通”的阶段结论判断当前环境。

代码已实现、环境能力已配置、真实链路已验收是三种状态。流水线部署成功不等于真实支付验收成功；尚未验收也不等于支付代码不存在。

## 制作时如何判定

1. 使用目标环境 MCP 的实时 schema。若缺少授权候选、保存选择或 get_recharge_config，先核对服务版本并刷新连接/工具清单；仍缺少时记录接口缺口，不将其解释为 Pay 不支持支付。
2. get_recharge_config 需要实际业务应用 ID。应用尚未创建时标记“待应用创建后核查”，不得伪造 ID，也不得直接推断 enabled=false。已有应用时记录环境、应用 ID、时间与真实返回；失败记录具体错误，不自行打开开关或绕过限制。
3. 返回 enabled=true 后按 SDK 与专属后端契约接入支付，正式可用还需验证实时账户、签名链路、渠道及回调。关闭或报错时不能宣称当前可付款，但可继续不依赖该能力的工作，不必将整个应用缩减为状态展示。
4. 支付通过业务应用后端、Ads、宿主收银台及 Pay 完成，不要求场景包存在一个“广告充值 MCP 工具”。没有建投/调投工具只证明相关投放能力缺失，不能据此判定平台支付不可用。
5. 当前未实现自动向广告平台划款；payment_status=paid 表示平台已收款，fulfillment_status=completed 表示运营确认广告账户到账。不得将前者冒充后者，不得把人工到账说明为自动充值。

修改已确认的自动建投、调投、自动到账等业务范围仍需用户决定；用户已明确选择的广告平台无需重复询问。禁止模拟付款成功、自造支付链接或未授权发起真实资金操作。

本文件与 Skill 修改需同步相关平台副本。代码推送、插件安装更新与 QA 部署分别核验，不能只更新文件就声称当前制作会话已加载新指引。

## 本轮 Review / MR 合入说明

本 MR 仅合入 `skills/business-app-creator/` 源目录的功能修改及本内部说明。`skill-release.json`、插件版本/市场清单、各平台副本和 zip 全部保持 main 的 v20260920-3c8136 / 2.0.7，不携带旧 T-3407 QA 发布产物。合入后在 main 按既有正式发布流程重新 release 并登记，源目录修复不等于当前安装插件已经生效；提交本 MR 时请把本段放入 MR 说明。

授权选择 CAS 冲突契约：Hub 返回 HTTP 409 / BUSINESS_UI_AUTHORIZATION_CHANGED，MCP 返回业务错误 error_code=2 并引导重新读取草稿与候选、确认后保存，不重试旧选择。Hub 的数据库行锁 CAS 冲突使用同一稳定码。冻结草稿返回 BUSINESS_UI_VERSION_FROZEN 并指引 ensure_draft。

摘要规则：authorization_candidates_revision / config_revision 必须为 64 位小写 hex；expected_authorization_policy_digest 允许空串（尚未保存授权策略）或同格式摘要，不能接受任意非空字符串。

payment.open 的 completed 只代表收银台流程结束。付款以查单 payment_status=paid 为准，广告账户到账以 fulfillment_status=completed 为准。

发布顺序：先 Hub，再制作 MCP，最后发布并更新 Skill。无新增 SQL/Nacos 配置。
