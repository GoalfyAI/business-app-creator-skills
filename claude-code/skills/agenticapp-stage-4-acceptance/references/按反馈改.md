# 按反馈改

④ 判定没通过要改、开发者看过报告说哪条不对或一次提了几处、⑤ 里他选了继续改、或他改口要放要上线时读。已上线的版本留着，不回滚、不下线：使用者看不到它，回滚还会多出一个版本。

## 能改的没通过

开发者靠制作进度知道你在改什么，所以先改进度再改代码，他打开看到的才和实际一致。

1. **先发进度**。第一个改代码或改资产的动作之前，保存新一版制作进度，受影响的功能改回「在做」，其他功能不动，同时发一条【③ 制作 → 正在做】的进度。已交过报告的，验收报告同步更新。
2. **改**。只改页面或后端代码的，在工作区改完直接往下，不先取草稿：`ship` 会派生新草稿，早取了这段时间在线预览就没有能打开的版本。要改路线、场景包或挂载的，上线版不能直接改，按 `agenticapp-tool-deploy`「修订、回滚、作废」取新草稿。
3. **再部署、再上线**。受影响的页面条目在演示版上重测，按 `agenticapp-tool-deploy` 更新在线预览，部署成功直接上线，版本号顺延一位。
4. **重测**。重测这一条和受影响的条目，报告只更新变了的行。写「重测过」之前核对这次运行跑的确实是改过的版本，旧版本的结果不算。

同一条最多改 3 轮。3 轮仍不过，或原因你改不了（平台故障、外部数据源、要开发者授权或付费），记「没通过」，写清原因和发布后使用者会遇到什么，由 ⑤ 问他继续改还是接受。

## 他提的意见

- **他说哪条不对**：按上面四步。
- **一次提了几处**：照他的原话编号记进 G6，每处标「已改，已验证」「已改，未验证（原因）」或「没改（原因）」，交接消息逐条回，不笼统说「改好了」。改一处时，把用到同一份数据或同一个判断的其他页面和路线一起核对。
- **要改到 PRD 没写的业务条件**（多一道核对、加启用开关、额外限制）：这是要的东西变了，回 ① 确认，不在实现里自己加。
- **结果不对、要换做法，或方案取舍要变**：回 ②，只改受影响的部分，已做好的不丢。

## 他改口

- **「这版先别上线」后说可以了**：上线最新代码部署成功的那一份，部署后又改过代码的先重新部署，报告更新后回 ⑤。
- **「先别放」后说放吧**：部署到 `success`，直接上线，按 ④ 第 3–5 步补测依赖已部署版本的条目，结果更新进报告；补测没通过的按上面改，改完回 ⑤。
- **他说先别上线时这一版已经上线**：告诉他已上线、使用者看不到，从下一次改动起不上线。回滚要他另外确认。
