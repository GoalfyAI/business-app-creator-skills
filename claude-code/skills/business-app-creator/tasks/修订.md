# 修订

## 识别信号

- 开发者要改已上线应用的页面、接口、表结构、路线、提示词或能力。
- 开发者按用户反馈报告要求改应用（先按 [../reference/用户反馈.md](../reference/用户反馈.md) 校验决定）。

## 先读什么

Studio 先只读核对已有应用与授权、生成本次修订方案并取得当前版本/摘要的精确原生确认，然后才能执行下列建工单、取草稿或工程写入；小文案/样式改动也不例外。

1. 建 write 工单；定位应用工程并按 [接续.md](接续.md) 核对本地与云端。
2. 看版本：`list_asset_versions` 看场景包、应用、模板各自的现役版本和有没有搁浅草稿。
3. 取可编辑草稿：场景包 `scene_package_manage(action="ensure_draft")`，应用 `business_ui_manage(action="ensure_draft")`，其他资产 `ensure_editable_asset_draft`。对上线行直接 update 会自动派生草稿，之后一律用返回的 `draft_asset_id`。规则见 [../reference/部署与版本.md](../reference/部署与版本.md)。
4. 评估影响：共享资产用 `get_asset_usage_impact` 看谁在用；改表结构先看 [../reference/数据模板.md](../reference/数据模板.md) 的迁移规则；改 TPE 的输入输出会波及路线映射和页面。
5. 核对本次差异（改什么、影响哪些功能、费用与副作用有没有变）：普通宿主写差异版确认页并确认一次，小文案/样式改动可在对话确认；Studio 沿本节开头已确认的差异方案，只有内容变化才提交新版并取得新原生确认后继续。

Studio 中先生成本次修订方案并取得匹配其版本/摘要的原生确认，再修改工程或业务资产；该确认只授权制作，不继承历史上线同意或自动授权。新候选不得继承旧候选的检查结果；V2 制作或失败期间保留 V1 正式在线实例，按 [Studio自动交付](../reference/Studio自动交付.md) 的保存状态协议换版，需要上线时在原对话询问，只有用户明确同意本次范围才调用现有 MCP；未答复或拒绝保持旧版。

## 从哪一段进

从受影响的最早一个 flow 开始，之后只做受影响的部分，用不到的 flow 跳过：

| 改什么 | 从哪个 flow 开始 |
|---|---|
| 业务规则、功能范围、分工 | G1 |
| 换工具或 FA、接新能力 | G2 |
| 脚本、提示词、路线 | G4 |
| 表结构、页面、后端接口 | G5 |
| 只改文案或样式 | G5（本地 verify 后直接 G6） |

每次修订完成与改动相称的检查；Studio 本地制作可独立完成，不要求每次改动都上线。需要上线且用户明确同意本次范围才进入 G7；编辑、批注、检查、轮次结束或恢复都不触发自动发布。普通宿主按原流程验收与定版，不存在「小改免验」。修订前后用 `compare_asset_versions` 取配置差异写进交付报告。
