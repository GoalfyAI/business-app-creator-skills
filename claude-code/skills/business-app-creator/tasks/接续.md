# 接续

## 识别信号

- 开发者说「继续」「接着做」「上次那个应用」，或当前目录已有 `app.json`、`WORKSPACE.md`、`workspace.json`。
- 开发者给了此前的 `task_id`、应用名或 `business_ui_id`。

## 先读什么

1. 当前应用工程根的三件套：`WORKSPACE.md` 的 `current_stage` 与 `business_ui_id`，`workspace.json` 各段状态，`docs/stages/` 下当前段的阶段文档，`docs/proposal/index.html` 的确认页。
2. 原工单：`task_manager(action="get", task_id=…)` 看已记的 checkpoint（资产 ID、版本、run_id）。原工单是只读或已结单时新建 write 工单并传 `continued_from_task_id`。
3. 本地缺失或换了机器：`workspace_remote_status` 看云端状态，`workspace_pull` 取回，先比较差异、保留本地新改动再合并，不默认用云端覆盖本地。规则见 [../reference/开发者中心与工作区.md](../reference/开发者中心与工作区.md)。
4. 脚手架版本：按 [../reference/脚手架与预置件.md](../reference/脚手架与预置件.md) 带 `workspace_id` 调一次 `download_template` 核门槛；低于必须线先迁移。
5. 缺失的工作区文件用 `npm run scaffold:repair -- --app-name "<应用名>"` 补，保留已有事实。

## 从哪一段进

从 `workspace.json` 里最早一个不是 `passed` 的段进。进入前按该段「出口」核对上一段的证据是否仍成立（资产还在、版本没被别人改、冒泡证据仍是当前合同下的）；不成立就回到证据失效的那一段。旧七阶段应用的阶段名可能是旧名，按 G 键对应，只改状态不改名。
