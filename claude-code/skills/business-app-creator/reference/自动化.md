# 自动化

## 适用场景

PRD 里有「到点自动做」或「数据一变就自动做」的功能，要给应用声明自动化规则、验证它、或排查自动运行没发起 / 被跳过时读。

## 规则

### 平台怎么发起

自动化只在应用发布后可用（开发者本人也一样）：使用者在应用的「自动化」面板开启规则后，平台以**使用者本人的正式身份**建一个新项目（出现在应用的历史运行记录里），提交这条路线的入口表单，效果与手动提交一致；每次运行的 `business_id` / `form_submit_id` 都是新的。运行怎么结束看路线的收尾方式（见「收尾方式」）：直接交付记「已完成」，等使用者确认记「待审阅」，Agent 收尾由 Agent 结束。

- **定时触发**：到点发起，项目名称为「自动化名称 · 计划时刻」。平台保证同一计划时刻只发起一次，但立即运行与失败后再跑仍会再来一次，写库按业务键幂等。
- **事件触发**：不看时间，看应用库——使用者实例库里声明的表发生新增、修改或删除后，平台稍后发起，项目名称为「自动化名称 · 变化发生时刻」，入口参数可取自那条记录。运行规则见「事件触发的运行规则」。捕获只作用于使用者实例库，开发工作集里的写入不会触发。
- **触发前的门禁**：应用已发布且使用者仍持有、实例就绪、账号可用、上一次已结束、配额与余额足够；不满足时本次记「跳过」并写原因。
- 超过声明的 `timeout_minutes` 平台停掉项目记「超时」；同一原因连续失败达到平台阈值后规则自动暂停。

### 声明与校验

PRD 写了「到点自动做」或「数据一变就自动做」的路线，制作时要让它能**无人值守地跑到交付**：自动发起时没有人在旁边答题。声明写在应用版本上（`business_ui_manage(update, automations=[…])`），场景包不改；平台在保存和发布时按下面几条逐项校验，不满足直接拒绝：

| 约束 | 不满足时的做法 |
|---|---|
| 入口 `input_schema` 的每个必填字段，都在声明 `params` 里有来源：`fixed`（固定值）、`user`（使用者开启时预先填）、`trigger_var`（定时触发为 `fire_time` / `fire_date` / `last_success_time`，事件触发为 `event_time` / `event_op`，只能填字符串字段）、`event_field`（仅事件触发，取触发记录的某一列，列类型要和入口字段类型相容） | 让路线第一个节点自己取数（例如按日期查收银系统），入口只留能预先确定的字段 |
| 入口不能有文件字段 | 改成路线内从数据源或应用库取文件 |
| 路线里没有运行中交互（`after_success` 表单）和 `sa_handoff` | 这类路线只能人工发起；需要自动化就把中途判断改成规则或 FA 判断 |
| 声明的 `review` 与路线 `delivery.review.type` 一致，收尾方式按「收尾方式」选 | 路线是 `agent_gate` 却想让使用者逐次确认（或反过来）：改路线的审阅形态或改声明，两者必须一致 |
| 路线要**自给**：前置记录由路线内节点创建，产出回流也在路线内完成（见 [数据模板.md](数据模板.md)「谁建行、谁写列」）；应用后端在无人访问时可能缩容到 0，不能指望到点时它在线接回调 | 把「应用后端先建记录再发起」改成路线第一个节点建记录 |
| 重复触发不重复写 | 回数据模板补唯一键与累加规则 |

每条声明还要写 `timeout_minutes`（超时平台会停掉项目）、`review`（`user_gate` 或 `agent_gate`，缺省 `user_gate`，必须等于路线的 `delivery.review.type`）和触发方式：

- **定时触发** `trigger{type:"schedule", default_cron（5 段）, timezone, min_interval_minutes, user_editable}`。
- **事件触发** `trigger{type:"event", table, operations, watch_columns, max_runs_per_hour, timezone}`：应用数据表 `table` 发生 `operations`（`insert` / `update` / `delete` 的非空子集）时运行。`table` 必须是应用挂载的数据模板里的表，写库里的真实表名（小写）；`watch_columns` 只对 `update` 生效，写了就只在这些列的值真的变化时触发，不写表示任意列变化都触发；`max_runs_per_hour` 必填，是每个使用者规则每小时最多发起的次数，取值范围以 `validate` 的校验结果为准；`timezone` 可选，只决定 `event_time` 用哪个时区。`event_field` 参数新增、修改取新值，删除取删除前的值。

### 事件触发的运行规则

| 平台行为 | 对路线的要求 |
|---|---|
| 应用后端写库、使用者手动对话里 Agent 写库都会触发；**自动化运行进行中自己写库不会再触发任何规则**（防止循环）；运行结束后使用者在那个项目里继续对话产生的写入照常触发 | 路线里可以放心回写同一张表；需要「A 写完再触发 B」的链式动作放在同一条路线里 |
| 同一条变化只发起一次；前一次运行没结束时，后面的变化按先后排队，前一次结束才发起下一次；排队有上限 | 单次运行要短；批量处理放进一条路线，不要每行一次 |
| 超过每小时上限或排队已满的变化不处理，计入规则的「已忽略」数；一条语句批量改动很多行时，只有前面一部分逐条触发 | 批量导入不要依赖事件逐行处理；需要全量处理的改成定时触发 |
| 规则暂停期间的变化不处理，只计数；恢复后只处理之后的变化 | 不要假设每一条变化都一定会跑到 |
| 触发记录过大时不带内容，必填的 `event_field` 取不到值，本次运行失败 | 大字段不要作为 `event_field`，改成路线里按主键查库 |
| 事件触发的规则也能在面板「立即运行」：没有触发记录，由使用者在弹窗里填写 `event_field` 参数对应的列值代替，`event_op` 取声明的第一种操作，`event_time` 取当下；这次运行记为手动运行，不计入每小时上限 | `event_field` 参数的入口字段类型要能由使用者手填（不要指向大字段或内部 id）；每个 `event_field` 参数写 `label`（弹窗里显示的中文名，例如「广告主编号」），需要说明格式时写 `help`（显示为输入框提示）；不写 `label` 弹窗直接显示列名 |

排队上限、逐条触发的行数上限、连续失败几次自动暂停、变化发生后多久发起等具体数值归平台管理，会随平台调整，制作时不按固定数值设计，以 `validate` 返回和平台当前配置为准。

`automation_key` 跨版本保持不变：改了等于删掉旧自动化，使用者已开的规则会被暂停并要求重新确认；定时与事件之间改触发方式，使用者要删掉旧规则重新开启。

### 收尾方式

路线跑完怎么结束，决定使用者要不要操作，也决定每次运行的费用：

| 收尾方式 | 路线 `delivery.review` 写法 | 声明 `review` | 效果 | 什么时候用 |
|---|---|---|---|---|
| 直接交付 | `type:"user_gate"`、`message_type:"result"`，只声明一个 `complete_business` 动作；`delivery.mapping.text` 指向发给使用者的那句话 | `user_gate` | 平台把 `text` 作为结果消息发给使用者并结束项目，不唤醒 Agent，没有 Agent 收尾的模型费用；运行记「已完成」 | 自动化的缺省选择：结果不需要使用者确认，也不需要 Agent 判断 |
| 等使用者确认 | `type:"user_gate"`（`message_type` 缺省为 `ask`） | `user_gate` | 交付停在审阅、进使用者消息中心，运行记「待审阅」 | 结果要使用者逐次确认才算数，而且触发不频繁 |
| Agent 收尾 | `type:"agent_gate"` | `agent_gate` | Agent 读交付后调用模型收尾，每次运行都有一笔 Agent 模型费用，常常比路线本身还贵 | 确实需要 Agent 按路线声明的标准判断结果好坏 |

业务条件（当天已经生成、应用开关没开、配额用完）放在路线第一个节点判断；判断为不用执行时照常输出一句说明映射到 `text` 并结束。配合直接交付，这类运行只花建项目时的少量费用；用 Agent 收尾则照样付整笔收尾费用。直接交付没有「失败」动作：节点报错照常记运行失败，业务上的不足（例如来源覆盖不全）写进 `text`。

### 验证

`business_ui_automation` 的几个动作各管一件事（花费按 [../SKILL.md](../SKILL.md)「花费」）：

- `validate` 校验声明；`bubble` 用冒泡按自动化的入口在开发工作集里跑一次，验处理逻辑。保存声明、`validate` 和 `bubble` 都按挂载的场景包校验：挂着本人场景包草稿时直接对草稿校验，不用先把场景包上线；返回的 `validated_against` 写明实际校验用的是哪一行。④ 用它们验收，到点真触发怎么记见 [../stages/4-试用验收.md](../stages/4-试用验收.md)「2.4 逐条判定」。
- `run_once` 以开发者身份在正式实例上真跑一次（事件触发的规则用 `run_once, event_row=…` 给一条模拟记录），`run_status` / `run_stop` 看和停。它要求应用已有上线版本、跑的是正式实例，不在开发工作集里，所以不用于 ④ ⑤ 的验证。
- 真实到点触发走正式入口：应用发布后，开发者本人从 GoalfyMax 打开这个应用，在「自动化」面板开启规则、立即运行、等到点触发，运行以他本人的正式身份建项目。MCP 不提供规则的创建与暂停，手动发起不等于定时运行。
- `rules` / `runs`：开发者发布并给自己开启规则后回来问到点结果时，用 `rules` 核对规则是否已保存、状态和下次运行时间，用 `runs`（可带 `rule_id`）看到点后是否已发起及结果。这两个动作只读、只看开发者本人的规则和他自己拥有的应用，不能开启或修改规则；规则不跟某个版本绑定，每次运行都用当前上线版本，`rules` 返回的 `version` 就是它。应用还不在开发者「我的应用」里时 `rules` 会被拒绝，请开发者先从 GoalfyMax 打开一次这个应用；`runs` 返回空列表只说明本人没有运行记录。

## 常见错误

- 入口有必填字段没有来源，或有文件字段，保存被拒。
- 路线里有中途表单或 `sa_handoff`，只能人工发起。
- 依赖应用后端在到点时在线建记录；后端可能已缩容到 0。
- 触发频繁的规则用「等使用者确认」收尾，待审阅堆满消息中心。
- 结果不需要判断的自动化用 `agent_gate` 收尾，每次运行白付一笔 Agent 模型费用；改成直接交付。
- 批量导入依赖事件逐行触发，超出每小时上限的变化被忽略。
- `event_field` 参数没写 `label`，使用者在「立即运行」弹窗里看到的是数据库列名。
- 改了 `automation_key`，使用者已开的规则被暂停。
- 拿 `run_once` 的结果当 ④ 的验收证据。
