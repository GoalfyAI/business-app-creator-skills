# P7 版本、部署、上线与恢复

> 细则正本。阶段文件 G1–G7 是唯一主线；本文只放 G 文件写不下的表格、契约、纪律清单与示例，在 G 文件点名时查阅。本文不含流程，不含进入与出口条件。

服务 G5a 能力容器定稿上线；G7 应用定稿、目录发布、反读、修订、回滚、下线、删除、交付报告与结单。版本体系正本见 references。

## 1. 上线门

上线门、定稿上线、交付报告与结单。

进入前提（总入口 4.1）：G5 出口条件全部满足——前三层候选验收通过、草稿态端到端全真到达终态、问题单无未处置 fail、结果检查表全绿。存在 `full_validation_skipped` 时**不得**进入本节。

发布是外部状态变更。开发者当前请求已明确要求上线，或已确认的总体 Plan 明确写出“前三层候选验收通过后上线”或同等清晰的执行动作时，发布授权已经成立，达到上线门后直接执行上线动作，**不得**重复询问。总体 Plan 只列发布范围、候选资产或路线而没有明确上线动作时，发布授权尚未成立，调用前**必须**单独确认（约束 6）。

## 2. 定稿与上线

上线动作把草稿态版本**定稿并真正上线**：草稿物理行由 `testing` 晋级为 `live` 并对最终用户可运行；同一家族的旧上线版本保持不变，已在使用旧版本的项目不受影响（详见 [场景包版本体系与发布逻辑](../references/场景包版本体系与发布逻辑.md)）。

定稿上线由平台执行以下闸门与动作，被拦时按结构化错误处理、**禁止**绕过：

- **运行时身份**：FastAgent、工具集、TPE 的物理行必须有运行时注册身份，否则上线后不可调用；
- **工具组连接信息**：URL、沙箱或启动命令三者其一，否则上线出的是不可运行的死配置；
- **文件物化就绪**：Skill 文件等对象存储内容必须已就绪，未就绪的草稿不允许定稿；
- **依赖闭包**：定稿时把依赖的 `latest` 引用钉到当刻解析的具体版本；开发者显式选择跟随最新的依赖保留 `latest` 语义——这意味着主动放弃"旧版本跑旧逻辑"，**必须**让开发者知情。

上线动作：`finalize_asset_version_online(asset_type="scenario_pack", draft_asset_id=<草稿行>, change_note=...)`——闭包校验通过后把草稿晋级 live，旧版本继续可用。被版本闸门拒绝（提示需要先定稿或先建草稿）时按 P8 第 4 节的报错对照处理。

## 3. 上线后反读

上线后**必须**反读线上状态和目标版本；**禁止**因为离线验收通过就宣称已发布（约束 10）。反读确认的线上版本是交付报告的事实基线，也是后续维护与诊断的起点。

## 4. 交付报告与工单收尾

交付前逐一核对：核心文件真实存在、路径在允许范围内、来源链与上游工具输出或开发者提供的文件一致。

报告包含计数、百分比、日期范围、排名或"来源—内容"配对时，**必须**逐条对照原始证据复核。无法证明的数字**必须**删除、修正或明确标为假设（约束 2）。

交付报告结论先行，包含：

- 场景包名称、标识和当前状态
- 解决的业务问题
- 里程碑与候选路线
- 核心资产与能力
- 验证证据层级
- 真机运行结果或跳过决定
- 效果结论：结果检查表通过情况（N 条 `passed` / M 条 `waived` 及理由）、问题单处置摘要（fail 修复记录、advice 采纳情况）、开发者业务标准（样例选择确定的验收判定）的符合情况
- 修订类任务：与上一 live 版本的配置差异摘要（`compare_asset_versions` 的结果按业务语言归纳，不贴原始 diff）
- 运行成本观察：全真运行的 FastAgent 调用次数、积分消耗与耗时（取自运行记录；没有可靠数字就写"未统计"，不估算）
- 能力缺口
- 剩余盲区和后续条件

## 5. 结单

用 `task_manager(insert)` 记录最终资产、验证层级、全真决定和盲区，再 `task_manager(complete)`。有业务路线时，必须检查结单响应中的 `completion_evidence.route_bubbles` 与发布范围逐条一致；返回 `WORKFLOW_TASK_ROUTE_BUBBLE_EVIDENCE_REQUIRED` 时，按其中的路线状态补跑或修复同一资产，禁止删标签、改文字或另开工单绕过。**禁止**用完整日志、凭证或临时地址充当工单交付内容。

结单前同时确认结果检查表快照（`result_checklist_snapshot`）为最新且全绿；存在 `pending` 或未 waive 的 fail 时回 G5 处理后再结单。

## 6. 版本出口

上线之后的版本操作（详见 [场景包版本体系与发布逻辑](../references/场景包版本体系与发布逻辑.md)）：

| 动作 | 工具 | 纪律 |
|---|---|---|
| **看家族** | `list_asset_versions` | 任何版本操作前先看清哪一行是现役 live、有没有搁浅草稿；`items[].id` 是后续回滚/比较要用的版本事实 id |
| **继续修订** | `ensure_editable_asset_draft` | 回 G1 第 1 节出草稿，走完整制作与验证循环 |
| **比较两版本** | `compare_asset_versions(base_version_id, target_version_id)` | 修订验收与交付报告的配置差异证据；它比的是**配置事实**，不是运行效果——效果仍靠结果检查表回归 |
| **作废草稿** | `abandon_asset_version_draft` | 只能作废未上线且未被引用的草稿；作废前**必须** `get_asset_usage_impact` 看影响面并告知开发者 |
| **回滚** | `rollback_asset_version(version_id)` | 以历史版本内容**克隆出新的 testing 草稿**（不修改任何历史行）→ 按 G5 验收 → `finalize` 上线。回滚属于外部状态变更，**必须**开发者确认（约束 6）；回滚后仍要处理引用方（G3 的 `mounted_by_stale` 清单同样适用） |

这套版本工具对六类资产（`scenario_pack` / `tpe` / `toolset` / `fast_agent` / `tool_group` / `business_ui`）同构；业务应用侧的用法见 app-creator G7。

## 7. 上线（finalize）

把验收通过的草稿定版上线，交付报告，结单；已上线应用的修订、回滚、下线、删除也在本节。上线是高危动作：**开发者明确授权后才执行**（拍板节点）。

`business_ui_manage(action="finalize", draft_asset_id=...)`（等价于 `finalize_asset_version_online(asset_type="business_ui")`）把草稿定版上线：闭包校验 + 模板升级链校验 + 迁移脚本彩排。**前提**：P6 第 9 节 自动化测试门三类全绿——工具闸门不检查这一条，凭工单 `autotest` 记录自证；没有记录或有未修复的失败，不 finalize。上线闸门用三个稳定错误码拒绝未就绪的定版，处置对照：

| 错误码 | 含义 | 处置 |
|---|---|---|
| `BUSINESS_UI_NO_BUNDLE` | 还没有源码包 | 回 P6 第 8 节：上传并 deploy 后再 finalize |
| `BUSINESS_UI_NOT_DEPLOYED` | 源码包没有成功构建发布 | `deploy` 到终态 `success` 再 finalize |
| `BUSINESS_UI_TEMPLATE_REQUIRED` | 带代码包的业务应用定版没有挂业务应用数据集模板 | 回 G5 建表并 `extract` 出模板版本 → `business_ui_manage(update, dataset_template_id, dataset_template_version)` 挂到草稿 → 重新 `deploy`（模板进指纹）→ finalize |
| `BUSINESS_UI_NOT_RELEASED`（`resolve` 时返回，不是 finalize） | 上线了但从未发布，使用者打开的是"已发布"版本所以打不开 | 在发布管理页发布一版；上线只影响开发者自测，不会推给使用者 |
| `BUSINESS_UI_CONTRACT_OUTDATED` | 挂载场景包的编排型 TPE 契约已变化 | 重新 `deploy`（吸收新契约）后再 finalize；契约变化波及页面时先回 G3 变更检查 |
| `BUSINESS_UI_TEMPLATE_SWITCHED` | 换绑到另一个模板家族（等于换库） | 不允许；需要新库就新建业务应用 |
| `BUSINESS_UI_TEMPLATE_UPGRADE_PATH_BROKEN` | 模板升级链缺迁移脚本 | 回 G5：破坏性变更的 `extract` 随带 `migration_script` |
| `BUSINESS_UI_TEMPLATE_REGRESSION` | 回滚钉回了更老的模板版本 | 没有降级：把旧结构重新抽成一个新版本再挂 |
| `BUSINESS_UI_UPGRADE_REHEARSAL_FAILED` | 迁移脚本在临时库彩排失败 | 按返回的错误修脚本，重新 `extract` |

上线成功后**必须反读**：`business_ui_manage(action="resolve")` 返回消费者视角的 `entry_url` 与挂载场景包身份——这是上线证据；resolve 报"还没有上线版本"说明 finalize 未生效，不得宣称已上线。定版时场景包引用钉到当时具体版本，**把该版本号记入工单与交付报告**。

## 8. 修订已上线版本

已上线版本不可直接改：`update` 会自动派生新草稿（或先 `ensure_draft` 显式出草稿）→ 修改（改元信息经 update；改源码经 P6 第 8 节重新上传部署）→ `finalize` 新草稿。两条纪律：

- 改挂载（场景包或业务应用数据集模板版本）属于**契约变更**，先回 G3 做变更影响检查再实现；换模板版本前先在 G5 `extract` 出新版本；
- 每次修订走完 G6 验收再 finalize，不存在"小改免验"；
- 修订前后用 `compare_asset_versions(asset_type="business_ui", base_version_id, target_version_id)` 取配置差异（版本事实 id 来自 `list_asset_versions`），作为验收与交付报告的证据——它比的是配置，页面行为仍靠 G6 真环境验收。

## 9. 回滚

线上版本出了问题要回到历史版本：`rollback_asset_version(asset_type="business_ui", asset_id, version_id=<list_asset_versions 里目标版本的 id>)`——以该历史版本的内容**克隆出一个新的 testing 草稿**，不修改任何历史行；然后 `business_ui_manage(get)` 反读草稿的挂载与源码包引用是否随版本恢复（未恢复的按 P6 第 8 节重新 deploy），走一遍 G6 验收，再 `finalize` 上线。回滚是外部状态变更，**必须**开发者确认（约束 6）；回滚后仍要按第 1 节反读 `entry_url`。

## 10. 删除（约束 6 高危）

`delete` **永久删除整个家族（全部版本）**及其全部实例、Pod、Schema、项目文件和源码包，不可恢复、无回收站；传任一版本行 ID 也是删整个家族，**不存在**"只删一个版本"。必须开发者明确授权（有在线版本或已发布到目录的应用要逐字复述应用名让开发者确认），且显式传 `confirm_permanent_delete=true`。受理即不可撤销，后台分阶段清理常超过 2 分钟。返回语义三态：

- `deleting`，或 `cleanup_failed` 且 `retrying=true`：**删除中**。后者是中途失败、后台正在自动重试，`attempts` 与 `max_attempts` 和原因都在返回里，**不得**向开发者报"删除失败"；
- `failed`：终态失败，自动重试已用尽，带 `error_code` 与 `error_message`。如实转告原因，围栏仍生效、应用不可再用；
- `deleted`：已永久删除。

查进度**只用** `business_ui_manage(action="deletion_status")`，它是只读的；**不要**用 `delete` 轮询，已有任务时 `delete` 也只回读，不会重复发起。终态 `failed` 要重新发起，必须开发者确认下游已修复后，`delete` 且 `retry_failed=true`——工具把意图传给 Hub，由 Hub 归零重试次数、从当前阶段继续；不带它 Hub 会拒绝并返回 409，这是**唯一**能重启终态失败的动作。

停用一个在用的应用**不用**删除，用第 11 节的下线。

## 11. 下线（offline，可逆）

`business_ui_manage(action="offline", business_ui_id=<家族 ID 或任一版本行 ID>)`：**家族下线**——拆掉全部容器（每个版本行的开发者容器 + 每个用户的实例容器），**用户库、源码包、版本记录全部保留**，家族标为未上线（用户点开与目录进入都被拒）。重新上线 = 对当前版本重新 `deploy` 后 `finalize`（P6 第 8 节 → 本文第 1 节）。

- 下线是外部状态变更，**必须**开发者确认（约束 6）；确认时说清用户会失去入口但数据不丢；
- `BUSINESS_UI_RELEASED_CANNOT_OFFLINE`：已发布到目录的应用不能直接下线，先在发布管理页取消发布（unpublish）再 `offline`——这就是总入口约束 7 "发布版不能下线"的确切含义；
- `BUSINESS_UI_OFFLINE_INCOMPLETE`：家族已标为未上线但部分容器没拆掉（`failures` 里有 user_id / deploy_id）——修复 p2s 后重复 `offline` 幂等重试；
- 下线后反读 `business_ui_manage(get)` 确认状态，记入工单。

## 12. 交付报告与结单

报告**结论先行**，包含：

- 应用名称与上线版本、`entry_url`、依赖的场景包版本（定版钉住的那个）、业务应用数据集模板与版本；
- 四类页面清单与接口清单；
- 验收结果：清单通过情况、遗留问题、明说的盲区（未验证什么）;
- 运行语义说明（开发者需要知道的平台行为）：用户首次打开时按模板 copy 出该用户的 schema 并部署实例；无流量实例会被静默缩容，首次访问冷启动稍慢。

结单前：结果检查表快照全绿、两张表最新快照已回写工单；确认线上实例已改为按钉的模板版本注库后，`dataset_template_workspace(close, data_uid)` 收掉 G5 开的工作集——它一路撑到这里才没有保留价值。
