## 为什么要迁

R-379（智能应用去 SA、单项目并行、去场景包）上线后，新建应用默认走新路：应用版本直接挂编排和 TPE，运行时没有主控 Agent（SA），每次运行叫一次「执行」，用服务端生成的 `business_id` 标识；每个使用者实例一个隐藏项目，多次执行在里面并行。旧应用仍按旧路运行，迁到新路才能用上并行执行和新 SDK 的页面能力。

这是 SDK 4 到 5 的主版本迁移，不是在原版本上小改：页面接口、配置文件声明、编排挂载位置都要换，做完要整体冒泡和试用验收。

## 判断依据

- 是否已在新路：看 `frontend/goalfy-app.json` 的 `executor`。新建应用用哪条路由当前脚手架模板决定，不要手工给旧模板加 `executor`，也不要在新模板里删掉它。
- 只换了固定层不算迁完：`manifest` 测试只说明配置文件已是新路，业务代码是否已改到执行层由 `business-code-on-execution` 判断，教学页面是否已清理由 `demo-cleaned` 判断。
- 同一应用的旧版本仍走旧路；发布新 SDK 版本后，新发起的执行才走新路。

## 层说明

本单只改 Studio 仓库，不改平台代码。`applies_to.layers` 写的是迁移时应用要跟着变的层：脚手架与 SDK（固定层和页面写法）、制作 Skill（新路制作口径）、平台（编排挂在应用版本上、执行与冒泡接口），供升级计划判断这份指南属于哪类改动。

## 常见错误

- 给新路应用又建场景包，或在 `setup` 里传 `scenario_pack_id`。
- 只保存改动的那条路线或漏了某个 TPE，保存被拒（`references unmounted tpe_id`）或覆盖掉其他路线。
- 沿用「交由 Agent 处理」的审阅动作，Hub 保存时拒收（400，`workflow orchestration invalid`）。
- 工具集挂在场景包而不在节点 TPE 上，运行时报 `invalid tool call name`。
- 冒泡或真跑时自己编 `business_id`，或想用 `send` 跟执行对话（新路没有对话）。
- 不带 `draft_asset_id` 读应用，读到的是上线版本，误以为草稿没挂上编排。
- 占位草稿还没挂编排就上传源码包或部署，被拒（`BUSINESS_UI_NO_SCENARIO_PACK`）；改过编排没重新部署就发布，被拒（`BUSINESS_UI_CONTRACT_OUTDATED`）。
