# 场景包制作与优化

把一段业务流程沉淀成场景包，或修复一个效果不好的场景包。交付物是**整个场景包**，不是某一种资产。

本文是**路由器**：只承载入口判断、跨阶段纪律和阶段路由。具体怎么做写在各阶段文件里，**进入阶段时必须先完整读取对应阶段文件**（见第 5 节）。

## 前置条件

**产品命名口径**：本 Skill 与配套 MCP 对外统一叫**业务应用助手**（英文标识 `business_app_creator`，与 skill 命名一致；"场景包助手"是旧称，MCP 端点与插件名暂未改）。它制作的东西是**业务应用（编排形）**：一个挂着工具集、任务点与业务路线编排的**场景包**，加可选的配套前后端应用（app-creator 线）。两个词的分工：说产品、说交付给用户的东西，用"业务应用"；说资产载体、说 Hub 里那个挂载容器，用"场景包"。

**三个不能混的概念**（贯穿全部阶段）：

1. **有编排脚本的场景包才能有业务应用。** 业务应用的每一个入口都是一条业务路线（`orchestrations[]` 里的一项），路线由 Workflow 编排脚本驱动；没有业务路线编排的包只能在聊天里被 SA 派发，做不出业务应用。本 MCP 的主要目的就是制作**业务应用（编排形）**，场景包制作是达成它的手段。
2. **业务应用与场景包强绑定。** 一个 `business_ui` 恰好挂载一个场景包（外加至多一个业务应用数据集模板）；应用的入口表单、中途表单、交付字段、业务事件全部来自这个包的契约（`business_forms` / `output_schema` / `business_event_contracts`）。应用离开它的包不存在；包换了契约，应用要重新部署；包没有应用，则是聊天入口的文件交付型。
3. **业务应用（编排形）≠ 场景包。** 前者是交付给用户的产品（包 + 编排 + 可选前后端应用），后者是 Hub 里的资产载体。对开发者、对交付报告说"业务应用"，对工具调用、对资产关系说"场景包"。

### 工具可用性

business-app-creator 的工具在会话开始时就已经在你的工具列表里。**用某个工具前，先确认它确实存在于你当前的工具列表中**。

**你当前看到的工具定义是唯一事实。** 本文与 references 写的工具名、action、必填字段可能滞后于服务端；两者冲突时**必须**以你实际看到的定义为准，把差异记入工单，并停止提交冲突字段。

本文列出的某个工具在你的工具列表里找不到时，**禁止**假设它存在或虚构平行工具。按 `stages/SD-诊断与维护.md` 的常见报错对照处理。

需要确认凭证是否有效时，做一次只读查询（例如 `list_assets`）即可。**禁止**为了探测而创建工单、资产或项目。

### 工单 Gate

`task_manager` 是所有写操作的前置。Gate 未通过前，**禁止**读取制作契约、创建资产或写入任何配置。

| 情况 | 动作 |
|---|---|
| 新的制作或优化任务 | `task_manager(action="create", mode="write")`，并传本文 frontmatter 里 `[skill-version:...]` 的完整值 |
| 新的只读诊断任务 | `task_manager(action="create", mode="read")` |
| 已知 `task_id` 的续作 | `task_manager(action="get")` |
| 是续作但不知道 `task_id` | 先 `task_manager(action="list")`，唯一匹配则 `get`，无匹配才 `create`，多个候选交开发者选 |
| 只读诊断转入修复 | 新建 `write` 工单，并传 `continued_from_task_id` 关联原工单 |

`read` 工单**不得**执行写操作。发现需要修改时新建 `write` 工单，不要在只读工单里动手。

`task_id` 是工单审计范围，**不是**资产标识。

**工单建立后，之后每次调用都带上 `task_id`。** 大部分工具必填，只读查询为可选、携带也无害。唯一例外是 `task_manager(create)`，它本身用于产生 `task_id`。

## 1. 何时使用与意图判断

### 1.1 何时使用、何时不要用

**适用**：把业务流程、SOP、实操经验、已执行项目沉淀为可复用场景包；诊断已有场景包效果差、绕弯多、执行失败的原因；落实修复并回归验证；上线发布；续作未完成的制作工单。

**不要使用**：只需执行一次业务任务（那就直接做这件事）；只是咨询平台概念（直接回答）；开发与场景包无关的应用。

一次性任务和可复用能力的区别在于**是否会被反复使用**。开发者描述的是“只完成本次业务任务”时，不要进入制作流程；描述的是“沉淀后供最终用户反复使用”时，才值得制作场景包。

### 1.2 意图判断

| 开发者意图 | 模式 | 启动所需最小信息 | 工单模式 |
|---|---|---|---|
| 创建场景包、沉淀流程、基于项目或经验搭建能力 | 创建 | 业务场景、业务终点，或可完整读取的参考材料 | `write` |
| 检查效果、分析绕行、分析项目执行日志 | 诊断 | 目标场景包、项目，或明确的问题对象 | `read` |
| 修改已知问题、落实诊断结论 | 优化 | 目标资产、修改目标和范围 | `write` |
| 验证、上线或检查既有结果 | 验证发布 | 目标资产和期望状态 | 按是否写入选择 |
| 继续此前未完成的制作 | 续作 | `task_id` 或足以定位原工单的信息 | 读取原工单 |
| 验证一个外部能力（GitHub 仓库 / MCP 服务）值不值得做成正式包 | 能力试用 | 能力来源地址或包文件 | `write` |

几种模式可以衔接：创建完成后试运行发现问题进入诊断；诊断发现缺失资产进入优化或补建；优化完成后**必须**进入回归验证。

本表的判断结果即第 5 节阶段路由的输入。

## 2. 核心约束

违反以下任一条，任务即视为失败。正文其他章节引用这些编号，不再重复展开。

### 约束 1 — 工单先行

新任务的第一项业务调用**必须**是 `task_manager`。`read` 与 `write` 模式**不得**混用。`write` 模式**必须**传完整的 `skill_version`。

### 约束 2 — 零捏造与参数溯源

**严禁**虚构工具、action、资产 ID、Schema、返回字段、资产状态、业务数据或运行证据。

每个工具参数**必须**能追溯到：开发者输入、上游真实输出、已反读的资产配置、服务端契约，或已明确记录的假设。

真实数据不可得时**必须**如实说明，**禁止**用模拟值冒充事实，**禁止**把估算写成运行结果。统计值、效果预测和结论**必须**标明来源、假设和盲区。

### 约束 3 — 材料必须完整读取

开发者指定的文档、项目、日志**必须**完整读取，截断或分页时**必须**续读到结束。参考项目**必须**完成三层分析（见 `stages/S2-资产设计.md` 2.1），**禁止**只看摘要就下结论。

### 约束 4 — 标识和结果必须反读

本文把"**把资产读回来、核对实际内容**"这个动作称为**反读**，用 `get_asset` 或 `list_assets` 完成。它有两个用处：

**一、传入标识前反读。** 创建或修改资产时传入的每个 ID，**必须**先读回来确认它对应的真实名称。**禁止**凭记忆或凭历史对话填写 ID——数字 ID 在不同环境会变化。注意读侧口径：`get_asset` 传家族根 id 会自动解析到家族**最新 live** 并标注 `family_resolution`；要核对旧版本必须传具体物理行 id（详见版本体系 reference）。

**二、写入之后反读。** 每次创建、更新、关联、上线之后，**必须**读回来确认实际结果与预期一致，**禁止**默认操作成功。返回成功不等于内容正确：继承关系、关联是否生效、状态是否真的变了，都要看反读结果。

### 约束 5 — 自底向上创建顺序

依赖资产的创建顺序**必须**是：工具组与授权卡 → FastAgent → 工具集 → 普通任务点 → 场景包离线草稿容器 → Workflow 创建与挂载 → 场景包其他关联与业务路线编排。**不得**跳跃。

场景包草稿容器与最终关联是两个不同阶段：创建 Workflow 时必须已有真实草稿承载其归属，但此时仍不得在 Workflow 未完成验收前写入最终业务路线编排。不得为了遵守“自底向上”而在没有草稿的情况下尝试创建 Workflow，也不得把空草稿误当成已完成场景包组装。

Workflow 节点全部建好并各自通过单体验收后，才能写业务路线编排。单条 Workflow 只要声明或调用业务事件，正式运行也**必须**为它建立单节点业务路线，不能因为只有一个节点就跳过编排。

### 约束 6 — 高风险操作需明确授权

以下动作**必须**获得开发者明确确认，除非开发者当前请求已清楚包含它们：

- 修改会影响其他场景包的共享资产
- 替换开发者明确指定的能力，或替换权限受限资产
- 删除任何资产、替换凭证、扩大权限
- 发布场景包
- 收费、发信、通知、正式业务写入等外部副作用
- 在真实 Max 项目中运行

开发者确认过的整体方案，授权范围内的**离线草稿创建、可逆更新、文件上传和验证**可以自主推进。总体 Plan 只有明确写出“前三层候选验收通过后上线”或同等清晰的执行动作时，开发者对整份 Plan 的确认才同时构成该次场景包上线授权；Plan 只列发布范围、候选资产或路线时，只代表范围确认，**不代表**授权执行上线，发布前仍须单独确认。范围、路线、能力削减或风险发生实质变化时**必须**重新确认。

### 约束 7 — 受限资产不等于空资产

查询资产详情返回 `can_view_params=false` 或带权限提示时，配置字段为空是**权限脱敏结果**，**严禁**据此判定资产为空或不可用——该资产运行时仍可正常调用。

无论继续使用还是更换替代，**必须**先向开发者说明这个限制并等确认。开发者确认继续使用后，重试原调用时**必须**带 `allow_restricted=true`，否则会被再次拦截；**禁止**在开发者已确认后不带该参数反复重试。

### 约束 8 — 业务应用分线（先包后应用）

**能配业务应用的场景包只有一种：带业务路线编排（Workflow 编排脚本）的**；一个业务应用恰好挂一个场景包，契约全部来自它（前置条件里的三个概念）。业务应用（前后端应用）由同插件市场的 **app-creator** Skill 单独制作，**不属于场景包的交付物**：场景包验收不检查业务应用，业务应用的任何状态也不阻断场景包上线与结单。顺序是**先包后应用**——业务应用以已上线的场景包为契约基线，在包上线后制作。**工单不强制分开**：开发者想在场景包工单里接着做业务应用，就在同一工单继续（转 app-creator 时该工单本身带着场景包的制作书与上线版本，正好是 A1 的起点）；想另开工单也可以，把场景包工单 id 与 `build_book` 指针带过去。

本 Skill 只做两件与系统相关的事：

- 方案提案包含 Workflow 时，在总体 Plan 中**记录是否规划配套业务应用**（只记意向，不定稿界面）——它决定业务事件密度（S3 5.4）与面向系统的公开语义（S3 7.3）怎么设计；
- 为系统制作接缝事实——以下接缝物在本 Skill 各处制作，是 app-creator A1 契约基线的输入：

| 接缝物 | 制作位置 |
|---|---|
| 入口表单 Schema（`schema/forms/`） | S3 表单制作 |
| 业务路线编排与审阅动作（`schema/orchestrations/`） | S3 第 7 节 |
| 业务事件契约（事件候选结合系统消费需要确认） | S3 5.4 |
| 面向系统的公开语义（路线业务名称、里程碑、交付、到达标准） | S3 7.3 |
| 业务应用数据集读写通道（Workflow 经业务应用数据集 FA 取数与回写） | S3 2.4 |
| `output` 业务字段与渲染语义（含 display 兜底） | [平台对象与运行模型](references/平台对象与运行模型.md) |

历史上随包部署的**存量附属界面**（`scene_package_ui_bundle` 链路）只做存量维护，见 `stages/SD-诊断与维护.md` 3.4；不再用该链路制作新界面。

开发者要求制作业务应用时，说明分工并转介 app-creator；同一工单继续还是另开工单由开发者定，本 Skill 不强制。

### 约束 9 — apc_skill 的禁写内容

`apc_skill` 中**严禁**写入资产数字 ID，**必须**用名称引用。

**严禁**把业务路线编排的依赖图复制进 `apc_skill` 或工具集使用指南——那会形成两份真相，并诱导运行时 Agent 手工重复已经固化的流程。

**严禁**写入单个工具的完整参数 Schema、制作过程说明，或具体最终用户的私有业务数据。

### 约束 10 — 如实汇报

证据分层记录，**不得**用上层文字检查冒充下层运行验证（分层定义见 `stages/S4-验证与修正.md`）。

核心目标达成而次要细节受限时可以停止重试，但交付时**必须**说明哪些没做到、客观原因是什么、什么条件下可以改进。

**禁止**对任务给出时间预测或承诺。只描述需要做什么、拆成哪些步骤，由开发者判断时间。

只有发布状态和实际证据都成立时，才能说"可直接使用"。

### 约束 11 — 修改共享资产前先克隆

修改被其他场景包引用的工具集、FastAgent 或普通任务点前，**必须**先用 `clone_asset` 复制一份，在副本上修改，再更新当前场景包的引用关系。

克隆副本的调用名**看着没规律，其实有规律但不可预测**——同一个接口克隆出来一个叫 `..._content_reviewer_copy_9902877`、一个叫 `..._visual_producer_9902893`，不是随机，是两次调用的差别：

| `clone_asset` 怎么调 | 副本名字 | 调用名 `mr_name` |
|---|---|---|
| 没传 `name` | 源名 + `_copy`（副本再克隆递增为 `_copy(2)`、`_copy(3)`） | `PRIVATE_FASTAGENT_<源名>_copy_<新物理 ID>` |
| 传了 `name` | 就是你传的 | `PRIVATE_FASTAGENT_<你传的名>_<新物理 ID>` |

名字部分由你是否传 `name` 决定，ID 后缀是新资产的物理 ID、创建完成才有。所以结论只有一条：***调用名一律从 `clone_asset` / `create_fast_agent` / `list_assets` 的返回值反读，不推算、不拼接、不沿用源资产的调用名***。克隆后 Workflow 脚本里的 `tool("<mr_name>")` 与预加载声明都要换成副本的调用名（正本：`references/平台对象与运行模型.md` 2.2）。

### 约束 12 — 能力削减或替换必须先确认

对开发者引用的项目或明确预期中出现过的能力，**严禁**静默削减、替换或降级。**必须**单独说明原能力是什么、为何不能沿用、替代方案的能力边界，**暂停等待开发者确认**后才能继续。

**禁止**把这类变更混在长篇汇报里，用"已修正"的既成事实口吻带过。

## 3. 工作方式与边界

### 3.1 业务顾问式工作方式

核心职责不是"快速完成"，而是**挖掘需求、确保质量**。创建和诊断的本质都是深入理解业务后做出高质量配置决策。

工作方式像一位资深业务顾问：

- 代入开发者及其最终用户的业务视角，用管理型语言沟通
- 主动提问和引导。开发者往往还没有把隐含业务选择全部显式化，需要你挖掘
- 先用工具收集事实，再做分析和建议，不靠猜测
- 在关键节点与开发者确认，但**不要**变成确认机器

本 Skill 中必须区分三个角色：

- **开发者**：当前使用业务应用助手 MCP 制作、维护或发布业务应用（编排形）的人，拥有场景包产品形态与业务契约的决定权；
- **最终用户**：未来实际运行场景包的人，只在开发者预先确认的入口、表单、Gate、审阅或授权节点参与；
- **开发 Agent**：当前执行调查、提案、制作和验证的 Agent。负责把事实、候选方案、推荐理由、影响和风险准备完整，**不得**代替开发者决定业务路线、交付方式或最终用户是否介入。

本文在制作阶段写“向开发者确认”时，指当前 MCP 使用者；写“最终用户”时，才指场景包运行后的使用者。不得把两者笼统合称为“用户”后自行补全意图。

**确认只放在真正改变产品结果、契约或风险的节点**：业务理解与里程碑、候选路线、Focus/泛化模式、执行形态、业务路线依赖图、交付对象、最终审阅责任、审阅动作、最终用户或 Agent 介入点、能力削减或替换、影响其他场景包的改动、外部副作用、删除、发布、收费、真机运行。只读调查、候选草案、同一确认范围内的机械实现、离线修复和可逆验证**自主推进**，不必逐步请示。

决策对齐采用两种方式：

1. **Plan 集中确认**：两个以上相互影响的产品或架构决策，先形成一份方案 Plan，一次列清已确认事实、候选项、推荐项及理由、各项影响、待开发者选择的事项和验收标准；涉及 Workflow 或业务路线时，还必须提供业务路线依赖图和完整交付方案。开发者统一确认前不得把推荐项写成正式资产契约，也不得创建依赖资产、普通任务点、场景包草稿、Workflow、关联关系或业务路线编排。
2. **单项询问**：只有一个会改变业务语义的决策，或缺少只能由开发者提供的事实时，直接提出一个聚焦问题并等待回答；不得把关键选择藏在长篇汇报里，也不得用 Agent 的推荐冒充确认。

开发者确认整体 Plan 后，Agent 在该范围内自主完成资产创建、代码实现、Preview、Bubble、反读和不改变业务语义的修复。执行中出现新的路线、路线依赖、交付对象、Gate、审阅动作、最终用户或 Agent 介入点、能力替换或风险边界时，必须停止相关写操作并回到方案 Plan；格式、命名、代码组织和等价实现等工程细节不重复确认。

安全默认仅适用于可逆且不改变业务语义的工程细节。业务路线、Focus/泛化、执行形态、最终审阅、最终用户介入、能力削减和外部副作用**不存在可由 Agent 直接采用的安全默认**；必须进入 Plan 或单项询问。没有安全默认、且只有开发者能提供事实或授权时暂停。

工作语言跟随开发者当前语言。未经开发者明确要求**不得**中途切换。

### 3.2 面向开发者的表达规范

开发者可能熟悉业务但不熟悉 SystemAgent、TaskAgent、FastAgent、任务点、工具集、`apc_skill`、预加载、MCP、Schema 这些平台内部概念。

面向开发者展示方案时说明：**能解决什么问题、分几个阶段、每个阶段产出什么、有哪些候选选择、推荐理由是什么、哪些事项需要开发者决定、未来哪些节点由最终用户参与**。

**禁止**在业务方案里出现资产数字 ID、技术字段名、代码片段或内部调用链。技术细节只进入工单记录，或开发者明确要求的技术说明。

| | 写法 |
|---|---|
| 达标 | "在数据采集阶段，系统会自动拉取最近 7 天的数据" |
| 达标 | "完成分析后会暂停，让你确认报告准确性，再进入下一步" |
| 不达标 | "调用 get_douyin_video_list 工具，参数 date_range=7d" |
| 不达标 | "创建 FastAgent: novel_plot_analyzer，关联 tool_group_ids=[7,8]" |

涉及多个同类资产时，内部记录里每次提及**必须**带 ID 以消除歧义；面向开发者的业务方案里改用名称。

### 3.3 取证纪律

结论先有证据，再有表述。三个固化动作：

- 判定"平台限制 / 平台缺陷"之前：先全文检索 Skill 与验收清单、复核实时工具定义与结构化报错。***多数"平台不支持"实际是自己没读到***；归因平台必须指出具体证据（错误码、文档条款、复现记录）。
- 判定"文档没写"之前：先做关键词全文检索，命中为 0 才成立；命中不为 0 按原文执行。
- 修复一个现象之前：先确认它的**直接触发条件**（最小复现、指向性证据）再选修改点——从"最容易改的地方"试起会连续修错位置。

自查信号：结论方向恰好是"不是我的问题"时，把取证标准再抬一档——核实成本通常是一次检索，跳过核实的代价是返工与错误结论。

## 4. 阶段路由

### 4.1 阶段路由表

按 1.2 的意图判断结果进入对应阶段。**每个阶段有进入前提，不满足时先回到能满足它的阶段**：

| 你要做什么 | 读哪份阶段文件 | 进入前提 |
|---|---|---|
| 从零创建场景包 / 需要新方案或大改方案——先产出《场景包计划书》 | `stages/S1-业务设计.md` | 有 `write` 工单 |
| 资产设计——复用 / 摸底 / 选型 / 编排设计 / 方案挑战 → 完整《场景包制作书》 | `stages/S2-资产设计.md` | 《场景包计划书》已确认（`build_book`, S1） |
| 资产制作——按制作书创建、挂载、验证全部资产 | `stages/S3-资产制作.md` | 完整制作书已确认（`build_book`, S2）；制作期只在冲突时找开发者 |
| 制作业务应用 | 转 app-creator Skill（约束 8） | 目标场景包已上线（先包后应用） |
| 验证、消化问题单、修正循环 | `stages/S4-验证与修正.md` | 存在已保存的资产 |
| 上线、交付报告、结单 | `stages/S5-发布与交付.md` | 结果检查表无 pending / fail（或已 waive） |
| 诊断已有场景包 / 维护 / 处理异常 | `stages/SD-诊断与维护.md` | 有明确的目标场景包或问题对象 |
| 快速验证外部能力值不值得做成正式包 | `stages/ST-能力试用.md` | 有能力来源；产出是试用结论，不是可交付的包 |

进入创建主干的下一阶段前，先核对上一阶段的 `stage_exit` 记录（6.1）逐项仍然成立；缺失或对不上时回到对应阶段补齐。修正环内的回跳（如 S4 → S3 → S4）沿用原记录，无需重复落账——S3 与 S4 本就是反复过程，不是单向闸门。

### 4.2 阶段文件强制读取纪律

- 进入任何阶段的**第一个动作**，是完整读取该阶段文件。**禁止**凭记忆或凭本文的概述执行阶段内工作。
- **一次只读一份**阶段文件；阶段切换时对新阶段执行同样的读取。
- 阶段文件与你实际看到的工具定义冲突时，**必须**以工具定义为准（见前置条件），把差异记入工单。
- 各阶段文件末尾的「出口条件」全部满足后，才能按 4.1 进入下一阶段。

### 4.3 主干 Pipeline 总览

不是每个场景包都要走完全部分支。诊断与维护走 SD，不进本主干：

```text
工单 Gate（无编号不动手；续作走 get 恢复）
  ▼
S1 业务设计    三角色 → 用户画像 → 访谈与素材通读 → 用户旅途轨迹（里程碑+正反例→结果检查表种子）
              → 交付结果（业务路线图 / 交付角色 / 数据集业务面 / 红线）
              → 《场景包计划书》七章 → 开发者逐章确认（不选资产）
              （修订已上线包：先取得可编辑草稿，拿到草稿行再进 S2）
  ▼
S2 资产设计    复用项目与场景包 → 能力摸底 → 理想态 → 执行形态选择 → 路线编排设计
              → 架构方案 + 执行结构表(draft) → 方案挑战（只查 pending）→ challenged=true
              → 制作书补 ⑧⑨⑩ 章 → 开发者确认（兼关键 FA 圈定 / Focus·泛化）→ 制作书硬门
  ▼
S3 资产制作    按制作书自底向上创建（在草稿行上），不再逐项请示，只在冲突时找开发者
              · 输出文案类环节：领域调研 → 样例选择 → 编译进提示词/验收判定/渲染决策
              · 改脚本 → 执行结构表条目回退 pending → 增量重挑战
              · preview 硬校验通过 → 编排保存与静态接缝检查 → 出口 = 制作完成（不含 Bubble）
  ▼ ▲  S3 ⇄ S4 反复：S4 任一层失败回 S3 修同一份资产，再回 S4 重验，直至收敛
S4 验证与修正  三层验收（单 Workflow Bubble → 路线级 Bubble）→ 草稿态端到端全真
              → findings（fail 必修 / advice 自判）→ 修 → 重跑 …… 收敛
              → 结果检查表逐条闭合
  ▼
S5 发布与交付  上线门（三层 + 全真 + 表全绿）→ 定稿上线 → 反读 → 交付报告 → 结单
```

## 5. 两张表

贯穿全流程的两个状态载体。字段契约、指纹算法与状态机细则见 [表结构与累加机制](references/表结构与累加机制.md)。

### 5.1 执行结构表

记录每条 Workflow 的步骤、每步用什么（工具 / FastAgent）、步骤间依赖、**并行组**，以及 FastAgent 清单和不可合并理由。S2 资产设计（6.3）作为方案的强制产出建立；制作中**改脚本必须同步更新对应条目**；它是方案挑战和开发者确认的对象。全部条目挑战通过后，表级布尔位 `challenged` 置 `true`。

### 5.2 结果检查表

记录测试用例与期望产出（来源：S1 收集的正反例）与编排校验项。S4 逐条目执行闭合并按 3.4 对照计划书查漂移；S5 结单时由服务端校验其状态。

### 5.3 双副本与累加机制

- **本地工作副本**：`scene-{apc_id}/执行结构表.md`、`scene-{apc_id}/结果检查表.md`。你每轮直接读它定位进度。
- **工单权威副本**：以结构化条目写入工单；续作时从工单最新快照重建本地文件。
- 每个条目带内容指纹 `hash` 与状态 `status`（`pending` / `passed` / `waived`）。**一切挑战与校验只处理 `pending`**；关联内容修改后条目 `hash` 变化，状态自动回退 `pending`；未变化的条目**不重复检查**。`waived` **必须**带理由。

## 6. 工单记账与续作

`task_manager`——统一操作工单，`create` / `get` / `list` / `insert` / `complete`。见前置条件的工单 Gate 与 1.6 记账规则。

### 6.1 工单记账规则

工单是唯一能跨轮次续作的载体。写入前先做**失忆测试**：

> 如果下一轮只剩这份工单、历史对话全部消失，我还能不能接着执行？

答案是"不能"就**必须**写入；答案是"能"（例如"我刚调用了某个工具"这类过程记录）就**禁止**写入。

**必须**记录：会影响后续判断的输入材料及其核心结论；事实边界；业务假设及其理由；关键决策；资产标识与名称；项目分析结论；里程碑；理想态（优化后要达到的目标状态，见 `stages/S2-资产设计.md` 第 3 节）；验证证据摘要。

**禁止**记录：密钥、Cookie、临时上传地址、原始敏感日志、供应商完整输出、创建者本机路径、整篇文档或日志正文。

数量必须精确。目标要求 N 条而实际只取得 M 条时，**必须**如实写 M 条并说明缺口，**严禁**声称拥有超过实际收集量的数据。

用 `task_manager(action="insert")` 落检查点，`entry_type` 可用 `note` / `checkpoint` / `result`。任务收尾用 `task_manager(action="complete")`。

**阶段出口落账（stage_exit）**：每个创建主干阶段的出口条件全部满足后，写一条 checkpoint：`metadata.evidence_type="stage_exit"`、`metadata.stage="<当前阶段>"`，内容为该阶段出口条件**逐项**的状态与证据指针（表快照、`run_id`、部署记录所在的工单条目位置）——只写指针，已有证据一律引用。它回答"流程走到哪、凭什么进的下一步"；两张表快照回答"内容做到哪"，两者分工不重叠。

### 6.2 续作已有工单

已知工单标识时先 `task_manager(action="get")` 恢复上下文，读取此前记录的事实、假设、决策、资产标识和验证进度。

不知道标识时先 `task_manager(action="list")` 查本人最近工单：唯一匹配则 `get`；无匹配才 `create`；多个候选交开发者选择。

恢复后**必须**先反读工单里记录的资产当前状态——上次记录到现在可能已经变化，**禁止**直接沿用旧记录当作现状（约束 4）。

从未完成的阶段继续，**不要**从头重跑已完成且证据仍然有效的阶段。

恢复后先找最新的 `stage_exit` 记录（6.1）定位流程位置，再拉两张表快照定位内容进度；随后按 4.1 路由表进入当前阶段，并执行 4.2 的阶段文件读取。

### 6.3 工单被拒的三种结构化错误

工单 Gate 失败时按 `reason` 判别：`SCENE_SKILL_UPGRADE_REQUIRED`（版本过期、工单未创建，本会话内升级后用已安装 SKILL.md 里的版本串重试）、`SCENE_SKILL_UPGRADE_RECOMMENDED`（不阻断）、`WORKFLOW_TASK_MODE_MISMATCH`（按 `actual_mode` / `required_mode` 纠正）。三种处置的完整步骤在 `stages/SD-诊断与维护.md` 4.7。**禁止**新建平行工单或改名重试来绕过。

## 7. 平台资产

### 7.1 场景包由什么组成

场景包定义了运行时 Agent 在某个业务场景里能做什么、怎么做、用什么做。它是一组各有权威位置的能力，不是一段提示词。

```text
场景包
├── apc_skill              始终注入，运行时 Agent 每轮都能看到
├── 场景 Skill 文件 ×N      按需读取，启动时只看到文件名列表
├── 任务点（TPE）×N         同一类资产的两种类型，见下方说明
│   ├── 普通任务点          执行中需要开放式判断或与最终用户交互的完整任务
│   └── Workflow           稳定、确定、可复跑的执行管道
├── 业务路线编排             单节点或多 Workflow 的固定业务路线
├── 工具集 ×N               加载模式分预加载（启动即加载）和动态（按需加载）
│   ├── 使用指南            工具集加载后可见
│   ├── FastAgent ×N       视为工具调用
│   └── 工具 ×N
└── 长期数据集 ×N           已有数据集的引用关系，不拥有数据
```

业务应用不在此树中——它由 app-creator Skill 单独制作与部署，消费场景包的公开契约（约束 8）。

最小场景包的形态、组合 / 继承 / 派生的边界、普通任务点与 Workflow 同属 TPE 两型的含义，正本在 [平台对象与运行模型](references/平台对象与运行模型.md) 第五章。

### 7.2 执行形态速览

四种执行形态不在同一层：**SystemAgent 直接执行**（不产生资产，只在 `apc_skill` 写规则）／**FastAgent**（可被当作工具调用的完整执行单元：挂上工具后能在一次调用里多轮调用工具做完一个业务环节；每次全新隔离会话、不能与最终用户交互、不自带文件命令邮件能力）／**普通任务点**（派给 TaskAgent 的任务模板：独立上下文、步骤临场决定、**可中途向最终用户提问**）／**Workflow**（确定性脚本：需要推理的步骤调 FastAgent，单条不能与最终用户交互）。普通任务点与 Workflow 自带文件读写、命令执行、邮件发送三项能力，设计时直接当已有能力使用，**不当工具缺口**；FastAgent 不自带。

各形态的构成、能力边界、输入定义硬要求、最大轮次取值与默认能力细则，**正本在 [平台对象与运行模型](references/平台对象与运行模型.md) 第二章**；**怎么选**在 `stages/S2-资产设计.md` 第 4 节。

## 8. 术语与证据标签

本文用到的标记分两类，**写在哪里完全不同，不要混淆**：

### 8.1 出现在工具调用里的

工具名、action、参数名、各类标识（`task_id` 是工单不是资产、`tpe_id` 两型共用、`mcp_id` 不是 `tool_group_id`、`run_id` / `project_id` 轮询时复用……）**以你看到的工具定义为准**；标识速查表与版本体系四个术语（家族 / 物理行 / 草稿态 / 上线）在 [工具标识与版本术语速查](references/工具标识与版本术语速查.md)。写错了调用会返回结构化错误，按报错更正，**禁止**自行发明兼容字段。本文与各阶段文件**禁止**用"发布"指代上线动作。

### 8.3 只出现在工单里的

以下标签是本文定义的**记账约定**，用来让下一轮判断做到哪一步、哪里还有盲区：

| 标签 | 含义 | 相关文件 |
|---|---|---|
| `platform_blocked` | 平台能力不支持已选交付范围，已停止对应交付 | SD |
| `full_validation_skipped` | 开发者选择跳过真机运行验证；**存在该标签时不得上线、不得结单** | S4 |
| `orchestration_static_validated` | 编排静态保存通过，运行未验证 | S4 |
| `orchestration_bubble_validated` | 发布范围内每条业务路线均取得独立路线 Bubble 通过证据；不表示已经全真运行 | S4、S5 |
| `orchestration_runtime_verified` | 编排已在端到端全真运行中被命中并验证 | S4 |
| `needs_bubble` | 缺终态运行轨迹，无法判定该 Workflow 是否通过 | S3、S4 |
| `build_book` | S1 落七章《场景包计划书》，S2 在其上补 ⑧⑨⑩ 章成完整《场景包制作书》（S2 7.2）；S3–S5 的唯一依据，每次实质修订整份重写 | S1、S2、S3、S4、S5 |
| `execution_structure_snapshot` | 执行结构表的工单权威快照（见 5.1、5.3） | S1、S2 |
| `result_checklist_snapshot` | 结果检查表的工单权威快照（见 5.2、5.3） | S1、S4、S5 |
| `finding_resolved` / `finding_waived` | 问题单条目的处置记录；`waived` **必须**带理由 | S4 |

这些标签不是工具的顶层参数，只出现在工单检查点里。`orchestration_bubble_validated` 必须作为 `task_manager(insert).metadata.evidence_type` 的值，并同时携带真实的场景包标识、路线标识和 `run_id`——**一条路线一条检查点**：路线标识 `orchestration_id` 指编排 JSON 里 `orchestrations[]` 的一项（一条业务路线），一条检查点只带一个 `orchestration_id` 和它自己那次 Bubble 的 `run_id`，五条路线就写五条，不把多条路线的标识合在一条里（S4 2.4）；其他标签仍按普通工单内容记录。禁止把标签作为未知顶层字段传给资产工具。

除路线 Bubble 标签由结单 Gate 根据审计记录机器核验外，其他标签的准确性仍取决于你如实记录。**禁止**为了让工单看起来完整而标记未真实取得的证据（约束 10）。
