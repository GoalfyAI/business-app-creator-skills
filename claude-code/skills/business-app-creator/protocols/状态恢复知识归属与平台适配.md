# 协议四：状态恢复、知识归属、模板选用与平台适配

工单保存跨轮次续作所需的审计与证据，本地应用工程保存当前制作进度；两者核对，不能用旧检查点覆盖新文件。知识分两类，问题分两类，分开存放。不内置业务模板。平台对象与执行形态的正本在 references。

## 1. 工单记账与续作

`task_manager` 提供五个 action：`create`、`get`、`list`、`insert`、`complete`。

**Gate 原文。**

`task_manager` 是所有写操作的前置。Gate 未通过前，**禁止**读取制作契约、创建资产或写入任何配置。

| 情况 | 动作 |
|---|---|
| 新的制作或优化任务 | `task_manager(action="create", mode="write")`，并传SKILL.md frontmatter 里 `[skill-version:...]` 的完整值 |
| 新的只读诊断任务 | `task_manager(action="create", mode="read")` |
| 已知 `task_id` 的续作 | `task_manager(action="get")` |
| 是续作但不知道 `task_id` | 先 `task_manager(action="list")`，唯一匹配则 `get`，无匹配才 `create`，多个候选交开发者选 |
| 只读诊断转入修复 | 新建 `write` 工单，并传 `continued_from_task_id` 关联原工单 |

`read` 工单**不得**执行写操作。发现需要修改时新建 `write` 工单，不要在只读工单里动手。

`task_id` 是工单审计范围，**不是**资产标识。

**按工具契约携带工单。** 制作、部署和运行工具声明 `task_id` 时带当前工单；`submit_dev_feedback` 支持用它关联审计。`workspace_remote_status`、`workspace_pull`、`workspace_push`、`dev_preferences`、`query_dev_feedback` 按自身 Schema 传参，身份由已验证上下文提供，这些入口没有 `task_id` 参数。`task_manager(create)` 生成工单标识。新增工具以当前实际 Schema 为准，工单 Gate 与各工具参数范围分别核对。

Gate 失败按 `reason` 处置：`SCENE_SKILL_UPGRADE_REQUIRED`，本会话升级后用已安装 SKILL.md 的版本串重试；`SCENE_SKILL_UPGRADE_RECOMMENDED`，不阻断；`WORKFLOW_TASK_MODE_MISMATCH`，按 `actual_mode` 与 `required_mode` 纠正。**禁止**新建平行工单或改名绕过。细则见 P8 第 4.7 节。

**失忆测试。** 写入前问一句：下一轮只剩这份工单，还能不能接着干。不能就必须写；能就**禁止**写。必须记录：影响后续判断的材料与核心结论、事实边界、业务假设与理由、关键决策、资产标识与名称、里程碑、理想态、验证证据摘要、U 行为的分阶段结论。**禁止**记录：密钥、Cookie、临时上传地址、原始敏感日志、供应商完整输出、本机路径、整篇正文。数量必须精确，缺口如实写。

**阶段出口落账。** 每个阶段出口条件全部满足后写一条 `stage_exit` 检查点，内容是出口条件逐项状态与证据指针，只写指针。续作时先找最新 `stage_exit` 定位流程位置，再拉表快照定位内容进度，再按 SKILL.md 路由进入阶段并完整读取阶段文件。恢复后先反读工单里记录的资产当前状态，**禁止**沿用旧记录当现状。从最早未满足的必要条件进入，**禁止**机械从 G1 重做。

**记账规则原文。**

工单必须能在对话丢失时恢复关键事实与决策，但不能替代本地工程或未保存的改动。写入前先做**失忆测试**：

> 如果下一轮只剩这份工单、历史对话全部消失，我还能不能接着执行？

答案是"不能"就**必须**写入；答案是"能"（例如"我刚调用了某个工具"这类过程记录）就**禁止**写入。

**必须**记录：会影响后续判断的输入材料及其核心结论；事实边界；业务假设及其理由；关键决策；资产标识与名称；项目分析结论；里程碑；理想态（优化后要达到的目标状态，见 P3 第 1 节）；验证证据摘要。

**禁止**记录：密钥、Cookie、临时上传地址、原始敏感日志、供应商完整输出、创建者本机路径、整篇文档或日志正文。

数量必须精确。目标要求 N 条而实际只取得 M 条时，**必须**如实写 M 条并说明缺口，**严禁**声称拥有超过实际收集量的数据。

用 `task_manager(action="insert")` 落检查点，`entry_type` 可用 `note` / `checkpoint` / `result`。任务收尾用 `task_manager(action="complete")`。

**阶段出口落账（stage_exit）**：每个创建主干阶段的出口条件全部满足后，写一条 checkpoint：`metadata.evidence_type="stage_exit"`、`metadata.stage="<当前阶段>"`，内容为该阶段出口条件**逐项**的状态与证据指针（表快照、`run_id`、部署记录所在的工单条目位置）——只写指针，已有证据一律引用。它回答"流程走到哪、凭什么进的下一步"；两张表快照回答"内容做到哪"，两者分工不重叠。

**续作原文。**

以下工单恢复只用于核对已记录的事实与证据，不是文件恢复指令。`stage_exit` 标记上次已通过的出口，不包含此后未保存的制作进度；本机接续、缺失恢复及两边差异的处置一律按第 6 节，不能据旧检查点回退当前本地文件。

已知工单标识时先 `task_manager(action="get")` 恢复上下文，读取此前记录的事实、假设、决策、资产标识和验证进度。

不知道标识时先 `task_manager(action="list")` 查本人最近工单：唯一匹配则 `get`；无匹配才 `create`；多个候选交开发者选择。

恢复后**必须**先反读工单里记录的资产当前状态——上次记录到现在可能已经变化，**禁止**直接沿用旧记录当作现状，规则见协议一约束 4。

从未完成的阶段继续，**不要**从头重跑已完成且证据仍然有效的阶段。

恢复后先找最新的 `stage_exit` 记录定位流程位置，再拉两张表快照定位内容进度；随后按 SKILL.md 第 2 节进入当前阶段并完整读取阶段文件。

**应用线记账原文。** 用 `task_manager` 同款体系：`create` 开工单、`insert` 落检查点与应用结构表/结果检查表快照、`complete` 结单。写入前做失忆测试（只剩工单还能不能接着干）；**禁止**记录密钥、PG 连接串、临时地址。阶段出口条件满足后落 `stage_exit` checkpoint（出口条件逐项状态 + 证据指针）；续作时用最新 `stage_exit` 与两张表快照核对本地实际进度，不覆盖出口之后的改动。两份固定 checkpoint：G3 确认版《智能应用计划书》落 `app_plan`（正文、方案页版本与设计位置），G7 自动化测试报告落 `autotest`（跑了几条 / 过了几条 / 覆盖的计划书条目 / 盲区）。

## 2. 两类知识、两类问题

| 类别 | 内容 | 绑定到 | 不进入 |
|---|---|---|---|
| 领域知识 | 业务规则、案例、来源、适用范围、生效时间 | 运行时真正需要它的执行者：apc_skill、场景 Skill 文件、FastAgent 提示词、工具集使用指南。能力容器里的文件不天然对 FastAgent 可见，方法见 P3 知识写作一节 | 平台文档 |
| 开发知识 | 工具接入、契约坑、SDK 与部署故障、可复用修复 | 平台与版本；同行业经验库；开发知识库 | 终端用户的业务资料 |
| 智能应用问题 | 表现、输入、产物、版本、根因、改进目标 | 路由到 G1 至 G7 的相应阶段，方法见 P8 | 无 |
| 平台与 Skill 问题 | 可复现证据、受影响版本、临时处置、修复状态 | 统一问题台账。流程固定：收集、分类、跟进、验证、回流。状态固定：待整理、已确认、处理中、待验证、已解决。临时绕过**不算**解决 | 每个应用的私有补丁 |

同行业经验库只收三类条目：业态知识、关键问题、参考经验。每条带适用条件与时间。个别用户的选择**不当作**业态通用规则。展示时按当前场景筛选。过期条目标"待复核"。G1 提问前、G3 识别决策前必须先查。

## 3. 优化能力与"优化已经有效"分开

开发期必须设计并验证六件事：反馈来自哪里；关联哪份输入、产物、版本；修改是纠错还是偏好；适用范围与撤销；下一次哪个节点使用；如何做可比对照。公共策略、模型、工具、编排的变化属于开发变更，进入相应阶段并回归。用户明确的长期偏好属于应用数据行为，在授权范围内生效。单次修改**不得**自动升级为长期偏好。长期收益必须由上线后的实际样本证明。

## 4. 模板选用

脚手架**不内置**多套业务模板。粗浅业务由 AI 直接写出；复杂专业业务我们不具备业务能力。智能应用是把客户方专业知识与 AI 结合的框架。脚手架 demo 只用于理解协议，规则见协议一约束 20。产品经理式改进走 P8 的提案制：你提出改进提案，开发者审核，修改后再审核发布。**禁止**绕过开发者改线上。

## 5. 平台适配

**命名口径。** 产品叫智能应用助手。插件、市场、仓库名 `business-app-creator`；MCP 名 `business-app-creator-mcp`；本 Skill 名 `business-app-creator`。交付给用户的是智能应用。场景包只是它的能力容器在平台里的名字，只在工具调用和资产关系里出现；"场景包助手"是旧称。任务点即 TPE，分两型：普通 TPE 派给 TaskAgent 临场执行；编排型 TPE 即 O-TPE，是确定性脚本，编排工具与 FastAgent。"Workflow"是编排型 TPE 的旧称。MCP 工具名 `otpe_manage` 与 `otpe_tool_test`，诊断文档 topic 以 `otpe_` 开头。平台契约字段**不改名**，包括 `tpe_type=workflow`、`workflow_orchestration`、`workflow_runtime_id`。

**智能应用、能力容器与数据模板的关系。** 智能应用通过能力容器的业务路线提供执行入口，挂载一个或多个能力容器，至多一份数据模板。默认按单容器设计；多容器时列清每条入口所属容器及版本，按 P6 第 7 节核对首个容器与当前运行入口的限制。

**平台对象与执行形态。** 正本见 `references/平台对象与运行模型.md`；标识与版本术语见 `references/工具标识与版本术语速查.md`；版本体系见 `references/场景包版本体系与发布逻辑.md`；依赖接入见 `references/依赖与MCP接入.md`。平台运行契约只通过实时 Schema 与 `get_diagnosis_doc` 获取。

**脚手架正本。** 根 `README.md`；`frontend/README.md` 与 `frontend/CLAUDE.md`；`frontend/docs/business-ui-guide.md`；`frontend/schema/README.md` 契约区 v4；`frontend/schema/api/` 公开接口 OpenAPI，一个接口一个文件；`frontend/src/sdk/docs/`；`backend/README.md`；当前模板前端 README 指向的测试文档；`frontend/docs/message-guide.md`。官方前端 guidance 副本在 `references/前端设计指南/`。

**手工版与平台版。** 案例库、步级记分、判定器校准、裸跑探针、差分归因、人工任务、回退链、确认即标注、再分配建议、问题台账、可视化工作台，首发一律按手工版执行：结果检查表加列、你手工填表、FastAgent 评分加开发者校准、脚本分支、中途表单收最终用户结果、工单评论加 OA。平台机制建成后替换。本 Skill **不承诺**平台没有的能力。

## 6. 工作区、阶段 md 与阶段状态

**先分清工作台目录与应用工程根。** Goalfy App 管工作台和 Codex 对话，本节文件都属于当前智能应用，不属于 App 安装目录。桌面分配的专属工作目录下以 `apps/<本应用目录名>` 承载工程，目录树顶层写实际业务目录名；创建、接续和命令定位按总入口第 1.3 节。一个会话只维护它对应的应用，保存、恢复、版本上报都用该应用自己的 `workspace_id`，不因名称相似复用别的目录或身份。Goalfy 管理的外层目录不自行改名。

**阶段状态的正本是应用工程根的 `workspace.json`。** 结构固定：`{"targets": [{"name": "业务目标与范围", "status": "passed"}, …]}`，有序数组，每项只有 `name` 与 `status` 两个字段，多写字段会被云端拒收。`name` 用阶段的中文名，**不写** `G1` 这种编号。`status` 只有四态 `not_started`、`in_progress`、`passed`、`failed`；阶段一开工就改成 `in_progress`，不等阶段出口才记。**没有阻塞态**：等补料、等授权、等修复时保持 `in_progress`，原因写在该阶段 md 的正文里。云端存储允许条数可变，本 Skill 固定七项 G1 到 G7、顺序不变，当前阶段、承诺状态和开发进度由你同步到方案 HTML。核对为同一份工作状态后，其他记录与 `workspace.json` 有分歧时以它为准；本地与云端的两份文件有差异时按下文比较，不能拿云端那份直接裁定本地过期。

**阶段 md 是给 Agent 的工作记录。** 七份固定名字 `docs/stages/G1-业务目标与范围.md` … `G7-预发布与交付.md`，每份以 YAML front matter 开头：`schema_version: goalfy.business_app.stage/v1`、`document_id`、`stage`、`stage_name`、`status`、`render_type`（G1、G3 `document`；G2 `workflow`；G4 到 G7 `business_app_iframe`）、`revision`；正文第一行是一级标题。front matter 里的 `status` 是**阶段文件契约，不是正本**：它是 `workspace.json` 的镜像，两处**必须在同一个动作里一起改**；保留这些字段不代表工作台展示 md 或提供阶段导航。`WORKSPACE.md` 的 `current_stage`、`current_revision`、`stage_documents` 与之对应。md 里记事实、证据、技术细节、工具调用与结论，开发者看的那份是 `docs/proposal/index.html`，见协议三第 7 节。

**两套持久化各管一件事。** 应用工程根的阶段 md 是 Agent 的工作记录；`docs/proposal/index.html` 是给开发者看的方案、进度与结果摘要；工单是审计、证据指针与结单 Gate。同一份阶段记录两边都有，改记录就重写工单条目，并将影响开发者判断的结论同步到方案页。续作先读本地 `WORKSPACE.md`、`workspace.json` 和阶段 md 定位实际进度，再 `task_manager(get)` 拉证据；工单里上次阶段出口不代表本地此后没有进展。

**阶段出口动作，顺序固定。** 门禁逐条通过后：把 `workspace.json` 里本阶段那一项改 `passed`、下一阶段那一项改 `in_progress`，并把两份阶段文档 front matter 的 `status` 同步成一样的值；把 `docs/proposal/index.html` 本阶段内容定稿、待定项改成结论、顶部阶段与版本同步；写 `stage_exit`；已有可部署代码且存在 `business_ui` 草稿时，`./scripts/pack.sh` 打包并经 `business_ui_bundle` 部署到终态 `success`，留下可核验的代码基线，但它不包含部署之后的本地改动；把 `WORKSPACE.md` 的 `current_stage` 改成下一阶段；最后按下文保存前核对规则，用 `workspace_push` 保存本应用工程根的完整受管理文件。**G4 出口的新应用是唯一例外**：先创建不带数据模板的身份草稿并 `scaffold:bind`，本阶段不部署，G5 完成后端和模板挂载后做第一次部署。

**历史与版本。** G7 上线成功后写 `docs/history/v{revision}.md`：版本、上线时间、本次承诺、变化、证据指针；`WORKSPACE.md` 的 `current_revision` 与七份文档的 `revision` 同步改成新版本。

**云端保存不等于本地恢复。** 应用工程根的受管理文档用三个工具保存到云端，每用户每工作区只留最新一份。`workspace_push` 在服务端整份覆盖，不做版本比较与合并；这是写入语义，**不是**收到 `workspace_pull` 后可以整份覆盖本地的授权：

- `workspace_remote_status(workspaceId)`：返回 `exists`、`updatedAt`、`fileCount`；读取失败会明确报错，**不得**把报错当成空工作区。
- `workspace_pull(workspaceId)`：只读取得全部受管理文件；从未保存返回 `WORKSPACE_NOT_FOUND`。先校验全部内容、路径与应用身份，暂存到独立目录做比较，**不默认写回或删除本地文件**。明确恢复范围后才逐文件临时写入再 rename，最后更新 `WORKSPACE.md`；云端没有列出的文件不能据此判为本地多余，任何覆盖或删除先保留可恢复副本并确认处置，**不删**源码与本机配置。
- `workspace_push(workspaceId, files)`：`files` 是本应用工程根的**完整**受管理文件清单，不是本次改动；本次没列出的旧文件会从云端删除；禁止空列表。允许路径四类：仓库根的 `app.json`、`WORKSPACE.md`、`workspace.json`，以及 `docs/` 下任意深度的 `.md` 与网页方案资源 `.html`、`.css`、`.js`、`.svg`。清单里**必须**同时有合法的 `app.json`、`WORKSPACE.md` 与 `workspace.json`：`app.json` 的 `schema_version` 形如 `goalfy.app/vN`，`workspace.json` 的 `targets` 非空且每项只有 `name` 与 `status`，多字段会被拒。单文件 512 KiB、总量 16 MiB、200 个文件以内。

**方案资源的保存范围。** `docs/proposal/index.html` 与它同目录的 `.css`、`.js`、`.svg` 都在白名单里，一并推上去。`workspace_push` 只收 UTF-8 文本，**png、jpg 这类位图推不上去**，已有位图属于本机资产。方案图优先内联 SVG；引用已有资料时保留来源，缺失就如实标记并补回，不让方案依赖未保存的资源。源码也不进云端，代码的云端副本是部署上传的 bundle。`saved=true` 才算保存；返回 `RESULT_UNKNOWN` 或 `STORAGE_ERROR` 时写入结果未知，**先 `workspace_pull` 核对云端内容再决定**，**禁止**盲目重试；保存失败不回滚本地状态，也**不得**声称已保存。

**接续分三种情况，不再一律先拉云端。**

1. **本机接续，本地工程仍在。** 先读当前应用的 `app.json`、`WORKSPACE.md`、`workspace.json`、阶段 md、方案页与代码改动，再核工单和平台资产。保留尚未提交、尚未保存到云端、尚未部署的进度；关闭重开 App、切换或新建开发会话都不是回滚理由。此时不因“接续”执行云端覆盖或用旧 bundle 重建工程。
2. **换机或本地缺失。** 先确认应用身份与缺失范围，再 `workspace_remote_status`；有保存才 `workspace_pull`，校验并暂存后只恢复缺失或已确认的内容。部分文件仍在时按第 3 种情况处理。源码优先从可核验的原工程、Git 或备份取回；确无更完整来源时，按真实 `business_ui_id` 核对最近一次成功部署的 bundle，解到独立目录作为候选代码基线。它不包含之后未部署的改动；没有成功部署也不能把新脚手架当旧应用代码。文档可能比 bundle 新，必须核对版本、阶段和证据，缺口如实记录，不能按较新的文档宣称代码已恢复。云端未保存不代表应用是新的，不重新生成身份。引用的本机资产缺失时补回来源，无法恢复就如实记录，不伪造历史证据。
3. **本地与云端都有内容。** 保留本地可恢复快照与云端暂存副本，按应用身份、文件内容、阶段记录、Git 改动及工单证据逐项比较；不只凭 `updatedAt`、阶段号或版本字符串判断谁较新。相同内容复用；单边变化核实来源后保留；双方各有进展或无法判断时展示差异与影响，由开发者确认取舍后再合并。冲突未解决前不整份覆盖任一侧，也不删除本地独有文件。

核对完成后，以保留实际进度的应用工程确认 `current_stage`，再按总入口核脚手架版本，从最早未满足的条件继续。**恢复会话不等于恢复文件，恢复文档不等于恢复源码。**

**什么时候 push。** 每个阶段出口动作的最后一步；开发者要求保存时；结单前。保存前重读当前本地文件，并用 `workspace_remote_status` 核对云端；已有云端内容时先只读 pull 比较，不能把其他会话或机器刚保存的进度盖掉。有差异按上面的第 3 种情况处理，再生成完整受管理清单；服务端没有并发版本保护，不并行 push 同一工作区，保存期间发现另一端写入就重新核对。代码不进 push，`saved=true` 不表示源码已备份；发生结果未知时只读核对，不用 pull 的旧内容回滚本地。

**不做的事。** 不改也不提交 `.workbench/`，它是应用调试与工作台的运行时目录；不改 `app.json` 的 `id` 而不同步改 `WORKSPACE.md` 的 `business_ui_id`；不在阶段文档 front matter 里加规范之外的字段；不把 `WORKSPACE.md` 当业务文档写正文；工作目录不离开仓根。
