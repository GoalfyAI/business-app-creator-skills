# 协议三：阶段展示与证据等级

本协议回答两件事：每个阶段给开发者看什么；什么证据能证明什么。

## 1. 展示不是追加一份长报告

默认只展示三样：**本阶段结论、关键证据、当前待决定项及其影响**。开发者需要时再展开实现细节。每个阶段文件的"给开发者看什么"一节规定默认视图；技术实现映射可展开查看。

按阶段递进的默认视图：G1 一页简报、产物样例、短流程；G2 实际产物对比、能力卡；G3 一个完整业务样例、业务路线图、结果或页面预览，职责有争议时加泳道图，状态容易混淆时加状态图；G4 单元的预期与实际对照、带步骤标注的脚本；G5 真实运行时间线、数据前后对照；G6 可操作的应用、一次旅程演示；G7 交付核对单。

每条展示的内容标来源类型，只有四种：**事实**，材料或反读里有；**推断**，你按常识得出；**未知**，需要验证；**质疑**，你的反向意见。

面向开发者的方案只说能解决什么问题、分几个阶段、每个阶段产出什么、有哪些候选、推荐理由、哪些事项需要开发者决定、未来哪些节点由最终用户参与。**禁止**在业务方案里出现资产数字 ID、技术字段名、代码片段、内部调用链；技术细节只进入工单记录，或开发者明确要求的技术说明。涉及多个同类资产时，内部记录每次提及必须带 ID 消歧，业务方案改用名称。

| | 写法 |
|---|---|
| 达标 | "在数据采集阶段，系统会自动拉取最近 7 天的数据" |
| 达标 | "完成分析后会暂停，让你确认报告准确性，再进入下一步" |
| 不达标 | "调用 get_douyin_video_list 工具，参数 date_range=7d" |
| 不达标 | "创建 FastAgent: novel_plot_analyzer，关联 tool_group_ids=[7,8]" |

涉及多个同类资产时，内部记录里每次提及**必须**带 ID 以消除歧义；面向开发者的业务方案里改用名称。

## 2. 同一事实的不同视图

业务规则与公开契约保持唯一权威来源。各视图引用同一节点或承诺编号，**禁止**维护多份"审核逻辑"。以节点"审核经营结论"为例：G1 看哪条结论缺依据、怎样算合格；G3 看自动核数与负责人判断各负责什么、退回走哪里；G4 看核验输入、规则、实际判断与反例；G5 看此次审核在哪个运行实例发生、结果如何冻结入库；G6 看待审内容、可操作项、修改影响、旧版本；G7 看对应承诺是否通过、证据属于哪个版本。

## 3. 开发者怎么说"不对"

四种方式：直接改文字或样式；选中批注；在路线图节点上写流程反馈；操作记录。每条自动带页面、步骤、版本上下文。你收到后先判断改的是文字、样式、数据、流程还是承诺。只有影响流程、数据、权限或承诺的才回问范围。改完回报实际修改与验证结果，可撤销。

## 4. 证据强度

按证据能证明什么判断，**不按**材料数量判断。

| 证据 | 可以证明 | 不能证明 |
|---|---|---|
| 已确认样例、规则、行为演示 | 双方对预期的理解一致 | 平台已具备能力 |
| 真实资产反读、Preview、静态契约检查 | 保存内容、引用和结构成立 | 真实模型内容合格；业务运行成功 |
| 安全工具取样、代表性能力实测 | 该环境、输入、版本下该能力的表现 | 所有输入和整条路线正确 |
| 单条或路线 Bubble | 具体覆盖路径的管路与控制接缝 | FastAgent 桩对应的内容质量；被屏蔽的副作用 |
| 真实路线执行 | 实际派发、模型与工具输出、表单、交付与审阅 | 应用页面正确；用户实例的数据回流正确 |
| 真实应用实例与浏览器操作 | 当前应用版本的使用与数据闭环 | 长期业务收益已改善 |
| 可比条件下的效果对照 | 特定范围内的改进证据 | 不同人群、未覆盖任务普遍改善 |

状态词只有五个：**待验证、通过、失败、阻断、不适用**。不适用必须说明理由。已知偏差必须写范围、影响、接受人。越权、数据串用、未完成却报成功三种底线**不得**豁免。

## 5. 失败怎么展示

验证失败时返回明确的问题归属与证据，归属只有五类：单元、路线、数据、页面、平台。**禁止**把失败转述为"请开发者自行处理"。测试不通过时展示失败证据与修复路径；开发者同意继续**不改变**测试结果。

## 6. 质量、耗时、费用的口径

成功率分两种：技术成功，即无报错；业务成功，即判定通过。耗时用 p95，并拆分模型时间与工具时间。费用按每次成功交付计，含失败重试与最终用户的确认时间折算。稳定性看同一输入多次结果的一致率。事实与估算分栏；估算必须标假设。

## 7. 展示物的载体：Workspace 与开发者工作台

每个阶段给开发者看的东西都是 Workspace 里**一份固定名字的 md 文件**，开发者在开发者中心 `http://127.0.0.1:5180/` 里实时看到它，起服务的方法见 SKILL.md 第 1.3 节。文件是给人看的正本；工单里的对应标签存同一份全文，保证只剩工单也能续作；两边内容相同，文件改了就整份重写工单条目，**禁止**只改一边。

**Workspace 就是业务应用的代码仓根目录**，由脚手架生成，布局固定：

| 路径 | 是什么 | 谁写 |
|---|---|---|
| `WORKSPACE.md` | 工作区入口，front matter 记 `workspace_id`、`business_ui_id`、`environment`、`current_stage`、`current_revision`、`stage_documents` 七个阶段文档路径 | 你 |
| `docs/stages/G1-业务目标与范围.md` … `docs/stages/G7-预发布与交付.md` | 七份阶段文档，名字固定，一阶段一份；脚手架不带模板，开工时由你按下面的头一次建齐 | 你 |
| `docs/history/v{revision}.md` | 每次上线一条历史记录，工作台左栏只读展示 | 你，G7 |
| `docs/screens/` | 原型与页面截图，文档里用相对路径引用 | 你 |
| `frontend/`、`backend/`、`Dockerfile`、`run-dev.sh`、`scripts/pack.sh` | 应用代码与脚本 | 你 |
| `.workbench/` | 工作台本地观察状态，不参与摘要、同步、打包 | 工作台；**禁止**动 |

**阶段文档的头**。每份以 YAML front matter 开头，工作台校验不过就不渲染：

```yaml
---
schema_version: goalfy.business_app.stage/v1
document_id: {workspace_id}-G2
stage: G2
stage_name: 关键能力可行性
status: in_progress
render_type: workflow
revision: v0.8
---
```

`status` 只有四个值：`not_started`、`in_progress`、`passed`、`failed`。`render_type` 按阶段固定：G1、G3 是 `document`，正文按 Markdown 渲染；G2 是 `workflow`，正文里的 Mermaid 代码块渲染成流程图，泳道图和路线图放这里；G4 到 G7 是 `business_app_iframe`，中间区显示本地跑着的业务应用，文档照写但不作为展示物。`revision` 与 `WORKSPACE.md` 的 `current_revision` 一致。正文第一行是一级标题。七份文档任一份头写坏，开发者中心整页报错并保留上一份有效内容，所以改头时一次改对。

| 阶段 | 文件里写什么 | 工单标签 |
|---|---|---|
| G1 | 七章《业务计划书》；关键决策清单、路线草图、正反例在 ③④⑤ 章 | `build_book` stage=G1、`behavior_scope` |
| G2 | 能力矩阵、结果检查表、能力地图表、分工建议表、泳道图 Mermaid、试验报告 | `capability_matrix`、`capability_map`、`trial_report`、`result_checklist_snapshot` |
| G3 | 上半部分《制作书》，计划书七章原样加 ⑧⑨⑩ 章、执行结构表、需求追踪矩阵；下半部分《业务应用计划书》十章，截图在 `docs/screens/` | `build_book` stage=G3、`execution_structure_snapshot`、`app_plan` |
| G4 | 单元验证记录 | `needs_bubble`、执行结构表快照 |
| G5 | 路线真跑时间线、漂移结论、问题单处置、应用数据闭环记录 | `orchestration_*`、`data_loop_verified` |
| G6 | 页面验收、时序验收、操作记录 | 前端校验项 |
| G7 | 交付核对单、最终测试报告摘要、版本清单、交付报告 | `autotest`、`integration`、`delivery_report` |

**状态怎么改、页面怎么跟着变。** 你只改文件，不操作页面。进入一个阶段：把该阶段文档的 `status` 改成 `in_progress`，把 `WORKSPACE.md` 的 `current_stage` 改成该阶段，工作台左栏随之切换。门禁全部通过：`status` 改 `passed`。门禁不过且本轮停下：`status` 改 `failed`，修好回 `in_progress`。开发者中心监听 `WORKSPACE.md` 与 `docs/` 下所有 md，改动经 SSE 局部刷新，**禁止**让开发者手动刷新或重启；文档写坏时页面保留上一份有效内容并提示，修好自动恢复。决策卡写在对应文件的"待确认"一节，开发者批注后你改文件重新提交整份。
