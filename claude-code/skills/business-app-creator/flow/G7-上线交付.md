# G7 上线交付

Studio 只有在需要上线且用户在原对话明确同意本次范围后，由 Agent 调用既有 MCP 定版/上线并回读结果。普通宿主仍由开发者说「可以上线」后由 Agent 定版，目录发布由开发者在发布管理页操作。两种模式均保留真实证据、精确版本、结单门与交付报告，Studio 详见 [Studio自动交付](../reference/Studio自动交付.md)。

## 1. 进入条件

- Studio：当前候选达到适用检查出口，且用户在原对话明确同意本次范围上线；方案确认、历史自动授权、编辑/批注完成和检查通过均不算上线同意。未答复、拒绝或接收未知不进入写入；不要求每次修改都走 G7。
- 普通宿主：G6 出口中开发者已确认预览，未验证项已记录。
- 普通宿主上线是外部状态变更：只有开发者这次明确说了「可以上线」或等价表述才执行。

## 2. 做什么

### Studio

1. **核对本次意图**：需要上线时已在同一原对话说明目标和修改范围；只有用户明确同意本次范围才继续。已明确要求本次上线时不再重复询问；未答复或拒绝就保留制作结果。范围实质变化先说明差异。方案卡只授权制作，旧自动授权不会恢复。
2. **调用现有 MCP**：沿 G6 和下方普通宿主的版本/数据检查，实际需要部署时复用 `business_ui_bundle(action="ship", ...)`；适用验收完成后使用 `business_ui_manage(action="finalize", draft_asset_id=…, task_id)`，再以 `business_ui_manage(action="get", ...)`、`business_ui_manage(action="resolve", ...)` 回读精确版本。实际参数取当前 Schema，不照抄省略号。目录上线沿原会话实际公布的既有 MCP；未暴露对应动作时报告具体缺项，不编造 publish 动作、不改平台、不回退自动 HTTP 发布。
3. **记录事实**：定版、当前 published release、正式 ready、真实业务操作分别留证。unknown 只查原记录，不换 operation/draft、不重放写入；原历史回执保留。V2 制作、未答复、拒绝或失败时保留 V1。无需新发布按钮、向导、专用确认卡或发布授权状态机。

### 普通宿主

1. **场景包版本核对**：G6 之后改过场景包的，重新部署应用，让预览跑的是最新草稿。场景包不用单独上线，下一步定版应用时会先校验、再把挂着的本人场景包草稿一起定版上线。
2. **定版前自查预览数据**：预览里确认过、上线后还要用的设定是否只存在工作集数据里；是的话先按 G5 第 5 步搬到代码默认值、场景包配置或首次设置入口，重新部署后再定版。
3. **定版应用**：`business_ui_manage(action="finalize", draft_asset_id=…, task_id)`；场景包草稿随它一起上线，定版后反读两者的版本号记进工单。被拒按 [../reference/部署与版本.md](../reference/部署与版本.md) 的定版错误码处理。
4. **反读**：`business_ui_manage(action="resolve")` 核对上线版本与挂载的场景包版本，`entry_url` 非空说明入口已写进版本；resolve 报没有上线版本说明定版没生效，**禁止**宣称已上线。`entry_url` 是开发者容器地址，**禁止**写进交付报告或发给开发者、使用者当入口。
5. **按本次交付范围处理目录发布**：目录发布不在本次范围内且不是交付前置时，据实单列发布状态，继续交付报告与结单，不额外等待开发者回复「已发布」。本次明确要求目录发布或交付项依赖已发布正式入口时，提示开发者在发布管理页发布，再核对当前正式发布状态；必需项未完成时保留受阻，不得结单或宣称该范围已完成。finalize/resolve 不是目录发布，未发布时保留「尚未发布」；实际返回 `BUSINESS_UI_NOT_RELEASED` 时按该入口合同处理，不把开发者容器地址当正式入口。正式入口就绪后才按已有授权验证自动化；没有真实到点记录不能写通过。

### 两种宿主共用

6. **结单门**：每条路线要以当前合同下最近一次到终态的运行通过，路线冒泡和真跑都算（真跑以 `route_runs` 里该路线 `succeeded` 为通过）。最近一次失败或没法验证时，先问开发者是否接受，再写（真跑失败时 `run_id` 填那次的 `project_id`）：

   ```text
   task_manager(action="insert", entry_type="checkpoint", metadata={"evidence_type": "route_verification_waived", "scene_package_id": …, "orchestration_id": …, "reason": "<至少 5 个字>", "run_id": <失败那次；没跑过就不带>})
   ```

   一条路线一条。`complete` 被拒（如 `WORKFLOW_TASK_ROUTE_BUBBLE_EVIDENCE_REQUIRED`）时按返回里逐条给的出口做，**禁止**删标签、改文字或另开工单绕过，也不要反复重试。
7. **交付报告**：Studio 不改已确认 artifact，将报告写入独立交付记录；普通宿主更新方案页。两种宿主均写进工单 `task_manager(action="insert", entry_type="result")` 并发给开发者，然后 `task_manager(action="complete")`；结单响应里的 `delivery_note` 原样补进报告。本轮记下的已绕过平台问题和功能诉求，此时汇总成一条 `submit_dev_feedback`（`blocking` 按主要情况选 `worked_around` 或 `request`），没有就不提。
8. **阶段评分**（仅 Codex）：交付报告发出后，按 [../design/阶段评分.md](../design/阶段评分.md) 单独发一条「正式上线」评分；G6 阶段文档里的评分还没回时，这条**必须**先列 G6 的三项、再列 G7 的三项，让开发者一起回；它和上一步汇总的问题反馈是两条，**禁止**合并。
9. **开发工作集保留**：上线后开发工作集继续绑定在应用上，**不要**解绑、不要为它重新 `deploy`、不要 `close`。开发版（在线试用）只能连工作集，下次修订改表结构也在这个工作集上改（见 [../reference/数据模板.md](../reference/数据模板.md)「改已上线的模板」）；它只给开发者用，改它不影响使用者各自的实例库。解绑后 `deploy` 会报 `BUSINESS_UI_PREVIEW_DATA_UNBOUND`，`close` 会被 `TEMPLATE_WORKSPACE_IN_USE_BY_DEPLOYMENT` 拒绝，遇到说明走错了，重新 `bind` 回原工作集即可；**禁止**为此 finalize 派生出来的草稿、下线或删除应用。工作区用 `workspace_push` 保存到云端。

## 3. 产出与落盘

交付报告结论先行，每一句「已验证」都能指到证据，至少包含：

| 项 | 内容 |
|---|---|
| 应用 | 名称、上线版本、是否已在目录发布 |
| 部署状态与入口 | 部署状态（`success` 与 `deployment_id`）和怎么打开分开写：目录发布后，开发者在 GoalfyMax → 我的资产 → 智能应用 → 打开，使用者从目录打开；Studio 在线预览仅展示已发布正式版本。不写容器地址 |
| 场景包 | 定版时钉住的版本；已验证的路线与冒泡 `run_id`；豁免的路线与理由 |
| 数据模板 | 模板 ID 与版本 |
| 部署 | `deployment_id`、`source_sha256`、`deployed_scaffold_version`；低于建议线时写「当前 vX 低于建议线 vY，建议下一轮升级」 |
| 真跑 | `project_id` 与结论，或省略的原因 |
| 验收清单 | 通过项数、不适用项、未验证项 |
| 运行说明 | 用户首次打开时按模板建自己的库；无流量实例会缩容，首次访问稍慢 |
| 已知限制 | 未验证项、能力缺口、下一步建议 |

「阶段评分」按 [../design/阶段评分.md](../design/阶段评分.md) 记进本段阶段文档。

只有本模式出口满足才记 G7 `passed`。Studio 写独立交付记录，不修改已确认方案。普通宿主方案页 `status` 改为 `done`，`.pv-summary` 写上线结论；「已验证 / 未验证」与交付报告一致。

## 4. 给开发者看什么

交付报告按实际状态说明「已定版，尚未目录发布」「已发布，正式页面待验证」或「已发布且正式运行已验证」。目录发布后可从 GoalfyMax → 我的资产 → 智能应用打开；Studio 使用在线预览。不附容器地址，不把草稿试用当正式入口；Studio 沿原对话已明确同意的现有 MCP 路线执行，未取得目录发布回读时不宣称正式发布。

交付报告发出之后，另发一条「正式上线」阶段评分（第 2 节第 8 步），不放进交付报告这条消息。

## 5. 出口

- Studio：保存本次明确上线答复与实际 MCP 回执，精确回读同一候选的定版和当前 published release；只有实际正式 ready/操作证据取得后才能报告相应项通过。
- 普通宿主：`resolve` 能取到上线版本，且 `entry_url` 非空；本次必需的目录发布与正式验证已完成。不在本次范围内且不是交付前置的目录发布据实单列，不阻塞结单；未验证项仍如实记录。
- 两种宿主：`task_manager(action="complete")` 成功；交付报告已写工单，Studio 写独立交付记录，普通宿主写方案页。

## 6. 出问题怎么办

Studio 的交付失败与未知按当前 MCP 合同查询原 task/draft/deployment/operation；旧宿主交付记录仅用 studio_read_creation 只读核对。不能套用下表重新部署或补跑来绕过未知记录。已明确的代码/路线缺陷按原授权修复，旧候选的证据不转给新候选，结单豁免也不替代 Studio 发布所需的真实检查。

| 现象 | 先看 | 回到 |
|---|---|---|
| 定版被拒 | [../reference/部署与版本.md](../reference/部署与版本.md) 定版错误码 | G6 或 G5 |
| 结单被拒 | 返回里的路线状态；补一次路线冒泡或真跑，或写豁免 | G4 或 G6 |
| 开发者上线后要改 | [../tasks/修订.md](../tasks/修订.md) | — |
| 要下线、回滚、删除 | [../reference/部署与版本.md](../reference/部署与版本.md)，每一步都要开发者确认 | — |
