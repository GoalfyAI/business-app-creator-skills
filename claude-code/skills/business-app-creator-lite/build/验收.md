# 3.4 验收、预览、上线

验证只有两层：**回放 / 冒泡管改，真跑管收**。改脚本时用 preview + verify + 一次冒泡迭代；只在最后真跑一次。

## 1. verify 出报告

- 每条 TPE：`otpe_manage(action="verify", task_id, tpe_id, run_id=<冒泡 run_id>)` 直到 `verdict=passed`；`blocked` 看 `failed` 与 `items[].detail` 改。
- 应用：`npm run verify` 全绿；上线前 `npm run verify:release`。
- 路线：`scene_package_manage(action="bubble")` 一次到 `success`（见编译规则第 8 步）。

## 2. 真跑一次

用真实样例跑一条完整路线，说清费用与副作用后执行：

1. `manage_goalfymax_project(action="run", task_id, idempotency_key, scenario_package_ids=[<草稿版本物理行 id>], submit_data={…}, business_ui_id=<有应用数据要写时才传>)`。
2. `manage_goalfymax_project(action="wait", project_id)` 等到终态；中途表单或审阅用 `reply`。
3. `get_project_execution_logs(action="workflow_trace", project_id)` 看每步；模型行的输出人眼核一遍（验收清单第 5 条）。
4. 写库的结果去对应的库里查一条（应用数据管理页或 `query_business_app_dataset`）。

失败在同一草稿改，再跑；每次只改一处，不同时改脚本和路线。

## 3. 部署预览给用户看

1. `./scripts/pack.sh` 打包；`business_ui_bundle(action="prepare_upload")` → 客户端 PUT → `complete_upload` → `deploy(source_sha256)` → `status(deployment_id)` 到 `success`。
2. `business_ui_manage(action="get")` 反读入口地址，把预览地址给用户，说明：能操作什么、数据是开发工作集、哪些是模拟数据。
3. 用户提的改动改完重新 deploy；每次部署前 `npm run verify:release`。

## 4. 上线

用户说「可以上线」后：

1. `finalize_asset_version_online(asset_type="scenario_pack", …)` 上线场景包版本。
2. `business_ui_manage(action="finalize", draft_asset_id=…, task_id)` 定版应用。
3. 目录发布由用户在发布管理页操作；告诉用户位置。
4. 交付报告写进工单 `task_manager(action="insert", entry_type="result")` 并发给用户；`task_manager(action="complete")` 结单。

## 5. 出问题怎么办

| 现象 | 先看 |
|---|---|
| verify `static_contract` 失败 | `errors[].where/msg`，多半是 `_output` 形状或事件契约 |
| verify `toolsets_online` / `tpe_online` 失败 | `online_toolsets` / `otpe_manage(action="online")` |
| 冒泡失败步骤 | `steps[].error`；`repeated_error_count>=2` 换策略不重跑 |
| 部署 `status` 失败 | 返回里的构建日志尾部；本地先 `npm run verify:release` |
| 真跑卡 `waiting-input` | 用 `reply` 回表单；用户没答就是正常挂起 |
| 疑似平台问题 | `submit_dev_feedback` 报上去，绕过后继续 |
