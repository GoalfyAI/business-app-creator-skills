# 场景包 Battle 检查契约

创建场景包前，对方案做反方审查时读。

本契约从 Beta `csp_battle_reviewer` 的审查提示词整理而来，用于 CC/Codex 在创建场景包前进行反方审查。它不启动 Max FastAgent，也不替代真实运行。

## 审查原则

1. 职责是找问题，不做礼貌性认可。每个问题必须说明：位置、后果、修改办法。
2. 先用 `list_assets`、`get_asset`、`dataset_read` 核对真实配置，再判断方案；不得只凭方案文字或记忆。
3. 用户不能决定的技术事实由资产证据裁决；业务取舍和高风险动作列为确认项，不替用户决定。
4. 多视角审查时分别给出结论，最后去重合并；不能用多次相同措辞冒充多视角。

## 检查输入

- 用户目标、目标角色与使用场景。
- 拟创建或复用的场景包、编排型 TPE、FA、Toolset、Tool Group、长期数据集和智能应用数据集模板。
- 审查视角，例如业务领域专家、数据治理专家或 Agent 架构专家。
- `list_assets`、`get_asset`、`dataset_read` 返回的真实资产配置。

## 必查问题

### 业务完整性

- 是否解决稳定、可复用的业务问题，而不是固化一次性项目内容。
- 业务里程碑是否覆盖完整主流程、异常路径和最终交付；每个阶段是否有清晰输入、输出和责任方。
- 授权、外部写入、通知、邮件、发布等高风险动作是否设置用户确认和 `ctx.dry_run` 护栏。

### 工具、数据与资产闭包

- 每个里程碑是否有真实工具或 FA 支撑，工具参数与能力是否匹配。
- 所需 Toolset、Tool Group、FA、编排型 TPE、长期数据集是否会实际挂到场景包，智能应用数据集模板是否已挂到 business_ui；不得按“用户可能拥有”推断。
- 数据源名称是否与绑定数据集一致，是否存在引用缺失或从未使用的冗余绑定。
- 不得依赖创建者本地路径、CC/Codex 沙盒或另一个 Max 项目的临时文件。

### 编排型 TPE / custom TPE / FA 选型

- 稳定、重复、无需临场判断的多步流程应优先编排型 TPE；需要上下文隔离和大模型逐轮推理的任务才使用 custom TPE。
- 只有内容判断、归纳、写作等确需大模型的步骤才使用 FA；确定性搜索、取数、转换和发送应直接调用工具。
- 编排型 TPE 必须是有数据流的多步业务路线；只调一个 FA 后直接返回属于空壳，应直接使用该 FA。
- 编排型 TPE 输入必须可由用户表单、上游编排型 TPE，或——仅在场景包配套了智能应用时——智能应用数据集（经 Business_app_fastagent 或 query_business_app_dataset 读取）提供；没有配套智能应用的场景包不得出现读写智能应用数据集的步骤，也不得挂 business_app_dataset 工具集；输出必须是用户或下游真正需要的稳定对象。
- 多条编排型 TPE 只有在依赖顺序固定时才配置 `workflow_orchestration`，不得为展示效果强行造 DAG。

### 鲁棒性与 Skill

- 数据缺失、格式变化、工具失败、外部系统变更时是否有明确失败或降级规则。
- 场景包 Skill 是否包含业务里程碑、权限边界、操作策略和必要系统认知，同时没有数字资产 ID 或第二份 DAG。
- Toolset Skill、FA Prompt 与真实工具是否一致，是否有泛化描述导致 Agent 自由发挥。

## 输出格式

按以下三级输出并写入工单摘要：

1. `关键问题（必须修正）`：会导致失败、错误交付或严重偏差的问题。
2. `改进建议（建议优化）`：不阻断基本功能但会影响稳定性或质量的问题。
3. `确认项（需要业务方判断）`：证据不足或属于业务取舍的问题。

同时记录审查视角和引用的资产 ID。不得声称已完成运行验证。
