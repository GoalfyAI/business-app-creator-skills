# 失败与降级正反例（二）：结果分类、重试与副作用

要区分空结果、部分成功和失败，判断能不能重试，或脚本里有发信、发布、扣费这类非幂等副作用时读；最后有判断清单。

本文分 2 份：[编排示例-失败-必需与可选.md](编排示例-失败-必需与可选.md)、[编排示例-失败-结果分类与副作用.md](编排示例-失败-结果分类与副作用.md)。

## 3. 空结果、部分成功和失败不是一回事

| 情况 | `items` | `degraded` | `warnings` | 整体状态 |
|---|---|---:|---|---|
| 工具成功，确实没有匹配项 | `[]` | `false` | `[]` | success |
| 工具成功，但正式返回声明部分子项失败 | 已成功子项 | `true` | `optional_source_partial` | success |
| 可选工具抛异常 | 可继续交付的数据 | `true` | `optional_source_unavailable` | success |
| 必需工具抛异常 | 不提交业务结果 | 不适用 | 不适用 | failure |

如果工具的正式输出本身提供逐项错误，按正式 Schema 消费，不要把整个步骤误判为完全失败：

```python
async def run(input, ctx):
    result = await tool(
        "demo_search",
        queries=input.get("queries", []),
        _output={
            "type": "object",
            "required": ["items", "errors"],
            "properties": {
                "items": {"type": "array"},
                "errors": {"type": "array"}
            }
        },
        _rationale="批量查询资料并保留工具声明的逐项错误"
    )
    partial = bool(result["errors"])
    return {
        "items": result["items"],
        "degraded": partial,
        "warnings": ["optional_source_partial"] if partial else []
    }
```

这里的 `errors` 必须来自工具正式 `output_schema` 或真实测试证据，不能为配合示例自行猜字段。

所属契约：成功空集是业务数据；部分成功是显式降级；抛异常是步骤失败。

## 4. 可重试与不可重试

当前编排型 TPE 脚本收到的是步骤异常，没有可供脚本可靠判断的结构化 `retryable` 字段。因此不要在脚本里按错误文案猜测，也不要给每个 `tool()` 包通用重试循环。让步骤失败，由 External MCP/项目控制层依据真实结构化错误做恢复决策。

| 错误类型 | 是否可原样重试 | 处理方式 |
|---|---|---|
| 明确标记 `retryable=true` 的超时、连接中断、429、502/503 | 仅当调用幂等或只读 | 有界重试；超过次数后保留真实失败 |
| 参数缺失、type/enum、输入/输出 Schema 不匹配 | 否 | 修改参数、脚本或 Schema 后再测试 |
| 权限、认证、资产不可见 | 否 | 修复授权或资产范围后再测试 |
| `KeyError`、确定性代码错误、错误字段路径 | 否 | 修改代码后再测试 |
| Workspace 路径不可信或文件不存在 | 否 | 修复文件来源或生成步骤后再测试 |
| 外部副作用执行结果不确定 | 否 | 先查幂等键/业务状态，不能盲重放 |

`retryable=true` 只是候选条件，不是自动重试授权；还必须确认操作幂等，并且重试仍在用户允许的副作用范围内。

所属契约：恢复决策同时依赖错误分类、幂等性和副作用授权。

## 5. 非幂等副作用：不要在脚本里盲重试，验证时必须隔离

错误脚本：

```python
async def run(input, ctx):
    sent = False
    for attempt in range(3):
        try:
            await tool(
                "send_email",
                subject=input.get("subject", ""),
                body=input.get("body", ""),
                _text=True,
                _rationale="发送用户确认过的邮件"
            )
            sent = True
            break
        except Exception:
            pass
    return {"sent": sent}
```

实际诊断边界：邮件可能已经发出，只是响应在返回途中丢失。脚本立即重试会发送多封邮件；三次都没有收到确认时又返回 `sent=false`，同样不能代表邮件没有发出。preview 无法仅凭语法证明该工具是否幂等，因此这类错误应由正反例约束，不新增猜测式 validator。

最小修复：

```diff
-    sent = False
-    for attempt in range(3):
-        try:
-            await tool(
-                "send_email",
-                subject=input.get("subject", ""),
-                body=input.get("body", ""),
-                _text=True,
-                _rationale="发送用户确认过的邮件"
-            )
-            sent = True
-            break
-        except Exception:
-            pass
-    return {"sent": sent}
+    if ctx.dry_run:
+        return {
+            "sent": False,
+            "validation_state": "external_side_effect_skipped"
+        }
+    await tool(
+        "send_email",
+        subject=input.get("subject", ""),
+        body=input.get("body", ""),
+        _text=True,
+        _rationale="发送用户确认过的邮件"
+    )
+    return {"sent": True, "validation_state": "executed"}
```

对应的最终 `output_schema` 必须同时声明 `sent:boolean` 和 `validation_state`，后者至少允许 `external_side_effect_skipped/executed`，让冒泡和全真验证返回明确的未执行验证态，而不是伪造已发送。

修复后证据：`ctx.dry_run=true` 时只隔离邮件这一对外副作用，普通工具、文件管路和最终 Schema 仍照常验证；非验证运行发送失败时整条编排型 TPE 明确失败，不会自动重复副作用。若工具提供正式幂等键和状态查询接口，应优先用它们确认业务事实，再决定是否由有权限的调用方重试。

所属契约：邮件、发布、扣费、创建对象等外部副作用默认不可盲重试。

## 判断清单

1. 去掉该步骤后，最终交付是否仍然有独立业务价值？没有则让失败冒泡；
2. 捕获异常时，最终 `output_schema` 是否强制声明 `degraded` 和 `warnings`？
3. 正常空集与工具失败是否能从最终结果中明确区分？
4. 部分成功字段是否来自工具正式 Schema 或真实测试，而不是脚本猜测？
5. 是否避免把原始异常和内部信息写进用户输出？
6. 重试是否同时具备结构化 `retryable` 证据、幂等性和副作用授权？
7. 非幂等动作结果不确定时，是否先查业务状态而不是直接重放？
8. 冒泡和 FA 真起验证时，是否只用 `ctx.dry_run` 隔离明确的对外副作用，并返回满足最终 Schema 的未执行验证态？
