## 7. 智能应用如何承接

本案例包含编排型 TPE，因此把智能应用作为同一制作工单的组成部分展示。实际开发必须从本工单下载的**当前官方模板**开始，并先确认模板与宿主公开了匹配版本的 Business/Runtime、业务交互和 Delivery Review 能力。

### 7.1 页面结构

| 页面状态 | 业务内容 | 不应出现 |
|---|---|---|
| 首次填写 | 门店资料、目标、预算、受众、品牌素材、禁用表达 | TPE ID、工具、节点、脚本 |
| 已受理/运行中 | 当前业务阶段、宿主状态、取消或回到聊天 | “方案已完成”的假成功 |
| Delivery 审阅 | 摘要、风险项、方案文件、接受/询问/修改 | 前端自行推进 DAG |
| 修订填写 | 原交付引用、修改意见 | 覆盖原文件的选项 |
| 失败/阻断 | 宿主错误、可恢复动作、回落聊天 | 猜测字段、静默换路线 |

### 7.2 字段与控件

- `budget_yuan` 使用有最小值的数值控件；
- `audience_preferences` 和 `forbidden_claims` 使用可增删列表，不让用户手写 JSON；
- 品牌素材使用模板 SDK 的文件上传，提交宿主返回的 Workspace 路径；
- 运行状态和结果来自宿主公开能力；提交成功只显示“已受理”；
- “修改”动作按公开 Review 契约开启 `revise_campaign_package` 的新 Runtime，不直接调用内部编排型 TPE。

### 7.3 开发和发布证据

1. 下载当前官方模板并核验归档；
2. 完整读取模板必读说明；
3. 冻结当前场景包、路线和编排型 TPE 的公开契约快照；
4. 实现真实表单、上传、状态、Delivery 和 Review；
5. 删除 Demo，完成类型检查、lint、测试、构建和 mock 主路径；
6. 打包源码，完成上传、部署、状态轮询和反读；
7. 记录源码 SHA256、部署标识、激活地址和剩余盲区。

如果模板只支持单条编排型 TPE `workflow.run`，却没有 2.0 Business/Runtime 能力，本案例界面必须标记 `platform_blocked`，不能选第一条编排型 TPE 冒充整包路线。

## 8. 验收矩阵

| 用例 | 预期 | 最低证据 | 不能声称 |
|---|---|---|---|
| 完整正例输入 | 两节点按 mapping 衔接，形成 Delivery | 两条单体 Preview/bubble、业务路线静态保存、路线 bubble、界面 mock | FastAgent 内容正确、整条路线已全真运行 |
| 缺少预算 | 入口拒绝，不能启动 Runtime | Schema/UI 负例测试 | 系统会自动选择合理预算 |
| 含禁用表达 | `risk_flags` 非空且进入交付 | 经授权全真结果或人工核对 | bubble 桩已验证真实识别能力 |
| 上传素材 | 节点接收 Workspace 路径 | 上传 mock、Schema、文件存在性检查 | URL 或文件名等价于 Workspace 文件 |
| 点击修改 | 原 Delivery 保留，新 Runtime 产生新文件 | 宿主 Runtime/Delivery 日志 | 在原 DAG 内完成循环 |
| 用户接受 | Business 在 Review 后 completed | 真实 Review 事件 | 编排型 TPE `succeeded` 自动等于 Business 完成 |
| 宿主缺 2.0 能力 | 停止界面发布并记录阻断 | 模板 SDK 和宿主 capability | 静态业务路线通过即可直接使用 |

### 8.1 单条编排型 TPE 验收

每条编排型 TPE 分别完成：Preview → create/update 后反读 → bubble 到终态 → 轨迹和语义验收。FA 桩、未触达数组元素、失败分支和副作用继续列为盲区。

### 8.2 业务路线验收

检查两条路线的入口、节点可达性、映射、Workspace 文件格式、业务事件、Delivery 和 Review。Hub 保存成功只能记 `orchestration_static_validated`；每条路线通过真实图控制器的演练 Runtime 后记 `orchestration_bubble_validated`；只有用户授权后的目标 Max 全真项目具备完整 Business、Runtime、TaskPoint、交互、Delivery 和 Review 日志，才能记 `orchestration_runtime_verified`。

### 8.3 智能应用验收

用真实 Schema 的 mock 覆盖输入、上传、提交、运行中、Delivery、修改和失败回落。部署成功后反读激活状态。页面能打开不等于智能应用通过。

### 8.4 全真验证

按需要验收的业务路线做端到端全真运行，不为三条编排型 TPE 分别询问；要不要先问开发者见 [编排型TPE总契约.md](编排型TPE总契约.md) 的全真运行规则。从对应路线的业务表单入口启动，在同一 Business/Runtime 中完成中途表单、Delivery 和 Review。全真运行会真实启动 FastAgent，并可能产生供应商费用；开发者不同意时可以交付已有层级证据，但要记录 `full_validation_skipped`，并列出真实内容、未触达分支和副作用盲区。

## 9. 最终交付应如何表述

达标的交付结论示例：

> 场景包已完成方案生成与修订两条路线的资产组装。三条编排型 TPE 均取得当前版本的 Preview 和单体 bubble 证据，2.0 业务路线已通过静态保存，两条公开路线的图业务路线 bubble 与智能应用部署证据按实际结果列明。端到端全真验证是否完成、FastAgent 内容和外部副作用是否已有证据，按获批业务路线单独列明。

不达标的表述：

> bubble 成功，所以朋友圈广告方案已经有效并且可以直接投放。

后者同时混淆了脚本完成、内容正确、整图运行、界面可用和真实广告发布五个不同证据层级。

## 10. 从案例中带走什么

可以带走：

- 先用正反例冻结业务规则，再拆编排型 TPE；
- 按职责和验证边界拆节点，不按步数机械拆；
- 修改路线通过新 Runtime 保留旧 Delivery，不在 DAG 画回边；
- 智能应用只消费公开运行契约；
- 每层证据只证明自己的范围。

不能带走：

- 本文的门店画像、预算和禁用词；
- `campaign_*` 名称与 `910001~910003` ID；
- 本文 Schema 一定适用于真实工具；
- 两条路线是朋友圈获客的唯一做法；
- 当前环境一定支持 2.0 智能应用；
- bubble 成功等于业务结果正确。
