# 事件契约与文件产物

给 TPE 声明业务事件、或脚本要产出和交付文件、要把一批数据交给 FA 读时读。

## 事件契约

- 每条编排型 TPE 都要声明，空声明 Preview 直接失败；声明了就进 Business Runtime 语义，正式运行经路线（单条 TPE 也建单节点路线）。额外的细分事件只在应用要用时才加。
- 硬门：首个业务动作前发 `stage_started`；每个正常 `return` 前发 `stage_result`；可解释的业务失败发 `stage_failed`。契约至少两条：`stage_started` + `stage_result`。`artifact_ready`、`delivery_ready` 由平台自动发，脚本不声明也不调用。
- 入口函数名、`emit_business_event` 的 `event_type`（`stage_started` / `stage_result` / `stage_failed`）和 `event_key` 都保持字符串字面量。
- `payload_schema.required` 必须含平台字段：`stage_started` 要 `stage_key`、`stage_name`；`stage_result` 要 `stage_key`；`stage_failed` 要 `stage_key`、`error_code`、`message`；`attention_required` 要 `level`、`title`、`message`。`additionalProperties` 必须为 `false`。
- 载荷不放内部 ID、原始工具返回、提示词或未脱敏错误。
- `stage_name` 就是使用者在应用顶部执行状态条上看到的那句话：写成「正在<动作><对象>」，如「正在核验商户资料」「正在生成跟进话术」。「正在处理本次任务」「正在执行」这类泛词让人看不出在做什么。
- 一条 TPE 里有两个以上使用者能分辨的业务步骤（如先核验资料、再生成话术）时，每个步骤开始前各发一次 `stage_started`，各用自己的 `event_key`、`stage_key` 并各自声明契约；同一步骤内部的工具调用不再发，也不为进度条声明 `stage_progress`。
- 契约随 `otpe_manage(action="create"|"update", business_event_contracts=[…])` 一起写，写后 `get_asset(asset_type="tpe")` 反读。

三种模板共用下面的契约形状，只改 `event_key` 与 stage 名：

```json
[
  {"event_type": "stage_started", "event_key": "<stage>_started", "event_version": "1.0.0", "description": "开始<stage>",
   "payload_schema": {"type": "object", "additionalProperties": false, "required": ["stage_key", "stage_name"],
                      "properties": {"stage_key": {"type": "string"}, "stage_name": {"type": "string"}}}},
  {"event_type": "stage_result", "event_key": "<stage>_completed", "event_version": "1.0.0", "description": "<stage>完成",
   "payload_schema": {"type": "object", "additionalProperties": false, "required": ["stage_key", "summary"],
                      "properties": {"stage_key": {"type": "string"}, "summary": {"type": "string"}}}},
  {"event_type": "stage_failed", "event_key": "<stage>_failed", "event_version": "1.0.0", "description": "<stage>失败",
   "payload_schema": {"type": "object", "additionalProperties": false, "required": ["stage_key", "error_code", "message"],
                      "properties": {"stage_key": {"type": "string"}, "error_code": {"type": "string"}, "message": {"type": "string"}}}}
]
```

模板二、三用到了 `stage_failed`，用模板一时删掉第三条契约。一条 TPE 有多个业务步骤时，每个步骤复制一条 `stage_started` 契约，换成该步骤的 `event_key`。

## 文件产物

- 要交付的文件写进 `ctx.output_dir`，在 `output_schema` 声明为 `format: workspace-file-path` 并返回真实路径，路线的交付映射也要引用它；入口素材、上游产物要作为本次附件时先复制进 `ctx.output_dir`。
- 输入素材从 `input` 里声明为文件的字段取，`ctx.process_dir` 用于过程文件，两个目录都自带结尾斜杠；本次新生成且要返回的文件（包括诊断附件）写进 `ctx.output_dir`。过程文件写入成功、路径存在，都不等于它已成为可信输出。
- 节点输出的来源校验接受 `ctx.output_dir` 下的路径、输入文件字段带入的路径，以及工具以裸路径或完整 JSON 返回的路径。`file` 工具的文字回执 `File written successfully: <path>` 不会被解析为可信来源；把 `ctx.process_dir` 文件仅凭该回执返回，会报 `WORKSPACE_PATH_UNTRUSTED`。将实际文件写入或复制到 `ctx.output_dir` 后再返回，不能只改路径字符串。节点来源校验通过后，最终交付仍须满足第一条的目录与映射要求。
- 要给使用者看的列表、正文、结论以业务字段出现在返回值里，不只落文件。不为消除报错给没有用途的路径补文件声明。

## 交给 FA 读的数据走文件

- 由脚本查出一批记录交给 FA 判断的：FA 的 `input_schema` 只收文件路径（`records_path`，或分片清单 `chunks_manifest_path`）和日期范围这类控制字段；输出按 `record_id` 逐条给标签和理由，总数、分类数由脚本统计。不把整批记录作为 FA 的入参字段（如 `records`、`records_json`、`feedback_items`、`items`）或 JSON 字符串传入，也不让 FA 输出总数、分类数。
- 过程文件按行或按文件分块：一条记录一行，或「简短清单 + 分片文件」。单次工具返回上限约 10000 token（中文约 28KB、英文约 50KB），超出部分只给预览；`file` 只能按整行续读，不能从一行中间接着读，所以把数据 `json.dumps` 成几十 KB 的一整行，后半截 FA 读不到，会反复读取直到 `FA_STEP_BUDGET_EXCEEDED`。截断提示出现「本次预览没有完整正文行」就是这种情况，改文件写法，不调高轮次。
- 单个分片控制在单次读取上限以内并留余量：中文约 18KB、英文约 35KB 以内；能一次读完就不要再切小，切得过碎只会增加读取轮次。
- 总条数、最后一条、求和、分类计数这类确定性结果由脚本计算，不让 FA 通读全部数据，也不把 FA 返回的计数当真值。要按语义分类计数时，脚本把记录写成 JSONL 或分片文件、只把路径传给 FA；FA 读文件后按 `record_id` 逐条返回标签（如分类、情绪、是否紧急），脚本再按标签统计。
- FA 只读需要语义判断的部分（如只读标题挑选），需要它通读多个分片时在提示词里要求同一轮并行读取。

## 常见错误

| 错误 | 正确做法 |
|---|---|
| 整批记录作为 FA 参数传入，或用 FA 给的总数、分类数 | 写成一条一行的过程文件只传路径；计数由脚本算 |
| `stage_name` 写「正在执行」，或每个 `tool()` 后都发事件 | 写「正在<动作><对象>」；只在使用者能分辨的业务步骤上发 |
| 要交付的文件只在 `output_schema` 里声明 | 写进 `ctx.output_dir` 并进 `delivery.mapping` |
