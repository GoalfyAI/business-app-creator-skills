# 工具集配置详解（二）：工具集技能与 Skill 文件

写工具集使用指南（`tool_usage_guide`）或给工具集上传 Skill 文件时读。

本文分 2 份：[工具集配置-名称描述与成员.md](工具集配置-名称描述与成员.md)、[工具集配置-技能与Skill文件.md](工具集配置-技能与Skill文件.md)。

## 工具集技能

文本输入框，工具集被加载后注入调用方（SA 或 TA）上下文。相当于这个工具集的使用说明书。

### 配置范式

**核心原则**：
- **不写**单个工具的描述、参数、返回值——每个工具在 MCP 层已自带完整说明，调用方加载工具集后能直接看到
- **要写**工具与工具、工具与 FA 之间的搭配模式——调用顺序、数据传递、路由判断（什么情况直接用工具、什么情况调 FA）
- **不写**业务场景 SOP——那是场景包 Skill 文件（或 TPE 系统提示词）的职责

**最小说明维度 = 搭配模式**（工具间搭配 + 工具与 FA 的协作路由），不是单个工具或 FA 的用法。

> **不能为空**：`create_toolset` 会拒绝空的 tool_usage_guide（`tool_usage_guide` 与 `tool_usage_guide_url` 至少给一个）。即使工具彼此独立、MCP 层描述已自洽且不含 FA，也要写清楚这一点本身——「这些工具互相独立，按各自描述单独调用即可」就是一份合格的搭配说明，调用方读到它才知道不必去猜工具之间有没有顺序依赖。

> **有 TPE 时**：工具集技能的读者可能是 SA（场景包下的工具集）或 TA（TPE 下的工具集）。技能内容应写**调用方视角**的搭配模式，对两种读者都适用。不要在技能中假设读者一定是 SA。

**固定结构模板**：

```markdown
# {工具集名称} - 使用指南

## 一、工具搭配模式

### 模式 1：{名称}（如"告警上下文获取"）
{描述为什么需要这样搭配}
1. 先调 {tool_a} 获取 {什么}（{tool_b} 需要用到）
2. 再调 {tool_b}，将上一步的 {字段} 作为参数传入
3. ...

### 模式 2：{名称}（如"批量操作策略"）
{描述该模块内工具批量使用时的注意事项}
- ...

## 二、FA 速查（如有 FA）

### {fa_name}
- 用途：{一句话，调用方视角}
- 何时使用：{什么情况下应该调这个 FA 而不是直接用工具}
- 输入：{关键参数概述}
- 输出：{返回什么结构}
- 调用方式：同步/异步

## 三、常见错误与处理

| 错误现象 | 原因 | 处理方法 |
| --- | --- | --- |
| ... | ... | ... |

## Skill 文件指南（如有 Skill 文件）
- {文件名}：{内容}，{阅读时机}
```

### 合格示例

**监控告警工具集 - 使用指南**

```markdown
# 监控告警工具集 - 使用指南

## 一、工具搭配模式

### 告警上下文获取
收到告警后，不要直接处理，先建立上下文。
1. 调 `get_alert_detail` 获取告警详情（触发指标、阈值、持续时间）
2. 调 `get_server_status` 获取告警服务器的当前状态（CPU/内存/磁盘/网络）
3. 调 `get_dependency_map` 获取该服务的上下游依赖，判断影响范围

### 批量告警聚合
短时间内多个告警可能是同一根因。
- 先调 `list_active_alerts` 获取当前所有活跃告警
- 按服务和时间窗口聚合后再处理，避免逐条重复排查

### 告警确认 + 关闭
确认处理完成后才能关闭告警。
1. 调 `acknowledge_alert` 标记为"处理中"（防止重复派发）
2. 执行修复操作
3. 调 `verify_metric` 确认指标恢复正常
4. 调 `resolve_alert` 关闭告警并填写处理说明

## 二、FA 速查

### 故障根因分析 Agent
- 用途：分析多维度监控数据，定位故障根因
- 何时使用：告警涉及多个关联服务、单看某个指标无法判断根因时
- 输入：alert_id + 关联服务列表
- 输出：根因分析报告（可能原因排序、证据链、建议修复方案）
- 调用方式：同步

## 三、常见错误与处理

| 错误现象 | 原因 | 处理方法 |
| --- | --- | --- |
| 关闭告警失败 "alert not acknowledged" | 未先确认告警 | 先调 acknowledge_alert 再关闭 |
| get_server_status 超时 | 目标服务器可能宕机 | 检查网络连通性，尝试通过跳板机访问 |
```

### 可以写 vs 不可以写

| 可以写 | 不可以写 |
| --- | --- |
| 关闭告警前必须先调 `verify_metric` 确认指标恢复正常（多工具搭配） | ~~`get_alert_detail` 接受 alert_id 参数，返回告警详情~~（单工具描述，MCP 层已有） |
| 批量操作每次最多 20 个（搭配层面的约束） | ~~`acknowledge_alert` 用于确认告警~~（单工具用途，MCP 层已有） |
| 故障根因分析 Agent：多服务关联故障时使用（FA 速查） | ~~P1 告警处理流程：先确认 → 排查根因 → 修复 → 复盘...~~（业务场景 SOP，属于场景 Skill 文件） |

### 诊断要点

- 工具集技能是否为空：tool_usage_guide 一律不能为空（服务端硬校验）。工具需要搭配使用时写清顺序、数据传递与路由；工具彼此独立时也要写明「互相独立、单独调用即可」，而不是留空
- 是否包含了单个工具的描述/参数/返回值（不应有，MCP 层已有）
- 是否包含了业务场景 SOP（不应有，属于场景 Skill 文件）
- 是否写了搭配模式——工具间搭配 + 工具与 FA 的协作路由（有搭配需求时应有）
- 如有 FA，是否有 FA 速查板块（应有，且只写调用方视角信息）
- FA 速查是否写了 FA 内部执行逻辑（不应有）
- 常见错误是否是工具搭配层面的（而非单个工具的使用错误）

## Skill 文件

上传知识文件，工具集加载后调用方（SA 或 TA）可按需读取文件内容。

### 配置范式

**一般情况下不需要。** 如果工具集技能保持精简就能覆盖全部搭配模式，Skill 文件就不需要。

以下情况考虑使用 Skill 文件：

| 情况 | 是否需要 | 原因 |
| --- | --- | --- |
| 搭配模式只有几条 | 不需要 | 直接写在技能文本里 |
| 某个工具有复杂的分页/重试/批量策略，太长写不下 | **需要** | 内容长且跟着工具走 |
| 错误码对照表很长（几十条以上） | **需要** | 太长不适合注入上下文，SA 遇到错误时按需读取 |
| 搭配模式数量多、按情境差异大 | **需要** | 高频搭配留技能文本，低频/复杂变体移到 Skill 文件按需读取 |
| 大量参数值参考表（枚举值对照、行业代码、地区代码等） | **需要** | SA 填参数时按需查阅，始终注入上下文太浪费 |
| 技能文本越写越长，超过合理长度 | **需要** | 高频内容留技能文本，低频参考内容移到 Skill 文件 |
| 领域知识（如平台规则、业务政策） | **不需要** | 放场景包知识 Skill 文件（不绑定工具集） |

**核心区分**：
- 工具集技能 = 高频使用指引（短、精），加载时自动注入上下文
- Skill 文件 = 低频详细参考资料（长、全），SA 需要时主动读取

> 如果有 Skill 文件，在技能文本末尾加 Skill 文件指南，告诉 SA 有什么文件、什么时候读。

### 诊断要点

- 技能文本是否过长（如果超过 500 字且包含低频参考内容，应拆到 Skill 文件）
- Skill 文件放的是否跟着工具集走的内容（如果是领域知识，应放场景包知识文件）
- 如果有 Skill 文件，技能文本末尾是否有 Skill 文件指南
