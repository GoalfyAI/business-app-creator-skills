# ⑤ 收尾

应用在 ④ 已经上线，这一段把账算清、结果写下、工作区存好、工单结掉。全部通过或只有未测时你直接做完，开发者不用回话；发不发布由他在发布管理页定，这一段不请他发布，也不等发布，验证已在 ④ 做完。

这一段最常见的错是**替开发者接受了没通过的条目**：有没通过就结单，或没等他表态就写豁免。结单后工单不能再写，豁免又要他知情，错了就成了他不知情的放行。其次是上线结果里漏掉没验证的条目，开发者以为全都验过了，照此发布后问题落到使用者身上。规矩以入口 `agenticapp-creator` 为准。

## 开始前确认

- ④ 交了棒，报告已发出。接续时：阶段文档 G6 里没有 ④ 的验收报告的，算 ④ 没验收，先加载 `agenticapp-stage-4-acceptance` 验收。G6 里已有的结论照旧保留，不重测。
- `business_ui_manage(action="get")` 看 `role`：`owner` 照本段做；`editor` 多一步提请，见第 2 步；`viewer` 不进 ⑤。

## 按这个顺序做

1. **定走哪一支**。这一步决定结不结单：

   | 情况 | 怎么走 |
   |---|---|
   | 全部通过或只有未测（「好不好你说了算」的算在内，实际结果已附在报告里），每条路线都有证据 | 直接收尾，从第 2 步做到结单，不等回话 |
   | 有没通过且改不了的条目（平台故障、外部数据源、要开发者授权或付费，或 3 轮仍不过），或路线最近一次失败、没法验证 | 工单开着，按下面「等他选」做 |
   | 他说过这版先别上线或先别放 | 工单开着，先保存到云端（第 7 步）再结束回复，等他改口，改口后按 ④「按反馈改」做。先别放的，结束回复时发 [assets/上线结果.md](assets/上线结果.md)「交接消息」里那一支 |
   | 上线或再部署被平台挡住，按 `agenticapp-tool-deploy` 报错表处理不了 | 工单开着，先保存到云端，发「卡住了」，报平台问题。不另开工单绕过，开发者可以等 |

2. **提请**。`editor` 报告交出后按 `agenticapp-role-collab`「提请属主上线」直接提请，不用协作者再说一句。做成：`request_finalize` 成功。`owner` 跳过这一步。
3. **结单门**：按 `agenticapp-tool-deploy`「结单」核每条路线：最近一次到终态的运行通过（路线冒泡和 ④ 的 `workspace` 实际跑都算；读写应用库的路线只认实际跑）。做成：每条路线有通过的 `run_id` 或 `project_id`，或有开发者接受后写的 `route_verification_waived` checkpoint（读写应用库的路线不能用它）。
4. **算总花费，汇总平台问题**：对工单里记下的每个冒泡、实际跑重新读一次 `cost_credits` 再相加：旧应用按项目编号去重读项目的，新 SDK 应用按执行编号读本次执行的；重读不到的用当时记下的读数，当时也没读到的不算 0；合计按入口 [提问与交接.md](../agenticapp-creator/references/提问与交接.md)「交接消息」的写法写「至少 N」、不含的来源和有几次没读到，**禁止**用隐藏项目的累计代替（口径见入口 [平台对象与用词.md](../agenticapp-creator/references/平台对象与用词.md)「积分」）。汇总开发期累计，写出「其中验证 N、失败重跑 N」（分法见入口「积分」），和 ① 的上限、② 的预计比。读不到的花费和本轮绕过的平台问题、功能诉求汇总成一条提交（入口「报错和平台问题」），编号写进上线结果；没有就不提。
5. **写上线结果**：照 [assets/上线结果.md](assets/上线结果.md) 写，`task_manager(action="insert", entry_type="result")` 写进工单，同时写进交付物。④ 有「未测」条目时单列。
6. **写阶段记录 G7**：`business_ui_stage` 写 G7，`next_stage` 填 `closeout`；阶段标记和方案页同一步按「记下来」改好。
7. **保存到云端**：按 `agenticapp-tool-workspace` 的「云端保存与换机」用 `workspace_push` 保存，成功后把回执记进工单。没拿到成功回执不结单，也不说「存好了」。开发工作集上线后继续绑定在应用上。
8. **结单**：按 `agenticapp-tool-deploy`「结单」调 `task_manager(action="complete")`。发布不在结单条件里。
9. **发出**：上线结果连同交接消息发给开发者，开头「【⑤ 收尾 → 已完成】」，「要你做的」照模板写。

## 等他选

有没通过的条目或路线失败时，这一版保持为他的正式版，不回滚、不下线，不请他发布。

1. 先做第 7 步保存到云端，再问：他可能一直不回话，工作区要先存好。
2. 发一道选择题，开头「【⑤ 收尾 → 等你确认】」：只有继续改 / 接受两项，逐条写清原因和发布后使用者会遇到什么。这道题要他说出选哪个，不用「回是」；「接受」「不改了」「这条不管了」都算选了接受；回得含糊（入口「开发者确认什么」的清单）就再问一次，不算接受，接受了结单后就撤不回。「未测」的不出这道题。协作者走这一支时不提请，告诉他原因，由他决定继续改还是接受后再提请。
3. 他选继续改：先把他的原话和要改的条目记进阶段文档 G6，再回 `agenticapp-stage-4-acceptance`「按反馈改」，改完回到本段第 1 步。
4. 他选接受：这才算知情。记「没通过，开发者选了接受」，路线失败或没法验证的按 `agenticapp-tool-deploy`「结单」写豁免，再从第 2 步做到结单。读写应用库的路线没实际跑通的不写豁免、不结单：照常写上线结果，写明这条路线还没在真实环境跑过、等什么解决后补跑，保存到云端后结束回复，工单开着；能跑时实际跑通再结单。
5. 他不回话：工单一直开着，不写豁免。他回来时读阶段文档接着处理。

## 这一段要做对的判断

| 判断什么 | 依据 | 判错的表现 |
|---|---|---|
| 走哪一支 | 报告里有没有「没通过」、路线最近一次运行的结果、他说过的「先别上线」「先别放」 | 有没通过就结单；全部通过时还等他回话 |
| 只在开发工作集里的设定有没有搬走 | ④ 的交报告前自查；使用者从空库开始，看不到工作集里的数据 | 使用者打开是空的、缺配置 |
| 没验证的和风险有没有如实列出 | ④ 的「未测」条目、开发者接受的没通过条目、能力缺口 | 上线结果里不提未测项，开发者以为全都验过了 |
| 开发者知不知道下一步 | 发布要准备的三样材料、「你可以做的事」 | 开发者不知道接下来该做什么；不发布，正式入口和到点自动运行他自己也用不上 |

## 你可能会这么想 → 实际

| 想法 | 实际 |
|---|---|
| 上线后请他去发布一下，再看看正式入口 | 不请他发布、不等发布；正式入口要发布后才能看，写进「你可以做的事」。他要你带着发布：只说去发布管理页发布、要填的材料已备好；页面上的按钮和弹窗你没见过就说没见过 |
| 他说「先发布再结单」或要你在正式版里跑一次 | 告诉他发布由他决定，验证已在 ④ 做完，照常结单；也不提议发布后再在正式版里跑 |
| 未测的在 ④ 报告里说过了，上线结果不用再写 | 单列，写清没确认过什么；不写成请他去看 |

## 记下来

- **工单**：上线结果（`entry_type="result"`）；`workspace_push` 回执；`complete` 成功。
- **阶段文档 G7**：发给开发者的上线结果消息原文（含「你可以做的事」「发布会怎样」），不写「见交接消息」；以及模板里「给后续 Agent 的部分」。
- **交付物**：方案页 `status` 改为 `done`，`.pv-summary` 写上线结论，`.pv-you` 写「你可以做的事」，`.pv-meta` 写开发期累计花费；「已验证 / 未验证」与上线结果一致，「未测」的留在「未验证」；等他选时 `status` 为 `waiting`，`.pv-you` 写这道选择题。Studio 宿主下上线结果写进开发文档「验收报告」最后一节，按 `agenticapp-host-studio`「验收报告」保存新的一版；保存或登记结果未知时只查原操作结果，不重新写入。
- **阶段标记**：`workspace.json` 的 G7 标 `passed`；有没通过时 G6 的标记（`workspace.json` 和 G6 文档一起）留 `in_progress`，他选接受后和 G7 一起标 `passed`；阶段记录 G7 `next_stage="closeout"`。

## 结束

全部满足，这张工单就结束了：

- 上线的是最新代码部署成功、④ 验收过的那一版：`resolve` 能取到上线版本且 `entry_url` 非空（协作者为 `request_finalize` 成功）；
- 上线结果照模板写全，有「未测」条目时单列了；
- `workspace_push` 成功，工作区已存到云端；
- G7 阶段记录在 `complete` 之前写了；
- `task_manager(action="complete")` 成功，上线结果已写入工单与交付物。

结单后开发者说要改什么，Agent 自动接上，他不用换入口：要改的加载 `agenticapp-task-revise`（新需求从 ① 走），只是问问题就只回答，查原因的加载 `agenticapp-task-diagnose`。

## 出问题

| 现象 | 处理 |
|---|---|
| 结单被拒 | `agenticapp-tool-deploy`「常见错误」；按「结单」补运行证据，或按「等他选」处理；源码问题回 ④「按反馈改」 |
| `BUSINESS_UI_FINALIZE_OWNER_ONLY`、`PERSONAL_VERSION_STALE_SOURCE` 或提请被拒 | `agenticapp-role-collab` 的协作报错；基线过期先合并 |
| `workspace_push` 两次都失败 | 按 `agenticapp-tool-workspace`「云端保存与换机」处理；不结单 |
| 开发者说发布被拒，把报错告诉你 | `agenticapp-tool-deploy` 报错表「开发者发布时」；要改的按 `agenticapp-task-revise` 修好、重新放好并上线，他再发布 |
| 开发者说发布被拒：新 SDK 版本不在灰度名单 | 把原文告诉他；不为了能发布改回旧应用 |
| 开发者说发布被拒：有运行中的执行 | 等执行结束，或由他决定取消 |
| 要下线、回滚、删除 | `agenticapp-tool-deploy` 的「版本操作、下线与删除」，每一步都要开发者确认 |
