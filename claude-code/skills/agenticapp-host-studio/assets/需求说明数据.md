# 需求说明（PRD）：数据说明与完整样例

写 `docs/studio/prd/data.json` 时照这里写，生成用 `build_studio_doc.mjs prd`。**写什么**按 `agenticapp-stage-1-requirements` 的 [PRD 模板](../../agenticapp-stage-1-requirements/assets/PRD.md)和[谁来做](../../agenticapp-stage-1-requirements/references/谁来做.md)，这里只说放进哪个字段。

页面只有两块：开头四行概览 → 一张完整业务流程图（点节点看输入、输出、重要信息）。花多少、副作用、外部数据、要他提供的、界面都在方案里，选择题在聊天里用表单问，都不写进来。

## 字段

| 字段 | 必填 | 写什么 |
|---|---|---|
| `app`、`version`、`updated`、`changes` | 是 | 应用名；整数版本号，每保存一版加一；实际时间 `2026-11-05 10:40`；第 2 版起写这一版改了什么 |
| `overview.audience / problem / goal / approach` | 是 | 服务对象、业务问题、建设目标、设计思路，**各一行**（≤60 字） |
| `phases[]` | 是 | 业务环节，一个刚需一个环节，按使用顺序排 |
| `phases[].title` | 是 | 环节名，用业务话 |
| `phases[].verified / evidence` | 是 | 核实结论四选一：`已试过，能做` `能做` `要新做，没试过` `做不到，见替代`；依据写真调、实测拿到的，一句话 |
| `phases[].nodes[]` | 是 | 每一步：`title`、`by`（`user` 使用者 / `app` 应用自动处理 / `ai` AI）、`input`、`output`、`rule`（重要信息）、`fail`（做不成时，可选）；`ai` 的还要写 `tier`（档位的说法）和 `cost`（每次约多少积分） |
| `loops[]` | 否 | 返回或复用的线：`from`、`to` 写节点名（一字不差），`label` 一句话 |

`rule` 里写什么按 PRD 模板「业务流程图」：环节最后一步写这样算对、这样不行、怎样算做成；保存那一步写存什么、谁能改；被替代那一步写替代做法和少了什么；按默认定下的原处标「按默认」。

## 完整样例

```json
{
  "app": "库存预警",
  "version": 2,
  "updated": "2026-11-05 10:40",
  "changes": ["「快过期」从 3 天改成 2 天（你在第 1 版批注里改的）"],
  "overview": {
    "audience": "一家餐厅的厨师长，每天开店前看一眼。",
    "problem": "食材快过期、快用完全靠记，经常到用时才发现没了。",
    "goal": "每天 7 点前给出一份清单：哪些快过期、哪些该补货。",
    "approach": "录入食材和批次，应用每天按规则算清单，厨师长打开就能看。"
  },
  "phases": [
    {
      "title": "录入食材",
      "verified": "已试过，能做",
      "evidence": "录入、修改、删除在开发库里都试过。",
      "nodes": [
        {"title": "录入食材和批次", "by": "user", "input": "食材名、单位、安全库存；批次的数量、进货日、保质天数。", "output": "一条待保存的批次。", "rule": "同名食材不能重复建；数量不能为负。"},
        {"title": "校验并保存", "by": "app", "input": "录入的批次。", "output": "批次表新增一行，到期日自动算好（五花肉 10 斤，11-03 进货，保质 5 天 → 11-08）。",
         "rule": "到期日 = 进货日 + 保质天数，改保质天数后跟着变。存进批次表（食材、数量、进货日、保质天数、到期日），厨师长写、能改，到期日由应用算。怎样算做成：录一个批次后，在食材页能看到它和算好的到期日。", "fail": "校验不过时原处提示哪一项不对，什么都不保存。"}
      ]
    },
    {
      "title": "每天出清单",
      "verified": "已试过，能做",
      "evidence": "用测试数据跑过 4 次，结果和手算一致，每次 0 积分。",
      "nodes": [
        {"title": "到点开始", "by": "app", "input": "每天 7:00。", "output": "开始算今天的清单。", "rule": "一天只出一份，重复触发只更新这一份。"},
        {"title": "按规则算清单", "by": "app", "input": "全部食材和还没用完的批次。", "output": "快过期 1 项、该补货 2 项、缺货 1 项（11-05 测试数据实算）。",
         "rule": "2 天内到期的进「快过期」（按默认），低于安全库存的进「该补货」；已用完的批次不算。存进清单表（日期、三组数字），应用写，不能改。怎样算做成：到 7 点清单自动出来，数字和手算一致。", "fail": "算到一半出错时这一天标「没算完」，下次到点重算。"}
      ]
    },
    {
      "title": "看清单",
      "verified": "能做",
      "evidence": "平台页面能读清单表。",
      "nodes": [
        {"title": "打开首页看清单", "by": "user", "input": "今天的清单。", "output": "首页先看到三个数字，下面按供应商分组列出（预期）。", "rule": "清单没出来时提示「今天的清单 7 点后出来」，不把旧的当今天的。怎样算做成：打开首页能看到今天的清单。"}
      ]
    }
  ],
  "loops": [{"from": "打开首页看清单", "to": "录入食材和批次", "label": "补货后再录入"}]
}
```

## 容易写错的

- 一个环节塞了十几个节点：节点是使用者能看懂的一步（「校验并保存」），不是函数调用；一个环节一般 2–5 个。
- `by` 按实际谁做：要模型判断的才是 `ai`，规则能算的是 `app`；`ai` 节点不写 `tier`、`cost` 脚本会拦下。
- 概述写成一段话：四项各一行，细节放进节点。
- `verified` 写「能做」却没有 `evidence`：依据写真调、实测拿到的东西，没查过就是「要新做，没试过」。
- 照旧写 `users`、`records`、`cost`、`side_effects` 这些：脚本会拦，并告诉你改写到哪。
