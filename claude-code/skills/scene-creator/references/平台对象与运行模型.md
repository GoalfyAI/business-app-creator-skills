# 平台对象与运行模型

平台对象（项目、四种执行形态与运行时默认能力）、一次运行的模型、渲染语义——本文是这三类知识的**正本**，各阶段文件只引用不复述。场景包的组成与资产树在路由器 `SKILL.md` §7.1，版本机制在 [场景包版本体系与发布逻辑](场景包版本体系与发布逻辑.md)。

## 一、项目：一次运行的容器

**项目**是场景包的一次运行实例的容器——最终用户每次要"跑一遍"，平台就创建（或复用）一个项目，把这次运行的对话、任务点、Runtime、交付物和日志都装在里面。制作侧要记住四件事：

- **怎么被创建**：由入口创建——聊天启动、业务应用的发起表单（新建 = 提交时建项目；复用 = 用户在下拉框选中已有项目，见 app-creator 约束 3）、制作期的全真验证（`manage_goalfymax_project(run)`）。**运行实例标识全部由服务端生成**，任何调用方不得传入（`stages/S4-验证与修正.md` 3.2）；
- **钉住包版本**：项目挂载的是场景包的**具体物理行**；包上线新版本后，已运行的项目继续跑旧版本、不受影响（版本体系 reference 第 1 节）；
- **数据从它进入运行**：业务应用数据集经项目绑定（`m_project.dataset_ids`）对项目内的沙箱可见；应用发起的项目带业务应用标识，`ds-cli` 走写通道（`stages/S3-资产制作.md` 2.4）；
- **诊断以它为单位**：真实运行的日志、产物、问题单都按项目标识读取（`get_project_execution_logs`）；同一实例内的轮询、追问、日志读取复用同一项目标识，不为查状态新建项目。

## 二、执行形态与运行时默认能力（正本）



### 2.1 运行时自带的默认能力

普通任务点和 Workflow **自动具备**以下三项能力，它们不属于任何工具集，也**不需要**挂载：

| 能力 | 用途 |
|---|---|
| 文件读写 | 读写工作区文件 |
| 命令执行 | 在沙盒中执行命令 |
| 邮件发送 | 把工作区产物发到最终用户明确提供的外部邮箱 |

设计任务点或 Workflow 时**直接当作已有能力使用**。**禁止**把它们当成工具缺口，也**禁止**在工具集里重复创建——用 `list_assets` 搜不到它们是正常的。

注意 FastAgent **不自带**这三项。某个 FastAgent 自己需要用，就得在它的工具配置里单独给。

### 2.2 四种执行形态

四种形态**不在同一层**，不是简单二选一。先弄清每种**是什么、由什么构成、能力边界在哪**，再谈怎么选。

#### SystemAgent 直接执行

运行时与最终用户对话的那个 Agent 自己调工具完成，**不产生任何资产**。要做的只是在 `apc_skill` 里写清什么条件下做什么、用哪些能力。

调用的指令和返回结果都占用主对话上下文，因此只适合次数确定、指令量小的动作。

#### FastAgent

一个**可以被当作工具调用的完整执行单元**：拿到一个业务环节的输入，自己调用挂载的工具（搜索、读取、取数、试错、写文件）多轮做完，产出该环节的交付。它有原子性——**一个环节一个 FastAgent，内部多轮工具调用是常态**。构成：

| 组成 | 说明 |
|---|---|
| 提示词 | 角色、执行策略、输出要求，启动时始终注入 |
| 输入定义 | 调用方传参的契约，顶层必须是对象结构 |
| 可用工具或工具组 | 直接配置，**不经过**工具集；这是它能独立干完一个环节的前提——该环节要用的工具都挂给它 |
| 模型与最大轮次 | 见下方要求 |
| Skill 文件（可选） | 按需读取的大段知识 |

关键边界：

- **每次调用都是全新的隔离会话**，读不到调用方的历史，也读不到其他 FastAgent 的结果。调用时**必须**把必要背景一并传入
- **不能**与最终用户交互。一次输入、执行到完成、一次产出
- **不自带**文件、命令、邮件能力（见 2.1），自身需要时**必须**单独配置
- 适合**需要大模型判断、且判断与工具调用交织**的完整环节：边搜边筛、读完再决定读什么、试错式取数、按规范产出并落文件——只要不需要中途问最终用户，一个 FastAgent 就应该把整个环节做完
- **粒度判据**：拆分 FastAgent 的唯一理由是**职责边界不同**（不同领域知识、不同产出契约、需要独立复用），**不是步骤不同**。为每个判断点建一个 FastAgent、或把一个环节按“角色”拆成几个，都是误用

输入定义的硬性要求：

- 顶层**必须**是对象结构
- 每个字段**必须**声明类型和足够详细的描述，让调用方能据此确定传什么值
- **禁止**空对象，**禁止**只声明类型而没有字段，**禁止**只有一两个字的描述
- 建议覆盖四类内容：本次任务的具体描述、期望交付物形态、上下文约束，以及该 FastAgent 领域内的业务参数

最大轮次的取值：50 轮是合适的上限——足够一个环节内的探查、多轮工具调用与纠错重试；设成 100 这类过高值只会让它在出错时反复重试而不是及时返回失败。

#### 普通任务点

派发给 TaskAgent 执行的**任务模板**，是 TPE 的一种类型（见路由器 §7.1）。构成：

| 组成 | 说明 |
|---|---|
| 提示词模板 | TaskAgent 的角色、行为准则、执行策略、领域知识 |
| 输入要求 | 派发时的输入格式，明确必填与选填 |
| 输出格式 | 输出结构，要能被上游解析 |
| 关联工具集 | 执行该任务类型时可用的能力 |
| Skill 文件（可选） | 按需读取的大段知识 |

关键边界：

- 运行在**独立上下文**里，不占用主对话
- **执行步骤不预设**，由大模型临场决定怎么走
- **可以**在运行中暂停、向最终用户补充提问、拿到答复后继续——这是它和 Workflow、FastAgent 最本质的区别
- **自带**文件、命令、邮件能力

#### Workflow

一段**确定性执行脚本**，也是 TPE 的一种类型（见路由器 §7.1）。构成：

| 组成 | 说明 |
|---|---|
| 脚本 | 按固定步骤执行，自己**不做推理** |
| 根对象输入定义 | 也用于渲染最终用户填参的入口表单 |
| 根对象输出定义 | 脚本最终必须直接返回符合它的对象 |
| 预加载工具集清单 | 脚本里用到的每个工具和 FastAgent **必须**在此声明 |
| 业务事件契约（按需） | 脚本需要被 Business Runtime 或业务应用观察时，在运行开始、正常结束、失败和最终交付等业务节点发布的公开事件声明 |
| 辅助文件（可选） | 脚本引用的模板、静态数据、子脚本 |

关键边界：

- 需要大模型的**环节**，在脚本里**调用 FastAgent**——Workflow 不是 FastAgent 的替代，而是环节之间的**编排器**。脚本里的 `tool()` 用在三处：FastAgent 之前的确定性准备（取表单值、取数据集固定字段）、FastAgent 之间的汇合与扇出、FastAgent 之后的固定收口（落产物目录、发事件、回写）。**“要看着上一步结果决定下一步查什么”的检索、读取、试错，属于 FastAgent 内部，不要在脚本里写成 tool → FastAgent → tool → FastAgent 的长链**
- 单条 Workflow 执行中**不能**与最终用户交互。需要中途补参或人工检查时，用业务路线编排的节点级机制（见 `stages/S3-资产制作.md` 第 4 节）；即使路线只有一个执行节点，也不能把交互写进 Workflow 脚本
- 依赖**必须**预先声明并上线，漏一个该步骤运行期就解析不到（见 `stages/S3-资产制作.md` 1.2 的两道上线检查）
- 产物目录与过程目录有明确约定，正式交付物放产物目录
- `output_schema` 描述脚本**正常返回**的业务结果：成功产物必须返回真实文件路径；技术失败让异常冒泡，禁止用空字符串或虚构路径凑成功对象
- “合法无产物”只有在没有产物本身是合法业务结果时才能正常返回：用明确状态区分，并省略不存在的文件字段；成功分支仍必须条件化要求其真实产物
- 业务事件不是所有 Workflow 的无条件必配项；未声明业务事件且脚本未调用 `emit_business_event` 的 Workflow 可以按当前直接派发契约运行
- Workflow 一旦声明业务事件或调用 `emit_business_event`，就进入 Business Runtime 语义：脚本必须覆盖运行开始和全部可解释终态分支；`artifact_ready` 与 `delivery_ready` 由 Runtime 在 Artifact 登记、Delivery 冻结后自动发布，脚本不得声明或调用。正式运行必须通过业务路线，单条 Workflow 也要建立单节点路线。事件设计见 `stages/S3-资产制作.md` 第 5 节
- 制作期可以做运行验证并取得终态轨迹（见 `stages/S3-资产制作.md` 4.3）
- **自带**文件、命令、邮件能力

脚本原语、输入输出定义的具体写法、文件路径规则、失败与降级处理，**必须**从 `get_diagnosis_doc` 读当前契约（见 `stages/S3-资产制作.md` 4.1）。

四种形态的选型决策（对照表、决策顺序、信号清单）在 `stages/S3-资产制作.md` 第 3 节；场景包的组成与资产树在路由器 `SKILL.md` §7.1。

## 三、运行模型

一次场景包运行中各角色的关系与时序。理解它才能设计出边界正确的资产，也才能判断哪些环节值得呈现给最终用户。

### 3.1 角色关系

```text
最终用户
  │ 聊天输入 / 业务应用表单
  ▼
SystemAgent（主对话，每轮可见 apc_skill）
  │ 按任务点描述路由，派发 TPE
  ├─▶ TaskAgent（普通任务点：独立上下文，临场决定步骤，可中途向用户提问）
  │      └─ 调工具 / 调 FastAgent
  ├─▶ Workflow（确定性脚本：按固定步骤执行）
  │      ├─ tool(...)          确定性工具调用
  │      └─ FastAgent(...)     脚本内需要大模型的完整环节（自带工具多轮执行；每次全新隔离会话）
  └─（挂了编排时）业务路线 Runtime：按依赖图确定性派发各节点 Workflow，
        处理入口表单、运行中交互、Agent 介入、Delivery 冻结与最终审阅
```

- **SystemAgent** 是全场唯一持续面对最终用户的 Agent；任务点与 Workflow 都在独立上下文运行，结果回流后由它衔接对话。
- **业务路线 Runtime** 是确定性控制器：路线一旦启动，节点派发、字段映射、交付冻结都不经过大模型；只有声明的 Agent 介入点和最终审阅会把控制权交回 Agent 或最终用户。
- **FastAgent 没有记忆**：每次调用都是隔离会话，脚本或调用方必须把全部必要背景随参数传入。

### 3.2 一次带编排的运行时序

```text
入口（用户提交入口表单 / 聊天启动路线）
  → Runtime 派发首批节点 Workflow
  → 节点执行：stage_started → 工具/FastAgent 步骤 → stage_result（或 stage_failed）
  → 产生文件交付物：脚本写入产物目录并按 output_schema 返回路径
  → 全部节点达成 → Delivery mapping 求值（文件路径字段的求值结果即 Artifact 登记来源）
      → 文件登记 → artifact_ready（平台自动，逐份） → 冻结 → delivery_ready（平台自动）
  → 最终审阅（user_gate + ask / user_gate + result / agent_gate，见 S1-4.2）
  → 按审阅动作：完成业务 / 结构化失败 / 开启新路线（新 Runtime，旧交付保留）
```

文件路径字段***必须同时***出现在 `output_schema` 与最终节点 `delivery.mapping` 中——只声明并返回、未进入 mapping 的文件不会被登记为 Artifact；mapping 引用的缺失字段自动跳过，必填由 `output_schema` 的 `required` 裁决（规则详见 `stages/S3-资产制作.md` 7.1）。

事件、表单握手与 Delivery Review 各自的契约细节见 `stages/S3-资产制作.md` 第 5 节；三种审阅形态的语义见 `stages/S1-业务设计.md` 4.2。

### 3.3 入口并存

已发布路线在业务应用与聊天两个入口天然并存，走哪个入口由最终用户自选：业务应用提交经 Runtime 运行（有业务事件、有界面状态）；聊天中直接派发已挂载的 Workflow 时业务事件自动降级不生效（无业务应用）。这是平台运行期行为，不是设计决策——制作侧不设计也不引导入口选择（见 `stages/S3-资产制作.md` 5.2）。

### 3.4 失败之后会发生什么（制作侧可依赖的事实）

- **失败是终态，不是暂停**：脚本可解释的业务失败以 `stage_failed` 收口，路线级失败以结构化 `fail_business` 结束 Business；技术异常冒泡后节点失败、路线中断。Runtime 不会替脚本重试。
- **再来一次 = 新的运行实例**：修订、重做、改路线都是"冻结当前交付、开启新 Runtime"（`stages/S3-资产制作.md` 4.2、`stages/S1-业务设计.md` 4.2），不在同一实例里回边续跑。制作侧不为"断点续跑"设计任何步骤；平台若提供恢复能力，以实时工具与 Runtime 契约为准。
- **由此推出的写入纪律**：凡对外部或业务应用数据集有写入的步骤都要按"会被再执行一次"来写——带唯一键或先查后写（S3-2.4 的幂等要求），并用演练标记挡住外部副作用（S3-4.3）。
- **中途要人**：运行中交互（业务表单）与 Agent 介入（`sa_handoff`）是唯一合法的"暂停点"，都要在编排里预先声明；没声明的地方不会停，也不能靠事件或消息制造停顿。

## 四、渲染语义

"渲染"指把运行中的事实投影给最终用户：业务应用的阶段状态、中间结果、提醒，以及交付页的最终呈现。本章回答**什么值得投影、何时投影、投影的意义**——具体的事件声明语法在 `stages/S3-资产制作.md` 第 5 节，界面工程细则在脚手架仓文档。

### 4.1 投影的通道

| 通道 | 载体 | 何时发生 |
|---|---|---|
| 业务阶段状态 | `stage_started` / `stage_result` / `stage_failed` 业务事件 | 脚本在业务节点显式发布（生命周期硬门必发；密度事件按需） |
| 平台交付事实 | `artifact_ready` / `delivery_ready` | Runtime 在文件登记、交付冻结后自动发布，脚本不参与 |
| 提醒 | `attention_required` 事件 | 不要求最终用户回答、但值得引起注意的事实 |
| 运行中交互 | 业务表单握手 | 上游成功后才能确定、且供未派发下游使用的输入 |
| 最终交付呈现 | `output` 业务字段（定制界面直接消费）；`output.display`（兜底出口） | Delivery 冻结后 |

### 4.2 什么值得投影（判断依据）

- **以最终用户的等待体验为出发点**：一次运行中，用户在界面上能否回答"现在到哪了、出了什么、接下来会怎样"。达不到就缺投影；能回答就够了，**不要**为完整而完整。
- **投影业务事实，不投影执行机制**：阶段名用最终用户能理解的业务语言，**禁止**出现 Workflow、节点、工具、Agent 这类平台概念（约束 9 与事件硬门的一贯要求）。
- **中间结果只在"值得单独看"时投影**：一个阶段的产出会影响用户对后续的预期（如"已找到 3 个候选方向"）才值得发中间 `stage_result`；纯技术过渡步骤不投影。**禁止**在每个 `tool()` 后机械发事件，业务应用不做进度条。
- **密度由消费方反推**：事件候选与其页面用途在方案 Plan 中提出并由开发者确认（`stages/S3-资产制作.md` 5.4；业务应用的页面设计在 app-creator 线完成）——没有消费方的事件不声明。

### 4.3 投影的意义

- 对**最终用户**：把不可见的多分钟执行变成可理解的业务进程，等待可容忍、异常可解释、结果可信任。
- 对**开发者与诊断**：持久化的业务事件是运行的公开事实轨迹，验收（事件覆盖核对）与诊断（阶段级定位）都建立在它上面。
- 对**交付质量**：交付页直接消费 `output` 业务字段呈现业务形态（对比、清单、结构化内容），`output.display` 是平台标准的**兜底展示出口**（无定制界面的包、聊天内呈现使用）。由此对 `output_schema` 有两条硬要求：
  - **字段描述必须含面向呈现的语义**（该字段是什么、每项含义），不能只写给下游脚本看；
  - ***要渲染的内容必须以业务字段出现在 `output` 中***：界面对工作区文件只有预览 URL 与下载，**读不到文件正文**——内容只落文件、`output` 只给计数和路径的契约，界面等于写在假数据上。凡要给最终用户看的列表、正文、结论、对比，都进业务字段。

投影设计的产物落点：事件契约（Workflow 资产）、渲染决策（样例选择编译产物之一，`stages/S3-资产制作.md` 3.2）、面向系统的公开语义（编排定稿后冻结，`stages/S3-资产制作.md` 7.3）；业务应用侧的事件归约与页面响应设计在 app-creator 线完成。
