# 表结构与累加机制

执行结构表与结果检查表的字段契约、状态机与指纹规则。两张表的定位与阶段职责见路由器第 5 节；本文是操作细则的正本。

## 1. 双副本

| 副本 | 位置 | 职责 |
|---|---|---|
| 本地工作副本 | `scene-{apc_id}/执行结构表.md`、`scene-{apc_id}/结果检查表.md` | 每轮直接读它定位进度；修改先落这里 |
| 工单权威副本 | `task_manager(insert)` 结构化条目，`metadata.evidence_type` 分别为 `execution_structure_snapshot` / `result_checklist_snapshot` | 跨轮次续作的唯一事实源；本地副本变更后**必须**回写快照 |

续作时（路由器 6.2）：从工单**最新快照**重建本地文件，**禁止**沿用上一轮残留的本地文件而不对账。

## 2. 执行结构表

每条 Workflow 一个分组，组内条目结构：

```json
{
  "workflow": "<Workflow 名称>",
  "items": [
    {
      "id": "steps",
      "content": {
        "steps": [
          {"seq": 1, "what": "<这一步做什么>", "by": "<工具名或 FastAgent 名>",
           "depends_on": [], "parallel_group": null}
        ],
        "no_parallel_reason": "<相邻无依赖步骤未并行时的原因；无则省略>"
      },
      "hash": "<内容指纹>", "status": "pending", "evidence": null, "waive_reason": null
    },
    {
      "id": "fa_roster",
      "content": {
        "fast_agents": [
          {"name": "...", "role": "...", "not_mergeable_reason": "<FA>3 时必填>"}
        ]
      },
      "hash": "<内容指纹>", "status": "pending", "evidence": null, "waive_reason": null
    }
  ],
  "challenged": false
}
```

- `parallel_group`：同组编号的步骤相互无依赖、可安全并发；相邻无依赖步骤不入组时**必须**写 `no_parallel_reason`（副作用顺序、共享路径、会话状态等）。
- `by` 为 FastAgent 的步骤，`what` **必须**说明该步的推理内容是什么——说不出推理内容的步骤就是误用（确定性操作应直接用工具，见 S1-6.4）。
- `challenged`（表级布尔位）：该 Workflow 分组全部条目 `passed`/`waived` 后置 `true`；任一条目回退 `pending` 时同步回退 `false`。全部分组 `challenged=true` 才算"表已出"，才能提交开发者确认（S1-10.3）。

## 3. 结果检查表

条目结构：

```json
{
  "id": "<稳定条目标识>",
  "kind": "test_case | frontend_check | orchestration_check",
  "content": {
    "input": "<测试输入；test_case 必填，来自 S1 正反例>",
    "expected": "<期望产出/期望行为；含样例选择确定的验收判定时一并写入>",
    "polarity": "positive | negative"
  },
  "hash": "<内容指纹>", "status": "pending", "evidence": null, "waive_reason": null
}
```

- `test_case` 来自 S1-4.3 正反例转入；`frontend_check` 来自 S3 出口；`orchestration_check` 按路线交付/审阅/重入行为建立。
- **跨工单继承**：修订类任务从上一工单的最新 `result_checklist_snapshot` 继承全部条目，再叠加本次新增；条目指纹对新版本重算，受影响条目按状态机回退 `pending`，未受影响条目保持 `passed`/`waived` 不重复验证（S1-11）。
- 闭合规则见 `stages/S4-验证与修正.md` 第 6 节；结单校验见 `stages/S5-发布与交付.md` 第 5 节。

## 4. 状态机与指纹

```text
                （新建 / 关联内容变化→hash 变化）
                          │
                          ▼
        ┌────────────  pending  ────────────┐
        │ 挑战或校验通过                      │ 确认不适用/开发者接受偏差
        ▼                                   ▼
      passed                             waived（必须带 waive_reason）
        │                                   │
        └──── 关联内容再次变化 → 回退 pending ──┘
```

- **指纹（hash）**：对条目 `content` 与其关联源（脚本片段、表单定义等）的规范化文本取摘要。实现上以"能稳定检测出实质变化"为准；**禁止**把时间戳、无关格式变动计入指纹。
- **只处理 pending**：一切挑战、校验、闭合动作只对 `pending` 条目执行；`passed`/`waived` 条目**不重复检查**。这是控制重复成本的核心机制，也称累加机制。
- **回退**：修改任何关联内容后**必须**重算指纹；变化则状态回退 `pending`（含所在分组的 `challenged` 回退）。**禁止**改了内容不回退状态、带着过期的 `passed` 继续推进。
- **evidence**：置 `passed` 时记录判定依据（挑战结论、运行 `run_id`、核对记录的工单条目位置），供结单与续作追溯。

## 5. 问题单（findings）条目

问题单的消化流程见 `stages/S4-验证与修正.md` 第 4 节。处置记录写入工单：

```json
{
  "finding_key": "<kind + where 的规范化标识>",
  "severity": "fail | advice",
  "disposition": "resolved | waived",
  "waive_reason": "<disposition=waived 时必填>",
  "evidence": "<修复后的 run_id 或判断依据>"
}
```

同一 `finding_key` 已有处置记录的，在后续运行中不重复报告、不重复处置。
