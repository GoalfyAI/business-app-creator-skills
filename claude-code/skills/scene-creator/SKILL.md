## 一、使用条件与接入方式

### 适用场景

在以下任务中加载本 Skill 并使用 `scene-creator` MCP：

- 创建新的 GoalfyMax 场景包；
- 把业务流程、SOP、经验体、文档或已完成项目沉淀为场景能力；
- 诊断场景包的执行绕行、成本、稳定性、交付质量或资产配置；
- 优化已有场景包及其场景 Skill、任务点、工具能力、数据、编排和业务界面；
- 根据真实项目执行日志复盘并持续迭代场景包；
- 验证、发布或继续已有场景包制作任务。

一次性业务执行、通用应用开发和产品概念咨询由对应领域能力处理。涉及场景资产读取、创建、修改、验证或发布时进入本 Skill。

### MCP Server 配置

MCP Server：`scene-creator`

```json
{
  "scene-creator": {
    "type": "streamable-http",
    "url": "https://workflow-mcp.qa.goalfyai.com/mcp",
    "headers": {
      "Authorization": "Bearer ${SCENE_CREATOR_API_KEY}"
    }
  }
}
```

- `SCENE_CREATOR_API_KEY` 使用当前用户的 GoalfyMax QA 个人 API 密钥，前缀为 `sk_`；
- 用户在 GoalfyMax QA“开发者工具 → API 密钥”（`/developer/api-keys`）创建个人密钥；
- Codex 从 `~/.codex/.env` 或启动进程环境读取；Claude Code 按插件配置读取同名环境变量；
- 身份认证只使用 `Authorization: Bearer ${SCENE_CREATOR_API_KEY}`；
- 完整密钥仅保存在本机环境变量中；
- 配置完成后重启 Agent 客户端，再执行连接验证。

需要用户配置时，发送以下内容：

```markdown
# 需要用户操作：连接 scene-creator

请在 GoalfyMax QA 的“开发者工具 → API 密钥”创建或选择个人密钥，将完整密钥写入本机 `SCENE_CREATOR_API_KEY` 环境变量。密钥仅保存在本机。

完成后请彻底重启当前 Agent 客户端，再回来进行连接验证。
```

### 连接验证

连接验证采用只读方式：确认 Skill 已加载、MCP 已连接、实时 `tools/list` 包含核心能力，并调用一次只读资产查询。连接验证完成后再创建工单、资产、项目或部署。

### 本地文件传输

外部 MCP 运行在远端，本地文件通过预签名传输流程交接：

1. MCP 生成上传请求或临时下载 URL；
2. 当前 Agent 负责传输本地文件字节；
3. 上传完成后回调 MCP；
4. 下载完成后校验文件并进入后续处理。

场景 Skill、辅助文件和业务界面源码均遵循该流程。本地路径保留在当前 Agent 环境，预签名 URL 仅用于当次传输。

## 二、MCP 定位与职责

### 定位

`scene-creator` 是场景包全生命周期 MCP。它把业务目标、业务知识、执行能力、数据、交互入口和验证证据组织成可在 GoalfyMax 使用的场景包。

Agent 以场景包创建与优化专家的身份使用该 MCP，从用户业务视角理解真实工作方式，基于线上资产、项目日志、业务文档和运行证据做出配置决策。

### 核心职责

- 访谈业务目标、适用用户、里程碑、候选路线、权限边界和验收标准；
- 查询、创建、更新和发布场景包；
- 编写和维护 `apc_skill` 与场景 Skill 文件；
- 搜索、复用和管理任务点、Toolset、Tool Group、FastAgent、Dataset、Workflow、场景编排和业务界面；
- 从真实项目执行日志定位场景知识、资产结构、提示词、工具契约和运行机制根因；
- 对创建或修改结果执行单项验证、场景包整体验证和可选真实项目验证；
- 保存可审计的任务、决策、验证证据、发布结果和已知盲区。

### 支持的任务类型

| 类型 | 目标 |
|---|---|
| 创建 | 把业务流程、SOP、经验、文档或项目沉淀为新场景包 |
| 诊断 | 基于资产配置和运行证据定位根因 |
| 优化 | 修改原场景包及受影响资产并完成回归验证 |
| 续作 | 沿用已有工单、资产、运行和部署标识继续执行 |
| 验证发布 | 检查业务闭环、资产关系、运行契约和发布状态 |

### 能力边界

- 线上资产事实来自 MCP 实时查询；
- Max 内部系统提示词和内部状态机由 Max 平台维护；
- 用户业务决策、发布授权、资金消耗和不可逆操作由用户确认；
- 外部系统能力通过已注册工具及其公开契约使用；
- 单次业务执行和通用应用开发由对应业务或开发能力承担。

### 完成交付的标准

1. 业务终点、适用用户、触发场景和能力边界明确；
2. 里程碑、候选路线、权限边界和用户可见产出得到确认；
3. `apc_skill`、场景知识、依赖资产和执行资产位于正确层级；
4. 被采用的资产真实存在、可访问并具备相应验证证据；
5. 场景包通过业务闭环、引用关系、执行路径和交付边界检查；
6. 发布后的资产已经反读确认；
7. 全真验证范围、路径覆盖和外部副作用盲区记录完整。

## 三、工作方式与交互协议

### 业务顾问式工作方式

- 从用户业务视角理解目标、现状、约束和实际工作方式；
- 主动识别业务信息缺口，并用渐进式访谈补齐关键事实；
- 基于真实资产、日志、文档、规范和运行证据形成判断；
- 先给出业务结论，再说明证据、影响和后续动作；
- 在方案、权限、副作用、发布和资金消耗等关键节点获得用户确认；
- 对安全、可逆、只读的调查与验证自主推进；
- 修改前提供清晰的改前、改后和影响范围；
- 每次操作后反读结果，确认真实状态。

### 沟通语言规范

- 面向用户统一使用“用户”作为第三人称指代，Agent 自称“Agent”或省略主语；
- 方案展示采用业务语言，说明能力、阶段、产出、风险和选择；
- 技术字段、资产 ID、Schema 和调用链仅在技术协作或执行记录中出现；
- 先给出结论和用户影响，再补充证据与执行依据；
- 问题、能力缺口和验证盲区使用准确、直接、可行动的表达。

### 工作语言

- 默认工作语言为简体中文；
- 用户可见文本、工具参数中的自然语言字段和任务记录使用同一工作语言；
- 同一任务保持语言和术语一致。

### 用户交互方式

根据当前宿主环境选择对应的交互能力：

| 交互类型 | 使用场景 | 行为 |
|---|---|---|
| 信息通知 | 汇报进展、发现和安全默认 | 发送后继续执行 |
| 默认方案确认 | 存在安全默认且用户意见可以改变后续方案 | 展示默认方案和影响，等待宿主交互结果 |
| 明确提问 | 缺少只有用户能够提供的信息，或涉及发布、资金、权限和不可逆操作 | 暂停相关动作并等待回答 |
| 最终交付 | 场景包完成验证与发布 | 提交结论、证据、资产、局限和后续建议 |

宿主提供结构化消息或确认工具时，用户可见交互统一通过该能力发送。普通文本用于无需用户作答的过程说明。

### 交互铁律

- 已知信息直接复用；
- 每轮问题聚焦最影响下一步的一至三个事项；
- 平台知识、资产现状、工具能力和 Schema 由 Agent 调查；
- 业务目标、用户偏好、权限授权和高风险选择由用户决定；
- 安全默认明确记录适用条件和影响；
- 用户拒绝、调整和选择作为后续选路的重要证据；
- 问题在发现时透明说明，并同步可行处理路径。

### 行为原则

每个执行动作遵循：

1. **执行**：完成当前最小原子操作；
2. **检查**：反读工具结果、状态和关联关系；
3. **记录**：保存影响续作的事实、决策、资产标识和验证证据；
4. **更新**：更新任务阶段和下一步；
5. **推进**：进入下一原子操作或触发相应用户交互。

参数、资产和结论均保持可追溯。统计值、版本、ID、运行状态和验证结论以真实输出为依据。

## 四、意图识别与任务启动

### 意图分类

收到任务后先判定模式：

| 用户意图 | 模式 | 启动信息 |
|---|---|---|
| 创建场景包、沉淀业务流程、基于经验或项目搭建能力 | 创建 | 业务场景、目标用户、业务终点或可读取的参考素材 |
| 检查效果、分析绕行、分析项目执行日志 | 诊断 | 场景包 ID、项目 ID 或明确诊断对象 |
| 修改已知问题、落实诊断结论 | 优化 | 目标资产、修改目标和已确认范围 |
| 继续已有制作、验证或发布任务 | 续作 | `task_id` 及已有资产、运行或部署标识 |

创建完成后的试运行可以进入诊断，诊断发现资产缺口可以进入资产补建，优化完成后进入回归验证。

### 意图迷雾

以下情况属于意图迷雾：

- 业务目标尚未明确；
- 创建任务缺少业务场景或业务终点；
- 诊断任务缺少场景包、项目或问题对象；
- 创建、诊断、优化和续作之间存在歧义；
- 用户提供的信息会导向不同的业务结果。

意图迷雾阶段只收集启动任务所需的最小信息。问题围绕业务目标、操作对象和关键约束组织，获得答案后再进入规划。

### 区分信息缺口

| 缺口 | 处理方式 |
|---|---|
| 意图缺失 | 确认创建、诊断、优化或续作模式 |
| 关键业务参数缺失 | 收集业务目标、对象、范围、输入或验收标准 |
| 平台知识缺失 | 查询工具契约、资产、规范和运行日志 |
| 可选偏好缺失 | 采用安全默认并记录影响 |
| 用户授权缺失 | 在对应动作前发起明确确认 |

### 最小充分上下文

根据任务逐步收集：

- **业务目标**：业务问题、服务对象和成功标准；
- **业务里程碑**：从触发到交付的关键阶段；
- **输入与产出**：已有资料、系统、数据和期望结果；
- **参考证据**：项目、完整执行日志、SOP、文档、经验体和已有场景包；
- **候选路线**：不同用户状态对应的可行路径；
- **业务档案**：影响选路的实体事实和情境事实；
- **权限与副作用**：自主动作和用户确认点；
- **验收标准**：可证明场景包有效的业务证据；
- **业务界面**：界面目标、使用人群和交互任务。

### 任务启动条件

同时满足以下条件后进入运行前准备：

1. 任务模式明确；
2. 操作对象或创建目标明确；
3. 执行所需关键业务参数齐备；
4. 高风险边界和授权要求已识别；
5. 后续调查可以通过 MCP、线上资产、参考文件或日志完成。

## 五、运行前能力准备与规划

### 事实源准备

正式规划前按以下优先级建立事实基础：

1. 当前 MCP `tools/list` 中的工具名、action、参数和必填字段；
2. `get_asset` 反读的线上资产、版本、关系、权限和 Schema；
3. `get_diagnosis_doc` 返回的服务端契约、示例和诊断规范；
4. Preview、Hub 保存校验、bubble、Max Runtime 和项目日志；
5. 本 `SKILL.md` 的领域模型和执行流程；
6. 本地专项参考文件。

资产 ID、工具名、参数、Schema、版本、返回字段和运行结果均来自真实查询。线上契约发生变化时，以当前线上事实执行，并记录需要同步更新的 Skill 内容。

### 能力准备

1. 查询目标场景包及其现有资产关系；
2. 搜索平台已有场景包、任务点、Toolset、FastAgent、Tool Group、Dataset 和业务界面；
3. 反读关键资产的完整配置、权限、Schema、版本和在线状态；
4. 识别可直接复用、需要克隆、需要新建和需要开发的能力；
5. 读取当前任务涉及的服务端规范与本地专项参考文件；
6. 把能力覆盖、缺口、风险和处理路径写入场景包方案。

### 路由选择

按照任务职责和运行特征选择实现形态：

| 运行需求 | 实现形态 |
|---|---|
| 少量确定的原子资产操作 | Agent 直接调用 MCP |
| 独立上下文、临场决策或执行中交互 | 普通任务点 / TaskAgent |
| 一次输入、独立推理、一次输出 | FastAgent |
| 多个顺序稳定、可重复验证的确定步骤 | Workflow |
| 多个 Workflow 的固定依赖、映射和交付关系 | `workflow_orchestration` |
| 场景包专属可视化操作入口 | 业务界面 |

路由选择记录业务职责、输入输出、复用价值、权限边界和验证方式。场景包可以组合多种实现形态。

### 规划路径

- **基础规划**：执行路径清晰、资产关系稳定、风险可控、验证方式明确；
- **深度规划**：需要多源资料整合、多方案权衡、架构重构、高代价决策，或既有策略已经失效。

规划内容至少包括：

1. 业务目标与交付物；
2. 里程碑与候选路线；
3. 所需场景知识和资产；
4. 用户确认点与权限边界；
5. 验证、发布和回滚方式；
6. 已知缺口与替代路径。

### 可审计任务

首次写操作前通过 `scene_package_task_manage(create)` 创建工单，保存 `task_id`。后续创建、修改、上传、验证、发布和续作均复用该 `task_id`，并在检查点记录资产标识、决策、验证结果和下一步。

### 计划提交约束

- 计划以业务结果定义阶段；
- 第一个阶段描述业务素材和场景理解成果；
- 计划提交表达拟执行方案，用户确认后进入写操作；
- 规划中发现新的关键歧义时回到意图澄清；
- 运行中发现策略失效时记录原因并重新规划；
- 资产创建、修改、删除、发布和资金消耗遵循相应授权边界。

### 静默提交协议

宿主提供交互式计划提交能力时：

1. 计划通过结构化计划接口提交；
2. 同一条消息的普通正文保持为空；
3. 计划内容由宿主界面统一渲染；
4. 用户确认结果作为后续执行授权；
5. 计划更新继续复用原计划标识和版本。

宿主只提供普通对话时，以简洁业务计划请求确认，并在收到确认后进入执行。

## 六、场景包核心模型

### 什么是场景包

场景包定义 GoalfyMax 在一类业务场景中能解决什么问题、如何选择执行路线、可以使用哪些能力、哪些事项必须由用户决定，以及最终交付什么。

场景包是围绕明确业务终点组织的运行时能力包。它承载 Agent 必须理解的业务知识、候选路线和权限边界，并按场景需要组合任务点、Toolset、FastAgent、工具、数据、Workflow 和业务界面。

典型组成：

```text
场景包
├── apc_skill：SA 始终可见的业务目标、路由、里程碑和边界
├── 场景 Skill 文件：按明确时机读取的知识、模板、案例和详细 SOP
├── 普通任务点：需要 TaskAgent 独立执行、临场判断或交互的完整任务
├── Toolset：按稳定能力域组织工具和 FastAgent
│   ├── Tool Group：真实 MCP 工具及其单工具契约
│   └── FastAgent：一次输入、独立推理、一次输出的子任务
├── Dataset：长期数据、关系、治理和查询规则
├── Workflow：可选的稳定、可测、可复跑的确定性执行片段
├── workflow_orchestration：可选的多 Workflow 固定 DAG 和映射
└── 业务界面：可选的场景包专属操作界面，是否存在只取决于开发者是否开发并发布
```

资产数量由业务职责决定。每个资产对应清晰、独立、可验证的职责，整体组合保持路由明确、成本可控和持续可维护。

### 场景包是一张路线地图

高质量场景包要区分：

- **共同业务终点**：场景承诺解决的问题和可验收结果；
- **候选路线**：满足不同目标、准备状态和约束的业务路径；
- **稳定路段**：不随用户改变、可以固化的执行片段；
- **选路节点**：需要结合用户现状、业务档案、风险和当前输入做判断的位置；
- **到达标准**：证明结果有效的业务证据。

参考项目中的执行路线作为候选路线和证据来源。场景包根据用户状态选择路线，并由 SA 直接执行、普通任务点、FastAgent、工具、Workflow 和用户确认共同完成。

### 用业务档案支持个性化选路

业务档案包括：

- **实体档案**：相对稳定的用户、企业、门店、产品、学员等事实；
- **情境档案**：当前目标、阶段、约束、偏好、近期选择、执行结果和未解决问题。

运行时只读取足以影响本次选路的内容，并坚持最小充分原则。业务档案通过实质改变本次执行的路线、参数、优先级或解释形成个性化结果。

遵守以下证据纪律：

- 用户当前明确表达和有效约束优先于历史记录；
- 用户选择、调整、拒绝和理由是强证据；
- Agent 推断以假设标注，并与用户明确表达的偏好区分；
- 档案缺失、过期、冲突或与当前任务无关时，向用户补充关键事实或使用安全默认；
- 场景包通过现有投稿与审稿机制形成候选事实，由对应机制更新用户档案；
- 档案使用始终遵守权限、确认和场景包能力边界。

### 资产角色与执行形态

- **System Agent**：面向用户理解意图、选择路线、组织能力和交付结果；
- **普通任务点 / TaskAgent**：执行需要独立上下文、临场决策或中途交互的完整任务；
- **FastAgent**：在隔离会话中执行一次输入、独立完成、一次输出的推理子任务；
- **Workflow**：把多个确定步骤固化成可验证脚本；可以调用工具或 FastAgent，开放式业务决策由 Agent 完成；
- **Toolset**：按能力域组织工具和 FastAgent，并说明它们如何搭配；
- **Tool Group**：承载单个 MCP 的真实工具描述和参数 Schema；
- **Dataset**：承载长期数据及其查询规则；
- **业务界面**：场景包的可选交互层；DAG 由运行时编排执行，界面的存在由场景交互需求和 `entry_url` 决定。

选择执行形态时按顺序判断：

1. 少量、一次性、低风险、无复用价值的确定调用，可由 SA 直接执行；
2. 任务需要独立上下文、临场选择或中途交互，使用普通任务点；
3. 任务是一次输入、独立推理、一次输出，使用 FastAgent；
4. 存在至少两个稳定真实步骤、多工具串并联或高频复跑，使用 Workflow；
5. 存在多个职责独立、依赖固定的 Workflow，才使用 `workflow_orchestration`；
6. 路线会因用户档案或运行结果改变时，由 Agent 负责选路，Workflow 负责稳定路段。

### 信息只写在正确层级

| 信息 | 权威位置 | 避免重复至 |
|---|---|---|
| 单个工具用途和参数 | Tool Group 工具描述与 Schema | Toolset Skill、`apc_skill` |
| 工具或 FastAgent 的搭配 | Toolset 使用指南 | 单工具描述 |
| 推理子任务的内部方法 | FastAgent 提示词 | `apc_skill`、Workflow 说明 |
| 交互式任务执行方法 | 普通任务点提示词 | Toolset 使用指南 |
| 稳定步骤和单阶段数据流 | Workflow 脚本 | `apc_skill` |
| 多 Workflow 依赖和映射 | `workflow_orchestration` | `apc_skill`、场景 Skill |
| 业务目标、里程碑、候选路线、权限和读取路由 | `apc_skill` | 工具描述 |
| 长知识、模板、案例和详细 SOP | 场景 Skill 文件 | `apc_skill` 正文 |
| 数据表语义和查询规则 | Dataset Skill | 场景 Skill |
| 业务界面代码和公开交互契约 | 业务界面源码包与宿主 SDK | Workflow、`apc_skill` |

同一规则只保留一个权威位置。避免复制 DAG、重复工具参数、把业务 SOP 写进 Toolset、把 FastAgent 内部循环写进场景 Skill，或让业务界面解释内部编排。

### `apc_skill` 的职责

`apc_skill` 是场景包运行时 SA 始终可见的核心知识，应包含：

- 场景包解决什么问题、共同业务终点是什么、何时使用；
- 业务里程碑，以及每阶段目标和用户可见产出；
- 通往终点的候选路线、适用条件和选路节点；
- 必需业务输入和预期交付；
- 哪些判断由 Agent 完成，哪些必须交给用户；
- 业务档案选路规则：如何识别相关实体档案和情境档案，读取哪些最小充分信息；
- 档案缺失、过期、冲突和 Agent 推断如何处理；
- 未被其他资产封装的关键业务规则、前置检查和工具选择；
- 在什么阶段读取哪个场景 Skill 文件；
- 执行后如何整理可投稿的候选事实，同时遵守审稿边界。

以下内容归属其他层级：

- 制作说明、调试记录和发布步骤；
- 数字资产 ID 或当前用户的具体私有档案事实；
- 已由 Workflow 或 `workflow_orchestration` 固化的执行步骤；
- 单个工具的完整参数说明；
- 某一条候选路线作为所有用户必须执行的唯一 SOP；
- 只有制作 Agent 才需要知道的验证与上传细节。

## 七、创建场景包

创建流程从真实业务素材出发，形成场景包蓝图，确认方案后完成资产创建、关系配置、验证和发布。

### 1. 收集真实业务素材

优先级从高到低：

1. 已执行项目及完整日志；
2. 用户提供的 SOP、规范、数据和文档；
3. 用户指定的经验体、场景包或其他资产；
4. 可通过 `list_assets`、`get_asset` 和 Dataset 发现的线上素材；
5. 服务端规范和示例。

用户提供参考项目时，完整读取需求、关键工具调用、TaskAgent/FastAgent 结果、失败重试、等待、最终交付和原始日志，分析有效推进、重复沟通、失败重试、瓶颈根因和实际调用链。

### 2. 形成场景包蓝图

蓝图至少包含：

- 目标用户、触发场景和共同业务终点；
- 业务里程碑及每阶段产出；
- 候选路线、适用条件、代价和选路节点；
- 业务档案如何影响路线、参数、优先级或解释；
- 必需输入、预期输出和验收证据；
- Agent、用户和确定性资产的责任边界；
- 能力覆盖、可复用资产和真实缺口；
- 数据集、场景知识和业务界面需求；
- 无法优化的部分和剩余盲区。

价值预测以真实基线为依据；缺少基线时采用定性判断并说明证据边界。

### 3. 能力摸底与资产复用

先搜索再创建：

- 场景包、普通任务点和 Workflow；
- Toolset、Tool Group、FastAgent；
- Dataset、经验体和项目；
- 已有 Skill 文件和业务界面。

对关键资产用 `get_asset` 反读真实配置、关系、权限、Schema、版本和在线状态。名称和描述用于初筛，完整配置用于最终判断。资产 ID 来自实时查询或创建结果；多个同类资产并列时，用名称和 ID 消除歧义。

### 4. 设计场景包整体架构

按蓝图逐阶段决定：

- 哪些内容写入 `apc_skill`；
- 哪些长知识放场景 Skill 文件；
- 哪些工作由 SA 直接执行；
- 哪些工作使用普通任务点、FastAgent 或 Workflow；
- Toolset 如何按稳定能力域划分，哪些预加载、哪些动态加载；
- 是否需要 Dataset 或固定版本模板；
- 是否需要业务界面，以及它服务什么交互；
- 多 Workflow 是否真的存在固定 DAG；
- 每个高风险动作在哪里确认。

业务界面是由开发者按场景交互需求创建并通过 `entry_url` 交付的独立资产。界面可以服务普通 SA、单 Workflow、多 Workflow或展示与管理任务。界面实际消费某个 Workflow 的公开输入或结果契约时，该契约变化会触发对应界面回归验证。

### 5. 方案挑战与用户确认

创建资产前完整读取 [方案挑战检查清单](references/方案挑战检查清单.md)，至少挑战：

- 是否真正解决共同业务终点；
- 是否把某一路线误写成唯一 SOP；
- 资产选择是否过度复杂；
- Agent 判断与确定性执行边界是否正确；
- 依赖和权限是否闭包；
- 交付物和验证证据是否充分；
- 业务界面是否独立于执行资产做出合理决策。

向用户展示管理型方案：各阶段能做什么、产生什么、哪里需要确认、有哪些能力缺口和局限。用户确认后再进入创建；修改意见会改变业务目标或整体路线时，回到蓝图重新设计并确认。

### 6. 创建可审计工单

工单 Gate 优先于后续规划、契约读取、资产搜索和并行规则：

1. 新建、诊断或优化一个独立任务时，第一项业务工具调用必须是 `task_manager(action="create", task_name=..., task_description=..., mode=<"read"|"write">, skill_version=<当前版本>)`，并且在拿到结果前它是唯一的业务工具调用。纯只读诊断使用 `mode="read"`；创建、优化或任何可能写入的任务使用 `mode="write"`。`skill_version` 必须逐字读取本文件 description 中唯一的 `[skill-version:...]` 标记，写模式不得省略、猜测或改写。
2. 继续已知 `task_id` 的任务时，第一项且唯一的业务工具调用是 `task_manager(action="get", task_id=<task_id>)`。
3. 明确是续作但当前上下文没有 `task_id` 时，第一项且唯一的业务工具调用是 `task_manager(action="list")`。下一轮若唯一匹配则再 `get`；没有匹配才按第 1 条 `create`；多个候选无法判断时先请用户选择，禁止静默绑定错误工单。
4. 必须等待上述调用成功，再读取制作契约、搜索资产、规划或执行任何修改；服务端拦截只用于兜底，不是正常启动方式。

`task_description` 应写明当前模式、业务目标、预期交付物和验收边界。保存返回的 `task_id`，后续需要审计的工具调用都传入该值。`list_assets` 和 `get_asset` 是只读搜索，不传 `task_id/op_summary`，也不形成逐次工具审计；如果搜索结论决定了复用、克隆或修改哪个资产，使用 `task_manager(action="insert", task_id=<task_id>, entry_type="checkpoint", content=...)` 记录选择结论。资产创建和验证后同样用 `insert` 写入简洁检查点，不复制完整工具输入、供应商输出、凭证或原始日志。

纯只读诊断后用户授权修复或优化时，不得复用 read `task_id` 执行任何写 action。重新读取当前版本标记，新建 `mode="write"` 工单并传 `continued_from_task_id=<原 read task_id>` 和 `skill_version=<当前版本>`；创建成功后改用新 write `task_id`。服务端返回 `WORKFLOW_TASK_MODE_MISMATCH` 时，根据 metadata 中的 `actual_mode` 和 `required_mode` 纠正工单，不把它误判为工单不存在或他人所有。

创建 write 工单返回 `SCENE_SKILL_UPGRADE_REQUIRED` 时立即停止写操作，只使用响应中的 `upgrade_source`：从 `git_url` 克隆精确 `ref`，并按 `platform_roots.codex` 或 `platform_roots.claude_code` 选择安装根目录执行对应 `UPDATE.md`；不得猜测下载地址或改用 ZIP。来源缺失、无权限或精确 ref 不存在时保持阻断并联系内部运维。`SCENE_SKILL_UPGRADE_RECOMMENDED` 只提示、不阻断本次工单，升级仍使用同一受控来源。

恢复检查点中的场景包 ID、资产 ID、验证结论和剩余问题。禁止为同一目标创建平行工单或同名资产绕过失败。Max 项目内的 shell、file、FA、消息和规划执行继续记录在项目执行日志中，不伪装成场景包 MCP 工具审计；工单只记录相应阶段结论和项目证据引用。

### 7. 读取规范和现有资产

开始任何任务时读取 [外部 MCP 工具路由](references/external-mcp-tools.md)。根据当前需要读取服务端规范：

- 场景包、Toolset、普通任务点、FastAgent、依赖和业务界面规范按实时 topic 获取；
- 只有实际决定制作 Workflow 时才读取 `workflow_authoring` 和 `workflow_single`；
- 只有实际决定制作多 Workflow 时才读取 `workflow_multi`；
- 只有需要特殊原语、正反例或修复已知问题时才读取 `workflow_examples` 及匹配示例。

同一工单复用已经读取的 topic 结论。审计记录 topic、返回文档名和关键结论。

### 8. 创建场景包草稿

基于已确认蓝图起草 `apc_skill`。正文覆盖共同终点、里程碑、候选路线、业务档案选路、权限边界、场景文件读取时机和交付标准；数字资产 ID、私有档案事实、制作过程和已固化流程保留在各自权威位置。

调用 `scene_package_manage(action="create", task_id=<task_id>, ...)` 创建离线场景包草稿并保存 `scene_package_id`。后续修复使用 `action="update"` 修改同一资产。

### 9. 补齐场景知识和数据

场景 Skill 文件只用于长业务知识、模板、案例、数据字典和详细 SOP，并且必须在 `apc_skill` 中给出明确读取时机。

使用 `workflow_file_upload` 完成交接：

```text
workflow_file_upload(action="prepare", task_id=<task_id>, ...)
→ 当前 Agent HTTP PUT 本地字节
→ workflow_file_upload(action="complete", task_id=<task_id>, ...)
```

已有可信 HTTPS 文件可以使用：

```text
workflow_file_upload(action="from_url", task_id=<task_id>, ...)
```

再通过 `scene_package_manage(..., skill_file_urls=[...], skill_files_mode="merge")` 绑定场景 Skill。

需要 Dataset 时先读取可访问数据集和治理规则，只绑定业务实际需要的数据。数据集创建、修改和删除由对应数据集能力完成；场景包制作流程负责说明依赖并在完成后继续绑定。

### 10. 按需补齐依赖资产

优先复用线上资产。只有确认存在真实缺口时，才通过 `workflow_dependency_manage` 创建或维护 Toolset、Tool Group、FastAgent、Auth Card 或普通自定义 TPE。

- 单工具描述和参数留在 Tool Group；
- 工具搭配留在 Toolset 使用指南；
- FastAgent 提示词只描述其自包含子任务；
- 普通自定义或预定义任务点使用相应创建能力；
- Workflow TPE 只能由 `workflow_tpe_manage` 管理；
- 修改共享资产前先确认影响范围，必要时克隆后替换引用；
- 受限资产的配置可见性和运行可用性分别判断，保留或替换由用户确认。

需要对没有可信 output Schema 的只读 MCP 工具取样时：

1. 确认调用安全、只读或已获授权；
2. 调用 `workflow_dependency_manage(action="test_tool", task_id=<task_id>, ...)` 获取代表性真实输出；
3. 起草最小候选 output Schema；
4. 换一组输入再次调用并传入候选 Schema 复验；
5. 检查点只保存契约结论，凭证和原始敏感输出保留在安全边界内。

破坏性、发布、凭证变更、金融和不可逆取样均在用户授权后执行。

### 11. 按需制作普通任务点、FastAgent 或 Workflow

资产制作顺序由真实依赖关系决定。每创建或更新一项资产，都反读真实配置并检查与场景包的关系。

#### 普通任务点与 FastAgent

- 任务需要独立上下文、临场决策或中途交互时使用普通任务点；
- 一次输入、独立推理、一次输出时使用 FastAgent；
- 输入要求、执行方法、输出要求和所需工具放在资产自身层级；
- 创建后检查描述是否足以让 SA 正确路由，工具和 Toolset 是否覆盖任务需要。

#### Workflow

只有已确认存在稳定、多步骤、可复跑的确定性片段时才制作 Workflow。详细契约以 `get_diagnosis_doc` 和实时 Schema 为准，主流程为：

```text
依赖闭包与 Toolset 上线反读
→ workflow_tpe_manage(action="preview", task_id=...)
→ 修复同一草稿
→ workflow_tpe_manage(action="create", task_id=..., scene_package_id=...)
→ workflow_tpe_manage(action="bubble", task_id=..., tpe_id=...)
→ 轮询同一 run_id 到终态
→ 读取 Workflow 验收检查清单并做语义验收
```

依赖 Toolset 上线硬门：脚本实际调用的 Toolset 必须完整存在，通过安全测试后执行上线，再用 `get_asset` 反读确认每个 Toolset 的 `is_online=true`，才能创建 Workflow。

Workflow 引用 `ctx.skill_dir` 时，先通过 `workflow_file_upload` 上传完整辅助文件集合。更新时确认服务端的 merge 或 replace 语义，并保留目标版本所需的全部文件。

每条 Workflow 必须有根对象 input/output Schema。Preview 通过只证明静态契约可保存；bubble success 只证明本次路径运行成功；FA 桩值、未触达分支和业务语义仍需单独验收。

#### 多 Workflow 编排

多个职责独立的 Workflow 存在固定依赖时，保存一个完整 `workflow_orchestration` 对象。DAG、输入映射和 delivery 以该对象为唯一权威位置。

`sa_handoff` 用于模型审阅、补充判断、用户确认或运行接管。普通结构化交付沿原执行路径完成。运行时控制动作来自当前服务端契约。

### 12. 按需制作业务界面

业务界面由开发者根据场景交互需求开发并发布，通过 `entry_url` 与场景包关联。它可以服务普通 SA、单 Workflow、多 Workflow或展示与管理交互。

需要新建或维护业务界面时，完整读取 [业务界面制作契约](references/业务界面制作契约.md)，并以 `scene_package_ui_bundle(action="download_template", task_id=<task_id>)` 返回的当前官方模板初始化项目。

界面实际消费的公开输入、动作、状态或结果契约发生变化时，重新执行相关界面验收。MCP 工具清单、内部提示词、Workflow 脚本、DAG、控制动作和平台凭证保留在制作与运行安全边界内。

按模板文档开发后执行检查、打包、`prepare_upload → PUT → complete_upload → deploy/status → get`，保存源码 SHA256、`deployment_id`、激活地址和验收结论。预签名 URL 仅用于当次传输。

### 13. 更新场景包整体关系

所有子资产就绪后，反读场景包并更新：

- `apc_skill` 和场景 Skill 文件；
- 预加载与动态 Toolset；
- 普通任务点和 Workflow；
- Dataset 或固定版本模板；
- 可选 `workflow_orchestration`；
- 可选业务界面绑定。

结构变化后检查引用、路由描述、Skill 文件索引和交付边界。场景包整体设计作为所有专项资产制作和续作的统一基线。

## 八、诊断和优化场景包

### 1. 确定目标与范围

先确认目标场景包、用户观察到的问题和诊断范围。用户只说“帮我看看”时，列出其可访问的场景包供选择，并区分全量诊断或聚焦诊断。

全量诊断先覆盖每个资产层级，再沿证据线索深入相关子资产。聚焦诊断覆盖用户指定范围，完成后再确认扩展范围。

### 2. 收集真实证据

反读场景包全貌和所有直接关系。用户提供项目 ID 时，完整分析：

1. 执行概览和用户需求序列；
2. 详细日志、关键轮次、工具调用、任务派发和错误；
3. 最终交付物及其与用户目标的差距；
4. 重复沟通、失败重试、等待和无效绕行；
5. 根因属于缺知识、缺工具、缺指引、资产结构错误、契约错误，还是运行机制问题。

诊断结论由完整日志和资产证据共同支撑。修复对象指向产生症状的场景知识、资产结构、工具契约或运行机制根因。

### 3. 按层诊断

按真实引用关系逐层检查：

```text
场景包
→ apc_skill 与场景 Skill
→ 普通任务点 / Workflow
→ Toolset
→ FastAgent / Tool Group
→ 单个工具、Dataset、业务界面
→ 真实运行证据
```

每层先读取对应规范，再检查：

- 名称和描述能否正确路由；
- 信息是否放在正确层级；
- 资产关系是否完整、可访问且在线；
- 输入输出契约是否支撑上下游；
- `apc_skill` 是否覆盖终点、里程碑、候选路线、业务档案和权限边界；
- 是否把 Agent 判断错误固化，或把确定步骤反复交给 Agent；
- 业务界面是否只消费公开契约，且没有被 Workflow 是否存在错误门控；
- 日志中的真实绕行点是否被现有知识和资产覆盖。

### 4. 输出分级诊断报告

- **严重问题**：影响正确性、安全、权限或核心业务闭环，必须修复；
- **警告**：影响稳定性、效率或使用体验，建议修复；
- **建议**：改善性优化。

每项包含位置、当前值、证据、根因、影响、建议和改前/改后。发现问题时及时说明并继续完成诊断范围。

### 5. 用户确认后修复原资产

修复顺序：

1. 先修结构和依赖关系；
2. 再修输入输出契约；
3. 再修场景 Skill、任务提示词和工具使用说明；
4. 最后处理界面表现和改善性问题。

修改前展示 diff 并获得确认；删除、发布、收费和不可逆操作单独确认。原资产承接同一问题的连续修复。共享资产影响其他场景包时，先确认影响范围，必要时克隆后替换目标场景包引用。

### 6. 对受影响路径回归验证

只重验受修改影响的资产和路径，但最终仍要做一次场景包整体一致性检查：

- 修改 Workflow：重新 Preview、bubble 和语义验收；
- 修改编排：重新检查 DAG、映射、handoff 和 delivery；
- 修改公开界面契约：重新验证并部署业务界面；
- 修改 Toolset 或工具：检查所有引用它的执行资产；
- 修改 `apc_skill` 或路线逻辑：重新检查业务终点、选路和权限；
- 需要真实效果证据时，在用户批准后运行项目并复盘日志。

## 九、场景包资产操作规范

### MCP 工具清单

当前稳定工具职责如下，实时数量和参数仍以 `tools/list` 为准：

| 工具 | 场景包制作中的职责 |
|---|---|
| `task_manager` | 创建、查找、恢复、追加和完成统一的场景包制作工单；新任务的第一项业务调用，后续复用同一 `task_id` |
| `list_assets` | 搜索场景包及其可复用子资产、经验和项目 |
| `get_asset` | 反读完整资产、关系、Schema、权限和版本 |
| `get_diagnosis_doc` | 读取服务端制作契约、示例和诊断规范 |
| `dataset_read` | 按权限读取场景需要的数据集内容 |
| `workflow_file_upload` | 交接场景 Skill、Workflow 辅助文件和其他工单文件 |
| `workflow_dependency_manage` | 维护 Toolset、Tool Group、FastAgent、Auth Card、普通任务点并做安全取样 |
| `scene_package_manage` | 创建、更新、反读、挂载关系并发布场景包 |
| `scene_package_ui_bundle` | 下载模板，上传、部署、查询和反读场景包业务界面 |
| `workflow_tpe_manage` | 为稳定、可复跑的确定流程提供 Preview、创建、更新、bubble 和发布 |
| `manage_goalfymax_project` | 在用户批准后运行和控制真实 Max 项目 |
| `get_project_execution_logs` | 分析真实日志并读取最终交付物 |

### 调用纪律

1. 任何 ID 必须来自实时查询或创建返回；
2. 先复用再创建；
3. 工单 Gate 成功后的审计调用携带同一 `task_id`，只读 `list_assets/get_asset` 除外；
4. 工具报错时按精确错误修正参数或策略，每次重试包含明确变化；
5. 受限资产的配置脱敏状态与运行可用性分别判断；
6. 上传、发布、收费、通知和正式业务写入按真实副作用处理；
7. 真实通过结论以真实执行、已触达路径和完整验证证据为依据；
8. Battle、Verify 和其他能力均从当前 MCP `tools/list` 获取。

## 十、验证、发布与交付

### 场景包专项验证

根据实际资产组合选择证据：

- 场景方案：读取 [方案挑战检查清单](references/方案挑战检查清单.md)；
- Workflow：执行“预览 → `bubble` → 语义验收 → 可选全真跑”，并读取 [Workflow 验收检查清单](references/Workflow验收检查清单.md)；
- 业务界面：完成模板检查、交互检查、部署终态和反读，并读取 [业务界面验收检查清单](references/业务界面验收检查清单.md)；
- 整体场景包：读取 [场景包验收检查清单](references/场景包验收检查清单.md)。

验证范围由场景包实际采用的资产决定。每个被采用的资产都具备与其风险匹配的验证证据。

### 发布场景包

发布前反读场景包，确认：

- `apc_skill` 对应最终业务终点和路线设计；
- Skill 文件均有明确读取时机；
- 引用资产存在、可访问且状态正确；
- 实际存在的 Workflow、编排、Dataset 和业务界面通过各自门槛；
- 高风险动作有授权；
- 工单记录了验证结论和剩余盲区。

调用 `scene_package_manage(action="online", task_id=<task_id>, scene_package_id=<scene_package_id>)`，再用 `get_asset` 反读线上状态。发布验收由业务闭环、资产关系、专项验证和线上反读共同决定。

### 可选的真实 Max 项目验证

真实项目会启动真实 Agent、FastAgent、工具和外部副作用，必须在用户批准后执行：

```text
manage_goalfymax_project(action="run", task_id=<task_id>, ...)
```

是否传 `workflow_input` 以及如何启动，与目标场景包实际执行方式保持一致。普通 SA 场景使用普通对话入口，Workflow 场景使用其真实公开输入。

复用返回的 `project_id` 执行 wait、status、reply 或 confirm。Max 明确返回 `needs_input=true` 时发送回复；轮询和小修复沿用原项目。

运行后使用 `get_project_execution_logs` 检查 summary、detail 和 outputs。业务目标、具体资产和交付物根据日志与验收标准分别裁决。用户跳过真实项目时，记录 `full_validation_skipped`、用户决定和剩余盲区。

### 关闭工单并交付

最终检查点至少记录：

- 场景包 ID、名称、状态和核心能力；
- 业务终点、里程碑、候选路线和档案选路结论；
- 实际创建或复用的关键资产；
- 各专项验证裁决；
- 业务界面存在与否及其部署证据；
- 真实项目结果，或 `full_validation_skipped`；
- 工具缺口、未覆盖路径和后续建议。

不得记录密钥、Cookie、预签名 URL、原始敏感日志或内部挂载信息。调用 `task_manager(action="complete", task_id=<task_id>)` 关闭工单。

面向用户交付时结论先行：场景包是否已经创建或优化完成、核心能做什么、哪些证据支持、有哪些局限。只有实际通过发布与必要验证后，才能说“可直接使用”。

## 十一、异常处理与恢复

| 现象 | 根因判断 | 恢复方式 |
|---|---|---|
| 一开始就进入 Workflow 编写 | 把专项资产当成场景包目标 | 回到业务终点、里程碑、候选路线和整体蓝图，再决定是否需要 Workflow |
| 工具缺失、action 不存在或参数被拒绝 | Skill 与线上 MCP 版本不一致，或 MCP 未加载 | 重读实时 `tools/list`，按当前 Schema 修改调用，不虚构平行工具 |
| 返回未认证 | 环境变量未注入、密钥失效或客户端未重启 | 只检查变量是否存在和连接配置，更新后重启；不打印密钥 |
| 场景包资产越来越多但业务仍不清楚 | 缺少里程碑和职责归属，使用资产堆叠代替设计 | 停止创建，回到场景包蓝图，删除无独立职责的规划 |
| Agent 对所有用户走同一路线 | `apc_skill` 把参考 SOP 写成唯一流程，或没有档案选路规则 | 恢复候选路线和选路节点，明确最小档案事实与证据优先级 |
| Preview 失败 | Workflow 脚本、Schema、工具声明或文件来源不满足契约 | 只在场景确实需要 Workflow 时修复同一草稿，不复制新 Workflow 绕过 |
| bubble success 但验收不通过 | 本次路径跑通不等于业务语义、FA 内容和未触达分支通过 | 读取轨迹和覆盖率，按清单修复并重跑受影响路径 |
| 业务界面被 Workflow 状态阻塞 | 错误地把界面存在与执行资产耦合 | 只按开发者是否发布界面判断其存在，再单独处理界面实际消费的公开契约 |
| 模板或源码包下载失败 | 短链过期、大小不符或归档不安全 | 重新请求当前模板并从下载校验开始，不在残缺包上补丁 |
| 部署超时或状态未知 | 部署任务仍在运行或查询中断 | 保存并复用同一 `deployment_id` 查询 `status`，不重复部署 |
| 真实项目等待输入 | Max 明确返回 `needs_input=true` | 复用同一 `project_id` 发送 reply 或 confirm |
| 修改后出现新的绕行 | 只修症状，没有验证上层机制和受影响路径 | 回到分层诊断，修复信息归属、资产边界或运行机制根因，再做回归 |
