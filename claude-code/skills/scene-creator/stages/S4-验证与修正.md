# S4 验证与修正

三层验收、草稿态端到端全真滚动、问题单消化与结果检查表闭合。

## 1. 验证总览

发布前读取 [场景包验收检查清单](../checklists/场景包验收检查清单.md)，把 `apc_skill`、Skill 文件、任务点、工具集、FastAgent、工具组、数据集、编排型 TPE、业务路线、交付物作为**一个业务闭环**完成前三层候选验收。逐项确认前期确认的每个里程碑、候选路线、业务路线图、交付对象、审阅责任、审阅动作、介入点、前置检查、授权和到达标准，都能在真实资产里找到对应承载；后续发生的任何实质变更都有开发者重新确认记录。

**S3 与本阶段是反复回路**：S3 交来的是“制作完成”的资产（Preview 过、业务路线保存过），本阶段从单条编排型 TPE Bubble 开始逐层验证；任一层失败，回 S3 对应节修同一份资产（改脚本回 S3 第 4 节、改业务路线回 S3 第 7 节、改依赖回 S3 第 1–2 节），再回本阶段重验，直至第四层收敛。回跳沿用原 `stage_exit` 记录，不重复落账。

**完整证据固定分为四层，不得互相替代：**

| 层级 | 必查内容 | 能证明 | 不能证明 |
|---|---|---|---|
| 1. Preview / 静态契约 | 资产反读、脚本、输入输出 Schema、工具引用、按需业务事件声明与静态生命周期、按需业务路线保存与接缝 | 当前资产和静态契约可保存、引用闭合 | Provider 真实返回、事件持久化、路线运行 |
| 2. 工具取样 / 依赖证据 | 安全低副作用工具的真实输入输出、依赖状态和权限 | 代表性依赖在当前环境可调用，候选 `_output` 有真实样本 | 整条编排型 TPE 或其他输入正确 |
| 3. 制作期 Bubble | 先逐编排型 TPE 检查当前路径的步骤、文件、输入输出、按需持久化业务事件和覆盖率，再逐路线检查真实图控制、表单、Delivery/Artifact 与终态 Review 接缝 | 当前版本当前输入的节点数据管路与路线控制接缝成立；带事件时可证明验证事件链成立 | FastAgent 真实内容、被阻断的外部副作用、未触达分支、正式业务运行 |
| 4. 场景包端到端真跑 | 在草稿态目标版本上、真实项目里**经入口表单直跑（`submit_data`）启动业务路线**：路线运行时真实派发、运行中业务表单、Agent 介入、FastAgent 真实内容、工具真实调用、业务事件、Delivery 冻结与最终审阅；再以聊天入口跑一次核路由；对照结果检查表（第 6 节）与计划书（3.4） | 场景包在真实路线运行时里按计划书跑通并交付 | 未运行情景和未来输入都正确；应用前端与 SDK 三次握手、回流入库（app-creator A4） |

**第四层端到端全真是上线（定稿并真正上线）的前置**：全部通过后才进入 S5 的上线门。没有第四层真实日志时，只能记录前三层通过和整图运行盲区；**禁止**用多条单条编排型 TPE 的运行证据拼接成整图运行证据。第四层经表单直跑走的是真实路线运行时：运行中表单、业务事件、Delivery 冻结、Review 这些 Runtime 接缝在这里真实验证；app-creator A4 只再验应用前端与 SDK 三次握手、回流入库，不重复验路线运行时。

前三层候选验收的裁决口径不变：critical 全部关闭；warning 已修复或经开发者明确接受；发布范围内资产与前三层证据一致；被跳过或被平台阻断的项都有明确影响说明和后续条件。

开发者选择跳过端到端全真时，**必须**记录跳过决定、FastAgent 内容盲区、未触达分支和副作用盲区（`full_validation_skipped`）；**存在该标签时不得上线、不得结单**（见路由器 8.3），**禁止**声称已有全真证据。

## 2. 三层验收

### 2.1 Preview 与静态契约

第一层证据：资产反读、脚本 Preview、输入输出 Schema、工具引用、业务事件静态生命周期（S3-4.3 的条件硬门）、业务路线保存反读与静态接缝检查（S3-7.2）。

### 2.2 工具取样与依赖证据

第二层证据：安全低副作用工具的真实调用取样（S3-2.2）、依赖状态与权限确认（S3-1.2 两道检查）。脚本直接调用的复用外部工具，有取样记录（安全只读的）或契约读取记录（不可取样的）时第二层证据更实；没有也不算未闭合——但冒泡阶段出现"参数格式不对""路径不存在"这类错误，多半是这一层省掉了，回 S3 2.2 补。

### 2.3 单条编排型 TPE Bubble

第三层第一段：逐编排型 TPE 执行 S3-4.3 闭环的第 6–8 步，取得终态轨迹并做语义验收。

带业务事件的编排型 TPE，单条 Bubble 必须读取 `run_evidence.business_events`：核对脚本声明的事件、已持久化事件、缺失必需事件、未触达事件、顺序与持久化裁决。只有数据库持久化成功的事件才能计入；实时投递成功本身不算证据。本次路径缺少 `stage_started`、缺少 `stage_result/stage_failed` 终态或顺序错误时，Bubble 必须失败。Runtime 自有的 `artifact_ready` 与 `delivery_ready` 不属于单条脚本生命周期门；它们在路线级 Bubble 中分别以 Artifact 登记和 Delivery 冻结后的真实事件为证。无业务事件的编排型 TPE 记录脚本事件检查为“不适用”，不得虚构空事件证据。

### 2.4 路线级 Bubble

全部节点完成单条编排型 TPE Bubble、业务路线保存反读并通过静态接缝检查后，对发布范围内的每条路线执行一次**路线级 Bubble**。它仍属于第三层制作期演练，不需要用户批准，也不替代第四层全真运行。调用顺序固定为：

1. 启动：`scene_package_manage(action="bubble", task_id=..., scene_package_id=..., orchestration_id=..., workflow_input=..., review_action_key=...)`。`workflow_input` 使用该路线的代表性入口根对象；只有 `delivery.review.type="agent_gate"` 时才传一个已声明的具体 `review_action_key`。
2. 轮询：后续只传同一 `task_id` 和服务端返回的 `run_id`，不得重复入口输入，不得创建或补写项目、Business、Runtime、表单或消息标识。
3. 回填：返回 `status="waiting_input"` 时，读取当次 `interaction.form_id/arguments`，再用同一 `task_id/run_id` 和 `formdata` 回复；每次只回答当前表单。
4. 终态：只有 `status="success"` 且 `validation.status="passed"` 才算路线 Bubble 通过；失败时优先读取 `failure_stage`、`repair_target`、`repair_action` 和可选的 `failed_node_id/failed_step_key`，按 `repair_action` 修正它指向的原编排型 TPE 或业务路线，再重新启动；只有 `repair_target="platform_runtime"` 时才按平台故障处理。禁止只看笼统错误自行猜修改入口，也不复用已结束的 `run_id`。

路线 Bubble 默认 `evidence_level="summary"`：只读取路线终态、节点与步骤计数、失败步骤错误、输出字段、事件覆盖摘要、Artifact 引用、Delivery 验证和 Review 结果。完整步骤输出、最终输出值和业务事件 Payload 仍保存在 Runtime；只有精简证据不足以定位失败时，才对同一 `run_id` 显式使用 `evidence_level="full"`。不得把完整证据默认塞入工单、记忆或最终交付，也不得因为默认响应精简就重复执行路线。

每条路线通过后，用 `task_manager(insert, entry_type="checkpoint")` 写一条精简证据——**建议一条路线一条检查点**：`orchestration_id` 与 `run_id` 各是单个标识，五条路线就写五条，各带自己的 `run_id`。把多条路线的标识用逗号合在一条里也能存，但工具会在响应里带 `format_warning` 提醒，而且 `complete` 按路线逐条核对时对不上——省下的那几次 insert 会在结单时还回来。把以下结构放入 `metadata`：`{"evidence_type":"orchestration_bubble_validated","scene_package_id":<真实场景包标识>,"orchestration_id":"<真实路线标识>","run_id":"<本次通过的真实 run_id>"}`。这不是人工自证：`task_manager(complete)` 会读取同一工单已有的工具调用审计，核对当前业务路线、`run_id` 和终态；缺失、失败、属于其他路线或早于最后一次业务路线修改的证据都会拒绝结单。结单成功响应中的 `completion_evidence.route_bubbles` 才是机器确认结果。

路线 Bubble 复用真实图 Runtime，检查节点依赖、mapping、扇出/汇合、运行中业务表单、持久化业务事件、Delivery 冻结、Artifact 登记和最终 Review。各节点仍使用既有 dry-run Bubble 语义：FastAgent 为桩，显式外部副作用由 `ctx.dry_run` 阻断；声明的 `sa_handoff` 只验证边界可跨越并记录为桩，不声称验证 Agent 判断；最终用户表单和 `user_gate` 使用真实结构化握手。当前路线 Bubble 的 Review 只接受终止本业务的 `complete_business` 或 `fail_business` 动作，不演练 `start_orchestration` 跳转；含跳转的路线保留到第四层全真运行验证。路线 Bubble 因此能证明本次输入下整图控制和交付接缝成立，不能证明 FastAgent 内容质量、被阻断的外部副作用或未触达分支。

### 2.5 证据强度分级

路线 Bubble 的验证证据带强度标记（如 `fa_stubbed`、`uses_shell`），按路线特征分级裁决：

- **纯工具链路**（不含 FastAgent 步骤）：桩跑证据即可放行进入第四层；
- **含 FastAgent 的路线**：桩跑证据只证明管路，**必须**在第四层全真中覆盖 FastAgent 真实内容后才算完整。

### 2.6 冒泡结论的引用纪律

引用冒泡证据时**必须**如实说明边界：Bubble 中 FastAgent 恒为桩，**不能证明任何内容质量**；桩值（空字符串、空数组、空对象、示例路径）可能触发脚本为真实异常准备的降级分支，使冒泡走过的路径与真跑不同——例如桩返回的示例底图路径与你传的素材对不上，脚本正确地走了“引用不存在、要求补拍”的拦截分支，成功路径反而没验到。处置是**换成与桩值对得上的输入重跑**把成功路径也覆盖到，不是改脚本去迁就桩，更不是拿拦截分支通过当成功。**禁止**以"冒泡通过"表述"质量可控"或"内容正确"；冒泡证明的只是当前输入下的管路与接缝。

## 3. 草稿态端到端全真滚动

### 3.1 授权与范围

场景包、需要的业务路线和上线前三层候选验收全部通过后，即可在**草稿态目标版本**上执行端到端真跑；不需要先上线。

第四层要验的是**路线运行时在真实项目里的运行**：只有经业务应用入口表单启动的路线才经过业务路线 Runtime——节点派发、字段映射、扇出汇合、运行中业务表单、Agent 介入、业务事件、Delivery 冻结、Artifact 登记、最终 Review 全在它手里；聊天入口直派编排型 TPE 时 Runtime 不参与、业务事件降级，验不到路线运行时。所以***第四层的主入口是表单直跑（`submit_data`）***，模拟的正是业务应用的首次提交，**不需要应用前端就绪**；聊天入口另跑一次只核路由。应用前端、SDK 三次握手与回流入库由 app-creator A4 验，不在本阶段重复。

一次性向开发者说明本轮真跑范围：要跑哪几条路线、每条用哪个入口表单与什么测试样例（来自计划书 ②③ 与 S1 3.2 的正例）、运行中表单打算怎么答、可能启动的全部编排型 TPE 与 FastAgent、费用与外部副作用，并询问是否真实运行。批准即为本轮滚动验证的**预授权**：修正环内的重复运行不再逐次询问；带业务事件的单条编排型 TPE 也按单节点路线申请和执行；**禁止**在每条编排型 TPE 的制作循环中逐条申请真跑。一次获批运行覆盖所选路线的完整业务路线、最终用户介入、Agent 介入、业务事件、Delivery 和 Review，**不把它拆成若干单条编排型 TPE 真跑，也不把带业务事件的编排型 TPE 改走聊天直派**。

草稿态真跑就是真实项目运行：外部副作用照常发生、FastAgent 照常计费，**必须**按约束 6 对待。

### 3.2 真跑四步：建项目、绑数据、看运行、拿结果

| 工具 | 用途 |
|---|---|
| `manage_goalfymax_project` | 在真实项目中挂载场景包并运行：`run` / `status` / `wait` / `send` / `reply` / `confirm` / `history` / `stop` |
| `get_project_execution_logs` | 读取真实项目日志与产物：`summary` / `detail` / `outputs` / `download` / `bundle`。`outputs` 帮你找产物：列 `/workspace/output`、每个编排型 TPE 节点的产物目录 `/workspace/task_agent/<taskpoint>/output/` 以及交付记录里登记的 artifacts；`download` 能拿项目 `/workspace` 下任何真实存在的文件（输入、挂载、缓存、密钥等受保护目录除外），路径不在 `outputs` 里也行，只要它存在 |
| `file_to_url(purpose="tool_test_fixture")` | 把本地测试素材换成文件引用，供 `run` 绑进项目 |

**① 创建项目并经入口表单启动路线（主入口）**（`submit_data` 里三个身份的来源：`orchestration_id` 填计划要跑的那条路线在 `orchestrations[]` 里的 id；`business_id` 由你生成，建议 `biz-<场景包简称>-<日期>-<两位序号>`，同一次业务实例的后续 `reply` 沿用同一个值；`form_id` 填该路线入口表单的 id；**`workflow_runtime_id` 不要传**，它由 Max Backend 生成，传了直接报错；`form_submit_id` 可不传，服务端按 `idempotency_key + form_id` 派生）：`manage_goalfymax_project(action="run", task_id, idempotency_key, scenario_package_ids=[<草稿态目标版本的物理行 id>], submit_data={...})`，**`task` 省略**——一次 `run` 创建一个真实项目、挂载草稿态目标版本，把 `submit_data` 当作业务应用的首次提交交给路线运行时直接启动路线，不经 SA。`scenario_package_ids` 必须且只能一个；反读确认挂的正是待验收那一行。`submit_data` 的字段按实时 Schema 填：入口表单所属的业务路线标识与表单标识、按该表单 `inputSchema` 填好的 `formdata`（用开发者确认的测试样例，不用验收话术）。***运行实例标识由服务端生成，任何情况下不由调用方传入***：首次启动只提交业务路线标识与入口表单；服务端校验并创建首批真实任务点后才回传运行实例标识；入口被拒或首批派发失败时不会也不得暴露预留标识；对话入口、Agent 介入和路线重入同样由服务端生成新标识；同一运行实例内的任务点、交互、交付和查询**必须**沿用同一标识。返回加密 `project_id`，后续 `status/wait/reply/confirm/history/stop` 与日志工具**全部复用它**，不要为了查状态或做小修反复新建项目。`idempotency_key` 必填，同一次运行的重试用同一个键；`mode` 与 `model` 建项目后固定。

**第二入口——聊天入口核路由**：主入口跑通后，再用 `task="<自然业务需求>"`（不传 `submit_data`）跑一次：`task` **必须**是自然、真实、可变化的业务情景，像最终用户直接提需求那样写——**禁止**验收话术，**禁止**指定编排型 TPE、FastAgent、工具名、内部 ID、调用顺序或分步方法，要让 SA 按 `apc_skill` 自己完成路由。这一跑只证明"聊天里能进到这条路线"（入口并存，reference 3.3）；带业务事件的编排型 TPE 在此入口事件降级是平台行为，不是缺陷，路线运行时的证据以主入口为准。

**② 用上传文件绑定数据**：情景需要素材（菜单、Excel、图片、历史文档）时，先逐个 `file_to_url(purpose="tool_test_fixture")` 取得 `file_ref`，在 `run` 里放进 `workspace_files`（每项 `purpose` / `file_key` / `file_name` / `relative_path`；`relative_path` 是目标项目数据目录下的**相对后缀**，***不要拼成 /workspace/...***）。表单直跑时每个文件**还必须**带 `formdata_pointer`：指向 `submit_data.formdata` 里现有 `null` 或空字符串占位字段的 JSON Pointer（如 `/menu_file`、`/attachments/0`），服务端上传完成后把真实 `/workspace/...` 路径写进该位置再启动；聊天入口那次不传 `formdata_pointer`，`task` 里按**文件名**引用附件。文件在 Agent 或编排型 TPE 启动前登记完成。测试素材来自开发者给的正反例（S1 3.2），不用虚构数据。

**③ 观察运行、异常与结果**：`status` 看当前状态，`wait`（单次 ≤45 s）等待推进，`history` 看对话与交互记录；运行中出现**业务表单**（路线声明的中途表单）时，用 `reply` 在同一项目、同一运行实例上提交按测试样例填好的结构化表单——到服务端业务确认才算答完；最终 Review 只用路线声明的动作 `confirm`；聊天入口那次 SA 追问用 `send` 回答；失控时 `stop`。日志与产物用 `get_project_execution_logs`：先 `summary` 看概览（阶段、Agent / 工具分布、等待与失败），再 `detail` 按 `log_type`（`system_agent` / `task_agents` / `fast_agents`）分页读原始日志定位问题，`outputs` 列产物、`download` / `bundle` 取回核对。异常分三类归因：**路由错**（SA 没走到该走的资产 → 看 `apc_skill` 与任务点描述）、**执行错**（FastAgent / 工具报错 → 看对应日志与依赖状态）、**产出错**（跑完了但结果不对 → 进第 5 节复盘与第 6 节对比）。

路线运行时专项核对（表单直跑到达终态后，逐项判定并记入工单）：节点派发顺序与依赖图一致；`delivery.mapping` 求值结果与产物一致；运行中表单在声明的节点出现、未声明处没有停顿；业务事件生命周期齐全（`stage_started` / `stage_result` 或 `stage_failed`，`artifact_ready` / `delivery_ready` 由 Runtime 自动发布）；Delivery 冻结、Artifact 登记与最终 Review 动作按声明生效；失败分支以结构化 `fail_business` 收口。

**④ 拿结果对比**：产物与终态对照结果检查表逐条判定（第 6 节）；再按 3.4 对照计划书做漂移检查。每次真跑的 `project_id`、情景、结论写入工单。

### 3.3 修正环

发现问题后，在**同一个草稿行**上修改并直接重跑，不需要每圈定稿或上线：

```text
草稿行真跑 → 分析（第 5 节）+ 漂移检查（3.4）+ 问题单（第 4 节）→ 修改草稿（回 S3 对应节 / 口径漂移回 S1）
     ▲                                                    │
     └────── 执行结构表条目指纹变化 → 回退 pending ──────────┘
```

- 修改脚本或结构后，执行结构表条目按 S3-4.4 回退 `pending`，仅对回退条目增量重挑战与重验；
- 结果检查表相关条目同步回退 `pending`，重跑后重新闭合；
- 修正环收敛（问题单无未处置 fail、检查表全绿）后，才进入 S5 定稿上线。

### 3.4 与计划书对比：漂移检查

每次真跑到达终态后，拿运行记录对照 S1 计划书（`build_book`，`stage="S1"`）的三章：

| 对照 | 看什么 | 漂移信号 | 处置 |
|---|---|---|---|
| ① 用户画像 | 运行中 SA / FastAgent 的用词、对象、假设是否落在画像里 | 用平台词对用户说话；把商家类型搞错；追问画像里已知的信息；产出不像给这类用户看的 | 用词与假设的问题回 S3（`apc_skill` / 提示词 / 规范文件）；画像本身写错回 S1 第 5 节 |
| ② 用户旅途 | 实际走过的里程碑、路线内的节点与停下来问用户的地方（表单直跑），以及聊天入口那次 SA 选中的路线，对照计划书 ②③ | 多走或少走了阶段；选路与人群不匹配；在计划书没安排的地方问用户，或该确认的地方没停 | 路线 / 任务点描述 / 业务路线回 S3；旅途设计本身错回 S1 |
| ⑥ 预计产出 | 交付物形态、业务字段、质量，对照计划书 ⑥ 与结果检查表 | 形态不同；缺业务字段、只给文件不给内容；质量低于正反例标准；红线被碰 | 资产回 S3；预期本身不合理或红线要调回 S1 |

漂移分两类处置：**实现偏离**——回 S3 修同一份资产再重跑；**口径偏离**——计划书要改，回 S1 第 5 节更新并重新确认，再改制作书（S2 7.2）与资产。三项都无漂移，本轮真跑才算“符合计划书”；漂移结论逐次写入工单，作为交付报告“效果结论”的依据。


## 4. 问题单（findings）消化

每次真跑到达终态后，读取本次运行的问题单：由平台按运行流转记录生成的结构化条目，每条包含类别、位置、证据、建议与严重级：

- **fail**：结构性底线违约（如拒绝产出却未给出理由清单、输出自相矛盾、话术承诺未兑现）。**必须**修复后重跑；不修复不得进入 S5。
- **advice**：优化建议（如相邻无依赖步骤串行执行、按真实耗时估算的并行收益）。由你结合业务判断是否采纳；不采纳时在工单记录理由。

问题单按条目指纹累加：已处置（`finding_resolved` / `finding_waived`）的条目在后续运行中不重复报告；`waived` **必须**带理由（路由器 8.3）。平台尚未提供问题单能力时，按第 5 节人工复盘并把发现按同一结构记入工单，不得虚构平台生成的问题单。

## 5. 运行结果三层复盘

与 `stages/S2-资产设计.md` 2.1 同样的三层方法：摘要建立概览 → 完整深读日志与产物 → 分析实际路线是否符合设计、工具调用是否合理、FastAgent 结果是否被有效采用、最终用户确认点是否正确、最终交付是否达到到达标准。

发现问题回到对应阶段修复并重验，形成"运行 → 分析 → 优化 → 回归"的闭环；闭环在草稿态内滚动（3.3），轮询和日志读取复用同一项目标识（3.2）。

## 6. 结果检查表闭合

对结果检查表逐条目执行闭合，**只处理状态为 `pending` 的条目**：

- **测试用例条目**（S1-3.3 转入的正反例）：以条目输入执行真跑或复用已有运行记录，对照期望产出判定。正例须产出与期望一致的交付；反例须正确识别并按预期方式处理（拒绝、改写或引导），**不得**产出反例描述的错误结果。含开发者在样例选择（S3-3.2）中确定的验收判定时，一并核对。
- **前端校验项不属于本表**：业务应用页面的验证在 app-creator A4 的应用结果检查表里；场景包的结果检查表只有 `test_case` 与 `orchestration_check` 两类。
- **业务路线校验项**：按路线级 Bubble 与全真记录核对交付、审阅与重入行为。

判定通过置 `passed`；确认不适用或开发者接受偏差时置 `waived` 并记录理由。**禁止**为凑全绿而放宽期望产出的判定标准；判定依据与运行证据记入工单。

## 7. 出口条件

以下全部满足后，按路由器 4.1 进入 S5：

- 发布范围内每条路线的路线级 Bubble 证据在案（`orchestration_bubble_validated`）；
- 草稿态端到端真跑到达终态，记录在案；含 FastAgent 的路线已按 2.5 在真跑中覆盖真实内容；3.4 漂移检查三项无漂移（或漂移已处置并重跑）；
- 问题单无未处置的 fail；
- 结果检查表全部 `passed` / `waived`。

以上全部满足后，按路由器 6.1 落一条 `stage_exit` 账，再进入下一阶段。
