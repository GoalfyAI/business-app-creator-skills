# 配置诊断检查清单

诊断场景包、TPE、工具集、FA 或工具的配置质量，要决定从哪层查起、查哪些维度时读。

本文档供 AI 诊断用户配置的资产时使用。诊断可以从任意层级资产发起，按策略逐层深入。

**诊断标准来源**：各层资产的配置范式、合格/不合格示例、诊断要点已在对应的配置详解文档（场景包、TPE、工具集、FastAgent、工具组配置详解）中详细定义。本文档定义诊断策略和流程——AI 应基于对各配置详解文档的理解来发现问题，而非对照固定清单逐条比对。

---

## 一、诊断策略

### 1.0 诊断边界

**诊断是审计，不是设计。**

- **可以做**：指出配置问题、分析能力缺口、建议调整配置层级的内容（Skill 文本、Skill 文件、工具集技能、TPE/FA 系统提示词等）
- **不可以做**：编造不存在的工具、设计新工具的参数结构、改写用户的工具描述或 MCP 接口

原因：工具和工具描述属于 MCP 层，是用户自己的服务和接口定义，不在场景包配置范围内。如果诊断发现能力缺口（如"该场景 SOP 的某个步骤没有工具能执行"），正确的做法是**指出缺口并说明需要什么能力**，而不是替用户设计工具。对于工具描述质量问题，**可以指出共性质量模式（如"多数工具描述缺少 When NOT to Use"）并结合 [工具组配置详解](../../agenticapp-tool-integration/references/工具组配置-选中工具与描述质量.md) 的标准给出合格示例作为参考**，但不逐个工具代写描述内容。

**只报确定性问题。** 每个诊断发现必须是从配置中可以明确判定的事实性问题，而非推测或偏好。如果某个检查项无法从当前配置信息中得出明确结论，跳过该项，不输出模棱两可的判断。宁可漏报不确定的，也不输出让用户白返工的误报。

**解释功能影响，不引用规范。** 每个改进建议必须解释"这样改对 Agent 执行有什么具体好处"，而非"因为规范文档要求这样做"。诊断的说服力来自对 SA/TA/FA 运行机制的理解——为什么某种写法让 SA/TA 更容易做出正确决策、为什么某种结构让调用方更高效地找到信息。禁止出现"为符合 XX 文档的格式要求"、"与规范模板保持一致"类理由。

### 1.1 诊断入口与递归深度

诊断可以从任意层级资产发起。**入口资产越高，需要递归诊断的层级越多。**

| 诊断入口 | 递归范围 |
| --- | --- |
| **场景包** | 场景包自身 → 每个 TPE（如有）→ 每个工具集 → 每个工具集下的 FA 和工具 → 跨层检查 |
| **TPE** | TPE 自身 → 下属工具集 → 工具集下的 FA 和工具 |
| **工具集** | 工具集自身 → 下属 FA 和工具 |
| **FA** | FA 自身 → 所选工具 |
| **工具** | 仅工具自身 |

### 1.2 三个诊断维度

每个资产从三个维度检查：

| 维度 | 检查什么 | 示例 |
| --- | --- | --- |
| **格式规范** | 配置是否符合模板和结构要求 | Skill 文本是否按需包含全局约束/场景索引/文件指南 |
| **上下级一致性** | 内容中引用的下级资产是否真实存在、信息是否越级 | 工具集技能提到的工具是否真的在工具集中 |
| **业务可行性** | 配置的能力是否足以支撑声明的业务目标 | 场景 SOP 的步骤能否被现有工具集和工具支撑 |

### 1.3 诊断路径

> **基础认知**：场景包挂路线、TPE 和工具集，工具集包含 FA 和工具。SA 始终看到场景包的 Skill 文本，Skill 文件按需读；工具集挂载时只看到描述，加载后才看到技能和工具。TA 看到 TPE 的提示词、输出要求和 Skill 文件。FA 只看到自己的提示词、工具和 Skill 文件。单个工具做什么、参数怎么填，只写在工具描述里。

**场景包诊断路径**（最完整）：

```
第一步：场景包自身诊断
├── 格式规范 → 必读 agenticapp-tool-workflow 的场景包配置详解
├── 上下级一致性（索引表 vs 文件、业务路线说明 vs 实际路线、TPE 路由表 vs 不在路线里的 TPE、场景 SOP vs 工具集/工具/FA）
└── 业务可行性（场景 SOP 的步骤能否被下级资产支撑）

第二步：逐个 TPE 诊断（如有 TPE）
├── 格式规范 → 先看 `get_asset` 的 `tpe_type`：`workflow` 是编排型，按 2.2 读编排型契约；其余是普通任务点，读 TPE 配置详解
├── 上下级一致性（普通任务点：系统提示词 vs 工具集、Skill 文件指南 vs 实际文件；编排型：脚本调用 vs 预加载工具集、事件声明 vs 脚本发布）
└── 业务可行性（TPE 的工具集能否支撑其执行流程）

第三步：逐个工具集诊断
├── 格式规范 → 必读 agenticapp-tool-integration 的工具集配置详解
├── 上下级一致性（技能内容 vs 实际包含的工具和 FA）
└── 业务可行性（描述声明的能力有无对应工具/FA 支撑）

第四步：逐个 FA 诊断
├── 格式规范 → 必读 agenticapp-tool-workflow 的 FastAgent 配置详解
├── 上下级一致性（系统提示词 vs 实际选择的工具）
└── 业务可行性（FA 的工具选择能否支撑其执行流程）

第五步：工具抽查
├── 格式规范 → 必读 agenticapp-tool-integration 的工具组配置详解
└── （工具无下级资产，无一致性和可行性检查）

第六步：跨层信息归属检查 → 见 2.6
└── 检查是否有信息放错层级或跨层重复
```

**TPE 诊断路径**：从第二步开始。
**工具集诊断路径**：从第三步开始。
**FA 诊断路径**：从第四步开始。
**工具诊断路径**：仅第五步。

### 1.4 诊断顺序原则

- **先自身，再下级**：先完成当前资产的三维度检查，再递归诊断下级资产
- **先格式，再一致性，再可行性**：格式问题最易判断；一致性需要对照下级资产；可行性需要理解业务意图，判断难度最高
- **每进入一个新资产层级，先读对应的配置详解文件**：配置详解包含配置范式、合格/不合格示例和模板，是判断质量的标准

## 二、各层诊断说明

以下说明各层诊断的关注点。每层的具体配置范式、合格/不合格示例和诊断要点见对应的配置详解文档。

### 2.1 场景包诊断

> **必读**：诊断前先阅读 [场景包配置详解](../../agenticapp-tool-workflow/references/场景包配置-名称描述工具集.md)（共四份，首份开头列了其余三份），掌握每个配置项的范式、合格示例和不合格示例。

- **格式规范**：名称、描述、全局约束、业务路线说明（如有路线）、TPE 路由表（如有不在路线里的 TPE）、场景文件结构、步骤类型标注、知识文件分离
- **上下级一致性**：索引表与文件的双向一致、业务路线说明与实际路线的双向一致、TPE 路由表与不在路线里的 TPE 的双向一致、场景文件引用的工具集/FA/工具/TPE 是否存在、加载模式合理性。有路线的包把路线里的 TPE 写成派发，判为问题：单独派发时运行不报错，但路线 Runtime 不参与，业务事件被抑制，现象是运行成功、页面没有进度、也没有交付和审阅
- **业务可行性**：场景 SOP 每步能否被下级资产支撑、TPE 处理的任务类型是否确实需要独立执行（而非 SA 直接处理就够了）

### 2.2 TPE 诊断

> **必读**：先看 `get_asset(asset_type="tpe")` 的 `tpe_type`，两类 TPE 配置的字段不同，诊断标准也不同。

**普通任务点**：读 [TPE 配置详解](../../agenticapp-tool-workflow/references/TPE配置-定位与输入输出.md)（共两份）。

- **格式规范**：名称、描述、输入要求清晰度、输出要求格式、系统提示词板块完整性（角色+执行流程+工具策略+输出要求+Skill指南）
- **上下级一致性**：系统提示词提到的工具集/FA 是否实际配置、Skill 文件指南与实际文件的一致性、不包含单工具描述或其他任务类型逻辑
- **业务可行性**：是否真的需要 TPE（而非 SA 直接处理）、所配工具集能否支撑执行流程、输入要求是否足够让 SA 构造高质量输入

**编排型 TPE**（`tpe_type=workflow`）：提示词、输入要求这些字段是空的，不算问题。读 [编排型TPE总契约.md](../../agenticapp-tool-workflow/references/编排型TPE总契约.md)、[单编排型TPE契约-脚本Schema与事件.md](../../agenticapp-tool-workflow/references/单编排型TPE契约-脚本Schema与事件.md)（共两份）和 [编排型TPE-Verify检查.md](../../agenticapp-tool-workflow/references/编排型TPE-Verify检查.md)。

- **格式规范**：脚本、`input_schema`、`output_schema`、`business_event_contracts` 是否符合契约
- **上下级一致性**：脚本调用的工具和 FA 是否都在预加载工具集里、事件声明与脚本发布是否一致、脚本传给 FA 的字段是否与 FA 的 `input_schema` 一致
- **业务可行性**：技术失败是否混进了合法的无结果状态、运行证据是否覆盖了关键分支

### 2.3 工具集诊断

> **必读**：诊断前先阅读 [工具集配置详解](../../agenticapp-tool-integration/references/工具集配置-名称描述与成员.md)（共两份），掌握每个配置项的范式、合格示例和不合格示例。

- **格式规范**：名称、描述、能力域划分、技能模板结构、Skill 文件归属
- **上下级一致性**：搭配模式和 FA 速查引用的工具/FA 是否实际包含、不越级包含单工具描述或业务 SOP
- **业务可行性**：描述声明的能力有无工具/FA 支撑、搭配模式的数据传递是否可行

### 2.4 FA 诊断

> **必读**：诊断前先阅读 [FastAgent 配置详解](../../agenticapp-tool-workflow/references/FastAgent配置-定位名称描述.md)（共三份），掌握每个配置项的范式、合格示例和不合格示例。

- **格式规范**：名称、描述、系统提示词板块完整性、输入参数定义、Skill 文件归属
- **上下级一致性**：提示词提到的工具是否都被选中、不越级包含单工具描述或上层场景逻辑
- **业务可行性**：是否真的需要 FA、所选工具能否支撑执行流程、调用方式是否正确

### 2.5 工具诊断

> **必读**：诊断前先阅读 [工具组配置详解](../../agenticapp-tool-integration/references/工具组配置-接入方式.md)（共两份），掌握工具描述的质量标准和迭代规范。

- **格式规范**：路由逻辑、防御性约束、参数描述、enum 使用、不在上层补充说明

> 工具无下级资产，无上下级一致性和业务可行性检查。

### 2.6 跨层信息归属检查

> **执行时机**：在完成所有层级的资产诊断后，进行跨层交叉检查。仅当诊断入口为场景包、TPE 或工具集时需要执行。

每条信息只写在一个地方，放在它跟着走的那一层：

| 信息跟着谁走 | 放在 |
| --- | --- |
| 单个工具（工具接口变了才变） | MCP 工具描述 |
| 工具之间、工具与 FA 的搭配 | 工具集技能 |
| 业务场景 | 场景 Skill 文件 |
| 任务类型的执行方法 | TPE 系统提示词、脚本或 TPE Skill 文件 |
| FA 的子任务 | FA 系统提示词或 FA Skill 文件 |
| 多个场景共用的领域知识 | 场景包知识 Skill 文件 |

据此检查是否有信息放错层级或跨层重复。核心关注：

- 单个工具的描述/参数是否只在 MCP 层（不在工具集技能或场景文件中重复）
- 搭配模式是否只在工具集技能中（不在场景文件中重复）
- 业务场景 SOP 是否只在场景 Skill 文件中（不在工具集技能中）
- FA 内部逻辑是否只在 FA 系统提示词中（不在场景文件或工具集技能中）
- 是否存在同一条信息出现在两个地方的情况

**有 TPE 时的额外跨层检查**：
- TPE 路由表中的 TPE 名称是否与实际 TPE 资产名称匹配，路线里的 TPE 是否被列了进去
- TPE 系统提示词中提到的工具集是否都在 TPE 工具集配置中
- 场景包知识 Skill 文件中的内容，TA 是否也需要（如需要，应在 TPE Skill 文件中提供）
- 任务类型级执行方法论是否在 TPE 系统提示词中（而非场景 Skill 文件中）
- 是否为 TPE 处理的任务类型多余地创建了场景 Skill 文件

### 2.7 名称注册与占位符检查

每个资产创建时自动获得注册名称（`mr_name`），格式是「来源前缀_资产类型_名称」，如 `GOALFYAI_TOOL_web_search`、`PRIVATE_FASTAGENT_xxx`。前缀区分官方和用户自建的同名资产。

配置文本（Skill 文本、工具集技能、TPE/FA 系统提示词、场景 Skill 文件）中引用其他资产时，推荐用 `[[[注册名称]]]` 占位符格式，保存时校验是否存在，运行时替换成注册名称。写原始名字能运行，只记为低级别建议：说明资产改名后引用会失效。编排型 TPE 脚本不用占位符，FA 用 `mr_name`，工具用 `name` 或 `mr_name`；业务路线说明写 `orchestration_id`，它不是注册资产。核心关注：

- 配置文本中引用的工具、FA、工具集是否使用了占位符格式（而非直接写原始名称）
- 占位符中的注册名称是否与实际资产的注册名称匹配
- 是否存在引用了已删除或未创建的资产的占位符
