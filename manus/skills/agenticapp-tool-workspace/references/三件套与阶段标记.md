# 三件套与阶段标记

改 `app.json`、`WORKSPACE.md`、`workspace.json`、阶段文档或方案页前读。

## 应用根里有什么

```text
<应用目录>/
├── app.json                应用名称与身份（id = business_ui_id）
├── WORKSPACE.md            工作区身份、current_stage、阶段文档索引
├── workspace.json          阶段标记正本（doctor 校验格式，开发观测读取）
├── scaffold-release.json   本应用实际采用的脚手架版本
├── docs/proposal/index.html  方案页（右栏「方案」；Studio 下没有）
├── docs/proposal/proposal.css  方案页固定样式（脚手架维护，不改）
├── docs/stages/            七份阶段文档
├── docs/history/           历史记录
├── frontend/
└── backend/
```

`.workbench/` 由工作台维护，不入库。

## 每个文件的规矩

| 文件 | 规则 |
|---|---|
| 三件套、方案页、阶段文档 | 一律由 `scaffold:init` / `scaffold:repair` 生成，之后只改状态和内容字段；手写的契约会逐条打回 |
| 身份 | `app.json` 的 `id` 与 `WORKSPACE.md` 的 `business_ui_id` 记同一个应用 ID。新写入是字符串；旧应用的数字写法仍有效（`84` 与 `"84"` 是同一应用）。G1–G4 可以是 `null`；进 G5 前用 `npm run scaffold:bind -- --business-ui-id <ID>` 原子回填，`<ID>` 原样用 `business_ui_manage(action="setup")` 的返回值（返回里的 `scaffold_bind_command` 就是这条命令）。数字与短码两种形态见入口的 `../../agenticapp-creator/references/平台对象与用词.md`「标识」 |
| 阶段文档 | 只用 `docs/stages/` 里已生成的七份，一个工作区阶段一份，不另建文件。② 的施工单、取舍和验收要求的答案、整版确认依据、验收条目、运行条件的花费算法都写进 G3 那一份。PRD 正本在方案页（Studio 下是开发文档 PRD）；确认版全文只在 G1 阶段文档存一次，之后各段写「依据 PRD 第 N 版」，只记和 PRD 不一样的地方 |
| `workspace.json` | 只有 `targets` 数组，按 G1–G7 顺序七项，每项只有 `name` 与 `status` |
| 阶段文档 front matter | `stage`、`stage_name`、`status`、`render_type` 等字段固定，只用约定字段 |
| 阶段名 | 以工作区里已有的为准，按 G 键对应，只改状态不改名 |

写入前重读受影响的文件，保留其他会话的新改动；有冲突先核对差异再写。

## 五段与七项

| 段 | 工作区阶段 |
|---|---|
| ① 需求确认 | G1、G2 |
| ② 方案 | G3 |
| ③ 制作 | G4、G5 |
| ④ 试用验收 | G6 |
| ⑤ 上线 | G7 |

## 状态怎么改

- 进入一段时，把它包含的第一项标 `in_progress`；段内每完成一项标 `passed`，失败标 `failed`。交棒时这一段的各项都应是 `passed`；没做的保持 `not_started`，阶段文档写一句原因。
- 退回到前一段：把那一段和之后各段已标 `passed` 的项改回 `in_progress` 或 `not_started`，阶段文档写明退回原因。旧的 `passed` 不算这一轮的结论。
- `workspace.json` 的 `status`、阶段文档 front matter 的 `status`、`WORKSPACE.md` 的 `current_stage` 在同一个动作里改，`current_stage` 指向正在做的那一项。契约不要求按顺序通过。
- 路线验证豁免（`route_verification_waived`）只记下这条路线没验证及原因，不算 `passed`。

## 两套取值

阶段标记（`workspace.json` 与 front matter 的 `status`）取 `not_started` / `in_progress` / `passed` / `failed`；阶段记录（`business_ui_stage` 的 `result`）取 `passed` / `partial` / `failed`。

| 这一项的情况 | 阶段标记 | 阶段记录 `result` |
|---|---|---|
| 做完，交棒条件都满足 | `passed` | `passed` |
| G6 交棒条件都满足，但有「未测」或开发者接受的「没通过」条目 | `passed` | `partial`（`completion` 逐条写这些条目与原因） |
| 没做成，或 G6 报告硬门不过 | `failed` | `failed` |

## 阶段文档和方案页各给谁看

`docs/stages/` 的七份给你和后续 Agent 存完整事实与证据，跳过的项对应文档只写一句跳过的原因；方案页给开发者看结论。两者要完整到另一个 Agent 只读它们（加上工单 checkpoint）就能接着做，不依赖聊天记录。

## 常见错误

| 错误 | 正确做法 |
|---|---|
| 把工作区已有的阶段改了名，和阶段文档路径对不上 | 阶段名以工作区为准，只改状态 |
