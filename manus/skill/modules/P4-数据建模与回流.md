> 细则正本。阶段文件 G1–G7 是唯一主线；本文只放 G 文件写不下的表格、契约、纪律清单与示例，在 G 文件点名时查阅。本文不含流程，不含进入与出口条件。

## 1. 业务应用数据集的业务面

***没有配套业务应用，就没有业务应用数据集。*** 它是用户点开应用时才 copy 出来的那份库；场景包单独运行时这份库根本不存在，业务应用数据集 FA 读到的只会是 `found=false`。所以计划书 ① 的业务终点里凡是"记下来 / 存起来 / 下次接着用 / 看历史成绩"这类目标，都以配套业务应用为前提——本章第一问"是否规划配套业务应用"就是这类目标的开关：规划 → 这些目标成立，数据面交 app-creator 线；不规划 → 这些目标从计划书移除，或改成"随交付给到用户的文件"，场景包里**不设计**读写数据集的路线与步骤、**不挂** `business_app_dataset` 工具集、脚本**不调**业务应用数据集 FA。资产目录里名为"××档案场景包""业务档案助手"的官方包属于业务档案产品线（另一套数据面），不是业务应用数据集，也不拿来替代它。

场景包规划配套业务应用（约束 8）时，最终用户的长期数据都在**业务应用数据集**里（app-creator 线制作模板，用户点开应用时各得一份）。计划书只回答**业务问题**——用画像的词，不谈字段落地：

| 问题 | 计划书里要写什么 |
|---|---|
| **如何作用** | 用户自己的哪些数据（门店档案、历史效果、禁用表达……）会影响路线怎么走、产出怎么写——逐项说影响的是选路、参数还是文案 |
| **何时用到** | 这些信息是发起时就该带上的（用户一填就有）、还是跑到中途才需要“看情况取”的——只做业务层面的区分，走表单还是走脚本读在 P4 第 2 节 决定 |
| **如何回流** | 哪些产出与效果数据应该留在用户的资产里供看板展示与下次参考、留成什么粒度、是直接生效还是先作草稿等用户确认（回流入库语义由开发者定） |

数据集里的表与列由 app-creator 线设计，但**列名与业务说明必须与本计划书的画像用词一致**——两条线各说各话，编排型 TPE 写回的字段应用就展示不出来。未规划配套业务应用时本节写“不适用”，并说明数据如何随交付给到用户。

## 2. 业务应用数据集读写的落地

计划书第 ⑤ 章只回答了业务问题；本节把它落到字段与通道：

| 计划书里的业务判断 | 落地 |
|---|---|
| 发起时就该带上的用户数据 | 进入口 `input_schema`，由业务应用在发起时带入，时机 1 见 P4 第 3 节——不为它起 FastAgent，也不在脚本里读 |
| 中途“看情况取”的数据 | 编排型 TPE 脚本调业务应用数据集 FA 读（P4 第 3 节 时机 2），每条业务流至多一次读；表单字段设可选、`found=false` 回退表单值 |
| 要回流的产出与效果数据 | 脚本收尾 `operation="write"`（P4 第 3 节 时机 3），`context_hint` 给唯一键；写回哪张表哪些列与 app-creator 线对齐，列名用画像的词 |

逐字段写进内部资产清单（6.2）与执行结构表（6.3）的对应步骤；未规划配套业务应用时本节不适用。

## 3. 业务应用数据集读写通道（为业务应用制作的场景包）

场景包配套业务应用（约束 8，app-creator 线）时，运行期的用户数据都存在**业务应用数据集**里——用户点开应用时从模板 copy 出的那份 PG schema，应用后端直连它，编排型 TPE 则经平台级的业务应用数据集 FA（cn-qa 现名 `Business_app_fastagent`，mr_name `GOALFYAI_FASTAGENT_Business_app_fastagent`，随 `business_app_dataset` 工具集一起上线；名字以 `get_asset(toolset)` 反读为准）读写同一份数据。它是**普通 FastAgent**：挂一个 HTTP 工具 `query_business_app_dataset`（经 max-backend → Hub → dataset-proxy 到库），**不进沙箱、不签凭证、没有 TTL**；由平台建一次，**包作者不用自制**。

**这是一个编排型 TPE 输入来源的设计决策，FA 调用要写在脚本里**——用法与脚本里调用任何其他 FastAgent 完全相同（`tool(...)` 显式调用 + 所在工具集进预加载清单），不是一套挂上就自动生效的特殊机制。 每条编排型 TPE 需要的每个业务输入，都由开发者在 S1 方案里决定从哪来、在 S2 落进 `input_schema` 与脚本：

| 输入来源 | 适用 | 怎么落 |
|---|---|---|
| **入口表单**（最终用户填） | 每次运行都会变、只有用户知道、数据集里没有的信息 | 进路线 /编排型 TPE 的 `input_schema`，由表单渲染 |
| **读业务应用数据集**（脚本调 FA） | 用户已经在应用里记载过、或能从历史数据推出的信息——本店信息、近 30 天效果、禁用表达、历史选题 | 脚本开头 `tool("GOALFYAI_FASTAGENT_Business_app_fastagent", operation="read", query="...", _output={...})`（mr_name 以反读为准），结果沿 node_output 流转给全部下游 |
| **两者组合兜底** | 数据集可能没有、可能不足 | 表单字段设为可选；脚本先读数据集，`found=false` 或所需字段缺失时**回退用表单值**；两边都没有时按通用策略执行或以 `stage_failed` 业务失败收口——回退顺序与缺失时的行为由开发者在 Plan 里定，不由脚本临场猜 |

脚本里的写法（正本是工具集使用指南与 FA 的 Skill 文件，运行时自动注入；这里只给形状）：

```python
ctx_data = tool("GOALFYAI_FASTAGENT_Business_app_fastagent",   # 必须写完整 mr_name，裸名解析不到
    _output={"type": "object", "required": ["found"],
             "properties": {"found": {"type": "boolean"},
                            "banned_words": {"type": "array", "items": {"type": "string"}}}},
    operation="read", query="读本店禁用表达清单")
banned = ctx_data["banned_words"] if ctx_data["found"] else input.get("banned_words", [])
```

- `_output` 按**本路线真正消费的切面**声明，必含 `found`；禁止"把表都读给我"式的大而全 schema；
- **每条业务流至多一次读**：结果沿 node_output 流转给全部下游，不逐节点重复取；
- 收尾**回写**同样写在脚本里：`operation="write"`，`context_hint` **必须**给出唯一键或幂等依据——业务路线重跑会让同一段写再执行一次；
- 不传 `sandbox_id`——它不进沙箱，传了也没有意义；`tool()` 里必须写完整 mr_name（`GOALFYAI_FASTAGENT_<name>`），裸名解析不到；
- 表不存在、查不到行、实例还没建、当前项目不是业务应用项目，都是 `found=false` 的常态结果，不重试、不报错、不编数。

**依赖声明**（是前置，不是使用方式）：脚本里用到的每个 FastAgent 必须在预加载工具集清单里声明（编排型 TPE 依赖规则）——把 **`business_app_dataset` 工具集**挂进该 TPE 的预加载清单，并过 1.2 的上线检查。

**三个时机的分工**（设计路线时按此归位，不要错配）：

| 时机 | 谁来做 | 走不走 FA |
|---|---|---|
| 项目启动铺底（门店信息、当前进度等上下文） | 应用后端直读 PG 拼进发起报文 | **否**——此时 agent 尚不存在；制作侧只需把这些字段放进 `input_schema` 供应用在发起报文里带入 |
| 执行中取数（需要理解业务语义的"要什么"） | 脚本调 FA（`operation="read"`） | 是——见上表第二行 |
| 收尾回写（交付结果与效果数据落库，供看板展示与下次运行参考） | 脚本调 FA（`operation="write"`） | 是 |

**两条纪律**：

- **`found=false` 是常态结果不是错误**：表不存在、查不到行都这样收口，下游必须把它当缺省处理（回退表单值或通用策略），***绝不因空数据 fail***；
- 写权由列注释声明裁决：FA 只写 `editable:agent` 列、模板结构只增不改（声明正本与写权矩阵见 app-creator 约束 9）。

## 4. 数据设计（本阶段的重心）

从一个已上线的场景包出发，设计出一个完整的业务应用：它是什么、给谁用、场景包给了它什么入口和出口、存什么数据、有几页、每页读什么写什么、字段的可编辑性怎么在页面上体现、文件在哪里出现。做法与场景包线一样：先向开发者要参考资料，再拿一份《业务应用计划书》（每页截图展示 + 后端功能阐述）给开发者确认，确认后才进入 A2 / A3 制作。

应用表是**用户的业务资产**。先分类，再逐表回答五问。

### 4.1 先把数据分四类，放对地方

| 类别 | 例子 | 放哪 |
|---|---|---|
| **用户自己的数据**（用户在应用里记载、编辑的） | 门店档案、账号绑定、素材索引、禁用表达、目标与偏好 | 业务应用数据集，列声明 `editable:user` |
| **场景包运行期所需 / 产出的字段** | 每次运行的选题、生成结果、效果指标、回写的统计 | 业务应用数据集，列声明 `editable:agent`；这些列是 S3-2.4 里编排型 TPE 读/写的对象 |
| **系统字段** | 主键、`created_at` / `updated_at` / `updated_by` / `last_run_id` / `row_version`、项目与 Runtime 关联 id | 业务应用数据集，列声明 `editable:system` |
| **界面意图与实体引用** | 草稿、筛选条件、当前 businessId、已读态 | `sdk.storage`（viewer × 实例隔离），**不进库** |
| 文案、路由名、开关 | — | 代码 |

***不要把该进库的数据写成前端 mock 数组、静态 JSON、后端常量或占位符***——这是脚手架的第一条数据纪律。

进库的表再按**实体 / 情境 / 历史事件**三类组织（长期慢变的经营对象 / 决定“这一次怎么做”的目标与约束 / 只增不改的运行与效果记录），情境与历史事件挂在实体上——这套约定的正本在场景包制作书 ⑧-6（business-app-creator P3 第 5.2 节），本节沿用它画出的运转链，不另起一套。

### 4.2 逐表五问

1. **存什么**：按 4.1 分类列出每列；看板要算的指标所需字段此刻就要有；“读历史数据优化后续选择”的预留字段也在这里定；
2. **逐列可编辑性**（约束 9）：`user` / `agent` / `system` 三态，**每列恰好一个写入方**——用户和生产都要写的信息，在模板阶段就拆成两列（用户填的 + AI 建议的），不靠运行期仲裁；
3. **审计**：每张有写入的表带四件套 + `row_version`；来源标记（`user_edited` / `generated`）落在哪列；
4. **冲突规则**：行级并发（用户在编辑页改用户列、生产同时重写产出列）靠 `row_version` 乐观锁——后写方重读重试；***没有“静默覆盖”这个选项***；
5. **回流入库语义**：生产产出**直接入库**还是**先作草稿、用户在编辑页确认后入库**——按业务风险定（对外表达类建议草稿确认，内部统计类可直接入库）。

### 4.3 文件怎么进数据面

数据集**只存路径与元数据，不存文件体**。三类文件各有来源与归属：

| 文件 | 从哪来 | 存什么 | 谁能改 |
|---|---|---|---|
| 用户现场上传（Excel、图片、素材） | 入口表单经草稿句柄 `project.upload` → 返回 `/workspace/...` 路径（项目级，属于这一次生产） | 表单值就是路径；要作为用户资产长期引用时，在数据集里存路径 + 文件名 + 上传时间（`editable:user`） | 用户（替换 / 清除） |
| 应用级持久文件（品牌手册、素材库、历史资料） | 应用内任意位置经 `sdk.file.upload` → 返回 `path`（不依赖项目、跨项目复用；`list` 能翻历史） | 表单值 / 数据集只存 `path` + `name` + `size` + 上传时间（`editable:user`）；作为编排型 TPE 输入时把 `path` 写进 formdata，宿主登记给目标项目 | 用户；源文件不因关联项目而移动或删除 |
| 过程交付物 | 编排型 TPE 写进 `ctx.output_dir`，经 `delivery.mapping` 登记为 `PublicDelivery.artifacts[].workspace_path` | 回流时存路径 + 所属 Runtime / delivery_id（`editable:agent`） | 生产（每次运行新增，不覆盖旧交付） |
| Runtime 用户文件 | 用户在执行记录页对某次运行补传/删除（`userFilePaths`，全量替换语义） | 不单独建表，读 Runtime 权威值 | 用户，经保留件 `useRuntimeUserFiles` |

产出：业务应用数据集模板草案（表 / 列 / 类型 / 逐列声明 / 审计字段 / 文件路径列），交 A2 落成真实模板。

## 5. 工作集是什么

开发者自己造模板的沙盒：`open` 给你一个**独立 PostgreSQL schema** 和 **2 小时有效的写连接串**，可以用 ORM/psql 建表、灌样例、跑查询；也可以不碰连接串，用 `create_table` 声明表。它**不是通用数据集**：不占配额、不出现在数据集列表、不给最终用户用。`extract` 从工作集的真实结构抽成**固定版本的模板**——只抽结构（表、列、类型、主键、注释、关系），不带样例数据、视图、索引；用户点开应用时系统照模板给每个用户建一套自己的库（`bui_{data_uid}`）。

## 6. 制作步骤

1. **开工作集**：`open(name=<模板名>, description)`，记下 `data_uid`。返回的连接串是凭据——***不进工单、不进聊天、不进代码***；过期用 `connect(data_uid)` 重签，已知目标应用时传 `business_ui_id` 让平台校验绑定，防止两个应用的库串用。
2. **逐列打标**：每列先按 P4 第 4.1 节 的四类归位——用户自己的数据 → `editable:user`；场景包运行期所需 / 产出 → `editable:agent`（这些正是 business-app-creator S3-2.4 里编排型 TPE 读写的列，列名要和场景包侧对齐）；主键 / 审计 / 关联 id → `editable:system`。界面意图（草稿、筛选）**不进模板**，那是 `sdk.storage` 的事。文件只存路径列（`text`）+ 文件名 + 时间，不存文件体。
3. **建表**（两种方式可混用）：
   - **声明式（推荐）**：`create_table(table_name, target_columns=[...])`。每表**至少一列 `primary_key=true`**（生成型代理主键用 `bigserial`）；类型写 PG 精确类型（`character varying(120)` / `numeric(10,2)` / `timestamptz` / `jsonb`）；***每列 `comment` 必填，且以 `[editable:user|agent|system] ` 开头再接业务说明***（约束 9）——它会写成 PG COMMENT 并随模板 copy，是应用后端与业务应用数据集 FA 读到写权声明的**唯一渠道**，漏写 = 该列被按最保守的 user 处理、生产写不进去；
   - **连接式**：用写连接 ORM/psql 建表、灌**最小真实样例**、跑 A1 设计的典型查询（看板聚合、编辑读写，`statement_timeout` 10 s 内）——样例只用于验证，不进模板。
   - **每张有写入的表带审计四件套 + 行版本**：`created_at` / `updated_at` / `updated_by`（`user|agent|system`，声明 `system`）/ `last_run_id`，加 `row_version` 做行级乐观锁——用户在编辑页改用户列、生产同时重写产出列时，靠它让后写方重读重试，而不是字段级仲裁。
4. **声明关系**：`set_relations(relations=[{source_table, source_column, target_table, target_column, relation_type}])`，整体替换、按表名。
5. **反读**：`inspect(data_uid)` 读回真实结构，逐表逐列核对类型、主键、**每列 comment 的声明可见**；与 A1 草案不一致时改到一致（`drop_table` 重建或经连接 ALTER），不带着偏差往下走。
6. **抽模板**：`extract(data_uid, template_name, template_description)`。首次不传 `template_id` 即新建模板；修订已有模板时传 `template_id` 给它**出新版本**（整数版本号递增；缺省沿用本工作集上次抽出的模板）。记录返回的模板 id 与版本号——A4 挂载、A5 交付报告都要用。
7. **挂载**（A4 创建 business_ui 后）：`business_ui_manage(update, business_ui_id, dataset_template_id, dataset_template_version)`，版本钉整数号、***禁止 follow latest***。
8. **不要在这里 close**：工作集要一直留到 A5 交付之后——A3 后端本地开发用的连接串就是它，A4 `deploy` 给开发者容器注入的也是它（`database.purpose=template_workspace`）；这里 close 掉，A3 没库、A4 退化成按模板新建空实例、A2 灌的验证样例全丢。收工动作在 P7 第 12 节 结单前。

**本地验证时的连接纪律**：写连接经 dataset-proxy，`BEGIN` / `COMMIT` / `ROLLBACK`、`SET ROLE`、`SET search_path` 都会被直接拒——autocommit 单条语句，要原子性就压进一条 SQL（CTE、`INSERT ... ON CONFLICT`、单条 `UPDATE ... FROM`）。A3 后端本地开发用的连接串就是这里 `open` 出来的，填进 `backend/.env`（模板 `backend/.env.example`），***不进工单、不进代码、不进聊天***。

## 7. 定稿门与变更纪律

- **定稿确认**：把 `inspect` 结果翻成业务语言交开发者确认——每张表存什么、哪些列用户能改、哪些列生产写、审计怎么查。确认后才 `extract`；
- **模板版本一旦被上线的 business_ui 钉住就不可变**：改结构 = 工作集里改 → `extract` 出新版本 → business_ui 出草稿改挂载版本 → 重新 deploy / finalize（A5 修订节）；
- **破坏性变更必须带迁移脚本**：与上一版 diff 为破坏性（删列 / 改类型）时，`extract` 必须随带 `migration_script`（`v{上一版}_to_v{新版}.sql`：幂等、单事务、只动本 schema、**不得建外键**），否则被拒并返回 diff。脚本挂在模板版本链上，business_ui 定版时校验升级链完整并在临时库**真跑一遍彩排**（失败即 `BUSINESS_UI_UPGRADE_REHEARSAL_FAILED`）；存量用户实例沿版本链**只往前升、没有降级**——回滚钉回更老的模板版本会被 `BUSINESS_UI_TEMPLATE_REGRESSION` 拒绝，要回退就把旧结构重新抽成一个新版本。所以：新增列 / 新增表优先，删列改类型先问“存量用户的数据怎么迁”，这是产品决策，进拍板；
- **换模板家族 = 换库**：把 business_ui 从一个模板家族换绑到另一个会被 `BUSINESS_UI_TEMPLATE_SWITCHED` 拒绝——那种情况请新建业务应用；
- 应用代码禁 `CREATE / ALTER TABLE`（约束 4），结构变更只走本节。

## 8. 一期红线（仍然成立）

- **一个业务应用只绑这一个数据集**：写权限是项目级放开的，多绑一个长期数据集就多放开一个写面；
- 应用角色**没有 DDL 权限**（数据库层拒，不靠自觉），表结构的唯一出口就是本节的模板；编排型 TPE 侧 FA 的“只增不改”仍靠提示词与本节纪律共同守住。
