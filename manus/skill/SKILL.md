# 业务应用开发指南（总入口）

> 版本：v3.0（2026-09-08）｜ 框架蓝本：钉钉《业务应用开发：七阶段流程与对象生命周期》与《Skill 框架设计》。本 Skill 是**一个主导入口、七个阶段、按需调用的八个专业模块、一套共享协议**。旧 scene-creator（能力容器制作）与 app-creator（应用制作）的全部内容已归位到模块层与协议层。

## 0. 这份 Skill 做什么

把业务目的变成**最终用户能持续使用的业务应用**：它包含一个能力容器（平台里叫场景包：挂着工具集、任务点、业务路线与知识）、一份业务应用数据模板、以及前后端应用。对开发者只说"业务应用"；"场景包"只在工具调用与资产关系里出现。交付物 = 能力容器版本 + 应用版本 + 数据模板版本 + 验收记录。

重构解决的四个缺口：认知顺序不连贯（两套计划书、阶段、检查表要开发者自己拼）；决策与实现过度捆绑（厚制作书一次确认才建设，但关键认识要靠试验、预览与实际操作形成）；证据彼此断开（节点、路线、数据库、页面测试之间没有一条承诺贯穿）；使用与优化缺少统一归位（恢复、修改、复用、反馈可靠性从设计开始，不上线后补）。

## 1. 总入口负责什么

1. **识别任务**：新建、接续、修订、诊断、能力试用、仅讨论。"仅讨论"不触发资产创建。
2. **盘点已有材料、资产与证据**，从最早未满足的必要条件进入，不机械从 G1 重做。
3. **每阶段给出**推荐下一步、理由、待决策事项、验收依据；平台术语由 Agent 转译。
4. **控制范围、权限、试验费用与副作用**：到必要决定点暂停，其余已授权工作连续推进。
5. **专业模块失败时返回明确的问题归属与证据**，不把失败转述为"请开发者自行处理"。
6. **最终验收整套业务应用**，不把能力容器工单结单误认为应用已交付。

### 1.1 任务识别

| 开发者要做什么 | 任务类型 | 工单 | 从哪进 |
|---|---|---|---|
| 把业务目的 / SOP / 经验 / 参考项目做成业务应用 | 新建 | `write` | G1 |
| 继续此前未完成的制作 | 接续 | `get` 原工单 | 最新 `stage_exit` 所在阶段 |
| 改已上线应用的页面 / 接口 / 表 / 路线 / 能力 | 修订 | `write`（先取可编辑草稿） | 受影响的最早阶段（协议一 C3） |
| 效果差、报错、数据不对、页面异常 | 诊断 | `read`（转修复新建 `write`） | P8 定位后路由到所属阶段 |
| 验证一个外部能力值不值得做进来 | 能力试用 | `write` | G2（P2 的 ST 流程） |
| 只想讨论方案、问概念 | 仅讨论 | 不建工单 | 不进阶段，不创建资产 |

先看总入口协议四 §1 的工单 Gate；意图或关键参数缺失时先问（缺口六类：意图 / 关键参数 / 知识 / 工程偏好 / 产品决策 / 授权，见 P1 的 S1 §2.2）。

### 1.2 前置：工具可用性

business-app-creator 的 MCP 工具在会话开始时已在工具列表里。用某个工具前先确认它存在；**当前看到的工具定义是唯一事实**（协议一 F5）。找不到的工具不得假设存在。确认凭证只做只读查询。

## 2. 七个阶段

```text
开发者提供业务目的、材料或已有应用
  ▼
G1 业务目标与范围        明确用户、结果、边界与好坏样例          验收：做什么、不做什么、合格结果对齐？    否→补事实或改范围
G2 关键能力可行性        真实工具和模型试验；必要时建隔离试用包    验收：关键路径有证据、缺口有处置？        否→换能力或回 G1
G3 运行设计与验收基线    路线、人机分工、数据、页面状态联合设计    验收：行为可理解、边界、实现映射、测试标准齐？ 否→改设计或回 G2
G4 核心执行单元验证      准备依赖与能力容器草稿；创建并验证 TPE    验收：单元契约与实际输出成立？            否→修同一资产
G5 后端业务闭环验证      组装路线真跑；数据模板、后端、验证实例    验收：执行、交付、入库、恢复在真实环境闭合？ 否→定位单元 / 路线 / 数据
G6 用户操作闭环验证      实现完整界面；接通 SDK、状态、修改与历史  验收：用户能完成、能修改、能继续？        否→修界面或回 G5
G7 预发布与交付          最终部署物完整验收、版本核对、授权上线    验收：承诺、证据、版本、授权与交付一致？   否→回问题所属阶段
  ▼
交付可持续使用的业务应用 ──真实问题与效果证据，确定影响范围后重入 G1（P8）
```

| 阶段 | 文件 | 进入依据 | 主责模块 |
|---|---|---|---|
| G1 | `stages/G1-业务目标与范围.md` | 一句目的 / PRD / SOP / 参考项目 / 已有应用问题任一 | P1 |
| G2 | `stages/G2-关键能力可行性.md` | G1 基线成立，未知项可列成试验问题 | P2 / P6 |
| G3 | `stages/G3-运行设计与验收基线.md` | 关键能力足以选路线 | P1 / P3 / P4 / P5 / P6 |
| G4 | `stages/G4-核心执行单元验证.md` | 当前切片设计与验收标准已确认，制作授权明确 | P2 / P3 / P6 |
| G5 | `stages/G5-后端业务闭环验证.md` | 单元通过适用验收，契约与 G3 一致 | P3 / P4 / P5 / P6 / P7 |
| G6 | `stages/G6-用户操作闭环验证.md` | 后端闭环成立，页面设计与真实契约一致 | P5 / P6 |
| G7 | `stages/G7-预发布与交付.md` | 使用闭环通过，发布范围与版本关系确定 | P6 / P7 / P8 |

**阶段文件读取纪律**：进入任何阶段的第一个动作是完整读取该阶段文件；一次只读一份；出口条件满足后落 `stage_exit` 再进下一阶段；修正环内的回跳沿用原记录。每个阶段固定七项：进入依据 → 本阶段建设 → 给开发者看什么 → 要确认哪些边界 → 门禁 Checklist → 证据与结论 → 失败回退。

**平台对象什么时候创建**（不提前建空容器，不用漂亮页面替代单元证据）：

| 对象 | G1–G3 | G4 | G5 | G6–G7 |
|---|---|---|---|---|
| 能力容器（场景包） | 确定能力边界、路线、依赖、知识归属；G2 可用标识明确的试用包 | 创建 / 复用正式草稿，反读继承 | 挂载已验单元、组装路线、整包真跑；达标且授权后定稿上线 | 应用绑定明确版本；契约变化触发受影响测试 |
| 工具组 / 授权卡 / 工具集 / FastAgent / 普通任务点 | 摸底、取样、判断职责与依赖 | 按真实依赖创建或复用；共享资产在副本改 | 在完整路线中验证实际调用 | 保留引用与版本记录 |
| 编排型 TPE | G2 验关键能力；G3 定职责、步骤、输入输出、失败出口、测试例 | 草稿与依赖就绪后创建；Preview、单条 Bubble、语义验证 | 作为路线节点补足整链真实证据 | 应用只消费其公开业务信息 |
| 业务路线 | G3 定入口、依赖、并行汇合、介入、交付、审阅、重入 | 可备设计稿，未验单元不写成正式路线 | 保存并反读；路线 Bubble → 全真 | 页面启动、应答、交付与当前契约一致 |
| 业务应用数据模板 | G1 定留存价值；G3 定表、字段、归属、写权、回流、下一轮读取点 | 可按设计准备结构，不混入正式数据 | 建工作集、提取模板版本、实现后端、建验证实例、验双通道读写 | 用户实例与正式数据隔离；迁移与版本绑定随交付 |
| 业务应用 | G1 定持续使用方式；G3 设计页面、状态与可操作预览 | 需要时准备脚手架 | 创建 `business_ui` 草稿与最小验证部署物 | G6 完整实现旅程；G7 复验、定稿、反读入口 |

## 5. 两层 Checklist

- **G 门禁**（`checklists/G门禁检查清单.md`）：回答"是否具备进入下一阶段的条件"，44 条，每条只有查什么 / 证据 / 不过怎么办三列；引用 U 项分阶段结论，不替代业务行为。
- **U 业务行为验收明细**（`checklists/U业务行为验收明细.md`）：U1 开始续用与历史、U2 信息准备与真正使用、U3 Agent 连续推进、U4 离开与异常恢复、U5 结果检查与反复修改、U6 留存偏好与效果回传、U7 跨应用 Agent（条件适用）、U8 临时编排（条件适用）；G3 实例化为本项目用例，G4/G5/G6 分层取证，G7 复验。
- **专业验收清单**：`checklists/方案挑战检查清单.md`（G3）、`checklists/编排型TPE验收检查清单.md`（G4）、`checklists/场景包验收检查清单.md`（G5a 能力容器上线门）、`checklists/应用验收检查清单.md`（G5b / G6 / G7）。

## 6. 贯穿七阶段的四项横向设计

1. **使用问题是开发要求**：U1–U6 按 G1 定价值、G2 验前提、G3 定行为、G4/G5 做能力、G6 验使用、G7 验最终版本；U7/U8 不是自动加入的必备功能，纳入承诺时 G2 必须验前提。
2. **优化能力与"优化已经有效"分开**（协议四 §3）。
3. **两类知识、两类问题分开存放**（协议四 §2）。
4. **展示—确认—执行—验收连起来**：不是每步都让人点确认（协议一 D3）；可视化是同一事实的不同视图（协议三 §2）；路线变更必须展示影响（协议二 §5）。
