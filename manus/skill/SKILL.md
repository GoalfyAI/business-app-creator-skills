# 智能应用制作
<!-- scaffold-min-required-version:v20260916-8941ec -->

> 本文件只放跨段规则、地图和路由。五段的做法在 `stages/`，其他任务入口在 `tasks/`，交给开发者的东西怎么写在 `design/`，平台机制在 `reference/`。平台参数以 MCP 当前 Schema 为准，长契约按需 `get_diagnosis_doc(topic)`；工程实现以当前应用模板的 README 与 package.json 为准。

## 1. 这个 Skill 做什么

为已有的 GoalfyMax 场景包制作、修订、诊断智能应用。智能应用交给一类明确的使用者持续使用：在约定范围内稳定完成一类反复发生的工作，下一次使用时复用已确认的信息。交付物是下面四样的版本加验收记录：

| 组成 | 是什么 | 使用者感受到的 |
|---|---|---|
| 前端应用 | 脚手架上的页面，只经 SDK 与平台交互；必备页面见 [reference/前端页面.md](reference/前端页面.md)「必备页面」 | 看现状、发起一件事、拿结果、改结果、离开再回来 |
| 专属后端 | Express + PG，直连这个使用者自己的库 | 编辑自己的数据；看板统计；产出回流入库 |
| 数据模板 | 表、字段、逐列可编辑性（user / agent / system）；使用者首次打开时从模板复制出自己的一份 | 不用重复交代；可查看、可纠正 |
| 场景包 | 能力容器：业务路线、编排型 TPE、工具集与 FastAgent、`apc_skill` | 在必要节点补信息、做选择、审阅结果 |

应用里每一步由三类之一来做：**脚本**（平台已有的服务和工具，或这次写的代码；结果固定、不花模型费）、**模型**（要判断或要写作的步骤，按所选模型计费）、**人**（使用者在应用里补信息、选择、确认、审阅）。PRD 按这三类写「每一步谁来做」，写法见 [design/谁来做.md](design/谁来做.md)。

平台对象：发布单位是智能应用（`business_ui`）。它挂一个场景包和**必须一份**数据模板（至少一张业务表，见 [reference/数据模板.md](reference/数据模板.md)）；挂的场景包至少有一条路线。对象、标识、版本词、积分、工具与术语查 [reference/平台对象速查.md](reference/平台对象速查.md)。

## 2. 角色与用词

| 角色 | 是谁 | 做什么 |
|---|---|---|
| 开发者 | 用本 Skill 制作、维护应用的人；懂业务，一般不懂代码 | 确认 PRD 和整版方案、看验收报告说「可以上线」、决定是否发布 |
| 需求方 | 提需求但不操作 AI 的人，可以就是开发者本人 | 不是同一人时，PRD 和验收报告里「好不好你说了算」的几条请需求方看过 |
| 使用者 | 应用发布后使用它的人。每人安装后用自己的一份，从空库开始、数据互不相通；平台没有组织和团队，一个应用里没有提交、审核、复核这类多人分工 | 只在确认过的入口、表单、审阅节点参与运行 |
| 你 | 执行本 Skill 的 Agent | 调查、核实、制作、验证；准备选择题和推荐答案，**不代替**开发者决定 |
| 运行 Agent | 应用运行时在场景包里执行任务的 Agent | 按已确认的设计执行 |

- **主语**：开发期的确认、授权写「开发者」；运行期每一步写「使用者」或「运行 Agent」，人的步骤写「人① 使用者」。不单独写「用户」，按实际指代写「使用者」或「开发者」。
- **部署、上线、发布各指一件事**：
  - 部署：`business_ui_bundle(action="ship")` 把草稿放到开发者自己的在线预览，在 ④ 做，要开发者单独授权（见「红线」）。
  - 上线：开发者说「可以上线」后你 `business_ui_manage(action="finalize")`，在 ⑤ 做；这一版成为开发者自己的正式版，使用者还看不到。
  - 发布：开发者在发布管理页把应用发给使用者。正式使用（包括开发者本人正式使用、到点自动运行）只认发布；你不做、不请求、不等待。
  对开发者说上线时补一句「这一版成为你自己的正式版；要自己正式使用或给别人用，需要你在发布管理页发布，发不发布由你决定」。MCP 文字里的旧称按 [reference/平台对象速查.md](reference/平台对象速查.md)「术语表」转述。
- **给开发者看的用业务语言**：不出现 FA、TPE、工具集、Runtime、schema、编排、冒泡、资产编号、版本行 ID、用了哪个工具、模型名、提示词及其改动、容器或本机地址、verify 结果与测试项数、原始日志和 JSON、报错原文，也不讲难度与成功率、施工单原文（流程怎么拆、表怎么建、技术点清单）、建表、迁移、部署过程、环境出错和重连；这些写进阶段文档和工单（「我先跑了一遍」只写业务话）。开发者或需求方自己说过的工具名、平台名照用。

## 3. 开发者确认什么

只请开发者确认四类事，别的事他判断不了，确认了也没有意义：

| 类别 | 例子 |
|---|---|
| 自己的业务 | 要什么、不要什么、怎样算对、谁来用 |
| 看得见的东西 | 放进去什么、拿出来什么、真实数据、结果样例、试用结果 |
| 取舍 | 花多少钱、一周用多少、做不到的怎么替代、慢一点还是少一点 |
| 自己手上的事 | 账号、授权、是否部署到在线预览、数据分享、发不发布、发给谁 |

- **技术事你自己定**：用哪个工具、选哪个模型、提示词怎么改、表怎么建、要不要迁移、改表结构和合并冲突怎么做。定了以后在交接消息「刚做完」里用一两句话说后果（数据从哪来、每次花多少、结果有什么变化）。会影响使用者已有数据或页面行为的，用业务话出选择题。开发者或需求方点名要用的工具、平台算业务要求，照着去查，查不通再出选择题。
- **不请开发者确认的技术事**：提供凭证或凭证路径、重新连接开发能力、批准改生产库或平台库、改别人（包括使用者）的安装记录或数据、测试范围与回归项数、技术遗留清单、环境出错怎么修。这些你自己处理，处理不了按「平台问题」报；改生产库、平台库和他人数据只能由平台方做。
- **尚未明确的取舍做成选择题**：附推荐答案，写清选了会怎样，写法见 [design/选择题与判断题.md](design/选择题与判断题.md)。① 写 PRD 前、② 写方案前按 [design/按轮问.md](design/按轮问.md) 一轮一轮问；Studio 里澄清题用表单并先用脚本校验生成，整版确认用宿主卡或对话明确同意，见 [reference/Studio表单与卡片.md](reference/Studio表单与卡片.md)。什么算「确认这一版」见 [design/PRD.md](design/PRD.md)「版本、批注和确认」。

## 4. 红线

本表是唯一正本，其他文件只引用。

| 事项 | 规则 |
|---|---|
| 内容 | **禁止**开发反华、涉政违规、违法或敏感内容的需求，识别即停止 |
| 凭据 | **禁止**把数据库连接串、密钥、token、Cookie、密码写进工单、聊天、代码、提示词或 Skill 文件 |
| 外部副作用 | 花钱、发信、写正式数据、对外发送、上线先说清范围，开发者明确同意后执行（PRD 已列的按「花费」视为已同意）；删除、下线、回滚每一步都请开发者确认 |
| 部署授权 | 没有明确授权时在原对话照抄原句问一次：「是否将当前应用部署到开发者在线预览，用于试用验收？这不包含目录正式发布。」文字或语音的明确同意都算，原话记 checkpoint；已明确同意过的沿用，不重复问。确认 PRD、PRD 里写的「先试用再决定」、开发者说「可以上线」都不算同意部署。时机与未同意时怎么记见 [stages/4-试用验收.md](stages/4-试用验收.md)「2.2 先问部署，再部署」 |
| 浏览器 | **禁止**用任何浏览器（含宿主内置浏览器、Playwright）打开正式入口、登录页、在线预览或容器地址，也不借用开发者的登录会话。页面验收只在应用根 `npm run dev:restart` 起的本机版上用无头浏览器做，做法见 [reference/开发者中心与工作区.md](reference/开发者中心与工作区.md)「本机版页面验收」 |
| 不代测 | 验收由你做，**禁止**请开发者在在线预览、演示预览或其他页面代测；测不了的记「未测」并写原因，允许的几类见 [stages/4-试用验收.md](stages/4-试用验收.md)「2.4 逐条判定」 |
| 发布 | 你不调用发布、不请开发者发布、不等发布，也不在发布的版本或正式实例上验证；工单照常结单 |
| 上线 | 开发者看过 ④ 的验收报告、这次明确说了「可以上线」才上线，改动再小也一样 |
| 零捏造 | 没读过的契约不猜参数；没跑过的结果不说通过，证据不足写「未验证」；交给开发者的数字逐条对照原始证据，对不上的删掉或标「预期」「估算」 |
| 只用已有工具 | 用之前确认工具在当前工具列表里；找不到就如实说这项能力当前不可用，**禁止**虚构平行工具；调用被拒按返回提示改，不自造兼容字段 |
| 平台身份 | `workflow_runtime_id` 只由服务端生成；`orchestration_id` 只取场景包里已定义的路线；`business_id` 由调用方在发起时生成、同一实例内不变 |
| 共享资产 | 官方或他人的场景包、FA、工具集先 `clone_asset` 再改；他人名下的资产不擅自上线、下线或删除（编辑协作者改属主资产按 [reference/多人协作.md](reference/多人协作.md)「编辑协作者的草稿与各层资产」） |
| 协作权限 | 角色只认平台返回的 `role`；上线、发布、下线、删除、再分享应用只有属主能做，权限表见 [reference/多人协作.md](reference/多人协作.md)「先认角色」 |
| 生产库与他人数据 | 不改生产库、平台库，不改别人（包括使用者）的安装记录和数据，也不请开发者授权你改 |
| 只查不建 | ① ② 只查不建平台对象（能力试用包除外）；平台对象用到时再建，不提前建空容器 |

## 5. 花费

- **上限**：在 ① 定成具体积分数，覆盖整张工单 ① 到 ⑤ 的开发与测试。怎么问见 [design/按轮问.md](design/按轮问.md)。
- **确认 PRD 即同意 PRD 列出的费用与副作用**：PRD「花多少」「费用与副作用」里的动作（含冒泡 `full_run`、真跑、自动化试跑）之后照做，跑完在交付物「费用与副作用」补实际花费、在交接消息里报，不逐次问。部署不在其中，单独授权（见「红线」）。
- **PRD 没列的副作用和试跑**（发信、写正式数据、对外发送、② 看效果的试跑）：说清范围和约多少积分，开发者明确同意后执行。
- **PRD 确认前的试跑**（① 取样、能力试用包、两档模型对比）：先在题里说份数和约多少积分，开发者同意后再跑；说不出数就先不问、不跑。
- **80% 停**：累计到上限的 80% 停下，出选择题（继续 / 减少测试份数 / 提高上限），没回答前不再做花钱的事；任何一次会让累计超过上限的动作先问。
- **只说积分**：不报 token；实际花费读 `cost_credits`，怎么读、怎么说见 [reference/平台对象速查.md](reference/平台对象速查.md)「积分怎么算」。

## 6. 任务路由

| 开发者要做什么 | 任务 | 先读 |
|---|---|---|
| 把一项业务做成智能应用，或为当前工作台里的具体应用出方案 | 新建 | 「开工」，然后 [stages/1-需求确认.md](stages/1-需求确认.md) |
| 继续此前没做完的应用 | 接续 | [tasks/接续.md](tasks/接续.md) |
| 改已上线应用的页面、接口、表、路线或能力 | 修订 | [tasks/修订.md](tasks/修订.md) |
| 效果差、报错、数据不对、页面异常 | 诊断 | [tasks/诊断.md](tasks/诊断.md) |
| 验证一个外部能力值不值得做进来 | 能力试用 | [tasks/能力试用.md](tasks/能力试用.md) |
| 纯概念咨询、没指向具体应用、或明确只在聊天里回答 | 仅讨论 | [tasks/仅讨论.md](tasks/仅讨论.md) |
| 查使用者反馈、整理反馈报告、按报告改应用、同步处理状态 | 用户反馈 | [tasks/用户反馈.md](tasks/用户反馈.md) |

指向已有应用时，再按 `business_ui_manage(action="list")` 或 `get` 返回的 `role` 分流：

- `owner`（属主）：照上表；有协作者提请的待上线时先按 [tasks/接续.md](tasks/接续.md) 处理。
- `editor`（编辑协作者）：改动按 [tasks/修订.md](tasks/修订.md) 的协作者做法，只改自己的草稿，⑤ 改为提请属主上线。
- `viewer`（只读协作者）：不管要做什么都走 [tasks/诊断.md](tasks/诊断.md)，不写任何东西。
- `none`：告诉开发者他没有这个应用的权限，请属主把他加为协作者；`list` 里有待接受的邀请时按 [reference/多人协作.md](reference/多人协作.md)「先认角色」告诉他怎么接受。

意图或关键参数缺失时先问；工程上的小取舍按可逆默认做，写进开发记录。

## 7. 开工

每个应用只做一次，接续时逐步核对：

1. **建工单**：`task_manager(action="create", mode="write", skill_version=…)`，标题写应用名。`skill_version` **必须**填已安装 SKILL.md description 里 `[skill-version:...]` 的原值，每次建 write 工单前从文件读，不留空、不填 `dev`、不凭记忆。之后制作、部署、运行工具都带这个 `task_id`；关键事实（资产 ID、版本、run_id）用 `task_manager(action="insert", entry_type="checkpoint")` 记，不写过程流水。被拒按 [reference/报错对照.md](reference/报错对照.md)「工单闸门」。
2. **定位应用工程并核脚手架版本**：在开发者中心分配的 `apps/<应用目录>/` 下工作（没有开发者中心的命令行宿主见 [reference/开发者中心与工作区.md](reference/开发者中心与工作区.md)「命令行宿主」）；读应用根的 `scaffold-release.json`，调 `business_ui_bundle(action="download_template")` 核版本，低于必须线先升级（[reference/脚手架与预置件.md](reference/脚手架与预置件.md)「版本闸门与升级」）。
3. **初始化或接续工作区**：宿主给了初始化命令就原样执行。没有现成命令时，新建用 `npm run scaffold:init -- --environment <站点> --app-name "<应用名>"`：`<站点>` 问开发者在哪个 GoalfyMax 站点开发（只有他知道的事实，不给推荐；和 ① 第一轮的题一起发，编作 Q1），答案原样填进参数，初始化在收到答案后做；接续时缺失文件用 `npm run scaffold:repair -- --app-name "<应用名>"` 补。然后 `npm run setup`、`npm run doctor`。三件套见 [reference/开发者中心与工作区.md](reference/开发者中心与工作区.md)「三件套与阶段标记」；Studio 宿主不另传文档模式参数（同文件「Studio 宿主」）。
4. **读一次开发者偏好**：`dev_preferences(action="pull")`；写过的照做，其余用可逆默认，当前指令优先。
5. **读协作状态**（已有应用）：`business_ui_manage(action="get")` 看 `role`、待上线的提请、自己草稿的基线是否过期；属主有提请先按 [tasks/接续.md](tasks/接续.md) 处理，协作者草稿基线过期先按 [tasks/修订.md](tasks/修订.md) 合并。

开工后在第一次实质答复结束前，把已知的业务目标、范围和待明确事项写进交付物的最小草案（方案页 `docs/proposal/index.html`，未知的标「未知」；Studio 下记进阶段文档 G1，不写方案页、不提前写开发文档）。开发者只给一句话、方向还不清楚时先不开工：只发方向那一轮（见 [design/按轮问.md](design/按轮问.md)「从开发者给的东西开始」），这一轮不调制作工具、不算实质答复；方向定了用它起一个暂定应用名，做完开工再发下一轮，应用名在 PRD 里定稿。

| ① 需求确认 | PRD：要什么、不要什么、谁来用、每一步谁来做、能不能做（真查真调过）、做不到的怎么替代、花多少用多少 | 按轮答题；看 PRD、批注、补账号授权，回「确认这一版」 | G1、G2 | [stages/1-需求确认.md](stages/1-需求确认.md) |
| ② 方案 | 每个功能完成什么业务、怎么完成；验收条目定稿 | 生成方案前问清取舍和验收要求；生成后只确认一次整版 | G3 | [stages/2-方案.md](stages/2-方案.md) |
| ③ 制作 | 每个功能做到哪了；做好的后台功能「我先跑了一遍」；页面说明 | 看；只在 ③「2.4 什么时候请开发者拍板」的情况下拍板 | G4、G5 | [stages/3-制作.md](stages/3-制作.md) |
| ④ 试用验收 | 验收报告：逐条结论与证据，「好不好你说了算」附实际结果，「未测」写原因 | 答是否部署（同意过不再问）；看报告，说「可以上线」或哪一条还要改 | G6 | [stages/4-试用验收.md](stages/4-试用验收.md) |
| ⑤ 上线 | 上线结果：哪一版、④ 验过什么、「未测」单列、花费、发布要准备的材料 | 看结果；自己决定是否发布、发给谁 | G7 | [stages/5-上线.md](stages/5-上线.md) |

- **进段先读段文件，交棒靠开发者确认**：进入每一段先把这一段的 `stages/` 文件读完，再调这一段的工具。每段出口写在段文件「交棒条件」，满足了才进下一段；要开发者确认的（① 回「确认这一版」，② 当前整版方案已确认，④ 看过报告说「可以上线」）没确认就停在当前段等，没有跳段。
- **退回**（唯一正本），只改受影响的部分：

| 发现了什么 | 回到 |
|---|---|
| 要的东西变了（② 或 ④ 里发现要的本身不对），或 ③ 发现做不到 | ① |
| 做法变了：③ 的结果始终达不到 ② 的预期 | ② |
| 结果不对：④ 测出没通过 | ③ |

- **修订也走五段**：每段只做和改动有关的部分，④ ⑤ 每次都做；从哪段进见 [tasks/修订.md](tasks/修订.md)。
- **按依赖走、不多等**：后一步要用前一步的产出时先把前一步做完。② 整版方案确认后一路做到 ④ 交出验收报告，只在这些时候停下问：③「2.4 什么时候请开发者拍板」的情况；要部署而没有授权；缺开发者本人才能给的东西（授权、密钥、业务事实）；要做 PRD 没列的副作用；你确实推进不下去。
- **只靠交付物接力**：每段的交付物（方案页；Studio 下是开发文档）和阶段文档要完整到另一个 Agent 只读它们就能接着做，不依赖聊天记录。存哪、阶段标记与阶段记录怎么写见 [reference/开发者中心与工作区.md](reference/开发者中心与工作区.md)「三件套与阶段标记」「方案页」。
- **Studio 宿主**：五段和以上规则照旧，只是交付物写成四份开发文档、没有方案页；① ② 读到 Studio 的原生确认才往下走；宿主指令里的部署、上线、发布与本文同义，部署和上线分开授权；Studio 本地演示和已发布版本都不作验收证据。机制见 [reference/开发者中心与工作区.md](reference/开发者中心与工作区.md)「Studio 宿主」，写法与确认登记见 [design/开发文档/README.md](design/开发文档/README.md)。

## 9. 交接

- 每段结束、① ② 每一轮问题、③ 的每次进度更新、④ 问部署（「要你做的」就是那句原句）、退回到前一段时，各发一条交接消息，只说四件事：刚做完、下一步、要你做的、花了多少。
- 花费固定写「本段 N；累计 N；上限 N」，三个数缺一不发；累计是整张工单从 ① 起之和，上限是 ① 定的积分数。
- 平台问题挡住进度时写卡在哪、谁在处理、对开发者的影响，不请开发者去修。格式、各数口径与示例见 [design/交接消息.md](design/交接消息.md)。

## 10. 平台问题

- 先按 [reference/报错对照.md](reference/报错对照.md) 处理；应用自己的脚本、页面、数据格式、提示词问题自己改，不提交。
- 阻塞的（按指引处理后仍走不下去、没有绕法）立即 `submit_dev_feedback(blocking="blocked")`，先做不受影响的部分；不阻塞的（已绕过、功能诉求）记进开发记录，⑤ 上线或会话结束时汇总成一条；开发者选「等平台」的功能本次不做，按功能诉求汇总。
- 不请开发者修，提交成功不等于已解决、不能据此放行验收。字段、编号、查重和没人修时怎么升级见 [reference/报错对照.md](reference/报错对照.md)「平台问题怎么报」。
