# 脚手架版本与升级

用于新建、恢复或接续已有应用、预部署前检查，以及处理脚手架版本拒绝。这里的版本属于智能应用脚手架，与 Skill 版本、插件版本及 business_ui 业务版本分别记录。

**工作台与应用脚手架分别更新。** 工作台随 Goalfy App 安装和更新；应用脚手架以本应用的版本清单和在线门槛为依据，低于门槛时完成代码迁移与验证，通过后继续制作或预部署。

## 版本依据

- 本地实际版本：应用根 `scaffold-release.json` 的 `version`，格式为 `vYYYYMMDD-六位随机hex`。没有文件就是未声明，不能从 package.json 或日期猜。
- Skill 最低要求：总入口的 `scaffold-min-required-version` 机器标记，发布清单自动镜像为 `scaffold_min_required_version` 并登记到 Hub。
- 环境最低要求：MCP 在线返回的 `min_required_version`，已合并环境抬杆与本版 Skill 最低要求，服务端按登记 ID 判断先后。不得自己按字符串排序。
- 环境建议要求：MCP 在线返回的 `min_recommended_version`，服务端按登记 ID 判断先后。低于建议线时允许继续开发和部署，但本地开发提示“建议升级脚手架版本”；线上运行或 wakeup 时提示升级脚手架版本。
- 最新可下载版本：当前环境已登记的最新模板；必须校验下载包 `sha256`，解包后版本必须与响应 `version` 相同。Goalfy App 的版本、模板压缩包名、智能应用名和目录名都不是脚手架版本依据。

## 新建与接续

建工单后、初始化或继续开发之前，调用 `business_ui_bundle(action="download_template", task_id=..., current_scaffold_version=<本地清单，缺失为空>, workspace_id=<已有应用的真实标识>)`。Skill 的最低脚手架版本在发布时已登记到 Hub，服务端按工单绑定的 Skill 版本取值，调用时只传上述参数，任何版本号都以 MCP 返回为准。

新建尚无工作区时省略 workspace_id，下载并校验最新模板，再 scaffold:init；使用缓存模板也必须先在线核版本，不能因为已经下载过就省略检查。下载响应的 `version`、`sha256`、`min_required_version`、`min_recommended_version`、`upgrade_required`、`upgrade_recommended` 必须齐全，最低版本可以按契约为空，不能自行补值。已有应用先恢复真实目录与阶段资料，再查版本；恢复了阶段文档或同步了 Codex 对话不代表恢复了脚手架代码。响应缺少版本治理字段或返回 `SCAFFOLD_POLICY_UNAVAILABLE` 时，记录缺口并等待环境就绪，不自行填写版本绕过。

**核版本要核当前应用。** 在总入口第 1.3 节确认的应用工程根读清单；模板暂存目录、其他应用、Goalfy 安装目录都不能替代。新模板先校验再放进本应用的独立目录，已有应用则走下面的迁移流程。不同应用分别使用自己的工作区标识，上报版本时不复用另一个应用的记录。

版本达到必须线可以继续，不必每次升级到最新。`upgrade_required=true` 时：

1. 将最新模板下载到独立目录并核 SHA256。保存当前应用可恢复的 Git 提交或完整备份。
2. 对照旧模板、新模板和当前应用，迁移前后端平台固定层、应用预览适配、校验脚本及受影响依赖；保留业务页面、后端业务逻辑、身份、阶段文档、方案页和数据。不能通过在业务目录直接 git pull 或整包覆盖来代替迁移，也不从已下载的新模板清单直接认定旧应用已升级。
3. 固定层迁移完成后带入目标模板的版本清单用于验证；运行 setup、doctor、verify 和适用的 verify:release。迁移冲突或验证失败时，记录未完成状态，不能上报升级完成或预部署。缺少真实工作集时，先完成所需绑定与配置，再跑 release 验证。
4. 通过后用相同 workspace_id 再调用下载入口，上报已采用版本；这是工单的 local_report。新下载模板的版本不能提前当成本地应用版本上报。

`upgrade_recommended=true` 时，当前本地脚手架低于建议线，开发可以继续，先在开发记录中写“建议升级脚手架版本”，并在下一次预部署前完成迁移、验证和重新上报。建议线由环境策略维护，不能由 Agent 自行修改。

### 前后端固定层迁移边界

“保留后端业务逻辑”不等于保留全部旧后端。按目标模板核对：前端 `src/sdk/`；后端平台模块（广告充值为 `backend/src/ads/`）；对应测试、检查脚本、依赖与锁文件；以及 `backend/src/app.ts` 中原始请求体采集、广告错误处理中间件和路由挂载。混合业务与平台代码的文件按差异合并，不整体覆盖业务路由。

仅迁移前端 SDK、Dockerfile 与版本清单不能证明升级完整。记录每一类固定层的来源、迁移或无需改动的依据及验证结果。目标模板提供 `test:platform` 时，保留平台固定层测试并通过 `doctor`、`verify` 执行；不得删测试、关闭检查来通过升级。充值应用还须核对实际应用路由能经过验签代理，不能只测试单独创建的代理 Router。版本号和源码包 SHA256 分别说明声明版本与包字节，不证明完整调用链已经接通；真实授权、支付和到账仍单独验收。

## 预部署与证据

预部署前再次调用下载入口查门槛，以覆盖开发期间的抬杆。脚手架清单必须随 `pack.sh` 打出的实际源码包上传；不要只放在被排除的 app.json、workspace.json 或 docs 中。

Hub 在建库、起容器前读取上传包，校验实际字节的 source_sha256、根版本清单、当前环境抬杆和工单对应 Skill 的已登记最低版本。工单自动追加 scaffold_version 记录，evidence=bundle_verified，并记录 gate_passed；只有 gate_passed=true 才表示这次版本检查通过，不代表部署或业务验收已成功。查询工单的 scaffold_versions 可分别看各工作区 local_report 和各 business_ui 的 bundle_verified，完整历史在 entries 中。

**实际部署版本单独核对。** `business_ui_bundle(deploy)` 与 `status` 返回的 `data.deployed_scaffold_version` 来自该条部署记录。到 `status="success"` 后，把应用家族与版本行、`deployment_id`、实际源码包 `source_sha256`、`deployed_scaffold_version` 一起写入部署证据；上线后再反读目标应用版本当前绑定的部署，确认是验过的同一份，并写入交付报告和 `docs/history/`。失败或进行中的部署仅记录本次尝试，当前线上版本沿用其成功绑定的部署事实。回滚时重新核对恢复的绑定与脚手架版本。

工单 `local_report` 表示本地申报，`bundle_verified` 表示源码包校验，`deployed_scaffold_version` 表示指定部署的来源版本，三者分别保留。历史部署空值记为“未知”；`latest_version`、`min_required_version` 和 `min_recommended_version` 用于升级判断，实际版本以部署记录为准。查询某个正在运行或 wakeup 的用户实例时，以该实例自己的部署绑定及版本为依据：低于必须线提示需要升级，低于建议线提示建议升级脚手架版本；应用最新提交的版本仅证明该提交，旧实例是否升级还需实例侧证据。

| 错误 | 处置 |
|---|---|
| SCAFFOLD_UPGRADE_REQUIRED | 下载当前环境最新版，完成迁移、验证、重新打包上传，再 deploy |
| SCAFFOLD_VERSION_MISSING | 旧包缺版本清单；核实并完成升级，不能凭空补版本 |
| SCAFFOLD_VERSION_UNKNOWN | 本地用了未在当前环境登记的版本；使用环境已登记模板，或由维护者先发布登记 |
| SCAFFOLD_MANIFEST_INVALID | 源码包损坏、根清单格式错误或重复；修复打包与清单，不能只改请求中的版本 |
| SCAFFOLD_BUNDLE_HASH_MISMATCH | SHA256 与实际上传包不符；对本次真实字节重新打包、算摘要、上传 |
| SCAFFOLD_POLICY_UNAVAILABLE | 环境缺少最低版本登记或策略不可读取；由维护者修复环境，不跳过检查 |

版本拦截不会自动覆盖本地业务文件，也不会通过另建工单消失。紧急放行只由服务端环境策略管理，制作 Agent 不修改该策略。
