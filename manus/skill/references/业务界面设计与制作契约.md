## 1. 设计目标与边界

业务界面是场景包业务模型的可视化操作层。它应让用户更容易完成以下事情：

- 理解这个场景包能解决什么问题；
- 选择适合当前目标和档案状态的业务路线；
- 以低错误率提供本次运行所需信息；
- 看懂当前执行到了哪个**业务阶段**、为什么需要等待或补充信息；
- 审阅最终交付、处理异常、继续修订或复用历史结果。

“与场景包强相关”不等于把脚本、节点、工具和内部字段显示在页面上。正确关系是：

```text
场景包定义业务终点、候选路线、权限和知识
  → 编排与表单定义公开输入、运行交互和交付
  → 业务界面把这些公开契约翻译成用户能理解和操作的页面
```

界面**不得**成为第二套业务规则：选路规则仍以场景包为准，执行依赖仍以编排为准，字段约束仍以表单 Schema 为准，最终状态仍以宿主 Runtime 为准。页面只负责解释、采集、展示和引导。

业务界面的产品范围由开发者决定。开发 Agent 负责根据场景事实形成用户旅程、页面形态、模块 include/exclude、状态—行动、事件响应和视觉方向的候选 Plan，说明每项推荐、事实依据、体验收益和代价；开发者确认后才能把它们冻结为 `ui_predesign_brief`。Schema 或 SDK 中存在某项能力、Agent 认为某模块“更好”，都不能代替开发者选择。

每个页面、模块和主要操作都必须能回答三个问题：

1. 它帮助哪类用户完成什么业务任务？
2. 它依据场景包或公开运行契约中的什么事实？
3. 删除它会损害哪一步体验或哪项业务正确性？

第三个问题答不出来的模块通常不该存在。

## 2. 设计前必须取得的场景事实

业务界面设计不能只拿一个 JSON Schema 开始。预设计前先取得场景事实；实现前再用已发布资产补齐公开运行事实，并把结论写入工单：

### 2.1 场景包事实

- **业务终点**：用户最终希望完成什么，不是“运行某条 Workflow”；
- **目标用户**：谁使用、熟悉程度如何、是否多人协作；
- **高频任务**：最常发生的一个动作是什么，频率和时效如何；
- **候选路线**：每条路线解决什么目标、适用什么前置状态、到达标准是什么；
- **里程碑**：用户能理解的业务阶段、各阶段的可见产出；
- **权限与风险**：哪些动作只读、哪些会产生费用或外部副作用、哪些必须确认；
- **业务档案规则**：哪些档案事实会改变路线、默认值、优先级或解释；
- **正例与反例**：一个正确输入到正确交付的具体案例，以及一个容易做错的案例。

### 2.2 公开运行事实

- 当前真实的 `schema/orchestrations/` 与 `schema/forms/` 定义；
- 每条路线的入口表单、可能出现的运行中表单和最终交付；
- 每条 Workflow 当前公开的业务事件声明：事件类型、稳定事件名、版本、成立条件和 Payload Schema；
- Runtime 状态、可恢复方式和历史查询能力；
- 文件字段、复杂对象、数组、日期及其真实校验约束；
- 用户可见的结构化结果、交付文件和审阅动作；
- 当前模板实际公开的 SDK 能力与限制。

### 2.3 真实使用证据

有参考项目或已上线界面时，优先读取真实日志、用户反馈和产物，定位：

- 用户在哪一步不知道该选什么；
- 哪些字段最容易填错或反复补充；
- 哪个阶段等待最长、最容易误以为卡死；
- 用户最关心结果里的哪三项信息；
- 哪些异常需要回到聊天处理；
- 哪些参数经常沿用上一次，可以安全复用。

没有证据时要明确标为假设，不能把个人审美当成业务事实。

## 3. 建立场景包到界面的映射

编码前必须建立一张“场景—界面映射表”。每一行都从场景事实出发，而不是从组件库出发：

| 场景事实 | 用户此刻的问题 | 界面响应 | 公开机制 | 验证证据 |
|---|---|---|---|---|
| 业务终点 | “这个入口能帮我得到什么？” | 首屏价值说明、主行动 | 场景包名称与描述 | 用户能复述预期交付 |
| 多条候选路线 | “我该走哪条？” | 路线卡片、适用条件、推荐理由 | 编排静态定义 | 正反例能选对路线 |
| 入口输入 | “开始前要准备什么？” | 业务化表单、分组、说明和校验 | 入口 Form Schema | 代表性输入可一次提交 |
| 档案会影响选择 | “为什么推荐这条？” | 档案摘要、推荐理由、可修改默认值 | 场景包档案规则 | 有档案和无档案均可完成 |
| 文件是关键输入 | “文件对不对、传成功了吗？” | 上传、格式说明、文件摘要或预览 | `format:file/image`、上传能力 | 错文件能在提交前发现 |
| 多个执行阶段 | “现在做到哪了？” | 当前业务阶段、已完成事项和等待说明 | Workflow 业务事件与 Runtime 快照 | 运行中不会误报完成 |
| 需要补充表单 | “为什么停住、我要做什么？” | 待处理事项置顶、保留回显、明确提交 | `onCall/pending/reply` | 刷新后仍能继续处理 |
| 结构化交付 | “结果是什么、下一步怎么办？” | 结果摘要、重点、文件、审阅和下一步 | 结果/交付业务事件、Delivery 与输出契约 | 用户无需读原始 JSON |
| 可修订或改走路线 | “怎么重做且不丢旧结果？” | 冻结旧交付、创建新运行、说明差异 | 新 Business/Runtime | 历史结果未被覆盖 |
| 异常或能力边界 | “哪里失败、能怎么恢复？” | 原因、可恢复动作、回到聊天 | 错误与 `openChat` | 不出现无效重试按钮 |

映射表完成后做两次检查：

- **正向检查**：场景包每条已确认路线、关键输入、交互和交付，都能在页面中找到承载；
- **反向检查**：页面每个主要模块，都能追溯到一条场景事实或体验风险。

强关联靠这两次检查建立，不靠在标题里写场景包名称。

## 4. 设计完整用户旅程与状态

### 4.1 先画旅程，再画页面

按用户视角描述一轮完整业务：

```text
了解价值
  → 选择路线
  → 准备与填写
  → 提交已送达
  → 业务受理或退回修改
  → 运行中
  → 等待用户 / 等待 Agent
  → 成功交付 / 失败 / 取消
  → 审阅、修订、复跑或回到聊天
```

不是每个场景都有全部环节，但任何真实存在的环节都必须有明确页面状态。不能只设计“填写表单”和“展示结果”两个截图。

### 4.2 状态—信息—行动矩阵

至少覆盖以下状态，并为每个状态写清“显示什么、主行动是什么、哪些操作禁用、如何恢复”：

| 状态 | 必须说明 | 主行动 |
|---|---|---|
| 未开始 | 价值、预计交付、所需材料 | 选择路线或开始填写 |
| 填写中 | 当前步骤、必填、档案默认值来源 | 校验并提交 |
| 上传中 | 文件名、大小、上传状态、失败原因 | 取消或重试上传 |
| 已送达待受理 | 请求已提交，但尚未开始执行 | 等待结果，避免重复提交 |
| 被退回修改 | 字段级原因、原输入和服务端回显 | 修改后原窗重提 |
| 运行中 | 当前业务里程碑、已完成事项 | 查看进度或切到聊天 |
| 等待用户 | 为什么暂停、需要补什么、影响什么 | 完成待处理表单 |
| 等待 Agent | Agent 正在检查什么 | 等待或查看说明 |
| 待最终审阅 | 已通过核验的业务结论、交付物与允许动作 | 接受、要求修订或选择另一路线 |
| 成功 | 业务结论、交付物、已接受的验收状态 | 下载、复跑或下一步 |
| 失败 | 失败发生在哪个业务阶段、是否可恢复 | 修正输入、重新运行或回到聊天 |
| 取消 | 已完成部分是否保留 | 返回历史或重新开始 |
| 只读协作 | 为什么不能提交、仍可查看什么 | 查看结果或联系所有者 |

提交回执、业务受理和最终完成是三个不同状态，文案和视觉上必须区分。

交付结果已渲染、文件可下载或技术核验已通过，都不等于最终业务验收已完成。当编排声明用户审阅时，界面**必须**先进入“待最终审阅”，按 Delivery Review 只展示允许的动作；只有服务端确认审阅接受后才能显示“成功”。修订或改路线要显示为新运行，当前 Delivery 保留为历史版本。

## 5. 按证据选择界面模块

模块不是越多越好。先满足主路径闭环，再根据业务证据添加增强模块。

### 5.1 基础闭环模块

只要界面承担对应环节，就必须有：

- 当前任务或路线的业务说明；
- 与真实 Form Schema 对应的输入控件和校验；
- 提交、受理、运行、等待、成功和失败反馈；
- 权限与输入互斥的正确禁用；
- 最终交付展示或明确的交付去向；
- 错误恢复和回到聊天的路径。

### 5.2 条件模块决策表

| 模块 | 应当加入的信号 | 不应加入的情况 | 主要事实源 |
|---|---|---|---|
| 路线选择 | 有两条以上用户可选路线，或用户目标会改变路线 | 只有一条可执行路线 | 场景候选路线、orchestrations |
| 推荐路线 | 档案或前置事实能形成可解释推荐 | 没有可靠依据，或推荐会替用户做高风险决定 | 档案规则、选路条件 |
| 新手引导 | 用户不熟悉任务，准备成本高，首次使用容易失败 | 高频熟练用户每次都要经过同样说明 | 用户画像、反例 |
| 分步向导 | 字段多、存在先后依赖、需要边填边解释 | 字段少且一次可理解 | Form Schema、正反例 |
| 文件上传与预览 | 文件或图片是关键输入，错误文件会造成返工 | 没有文件输入 | `format:file/image` |
| 数据摘要预检 | 大文件、表格或批量对象需要先确认范围和质量 | 服务端无预检能力，前端无法可靠解析 | 工具能力、输入契约 |
| 档案摘要 | 档案会改变路线、默认值或结果解释 | 档案与本次任务无关 | 场景档案最小读取规则 |
| 阶段状态 | 多阶段或执行时间明显，且 Workflow 声明了可消费的阶段事件 | 同步快速完成、无中间状态，或没有可靠业务事件 | 场景里程碑、业务事件契约、Runtime |
| 待处理中心 | 运行中可能出现一个或多个用户表单 | 没有运行中交互 | Forms、`pending/onCall` |
| 结果工作台 | 输出包含多模块、文件、结论或后续动作 | 只返回一句短结论 | 结果/交付业务事件、Delivery、output Schema |
| 对比与审阅 | 用户必须在方案间选择、批准或要求修订 | 结果没有人审节点 | 交付审阅动作 |
| 历史记录 | 任务高频复跑、需要追溯或对比版本 | 一次性任务且无历史价值 | `business.list/get` |
| 快速复跑 | 上次参数大部分可复用，且复跑风险低 | 输入变化大、外部副作用高或必须重新确认 | 历史输入、权限规则 |
| 协作者与权限提示 | 项目可能多人协作或存在只读角色 | 永远单人且权限固定 | `project` 权限 |
| 聊天协作入口 | 异常、开放式判断或复杂解释需要 Agent | 页面主路径本身已经完整，不需要常驻聊天窗 | 场景边界、`openChat` |

### 5.3 模块选择纪律

- 条件决策表用于生成模块候选和推荐，不是授权 Agent 直接定稿；页面范围、主行动、路线入口、审阅方式以及历史、聊天、档案等关键模块必须进入预设计 Plan，由开发者集中确认。
- **不要因为 SDK 有某项能力就做对应模块。** 能力是可用工具，不是产品需求。
- **不要把所有路线、历史、聊天、统计塞进首页。** 首页只承载当前用户最可能的主行动。
- **不要让推荐替代用户授权。** 涉及费用、发布、删除或高风险路线时，只能解释和预选，不能自动提交。
- **不要重复宿主已经提供的通用能力。** 能用 `openChat` 完成异常协作时，不另造一个残缺聊天系统。
- 条件模块加入或排除都要写理由。排除不是遗漏，无法说明理由才是遗漏。

## 6. 选择合适的页面形态

开发 Agent 根据主任务和下表形成页面形态候选，说明每种形态对最终用户主路径、信息密度和实现范围的影响，并把推荐形态放入预设计 Plan 交开发者确认。页面形态可组合，但不得无目的混搭，也不得由 Agent 因个人审美直接定稿：

| 形态 | 适用信号 | 典型结构 |
|---|---|---|
| 单任务启动页 | 单路线、输入明确、主要目标是快速开始 | 价值说明 → 表单 → 状态 → 结果 |
| 多路线工作台 | 多个明确业务目标，用户需要选择 | 路线选择 → 路线专属表单 → 统一进度与交付 |
| 分步向导 | 准备复杂、字段有依赖、首次错误成本高 | 步骤导航 → 分段输入 → 汇总确认 → 提交 |
| 文件分析工作台 | 文件是核心输入，结果围绕文件产生 | 上传与预检 → 参数 → 阶段状态 → 结构化报告 |
| 审阅决策台 | 核心价值是比较、批准、退回和留痕 | 摘要 → 差异 → 证据 → 决策与意见 |
| 周期运营看板 | 高频复跑、历史对比和状态追踪很重要 | 今日主行动 → 进行中 → 最近交付 → 快速复跑 |

“数据很多”不自动意味着做看板；“步骤很多”也不自动意味着做向导。只有这些结构能降低真实认知负担或返工时才建议采用，最终选择以开发者确认的预设计 Plan 为准。

## 7. 关键体验机制

### 7.1 用业务语言隐藏技术结构

- 路线名称描述用户目标，例如“生成本周经营诊断”，不要写 Workflow 名；
- 进度描述业务里程碑，例如“正在核对成本结构”，不要显示节点 ID；
- 失败说明用户可采取的动作，不展示 RPC、堆栈或内部状态码；
- 结果按用户决策顺序组织：结论 → 影响 → 证据 → 下一步。

### 7.2 渐进披露

首屏只问决定路线和执行所需的最小信息；专业参数放到“高级设置”，解释默认值的适用条件。最终提交前集中展示高风险动作、费用、外部影响和不可逆项。

不要为了“表单完整”把所有 Schema 字段平铺。字段可以按业务语义分组、分步和使用专属控件，但提交值必须仍符合原 Schema。

### 7.3 档案驱动的个性化

业务档案可用于：

- 推荐路线并解释依据；
- 预填稳定信息；
- 调整字段优先级和默认值；
- 在结果中提供与历史或目标的对照。

使用时必须遵守：只读与本次决策有关的最小事实；显示关键默认值的来源；允许用户修改；档案缺失、过期或冲突时退回普通输入；用户当前明确表达优先于历史档案。**禁止**用档案在后台替用户完成高风险选择。

### 7.4 提交与等待体验

- 提交前做字段级校验，错误贴近字段，保留用户已填内容；
- 上传、提交、等待受理和运行中使用不同 loading；
- 收到“请求已送达”只显示已提交，不能显示已完成；
- 被退回时保留服务端回显和原输入，聚焦第一个错误字段；
- 长运行展示当前业务阶段、已完成事项、最近更新时间和可执行动作；不制作进度条，也不用无意义转圈冒充状态；
- 输入被聊天或表单占用时，说明由谁占用以及怎样继续。

### 7.5 结果与下一步

结果页优先回答：是否达到业务终点、最重要结论是什么、证据或交付文件在哪里、用户现在要做什么。

如果支持批准、修订、改走路线或复跑：

- 明确每个动作会创建什么新运行；
- 保留旧交付和版本，禁止原地覆盖；
- 修订时带回必要上下文，避免用户重复填写不变信息；
- 高风险复跑重新确认，不因历史参数存在而静默执行。

### 7.6 空态、错误和降级

- 空态说明为什么为空以及下一步，不只放一张插图；
- 错误区分字段错误、业务拒绝、运行失败、权限不足和平台不可用；
- 只有真正可恢复时才显示“重试”；
- 开放式异常、契约漂移或页面无法表达的情况，保留现场并引导回到聊天；
- 页面刷新后从公开快照恢复，不依赖只存在于组件内存的关键状态。

### 7.7 可读性与宿主协作

- 主行动在每个状态最多一个，次行动降低视觉权重；
- 复杂结果支持摘要、展开和下载，不把原始 JSON 直接交付；
- 交互组件避开宿主保留区，支持明暗主题；
- 重要状态不能只靠颜色表达；
- 表单标签、错误和按钮使用一致术语；
- 桌面宽屏优先保证信息层级，小尺寸下仍能完成主路径。

## 8. 视觉风格与内容语言

业务界面的风格需要与场景、使用者和决策节奏相符，不得从“专业、简洁、有科技感”这类空泛形容词直接进入编码。参照 web-deploy 的设计纪律，编码前必须先做出具体、可检查的视觉承诺；但业务界面首先是工作界面，任何个性表达都不得损害表单效率、状态辨识、中文可读性和无障碍性。

### 8.1 六项视觉承诺

开发 Agent 必须为 `ui_design_brief` 准备以下六项具体候选与取舍依据，开发者在预设计 Plan 中确认风格方向、关键参考和唯一识别点；配色数值、间距和组件拆分等不改变已确认体验语义的实现细节由 Agent 自主完成。答案不能只是形容词：

1. **使用场景**：什么人在什么环境、什么压力下使用？例如“店长在营业结束后用笔记本快速完成日结”，不写“高端专业”。
2. **风格取向**：选择一个明确方向，如“编辑式业务简报”、“高密度调度台”、“温和的一对一顾问工作台”或“严谨审核台”，并说明它为何符合业务。
3. **具体参考**：可选二至三个真实产品或出版物作为层级、密度或信息组织参考，必须写清“参考哪一点”；不得照搬品牌、商标或整页布局。
4. **唯一识别点**：用一句话说明用户一眼能记住的视觉或交互特征，例如“用餐桌布局呈现门店的收入与成本平衡”。它必须帮助理解业务，不能只是装饰。
5. **字体与层级**：明确中文标题、正文、数字和表格的字体、字重、字号跳跃和行高。优先使用脚手架已有字体和安全回退，不为了个性引入不可用的外部字体。
6. **取舍清单**：记录主色、强调色、页面骨架、信息密度、动效原则以及本次明确不采用的字体、颜色、结构和套路，防止不同业务界面收敛成同一张模板。

一份合格的风格描述应当能指导实现：

> 采用“温和的经营复盘手记”方向，服务于营业结束后需要快速决策的店长。亮色纸张底色承载大面积内容，深墨绿只用于主行动和已确认结论，风险使用砖红且配文字标签。首屏不放通用指标卡，而是以“今日最需要决定的一件事”作为主视觉；输入页空间充裕，结果页转为高密度摘要。不使用蓝紫渐变、等权统计卡、装饰性光斑和无业务含义的大数字。

“蓝紫渐变、玻璃卡片、科技感、简洁大气”不是合格的风格描述，因为它没有回答业务场景、信息优先级、主行动和取舍。

### 8.2 业务界面的视觉纪律

- 先定一个主导色和一个主要强调色，再为成功、预警、失败补充语义色；禁止五个以上等权强调色造成无主次的“彩色仪表盘”。
- 使用明确的字号、字重、留白和对齐建立层级，不靠每个区块加卡片和边框建立层级。
- 首屏突出当前主任务或当前结论，不默认堆四张统计卡、六张等宽功能卡和无意义的欢迎横幅。
- 背景可以有纸张、网格、分区或弱纹理，但必须服务视线和分区；禁止无场景理由的渐变光斑、光晕、网格弧线和悬浮球。
- 数据展示先确定用户要比较什么、发现什么、做什么决定；图表、大数字和进度环不得作为装饰。
- 动效只用于说明状态变化、层级转换和操作回馈；支持减少动效，禁止循环抢占注意力或让长运行界面持续抖动。
- 表单的标签、说明和错误比装饰优先；长表单通过分组、步骤和渐进披露降低负担，不用小字和紧密排列强行压缩。
- 所有主要交互均保证键盘操作、明显焦点、足够点击面积和不依赖颜色的状态标识。
- 先与宿主的明暗主题、保留区和实际内容宽度协同，再做个性表达；禁止假设业务界面拥有整个浏览器视口。

### 8.3 全中文界面和内容规则

默认交付的业务界面使用简体中文。用户可见的页面标题、导航、按钮、字段标签、占位语、状态、徽标、空态、错误、提示、下载说明和无障碍文案均必须是中文。

**禁止把开发术语直接当作界面文案**，例如 `Dashboard`、`Submit`、`Loading`、`Pending`、`Retry`、`Back`、`Workflow`、`Runtime`、`Schema`、`ID`、`Success` 或 `Error`。应根据语境分别表达为“经营概览”、“提交审阅”、“正在上传”、“等待补充”、“重新尝试”、“返回上一步”、“业务路线”、“本次执行”、“填写要求”、“已完成”或“未能完成”。

仅在以下情况保留英文：

- 开发者明确要求英文或双语界面；
- 不可翻译的注册商标、产品名或法定缩写；
- 用户真实文件名、扩展名或业务数据原文；
- 权威来源的原始引文必须保真时，同时提供中文解释。

以上例外不包括开发者方便。变量名、枚举值、组件名和服务端文案必须经过界面文案映射，不得直接渲染。中英文和数字之间的空格、标点、日期、金额和单位必须统一。

界面文案应描述具体事实和动作，禁止用“全方位、一站式、全景、深度、智能赋能、开启旅程、无缝体验”等套话填充首屏、空态或按钮。主按钮写用户即将完成的真实动作，例如“提交经营数据”或“确认修订意见”，不写“立即体验”或“开始探索”。

### 8.4 内部标识不可见

内部标识可以存在于 SDK 调用、页面内存和安全的运行状态中，但不得出现在页面文字、表格列、提示气泡、错误详情、下载文件名、可复制内容或用户可见网址中。包括但不限于：

- 场景包、任务点、Workflow、编排、表单、运行、业务、项目的内部 ID 或 slug；
- `scene_package_id`、`tpe_id`、`orchestration_id`、`form_id`、`node_id`、`taskpointEventId`、`workflowRuntimeId`、`businessId`、`formSubmitId` 和 `callMsgId`；
- 工具、工具组、Toolset、FastAgent、部署、跟踪、消息和存储对象的 ID；
- RPC 名称、错误码、堆栈、内部路径、Workspace 路径、预签名 URL、存储 key 和原始调试对象。

页面如果需要帮助客服定位问题，只显示服务端专门返回的、可对外公开的“问题参考号”，不得用任何内部 ID 替代。业务本身的订单号、门店编码、合同号等只有在用户理解和操作确实需要时才可展示，并应使用业务名称、按权限脱敏，不得统称为“ID”。

原始错误对象必须先做类型判断和映射，再显示“发生了什么—对当前任务有什么影响—现在可以做什么”。严禁渲染 `[object Object]`、原始 JSON、服务名、函数名或开发者调试信息。

## 9. 边界情况与降级设计

设计不能只用“一个有权用户、一条路线、一份完美数据、一次成功”的理想样例。在开始编码前，至少将以下边界写入状态—行动矩阵和验收样例：

| 类别 | 必须考虑的情况 | 界面原则 |
|---|---|---|
| 内容 | 超长中文名称、多行说明、空值、零值、未知枚举、大数和高精度小数 | 合理换行与省略；零不冒充空；未知值用中文安全表达，不泄漏原始值 |
| 路线 | 无可用路线、只有一条、多条相似、已下线、档案无法支持推荐 | 不用空选择器；说明不可用原因；证据不足时取消推荐 |
| 档案 | 缺失、过期、矛盾、无权读取或只有部分字段 | 降级为普通输入；标明依据不完整；用户当前输入优先 |
| 表单 | 动态字段、不支持的复杂结构、条件字段切换、服务端返回多个字段错误 | 不猜 Schema；不降级成 JSON 文本框；保留输入并定位首个错误 |
| 文件 | 过大、类型错误、同名、重复上传、中断、超时、上传后处理失败 | 提交前尽可能发现；分开上传与处理状态；不显示内部路径或临时 URL |
| 权限 | 页面打开后权限变化、只读协作者、项目正在执行、输入权被其他界面占用 | 操作前重新确认权限；不展示无效提交入口；说明如何恢复 |
| 事件 | 迟到、重复、乱序、断线重连、订阅晚于事件、推送与查询快照不一致 | 以服务端当前快照收敛；操作幂等；不倒退显示状态 |
| 运行 | 长时间无更新、等待用户、等待 Agent、失败、取消、运行不存在或已过期 | 分清等待对象和恢复动作；不用无限加载；不自行重建运行 |
| 交付 | 只有部分结果、文件缺失、多版本、审阅被拒、重新修订、下载失败 | 明确完整性和版本；不用部分成功冒充整体成功；保留旧版 |
| 历史 | 无历史、大量历史、同名记录、记录已删除或不再有权 | 使用业务摘要和时间区分；分页或渐进加载；不用内部 ID 补语义 |
| 环境 | 宿主明暗主题、保留区变化、窄屏、浏览器缩放、大字号、减少动效 | 不假设固定视口；主路径在小尺寸和放大文字后仍可完成 |
| 网络与平台 | 弱网、离线、超时、宿主能力缺失、SDK 版本不兼容、契约漂移 | 保留现场；禁用不可用能力；明确回落聊天或记录为平台阻塞 |
| 隐私 | 手机号、证件、地址、金额、内部备注和下载交付 | 最小展示、按权限脱敏、敏感下载前确认，不把敏感值写入错误或网址 |

日期、时区、币种、百分比和计量单位也必须作为业务契约处理：展示值要有单位，不猜测时区和币种，不用格式化四舍五入改变用户要审阅的原始精度。

## 10. 平台机制如何服务体验

具体签名以当前模板 SDK 文档为准。设计阶段按能力域判断，不在 Skill 中复制实现代码：

| 体验需求 | 使用机制 | 设计注意 |
|---|---|---|
| 展示可用路线和表单 | `getOrchestrations/getForms` | 编码期契约与页面文案必须一致 |
| 启动路线 | `business.start` | 回执、受理、完成三态分开 |
| 接收运行中表单 | `onCall` + `pending` | 支持迟到订阅和刷新恢复 |
| 提交补充信息 | `business.reply` | loading 持续到业务确认；rejected 原窗重填 |
| 感知受理结果 | `onResult` | accepted/rejected/failed 分别处理 |
| 展示业务阶段与结果 | Workflow 业务事件 + Runtime 查询 | 事件驱动更新，查询用于首次打开、刷新恢复和最终收敛；不从任务点、工具调用或技术状态反推业务语义 |
| 展示历史和版本 | `business.list/get` | 以一次 Business 为单位组织，不拼内部节点 |
| 防止并发输入冲突 | `inputOwnership` | 禁用时解释当前占用方 |
| 判断权限与项目状态 | `project.get/onChange` | 动作前实时拉取，渲染使用推送镜像 |
| 上传文件 | `upload` | 展示上传态，提交返回的 Workspace 路径 |
| 处理开放式异常 | `ui.openChat` | 保留当前页面状态，不重复建设聊天协议 |
| 展示普通消息 | `chat.history/onMessage` | 仅确有业务价值时加入，遵守消息指南 |

界面使用某项机制前必须阅读模板对应文档和参考实现。参考实现只用于学习状态管理和调用方法，不能复制它的业务文案、路由、表单或示例数据。

### 10.1 Workflow 业务事件设计

业务事件契约需要在 Workflow 设计阶段与界面模块一起确定。先为每条 Workflow 建立一张“业务节点—事件—界面响应”表，至少记录：业务事实何时成立、事件类型、稳定事件名、Payload 字段、是否硬门、对应界面模块、刷新恢复后的快照来源。事件名和 Payload 表达业务语义，不得出现 Workflow 名、节点 ID、工具名或原始工具返回。

以下生命周期事件是 Workflow 闭环的硬门：

| 业务节点 | Workflow 要求 | 业务界面用途 |
|---|---|---|
| 开始执行 | 每条 Workflow 在首个业务动作前***必须***发布 `stage_started` | 将对应业务阶段置为进行中，避免界面只能显示无意义加载 |
| 正常结束 | 每个正常返回分支在结果真实成立后***必须***发布 `stage_result` | 更新结构化结果或阶段摘要，并与 Runtime 终态交叉收敛 |
| 文件可交付 | Runtime 在正式 Artifact 登记后为每份文件自动发布 `artifact_ready`；Workflow 脚本不声明或发布 | 将公开文件引用加入交付物区域；不得从脚本事件接收 Workspace 路径或临时 URL |
| 最终结果可交付 | 最终节点正常返回后，Runtime 在 Delivery mapping、文件登记和冻结完成后***必须***自动发布 `delivery_ready`；Workflow 脚本不声明或发布 | 使用冻结的 `PublicDelivery` 进入待最终审阅或可交付状态；不得直接显示为用户已接受 |
| 可控业务失败 | 被脚本明确识别的业务失败终态***必须***发布 `stage_failed` | 展示稳定中文原因、影响和可行恢复动作 |

细分阶段的额外 `stage_started`、值得独立呈现的中间 `stage_result` 和不要求用户回答的 `attention_required`，均***建议结合业务界面考虑***。只有模块确实需要该事实才能改善理解、等待或决策时才增加；页面没有消费理由的事件不应声明，脚本也不得在每个工具调用后机械发送。业务界面不制作进度条，因此不把 `stage_progress` 纳入界面契约。

Workflow 脚本只通过 `emit_business_event(event_type=..., event_key=..., payload=...)` 发布脚本所有的业务事件。事件类型和事件名必须是稳定字符串字面量，并在 Workflow 资产的 `business_event_contracts` 中预先声明版本、说明和关闭的根对象 Payload Schema（`additionalProperties:false`）。`artifact_ready` 与 `delivery_ready` 由 Runtime 自动发布，不写入脚本契约。业务界面只消费公开业务字段，不读取原语返回的内部运行身份，也不要求脚本使用 `print_event`、标准输出或普通消息模拟事件。

事件不承担双向交互。入口提交、运行中补充信息、Runtime 恢复和最终审阅仍使用现有 Business/Runtime 握手；等待用户填写表单时不再用 `attention_required` 重复同一事实。`delivery_ready` 只说明结果具备审阅条件，只有服务端确认 Delivery Review 接受后，界面才能显示业务成功。

事件驱动不删除权威查询。业务界面应把事件理解为“已发生的业务事实”，把 Runtime 快照理解为“当前运行真值”，把 Business 表单握手理解为“当前输入真值”，把 Delivery Review 理解为“最终验收真值”。四者不得互相替代。

### 10.2 SDK 事件消费状态机

实现前必须以本次下载模板的 `src/sdk/docs/business.md`、`src/sdk/docs/types.md` 和实际类型定义为准，记录 SDK 版本与运行契约版本。界面只使用 SDK 对 App 暴露的 camelCase 对象，不解析宿主传输帧，不依赖内部 `event_type`、`sub_event_type` 或消息包装结构。

每个业务工作台只在共享布局或统一运行协调层建立一次事件订阅，禁止每个路由和卡片各自订阅。页面打开或刷新时遵守以下顺序：

1. 先注册 `sdk.business.onBusinessEvent(...)`，并在组件卸载或运行上下文切换时取消订阅；
2. 将 `live`、`backfill` 和 `replay` 三类批次送入同一个纯事件归约器，同一事件重复应用不得改变结果；
3. 订阅建立后，对当前 `workflowRuntimeId` 执行一次 `getWorkflowRuntime(...)` 快照读取；快照水位领先时，由 SDK 自动补齐历史事件；
4. 以快照的 Runtime 状态收敛运行终态，以事件投影阶段、结果、交付物和提醒；
5. 只允许首次打开、用户主动刷新，或 `onTaskpointStatusChange` 的 `live` 终态批次触发一次有界快照更新。

SDK 和业务界面的责任分工如下：

| 责任 | 归属 | 业务界面不得做什么 |
|---|---|---|
| 按 `sequence` 排序、按 `eventId` 去重、缺口检测与补拉、迟到订阅回放、快照水位对齐 | SDK | 重新实现排序、去重、水位、补拉或重试循环 |
| 校验已冻结的 `eventType + eventKey + eventVersion + payload`，更新业务视图 | App | 从内部 ID、原始工具输出或技术过程帧猜业务含义 |
| Runtime 终态、Artifact 登记与公开下载引用 | 宿主与 Runtime | 用 `stage_result`、`stage_failed` 或 `delivery_ready` 自行改写整体终态 |
| 表单待填、提交、受理与重填 | Business 握手 | 用 `attention_required` 伪造可提交表单 |
| 用户接受、修订、改路线或交给 Agent | Delivery Review | 把 `delivery_ready` 显示为“已验收”或“已成功” |

`onBusinessEvent` 回调返回单 Runtime 的批次，其 `events` 已按序、已去重。共享协调层先按批次的 `workflowRuntimeId` 隔离不同运行的视图投影，再应用事件，禁止让历史运行或并行路线的事件污染当前页面。运行、业务、编排和事件标识只用于前端内部关联，不得显示。

三类 `source` 的数据均经过同一归约器：`live` 可以在状态归约之后产生一次性过渡、弱动效或有克制的业务提示；`backfill` 和 `replay` 只恢复视图，不得弹重复提示、提交表单、打开页面或触发任何查询。

业务事件到视图的基础映射如下，实际字段仍必须以当前 Workflow 的已发布契约为准：

| 事件类型 | 应当更新 | 禁止推导 |
|---|---|---|
| `stage_started` | 按稳定 `eventKey` 新建或更新业务阶段为进行中 | 不用 Workflow 或节点名称展示阶段 |
| `stage_result` | 更新该阶段的结构化摘要、结论或局部结果 | 不单独推导 Runtime 已结束 |
| `artifact_ready` | 增加已登记的公开交付物引用 | 不接收或显示 Workspace 路径、临时 URL 或存储密钥 |
| `attention_required` | 展示不要求当场回答的业务注意事项 | 不构造表单，不复制 `pending/onCall` 已表达的待办 |
| `stage_failed` | 标记对应业务阶段失败，显示稳定中文原因与恢复动作 | 不用它替代 Runtime 整体终态 |
| `delivery_ready` | 从 `payload.delivery` 读取冻结的 `PublicDelivery`，将对应路线转为待审阅或具备交付条件 | 不显示为用户已接受或业务已验收；不把 Workspace 路径当正文显示 |

当 `eventKey`、`eventVersion` 或 Payload 与冻结契约不符时，只隔离该事件影响的模块，保留 Runtime 快照和其他已验证内容。对用户使用稳定中文说明“部分进度或结果暂时无法展示”并提供回到聊天的路径；禁止让未知事件导致整页崩溃，禁止把原始 Payload、版本、内部标识或调试对象显示给用户。

### 10.3 查询与技术事件边界

- `getBusinessEvents(...)` 只用于最终用户明确打开历史或开发者排查恢复时的有界查询，日常增量由 SDK 自动补拉；禁止用它轮询。
- `onTaskpointEvent(...)` 是高频技术过程帧，只在确有业务价值时做低权重过程展示或内部诊断；回调内禁止查 Runtime、TaskPoint 或业务事件，禁止从中推导业务阶段、结果或成功。
- `onTaskpointStatusChange(...)` 的 `replay` 只恢复 UI；只有 `live` 终态批次可以触发一次有界快照刷新，一个批次不得按项发起多次查询。
- 禁止使用 `setInterval`、递归 `setTimeout`、`refetchInterval` 或事件回调内查询来刷新进度。需要恢复时使用订阅、一次快照、SDK 自动补拉和用户手动刷新。
- SDK 不是业务结果缓存层。路由来回导致的查询限流应按错误降级，不得为规避限流在前端新建另一套权威缓存。

### 10.4 Delivery Review 的载荷与应答

路线最终节点正常返回后，Runtime 先完成 Delivery mapping、Artifact 登记与 Delivery 冻结，再自动发布 `eventType = "delivery_ready"`、`eventKey = "runtime.delivery_ready"` 的权威业务事件。事件 Payload 固定为 `{ delivery: PublicDelivery }`。业务界面可以据此展示本轮冻结结果和文件，但只能进入“待审阅/可交付”，不能推导用户已经接受。

业务代码必须使用当前模板从 `@/sdk` 导出的守卫和常量消费交付：`isRuntimeDeliveryReadyEvent`、`isDeliveryReviewCall`、`DELIVERY_REVIEW_FORM_ID` 和 `RUNTIME_DELIVERY_READY_EVENT_KEY`。守卫负责确认事件来源、版本和公开载荷形状，业务代码不得只比较字符串后直接断言类型，也不得复制 SDK 内部校验形成第二份协议。未通过 `isRuntimeDeliveryReadyEvent` 的事件按普通业务提示降级，未通过 `isDeliveryReviewCall` 的调用按普通 Call 降级或引导回聊天；两者都不得进入交付卡片或交付动作区。

编排声明 `delivery.review.type = "user_gate"` 且 `message_type = "ask"` 时，Runtime 随后通过现有 Business 表单握手下发固定 `formId = "delivery.review"` 的调用。它是平台内置审阅表单，不是 TPE 自定义业务表单：**不要求也不应在 `schema/forms/` 自造一份 `delivery.review` Schema**。`delivery.` 整个前缀均为平台保留的 `form_id` 命名空间，业务表单不得占用。业务代码通过 `isDeliveryReviewCall(call)` 收窄类型，再读取本轮参数。

最终用户提交有效动作并收到 `accepted` 后，Runtime 直接执行该动作：完成或失败会收敛当前 Business，改走路线会创建并进入新的 Runtime。业务界面不得等待一条额外的 Agent 消息来完成本次审阅，也不得同时打开普通聊天输入；只有审阅契约明确进入 `agent_gate`，或用户选择了已声明的“交由 Agent 处理”动作时，界面才进入“等待 Agent”。

SDK 面向 App 的 `BusinessCall` 字段是平铺的：`callMsgId / businessId / orchestrationId / workflowRuntimeId / formId / formSubmitId / arguments / content`。`formId` 与 `arguments` 是同级字段，**不存在额外的 `interaction` 包装层**。宿主传输帧和 SDK 内部桥接结构不属于业务代码契约，业务界面不得解析。

`delivery.review` 的 `call.arguments` 固定只有两个顶层键：

| 字段 | 结构与用途 |
|---|---|
| `delivery` | 与 `runtime.delivery_ready` 事件中相同的冻结 `PublicDelivery`；即使业务事件迟到、回放或先于表单到达，本次表单仍自包含完整审阅内容 |
| `allowed_actions` | 当前允许用户选择的公开动作；每项只有 `action_key`、`label`，以及可选 `description` |

`PublicDelivery` 是关闭的根对象，只包含以下字段：

| 字段 | 结构与界面处理 |
|---|---|
| `delivery_id` | 本轮冻结交付的关联键，只在页面内部用于合并事件与表单，不向最终用户显示 |
| `output` | 编排 `delivery.mapping` 的求值结果，根必须为对象；其中 `output.display` 是平台标准展示出口。界面先校验标准结构，再按四个业务区块渲染，**不得**遍历整份 `delivery` 或猜测任意输出字段 |
| `artifacts` | 已登记文件数组。每项包含 `artifact_ref / display_name / media_type / size_bytes / workspace_path / output_paths` |
| `review` | `{ type, message_type }` 的审阅摘要，用于解释当前由用户还是 Agent 审阅；内部动作路由不在这里公开 |

`artifacts[].output_paths` 是该文件在 `delivery.output` 中出现的稳定 JSON 路径，例如 `$.report`；它用于把结构化业务字段与文件卡片建立关系。`workspace_path` 是 SDK 文件展示和下载能力所需的定位值：业务代码可以把它交给当前模板公开的 `sdk.file.getViewUrl`、`sdk.file.download` 或保留件，但**禁止**把路径本身作为文本、复制内容、网址或调试信息显示给用户。临时展示 URL 现取现用，不写入状态、表单或存储。

`output.display` 使用 `DeliveryDisplay` 标准结构，五个字段全部必填，三个数组允许为空：

| 字段 | 结构与界面处理 |
|---|---|
| `schema_version` | 当前固定为 `"1.0"`，只用于兼容判断，不作为用户文案展示 |
| `headline` | 交付主标题，作为结果区最高层级标题 |
| `facts` | `key/label/value/unit?` 组成的事实数组，按稳定键值或指标行展示 |
| `notices` | `key/level/title/message` 组成的提醒数组，按 `info/warning/error` 映射为分级中文提示 |
| `sections` | `key/title/content` 组成的正文数组，按数组顺序展示分节内容 |

`isRuntimeDeliveryReadyEvent` 和 `isDeliveryReviewCall` 只保证公开 Delivery 根结构及通道身份成立，不替业务页面校验 `output.display` 的五字段。标准展示不合契约时，保留已验证的 Runtime 状态和文件能力，将结果区降级为稳定中文提示并引导回聊天；禁止遍历原始 `output`、展示 JSON 或自行猜测字段。当前脚手架的 `src/pages/demo2/DeliveryReviewPage.tsx` 展示了守卫、双通道按 `delivery_id` 合并、四区块展示、文件区和动作区的完整参考；它仅用于理解 SDK，正式业务界面必须按本场景重做设计并在打包前删除 Demo。

`allowed_actions` 已由 Runtime 根据编排动作生成中文 `label`，可以直接作为按钮文案；`description` 存在时作为影响说明。界面不得根据 `action_key` 猜内部 `kind`、目标路线或风险，也不得自造一套动作。提交时只回传 `{ "action_key": "<用户选择>" }`：

```ts
await sdk.business.reply(call.callMsgId, { action_key: selectedActionKey });
```

`action_key` 不在当前 `allowed_actions` 内时，服务端返回 `rejected` 并保持同一待处理调用；界面保留交付内容和选择状态，提示用户重新选择，复用同一 `callMsgId`，不得关闭审阅页或自动重试。只有 `accepted` 的第三次握手与后续 Business 状态才能收敛业务完成度；Runtime 成功只表示执行成功，不能替代业务验收。

`runtime.delivery_ready` 事件与 `delivery.review` 表单是两条可独立重放的现有通道，可能因实时投递、补拉或迟到订阅而先后到达。界面按 `delivery_id` 幂等合并视图，不要求先收到事件才能渲染表单，也不因表单先到而伪造业务事件。`delivery.review.type = "agent_gate"`，或 `user_gate` 且 `message_type = "result"` 时不会下发审阅表单：前者是唯一默认唤起 Agent 的审阅形态，后者由 Runtime 按现有结果消息与结束链路自动完成。

## 11. 预设计与编码前必须形成的设计产物

方案确认将包含 Workflow 后，在 Workflow 脚本制作前记录 `ui_predesign_brief`；全部 Workflow、业务事件和顶层编排稳定后，再用真实资产把它更新为 `ui_design_brief`。两份检查点使用相同结构，前者允许把尚未发布的运行事实标为待冻结，后者不得保留未经核对的假设。至少包含：

### 11.1 产品摘要

- 业务界面的一句话价值；
- 主要用户和最高频任务；
- 本次覆盖的路线与明确不覆盖的路线；
- 最终交付及到达标准；
- 档案如何影响界面；
- 高风险与权限边界。

### 11.2 场景—界面映射表

使用第 3 节结构，覆盖每条路线、入口表单、运行中交互和交付。

### 11.3 页面地图

列出每个页面或主要视图：进入条件、解决的问题、主行动、离开条件。没有独立导航价值的状态优先做同页状态，不为了页面数量拆路由。

### 11.4 模块决策账本

| 模块 | include / exclude | 业务理由 | 事实源 | 验收场景 |
|---|---|---|---|---|

所有条件模块都要登记。`exclude` 同样要说明为什么不会伤害主路径。

### 11.5 状态—行动矩阵

使用第 4.2 节结构，补上本场景真实状态、文案、禁用策略和恢复动作。

同时补充业务事件归约表：每个已声明的 `eventKey/eventVersion` 对应哪个视图状态、哪些 Payload 字段可展示、`live/backfill/replay` 是否产生一次性反馈，以及与 Runtime 快照、Business 表单握手和 Delivery Review 冲突时的权威来源。

### 11.6 视觉与文案承诺

按第 8 节的六项承诺记录：使用场景、风格取向、参考与参考点、唯一识别点、字体层级、颜色/密度/动效/趋同回避。同时列出业务术语表、服务端枚举到中文状态的映射、允许保留的英文例外，以及本界面中必须隐藏的内部标识类型。

### 11.7 关键交互与边界样例

至少准备：

- 一条主路径正例；
- 一条入口被退回修改的反例；
- 一条运行中需要用户补充的路径（如果存在）；
- 一条权限不足或运行失败路径；
- 一条成功交付后的审阅或复跑路径。

此外从第 9 节中选出本场景最可能发生的边界，至少覆盖：超长中文、空数据、权限变化、重复提交、事件迟到或乱序、契约漂移，以及一个涉及文件或敏感数据的异常。

只有当这些产物能相互对齐，且页面范围、关键模块、路线入口、档案使用、高风险默认值和交付方式已由开发者确认，才进入脚手架编码。两项以上关联决策通过预设计 Plan 集中确认，单个新增决策单独询问；纯布局、组件拆分和不改变体验语义的工程细节可以自主完成。

## 12. 设计验收与常见反模式

### 12.1 设计验收

- **业务相关性**：不看 Logo 也能从任务、字段、阶段和结果看出这是哪个业务场景；
- **可追溯性**：每个核心模块都能追溯到场景事实和公开契约；
- **主路径闭环**：从开始到交付无需跳出页面补做本可预见的步骤；
- **审阅不缺位**：需要用户批准、满意度确认、方案选择或修订的路线，已按 Delivery Review 展示结果和允许动作，没有用“结果已生成”冒充“用户已接受”；
- **状态完整**：送达、受理、运行、等待、成功、失败和只读没有混淆；
- **选择克制**：没有因为“可能有用”而堆入无证据模块；
- **个性化可解释**：档案推荐和默认值可见、可改、可降级；
- **错误可恢复**：退回不丢输入，失败不给无效动作，异常能回到聊天；
- **结果可决策**：用户能理解结论、证据、交付物和下一步；
- **技术不外露**：不显示内部 ID、节点、工具、提示词或原始 JSON。
- **风格有承诺**：视觉选择具体且与业务相关，不是通用渐变、统计卡和“科技感”套路。
- **中文完整**：用户可见的交互文案默认全中文，必要英文均属于明确例外并有中文语境。
- **边界可收敛**：空、长、慢、重复、乱序、无权、漂移和部分交付都有明确界面结果。
- **事件可恢复**：订阅、快照、自动补拉和纯归约器的职责清楚；迟到订阅、回放、断线、缺口和契约漂移不会触发重复副作用或整页失效。

### 12.2 常见反模式

| 反模式 | 为什么有问题 | 改法 |
|---|---|---|
| 把通用 SchemaForm 当成正式产品 | 只保证能输入，不能保证用户理解和低错误率 | 按业务分组、专属控件和正反例重构 |
| 首页堆满路线、历史、聊天、统计 | 主行动不清，认知负担高 | 以最高频任务为首页，其他按需进入 |
| 显示 Workflow、节点和技术状态 | 用户无法据此决策 | 映射为业务路线、里程碑和影响 |
| 只设计成功截图 | 真正使用时等待、退回和失败体验断裂 | 先完成状态—行动矩阵 |
| 推荐没有依据 | 用户误以为平台替其做了可靠判断 | 展示依据，证据不足时不推荐 |
| 档案默认值不可修改 | 历史错误会被固化 | 标记来源、允许覆盖、冲突时询问 |
| 收到提交回执就跳结果页 | 把送达误报成完成 | 等待受理和 Runtime 终态 |
| 为了“智能”重复造聊天框 | 与宿主输入互斥、历史和权限机制冲突 | 用 `openChat`，只在确有价值时展示消息 |
| 错误统一显示“请重试” | 权限、业务拒绝和不可恢复失败不能靠重试解决 | 按错误类型给真实下一步 |
| 为了显得完整做无用看板 | 数据块很多但没有决策价值 | 每个指标绑定用户动作，否则删除 |
| 通用蓝紫渐变加等权卡片 | 与业务无关，层级和品牌识别都很弱 | 先完成六项视觉承诺，用主任务和业务识别点组织界面 |
| 英文按钮、状态或技术枚举直出 | 用户被迫理解开发契约，术语还会随后端变化 | 建立稳定的中文业务文案映射 |
| 为便于定位问题显示内部 ID | 泄漏实现细节，且对用户没有行动价值 | 页面内部持有；对外只显示业务名称或服务端公开的问题参考号 |
| 直接渲染错误对象 | 出现 `[object Object]`、原始代码或敏感信息 | 按错误类型映射中文解释和可执行下一步 |
| 在事件回调内查询或轮询状态 | 高频帧会放大为查询风暴，回放还会重复副作用 | 一次建立 `onBusinessEvent` 订阅，首次读 Runtime 快照，其余交给 SDK 自动补拉 |
| 页面各自维护事件去重和水位 | 路由切换后产生多个事实版本，与 SDK 内置机制冲突 | 共享协调层只保留业务投影，排序、去重、缺口和回放交给 SDK |
| 遍历整个 `delivery` 或任意 `output` 对象渲染交付结果 | 内部标识与 Workspace 路径被摆给用户，展示结构随业务输出漂移 | 校验并渲染 `delivery.output.display`，文件经 `artifacts`，其余字段不做通用遍历（§10.4） |
| 界面按自己定义的输出结构猜着渲染 | 结构由本场景包的 `output_schema` 与 `delivery.mapping` 决定，猜出来的字段名对不上 | 回读自己已冻结的 Schema 与 mapping，按真实字段写专属渲染 |

## 13. 仅供参考的完整示例

以下示例只展示方法，**不得**复制它的路线、字段、文案或页面结构到其他场景包。

假设一个“门店经营诊断”场景包有三条候选路线：经营诊断与增长方案、门店风险处置、既有方案修订。业务档案包含门店类型、历史经营指标和已确认风险。

### 场景—界面映射摘要

| 场景事实 | 界面设计 |
|---|---|
| 三条路线解决不同目标 | 首页显示三张业务路线卡；根据档案给出可解释推荐，但用户可切换 |
| 经营诊断需要收入、成本和门店基本信息 | 采用分组表单；档案已有信息预填并标注来源 |
| 风险处置需要已识别风险 | 路线卡显示当前已知风险数量；无风险事实时不推荐该路线 |
| 方案修订必须基于既有交付 | 先选择历史交付，再填写修订意见；不让用户重新输入全部门店信息 |
| 执行分多个阶段 | 进度显示“数据核对—问题诊断—方案生成—结果审阅”，不显示节点名 |
| 结果需要用户审阅 | 结果工作台展示摘要、证据、交付文件和“批准/要求修订” |

### 模块决策摘要

| 模块 | 决定 | 理由 |
|---|---|---|
| 路线选择 | include | 用户目标不同，会改变执行路线 |
| 档案摘要与推荐 | include | 档案事实能影响路线与默认值，且可解释 |
| 分步向导 | include | 经营字段多且有分组，首次输入容易遗漏 |
| 文件上传预览 | exclude | 当前真实入口没有文件字段 |
| 阶段状态 | include | 执行多阶段，用户需要辨别当前阶段、已完成事项与等待原因 |
| 待处理中心 | include | 结果生成后有正式审阅表单 |
| 历史与修订 | include | “方案修订”依赖旧交付，历史具有直接业务价值 |
| 常驻聊天窗 | exclude | 主路径可由结构化界面完成；异常时打开宿主聊天即可 |

### 视觉与文案承诺摘要

- **使用场景**：店长在营业结束后用桌面端快速录入、查看问题并做次日决策；
- **风格取向**：温和的经营复盘手记，而非技术监控仪表盘；
- **参考点**：参考编辑简报的标题层级和纸面留白，参考成熟财务工具对数字对齐和风险语义的处理，不复制其品牌外观；
- **唯一识别点**：首屏以“今日最需要决定的一件事”带出主路线，而非统计卡集合；
- **字体与层级**：使用脚手架中文字体栈，标题、正文、表格和金额各自有稳定字重与行高，不引入无法保证加载的外部字体；
- **取舍**：亮色纸张底、深墨绿主行动、砖红风险语义；不用蓝紫渐变、玻璃卡片、等权彩色统计卡、装饰性光斑和循环动画；
- **文案**：界面交互全部使用简体中文，路线、状态和错误均使用门店经营语言，不显示任何内部标识或开发术语。

这个示例的价值在于：每个模块都有场景事实支撑，且被排除的模块也有明确理由。实际项目必须重新读取自己的场景包、编排、表单、档案和真实使用证据后独立设计。

## 14. 定位与生命周期

业务界面是场景包面向最终用户的专属操作层，不是独立于场景包存在的普通网站。一个业务界面**必须**：

- 绑定唯一 `scene_package_id`；
- 在同一个场景包制作工单中创建、验证、部署和留痕；
- 消费该场景包公开的输入、状态和交付契约，不读取内部脚本、提示词、DAG 或工具配置；
- 场景包相关运行契约变化后重新验证和部署。

业务界面是否交付由开发者选择决定，不由 Workflow 资产或开发 Agent 自动决定。场景包总体方案提案包含一条或多条 Workflow 时，场景包助手 MCP 在同一份总体 Plan 中说明业务界面的价值、范围与额外制作工作，并询问开发者是否制作。总体 Plan 确认后不再重复询问：选择制作时，进一步提交页面范围和模块预设计 Plan；未完成预设计确认、契约冻结、界面验收和部署就**不得**宣称业务界面已交付。选择不制作时，继续完成场景包且不执行任何界面校验。没有 Workflow、当前不具备制作前提时不进入界面制作。开发者决定只写入工单事实，不转换成场景包资产字段或验收门。

当前 `scene_package_ui_bundle` 除模板下载外要求目标场景包至少挂载一个 Workflow。因此定制业务界面目前**只能**作为 Workflow 场景包的交互层，纯 SA 或只有普通任务点的场景包无法制作。若未来实时契约解除该限制，再按新版本调整；**禁止**通过伪造 Workflow、借用无关 Workflow 或直接上传绕过。

## 15. 事实源和模式门

按以下优先级判断当前真实能力，低层资料**不得**覆盖高层事实：

1. 你当前工具列表里 `scene_package_ui_bundle` 的实际 action 和参数定义；
2. 本工单通过 `download_template` 下载的官方模板、SDK 类型和模板内文档；
3. `get_asset` 反读的当前场景包、Workflow 和 `workflow_orchestration`；
4. 服务端 Preview、Bubble、部署校验和 Max Runtime 的真实结果；
5. 历史仓库分支、示例和本文的流程说明。

**不得**把历史脚手架分支固定写入交付物。每次制作都下载当前官方模板，记录模板返回的可验证版本信息；若响应没有版本或 SHA256，只记录实际文件名、大小和下载时间，并把“模板身份不可复现”列为平台盲区。

### 当前模式分流

- **单路线**：场景包即使只有一条业务路线，也通过当前 Business 契约的公开 `orchestration_id/form_id` 启动；页面不直接运行某个 Workflow，也不暴露 Workflow slug。
- **多路线图编排**：只有模板和宿主同时公开匹配版本的 Business/Runtime 启动、状态、交互和 Delivery Review 契约时，才按公开 `orchestration_id/form_id` 启动路线；页面不选择 `tpe_id/node_id`，不执行或解释 DAG。
- **平台能力不完整**：编排能保存 2.0 但宿主或模板 SDK 尚未支持对应 Runtime 时，记录 `platform_blocked` 并回落 Agent 对话界面。设计稿和集成分支不是可用性证据。
- **契约不兼容**：把开发者已选择制作的业务界面标记为 `platform_blocked`，暂时回落现有 Agent 对话界面；该结论只约束界面发布。是否交付不含界面的场景包，按开发者确认的范围和剩余能力处理。

如果当前模板没有公开与场景包编排版本匹配的 Business 启动、交互和 Runtime 能力，**必须**停止发布并报告宿主 SDK 能力缺口。**禁止**选择第一条 Workflow、直接运行入口 Workflow、伪造 Gate，或在前端手工推进节点来冒充整包编排。

## 16. 冻结业务界面契约

本节位于业务界面实现阶段。只有全部受影响 Workflow 完成 Preview、bubble 和单体验收，顶层编排保存并反读通过，且目标环境支持的路线冒泡已执行后，才能把第 1–13 节形成的 `ui_predesign_brief` 更新为最终 `ui_design_brief` 并冻结工程契约。目标环境未提供路线冒泡入口时记录整图运行盲区，不把单条轨迹拼成整图证据；这本身不替代对宿主 Business/Runtime 契约是否可用的判断。预设计提前影响 Workflow 的事件和公开语义；编码、模板下载和部署仍必须等待以下事实稳定：

1. 用 `get_asset(asset_type="scenario_package")` 反读场景包 ID、名称、TPE 列表、编排版本和当前 `workflow_orchestration`。
2. 对每条业务界面涉及的 Workflow 调用 `get_asset(asset_type="tpe")`，取得真实 `slash_command`、`input_schema`、`output_schema`、业务事件声明和当前脚本版本/摘要；同时反读顶层编排中的路线、入口、节点映射、运行中交互和交付。
3. 将本次反读结果与现有 `schema/orchestrations/`、`schema/forms/`、业务事件契约快照、页面控件/结果渲染逻辑和 `ui_contract_snapshot` 逐项对比，判断界面契约是否仍为最新。输入 Schema 变化要检查表单与校验，输出 Schema 变化要检查结果与文件展示，事件变化要检查阶段、结果、提醒和交付模块，编排或脚本变化要检查路线入口、用户/Agent 介入、里程碑和交付语义。
4. 变化影响公开输入、运行中交互、业务事件、结果、路线或交付时，先更新业务界面契约和界面实现，再重做交互、构建与部署验收。脚本实现改变但公开契约未变时，仍要更新快照中的脚本版本/摘要并回归主路径。无法证明兼容时停止发布，禁止用旧 Schema 或旧事件契约迁就新 TPE 或新编排。
5. 只在宿主公开对应 Business/Runtime 契约时，以路线入口表单为输入、以 Delivery Review 后的公开结构为结果；单条 Workflow Schema 只用于核对节点输入输出，**不能**直接充当页面公开契约。
6. 按当前编排逐条生成 `schema/orchestrations/<orchestration_id>.json`：业务名称、描述、入口 `form_id` 和必要说明来自已确认的场景路线，文件名与公开 ID 一致。
7. 按入口表单和运行中自定义交互生成 `schema/forms/<form_id>.json`：完整保留真实 JSON Schema；可在 notes 中补充经确认的控件、分组、只读回显和用户解释建议。固定平台表单 `delivery.review` 没有独立 Form Schema，不在此目录自造文件，按 10.4 的 `BusinessCall` 约定专门渲染。
8. 删除模板自带的演示编排、演示表单和 v1 遗留 `schema/workflows/` 内容。页面只读取当前场景包的 `orchestrations/forms`，不从设计稿复制未来字段。
9. 记录场景包 ID、编排版本、Workflow 脚本版本/摘要、业务事件契约版本/摘要、公开 orchestration/form ID、Schema 摘要，以及可用的 revision/hash，形成 `ui_contract_snapshot` 检查点。

`schema/orchestrations/` 与 `schema/forms/` 是编码期快照，不是运行期执行引擎。页面只通过宿主公开的 Business/Runtime 能力启动和跟踪运行；发现编排版本、公开 ID 或 Schema 不兼容时停止结构化提交并引导用户回到聊天，不在浏览器本地猜测或修补。

上述对比在**开始业务界面开发前**和**每次上传/部署前**各执行一次，防止开发期间 TPE Schema 或编排脚本已变更而界面仍按旧快照发布。比较脚本是为了识别语义和版本变化，**不得**将脚本正文复制到前端 Schema、源码或用户界面。

以下任一变化都会使既有界面验收失效：

- Workflow 输入输出、是否上线或其公开业务语义发生变化；
- Workflow 业务事件类型、事件名、版本、成立条件或 Payload Schema 发生不兼容变化；
- 顶层编排输入、节点映射、delivery 或编排契约版本发生变化；
- 公开 orchestration/form ID、入口表单或运行中交互表单发生变化；
- App 使用的 SDK capability 或最低 SDK 版本发生变化；
- 场景包绑定关系发生变化。

## 17. 使用官方脚手架开发

初始化闭环有三条不可跳过的原则：**下载官方模板是强制第一步、必须在返回的目录里开发、先读完模板说明再动手**。

1. 冻结界面契约后，**首先**调用 `scene_package_ui_bundle(action="download_template", task_id=<task_id>)`。业务界面开发**禁止**从空目录、其他脚手架、代码仓库克隆或旧源码副本开始。
2. 只有响应 `success=true` 且 `data` 同时提供非空 `file_name`、正整数 `size_bytes`、非空 `download_url` 和正数 `expires_in` 时才继续。短链是临时凭证，只用于本次下载，不向开发者或最终用户展示，也不写入工单、源码、日志或记忆文件。
3. 在短链有效期内，用支持 HTTPS、重定向和非 2xx 失败退出的下载能力，把文件写入当前可写工作区的独立过程目录。**不得**把短链当成本地路径交给文件读取工具，也**不得**假定工具已自动解压。
4. 下载后检查文件真实存在且非空，实际字节数**必须**等于 `data.size_bytes`；文件名和实际归档均须为 `.tar.gz` 或 `.tgz`。不一致时停止开发并重新取得当前模板，**禁止**继续使用残缺包。
5. 解压前先检查归档成员，拒绝绝对路径、`..` 路径穿越、逃逸目标目录的链接或设备文件；解压到新的空目录，**禁止**覆盖已有项目。
6. **解压后清理 macOS 元数据残留**。官方模板包在 macOS 上打包时可能带入 AppleDouble 旁车文件，
   它们是二进制内容却带着源码扩展名，会让测试框架把 `src/._App.test.tsx` 当成测试文件解析，
   直接报 `[PARSE_ERROR] Invalid Character`：

   ```bash
   find <模板根目录> \( -name '._*' -o -name '.DS_Store' \) -delete
   rm -rf <模板根目录>/__MACOSX
   ```

   删除后再开始开发。**不要**因为构建报解析错误就去改模板源码或跳过测试——先确认是不是
   这些残留文件造成的。
7. 解压后定位唯一包含 `goalfy-app.json` 的模板根目录，并把它记录为本次业务界面的唯一开发目录。不存在或存在多个候选根目录时停止，**不得**猜选。
8. 完整阅读模板根目录的 `AGENTS.md`、`README.md`、`schema/README.md` 和 `src/sdk/docs/README.md`。涉及业务事件与最终交付时，继续读取 `src/sdk/docs/business.md`、`src/sdk/delivery.ts`、`src/sdk/business-types.ts` 和 `src/pages/demo2/DeliveryReviewPage.tsx`；文档与类型实现不一致时以当前固定 SDK 源码为准并记录模板文档缺口，不修改 SDK。缺失任一模板声明的必读文件，或其指令相互冲突时，停止编码并报告模板问题。
9. 记录不含短链的 `template_identity`：返回文件名、声明字节数、实际字节数、下载时间，以及模板响应实际提供的版本或校验值。响应未提供版本或 SHA256 时明确记录该盲区，不自行计算模板内容哈希并冒充官方版本。

`download_template` 初始化的是与场景包同工单、随后由 `scene_package_ui_bundle` 上传和发布的业务界面源码。用其他方式初始化的目录，**不能**证明取得了当前场景包的界面模板。

遵守以下开发边界：

- 业务代码只写入模板声明的业务页面和组件目录；
- `src/sdk/**`、启动入口、错误边界和桥协议是固定层，**禁止修改**；
- `src/shared/**` 是脚手架保留件，业务代码可使用、不修改、不删除；新的共享业务组件放在模板声明的业务目录；
- 使用模板既有框架、路由和样式方案，不另起一个前端工程；
- `goalfy-app.json.scenario_pack_id` **必须**等于本工单真实场景包 ID；
- `name/version/default_route/min_sdk/capabilities` 与实际页面和 SDK 调用一致；其中由脚手架命令维护的能力声明不手工改写；
- 文件字段使用 JSON Schema 的 `format:file/image` 渲染上传，提交 SDK 上传接口返回的当前项目内路径，**不要**自行拼接路径；
- 复杂数组、对象、日期、表格、时间线或画布使用专属业务控件，不把 JSON 文本框当成默认完成态；
- 提交成功只代表请求被接受，不代表 Workflow 完成；阶段和结果**必须**使用已声明的 Workflow 业务事件与宿主权威快照，不得从任务点、工具调用或普通消息猜测。
- `runtime.delivery_ready` 与 `delivery.review` 必须分别通过当前 SDK 的 `isRuntimeDeliveryReadyEvent`、`isDeliveryReviewCall` 守卫；使用 SDK 导出的保留常量，不复制字符串协议。守卫通过后直接消费 `payload.delivery` 或同级 `arguments.delivery/allowed_actions`，以 `output.display` 渲染标准结果；不得要求静态表单 Schema、不得读取不存在的 `interaction` 包装层。守卫失败时安全降级，不得强制断言为交付。
- 用户可见文案默认全部使用简体中文；不可翻译的品牌、用户原始文件名或原文引用才可保留英文，且按设计指南提供中文语境；
- 服务端枚举、开发术语和错误信息必须映射为稳定的中文业务文案，不直接渲染原始对象、JSON 或 `[object Object]`；
- 场景包、Workflow、任务点、编排、表单、运行、业务、项目、工具、部署、跟踪和存储等内部 ID/slug，以及 Workspace 路径、预签名 URL、错误码和堆栈，只能在代码内部使用，禁止出现在用户可见界面、文件名和网址中；
- 开发前完成视觉与文案承诺，并将中文完整性、内部标识不可见、错误脱敏及本场景高风险边界纳入测试。

开发阶段保留模板 Demo 作为调用示例，但正式打包前**必须**删除 Demo 页面、演示路由、演示 Workflow 契约和首页占位文案。**不得**把演示场景包 ID、Workflow slug、测试文件路径、用户身份或构建机路径写入源码。

## 18. SDK 与安全边界

业务代码只使用当前模板公开的 SDK。Skill 中不复制完整 SDK 类型；开发时以模板的类型定义和文档为准。

典型能力域包括：

- 会话、语言和初始路由；
- Workflow/整轮编排的公开运行入口；
- 项目状态和协作者权限；
- 历史消息与实时消息；
- Workflow 业务事件订阅、重放与 Runtime 快照；
- Delivery 守卫、标准结果展示、最终审阅与交付文件；
- 文件上传；
- 打开宿主聊天；
- 主题同步。

**禁止**：

- 直接使用 `fetch/XMLHttpRequest/axios` 访问平台内部 API；
- 读取或写入 `localStorage/sessionStorage/document.cookie`；
- 访问 `window.parent/window.top` 或自行定义 postMessage 协议；
- 向 iframe 下发登录 token、Cookie、预签名 URL、Workspace 挂载信息或数据库身份；
- 在业务界面公开 MCP 工具清单、Toolset、FastAgent、提示词、脚本、`input_mapping` 或 `sa_handoff` 内部指令；
- 在前端执行 DAG、选择下一节点、构造未声明的 Gate action 或直接重试失败节点。
- 直接展示英文按钮、英文状态、内部字段名、枚举值或开发者错误文案；
- 为了调试或客服定位，把任何内部 ID、slug、路径、临时 URL、原始错误对象或平台调用细节放到页面。

MCP 工具清单只服务制作 Agent。浏览器业务界面只看到宿主 SDK 和公开运行契约。

## 19. 打包、上传和部署

开发过程执行当前模板要求的 `npm run check`，交付前执行 `npm run check:release` 和 mock 交互验证。当前模板明确把构建、上传和发布交给场景包制作流程时，禁止在本地自行 build 或发布。仅命令执行通过、但没有实际验证关键输入、上传、提交、等待、事件恢复和结果展示，不算界面验收。mock 只验证界面状态机，不得用它证明真实业务路线成立。

打包源码而不是构建产物：

1. 删除 `node_modules`、`dist`、`.git`、`.env*`、系统元数据和模板 Demo。
2. 创建 `.tar.gz` 或 `.tgz`，使用稳定相对路径，避免把外层临时目录多包一层。
   **在 macOS 上打包必须加 `COPYFILE_DISABLE=1`**：

   ```bash
   COPYFILE_DISABLE=1 tar czf template.tar.gz -C <源码目录> .
   ```

   不加这个变量时，`tar` 会为每个文件额外写入一份 `._` 开头的 AppleDouble 元数据旁车文件。
   它们是二进制内容却带着源码扩展名，测试框架会把 `src/._App.test.tsx` 当成测试文件解析，
   直接报 `[PARSE_ERROR] Invalid Character`，构建必挂。
3. **打包后必须核对归档清单**，确认没有禁入条目：

   ```bash
   tar -tzf <包名>.tar.gz | grep -E '(^|/)\._|\.DS_Store|__MACOSX' && echo "存在禁入条目，需重新打包"
   ```

   任意目录层级出现 `._*`、`.DS_Store` 或 `__MACOSX` 都**必须**删除并重新打包，
   **禁止**带着它们上传。这类文件不是源码，也不能靠"上传后再说"补救。
4. 对实际压缩包字节计算 `size_bytes` 和 64 位小写 SHA256。
5. 调用 `scene_package_ui_bundle(action="prepare_upload", ...)`。
6. 严格按返回的 method、headers 和 URL 执行 HTTP PUT，不把预签名 URL写入工单。
7. 调用 `complete_upload` 绑定当前源码包。
8. 调用 `deploy`，传入实际压缩包 SHA256。
9. 若未返回终态，使用同一 `deployment_id` 调用 `status`，直到成功、失败或平台明确超时。
10. 成功后调用 `get` 反读当前包和激活地址。

部署是外部发布动作。开始 `deploy` 前向开发者说明会发布业务界面；如果当前任务上下文已经明确授权创建并发布整个场景包及其业务界面，则不重复确认同一动作。上传源码包本身不等于发布成功。

## 20. 更新、诊断和失败恢复

- **界面代码问题**：修复同一源码目录，重新检查、打包、上传和部署。
- **Workflow 契约变化**：输入输出、业务事件、脚本或公开语义变化时，先更新并重新验收 Workflow，再重新生成界面契约和部署；**不得**只改前端适配旧快照。
- **部署超时**：保存 `deployment_id`，使用 `status` 续查；不要重复 `deploy` 创建并行任务。
- **部署失败**：依据结构化 stage/error 修复根因，**禁止**只改错误文案或跳过失败检查。
- **模板下载失败**：区分短链过期、HTTP 失败、大小不一致和归档不安全；重新获取当前短链后从下载校验开始，不在旧文件上续写或手工补齐缺失内容。
- **模板根目录不唯一或必读说明缺失**：裁决为模板交付问题并停止编码；**不得**自行挑选目录或从历史仓库补文件。
- **模板能力不足**：记录缺失的 SDK 能力和受影响场景，停止该界面发布；**不得**修改固定桥协议自造平台能力。
- **诊断已有界面**：先 `get` 读取当前元数据，必要时 `download` 当前源码，再与场景包和 Workflow 当前契约比较；下载短链仅用于本次读取。

最终工单检查点记录：业务界面决策、场景包 ID、契约摘要、源码 SHA256、deployment_id、激活地址、验收裁决和剩余盲区。**不得**记录上传/下载短链、密钥、Cookie 或内部挂载信息。
