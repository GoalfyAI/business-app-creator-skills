# 验收报告与上线结果

④ 交给开发者的验收报告、⑤ 交给开发者的上线结果怎么写。什么时候交、过哪些门、结论怎么判，见 [../stages/4-试用验收.md](../stages/4-试用验收.md)「2.4 逐条判定」「2.5 交验收报告」和 [../stages/5-上线.md](../stages/5-上线.md)「2.5 上线结果」「2.6 发布要准备的材料」。Studio 下两者写进开发文档「验收报告」，版式见 [开发文档/验收报告.md](开发文档/验收报告.md)，内容照本文件。

两份都只放这个应用自己的东西，用业务话写，结论先行，每一句「通过」「已验证」都能指到证据；用词按 [../SKILL.md](../SKILL.md)「角色与用词」。

## 验收报告

本机版的检查做完就交报告。之前开发者没有明确同意过部署的，在交报告的同一条消息里问是否部署到开发者在线预览（原句见 [../SKILL.md](../SKILL.md)「红线」），依赖已部署版本的条目先记「未测」，同意后部署补测、出新一版。只交「部署好了」「请你试一下」不算交报告；「未测」的条目逐条列原因，不请开发者去演示预览、在线预览或正式入口里看、试条目。

交接消息开头「【④ 试用验收 → 等你确认】」，附验收报告，七项：

| 项 | 写什么 |
|---|---|
| 结论 | 四格依次：没通过、通过、要你判断（好不好你说了算）、未测，四格相加等于总条数；再单列「开发者已接受的没通过」几条。还有没通过、未测的条目时说清影响 |
| 好不好你说了算 | 每条附实际结果：报告全文或链接、内容原文、前后对比；开发者觉得不行直接说是哪一条 |
| 未测的 | 逐条写条目和原因（原因原文照 ④「2.4 逐条判定」的「未测」表），本机版起不来的写做过哪些处理和错误原文；说明这些行为没有验证，并写清以后开发者自己在哪看 |
| 全部条目 | 默认折叠，固定六列，一条验收条目一行，每格都要填（见下） |
| 用真实数据跑出的结果 | 本段真跑的结果摘要，加上 ③ 里 `full_run` 跑出的内容，和 ② 的预期对照 |
| 自动发生的 | 自动化冒泡的结果（`run_once` 不用于 ④） |
| 实际花费 | 每个按钮实际花了多少，和估算比；每份要等多久、能不能同时开几个 |

「全部条目」照这个表头抄：

```text
| # | 验收条目 | 结论 | 怎么测的 | 看到的结果 | 证据 |
|---|---|---|---|---|---|
```

- 结论只写：通过 / 没通过 / 好不好你说了算 / 未测；开发者选了接受的写「没通过，开发者选了接受」。
- 后三列用业务话，开发者不懂平台也能看懂：
  - 「怎么测的」写在哪测、做了什么。页面条目写「本机版：」加操作步骤；业务条目写「真跑：」加用了哪个例子。
  - 「看到的结果」写实际看到的页面反应、拿到的内容或写进去的记录，和条目的「这样算对」对照。
  - 「证据」写开发者能直接看的东西。页面条目放截图，Studio 下截图要能点开（[开发文档/验收报告.md](开发文档/验收报告.md)「截图证据」），不截图的写断言原文。写库的业务条目写查到的那条记录的关键内容，不写库的写拿到的产出摘要。
  - 未测的三列都写「无」。
- 真跑的 `project_id`、`workflow_trace` 摘要、本机路由、截图文件路径这类核对字段写进阶段文档 G6，不放进报告。
- 按反馈重测后只更新变了的行，修改记录写「问题 / 改了什么 / 重测了哪几条」。

「要你做的」照抄：

> ① 看验收报告；② 看「好不好你说了算」的几条，实际结果已经附在报告里；③ 都没问题回「可以上线」，有问题回「还要改：第几条」。

按情况加：

- 有「未测」条目：「这几条没有测，原因见报告；你仍然可以回『可以上线』，上线结果会单列它们，并写清你以后怎么自己看。」
- 有因为开发者还没同意部署而未测的：「你同意部署时我再部署补测；还没部署到在线预览的应用上不了线，你回『可以上线』时我会再问一次是否部署；补测有没通过的，我能改的自己改好再测（最多 3 轮），改不了或 3 轮还没过的逐条问你接不接受先上线；有要你判断的我把结果给你看，请你再说一次『可以上线』。」
- 有「没通过」的条目：先放逐条的「接受，先上线 / 等改好再上线」选择题（④「2.6 按反馈改」），开发者选完再请他回「可以上线」。
- 需求方和开发者不是同一人：请开发者把「好不好你说了算」的几条转给需求方看。

## 上线结果

### 给开发者的部分

写进工单和交付物，发给开发者：

| 项 | 写什么 |
|---|---|
| 上线的版本 | 已上线的是第几版、和上一版比改了什么；照抄「这一版成为你自己的正式版；要自己正式使用或给别人用，需要你在发布管理页发布，发不发布由你决定」。协作者提请时写「已提请，等属主上线」和草稿版本、变更说明 |
| ④ 验过什么 | 通过几条、「好不好你说了算」几条及开发者的意见、开发者选了接受的没通过条目；用真实数据跑出的结果一句话 |
| 未测的 | ④ 有「未测」条目时单列：逐条写条目和原因，说明这些行为没有验证，并写开发者自己怎么看：只有线上才能验证的，在工作台「在线预览」里或发布后在正式入口看；到点真触发、从目录或分享打开，发布后看（写清怎么看）。没有就写「没有」 |
| 实际花了多少 | 本段 N；累计 N；上限 N。以后每用一次约多少，按 PRD 的用量每周约多少 |
| 发布会怎样 | 照抄：「发布后你自己和已安装的使用者会用上这一版；正式入口和到点自动运行在发布后才能用，你自己也一样；发不发、发给谁由你定」 |
| 发布要准备的 | 发布页要的描述、Logo、版本更新说明，已按下面「发布要准备的材料」备好 |
| 你可以做的事 | 编号列出，都由开发者自己决定做不做：① 在发布管理页发布，选发给谁，填上准备好的描述、Logo、更新说明；② 发布后从 GoalfyMax 打开这个应用，看「未测的」里的几条（写清怎么看）；③ 有定时任务的，发布后在应用的「自动化」面板打开规则，外部数据有固定更新时间的写清规则时间要在它之后（按北京时间）；④ 把应用分享给使用者，可以附上下面的使用说明 |

### 附在交接消息里的几句

在上线结果后面附，不单独成节、不放进交付物的上线结果：

- **怎么打开**：发布后开发者和使用者从 GoalfyMax 打开这个应用，或从目录、分享打开；发布前开发者想自己看，用工作台「在线预览」。不写容器地址。
- **使用说明**：使用者第一次打开看到什么、先做什么（每人一份自己的数据，打开是空的；在线预览里的数据不会带过去），平时怎么用，按业务顺序一句话；有授权的按 [../reference/授权与充值.md](../reference/授权与充值.md)「上线前核对」列出要授权的平台。
- **平台提醒**：平台通用的提醒照实写一句，例如刚发布一两分钟内可能启动失败、一段时间没人用会休眠；改已上线的应用时，发布后正在用的人会看到什么变化、已有数据怎么处理。
- **还没验证的和风险**：④ 里开发者选了接受的没通过条目、能力缺口。

### 发布要准备的材料

发布页要求描述、Logo、版本更新说明。三样都在上线结果里备好，开发者发布时直接用：

| 材料 | 给什么 | 怎么写 |
|---|---|---|
| 描述 | 可直接粘贴的一段文字 | 给使用者看：这个应用帮谁做什么、打开后先做什么，两三句业务话，不写平台术语和内部名称 |
| Logo | 应用工程里图片文件的路径 | 用应用工程里已有的 Logo 图片；没有就按 [../reference/前端页面.md](../reference/前端页面.md)「Logo」做一张放进工程，给出路径 |
| 版本更新说明 | 可直接粘贴的一段文字 | 第一次上线写「首个版本」加主要功能；改已上线的应用写和上一版比改了什么、使用者会看到什么变化、已有数据怎么处理 |

### 交接消息怎么写

交接消息开头「【⑤ 上线 → 已完成】」，「刚做完」写上线的是第几版并补「这一版成为你自己的正式版；要自己正式使用或给别人用，需要你在发布管理页发布，发不发布由你决定」；「要你做的」写：

> 看上线结果；发不发布、发给谁由你定，发布要用的描述、Logo、更新说明已备好，不用回复我。

「要你做的」不写「请你发布」，也不等开发者回「发布了」再结单。

协作者提请时交接消息只说：「已提请，等属主上线。」后续说法见 [../reference/多人协作.md](../reference/多人协作.md)「提请属主上线」。
