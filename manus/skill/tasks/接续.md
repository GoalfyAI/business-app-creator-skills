# 接续

## 识别信号

- 开发者说「继续」「接着做」「上次那个应用」，或当前目录已有 `app.json`、`WORKSPACE.md`、`workspace.json`。
- 开发者给了此前的 `task_id`、应用名或 `business_ui_id`。

## 先读什么

1. 阶段记录：先 `business_ui_stage(action="list", task_id=…)`（只知道应用时用 `business_ui_id`），看当前阶段和最新一条的下一段计划；为空而本地已有 `passed` 的 flow 时按空链补记。规则见 [../reference/阶段记录.md](../reference/阶段记录.md)「接续与修订先 list」。
2. 当前应用工程根的三件套：`WORKSPACE.md` 的 `current_stage` 与 `business_ui_id`，`workspace.json` 的阶段标记，`docs/stages/` 下当前 flow 的阶段文档，`docs/proposal/index.html` 的确认页与 `status`。
3. 原工单：`task_manager(action="get", task_id=…)` 看已记的 checkpoint（资产 ID、版本、run_id）。原工单是只读或已结单时新建 write 工单并传 `continued_from_task_id`。
4. 本地缺失或换了机器：`workspace_remote_status` 看云端状态，`workspace_pull` 取回，先比较差异、保留本地新改动再合并，不默认用云端覆盖本地。规则见 [../reference/开发者中心与工作区.md](../reference/开发者中心与工作区.md)。
5. 脚手架版本：按 [../reference/脚手架与预置件.md](../reference/脚手架与预置件.md) 带 `workspace_id` 调一次 `download_template` 核门槛；低于必须线先迁移。
6. 缺失的工作区文件用 `npm run scaffold:repair -- --app-name "<应用名>"` 补，保留已有事实。

## 从哪一段进

按阶段记录最新一条、方案页 `status`、`current_stage` 和工单 checkpoint 判断做到了哪一步，先用一句话告诉开发者上次做完哪一段、下一步做什么，从还没完成的那个 flow 接上；标记为 `not_started` 的可能是上次有意跳过的，按第 5 节重新判断要不要做，不因为没标 `passed` 就补做。接上前核对它依赖的证据是否仍成立（资产还在、版本没被别人改、冒泡证据仍是当前合同下的）；不成立就回到证据失效的那个 flow。旧应用的阶段名可能是旧名，按 G 键对应，只改状态不改名。

开发者要看本地页面而「演示预览」是空的，按 [../reference/开发者中心与工作区.md](../reference/开发者中心与工作区.md) 的「演示预览为空」判断是还没生成完成版、需要生成，还是要重新启动。
