# 自动化

## 适用场景

确认页里有「到点自动做」或「数据一变就自动做」的功能，要给应用声明自动化规则、验证它、或排查自动运行没发起 / 被跳过时读。

## 规则

### 平台怎么发起

用户在智能应用的「自动化」面板开启规则后，到点由 GoalfyMax 后台以**用户本人的正式身份**建一个新项目（出现在用户项目列表，名称为「自动化名称 · 计划时刻」），提交这条路线的入口表单，效果与用户手动提交一致；每次运行的 `business_id` / `form_submit_id` 都是新的。交付停在 `user_gate` 审阅进消息中心，运行记录里记为「待审阅」。触发前的门禁：应用已发布且用户仍持有、实例就绪、账号与组织可用、上一次已结束、配额与余额足够；不满足时本次记「跳过」并写原因。超过声明的 `timeout_minutes` 平台停掉项目记「超时」；同一原因连续失败达到平台阈值后规则自动暂停。平台保证同一计划时刻只发起一次，但立即运行与失败后再跑仍会再来一次，写入纪律同下一节。

事件触发的规则不看时间，看应用库：用户实例库里声明的表发生新增、修改或删除后，平台稍后以同样方式建项目（名称为「自动化名称 · 变化发生时刻」），入口参数可取自那条记录；应用后端写库与用户手动对话里 Agent 写库都算，自动化运行自己写库不算。同一条变化只发起一次；同一规则前一次没结束时后面的排队，超过每小时上限或排队已满的不处理；规则暂停期间的变化只计数不运行。捕获只作用于用户实例库，开发者工作集里的写入不会触发。

### 声明与校验

确认页写了「到点自动做」或「数据一变就自动做」的路线，制作时必须让它能**无人值守地跑到交付**。自动发起时平台以最终用户本人的身份建项目、提交这条路线的入口表单，没有人在旁边答题。声明写在智能应用版本上（`business_ui_manage(update, automations=[…])`），场景包不改；Hub 在保存和发布时按下面几条逐项校验，不满足直接拒绝：

| 约束 | 不满足时的做法 |
|---|---|
| 入口 `input_schema` 的每个必填字段，都在声明 `params` 里有来源：`fixed`（固定值）、`user`（用户开启时预先填）、`trigger_var`（定时触发为 `fire_time` / `fire_date` / `last_success_time`，事件触发为 `event_time` / `event_op`，只能填字符串字段）、`event_field`（仅事件触发，取触发记录的某一列，列类型要和入口字段类型相容） | 让路线第一个节点自己取数（例如按日期查收银系统），入口只留能预先确定的字段 |
| 入口不能有文件字段 | 改成路线内从数据源或应用库取文件 |
| 路线里没有运行中交互（`after_success` 表单）和 `sa_handoff` | 这类路线只能人工发起；需要自动化就把中途判断改成规则或 FastAgent 判断 |
| 声明的 `review` 与路线 `delivery.review.type` 一致：`user_gate`（缺省）交付停在审阅、进用户消息中心等确认；`agent_gate` 由 Agent 按路线声明的标准收尾、用户不用逐次审阅。事件触发这类一天可能跑几十次的自动化用 `agent_gate`，否则待审阅会堆满消息中心 | 路线是 `agent_gate` 却想让用户逐次确认（或反过来）：改路线的审阅形态或改声明，两者必须一致 |
| 路线要**自给**：前置记录由路线内节点创建，产出回流也在路线内完成（见 [数据模板.md](数据模板.md)「谁建行」的例外）；应用后端在无人访问时可能缩容到 0，不能指望到点时它在线接回调 | 把「应用后端先建记录再发起」改成路线第一个节点建记录 |
| 重复触发不重复写：同一计划时刻只会发起一次，但立即运行、失败后手动再跑都会再来一次，写库按业务键幂等 | 回数据模板补唯一键与累加规则 |

每条声明还要写 `timeout_minutes`（超时平台会停掉项目）、`review`（`user_gate` 或 `agent_gate`，缺省 `user_gate`，必须等于路线的 `delivery.review.type`）和触发方式：

- **定时触发** `trigger{type:"schedule", default_cron（5 段）, timezone, min_interval_minutes, user_editable}`。
- **事件触发** `trigger{type:"event", table, operations, watch_columns, max_runs_per_hour, timezone}`：应用数据表 `table` 发生 `operations`（`insert` / `update` / `delete` 的非空子集）时运行。`table` 必须是应用挂载的数据集模板里的表，写库里的真实表名（小写）；`watch_columns` 只对 `update` 生效，写了就只在这些列的值真的变化时触发，不写表示任意列变化都触发；`max_runs_per_hour` 必填，是每个用户规则每小时最多发起的次数，取值范围以 `validate` 的校验结果为准；`timezone` 可选，只决定 `event_time` 用哪个时区。`event_field` 参数新增、修改取新值，删除取删除前的值。

事件触发的运行规则，设计路线时要按它来：

| 平台行为 | 对路线的要求 |
|---|---|
| 应用后端写库、用户手动对话里 Agent 写库都会触发；**自动化运行进行中自己写库不会再触发任何规则**（防止循环）；运行结束后用户在那个项目里继续对话产生的写入照常触发 | 路线里可以放心回写同一张表；需要「A 写完再触发 B」的链式动作放在同一条路线里 |
| 前一次运行没结束时，后面的变化按先后排队，前一次结束才发起下一次；排队有上限 | 单次运行要短；批量处理放进一条路线，不要每行一次 |
| 超过每小时上限或排队已满的变化不处理，计入规则的「已忽略」数；一条语句批量改动很多行时，只有前面一部分逐条触发 | 批量导入不要依赖事件逐行处理；需要全量处理的改成定时触发 |
| 规则暂停期间的变化不处理，只计数；恢复后只处理之后的变化 | 不要假设每一条变化都一定会跑到 |
| 触发记录过大时不带内容，必填的 `event_field` 取不到值，本次运行失败 | 大字段不要作为 `event_field`，改成路线里按主键查库 |
| 事件触发的规则也能在面板「立即运行」：没有触发记录，由用户在弹窗里填写 `event_field` 参数对应的列值代替，`event_op` 取声明的第一种操作，`event_time` 取当下；这次运行记为手动运行，不计入每小时上限 | `event_field` 参数的入口字段类型要能由用户手填（不要指向大字段或内部 id）；开发期验证用 `business_ui_automation(run_once, event_row=…)` |

排队上限、逐条触发的行数上限、连续失败几次自动暂停、变化发生后多久发起等具体数值归平台管理，会随平台调整，制作时不要按固定数值设计，以 `validate` 返回和平台当前配置为准。

`automation_key` 跨版本保持不变：改了等于删掉旧自动化，用户已开的规则会被暂停并要求重新确认；定时与事件之间改触发方式，用户要删掉旧规则重新开启。

### 验证

用 `business_ui_automation` 验证：`validate` 校验声明；`bubble` 用冒泡跑一次；`run_once` 以开发者身份真跑一次（事件触发的规则用 `run_once, event_row=…` 给一条模拟记录）；`run_status` / `run_stop` 看和停。真跑有费用和副作用：确认页已列的直接跑、跑完报花费，会对外发送或超出确认页范围的先问开发者。

开发者在应用「自动化」面板里给自己开启规则后，用 `rules` 核对规则是否已保存、状态和下次运行时间，用 `runs`（可带 `rule_id`）看到点后是否已发起及结果。这两个动作只读、只看开发者本人的规则，不能开启或修改规则；规则不绑定版本，每次运行都用当前上线版本，`rules` 返回的 `version` 就是它。应用还不在开发者「我的应用」里时会被拒绝，先在 GoalfyMax 打开一次应用。

## 常见错误

- 入口有必填字段没有来源，或有文件字段，保存被拒。
- 路线里有中途表单或 `sa_handoff`，只能人工发起。
- 依赖应用后端在到点时在线建记录；后端可能已缩容到 0。
- 事件触发的规则用 `user_gate`，待审阅堆满消息中心。
- 批量导入依赖事件逐行触发，超出每小时上限的变化被忽略。
- 改了 `automation_key`，用户已开的规则被暂停。

## 相关工具与契约主题

`business_ui_manage(action="update", automations=[…])`、`business_ui_automation(action=validate / bubble / run_once / run_status / run_stop / rules / runs)`；应用工程里 SDK 的 `sdk.automations` 文档；契约主题 `otpe_multi`。
