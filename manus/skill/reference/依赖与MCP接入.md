# 依赖与 MCP 接入

## 适用场景

接入新的 MCP 服务、上传私有包、导入 Skill 包、配置授权卡、让工具集上线、对工具取样、使用别人分享来的工具组、处理工具组变更时读。要不要接入新能力由 [../stages/1-需求确认.md](../stages/1-需求确认.md)「2.3 同时核实」判定；接入前先用 `list_assets` 和 `get_asset` 确认平台上没有可复用的工具组，重复注册同一个 MCP 会产生互相冲突的重复资产。你实际看到的工具定义与服务端报错始终优先于本文。

## 规则

### 接入现有 MCP 服务

#### 标准流程

先预览、再注册：预览确认连接可用并发现真实工具清单，跳过预览直接注册会把不可用的连接写成正式资产。

```text
1. preview_tool_group        传连接类型，以及地址或启动命令
2. 成功 → register_and_refresh_tool_group   传相同的连接参数，并选择要纳入的工具
3. 失败 → 进入下方调试循环
4. 注册成功后按需配授权卡
```

注册返回里有 `tool_group_id` 和 `mcp_id` 两个标识：配授权卡用 `mcp_id`，它不是工具组标识。

#### 预览失败的调试循环

以启动命令方式接入时，最常见的失败原因是运行环境缺少依赖、服务起不来：

```text
1. 读预览返回的错误信息，判断缺什么
2. 在自己的环境里实际调试安装命令，直到能起得来
3. 把验证过的安装命令收集成前置安装步骤
4. 带上这些安装步骤重新预览
5. 仍失败则继续调试，直到成功
6. 预览成功后，注册时带上同一组安装步骤
```

预览时装过的依赖不会自动带到运行时：注册时漏传安装步骤，运行时会再次因为缺依赖而失败，而且要等到真正调用工具时才暴露。调试过程中的失败尝试不用写进工单，最终有效的安装步骤要记下来，下次刷新或排查时要用。

#### 私有包

开发者提供的本地包走上传路径：预览工具运行在独立服务里，访问不到你本地的文件系统。

```text
1. file_to_url            把本地包交给平台，声明对应用途
2. upload_and_register_tool_group   用返回的文件引用注册，同样支持前置安装步骤
```

平台运行私有包的环境没有系统时区数据，开发者本机一般有，所以本机能跑不代表平台能跑：

- 包里用到 `zoneinfo` 时，在 `pyproject.toml` 的 `dependencies` 里声明 `tzdata`；不用时区的包不加。
- 上传前用 `PYTHONTZPATH= uvx --from <本地 wheel> <入口命令>` 启动包，模拟没有系统时区数据的环境，并通过标准输入依次送 `initialize`、`notifications/initialized`、`tools/call` 三行 JSON-RPC，真实调用一次用到时区的工具。送完后标准输入要再保持打开几秒，例如 `{ cat calls.jsonl; sleep 5; } | PYTHONTZPATH= uvx --from <本地 wheel> <入口命令>`；输入一结束就关闭，进程可能来不及返回 `tools/call` 的响应。收到 `tools/call` 的响应且 `isError` 不为 `true` 才算通过；进程提前退出、没有 `tools/call` 响应、`isError: true` 都算失败。只启动不调用工具不能作为通过依据：只在工具函数里用 `zoneinfo` 的包启动时不报错，调用时才失败。
- 补依赖后重新打包要提升 `pyproject.toml` 的版本号再上传。平台按包名和版本号定位包，同一版本号内容不同的包会被拒绝。

#### 标准 Skill 包导入

开发者提供的标准 Skill 包（含 Skill 入口文件的压缩包）可以一键导入成工具集：

```text
1. file_to_url            上传压缩包
2. import_skill_package   用文件引用导入
```

导入会自动解析入口文件并创建**离线**工具集，之后仍要通过下方的上线检查。

### 授权卡

#### 什么时候要配

看授权凭证是每个使用者一份，还是全场景包共用一份：

| 情况 | 处理 |
|---|---|
| 每个使用者用自己的第三方账号授权 | 配授权卡；没配时使用者无法完成授权，工具调用会失败 |
| 服务级认证，全场景包共用一份凭证 | 写在连接配置的请求头里，不需要授权卡 |

漏配授权卡时，制作期你自己测试可能正常（用的是你的凭证），交给使用者后全部调用失败。

#### 三种操作

| 需求 | 工具 | 要点 |
|---|---|---|
| 新建一张卡 | `create_auth_card` | 传 `mcp_id`、授权类型和授权配置 |
| 改已绑卡片的配置 | `update_auth_card` | 只传要改的字段 |
| 复用别人已有的卡 | `link_auth_card` | 需要卡片标识 `auth_card_key`；替换已绑卡片要显式确认，替换前先请开发者确认 |

授权配置的必填内容随授权类型不同：标准授权流程需要三个服务端端点；自定义方式需要字段清单，每个字段要有键名、展示名、类型和是否必填。具体必填项以实时 Schema 为准。

创建成功后返回的卡片标识记进工单 checkpoint，不交给开发者；之后要让别的 MCP 共用这张卡的使用者授权时，从 checkpoint 取它 `link_auth_card`。

#### 安全边界

个人令牌、Cookie 或密码不写进 Skill 文本、脚本、提示词或工单：授权卡的作用就是让凭证留在平台侧、不进入配置内容。

### 工具集上线的两道检查

新建或导入的工具集处于**离线**状态。离线工具集可以被关联配置，但运行时不会被加载——这是「配置看起来齐全但运行时找不到能力」最常见的原因，编排型 TPE 也建不了。两道检查都要做。

#### 第一道：编排型 TPE 创建前

```text
1. 根据脚本确定完整的预加载工具集清单：把核实过的工具组、FA 用
   create_toolset(name, description, tool_group_ids, fast_agent_ids) 装成工具集，一条路线通常一个；
   脚本要读写应用库的，工具集里装上工具组「query_business_app_dataset」
2. 对其中本轮新建或导入、含 MCP 工具组的工具集，用 otpe_tool_test 做一次安全的真实取样（见「工具取样」）；
   只含 FA 的工具集没有单独的测试入口，get_asset 反读 FA 配置无误即可，首次运行测试放到路线冒泡；
   读写应用库的路线首次运行测试放到 ④ 工作集真跑
3. 全部无失败后 → online_toolsets（只传本轮新建的标识）
4. get_asset 反读，确认清单里每一个都已上线
5. 通过后才创建编排型 TPE；在此之前只做预览
```

#### 第二道：④ 部署前

对待上线清单里尚未上线的工具集：

```text
1. 含 MCP 工具组的逐一做安全的真实取样，破坏性操作跳过；只含 FA 的按第一道的口径处理
2. 全部无失败后 → online_toolsets
3. get_asset 反读确认全部已上线
4. 已在第一道检查里上线过的，这里只反读、不重复上线
```

#### 失败与中断

任一测试失败、余额不足、授权中断或流程异常时：保留原资产和进度，恢复后从未完成的验证继续；验证都通过才上线。

#### 开发者已有的离线工具集

场景包要用的工具集不是本工单新建、仍处于离线时，运行时加载不到：

- 开发者本人名下的：按上面两道检查测过后，由你上线并关联。
- 别人的：不改它的上线状态；停下告诉开发者影响哪个功能，由开发者决定怎么处理。

### 工具取样

需要确认某个已有 MCP 工具的真实返回结构时，用 `otpe_tool_test(task_id, tool_group_id, tool_id, input=<最小合法参数>)` 做一次真实调用取样，看返回的 `structured_content` 是不是 PRD 要的那个对象。

**这会真实调用供应商接口。** 只对安全只读的工具取样；下面这些只看参数说明，不取样：

- 破坏性操作（删除、清空、重置）
- 发布或对外通知（发信、推送、发单）
- 涉及凭证变更
- 涉及资金
- 任何不可逆的动作

脚本要直接调用的复用工具里拿不准的那些建议取样一次，既验输入约定（文件参数收 URL 还是 workspace 路径）也验真实返回结构。可以同时提交一个候选的输出结构一起校验本次样本。

只依赖已有业务项目上下文的工具还要传项目标识——服务端会把它和可信身份一起作为运行请求头传给目标 MCP，不会因此启动新项目。

目标工具需要读取 `/workspace` 测试文件时，不借用使用者的项目。先对 Agent 本地文件调用 `file_to_url(purpose="tool_test_fixture")`，完成 `prepare → 客户端 PUT → complete`，取得 `data.file_ref`。再给 `otpe_tool_test` 提供两组相互独立的信息：`workspace_files` 只接收这些文件引用；`workspace_bindings` 负责把某个文件的真实路径或父目录注入目标工具顶层参数。服务端会复用编排型 TPE 冒泡使用的隐藏验证项目，从临时 HTTPS URL 下载文件、写入真实工作区、完成一次 `tools/call`，随后无论成功或失败都释放隐藏项目。这种模式下不传 `project_id`。

示例：测试目录扫描工具时，分别上传 `docs/a.md` 与 `docs/b.md`，在 `workspace_files` 中提供两个文件引用，只在 `workspace_bindings` 中把其中一个文件的 `parent_dir` 绑定到 `path`，并在普通 `input` 中保留 `pattern: "*.md"`；测试单文件读取工具时，把对应文件的 `file_path` 绑定到文件参数。文件准备数量与参数绑定数量彼此独立，不为第二个文件虚构 `path2` 或 `urls`。该样本只能证明这一次真实调用和返回结构，不能代替整条编排型 TPE 冒泡验证。

### 分享来的工具组

- **搜索**：`list_assets` 的关键词只匹配名称和 ID，用英文短词多试几次。分享来的工具组名字常和开发者说的不一样：先用开发者给的工具名、平台名的英文短词再试；还搜不到，在「要你做的」里请开发者给工具组 ID（开发者中心资产页或分享消息里能看到），或请分享人再分享一次。拿到 ID 后 `get_asset` 看权限。
- **看不到参数**（`get_asset` 配置为空且 `can_view_params=false`、工具列表为空）：这是脱敏，不是空资产。先用 `otpe_tool_test` 按工具描述或开发者给的样例里能看出的参数取样一次；调用被拒或返回参数错误时，按报错提示补参数再试一次。仍拿不到真实返回的，在制作中第一次真跑时核实（核实结论和 PRD 里怎么写见 [../stages/1-需求确认.md](../stages/1-需求确认.md)「2.3 同时核实」）。
- 不能克隆的分享资产按原样用，不改它；分享人收回或改动后，用到它的步骤会停。

### 依赖变更后的连带处理

工具组刷新（`register_and_refresh_tool_group` 会给出差异）、工具删除或参数变化后：

- 回头核对所有引用它的地方——工具集使用指南、FastAgent 提示词、编排型 TPE 脚本、`apc_skill`、场景 Skill 文件。留着失效知识会让运行时 Agent 反复尝试不存在的能力，而且这类问题在静态检查里看不出来。
- 变更完成后重跑所有受影响的预览、运行验证和整包验收。

## 常见错误

- 跳过预览直接注册，把不可用的连接写成正式资产。
- 预览时装过依赖，注册时漏传同一组安装步骤，运行时才暴露。
- 给预览工具传本地文件路径；私有包要走 `file_to_url` 上传。
- 私有包用了 `zoneinfo` 没声明 `tzdata`：本机正常，平台上启动或调用工具失败。
- 配授权卡时传了 `tool_group_id`，应传 `mcp_id`。
- 需要使用者各自授权的工具没配授权卡：制作期自测正常，交付后全部失败。
- 工具集还是离线就创建编排型 TPE，运行时加载不到。
- 对发信、删除、付款这类工具取样，产生了真实副作用。
- 把 `can_view_params=false` 的分享工具组当成空资产。
