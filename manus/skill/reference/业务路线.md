# 业务路线

## 适用场景

保存或修改应用版本上的路线、用 `assemble`、加中途表单、设计交付与审阅、处理「改稿 / 重做 / 换路线」、做路线冒泡、路线保存或冒泡报错时读。多节点、并行、扇出、中途表单、跳转路线的字段写法读 `get_diagnosis_doc(topic="otpe_multi")`；那份文档里的 `agent_gate`、`sa_handoff` 和旧挂载方式的 checkpoint 写法不适用，只用其中的 `user_gate`、多节点、中途表单与跳转写法。

## 规则

### 路线挂在应用版本上

- 路线与编排型 TPE 挂在应用版本上，不另建别的容器。应用占位在 ① 开发者确认 PRD 后用 `business_ui_manage(action="create", task_id, name)` 建好，拿到 `business_ui_id`（[数据模板.md](数据模板.md)「建应用身份与挂模板」）。
- 保存：`business_ui_manage(action="update", business_ui_id, workflow_orchestration, tpe_ids)`。
- **整体替换**：`workflow_orchestration` 是一整份，写前反读原值（`business_ui_manage(action="get")`），改完整份传回；只传改动的那条路线会覆盖掉其他路线。没传的字段（如 `automations`）不动；只传路线不传 `tpe_ids` 时沿用已存的 `tpe_ids`；改了路线后已存的自动化会重新校验，对不上时保存被拒（`BUSINESS_UI_AUTOMATION_INVALID`）。目标是草稿时带上 `draft_asset_id`（有多份草稿时必带）。
- `tpe_ids` 规则：编排里引用的每个 TPE 都要在 `tpe_ids` 里，漏了保存被拒（`references unmounted tpe_id`）。传给 `update` 的每项写 `{tpe_id, tpe_version}`：`tpe_id` 是 TPE 资源组 ID（新建 TPE 时 `otpe_manage(create)` 回执的 `tpe_id` 就是它），**不要**写某个版本行的 ID；`tpe_version` 写具体版本号，或 `latest`（`assemble` 给新加的 TPE 写的就是它，可原样保存；草稿期间跟随最新版本，上线时钉死）。`get` 读回的形状是 `{id, version}`，改完传回时换成 `{tpe_id, tpe_version}`。
- 节点脚本调用的工具集写进该节点 TPE 的 `preload_toolset_ids`（`otpe_manage` 的 `create` / `update` 时传；`create` 通过静态校验即自动上线，`update` 后反读，没上线再 `online`），FastAgent 自己的工具照常；应用版本上没有另外的工具箱。已上线的 TPE 改挂载要出新版本：用 `otpe_manage(action="update")` 改 `preload_toolset_ids`（名单按脚本实际引用收敛，脚本不再调用的工具集会被移除）；`update_asset_relations(asset_type="tpe", asset_id, add_toolset_ids)` 不会自动上线，只在草稿上补挂，补完再 `otpe_manage(action="online")`。
- 占位草稿还没挂编排时不能上传源码包和部署（`BUSINESS_UI_NO_SCENARIO_PACK`，意思是「没挂编排」），所以 ③ 里先把编排与 `tpe_ids` 挂上，再部署（[部署与版本.md](部署与版本.md)「上线与发布」）。改过编排后要重新部署再发布。

### 路线对象

- 应用版本上的 `workflow_orchestration` 是整体业务路线，里面 `orchestrations[]` 每一项是一条路线，`orchestration_id` 是它的标识；路线冒泡、真跑、结单核对都以它为单位。
- 一条路线包含：入口表单标识、路线级输入定义、节点依赖图（节点引用已挂上的编排型 TPE，无环且全部可达）、节点输入映射、可选的节点级中途表单、唯一的最终交付与审阅。
- 保存成功只证明静态结构合法，不能代替冒泡。
- 路线只调度已存在且 verify 静态项已过（`needs_bubble` 且 `failed` 为空）的编排型 TPE；还没有编排型 TPE 时先建 TPE，不放空节点或空图。
- 应用版本至少要挂一条路线；只有规则步骤的应用也建一条最小的单节点路线。
- 执行里没有 Agent 接手：审阅只用 `user_gate`，动作只用下文「交付与审阅」的三种；写了别的审阅形态、交给 Agent 处理的动作或节点级 Agent 介入，Hub 保存拒收（400，报错含 `not supported by launch agent` 和节点或路线位置）。能用规则判断的写进 TPE：输出校验、`business_gate`。

### 什么时候用路线、用哪种

| 情况 | 做法 |
|---|---|
| 单条 TPE 就能完成一件事（含声明或调用业务事件、需要表单握手或交付审阅、要从应用发起） | 单节点路线；执行只能从路线发起 |
| 多条 TPE 有固定依赖、扇出、汇合 | 多节点路线；一条路线通常一条编排型 TPE 就够，要中途表单或并行时才拆成多个节点 |
| 使用者改稿、重做、要在上一次交付基础上改 | 审阅加跳转到修正路线的动作，见下文「修正上次交付」；不画回边模拟循环，不覆盖旧交付 |
| 使用者要改走另一条路线 | 审阅加 `start_orchestration` 动作跳转；仍在同一次执行里（执行号不变），接着跑目标路线 |
| 制作期就能预知的使用者输入 | 全部放入口表单 |
| 只有上游成功后才知道、且要喂给未派发下游的输入 | 节点级中途表单 |
| 节点成功后要检查结果 | 能用规则判断的写进 TPE（输出校验、`business_gate`）；要人判断的放最终审阅由使用者决定 |

### assemble 怎么用

1. 各节点 TPE 已建好后，按执行顺序调 `scene_package_manage(action="assemble", task_id, business_ui_id, tpe_ids=[…], orchestration_id, title, entry_form_id)`（路线组装工具；工具名是历史叫法，应用标识只用 `business_ui_id`，不传 `scene_package_id`）。
2. 它读各 TPE 的输入输出 Schema：同名字段接上游输出，并把被读的节点列为直接依赖；其余字段进入口表单；交付覆盖末节点输出；审阅缺省 `user_gate`。它并入应用版本原有的路线与 TPE，返回 `workflow_orchestration` 与 `tpe_ids` 草稿，不写库。入口映射、节点映射、交付映射都由它生成，你只审 `unresolved` 与 `notes`。
3. 先处理 `unresolved`（类型不一致、输出为空）与 `notes`（需改名的字段），再把返回的 `workflow_orchestration` 与 `tpe_ids` 原样传给 `business_ui_manage(action="update", business_ui_id, workflow_orchestration, tpe_ids)` 保存。
4. 局限：只做线性和「读谁就依赖谁」的接线；分支、并行、扇出、中途表单、跳转到另一条路线仍按 `otpe_multi` 手写。节点只能从直接依赖的上游读 `node_output`。

### 交付与审阅

- **交付映射**：要交付的文件，路径字段必须进 `delivery.mapping`，否则不会登记为附件；映射引用的字段本次缺失时跳过，必填由 `output_schema` 的 `required` 决定。文件必须真实存在、声明为 `workspace-file-path`、在最终节点的 `ctx.output_dir` 里。
- **交付的展示**：审阅页的标题和正文来自交付输出的 `display` 对象：末节点 `output_schema` 返回 `display`（`schema_version:"1.0"`、`headline` 字符串、`facts[]`、`notices[]`、`sections[]` 三个数组都要有），`delivery.mapping` 写 `"display": "$.display"`（`assemble` 会把末节点顶层字段都映射上）。`headline` 作审阅标题，`sections[]` 按顺序显示成「标题 + 纯文本段落」，不渲染 Markdown；字段不全时整块不显示，摘要退回 `summary` / `message` / `text`。
- 未声明为文件的 workspace 路径不会成为附件，交付里显示为「内部资料：文件名」。本来要交付的文件没成为附件时，补齐复制、声明和映射，不以引用文字代替。
- **审阅形态只有 `user_gate`**：
  - 停在审阅等使用者确认（缺省，`message_type` 为 `ask`）。
  - 直接交付：加 `message_type:"result"`，平台把 `delivery.mapping.text` 作为结果消息发给使用者并结束执行；要求 `delivery.mapping.text` 存在且只声明一个 `complete_business` 动作。
  - 结果好不好由使用者审阅，平台不替你判断。自动化路线怎么选见 [自动化.md](自动化.md)「收尾方式」。
- **审阅动作**：`kind` 只在三种里选——`complete_business`（结束业务）、`fail_business`（以结构化原因拒绝并结束）、`start_orchestration`（跳转到另一条路线）。每个动作只写 `action_key` 与 `kind`，跳转另加 `orchestration_id` 与可选 `target_input_mapping`；按钮文案由平台生成，动作里不写 `label`、`description`。
- **跳转两种形态**：跳转动作必须带 `form_id`，且等于目标路线的 `entry.form_id`。不需要使用者新输入时声明 `target_input_mapping`（每项 `source='delivery'`，从本次交付输出取值，覆盖目标路线全部必填字段），使用者点了直接启动；映射出的输入不符合目标路线入口 Schema 时，平台改为展示入口表单。需要新输入（如写修改意见）时不声明映射，跳转后展示目标路线的入口表单。
- **跳转不换执行**：跳转后仍是同一次执行（执行号不变），页面不用切换执行；每跳一次在执行里多一趟路线运行，同一次执行最多约 50 趟，超了报 `EXECUTION_STATE_LIMIT`。
- **按钮文案**：平台按动作类型给默认文案（`complete_business`「接受并完成」、`fail_business`「结束本次流程」、`start_orchestration`「继续下一步」），路线里写不了 `label`。要换成业务说法，在页面里按 `action_key` 显示自己的按钮文字（写法见 [前端页面.md](前端页面.md)「业务页面」）。
- **`fail_business` 的结局**：不带使用者填的原因，平台记固定码 `DELIVERY_REJECTED`；执行状态变成「失败」（`failed`，不可重试），平台各处都按失败显示。应用页面里可按 `error.code === 'DELIVERY_REJECTED'` 改说「已放弃」这类业务话；PRD 里写明「选了不要这份结果，这次会显示为失败结束」。

### 确认后入库

使用者点「接受」后平台只把执行标成完成，不再跑任何节点、不调应用后端；审阅应答也只交 `action_key`。所以「使用者确认后才存」不能靠 `complete_business` 本身，标准做法：

1. 生成路线的节点只产出内容，不写正式记录（写了的话，使用者放弃的草稿也会进表）。
2. 审阅的「保存」动作写成 `start_orchestration`，跳到一条单节点「保存」路线：用 `target_input_mapping`（`source='delivery'`）把要存的字段从本次交付带过去，`form_id` 等于保存路线的入口表单；要存文件的，保存节点从 `ctx.previous_delivery.file_paths` 读。
3. 保存节点写库（照 [编排脚本.md](编排脚本.md)「读写应用库」，按业务键幂等），保存路线的审阅用 `message_type:"result"` 和唯一的 `complete_business` 直接收尾。整个过程仍是同一次执行。
4. 这个按钮默认显示「继续下一步」，页面按 `action_key` 改成「保存」（见上文「按钮文案」）。

### 修正上次交付

使用者审阅不满意、要在上一趟基础上改时：

1. 审阅加一个 `start_orchestration` 动作，指向修正路线（可以就是原路线自己，每轮改稿都跳回它）。要使用者写修改意见时，不声明 `target_input_mapping`，跳转后展示修正路线的入口表单，表单里放反馈字段，修正路线的节点从入口输入读到它。不在审阅页上带反馈字段：页面模板的审阅应答只收 `{ action_key }`，夹带字段会被 SDK 本地拒收（见 [前端页面.md](前端页面.md)「业务页面」）。
2. 修正路线的脚本从 `ctx.previous_delivery` 读上一趟：`previous_runtime_id`、`orchestration_id`、`delivery_id`、`file_paths`（上一趟交付文件路径）、`action_key`、`feedback`、`summary`（交付内容摘要，最多 2000 字，`summary_truncated` 标是否截断）。它只指紧挨着的上一趟。要全文就读 `file_paths` 里的文件，在它基础上改，**禁止**从头重做。第一趟时它是 `None`。
3. 交付文件在同一使用者的隐藏项目里，按普通 workspace 路径读；要随本次交付的文件照常复制进本节点 `ctx.output_dir`。
4. 改稿都在同一次执行里（执行号不变，页面不用跟新的执行），每轮多一趟路线运行，最多约 50 趟（超了 `EXECUTION_STATE_LIMIT`，请使用者重新发起）。同一份业务对象改多版要存时，用业务键关联（如报告编号，第一趟生成后放进交付输出和文件），保存时按业务键更新同一条或按「业务键 + 版次」新增，按 ② 定的写法。

### 表单定义放哪

平台不登记表单 Schema，路线里只有 `form_id` 和映射；字段清单来自路线与 TPE 的输入 Schema。标题、字段说明、控件提示、顺序这些展示信息，写路线时同步放进前端工程 `frontend/schema/packs/<pack>/forms/`（路线展示放 `frontend/schema/packs/<pack>/orchestrations/`），构建时收集；`frontend/goalfy-app.json` 的 `packs` 列出用到的目录（`pack` 只是目录名，用来组织代码，和平台对象无关）。

- **表单文件**：一张表单一个 `forms/<form_id>.json`，文件名等于里面的 `id`，也就是路线里的 `form_id`；字段 `id`、`name`、`inputSchema`（照 TPE / 路线入口 Schema 原样写，不裁剪）、可选 `notes`。`form_id` 在全部目录里唯一，`delivery.` 开头的是平台保留（最终审阅表单），业务表单不用。
- **路线文件**：只给页面能主动发起的路线建 `orchestrations/<orchestration_id>.json`：`id`（等于 `orchestration_id`）、`name`（页面上显示的路线名）、`entryFormId`（等于路线的 `entry.form_id`，且在 `forms/` 里有文件）、可选 `formIds`、`notes`。中途表单和只靠跳转进入的路线入口表单只放 `forms/`。这里的 `delivery` 字段只给本机 Mock 用，改不了线上审阅按钮。

- **入口映射**：`entry.input_mapping` 的规则只声明 `source/node_id/path/transform`，来源只能是 `formdata`；默认值不直接写成 `default` 字段，按下一条用变换声明。完整写法以 `get_diagnosis_doc(topic="otpe_multi")` 为准。
- **入口默认值**：用映射的变换声明，写成 `{"source":"formdata","path":"$.x","transform":{"kind":"default","value":…}}`；表单没填这个字段时，运行时自动补上 `value`，入口表单也不再把它列为必填。Schema 的 `default` 只是声明，不会自动填值。字段如果在 Schema 里是必填，定时自动化发起时仍要传值。

### 冒泡

- 发起：`scene_package_manage(action="bubble", task_id, business_ui_id, orchestration_id, workflow_input=<例子>)`，对你最新的草稿发起一次预览执行；回执的 `run_id` 就是执行号 `business_id`（`BIZ-` 开头，服务端生成，不自己编）。要模型步骤真的跑出内容时加 `full_run=true`（FA 桩与 `full_run` 的区别见 [编排脚本.md](编排脚本.md)「冒泡与真跑能证明什么」）。
- 续等只传 `run_id`（可带 `evidence_level`）；回填中途表单或审阅传 `run_id + formdata`，审阅动作放 `formdata.action_key`。三种组合只选一种，回填或首次发起时带的 `evidence_level` 会被忽略；不接受 `review_action_key`、`workspace_files`。止损用 `action="cancel", run_id`。
- 到终态后，对路线里每条 TPE 用这次的 `BIZ-` run_id 调 `otpe_manage(action="verify", task_id, tpe_id, run_id)`；单节点路线不必再单独冒泡。每一步做了什么、产出什么看冒泡回执的 `steps` 与 verify 返回的节点证据；冒泡回执不带 `project_id`，`get_project_execution_logs(action="workflow_trace", project_id, business_id)` 只用于真跑（见 [部署与版本.md](部署与版本.md)「真跑」）。
- 每条路线以当前合同下最近一次到终态的执行为准，路线冒泡与真跑都算；路线或节点改过之后旧证据作废，要重跑。
- 一条路线一条工单 checkpoint，各带自己的 `run_id`；结单门豁免写 `business_ui_id`、`business_ui_version_id`（冒泡回执，或真跑 `status` / `wait` 回执里的版本行）、`orchestration_id`（[部署与版本.md](部署与版本.md)「三道门」）。

## 常见错误

- 改路线时只传改动的那条，覆盖掉其他路线（整体替换语义）。
- 漏了 `tpe_ids` 里的 TPE，保存被拒（`references unmounted tpe_id`）；或 `tpe_ids` 写成版本行 ID。
- 审阅写了 `user_gate` 以外的形态、交给 Agent 处理的动作或节点级 Agent 介入，保存被拒（报错含 `not supported by launch agent`）。
- 「接受」后才存的数据写在生成节点里，或指望接受动作触发保存；应按「确认后入库」跳到保存路线。
- 跳转动作没带 `form_id`，或它不等于目标路线的入口表单。
- 节点读了非直接依赖的上游输出，保存被拒。
- 节点脚本调的工具没挂在该节点 TPE 上，运行时报工具名无效（`invalid tool call name`）。
- 要交付的文件只在 `output_schema` 里声明，没进交付映射，界面显示无产出文件。
- 审阅动作写了 `label`，保存门拒收未知字段。
- 在入口映射规则里直接写 `default` 字段。
- 用多条单条 TPE 的冒泡拼成路线证据。
- 为改稿在同一张图里画回边；或修正路线不读 `ctx.previous_delivery`，从头重做。
- 冒泡自己编 `business_id`。

## 相关工具与契约主题

`business_ui_manage(action=create / get / update)`、`scene_package_manage(action=assemble / bubble / cancel)`（工具名是历史叫法，应用标识只用 `business_ui_id`，不传 `scene_package_id`）、`update_asset_relations(asset_type="tpe")`、`otpe_manage(action="verify")`、`get_project_execution_logs(action="workflow_trace", project_id, business_id)`（真跑）；契约主题 `otpe_multi`、`otpe_example_parallel`、`otpe_example_failure`。
