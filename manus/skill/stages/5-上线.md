# ⑤ 上线（工作区阶段 G7）

开发者看完 ④ 的验收报告说「可以上线」后，你上线报告里验过、④ 已部署成功的那一版：这一版成为开发者自己的正式版；要自己正式使用或给别人用，需要开发者在发布管理页发布，发不发布由他决定。然后交一份上线结果：上线的是哪一版、④ 验过什么、实际花了多少、发布要准备的描述、Logo 和更新说明、开发者可以做的事。这一段不再请开发者确认什么，也不请他发布、不等发布；验证已在 ④ 的本机版和开发工作集里做完。

## 1. 进入条件

- ④ 交棒（[4-试用验收.md](4-试用验收.md)「交棒条件」）；报告里有「未测」条目时同样进 ⑤，不追问。④ 没部署过的也进 ⑤，按 2.1 处理。
- 开发者这次明确说了「可以上线」或等价表述；上线的时间晚于这句话的 checkpoint，补测后请他再说过一次的，晚于再说的那一次。
- 已用 `business_ui_manage(action="get")` 确认当前 `role`：`owner` 照本段做；`editor` 在 2.3 改为提请属主上线；`viewer` 不进 ⑤。

## 2. 段里怎么做

### 2.1 只上线已部署的草稿

- 上线的是 ④ 已部署成功的最新草稿。④ 之后改过场景包或应用的，按 ④「2.2 先问部署，再部署」重新部署，改动影响到的条目按 ④「2.6 按反馈改」重测。
- ④ 因为开发者还没同意部署而没有部署过的：如实说「还没部署到在线预览，上不了线」，再照 [../SKILL.md](../SKILL.md)「红线」的部署授权原句问一次。
  - 同意：部署到 `success`，按 ④「2.3 工作集真跑」「2.4 逐条判定」补测依赖已部署版本的条目，结果更新进验收报告。补测有没通过的，回 ④「2.6 按反馈改」修好再测；有「好不好你说了算」的，把实际结果给开发者看，请他看过后再说一次「可以上线」。补测的条目全部通过（判断类以他再说的这一次为准）才上线。
  - 不同意：停在这里，告诉开发者这一版还没部署、所以没有上线，不上线。
- 挂在应用上的本人场景包草稿不单独上线，随应用一起上线。

### 2.2 上线前自查

- ④ 里确认过、上线后还要用的设定如果只存在开发工作集里（使用者从空库开始，看不到它），先搬到代码默认值、场景包配置或首次设置入口（做法同 [3-制作.md](3-制作.md)「2.2 数据和页面」），重新部署后再上线。
- 有授权或充值的，按 [../reference/授权与充值.md](../reference/授权与充值.md)「上线前核对」核一遍。

### 2.3 上线与反读

- `owner`：按 [../reference/部署与版本.md](../reference/部署与版本.md)「上线」做：显式传要上线的 `draft_asset_id`，场景包草稿随它一起上线，`resolve` 反读上线版本与场景包版本记进工单。`resolve` 取不到上线版本说明上线没生效，照实说没上线。被拒按 [../reference/报错对照.md](../reference/报错对照.md)「应用上线与数据模板」处理。
- `editor`：改为 `business_ui_manage(action="request_finalize")` 提请属主上线，做法、说法与报错见 [../reference/多人协作.md](../reference/多人协作.md)「提请属主上线」；不调 `finalize`、`resolve`。之后 2.4 的结单门、花费、阶段记录、结单照做，上线结果的「上线的版本」写「已提请，等属主上线」。
- 属主处理协作者的提请：依据是协作者为这份草稿做的 ④ 验收报告（提请说明里附；没有就请提请人先补 ④），先问开发者要不要上线（[../tasks/接续.md](../tasks/接续.md)），他看过报告说「可以上线」后照本段做，`draft_asset_id` 用那份协作者草稿（[../reference/多人协作.md](../reference/多人协作.md)「提请属主上线」）。

### 2.4 结单

1. **结单门**：按 [../reference/部署与版本.md](../reference/部署与版本.md)「三道门」——每条路线最近一次到终态的运行通过（路线冒泡和 ④ 的 `workspace` 真跑都算）；最近一次失败或没法验证时，先问开发者是否接受，接受后写豁免。
2. **算总花费**：对工单里记下的每个冒泡、真跑项目重新读一次 `cost_credits`（[../reference/平台对象速查.md](../reference/平台对象速查.md)「积分怎么算」），汇总开发期累计，和 ① 的上限、② 的预计比。
3. **写上线结果**：按 2.5 写，写进工单 `task_manager(action="insert", entry_type="result")` 和交付物。
4. **写阶段记录 G7**：用 `business_ui_stage` 写 G7，`next_stage` 填 `closeout`，在下一步 `complete` 之前写。
5. **结单**：`task_manager(action="complete")`；返回的 `delivery_note` 原样补进上线结果。被拒按 [../reference/报错对照.md](../reference/报错对照.md)「版本与结单」处理。上线后即结单，发布不在结单条件里。
6. **汇总平台问题**：本轮记下的已绕过平台问题和功能诉求，此时汇总成一条提交，没有就不提；怎么报见 [../reference/报错对照.md](../reference/报错对照.md)「平台问题怎么报」。
7. **保存**：开发工作集上线后继续绑定在应用上（[../reference/数据模板.md](../reference/数据模板.md)「开发工作集」）；工作区用 `workspace_push` 保存到云端（[../reference/开发者中心与工作区.md](../reference/开发者中心与工作区.md)「云端保存与换机」）。
8. **发出**：把上线结果连同交接消息发给开发者。

### 2.5 上线结果

给开发者的部分（上线的版本、④ 验过什么、未测的、实际花了多少、发布会怎样、发布要准备的、你可以做的事），以及交接消息后附的怎么打开、使用说明、平台提醒、还没验证的和风险，写法和照抄的原句见 [../design/验收报告与上线结果.md](../design/验收报告与上线结果.md)「上线结果」。④ 有「未测」条目时单列。

给后续 Agent 的部分写进工单和阶段文档 G7，不发给开发者：应用名、上线版本、是否已发布（结单时写「未发布，由开发者决定」）；部署状态（`success`）与部署证据（`deployment_id`、`source_sha256`、`deployed_scaffold_version`；低于建议线时写「当前 vX 低于建议线 vY，建议下一轮升级」；有 `scaffold_upgrade_notice` 原样写）；场景包上线版本、已验证路线与 `run_id`、豁免的路线与理由；数据模板 ID 与版本；④ 真跑的 `project_id` 与结论，或省略真跑的原因；验收清单通过项数、不适用项、未测的条目与原因；修订时 `compare_asset_versions` 取的前后配置差异。

### 2.6 发布要准备的材料

开发者自己正式使用、到点自动运行、给使用者用，都要先发布；发布页要求描述、Logo、版本更新说明。你在上线结果里把这三样备好：描述与更新说明给出可直接粘贴的文字；Logo 给出应用工程里的图片文件路径，没有就按 [../reference/前端页面.md](../reference/前端页面.md)「Logo」做一张。写法见 [../design/验收报告与上线结果.md](../design/验收报告与上线结果.md)「发布要准备的材料」。告诉开发者发布在发布管理页由他决定；你不请他发布、不等发布。

## 3. 开发者要看、要做的

- 看上线结果。
- 自己决定发不发布、发给谁、什么时候发；发布时用备好的描述、Logo、更新说明；发布后按「你可以做的事」看正式入口、开定时任务、分享。

交接消息的开头、「刚做完」和「要你做的」照 [../design/验收报告与上线结果.md](../design/验收报告与上线结果.md)「交接消息怎么写」写。开发者之后说正式入口里哪条不对、到点触发的结果不对，按 [../tasks/修订.md](../tasks/修订.md) 或 [../tasks/诊断.md](../tasks/诊断.md) 开新工单处理。

## 4. 产出与落盘

- 工单：上线结果（`entry_type="result"`），`complete` 成功。
- 阶段文档 G7：上线结果全文、给后续 Agent 的部分。
- 交付物：方案页 `status` 改为 `done`，`.pv-summary` 写上线结论，`.pv-you` 写「你可以做的事」，`.pv-meta` 写开发期累计花费；「已验证 / 未验证」与上线结果一致，「未测」的留在「未验证」。Studio 下上线结果写进开发文档「验收报告」最后一节（[../design/开发文档/验收报告.md](../design/开发文档/验收报告.md)），用 `studio_write_proposal(documentType="acceptance")` 保存新的一版；保存或登记结果未知时只查原操作结果，不重新写入（[../reference/开发者中心与工作区.md](../reference/开发者中心与工作区.md)「Studio 宿主」）。
- 阶段标记：`workspace.json` 的 G7 标 `passed`；阶段记录 G7 `next_stage="closeout"`。

## 5. 交棒条件

- 开发者说「可以上线」之后才上线；上线的是 ④ 验收过、已部署成功的那一版：`resolve` 能取到上线版本，且 `entry_url` 非空（协作者为 `request_finalize` 成功）；
- 上线结果写了上线的版本、④ 的结论、三个花费数、发布会怎样、发布要准备的三样材料和你可以做的事；有「未测」条目时单列了；
- G7 阶段记录在 `complete` 之前写了；
- `task_manager(action="complete")` 成功，上线结果已写入工单与交付物。

## 6. 出问题怎么办

| 现象 | 先看 | 回到 |
|---|---|---|
| ④ 没部署过，开发者说「可以上线」 | 本段 2.1：说明上不了线，再问一次是否部署 | ④ 2.2 |
| 部署后补测有「没通过」或「好不好你说了算」 | 本段 2.1：没通过的修好再测；要开发者判断的给他看结果，请他再说一次「可以上线」 | ④ 2.6 |
| 上线被拒 | [../reference/报错对照.md](../reference/报错对照.md)「应用上线与数据模板」 | ④ 或 ③ |
| `BUSINESS_UI_FINALIZE_OWNER_ONLY`、`PERSONAL_VERSION_STALE_SOURCE` 或提请被拒 | [../reference/多人协作.md](../reference/多人协作.md)「协作相关报错」 | 提请或基线过期的合并 |
| 结单被拒 | [../reference/报错对照.md](../reference/报错对照.md)「版本与结单」：补一次路线冒泡或 `workspace` 真跑，或问开发者后写豁免 | ③ 或 ④ |
| 开发者说「先发布再结单」或要你在正式版里跑一次 | 告诉他发布由他决定，验证已在 ④ 的本机版和开发工作集里做完；照常结单 | 本段 2.4 |
| 开发者上线后要改 | [../tasks/修订.md](../tasks/修订.md)，新需求从 ① 走 | — |
| 要下线、回滚、删除 | [../reference/部署与版本.md](../reference/部署与版本.md)「下线与删除」「修订、回滚、作废」，每一步都要开发者确认 | — |
