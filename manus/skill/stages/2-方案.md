# ② 方案（工作区阶段 G3）

让开发者确认「你们是按我的想法在做」。先按轮问清做法上的取舍；再把 PRD 和取舍的答案编成施工单（只给你和后续 Agent 用）；然后按功能翻成业务说明：这个功能帮你完成什么业务，按什么顺序、用什么数据、每一步谁来做，完成后你拿到什么、记在哪里。每个功能一道判断题，开发者逐题答「对」或「不对」；另交验收条目定稿和费用复核。

## 1. 进入条件

- ① 交棒：PRD 已确认，核实对照表里每一步都有能力来源。
- 从修订进来时，只编译和说明受影响的功能。

## 2. 段里怎么做

### 2.1 问取舍

PRD 定了要什么，同一件事往往有几种做法都能做，但使用者的感受不一样（快慢、全不全、要不要人把关）。这些取舍写方案前问清，不留到判断题里才发现不对。

1. **找出取舍**：按 PRD 每个刚需，在心里过一遍做法（不写给开发者），从 [../design/按轮问.md](../design/按轮问.md) 里 ② 的起步方向开始，列出两种以上做法都成立、选哪种使用者感受得到的地方；对话中冒出新的取舍随时加上。只有一种做法成立的、或使用者感受不到的你自己定（[../SKILL.md](../SKILL.md)「开发者确认什么」）。
2. **要看效果的先试跑**：取舍要看真实效果才能选的（例如报告看 6 篇要多久、看全要多久），用 ① 的真实样例按 [../tasks/能力试用.md](../tasks/能力试用.md) 建极简试用包把关键模型步骤跑一次，记下输出、用时、花费，写进题干。花费按 [../SKILL.md](../SKILL.md)「花费」。依赖试跑结果的题等结果出来再问，其余照常发。
3. **按轮问**：按 [../design/按轮问.md](../design/按轮问.md) 问，题目写法按 [../design/选择题与判断题.md](../design/选择题与判断题.md)「选择题」；PRD 和 ① 里已定的事不再问，问到没有空着的取舍为止。每轮的交接消息开头「【② 方案 → 等你确认】」。
4. **确认理解**：问完发「我理解的是这些」，按功能列出定下的取舍，开发者回「对」再编施工单。

没有取舍可问时（只有一种做法成立），在交接消息里说一句「做法上没有要你选的」，直接往下做。

### 2.2 编施工单

逐行把 PRD「每一步谁来做」映射成要造的东西，顺序固定：工具集 → FA → 编排型 TPE → 路线。

| PRD 里的 | 变成 | 怎么定 |
|---|---|---|
| 脚本步骤 | 编排脚本里的一步 `await tool(…)` | 从 [../reference/编排脚本.md](../reference/编排脚本.md)「三种模板」选一种改。路线要读写应用库的，现在就读 [../reference/数据模板.md](../reference/数据模板.md)「编排脚本怎么读写应用库」逐行写清：哪些固定读写由脚本做、哪些数据由 FA 按情况查、有没有应用后端回流 |
| 模型步骤 | 一个 FastAgent（复用或新建） | 定输出对象每个字段的含义和非成功状态（`needs_input`、`insufficient_evidence` 等）；档位照 PRD，建法见 [../reference/编排脚本.md](../reference/编排脚本.md)「建 FA」 |
| 人 · 开始 | 路线入口表单 | [../reference/数据模板.md](../reference/数据模板.md)「入口字段放哪」；[../reference/业务路线.md](../reference/业务路线.md)「assemble 怎么用」 |
| 人 · 在应用页面上操作（选一项、改字段、采纳或不采用、标记状态，不需要模型） | 页面 + 应用后端接口写表，不经路线 | 写哪张表、哪几列（列为 `user` 可编辑），接口见 [../reference/前端页面.md](../reference/前端页面.md)「业务页面」；操作后要让模型接着做的，由页面发起下一条路线，入口只传业务键，路线自己读库 |
| 人 · 中途补信息 | 节点级运行中交互 | [../reference/业务路线.md](../reference/业务路线.md)「什么时候用路线、用哪种」 |
| 人 · 审阅结果 | 路线的交付审阅 | [../reference/业务路线.md](../reference/业务路线.md)「交付与审阅」；要「修改后重跑」的加跳转到另一条路线 |
| 放进去 / 拿出来 | TPE 的 `input_schema` / `output_schema`，以及模板表 | 字段名用英文蛇形，含义写进 `description`；文件字段见 [../reference/编排脚本.md](../reference/编排脚本.md)「文件产物」 |
| 会停下的情况（停下 / 标记继续 / 重试一次） | 脚本的失败出口 | [../reference/编排脚本.md](../reference/编排脚本.md)「失败出口怎么写」 |
| 会记下来的东西 | 数据模板里的表与列 | 每列定 `user / agent / system`，见 [../reference/数据模板.md](../reference/数据模板.md)「每张表回答五问」 |
| 页面 | 预置件、生成页或定制页 | 按 PRD「界面」，见 [../reference/前端页面.md](../reference/前端页面.md) |
| 用量上限 | 一次最多处理多少条、单次运行时长 | 超过平台单次运行能力的改成分批或分片；做不到回 ① |

再定：

- **路线数**：按 [../reference/业务路线.md](../reference/业务路线.md)「什么时候用路线、用哪种」定拆几条；只有脚本步骤的应用也建一条最小路线，只作平台要求的挂载依赖，不为纯数据管理应用虚构额外业务流程。
- **数据怎么进出**：每个业务输入从入口来还是读库，按「入口字段放哪」定，同一个值只走一边；每个产出写到哪（更新已建行 / 回流建新行），以及同一业务再做一次时是更新原记录（写明业务键，如「同一门店同一周」）还是每次新增一条（如巡检历史），按 [../reference/数据模板.md](../reference/数据模板.md)「谁建行、谁写列」。
- **只有脚本步骤时**：施工单写一行「一条最小路线 + N 张表 + 数据页」即可；业务说明、判断题和验收条目照写。

施工单写进 G3：

| 清单 | 每项写什么 |
|---|---|
| 资产清单 | 类型、名称、复用还是新建、来源资产 ID、FA 的模型 |
| 路线草图 | 每条路线：`orchestration_id`、节点顺序、入口字段、中途表单、审阅方式 |
| 表清单 | 表名、列、每列可编辑性、唯一键、谁建行 |
| 页面清单 | 预置件 / 生成页 / 定制页，各自读写哪张表或哪条路线 |

### 2.3 业务说明与判断题

每个刚需写一段：

| 内容 | 写什么 |
|---|---|
| 完成什么业务 | 一句话 |
| 怎么完成 | 按什么顺序、用什么数据、每一步谁来做；数据从哪来、什么时候算、哪一步要人把关 |
| 做不成时 | 使用者看到什么 |
| 完成后 | 拿到什么、记在哪里 |
| 例子 | 用 ① 里开发者给的或真拿到的数据举例；模型要写的内容还没做出来，写成「预期会得到……」并标「预期」 |
| 判断题 | 一题，写法见 [../design/选择题与判断题.md](../design/选择题与判断题.md)「判断题」 |

另加一张「每一步用什么、花多少」：每一步写脚本还是模型、哪一档、为什么这样选、每次约多少积分，配一道判断题。

页面不进业务说明：页面长什么样已在 PRD「界面」确认过，页面上点了以后发生什么，有取舍的已在 2.1 问过。

### 2.4 验收条目

把 PRD 每个刚需的「怎样算做成」写成能逐条照做的验收条目，④ 按它验收。写法（五列、首次和日常分开、预标「AI 能判断 / 要人判断」）见 [../design/选择题与判断题.md](../design/选择题与判断题.md)「验收条目」。每个刚需至少一条；有中途补信息、审阅、会停下的情况的，各写一条走到那一步的。

### 2.5 费用与副作用复核

按施工单重算：制作还要花多少（冒泡、`full_run`、真跑的份数 × 每份花费）、上线后每用一次多少。读写应用库的路线 ④ 部署后才能真跑，拿不到实测时按 [../reference/平台对象速查.md](../reference/平台对象速查.md)「积分怎么算」估算并标「估算」、写出算法；之后有实测就换成实测。超出 ① 的上限时，做成选择题放进这次交付；累计花费怎么控按 [../SKILL.md](../SKILL.md)「花费」。

再核对会调的收费工具、会写或发出去的东西，与 PRD「费用与副作用」一致；施工单里多出 PRD 没列的写入或发送，回 ① 补确认。

### 2.6 发出

一次发出：每个功能的业务说明和判断题、「每一步用什么、花多少」、验收条目、费用复核、一句施工摘要（要做几件事）。交接消息开头「【② 方案 → 等你确认】」，「要你做的」写「逐题答对或不对；看一遍验收条目」。Studio 下本段交付物写成开发文档「方案」（[../design/开发文档/README.md](../design/开发文档/README.md)）。

开发者答「不对」的题，按 [../design/选择题与判断题.md](../design/选择题与判断题.md)「判断题」改完重问；要改的是要什么、不要什么时退回 ①。

## 3. 开发者要看、要做的

- 写方案前，按轮回答做法上的取舍题（同意推荐的回「按推荐」）。
- 读每个功能的业务说明和例子，判断是不是自己想的那样。
- 逐题回答判断题。
- 确认验收条目。

## 4. 产出与落盘

- 阶段文档 G3：取舍题的「已定的事」（每条写是什么、谁说的或按默认、哪一轮定的）和试跑记录、施工单、给开发者的业务说明、每道判断题和开发者的回答（含「不对」时的原话和改动）、验收条目定稿、费用复核。
- 交付物：方案页「开发内容」补「怎么做」（业务说明，用业务话说有几条路线、存几张表、几个页面）与「怎么验收」（验收条目），与 PRD 不一致的地方按 [../reference/开发者中心与工作区.md](../reference/开发者中心与工作区.md)「方案页」标出改动并升版；Studio 下写成开发文档「方案」，另交与验收条目一致的 `acceptance.json`。
- 工单 checkpoint：`方案已确认`，附资产清单摘要、路线与表名、验收条目数。
- 出口标记：G3 `passed`，用 `business_ui_stage` 写 G3 一条（写法见 [../reference/开发者中心与工作区.md](../reference/开发者中心与工作区.md)「三件套与阶段标记」）。

## 5. 交棒条件

- 取舍都定了（开发者答的或按默认），开发者对「我理解的是这些」回了「对」，施工单按定下的取舍写；
- 每个功能的判断题都单独发给了开发者，并且都答了「对」；Studio 下读到当前这一版方案的确认；
- 验收条目开发者确认了，PRD 每个刚需至少一条；
- PRD 每一行在施工单里都能找到对应项；费用没有超出上限（或超出部分开发者已选过）；副作用没有超出 PRD「费用与副作用」；
- 出口标记已写。

## 6. 出问题怎么办

| 现象 | 回到 |
|---|---|
| 某一行编不出来（没有对应能力） | ①：对照 G2，改 PRD，告诉开发者做不到和替代 |
| 编完费用超出上限 | 本段 2.5 做成选择题 |
| 编完多出 PRD 没列的写入或发送 | ①：补确认 |
| 开发者要的东西变了 | ①：改 PRD 再确认 |
| 取舍要看效果才能选，试跑跑不了（读写应用库要部署后才能跑、工具被平台问题挡住） | 本段：用 ① 真调拿到的数据和同类步骤的估算写题干，标「估算」，照常问；只是还没跑完的，等结果 |
| PRD 里有只能由平台方做的事（例如改使用者的安装记录、改生产库） | 施工单只编 Skill 允许的做法，这一项不编；按 [../SKILL.md](../SKILL.md)「平台问题」报，交接消息里说清对哪个功能有影响；退回 ① 把 PRD 那一处改成平台问题和对开发者的影响，开发者确认后再回来 |
| 一条路线步骤太多、业务说明讲不清 | 本段 2.2：按 [../design/谁来做.md](../design/谁来做.md)「填写规则」的写法建议考虑拆成两条，业务说明里讲清 |
