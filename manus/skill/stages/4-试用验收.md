# ④ 试用验收（工作区阶段 G6）

你先部署，用真实数据把应用按验收条目逐条验一遍，没过的改好再验，全部通过后交一份验收报告。开发者不再逐条试、不打勾：他看报告，「好不好你说了算」的几条看你附上的实际结果，最后说「可以上线」。验证只有两层：冒泡管改，真跑和验收报告管收。

你不开浏览器进「在线试用」、正式入口或登录页（`SKILL.md` 第 0 节）。页面上的操作在本机版上验，业务结果用真实数据真跑验；只有线上页面、用真实身份才能点的，列为「我试不了的」，放进 ⑤ 上线后请开发者在正式版里试。

## 1. 进入条件

- ③ 交棒：应用根 `npm run verify` 全绿，每个功能都做好了或标明没做成；读写应用库的路线在阶段文档 G4 有反读自查表且四项都是「有」，没有就回 ③ 补，不部署。
- 本轮需求已全部实现：在桌面开发者中心里执行 `prepare_business_app_skill` 返回的完成版命令，开发者就能在「演示预览」看本地完成版（见 [../reference/开发者中心与工作区.md](../reference/开发者中心与工作区.md)「演示预览为空」）。

## 2. 段里怎么做

### 2.1 部署

场景包不必先上线：挂着你本人的场景包草稿也能部署。

1. 先调 `business_ui_bundle(action="download_template")` 核脚手架门槛，需要升级时完成迁移与验证。
2. 在应用根目录运行 `npm run verify:release`，全部检查通过后生成 `.pack/business-ui-bundle.tar.gz`，按这个包算 `source_sha256` 与 `size_bytes`。**禁止**用 `npm run pack`、直接运行打包脚本或手写 tar 代替 `verify:release`，那样会跳过发布检查。
3. `business_ui_bundle(action="ship", task_id, business_ui_id, source_sha256, file_name="business-ui-bundle.tar.gz", size_bytes)`（`file_name` 只写文件名，带目录会被拒；`business_ui_id` 是上线行、要自动派生草稿时同时带 `change_note`，写这次改了什么）：
   - 返回 `status=upload_required`：按 `upload_url` 与 `headers` PUT 源码包原字节，原参数加 `bundle_key` 再调；
   - 返回未终态：原参数加 `deployment_id` 再调，服务端每次最多等约 45 秒；**禁止**去掉 `deployment_id` 重调，那会重新起容器；
   - 到 `success` 为止。`steps` 标明每步 done / skipped / resumed。明确失败且原因不在源码包时，再用 `prepare_upload` / `complete_upload` / `deploy` / `status` 单步排查。
4. `business_ui_manage(action="get")` 核对部署已写进当前草稿；记下 `deployment_id`、`source_sha256`、`deployed_scaffold_version`。`entry_url` 是开发者容器地址，只用来核对绑定，不打开、不发给任何人。`deploy` 返回带 `scaffold_upgrade_notice` 时原样记进开发记录，上线结果要写。

### 2.2 用真实数据跑

有模型步骤，或路线要读写应用库、调外部接口时做；只有脚本步骤且 ③ 的 `full_run` 已覆盖时可省，省了写明原因。例子由你挑，挑法同 ③ 2.1 第 9 步，验收条目里点名的样例都要跑到。PRD 已列的费用直接执行；没列的、会对外发送或写正式数据的先说明再执行。

1. `manage_goalfymax_project(action="run", task_id, idempotency_key, scenario_package_ids=[<场景包当前草稿或上线版本的物理行 ID>], submit_data={…}, business_ui_id=<应用家族 ID，路线读写应用库时传>, business_ui_data_space="workspace")`。返回 `BUSINESS_UI_NOT_ONLINE` 或要求先上线时，补 `business_ui_data_space="workspace"` 重跑，不要为真跑去 finalize。`workspace` 跑你刚部署的版本，读写开发工作集，和「在线试用」是同一份库，应用不用先上线；路线不碰应用库就不传 `business_ui_id`。
   `submit_data` 里必须有 `business_id`（你生成，例如 `biz-<场景包简称>-<日期>-<序号>`，同一业务实例里不变，后面 `reply` 沿用）和 `orchestration_id`（场景包编排里要启动的那条路线的 id），其余是入口表单字段。
2. `manage_goalfymax_project(action="wait", project_id)` 等到终态（`wait` 不接受 `wait_seconds`），中途表单或审阅用 `reply`，回业务表单时 `content` 传空字符串、答案放在表单数据里；以 `route_runs` 里各路线的状态为准（路线完成后项目可能仍显示 running），`succeeded` 表示这条路线真跑通过，结单门会把它记为这条路线的证据。
3. 对路线里每条 TPE 调 `otpe_manage(action="verify", task_id, tpe_id, project_id)`，`passed` 即完成；③ 只差运行证据的 TPE 必须在这里补齐，读写应用库的路线不能用冒泡或结单门豁免代替这一步。
4. `get_project_execution_logs(action="workflow_trace", project_id)` 看每步，模型步骤的输出你逐条读一遍；写库的结果去应用库里查到那一行。
5. 记下每个按钮这次实际花了多少（`cost_credits`），和 PRD 的估算比。
6. **回写演示示例**：③ 在阶段文档 G5 记了「待 ④ 回写」的演示和示例，从这次真跑通过的结果里选一份写回代码，去掉「示例」占位，按 2.1 重新 `verify:release` 并部署，修改记录写明。回写不算退回 ③，在 2.3 逐条验之前做完。

失败在同一草稿改再跑；每次只改一处，不同时改脚本和路线。

### 2.3 按验收条目逐条验

逐条对照 ② 定稿的验收条目，照「照着做」做一遍，按「这样算对」判通过或不通过，每条记「怎么验的」和证据。按条目要看的东西选验法：

| 条目要看的 | 怎么验 | 证据 |
|---|---|---|
| 业务结果：报告、内容、识别出来的东西、写进库的记录、发出的消息 | 2.2 的真跑；条目点名的样例没跑到的，照条目再真跑一次 | `project_id`、`workflow_trace` 摘录、库里查到的行 |
| 页面上的操作和显示：点哪、跳到哪、空态、提示文字、必填校验、打回和重新生成、切语言、只读置灰、离开再回来 | 本机版：在应用根用 `npm run dev:restart` 起本地页面和后端（后端连开发工作集，平台消息和发起路线走本机内置 Mock），用无头浏览器**只访问本机地址**照条目操作；再跑脚手架的前端测试和本地布局回归 | 操作步骤与截图，写明「本机版」 |
| 只有线上页面、用真实身份才看得到的：消息中心铃铛跳转、真实授权与付款、正式入口里的复制和下载、多种人各自登录看到的东西 | 你试不了 | 列进「我试不了的」，写为什么、上线后怎么试 |

- **看实际产出，不只看状态**：页面或日志显示「已完成」「成功」不算通过，要看到真的产出（报告内容、库里的行、发出的消息）。
- **每条「通过」都要附证据**：业务条目附这次 `workspace` 真跑的 `project_id`、`workflow_trace` 里对应步骤的摘要、库里查到的那一行；页面条目附本机地址、无头浏览器的操作步骤和截图文件路径或断言原文；只请求过页面地址（`curl`、HEAD 返回 200）不算操作过。缺任何一样就不能写「通过」，先补证据。冒泡（含 `full_run`）只证明路线能跑，不证明应用库的真实读写，不能拿来给读写应用库的条目标「通过」。部署成功、请开发者打开「演示预览」或「在线试用」都不算验收，不能代替这一步。
- 按 ③ 的业务含义对应核首页、历史、详情、消息、发起、补充、提交查看、审阅及返回：名称对应同一实际事项，上传不冒充已发起，提交或受理不冒充完成，未定义产物不出现报告；加载、空态、只读、暂停、失效也核对。
- ② 里标「要人判断」的条目（内容能不能直接对外、语气像不像、业务判断对不对、前后两批有没有变好），你照样做一遍，但不下结论：把实际结果原文附进报告，标「好不好你说了算」。
- **没通过的**：改好、按 2.1 重新部署，再验这一条和受它影响的条目；改不好、要换做法的回 ③，和预期差得多的按 ③ 2.4 出选择题。报告要等所有条目都有结论再交，交之前进度照常按「正在做」报。
- 按 [../checklists/验收清单.md](../checklists/验收清单.md) 逐条写「通过 / 不适用 + 一句依据」；只有下面「我试不了」允许的那几类能列进「我试不了的」，其余做不到的按「没通过」处理。

### 2.4 交验收报告

发交接消息，开头「【④ 试用验收 → 等你确认】」，附验收报告：

| 项 | 写什么 |
|---|---|
| 结论 | 一共几条：通过几条、我试不了几条；有开发者选了接受的没通过条目，单独写几条 |
| 好不好你说了算 | 每条附实际结果：报告全文或链接、内容原文、前后对比；开发者觉得不行直接说是哪一条 |
| 我试不了的 | 每条写为什么试不了、上线后在正式版里怎么试；这几条会写进 ⑤「你要做的」 |
| 全部条目 | 默认折叠，固定六列，每格都要填：#、验收条目、结论（通过 / 没通过 / 好不好你说了算 / 我试不了）、`project_id`（本机版写「本机版」）、`workflow_trace` 摘要或本机操作步骤、查到的行或本机截图（不写库的写拿到的产出） |
| 用真实数据跑出的结果 | 本段真跑的结果摘要，加上 ③ 里 `full_run` 跑出的内容，和 ② 的预期对照 |
| 自动发生的 | 到点或有新记录时自动开始的，这里用 `business_ui_automation(bubble)` 按自动化的入口跑一次，结果附上；`run_once` 要求应用已上线，真跑和到点触发在 ⑤ 验（见 [../reference/自动化.md](../reference/自动化.md)「验证」） |
| 实际花费 | 每个按钮实际花了多少，和估算比；每份要等多久、能不能同时开几个 |

「全部条目」照这个表头抄，一条验收条目一行：

```text
| # | 验收条目 | 结论 | project_id | workflow_trace 摘要 / 本机操作步骤 | 查到的行 / 本机截图 / 拿到的产出 |
|---|---|---|---|---|---|
```

读写应用库的条目只有冒泡证据（冒泡里读库报 `not_a_business_app_project`、写库被 `ctx.dry_run` 跳过），没有 `workspace` 真跑查到的行时，自查记录里写「未验证：只冒泡过，没在开发工作集里真跑」，不写「通过」，先回 2.2 真跑补上，补完再交报告。

「我试不了」只允许这几类：2.3 表第三行（消息中心铃铛跳转、真实授权与付款、正式入口里的复制和下载、多种人各自登录看到的东西），以及到点触发、正式版真跑。页面交互（含必填校验、打回、重新生成）在本机版上验，数据行在 `workspace` 真跑后查，风险行、边界情况用 ③ 挑过的例子真跑；这几类只能是「通过」或「没通过」，证据不够就是「没通过」，回 2.2、2.3 补。

**报告的硬门**：出现下面任一种，G6 标 `failed`，报告不交，**禁止**请开发者回「可以上线」，先回 2.2、2.3 补证据：结论是「通过」的行，后三列缺任一格；有「未验证」的行；页面交互、数据行写成了「我试不了」；报告、交接消息里请开发者去「在线试用」「演示预览」里看、点或查数据。

「要你做的」只有这三项，照抄：① 看验收报告；② 看「好不好你说了算」的几条，实际结果已经附在报告里；③ 都没问题回「可以上线」，有问题回「还要改：第几条」。报告里有「没通过」的条目时，先按 2.5 最后一条把它们做成选择题放进「要你做的」，开发者选完再请他回「可以上线」。**禁止**在「要你做的」里请开发者打开「演示预览」「在线试用」或正式版去看、去点、去查数据。需求方和开发者不是同一人时，请开发者把「好不好你说了算」的几条转给需求方看。

开发者想自己用，随时可以在开发者中心右侧「在线试用」里用（这句只在开发者问起时说，不写进交接消息）：它带真实身份和真实路线，不需要先上线；试用里的数据写在开发用的一份库里，正式版不会带过去，真实的付款和授权是真的。他用的时候发现问题，按 2.5 处理。你不开任何浏览器去打开「在线试用」、正式入口或登录页。

### 2.5 按反馈改，只重验受影响的

- 开发者说哪条不对、或「好不好你说了算」的结果不满意：改完重新 `verify:release` 并部署，重验这一条和受影响的条目，报告里只更新变了的条目，修改记录写「问题 / 改了什么 / 重验了哪几条」。
- 改了场景包草稿的重新部署即可，不用上线。应用已上线过、挂载钉在旧版本号时，先 `business_ui_manage(action="update", business_ui_id, scenario_pack_id, scenario_pack_version=<场景包草稿版本号>)` 换挂到草稿再部署，否则试用仍跑旧的上线版本。
- 结果不对、要改做法的回 ③；开发者发现要的东西本身不对，回 ①。
- 开发者要在还有条目没通过时直接上线：把没通过的条目逐条做成「接受，先上线 / 等改好再上线」选择题，写清上线后使用者会遇到什么；选了「接受」的条目结论记「没通过，开发者选了接受」，上线结果「还没验证的和风险」里写明。

### 2.6 阶段评分（仅 Codex）

开发者说「可以上线」之后，按 [../design/阶段评分.md](../design/阶段评分.md) 单独发一条「G6 demo 试用」评分，发完直接进 ⑤，**禁止**等评分回复。

## 3. 开发者要看、要做的

- 看验收报告；「好不好你说了算」的几条看实际结果。
- 说「可以上线」，或说哪一条还要改。

## 4. 不给开发者的

部署过程、`verify` 与在线检查结果、版本号、容器地址、原始日志和 JSON。没有结论的条目不交报告。

## 5. 产出与落盘

- 工单 checkpoint：场景包草稿或上线版本、`deployment_id`、`source_sha256`、`deployed_scaffold_version`、真跑的 `project_id` 与结论、每条 TPE 的 `verify(tpe_id, project_id)` 结论、开发者（和需求方）说「可以上线」的原话、我试不了的条目、开发者选了接受的条目。
- 阶段文档 G6：验收报告全文（每条怎么验的、证据、结论）、修改记录、验收清单逐条结论、实际花费；「阶段评分」一节按 [../design/阶段评分.md](../design/阶段评分.md) 记录。
- 方案页：交报告时 `status` 为 `waiting`，`.pv-you` 写「看验收报告，没问题回『可以上线』」；入口、权限、部署问题推进不了时为 `blocked` 并写 `.pv-owner`；通过的条目移入「已验证」，证据写部署编号与真跑的 `project_id` 或「本机版」；我试不了的留在「未验证」并写原因。
- 阶段标记：G6 `passed`。

## 6. 交棒条件

下面都满足后，先用命令把 [5-上线.md](5-上线.md) 从头读到尾，再做 ⑤ 的第一件事。

- 最近一次部署 `status=success`；
- 每条验收条目都有结论：通过（带 2.3 规定的证据）/ 我试不了（写了原因和上线后怎么试）/ 没通过且开发者选了接受；读写应用库的条目至少有一次 `workspace` 真跑的 `project_id`；
- 验收报告已经发给开发者，过了 2.4「报告的硬门」，开发者说「可以上线」是在看过报告之后；
- 验收清单逐条有结论；
- 读写应用库的路线，每条 TPE 最近一次 `verify(tpe_id, project_id)` 为 `passed`；
- 开发者（和需求方）看过报告，明确说了「可以上线」或等价表述。

## 7. 出问题怎么办

| 现象 | 先看 | 回到 |
|---|---|---|
| 部署 `status` 失败 | 返回里的构建日志尾部；本地先 `npm run verify:release` | ③ |
| 部署被脚手架闸门拒绝 | [../reference/脚手架与预置件.md](../reference/脚手架与预置件.md) 错误码表 | 升级后重来 |
| 开发者说「在线试用」打不开或提示未就绪 | `PREVIEW_NOT_READY`：当前草稿没有部署成功的记录，在当前草稿行重新 `ship` 到 `success`；再核对 `business_ui_id` 与环境；`ship` 已成功仍未就绪才报平台问题 | 本段 2.1 |
| 定版前 `resolve` 报「还没有上线版本」 | `resolve` 只认上线版本，定版前本来就这样；不记 platform_blocked，也不为拿入口去 finalize | 本段 2.3 |
| 本机版起不来或连不上开发工作集 | `npm run doctor`、`backend/.env` 的连接串是否过期（`dataset_template_workspace(action="connect")` 重签） | 本段 2.3 |
| 真跑卡 `waiting-input` | 用 `reply` 回表单；没人答就是正常挂起 | 本段 |
| 真跑返回 `BUSINESS_UI_NOT_ONLINE` | 传了 `business_ui_id` 没传 `business_ui_data_space="workspace"`；补上再跑，不需要 finalize，不记 platform_blocked | 本段 2.2 |
| 真跑返回 `BUSINESS_UI_NOT_DEPLOYED` | 还没有你本人部署成功的版本，或 `business_ui_id` 传成了版本行 ID；先 `ship` 到 `success`，用家族 ID 重跑 | 本段 2.1 |
| 协作者预览提示需用新版脚手架重建，或充值相关操作被拒 | [../reference/多人协作.md](../reference/多人协作.md)「预览、费用与限制」，这是预期限制，不报平台问题 | 本段 2.1 |
| 真跑内容不对 | 模型步骤提示词、模型档位或输出字段 | ③ |
| 页面行为不对 | 页面块或生成页 | ③ |
| 开发者说要的东西本身不对 | — | ①：改 PRD，只重做受影响的部分 |
| 疑似平台问题 | 走不下去才立即 `submit_dev_feedback(blocking="blocked")`；能绕过就继续，记进开发记录，⑤ 交付时汇总；提交后没人修按 `SKILL.md` 第 7 节的升级顺序做 | — |
