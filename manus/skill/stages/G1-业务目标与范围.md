# G1 业务目标与范围

> 阶段层文件。固定七项：进入依据 → 本阶段建设 → 给开发者看什么 → 要确认哪些边界 → 门禁 Checklist → 证据与结论 → 失败回退。方法细节在专业模块，本文只说此刻要确定什么、展示什么、验证什么。

## 1. 进入依据

一句业务目的、PRD、SOP、参考项目、或一个已有应用的问题——**任一种均可**。不得要求先交齐完整产品文档；材料不足时由 Agent 提案补齐，标明哪些是推断。

进入前已完成总入口的任务识别与工单 Gate（`SKILL.md` §1–2）。接续任务先盘点已有业务基线，只补未满足项。

## 2. 本阶段建设

按 [P1 业务访谈、价值判断与领域依据](../modules/P1-业务访谈与价值判断.md) 的方法执行，产出下列内容：

1. **理解材料**：完整读取（协议《事实、决定、授权与变更》约束 3）；把内容分成**已知事实 / Agent 推断 / 待确认项**三栏；有真实执行项目时按 P1 §2 提炼现有工作法与困难。
2. **目标诊断**（P1 §1–2 + 附录 D1 框架）：使用者到底要完成什么业务结果；当前怎么完成；困难在生产、专业判断、协作还是持续管理；直接做一次 / 复用已有能力 / 制作能力容器 / 制作完整应用哪个必要；哪些信息必须向业务方确认。
3. **把动作补成结果**：写出"用户带什么进入 → 经过什么 → 最终得到什么"；把"生成周报"补成"负责人能据此判断哪些门店需要跟进"。业务目标分三层写：客户期望改善什么 / 应用负责交付到哪 / 一次运行完成什么，三者不互相冒充。
4. **正例与反例**：Agent 先草拟供业务方修正；来源不足标"合成示例"，不冒充真实案例，也不因业务方不会写案例就停住（P1 §3.2）。
5. **初始评价方式**：质量、时间、成本、操作负担各定一个可检查的判断依据；没有基线就写"待测"，不编造改善幅度。
6. **采购理由与合格交付物**：客户为什么买、什么算合格（事实无误、素材相符、满足约定要求、文件可用、修改被处理）；用户按"通过"只说明接受动作。
7. **U1–U8 适用范围审查**：逐项判断本应用是否提供首用 / 续用 / 历史、修订、长期偏好、跨应用、临时编排；不支持某能力不等于该项不适用；既有承诺不得静默删除。

## 3. 给开发者看什么

**一页业务简报 + 可检查的目标产物样例 + 首次 / 再次使用的短流程。**展示"如果现在交付这个，你能不能完成原来的工作"，而不是先展示数据库、TPE 或页面。

简报固定内容：服务对象与情境；用户带入 / 经过 / 得到；正例与反例（标来源）；三层目标；采购理由与合格定义；不做什么与先停条件；未知项与验证办法。每条标注 事实 / 推断 / 未知 / 挑战（唱反调：客户要的也许不是这个产物；基础组件易得凭什么用你的；模板复制的是方法不是页面）。

## 4. 要确认哪些边界

服务对象与规模；输入来源和可用权限；必须交付项；明确不做项；需要人判断的事项；对外动作（发送、发布、写入外部系统）。区分**硬限制**与**可协商**。

确认方式：Agent 出决策卡（当前问题、证据、推荐、替代、选择后改变什么、验收怎么看、需要决定什么），聚焦关键分歧；不逐章全文确认（协议《阶段展示与证据等级》）。

## 5. 门禁 Checklist（G1，必须引用适用 U 项的分阶段结论）

见 [G 门禁检查清单](../checklists/G门禁检查清单.md) G1-01 … G1-05：

- `G1-01` 首次、处理中返回、查看历史、再次使用的目标分别说明（U1）。
- `G1-02` 制作完整应用的理由成立；一次性工作不进入完整流程。
- `G1-03` 关键交付有样例与不合格反例；"专业、好看、智能"已转成判断依据。
- `G1-04` U1–U8 适用范围已审查；事实、假设、授权分开。
- `G1-05` 每项必须能力都有后续验证责任；未知项未被当作事实。

## 6. 证据与结论

产出：**业务基线初版**（简报 + 样例与来源 + 决定记录 + 待测假设），落工单 `business_baseline` 检查点；U1–U8 适用性判断表落 `behavior_scope`。

结论只到"目标与范围已对齐"，不宣称能力可行。

## 7. 失败回退

必要目标仍不清 → 不通过，可进入调查补事实（只读，不创建正式资产）。业务方改范围 → 更新基线并重新过门禁。
