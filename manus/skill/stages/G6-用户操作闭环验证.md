# G6 用户操作闭环验证

本阶段的目的是**证明已做好的能力，最终用户真的用得上**。实现完整业务界面，接通 SDK、状态、修改与历史，在真实预部署物上按用户旅程操作。前端细则与正本地图见 P5，时序验收表见 P6。

## 1. 进入依据

G5 后端关键闭环成立；页面设计与真实公开契约一致；《业务应用计划书》已确认。未就绪的业务切片**不得**伪装可用。

进入本阶段先把 `workspace.json` 里 G6 那一项改成 `in_progress`，`docs/stages/G6-用户操作闭环验证.md` front matter 的 `status` 同步改成 `in_progress`，`WORKSPACE.md` 的 `current_stage` 改成 G6。

## 2. 本阶段建设

### 2.1 实现前端

正本是 `frontend/README.md` 与 `frontend/docs/business-ui-guide.md`；脚手架 demo 只用于理解协议，**禁止**复用其页面结构、排版与视觉。原型代码直接演进为正式实现，不重写。

**SDK 两层与保留件。** App 层是 `session`、`projects`、`getProject`、`inbox`、`api`、`storage`、`ui.reservedAreas`、`theme`；项目句柄层是 `business`、`upload`、`file`、`chat`、`observe`、`info`。保留件**必经，不改不删**：`useProject`、`useProjectExecution`、`useProjectDraft`、`useInbox`、`useRuntimeUserFiles`、表单渲染、错误归一化、`FileField`、`MarkdownContent`、局部错误边界。表单预填已下线，残留文件**不接入、不依赖**；表单 Schema 唯一真源是契约包 `forms/` 与 `getForms(formId)`。一切平台调用经 SDK，后端 API 走 `sdk.api.request`，`code !== 0` 必须给用户反馈，无静默失败、无自动重试；**禁 fetch、XHR、axios**。所有前端源码在 `frontend/src/` 下。

**三个必备页面。** 首页非占位、非空白，待办入口带 `useInbox().unreadCount` 角标；项目列表页 `sdk.projects.list` 在打开、翻页、刷新时拉，`onStatusChange` 按 `projectId` 就地更新，**禁轮询**，空列表引导去发起首个项目；消息中心必经 `useInbox()`，点击导航到对应项目的应答状态。

**四类业务页面。** 看板数据只来自后端统计 API，每个数值可溯源，空数据有引导态；数据管理只对 `editable:user` 列开放编辑，`agent` 列只读并标来源，批量与删除有确认；业务发起必经 `useProjectDraft(draftKey)`，按 `getForms(formId)` 渲染，**没有预填**，文件经 `project.upload`，提交必须等全部上传终态，`accepted` 转正入列表并导航到项目页，`rejected` 原窗重填，`failed` 展示结构化错误不自动重试，复用已有项目由用户在下拉框显式选中；项目页阶段进度按业务事件订阅一次纯归约，服务端调起表单到达后导航到可恢复的应答状态，交付审阅页按 `display` 五字段渲染，只在存在活动 Call 时渲染动作按钮，只提交 `action_key`，执行记录三级下钻每级只拉一次，已提交表单以 key-value 展示。

**应答提交到运行的过渡。** 项目层用 `useProject(projectId)` 持有句柄并在同一层调用 `useProjectExecution(project)`，应答页、进度页、交付审阅页共享 `projectStatus`、`pendingRun`、`submitting`、`workflowRuntimeId` 和 `reply`；应答入口用 `execution.reply`，**不得**绕过它另调 `project.business.reply`。**不得**在每个子路由重建句柄或执行态保留件。状态固定六种：提交中、已受理、运行中、待补充或审阅、失败、完成。**禁止**自己猜进度。逐状态的页面反馈与提交锁边界表见 P5 第 7.3.1 节。

**表单与文件纪律。** 三类回显各归其位：草稿、驳回、已提交。校验失败有 toast、无效项高亮、首个无效项聚焦。文件字段值只能由上传产生、全程只读卡片；展示 URL 经 `getViewUrl` 现取现用，下载只在用户点击处理器内调用；数据管理页**不能**用 `project.upload`；应用级文件用 `sdk.file` 与 `shared/ApplicationFileField`。**禁止**把当前路由写进 `sdk.storage`。

**构建与打磨。** 组件只从白名单取：Magic UI、Cult UI、KokonutUI、shadcn/ui；取来的组件适配项目 token、响应式、`prefers-reduced-motion`。每个动效有目的，过渡可被安全打断。**至少完成一轮真实渲染页修正**，桌面与移动各过主旅程和非正常态，查键盘导航、可见焦点、对比度、触控目标、长文本、溢出。对照《业务应用计划书》逐条核对，**测试每一个可交互的地方**。开发中发现设计做不了，回 G3 改设计并带更新后的原型重过确认，**禁止**静默改设计继续做。文案与注释一律中文。

### 2.2 本地测试

1. 后端 `npm test` 全绿。
2. `npm run dev` 真跑，两个档位分开取证，**禁止**互相顶替：Direct Mock 走通自测矩阵 A 到 E 组，含旗标态 `?mock=view|preview|permission-cycle|storage-off|attention|frames-off`，它只证明界面状态机完备，**不打本地后端**；Dev Host 的 local-backend 模式证明界面经 Bridge 真的打到了本地后端 8000，含请求限制、身份注入、超时、响应上限与信封检查，但**不能**证明平台寻址、真实身份、真实 schema 与部署网络。需要宿主主动事件的场景用 Dev Host Mock。
3. mock 可测边界是封闭白名单：业务事件真实语义、真实路线行为、真实文件 URL、后端真实行为**不可 mock**；不为可测改 mock、不自造桩、不降断言。
4. Playwright 用例按真实页面、`schema/` 与路由动态编写，覆盖表**必须**含编辑场景与看板场景；用例名带《业务应用计划书》⑤⑦⑨ 的条目编号；不绑 mock 数据具体值；断言谓词先证明能失败。
5. `cd frontend && npm run check` 通过；交付前在仓根跑 `npm run verify`，它依次做脚手架诊断、接口与数据集契约核对、前后端测试和构建。示例残留即失败。业务页面不写单元测试。

### 2.3 预部署真验

重新 `./scripts/pack.sh` 打包，经 `business_ui_bundle` 上传部署到终态 `success`，`business_ui_manage(get)` 反读预部署入口。在真实宿主用测试账号走一遍用户旅程：首次使用、已有任务、返回历史、局部修改、结果预览与下载、数据管理、反馈入口。**禁止**把后台管理界面直接交给用户。

**时序验收**：中途表单和有应答动作的交付审阅都要覆盖 `accepted` 与 `running` 乱序、其他项目推送、切页与刷新、`rejected` 与 `failed`、权威终止先到等场景，断言实际页面变化和提交锁，场景表见 P6 第 9.3 节。报告分别写清"辅助函数已加入""实际页面已接入""部署物已验证"，前一项不能替代后一项。

**实际操作检查**：看得懂、点得对、回得来。验证长文本、空态、错误态、窄屏、键盘、权限变化。`view` 权限下全部写入口置灰并说明原因。按应用验收检查清单的前端部分逐条给判定与依据。

## 3. 给开发者看什么

默认展示两样：**可操作的应用、一个用户旅程的实际演示**。页面只把顶部的当前阶段改成 G6；操作记录、时序验收结果记在本阶段 md 里。页面设计因验收要改时，同步改页面里的页面清单。开发者说"这里不对"时，你定位到具体状态或动作与影响范围，**禁止**让开发者自行描述 SDK 实现。

## 4. 要确认哪些边界

哪些信息常驻显示、哪些只在决策时出现；修改作用范围；删除与提交的确认语义；长期偏好保存意图。信息显示不等于授权；按钮不可用必须说明原因。

## 5. 门禁 Checklist

**出口判定只有两句**：本阶段涉及的每条承诺（`C` 编号）各有用户操作证据，等级按协议三第 4 节的表核对过；开发者用过页面后说了一句话，原话记进本阶段 md。两句成立才算出口，下面逐条是核对这两句的依据，不替代这两句。

- `G6-01` 分别用零历史、已有资料、未完成任务、历史结果四种状态进入应用并验证后续行为。**禁止**用一次新建演示代替。对应 U1。
- `G6-02` 用户在页面上能核对本次对象、输入来源、推断与冲突提示、完整产物，并完成 U2 与 U5 的动作；不要求阅读内部 JSON 或执行日志。
- `G6-03` accepted 与 running 乱序、其他项目推送、切页与刷新不误报成功、不闪回旧表单、不重复提交；提交锁与执行展示各有依据。
- `G6-04` 按 U4 在真实页面执行离开与返回、补充、重试；另测上传失败后的替换与提交拦截。
- `G6-05` 从指定旧版本发起局部修改、关联修改、失败重试，逐项核对 U5-02 至 U5-05。"重新生成"按钮**不算**全部修改能力。
- `G6-06` 分别完成 U6 的复用、单次隔离、纠正与撤销、效果回传。核对实际执行输入，**禁止**只看设置页已保存。
- `G6-07` 实际浏览器操作与基本可访问性通过。Mock 与截图**不能**代替当前真实部署物的证据。

## 6. 证据与结论

产出操作录像或逐步截图、页面专属自动化测试报告、时序验收时间线、真实运行与数据库关联记录、`npm run verify` 结果。前端校验项转入结果检查表，用预部署真实数据闭合。 本阶段结束时更新承诺清单：本阶段取到证据的承诺逐条填证据指针与状态，整份重写 `commitment_list`。

**阶段出口动作**：门禁全过后，把 `workspace.json` 里本阶段那一项改 `passed`、下一阶段那一项改 `in_progress`，`docs/stages/G6-用户操作闭环验证.md` front matter 的 `status` 同步改 `passed`，写 `stage_exit`，从存在 business_ui 草稿起打包部署一次，再把 `WORKSPACE.md` 的 `current_stage` 改成下一阶段并把下一阶段文档 front matter 同步，`docs/proposal/index.html` 本阶段各块定稿、顶部阶段同步，最后 `workspace_push` 整个 goalfy-app-workbench 目录；开发者中心自动刷新。顺序见协议四第 6 节。

## 7. 失败回退

失败一律带归属，五类之一：单元、路线、数据、页面、平台，规则见协议三第 5 节；没有归属的失败描述不算结论。

交互实现错误：在 G6 修。数据或运行事实错误：回 G5。原设计不可用：回 G3。
