## 2. 本阶段建设

### 2.1 实现前端

正本是 `frontend/README.md` 与 `frontend/docs/business-ui-guide.md`；脚手架 demo 只用于理解协议，**禁止**复用其页面结构、排版与视觉。原型代码直接演进为正式实现，不重写。

**SDK 两层与保留件。** App 层是 `session`、`projects`、`getProject`、`inbox`、`api`、`storage`、`ui.reservedAreas`、`theme`；项目句柄层是 `business`、`upload`、`file`、`chat`、`observe`、`info`。保留件**必经，不改不删**：`useProject`、`useProjectExecution`、`useProjectDraft`、`useInbox`、`useRuntimeUserFiles`、表单渲染、错误归一化、`FileField`、`MarkdownContent`、局部错误边界。表单预填已下线，残留文件**不接入、不依赖**；表单 Schema 唯一真源是契约包 `forms/` 与 `getForms(formId)`。一切平台调用经 SDK，后端 API 走 `sdk.api.request`，`code !== 0` 必须给用户反馈，无静默失败、无自动重试；**禁 fetch、XHR、axios**。所有前端源码在 `frontend/src/` 下。

**三个必备页面。** 首页非占位、非空白，待办入口带 `useInbox().unreadCount` 角标；项目列表页 `sdk.projects.list` 在打开、翻页、刷新时拉，`onStatusChange` 按 `projectId` 就地更新，**禁轮询**，空列表引导去发起首个项目；消息中心必经 `useInbox()`，点击导航到对应项目的应答状态。

**四类业务页面。** 看板数据只来自后端统计 API，每个数值可溯源，空数据有引导态；数据管理只对 `editable:user` 列开放编辑，`agent` 列只读并标来源，批量与删除有确认；业务发起必经 `useProjectDraft(draftKey)`，按 `getForms(formId)` 渲染，**没有预填**，文件经 `project.upload`，提交必须等全部上传终态，`accepted` 转正入列表并导航到项目页，`rejected` 原窗重填，`failed` 展示结构化错误不自动重试，复用已有项目由用户在下拉框显式选中；项目页阶段进度按业务事件订阅一次纯归约，服务端调起表单到达后导航到可恢复的应答状态，交付审阅页按 `display` 五字段渲染，只在存在活动 Call 时渲染动作按钮，只提交 `action_key`，执行记录三级下钻每级只拉一次，已提交表单以 key-value 展示。

**应答提交到运行的过渡。** 项目层用 `useProject(projectId)` 持有句柄并在同一层调用 `useProjectExecution(project)`，应答页、进度页、交付审阅页共享 `projectStatus`、`pendingRun`、`submitting`、`workflowRuntimeId` 和 `reply`；应答入口用 `execution.reply`，**不得**绕过它另调 `project.business.reply`。**不得**在每个子路由重建句柄或执行态保留件。状态固定六种：提交中、已受理、运行中、待补充或审阅、失败、完成。**禁止**自己猜进度。逐状态的页面反馈与提交锁边界表见 本文第 8.1.3.1 节。

**表单与文件纪律。** 三类回显各归其位：草稿、驳回、已提交。校验失败有 toast、无效项高亮、首个无效项聚焦。文件字段值只能由上传产生、全程只读卡片；展示 URL 经 `getViewUrl` 现取现用，下载只在用户点击处理器内调用；数据管理页**不能**用 `project.upload`；应用级文件用 `sdk.file` 与 `shared/ApplicationFileField`。**禁止**把当前路由写进 `sdk.storage`。

**构建与打磨。** 组件只从白名单取：Magic UI、Cult UI、KokonutUI、shadcn/ui；取来的组件适配项目 token、响应式、`prefers-reduced-motion`。每个动效有目的，过渡可被安全打断。**至少完成一轮真实渲染页修正**，桌面与移动各过主旅程和非正常态，查键盘导航、可见焦点、对比度、触控目标、长文本、溢出。对照《业务应用计划书》逐条核对，**测试每一个可交互的地方**。开发中发现设计做不了，回 G3 改设计并带更新后的原型重过确认，**禁止**静默改设计继续做。文案与注释一律中文。

本节是第 2 节各步骤点名的表格、契约、纪律清单与示例。它不是流程：进入与出口以第 1 节和第 5 节为准，**禁止**从本节推断阶段顺序。

### 8.1 前端实现


**正本是 `frontend/README.md` 与 `frontend/docs/business-ui-guide.md`；demo 只用于理解协议，第一规则禁止复用其页面结构、排版与视觉。**

#### 8.1.1 SDK 两层与保留件

- **App 层**（顶层 `sdk`）：`session`（实例上下文与权限，`permission='view'` 时置灰全部发起入口）、`projects`（归属项目集合，拉推成对）、`getProject` / `createProject`、`inbox`（跨项目待办）、`api`（自家后端通道）、`storage`（viewer × 实例隔离的界面意图，32 key / 512 KiB）、`ui.reservedAreas`（宿主浮层占用区，交互组件必须避开）、`theme`；
- **项目句柄层**：`business`（start / onCall / reply / onResult / 查询面）、`upload`、`file`、`chat`、`observe`、`info`、输入互斥；
- **保留件必经，不改不删**：`useProject` / `useProjectExecution` / `useProjectDraft` / `useInbox` / `useRuntimeUserFiles`、表单渲染、错误归一化、`FileField`、`MarkdownContent`、局部错误边界。表单预填（`useFormPrefill` / `getFormPrefill`）已下线，脚手架里若仍残留相关文件或文档，**不接入、不依赖**；表单 schema 的唯一真源是契约包 `forms/` 与 `getForms(formId)`；
- **一切平台调用经 SDK**：后端 API 走 `sdk.api.request`（path 纯路径、GET/DELETE 无 body、`query` 仅标量或一维数组、载荷 ≤ 256 KiB；`code !== 0` 必须给用户反馈，无静默失败、无自动重试）；项目文件走 `project.upload` 只传路径，应用级持久文件走 `sdk.file`（正本 `src/sdk/docs/application-file.md`）；**禁 fetch/XHR/axios（ESLint 硬禁）**。

#### 8.1.2 三个必备页面

- **首页**：根路由呈现欢迎页 / 业务展示页（可以就是看板），非脚手架占位、非空白、不直落深层表单；待办入口带 `useInbox().unreadCount` 角标；
- **项目列表页**：`sdk.projects.list` 打开/翻页/手动刷新时拉（禁轮询）+ `onStatusChange` 按 `projectId` 就地更新（禁止收推送就整页重拉）；行内有项目名、状态、更新时间；临时项目不入列表是设计使然；空列表引导去发起首个项目；
- **消息中心**：必经 `useInbox()`（合流、去重在 SDK；禁止页面自行订阅 `sdk.inbox` 手写状态机、禁止把待办写进 storage）；条目带归属项目、表单显示名、下发文案；点击导航到对应项目的应答状态并走对账链路；已读态只影响展示。

#### 8.1.3 四类业务页面

- **看板**：数据只来自后端统计 API；图表选型自由；每个数值可溯源（点开能看口径）；空数据引导态；跟随 `sdk.theme` 亮暗；
- **数据管理**：控件按列类型渲染，**只对 `editable:user` 列开放编辑**，`agent` 列只读并标注来源；提交走后端 CRUD，错误按信封 `code/msg` 呈现；批量与删除有确认；
- **业务发起（入口表单）**：必经 `useProjectDraft(draftKey)`（一个表单会话一个草稿句柄；`restoring` 期间禁提交）；入口表单按 `getForms(formId)` 的静态 schema 渲染，**没有预填**：用户自己的门店 / 账号等稳定信息若要少填，由应用后端在发起时拼进 `submit_data`（S3-2.4 的"时机 1"），不在表单里回填；文件字段经 `project.upload`（草稿句柄上首个 upload/start 懒创建临时项目，对 App 透明）；**提交必须等全部上传终态**（按钮禁用 + onFinish 内拦截）；`start()` → `accepted` 转正入列表、导航到项目页并写提交快照；`rejected` 原窗重填（保留草稿、复用同一提交记录）；`failed` 展示结构化错误不自动重试。复用已有项目 = 用户在下拉框显式选中（选项只来自后端项目列表）后在该项目句柄上 `start()`；
- **项目页**：项目状态与应答过渡按 §4.3.1 接入；阶段进度按业务事件（订阅一次、纯归约、live/backfill/replay 同构消费，禁轮询）；服务端调起表单到达 → 导航到可恢复的应答状态，按 `formId` 从契约区取 `inputSchema` 渲染、`arguments` 只做回显；**交付审阅页**按 `display` 五字段语义渲染（`headline` / `facts` / `notices` / `sections`，`schema_version` 不渲染），业务字段按 A1 出口设计呈现，**只在存在活动 Call 时渲染动作按钮**、只提交 `action_key`，`agent_gate` 只读；执行记录三级下钻（`list` → `get` → 三件套）每级只拉一次；已提交表单以 key-value 展示（label 用 schema title、选项值映射显示名、file 字段只读卡片，禁裸 JSON、禁裸路径）；Runtime 用户文件经 `useRuntimeUserFiles`（全量替换语义）。

##### 8.1.3.1 应答提交到运行的页面过渡

项目层通过 `useProject(projectId)` 持有一个句柄，并在同一层调用 `useProjectExecution(project)`；应答页、进度页与交付审阅页共享返回的 `projectStatus`、`pendingRun`、`submitting`、`workflowRuntimeId` 和 `reply`。实际应答入口使用 `execution.reply`（与原 SDK `reply` 签名相同），由保留件封装 `sdk.projects.onStatusChange` 的当前 `projectId` 筛选与启动过渡；不要绕过它另调 `project.business.reply` 后手写另一套过渡。**不得在每个子路由重新创建句柄或执行态保留件，也不得因 inbox / pending 列表变化重建它们**；消息中心只负责提醒与导航。`onCall` 监听也不得因子路由、`pathname` 或导航函数引用变化而重建，以免重新订阅触发 replay，把用户拉回旧表单。仅把辅助函数导出、未在实际页面接入，不算完成。

| 依据 | 页面反馈 | 提交与过渡边界 |
|---|---|---|
| 用户通过校验并点击应答提交 | 立即显示“正在提交”或同义反馈，禁重复提交 | 提交握手尚未完成；不能显示为已受理或已执行 |
| `reply()` 返回 `accepted`，当前项目尚未收到 `running` | 显示“已受理，准备继续” | 提交握手完成；启动过渡仍保留，不能恢复为可再次应答的旧表单 |
| 当前项目收到 `running` | 立即切到执行中的展示，不等业务事件、`getWorkflowRuntime` 或 `getRuntimeForms` 刷新 | 启动过渡结束；若业务结果仍未返回，提交锁仍保持，运行推送不代替第三次握手 |
| `rejected` / `failed` / 发送异常 | 分别恢复原窗重填或显示可读错误 | 结束本次启动过渡；不自动重试，不把其他项目或旧运行状态当成本次成功 |
| 权威终止状态或新的待处理 Call 到达 | 展示终止/错误，或进入新的应答状态 | 按权威事实结束启动过渡，不必等一个不会再来的 `running`，也不把它解释为运行成功；未完成的提交锁仍由业务结果或发送失败收束 |

项目执行态只可优先投影到 `execution.workflowRuntimeId` 对应的**本次应答 Runtime**，不能把同项目历史 Runtime 或已有终态改显示为 running；阶段进度、已提交内容和交付仍以各自权威数据为准。`pendingRun` 是短暂的界面过渡，**不能落为服务端业务事实或持久化运行结果**。同一项目切换应答页与进度页时继续消费原句柄的结果和状态，不能丢提交等待者、闪回旧表单或重复发出 `reply()`。真实离开项目或切换项目时按保留件生命周期清理；刷新后的恢复走服务端权威数据，不把内存过渡伪装成已恢复的运行。

#### 8.1.4 表单与文件的通用纪律

- 三类回显各归其位：草稿回显（`sdk.storage`，稳定 `draftId`）/ 驳回回显（`rejected.next.arguments` 原窗重填）/ 已提交回显（`getRuntimeForms` 权威源，提交快照兜底）；`accepted` 后删草稿写快照，`rejected` 保留草稿；
- 校验失败：视口顶部居中一条 toast，全部无效项高亮，首个无效项展开、滚入、聚焦；`form-submitting` 期间禁用全部写入口并持续显示原因；
- 文件字段：值只能由上传产生、全程只读卡片、上传中有状态、失败可删后重传、编辑态有替换/清除、多文件按契约数组提交；展示 URL 经 `getViewUrl` 现取现用；下载只经 `project.file.download` 且只在用户点击处理器内调用，禁自动/批量、禁自动重试；
- **Excel 等结构化上传的表单内预览**：文件本体照常上传得 path；预览/填入在浏览器端解析（表头 + 前几行），解析失败不阻断上传；
- **应用级文件库**（`sdk.file`，G3 第 8.10.2 节 勾选了才做）：`upload(file)` 不建项目、返回的 `path` 是唯一可写进 formdata / storage 的值；`list` 是不透明游标分页，只在打开、刷新、用户点“加载更多”时调（禁轮询）；`getViewUrl` 短时效、用完即弃；`download` 只在用户点击处理器内调。表单里用脚手架 `shared/ApplicationFileField`（上传 + 历史分页 + 图片/PDF 预览 + 下载 + 多选，值只存 path）；`shared/FileField` 仍是项目级、必须传项目句柄。选中的应用文件 path 直接写进 `business.start` / `reply` 的 formdata，宿主发帧前重新解析并登记给目标项目，解析失败会阻止启动而不会静默漏附件；源文件不因关联项目而移动。`permission='view'` 时上传入口必须禁用。capability（upload / file.read / file.download）由 `npm run check` 自动扫描；
- **可排序表单**：数组字段可做拖拽排序，提交按数组顺序；顺序语义以编排型 TPE `input_schema` 为准（G3 第 8.12.4 节）；
- 禁止把当前路由写进 `sdk.storage`（宿主已持久化 last_route）；禁止业务代码调 `sdk.notifyRoute` / `onHostNavigate`。

#### 8.1.5 构建与打磨（前端设计工作流后半程）

原型确认后，原型代码直接演进为正式实现，不重写。按顺序：

1. **用精选组件构建**（`components` 指南，MIT 白名单：Magic UI / Cult UI / KokonutUI / shadcn/ui；***不从 Aceternity、ReactBits、Vue Bits、Tremor、21st.dev 或名单外的库取代码***）：一屏至多一个主视觉件；取来的组件适配项目 token、响应式、内容、性能与 `prefers-reduced-motion`，不原样出厂；UI 库与样式方案自由（antd + Less CSS Modules 是默认可替换），限定业务样式作用域、支持宿主亮暗、避开 `reservedAreas`；
2. **打磨交互工艺**（`emil-design-eng` 指南）：每个动效有目的；高频操作即时；缓动时长跟手；按压/悬停/聚焦一致；过渡可被安全打断；凡引起内容变化的交互都有过程动画不闪烁跳变，`prefers-reduced-motion` 时去位移缩放、保留并缩短透明度过渡；
3. **真实渲染、走一遍、再修一轮**：跑起来用浏览器看真实渲染；桌面与移动各过主旅程和非正常态；查键盘导航、可见焦点、对比度、触控目标、长文本、溢出；先修结构再修装饰；***至少完成一轮渲染页修正，不许只看源码就宣布完成***；
4. **对照设计文档逐条核对**模块划分、页面结构、交互流转、视觉层级，不一致改到一致；**测试每一个可交互的地方**——能点、能填、能拖、能切换的都实际操作一遍；
5. **冲突处理**：开发中发现设计做不了（SDK 拿不到的数据、编排型 TPE 不发的事件）→ 回 A1 改设计、带更新后的原型重过确认；***禁止静默改设计继续往下做***；
6. 冲突规则：用户要求与仓库约束 > 一切 guidance；产品清晰与任务完成 > 视觉新奇；无障碍与减少动效 > 动画偏好；本节白名单 > guidance 目录里的更大清单。

文案与注释一律中文；组件单一职责，超 ~200 行考虑拆分。

### 8.2 本地测试


正本：`frontend/README.md` §五「完成定义与自测矩阵」（唯一权威）与 `frontend/docs/dev-host-testing.md`。顺序：

1. 后端 `npm test` 全绿（含信封契约自检）；
2. `./run-dev.sh start` 真跑：Direct Mock 下走通 **自测矩阵 A–E 组**（三面 / 入口表单两段式 / 项目详情 / api 通道与路由 / 旗标态 `?mock=view|preview|permission-cycle|storage-off|attention|frames-off`，以 `frontend/README.md` §五自测矩阵为准）——mock 验证的是界面状态机完备性，**mock 跑通 ≠ 功能正确**；**Direct Mock 下 `sdk.api.request` 全部在内存 mock 里应答，根本不会打本地后端**（vite 没有 `/api` 代理），所以"本地界面数据展示正常"**不能**作为前后端联调证据；后端只能靠 `npm test` 与浏览器直连 `:8000`（本地才开 CORS）单独验；真实链路（宿主服务端转发、身份注入、真实 schema）只在上传后的远端调试阶段（A4）验证；需要宿主主动事件或 Bridge 证据的场景用 Dev Host Mock（:5176）；
3. **mock 可测边界是封闭白名单**：业务事件真实语义、真实业务路线行为、真实文件 URL、开发者后端真实行为等**不可 mock**——不为了可测而改 mock/固定层、不自造桩、不降断言，在完成回复中标注“留待远端调试阶段验证”；
4. **Playwright 动态验收门**：按真实页面、`schema/` 与路由动态编写用例，覆盖表**必须包含编辑场景（写权校验、误删确认、编辑后看板刷新）与看板场景（空数据、分页）**，禁止复制 demo 字段或选择器；断言谓词先证明自己能失败；这套用例在 G7 第 8.1 节 要对着预部署部署物整套重跑，所以从第一条起就不绑 mock 数据的具体值——换成真数据仍成立；用例名带《业务应用计划书》⑤ / ⑦ / ⑨ 的条目编号，A4 才能对账“确认过的功能都测了”；
5. `cd frontend && npm run check` 通过（type-check + lint + capabilities/packs 校验）；交付前 `npm run check:release`（加示例残留检测：示例目录、演示包契约、起始页占位、`packs` 未声明真实场景包，任一残留即失败）。
6. 业务页面不写单元测试；`npm test`/`vitest` 跑的是脚手架自身的测试，与 App 完成定义无关，不需要运行。

前端校验项与后端校验项转入结果检查表（状态 `pending`，A4 用预部署真实数据闭合）。

### 8.4 术语速查


| 术语 | 人话 |
|---|---|
| 业务应用 | 前端 + 专属后端 + 每用户一份 schema，打进一个镜像一个 Pod；平台里的一级实体，一个实例管 N 个项目，用户的 SaaS 工作台 |
| 项目 | 业务应用之下的一层：用户的一次计划选择，一次业务路线运行及其表单、消息、文件、交付都装在项目里；由用户在应用里**创建**（表单提交时两段式建项目）或**复用**（下拉框选已有项目）；应用经 `sdk.projects` 拿到本实例名下全部项目（G3 第 8.10.1 节） |
| 《业务应用计划书》 | A1 的交付物：一份 MD，含功能清单、每页截图展示、后端功能阐述、自动化测试计划；开发者确认后才进 A2/A3，之后按它干、不再问（G3 第 8.13 节） |
| 应用级文件 / 项目文件 | `sdk.file`：不依赖项目、跨项目复用的持久文件（资料库）；`project.upload` + `project.file`：属于某个项目的文件。两者并存，表单值都只存 workspace 路径 |
| business_ui | 业务应用的发布单位：独立资产（家族 + 版本），挂 1 个场景包 + ≤1 个业务应用数据集模板；create → 上传 deploy 源码包 → finalize 上线（A4/A5） |
| 业务应用数据集 | 应用的后端数据库：用户点开应用时从模板 copy 出的专属 PG schema，存用户记载、交互历史、交付与流转数据；应用后端直连 + 项目内 agent 经业务应用数据集 FA 访问同一份 |
| 业务应用数据集模板 | 开发期定稿的表结构模板资产（含逐列声明与审计字段）；用户首次打开应用时从它 copy 出业务应用数据集 |
| 业务应用数据集 FA | 平台级 FastAgent（cn-qa 现名 `Business_app_fastagent`，随 `business_app_dataset` 工具集上线）：场景包编排型 TPE 经它的 HTTP 工具读写业务应用数据集，不进沙箱（A3 第 3 节三件事实）。**这是给项目内 agent 用的通道**；应用自己的前后端读写走后端直连 `buiTable()`（A3 第 3 节） |
| `buiTable('表名')` | 后端引用自己 schema 里表的唯一写法，从 `DATASETS_MANIFEST` 解析真名（`bui_{data_uid}`）；不写死 schema 名、不用 handle |
| 三个必备页面 | 首页 / 项目列表页 / 消息中心——脚手架硬约束，只约束存在且可达，不约束形态 |
| 可编辑性声明 | PG 列注释里的 `[editable:user\|agent\|system]` 前缀，谁能写这列的唯一正本 |
| 创建态 / 进行态 | 应用页 = 发起一切；项目页 = 只看进度和回表单 |
| 生产回流 / 编辑回流 | 场景包产出写库 / 用户手动改库——两条写入通道，共治规则见约束 9 |
| 信封 | 后端响应固定 `{code, msg, data}`；`msg` 不是 `message`，`data` 非 null 对象 |
