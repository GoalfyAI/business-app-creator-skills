# G7 预发布与交付

本阶段的目的是**保证现在交付的版本就是验过的版本**。这是整套业务应用的总出口：对最终预部署物跑完整验收集，核对版本绑定与迁移，执行已授权的上线动作，反读入口，交付报告，结单。上线后的修订、回滚、下线、删除也在本阶段。闸门码表与版本工具见 本文第 8 节。

## 1. 进入依据

G6 使用闭环通过；发布范围确定；能力容器、应用、数据模板三者的版本关系准确；开发中的增量复验**不代替**本阶段的门。

## 2. 本阶段建设

### 2.1 自动化测试门

对最终预部署物跑三类用例，**三类全绿才进入后续步骤**，任一失败回 G6 修、重新打包部署、**整套重跑**：

1. **与开发者确认过的功能**：《业务应用计划书》第 ⑤ 章每个勾选功能；第 ⑦ 章每页每个状态，空态、只读、出错、加载、`form-submitting`；孤岛与返回入口。用例名带第 ⑨ 章条目编号，指向 `business_ui_manage(get)` 反读的预部署入口，登录态用开发者提供的测试账号。
2. **业务路线运作**：每条可发起路线从业务发起页提交，到项目受理、业务事件进度、运行中表单三次握手到业务确认、交付审阅动作、生产回流入库；在已有项目上复用再发起一次。后端侧用 `manage_goalfymax_project(run, submit_data)` 直跑同一张表单，`get_project_execution_logs` 取证两边一致。
3. **数据增删改查**：每张模板表经后端接口增、查、改、删；写权矩阵，`agent` 与 `system` 列被拒且信封 `code ≥ 1000`、界面有可读 `msg`；同一 `X-Goalfy-Business-Request-Id` 重放不产生第二行；`row_version` 冲突后写方被拒；来源标记落库；删除语义按计划书。落库结果直接查库核对。

纪律：用专用测试用户实例跑，测完清理自己写的行；用例不绑 mock 字段与选择器；报告摘要与失败清单落工单 `autotest`，写清跑了几条、过了几条、覆盖了哪些条目、盲区是什么；每次重新 deploy 都重跑。

### 2.2 预部署环境验收

1. `business_ui_manage(get)` 与 `business_ui_bundle(status)` 反读部署终态，证据入工单。
2. 真环境把 SaaS 链路完整走一遍：发起、生产、回流、编辑、看板刷新。本阶段独有的是应用前端加 SDK 这一层，路线运行时本身已在 G5 验过，不重复证明。
3. 按应用验收检查清单**逐条执行**，每条给判定与依据。
4. 结果检查表用预部署环境的**真实数据**闭合，mock 证据只能作为过程记录。
5. **真联调与授权边界三条证据**落 `integration`：请求确实经宿主转发到达本后端，后端日志能对上本次的 `X-Goalfy-Business-Request-Id` 且 `X-Goalfy-Context` 解出的 `user_id` 是测试账号；`view` 权限的查看者打写接口被本后端以业务码拒绝且界面有可读 `msg`；生产态响应无 `Access-Control-Allow-Origin`。
6. 汇总证据：真实产物、端到端操作、错误恢复、权限、耗时与费用。必要时做已授权的受控试用。

### 2.3 核对版本绑定与迁移

能力容器、应用、数据模板版本一致，最近变更没有使已有证据失效。模板有破坏性变更时 `extract` 已随带 `migration_script`，定版会在临时库真跑一遍彩排；存量用户实例沿版本链只往前升，回滚钉回更老的模板版本会被拒，要回退就把旧结构重新抽成新版本。换模板家族等于换库，需要新库就新建业务应用。升级后已有用户数据怎么处理是产品决策，进确认。

### 2.4 分清四种动作，只执行已授权的

1. **能力容器上线**：G5 未做的在此执行，`finalize_asset_version_online(asset_type="scenario_pack")`。
2. **应用部署**：源码包 deploy 到 `success`，已在 2.1 前完成。
3. **应用定稿上线**：`business_ui_manage(action="finalize", draft_asset_id=...)`，平台做闭包校验、模板升级链校验、迁移彩排；工具闸门不检查自动化测试，凭工单 `autotest` 记录自证，没有记录或有未修复失败**不 finalize**。被拒时按错误码处置，表见 本文第 8.6 节。上线成功后**必须反读** `business_ui_manage(action="resolve")` 取 `entry_url` 与挂载身份；resolve 报没有上线版本说明 finalize 未生效，**不得**宣称已上线。定版时能力容器引用钉到的具体版本记入工单与交付报告。
4. **目录发布**：在发布管理页发布一版，上线只影响开发者自测，不推给使用者；已发布的应用不能直接下线。

上线是外部状态变更，开发者明确授权后才执行；未授权的自动通知、跨应用操作、公共策略更新**不得**随发布附带启用。

### 2.5 交付报告与结单

交付报告结论先行，固定包含：应用名称与上线版本、`entry_url`、依赖的能力容器版本、数据模板与版本；能力容器名称、标识与状态；解决的业务问题与价值假设原文；里程碑与路线；核心资产与能力矩阵终版；分工理由；四类页面清单与接口清单；验证证据层级与真机运行结果；效果结论，结果检查表 `passed` 与 `waived` 数量及理由、问题单处置摘要、开发者业务标准的符合情况；修订类任务与上一版本的配置差异摘要，来自 `compare_asset_versions` 按业务语言归纳；运行成本观察，来自运行记录，没有可靠数字写"未统计"；能力缺口；剩余风险与盲区；运行边界、遗留事项、诊断路径、恢复方案；观察指标基线，固定为首次可用交付耗时、用户投入分钟数、纠错与返工次数、采用比例、确认率、每次成功费用；客户初始化清单。报告里的计数、百分比、日期、排名**必须**逐条对照原始证据复核。运行语义说明：用户首次打开时按模板 copy 出自己的 schema 并部署实例，无流量实例会被缩容，首次访问冷启动稍慢。

结单：`task_manager(insert)` 记录最终资产、验证层级、全真决定和盲区；确认结果检查表快照全绿、三张表快照已回写；确认线上实例已按钉的模板版本注库后 `dataset_template_workspace(close, data_uid)` 收掉工作集；`task_manager(complete)`。有业务路线时核对响应里 `completion_evidence.route_bubbles` 与发布范围逐条一致，返回 `WORKFLOW_TASK_ROUTE_BUBBLE_EVIDENCE_REQUIRED` 时按其中的路线状态补跑或修复同一资产，**禁止**删标签、改文字或另开工单绕过。

### 2.6 上线后的操作

- **修订**：已上线版本不可直接改，`update` 自动派生新草稿或先 `ensure_draft`；改元信息经 `update`，改源码重新上传部署；每次修订走完 G6 与本阶段验收再 `finalize`，**不存在小改免验**；改挂载属于契约变更，先回 G3 做变更影响检查；修订前后用 `compare_asset_versions` 取配置差异。
- **回滚**：`rollback_asset_version(asset_type="business_ui", asset_id, version_id)` 以历史版本克隆出新的 testing 草稿，反读挂载与源码包引用，走一遍验收再 `finalize`；回滚**必须**开发者确认；回滚应用不等于数据库可降级。
- **下线**：`business_ui_manage(action="offline")` 家族下线，拆容器，保留库、源码包、版本记录，可重新上线；已发布到目录的先取消发布；**必须**开发者确认，说清用户失去入口但数据不丢。
- **删除**：`delete` 永久删除全部实例、Pod、Schema、项目文件和源码包，不可恢复；**必须**开发者明确授权并显式传 `confirm_permanent_delete=true`。停用在用的应用**不用删除**，用下线。
- **用户反馈**：交付后查询使用者反馈、生成带图报告或按已采纳问题修改，按 `references/用户反馈报告.md` 的流程执行，调用 `business_ui_feedback` 只读工具。

## 3. 给开发者看什么

默认展示**交付核对单**：本次承诺、实际可用能力、当前版本、通过证据、未覆盖范围、发布影响。每个阻断项直接可见，**禁止**埋进日志。

## 4. 要确认哪些边界

发布对象与人群；风险接受范围；上线授权；费用边界；试用退出条件；故障处理责任；存量用户数据的迁移处置。

## 5. 门禁 Checklist

- `G7-01` 交付范围内的 G 门禁有对应 U 用例与专业验收证据；每项注明目标版本、适用范围、失败或阻断或偏差。覆盖矩阵中存在编号**不代表**业务已验证。
- `G7-02` 最终部署版本完成全部适用行为用例、三类自动化测试、关键组合旅程：首次发起、必要补充、离开返回、修订、确认、再次使用。
- `G7-03` 应用、能力容器、工具依赖、数据模板版本一致；最近变更没有使已有证据失效。
- `G7-04` 迁移与恢复策略有验证依据；恢复不静默丢用户数据；**禁止**把删除当停用。
- `G7-05` 发布动作有授权；上线后反读入口与版本成立才称已上线。部署成功**不等于**用户已可用。
- `G7-06` 效果回传关联、下一轮使用、受控改进对照分别有结论；没有长期样本**不得**宣称业务收益提高。U7、U8 仅在纳入范围且实测通过时交付。对应 U6-05、U6-06。

## 6. 证据与结论

产出交付清单、最终测试报告、版本清单、上线反读、迁移与恢复记录、后续问题入口。落工单标签 `autotest`、`integration`、`delivery_report`，然后结单。

## 7. 失败回退

失败回问题所属阶段。**禁止**以关工单为目标放宽标准。交付后的真实问题与效果证据，按 本文第 8 节 归因，确定影响范围后重入对应阶段。

## 8. 细则

本节是第 2 节各步骤点名的表格、契约、纪律清单与示例。它不是流程：进入与出口以第 1 节和第 5 节为准，**禁止**从本节推断阶段顺序。

### 8.1 自动化测试门（预部署之后、上线之前，硬门）


deploy 到 `success` 只证明部署物起来了。***上线前必须对这份预部署部署物跑一遍自动化测试，三类全绿才进入第 5 节的真环境验收与第 6 节出口；任一失败回 A3 修、重新打包部署、整套重跑。*** 测试对象是预部署出来的应用（真后端、真模板 schema、真宿主），本地 mock 与 dev-host 的结果只算过程记录。

#### 8.1.1 三类内容，缺一不可

| 类 | 测什么 | 用例从哪来 | 怎么跑 |
|---|---|---|---|
| **① 与开发者确认过的功能** | 《业务应用计划书》⑤ 功能清单里每个勾选功能；⑦ 每页每个状态（空态 / 只读 `view` / 出错 / 加载 / `form-submitting`）；孤岛与返回入口 | 计划书 ⑨ 的编号条目：一个功能至少一条用例，用例名带条目编号 | G6 第 8.2 节 第 4 条那套 Playwright 页面专属用例，指向预部署入口（`business_ui_manage(get)` 反读的地址），登录态用开发者提供的测试账号 |
| **② 工作流业务路线运作** | 每条可发起路线：业务发起页提交 → 项目创建并受理（`accepted`，临时项目转正入列表）→ 业务事件进度 → 运行中表单三次握手（到业务确认才结束）→ 交付审阅动作 → 生产回流入库（`agent` 列出现新值、来源 `generated`）；在已有项目上**复用**再发起一次 | 契约基线表（G3 第 8.11 节）：几条路线、哪些中途表单、什么审阅形态 | 前端 Playwright 走真实提交；后端侧对照用第 5 节第 2 条的直跑通道（`manage_goalfymax_project(run, submit_data)`）跑同一张表单，`get_project_execution_logs` 取证两边一致 |
| **③ 数据增删改查** | 每张模板表经后端接口 增 / 查（分页）/ 改 / 删；写权矩阵（`editable:user` 列可写，`agent` / `system` 列被拒且信封 `code ≥ 1000`、界面有可读 `msg`）；同一 `X-Goalfy-Business-Request-Id` 重放不产生第二行；`row_version` 冲突后写方被拒；来源标记落库；删除语义按计划书（软删 / 二次确认） | 模板 `inspect` 反读的表与列注释（A2） | 后端接口用例打预部署地址，或经数据管理页 Playwright 驱动；核对落库结果直接查库：预部署容器连的是开发者自己的库——A2 工作集还开着时就是工作集 schema，用 `dataset_template_workspace(connect)` 拿连接串查；工作集已 close 时 Hub 按钉的模板给开发者建了实例，经后端只读接口核对（`dataset_read` 只读长期数据集，读不到业务应用数据集） |

#### 8.1.2 纪律

- 用专用测试用户实例跑，测完清理自己写的行；不碰开发者的真实数据；
- 用例不绑 mock 字段与选择器，断言谓词先证明能失败（G6 第 8.2 节）；
- 报告（Playwright HTML / JUnit + 后端测试输出）的摘要与失败清单落工单 checkpoint `autotest`：跑了几条、过了几条、覆盖了计划书哪些条目、盲区是什么；
- 结果检查表的前端校验项与后端校验项由这三类用例闭合，仍不允许用 mock 置 `passed`；
- 修复后**整套重跑**，不做“只重跑失败那条”；每次重新 deploy 都重跑。

#### 8.1.3 应答提交到运行的时序验收

中途表单和有应答动作的交付审阅都必须覆盖下列时序，断言**实际页面变化和提交锁**，不能只等最终成功。A3 先在受控测试宿主中验证延迟与乱序；A4 再对当前预部署部署物在真实宿主点击应答，记录点击、首次反馈、业务结果、当前项目 `running` 与页面进入执行态的时间线。受控测试证据不代替真实宿主证据，也不得为测试修改真实项目的状态。

| 场景 | 必须观察到 |
|---|---|
| 点击后第三次握手尚未返回 | 下一次页面渲染立即出现提交反馈；重复点击/回车不产生第二次提交 |
| `accepted` 已到、`running` 延后 | 持续显示“已受理，准备继续”，不解除为可再次应答的旧表单 |
| `running` 先于 `accepted` | 立即展示执行中；未完成的提交锁仍在，业务结果到达后才结束握手 |
| `running` 已到，业务事件、Runtime / 已提交表单查询仍延迟或返回旧快照 | 页面已经是执行态，不等待明细查询或阶段事件，也不被旧 `waiting_user` 展示覆盖；阶段进度不伪造 |
| 查看同项目历史 Runtime 或已经到达终态的 Runtime | 本次应答的执行投影不覆盖这些记录，只作用于保留件返回的 `workflowRuntimeId` 对应的本次运行 |
| 其他项目推送或当前项目 `created` 等非终止状态推送 | 不错误结束本次启动过渡，不把其他项目状态显示为当前项目进度；权威终止与新 Call 按下方专门用例处理 |
| `rejected`、`failed`、发送失败 | 原窗可修正或错误可见；启动过渡结束，没有自动重试和残留的“正在启动” |
| 权威终止状态或新的待处理 Call 先于 `running` 到达 | 按权威事实结束启动过渡并显示对应状态，不无限等 `running`，不把终止或待处理解释为运行成功；提交锁仍独立收束 |
| 提交后在同项目应答页、进度页之间切换；同时 inbox 更新 | 句柄与执行态保留件保持同一实例，提交结果仍可配对；不重发应答、不丢过渡、不闪回旧表单 |

报告需分别写清“辅助函数已加入”“实际页面已接入”“部署物已验证”的证据，前一项不能替代后一项。

### 8.2 预部署环境验收


1. `business_ui_manage(get)` 与 `status` 反读部署终态，证据入工单；
2. 真环境把 **SaaS 链路闭环**完整走一遍：发起 → 生产 → 回流 → 编辑 → 看板刷新。其中本线独有的是**应用前端 + SDK 这一层**：入口表单在页面上提交、`chat.start + metadata.submit_data` 打包、运行中表单三次握手到业务确认、审阅动作、产出回流入库——路线运行时本身已在场景包 S4 第四层用 `submit_data` 直跑验过，这里不重复证明，只证明应用把它接对了。应用前端未就绪或要单测契约时，可用 `manage_goalfymax_project(action="run", submit_data={business_id, orchestration_id, form_id, formdata}, workspace_files[].formdata_pointer=...)` **直跑表单入口**（不经 SA，由确定性的编排型 TPE 直接执行；文件先经 `file_to_url(tool_test_fixture)` 上传，`formdata_pointer` 指向 formdata 里的空占位字段）；
3. 按 [应用验收检查清单](../checklists/应用验收检查清单.md) **逐条执行**（每条给判定与依据）；
4. 结果检查表用预部署环境的**真实数据**闭合——mock 证据只能作为过程记录，不得置 `passed`；
5. **前后端真联调与授权边界取证**（约束 5）：本地 Direct Mock 不打本地后端，"本地界面数据展示正常"不是联调证据。联调成立的证据是：① 请求确实经宿主服务端转发到达本后端——后端日志里能对上前端本次的 `X-Goalfy-Business-Request-Id`，且 `X-Goalfy-Context` 解出的 `user_id` 是测试账号；② 用 `view` 权限的查看者（非 owner 的测试账号，或 `?mock=view` 之外的真环境协作身份）打写接口，被本后端以业务码 `≥1000` 拒绝且界面有可读 `msg`——写权限是后端自己判的，宿主不兜底；③ 生产态后端响应无 `Access-Control-Allow-Origin`。三条证据入工单 checkpoint `integration`。

### 8.3 交付报告与工单收尾


交付前逐一核对：核心文件真实存在、路径在允许范围内、来源链与上游工具输出或开发者提供的文件一致。

报告包含计数、百分比、日期范围、排名或"来源—内容"配对时，**必须**逐条对照原始证据复核。无法证明的数字**必须**删除、修正或明确标为假设（约束 2）。

交付报告结论先行，包含：

- 场景包名称、标识和当前状态
- 解决的业务问题
- 里程碑与候选路线
- 核心资产与能力
- 验证证据层级
- 真机运行结果或跳过决定
- 效果结论：结果检查表通过情况（N 条 `passed` / M 条 `waived` 及理由）、问题单处置摘要（fail 修复记录、advice 采纳情况）、开发者业务标准（样例选择确定的验收判定）的符合情况
- 修订类任务：与上一 live 版本的配置差异摘要（`compare_asset_versions` 的结果按业务语言归纳，不贴原始 diff）
- 运行成本观察：全真运行的 FastAgent 调用次数、积分消耗与耗时（取自运行记录；没有可靠数字就写"未统计"，不估算）
- 能力缺口
- 剩余盲区和后续条件

### 8.4 结单


用 `task_manager(insert)` 记录最终资产、验证层级、全真决定和盲区，再 `task_manager(complete)`。有业务路线时，必须检查结单响应中的 `completion_evidence.route_bubbles` 与发布范围逐条一致；返回 `WORKFLOW_TASK_ROUTE_BUBBLE_EVIDENCE_REQUIRED` 时，按其中的路线状态补跑或修复同一资产，禁止删标签、改文字或另开工单绕过。**禁止**用完整日志、凭证或临时地址充当工单交付内容。

结单前同时确认结果检查表快照（`result_checklist_snapshot`）为最新且全绿；存在 `pending` 或未 waive 的 fail 时回 S4 处理后再结单。

### 8.5 版本出口


上线之后的版本操作（详见 [场景包版本体系与发布逻辑](../references/场景包版本体系与发布逻辑.md)）：

| 动作 | 工具 | 纪律 |
|---|---|---|
| **看家族** | `list_asset_versions` | 任何版本操作前先看清哪一行是现役 live、有没有搁浅草稿；`items[].id` 是后续回滚/比较要用的版本事实 id |
| **继续修订** | `ensure_editable_asset_draft` | 回 G1 第 8.6 节，走完整制作与验证循环 |
| **比较两版本** | `compare_asset_versions(base_version_id, target_version_id)` | 修订验收与交付报告的配置差异证据；它比的是**配置事实**，不是运行效果——效果仍靠结果检查表回归 |
| **作废草稿** | `abandon_asset_version_draft` | 只能作废未上线且未被引用的草稿；作废前**必须** `get_asset_usage_impact` 看影响面并告知开发者 |
| **回滚** | `rollback_asset_version(version_id)` | 以历史版本内容**克隆出新的 testing 草稿**（不修改任何历史行）→ 按 S4 验收 → `finalize` 上线。回滚属于外部状态变更，**必须**开发者确认（约束 6）；回滚后仍要处理引用方（S2 的 `mounted_by_stale` 清单同样适用） |

这套版本工具对六类资产（`scenario_pack` / `tpe` / `toolset` / `fast_agent` / `tool_group` / `business_ui`）同构；业务应用侧的用法见 app-creator A5。

### 8.6 上线（finalize）


把验收通过的草稿定版上线，交付报告，结单；已上线应用的修订、回滚、下线、删除也在本节。上线是高危动作：**开发者明确授权后才执行**（拍板节点）。

`business_ui_manage(action="finalize", draft_asset_id=...)`（等价于 `finalize_asset_version_online(asset_type="business_ui")`）把草稿定版上线：闭包校验 + 模板升级链校验 + 迁移脚本彩排。**前提**：本文第 8.1 节 自动化测试门三类全绿——工具闸门不检查这一条，凭工单 `autotest` 记录自证；没有记录或有未修复的失败，不 finalize。上线闸门用三个稳定错误码拒绝未就绪的定版，处置对照：

| 错误码 | 含义 | 处置 |
|---|---|---|
| `BUSINESS_UI_NO_BUNDLE` | 还没有源码包 | 回 G5 第 8.9 节：上传并 deploy 后再 finalize |
| `BUSINESS_UI_NOT_DEPLOYED` | 源码包没有成功构建发布 | `deploy` 到终态 `success` 再 finalize |
| `BUSINESS_UI_TEMPLATE_REQUIRED` | 带代码包的业务应用定版没有挂业务应用数据集模板 | 回 A2 建表并 `extract` 出模板版本 → `business_ui_manage(update, dataset_template_id, dataset_template_version)` 挂到草稿 → 重新 `deploy`（模板进指纹）→ finalize |
| `BUSINESS_UI_NOT_RELEASED`（`resolve` 时返回，不是 finalize） | 上线了但从未发布，使用者打开的是"已发布"版本所以打不开 | 在发布管理页发布一版；上线只影响开发者自测，不会推给使用者 |
| `BUSINESS_UI_CONTRACT_OUTDATED` | 挂载场景包的编排型 TPE 契约已变化 | 重新 `deploy`（吸收新契约）后再 finalize；契约变化波及页面时先回 A1 变更检查 |
| `BUSINESS_UI_TEMPLATE_SWITCHED` | 换绑到另一个模板家族（等于换库） | 不允许；需要新库就新建业务应用 |
| `BUSINESS_UI_TEMPLATE_UPGRADE_PATH_BROKEN` | 模板升级链缺迁移脚本 | 回 A2：破坏性变更的 `extract` 随带 `migration_script` |
| `BUSINESS_UI_TEMPLATE_REGRESSION` | 回滚钉回了更老的模板版本 | 没有降级：把旧结构重新抽成一个新版本再挂 |
| `BUSINESS_UI_UPGRADE_REHEARSAL_FAILED` | 迁移脚本在临时库彩排失败 | 按返回的错误修脚本，重新 `extract` |

上线成功后**必须反读**：`business_ui_manage(action="resolve")` 返回消费者视角的 `entry_url` 与挂载场景包身份——这是上线证据；resolve 报"还没有上线版本"说明 finalize 未生效，不得宣称已上线。定版时场景包引用钉到当时具体版本，**把该版本号记入工单与交付报告**。

### 8.7 修订已上线版本


已上线版本不可直接改：`update` 会自动派生新草稿（或先 `ensure_draft` 显式出草稿）→ 修改（改元信息经 update；改源码经 G5 第 8.9 节重新上传部署）→ `finalize` 新草稿。两条纪律：

- 改挂载（场景包或业务应用数据集模板版本）属于**契约变更**，先回 A1 做变更影响检查再实现；换模板版本前先在 A2 `extract` 出新版本；
- 每次修订走完 A4 验收再 finalize，不存在"小改免验"；
- 修订前后用 `compare_asset_versions(asset_type="business_ui", base_version_id, target_version_id)` 取配置差异（版本事实 id 来自 `list_asset_versions`），作为验收与交付报告的证据——它比的是配置，页面行为仍靠 A4 真环境验收。

### 8.8 回滚


线上版本出了问题要回到历史版本：`rollback_asset_version(asset_type="business_ui", asset_id, version_id=<list_asset_versions 里目标版本的 id>)`——以该历史版本的内容**克隆出一个新的 testing 草稿**，不修改任何历史行；然后 `business_ui_manage(get)` 反读草稿的挂载与源码包引用是否随版本恢复（未恢复的按 G5 第 8.9 节重新 deploy），走一遍 A4 验收，再 `finalize` 上线。回滚是外部状态变更，**必须**开发者确认（约束 6）；回滚后仍要按第 1 节反读 `entry_url`。

### 8.9 删除（约束 6 高危）


`delete` **永久删除**界面及其全部实例、Pod、Schema、项目文件和源码包，不可恢复。必须开发者明确授权，且显式传 `confirm_permanent_delete=true`。返回语义：

- `deleting`：资源仍在收口，重复 `delete` 幂等推进并查询最新状态；
- `cleanup_failed`：收口失败但删除围栏仍生效，修复下游后重复 `delete` 重试。

停用一个在用的应用**不用删除**，用第 5 节的下线。

### 8.10 下线（offline，可逆）


`business_ui_manage(action="offline", business_ui_id=<家族 ID 或任一版本行 ID>)`：**家族下线**——拆掉全部容器（每个版本行的开发者容器 + 每个用户的实例容器），**用户库、源码包、版本记录全部保留**，家族标为未上线（用户点开与目录进入都被拒）。重新上线 = 对当前版本重新 `deploy` 后 `finalize`（G5 第 8.9 节 → 本文第 1 节）。

- 下线是外部状态变更，**必须**开发者确认（约束 6）；确认时说清用户会失去入口但数据不丢；
- `BUSINESS_UI_RELEASED_CANNOT_OFFLINE`：已发布到目录的应用不能直接下线，先在发布管理页取消发布（unpublish）再 `offline`——这就是总入口约束 7 "发布版不能下线"的确切含义；
- `BUSINESS_UI_OFFLINE_INCOMPLETE`：家族已标为未上线但部分容器没拆掉（`failures` 里有 user_id / deploy_id）——修复 p2s 后重复 `offline` 幂等重试；
- 下线后反读 `business_ui_manage(get)` 确认状态，记入工单。

### 8.11 交付报告与结单


报告**结论先行**，包含：

- 应用名称与上线版本、`entry_url`、依赖的场景包版本（定版钉住的那个）、业务应用数据集模板与版本；
- 四类页面清单与接口清单；
- 验收结果：清单通过情况、遗留问题、明说的盲区（未验证什么）;
- 运行语义说明（开发者需要知道的平台行为）：用户首次打开时按模板 copy 出该用户的 schema 并部署实例；无流量实例会被静默缩容，首次访问冷启动稍慢。

结单前：结果检查表快照全绿、两张表最新快照已回写工单；确认线上实例已改为按钉的模板版本注库后，`dataset_template_workspace(close, data_uid)` 收掉 A2 开的工作集——它一路撑到这里才没有保留价值。

### 8.12 诊断已有场景包


诊断已有场景包、落实修复与回归、维护已上线场景包、异常与恢复。本节从总入口 4.1 独立进入，不属于创建主干。

#### 8.12.1 确定对象与范围

了解开发者的问题或优化目标：开发者主动描述的症状、提供的项目标识（按 G2 第 8.1.1 节三层分析）、或只是想全面检查一遍。

用 `list_assets` 列出开发者有权维护的场景包，开发者选定后用 `get_asset` 获取全貌。确认范围是**全量诊断**还是**聚焦诊断**。

#### 8.12.2 逐层检查维度

按场景包 → 任务点与编排型 TPE → 工具集 → FastAgent → 工具组的顺序逐层分析。每层先用 `get_diagnosis_doc` 取对应规范，再对照检查。

**场景包层**：名称与描述是否表达清楚业务边界；`apc_skill` 是否覆盖已确认的里程碑与路线、是否达到瓶颈所需颗粒度；Skill 文件索引是否建立；预加载与动态工具集分配是否合理；信息是否放错层级；有没有硬编码数字 ID 或复制的业务路线图。

**任务点与编排型 TPE 层**：SystemAgent 能否仅凭名称和描述正确路由；与其他任务点边界是否重叠；输入要求、输出格式、提示词或脚本、模型、文件、依赖、交付是否闭合；这个职责是否真的需要这种执行形态。

**工具集层**：描述是否足以支撑动态加载判断；使用指南是否说明真实工具与 FastAgent 的搭配；成员是否属于同一能力域；引用的工具是否真实存在于该工具集中。

**FastAgent 层**：调用时机是否清晰；提示词是否包含角色、执行流程、工具策略、输出要求；工具选择是否支撑其任务——环节内要用的工具是否都挂给了它（不挂工具只做文字变换、或一个环节被拆成多个 FastAgent 串在脚本里，都是粒度误用，见 S2-4.4）；执行所需的知识文件是否挂在其名下并被提示词索引——场景包的 Skill 文件对 FastAgent 不可见，只挂在场景包下等于没挂（S3-8.2 可见性边界）；模型与轮次是否匹配复杂度；输入定义的字段是否有业务语义、必填选填是否区分；是否本该由 SystemAgent 直接执行。

**工具组层**：描述是否包含路由逻辑（何时用、何时不用）和防御性约束；参数约束是否充分。

**产出效果层**：拉取目标包的真实运行记录，扫描结构性底线违约（拒绝无理由、自相矛盾、承诺未兑现——违约即质量失败，即使运行状态为 success）；持有历史结果检查表快照时，对当前版本重跑回归（正例产出是否仍一致、反例是否仍被正确处理）。前五层查的是"搭得对不对"，本层查的是"产出行不行"——"效果不好""产出无效"这类症状**优先**从本层入手，再回头到配置层找根因。

逐层都要显式调用 `get_asset`（用法见 G2 第 8.1.3 节）。

#### 8.12.3 先广后深

**全量诊断的含义是每层都扫到，不是每个底层资产都无差别深挖。**

- 场景包层、任务点与编排型 TPE 层：**全部检查**（数量少、影响大）
- 工具集层：**全部**检查描述和使用指南；内部 FastAgent 与工具**只在**上层发现线索、开发者反馈指向、或使用指南明确引用时才下钻
- FastAgent 层、工具组层：**只查**被上层标记或开发者反馈相关的

#### 8.12.4 分级报告

按严重程度分级：

| 级别 | 含义 | 处理 |
|---|---|---|
| critical | 功能正确性、权限、安全、数据或交付成立条件已被破坏 | **必须**修复 |
| warning | 会造成错误路由、低效、体验下降或未来高概率失败 | 建议修复，或由开发者明确接受 |
| suggestion | 不影响当前成立性的改善 | 可选 |

每项发现**必须**包含：位置（资产类型 → 名称 → 字段）、当前事实、问题（为什么是问题、引用哪条规范）、根因、业务影响、建议、**改前与改后对照**。

报告结构：概览（场景包名称、资产数量、发现总数与分级计数）→ 发现详情 → 优化优先级。

发现问题时**立即说明**问题和影响，**不要**累积到最后一次性输出。

全层检查后没有发现问题时，**明确报告检查范围和证据**，**禁止**为了显得有产出而制造建议。

#### 8.12.5 家族视角

诊断进入统一版本体系的资产时，先确认问题出在**哪个物理行**（家族内哪一版）：线上问题看当前上线版本，制作期问题看草稿行；不同版本行的配置相互独立，**禁止**拿草稿行的配置解释线上行为（详见 [场景包版本体系与发布逻辑](../references/场景包版本体系与发布逻辑.md)）。统一版本体系之前创建的存量资产可能整族没有版本事实，平台会在需要时就地补基线——这是正常兜底，不作为诊断发现。同家族多个 live 行也是正常现象（旧上线版本保留）；排查"修了但没生效"类症状时，先核对引用方指向的是哪一行——常见根因正是修复出了新版本行而引用未切换（见 2.2）。工具：`list_asset_versions` 看家族全貌、`compare_asset_versions` 看两版本配置差异（"上线后突然变差"先比现役 live 与上一版）、`get_asset_usage_impact` 看谁在引用、`get_scene_package_lineage` 看这个包是从哪个包派生来的（派生包的问题可能源自来源包的设计）。

### 8.13 落实修复与回归


#### 8.13.1 修复优先级

1. **结构与关系类优先**：预加载工具集缺失、FastAgent 工具关联不足、任务点缺工具集——用 `update_asset_relations` 修。**结构不修，文本改得再好也没用**
2. **输入输出契约类**
3. **文本、提示词与知识类**：用 `update_asset_field` 修，需要传改前与改后内容
4. **存量附属界面类**（历史随包部署的界面维护；新业务应用的诊断走 app-creator 线）
5. 以上都无法覆盖时才**重建资产**：创建新资产 → 更新关联 → 清理旧资产残留
6. 确认不需要的资产才删除，删除前**必须**开发者确认（约束 6）

#### 8.13.2 受影响项重验

每次修复后**必须**重跑所有受影响的验证。编排型 TPE 有变更就回到 G4 第 8.4 节重验该条；整包配置有变更就重新执行 G5 第 8 节。

修复以**新版本行**上线时，引用不会自动跟随。修订编排型 TPE 时 `otpe_manage(update)` 对 testing/offline 草稿会**自动采用**（未显式传 `target_scene_package_draft_id` 也生效；live 包不动，需显式 `attach`），响应 `message` 开头以【自动采用】说明改了哪个草稿、业务路线引用是否重写——本地手里的业务路线 JSON 此时已过期，先反读再继续改；定稿上线后工具在 `output.mounted_by_stale` 里列出仍钉旧版的场景包并给出 attach 指引——**逐个处置该清单，或在工单记录明确不跟进的理由**。清单之外仍要检查的引用（工具集关联等），显式切换到新版本行并反读确认——***不切换，修复永不生效***。核对方法：`list_asset_versions` 看家族内 live 行，比对引用方指向的是不是修复后的那一行。

**禁止**改完就宣称修复完成——没有重验就没有证据（约束 10）。

修复对象在两张表覆盖范围内时，受影响条目按指纹变化自动回退 `pending`（总入口 5.3）；**重验范围即全部回退条目**，未变化条目不重复验证。

### 8.14 维护已上线场景包


#### 8.14.1 资产维护工具

| 工具 | 用途 |
|---|---|
| `update_asset_field` | 修改资产的文本字段，需要传改前内容，并通过 `new_string` 或实时 Schema 支持的 `new_string_url` 提交改后完整文本；平台仍沿用原有 diff 确认和保存链路 |
| `update_asset_relations` | 修改资产关联关系，按集合增删 |
| `upload_skill_files` | 给已有资产补挂或替换 Skill 文件（见 G4 第 8.8.3 节第二步） |
| `clone_asset` | 克隆资产，也可克隆官方资产 |
| `delete_asset` | 删除资产 |

`delete_asset` 是**完整删除**。调用前**必须**按约束 6 向开发者确认，并告知资产名称。

修改共享资产前先克隆（约束 11）。

#### 8.14.2 工具组刷新与差异比对

关联的 MCP 服务更新后需要主动同步。刷新**前必须**先反读旧的工具集合，刷新结果不会给出分组的差异明细，**必须**自己按工具名逐个比较新增、参数变化和删除。

- **新增工具**：只在场景确实需要时更新工具集使用指南。注意新增工具只有落在已选工具范围内才会自动同步到下游
- **参数变化**：**必须**重新核对所有引用它的脚本和提示词

#### 8.14.3 工具删除的级联清理

工具被删除时**必须**检查该工具组关联的所有工具集和 FastAgent 里是否有引用（`get_asset_usage_impact` 给出当前与历史版本快照的引用范围，作为核对起点），并**确认级联清理真实发生**。

还要清理知识文本：被删除的工具如果在 `apc_skill` 或工具集使用指南里被提及，**必须**用 `update_asset_field` 清理相关描述——留着失效知识会让运行时 Agent 反复尝试不存在的能力。

重要变更完成后**必须**重跑所有受影响的预览、运行验证和整包验收。

#### 8.14.4 存量附属界面

历史上随包部署的附属界面（`scene_package_ui_bundle` 链路：下载官方模板、上传源码、部署、查状态）只做**存量维护**，不再用它制作新界面（新业务应用走 app-creator）。带存量界面的包派生新草稿行后部署地址不继承（`entry_url` 为空），上线前须在新行重新部署并反读确认非空（报错对照见 4.6）。

### 8.15 异常与恢复


#### 8.15.1 四类分流

| 类型 | 判定 | 处理 |
|---|---|---|
| **可自愈** | 参数错误、偶发超时、路径或版本指针错误 | 读结构化报错，改参数或策略后重试（见 4.2），回到原步骤 |
| **有安全默认** | 可逆、等价且不改变业务语义的工程细节 | 说明默认方案、适用条件和影响后继续，记录到工单；产品决策不得进入此类 |
| **策略失效** | 依赖不存在、方向错误、契约已变、方案挑战发现严重结构问题 | 标记原策略失效，回到里程碑或方案设计阶段重构，**禁止**在错误架构上叠加局部修补 |
| **只能由开发者决定** | 产品契约、资金、删除、凭证、隐私、发布、能力削减 | 通过 Plan 或单项询问暂停等待开发者选择、授权或事实（总入口 3.1、约束 6、12） |

工具缺口本身**不终止**创建流程，但缺口影响和开发者选择**必须**进入最终交付（见 G2 第 8.1.4 节）。

#### 8.15.2 重试纪律

可恢复问题最多重试**三次**，**每次必须有新增证据或不同策略**。**严禁**原样重试，**严禁**发起参数完全相同的重复调用。三次仍失败则执行路径降级或上报，**禁止**陷入死循环。

预览、运行验证、业务路线保存或界面部署失败时，**必须**修**同一份**资产或源码后重跑受影响的验证，**禁止**新建平行资产规避问题。

#### 8.15.3 并发与串行

**可以并行**：多个无数据依赖的只读查询；多个独立资产的反读；多条互不依赖的编排型 TPE 各自的预览。

**必须串行**：下游参数依赖上游输出时；后一步需要前一步产出的文件或资产存在时；验证必须在继续之前完成时；同一份资产的连续修改。

#### 8.15.4 平台能力不支持时

当前平台无法表达计划中的路线模式或界面模式时，**保留业务设计**，先重新读取实时工具、当前契约、结构化错误和已有官方能力，修复同一份产物并按 4.2 重试。确认已有能力仍无法表达时，记录平台阻断（见总入口 8.3）。

**禁止**用前端或脚本伪装平台尚不具备的能力，**禁止**把已确认要做的交付项静默改记为不做。

被平台阻断的事项仍在开发者确认范围内时，工单保持未完成。只有开发者明确修改总体 Plan、移除或改变该交付范围后，才能按新范围继续。

#### 8.15.5 受限资产处理

按总入口约束 7 处理：配置字段为空先判断是权限脱敏还是真的空；告知开发者并等确认；确认继续使用后重试原调用**必须**带 `allow_restricted=true`。

#### 8.15.6 常见报错对照

| 现象 | 处理 |
|---|---|
| 工具或 action 不存在 | 回看你当前的工具定义，按实际 action 和字段更新调用。工具确实不在列表里时，如实告知开发者该能力当前不可用，**禁止**虚构平行工具。`list_tools`、`scene_package_task_manage` 这类名称不存在，**禁止**调用 |
| 预览报字段、工具或路径错误 | 按报错精确修同一份草稿，再重跑预览 |
| 运行验证未到终态或报错 | 检查是否复用了同一运行标识；修脚本后重新运行取新证据 |
| `Workflow business event requires persisted Runtime identity` | 先区分正式运行与 Bubble：正式运行通常是把带业务事件的编排型 TPE 直接派发，应建立或修正单节点/多节点业务路线并从路线入口重跑；Bubble 则检查服务端是否分配验证身份，缺失时记录 `platform_blocked`。禁止在脚本或调用参数里伪造 Runtime ID |
| 业务路线保存被拒 | 按返回的节点、字段、路径错误修同一个对象，**禁止**自造兼容字段 |
| 资产详情字段为空 | 先判断是权限脱敏还是真的空（约束 7），告知开发者后再决定 |
| 工具集关联成功但运行时加载不到 | 检查是否有工具集仍处于离线（见 G4 第 8.2.2 节） |
| 需要最终用户各自授权的工具调用失败 | 检查授权卡是否配置并绑定（见 G4 第 8.2.3 节） |

| `WORKFLOW_RUNTIME_IDENTITY_INCONSISTENT` | Runtime 身份三态中的"部分缺失"：三元身份既非齐全也非全缺，属于内部调用链错误，不是业务输入问题。核对调用入口是否完整传递了服务端生成的身份；**禁止**手工补齐或伪造缺失字段 |
| 版本闸门拒绝（提示需要先定稿或先建草稿，如 `PERSONAL_VERSION_FINALIZE_REQUIRED`） | 内容修改撞了上线版本 → 回 G1 第 8.6 节取得可编辑草稿；上线动作撞了未定稿草稿 → 走 G5 第 8.17 节定稿上线。**禁止**绕过闸门直接改写状态字段 |
| `task_manager(insert)` 响应带 `format_warning`（“检查点建议一条路线一条”） | 记录已写入，但把多条路线的 `orchestration_id` 或 `run_id` 合在了一条里，或传成了数组；结单核对时会对不上。建议补成每条路线一条 `insert`，各带自己的 `run_id`（G5 第 8.3.1 节） |
| `task_manager(complete)` 返回 `WORKFLOW_TASK_ROUTE_BUBBLE_EVIDENCE_REQUIRED` | 发布范围里有路线没有对得上的 Bubble 证据：没跑、跑失败、`run_id` 属于别的路线、或证据早于最后一次业务路线修改。按响应里的路线状态补跑或修同一资产后重跑（G5 第 8.18 节）；**禁止**删标签、改文字或另开工单绕过 |
| `get_project_execution_logs(download)` 报“不存在”或“受保护目录” | 不存在：路径写错或文件确实没落盘——先 `outputs` 看清单，编排型 TPE 节点产物在 `/workspace/task_agent/<taskpoint>/output/`；清单里也没有时，看该节点是否把文件收进了 `ctx.output_dir` 并进了 `delivery.mapping`（G4 第 8.4.3 节 产出文件的交付链）。受保护目录：`input/`、`UserProjectData/`、`skills/`、`.env`、缓存与挂载目录本来就不提供下载 |
| 外部工具报参数格式错、路径不存在、文件读不到 | 先回该工具的实时契约看文件参数收什么（`file_to_url` 换出的 URL、`/workspace` 路径还是内容本体），再核对脚本里的准备步骤；多半是写脚本前没读契约、没取样（G4 第 8.8.2 节）。按契约改准备步骤，拿不准就取样一次，不要在脚本里加分支猜格式 |
| `has_ui: true` 但 `entry_url` 为空字符串 | 界面地址未随派生继承：部署之后又发生了派生新草稿行的修改（如改业务路线），激活地址留在旧行。在当前草稿行重新部署界面（`scene_package_ui_bundle`，属存量附属界面维护，见本文 3.4），反读 `entry_url` 非空后再上线 |

#### 8.15.7 工单 Gate 的三种结构化错误

（自总入口 6.3 搬入；总入口只留一句判别。）

工单 Gate 失败时按 `reason` 判别，三种处理方式互不相同。**禁止**新建平行工单或改名重试来绕过。

**`SCENE_SKILL_UPGRADE_REQUIRED`** — Skill 版本过期，工单**未创建**。立即停止所有写操作，
在**本次会话内**完成升级：先判断所在平台，从 `metadata.update.update_guides` 取该平台的
升级文档链接，拉取后逐步照做；再搜索已安装的 SKILL.md，从 description 读出
`[skill-version:...]` 标记，原样填入 `skill_version` 重试（Claude Code 平台可直接
`grep -r "skill-version" ~/.claude/plugins/cache` 定位；其他平台按各自安装目录搜索）。

合法版本串**只能**来自升级后已安装的 SKILL.md。拒单响应里不含可用于重试的版本串，
**禁止**从响应、changelog 或记忆里取值重试。搜不到已安装的 SKILL.md、或文件里没有
`[skill-version:...]` 标记，说明未安装或安装已损坏，改取 `metadata.update.install_guides`
里该平台的安装文档重新安装后再读标记，**禁止**因为读不到就编造一个版本串。升级成功并重试
通过之后，才提示开发者重启客户端让新 Skill 内容生效——重试只解除闸门，你上下文里的 Skill
内容仍是旧版。

**`SCENE_SKILL_UPGRADE_RECOMMENDED`** — 有新版本但**不阻断**，工单已正常创建，`task_id` 可直接使用。
继续当前任务，交付时顺带提示开发者升级即可。

**`WORKFLOW_TASK_MODE_MISMATCH`** — 工单模式与动作不匹配。按 `metadata` 里的 `actual_mode` 和
`required_mode` 纠正：只读工单要执行写操作时，按「前置条件 / 工单 Gate」的对照表新建
`mode="write"` 工单并传 `continued_from_task_id`。**禁止**误判为工单不存在或属于他人。

### 8.16 诊断维度（骨架）


1. **信封层**：前端收到 `BAD_GATEWAY`(7) 多为后端信封违约（`message` 拼错 / `data:null` / 非 200）；`TIMEOUT` 多为 async 路由漏 try-catch 挂死或查询超 10s；
2. **数据面**：schema 名硬编码（换环境即坏）→ 全部改 `tableOf`；写权异常 → describe 反读列声明与后端校验比对；
3. **部署层**：宿主注入头缺失（头名定稿前字段可能 undefined）；schema copy 失败；P2S 状态；
4. **场景包升级适配**：依赖的包出新版本时，反读新契约与应用的 forms/orchestrations 引用逐项 diff，受影响页面与回流字段重验后再升级绑定版本。
