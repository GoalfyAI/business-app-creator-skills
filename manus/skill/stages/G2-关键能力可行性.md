# G2 关键能力可行性

本阶段的目的是**在写任何正式资产之前，证明关键能力真的可行**。把试错前移：先试最可能失败的部分，用真实取样和真实产物说话。产出能力矩阵与试验报告，它们是 G3 决定谁来做、怎么做的直接输入。细则表格见 本文第 8 节。

## 1. 进入依据

G1 的业务基线、关键决策清单与业务路线草图已确认；关键未知项已列成试验问题。试验授权与正式制作授权**分开取得**：试验授权包括试验数据、隔离环境、费用与调用范围、停止条件。

进入前已有 `write` 工单。试验会创建工具组、工具集和试用包草稿，`read` 工单**不得**执行。

## 2. 本阶段建设

### 2.1 建立承诺、能力、证据、缺口矩阵

把 G1 的每条业务承诺和每个关键决策展开成一行：需要什么能力、已有什么证据、缺什么。证据来源按可信度排三个顺序，**先复用、再摸底、最后才谈缺口**。

**第一来源：参考项目。** 开发者给了参考项目，你**必须**完成三层，**禁止**只看摘要下结论：

1. 概览。读项目摘要，统计总轮次、最终用户请求序列、执行阶段、Agent 与工具分布、等待与失败概况。摘要只用来建立全局视图和定位要深挖的轮次。
2. 深读。读完整原始日志的全部分页，截断时续读到结束。重点看最终用户的原始意图与约束、规划逻辑、工具调用密集的阶段、任务点与 FastAgent 的输入输出质量、失败重试、等待原因、最终交付是否匹配预期。
3. 分析。写入工单四项结论：轮次分类统计；瓶颈定位与根因归类，缺知识、缺工具、缺指引、缺前置检查或资产边界错误；真实调用链；Skill 使用情况。多个项目逐项目保留独立事实再提炼共性，**禁止**用平均值掩盖异常。

**第二来源：已有能力容器与官方基础包。** 用 `get_asset` 读官方基础包的完整配置，理解预加载与动态工具集的组合方式，作为选型基准。用 `list_assets` 加 `get_asset` 找可参考的已有能力容器；开发者要基于某个已上线包做变体时，用 `get_scene_package_lineage` 看来源与派生，评估走派生还是新建。用 `get_diagnosis_doc(scene_package)` 读当前契约。复用的判据是 G1 基线：候选覆盖了哪些路线与交付，用词与画像是否一致，缺什么。

**第三来源：平台能力摸底。** 用 `list_assets` 搜索，用 `get_asset` 完整反读能力容器、任务点、工具集、FastAgent、工具组、数据集。看 Schema 和真实配置，**不要**只看描述。搜索结果不是完整契约，选型前**必须**用 `get_asset` 下钻；一次 `get_asset` 不展开子资产，**必须**逐级下钻。涉及数据查询时用 `list_assets` 列出开发者有权访问的长期数据集，用 `dataset_read` 确认表结构与权限；**禁止**假设开发者拥有某个数据集。名为"××档案场景包"的官方包属于业务档案产品线，不是业务应用数据集的来源。

矩阵的每行落六态之一：已覆盖、可组合覆盖、需维护、真实缺口、受限能力、待验证。选择结论用 `task_manager(insert)` 留痕。

### 2.2 先试最可能失败的部分

按风险排序，顺序固定：取不到数据；模型不能可靠判断；外部工具效果差；成本或时间不可接受。每一项对应一个试验问题，试验问题只有两种答案：有真实证据的可行，或者明确的不可行与原因。

### 2.3 能力缺口的四层处理

缺口**不阻塞**流程，但**不得**静默削减开发者明确要求或参考项目里已有的能力。按优先级处理：

1. **Skill 弥补。** 工具能力已覆盖，缺的只是调用顺序、前置检查、字段准备或结果审视方法。把指导写进正确层级即可。
2. **接入现有能力。** 平台内先用 `list_assets` 与 `get_asset` 确认没有可复用的工具组，重复注册同一服务会产生冲突资产。平台没有再去外部找：MCP 官方索引、代码托管平台、包管理平台、开发者自己的私有仓库。评估四维度：是否仍在维护；连接方式；认证方式，全容器共用凭证还是每个最终用户各自授权；有无破坏性操作。任一维度足以否决时直接出结论。
3. **形成开发需求。** 开发者有协作团队时，写一份可直接转交的需求说明：业务动作、目标系统、必需输入与输出、授权方式、隔离要求、副作用、失败语义、验收样例。
4. **开发者确认后降级。** 用已有能力继续，**必须**写明未覆盖的阶段、对结果的影响、以后补齐的条件与受影响的验证，并取得确认。

不知道某个效果怎么实现时，先问开发者有没有参考资料或同类产品；没有再自行调研实现思路。结论与来源记入工单。

### 2.4 能力试用与真实取样

外部能力要不要用、能不能用，靠试用回答，**禁止**先建全套正式资产。顺序固定：

1. **摸底定形态。** 完整读能力来源的文档。现成 MCP 服务和标准 Skill 包直接进下一步；CLI 工具、代码库、普通应用需要先包装，默认只评估包装成本并出结论，开发者明确要求时才动手包装。
2. **本地验证先行。** 起服务、装依赖，确认工具清单与真实返回结构。本地能起来再注册，注册基本一次通过；反过来每轮都要等平台反馈。本地不可用直接出结论并附证据。
3. **平台接入。** `preview_tool_group` 预览并发现工具，再 `register_and_refresh_tool_group` 注册；预览时用过的前置安装步骤，注册时**必须**一并带上。标准 Skill 包用 `import_skill_package`；开发者的私有包先 `file_to_url` 换取引用再 `upload_and_register_tool_group`。需要最终用户各自授权的能力，试用期就要用 `create_auth_card` 配授权卡，否则试跑走不通。**禁止**把任何个人令牌写进 Skill 文本、脚本或工单。
4. **复用工具先读契约，再真实取样。** 脚本要直接调用的已有工具，先用 `get_asset` 下钻到工具组，读描述与输入定义：文件参数收 URL 还是 workspace 路径；必填与互斥；值域与格式；返回结构是否声明；副作用与授权。拿不准的安全只读工具做一次 `otpe_tool_test` 取样，输入用代表性真实值，文件先 `file_to_url(purpose="tool_test_fixture")` 上传并同时提供 `workspace_files` 与 `workspace_bindings`。取样验两件事：输入按约定能不能被接受；真实返回的嵌套形状。破坏性、发布、凭证、金融、不可逆的工具**禁止**取样。样本要点记入工单，不含 URL 与凭证。
5. **需要看模型判断时组极简试用包。** `scene_package_manage(create)` 建草稿并反读继承；新建工具集装入本次工具组并上线；`apc_skill` 只写这个能力是什么、什么时候用、关键注意点。名称**必须**带试用标识。用 `manage_goalfymax_project(run)` 跑开发者关心的 1 至 3 个真实任务，任务描述用自然业务需求，**禁止**指定工具名或调用顺序。试跑是真实运行，FastAgent 计费、外部副作用照常发生，**必须**先取得授权；含破坏性工具的任务**禁止**作为试跑任务。逐任务记录任务、实际调用、结果质量、耗时与积分、失败与原因。
6. **收尾。** 试用包草稿**永不上线**，出结论后经开发者确认用 `delete_asset` 作废；工具组与工具集保留，转正式时直接复用。

### 2.5 用同一代表性输入比较候选

每个模型或工具候选跑同一输入，记录质量、耗时、费用、失败形态。改稿类承诺**必须**试"旧产物加修改约束"；续作类承诺**必须**试恢复所需的状态与产物读取。只证明从零生成**不算**通过。样本量不足时**禁止**声称稳定成功率。

### 2.6 验证 U 项前提

U2：数据粒度、权限、文件读取、上下文传递，用实际对象核实。U3：模型判断与连续执行的关键样例，覆盖应继续、应补充、应停止三种情境，桩跑不算判断能力。纳入范围时另验 U7 的发现与授权、U8 平台可表达的动态行为。

### 2.7 写试验报告与能力矩阵

报告结论先行，写入工单：结论，可行、不可行、需要包装后再评估；能力形态与接入方式；验证证据，本地验证、工具清单与返回结构要点、逐任务记录；质量印象；成本，接入耗时、试跑积分、包装预估；风险，维护状态、认证模式、破坏性边界、许可证；盲区，没试到什么、哪些结论是外推的。能力矩阵更新每行的状态与证据。

## 3. 给开发者看什么

默认展示两样：**实际产物对比、关键路径能力卡**。每张能力卡回答四个问题：要证明什么、试了什么、结果怎样、现在能承诺到哪。费用与耗时分事实与估算两栏。候选路线只在有显著取舍时并列，**禁止**为凑数量造方案。缺口处理方案带影响与推荐，由开发者选，你**不得**以缺口不可阻塞为由自行削减目标。

## 4. 要确认哪些边界

试验数据；隔离环境；允许的读写；费用与调用范围；停止条件；最终用户兜底是否可接受。使用更大模型**不得**自动扩大费用和数据外发范围。

## 5. 门禁 Checklist

- `G2-01` 试验覆盖本次实际使用方式，包括改稿与续作，不只从零生成。对应 U4、U5。
- `G2-02` 已用实际对象核实数据粒度、权限、文件读取、上下文传递；受限详情未被误判为空资产。对应 U2、U5-02。
- `G2-03` 模型判断与连续执行有真实证据，覆盖应继续、应补充、应停止；桩跑不算判断能力。对应 U3。
- `G2-04` 质量、耗时、费用的事实与估算分开；超限方案未被默认采用。
- `G2-05` 关键路径缺口已解决，或开发者明确改范围。"以后补"不能让原承诺通过。
- `G2-06` 试验环境与资产有标识及清理或保留计划；未擅自上线；无未授权副作用。

## 6. 证据与结论

产出试验报告、真实输出、能力矩阵、选择依据、剩余盲区。落工单检查点 `capability_matrix` 与 `trial_report`。已注册的工具组与工具集、工具真实返回结构、试跑记录直接进入 G3 与 G4 复用。

## 7. 失败回退

能力失败：先换试验策略，包括换工具、补信息、升级模型。目标不成立：回 G1 修改承诺范围。

## 8. 细则

本节是第 2 节各步骤点名的表格、契约、纪律清单与示例。它不是流程：进入与出口以第 1 节和第 5 节为准，**禁止**从本节推断阶段顺序。

### 8.1 复用：项目、场景包与资产摸底


拿着已确认的计划书（`build_book`，S1）开始资产设计。先复用、再摸底、最后才谈缺口——三个来源按此顺序看：参考项目（真实执行记录，可信度最高）、已有场景包与官方基础包（能派生就不从零建）、平台能力（工具组 / 工具集 / FastAgent / 数据集）。

#### 8.1.1 参考项目三层深读

开发者提供了参考项目时**必须**完成三层，**禁止**只看摘要下结论（约束 3）。

**第一层 概览**：读项目摘要，统计总轮次、最终用户请求序列、执行阶段、Agent 与工具分布、等待与失败概况。摘要是压缩后的统计信息，**只能**用于建立全局视图和定位需要深挖的轮次，**不能**作为结论。

**第二层 深读**：读取完整原始日志的全部分页，截断时**必须**续读到结束。重点看：最终用户原始意图与约束、规划逻辑与步骤拆分、工具调用密集的阶段（调用链、参数传递、前后依赖）、任务点与 FastAgent 的输入输出质量、失败重试、等待原因、最终交付是否匹配预期。

**第三层 分析**：形成以下可复核结论并写入工单：

- **轮次分类统计**：总轮次、有效推进、重复沟通、失败重试、等待
- **瓶颈定位**：消耗最多轮次的阶段，根因归类为缺知识、缺工具、缺指引、缺前置检查或资产边界错误
- **真实调用链提取**：每个业务阶段实际调了什么、顺序如何、有没有前置依赖但 Agent 不知道
- **Skill 使用情况**：哪些文件被读取、哪些应该被引导读取但没有

多个项目对比时，**必须**逐项目保留独立事实，再提炼共性，**禁止**用平均值掩盖异常。

**完成标准**：三层全部完成并写入工单后才能进入下一步。**禁止**只看摘要就跳过深读——这是本节最容易出现的问题。

#### 8.1.2 复用已有场景包与官方基础包

你**必须**主动获取的：

- 用 `get_asset` 查看**官方基础场景包**的完整配置，理解其预加载与动态工具集的组合方式，作为选型基准
- 用 `list_assets` 加 `get_asset` 查找可参考的已有场景包；开发者要"基于某个已上线包做一个变体"时，用 `get_scene_package_lineage` 看它的来源与派生包，再评估是走**派生**（`create_derived_scene_package`，见总入口 §7.1）还是新建
- 用 `get_diagnosis_doc(scene_package)` 读当前场景包契约

复用的判据是**计划书**：候选场景包 / 派生来源覆盖了计划书 ②③ 章里的哪些路线与交付、用词与画像是否一致、缺什么。能派生就不从零建（组合 / 继承 / 派生的边界见 [平台对象与运行模型](../references/平台对象与运行模型.md) 第五章）。

#### 8.1.3 能力摸底与覆盖矩阵

三个只读工具：

| 工具 | 用途 |
|---|---|
| `list_assets` | 按类型搜索可复用资产。关键词只匹配名称和 ID，建议用英文短词；不传关键词会返回全量，注意上下文开销 |
| `get_asset` | 批量反读完整配置、关系、Schema、状态，一次 1–20 个 |
| `dataset_read` | 只读查看长期数据集：描述、使用指南、Skill 文件、表、列、行 |

用 `list_assets` 和 `get_asset` 搜索并完整反读场景包、任务点、工具集、FastAgent、工具组、数据集；摸底的目标来自计划书第 ②③⑥ 章——每个里程碑、每条路线、每类产出各需要什么能力。看 Schema 和真实配置，**不要**只看描述。

搜索结果**不是**完整资产契约，选型前**必须**用 `get_asset` 下钻（约束 4）。重要选择结论用 `task_manager(insert)` 留痕。

一次 `get_asset` 只返回该资产自身的配置，**不会**展开它引用的子资产。诊断时**必须**按层逐级下钻。

场景涉及数据查询或报表时，用 `list_assets` 列出开发者有权访问的长期数据集，`get_asset` 或 `dataset_read` 确认表结构与权限范围。数据集**只能**绑定真实可访问的，**禁止**假设开发者拥有某个数据集。开发者没有对应数据集时明确告知需要先去准备。

两类不要误认的资产：目录里名为"××档案场景包""业务档案助手"的官方包是业务档案产品线（另一套数据面），不是业务应用数据集的来源，也不要为了"留存用户数据"去复用它们；`business_app_dataset` 工具集（业务应用数据集 FA 所在）只在场景包配套业务应用时才挂——计划书 ⑤ 写"不适用"的包不挂它。

按每个里程碑建立覆盖矩阵：**已覆盖 / 可组合覆盖 / 需维护 / 真实缺口 / 受限能力 / 验证方式**。

向开发者输出每个里程碑的覆盖情况，把缺口处理选项、影响和推荐纳入制作书第 ⑨ 章（7.2），由开发者确认；Agent 不得以“工具缺口不可阻塞”为由自行削减业务目标。

#### 8.1.4 工具缺口四层处理

工具缺口**不可**阻塞创建流程，但**不得**静默削减开发者明确要求或参考项目中已有的能力（约束 12）。按以下优先级处理：

**第一层 Skill 弥补**（成本最低，优先尝试）：工具能力已覆盖，问题只是缺调用顺序、前置检查、字段准备或结果审视方法。把指导写进正确层级即可。

**第二层 接入现有能力**：先在平台上找，平台没有再去外部找。

平台内：用 `list_assets` 和 `get_asset` 确认是否已有可复用的工具组——重复注册同一个服务会产生互相冲突的资产。

平台没有时**从外部获取**。你运行在能联网、能读写本地文件、能执行命令的环境里，这是 Max 内部制作助手做不到的，**应当主动利用**：

| 目标 | 去哪找 |
|---|---|
| 现成 MCP 服务 | MCP 官方索引、代码托管平台、包管理平台（npm / PyPI），以及开发者自己的私有仓库 |
| 现成 Skill 包 | 同上；开发者手里可能已有内部沉淀的包 |

找到候选后**先在本地验证，再走平台注册**。顺序反了会浪费大量试错：本地能起来、工具清单和返回结构都确认过，注册基本一次通过；直接注册再排错，每轮都要等平台反馈。

评估候选时**必须**看清四件事：

| 维度 | 为什么要看 |
|---|---|
| 是否仍在维护 | 长期不更新的服务上线后容易失效 |
| 连接方式 | 决定注册时传地址还是启动命令，以及运行环境要装什么 |
| 认证方式 | 全场景包共用一份凭证，还是每个终端用户各自授权——后者**必须**配授权卡 |
| 有无破坏性操作 | 决定哪些工具可以取样、哪些**禁止**取样，以及要不要在使用指南里加约束 |

开发者提供本地包或压缩包时，走 `file_to_url` 换取引用后注册或导入（见 G4 第 8.8.3 节）。完整的注册流程、失败调试循环和上线检查见 [依赖与 MCP 接入](../references/依赖与MCP接入.md)。

**第三层 形成开发需求**（开发者有协作团队时）：为缺失能力生成可直接转交的需求说明，**必须**写明业务动作、目标系统、必需输入与输出、授权方式、最终用户与项目隔离要求、副作用、失败语义、验收样例。格式要便于开发者一键转发给工程师。

**第四层 开发者确认后降级**：用已有能力继续制作，**必须**明确说明未覆盖的阶段、对结果的影响、以后补齐的条件和受影响的验证，并取得开发者确认。

#### 8.1.5 实现思路调研

**不知道某个效果如何实现时**（有目标、无做法）——**先询问开发者是否有参考资料或已知同类产品**；没有再去 GitHub 等开源平台自行调研同类实现。调研的是**实现思路**而非现成资产，产出可以是自建编排型 TPE / 工具的设计依据，或转交开发需求（第三层）的技术方案参考。结论与来源记入工单。

### 8.2 进入前提与定位


快速验证一个外部能力（GitHub 仓库、MCP 服务、Skill 包）**值不值得做成正式场景包**。本节从总入口 4.1 独立进入，不属于创建主干；产出是**一份带证据的试用结论**，不是可交付的场景包。

进入前提：有 `write` 工单（试用会创建工具组、工具集与试用包草稿）；开发者已给出能力来源（仓库地址 / MCP 服务地址 / 包文件），以及（可选）想验证的具体问题。

**定位边界，先讲清楚再开始**：

- 试用包**永不上线**：不定稿、不交付给最终用户、不结正式交付单。它的生命周期终点是本节的试用结论。
- 试用结论为"值得"时，正式化**必须**新开工单走 S1 完整流程（见第 8 节的材料复用）；**禁止**把试用包就地转成正式包绕过质量门。
- 试用跳过的是业务设计与验收流程，**不跳过**：工单 Gate（约束 1）、本地验证先行、真跑授权（约束 6）、如实汇报（约束 10）。

### 8.3 摸底定形态


完整读取能力来源的文档（README、使用说明；约束 3 同样适用），回答两件事：

**能力形态**：

| 形态 | 试用路径 |
|---|---|
| 现成 MCP 服务 | 直接走第 3–6 节 |
| 标准 Skill 包 | 直接走第 3–6 节（接入用 `import_skill_package`） |
| CLI 工具 / 代码库 / 普通应用 | **需要先包装成可注册的包才能进平台。** 默认只评估包装成本并直接进入第 7 节出结论（"需要包装，预估成本与路径"本身就是结论的一部分）；**仅当开发者明确要求时**才动手包装并继续试用 |

**评估四维度**（与 S2-2.4 同一套判据）：

| 维度 | 为什么要看 |
|---|---|
| 是否仍在维护 | 长期不更新的服务上线后容易失效 |
| 连接方式 | 决定注册时传地址还是启动命令，以及运行环境要装什么 |
| 认证方式 | 全场景包共用一份凭证，还是每个终端用户各自授权——后者**必须**配授权卡 |
| 有无破坏性操作 | 决定哪些工具可以取样、哪些**禁止**取样，以及试跑任务的安全边界 |

四维度中任一项已足以否决（如项目已停止维护、认证模式平台无法承载）时，**可以**直接进入第 7 节出"不值得"结论，不必走完后续步骤——试用通道的价值就是尽早给出答案。

### 8.4 本地验证


**先在本地验证，再走平台注册**：起服务、装依赖，确认工具清单与真实返回结构。顺序反了会浪费大量试错：本地能起来、工具清单和返回结构都确认过，注册基本一次通过；直接注册再排错，每轮都要等平台反馈。

本地验证失败且排查后仍不可用时，直接进入第 7 节出结论，附失败证据。

### 8.5 平台接入


按 G4 第 8.8.1 节的接入工具链执行：`preview_tool_group` → `register_and_refresh_tool_group`（或 `import_skill_package` / `upload_and_register_tool_group`）；预览时用过的前置安装步骤，注册时必须一并带上。需要终端用户各自授权的能力，试用期即须配授权卡（S3-1.3），否则试跑走不通。

注册前**必须**用 `list_assets` 确认平台上没有同一服务的既有工具组——重复注册同一个服务会产生互相冲突的资产（S2-2.4）。已有注册时直接复用，并在结论里注明。

### 8.6 极简试用包


组一个**最小可跑**的试用包：

1. `scene_package_manage(create)` 建草稿（默认克隆官方基础包，立即反读继承）；
2. 新建工具集装入本次接入的工具组（或导入 Skill 包产生的工具集），关联到试用包；工具集须过安全测试并上线（S3-1.2 第一道检查同样适用——离线工具集运行时不加载）；
3. `apc_skill` 只写最小内容：这个能力是什么、什么时候用、调用时的关键注意点（认证、破坏性边界）。**不写**里程碑、候选路线、正反例；**不建**执行结构表与结果检查表；**不做**方案挑战。

试用包名称**必须**带明显的试用标识（如「试用」前缀），防止被误认为正式包。

### 8.7 草稿态试跑


用开发者关心的 **1–3 个真实任务**在草稿态试跑（`manage_goalfymax_project`，真跑纪律与运行实例规则同 G5 第 8.4.2 节）：

- 试跑是真实运行：FastAgent 照常计费、外部副作用照常发生，**必须**先按约束 6 取得开发者授权；含破坏性工具的任务**禁止**作为试跑任务；
- 任务描述用自然业务需求，**禁止**指定工具名或调用顺序——试的就是"平台上的 Agent 能不能用好它"；
- 逐任务记录：任务、实际调用、结果质量、耗时与积分消耗、失败与原因。

### 8.8 试用结论


出一份**结论先行**的试用报告，写入工单：

- **结论**：值得做成正式包 / 不值得 / 需要包装后再评估
- **能力形态与接入方式**：形态判定、注册结果（或包装成本预估与路径）
- **验证证据**：本地验证结果、工具清单与真实返回结构要点、逐任务试跑记录
- **质量印象**：结果能不能用、稳定性、与预期的差距
- **成本**：接入耗时、试跑积分消耗、（若适用）包装预估成本
- **风险**：维护状态、认证模式、破坏性边界、许可证
- **值得时**：建议的正式化范围（哪些能力值得进正式包、适合什么业务场景）
- **盲区**：没试到什么、哪些结论是从有限任务外推的（约束 10——**禁止**夸大试用覆盖面）

### 8.9 收尾与正式化衔接


**收尾（出结论后立即执行）**：

- **试用包草稿作废**（`delete_asset`，删除前按约束 6 确认并告知名称）——防止试用包被当正式包使用；
- **工具组与工具集保留**：注册是重资产（重复注册冲突），转正式时直接复用；结论为"不值得"且开发者同意清理时才删除；
- 工单以试用结论作为最终记录，`task_manager(complete)` 收尾。

**正式化衔接（结论为"值得"、开发者决定做正式包时）**：新开 `write` 工单进入 S1，以下试用产出直接复用：

| 试用产出 | 在正式流程中的用途 |
|---|---|
| 已注册的工具组/工具集 | S2 依赖准备直接引用，免重复注册 |
| 工具真实返回结构 | S3-2.2 取样要拿的东西，试用已拿到 |
| 试跑记录 | S1-2.1 的参考素材（真实执行记录，可信度最高级） |
| 试用报告的正式化范围建议 | S1 里程碑与候选路线的输入 |
