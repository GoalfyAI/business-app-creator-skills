# S3 业务界面

从预设计到部署验收。本阶段只在开发者已在总体方案 Plan 中选择制作业务界面时执行（约束 8）。

## 1. 进入前提与选择门

业务界面的选择规则、交付门与 `platform_blocked` 纪律见路由器约束 8，进入本阶段前重读一遍。

预设计（第 2 节）在 S1 方案确认后、Workflow 脚本动笔前完成。

### 1.1 实现阶段入口

本节只在开发者已明确选择制作业务界面时执行。业务界面预设计和官方脚手架首次阅读已在第 2 节完成，本节只处理最终契约冻结与工程实现，不重新从页面创意开始。进入本节前必须同时满足：第 5 节设计确认门已通过（设计文档与原型经开发者确认）；场景包包含 Workflow；受影响 Workflow 已完成 Preview、必要的工具取样、单条 bubble 和语义验收；顶层编排已保存反读并完成静态接缝检查；发布范围内每条业务路线的路线级 Bubble 已通过；`ui_predesign_brief` 已按真实事件、Schema 和编排更新；预设计阶段的脚手架已安全解压、必读文件已完整阅读且 `template_identity` 已记录。

任一条件不成立时回到对应阶段处理。不得用单条轨迹拼接成整图证据；业务事件、宿主运行契约、官方模板、部署或绑定能力不足以完成开发者已选择的业务界面时，先按约束 8 读取并复用已有能力修复同一份产物；确认仍不可完成后才记录 `platform_blocked`。该状态未解除且总体 Plan 未移除业务界面时，不得通过提前编码绕过，也不得上线场景包或结单。

## 2. 业务界面预设计

总体方案 Plan 提案包含一条或多条 Workflow 时，已应按约束 8 向开发者说明业务界面可承载专属输入、业务阶段状态、运行中交互、结果与交付物，并在同一份 Plan 中确认本次是否制作。进入本节时直接读取已确认选择，**不得再次询问**。

开发者选择制作时，**必须**在编写脚本和创建 Workflow 资产前完成以下准备：

1. 完整读取 [业务界面设计方法论](../references/业务界面设计方法论.md)；
2. 调用 `scene_package_ui_bundle(action="download_template", task_id=<task_id>)` 下载当前官方脚手架，核验响应、字节数、归档格式、安全路径和唯一模板根目录，并记录不含临时下载地址的 `template_identity`；
3. 完整阅读模板根目录的 `AGENTS.md`、`README.md`、`schema/README.md` 和 `src/sdk/docs/README.md`；涉及业务事件或最终交付时，继续读取模板当前要求的 Business、Delivery、类型定义与参考页面文件；界面含消息流时，`docs/message-guide.md` 与 `src/sdk/docs/chat.md`、`observe.md` 同列必读（逐消息类型的字段字典在 `docs/message/`，做消息展示前先查它）；
4. 基于真实脚手架能力，把最终用户旅程、页面地图、模块 include/exclude、状态—行动、事件响应、视觉方向和边界样例整理成 `ui_predesign_brief` 与预设计 Plan，由开发者确认页面范围和关键体验。

本阶段只建立模板能力认知与界面预设计，**不修改模板业务代码、不开始编码、不冻结尚未稳定的运行标识**。开发者选择不制作时，记录决定并直接进入后续资产制作，不下载脚手架、不生成占位设计、不把缺少界面列为验收问题。

预设计至少包含：

- 最终用户从选择路线、填写入口信息、等待执行、补充中途表单到审阅交付的完整旅程；
- 页面地图、模块决策账本，以及每个模块采用、合并、延后或不采用的理由；
- 状态—行动矩阵，明确每种业务状态下的可见信息、允许动作和恢复方式；
- 业务节点—事件—界面响应表，写清稳定事件名与版本、Payload 字段、归约后视图状态、回放/补拉反馈和快照权威边界，用于反向约束 Workflow 必须事件和建议事件；
- 关键交互、边界样例、视觉方向和中文文案承诺。

预设计 Plan 确认的是**页面范围与关键体验**（含业务事件候选，S2-6.4 依赖此时点）；视觉与手感不在此定稿——它们在第 5 节的设计确认门随可交互原型一次确认。

JSON Schema 与 SDK 能力只是设计事实，不能直接推导页面模块；Agent 的模块推荐也不能代替开发者确认。预设计可以随 Workflow 和编排事实修订，但不得提前写死内部 ID、Workspace 路径、工具步骤或未发布 Schema。仅当开发者已选择制作业务界面时，`ui_predesign_brief` 未完成或关键模块仍未确认才阻止开始 Workflow 脚本制作。

## 3. 呈现原则：交付页与消息流

交付页应**直接消费 `output` 业务字段**做贴合业务的呈现——脚本按 `output_schema` 返回的全部业务字段都会随交付到达界面，界面按已冻结契约渲染对比、列表、结构化内容等业务形态；`output.display` 是平台标准的**兜底展示出口**（未制作定制界面的包、聊天内呈现使用）。为支撑界面消费，`output_schema` 的字段描述**必须**含面向呈现的语义（该字段是什么、每项含义），不能只写给下游脚本看。什么值得投影、何时渲染的判断依据见 [运行模型与渲染语义](../references/运行模型与渲染语义.md)；页面结构、守卫与渲染的工程细则以脚手架仓当前文档为准。

**要渲染的内容必须在业务字段里**：界面对工作区文件只有预览 URL 与下载（`sdk.file`），***读不到文件正文***。凡界面要展示的内容（列表、正文、结论、对比），必须以业务字段出现在 `output` 中；内容只落文件、`output` 只给计数和路径的契约，界面等于写在假数据上。

**消息流的呈现原则**：业务界面的消息流是**操作回执与过程通知**，不承载业务状态。三类权威事实各有专属承载——进度归业务事件、输入归结构化表单、交付归 Delivery 模块——消息流只做每个时刻的"人话补充"：

| 时刻 | 展示什么（有用的） | 权威事实在哪 |
|---|---|---|
| 等待执行中 | 用户自己的提交回显（含表单提交标记 `interaction`，让用户确认"我提交了什么"）；平台产生的可读说明与通知（`kind=answer`）。设计期判定要给用户看的步骤产出经业务事件或交付模块呈现（S1-9.3），不经消息流 | 阶段与进度以业务事件模块为准，***不让用户从消息流里拼业务状态*** |
| 需要输入时 | 引导性提示消息（说明为什么需要补充）；输入动作本身走运行中业务表单 | 表单请求与回复状态以 Business 握手为准，不用消息代替表单 |
| 拿到交付时 | Agent 的总结性可读消息可留在流内作为收尾叙述 | 交付内容以 Delivery 模块（`PublicDelivery`）为准，消息流不承载交付物与文件 |

展示范围的契约（`kind` 白名单、去重、翻页）与实现细则以脚手架 `docs/message-guide.md` 为准；执行过程内部消息（`kind=other`）任何时刻都不面向最终用户。

## 4. 最终契约冻结

全部受影响 Workflow 已完成前三层验证，顶层编排已保存反读并完成静态接缝检查，且发布范围内每条业务路线的路线级 Bubble 已通过后，才进入业务界面实现阶段。此时把 `ui_predesign_brief` 与真实资产合并为最终 `ui_design_brief`，补齐场景—界面映射、视觉取舍、边界样例和最终页面状态，并冻结场景包、Workflow、业务事件、顶层编排、表单和宿主运行契约。路线级 Bubble 未通过或当前环境无法提供该证据时，业务界面记录为 `platform_blocked`，不得进入编码。

在首次编码前和每次上传/部署前，均执行契约变更检查：

1. 反读当前 TPE 的输入/输出 Schema、业务事件契约、Workflow 脚本版本和场景包顶层编排契约；
2. 与业务界面的 `schema/orchestrations/`、`schema/forms/`、事件归约表、控件与结果渲染逻辑、`ui_contract_snapshot` 逐项比对；
3. 根据差异判定路线、入口、运行中交互、里程碑、结果和交付所受影响；
4. 对受影响的界面契约和实现完成更新，并重新执行相关验收。

**契约门**：无法证明新旧契约兼容时，停止业务界面发布。编排脚本仅作为制作期变更检查的事实依据，不得写入前端源码、由浏览器执行或向最终用户展示。

## 5. 设计与原型

契约冻结后、工程实现前，先完成设计并经开发者确认——**拿到契约直接从组件库或视觉起手闷头编码，是产出千篇一律界面的根源**。本节全程使用 `frontend-product-studio` skill（随本插件同装）：按"理解产品 → 定视觉方向 → 设计完整交互 → 组件构建 → 工艺打磨"推进；其运行时加载的外部 guidance 服从脚手架仓 AGENTS.md 的工程与安全约束与本 Skill 的平台硬约束。

### 5.1 需求基线

从已冻结的契约提取确定事实，不靠推测：

| 来源 | 确定什么 |
|---|---|
| `schema/forms/*.json` | 表单清单：字段、类型、必填、file 字段 |
| `schema/orchestrations/*.json` | 路线数量、入口表单、交付审阅动作 |
| Workflow `output_schema` / `display` | 结果页展示区块；核对要渲染的内容是否真的在业务字段里——只给文件路径渲染不出来（见第 3 节） |
| 业务事件契约 | 有无阶段状态可展示——没声明就不做进度模块 |

### 5.2 竞品调研（视觉方向的取材）

与 S2-4.2 样例选择同一套方法：**先询问开发者有无参考**（品牌规范、喜欢的产品）；没有再调研 **3 个及以上**该业务领域的真实产品，看三件事——功能模块划分、交互设计（主行动怎么突出、状态怎么表达、空态/等待/失败怎么处理、长表单怎么分组）、视觉层级靠什么建立（字重/留白/分隔线/色块）。**调研截图与报告留存进工单作为证据**；只取参考点，不照搬品牌、商标与整页布局。

***脚手架 demo 页与端到端示例案例只是机制参考，它们的布局、配色、组件组合不是默认起点***——不同业务的界面应当长成不同样子。Ant Design 不强制使用：合适就用，不合适就换，也可以混用。

### 5.3 产品设计文档

按"卖给外部客户的生产级 SaaS 产品"的立场设计，出发点是用户体验，不是把契约字段排版一遍。文档包含：

- 产品定位：这是个什么产品，面向什么人群
- 总体模块设计：页面划分、各自职责、页面间流转
- 每页 UI 与交互：text 示意图 + 功能说明
- 模块决策账本：含明确**不做**的模块及理由
- 文案与术语检查（见下）
- 一句话风格主张（例：「营业结束后快速复盘的手记感，不是数据大屏」）

验收标准只有一条：**一个不懂前端的人能读完，并且提得出意见**。

**文案与术语检查两关**：①术语是否符合品类通用定义、目标用户是否一眼能懂；②能靠交互说清的不写解释文字——***契约字段的 `description` 是写给 Agent 的，不搬上界面当说明文案***；确需解释的放在被解释元素旁的问号气泡里，不常驻页面、不堆到页首页尾。验收方法：把常驻解释性文字全部删掉，界面还能不能用。

设计文档不单独找开发者确认——随 5.4 的原型一起一次确认（文字看不出丑不丑，单独确认只会让开发者盖个章，看到实物再推翻）。

### 5.4 本地可交互原型

四条硬要求：**生产级**（真实组件、间距、字号与交互态，不是灰块线框图）；**所有路由都能打开**（含结果页、运行中、空态、失败态）；**每页有贴合业务的演示数据**（空态另出一版单独给开发者看）；**主动线可点通**。

原型是确认用的中间产物：只跑本地 `npm run dev`；演示数据仅以 `import.meta.env.DEV` 判据注入，不做原型专用构建变量；***原型不上传、不部署、不上线——部署会顶掉真实业务界面、把假数据带进系统***。确认后原型代码直接演进为正式实现，不重写。

交给开发者之前先自查：逐页自看一遍、改掉明显问题，再用 `impeccable`（随本插件市场同装）跑一轮 `/impeccable critique`（UX 评审）与 `/impeccable audit`（可访问性/响应式）——把 AI 味和硬伤消掉再给人看。impeccable 产生的修改同样受平台硬约束（SDK 唯一通道、保留件、保留区避让、内部标识不可见）与已冻结契约约束。

### 5.5 设计确认门

把设计文档与原型的**本地地址**一起交给开发者，开发者自己打开点。文档确认信息架构与模块取舍，原型确认视觉与手感——两者互为对照，缺一样都确认不了。***开发者确认后才能进入第 6 节正式编码；未确认不得编码。***

**设计上下文单一正本**：`impeccable init` 生成的 PRODUCT.md / DESIGN.md 从本节设计文档派生；冲突时以设计文档为准并回改。

## 6. 官方模板复核与工程实现

### 6.1 官方模板复核与工程初始化

工程实现使用第 2 节已下载并阅读的官方模板，但在首次修改业务代码前必须复核模板是否仍为当前版本：

1. 重新取得当前官方模板信息，与预设计阶段的 `template_identity` 比较；
2. 官方返回的版本或校验值可比且确认未变时，继续使用已验证的唯一模板根目录；
3. 模板已变更，或响应没有足以证明未变的版本/校验信息时，重新下载当前模板，重做字节数、归档、安全解压和唯一根目录检查，重读变更文档与固定 SDK 源码，更新 `template_identity`、`ui_predesign_brief` 和 `ui_design_brief`；
4. 只有模板复核、最终契约冻结和开发者已确认的设计范围同时成立后，才在模板声明的业务代码范围内开始编码。保持 SDK、启动入口、桥接协议、错误边界和模板保留件不变。

不得从空目录、通用脚手架、仓库克隆或历史源码副本初始化；预设计阶段不得修改脚手架业务代码。业务界面仅消费宿主公开的运行契约；任务点标识、工具清单、提示词、脚本、依赖图和 Agent 控制动作均不属于前端契约。

### 6.2 实现、检查与打包

按已冻结的设计与运行契约，完成业务控件、文件上传、提交与受理、等待、权限、错误恢复、结果展示和回落路径。两条实现原则：破坏性动作（提交、删除、付费）不放在"同一位置按条件切换"的控件上——切换瞬间的点击会落到新按钮上；同一份业务事实只有一个数据源，服务端知道的事实一律以服务端为准，本地状态只承载本地草稿态。

**交互动效**：凡引起页面内容变化的交互都要有过程动画，不闪烁跳变——路由切换、展开折叠、筛选、加载、状态推进、上传、校验提示、禁用态切换、空态转有内容、角标数字变化，一个都不例外。时长、缓动与实现手法按 `frontend-product-studio` 的动效工艺处理；`prefers-reduced-motion: reduce` 时去掉位移和缩放、保留并缩短透明度过渡，而不是关掉全部动画——那会退回闪烁。

**自查两件事**（开发阶段内部闭环，不需要开发者介入）：①对照 5.3 设计文档逐条核对模块划分、页面结构、交互流转、视觉层级，不一致改到一致；②**测试每一个可交互的地方**——所有能点、能填、能拖、能切换的都实际操作一遍，确认真的发生了预期的事，而不是看着能点。

**冲突处理**：开发中发现设计做不了（需要的数据 SDK 拿不到、某个状态 Workflow 不发事件）时，回到 5.3 改设计、带更新后的原型重过 5.5 确认；***禁止静默改设计继续往下做***。三种消息语义各走专属通道：对话走 `sdk.chat`、业务进度走 business 事件与查询面、过程观察仅限调试——细则以脚手架 `docs/message-guide.md` 为准。提交报文按用户实际填写组织：未填写的可选字段直接省略即可——入口映射会跳过缺失字段，必填由路线 `input_schema` 的 `required` 裁决（见 S2-8.1）。***同时消费入口提交的拒绝报文***：`status="rejected"` 时呈现 `field_errors` 并允许修正——被拒却仍显示提交成功，是最难排查的一类假象。业务阶段状态在共享协调层只建立一次 `onBusinessEvent` 订阅，三类批次使用同一纯归约器；订阅后对当前 Runtime 读取一次快照，由 SDK 负责排序、去重、缺口补拉和回放。禁止使用定时器、事件回调查询或 `getBusinessEvents` 轮询状态；Runtime 终态、表单握手和 Delivery Review 仍是各自领域的权威事实。

最终交付必须按 [业务界面设计方法论](../references/业务界面设计方法论.md) 的固定契约处理：`runtime.delivery_ready` 由 Runtime 自动发布，`delivery.review` 通过既有 Business Call 三次握手完成；业务代码使用当前模板导出的 `isRuntimeDeliveryReadyEvent`、`isDeliveryReviewCall` 及对应常量识别两条通道，不手写协议判断或修改固定 SDK。事件和 Call 未通过守卫时分别降级为普通业务提示和普通 Call，不得当作交付渲染。`PublicDelivery.output.display` 按 `schema_version/headline/facts/notices/sections` 的标准结构渲染主标题、事实、提醒和正文；文件只把 `workspace_path` 交给 `sdk.file.*`，`output_paths` 仅作结果字段归属标签。`delivery.*` 是平台保留表单命名空间，不另造协议或静态表单 Schema；`call.formId` 与 `call.arguments` 同级，不存在额外 `interaction` 包装层。当前模板缺少这些 Delivery 守卫、Business `onCall/pending/reply` 或文件能力时，记录具体缺口并裁决为 `platform_blocked`，不得在业务代码中补造兼容层。

（呈现补充，不改变上段的守卫与文件纪律：上段对 `output.display` 的四区块渲染要求适用于**兜底出口**；定制界面按第 3 节直接消费 `output` 业务字段做贴业务呈现，display 的渲染规范以脚手架仓当前文档为准。）

### 6.3 动态 Playwright 验收门

正式业务代码完成且演示内容清理后，必须按当前模板 `docs/dev-host-testing.md` 执行动态浏览器验收。***基础冒烟通过不代表业务表单通过***：Agent 必须读取本次界面的真实路由、`schema/forms/` 与 `schema/orchestrations/`，为当前页面动态编写 Playwright 用例；禁止复制 Demo 字段或选择器，禁止为了通用测试要求业务页面增加 `data-goalfy-*` 等专用 DOM 标记或测试 Schema 字段。

执行顺序固定为：

1. 建立本次表单覆盖表：除平台保留的 `delivery.*` 外，每个业务表单都标明它作为入口、服务端调起或两者兼有的每条实际路径、对应路由和验收用例；没有可达页面或调用路径时先修正实现，不得静默漏测。
2. 做环境预检：当前模板必须提供 `test:e2e:external` 与 Dev Host 测试指南；若模板身份已变化则按 6.1 重新下载复核。已有 `GOALFY_DEV_EXTERNAL_MOCK_URL` 时连接该 Mock；否则只使用环境提供的 `GOALFY_DEV_MOCK_BACKEND_DIR` 或模板默认相邻目录启动 Max Mock。不得在源码或 Skill 中写死本机绝对路径、主机或端口。依赖尚未安装时按当前锁文件安装；Playwright 缺少浏览器运行时时，只安装当前测试所需的 Chromium，不修改业务依赖。
3. 动态用例至少覆盖：每个业务表单的每种实际调用模式各完成一次合法填写和提交；入口模式检查受理与页面状态变化；服务端调起模式经真实 `business.pushCall` 到达、填写并回复；适用的必填、枚举、数字、文件、图片、数组和复杂控件；存在可填顶层字符串字段时至少一次 `FAIL` 服务端失败回显。没有兼容字段时不得伪造字段来触发 `FAIL`，改用该表单真实可达的校验或错误路径并记录边界。
4. 运行 `npm run test:e2e:external`，同时检查命令回执、transcript 和浏览器可见结果；断言页面无未处理异常、无原始 JSON 或内部字段直出。测试失败必须在同一源码上修复并重跑；基础冒烟、HTTP 200 或 iframe 可见均不能替代页面专属用例通过。
5. 把最终命令、覆盖的路由与表单、关键 `requestId`、三层断言和结果写入工单；在结果检查表的对应前端校验项追加本地证据但保持 `pending`，留待 S4 用真实运行数据闭合，不得因 Mock 通过提前置为 `passed`。不得记录 token。业务代码、Schema、路由或 Mock 契约变化后，受影响用例必须重跑。

当前官方模板确认缺少上述脚本、控制链路或动态用例运行能力时，按既有模板修复纪律重试，仍缺失才裁决为 `platform_blocked`。仅本机缺少 Max Mock 源码或可访问服务、Go、Node 或浏览器运行时，属于执行环境 `blocked`，必须准确记录缺项并停止打包部署，不能冒充平台缺陷，也不能静默回退内置 Mock。

正式打包前，先做一轮完成后优化：`/impeccable harden`（错误处理、文本溢出、边界情况）→ `/impeccable audit` → `/impeccable polish`（出货就绪）；优化产生的修改受硬约束与已冻结契约约束，做完重跑上面的自查两件事。随后：

1. 移除演示页面、演示路由、演示契约和占位文案（原型阶段以 `import.meta.env.DEV` 判据注入的演示数据不算残留，但不得进入生产构建路径）；
2. 执行模板当前要求的 `npm run check`，再完成 6.3 的动态 Playwright 验收门；
3. 动态用例全部通过后执行 `npm run check:release`；除非当前模板明确改变流程，不在本地执行独立 build 或发布；
4. 验证主路径、权限变化、空态、错误、刷新恢复和契约漂移等关键边界；
5. 打包源码，校验归档清单、字节数和摘要。

macOS 环境中，解压后必须清理 `._*`、`.DS_Store` 和 `__MACOSX`；打包时使用 `COPYFILE_DISABLE=1` 并重新核对归档清单。AppleDouble 旁车文件含二进制内容，测试框架可能将其误识别为源码或测试文件并触发 `[PARSE_ERROR]`。出现此类解析错误时，先检查归档元数据残留，不得因此修改模板固定层或跳过测试。

## 7. 部署与验收

**部署顺序**：业务界面部署是草稿行上的**最后一步内容动作**。正确顺序：先完成编排修改（`publish_mode=staged`）→ 在**同一草稿行**上部署业务界面 → 最后上线该草稿。部署完成后再修改编排会派生新草稿行，源码包随行继承（`has_ui: true`），但**部署激活地址不继承**（`entry_url` 为空字符串），界面地址丢失，必须在新草稿上重新部署。上线前反读确认 `entry_url` 非空。

完成打包后，依次执行源码包上传、部署、终态查询和绑定结果反读。部署达到成功终态后，按 [业务界面验收检查清单](../checklists/业务界面验收检查清单.md) 执行验收。

**交付门**：

- 运行契约发生变化时，重新执行契约冻结、受影响回归和部署验收；
- 宿主能力不支持目标 Workflow 运行契约时，先按约束 8 复核并重试已有能力；确认仍不支持后记录业务界面平台阻断，并停止业务界面发布、场景包上线和工单结单。只有开发者明确修改总体 Plan、移除业务界面交付后，才按新范围继续；
- 未取得部署成功终态和绑定反读证据时，不得宣称业务界面已交付。

## 8. 出口条件

以下全部满足后，按路由器 4.1 进入 S4：

- 部署达到成功终态，绑定结果反读证据在案；
- `npm run check:release` 通过；
- 最终源码对应的动态 Playwright 页面专属用例全部通过，表单覆盖表无遗漏，证据已写入工单；
- 前端校验项已转入结果检查表（状态 `pending`，S4 闭合）。

以上全部满足后，按路由器 6.1 落一条 `stage_exit` 账，再进入下一阶段。
